## 三、关键过程：两次失败与修正

拆分并非一次成功。两次编译失败都发生在 S4，如实记录以保证可复现。

### 3.1 第一次：辅助函数跨编译单元不可见（8 个错误）

首次构建 `build exit=2`，8 条错误全部指向同一个文件：

```
Collision_Proxy/core/事件交互.cpp(75/91/107/129/145/161/191): error C3861: "text_read": 找不到标识符
Collision_Proxy/core/事件交互.cpp(197):                     error C3861: "number_read": 找不到标识符
```

**根因**：计划 3.1 的归组依据是「`text_read` 只服务 `region_boundary_set` / `config_apply`；`number_read` / `vector_read` 只服务 `collider_config_apply`」，但实测发现 **`event_process` 也在使用 `text_read`（7 处）与 `number_read`（1 处）**——这两个辅助的使用者横跨 `空间边界与配置.cpp`、`碰撞体配置.cpp`、`事件交互.cpp` 三个编译单元。它们位于匿名命名空间（内部链接），跨 TU 不可见。

**处理**：遵循计划既定原则「**优先挪函数，不提高辅助可见性**」——三个使用者无法并入同一单元（各自还承载大量其他函数），故为 `事件交互.cpp` 补上属于它自己的一份 `text_read` + `number_read`（仍置于匿名命名空间内，保持内部链接）。辅助文本由脚本从已生成的兄弟文件中原样提取，不手抄。

### 3.2 第二次：插入块缺少匿名命名空间闭合（6 个错误）

修补后重建仍 `build exit=2`：

```
Collision_Proxy/core/事件交互.cpp(33):  error C2888: "void engine::Collision_Proxy::attach(void)": 不能在命名空间"anonymous-namespace"内定义符号
Collision_Proxy/core/事件交互.cpp(44):  error C2888: "engine::Collision_Proxy::attach::<lambda_1>": ...
Collision_Proxy/core/事件交互.cpp(71):  error C2888: ... event_process ...
Collision_Proxy/core/事件交互.cpp(249): error C2888: ... event_publish ...
Collision_Proxy/core/事件交互.cpp(5):   fatal error C1075: "{": 未找到匹配令牌
```

**根因**：插入辅助时只带了 `namespace {` 与函数体，**漏掉匿名命名空间的闭合 `}`**，导致其后 `attach` / `event_process` / `event_publish` 全被卷进匿名命名空间。

**处理**：放弃增量修补，改为**修正生成脚本后整批重跑**——脚本增加「原文件不在工作区时从 `HEAD` 取回原文」的能力，把 `text_read` ＋ `number_read` ＋ 闭合 `}` 一并纳入 `事件交互.cpp` 的分组定义，一次性重生成全部 9 个文件（并重跑覆盖自检）。此后构建一次通过。

> 事后看，从脚本层整体重生成比手工补丁更稳：9 个文件与生成逻辑保持一一对应，第四节的归属表即脚本里的分组定义。

## 六、偏差与说明

### 6.1 `形状构建.cpp` 306 行，未按计划挪动（计划授权的偏差项）

计划 3.2 对 `形状构建.cpp` 的预估是 ~290 行，实际 **306 行**，超出「300 行以上需在相邻分组间挪动一到两个函数」的调整线 6 行。**本次没有挪动**，理由如下：

- 该文件的 5 个函数构成一条不可分割的调用链：`memory_malloc`（匿名模板）被 `mesh_shape_build` 与 `shape_build` **共用**；`mesh_shape_build` 又被 `boundary_build`（在 `空间与边界.cpp`）与 `shape_build` 调用。
- `memory_malloc` 位于匿名命名空间（内部链接），既不能提到头文件（会改 `.h`，违反不变量 1），也不能改成具名命名空间（会**新增外部符号**，违反验收标准 3）。因此它必须与 `shape_build` 同文件，`mesh_shape_build` 也跟着必须留在同一单元。
- 真正可外移的只有三个几何字段读取辅助（`scalar_read` / `vector_read` / `quaternion_read`，合计 60 行）。但：
  - 移入 `碰撞体管理.cpp`（279 行）→ **339 行，接收方反而越界**；
  - 移入 `检测执行.cpp`（174 行）→ 234 行，行数达标但**语义错位**（该文件是扫描式碰撞检测，与几何字段解析无关）；
  - 只移其中一个（如 `scalar_read`，18 行）虽恰好让双方落线，却会把三个同源辅助**割裂到两个单元**，损害内聚。
- **结论**：306 行相对原 839 行已达成拆分的全部目的（单文件规模下降 63%），且是当前分组原则下唯一「不损害内聚、不触碰符号集」的选择。此处按「技术判断优先于形式指标」处理，并把偏差摆在明处：**超出计划上限 6 行（2%）**，供你复核。

### 6.2 告警：C4715 / C4828 逐条一致，C4005 增量有完整解释

| 告警 | 基线 | 本次 | 判定 |
| --- | --- | --- | --- |
| C4715（并非所有控件路径都返回值） | 3 | 3 | **逐条相同** |
| C4828（文件含非法字符） | 2 | 2 | **逐条相同** |
| C4005（`APIENTRY` 重定义） | 12 | 19 | 增量 +7，**由拆分本身解释**，非新增问题 |

- C4715 / C4828 的具体来源在两次构建中**完全一致**：`external/bullet3/…/btGImpactShape.h(1)` ×2、`Quadtree/core/区块信息检索.hpp(72)` ×2、`Event_Broker/core/事件中转器.cpp(221)` ×1 —— 全部落在外部库与无关模块，与碰撞两模块无关。
- C4005 的来源也完全一致：全部是 `Windows Kits/…/minwindef.h(130)` 与 `external/glfw/GLFW/glfw3.h(123)` 的 `APIENTRY` 重定义（两次构建中 `minwindef.h(130)` 的出现次数分别等于各自 C4005 计数：12 与 19）。
- 增量 7 的来源：**该警告每个编译单元各报一次**（凡同时包含 Windows 头与 glfw 头的 TU 都会触发）。碰撞模块由 2 个编译单元变为 9 个（+7），全项目编译单元由 **120 → 127**（+7），C4005 恰好由 **12 → 19**（+7）。三者一一对应，无残余项。
- 判定：**无新增告警种类、无新增告警来源，仅有既知同源告警随编译单元数线性放大**。

### 6.3 计划事实项的一处修正：辅助的使用者跨越三个文件

计划「二、已确认事实」记「`text_read` 仅服务 `region_boundary_set` / `config_apply`」，实测不成立——`event_process` 也在使用它（7 处），`number_read` 同理（1 处）。这不是理解偏差，而是**事实层面的遗漏**；发现过程与处置见第三节 3.1，此处仅标注计划文本需据此更正。

处置结果符合计划的既定原则序（先挪函数；行不通则不提高辅助可见性）：辅助仍是匿名命名空间内的内部链接实体，未新增任何外部符号——这一点由 S6 的零差异直接证明。

### 6.4 最小 include 的实际分布

计划 3.3 要求「每个新 `.cpp` 顶部只加最小 include 集」。实际分布：

- `网格加载器.h`：1 个单元（`形状构建`，供 `mesh_shape_build` 使用）。

按「谁用谁 include」逐文件判定，未出现整套复制的情况；两次构建失败（第三节）均与 include 无关。
