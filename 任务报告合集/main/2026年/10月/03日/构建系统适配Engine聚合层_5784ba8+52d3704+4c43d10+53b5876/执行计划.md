## 二、目标架构

### 2.1 目录布局

```
白银纪元/                                   ← 项目根
├── CMakeLists.txt                          ← 顶层编排（见 §4 待裁定 D6）
├── CMakeSettings.json
├── .gitignore
├── Engine/                                 ← 聚合层 Engine（真正的 CMake 层）
│   ├── CMakeLists.txt                      ← 聚合层构建脚本（不编源码，只聚合＋导出合并头快照）
│   ├── cmake/
│   │   ├── 对外接口.cmake                   ← BYJY_ENGINE_*：聚合 EngineCore＋EngineSystem
│   │   └── 接入下层.cmake                   ← 通用接入函数（扩展为多库）
│   ├── EngineCore/                         ← 原 Engine 层（独立仓库）
│   │   ├── CMakeLists.txt
│   │   ├── cmake/{对外接口,接入下层,导出头快照,ar_rsp_bom}.cmake/ps1
│   │   ├── common/  src/  external/  CMakeSettings.json  README.md
│   └── EngineSystem/                       ← 原 System 层（独立仓库）
│       ├── CMakeLists.txt
│       ├── cmake/{对外接口,接入下层}.cmake
│       ├── common/  src/  external/  assets/  CMakeSettings.json  README.md
└── Application/                            ← 应用层目录
    ├── Test/                               ← 原 Test 层（独立仓库）
    │   ├── CMakeLists.txt
    │   ├── cmake/{对外接口,接入下层}.cmake
    │   └── external/  src/  assets/
    └── Game/                               ← 原 Game 层（独立仓库）
        ├── CMakeLists.txt
        └── cmake/{对外接口,接入下层}.cmake
```

### 2.2 依赖链与构建顺序

```
EngineCore  →  EngineSystem  →  Engine(聚合)  →  { Application/Game, Application/Test }
（最底，无下层）   （依赖 Core）    （聚合 Core+System）   （只接 Engine 一层）
```

构建顺序（严格串行，每层一次性配置＋构建）：

```
1) Engine/EngineCore      → EngineCore/out/build/<cfg>/lib/EngineCore.lib
2) Engine/EngineSystem    → Engine/EngineSystem/out/build/<cfg>/lib/EngineSystem.lib
3) Engine                 → Engine/out/build/<cfg>/include/**（合并头快照）+ 聚合对外面
4) Application/Game       → GameCore.lib
5) Application/Test       → EngineTests.exe（唯一可执行产物）
```

### 2.3 包含路径方案（任务<2> 落地形态）

**统一规则：项目内部一切跨层包含一律写「项目根相对全路径」；各层自身的包含根一律收敛为项目根。第三方头保持原样（`<nlohmann/json.hpp>`、`<GLFW/glfw3.h>`、`<sol/sol.hpp>`、bullet3 等）。**

| 位置 | 现状 | 目标 |
| --- | --- | --- |
| EngineCore 内部头 | `#include "common/前置头文件包含.h"`、`#include "src/tools/Detail/哈希混合.h"` | `#include "Engine/EngineCore/common/前置头文件包含.h"`、`#include "Engine/EngineCore/src/tools/Detail/哈希混合.h"` |
| EngineCore 公共头 `common/引擎.h` | `#include "src/core/event/事件系统运行包.h"` | `#include "Engine/EngineCore/src/core/event/事件系统运行包.h"` |
| EngineSystem 头中引引擎 | `#include "src/core/object/Object/对象.h"`、`#include "common/前置头文件包含.h"` | `#include "Engine/EngineCore/src/core/object/Object/对象.h"`、`#include "Engine/EngineCore/common/前置头文件包含.h"` |

| EngineSystem 相对跨层 | `common/前置头文件包含.h` 内 `#include "../../引擎层/common/前置头文件包含.h"` | `#include "Engine/EngineCore/common/前置头文件包含.h"` |
| Application/Test 引引擎 | `#include "src/core/..."` | `#include "Engine/EngineCore/src/..."` |

| Application/Game | 暂无源码 | —（预置 `Application/Game/...` 前缀规则） |

> **包含根顺序约束（关键）**：Application/Test 与 Application/Game 的编译包含根为
> `[ <Engine 构建目录>/include（快照，置前） , <项目根>（供 Application/** 自身头） ]`。
> 快照根必须排在项目根之前，否则 `Engine/...` 会命中源码树、绕过快照，重新引入「新头配旧库」风险。
> 该顺序在阶段 E 用 `compile_commands.json` 的 `-I` 次序实测确认。

**各层包含根的最终形态**

| 层 | 编译期包含根（PRIVATE，供自身源码） | 对外包含根（INTERFACE，供上层） |
| --- | --- | --- |
| EngineCore | 项目根 | 项目根 ＋ 三个第三方目录 |
| EngineSystem | 项目根 | 项目根 ＋ Sol2/Lua ＋ 并入的 EngineCore 面 |
| Engine（聚合） | 项目根（无源码编译） | 项目根 ＋ 并入的 EngineSystem 面（含 EngineCore 面） |
| Application/Game | 项目根 ＋ Game 根自身 | 项目根 ＋ Game 根 |
| Application/Test | 项目根 ＋ Test 根自身 | 项目根 ＋ Test 根 |

第三方面（保持绝对路径、不参与快照）：`Engine/EngineCore/external/Json`、`.../glfw`、`.../bullet3/src`、`EngineSystem/external/Sol2/include`、`.../external/Lua`。

## 三、四项任务的实现方案

### 任务<1> CMake 与 VS 增删文件同步

保留 `GLOB_RECURSE CONFIGURE_DEPENDS`，**新增目录级配置依赖登记**，让「目录内容变化」也能触发重新配置：

1. 在各层 CMakeLists 收集完 GLOB 后，对每个被 GLOB 的**源根目录**执行
   `set_property(DIRECTORY APPEND PROPERTY CMAKE_CONFIGURE_DEPENDS <目录>)`
   （目录 mtime 变化 = 增删文件；Ninja 把该目录登记为 `build.ninja` 的依赖，构建前自动重跑配置，从而重扫 GLOB）。
2. 顶层与各层 `CMakeSettings.json` 增加说明性配置项，保持 `Ninja` 生成器（VS 的 CMake 集成始终走同一配置）。
3. 清理陈旧 IDE 缓存：删除 `.vs/游戏引擎*`、`.vs/引擎层*`、各层 `.vs/引擎层*` 等按旧目录名生成的缓存（一次性；重开文件夹后由 VS 重建）。
4. 若复核后仍出现「VS 目录视图」滞后（VS 侧不读目录级 configureDepends），**回退方案**为把该层切换为显式源清单（见 §4 D4）——需你届时拍板。

**验收**：删除/改名一个 `.cpp` 后不加任何手动操作，直接构建成功且 VS 视图无旧文件；新增一个 `.cpp` 后直接构建即被编入。

### 任务<2> 引擎对外包含前缀 `Engine/`

1. `EngineCore/cmake/对外接口.cmake`：`BYJY_ENGINE_CORE_OUT_INC` 的首项由 `<EngineCore 根>` 改为**项目根**（`${BYJY_ENGINE_CORE_ROOT}/../..`）；第三方三项不变。
2. 按 §2.3 表**全量改写 include 语句**：
   - EngineCore：约 92 处 / 60 文件（内部互引）；
   - EngineSystem：约 68 处 / 21 文件（引引擎 ＋ 引自身）；
   - Application/Test：约 51 处 / 32 文件（引引擎、引系统）；
   - Application/Game：无源码，无改动。
3. 各层 CMakeLists 的 `target_include_directories` 同步改为项目根。
4. 头快照镜像范围改为「项目根相对」，快照内落地为 `<快照根>/Engine/EngineCore/**`、`<快照根>/Engine/EngineSystem/**`。

### 任务<3> 各层 CMake 适配新架构

1. **顶层 `CMakeLists.txt`：删除**（用户裁定 D6）。顶层不再 `add_subdirectory` 任何层；`README.md` 改写为「按 §2.2 顺序逐层独立构建」的命令清单。
2. `EngineCore/CMakeLists.txt`：`project(EngineCore)`；GLOB 与包含根路径更新；快照 `MIRROR_DIRS` 前缀化；目录级 configureDepends 登记；产物仍为 `EngineCore.lib`。
3. `EngineSystem/CMakeLists.txt`（由原 System 层迁移）：`project(EngineSystem)`；**目标与产物由 `SystemCore` 改名 `EngineSystem`**；`接入下层` 目标改为 `EngineCore`，接口文件路径 `../EngineCore/cmake/对外接口.cmake`；快照/包含根更新；无自身头快照（其消费方仅聚合层，聚合层不编译）。
4. **新增 `Engine/CMakeLists.txt`**（聚合层）：
   - `project(Engine)`；`接入` EngineSystem 的对外接口（连带 EngineCore 面）；
   - 不编任何源码、不产出静态库；
   - 新增常驻目标，把 `Engine/EngineCore/**` 与 `Engine/EngineSystem/**` 的头**合并镜像**到 `<Engine 构建目录>/include/Engine/{EngineCore,EngineSystem}/**`（复用 `导出头快照.cmake`）。

### 任务<4> 层间静态依赖（保留并扩展接口机制）

保留「配置期定位预编译 `.lib` ＋ IMPORTED 目标」主干，作**最小必要扩展**以承载聚合层：

1. **契约扩展**（五变量 → 七变量，向后兼容）：
   - `BYJY_<P>_OUT_LIB` 允许为**分号分隔的库名列表**（聚合层转发多个库；非聚合层仍为单元素）；
   - 新增 `BYJY_<P>_OUT_LIBDIR`：与 `OUT_LIB` **一一对应**的「该库所在层目录」，用于自动探测 `out/build/*/lib/<库名>.lib`（缺省 = 本层目录）。
2. `byjy_jieru_xiaceng()` 扩展：按 `OUT_LIB` × `OUT_LIBDIR` 逐对定位并建立 IMPORTED 目标；对每个目标仍实现「①覆盖变量优先 → ②自动探测最新 → ③硬失败，绝不回退编源码」。
3. 头快照切换：
   - EngineSystem 编译时：`项目根 → <EngineCore 构建目录>/include`（EngineCore 单层快照）；
   - Application/Game、Application/Test 编译时：`项目根 → <Engine 构建目录>/include`（聚合合并快照，单根，避免多根并集）；
   - 移除 System 层原有的自身头快照（无人消费）。
4. **不改动**：绝不把下层源码 `add_subdirectory` 进上层构建树；上层一律只链接已构建 `.lib`。

## 八、风险与回滚

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 全量 include 改写量大（~113 文件） | 个别漏改导致编译失败 | 分阶段编译，逐层收割错误；用检索确保 `src/`、`common/` 跨层引用归零 |
| GLOB 与 VS 视图刷新仍不达标（D4） | 任务<1> 未根治 | 回退显式源清单；本阶段先交付目录级 configureDepends |
| 聚合层合并头快照与子层构建不同步 | 新头配旧库 | 强制按 §2.2 顺序构建；聚合层构建时校验子层库与快照存在，缺失即硬失败 |
| 四层独立仓库的提交/推送口径 | 漏推或推错分支 | 提交前逐仓库 `git status` 核对；按远端分支名显式 refspec（`main:engine` 等）——阶段 G 前与你确认（D12） |
| 应用层自身包含根与快照根的先后次序被 CMake 重排 | 快照被源码树旁路 | 阶段 E 用 `compile_commands.json` 实测 `-I` 次序；不达标则改用「应用层自身头也做快照根」的方案 |

**回滚**：本阶段所有改动集中在构建脚本与 include 路径；如整体不达预期，可按层 `git checkout -- .` 回退（各层为独立仓库，互不影响），目录搬迁可反向 `Move-Item` 复原。
