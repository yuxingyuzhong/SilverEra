## 一、渲染层定位与边界

### 1.1 在工程五层结构中的位置

```
EngineCore.lib ──▶ (EngineSystem.lib ──▶ Engine 聚合面 ──▶ Application/{Test,Game})
      │
      └──────────▶ Application/Renderer ──▶ RendererCore.lib
                   （只接 EngineCore 单层）
```

渲染层是「应用层的一个并列子层」，与 `Test` / `Game` / `Editor` 平级；它**不是**引擎聚合面的下游，而是与聚合面并列、各自直接消费 `EngineCore.lib`。

这一点已在 `d34da1c` 落地并被 `cmake/对外接口.cmake` 的首行 `include` 固化：

```cmake
include("${CMAKE_CURRENT_LIST_DIR}/../../../Engine/EngineCore/cmake/对外接口.cmake")
```

**为什么只接 EngineCore**（已与你确认的口径，此处记录理由以备后续回溯）：渲染层与实体 / 属性 / 效应（`EngineSystem`）没有任何关系，公共头里也不会出现 `EngineSystem` 的类型。接 `Engine` 聚合面只会把 `EngineSystem.lib` 变成渲染层的链接依赖，放大耦合，并让「`EngineSystem` 未跟进 `EngineCore` 重构」这类下层问题直接堵死渲染层构建。该决策**完全可逆**：将来真要用到实体 / 属性 / 效应时，把 `include` 目标换回聚合面、并同步 `CMakeLists.txt` 第 1 节的库映射即可。

### 1.2 渲染层的职责（做什么）

| 编号 | 职责 | 说明 |
| --- | --- | --- |
| R1 | **GPU 设备管理** | Vulkan 实例、校验层、物理设备选取、逻辑设备与队列；失败时干净回退 |
| R2 | **平台与呈现** | SDL3 窗口与事件泵、`VkSurfaceKHR`、交换链（创建 / 重建 / 呈现模式选择） |
| R3 | **内存与资源** | VMA 分配器封装、缓冲与图像的创建 / 上传 / 销毁、延迟销毁队列 |
| R4 | **帧编排与同步** | 帧槽（命令池 / 命令缓冲 / 栅栏 / 信号量）、提交与呈现、在途帧重叠 |
| R5 | **绘制** | 着色器模块、图形管线（动态渲染）、描述符、索引 / 顶点绘制 |
| R6 | **渲染层自有的最小配置与日志** | 复用 EngineCore 的 `Log` 与 `Engine_Env`，不自建 |

### 1.3 渲染层的非职责（不做什么）

| 编号 | 不做 | 归属 |
| --- | --- | --- |
| N1 | 不做窗口内的 UI（ImGui 等） | 现由 `Application/Test` 自持；长期见 §1.4 |
| N2 | 不做场景图 / 材质系统 / 资源热重载 | 后续轮次（`Scene/`、`Mesh/`），本轮不设计 |
| N3 | 不产出可执行文件 | 层级契约：全项目唯一可执行文件是 `EngineTests.exe`（Test 层） |
| N4 | 不管物理、碰撞、空间分区 | `EngineCore` |
| N5 | 不接管逻辑帧推进 | `EngineCore` 的 `Engine_Env`（`logic_frames_get` / `frame_tick`） |
| N6 | 不在层外暴露 SDL3 / VMA 类型 | 见 §4.1 |

### 1.4 与现有 OpenGL 路径的关系（重要，需你知晓）

**当前工程里已经存在一条图形路径**，与本层并行：

| 事实 | 证据 |
| --- | --- |
| `Application/Test` 有一个图形化「测试选择窗口」 | `src/主调/图形选择窗口.cpp/.h` |
| 它走 **glfw + glad(OpenGL 3) + Dear ImGui** | 同上；`Test/external/{glad,Dear_ImGui}` |
| `EngineCore` 的对外面已携带 glfw 与 OpenGL 相关项 | `Engine/EngineCore/cmake/对外接口.cmake`：`OUT_LINK=glfw3.lib`、`OUT_DEF=GLFW_STATIC`、`OUT_SYS` 含 `opengl32;gdi32` |
| `EngineCore` 自身源码**不使用** glfw | 全层 grep 仅命中 README / CMake / 对外接口 / external 头 |

也就是说：**glfw 是「为 Test 的 ImGui 选择窗口而挂在上层面上的」**，与引擎核心逻辑无关。

渲染层与它的关系，我建议分两阶段：

- **近期（Phase 2~9）：两条路径并存、互不干扰。**
  测试选择窗口是「启动期的用例挑选 UI」，渲染用例是「被选中后运行的用例」，二者不在同一次运行里争用窗口与消息泵。
  渲染层**引入 SDL3，不引入 glfw**：SDL3 已覆盖窗口 / 输入 / 平台与 Vulkan 表面所需的全部能力，再拉一套窗口库只会放大依赖面与符号冲突风险。
- **长期（Phase 10 及以后）：若确实需要「同一窗口内既渲染又出 UI」，再评估迁移。**
  可行路线是让 ImGui 走 Vulkan 后端（`imgui_impl_vulkan`）并把该后端编入渲染层，由渲染层提供 `ui_draw` 入口；`glfw/glad` 届时退役。**本轮不承诺、不设计。**

### 1.5 与 Test / Game / Editor 的关系

| 层 | 与渲染层的关系 | 当前状态 |
| --- | --- | --- |
| `Application/Test` | **首个消费方**：加渲染用例，链接 `RendererCore.lib`；`EngineTests.exe` 是渲染层唯一的运行载体 | 尚未接线（Phase 2 起处理） |

## 二、技术选型与理由

### 2.1 为什么是 Vulkan（而不是继续 OpenGL）

| 维度 | 说明 |
| --- | --- |
| 工程定位 | 项目是「自研引擎」，GL 的隐式全局状态机与驱动替你做的决策，恰恰是引擎层最该显式掌控的部分 |
| 显式资源管理 | Vulkan 要求显式描述内存、同步、生命周期——这正是「引擎」相对「应用」的价值所在 |
| 现代特性 | 动态渲染、同步 2、时间线信号量、`VK_EXT_shader_object` 等，后续可按需启用 |
| 代价（必须承认） | 样板代码量远大于 GL；一个「能清屏的窗口」需要约 700~1000 行。这些代价在 Phase 5 之前必须付出，无法跳过 |

> **已配置环境**：本机 `C:\VulkanSDK\1.4.363.0`，探测口径收口在 `cmake/VulkanSDK探测.cmake`（优先环境变量 `VULKAN_SDK`，未设则回退 `C:/VulkanSDK/<版本最大者>`，都没有则硬失败）。

### 2.2 为什么是 SDL3（而不是 glfw）

| 维度 | SDL3 | glfw |
| --- | --- | --- |
| Vulkan 表面 | `SDL_Vulkan_CreateSurface` 直出 `VkSurfaceKHR`，且给出实例扩展清单 | 需 `glfwCreateWindowSurface`，能力等价 |
| 与现有工程 | 已备于 `external/`（`SDL2` 目录实为 3.4.18，`d34da1c` 已改名 `SDL3` 并就地裁剪） | 已由 EngineCore 对外面携带（为 Test 的 ImGui 用） |
| 输入 / 事件 / 平台 | 覆盖更广（输入设备、剪贴板、计时、多平台） | 仅窗口 + 输入 |
| 引入代价 | 已支付（236 个编译单元，已编入 `RendererCore`） | 若引入则出现两套窗口库 |

结论：渲染层用 SDL3；glfw 维持在 EngineCore 对外面上不动（Test 继续用），两条路径互不引用。

### 2.3 为什么是 VMA

Vulkan 原生内存管理需要应用自行处理内存类型选择、子分配、映射与对齐。VMA 是 Khronos 官方维护的子分配器，header-only，只需一个编译单元定义 `VMA_IMPLEMENTATION`——`d34da1c` 已落地该单元（当前位于 `src/render/Renderer/core/VMA实现.cpp`，Phase 3 建议迁入 `Memory/core/`，见 §3.1）。

VMA 与「直接用 `vkAllocateMemory`」相比的收益：`VMA_MEMORY_USAGE_AUTO` 让「缓冲区 / 图像的一次性分配」无需手工挑内存类型；对后续「上传环」「描述符缓冲池」等复用型分配也有现成设施。

### 2.4 着色器流程选型

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 离线编译 + 运行时加载 `.spv` | 构建期用 Vulkan SDK 自带的 `glslc.exe` 把 `.vert/.frag` 编成 `.spv`；运行时读文件 | **推荐** |
| B. 运行时用 libshaderc 编译 GLSL | 无需构建期工具，但要引入 shaderc 依赖并把编译器塞进产品 | 不采用（依赖面过大） |
| C. `VK_EXT_shader_object` 直接给 SPIR-V | 免管线对象，更灵活 | 后续可选优化，不作为起步方案（驱动支持面 + 学习成本） |

方案 A 的落点：源着色器放 `Application/Renderer/assets/shaders/`，构建期输出到 `<渲染层构建树>/shaders/`；**产物不入库**（沿用工程「生成物不入库」的习惯）。找不到 `glslc.exe` 时只告警不硬失败（不影响本层静态库构建，但依赖着色器的用例会失败）。着色器目录由调用方通过 `Renderer_Config::shader_dir` 指定（渲染层是库，不能假定 exe 位置；Test 层按既有习惯用 `Application/Renderer/out/build/x64-<类型>/shaders/` 定位并拷到自己的输出目录）。

### 2.5 数学库选型（**已定：引入 glm**）

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| **重新引入 `glm` 到本层 `external/`** | 成熟、与教程生态一致，出错概率最低 | **✅ 已定（2026-10-10 用户拍板）** |
| 自建渲染层 `Math` 模块 | `Vec2/Vec3/Vec4/Mat4/Quat` ＋ 透视 / 正交 / 视图矩阵 | 不采用（与用户决定相反，记录备查） |
| 复用 `bullet3` 线性数学 | `btVector3/btTransform/btMatrix3x3` 已在 EngineCore 对外面上 | 不采用：把「渲染 → 物理」写成依赖，语义错位 |

**落地口径（Phase 8 执行）**：

1. **放置位置**：`Application/Renderer/external/glm/`（与 `src/` 平级，符合《外部库引入约束》<1>）。
2. **目录形态**：沿用工程内**既有**的 `glm` 摊平形态 —— `Engine/EngineSystem/external/glm/` 就是把 `glm/` 子目录的内容直接摊在 `external/glm/` 下（432 文件 / 2.18 MB，含 `glm.hpp`、`vec3.hpp`、`detail/`、`gtc/`、`gtx/`、`ext/`、`simd/`）。**必须拷贝至本层，不得用投影文件夹或 `add_subdirectory` 绑定别处**（《外部库引入约束》<2>）。
3. **包含方式**：本层 PRIVATE 包含根增加 `${本层根}/external`，代码写 `#include <glm/glm.hpp>` —— 与 EngineSystem 现有写法一致（EngineCore 的对外面里也把 `${本层根}/external` 作为包含根，两者同源）。glm 只在 `.cpp` 内包含，**不进公共头**，故该包含根留在 PRIVATE。
4. **Vulkan 适配宏**：`GLM_FORCE_DEPTH_ZERO_TO_ONE`（深度范围 `[0,1]`，见 K1）与 `GLM_FORCE_RADIANS` 由本层编译定义给出，**不在公共头里给**（否则污染上层）。
5. **来源核对**：本地已存在两处可用来源 —— `Engine/EngineSystem/external/glm/`（工程内已裁剪副本）与 `D:\rely\glm-master`（glm **1.1.0** 原始发布包，1673 文件 / 20.61 MB）。落地时以工程内那份为基准，并与原始发布包比对版本号后记录进本层 README。
6. **已知形态风险**：glm 摊平后 `external/` 会同时成为「SDL3 的父目录」与「glm 的包含根」。`#include <glm/...>` 与 `#include <SDL3/...>`（无人会这么写）不冲突，但**不得**把 `external/` 提升为 PUBLIC 包含根 —— 那会把 glm 暴露给上层。

> **重复拷贝的取舍**：本层自带一份 glm 后，工程内会出现第二份 glm（`EngineSystem` 也有一份）。这是「每层是独立 git 仓库、层间只通过已构建静态库交接」这条硬约定的必然代价 —— 本层不能去引用 `EngineSystem/external/glm`（那是别层的目录，且渲染层根本不依赖 EngineSystem）。**备选**：把 glm 恢复到 `EngineCore/external/glm`，由渲染层透传获得（工程内只留一份）；但这会让 EngineCore 重新携带一个它自己不使用的依赖，与它当初移除 glm 的决定相悖，故不作首选。

### 3.2 各模块职责与拥有的 Vulkan 对象

| 模块 | 一句话职责 | 拥有的对象（创建 / 销毁） |
| --- | --- | --- |

| `Device` | 实例、校验层、物理设备选取、逻辑设备与队列 | `VkInstance`、`VkDebugUtilsMessengerEXT`、`VkDevice`、队列族索引 |
| `Memory` | VMA 分配器、缓冲 / 图像的创建与销毁、上传 | `VmaAllocator`、`VkBuffer`、`VkImage`、`VkImageView` |
| `Swapchain` | 交换链、其图像视图、格式与呈现模式选择、重建 | `VkSwapchainKHR`、交换链图像视图 |
| `Frame` | 帧槽、命令录制、提交与呈现、延迟销毁队列 | `VkCommandPool`、`VkCommandBuffer`、`VkFence`、`VkSemaphore` |

**销毁职责与创建职责同属一个模块**，销毁顺序由 `Renderer` 按依赖反序编排（见 §5.4）。这条规则的价值在于：任何一次「谁负责销毁」的疑问都能在模块边界上直接回答。

### 3.3 模块依赖拓扑

```
                      ┌──────────────┐
                      │   Renderer   │  门面（依赖全部）
                      └──────┬───────┘
        ┌──────────┬─────────┼─────────┬──────────┐
        ▼          ▼         ▼         ▼          ▼
   ┌─────────┐┌─────────┐┌────────┐┌──────────┐┌────────┐
   │Platform ││ Device  ││ Memory ││Swapchain ││ Frame  │
   └────┬────┘└────┬────┘└───┬────┘└────┬─────┘└───┬────┘
        │          │         │          │          │
        └──────────┴─────────┴──────────┴──────────┘
                            │
                      ┌─────▼──────┐
                      │ EngineCore │（Log / Engine_Env / 工具集）
                      └────────────┘
```

允许的依赖方向（`A → B` 读作「A 可以 include B 的模块对外头」）：

| 边 | 理由 |
| --- | --- |
| `Renderer → 全部` | 门面负责编排 |
| `Swapchain → Device, Platform, Memory` | 交换链需要设备、表面、图像视图 |
| `Frame → Device, Swapchain, Memory` | 帧槽需要设备（命令池）、交换链图像、延迟销毁 |
| `Device → Platform` | 实例的扩展清单来自 SDL3 |
| `Memory → Device` | VMA 分配器绑定 instance / physicalDevice / device |
| `全部 → EngineCore` | 日志与路径解析 |
| **禁止** `Platform` / `Device` / `Memory` → 上层模块 | 任何反向依赖都是设计错误 |

同理**禁止** `Swapchain ↔ Frame` 双向依赖：`Frame` 单向看 `Swapchain`，交换链重建时由 `Renderer` 居中协调（`Frame` 不感知重建）。

### 3.4 模块骨架落地的具体口径

按 `agent开发指南` 的《文件架构约束》：

1. 每个模块目录下有 `core/`（实现）、`局部命名空间使用.h`（`using` 声明集）、模块对外头（如 `平台上下文.h`）。
2. 模块对外头中：**类声明放在 `namespace engine` 内**（减少前缀），其余自由函数 / 变量类型声明**带 `engine::` 前缀**。
3. `局部命名空间使用.h` 用 `using` 引入该模块 `.cpp/.hpp` 用到的全部类型，之后模块内代码一律不写命名空间前缀。
4. 命名：函数 / 变量 `小写下划线`、名词在前动词在后（如 `swapchain_build`、`frame_count_get`）；无参函数声明写 `(void)`；自定义类型 `首字母大写`（如 `Device_Context`、`Frame_Slot`）。
5. 注释：中文；`//` 连续少于三行，`/* */` 三行及以上；换行注释而非行尾注释。
6. 内存分配：全面禁用异常，`new(std::nothrow)`；本层**对外接口一律 `bool` 返回 + 日志**，不用异常（Vulkan 本身也不抛异常）。
7. 大括号换行、单语句 `if/for` 不加代码块——与 EngineCore 现有风格一致。

## 四、对外接口设计

### 4.1 公共面与私有面的边界

`d34da1c` 已把这条边界写进 `cmake/对外接口.cmake` 与 `CMakeLists.txt`：

- **PUBLIC 包含根**：`EngineCore 头快照根` ＋ `项目根`（供层内全路径 `Application/Renderer/...`）
- **PRIVATE 包含根**：SDL3、VMA、**Vulkan SDK**

由此得到一条**由构建系统强制执行的**边界：

> 层外代码包含渲染层公共头时，**拿不到** SDL3 / Vulkan / VMA 的任何头文件。任何在公共头里写 `#include <vulkan/vulkan.h>` 或出现 `VkDevice` / `SDL_Window*` 的写法都会在层外编译失败。

我建议**在 Phase 2~9 保持这条边界**，公共面只出现「引擎语义」的类型：

| 允许出现在公共头 | 不允许出现在公共头 |
| --- | --- |
| `uint32_t` 尺寸、`std::string` 标题、`bool` 开关 | `VkInstance` / `VkDevice` / `VkSwapchainKHR` … |
| 渲染层自定义不透明句柄（如 `Mesh_Handle = uint64_t`） | `VmaAllocator` / `VkBuffer` … |
| 不完整类型 `class Renderer::Impl` | `SDL_Window*` / `SDL_Event` … |

**代价与例外**：Phase 10 若要让 ImGui 走 Vulkan 后端，或让上层自定义渲染通道，可能需要把 Vulkan 类型提到公共面。届时两条路：①把 Vulkan SDK 包含根提升为 PUBLIC（改动只有一行，成本极低）；②保持隐藏，由渲染层代管 UI 与通道。**这是第 10 章的待决项之一。**

### 4.2 对外头 API 草案（`src/render/Renderer/渲染器.h`）

以下为**设计草案**，命名与风格已按《命名约束》对齐（`(void)`、名词在前动词在后、类型首字母大写）。

```cpp
#pragma once
//预编译头
#include "Application/Renderer/common/前置头文件包含.h"

//游戏引擎命名空间
namespace engine
{
	//渲染层版本查询（d34da1c 已存在，保留）
	std::string renderer_version(void);

	//渲染层配置
	struct Renderer_Config
	{
		//窗口客户区宽度（像素）
		uint32_t width = 1280;
		//窗口客户区高度（像素）
		uint32_t height = 720;
		//窗口标题
		std::string title = "白银纪元";
		//在途帧数量（1 = 不重叠，2 = 双缓冲，3 = 三缓冲）
		uint32_t frame_overlap = 2;
		//垂直同步（true → FIFO 呈现模式）
		bool vsync = true;
		//校验层开关（仅 Debug 构建有效；Release 强制关闭）
		bool validation = true;
		//窗口是否隐藏（无头用例用；仍创建真实窗口与表面）
		bool hidden = false;
		//着色器目录（空 → 相对可执行文件目录的 "shaders"）
		std::string shader_dir = "";
	};

	/*
	渲染器（门面）
	生命周期：init → frame_render × N → shutdown
	状态机：未初始化 → 已初始化 → 已销毁（shutdown 幂等，可重复调用）
	非线程安全：要求所有调用来自同一线程（见 §4.5）
	*/
	class Renderer
	{
	public:
		//构造（不创建任何 GPU 资源）
		Renderer(void);
		//析构（内部调用 shutdown，保证资源不泄漏）
		~Renderer(void);
		//不可拷贝、不可移动（持有 GPU 资源与线程亲和）
		Renderer(const Renderer&) = delete;
		Renderer& operator=(const Renderer&) = delete;

		//初始化（任一环节失败即逆序回退并返回 false，不留下半初始化状态）
		bool init(const Renderer_Config& config);
		//关闭（幂等）
		void shutdown(void);
		//是否已初始化
		bool valid(void) const;
		//每帧推进（泵事件 → 取图像 → 录制 → 提交 → 呈现）
		bool frame_render(void);
		//窗口是否请求退出
		bool close_requested(void) const;
		//已呈现帧数（调试与用例断言用）
		uint64_t frame_count(void) const;
		//当前交换链尺寸（窗口缩放后可能变化）
		uint32_t extent_width(void) const;
		uint32_t extent_height(void) const;
	private:
		//实现体（把 SDL3 / Vulkan / VMA 全部关在 .cpp 里）
		class Impl;
		std::unique_ptr<Impl> impl;
	};
}
```

设计要点：

1. **PIMPL 是硬要求**，不是风格偏好——它同时满足「不暴露第三方类型」与「改实现不动公共头」两个目标。
2. **`init` 必须做到「失败即无痕」**：任何一步失败都要把已创建的对象逆序销毁并返回 `false`；不能出现「`valid()==false` 但设备还开着」的状态。这是渲染层最容易写错的地方，必须有专门用例覆盖（§8）。
3. **`frame_render` 返回 `bool` 而不是 `void`**：交换链重建、最小化挂起、设备丢失等都会让某一帧「没画成」，但进程不该崩；返回值供调用方决定是继续还是收敛。
4. **`shutdown` 幂等 + 析构兜底**：调用方忘记调用也不会泄漏。
5. 需要 `extent_width/height` 是因为窗口可缩放，呈现分辨率不再等于配置值——渲染管线的视口与投影必须用后者。

### 4.3 生命周期状态机

```
            ┌──────────────┐
            │  未初始化     │◀────────────┐
            └──────┬───────┘             │
                   │ init()              │ shutdown()
                   │ 失败 → 回到未初始化   │ （幂等）
                   ▼                     │
            ┌──────────────┐             │
            │  已初始化     │─────────────┘
            └──────┬───────┘
                   │ 析构（自动 shutdown）
                   ▼
            ┌──────────────┐
            │   已销毁      │  （此后任何调用都安全返回 false / 无操作）
            └──────────────┘
```

`init` 内部的实际创建顺序与失败回退顺序（逆序）：

```
SDL_InitSubSystem(VIDEO)
  → SDL_CreateWindow
    → 收集实例扩展 / 校验层
      → vkCreateInstance → 建调试回调
        → vkCreateSurfaceKHR（SDL3）
          → 选物理设备（打分） → 选队列族
            → vkCreateDevice
              → vmaCreateAllocator
                → 查交换链能力 / 选格式与呈现模式
                  → vkCreateSwapchainKHR + 图像视图
                    → 建帧槽（命令池 / 命令缓冲 / 栅栏 / 信号量）
```

### 4.4 错误处理约定（无异常）

全项目禁用异常（《编码风格约束》<5>），Vulkan 又天然返回 `VkResult`，因此：

1. 所有 Vulkan 调用经 `core/结果检查.h` 的检查出口，失败时记 `Log::error`，消息里带 **`VkResult` 名字 + 调用处**（借 EngineCore 的 `Log::Format` 已携带 `std::source_location`，无需自造）。
2. 结果检查只有**一个实现点**，避免「有的地方查、有的地方不查」。
3. **必须检查但可接受的返回值**（`VK_SUBOPTIMAL_KHR`、`VK_ERROR_OUT_OF_DATE_KHR`、`VK_TIMEOUT`）走单独的判定函数，与硬错误分开，不混进 `Log::error`。
4. 校验层（`VK_LAYER_KHRONOS_validation`）在 Debug 树默认开启，并接 `VK_EXT_debug_utils` 回调把校验消息**转投 EngineCore 的 `Log`**——这样校验输出与引擎日志同一条流，调试时不必看两个控制台。

### 4.5 线程模型

**第一版：单线程（渲染层内部无线程）。**

理由：引擎目前也没有独立渲染线程（`Engine_Env` 的逻辑帧是主循环驱动）；引入渲染线程会立刻带来「资源创建命令池的线程归属」「帧槽与主线程的交接队列」「交换链重建与主线程的竞态」三块复杂度，而在「还没有画出第一个三角形」的阶段，这些复杂度换不来任何可见收益。

**约束**：`Renderer` 的所有方法必须来自同一线程；若将来引入渲染线程，本层内部需要新增「线程归属命令池 + 交接队列」，届时再设计。此约束写进公共头注释（§4.2 已写）。

### 4.6 六变量契约在渲染层的现有形态

`d34da1c` 已定，此处仅做记录，便于后续变更时对照：

| 变量 | 值 |
| --- | --- |
| `BYJY_RENDERER_OUT_LIB` | `RendererCore` |
| `BYJY_RENDERER_OUT_LIBDIR` | `Application/Renderer` |
| `BYJY_RENDERER_OUT_INC` | 承接 `BYJY_ENGINE_CORE_OUT_INC`（含项目根，故本项目内一律写 `Application/Renderer/...` 全路径） |
| `BYJY_RENDERER_OUT_DEF` | 承接 `BYJY_ENGINE_CORE_OUT_DEF`（`GLFW_STATIC`） |
| `BYJY_RENDERER_OUT_LINK` | EngineCore 的 ＋ `Lib/vulkan-1.lib` |
| `BYJY_RENDERER_OUT_SYS` | EngineCore 的 ＋ `setupapi;winmm;imm32;version;ole32;oleaut32;advapi32;uuid` |

**本设计不改动这六项**。唯一需要上层配合的改动在 Test 层（新增一条 `byjy_jieru_xiaceng(... Application/Renderer/cmake/对外接口.cmake ...)`，见 §8.2）。

## 五、关键数据流

### 5.1 初始化链路（`init`）

```
Renderer::init(config)
  └─ ① 参数校验（宽高非 0、frame_overlap ∈ [1,3]、title 可空）
  └─ ② Platform::build(config)
        SDL_InitSubSystem(SDL_INIT_VIDEO)
        SDL_CreateWindow(title, w, h, SDL_WINDOW_VULKAN [| SDL_WINDOW_HIDDEN])
  └─ ③ Platform::instance_extensions_get(receiver)      ← SDL_Vulkan_GetInstanceExtensions
  └─ ④ Device::build(instance_extensions)
        校验层可用性查询 → vkCreateInstance → vkCreateDebugUtilsMessengerEXT
        → 枚举物理设备 → 打分选取 → 检查交换链能力与队列族 → vkCreateDevice
  └─ ⑤ Platform::surface_build(device.instance)          ← SDL_Vulkan_CreateSurface
  └─ ⑥ Memory::build(device)                             ← vmaCreateAllocator
  └─ ⑦ Swapchain::build(device, surface, window_size)
        能力查询 → 格式选择 → 呈现模式选择 → 图像数确定 → vkCreateSwapchainKHR → 图像视图
  └─ ⑧ Frame::build(device, swapchain, frame_overlap)
        每帧槽：命令池 + 主命令缓冲 + 完成栅栏
        每交换链图像：acquire 信号量
        交换链级：呈现完成信号量
  └─ 任一步失败 → 逆序销毁已建部分 → 返回 false
```

**顺序不可调换的原因**（三条硬依赖）：
- ③ 必须在 ② 之后（SDL3 要先初始化视频子系统才能查扩展）；
- ⑤ 必须在 ④ 之后（`VkSurfaceKHR` 需要一个已存在的 `VkInstance`）；
- ⑦ 必须在 ④ 之后（交换链格式 / 呈现模式 / 能力查询都要物理设备 + 表面）。

### 5.2 每帧链路（`frame_render`）

```
Renderer::frame_render()
  └─ ① Platform::events_pump()
        轮询 SDL_Event：
          SDL_EVENT_QUIT          → 置退出标志
          SDL_EVENT_WINDOW_RESIZED→ 置「交换链待重建」标志（不立即重建）
          SDL_EVENT_WINDOW_MINIMIZED → 置「挂起」标志
  └─ ② 若退出标志 → 返回 true（由调用方查 close_requested 收敛）
  └─ ③ 若挂起标志 → 等待（避免 0×0 交换链）→ 返回 true
  └─ ④ 若待重建标志 → Swapchain::rebuild()（见 §5.3）
  └─ ⑤ 取当前帧槽 f = frame_index % frame_overlap
        vkWaitForFences(f.fence)（超时给足，避免静默死等）
        vkResetFences(f.fence)
  └─ ⑥ 取图像：vkAcquireNextImageKHR(swapchain, 超时, image_available[image_index], fence=空)
        若 OUT_OF_DATE / SUBOPTIMAL → 重建并返回 true（本帧不画）
  └─ ⑦ vkResetCommandPool(f.pool) → 录制：
        图像布局转换（UNDEFINED → COLOR_ATTACHMENT_OPTIMAL，srcStage=NONE 由 acquire 信号量保护）
        动态渲染（vkCmdBeginRendering）：清屏色 / 视口 / 裁剪
        绘制调用（Phase 6 起：绑定管线、描述符、顶点 / 索引缓冲、vkCmdDrawIndexed）
        vkCmdEndRendering
        图像布局转换（COLOR_ATTACHMENT_OPTIMAL → PRESENT_SRC_KHR，dstStage=BOTTOM_OF_PIPE）
  └─ ⑧ vkQueueSubmit2(
        等待   : image_available[image_index]（srcStage=COLOR_ATTACHMENT_OUTPUT）
        命令缓冲: f.cmd
        信号   : render_finished[f]（每帧槽一个）
        栅栏   : f.fence
       )
  └─ ⑨ vkQueuePresentKHR(
        等待   : render_finished[f]
        交换链 : swapchain, image_index
       )
        若 OUT_OF_DATE / SUBOPTIMAL → 置待重建标志
  └─ ⑩ frame_index++ → 返回 true
```

**同步原语的归属**（这是 Vulkan 最容易写错的地方，必须按此固定）：

| 原语 | 粒度 | 数量 | 等待者 / 信号者 |
| --- | --- | --- | --- |
| 图像可用信号量 | **每交换链图像** | = 交换链图像数 | 提交等待 / acquire 信号 |
| 呈现完成信号量 | **每帧槽** | = `frame_overlap` | present 等待 / 提交信号 |
| 帧栅栏 | **每帧槽** | = `frame_overlap` | 主机等待 / 提交信号 |

「图像可用信号量不能做成每帧槽一个」是硬性正确性问题：`vkAcquireNextImageKHR` 可能返回与上一帧相同的图像索引，若信号量被复用就会出现「仍被上一帧等待中」的冲突，校验层会直接报错。

### 5.3 交换链重建链路

```
Swapchain::rebuild()
  └─ ① vkDeviceWaitIdle（简化版；优化见下）
  └─ ② 销毁旧图像视图与旧交换链（VkSwapchainKHR 本体）
  └─ ③ 用当前窗口尺寸重新查询能力（currentExtent / minImageCount / 变换 / 合成模式）
  └─ ④ 重建交换链与图像视图
  └─ ⑤ 重建「每交换链图像」的 acquire 信号量（数量可能变化）
  └─ ⑥ Frame 的帧槽本身不变（数量由 frame_overlap 决定，与交换链无关）→ 通知 Frame 标记「首帧须等待」
```

`vkDeviceWaitIdle` 是「正确但粗暴」的做法：它会让重建瞬间停顿。**第一版就这么做**，等有了性能关注点再换成 §6.4 的延迟销毁 + 时间线信号量。理由：在还没有画出第一个三角形的时候追求无停顿重建，属于过早优化。

### 5.4 关闭链路（`shutdown`，严格逆序）

```
① Frame::destroy()        先等设备空闲 → 销毁信号量 / 栅栏 / 命令池
② Swapchain::destroy()   图像视图 → 交换链
③ Memory::destroy()      延迟销毁队列清空（等空闲）→ 用户资源 → vmaDestroyAllocator
④ Device::destroy()      vkDestroyDevice → 调试回调 → vkDestroyInstance
⑤ Platform::destroy()    vkDestroySurfaceKHR → SDL_DestroyWindow → SDL_QuitSubSystem(VIDEO)
```

**`vkDeviceWaitIdle` 必须出现在销毁命令池 / 交换链之前**：否则可能销毁仍在 GPU 执行中的对象。

## 六、核心机制设计

### 6.1 内存分配模型（VMA）

| 用途 | 分配口径 |
| --- | --- |
| 顶点 / 索引缓冲（设备本地） | `VMA_MEMORY_USAGE_AUTO` ＋ `VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT`（大且长命） |
| 统一缓冲（每帧更新） | `VMA_MEMORY_USAGE_AUTO` ＋ `HOST_ACCESS_SEQUENTIAL_WRITE` ＋ 持久映射 |
| 纹理图像 | `VMA_MEMORY_USAGE_AUTO`，`VK_IMAGE_TILING_OPTIMAL` |
| 上传暂存缓冲 | 每次上传临时创建，用完立即销毁（第一版）；后续换环形上传缓冲 |

**第一版的取舍**：不做子分配池、不做上传环、不做内存预算。每个资源一次 `vmaCreateBuffer` / `vmaCreateImage`，由 VMA 内部做子分配。等出现实际分配的瓶颈（帧内几十次分配）再引入复用。

**`VK_NO_PROTOTYPES` 不要定义**：本层直接静态链接 `vulkan-1.lib`（已在 `OUT_LINK` 里），VMA 保持默认的 `VMA_STATIC_VULKAN_FUNCTIONS=1` 即可，不需要 volk。若将来引入 volk，需要同时打开 `VMA_DYNAMIC_VULKAN_FUNCTIONS` 并把函数表交给 VMA——**这个切换点集中在 `Memory/core/VMA实现.cpp` 一个文件内**（该文件目前就是这么写的注释，设计上保留这个性质）。

### 6.2 帧与同步模型

- **在途帧数 `frame_overlap`**：默认 2。含义是「CPU 最多领先 GPU 两帧」；调大提高吞吐、增加输入延迟。
- **每帧槽（`Frame_Slot`）持有**：`VkCommandPool`、主 `VkCommandBuffer`、完成 `VkFence`、呈现完成 `VkSemaphore`、以及该槽的描述符集（Phase 6 引入）。
- **呈现模式选择顺序**：`MAILBOX`（若支持且 `vsync=false`）→ `FIFO`（`vsync=true` 或兜底）。`FIFO` 永远可用，是最终兜底。
- **交换链图像数**：`clamp(能力.minImageCount + 1, 下限, 能力.maxImageCount)`（`maxImageCount == 0` 表示无上限）。
- **`currentExtent` 特殊值**：为 `UINT32_MAX` 时表示「由应用决定」，此时用窗口客户区尺寸。

### 6.3 交换链模型

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 表面格式 | 从 `vkGetPhysicalDeviceSurfaceFormatsKHR` 结果中**优先选 `B8G8R8A8_SRGB` 或 `R8G8B8A8_SRGB`**，其次 `_UNORM` | Windows 上常见 `B8G8R8A8_*`；**不能硬编码** |
| 色彩空间 | `VK_COLOR_SPACE_SRGB_NONLINEAR_KHR`（若在支持列表内） | 与 sRGB 格式配套 |
| 图像用法 | `VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT`（Phase 10 加 UI 时再加 `TRANSFER_DST`/`TRANSFER_SRC`） | 最小必要 |
| 预变换 | `surfaceCapabilities.currentTransform` | 移动端场景需要，桌面直接取当前值 |
| 合成模式 | `VK_COMPOSITE_ALPHA_OPAQUE_BIT_KHR`（若在支持列表内） | 桌面窗口不透明 |
| 裁剪 | `VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT` 与能力求交 | 避免能力不足时创建失败 |
| 呈现时销毁旧交换链 | **否**，走延迟销毁队列（§6.4） | 在途帧可能仍引用旧交换链图像 |

### 6.4 资源生命周期与延迟销毁

第一版的规则简单到可以写死：

1. **长命资源**（缓冲 / 图像 / 管线）：由创建者显式销毁；销毁前若不确定 GPU 是否还在用，先 `vkDeviceWaitIdle`。
2. **短命资源**（上传暂存缓冲、临时命令缓冲）：用完即销毁。
3. **被交换链重建牵连的资源**（旧交换链、旧图像视图、旧 acquire 信号量的残留）：推入**延迟销毁队列**，标记「需等 `frame_overlap` 帧后再销毁」；`Frame::frame_advance` 每帧检查并释放到期的条目。

第一版为了减少出错面，`vkDeviceWaitIdle` 会先用上（§5.3），延迟销毁队列从 Phase 5 起**同时存在**，但初期只在「旧交换链」这一处使用——先让机制在场，再逐步扩大适用范围。

### 6.5 路径解析与资源定位（必须复用 EngineCore）

| 场景 | 口径 |
| --- | --- |
| `.spv` 着色器、外部资产 | `Engine_Env::absolute_path_get(...)`（**锚定 exe 目录**，不是 CWD；且该函数已处理中文路径的 UTF-8 → `std::filesystem::path` 转换） |
| 未显式指定 `shader_dir` | `exe_dir_get() / "shaders"` |
| 日志 | `Log` 单例（`Log::info/warn/error/debug`），**不自建日志** |
| 帧率 / 帧计数 | `Engine_Env::logic_frames_get()` / `frame_count_get()`；渲染层不自己维护「逻辑帧」 |

**为什么必须锚定 exe 目录**：工程已有明确教训（见工作站 `项目导航合集/main/工具集.md` §4.2）——CWD 会因「调试器启动 / 直接双击 / 从别的目录启动」而不同，导致资源找不到。渲染层若用相对路径拼资源路径，会重犯这个错。

## 七、Vulkan 已知坑位清单（实现时必须逐条对照）

这一章是「把教程代码抄进来会踩的雷」的集中清单。每条都对应一个具体的失败现象。

### 7.1 坐标系与投影

| 编号 | 坑 | 正确做法 |
| --- | --- | --- |
| K1 | Vulkan 的 NDC：**Y 轴向下**、**Z ∈ [0, 1]**；OpenGL 是 Y 向上、Z ∈ [-1, 1] | 投影矩阵按 Z ∈ [0,1] 构造；并翻转 Y（等价于把投影矩阵 `[1][1]` 取负）。若用 GLM，需 `GLM_FORCE_DEPTH_ZERO_TO_ONE` |
| K2 | 视口 Y 轴也向下 | 用 `VkViewport` 的 `height` 正数即可（配合 K1 的翻转）；不要靠「负高度」去纠正，那会连带影响裁剪 |

### 7.2 交换链

| 编号 | 坑 | 正确做法 |
| --- | --- | --- |
| K3 | 交换链格式**不能硬编码** `VK_FORMAT_B8G8R8A8_UNORM` | 必须先 `vkGetPhysicalDeviceSurfaceFormatsKHR` 再选（§6.3） |
| K4 | `MAILBOX` 呈现模式**不保证支持** | 必须先查 `vkGetPhysicalDeviceSurfacePresentModesKHR`，兜底 `FIFO` |
| K5 | 图像数量：请求 `minImageCount` 可能不足 | 请求 `minImageCount + 1`；`maxImageCount != 0` 时不得超过 |
| K6 | `currentExtent` 可能是 `UINT32_MAX` | 此时用窗口客户区尺寸 |
| K7 | 最小化时尺寸为 0，创建交换链会失败 | 检测 `0×0` 时**挂起**（跳过帧），不要尝试重建 |
| K8 | 窗口缩放事件风暴 | 重建前先合并标志，每帧最多重建一次 |
| K9 | 每次 `vkAcquireNextImageKHR` 前忘记 `vkWaitForFences` | 必须先等该帧槽栅栏，再取图像 |

### 7.3 同步

| 编号 | 坑 | 正确做法 |
| --- | --- | --- |
| K10 | 把「图像可用信号量」做成每帧槽一个 | 必须**每交换链图像**一个（§5.2） |
| K11 | 图像布局转换的 `srcStageMask` 用 `TOP_OF_PIPE` | 由 acquire 信号量保护时，`srcStageMask = COLOR_ATTACHMENT_OUTPUT`、`srcAccessMask = 0` |
| K12 | 呈现前的布局转换缺少 `dstStageMask` | 转 `PRESENT_SRC_KHR` 时 `dstStageMask = BOTTOM_OF_PIPE`、`dstAccessMask = 0` |
| K13 | 同一信号量在一帧内被两次等待 / 两次信号 | 严格按 §5.2 的归属表分配 |

### 7.4 SDL3 与 SDL2 的差异（照抄 SDL2 示例会编译失败）

| 编号 | 差异 |
| --- | --- |
| K14 | `SDL_Vulkan_GetInstanceExtensions` 在 SDL3 **去掉了窗口参数**（不再依赖具体窗口） |
| K15 | `SDL_Vulkan_CreateSurface` 在 SDL3 **保留了 allocator 参数**；两版签名不同，勿混用示例 |
| K16 | 事件类型枚举名改为 `SDL_EVENT_QUIT` / `SDL_EVENT_WINDOW_RESIZED` / `SDL_EVENT_WINDOW_MINIMIZED`（SDL2 是 `SDL_QUIT` 等） |
| K17 | SDL3 移除 `SDL_bool`，改用 C23 `bool` |
| K18 | 本层在库内**不接管入口点**：需确认 `SDL_MAIN_HANDLED` / `SDL_SetMainReady()` 的处理口径（**待实测确认**：库内包含 SDL3 头时不应触发 `main` 重定义；若 `SDL_Init` 在自定义 `main` 下要求先 `SDL_SetMainReady()`，则在 `Platform` 模块初始化入口统一调用一次） |

### 7.5 校验层与调试

| 编号 | 坑 | 正确做法 |
| --- | --- | --- |
| K19 | 校验层在某些机器上不存在 | 先 `vkEnumerateInstanceLayerProperties` 查询，缺了就告警降级，**不要硬失败** |

| K21 | Release 树误开校验层 | 由 `CMAKE_BUILD_TYPE` 决定默认值，且 `Renderer_Config::validation` 在 Release 下强制 `false` |

### 7.6 工程环境相关（本项目特有）

| 编号 | 坑 | 正确做法 |
| --- | --- | --- |
| K22 | `TMP` / `TEMP` 含中文用户名会让 `cl.exe` 报 `D8050` | 构建前把 `TMP`/`TEMP` 指向纯 ASCII 目录（既有做法：`D:\agent\_byjy_tmp`） |

### 与下层重构的关系（风险提示）

`EngineCore` 的 `Object_Pool` 当前处于跨层重构半途（`对象池.h` 存在语法错误），**下层目前无法整体重建**。

- 对渲染层的影响：**无**。渲染层只消费已构建好的 `EngineCore.lib`（Debug / Release 两版均在重构前产出，位于各自的 `out/build/x64-*/lib/`），不编译下层源码。
- 需要留意的时机：Phase 2 起渲染层会真正**链接** `EngineCore.lib`（当前只是静态库归档，不消费符号）。届时应确认下层 `Object_Pool` 重构已收口并重建，否则渲染层若意外引用到被改动的符号，会出现链接期问题。

以下逐项保留原决策过程与备选方案，便于后续回溯「为什么这么选」。

### 10.1 公共面是否保持「不暴露 Vulkan / SDL3 类型」

- **已定：保持**（PIMPL，公共头只出现引擎语义类型）。
  代价：Phase 10 若要做「同窗 UI」或上层自定义渲染通道，需再改一次边界。
- 备选：现在就把 Vulkan SDK 包含根提升为 PUBLIC（一行改动），换取后续灵活性，代价是上层的头环境被 Vulkan 污染。**D7 已定为「暂时不计划同窗」，故备选不启用。**

### 10.2 数学库：自研 `Math` 模块 / 复用 bullet3 / 重新引入 glm

- **已定：引入 `glm`**（用户拍板，与我的原推荐相反）。落地口径见 §2.5。
- 不采用：自研 `Math`；复用 bullet3 线性数学。

### 10.3 着色器流程

- **已定：构建期 `glslc` 离线编译 → 运行时加载 `.spv`；产物不入库**；找不到 `glslc` 只告警。
- 备选：`.spv` 生成后提交入库（环境无关，但有生成物入库的维护负担）。

### 10.4 窗口归属

- **已定：窗口由渲染层自建（SDL3），对外只给 宽/高/标题/是否隐藏**。
  代价：渲染层运行期间不与 glfw/ImGui 窗口并存（§1.4）。
- 备选：窗口由调用方创建并传入（`Renderer_Config` 传原生窗口句柄）——渲染层不再依赖 SDL3 的窗口能力，但调用方必须懂平台细节，且公共面需要接触平台类型。

### 10.5 线程模型

- **已定：第一版单线程**，`Renderer` 方法不得跨线程调用。
- 备选：现在就引入渲染线程与交接队列（复杂度高，当前收益低）。

### 10.6 交换链重建策略

## 十一、风险与备选方案

| 风险 | 触发条件 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 驱动不支持所需 Vulkan 版本 | 老显卡 / 虚拟机 | 设备创建失败 | 请求 `VK_API_VERSION_1_3` 前先读 `VkPhysicalDeviceProperties::apiVersion`，取二者较小值；真不支持则给出明确日志而不是崩溃 |
| 校验层缺失 | 精简版 SDK / 运行机 | Debug 下无法自检 | 查询后降级并告警（K19） |
| SDL3 与 glfw 消息泵冲突 | 同一进程同时驱动两套窗口 | 窗口无响应 / 事件丢失 | 近期口径下二者不在同一次运行中活跃（§1.4）；若将来必须并存，让 ImGui 走 Vulkan 后端 |
| 双构建树与下层库错配 | Release 树误取 Debug 版 `EngineCore.lib` | `/MD` 配 `/MDd` → `LNK4098`，严重时堆损坏 | 已在 `CMakeLists.txt` 第 1 节按 `CMAKE_BUILD_TYPE` 显式映射（不依赖下层的「优先 Debug」猜测） |
| 样板期过长导致进度焦虑 | Phase 2~5 无可视产出 | —— | 用 §8.3 的「隐藏窗口 60 帧」作为阶段性可见证据 |
| `Object_Pool` 重构未收口 | 下层无法重建 | 渲染层一旦需要重编下层即受阻 | 已确认当前不阻塞（§9 末尾）；Phase 2 前请你收口 |

## 附录 B：与已批准计划（第一轮）的对照

第一轮《执行计划》第十一节列出的「下一轮任务预告」是「Vulkan 基础设施 / SDL3 窗口与 Surface / 交换链 / VMA 接入 / Test 层用例 / 着色器流程」。本文档把这一串**重排**为 Phase 2~10，并给出理由：

- 新增「数学（Phase 8，最终定为引入 `glm`）」与「同窗 UI 评估（Phase 10）」两项在第一轮未预见；
- 明确「Phase 2~5 无可视产出」这一预期，避免中途误判为进度异常。
