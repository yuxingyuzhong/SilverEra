## 1. 方向 A：GPU 时间戳与 GPU 侧耗时统计

### 1.1 能力探测（`Frame/core/帧槽创建.cpp` 的 `build`）
- `vkGetPhysicalDeviceProperties` → `limits.timestampPeriod`（纳秒 / tick）与 `limits.timestampComputeAndGraphics`；
- `vkGetPhysicalDeviceQueueFamilyProperties` → 图形队列族的 `timestampValidBits`；
- 三项同时满足（`timestampComputeAndGraphics == VK_TRUE` 且 `timestampPeriod > 0` 且 `validBits > 0`）才置 `timestamp_supported = true`；否则记 `logger.warn` 并**降级**（不创建查询池、字段恒 0、不影响构建与渲染）。

### 1.2 查询池随帧槽创建 / 销毁
- `Frame_Slot` 增 `VkQueryPool timestamp_pool`（`queryCount = 2`：帧始 / 帧末）与 `bool timestamp_written`；
- `frame_slot_create`：仅能力支持时创建；`vkCreateQueryPool` 失败**只记日志并降级该槽**（不使整体构建失败）；
- `frame_slot_destroy`：归还查询池并复位两字段。

### 1.3 时间戳写入（`Frame/core/命令录制.cpp`）
三条录制路径（`command_record` / `command_record_target` / `command_record_target_present`）各增 `VkQueryPool timestamp_pool` 形参：
- `vkBeginCommandBuffer` 之后（渲染通道之外，满足 `vkCmdResetQueryPool` 的位置约束）：`vkCmdResetQueryPool(cmd, pool, 0, 2)` ＋ `vkCmdWriteTimestamp(cmd, VK_PIPELINE_STAGE_TOP_OF_PIPE_BIT, pool, 0)`；
- `vkEndCommandBuffer` 之前（收尾布局转换之后）：`vkCmdWriteTimestamp(cmd, VK_PIPELINE_STAGE_BOTTOM_OF_PIPE_BIT, pool, 1)`。
同帧多 pass 路径的起止覆盖两个 pass，故其 GPU 耗时是「目标 pass ＋ 后处理 pass」之和。

### 1.4 时间戳读回与换算（`Frame/core/提交呈现.cpp`）
- 新增私有 `gpu_timestamp_read(Frame_Slot&)`：在每条渲染路径「`slot_fence_wait` 之后、本帧录制之前」调用 —— 此时该槽**上一轮**提交已完成，结果就绪（**环形口径**，避免与上一帧混淆）；
- `vkGetQueryPoolResults(..., 2, 16 字节, sizeof(uint64_t), VK_QUERY_RESULT_64_BIT)`；返回非 `VK_SUCCESS` 即静默跳过（首轮 / 尚未执行完）；
- 按 `timestamp_valid_bits`（< 64 时）掩去高位再相减，按 `(end − begin) * timestampPeriod / 1e6` 换算毫秒写入 `last_gpu_frame_ms`；
- 三条路径在提交成功后置 `slot.timestamp_written = true`。

### 1.5 门面
- `渲染器.h`：`Frame_Stats` 增 `double gpu_frame_ms`；新增只读 `bool gpu_timestamp_supported(void) const`；
- `渲染器.cpp`：`frame_stats_get` 填 `gpu_frame_ms`；`gpu_timestamp_supported` 转调帧模块 `gpu_timestamp_supported_get`。

### 1.6 修改 / 新增文件（相对 Renderer 层根 `Application/Renderer`）
`src/render/Frame/帧上下文.h`、`core/帧槽创建.cpp`、`core/命令录制.cpp`、`core/提交呈现.cpp`、`src/render/Renderer/渲染器.h`、`core/渲染器.cpp`；Test 层新增 `Application/Test/src/单元测试/渲染/渲染GPU耗时测试.cpp`。

### 1.7 验收

## 2. 方向 B：帧 / 资源层遗留收口

### 2.1 `R-FRAME-08` 结案
`Frame/core/提交呈现.cpp` 的 `render_to_target` 前置校验补 `target.depth_view == VK_NULL_HANDLE`（与 `render_to_target_present` 同口径）。该条为**防御性校验**（门面经 `target_get` 组装时必带有效深度视图，公共面无法构造空缺场景），故无对应新用例，以「无回归」验证。

### 2.2 材质 blend 具名管线改为「按档缓存复用」
- `Renderer/core/渲染器实现.h`：`Material_Record` **删除** `owns_pipeline`；新增 `std::vector<uint64_t> blend_pipelines`（下标 = 档位序，0 表该档尚未登记）；
- `material_load`：`pipeline == 0 && blend != Opaque` 时按档位取下标、按需扩容缓存表；该档未登记则以默认场景着色器对 `pipeline_load` 登记一条并写入缓存；材质**共享**该管线（`record.pipeline = blend_pipelines[index]`）；
- `material_unload`：**不再**释放具名管线（所有权归门面），仅复位记录；
- `shutdown`：`materials.clear()` 后增 `blend_pipelines.clear()`（具名管线已随 `extra_pipelines` 统一释放）。

**语义变化与影响**：同 blend 的 N 个材质由「各登记一条具名管线 ＋ 2N 个着色器模块」变为「共享一条 ＋ 2 个着色器模块」；既有 5 例材质用例（含「登记卸载材质幂等」「混合档材质登记并绘制」）**全部仍通过**，并新增 1 例「同混合档材质共享管线」（同档两材质，卸载其一后另一仍可绑定并绘制一帧）。

### 2.3 具名管线 / 采样器是否统一进帧延迟队列（**本轮仅评估，不改机制**）
第 7 轮对二者采用 `Frame_Context::frames_wait()`（同步等待全部在途帧）而非延迟释放。二者性质不同：管线 / 采样器**无「内存模块归属」**（不经 VMA 归还），而延迟队列的归还出口是「导出器 → 内存模块」，故纳入需扩展 `Deferred_Memory_Resource` 语义；且 `frames_wait` 已保证正确性（校验消息恒 0）。**结论：维持现状**（同步等待），理由记入导航。

## 4. 构建坑与注意事项
- 新增 Test 层用例文件由 `CONFIGURE_DEPENDS` 自动纳入；新增 Renderer 头文件触发头快照导出（本轮 35 → **36** 个）。
- `vkCmdResetQueryPool` **必须录在渲染通道之外**，故其紧跟 `vkBeginCommandBuffer` 之后；终点时间戳写在 `vkEndCommandBuffer` 之前（收尾布局转换之后），此时亦在渲染通道外。
- 时间戳查询是**按帧槽**的，读回必须在「该槽上一轮已完成」之后（本轮取「帧栅栏等待后、本帧录制前」的环形口径），否则会读到未执行 / 混淆值。
- `timestampValidBits < 64` 时必须掩高位；设备不支持时必须降级（不得报错、不得影响既有用例）。
