## 三、契约变更

### 3.1 路由条目新增两字段（T1）

路由条目由 `{object, config_path, dirty_mark}` 变为可携带事件名：

```json
{
  "object": "Entity_Manager",
  "config_path": "config/entities/史莱姆 (Slime).json",
  "event_category": "Config",
  "event_tag": "Load",
  "dirty_mark": 12345678901234567890
}
```

- `event_category` / `event_tag` **均为可选**；缺失、非字符串或空串时回落 `Config` / `Load`。
- 与现有 `config_path` / `object` 一样，是**路由条目的字段**，不属于配置正文；配置正文仍只剔除 `dirty_mark` 后投递，故事件名字段不会污染载荷。
- 向后兼容：旧条目（无此二字段）行为与当前完全一致。

### 3.2 订阅事件表（由 4 条增至 6 条）

| 事件 | 语义 | 载荷 |
| --- | --- | --- |
| `Believed_Root` / `Load` | 登记可信根（已有） | `route` ＋ `config` |
| `Believed_Root` / `Unload` | 撤销可信根（已有） | `route` ＋ `config` |
| `Route` / `load` | 加载对象某目录对（已有） | `object` ＋ `route` ＋ `config` |
| `Config` / `load` | 加载对象配置（已有） | `object` ＋ 可选 `files` |
| **`Route` / `Unload`** | **卸载对象某目录对（新增）** | `object` ＋ `route` ＋ `config` |
| **`Config` / `Unload`** | **卸载对象配置（新增）** | `object` ＋ 可选 `files` |

### 3.3 卸载的层级归属（T2 / T3）

| 事件 | 清 `config_routes` | 清 `config_files` | 清路由文件标记 | 既有参照 |
| --- | --- | --- | --- | --- |
| `Believed_Root/Unload` | 前缀命中全部清 | 前缀命中全部清 | **不清**（既有行为，本轮不动） | `root_cache_clear` |
| `Route/Unload` | 精确清该目录对 | 该目录对下全部清 | 清（条目 ＋ 顶层） | 新增 |
| `Config/Unload` | **不动** | 指定文件（或全部） | 清（对应条目 ＋ 顶层） | 新增 |

## 五、实现要点

### 5.1 T1 —— 事件名定制（`配置加载.cpp`）

`object_config_deliver` 中把硬编码的 `"Config"` / `"Load"` 换为条目取值：

```cpp
//取本次投递事件类别与标签（缺省回落「Config」「Load」）
const string event_category = detail::field_check<string>(entry, "event_category")
    ? entry["event_category"].get<string>() : "Config";
const string event_tag = detail::field_check<string>(entry, "event_tag")
    ? entry["event_tag"].get<string>() : "Load";
//构造配置事件
auto evt = event_terminal.build("Config_Loader", object, event_category, event_tag);
```

- 采用 `detail::field_check` 与工程既有口径一致（该函数自带「存在 ＋ 类型 ＋ 非空」三重检查）。
- **已知副作用**：`field_check` 命中「字段不存在」时会经 `logger.warn` 打印 `detail::未包含指定字段`。仓库既有代码对可选字段（如 `route_file_read` 里的 `dirty_mark`）同样如此，故本轮沿用；若实测日志噪音不可接受，再改为轻量判定（`entry.contains(k) && entry[k].is_string()`），此项留作阶段 1 的观察点。

### 5.2 T4 —— 卸标记能力（`配置加载器.h` ＋ `路由文件操作.cpp`）

`route_file_write` 现签名只能「写一个数字标记」，卸载需要表达「顶层无标记」。改为 json 形参：

```cpp
//路由文件写回（mark 为空值时仅写路由条目，用于卸载清除顶层脏标记）
bool route_file_write(const std::filesystem::path& file_path, const nlohmann::json& mark,
    const nlohmann::json& entries) const;
```

实现内 `if (!mark.is_null()) route_file["dirty_mark"] = mark;`。

- 既有调用点只有一处（`route_file_process` 尾部的 `route_file_write(file_path, mark_make(...), entries)`），`uint64_t` 隐式转 `json` 成立，同步即可。
- 顶层无标记正是路由文件「初态」的形态，与测试夹具 `route_file_reset` 写出的初态一致，语义自洽。

### 5.3 T2/T3 —— 两级卸载

**`route_file_unload`（组5，`路由文件操作.cpp`）** —— 单份路由文件的卸载，与 `route_file_process` 严格对称：

```
读取（mark / entries）→ entries 非数组即报错返回 false
逐条：
    字段检查 object / config_path（不合法即 continue）
    非目标对象即 continue；only_files 非空且不含该路径即 continue
    path_safety_check 失败即 continue
    推导 object_content（与 route_file_process 同式：路由文件父目录 + 配置路径父目录）
    config_routes[object].erase(object_content)      ← 清路由缓存
    config_files[object].erase(config_path)          ← 清配置缓存
    entry.erase("dirty_mark")                        ← 清条目标记
    有改动则置 changed
若 changed：route_file_write(file_path, json(), entries)   ← 清顶层标记并回写
清理 config_routes / config_files 中已空的对象条目
```

**`route_unload`（组7，`缓存清除.cpp`）** —— 事件入口，对齐 `route_load` 的骨架：

1. `content_scan(content.route)` 扫该路由目录下路由文件；
2. 逐份 `route_file_unload(content, file_path, object, {})`。

**`config_unload`（组7，`缓存清除.cpp`）** —— 事件入口：

1. 校验 `config_files` 是否含该对象，无则告警返回；
2. 解析 `files`（可选）：非空即取交集，逐个文件从 `config_files[object]` 剔除；为空即整表剔除；
3. 依据 `config_routes[object]` 的目录对定位路由文件，逐份 `route_file_unload(目录对, file_path, object, files)` 抹除对应条目标记（**只清标记，不再重复清缓存**）；
4. 若 `config_routes[object]` 为空（路由缓存已被先行卸载），则仅清内存并告警说明「路由缓存缺失，磁盘条目标记未清理」。

> 关于「只清标记」：`route_file_unload` 的语义是「按过滤条件剔除内存缓存与条目标记」。`config_unload` 复用时会先精确清内存、再调它清标记；`config_routes[object].erase(object_content)` 对已剔除项是空操作（幂等），故无需为此增加分支参数，实现保持单一。

### 5.4 事件分派（`事件处理.cpp`）

- `attach()` 的 `needed_events` 增至 6 条（新增 `Route/Unload`、`Config/Unload`）。
- `event_process` 在 `Route/load` 之后追加 `Route/Unload` 分支（载荷校验、对象存在性校验、目录对缓存命中校验与 `Route/load` 完全一致，命中才调 `route_unload`）；在 `Config/load` 之后追加 `Config/Unload` 分支（校验 `object` 后调 `config_unload`）。
- 卸载分支不调用 `receiver_check`，不发送任何事件（用户明确不通知消费者）。

### 5.5 编码约束（沿用工程既有风格）

中文注释；连续少于三行用 `//`、三行及以上用 `/* */`；换行注释、`//` 后不空格；`if`/`for` 单语句不加代码块（嵌套时外层加块）；大括号换行；内存分配不用异常。函数声明顺序保持「被依赖者在依赖者前面 ＋ 功能相近者相邻」，并同步更新 `配置加载器.h` 顶部的分组注释。

## 八、测试用例清单（追加进 `Application/Test/src/单元测试/核心/配置加载器测试.cpp`）

夹具扩展：

- `object_attach(category, tag)` —— 支持订阅任意外发事件名，默认仍是 `Config` / `Load`；
- `route_file_reset(category, tag)` —— 非空时向条目写入 `event_category` / `event_tag`。

| # | 用例名 | 断言要点 |
| --- | --- | --- |
| A | 自定义事件名投递 | 条目带 `event_category="Property"` / `event_tag="Push"`，订阅该事件者收到 1 次；仅订阅 `Config/Load` 者收到 0 次 |
| B | 事件名缺省回落 | 条目不带两字段，`Config/Load` 订阅者收到 1 次（现有 5 条用例本身即是此回归面） |
| C | 配置卸载后可重建 | 加载（1 次）→ `Config/Unload`（带 `files`）→ `Config/load` 不再投递（证明内存缓存已清）→ `Route/load` 再次投递（证明条目标记与顶层标记已被抹除） |
| D | 路由目录卸载后可重建 | 加载（1 次）→ `Route/Unload`（对象自身目录对）→ `Route/load` 再次投递 |
| E | 配置卸载空载荷全卸载 | `Config/Unload` 不带 `files` → 该对象全部配置文件缓存被清（`Route/load` 后全部重新投递） |
| F | 卸载非法目标被驳回 | 未缓存的对象 / 未缓存的目录对 / 缺字段载荷：告警且无副作用（投递计数不变） |

> 用例 C/D 是「卸载后应能重新加载」这一决策的直接证据：若顶层标记未清，`route_load` 会整份跳过，重新投递不可能发生。

| 6 | 本机环境三坑（`TMP`/`TEMP` 含中文会使带 `/Zi` 的编译报 `D8050`；`chcp 65001` 须在 VS 环境之后；`ctest`/`ninja` 需绝对路径、`EngineTests.exe` 工作目录须为 Test 层目录） | 阶段 0 一次性固定口径 |
