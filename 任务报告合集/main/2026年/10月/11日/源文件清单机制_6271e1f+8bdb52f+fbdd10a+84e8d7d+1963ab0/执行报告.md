## 一、根因（一句话）

VS 文件视图的改名 / 迁移靠 File API `codemodel` 的 backtrace 找「可改写的引用」，而 backtrace **只落在把源文件直接加入 target 的那条命令上**；`GLOB` 工程的 `add_library(... ${VAR})` 里没有字面文件名，于是 VS 报「引用了文件……但无法修改引用」，**既不重配也不刷新工程模型**，磁盘已被改名 → 模型停在旧版次 → 报错列表爆红，用户侧表现为「生成到一半自行取消」。

更隐蔽的是**相对路径基准不一致**（这是本轮踩到并修正的坑）：

- CMake 解析 `target_sources` 相对路径的基准 = 「被 `include` 的 `CMakeLists` 所在目录」= **层根**；
- VS 改写引用时写出的相对路径基准 = 「被编辑的 `.cmake` 文件自身所在目录」。

若清单放在各层 `cmake/` 子目录，VS 会写出 `../src/…`，CMake 按层根基准解析成不存在的 `Engine/src/…` → `Cannot find source file` ＋ `No SOURCES given to target` → 配置失败 → VS 取消并回滚改名。**只有把清单放到层根，两个基准才重合。**

## 二、方案与改动清单

### 2.1 机制总览

```
file(GLOB_RECURSE …)  ──▶  byjy_source_list_sync()  ──▶  <层根>/源文件列表*.cmake（target_sources 字面量）
                                                              │
                                          CMakeLists：add_library(… STATIC)〔不传源文件〕→ include(<层根>/源文件列表*.cmake)
```

- 清单是「这些文件唯一的加入点」：`add_library` 不再接收它们，否则 backtrace 归 `add_library`、VS 仍无法改写。
- 清单由 CMakeLists `include`，属**配置依赖**：被 VS 改写即触发重新配置，从而启动改名后的自动同步。
- 清单只在**路径集合有差异**时写回（按集合而非逐字节比对），避免时间戳反复刷新与配置依赖咬合成「每次构建都重配」。

## 六、可快速重做本任务的全部信息

1. 新增共享脚本 `Engine/EngineCore/cmake/生成源文件列表.cmake`（内容见仓库，含三条约束与根因说明）。
2. 五层 CMakeLists：`file(GLOB_RECURSE …)` + 目录登记之后，`include("…/生成源文件列表.cmake")` 并调用 `byjy_source_list_sync("<层根>/源文件列表*.cmake" "<层根>" <target> <源变量> <头变量> "<层显示名>")`；随后 `add_library/add_executable(<target> STATIC)` **不传源文件**，再 `include("<层根>/源文件列表*.cmake")`。
3. 头文件也经清单 `target_sources` 列出（只为 IDE 建索引、不参与编译），使头改名同样能被 VS 改写。
4. **清单必须落在层根**——这是全案的成败点（相对路径基准重合）。
5. 构建环境：`TMP`/`TEMP` 指向纯 ASCII 目录 → 进 VS 开发人员环境 → `chcp 65001`（顺序不可反）→ `cmake`。
