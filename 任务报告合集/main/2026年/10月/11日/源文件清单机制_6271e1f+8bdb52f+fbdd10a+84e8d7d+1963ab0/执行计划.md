## 一、前置结论（诊断已完成，此处为可复现依据）

### 1.1 现象

在 VS 的**文件视图**里给文件改名 / 迁移目录后：

1. 认为"CMake 缓存重配置没被唤起"；
2. 反而出现"错误列表"（用户未提供具体报错文本，本计划把它列为阶段 A 的必采信息）。

### 1.2 机制（已由本机文件证据确认，共三条）

> **一、VS 的重配触发集里没有"被 GLOB 收集的源文件"。**
> VS 判定 CMake 缓存是否过期，依据它监视的那批脚本/配置：`CMakeLists.txt`、`*.cmake`、`CMakePresets.json`/`CMakeSettings.json`、`CMakeCache.txt`。
> 在文件视图里改名时，VS 走的是它的「CMake 项目操作」：**靠改写 CMakeLists 里的文件引用**去同步。本层这些文件在 CMakeLists 里**没有文字引用**（只被 `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)` 隐式扫到），于是没有可改写对象 → 不改动任何脚本 → VS 认为环境仍是最新 → 不重配。
> CMake 给 VS 的 File API 应答**确实带**通配符信息（`Engine/EngineCore/out/build/x64-Debug/.cmake/api/v1/reply/cmakeFiles-v1-*.json` 里 `"globsDependent": true` ＋ 每条 `"expression": ".../src/*.cpp"` ＋ 旧 `paths`），但 VS 只**记录**，不自行重算通配符。

> **二、真正会重扫 GLOB 的检查写在生成系统里，只在构建时执行。**
> `CMakeFiles/VerifyGlobs.cmake`（每次构建前用同一组通配符重扫并与上次配置的 `OLD_GLOB` 逐条比对，不等就 `TOUCH cmake.verify_globs`）→ `cmake.verify_globs` 是 `build.ninja` **再生成边的显式输入** → 另加各 GLOB 基点目录作为再生成边依赖（`Engine/EngineCore/CMakeLists.txt` 的目录登记）。
> 结论：改名/迁移**一定会在下一次构建被抓住**（ninja 打印 `Re-checking globbed directories...` 后自动重配），但**抓不住"你在视图里松手的那一刻"**。VS 只有三种情况会走到这里：脚本/配置有改动、你主动「配置缓存 / 删除缓存并重新配置」、或构建。

> **三、"错误列表"是 VS 工程模型过期的表现，不是 CMake 配置失败。**
> VS 的工程模型来自上一次配置的 File API 应答（含**旧路径**）。你先把磁盘路径改了，模型里那条就是悬空引用 → 立即报"找不到该文件 / 引用的项不存在"；同时所有 `#include 旧名` 的翻译单元报 `E1696`/`C1083`（这是**真实 include 断裂**，得改代码）。
> 本层 GLOB 与头快照脚本全部基于通配符，**纯改名不会让配置期报错**；`.vs` 下 `AutoPCH/*.ipch`、`Browse.VC.db` 的时间戳反复跳动即是这套过期模型在重建索引。
