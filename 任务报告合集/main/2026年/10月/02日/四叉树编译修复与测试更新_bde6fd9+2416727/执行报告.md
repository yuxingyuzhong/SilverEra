## 三、编译错误修复（3 处）

### 1-2. `引擎层/src/core/spatial/partition/Quadtree/core/区块信息检索.hpp`

`Node::data` 已由 `union` 改为 `std::variant<std::array<Node*, 4>, std::shared_ptr<T>>`，全模块基本已改用 `std::get<0>/<1>`，仅两处遗漏：

- L229（`leaf_collect` 卸载分支）、L365（`node_operate` 单点卸载分支）：
  `X->data[recur_direct]->data.reset()`
  → `Node* leaf_node = std::get<0>(X->data)[recur_direct]; std::get<1>(leaf_node->data).reset();`

**注意**：原写法除缺 `std::get<0>` 外还有第二个错——**`std::variant` 没有 `reset()` 成员**（那是 `std::optional` / `std::any` 的接口）。也就是说这两行在 variant 化之后**从未编译通过**。本次按原意（释放叶子持有的区块数据）改为 `std::get<1>(leaf_node->data).reset()`，语义最接近原设计。

### 3. `引擎层/src/core/spatial/partition/Quadtree_Manager/core/区块信息检索.hpp`（`target_range_amend`）

`target_excel` 已由 `std::shared_ptr<bool>` 改为 `std::vector<bool>`，但函数内仍取行首指针：

```cpp
bool* p = &excel.front() + row * width;   // vector<bool> 的 front() 返回代理引用，无法转 bool*
```

`std::vector<bool>` 是位压缩特化，元素为 `std::_Vb_reference` 代理，**取不到 `bool*`**。改为行列下标定位：

```cpp
for (int64_t row = Y_start; row < Y_end; row++)
{
    for (int64_t col = X_start; col < X_end; col++)
        excel[row * width + col] = true;
}
```

## 五、缺陷清单（本任务核心交付物）

### D1【严重】析构函数把整棵树按 4^递归级数 物化

- 位置：`引擎层/src/core/spatial/partition/Quadtree/core/设置与交互.hpp` 析构 L29-37、`recur_unload` L42-79
- 机理：两处递归都调用 `child_node_recur(ptr_next, recur_direct, type, false)`，`read_only=false` 会在**子节点为空时 `new(std::nothrow) Node(type)`**。于是析构过程会为所有缺失子节点分配内存、再 `delete`，等于把整棵完全四叉树物化一遍。
- 后果：析构复杂度 **O(4^level)** 而非 O(实际节点数)。实测：边长 262144（级数 14）析构约 **188 秒**；边长 2^41（级数 37）**无法完成**。
- 影响面：管理器智能创建出的树、64 位大坐标树，一经析构即卡死；这会让上层任何用完即弃的场景不可用。
- 方向：递归时只遍历**已存在**的子节点（空则跳过），不要复用会创建节点的 `child_node_recur`。

### D2【严重】退化树析构无限递归 → 栈溢出

- 位置：同上 `recur_unload` L42-79
- 机理：边长 ≤ 区块单元时 `recur_level_calcu` 得 `max_level = 0`。析构以 `recur_unload(1, 0, ...)` 进入：`now_level(1)` 既不等于 `max_level(0)`，也不等于 `max_level-1(-1)`，于是按 MIDDLE 分支继续向 `now_level+1` 递归，**永不命中终止条件**。
- 后果：栈溢出崩溃。`engine::Quadtree<int> tree(16, {0.5, 0.5});` 即可复现。
- 旁证：测试 `Quadtree_Test.退化树范围查询不产出结果` 因此只能以堆对象构造并刻意不释放。

### D3【中】卸载后叶子节点仍留在树中，父节点子指针未置空

- 位置：`Quadtree/core/区块信息检索.hpp` L225-233（范围卸载）、L360-369（单点卸载）
- 机理：卸载只做 `std::get<1>(leaf->data).reset()`，即仅释放叶子持有的 `shared_ptr<T>`；叶子节点本身、父节点指向它的指针都原样保留。
- 后果：卸载后 `seek` 该点得到的是 `ptr_data == nullptr` 的区块，**而不是「未找到」**；且节点内存不回收，"卸载"名义与实际语义不符。上层若按「卸载后即为空」判断会出错。
- 方向：明确「卸载」的定义——是回收叶子节点并置空父指针（区块回到未建状态），还是仅释放数据。

### D4【中】卸载路径未判空即解引用

- 位置：`Quadtree/core/区块信息检索.hpp` L365（单点）、`leaf_collect` 卸载分支 L229（范围）
- 机理：`std::get<0>(X->data)[recur_direct]` 直接解引用，未检查该子指针是否为 `nullptr`；卸载路径不创建节点，因此指向从未建过的区块时就是**野指针解引用**（UB）。
- 后果：对未建区块调用 `unload` 即崩溃。测试中因此被约束为「只对已 build 的坐标调用 unload」，该约束已写入用例注释。

### D5【中】`seekable_analyse`（单点重载）并非所有路径都返回值

- 位置：`Quadtree/core/区块信息检索.hpp` L70 附近，编译器告警 **C4715**
- 后果：该函数返回 `Analysis_Result`，调用方按 `FEASIBLE / IN_PROGRESS / INFEASIBLE` 三分支处理；未定义返回值会落到意外的分支，行为不确定。

### D6【中】退化树的单点查询抛 `std::bad_variant_access`

- 位置：`Quadtree/core/区块信息检索.hpp` `node_operate` 单点重载末尾 L382-397
- 机理：`recur_level_max == 0` 时寻址循环一次都不执行，`child_node` 仍是根节点；而根节点在建/查路径下是 MIDDLE（alternative 0），末尾却直接 `std::get<1>(child_node->data)` 取区块 → 抛 `std::bad_variant_access`。
- 后果：边长 ≤ 区块单元时，单点 `build` / `seek` / `get` 全部崩溃。
- 旁证：测试 `Quadtree_Test.退化树单点查询触发引擎缺陷` 因该缺陷被 `GTEST_SKIP` 跳过（非放宽断言）。

### D7【低】管理器已移除退化树拦截

- 位置：`Quadtree_Manager`，`quadtree_build_smart` 不再拒绝边长 ≤ 区块单元的退化树创建。
- 后果：一旦建出退化树，就会撞上 D2（析构栈溢出）与 D6（查询抛异常）。
- 旁证：测试 `Quadtree_Manager_Test.退化树创建被拒绝` 语义已不成立，被 `GTEST_SKIP`。

### D8【待确认，未证实】管理器范围查询的网格基准疑似不一致

- 位置：`Quadtree_Manager/core/区块信息检索.hpp` L216-218
- 现象：
  - L188 `excel_element_to_coord(seekable_range, seek_time, target)` —— 以 `seekable_range` 作为**索引网格**；
  - L216 `ptr_tree->tree->seekable_range_calcu(seekable_range, tree_range)` —— 该函数第二参数是出参，会把 `tree_range` 覆写为裁剪后的范围，同时返回扩大标记（此处返回值被丢弃）；
  - L218 `target_range_amend(tree_range, target_excel, seekable_range)` —— 却拿 `tree_range` 当**网格**、`seekable_range` 当**区域**。
- 疑点：标记与索引使用了不同的网格基准，行列宽度不一致时可能漏标记已覆盖区块，导致同一区块被重复查询（结果重复或重复建树）。
- 状态：**未证实**。该段是你正在 review 的在建代码，我未改动也未构造反例，仅按阅读标记风险点，供你自己判断。
