## 三、关键设计口径

- **合并判据**：相邻项管线、布局、描述符集数量与集合、推送常量（偏移 / 长度 / 逐字节）、顶点 / 索引 / 实例缓冲、索引区（`index_offset` / `index_count`）全部一致，且下一项 `instance_offset` 恰为上一段末尾（按 80 字节 / 实例）。任何不满足即断开。
- **首实例语义**：`first_instance = 段首项 instance_offset / 80`；需设备 `drawIndirectFirstInstance` 特性，探测为假时不创建缓冲、整轮回落逐项。
- **回落条件**：开关关、映射 / 缓冲 / 容量不可用、`active_secondary_count > 1`（并行分段录制会多线程写同一映射区）、命令总数超 `4096`、阴影 pass。回落路径代码零改动，保证默认逐字节不变。
- **一致性**：间接缓冲以 `VK_MEMORY_PROPERTY_HOST_COHERENT_BIT` 硬性要求分配，命令由主机写入后无需显式冲刷。
- **容量与游标**：`frame_indirect_commands` 在每次渲染入口清零；同一帧多 pass（如阴影 → 主 scene）各自重置，避免覆盖已录制命令。

  - 结论：合批降低的是**主机侧录制耗时**（命令数减少），GPU 帧耗时基本持平；规划中「多批次 GPU 耗时下降 ≥ 12%」未达成，原因见下。

## 五、与执行计划的偏差

1. `Memory_Context` 未增 `buffer_unmap`：使用 VMA 持久映射，无需成对解映射。
2. 未新增门面 `gpu_indirect_supported()`：`compute_capabilities_get()` 已暴露 `multi_draw_indirect` 与 `draw_indirect_count`，阶段 C 直接取用。
3. 未做「容量回落」用例：正常 API 下相邻项实例区连续且状态一致，合批后命令数远小于 4096，无法在不引入人为断点的情况下触达容量上限；容量判定逻辑以代码审查覆盖。
4. 阶段目标「GPU 耗时下降 ≥ 12%」未达成：1 万实例为单条绘制命令，间接替换无收益；100 批场景收益体现在录制耗时。后续 Cluster 方向（263–273）才可能带来 GPU 侧收益。
