# 执行计划 · 后处理链 UI 后置（UI 不吃后处理）

- 决策：采用**简单迁移**（UI 在末级后处理之后绘制到交换链），不走双目标合成
- 代码版次：Renderer `10f1693` → **`f5e7578`**；Test `f0f4fb0` → **`aed34e5`**

## 一、现状（改动前）

| 路径 | UI 位置 | 结果 |
| --- | --- | --- |
| `command_record`（交换链直通，无后处理） | 场景 pass 结束后、呈现前 | 正常（无后处理，不存在被处理问题） |
| `command_record_target`（离屏目标） | 场景 pass 结束后 | UI 被烘焙进目标；若上层再对该目标做后处理链，UI 一并被处理 |
| `command_record_chain_present`（同帧后处理链 / SSAA） | **完全不调用 UI 回调** | 链模式下 UI 直接缺失 |

结论：「UI 吃不吃后处理」的根因是 UI 被画在**后处理之前**（或被链路径直接丢弃）。

## 二、方案对比与定案

1. **简单迁移（选定）**：链路径在末级后处理 pass 结束后，以「保留内容」的单采样 UI 通道把 UI 叠加到交换链图像。
   - 优点：零新增目标、零合成开销、时序与既有 MSAA UI 通道一致（复用 `ui_pass_record`）；
   - 代价：UI 无法再参与后处理（这正是目标语义）。
2. 双目标合成：场景后处理到目标 A、UI 画到目标 B、再全屏合成。
   - 优点：可对 UI 单独做效果；缺点：多一张全屏目标与一次合成 pass，带宽与代码复杂度都不划算，
     且当前需求就是「UI 不吃后处理」，无需合成层。→ 不采用。

## 三、实施步骤

1. `帧上下文.h`：`command_record_chain_present` / `render_chain_present` / `render_to_target_present` 增末位参数 `ui_callback`（默认空，行为完全不变）；
2. `命令录制.cpp`：末级 `vkCmdEndRendering` 之后、回读 / 呈现转换之前，若回调非空则调用 `ui_pass_record`
   （交换链范围视口 / 裁剪，`loadOp = LOAD`）；
3. `提交呈现.cpp`：参数透传；
4. `渲染器.cpp`：同帧后处理链与 SSAA 两条链路径传入 `impl->ui_channel.draw_callback_get()`；
5. 新增用例 `Renderer_Post_Chain_Test.后处理链上UI不被处理`（灰度链下 UI 保留通道差）。

## 四、验收

- 灰度链：场景被去色（三通道差 ≤ 4），UI 覆盖处通道差 ≥ 40（证明 UI 在链之后）；
- 全量回归 1351 例通过。
