# 构建归档响应文件编码问题 · 排查报告

> 项目：白银纪元 / 引擎层
> 分支：main
> 对应版次：`e430610e9ae3ca552b300cc9756b09b58195b725`
> 报告时间：2026-09-24
> 任务类型：故障排查（只读勘查 + 复现实验，工作区**零改动**）

---

## 一、现象

构建在**归档（静态库生成）**阶段中断，报错原文：

```
LINK : fatal error LNK1181: 无法打开输入文件“CMakeFiles\EngineCore.dir\src\core\event\Event_Terminal\core\浜嬩欢缁堢.cpp.obj”
```

`exitCode = 1181`。

报错路径里的 `浜嬩欢缁堢` 是乱码，实际文件名为 `事件终端`。

**关键特征**：编译阶段全部成功，磁盘上所有 `.obj` 都在且名字正确；只有把它们封进 `.lib` 的那一步失败。

受影响构建树：`引擎层/out/build/x64-Debug`（生成器 Ninja，CMake 4.3.1，MSVC 14.51.36231）。

---

## 二、根因

**Ninja 写出的响应文件（response file）是 UTF-8 无 BOM 编码，而 MSVC 命令行工具默认按系统 ANSI 代码页解读响应文件。**

本机 ANSI 代码页为 936（GBK，`GetACP` 实测），于是响应文件中的 UTF-8 中文路径被逐字节按 GBK 重新解码，得到乱码路径，`lib.exe` 按乱码名字去开文件 → 找不到 → LNK1181。

一句话：**路径在「命令行」通道里是安全的，进了「响应文件」通道就变成裸字节，编码假设一错就断。**

---

## 三、证据链

**1. 归档规则原文**（`引擎层/out/build/x64-Debug/CMakeFiles/rules.ninja` 第 61–66 行）

```
rule CXX_STATIC_LIBRARY_LINKER__EngineCore_Debug
  command = cmd.exe /C "$PRE_LINK && ...lib.exe /nologo $LINK_FLAGS /out:$TARGET_FILE @$RSP_FILE && $POST_BUILD"
  rspfile = $RSP_FILE
  rspfile_content = $in_newline $LINK_PATH $LINK_LIBRARIES
```

对象列表经 `@$RSP_FILE` 传入，不再上命令行。

**2. 响应文件本体**：`引擎层/out/build/x64-Debug/CMakeFiles/EngineCore.rsp`

- 长度 12709 字节
- 首 16 字节：`43 4D 61 6B 65 46 69 6C 65 73 5C 45 6E 67 69 6E`（即 `CMakeFiles\Engine`）
- **无 BOM**（否则应以 `EF BB BF` 开头）

**3. 按 UTF-8 解码 → 路径正确**

```
CMakeFiles\EngineCore.dir\src\core\event\Event_Terminal\core\事件终端.cpp.obj
CMakeFiles\EngineCore.dir\src\core\event\Event_Terminal\core\终端接口.cpp.obj
```

**4. 按 CP936 解码 → 精确复现报错文字**

```
CMakeFiles\EngineCore.dir\src\core\event\Event_Terminal\core\浜嬩欢缁堢.cpp.obj
CMakeFiles\EngineCore.dir\src\core\event\Event_Terminal\core\缁堢鎺ュ彛.cpp.obj
```

与用户报错中的路径字符串**逐字相同**。

**5. 磁盘上的对象真实存在且名字正确**

`引擎层/out/build/x64-Debug/CMakeFiles/EngineCore.dir/src/core/event/Event_Terminal/core/` 下：

- `事件终端.cpp.obj` —— 1.9 MB
- `终端接口.cpp.obj` —— 587.5 KB

**6. 直接重放归档步骤**

以构建目录为工作目录执行：

```
lib.exe /nologo /out:<临时目录>\probe.lib @CMakeFiles\EngineCore.rsp
```

结果：`LNK1181`，报错文字与用户所贴**完全一致**，`exitCode = 1181`。故障可在工作区外独立复现。

**7. 编码变体对照实验**（同一份对象清单，只改响应文件编码）

| 响应文件编码 | 结果 |
|---|---|
| UTF-8 无 BOM（Ninja 原样） | ❌ LNK1181 |
| GBK / CP936 | ✅ 成功产出 .lib |
| UTF-8 **带 BOM** | ✅ 成功产出 .lib |

第三行说明：MSVC 工具链**认** BOM 声明的 UTF-8，问题只出在「无 BOM 且被当 ANSI」这一种组合。

**8. 受影响条目的分布**

响应文件里非 ASCII 路径共 **10 条**（即引擎层自己的 10 个实现文件），全部位于最后：

```
113  碰撞代理器.cpp.obj
114  事件中转器.cpp.obj
115  事件终端.cpp.obj          ← lib.exe 报的是这一条
116  终端接口.cpp.obj
117  对象池实例化.cpp.obj
118  四叉树实例化.cpp.obj
119  四叉树管理器实例化.cpp.obj
120  配置加载器.cpp.obj
121  随机数生成器.cpp.obj
122  计时器.cpp.obj
```

> 附注：`lib.exe` 报的是第 115 行，而不是列表里最早的 113 行。推测与「部分文件名 UTF-8 字节数为奇数，最后一个字节吞掉后续字符、导致路径解析错位」有关。**此点为推断，本次未深入验证。**

## 四、为什么以前不触发（本次排查的关键一环）

2026-09-19 16:39 那一轮，`out/_verify/srcfix` 里是**成功**产出过 `EngineCore.lib`（35,095,810 字节）的，而那棵构建树里**同样存在** `事件终端.cpp.obj` 这类中文对象。也就是说，中文路径本身从来不是问题。

真正变化的，是归档规则的写法：

| 对比项 | 09-19 树（`out/_verify/srcfix`，成功） | 今天这棵树（`out/build/x64-Debug`，失败） |
|---|---|---|
| 归档规则命令 | `lib.exe … /out:$TARGET_FILE $in` | `lib.exe … /out:$TARGET_FILE @$RSP_FILE` |
| 对象传递通道 | **命令行**（UTF-16，不受代码页影响） | **响应文件**（UTF-8 裸字节） |
| EngineCore 对象数 | 51 | 122 |
| 响应文件 | 不存在 | 12709 字节 |

- 两棵树生成器都是 Ninja，CMake 均为 4.3.1，MSVC 同为 14.51.36231（已逐项核对）。
- 两棵树的 `build.ninja` 均为 UTF-8（实测 `代码存储`、`事件终端` 等字符串按 UTF-8 可解、按 GBK 不可解）。
- 09-19 那棵树里连可执行文件链接规则也是 `$in` 直传，整棵树**完全没有响应文件**。

所以：**缺陷一直在，只是过去走的通道恰好对它免疫。** 今天对象数从 51 涨到 122（bullet3 的 117 个对象被纳入 EngineCore），归档命令随之改为走响应文件，缺陷才浮出水面。

关于「为什么不走响应文件会变」：本版 CMake 中 `CMAKE_NINJA_FORCE_RESPONSE_FILE` 已不是可查变量（`--help-variable` 报未定义），项目侧也没有任何相关设置；因此这个切换是 CMake 的自动判定。**推断**与命令行长度有关，但**此条未有直接证据，未验证**。

## 五、影响面

- 只影响**链接 / 归档**阶段。编译阶段由 `cl.exe` 经命令行接收路径（UTF-16 通道），不受影响——这正是「所有 obj 都在，只死在最后一步」的原因。
- 只有文件名含非 ASCII 字符的对象会触发。
- 任何走响应文件的归档/链接目标都可能撞上：当前是 `EngineCore`；将来对象数继续增长、其他目标也切换到响应文件时同样会中。
- 与系统区域设置相关：本机 `GetACP = 936`、`Get-Culture = zh-CN`、`Get-WinSystemLocale = zh-CN`（实测）。
- **`chcp 65001` 无效**（实测：改控制台代码页后重放，仍报同一错误）。控制台代码页与进程 ANSI 代码页不是一回事。
