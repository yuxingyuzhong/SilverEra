## 四、实施过程与关键决策

1. **引擎层采用全量重编而非增量**。计划 A1 写的是增量构建，实际改为 `ninja -t clean` 后全量重编：该构建树的 `build.ninja` 不包含头文件依赖（`碰撞代理器.h` 在其中出现 0 次），增量结果不可信。全量重编结果 `ERR=0`、`WARN=17`（C4005 ×12、C4715 ×3、C4828 ×2，**全部为既有告警**），产出 `out/build/x64-Debug/lib/EngineCore.lib`。
2. **提交面以实测为准**。计划记录 17 文件，实查为 18 项——多出 `Collision_Proxy/碰撞代理器.h`（纯行尾变更）。经与用户确认后一并提交，并在报告中单列该文件性质，避免被误读为实质改动。
3. **禁用用例逐条读源码核实后再转正**。对四叉树管理器与对象池共 21 条 `DISABLED_`，逐条回到引擎层源码确认对应缺陷确已修复（如 `tree_record::size` 已是 `uint64_t`、`set_min_size` 确实只写下限、`block_seek` 的 `max_size` 已是 `uint64_t`），确认后才恢复真实用例体，**未采用「改断言迁就现状」的做法**。四叉树管理器那批用例原本整段测试体被注释，本次将其恢复为可执行代码。
4. **回归暴露的 3 处失败逐一处置**（详见第五节），其中两处经用户拍板：
   - `Object_Pool_Test.卸载仅清有效标记`：引擎 `unload` 现在会把对象 ID 回收并置零（`it->ID_set(0)`），用例断言过时 → 改名 `卸载后记录保留但ID清零`，断言同步为 `ID() == 0u`。
   - `Quadtree_Test.越界检索单次调用只扩大一次`：`block_seek` 的实现本就是「循环扩大直到容纳目标或触达上限」（源码注释明确写出该设计意图），用例期望「只扩大一次」与实现不符 → **经用户选择**按实现语义同步（改名 `越界检索连续扩大直至容纳目标`，期望边长 `512` → `262144`）。
   - `Quadtree_Manager_Test.超大边长上限下区块检索次数正常`（本次转正的 23 条之一）：边长上限设到 `1ull << 33` 后建树抛出 **SEH 0xC0000094（整数除零）**，定位到 `Quadtree/core/区块信息检索.hpp` 的 `block_seek` 第 155 行 `for (; (max_size /= 2) / state.size > 1;)` —— `state.size` 为 0 时无防御 → **经用户选择**退回 `DISABLED_`，并在用例注释中写明缺陷位置与表现，未擅自扩大引擎修复范围。
5. **日志落盘探针纳入忽略规则**。日志用例会在工作目录写出 `engine_log_probe.txt`，用例末尾虽尝试删除，但活跃输出流仍持有文件句柄，Windows 下删除失败而残留；已补 `.gitignore` 规则并清掉残留文件。
6. **未使用子代理**，全程单线程推进；两次方向性决策（越界检索用例口径、除零缺陷处置）均通过提问卡片取得用户确认。
7. **转正试验后的回退（本版次最后一轮）**。按用户首次决定把 `DISABLED_超大边长上限下区块检索次数正常` 转正并重跑，结果仍抛 `SEH 0xC0000094`。静态排查确认崩点**不在** `block_seek`（`max_size` 与 `state.size` 均为 `uint64_t`，`size > 0` 时该表达式不会除零），而在 `Quadtree_Manager/core/区块信息检索.hpp` 的 `excel_element_to_coord` 中 `element_ID / width`（`width` 由范围宽度除以 `block_size` 得来，可为 0）。据此把新事实回报用户并重新拍板，最终决定：**保留并提交引擎层防御（`16d74df`），用例退回禁用并把注释改写为真实崩点（`d48362e`）**。

## 六、遗留与未完成

1. **超大边长上限的整数除零缺陷未修（崩点已重新定位）**。实际崩点在 `Quadtree_Manager/core/区块信息检索.hpp` 的 `excel_element_to_coord`：
   ```cpp
   int width = (excel_range.right - excel_range.left + 1) / settings.block_size;
   int row = element_ID / width;
   int col = element_ID % width;
   ```
   当格式化后的查询范围宽度不足一个 `block_size` 时 `width` 为 0，除法抛 `SEH 0xC0000094`。根因涉及 `int` 型坐标表示无法承载 `INT_MAX` 以上的树尺寸（`Rect2i` 各分量为 `int`，`manage_range_calcu` 按 `tree_size` 计算范围时会溢出），需架构层调整，非局部防御可解。
   本版次补交的 `block_seek` 零尺寸防御（`16d74df`）修掉的是该函数自身的潜在除零点，**不足以**让这条用例通过；用例 `DISABLED_超大边长上限下区块检索次数正常` 保持禁用，注释已写明真实崩点与根因，修复后去掉前缀即可转正。
2. `区块信息检索.hpp(72)` 的 `warning C4715`（`point_seekable_analyse` 并非所有控件路径都返回值）为既有告警，本版次未处理。
3. 坐标类型用例（21 例）只覆盖接口契约本身（构造、ULP 相等、转换取整、矩形边界），未做与四叉树检索路径的交叉验证。
4. 日志系统 `active_file_stream` / `streams` 为静态成员，`设置活跃流后日志落文件` 用例虽在末尾还原为空串，但静态状态跨用例仍具全局性；当前顺序执行无问题，后续若用例顺序变动需留意。
