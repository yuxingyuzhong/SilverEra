## 二、脏标记方案（实际落地）

### 2.1 格式
```json
{
  "dirty_mark": 12345678901234567890,
  "routes": [
    { "object": "Collision_Proxy", "config_path": "assets/config/collision.json", "dirty_mark": 987654321 }
  ]
}
```
- 顶层 `dirty_mark` = `hash(盐, 路由文件路径)` —— 该路由文件本轮**是否产出过配置投递**。
- 条目 `dirty_mark` = `hash(盐, object, config_path)` —— 该「对象×文件」本轮**是否已投递**。
- **配置文件本体不写标记**；投递时若正文含 `dirty_mark` 字段则剔除（脏标记不参与投递）。

### 2.2 盐
`run_salt_get()`：函数局部 `static`，由 `Random_Generator<int64_t>` 混入 `steady_clock` 计数构成 ⇒ 进程内唯一、跨运行随机 ⇒ 上一轮遗留标记自动失效，无需收尾。

### 2.3 写入时机（严格遵守你强调的口径）
**只有「真正读取配置文件」且「成功发送 `Config/Load`」之后**才写条目标记；回写路由文件（连同顶层标记）也仅在**本轮至少成功投递过一次**时发生。**仅缓存路由（写 `routes`）绝不写任何脏标记。**

### 2.4 第三方重置契约
动态改配置者只需把对应条目的 `dirty_mark` 改成任意随机值即可令其重载；若要让 `Route/Reload` 生效，还需把路由文件**顶层** `dirty_mark` 一并重置。此契约已写入代码注释，需同步到配置资产文档。

## 三、四项任务落地

| 任务 | 实现 |
| --- | --- |
| **<1> 事件响应** | `attach()` 订阅 `Route/Reload`、`Config/Reload` 两条；`event_process` 分派，另接收中转站转发的 `Subscriber/Call` 与 `Subscriber/Response`。载荷：`Config/Reload` = `{"object", "files":[…]}`（`files` 缺省=该对象全部）；`Route/Reload` = `{"route","config"}`（对应 `Config_Content` 两字段）。载荷缺失一律 `logger.error` 驳回 |
| **<2> 接收者检查** | 路由条目读入并写入 `routes` 缓存后，逐对象发 `Subscriber/Check`（`event_terminal.interact`），读回 `object_existence`；为假则**取消该对象配置信息传递**（不读配置、不写标记）。`Subscriber/Call` 到达时以 `sender_object` 为对象名**全量定向补投** |
| **<3> 对象配置文件路径缓存** | 即 `routes`（`object → {config_path}`），在**对象存在性检查之前**写入（它是路由数据，不依赖存在性） |
| **<4> 二次加载** | (a) `Config/Reload` → 复用 `config_load(object, files)`：命中条目标记者按事件语义 `logger.warn("事件指定但无需重新加载的文件，已跳过")` 并跳过，其余重载；(b) `Route/Reload` → 先查阅路由文件顶层标记，命中者 `logger.warn("事件指定但无需重新加载的路由文件，已跳过")`，其余重新解析并刷新 `routes`。**无强制重载通道**（性能防御优先） |

**`Subscriber/Call` 补投**：`force_reload = true`，**忽略脏标记**强制重读并投递该对象全部配置，投递成功后照常写标记（幂等）—— 否则"接收者后接入"将永远拿不到配置。此为实现层自决，已在上一轮向你说明。

### 关键实现细节（自决项）
- `route_file_process(content, file_path, only_object, only_files, force_reload)`：**唯一**的路由文件处理入口，`config_load`(两条重载) / `route_reload` / `config_call` 全部复用它，避免重复实现。
- `receiver_check` 对答复做了**双通道兜底**：先看 `event_process` 是否回填（`check_object`/`check_result`），否则从 `event_terminal.query` 的新增事件末条取用。原因：中转站的 `Subscriber/Response` 事件**不携带被查对象标识**，只能按"最近一次检查"关联。
- 新增 `object_contents`（对象→配置目录）：`Config/Reload` 与 `Call` 的载荷不含配置目录，无它则无法做路径安全检查（逐节前缀比对）。

2. 事件中转站接线（**按既有策略：由使用者自行接线，非缺陷 —— 用户裁定**）：引擎层只提供终端插槽（`attach_handler` / `event_interactor` / `event_sender` / `event_receiver` 等），**接线责任在使用者（宿主）** —— 测试层即自行接线（`碰撞测试.cpp` 内显式 `attach_handler_register(...)`）。**使用要求**：宿主须先把 `Event_Broker` 的入口注册进各终端，再调用模块的 `attach()`；否则 `attach()` 会解引用空 `unique_ptr`（而 `send` / `interact` 有存在性保护，仅返回 false）。本任务不涉及接线；Config_Loader 的接收者检查、事件响应与二次加载需宿主完成接线后方可运行。

## 九、附加：IDE/CMake 文件识别问题与 Object_Pool 新设计适配（同日追加）

### 9.1 问题：VS 报「在当前源文件的目录中或生成系统中未找到文件"XXX.h"」
**根因**：四层 `CMakeLists.txt` 均为 `file(GLOB_RECURSE ... "src/*.cpp")`，**只收 `.cpp`/`.c`，头文件从不进入任何 target**；而 `CONFIGURE_DEPENDS` 只对已列出的模式重新扫描。VS 解析 include 时只在两处找文件——「当前源文件所在目录」与「生成系统的文件清单」——头文件两头都不在，故**总是**报错，且「删除缓存并重新配置」无效（头文件依旧不在生成系统里）。

### 9.2 处置
1. 四层 `CMakeLists.txt` 各新增 `.h/.hpp` 递归收集并纳入对应目标（`EngineCore` / `SystemCore` / `TestCore` / `EngineTestObjects` / `TestLauncher` / `EngineTests` / `GameCore`）——**仅供 IDE 与生成系统建立索引，不参与编译**；测试层的 `src/主调/*.h` 单独收为 `MAIN_HEADERS`，由 `TestLauncher` 与 `EngineTests` 共用。
2. 四层开启 `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)`（Ninja 生成器默认不产出 `compile_commands.json`）。
3. VS 侧仍需执行「删除缓存并重新配置」；若仍无效，须**完全退出 VS** 后删除 `引擎层/.vs` 与仓库根 `.vs` 再重开（IntelliSense 数据库独立于 CMake 缓存）。

载荷一律 `{"route":"<索引目录>","config":"<配置目录>"}`，**无 `object` 字段**（不做对象缓存匹配）；字段缺失/为空 → `logger.error` 驳回。

| 事件 | 行为 |
| --- | --- |
| `Belived_Root/Add` | 已登记 → `logger.warn` 跳过；否则 `believed_roots.insert(root)` → `root_scan(root)` |
| `Belived_Root/Load` | 未登记则补登记 → `root_scan(root)`（**增量重建**，不清旧缓存，且服从路由文件头脏标记） |
| `Belived_Root/Unload` | 未登记 → `logger.warn` 跳过；否则 `root_cache_clear(root)` → `believed_roots.erase(root)` |

**`root_scan(root)`**：`content_scan(root.route)` → 逐路由文件 `route_file_read` 取头标记 → 命中 `mark_make(文件路径)` 则告警跳过 → 否则 `route_file_process(root, file_path, "", {}, /*deliver=*/false)`。全程**不投递**、**不回写磁盘路由文件**。

**`root_cache_clear(root)`**：`config_routes` 逐对象 `std::erase_if`（`root.route` **且** `root.config` 同为该对象目录对的前缀才剔除）；`config_files` 逐对象按键（`config_path` 转 path）以 `root.config` 为前缀剔除；两侧均清空后移除对象键。

## 三、缓存写入口与"对象自身目录对"

### 3.1 唯一写入口
`config_routes` / `config_files` 的写入全部收敛在 `route_file_process` 内：

```cpp
//推导对象自身目录对（路由文件所在目录 + 配置文件所在目录）
const Config_Content object_content(
    file_path.parent_path().lexically_relative(base_dir_get()),
    detail::string_to_path(config_path).parent_path());
config_routes[object].insert(object_content);
config_files[object][config_path] = entry;
```

- **`config_routes[对象]` = 对象自身目录对**（口径 1）：`route` = 该对象路由文件所在目录（相对基目录），`config` = 条目 `config_path` 的父目录。天然满足"对象目录 ⊆ 可信根目录"，故 `Unload` 可用前缀匹配精确圈定。
- 非投递模式（`deliver == false`）在写缓存后 `continue`；`delivered` 恒假 ⇒ 不回写磁盘路由文件。
- `path_safety_check` 仍以**扫描根** `content` 为边界（Belived_Root = 可信根，Route/load = 事件给定目录），安全检查强度未降低。

### 3.2 防御机制核查结论（未改其他链路）
| 链路 | 防御点 |
| --- | --- |
| `Route/load` | `config_routes.count(object)` + `config_routes[object].count(content)` 双判定，未登记即告警驳回 |
| `Subscriber/Call` | `config_routes[sender]` 为空即驳回；非空只遍历**已登记**目录对调 `route_load` |
| `Config/load` | `config_load` 先 `config_files.find(object)`，无记录即返回；逐文件未缓存仅告警 |
| `route_file_process` | 以 `only_object` / `only_files` 过滤，外部无法借已登记目录写入其他对象缓存 |

⇒ 缓存**成员资格**只能由 Belived_Root 链路决定，其余链路至多做等值重写。**结论：防御有效，三条链路逻辑保持原样。**

### 3.3 路径规范化（新增工具方法）
事件侧目录对来自 UTF-8 文本（`/` 分隔），磁盘侧来自 `lexically_relative`（Windows 为 `\`），直接比较/哈希必不相等 ⇒ `count(content)` 永不命中。故 `Config_Content` 构造统一走 `detail::path_normalize`，使两侧落入同一形态。`path_safety_check` 的**逐节**比较不受影响。

## 七、遗留与风险

1. **`Config/load` 的"缺省 = 该对象全部文件"未实现**：`config_load(object, paths)` 只遍历 `paths`，`paths` 为空则**什么都不加载**（事件处理器注释声称"缺省表示该对象全部文件"）。本阶段按"不改其他链路"未动它，测试改为显式传 `files`。**需你裁定**：是否补"空清单 ⇒ 投递该对象全部缓存条目"。
2. **`send({ evt }, acl_key)` 的重载歧义**：`object_config_deliver` 用花括号初始化列表发送，MSVC 解析为**单事件重载**（`shared_ptr`），故宿主必须注册**单事件** `event_sender`，仅注册批量发送会导致投递失败（本次测试接线即因此先失败后修正）。建议后续把该调用显式写成 `send(std::vector<std::shared_ptr<Event>>{ evt }, acl_key)` 以消除歧义 —— **待你裁定**。
3. **`Belived_Root/Load` 服从路由文件头脏标记**：按你的裁定实现。因缓存链路自身**不回写**头标记，该标记只可能由 `Route/load` 的投递产生；若某路由文件在 `Load` 之前已被 `Route/load` 投递过，则 `Load` 会跳过它（增量语义，非重建）。
4. **对象目录推导依赖磁盘布局**：`route` = 路由文件所在目录、`config` = `config_path` 父目录。故 `Route/load` 的载荷必须与磁盘布局推出的目录对**完全一致**才能命中（分隔符差异已由 `path_normalize` 吸收）。
5. **`content_scan` 为递归扫描**：可信根下任意深度的路由文件都会被收录；同一对象跨多目录时会形成多个目录对（集合语义，已支持）。
6. 未建立项目导航、未提交 git（沿用近期口径）。
