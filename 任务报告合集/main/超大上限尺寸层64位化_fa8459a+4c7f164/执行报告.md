## 三、核心缺陷与实测钉死

### 3.1 崩溃链条（已确认）

```cpp
// 旧代码（prepare_smart_create_params）
int father_block_size = settings.max_tree_size;        // 2^33 按模 2^32 截断 → 0
int width = recta_range.right - recta_range.left + 1;  // = 1
if (width % father_block_size != 0)                    // 1 % 0 → SEH 0xC0000094
```

### 3.2 最小复现程序的实测输出

```
[probe] 2^33 stored into int = 0
[probe] about to compute 1 % 0
[INFO] run_exit=-1073741676
```

`-1073741676` 即 `0xC0000094` 的有符号表示（`3221225620 − 2^32`），与上一版次用例注释里记录的异常码完全一致。**结论**：主崩点机制为「int 截断为 0 → 取模除零」，实测确认，非推演。

### 3.3 修复方式

`father_block_size` 提升为 `int64_t`，并在取模前加 `father_block_size <= 0` 早退（防 `set_max_size(0)` 一类误配）；同层补齐 `max_block_num_total <= 0 || max_block_size <= 0` 早退。

## 七、已知限制与遗留

1. **超大树上的范围查询仍不作为承诺**：本版次用例只覆盖「建树 ＋ 单点检索」。`range_seek` 在 2^33 边长树上做覆盖式范围查询会真实分配巨量区块，受内存物理限制；代码层已加零尺寸与乘法溢出防御（越界直接返回），但**该行为的正确性未验证**。
2. **游戏世界坐标仍受 int 约束**：对外接口保持 `Point2i`（±2^31）。这是本次的分层取舍——查询点本身 int 够用，超标的只是「树尺寸与推导边界」。若将来需要超 int 的世界坐标，需要再做一轮对外契约升级。
3. **残留 32 位类型均为已确认保留项**：`coord_set` 的 `Point2i` 等（对外契约面），非隐患。
4. **系统层 / 游戏层未触碰**，两处对四叉树 API 零引用，故不受本次契约变化影响。
5. **测试层三文件行尾状态**：工作区为 LF，检出时按仓库规则还原 CRLF，内容无差异。
