## 二、模块功能介绍

### 2.1 模块定位

「帧」模块位于渲染层源码目录 `Application/Renderer/src/render/Frame/`，与设备模块（`render/Device/`）、交换链模块（`render/Swapchain/`）、内存模块（`render/Memory/`）等并列，是渲染层中**唯一承担「一帧生命周期编排」的基础模块**。它把 Vulkan 每帧必须重复的一整套动作——**等待上一轮提交完成、向交换链取图像、重置并录制命令缓冲、提交到图形队列、呈现到呈现队列**——收拢进一个门面类 `Frame_Context`，并额外提供「在途帧轮转（帧槽）」与「延迟销毁队列」两项基础设施。

模块内部把「帧槽（命令池 / 命令缓冲 / 栅栏）的创建与销毁」「命令缓冲的录制内容（含场景绘制与可选 UI 阶段）」「提交与呈现」「延迟销毁队列」四件事拆成四个编译单元，分别放在 `core/帧槽创建.cpp`、`core/命令录制.cpp`、`core/提交呈现.cpp`、`core/延迟销毁.cpp`。`Frame_Context` 自身的构建、销毁、状态查询、帧号查询、帧槽序号查询、帧槽等待与私有栅栏等待则与帧槽创建同置一处（`core/帧槽创建.cpp`）。

一句话概括：**本模块是渲染层「把一幅画面真正送到屏幕上」的执行末端——它把门面组装好的渲染项列表（并在末尾接上可选的 UI 绘制回调）转成 Vulkan 命令，并管理多帧并行所必需的同步原语。**

### 2.2 职责边界与解决的问题

`Frame_Context` 解决的问题可归纳为七点：

1. **在途帧轮转（帧槽 / Frame-in-Flight）**。GPU 与 CPU 并行工作时，若只用一份命令缓冲与一套同步原语，CPU 在录制下一帧时会覆写 GPU 仍在执行的命令。本模块创建 `frame_overlap` 份**帧槽**（每槽独立持有命令池、主命令缓冲、完成栅栏），按下标轮转使用，使 CPU 至多领先 GPU `frame_overlap` 帧，兼顾吞吐与安全。

2. **把「每帧重复的 Vulkan 命令」固化成一次 `render` 调用**。上层的渲染门面只需依次给出「交换链、渲染项列表、清屏色、可选的 UI 绘制回调」，本模块内部完成：等栅栏 → 取图像 → 重置命令池与栅栏 → 录制布局转换与动态渲染（含场景绘制、可选 UI 阶段）→ 提交 → 呈现，并把「交换链过期/次优」这种非致命结果通过出参回传。

3. **动态渲染（Dynamic Rendering）的布局管理**。本模块不依赖传统 `VkRenderPass`，而是使用 Vulkan 1.3 的 `vkCmdBeginRendering`/`vkCmdEndRendering`。命令录制中手工完成颜色附件从 `UNDEFINED` → `COLOR_ATTACHMENT_OPTIMAL` → `PRESENT_SRC_KHR` 的两次布局转换，深度附件则由交换链模块预先转好布局，本帧仅做清屏。

4. **正确的同步原语归属与数量**。同步原语按「每帧槽」与「每交换链图像」两类归属拆分：完成栅栏（`in_flight_fence`）属**每帧槽**，数量 = `frame_overlap`，由帧模块持有；图像可用信号量（`image_available`）与呈现完成信号量（`render_finished`）均属**每交换链图像**，数量 = 交换链图像数，由交换链模块持有。本模块对二者均只「借用」，不拥有、不销毁。（本轮改动：呈现完成信号量由原先的「每帧槽」归属改为「每交换链图像」归属，`Frame_Slot::render_finished` 成员已移除。）

5. **写入前置等待（竞态修复点）**。渲染门面在调用 `render` **之前**就要写入本帧槽的场景 UBO（因为描述符集要指向本帧槽的 UBO）。若此时该帧槽上一轮提交仍在飞行，CPU 覆写会破坏 GPU 正在读取的数据。为此本模块提供 `slot_wait()`，让门面在写入前先等本帧槽栅栏；`render` 内部还会对**同一根栅栏**再等一次（届时栅栏仍为已发出态，`vkWaitForFences` 立即返回，无副作用），形成双保险。`slot_wait` 为**可选推荐**：跳过它直接 `render`，`render` 内部的等待本身也对同一栅栏有效。两处等待均经私有 `slot_fence_wait` 实现（先查栅栏状态，多数帧命中「已完成」快速路径而免去一次阻塞等待调用）。

6. **延迟销毁队列（本轮启用）**。交换链重建会牵连旧的交换链、图像视图、两类信号量与深度资源。本模块提供「把旧资源登记到延迟销毁队列、在 N 帧后回收」的机制（`deferred_push`/`deferred_flush`），以支持**无整帧停顿**重建；**本轮起已启用**——门面在交换链重建后把旧资源（`Swapchain_Old_Resources`）压入队列，延迟 = 在途帧数 + 1，由 `deferred_flush` 在到期帧释放（见 §6.7）。

7. **离屏渲染路径（本版次新增）**。除「取交换链图像 → 渲染 → 呈现」的交换链路径外，本模块新增 `render_to_target`：把场景渲染进一张**离屏渲染目标**（颜色 + 深度附件），**不取交换链图像、不呈现、无信号量**，仅以帧槽完成栅栏提交；与 `render` **共用同一批帧槽与帧计数轮转**，故两者可交替调用而不打乱在途帧同步。离屏目标由「渲染层-渲染目标」模块提供（见该模块文档），本模块只消费其颜色图像 / 颜色视图 / 深度视图 / 范围。

8. **运行时资源销毁的时序收口（本轮新增）**。运行期卸载网格 / 纹理 / 渲染目标时，要销毁的缓冲 / 图像可能仍被在途命令缓冲或描述符集引用，立即销毁会触发校验告警甚至未定义行为。本模块据此把这类资源收进延迟销毁队列——`Deferred_Entry` 新增 `memory_resources`（`std::vector<Deferred_Memory_Resource>`，逐条持缓冲 / 缓冲内存 / 图像 / 图像内存 / 视图），由 `deferred_entry_release` 在到期帧**经内存模块归还**（见 §6.7 / §6.18）。另新增公开 `frames_wait`，供门面在「修改被在途帧引用的长命对象（帧槽 `set1`、共享采样器、图形管线）」之前先收口**全部**帧槽。

9. **帧性能统计（本轮新增）**。本模块以主机侧 `std::chrono::steady_clock` 统计「录制 ＋ 提交 ＋ 呈现调用」耗时（`last_frame_ms`），并按每帧登记项累计**绘制项数**与**实例数**（`total_draw_items` / `total_instances`），经三个只读 getter（`last_frame_ms_get` / `total_draw_items_get` / `total_instances_get`）向外提供；**不引入 GPU 时间戳查询**（见 §6.18）。

10. **GPU 时间戳耗时统计（本版次第九轮新增）**。本模块在 `build` 时探测设备与图形队列族的时间戳能力，支持时为每个帧槽建立查询池，并在四条渲染路径的命令录制中写入「帧始 / 帧末」两个时间戳；提交完成后由私有 `gpu_timestamp_read` 按**帧槽环形**读回（滞后 = 在途帧数），按设备 `timestampPeriod` 换算为毫秒写入 `last_gpu_frame_ms`，经只读 getter `last_gpu_frame_ms_get` 向外提供，能力探测结果经 `gpu_timestamp_supported_get` 查询；**设备 / 队列族不支持时间戳时优雅降级**（不建查询池、GPU 耗时恒 0、不影响构建与渲染）（见 §6.19）。

11. **N 级后处理链与累计观测（本轮新增）**。`render_chain_present` 在**同一命令缓冲**内把场景渲染进 `scene_target`，再逐级 ping-pong 后处理（每级源仅可能取「偶/奇」两种中间目标之一），末级呈现到交换链；级数由调用方决定（`post_count >= 1`，`post_count == 1` 时等价于 `render_to_target_present`）。另补三个**累计**观测 getter（`total_frame_ms_get` / `total_gpu_frame_ms_get` / `gpu_sample_count_get`），把主机侧累计耗时、GPU 累计耗时、已读回 GPU 时间戳的样本数对外供出（见 §6.20 / §3.18 / §3.19）。

### 2.3 在整体架构中的位置

「帧」模块位于渲染层的**执行层**：其上游是渲染门面（`render/Renderer/`），其下游依赖交换链模块（取图像、取图像视图、取深度视图、取范围、取与归还同步原语）与 Vulkan Loader。它自身不创建任何图像或缓冲，也不持有设备——设备句柄与两条队列由门面在 `build` 时以入参注入。

```
                ┌───────────────────────────────────────────────┐
                │              Renderer（渲染器门面）             │
                │  每帧：slot_wait() → 写本帧槽 UBO/描述符集      │
                │        → render(swapchain, items, clear, ui)   │
                │  rebuild_needed 为真 → 触发交换链重建            │
                └───────┬───────────────────────────┬───────────┘
                        │ build(device, queues,      │ render / slot_wait
                        │  swapchain, frame_overlap) │ (+ ui_callback)
                        ▼                            ▼
        ┌───────────────────────────────────────────────────────────┐
        │                    Frame_Context（帧上下文）                │
        │  帧槽集合[frame_overlap]：命令池/命令缓冲/完成栅栏           │
        │  延迟销毁队列 / acquire_cursor / frame_count（轮转+释放判据）│
        │  借用：图像可用信号量、呈现完成信号量（均属每交换链图像）    │
        └───────┬───────────────┬───────────────┬───────────────────┘
        取图像/视图 │        提交命令 │      呈现     │
                ▼               ▼               ▼
        ┌───────────────┐ ┌───────────────┐ ┌───────────────┐
        │ Swapchain     │ │ 图形队列       │ │ 呈现队列       │
        │ （图像、视图、 │ │ graphics_queue│ │ present_queue  │
        │  深度视图、   │ └───────────────┘ └───────────────┘
        │  图像可用信号 │
        │  量、呈现完成 │
        │  信号量、范围）│
        └───────────────┘
```

- **向上**：调用方是渲染器门面。门面按依赖顺序在交换链就绪后调用 `build` 注入设备与交换链，每帧调用 `slot_wait` 与 `render`（第四个渲染入参为可选的 UI 绘制回调），并在 `rebuild_needed_out` 为真时组织交换链重建。
- **向下**：依赖交换链模块（`Swapchain_Context` 的 getter、`image_available_semaphore_get`、`render_finished_semaphore_get`）、Vulkan Loader（`vk*` 全部调用）、引擎核心层日志系统（`logger`，经 `结果检查.h` 间接引入）。
- **横向**：本模块不依赖内存、设备、管线、网格、纹理等模块的头文件——它只持裸 Vulkan 句柄，故与这些模块无编译期依赖边。UI 绘制回调的「上层实现」位于渲染器模块的 UI 通道（`Ui_Channel_Context::draw_callback_get`）与 Test 层之间，本模块只按 `Frame_Ui_Callback` 定义调用之（见 6.14）。

### 2.4 与相邻模块的职责分界

| 相邻模块 | 分界 |
| --- | --- |
| 交换链模块（`render/Swapchain/`） | 交换链模块**拥有**交换链、图像视图、图像可用信号量与深度图像，并负责重建；**本轮起亦拥有呈现完成信号量（每交换链图像一组）**。帧模块只**借用**它们（`handle_get`/`image_get`/`image_view_get`/`depth_view_get`/`extent_get`/`image_available_semaphore_get`/`render_finished_semaphore_get` 等），并在取图像返回过期/次优时**置标志**交由上层重建，自身**不重建**交换链。 |
| 渲染器门面（`render/Renderer/`） | 门面负责**编排与决策**：组装渲染项、在写 UBO 前调用 `slot_wait`、依据 `rebuild_needed_out` 组织重建、决定 `frame_overlap` 取值、每帧取 UI 绘制回调传入 `render`。帧模块只保证「单帧执行正确、失败不留半成品、`destroy` 幂等」。门面还负责在 `init` 中把 `frame_overlap` 钳制到图像可用信号量数以内（K13 的前提，见 6.8），再把调整后的值传入 `build`。 |
| 设备模块（`render/Device/`） | 设备模块提供 `VkDevice`、物理设备、图形/呈现队列族与两条队列；帧模块**不创建设备**，只在 `build` 时接收并保存这些句柄（`physical_device`/`present_family` 仅保存备用，当前源码未使用）。 |
| 内存模块（`render/Memory/`） | 帧模块**不创建任何缓冲/图像**；命令缓冲由 `vkAllocateCommandBuffers` 直接分配，不经内存模块。深度图像由交换链模块经内存模块创建。像素回读缓冲经 `Memory_Context` 创建 / 销毁（本模块与内存模块的唯一依赖边，见 3.12）。 |
| 渲染目标模块（`render/RenderTarget/`，`Render_Target_Context`） | 该模块持有离屏渲染目标的颜色 / 深度图像与视图；本模块 `render_to_target` **消费**其附件集合 `Frame_Render_Target`（由门面经 `target_get` 组装后传入），把场景渲染进该目标。本模块**不创建目标、不拥有其图像**；二者无直接编译期依赖边（图像 / 视图 / 范围均以裸句柄经门面传入）。 |
| 「渲染层-渲染器」模块的 `结果检查.h` | 帧模块全部 `VkResult` 检查都调用该头的 `vk_result_check`（唯一检查出口），而 `vkGetFenceStatus`/`vkWaitForFences` 的查询与等待、`vkResetFences` 的重置亦统一经它判定。 |
| 「渲染层-渲染器」模块的 UI 通道（`渲染器_UI通道.h`、`core/UI通道.cpp`） | 该模块以 `Ui_Channel_Context::draw_callback_get()` 向外提供 `const Frame_Ui_Callback*`（`Frame_Ui_Callback` 类型定义于本模块 `帧上下文.h`）；门面每帧取之传给 `render`。帧模块只定义该回调类型并在场景 pass 内调用之，不持有、不代管 UI（见 6.14）。 |
| 日志系统（`Engine/EngineCore/src/tools/Logging/`） | 帧模块只把 `logger` 当输出通道使用，不配置日志规则。 |

### 2.5 生命周期与调用契约

`Frame_Context` 的完整生命周期为：

```
构造（default，不创建任何 Vulkan 对象）
   → build(device, physical_device,
           graphics_family, graphics_queue,
           present_family, present_queue,
           swapchain, frame_overlap)          ← 创建 frame_overlap 个帧槽
   → [每帧]（交换链路径）
        slot_wait()                            ← 门面写本帧槽 UBO 之前（可选但推荐）
        render(swapchain, items, count,
               rebuild_needed_out, clear,
               ui_callback)                    ← 取图像 → 录制 → 提交 → 呈现
        （rebuild_needed_out 为真 → 上层重建交换链）
   → [每帧]（离屏路径；本版次新增）
        render_to_target(target, items, count,
                          clear, ui_callback)  ← 录制进目标 → 仅以帧槽栅栏提交 →（可选）回读
   → destroy()                                 ← 幂等；先 vkDeviceWaitIdle，再销毁帧槽
   → 析构（兜底再调用一次 destroy，保证资源不泄漏）
```

- 状态机只有两态：**未构建完成**与**构建完成**。`valid()` 的判据是「逻辑设备句柄非空 且 帧槽集合非空」。
- `destroy()` 可重复调用，第二次及以后为空操作；析构函数内部再调一次 `destroy()`，因此「显式销毁 + 析构」不会重复释放。
- 类**不可拷贝、不可移动**（持有 Vulkan 句柄与队列），以 `= delete` 显式禁用。
- `render` 的 `ui_callback` 形参默认为 `nullptr`，属**可选**入参；传入空回调时命令录制的 UI 阶段整体跳过。
- **调用契约（重要）**：帧槽集合一旦按 `frame_overlap` 建立，`frame_overlap` 在生命周期内**不应改变**（`slot_index_get` 与 `render` 均以下标 `% frame_overlap` 定位帧槽）；同一帧内「门面写 UBO 的槽」必须与「`render` 实际使用的槽」一致，这正是 `slot_wait`/`slot_index_get` 存在的意义。
- **双路径共用轮转（本版次）**：`render` 与 `render_to_target` **共用同一批帧槽与同一 `frame_count` 轮转**，故两者可在同一进程内交替调用（如「先离屏渲染进目标、再切回交换链采样显示」），不会打乱在途帧同步；`slot_index_get` / `slot_wait` 对两条路径同样适用（见 §6.16）。
- **运行时卸载收口（本轮）**：门面在运行时卸载网格 / 纹理 / 渲染目标时不再立即销毁，而是「`*_detach` 摘出 → 组装 `Deferred_Entry`（缓冲 / 图像填入 `memory_resources`）→ `deferred_push(entry, in_flight_count_get() + 1)`」，由 `deferred_flush` 在到期帧释放；销毁 / 更新仍被在途帧引用的长命对象（帧槽 `set1`、共享采样器、具名图形管线）前，门面先调 `frames_wait()` 收口全部帧槽（见 §6.18）。

### 3.3 构造与析构

#### 3.3.1 `Frame_Context(void) = default`

- **签名**：隐式等价于默认构造。
- **参数**：无。**返回值**：无（构造）。
- **约束**：**不创建任何 Vulkan 对象**。各句柄成员保持 `VK_NULL_HANDLE`、各计数保持 `0`、`slots` 与 `deferred_entries` 为空。默认构造后的对象处于「未构建完成」态，`valid()` 为假。

#### 3.3.2 `~Frame_Context(void)`

- **签名**：`~Frame_Context(void)`。**实现**：`core/帧槽创建.cpp`。
- **约束与行为**：函数体只有一步——调用 `destroy()`。因此析构是**资源不泄漏的最后兜底**：即便调用方忘记显式 `destroy()`，析构也会在设备句柄仍有效时释放全部帧槽。因 `destroy()` 幂等，析构不会重复释放。

#### 3.3.3 拷贝/移动删除

- **签名**：`Frame_Context(const Frame_Context&) = delete` 与 `Frame_Context& operator=(const Frame_Context&) = delete`。
- **约束**：显式删除拷贝构造与拷贝赋值；未声明移动构造/移动赋值，故移动同样不可用。原因：对象持有 Vulkan 句柄与队列，浅拷贝会导致同一句柄被 `destroy` 两次。

### 3.4 `build`（构建：创建帧槽集合）

- **签名**：`bool build(VkDevice device, VkPhysicalDevice physical_device, uint32_t graphics_family, VkQueue graphics_queue, uint32_t present_family, VkQueue present_queue, Swapchain_Context& swapchain, Memory_Context& memory, uint32_t frame_overlap)`（本版次新增 `memory` 形参）
- **声明**：`帧上下文.h`；**实现**：`core/帧槽创建.cpp`。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `device` | `VkDevice` | 逻辑设备句柄 | 必须非 `VK_NULL_HANDLE`，否则报错返回假 |
| `physical_device` | `VkPhysicalDevice` | 物理设备句柄 | 仅**保存备用**，当前源码未使用；允许为空 |
| `graphics_family` | `uint32_t` | 图形队列族索引 | 用于命令池的 `queueFamilyIndex`，须与 `graphics_queue` 所属族一致 |
| `graphics_queue` | `VkQueue` | 图形队列 | 必须非 `VK_NULL_HANDLE`，否则报错返回假；提交命令的目标队列 |
| `present_family` | `uint32_t` | 呈现队列族索引 | 仅保存备用，当前源码未使用 |
| `present_queue` | `VkQueue` | 呈现队列 | 必须非 `VK_NULL_HANDLE`，否则报错返回假；呈现的目标队列 |
| `swapchain` | `Swapchain_Context&` | 已构建的交换链上下文 | `swapchain.valid()` 必须为真，否则报错返回假；帧链路取图像依赖它 |
| `memory` | `Memory_Context&` | 已构建的内存上下文 | `memory.valid()` 必须为真，否则报错返回假；像素回读缓冲的创建 / 销毁依赖它（本版次新增，形成依赖边 Frame → Memory） |
| `frame_overlap` | `uint32_t` | 在途帧数（帧槽数量） | 必须为正，为 0 报错返回假 |

- **返回值**：`bool`。`true` 表示全部帧槽创建成功；`false` 表示前置检查失败或任一帧槽创建失败（此时已内部回退）。
- **行为要点**：
  1. **四重前置检查**（均为 `logger.error` 后返回假）：`device`/`graphics_queue`/`present_queue` 任一为 `VK_NULL_HANDLE`；`!swapchain.valid()`；`!memory.valid()`（本版次新增）；`frame_overlap == 0`。
  2. 记录设备与队列到私有字段（含 `physical_device`/`present_family`），并记录 `this->memory = &memory`（本版次新增）；**第九轮新增**：据 `physical_device` 探测 GPU 时间戳能力——`vkGetPhysicalDeviceProperties` 取 `limits.timestampPeriod`（纳秒 / tick）与 `limits.timestampComputeAndGraphics`，`vkGetPhysicalDeviceQueueFamilyProperties` 取图形队列族（`graphics_family`）的 `timestampValidBits`；**三项同时满足**（`timestampComputeAndGraphics == VK_TRUE` 且 `timestampPeriod > 0` 且 `validBits > 0`）才置 `timestamp_supported = true`，否则记 `logger.warn` 并**优雅降级**（保持 `timestamp_supported = false`，`frame_slot_create` 不建查询池、GPU 耗时恒 0，不影响构建与渲染）。
  3. `slots.resize(frame_overlap)` 后**逐个**调用 `frame_slot_create(slots[index])`。
  4. **任一帧槽失败即整体回退**：记 `logger.error("帧上下文:: 第 {} 个帧槽创建失败，回退", index)`，调用 `destroy()`（先 `vkDeviceWaitIdle` 再回收已建帧槽、清空集合），返回假。
  5. 成功记 `logger.info("帧上下文:: 帧基础设施构建完成（在途帧 {}，交换链图像 {}，图像可用信号量 {}，呈现完成信号量 {}）", frame_overlap, swapchain.image_count_get(), swapchain.image_available_count_get(), swapchain.render_finished_count_get())`，返回真（本轮起日志新增「呈现完成信号量」项，取自交换链的 `render_finished_count_get()`）。
- **幂等/重入**：`build` 本身**不**先 `destroy`；若在已构建对象上重复调用 `build`，会覆盖 `slots.resize` 造成旧帧槽句柄泄漏。故约定 `build` 只在未构建状态下调用一次。

### 3.5 `destroy`（销毁）

- **签名**：`void destroy(void)`。**实现**：`core/帧槽创建.cpp`。
- **参数/返回值**：无。
- **约束与行为**：**幂等**：
  1. 若 `device != VK_NULL_HANDLE`：先 `vkDeviceWaitIdle(device)`（等设备空闲，避免销毁仍在使用的对象），再**顺序**遍历 `slots` 逐个 `frame_slot_destroy`（注：源码为 `for` 正序遍历，注释称「逆序销毁全部帧槽」，实际为顺序遍历，因各帧槽相互独立，顺序不影响正确性）；**同分支内随后调用私有 `readback_buffer_destroy()` 归还像素回读缓冲**（须先于内存模块销毁；本版次新增）；**再调用私有 `deferred_release_all()` 立即释放全部残留的延迟销毁条目**（关闭前已等设备空闲，故不再按 `release_frame` 判据；**须先于内存模块销毁**，否则残留的旧深度图像与其内存会泄漏——曾实测触发 VMA `Unfreed dedicated allocations found!` 断言；本轮新增）。
  2. `slots.clear()`、`deferred_entries.clear()`。
  3. 复位全部句柄与计数：`device`/`physical_device`/`graphics_queue`/`present_queue` 置 `VK_NULL_HANDLE`，`graphics_family`/`present_family`/`frame_overlap`/`acquire_cursor`/`frame_count` 置 `0`，并把 `memory` 复位为 `nullptr`（本版次新增）；**本轮起**另复位帧统计三字段 `last_frame_ms = 0.0`、`total_draw_items = 0`、`total_instances = 0`；**第九轮新增**再复位 GPU 时间戳四字段 `timestamp_supported = false`、`timestamp_period = 0.0f`、`timestamp_valid_bits = 0`、`last_gpu_frame_ms = 0.0`（各槽查询池已随 `frame_slot_destroy` 归还）；**本轮新增**另复位三个累计字段 `total_frame_ms = 0.0`、`total_gpu_frame_ms = 0.0`、`gpu_sample_count = 0`；**第十一轮新增**再复位实际绘制量三字段 `total_drawn_items = 0`、`total_drawn_instances = 0`、`frame_recorded = Recorded_Counts{}`（紧随 `total_instances = 0`）。
- **注意**：`destroy` 只销毁帧槽自有对象（命令池、命令缓冲随池回收、完成栅栏）；借用的交换链对象（交换链、图像、图像视图、深度图像、图像可用信号量与呈现完成信号量）**不**在其职责内。

### 3.6 `valid`（状态查询）

- **签名**：`bool valid(void) const`。
- **返回值**：`device != VK_NULL_HANDLE && !slots.empty()`。
- **语义**：仅当「逻辑设备已记录 且 至少一个帧槽存在」时为真。**不**检查各帧槽内部句柄是否齐全（`frame_slot_create` 已保证成功返回时帧槽自洽）。

### 3.7 `render`（渲染一帧）

- **签名**：`bool render(Swapchain_Context& swapchain, const Frame_Render_Item* items, uint32_t item_count, bool& rebuild_needed_out, const float clear_color[4], const Frame_Ui_Callback* ui_callback = nullptr, Frame_Readback_Request* readback = nullptr)`（本版次新增末位 `readback` 形参）
- **声明**：`帧上下文.h`；**实现**：`core/提交呈现.cpp`。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `swapchain` | `Swapchain_Context&` | 当前交换链 | `valid()` 须为真，且图像数、图像可用信号量数、呈现完成信号量数均非 0，否则报错返回假 |
| `items` | `const Frame_Render_Item*` | 渲染项数组首地址 | 可为空指针；为空或 `item_count == 0` 时只清屏 |
| `item_count` | `uint32_t` | 渲染项数量 | `items` 非空时表示有效元素个数 |
| `rebuild_needed_out` | `bool&` | 出参：是否需要重建交换链 | 进入时被**无条件置假**；取图像或呈现返回过期/次优时置真 |
| `clear_color` | `const float[4]` | 清屏色 RGBA | 须至少 4 个 `float` 有效 |
| `ui_callback` | `const Frame_Ui_Callback*` | UI 绘制回调（可空，默认 `nullptr`） | 非空且 `fn` 非空时，在场景 pass 内、`vkCmdEndRendering` 之前调用 |
| `readback` | `Frame_Readback_Request*` | 像素回读请求（可空，默认 `nullptr`） | 非空且 `->pixels` 非空时本帧把颜色附件拷回该缓冲；须交换链具备传输源用法且 `capacity >= 宽 × 高 × 4`，否则报错返回假（本版次新增） |

- **返回值**：`bool`。`true` 表示本帧被正常处理（**含**「取图像/呈现返回过期或次优、已置 `rebuild_needed_out` 并跳过本帧」的情形）；`false` 视为硬错误（前置失败、等栅栏失败、取图像硬错误、重置栅栏/命令池失败、提交/呈现硬错误）。
- **行为要点（完整顺序）**：
  1. `rebuild_needed_out = false`。
  2. 前置检查 `!valid() || !swapchain.valid()` → `logger.error("提交呈现:: 帧上下文或交换链尚未构建")`，返回假。
  3. 前置检查 `swapchain.image_count_get() == 0 || swapchain.image_available_count_get() == 0 || swapchain.render_finished_count_get() == 0` → `logger.error("提交呈现:: 交换链图像或信号量为空")`，返回假（本轮起新增「呈现完成信号量数非 0」这一条件，并把日志文案由「交换链图像或图像可用信号量为空」改为「交换链图像或信号量为空」）。
  4. **取当前帧槽**：`Frame_Slot& slot = slots[frame_count % frame_overlap]`（此处按 `frame_count` 取槽，与 `slot_index_get` 同一基准）。
  5. **等待该帧槽前一次提交完成**：调用私有 `slot_fence_wait(slot)`（先 `vkGetFenceStatus` 查状态，已完成立即返回；未就绪再 `vkWaitForFences`，超时 `UINT64_MAX`、`waitAll` 为真；查询硬错误经 `vk_result_check`）。失败返回假。
  6. **取图像可用信号量**：`swapchain.image_available_semaphore_get(acquire_cursor % swapchain.image_available_count_get())`（轮转游标在信号量池中顺序取用；取图像前图像索引未知）。
  7. **取下一张交换链图像**：`vkAcquireNextImageKHR(device, swapchain.handle_get(), UINT64_MAX, image_available, VK_NULL_HANDLE, &image_index)`。
     - 若返回 `VK_ERROR_OUT_OF_DATE_KHR` 或 `VK_SUBOPTIMAL_KHR`：置 `rebuild_needed_out = true`，记 `logger.debug("提交呈现:: 取图像返回 {}，标记交换链待重建", vk_result_name_get(acquire))`，**提前返回真**（不作为硬错误）。
     - 若为其它非成功码：经 `vk_result_check` 记日志，返回假。
     - 成功：`++acquire_cursor`。
  8. **重置本帧槽完成栅栏**（**放在取图像成功之后**）：`vkResetFences(device, 1, &slot.in_flight_fence)` 经检查；失败返回假。
  9. **重置本帧槽命令池**：`vkResetCommandPool(device, slot.command_pool, 0)` 经检查；失败返回假。
  10. **像素回读准备（可选；本版次新增）**：`readback_active = (readback != nullptr && readback->pixels != nullptr)`；为真时①校验 `swapchain.color_transfer_src_get()`（为假记 `logger.error("提交呈现:: 交换链图像不具备传输源用法，像素回读不可用")` 并返回假），②校验 `readback->capacity >= 宽 × 高 × 4`（不足记 `logger.error("提交呈现:: 回读目标容量不足（需 {} 字节，有 {} 字节）", …)` 并返回假），③`readback_buffer_ensure(宽 × 高 × 4)` 让回读缓冲就绪，取得 `readback_target`（未请求回读时保持 `VK_NULL_HANDLE`）。
  11. **录制命令缓冲**：`command_record(slot.command_buffer, swapchain.image_get(image_index), swapchain.image_view_get(image_index), swapchain.depth_view_get(image_index), swapchain.extent_get(), items, item_count, clear_color, ui_callback, readback_target)`（末位传入本帧 UI 回调与回读缓冲句柄）。
  12. **取本帧呈现完成信号量**：`VkSemaphore render_finished = swapchain.render_finished_semaphore_get(image_index);`（本轮起：呈现完成信号量属「每交换链图像」，按本次 acquire 得到的 `image_index` 取用，而非再取帧槽自有信号量）。
  13. **提交并呈现**：`submit_present(slot, image_index, image_available, render_finished, swapchain, rebuild_needed_out)`；失败返回假。
  14. **像素读出（可选；本版次新增）**：`readback_active` 为真时调用 `readback_read(slot, *readback, swapchain.extent_get())`（等本帧槽完成栅栏 → 经内存模块读回主机 → 回填宽 / 高 / 字节数）；失败返回假。
  15. **推进计数**：`++frame_count;`（单一帧计数，兼作帧槽轮转依据与延迟销毁的释放判据）。
  16. **释放到期延迟销毁条目**：`deferred_flush()`。
  17. 返回真。

### 3.8 `frame_count_get`（已推进帧数查询）

- **签名**：`uint32_t frame_count_get(void) const`。**返回值**：`frame_count`。
- **语义**：返回自 `build` 成功以来**成功提交并呈现**的帧数（每次 `render` 走到末尾才自增；取图像/呈现返回过期而提前返回时**不自增**）。`destroy` 后复位为 `0`。

### 3.9 `slot_index_get`（本帧槽序号查询）

- **签名**：`uint32_t slot_index_get(void) const`。**返回值**：`frame_overlap == 0 ? 0 : frame_count % frame_overlap`。
- **语义**：返回「**本次 `render` 将要使用的**帧槽序号」，供门面在调用 `render` **之前**取用同一槽的场景 UBO / 描述符集，保证与帧内部一致。
- **实现注意**：本函数与 `render` 内部**同以 `frame_count % frame_overlap` 计算槽号**（本轮起已把原 64 位帧序号成员并入 `frame_count`，见 6.6），故两者结果必然一致，门面依据 `slot_index_get` 写入的槽与 `render` 实际使用的槽不会错位。

### 3.10 `slot_wait`（等待本帧槽栅栏）

- **签名**：`bool slot_wait(void)`。**实现**：`core/帧槽创建.cpp`。
- **参数**：无。
- **返回值**：`bool`。`true` 表示等待成功；`false` 表示帧上下文未构建或等待失败。
- **语义与约束**：**供门面在写入「本帧槽」资源（如场景 UBO）之前调用**，避免 CPU 覆写 GPU 仍在读取的上一轮内容。
  - 若 `!valid()`：记 `logger.error("帧槽创建:: 帧上下文尚未构建，无法等待帧槽")`，返回假。
  - 取本帧槽 `slots[frame_count % frame_overlap]`，调用私有 `slot_fence_wait(slot)`（本轮起不再直接调 `vkWaitForFences`，改经该私有方法：先查状态，未完成再阻塞等待）。
  - `render` 内部还会再等一次**同一根帧栅栏**。两处等待之间**不发生栅栏重置**（重置只发生在 `vkAcquireNextImageKHR` 成功之后，见 6.2），届时该栅栏仍为已发出态，`vkWaitForFences` 立即返回，无副作用。源码注释描述的是「先 `slot_wait` 后 `render`」的**推荐时序**，而非调用必要性约束：**跳过 `slot_wait` 直接 `render` 也能正确等待该槽栅栏**（`render` 内部对同一栅栏的等待本身即有效）。

### 3.11 `render_to_target`（离屏渲染一帧；本版次新增）

- **签名**：`bool render_to_target(const Frame_Render_Target& target, const Frame_Render_Item* items, uint32_t item_count, const float clear_color[4], const Frame_Ui_Callback* ui_callback = nullptr, Frame_Readback_Request* readback = nullptr)`
- **声明**：`帧上下文.h`；**实现**：`core/提交呈现.cpp`。
- **语义**：把场景渲染进一张**离屏渲染目标**，**不取交换链图像、不呈现、无信号量**；仅以帧槽完成栅栏提交。顺序为：帧槽等待 → 重置栅栏 / 命令池 → 回读缓冲就绪 → `command_record_target` → 提交 →（可选）回读 → 帧计数推进 + 延迟销毁刷新。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `target` | `const Frame_Render_Target&` | 离屏目标附件集合（颜色图像 / 颜色视图 / 深度视图 / 范围） | 颜色图像、颜色视图须非空、范围宽高非零，否则报错返回假；约定颜色进入时为 `SHADER_READ_ONLY_OPTIMAL`、深度进入时恒为 `DEPTH_ATTACHMENT_OPTIMAL` |
| `items` | `const Frame_Render_Item*` | 渲染项数组首地址 | 可为空；为空或 `item_count == 0` 时只清屏 |
| `item_count` | `uint32_t` | 渲染项数量 | —— |
| `clear_color` | `const float[4]` | 清屏色 RGBA | —— |
| `ui_callback` | `const Frame_Ui_Callback*` | UI 绘制回调（可空，默认 `nullptr`） | 与 `render` 同一时机（场景 pass 内、`vkCmdEndRendering` 之前） |
| `readback` | `Frame_Readback_Request*` | 像素回读请求（可空，默认 `nullptr`） | 非空且 `->pixels` 非空时把**目标颜色附件**拷回该缓冲；须 `capacity >= 目标宽 × 高 × 4`，否则报错返回假 |

- **返回值**：`bool`。`true` 表示本帧被正常处理；`false` 视为硬错误（前置失败、等栅栏失败、重置栅栏 / 命令池失败、提交失败、容量不足）。
- **行为要点（完整顺序）**：
  1. 前置检查 `!valid() || target.color_image == VK_NULL_HANDLE || target.color_view == VK_NULL_HANDLE || 宽高为 0` → `logger.error("提交呈现:: 帧上下文或离屏目标尚未就绪")`，返回假。
  2. **取当前帧槽**：`Frame_Slot& slot = slots[frame_count % frame_overlap]`（与 `render` **共用同一轮转**）。
  3. **等待该帧槽前一次提交完成**：`slot_fence_wait(slot)`；失败返回假。
  4. **重置本帧槽完成栅栏**：`vkResetFences`（离屏路径无「取图像」步骤，故栅栏重置紧随等待之后）；失败返回假。
  5. **重置本帧槽命令池**：`vkResetCommandPool`；失败返回假。
  6. **像素回读准备（可选）**：`readback_active = (readback != nullptr && readback->pixels != nullptr)`；为真时校验 `readback->capacity >= 目标宽 × 高 × 4`（不足记 error 返回假），再 `readback_buffer_ensure(目标宽 × 高 × 4)` 取得 `readback_target`。**回读来源为目标的颜色附件**，故不做交换链传输源能力校验。
  7. **录制命令缓冲**：`command_record_target(slot.command_buffer, target, items, item_count, clear_color, ui_callback, readback_target)`（见 §四.9）。
  8. **仅以完成栅栏提交**：构造 `VkCommandBufferSubmitInfo` + `VkSubmitInfo2`（**无等待信号量、无信号信号量**，仅 `pCommandBufferInfos`），`vkQueueSubmit2(graphics_queue, 1, &submit_info, slot.in_flight_fence)`；失败返回假。
  9. **像素读出（可选）**：`readback_active` 为真时 `readback_read(slot, *readback, target.extent)`；失败返回假。
  10. **推进计数**：`++frame_count;`。
  11. **释放到期延迟销毁条目**：`deferred_flush()`。
  12. 返回真。
- **与 `render` 的差异**：无 `swapchain` 入参、无 `rebuild_needed_out` 出参；不取交换链图像、不提交信号量、不呈现；回读来源为目标颜色附件（而非交换链颜色附件）。**相同点**：帧槽轮转、栅栏等待 / 重置、命令池重置、UI 回调时机、回读缓冲与 `frame_count` 推进完全一致。

### 3.14 `render_to_target_present`（同帧多 pass：目标 → 后处理 → 交换链；本轮新增；第十轮起为薄封装）

- **签名**：`bool render_to_target_present(Swapchain_Context& swapchain, const Frame_Render_Target& target, const Frame_Render_Item* items, uint32_t item_count, const Frame_Render_Item& post_item, const float clear_color[4], bool& rebuild_needed_out, Frame_Readback_Request* readback = nullptr)`
- **声明**：`帧上下文.h`；**实现**：`core/提交呈现.cpp`。
- **语义**：在**同一命令缓冲**内先以 `items` 把场景渲染进离屏目标（pass 1），随即以 `post_item` 做一次全屏后处理 pass 采样该目标并**呈现到交换链**（pass 2）。取图像 / 提交 / 呈现 / 回读与 `render` 同口径（帧槽等待 / 重置栅栏 / 重置命令池 / 取图像可用与呈现完成信号量 / `submit_present` 呈现 / `frame_count` 推进 / `deferred_flush`）；**回读来源为交换链颜色附件**（即后处理输出）。**无 UI 回调参数**（该路径不经过 UI 回调）。
- **第十轮收口（薄封装）**：本函数已降级为 `render_chain_present` 的**单级特例薄封装**——函数体只剩一行 `return render_chain_present(swapchain, &target, 1, items, item_count, &post_item, 1, clear_color, rebuild_needed_out, readback);`（目标组仅 1 项、后处理级数 = 1）。文件内注释与头文件注释均注明「第十轮收口：本函数是 render_chain_present 的单级特例薄封装」。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `swapchain` | `Swapchain_Context&` | 当前交换链 | `valid()` 须为真；图像与两类信号量数非 0 |
| `target` | `const Frame_Render_Target&` | 离屏目标附件（颜色图像 / 颜色视图 / 深度视图 / 范围） | 颜色图像 / 颜色视图 / 深度视图须非空、范围宽高非零 |
| `items` / `item_count` | 同 `render` | **第一个 pass（场景）**的渲染项 | 可为空（只清屏） |
| `post_item` | `const Frame_Render_Item&` | **第二个 pass（后处理）**的单个绘制项（管线 / 布局 / 描述符集 / 全屏几何 / 实例缓冲） | 管线 / 布局 / 顶点 / 索引 / 索引数 / 实例缓冲 / 实例数须齐备，否则前置失败 |
| `clear_color` | `const float[4]` | 清屏色（两 pass 共用） | —— |
| `rebuild_needed_out` | `bool&` | 出参：是否需要重建（取图像 / 呈现返回过期或次优时置真） | 进入即被置假 |
| `readback` | `Frame_Readback_Request*` | 像素回读请求（可空） | 非空且 `->pixels` 非空时把**交换链颜色附件**拷回；须交换链具备传输源用法且 `capacity >= 宽 × 高 × 4` |

- **前置与流程**：见 `render_chain_present`（§3.18）的单级特例（`post_count = 1`、目标组仅含 `target`）——原「帧上下文 / 交换链 / 目标 / `post_item` 完备」校验、「取图像 → 录制 → 提交 → 呈现 → 回读」流程与统计累计均由 `render_chain_present` 统一执行；**本函数不再有独立实现**，自身不校验、不录制、不计时。
- **要求**：`target` / `post_item` 的完备性约束不变，但由 `render_chain_present` 承担；**目标范围与交换链范围一致**亦由 `render_chain_present` 做硬校验（不一致 → `logger.error` 记录两侧尺寸并返回假，处置 `R-FRAME-09`），见 §3.18 / §6.20。

### 3.15 `frames_wait`（等待全部帧槽；本轮新增）

- **签名**：`bool frames_wait(void)`。**实现**：`core/帧槽创建.cpp`。
- **参数**：无。
- **返回值**：`bool`。`true` 表示全部帧槽的前一次提交均已完成；`false` 表示帧上下文未构建或任一帧槽等待失败。
- **语义与约束**：与 `slot_wait` 同源（逐槽经私有 `slot_fence_wait`「先查状态、未完成再阻塞等待」），差别在于**遍历全部帧槽**而非仅本帧槽。供门面在「修改被在途命令缓冲 / 描述符集引用的**长命对象**」之前调用——即 `texture_bind_set` / `texture_bind_target` 写满全部帧槽 `set1` 之前、`texture_sampler_state_set` 销毁并重建共享采样器之前、`pipeline_unload` 注销图形管线之前（见 §6.18 与《渲染层-渲染器》）。
  - 若 `!valid()`：记 `logger.error("帧槽创建:: 帧上下文尚未构建，无法等待全部帧槽")`，返回假。
  - 逐槽调 `slot_fence_wait`，任一失败即返回假（不继续）。
- **与 `slot_wait` 的关系**：`slot_wait` 只保护「本帧槽的 UBO 写入」；`frames_wait` 保护「被任意帧槽引用的长命资源」，故二者不可互相替代。

### 3.16 帧统计三个 getter（本轮新增）

- **签名**：`double last_frame_ms_get(void) const`、`uint64_t total_draw_items_get(void) const`、`uint64_t total_instances_get(void) const`。**实现**：`core/帧槽创建.cpp`。
- **返回值**：
  - `last_frame_ms_get`：最近一帧**主机侧**耗时（毫秒）——`render` / `render_to_target` / `render_to_target_present` / `render_chain_present` 以 `std::chrono::steady_clock` 在「录制前取起点、提交（呈现）后取终点」，故区间为「录制 ＋ 提交 ＋ 呈现调用」，**不含 GPU 时间戳**；`destroy` 复位为 `0.0`。
  - `total_draw_items_get`：自 `build` 成功以来累计的**绘制项数**——按每帧登记项计（`render` / `render_to_target` 累加 `item_count`；`render_to_target_present` 在场景项之外**另加 1** 个后处理绘制项，**第十轮起经薄封装由 `render_chain_present`（`post_count = 1`）累计，口径与结果不变**；`render_chain_present` 在场景项之外**另加 `post_count`** 个后处理绘制项）；`destroy` 复位为 `0`。
  - `total_instances_get`：累计**实例数**——各绘制项 `instance_count` 之和（`render_to_target_present` 另计后处理项的 `instance_count`，**第十轮起同由链路径逐级累计**；`render_chain_present` 逐级另计各级 `instance_count`）；`destroy` 复位为 `0`。
- **用途**：供门面 `frame_stats_get` 组装 `Frame_Stats` 快照（见《渲染层-渲染器》§3.4.42）。
- **口径提示**：本组 getter 按**登记项**累计（被跳过的渲染项仍计入 `item_count`），故与 GPU 实际绘制量可能不等——**第十一轮起**实际绘制量另由 `total_drawn_items_get` / `total_drawn_instances_get` 分列（见 §3.20 / §6.21），两量相等即表示所有登记项都真正下达了绘制命令。原「是否应改为仅计实际绘制项」的待确认 **`R-FRAME-10` 已结案**（口径定为分列，见附录 C）。

### 3.17 GPU 耗时的两个 getter（本版次第九轮新增）

- **签名**：`bool gpu_timestamp_supported_get(void) const`、`double last_gpu_frame_ms_get(void) const`。**实现**：`core/帧槽创建.cpp`。
- **参数**：无。
- **返回值**：
  - `gpu_timestamp_supported_get`：`timestamp_supported`——`build` 能力探测结果（设备 `limits.timestampComputeAndGraphics == VK_TRUE` ＋ `timestampPeriod > 0` ＋ 图形队列族 `timestampValidBits > 0` 三项同时满足才为真）；未构建 / 能力不足为假。
  - `last_gpu_frame_ms_get`：最近一次读回的 **GPU 耗时**（毫秒）——由私有 `gpu_timestamp_read` 在「`slot_fence_wait` 之后、本帧录制之前」读该帧槽**上一轮**提交的时间戳，按 `(end − begin) × timestampPeriod / 1e6` 换算；能力不足时恒为 `0.0`；`destroy` 复位为 `0.0`。
- **用途**：供门面 `frame_stats_get` 填 `Frame_Stats.gpu_frame_ms`，并由门面 `gpu_timestamp_supported()` 转调本 getter（见《渲染层-渲染器》§3.4.42 / §3.4.43）。
- **口径提示**：读回为**帧槽环形**、滞后 = 在途帧数；同帧多 pass 路径含两个 pass 之和；`timestampValidBits < 64` 时掩高位（见 §6.19 与 `R-FRAME-11`）。【待确认：R-FRAME-11】

### 3.18 `render_chain_present`（N 级后处理链：场景 → 逐级多目标轮转后处理 → 呈现；本轮新增；第十五轮改多目标）

- **签名**：`bool render_chain_present(Swapchain_Context& swapchain, const Frame_Render_Target* targets, uint32_t target_count, const Frame_Render_Item* items, uint32_t item_count, const Frame_Render_Item* post_items, uint32_t post_count, const float clear_color[4], bool& rebuild_needed_out, Frame_Readback_Request* readback = nullptr)`
- **声明**：`帧上下文.h`；**实现**：`core/提交呈现.cpp`。
- **语义**：在**同一命令缓冲**内先以 `items` 把场景渲染进 `targets[0]`，随后顺序执行 `post_count` 级后处理：**第 i 级源 = `targets[i % target_count]`、非末级宿 = `targets[(i + 1) % target_count]`**（末级恒呈现到交换链）。取图像 / 提交 / 呈现 / 像素回读与 `render_to_target_present` **同口径**（共用 `submit_present` 与 `readback_read`），并与其余路径共用同一批帧槽与 `acquire_cursor` 轮转，故可与交换链路径交替调用。**无 UI 回调参数**。**第十轮收口起**：`render_to_target_present` 即为本方法 `target_count = 1`、`post_count = 1` 的单级特例薄封装，单级路径不再有独立的录制 / 提交 / 统计实现。**第十五轮**：目标参数由「场景目标 ＋ 第二目标」两个具名引用改为「目标组 ＋ 数量」，N = 2 时轮转结果与旧 ping-pong **逐字等价**。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `swapchain` | `Swapchain_Context&` | 当前交换链 | `valid()` 须为真；图像与两类信号量数非 0 |
| `targets` | `const Frame_Render_Target*` | 中间目标组（`targets[0]` = 场景目标） | 非空；`target_count >= 1`；**每个**目标 `color_image` / `color_view` / `depth_view` 须非空、范围宽高非零 |
| `target_count` | `uint32_t` | 目标数 | `>= 1`；`post_count >= 2` 时**必须 `>= 2`**（单目标无法轮转）；上限 4（门面以 `POST_SET_PER_SLOT` 约束） |
| `items` / `item_count` | 同 `render` | 场景 pass 的渲染项 | 可为空（只清屏） |
| `post_items` | `const Frame_Render_Item*` | 各级后处理绘制项（长度 = `post_count`） | `post_count >= 1` 且非空；逐级须管线 / 布局 / 顶点 / 索引 / 索引数 / 实例缓冲 / 实例数齐备，否则前置失败；各级 `sampler_set` 须按 `级序 % target_count` 绑定对应源的采样集 |
| `post_count` | `uint32_t` | 后处理级数 | `>= 1`；**帧模块不设级数上限**，上限由门面 `post_chain_set` 约束（`POST_CHAIN_MAX_STAGES = 8`，见《渲染层-渲染器》§3.4.47 / 附录 D 的 `R-FRAME-12`） |
| `clear_color` | `const float[4]` | 清屏色（场景 pass 与各级共用） | —— |
| `rebuild_needed_out` | `bool&` | 出参：是否需要重建（取图像 / 呈现返回过期或次优时置真） | 进入即被置假 |
| `readback` | `Frame_Readback_Request*` | 像素回读请求（可空） | 非空且 `->pixels` 非空时回读**末级呈现到交换链**的颜色附件；须交换链具备传输源用法且 `capacity >= 宽 × 高 × 4` |

- **前置校验**：`valid()`、`swapchain.valid()`、`post_count >= 1`、`post_items != nullptr`、`targets != nullptr`、`target_count >= 1`、交换链图像 / 两类信号量数非 0；`post_count >= 2` 且 `target_count < 2` → 硬错误；随后**逐目标**校验附件（`color_image` / `color_view` / `depth_view` / `extent`）齐备；逐级校验 `post_items[stage]` 完整性（`pipeline` / `layout` / `vertex_buffer` / `index_buffer` / `index_count` / `instance_buffer` / `instance_count`）；**第十七轮**起仅再校验「交换链范围非零」——目标尺寸**不再要求**等于交换链（像素映射由片元按推送尺寸完成）。
- **流程**：取帧槽 → `slot_fence_wait` → `gpu_timestamp_read` → 取图像可用信号量 → `vkAcquireNextImageKHR`（过期 / 次优置 `rebuild_needed_out` 并提前返回真）→ `vkResetFences` → `vkResetCommandPool` → 回读准备（按交换链范围、校验传输源能力）→ `command_record_chain_present(...)`（见 §6.20）→ 取呈现完成信号量 → `submit_present` → 可选回读 → 统计累计 → `++frame_count` → `deferred_flush`。
- **统计**：累计场景项（`frame_stats_accumulate(items, item_count)`）后，**逐级** `total_draw_items += 1` 与 `total_instances += post_items[stage].instance_count`（`post_count` 个后处理绘制项逐个计入）。**第十一轮**：各级的**实际绘制量**由 `command_record_chain_present` 内的 `frame_recorded` 逐级累加（见 §4.10 / §4.16 / §3.20）。
- **要求**：**各目标尺寸可互不相同**（第十七轮起）：后处理片元按推送的「源 / 宿尺寸」做像素映射，1:1 时为恒等；仅要求每个目标尺寸非零、交换链范围非零。`post_count == 1` 时目标组可只含 `targets[0]`；`render_to_target_present` 即经本方法的该特例实现。

### 3.19 累计观测三个 getter（本轮新增）

- **签名**：`double total_frame_ms_get(void) const`、`double total_gpu_frame_ms_get(void) const`、`uint64_t gpu_sample_count_get(void) const`。**实现**：`core/帧槽创建.cpp`。
- **返回值**：
  - `total_frame_ms_get`：自 `build` 成功以来**累计主机侧耗时**（毫秒）——四条渲染路径（`render` / `render_to_target` / `render_to_target_present` / `render_chain_present`）在写 `last_frame_ms` 之后紧接 `total_frame_ms += last_frame_ms;`；`destroy` 复位为 `0.0`。
  - `total_gpu_frame_ms_get`：自 `build` 成功以来**累计 GPU 耗时**（毫秒）——`gpu_timestamp_read` 在 `vkGetQueryPoolResults` 返回 `VK_SUCCESS` 之后执行 `total_gpu_frame_ms += last_gpu_frame_ms;`；能力不足时恒 `0.0`；`destroy` 复位。
  - `gpu_sample_count_get`：已**成功**读回 GPU 时间戳的**样本数**——与 `total_gpu_frame_ms` 同一累计点 `++gpu_sample_count;`；其与帧数的关系为 `max(0, frames − 在途帧数)`；`destroy` 复位为 `0`。
  - `last_post_stages_get`（**第二十二轮**）：最近一帧实际执行的后处理级数——`render` 与 `render_to_target` 路径写 `0`，`render_chain_present` 路径写 `post_count`；为**单帧值**（不是累计量），故每次 render 成功提交后即被本帧结果覆盖。
- **用途**：供门面 `frame_stats_get` 组装 `Frame_Stats`（`frame_total_ms` / `gpu_total_ms` / `gpu_samples`，见《渲染层-渲染器》）。
- **口径提示**：累计值与 `last_*`（最近一帧）字段并列；GPU 两项与 GPU 时间戳能力 / 环形读回滞后绑定（见 §6.19 与 `R-FRAME-11`）。

### 3.20 实际绘制量两个 getter（第十一轮新增）

- **签名**：`uint64_t total_drawn_items_get(void) const`、`uint64_t total_drawn_instances_get(void) const`。**实现**：`core/帧槽创建.cpp`（紧邻 `total_draw_items_get` 之后）。
- **参数**：无。
- **返回值**：
  - `total_drawn_items_get`：自 `build` 成功以来**实际下达绘制命令**的项数——返回 `total_drawn_items`，即各帧 `items_record` 返回值 `items` 的累计（`frame_stats_accumulate` 每次 `+= frame_recorded.items`）；被 `continue` 跳过的不完整项不计。
  - `total_drawn_instances_get`：自 `build` 成功以来**实际下达绘制命令**的实例数——返回 `total_drawn_instances`，即各帧 `items_record` 返回值 `instances` 的累计。
- **用途**：供门面 `frame_stats_get` 填 `Frame_Stats.drawn_items` / `drawn_instances`（见《渲染层-渲染器》§3.4.42 / §6.19）。
- **与 §3.16 的区别**：`total_draw_items_get` / `total_instances_get` 按**登记项**累计（含被跳过的不完整项）；本组按**实际绘制**累计。两量相等即表示所有登记项都真正下达了绘制命令。口径与取舍见 §6.21。

## 四、模块私有方法介绍

本章逐条列出 `Frame_Context` 的**类内私有成员函数**（签名 + 作用 + 关键行为）。数据成员说明见第五节。

### 4.1 私有 `slot_fence_wait`

- **签名**：`bool slot_fence_wait(Frame_Slot& slot)`（private，实现 `core/帧槽创建.cpp`；本轮**新增**）。
- **作用**：等待某帧槽前一次提交完成（供 `slot_wait` 与 `render` 共用）。
- **关键行为**：
  1. `VkResult status = vkGetFenceStatus(device, slot.in_flight_fence)` 查询该帧槽栅栏当前状态。
  2. 若 `status` 既非 `VK_SUCCESS` 也非 `VK_NOT_READY`（查询遭遇硬错误）→ 返回 `vk_result_check(status, "vkGetFenceStatus")`。
  3. 若 `status == VK_SUCCESS`（已完成）→ 直接返回真（**快速路径**：多数帧命中此路径，免去一次阻塞等待调用）。
  4. 否则（`VK_NOT_READY`，未完成）→ 返回 `vk_result_check(vkWaitForFences(device, 1, &slot.in_flight_fence, VK_TRUE, UINT64_MAX), "vkWaitForFences")`（阻塞等待，超时给足，`waitAll` 为真；K9）。

### 4.2 私有 `frame_slot_create`

- **签名**：`bool frame_slot_create(Frame_Slot& slot)`（private，实现 `core/帧槽创建.cpp`）。
- **作用**：创建一个帧槽的全部自有对象，成功返回真。
- **关键行为**：创建顺序为 命令池 → 命令缓冲 → 完成栅栏（`VK_FENCE_CREATE_SIGNALED_BIT`，初始即「已发出」，首帧等待不阻塞）。任一步失败时**先** `frame_slot_destroy(slot)` 回退该槽半成品，**再**返回假。**（本轮改动：不再创建「呈现完成信号量」——该信号量已改属每交换链图像，由交换链模块持有。）**

### 4.3 私有 `frame_slot_destroy`

- **签名**：`void frame_slot_destroy(Frame_Slot& slot)`（private，实现 `core/帧槽创建.cpp`）。
- **作用**：销毁一个帧槽的自有对象并复位句柄。
- **关键行为**：仅在 `device != VK_NULL_HANDLE` 时执行销毁；销毁顺序为 完成栅栏 → 命令池（连带回收其分配的命令缓冲）；随后把三个句柄（`in_flight_fence`/`command_pool`/`command_buffer`）全部复位为 `VK_NULL_HANDLE`。**幂等**（句柄空则跳过）。**（本轮改动：不再销毁「呈现完成信号量」；原「呈现完成信号量 → 完成栅栏 → 命令池」的顺序简化为「完成栅栏 → 命令池」，`slot.render_finished` 复位语句删除。）**

### 4.4 私有 `command_record`

- **签名**：`void command_record(VkCommandBuffer command_buffer, VkImage image, VkImageView image_view, VkImageView depth_view, VkExtent2D extent, const Frame_Render_Item* items, uint32_t item_count, const float clear_color[4], const Frame_Ui_Callback* ui_callback = nullptr, VkBuffer readback_buffer = VK_NULL_HANDLE)`（private，实现 `core/命令录制.cpp`）。
- **语义**：无返回值（录制失败经内部 `vk_result_check` 记日志，但不向上回传）。逐命令流程见 6.4；本轮已有「状态缓存」与「UI 阶段」两处，**本版次新增末位 `readback_buffer`**：非空时在 `vkCmdEndRendering` 之后插入「颜色附件 → 传输源」转换 + `vkCmdCopyImageToBuffer` + 「传输源 → 呈现」转换；为空时保持原「颜色附件 → 呈现」单次转换（见 6.15）。

### 4.5 私有 `submit_present`

- **签名**：`bool submit_present(Frame_Slot& slot, uint32_t image_index, VkSemaphore image_available, VkSemaphore render_finished, Swapchain_Context& swapchain, bool& rebuild_needed_out)`（private，实现 `core/提交呈现.cpp`）。
- **语义**：以 `VkSubmitInfo2` 提交命令缓冲（等待图像可用信号量、发出呈现完成信号量、以帧栅栏作完成信号），随后 `vkQueuePresentKHR` 呈现；呈现返回过期/次优时置 `rebuild_needed_out` 并返回真。**（本轮改动：新增 `render_finished` 形参；不再读取 `slot.render_finished`，改由调用方以 `swapchain.render_finished_semaphore_get(image_index)` 传入。）** 详见 6.5。

### 4.6 `deferred_push`（本轮由私有改公开）

- **签名**：`void deferred_push(Deferred_Entry entry, uint32_t delay_frames)`（**public**，实现 `core/延迟销毁.cpp`）。
- **语义**：把条目的 `release_frame` 置为 `frame_count + delay_frames` 后入队 `deferred_entries`（`push_back(std::move(entry))`）。
- **启用状态**：**本轮起已启用**——门面在交换链重建（`swapchain_rebuild_deferred`）后把交换链模块移交的旧资源组装为 `Deferred_Entry` 并调用本函数压入，延迟 = `frame.in_flight_count_get() + 1`（见 §6.7）。

### 4.7 私有 `deferred_flush`

- **签名**：`void deferred_flush(void)`（private，实现 `core/延迟销毁.cpp`）。
- **语义**：若队列为空或 `device` 不可用则直接返回；否则遍历队列，对 `release_frame <= frame_count` 的条目调用 `deferred_entry_release` 并 `erase` 该条目。`render` / `render_to_target` / `render_to_target_present` / `render_chain_present` 每帧末尾调用（本轮起队列不再恒空）。

### 4.8 私有像素回读三方法（本版次新增）

- **`bool readback_buffer_ensure(VkDeviceSize size)`**（实现 `core/像素回读.cpp`）
  - **作用**：确保回读缓冲就绪并满足 `size` 字节。
  - **关键行为**：`memory == nullptr` → 记错返回假；已有缓冲且 `readback_size >= size` → 直接返回真（**复用**）；否则先 `readback_buffer_destroy()` 归还旧缓冲，再 `memory->buffer_create(readback_buffer, readback_alloc, size, VK_BUFFER_USAGE_TRANSFER_DST_BIT, /*host_visible*/true, /*sequential_write*/false)` 新建（主机**随机读写**型内存、保持映射），成功后记录 `readback_size = size`。失败时三个字段一并复位。
- **`void readback_buffer_destroy(void)`**（实现 `core/像素回读.cpp`）
  - **作用**：归还回读缓冲并复位字段。`memory` 可用且缓冲句柄有效时才真正归还；**幂等**（无句柄即仅复位）。由 `destroy()` 与 `readback_buffer_ensure` 的「重建」路径调用。
- **`bool readback_read(Frame_Slot& slot, Frame_Readback_Request& request, VkExtent2D extent)`**（实现 `core/像素回读.cpp`）
  - **作用**：把本帧已拷入回读缓冲的像素读出到调用方主机缓冲。
  - **关键行为**：①`request.pixels == nullptr` 或缓冲句柄为空 → 记错返回假；②`byte_count = extent.width * extent.height * 4`，若 `request.capacity < byte_count` → 记错返回假；③`vkWaitForFences(device, 1, &slot.in_flight_fence, VK_TRUE, UINT64_MAX)`（渲染与拷贝同批提交，栅栏发出即数据就绪）；④`memory->buffer_read(readback_buffer, readback_alloc, request.pixels, byte_count, 0)`；⑤回填 `request.width / height / bytes`。

### 4.9 私有 `command_record_target`（离屏命令录制；本版次新增）

- **签名**：`void command_record_target(VkCommandBuffer command_buffer, const Frame_Render_Target& target, const Frame_Render_Item* items, uint32_t item_count, const float clear_color[4], const Frame_Ui_Callback* ui_callback = nullptr, VkBuffer readback_buffer = VK_NULL_HANDLE)`（private，实现 `core/命令录制.cpp`）。
- **语义**：无返回值（录制失败经内部 `vk_result_check` 记日志，不向上回传）。为 `render_to_target` 录制命令：颜色进入布局为 `SHADER_READ_ONLY_OPTIMAL`，故先转入 `COLOR_ATTACHMENT_OPTIMAL`；动态渲染范围 = 目标 `extent`（颜色 + 深度附件，均 `LOAD_OP_CLEAR`）；逐项绘制经 `items_record`；可选 UI 阶段；`vkCmdEndRendering` 后按是否回读转出布局（回读：`COLOR_ATTACHMENT → TRANSFER_SRC`（拷贝）`→ SHADER_READ_ONLY`；无回读：`COLOR_ATTACHMENT → SHADER_READ_ONLY`）。逐命令流程见 §6.16。

### 4.10 私有 `items_record`（逐项绘制；本版次新增）

- **签名**：`Recorded_Counts items_record(VkCommandBuffer command_buffer, const Frame_Render_Item* items, uint32_t item_count)`（private，实现 `core/命令录制.cpp`）。**第十一轮起返回类型由 `void` 改为 `Recorded_Counts`。**
- **返回值**：`Recorded_Counts`——`items` = 本批**实际绘制**的项数、`instances` = 实际绘制的实例数。函数内 `counts.items` 在每次真正下达 `vkCmdDrawIndexed` 之后 `+1`、`counts.instances += item.instance_count`；被 `continue` 跳过的不完整项（管线 / 顶点 / 索引 / 实例缓冲缺失，索引数或实例数为 0）不计；末尾 `return counts`。
- **语义**：把「状态缓存的管线 / 描述符集绑定 ＋ 推送常量 ＋ 顶点 / 索引 / 实例缓冲绑定 ＋ `vkCmdDrawIndexed`」抽成独立方法，**由 `command_record`（交换链路径）、`command_record_target`（离屏路径）与 `command_record_chain_present`（链路径）共用**。`command_record` 借此把原先内联于自身的逐项绘制逻辑移出，**对外行为逐字节不变**（原注释「同帧各渲染项共用同一条场景管线」更新为「同帧各渲染项**可挂不同图形管线**，故管线与描述符集只在变化时重绑」）。
- **调用点（第十一轮）**：三条录制路径的场景 pass 处统一为「先 `frame_recorded = Recorded_Counts{};` 清零，再 `frame_recorded = items_record(...)`」；链路径的各级后处理为 `Recorded_Counts stage_counts = items_record(command_buffer, &post_items[stage], 1);` 后 `frame_recorded.items += stage_counts.items;`、`frame_recorded.instances += stage_counts.instances;`（各级累加）。

### 4.11 私有 `deferred_entry_release`（本轮新增）

- **签名**：`void deferred_entry_release(Deferred_Entry& entry)`（private，实现 `core/延迟销毁.cpp`）。
- **作用**：释放单个延迟条目持有的资源（调用方须保证其已不再被在途帧引用）——既含**运行时摘出的内存资源**（`memory_resources`，本轮新增），也含**交换链重建移交的旧资源**（`resources`）。
- **流程（源码顺序）**：
  1. **运行时摘出的内存资源经内存模块归还（本轮新增）**：`memory != nullptr` 时逐条遍历 `entry.memory_resources`，对其 `buffer` 非空者 `memory->buffer_destroy(buffer, buffer_allocation)`、`view` 非空者 `memory->image_view_destroy(view)`、`image` 非空者 `memory->image_destroy(image, image_allocation)`；
  2. **旧深度资源经内存模块归还**：`memory != nullptr` 时，逐索引 `memory->image_view_destroy(entry.resources.depth_views[i])`，并在 `i < depth_images.size() && i < depth_allocations.size()` 时 `memory->image_destroy(entry.resources.depth_images[i], entry.resources.depth_allocations[i])`；
  3. 遍历 `entry.resources.image_views`，对非空句柄 `vkDestroyImageView`；
  4. 遍历 `entry.resources.image_available_semaphores`，对非空句柄 `vkDestroySemaphore`；
  5. 遍历 `entry.resources.render_finished_semaphores`，对非空句柄 `vkDestroySemaphore`；
  6. `entry.resources.swapchain != VK_NULL_HANDLE` 时 `vkDestroySwapchainKHR`。
- **要点**：两类资源均**回到内存模块**（而非原生 Vulkan 归还）——缓冲 / 图像分别经 `buffer_destroy` / `image_view_destroy` / `image_destroy` 归还，与交换链模块的移交口径一致；`depth_*` 索引越界时跳过（防御残缺条目），`memory_resources` 各字段逐条判空（同一资源可仅含缓冲、或仅含图像 ＋ 视图）。

### 4.12 私有 `deferred_release_all`（本轮新增）

- **签名**：`void deferred_release_all(void)`（private，实现 `core/延迟销毁.cpp`）。
- **作用**：**关闭期强制释放全部残留条目**（忽略 `release_frame` 判据）。
- **流程**：`device != VK_NULL_HANDLE` 时逐条调用 `deferred_entry_release`，随后 `deferred_entries.clear()`。
- **要点**：由 `destroy` 在 `vkDeviceWaitIdle` 之后、`readback_buffer_destroy()` 之后调用，**必须早于内存模块销毁**，否则旧深度图像与其内存会泄漏（曾实测触发 VMA `Unfreed dedicated allocations found!` 断言）。见 §6.7。

### 4.13 私有 `command_record_target_present`（已删除；第十轮）

- **状态**：**第十轮删除**（连同 `帧上下文.h` 中的声明）。原实现约 249 行，用于单级「目标 pass ＋ 后处理 pass」录制；删除后 `core/命令录制.cpp` 只保留 `command_record_target` 与 `command_record_chain_present` 两个目标相关录制函数。
- **替代路径**：单级后处理改由公开方法 `render_to_target_present` **薄封装** `render_chain_present`（`post_count = 1`、`second_target` 为空）实现，命令录制统一由 `command_record_chain_present`（§4.16）承担；原 `command_record_target_present` 的两 pass 流程即 §6.20 中 `post_count = 1` 的特例。详见 §6.17 / §6.20。

### 4.14 私有 `frame_stats_accumulate`（帧统计累计；本轮新增）

- **签名**：`void frame_stats_accumulate(const Frame_Render_Item* items, uint32_t item_count)`（private，实现 `core/提交呈现.cpp`）。
- **作用**：累计本帧绘制统计（**登记量 ＋ 实际绘制量**，第十一轮起）——`total_draw_items += item_count`，逐项 `total_instances += items[index].instance_count`，再 `total_drawn_items += frame_recorded.items`、`total_drawn_instances += frame_recorded.instances`（实际绘制量取 `items_record` 的返回值 `frame_recorded`，跳过项不计）。
- **调用点**：`render`、`render_to_target`、`render_chain_present` 在**提交成功之后**调用（`render_chain_present` 随后**逐级**另计 `total_draw_items += 1` 与 `total_instances += post_items[stage].instance_count`；`render_to_target_present` 第十轮起为薄封装（`post_count = 1`），统计同样由该链路径累计，单级结果与收口前逐字节一致）。
- **要点**：登记量按**登记项**计（被跳过的渲染项仍计入 `item_count`、其 `instance_count` 亦计入实例数），实际绘制量按 `items_record` 真正下达的绘制计——两者分列即本版次口径（见 §6.21）；`<chrono>` 计时与统计同处 `core/提交呈现.cpp`，**仅此一编译单元引入 `<chrono>`**。

### 4.15 私有 `gpu_timestamp_read`（GPU 耗时读回；本版次第九轮新增）

- **签名**：`void gpu_timestamp_read(Frame_Slot& slot)`（private，实现 `core/提交呈现.cpp`）。
- **作用**：读回某帧槽**上一轮**提交写入的两个时间戳，换算为毫秒写入 `last_gpu_frame_ms`。
- **关键行为**：
  1. 若 `slot.timestamp_pool == VK_NULL_HANDLE || !slot.timestamp_written || !timestamp_supported` → 直接返回（**静默跳过**：首轮 / 未写过 / 能力不足三种情形均不改动 `last_gpu_frame_ms`）。
  2. `vkGetQueryPoolResults(device, slot.timestamp_pool, 0, 2, 2 × sizeof(uint64_t), results, sizeof(uint64_t), VK_QUERY_RESULT_64_BIT)`；返回非 `VK_SUCCESS`（如结果尚未就绪）→ 静默返回。
  3. 按 `timestamp_valid_bits` **掩高位**（`< 64` 时 `(1ull << timestamp_valid_bits) − 1ull`）再相减，避免高位回绕污染。
  4. `last_gpu_frame_ms = (end_ticks − begin_ticks) × timestamp_period / 1e6`。
- **调用点**：`render` / `render_to_target` / `render_chain_present` 均在「`slot_fence_wait(slot)` 之后、本帧命令录制之前」调用（`render_to_target_present` 第十轮起经 `render_chain_present` 间接调用；此时该槽上一轮提交已完成、结果就绪），故为**按帧槽环形读回**、滞后 = 在途帧数；**本轮新增**：在 `vkGetQueryPoolResults` 返回 `VK_SUCCESS` 之后执行 `total_gpu_frame_ms += last_gpu_frame_ms;` 与 `++gpu_sample_count;`（累计观测）。写入侧见 §6.4 与 §6.19。
- **要点**：写侧时间戳由三条录制路径（`command_record` / `command_record_target` / `command_record_chain_present`）在渲染通道之外写入（满足 `vkCmdResetQueryPool` 的位置约束）；`command_record_chain_present` 覆盖「场景 pass ＋ 全部后处理 pass」（单级时即两个 pass），故其读回值为相应多 pass 之和。

### 4.16 私有 `command_record_chain_present`（N 级后处理链命令录制；本轮新增）

- **签名**：`void command_record_chain_present(VkCommandBuffer command_buffer, VkImage swapchain_image, VkImageView swapchain_view, VkImageView swapchain_depth_view, VkExtent2D swapchain_extent, const Frame_Render_Target& scene_target, const Frame_Render_Target& second_target, const Frame_Render_Item* items, uint32_t item_count, const Frame_Render_Item* post_items, uint32_t post_count, const float clear_color[4], VkBuffer readback_buffer = VK_NULL_HANDLE, VkQueryPool timestamp_pool = VK_NULL_HANDLE)`（private，实现 `core/命令录制.cpp`）。
- **语义**：无返回值。为 `render_chain_present` 在**单命令缓冲**内录制「场景 pass ＋ N 级 ping-pong 后处理 pass ＋ 呈现收尾」：
  - **场景 pass**：`scene_target` 颜色 `SHADER_READ_ONLY_OPTIMAL → COLOR_ATTACHMENT_OPTIMAL`（`srcStage=FRAGMENT_SHADER`、`srcAccess=SHADER_READ`）；动态渲染（范围 = 场景目标范围，颜色 + 深度均清屏）→ 视口 / 裁剪 = 场景目标范围 → `items_record(items)` → `vkCmdEndRendering`；随后 `scene_target` 颜色转回 `SHADER_READ_ONLY_OPTIMAL`（`COLOR_ATTACHMENT_OUTPUT`/`COLOR_ATTACHMENT_WRITE` → `FRAGMENT_SHADER`/`SHADER_READ`），使首级后处理可采样。
  - **后处理各级（`stage` 自 0 起）**：**源** = `stage % 2 == 0` → `scene_target`、`== 1` → `second_target`（源恒为 `SHADER_READ_ONLY_OPTIMAL`，可直接采样，无需再转换该图像）；**宿** = 末级 → 交换链图像（`UNDEFINED → COLOR_ATTACHMENT`，K11 同步口径）、非末级 → 另一中间目标（`SHADER_READ_ONLY → COLOR_ATTACHMENT`）；本级以 `post_items[stage]` 全屏绘制（`items_record(&post_items[stage], 1)`；各宿另配深度附件：末级用交换链深度视图，非末级用该中间目标深度视图）。
  - **非末级写完后**：宿 `COLOR_ATTACHMENT → SHADER_READ_ONLY`，使下一级可采样且**帧间恒保持该布局**（与 `render_to_target` / `render_to_target_present` 的中间目标不变量一致）。
  - **末级交换链收尾**：回读则 `COLOR_ATTACHMENT → TRANSFER_SRC → vkCmdCopyImageToBuffer → PRESENT_SRC`，否则 `COLOR_ATTACHMENT → PRESENT_SRC`（与既有路径逐字节同口径）。
  - **GPU 时间戳**：`vkBeginCommandBuffer` 之后、渲染通道之外执行 `vkCmdResetQueryPool` ＋ 起点时间戳；终点写在收尾转换之后、`vkEndCommandBuffer` 之前（覆盖场景 pass ＋ 全部后处理 pass）。
- **要点**：链路径为**单级路径的唯一实现**——`render_to_target_present` 已薄封装至本方法（`post_count = 1`），原 `command_record_target_present` 第十轮删除，双实现并存问题结案（见 `R-FRAME-12`）。逐命令流程见 §6.20。

#### 5.3.1 `Frame_Slot`（帧槽，`帧上下文.h`）

> 头注释：每帧槽持有命令池、主命令缓冲、完成栅栏；数量 = 在途帧数 `frame_overlap`，与交换链图像数无关。呈现完成信号量属「每交换链图像」，由交换链模块持有（数量 = 交换链图像数）。**（本轮改动：删除原 `render_finished` 成员。）**

| 字段 | 类型 | 初值 | 含义 | 约束/不变量 |
| --- | --- | --- | --- | --- |
| `command_pool` | `VkCommandPool` | `VK_NULL_HANDLE` | 命令池（每帧经 `vkResetCommandPool` 重置） | 建自 `graphics_family`；`VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT` 未置位，故命令缓冲随池整体重置 |
| `command_buffer` | `VkCommandBuffer` | `VK_NULL_HANDLE` | 主命令缓冲（逐帧录制） | `VK_COMMAND_BUFFER_LEVEL_PRIMARY`，每池一个 |
| `in_flight_fence` | `VkFence` | `VK_NULL_HANDLE` | 完成栅栏（主机侧等待该槽前一次提交完成） | 创建时置 `SIGNALED`，首帧等待不阻塞 |
| `timestamp_pool` | `VkQueryPool` | `VK_NULL_HANDLE` | GPU 时间戳查询池（`queryCount = 2`：索引 0 = 帧始、1 = 帧末） | 仅当 `build` 探测到时间戳能力时才创建；`vkCreateQueryPool` 失败只记日志并**降级该槽**（不使整体构建失败）；`frame_slot_destroy` 归还（**第九轮新增**） |

#### 5.3.2 `Deferred_Entry`（延迟销毁条目，`帧上下文.h`；本轮改造）

### 5.5 `局部命名空间使用.h` 的做法

```cpp
#pragma once
#include "帧上下文.h"

// ---------- 基本类型别名 ----------
using std::string;
using std::vector;
```

- **只需两条 `using`**：本模块 `.cpp` 用到的标准库类型只有 `std::string`（注释未直接体现，但收敛头统一给出）与 `std::vector`（帧槽集合、延迟销毁队列）。Vulkan 类型位于全局命名空间，无需 `using`。

## 六、模块设计/实现细节

### 6.1 帧槽与在途帧轮转（核心设计）

**问题**：CPU 录制命令与 GPU 执行命令是并行的。若只有一份命令缓冲，CPU 录制第 N+1 帧时会覆写 GPU 尚在执行的第 N 帧命令，导致画面错乱或校验层报错；若只有一套同步原语，等栅栏会退化为「每帧完全串行」，丧失并行度。

**解法**：把「一帧所需的一整套对象」打包成**帧槽**（`Frame_Slot`），创建 `frame_overlap` 份并按下标轮转。每槽独立持有：

- `command_pool` + `command_buffer`：命令录制与重置的独立容器（重置本槽命令池不影响其它槽）；
- `in_flight_fence`：主机侧等待「该槽前一次提交」完成的完成栅栏。

于是 CPU 至多领先 GPU `frame_overlap` 帧：在录制第 N 帧槽时，等待的是该槽第 N-`frame_overlap` 帧的提交，此时 GPU 不可能仍在读取第 N-`frame_overlap` 帧的该槽资源。

**关键设计（数量与图像数解耦）**：帧槽数量 = `frame_overlap`，**与交换链图像数无关**。头注释明确「数量 = 在途帧数 `frame_overlap`，与交换链图像数无关」。这正是同步原语归属拆分的直接后果：帧栅栏属每帧槽（数量 = `frame_overlap`）；图像可用信号量与呈现完成信号量则均属每交换链图像（数量 = 图像数，由交换链模块持有）。**（本轮改动：呈现完成信号量由「每帧槽」改归「每交换链图像」。）**

**取图像信号量的轮转**：取图像前不知道会拿到哪张图像，因此无法「按图像索引」选信号量。本模块以 `acquire_cursor` 在「图像可用信号量池」（大小 = `image_available_count`）中顺序轮转取用，即第 k 次成功取图像用第 `k % image_available_count` 个信号量。

### 6.2 栅栏的初始状态与「重置时机」（K9 关键坑位）

**初始已发出**：`frame_slot_create` 创建 `in_flight_fence` 时置 `VK_FENCE_CREATE_SIGNALED_BIT`。原因（源码注释）：「初始即置为『已发出』状态：首帧 `vkWaitForFences` 才不至于无限等待。」若初始为未发出，首次 `render` 的等栅栏将永远阻塞。

**重置放在取图像成功之后**：`render` 中 `vkResetFences` 的位置刻意**不在**「等栅栏之后」，而在「`vkAcquireNextImageKHR` 成功之后」。源码注释给出成因：

> 重置本帧槽完成栅栏，放在「取图像成功之后」而非「等待栅栏之后」：若取图像返回过期 / 次优而提前返回，栅栏必须保持已发出状态，否则下一帧（复用同一帧槽）`vkWaitForFences` 将无限等待（K9）。

也就是说：若取图像返回 `VK_ERROR_OUT_OF_DATE_KHR`/`VK_SUBOPTIMAL_KHR`，`render` 会**提前返回真且不自增帧计数**，下一帧仍复用**同一个帧槽**。此时该槽栅栏若已被重置为未发出、又没有任何提交去发出它，下一帧的 `vkWaitForFences` 就会死锁。把重置推迟到「确定要提交本帧」之后，天然规避了这一死锁。

**对称约束**：`render` 的任一**硬错误提前返回路径**也必须保证「本槽栅栏处于已发出状态」或「后续不会对该槽无提交地等待」。当前源码的提前返回点：
- 前置检查失败（未取槽、未重置）→ 栅栏保持原状态（此时尚未触碰栅栏）；
- 栅栏查询/等待失败 → 直接返回假（调用方视为硬错误，通常终止）；
- 取图像硬错误 → 未重置栅栏，保持已发出；
- **取图像成功后**的 `vkResetFences`/`vkResetCommandPool`/`submit_present` 失败 → 已重置栅栏但未成功提交，**这会使该槽栅栏停留于未发出态**；由于这些均为「视为终止的硬错误」（返回假），调用方应停止渲染并销毁，故不构成死锁回放。此点属硬错误后续语义，见 7.4 边界表。

### 6.3 `slot_wait`：写入前置等待（竞态修复点）

**问题**：渲染门面在调用 `render` **之前**就要写入本帧槽的场景 UBO（因为要先把描述符集指向本帧槽的 UBO，再录制使用该描述符集的命令）。若此时该帧槽前一轮提交仍在 GPU 飞行中，CPU 直接覆写 UBO 会破坏 GPU 正在读取的内容（数据竞争 / 撕裂）。

**解法**：`Frame_Context::slot_wait()`。门面在写本帧槽 UBO 之前先调用它，函数内部对**本帧槽**（`slots[frame_count % frame_overlap]`）的 `in_flight_fence` 经 `slot_fence_wait` 执行「先查状态、未完成再 `vkWaitForFences(..., VK_TRUE, UINT64_MAX)`」，从而保证「本帧槽前一次提交已完成」后才允许 CPU 覆写。

**与 `render` 内部等待的关系（双保险）**：`render` 内部第 5 步也会经 `slot_fence_wait` 等同一栅栏。头注释说明：

> `render` 内部还会再等一次，届时栅栏已发出，`vkWaitForFences` 立即返回，无副作用。

时序推演（正常无插帧情形）：
1. 帧 f 开始，门面调 `slot_wait()`：等待槽 `f % F` 的栅栏（该栅栏由帧 `f - F` 的提交发出）。**注意**：若调用方此前从未提交过该槽（首次使用），栅栏因创建时即置 `SIGNALED` 而立即通过。
2. 门面写本帧槽 UBO/描述符集（此时 GPU 已确定不再读取该槽 UBO）。
3. 门面调 `render`：内部再等同一栅栏——**该栅栏此时仍为已发出态**（步骤 1 只等待未重置），故立即返回。
4. `render` 取图像成功后 `vkResetFences`（转为未发出）→ 录制 → 提交（提交完成时由 GPU 重新发出该栅栏）。

因此两次等待不冲突：`slot_wait` 与 `render` 内部等待之间**不发生栅栏重置**，第二次等待必为「已发出」而立即通过。这解释了源码注释「届时栅栏已发出」。**约定（已确证）**：若调用方**跳过** `slot_wait` 直接 `render`，`render` 内部对该槽栅栏的等待**本身即有效**，语义与调用 `slot_wait` 一致；`slot_wait` 因此是**可选推荐**（用于保护「门面写 UBO」这一 render 之前的写操作），而非强制。

### 6.4 `command_record`：动态渲染录制细节

录制流程（`core/命令录制.cpp`）逐命令说明（其中第 9 步「逐渲染项绘制」现已抽为独立私有方法 `items_record`，由 `command_record` 与 `command_record_target` 共用，见 §四.10）：

1. `vkBeginCommandBuffer`，`flags = VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT`。**（第九轮新增）** 随后若末位 `timestamp_pool` 非空，执行 `vkCmdResetQueryPool(command_buffer, timestamp_pool, 0, 2)` ＋ `vkCmdWriteTimestamp(command_buffer, VK_PIPELINE_STAGE_TOP_OF_PIPE_BIT, timestamp_pool, 0)`——**位于渲染通道之外**（`vkCmdResetQueryPool` 不允许处于渲染实例内），池为空即整段跳过。
2. **颜色布局转换 #1**：`UNDEFINED → COLOR_ATTACHMENT_OPTIMAL`。`srcStage = COLOR_ATTACHMENT_OUTPUT`、`dstStage = COLOR_ATTACHMENT_OUTPUT`、`srcAccessMask = 0`、`dstAccessMask = COLOR_ATTACHMENT_WRITE`。源码注释（K11）：同步由 acquire 信号量保护，故 `srcStage = COLOR_ATTACHMENT_OUTPUT`、`srcAccess = 0`。
3. **颜色附件信息**：`loadOp = CLEAR`、`storeOp = STORE`，`clearValue` 取入参 `clear_color[0..3]`，`imageLayout = COLOR_ATTACHMENT_OPTIMAL`。
4. **深度附件信息**：`loadOp = CLEAR`、`storeOp = STORE`，`clearValue.depthStencil = {1.0f, 0}`，`imageLayout = DEPTH_ATTACHMENT_OPTIMAL`。源码注释说明：深度图像由交换链模块持有，布局已在交换链重建时统一转为 `DEPTH_ATTACHMENT_OPTIMAL`，故此处**不再逐帧转换**，仅清屏后保留。
5. **渲染信息**：`renderArea = {0,0} .. extent`、`layerCount = 1`、单颜色附件 + 深度附件。
6. `vkCmdBeginRendering` 进入动态渲染。
7. **视口**：`x=y=0`，`width/height = extent`，`minDepth = 0`、`maxDepth = 1`。注释（K2）：视口高度为正，Y 轴向下由投影处理。
8. **裁剪区**：`{0,0} .. extent`。
9. **逐渲染项绘制（带状态缓存，本轮新增）**（`for index in [0, item_count)`）：先声明四个缓存量并初始化——`bound_pipeline = VK_NULL_HANDLE`、`bound_layout = VK_NULL_HANDLE`、`bound_set_count = 0`、`bound_sets[2] = {VK_NULL_HANDLE, VK_NULL_HANDLE}`；随后对每项：
   - 取 `const Frame_Render_Item& item = items[index]`；
   - **跳过条件**：`pipeline`、`vertex_buffer`、`index_buffer` 任一为空，或 `index_count == 0` → `continue`；
   - **管线（仅在与 `bound_pipeline` 不同时重绑）**：`vkCmdBindPipeline(GRAPHICS, item.pipeline)`，并把 `bound_pipeline` 更新为该项管线；因管线变化使「已绑布局 / 描述符集」失效，一并复位 `bound_layout = VK_NULL_HANDLE`、`bound_set_count = 0` 与 `bound_sets`（本层可有多条具名管线，**同帧各渲染项可挂不同图形管线**，故管线与描述符集只在变化时重绑）；
   - **描述符集（仅在 布局 / 数量 / 集合 任一不同时重绑）**：若 `descriptor_set_count > 0` 且满足 `item.layout != bound_layout || descriptor_set_count != bound_set_count || scene_set != bound_sets[0] || sampler_set != bound_sets[1]`，则以 `VkDescriptorSet sets[2] = {scene_set, sampler_set}`（set0 在前、set1 在后），`vkCmdBindDescriptorSets(..., item.layout, 0, descriptor_set_count, sets, 0, nullptr)`，并更新四个缓存量；
   - **推送常量（逐项，不缓存）**：若 `push_constants != nullptr && push_constant_size > 0`：`vkCmdPushConstants(..., item.layout, VK_SHADER_STAGE_VERTEX_BIT, 0, push_constant_size, push_constants)`（**只推给顶点阶段**）；
   - **顶点缓冲（逐项）**：`vkCmdBindVertexBuffers(0, 1, &item.vertex_buffer, &offset)`，`offset = 0`（binding 0）；
   - **索引缓冲（逐项，偏移取 `item.index_offset`）**：`vkCmdBindIndexBuffer(command_buffer, item.index_buffer, item.index_offset, VK_INDEX_TYPE_UINT32)`（uint32 索引；本轮起偏移不再写死 0，改用渲染项给出的 `index_offset`，以支持「顶点与索引共用一个缓冲」）；
   - `vkCmdDrawIndexed(item.index_count, 1, 0, 0, 0)`。
10. **UI 阶段（本轮新增）**：若 `ui_callback != nullptr && ui_callback->fn != nullptr`，调用 `ui_callback->fn(command_buffer, ui_callback->user_data)`，把本帧命令缓冲交还上层绘制 UI。该调用发生在**场景动态渲染通道仍处于开启状态、`vkCmdEndRendering` 之前**，故上层（Test 层）的 `ImGui_ImplVulkan_RenderDrawData` 直接画在本帧同一动态渲染通道内；回调返回后本通道仍开启。上层 ImGui 管线的 `PipelineRenderingCreateInfo` 必须与本通道附件格式（交换链颜色附件 + 深度附件）相容（见 6.14）。
11. `vkCmdEndRendering` 退出动态渲染。
12. **颜色布局转换 #2**：`COLOR_ATTACHMENT_OPTIMAL → PRESENT_SRC_KHR`。`srcStage = COLOR_ATTACHMENT_OUTPUT`、`dstStage = BOTTOM_OF_PIPE`、`srcAccessMask = COLOR_ATTACHMENT_WRITE`、`dstAccessMask = 0`。源码注释（K12）：呈现同步由 `render_finished` 信号量与 present 等待承担，故 `dstStage = BOTTOM_OF_PIPE`、`dstAccess = 0`。
13. **（第九轮新增）** 若 `timestamp_pool` 非空，在 `vkEndCommandBuffer` **之前**（收尾布局转换之后）执行 `vkCmdWriteTimestamp(command_buffer, VK_PIPELINE_STAGE_BOTTOM_OF_PIPE_BIT, timestamp_pool, 1)`。
14. `vkEndCommandBuffer`。

**取舍说明**：全程使用 Vulkan 1.3 动态渲染，无 `VkRenderPass`/`VkFramebuffer`。布局转换是**显式写死**的（因为附件布局转换是动态渲染不再自动处理的部分）；深度布局之所以不复用同一段转换，是因为交换链模块已在重建时把深度图统一置于 `DEPTH_ATTACHMENT_OPTIMAL`，逐帧重复转换既无必要也增加屏障开销。**状态缓存**的取舍：同帧各渲染项的 set0 / set1 都是「本帧槽」的同一组值（门面按 slot 统一填装），但**各渲染项可挂不同图形管线**（默认场景管线或具名管线），故管线与描述符集**只在发生变化时重绑**（避免把不同管线误当作同一条而漏绑），兼顾正确性与 GPU 状态切换开销；推送常量与顶点 / 索引 / 实例缓冲各网格不同，仍须逐项绑定。

**一处细节（复用 `barrier` 变量）**：颜色布局转换 #1 与 #2 复用同一个 `VkImageMemoryBarrier barrier` 局部量，仅在 #2 处改写 `oldLayout/newLayout/srcAccessMask/dstAccessMask`（`image`/`subresourceRange`/队列族索引保持不变）。这是可行的，因为 `vkCmdPipelineBarrier` 会**立即拷贝**屏障内容入命令流。

### 6.5 `submit_present`：提交与呈现

**提交（`vkQueueSubmit2`）**：使用 Vulkan 1.3 的 `VkSubmitInfo2`：

| 部分 | 内容 | 说明 |
| --- | --- | --- |
| `waitSemaphoreInfoCount = 1` | `{ semaphore = image_available, stageMask = COLOR_ATTACHMENT_OUTPUT }` | 等图像可用后才进入颜色输出阶段（与布局转换 #1 的 `srcStage` 呼应） |
| `commandBufferInfoCount = 1` | `{ commandBuffer = slot.command_buffer }` | 本帧槽命令缓冲 |
| `signalSemaphoreInfoCount = 1` | `{ semaphore = render_finished, stageMask = ALL_COMMANDS }` | 全部命令完成后发出呈现完成信号量 |
| 完成信号 | `vkQueueSubmit2(graphics_queue, 1, &submit_info, slot.in_flight_fence)` | 帧栅栏作提交完成信号 |

**呈现（`vkQueuePresentKHR`）**：`waitSemaphoreCount = 1`、`pWaitSemaphores = &render_finished`（等呈现完成信号量）、`swapchainCount = 1`、`pSwapchains = &swapchain_handle`（局部量承接 `handle_get()`，因需取地址）、`pImageIndices = &image_index`。

> **本轮改动**：`render_finished` 由「帧槽自有」改为「按本次 acquire 的 `image_index` 从交换链取用」——`submit_present` 新增 `VkSemaphore render_finished` 形参，提交的 `signal_info.semaphore` 与 present 的 `pWaitSemaphores` 均指向该形参，不再指向 `slot.render_finished`。

**过期/次优分支（K7/K8）**：`vkQueuePresentKHR` 返回 `VK_ERROR_OUT_OF_DATE_KHR` 或 `VK_SUBOPTIMAL_KHR` 时，置 `rebuild_needed_out = true`，记 `logger.debug("提交呈现:: 呈现返回 {}，标记交换链待重建", vk_result_name_get(present_result))`，**返回真**（非硬错误）；其它非成功码经 `vk_result_check` 判定并返回其结果。

**取图像的过期/次优分支（K7/K8）**：在 `render` 中，`vkAcquireNextImageKHR` 返回过期/次优时置标志、提前返回真、**不重置栅栏、不自增计数**（见 6.2）。

**同步语义小结**：一整帧的同步链为「图像可用信号量（acquire → 提交的等待）→ 颜色输出 → 呈现完成信号量（提交的信号 → present 的等待）→ 帧栅栏（提交的完成信号 → 主机侧查询/等待）」。

### 6.6 单一帧计数 `frame_count`（本轮起合并）

本模块**只维护一个帧计数** `frame_count`（`uint32_t`），由它同时承担三项职责：① `frame_count_get` 对外查询「已推进帧数」；② `slot_index_get` 与 `render` 共用的**帧槽轮转依据**（`slots[frame_count % frame_overlap]`）；③ 延迟销毁队列的**释放判据**（`release_frame = frame_count + delay_frames`，`release_frame <= frame_count` 时释放）。

**合并由来**：此前本模块并存两个计数器——一个 64 位内部帧序号（供 `render` 槽轮转与延迟销毁判据）与一个 32 位对外计数 `frame_count`（供对外查询）。两者始终**同步自增**（仅在 `render` 成功走到末尾时一起 `++`；取图像/呈现过期提前返回时不增；硬错误返回时不增），唯一差异是取模基准与位宽，属**冗余而非有意设计**；且「两计数器必须恒同步」是一条**隐式前提**，一旦被破坏（如重建时仅复位其一），门面依据 `slot_index_get` 写入的槽将与 `render` 实际使用的槽错位。

本轮已把该 64 位帧序号成员并入 `frame_count`，消除该隐式前提。

**释放判据的选取**：`release_frame` 现直接以 `frame_count`（32 位）为基准（`frame_count + delay_frames`），与帧槽轮转共用同一计数；`destroy` 复位 `frame_count` 的同时清空 `deferred_entries`，故不存在「跨生命周期沿用旧帧号」的问题（源码未就 32 位计数的超长运行回绕做额外防护）。

### 6.7 延迟销毁队列（本轮启用）

**设计意图**：交换链重建时，旧的交换链、图像视图、两类信号量、深度资源可能仍被 GPU 飞行中的帧使用，不能立即销毁。做法是「登记到队列，待 `frame_overlap + 1` 帧之后再销毁」，以避免 `vkDeviceWaitIdle` 造成的全暂停。

**本轮实现（已启用）**：
- `deferred_push(entry, delay_frames)`（**public**，本轮由私有改公开）：`release_frame = frame_count + delay_frames` 后入队。**调用者为门面**——`swapchain_rebuild_deferred` 把交换链模块移交的旧资源组装为 `Deferred_Entry`，并以 `delay_frames = frame.in_flight_count_get() + 1` 压入（延迟 = 在途帧数 + 1，保证在途帧用尽后才释放）。
- `deferred_flush()`（private）：每帧 `render` / `render_to_target` / `render_to_target_present` / `render_chain_present` 末尾调用；遍历队列，对 `release_frame <= frame_count` 的条目调用 `deferred_entry_release`（**归还运行时内存资源 →** 归还旧深度资源 → 销毁旧视图 → 销毁两类信号量 → 销毁旧交换链）并 `erase`。
- `deferred_entry_release(entry)`（private，本轮新增）：释放单条目的资源——**先**逐条归还运行时摘出的 `memory_resources`（缓冲 / 图像 / 视图经内存模块 `buffer_destroy` / `image_view_destroy` / `image_destroy`），**再**归还交换链旧资源（旧深度资源经内存模块 `image_view_destroy` / `image_destroy`，另销毁旧视图 / 两类信号量 / 旧交换链）。
- `deferred_release_all()`（private，本轮新增）：**关闭期强制释放全部残留条目**（忽略帧号判据），由 `destroy` 在 `vkDeviceWaitIdle` 之后、`readback_buffer_destroy()` 之后、**内存模块销毁之前**调用。

**运行时卸载复用同一队列（本轮扩展）**：`memory_resources` 由门面在运行期卸载网格 / 纹理 / 渲染目标时填入（资源经各模块的 `mesh_detach` / `texture_detach` / `target_detach` 摘出而不销毁）；`deferred_entry_release` **先**归还该类资源、**再**归还交换链旧资源（见 §6.18）。

**为何必须 `deferred_release_all` 且早于内存模块销毁**：在途帧尚未用尽时，队列中可能仍有未到期条目；若不在关闭前强制释放，旧深度图像与其 VMA 分配会残留到内存模块销毁，触发 VMA `Unfreed dedicated allocations found!` 断言（实测）。故关闭路径必须显式清空队列。

### 6.8 同步原语归属与所有权约定

| 同步原语 | 归属 | 数量 | 创建/销毁方 | 帧模块的角色 |
| --- | --- | --- | --- | --- |
| `image_available`（图像可用信号量） | 每交换链图像 | = 交换链图像数 | 交换链模块（随重建而重建） | **借用**：取图像时传入，提交时等待；**不**创建、**不**销毁 |
| `render_finished`（呈现完成信号量） | **每交换链图像（本轮改动）** | = 交换链图像数 | 交换链模块 | **借用**：按 `image_index` 取用，提交时发出、present 时等待；**不**创建、**不**销毁 |
| `in_flight_fence`（完成栅栏） | 每帧槽 | = `frame_overlap` | 帧模块（`frame_slot_create`/`frame_slot_destroy`） | 拥有；主机侧查询/等待该槽提交完成 |

**「借用信号量的复用安全」**（K13）：图像的轮转信号量被复用时，必须保证它上一次的等待已被消费（二元信号量不得在等待完成前再次发出）。源码注释：

> 由「先等帧栅栏」保证：被取用的信号量在前一次使用时已被等待消费（K13）。

推演：图像可用信号量索引 = `acquire_cursor % image_available_count`（`acquire_cursor` 与 `frame_count` 在同一帧成功取图后同步推进），上一次使用它是在 `frame_count - image_available_count` 帧，其提交会等待该信号量；而「先等帧栅栏」在每帧开头等待 `slot(frame_count % frame_overlap)` 的栅栏。**该保证显式依赖 `image_available_count >= frame_overlap`**：当 `image_available_count >= frame_overlap` 时，`frame_count - image_available_count` 帧所用的槽的栅栏必已在此前某帧被等待过，故其提交已完成、信号量等待已消费；否则保证不成立。

**呈现完成信号量的复用推理（本轮改动附带）**：呈现完成信号量按本次 acquire 得到的 `image_index` 取用（`render_finished_semaphore_get(image_index)`），源码注释给出推理——同一信号量只会在同一张交换链图像被再次获取时才复用，而那时上一次 present 必然已消费它（帧栅栏只保证提交完成，不保证 present 已取走信号量）。

**前提显式化（上一轮修复，仍有效）**：源码此前既未断言也未钳制 `image_available_count >= frame_overlap` 这一前提，属遗漏；现已在**门面 `init` 的交换链建成处**加钳制——取 `swapchain.image_available_count_get()`，若 `frame_overlap > image_available_count`（且后者非 0）则下调 `frame_overlap` 至图像可用信号量数并 `logger.warn`，再以调整后的值调用帧模块 `build` 与管线 `build`。该钳制实现位于 `Application/Renderer/src/render/Renderer/core/渲染器.cpp`（门面属「渲染层-渲染器」模块，此处仅作说明）。

### 6.9 保存但未使用的句柄

`physical_device` 与 `present_family` 在 `build` 中被记录、在 `destroy` 中被复位，但**在帧模块全部实现中未被读取使用**——帧模块的运行链路只用到设备、图形/呈现队列与交换链，不消费这两个字段。**属有意保留的预留字段**（保持上下文信息完整、与设备/交换链模块接口对称）：后续若需「呈现队列族查询」或「物理设备特性核对」，可直接取用，无需改动 `build` 签名。

### 6.10 线程/并发与调用约定

- **非线程安全**：`Frame_Context` 无任何互斥保护，`slots`/`acquire_cursor`/`frame_count`/`deferred_entries` 的更新均为非原子。约定**由单一渲染线程**独占调用 `build`/`render`/`slot_wait`/`destroy`。
- **GPU/CPU 并行由 Vulkan 同步原语承担**，而非主机锁：帧栅栏保护「本槽资源不被 CPU 提前覆写」，信号量保护「取图像、呈现与提交的队列侧顺序」。
- **`slot_wait` 与 `render` 必须在同一线程、同一帧内成对（顺序）调用**：`slot_wait`（写 UBO 前）→ 写 UBO → `render`。`slot_wait` 之后到 `render` 内部等待之前，不得有其它帧的推进（否则槽号变化）。

### 6.11 编码约定与易错点清单

- **异常禁用**：本模块不做任何可能抛异常的内存分配（唯一动态分配是 `std::vector` 的 `resize`/`push_back`，属标准库内部行为）；未使用 `new`，故无需 `std::nothrow`。
- **等待超时给足**：`slot_fence_wait` 内 `vkWaitForFences` 传 `timeout = UINT64_MAX`（永不超时）；`vkAcquireNextImageKHR` 的 timeout 亦为 `UINT64_MAX`。
- **栅栏等待走快速路径**：`slot_fence_wait` 先 `vkGetFenceStatus` 查询，已完成即免阻塞；未就绪才落 `vkWaitForFences`。查询硬错误（非 `VK_SUCCESS`/`VK_NOT_READY`）经 `vk_result_check` 判定。
- **`vkResetFences` 位置**：见 6.2，是最易错点，改动顺序会引入死锁。
- **`slot_index_get` 与 `frame_count`**：见 6.6，`slot_index_get` 与 `render` 同以 `frame_count % frame_overlap` 取槽，基准唯一、不会错位。
- **`image_available` 游标不自增的路径**：取图像**硬错误**时 `++acquire_cursor` 不执行（仅成功时自增），避免跳过信号量；但**过期/次优提前返回**时也不自增（因为取图像未成功拿图）。
- **`command_record` 不向上回传失败**：内部 `vk_result_check` 只记日志；但因录制错误（如 `vkBeginCommandBuffer` 失败）在正常参数下极罕见，故未向上传递。
- **`destroy` 的 `for` 遍历注释为「逆序」，实际为正序**：因帧槽相互独立，顺序正确。
- **`build` 不自动先 `destroy`**：重复 `build` 会泄漏旧帧槽，调用方须保证「未构建态调用一次」。
- **呈现完成信号量归属**：见 6.8，属每交换链图像而非每帧槽；误当帧槽自有会导致重建时信号量被过早销毁或数量错配。
- **`index_offset`**：见 6.4 第 9 步，索引缓冲绑定偏移取渲染项的 `index_offset`，不再是 0；本地已有「顶点与索引共用一个缓冲」的网格须正确填该字段。
- **运行时卸载须走 `detach` ＋ 延迟销毁（本轮新增）**：门面 `mesh_unload` / `texture_unload` / `render_target_destroy` 已改为「`*_detach` 摘出 → `deferred_push`」，**不得**再直接调模块的 `*_destroy`（`mesh_destroy` / `texture_destroy` / `target_destroy` 仍保留，但仅供各模块内部 `destroy` 与「确定无在途引用」的场合）；`detach` 摘出后原记录即复位，故摘出后**不得再查询该句柄**。
- **修改长命对象前须 `frames_wait`（本轮新增）**：写满帧槽 `set1`、切换共享采样器、注销具名管线前必须调用 `frames_wait()`；仅等本帧槽（`slot_wait`）**不足**——`set1` 被**全部**帧槽的在途命令缓冲引用。见 §6.18。
- **帧统计口径（本轮新增）**：`last_frame_ms` 是主机侧墙钟耗时（不含 GPU）；`total_draw_items` / `total_instances` 按**登记项**累计（含被跳过项），与 GPU 实际绘制量可能不同；`destroy` 复位三者为 0。
- **GPU 耗时口径（第九轮新增）**：`last_gpu_frame_ms` 为**帧槽环形读回**的 GPU 耗时（滞后 = 在途帧数、同帧多 pass 含两 pass 之和、不支持时间戳即恒 0）；`timestamp_pool` 为空（能力不足 / 创建失败）时写侧与读侧整体跳过；`destroy` 复位四字段。

### 6.14 UI 通道与帧绘制回调的衔接

**回调类型（帧侧定义）**：本模块在 `帧上下文.h` 定义 `Frame_Ui_Callback`（`fn` + `user_data`，见 5.3.4），并把它作为 `render` 与 `command_record` 的可选末位形参。

**调用时机（帧侧执行）**：`command_record` 在**场景动态渲染通道仍开启、`vkCmdEndRendering` 之前**调用 `ui_callback->fn(command_buffer, ui_callback->user_data)`（见 6.4 第 10 步）。因该通道附件为交换链颜色附件 + 深度附件，上层应在此回调内直接进行绘制（不新开渲染通道）。

**调用方（渲染层外/内衔接）**：
- 「渲染层-渲染器」模块的 UI 通道（`渲染器_UI通道.h`、`core/UI通道.cpp`）以 `Ui_Channel_Context::draw_callback_get()` 返回 `const Frame_Ui_Callback*`（未设置时返回空），供门面每帧查询。
- 渲染器门面在每帧链路中以 `frame.render(swapchain, pending_items.data(), size, rebuild_needed, clear_color, ui_channel.draw_callback_get())` 把该回调传入（实现见 `Application/Renderer/src/render/Renderer/core/渲染器.cpp`）。
- 回调由上层经 `Renderer::ui_channel()->draw_callback_set(fn, user_data)` 注册；上层（Test 层）的回调体内调用 `ImGui_ImplVulkan_RenderDrawData(ImGui::GetDrawData(), 命令缓冲)`（见 `Application/Test/src/主调/图形操作界面.cpp`）。

**约定**：回调为**可空**（默认 `nullptr`）；`render` 与 `command_record` 均以「`ui_callback != nullptr && ui_callback->fn != nullptr`」双重判空，任一为空即跳过 UI 阶段，此时本帧行为与未引入该机制前一致。渲染层**不代管 UI**——不 include ImGui、不持有 ImGui 上下文，仅提供回调时机与通道信息。

### 6.15 像素回读链路（本版次新增）

**目标**：把每帧最终颜色附件拷回主机内存，形成「截图 / 像素级回归」能力；同时为后续图形特性（实例化、alpha 混合、多材质 / 多管线、离屏与后处理、文字渲染、纹理解码、mipmap）提供**可断言**的验收手段——这些特性若没有像素断言，只能退化为「跑帧不崩」的弱验证。

**三段构成**
1. **能力前提（交换链侧）**：交换链图像用法改为 `(COLOR_ATTACHMENT | TRANSFER_SRC) & supportedUsageFlags`；求交后不含传输源位时仍按原样建链，并把 `color_transfer_src_get()` 置假（建链时记 `logger.warn("交换链:: 表面不支持传输源用法，像素回读不可用")`）。见交换链模块文档。
2. **缓冲与录制（本模块）**：`readback_buffer_ensure` 按需求 `宽 × 高 × 4` 保证一个**主机可见、用途 `TRANSFER_DST`** 的缓冲；`command_record` 在 `vkCmdEndRendering` 之后插入两段屏障与一次 `vkCmdCopyImageToBuffer`。
3. **读出（本模块）**：提交并呈现成功后 `readback_read` 等本帧槽栅栏 → `memory->buffer_read` → 回填宽 / 高 / 字节数。

**布局账（关键）**
- **无回读**：`UNDEFINED → COLOR_ATTACHMENT_OPTIMAL → PRESENT_SRC_KHR`（与引入回读前**逐字节一致**）。
- **有回读**：`UNDEFINED → COLOR_ATTACHMENT_OPTIMAL → TRANSFER_SRC_OPTIMAL → PRESENT_SRC_KHR`。
- 拷贝前屏障：`srcStage = COLOR_ATTACHMENT_OUTPUT` / `srcAccess = COLOR_ATTACHMENT_WRITE` → `dstStage = TRANSFER` / `dstAccess = TRANSFER_READ`；收尾屏障：`srcStage = TRANSFER` / `srcAccess = TRANSFER_READ` → `dstStage = BOTTOM_OF_PIPE` / `dstAccess = 0`（与原有「呈现前转换」同口径，K12）。
- 拷贝区域：`aspectMask = COLOR`、`mipLevel = 0`、`baseArrayLayer = 0`、`layerCount = 1`、`bufferRowLength = 0` 且 `bufferImageHeight = 0`（按 `imageExtent` 紧排）、`imageExtent = { extent.width, extent.height, 1 }`。

**同步代价与边界**
- 拷贝与渲染录在**同一命令缓冲**内，故不需要额外信号量、也不需要第二次提交；`readback_read` 的 `vkWaitForFences`（`waitAll = VK_TRUE`、超时 `UINT64_MAX`）只对**显式请求回读的帧**生效——未请求回读的帧路径**零额外等待**。
- 交换链过期 / 次优而提前返回、或窗口最小化 / 关闭请求造成的挂起帧**不产出像素**：门面据 `request.bytes == 0` 判定「回读未兑现」，报错返回假并保持尺寸出参为零。
- 回读缓冲按需创建、`readback_size >= 需求` 时复用，故交换链**放大后自动重建**（下次请求时需求变大即触发）；`destroy` 时归还，且**先于内存模块销毁**（否则分配器已回收）。
- 能力位缺失的极端驱动下：门面 `readback_supported()` 为假，请求回读的调用报错返回假，**原有渲染路径完全不受影响**。

### 6.16 离屏渲染路径（本版次新增）

**目标**：在不取交换链图像、不呈现的前提下，把场景渲染进一张离屏渲染目标，使「离屏渲染 → 采样合成」的后处理闭环成为可能，并为多材质 / 后处理 / 文字渲染等后续特性提供「渲染到任意目标」的通用能力。

**两条路径的异同**

| 维度 | `render`（交换链路径） | `render_to_target`（离屏路径） |
| --- | --- | --- |
| 取交换链图像 | 是（`vkAcquireNextImageKHR`） | **否** |
| 信号量 | 等待 `image_available`、发出 `render_finished` | **无**（提交不带任何信号量） |
| 呈现 | `vkQueuePresentKHR` | **否** |
| 提交 | `vkQueueSubmit2`（等信号量 + 命令 + 信号量，帧栅栏作完成） | `vkQueueSubmit2`（**仅命令**，帧栅栏作完成） |
| 颜色进入布局 | `UNDEFINED` | `SHADER_READ_ONLY_OPTIMAL` |
| 颜色退出布局 | `PRESENT_SRC_KHR` | `SHADER_READ_ONLY_OPTIMAL` |
| 深度进入布局 | `DEPTH_ATTACHMENT_OPTIMAL`（交换链，仅清屏） | `DEPTH_ATTACHMENT_OPTIMAL`（目标，仅清屏） |
| 回读来源 | 交换链颜色附件 | **目标颜色附件** |
| 帧槽轮转 / `frame_count` | 共用 | **共用** |

**`command_record_target` 逐命令流程**

1. `vkBeginCommandBuffer`（`ONE_TIME_SUBMIT_BIT`）。
2. **颜色布局转换（进入）**：`SHADER_READ_ONLY_OPTIMAL → COLOR_ATTACHMENT_OPTIMAL`，`srcStage = FRAGMENT_SHADER`、`srcAccess = SHADER_READ`、`dstStage = COLOR_ATTACHMENT_OUTPUT`、`dstAccess = COLOR_ATTACHMENT_WRITE`（说明颜色在上一帧结束后被采样过）。
3. **颜色附件**：`loadOp = CLEAR`、`storeOp = STORE`、`clearValue = clear_color`、`imageLayout = COLOR_ATTACHMENT_OPTIMAL`。
4. **深度附件**：`loadOp = CLEAR`、`storeOp = STORE`、`clearValue.depthStencil = {1.0, 0}`、`imageLayout = DEPTH_ATTACHMENT_OPTIMAL`（深度恒处于该布局，故**不转换**，仅清空）。
5. **渲染信息**：`renderArea.extent = target.extent`、单颜色附件 + 深度附件。
6. `vkCmdBeginRendering` → 视口 / 裁剪（范围 = `target.extent`）→ `items_record`（逐项绘制，**与交换链路径同一方法**）→ 可选 UI 回调 → `vkCmdEndRendering`。
7. **转出布局**：
   - 有回读：`COLOR_ATTACHMENT → TRANSFER_SRC`（`COLOR_ATTACHMENT_OUTPUT`/`COLOR_ATTACHMENT_WRITE` → `TRANSFER`/`TRANSFER_READ`）→ `vkCmdCopyImageToBuffer`（拷目标颜色附件到回读缓冲）→ `TRANSFER_SRC → SHADER_READ_ONLY`（`TRANSFER`/`TRANSFER_READ` → `FRAGMENT_SHADER`/`SHADER_READ`）。
   - 无回读：直接 `COLOR_ATTACHMENT → SHADER_READ_ONLY`（`COLOR_ATTACHMENT_OUTPUT`/`COLOR_ATTACHMENT_WRITE` → `FRAGMENT_SHADER`/`SHADER_READ`）。
8. `vkEndCommandBuffer`。

**不变量与取舍**
- 两条转出路径都把颜色送回 `SHADER_READ_ONLY_OPTIMAL`，与「渲染层-渲染目标」模块的「帧间恒可采样」不变量一致（见该模块文档）。
- **离屏路径本帧不呈现到窗口**：离屏结果需经门面 `texture_bind_target` 把目标颜色视图绑入帧槽 `set 1`、再以正常绘制采样显示（后处理闭环）。此为有意取舍（离屏渲染本身不面向窗口）。
- 两条路径共用同一批帧槽与 `frame_count` 轮转，故交替调用（先离屏、后交换链采样）不会打乱在途帧同步。

### 6.17 同帧多 pass 后处理路径（本轮新增）

**目标**：在**同一帧、同一命令缓冲**内完成「场景渲染进离屏目标 → 以该目标为纹理做全屏后处理 → 呈现到交换链」，无需跨帧中间态（与 §6.16 的「先离屏、后帧采样合成」闭环互补）。

**第十轮收口**：单级路径已并入 N 级后处理链（§6.20）——`render_to_target_present` 是 `render_chain_present` 的**薄封装**（`post_count = 1`、第二目标为空），`command_record_target_present` 已删除；本节所述两 pass 流程即 `command_record_chain_present` 在 `post_count = 1` 时的特例，单级路径不再有独立的录制 / 提交 / 统计实现。

**路径分派**：由门面 `Renderer::frame_render` 按三路互斥分派——① 同帧多 pass（`present_target` 有效且资源就绪）→ ② 离屏（`active_target`）→ ③ 交换链（默认）。

**两条 pass（`command_record_chain_present` 在 `post_count = 1` 时的逐命令流程）**：

1. `vkBeginCommandBuffer`（`ONE_TIME_SUBMIT_BIT`）。
2. **pass 1 · 目标颜色进入**：`SHADER_READ_ONLY_OPTIMAL → COLOR_ATTACHMENT_OPTIMAL`（`FRAGMENT_SHADER`/`SHADER_READ` → `COLOR_ATTACHMENT_OUTPUT`/`COLOR_ATTACHMENT_WRITE`）。
3. **pass 1 · 动态渲染**：范围 = 目标范围；颜色 + 深度附件（均 `LOAD_OP_CLEAR`）；视口 / 裁剪 = 目标范围；`items_record(items)`；`vkCmdEndRendering`。
4. **pass 1 → pass 2 · 目标颜色转回**：`COLOR_ATTACHMENT_OPTIMAL → SHADER_READ_ONLY_OPTIMAL`（`COLOR_ATTACHMENT_OUTPUT`/`COLOR_ATTACHMENT_WRITE` → `FRAGMENT_SHADER`/`SHADER_READ`）。
5. **pass 2 · 交换链进入**：`UNDEFINED → COLOR_ATTACHMENT_OPTIMAL`（`srcStage = COLOR_ATTACHMENT_OUTPUT`、`srcAccess = 0`，由 acquire 信号量保护，K11）。
6. **pass 2 · 动态渲染**：范围 = 交换链范围；颜色 + 深度附件（均 `LOAD_OP_CLEAR`）；视口 / 裁剪 = 交换链范围；`items_record(&post_item, 1)` 全屏绘制（后处理管线采样目标颜色）；`vkCmdEndRendering`。
7. **交换链收尾（与交换链路径同口径）**：回读则 `COLOR_ATTACHMENT → TRANSFER_SRC → vkCmdCopyImageToBuffer → PRESENT_SRC`；不回读则 `COLOR_ATTACHMENT → PRESENT_SRC`。
8. `vkEndCommandBuffer`。

**要点与约束**：
- **目标尺寸独立（第十七轮）**：后处理片元不再 1:1 取源；帧模块在链路径**逐级**向绘制项副本推送 `vec4(源宽, 源高, 宿宽, 宿高)`（推送常量 offset 80），片元据此映射像素坐标。故各目标尺寸可不同（半分辨率泛光等），仅要求非零。
- **不经 UI 回调**：本路径**无** `ui_callback` 形参，UI 不参与同帧后处理路径（与 `render` / `render_to_target` 不同）。
- **回读来源为交换链颜色附件**（即后处理输出），非离屏目标颜色。
- 与其余路径共用同一批帧槽与 `frame_count` 轮转。

### 6.18 资源销毁时序收口与帧性能统计（本轮新增）

**目标**：消除「运行时卸载仍被在途命令缓冲 / 描述符集引用的资源」所触发的校验告警（本轮前全量残余 6 条，**本轮降至 0 条**），并补足帧级性能观测（主机侧耗时与绘制量）。

**一、资源销毁时序收口**

- **问题**：门面在运行时 `mesh_unload` / `texture_unload` / `render_target_destroy` 时，若直接 `*_destroy` 立即归还缓冲 / 图像，而此时**仍有在途帧的命令缓冲或描述符集引用**它们（描述符集 `set1` 已把视图句柄写死在各帧槽），销毁即为未定义行为并触发校验告警。
- **解法**：
  1. 三个资源模块各新增「**摘出而不销毁**」接口——`mesh_detach` / `texture_detach` / `target_detach`（见各自文档），把记录的句柄整体写出并把原记录复位（归还责任移交调用方）；
  2. 门面把摘出的句柄填入 `Deferred_Memory_Resource`（网格：`buffer` ＋ `buffer_allocation`；纹理：`image` ＋ `image_allocation` ＋ `view`；渲染目标：颜色与深度各一条），组装 `Deferred_Entry` 后 `frame.deferred_push(entry, frame.in_flight_count_get() + 1)`（**延迟 = 在途帧数 + 1**，与交换链重建同口径，保证在途帧用尽后才释放）；
  3. `deferred_entry_release` 在到期帧经内存模块归还 `memory_resources`（见 §6.7 / §四.11）。
- **对长命对象的额外保护**：`texture_bind_set` / `texture_bind_target` 在**写满全部帧槽 `set1` 之前**、`texture_sampler_state_set` 在**销毁并重建共享采样器之前**、`pipeline_unload` 在**注销图形管线之前**，均先调用公开 `frames_wait()`（见 §3.15）收口全部在途帧——这些对象（`set1` 指向的视图、共享采样器、图形管线）被**任一**帧槽的在途命令缓冲引用，必须等无命令缓冲在途后才可修改 / 销毁。仅 `slot_wait`（只等本帧槽）**不足**。
- **附带**：门面以 `bound_view` 记录「当前绑定视图」（纹理与渲染目标共用该语义），故采样器状态切换后以该视图重写 `set1`，不再按纹理句柄回落而覆盖目标绑定（见《渲染层-渲染器》的 `R-FACADE-06` 结案）。

**二、帧性能统计**

- **计时**：`render` / `render_to_target` / `render_to_target_present` / `render_chain_present` 在**录制前**取 `std::chrono::steady_clock::now()` 为起点，在**提交成功后**（`render`、同帧多 pass 与后处理链路径为 `submit_present` 返回后、离屏路径为 `vkQueueSubmit2` 返回后）取终点写入 `last_frame_ms`（毫秒）。故区间为「主机侧录制 ＋ 提交 ＋（交换链路径）呈现调用」，**不含 GPU 执行时间**。
- **绘制统计**：`frame_stats_accumulate(items, item_count)` 累加绘制项数与实例数；`render_to_target_present` 在场景项之外**另计 1 个后处理绘制项**及其 `instance_count`（见 §四.14）；`render_chain_present` 逐级另计 `post_count` 个后处理绘制项及其 `instance_count`（见 §6.20）。
- **取用**：门面 `frame_stats_get()` 组装 `Frame_Stats`（`frames` 取门面自有的已推进帧数，其余取本模块三 getter），未初始化返回全零。**第十一轮起**另取实际绘制量两 getter（`total_drawn_items_get` / `total_drawn_instances_get`）填入 `drawn_items` / `drawn_instances`（见 §3.20 / §6.21）。
- **取舍**：**不引入 GPU 时间戳查询**（本轮范围外）——`last_frame_ms` 是主机侧墙钟耗时、非 GPU 帧时间；绘制项数按**登记项**计（含被跳过项），非 GPU 实际绘制次数。相关口径登记为待确认（见附录 C 的 `R-FRAME-10`）。
- **第十一轮补充（实际绘制量分列）**：登记量口径保持不变（`total_draw_items` / `total_instances`），另新增**实际绘制量** `total_drawn_items` / `total_drawn_instances`——由 `items_record` 每真正下达一次 `vkCmdDrawIndexed` 在 `frame_recorded` 中递增，`frame_stats_accumulate` 在提交成功后累入；链路径各级逐级累加。故 `draw_items − drawn_items` 即「被跳过的不完整登记项数」。**`R-FRAME-10` 结案**：口径即「两量分列」，把绘制统计改为「仅计实际绘制项」的旧选项不再采纳；GPU 耗时**维持帧槽环形读回**（同帧读回需提交后同步等待，代价大于收益，见 §6.19）。

### 6.19 GPU 时间戳耗时统计（本版次第九轮新增）

**目标**：在已有的主机侧帧耗时（§6.18 二）之外，补一路 **GPU 侧**耗时观测——以 Vulkan 时间戳查询池量测「命令缓冲在 GPU 上的实际执行时长」，供上层对照「CPU 提交开销」与「GPU 执行开销」。

**能力前提（`build` 探测，不支持即降级）**：以 `vkGetPhysicalDeviceProperties` 取 `limits.timestampPeriod`（纳秒 / tick）与 `limits.timestampComputeAndGraphics`，以 `vkGetPhysicalDeviceQueueFamilyProperties` 取图形队列族（`graphics_family`）的 `timestampValidBits`；**三项同时满足**（`timestampComputeAndGraphics == VK_TRUE` 且 `timestampPeriod > 0` 且 `validBits > 0`）才置 `timestamp_supported = true`；否则记 `logger.warn` 并**优雅降级**——`frame_slot_create` 不建查询池、`last_gpu_frame_ms` 恒 0，**不影响构建与渲染**（见 §3.4 行为要点 2）。

**写侧（查询池与时间戳写入）**：
- `frame_slot_create` 在 `timestamp_supported` 为真时为该槽 `vkCreateQueryPool`（`queryCount = 2`）写入 `Frame_Slot::timestamp_pool`；`vkCreateQueryPool` 失败**只记日志并降级该槽**（保持 `VK_NULL_HANDLE`，不使整体构建失败）；`frame_slot_destroy` 归还查询池并复位 `timestamp_pool` / `timestamp_written`（见 §5.3.1）。
- 三条命令录制路径（`command_record` / `command_record_target` / `command_record_chain_present`；单级后处理经 `render_to_target_present` 薄封装亦走后者，`post_count = 1`）各接收末位 `VkQueryPool timestamp_pool = VK_NULL_HANDLE`：在 `vkBeginCommandBuffer` 之后、**渲染通道之外**执行 `vkCmdResetQueryPool(cmd, pool, 0, 2)` ＋ `vkCmdWriteTimestamp(cmd, VK_PIPELINE_STAGE_TOP_OF_PIPE_BIT, pool, 0)`（置于通道外以满足 `vkCmdResetQueryPool` 不能位于渲染实例内的约束）；在 `vkEndCommandBuffer` **之前**（收尾布局转换之后）执行 `vkCmdWriteTimestamp(cmd, VK_PIPELINE_STAGE_BOTTOM_OF_PIPE_BIT, pool, 1)`。池为空即整段跳过（见 §6.4）。
- 三条路径提交成功后置 `slot.timestamp_written = true`。

**读侧（环形读回与换算）**：
- 三条渲染路径（`render` / `render_to_target` / `render_chain_present`；`render_to_target_present` 第十轮起经 `render_chain_present` 间接调用）在「`slot_fence_wait(slot)` 之后、本帧命令录制之前」调用私有 `gpu_timestamp_read(slot)`——此时该槽**上一轮**提交已完成、查询结果就绪，故为**按帧槽环形读回**，**滞后 = 在途帧数**（需「在途帧数 + 1」帧才读得到首轮结果）。
- `vkGetQueryPoolResults(..., 2, 2 × sizeof(uint64_t), sizeof(uint64_t), VK_QUERY_RESULT_64_BIT)`；返回非 `VK_SUCCESS`（首轮 / 未执行完）即**静默跳过**、不改动 `last_gpu_frame_ms`。
- 按 `timestamp_valid_bits`（< 64 时）**掩高位**再相减；按 `(end − begin) × timestampPeriod / 1e6` 换算毫秒写 `last_gpu_frame_ms`（见 §四.15）。

**口径与取舍**：
- **同帧多 pass（单级）**：`command_record_chain_present` 在 `post_count = 1` 时的起止覆盖两个 pass，故该路径的 GPU 耗时为「目标 pass ＋ 后处理 pass」**之和**（非单 pass）；**后处理链**：`command_record_chain_present` 的起止覆盖「场景 pass ＋ 全部后处理 pass」，故其读回值为这些 pass 之和。
- **滞后性**：读回取的是该槽上一轮提交的耗时，故统计与「当前帧」相差在途帧数；这是「不阻塞等待本帧完成」的取舍结果（若同步等本帧时间戳就绪将引入全暂停）。相关口径登记为待确认（见附录 C 的 `R-FRAME-11`）。
- **与主机侧耗时的关系**：`last_frame_ms`（主机侧，§6.18 二）与 `last_gpu_frame_ms`（GPU 侧）**不同量**，二者共同经门面 `Frame_Stats` 对外（见《渲染层-渲染器》§6.16）。
- `destroy` 复位 `timestamp_supported` / `timestamp_period` / `timestamp_valid_bits` / `last_gpu_frame_ms` 四者（见 §3.5）；本轮另复位累计三字段 `total_frame_ms` / `total_gpu_frame_ms` / `gpu_sample_count`。

### 6.20 N 级后处理链（本轮新增）

**目标**：在单级后处理（§6.17）之外，支持**任意级数**的后处理链——场景渲染进 `scene_target` 后，逐级以「偶/奇」两种中间目标 ping-pong 后处理，末级呈现到交换链；级数由调用方决定（`post_count`）。

**与既有路径的关系**：`render_to_target_present` **第十轮起为 `render_chain_present` 的薄封装**（`post_count = 1`、`second_target` 为空），二者共用「取图像 / 提交 / 呈现 / 回读」与录制实现（同用 `submit_present` 与 `readback_read`）；区别仅在后处理级数可变、且**逐级**登记统计。

**`command_record_chain_present` 逐命令流程**：

1. `vkBeginCommandBuffer`（`ONE_TIME_SUBMIT_BIT`）；若 `timestamp_pool` 非空，在渲染通道之外 `vkCmdResetQueryPool` ＋ 起点时间戳（覆盖场景 pass ＋ 全部后处理 pass）。
2. **场景 pass**：`scene_target` 颜色 `SHADER_READ_ONLY → COLOR_ATTACHMENT`（`FRAGMENT_SHADER`/`SHADER_READ` → `COLOR_ATTACHMENT_OUTPUT`/`COLOR_ATTACHMENT_WRITE`）→ 动态渲染（范围 = 场景目标，颜色 + 深度清屏）→ 视口 / 裁剪 → `items_record(items)` → `vkCmdEndRendering` → 颜色转回 `SHADER_READ_ONLY`。
3. **后处理各级（`stage` 自 0 起，共 `post_count` 级）**：
   - 源 = `targets[stage % target_count]`（源恒为 `SHADER_READ_ONLY`，可直接采样）；
   - 宿 = 末级 → 交换链图像（`UNDEFINED → COLOR_ATTACHMENT`，K11）、非末级 → `targets[(stage + 1) % target_count]`（`SHADER_READ_ONLY → COLOR_ATTACHMENT`）；
   - 动态渲染（范围 / 深度 / 视口随宿）→ 构造 `stage_item`（复制 `post_items[stage]` ＋ 推送「源 / 宿尺寸 ＋ 泛光参数」共 **8 浮点**于 offset 80，**第二十一轮**）→ `items_record(&stage_item, 1)` 全屏绘制 → `vkCmdEndRendering`；
   - 非末级写完后：宿 `COLOR_ATTACHMENT → SHADER_READ_ONLY`（帧间恒保持该布局）。
4. **末级交换链收尾**：回读则 `COLOR_ATTACHMENT → TRANSFER_SRC → vkCmdCopyImageToBuffer → PRESENT_SRC`；不回读则 `COLOR_ATTACHMENT → PRESENT_SRC`（与既有路径逐字节同口径）。
5. 终点时间戳写在收尾转换之后、`vkEndCommandBuffer` 之前。

**要点与约束**：
- **目标尺寸可不同（第十七轮）**：`render_chain_present` 只校验「每个目标尺寸非零 + 交换链范围非零」；像素映射由各后处理片元按帧模块推送的「源 / 宿尺寸」完成（1:1 时为恒等，非 1:1 时为点采样）。
- **单级路径已并入本实现**：`render_to_target_present` 是 `post_count = 1` 的薄封装，原 `command_record_target_present` 已删除（第十轮），双实现并存问题结案（见 `R-FRAME-12`）。
- **不经 UI 回调**（该路径无 `ui_callback` 形参）。
- 回读来源为**末级呈现到交换链**的颜色附件（即链输出）。
- 与其余路径共用同一批帧槽与 `frame_count` 轮转；**帧模块 `render_chain_present` 本身不设级数上限**（只接受 `post_count`），级数上限由门面 `post_chain_set` 约束（`POST_CHAIN_MAX_STAGES = 8`，见《渲染层-渲染器》§3.4.47 与附录 C 的 `R-FRAME-12`）。

### 6.21 帧统计口径分列（第十一轮新增）

**目标**：把「上层登记了多少个渲染项」与「真正下达了多少次绘制」分为两套观测值，消除此前「登记量与实际绘制量混为一谈」的口径歧义（处置 `R-FRAME-10`，结案）。

**口径定义**：
- **登记量**：`total_draw_items`（项数）与 `total_instances`（实例数）——按上层传入的 `item_count` 与各 `instance_count` 累加，**含被跳过的不完整项**。
- **实际绘制量**：`total_drawn_items`（项数）与 `total_drawn_instances`（实例数）——只统计**真正下达 `vkCmdDrawIndexed`** 的项；不完整项（`pipeline` / `vertex_buffer` / `index_buffer` / `instance_buffer` 为空、`index_count` 或 `instance_count` 为 0）被 `continue` 跳过，不计入。
- 两量相等即表示「所有登记项都真正下达了绘制命令」；`登记量 − 实际绘制量` 即被跳过的不完整项数 / 实例数。

**采集链路（写侧）**：
1. `items_record` 内部维护局部 `Recorded_Counts counts{}`，在每次真正下达 `vkCmdDrawIndexed` 之后 `++counts.items`、`counts.instances += item.instance_count`，末尾返回；
2. `command_record` / `command_record_target` / `command_record_chain_present` 的场景 pass 处：**先** `frame_recorded = Recorded_Counts{};`（清零本次录制的累计），**再** `frame_recorded = items_record(...)`；
3. 链路径各级后处理：`Recorded_Counts stage_counts = items_record(command_buffer, &post_items[stage], 1);` 后 `frame_recorded.items += stage_counts.items;`、`frame_recorded.instances += stage_counts.instances;`（各级累加，故 `frame_recorded` 覆盖「场景 pass ＋ 全部后处理 pass」）；
4. `frame_stats_accumulate`（提交成功后调用）除登记量外，另执行 `total_drawn_items += frame_recorded.items;`、`total_drawn_instances += frame_recorded.instances;`。

**读侧**：`total_drawn_items_get` / `total_drawn_instances_get`（§3.20）返回累计值，由门面 `frame_stats_get` 填 `Frame_Stats.drawn_items` / `drawn_instances`（见《渲染层-渲染器》§3.4.42 / §6.19）。

**复位**：`destroy` 复位 `total_drawn_items = 0`、`total_drawn_instances = 0`、`frame_recorded = Recorded_Counts{}`（紧随 `total_instances = 0`）。

**取舍**：
- **GPU 耗时维持帧槽环形读回**（§6.19）——同帧读回需在提交后同步等待本帧时间戳就绪，引入全暂停，代价大于滞后带来的观测偏差；故不改为「同帧同步读回」。
- 实际绘制量**不区分 pass**（场景与各级后处理合并计），与登记量同粒度；逐级明细未单独保留。

## 七、模块运行链路详例

本章以「调用方 → 模块 → 被调方」的时序描述典型链路。调用方在渲染层内主要是渲染器门面。

### 7.1 主流程一：`build`（创建帧槽集合）

1. **调用方（渲染器门面）** 在设备、交换链、内存等模块就绪后，从设备模块取 `device`/`physical_device`/`graphics_family`/`graphics_queue`/`present_family`/`present_queue`，并传入已构建的 `swapchain` 与选定的 `frame_overlap`，调用 `frame.build(...)`。其中 `frame_overlap` 由门面在 `init` 中先按图像可用信号量数钳制（若选定值超过 `swapchain.image_available_count_get()` 则下调至后者并告警，见 6.8），故传入 `build` 的是钳制后的值。
2. **`build`** 前置检查：设备句柄与两条队列非空、`swapchain.valid()` 为真、`frame_overlap > 0`；任一不满足 → `logger.error` 并返回假。
3. 记录设备与队列字段。
4. `slots.resize(frame_overlap)`；对 `index ∈ [0, frame_overlap)` 调 `frame_slot_create(slots[index])`：
   a. `vkCreateCommandPool`（`queueFamilyIndex = graphics_family`）；
   b. `vkAllocateCommandBuffers`（`PRIMARY`、数量 1）；
   c. `vkCreateFence`（`VK_FENCE_CREATE_SIGNALED_BIT`）；
   d. 任一步失败 → 内部 `frame_slot_destroy(slot)` 回退该槽 → 返回假。
5. 若某槽失败 → **`build` 整体回退**：`logger.error("帧上下文:: 第 {} 个帧槽创建失败，回退", index)` → `destroy()` → 返回假。
6. 全部成功 → `logger.info("帧上下文:: 帧基础设施构建完成（… 呈现完成信号量 {}）")` → 返回真。此后 `valid()` 为真，可开始逐帧 `render`。

### 7.2 主流程二：一帧渲染（`slot_wait` + `render`）

1. **调用方（渲染器门面）**：
   a. 调 `slot_index_get()` 取「本帧槽序号」（用于定位本帧槽 UBO/描述符集）；
   b. 调 `slot_wait()` 等本帧槽栅栏完成（保护即将进行的 UBO 写入）；
   c. 写入本帧槽的场景 UBO、组装 `Frame_Render_Item` 数组（管线、布局、描述符集、顶点/索引缓冲与 `index_offset`、推送常量）；
   d. 取 UI 绘制回调 `ui_channel.draw_callback_get()`（供下一步传入；可为空）。
2. **`render(swapchain, items, item_count, rebuild_needed_out, clear_color, ui_callback)`**：
   a. `rebuild_needed_out = false`；前置检查 `valid()`、`swapchain.valid()`、图像数 / 图像可用信号量数 / 呈现完成信号量数均非 0。
   b. 取当前帧槽 `slots[frame_count % frame_overlap]`。
   c. `slot_fence_wait(slot)`（先 `vkGetFenceStatus` 查状态，未完成再 `vkWaitForFences`；该槽前一次提交完成）；随后 `gpu_timestamp_read(slot)` 读回该槽**上一轮**的 GPU 耗时（第九轮新增；无能力 / 首轮 / 未写过时静默跳过）。
   d. 从交换链取图像可用信号量 `image_available_semaphore_get(acquire_cursor % image_available_count)`。
   e. `vkAcquireNextImageKHR(device, swapchain.handle_get(), UINT64_MAX, image_available, VK_NULL_HANDLE, &image_index)`：
      - 过期/次优 → `rebuild_needed_out = true`、`logger.debug`、**提前返回真**；
      - 其它非成功 → `logger.error`，返回假；
      - 成功 → `++acquire_cursor`。
   f. `vkResetFences`（**此时才重置**）；`vkResetCommandPool`。
   g. `command_record(slot.command_buffer, image_get, image_view_get, depth_view_get, extent_get, items, item_count, clear_color, ui_callback)`：
      - 颜色布局转换（UNDEFINED→COLOR_ATTACHMENT_OPTIMAL）→ 动态渲染（清屏 + 逐项绑定（带状态缓存）与 `vkCmdDrawIndexed` + 可选 UI 阶段）→ 颜色布局转换（COLOR_ATTACHMENT_OPTIMAL→PRESENT_SRC_KHR）。
   h. 取本帧呈现完成信号量 `render_finished = render_finished_semaphore_get(image_index)`。
   i. `submit_present(slot, image_index, image_available, render_finished, swapchain, rebuild_needed_out)`：
      - `vkQueueSubmit2`（等 `image_available`@COLOR_ATTACHMENT_OUTPUT → 执行命令 → 发 `render_finished`@ALL_COMMANDS，`in_flight_fence` 作完成信号）；
      - `vkQueuePresentKHR(present_queue, {pWaitSemaphores = &render_finished, pImageIndices = &image_index})`；
      - 呈现过期/次优 → `rebuild_needed_out = true`、`logger.debug`、返回真；其它非成功 → `logger.error`、返回假。
   j. `++frame_count;`（单一帧计数，兼作轮转与释放判据）。
   k. `deferred_flush()`（当前为空操作）。
   l. 返回真。
3. **调用方**：若 `rebuild_needed_out == true`，组织交换链重建（重建由上层/交换链模块执行，帧模块只出标志），并在重建完成后继续后续帧。

### 7.3 主流程三：`destroy`（销毁）

1. **调用方** 在关闭流程中调用 `frame.destroy()`（通常在交换链销毁之前，因为帧槽引用交换链设备的命令池族与队列）。
2. 若 `device` 非空：`vkDeviceWaitIdle(device)`；遍历 `slots` 逐个 `frame_slot_destroy`（完成栅栏 → 命令池）。
3. `slots.clear()`、`deferred_entries.clear()`。
4. 复位全部句柄与计数。
5. 再次调用 `destroy` → 各守卫均不成立 → 无操作（幂等）。**析构兜底**：对象析构时再调一次 `destroy()`。

### 7.4 关键边界分支汇总表

| 场景 | 触发点 | 处理 | 结果 |
| --- | --- | --- | --- |
| `build` 时设备/队列为空 | `build` 前置检查 | `logger.error("…句柄或队列不完整")` | 返回假，无副作用 |
| `build` 时交换链未构建 | `build` 前置检查 | `logger.error("…交换链尚未构建…")` | 返回假 |
| `build` 时 `frame_overlap == 0` | `build` 前置检查 | `logger.error("…在途帧数必须为正")` | 返回假 |
| 第 i 个帧槽创建失败 | `frame_slot_create` | 内部先销毁该槽半成品；`build` 记 error 后 `destroy()` 整体回退 | 返回假，已建帧槽全部回收 |
| 帧上下文/交换链未就绪 | `render` 前置检查 | `logger.error("提交呈现:: …尚未构建")` | 返回假（硬错误） |
| 交换链图像或信号量为空 | `render` 前置检查 | `logger.error("提交呈现:: 交换链图像或信号量为空")` | 返回假（硬错误） |
| 帧栅栏查询遇硬错误（`slot_fence_wait`） | `render` 第 c 步 / `slot_wait` | `vk_result_check(status, "vkGetFenceStatus")` 记日志 | 返回假（硬错误） |
| 等当前帧槽栅栏失败 | `render` 第 c 步 / `slot_wait` | `slot_fence_wait` 内 `vk_result_check` 记日志 | 返回假（硬错误） |
| 取图像返回 `VK_ERROR_OUT_OF_DATE_KHR` | `render` 第 e 步 | 置 `rebuild_needed_out=true`、`logger.debug`、**不重置栅栏、不自增计数** | **返回真**（提前返回，上层重建） |
| 取图像返回 `VK_SUBOPTIMAL_KHR` | `render` 第 e 步 | 同上 | 返回真 |
| 取图像其它非成功码 | `render` 第 e 步 | `vk_result_check` 记 error | 返回假（硬错误） |
| `vkResetFences` 失败（取图像成功后） | `render` 第 f 步 | `vk_result_check` 记 error；栅栏停留于未发出 | 返回假（视为终止；调用方须停止渲染） |
| `vkResetCommandPool` 失败 | `render` 第 f 步 | `vk_result_check` 记 error | 返回假（硬错误） |
| `vkQueueSubmit2` 失败 | `submit_present` | `vk_result_check` 记 error | 返回假（硬错误） |
| 呈现返回 `VK_ERROR_OUT_OF_DATE_KHR`/`VK_SUBOPTIMAL_KHR` | `submit_present` | 置 `rebuild_needed_out=true`、`logger.debug` | 返回真（非硬错误） |
| 呈现其它非成功码 | `submit_present` | `vk_result_check` 记 error | 返回假（硬错误） |
| 渲染项缺管线/顶点/索引缓冲或索引数为 0 | `command_record` | `continue` 跳过该项 | 该项不绘制，其余继续 |
| 描述符集数量为 0 | `command_record` | 不绑定描述符集 | 该渲染项按无描述符集绘制 |
| 推送常量为空或大小为 0 | `command_record` | 不推送 | 该渲染项按无推送常量绘制 |
| UI 回调为空或 `fn` 为空 | `command_record` 第 10 步 | 跳过 UI 阶段 | 本帧不绘制 UI，其余照常 |
| `slot_wait` 时帧上下文未构建 | `slot_wait` | `logger.error("帧槽创建:: …无法等待帧槽")` | 返回假（硬错误） |
| 延迟队列为空 | `deferred_flush` | 直接返回 | 空操作 |
| 重复 `destroy` / 析构 | `destroy` 各守卫 | 跳过已释放对象 | 幂等无副作用 |
| 离屏目标未就绪（颜色图像/视图为空或范围为零） | `render_to_target` 前置检查 | `logger.error("提交呈现:: 帧上下文或离屏目标尚未就绪")` | 返回假（硬错误） |
| 离屏回读容量不足 | `render_to_target` 回读准备 | `logger.error("提交呈现:: 离屏回读目标容量不足（需 {} 字节，有 {} 字节）")` | 返回假（硬错误） |
| 离屏提交失败 | `render_to_target` 提交步 | `vk_result_check(vkQueueSubmit2（离屏）)` 记 error | 返回假（硬错误） |
| 后处理链交换链范围为零 | `render_chain_present` 前置 | `logger.error("提交呈现:: 交换链范围为零（后处理链）")` | 返回假（硬错误；**第十七轮新增**；原「目标范围不一致」拒绝已随尺寸独立解除） |
| 后处理链级数 ≥ 2 但目标不足 2 个 | `render_chain_present` 前置 | `logger.error("提交呈现:: 后处理级数 {} ≥ 2 但目标组仅 {} 个（后处理链）")` | 返回假（硬错误；**第十五轮新增**） |

### 7.5 主流程四：离屏渲染一帧（`render_to_target`；本版次新增）

1. **调用方（渲染器门面）**：取本帧槽 UBO / 描述符集（同交换链路径，`slot_index_get` / `slot_wait`），组装渲染项后按**三路互斥**分派（`present_target` 有效且资源就绪 → 同帧多 pass，见 §7.6；否则 `active_target` 有效 → 离屏；否则交换链）——离屏分支用 `render_target.target_get(handle, ...)` 取「颜色图像 / 颜色视图 / 深度视图 / 范围」组装 `Frame_Render_Target`，调 `frame.render_to_target(target, items, count, clear_color, ui_callback, readback_ptr)`；交换链分支调 `frame.render(...)`。
2. **`render_to_target`**：
   a. 前置检查（帧上下文 + 目标颜色图像 / 视图 / 范围）；失败返回假。
   b. 取当前帧槽 `slots[frame_count % frame_overlap]`。
   c. `slot_fence_wait(slot)` → `vkResetFences` → `vkResetCommandPool`；任一失败返回假。
   d. 若请求回读：校验容量并 `readback_buffer_ensure(目标宽 × 高 × 4)`。
   e. `command_record_target(...)`：颜色 `SHADER_READ_ONLY → COLOR_ATTACHMENT`（进入）→ 动态渲染（清屏 + `items_record` 逐项 + 可选 UI）→ `vkCmdEndRendering` → 有回读则 `COLOR_ATTACHMENT → TRANSFER_SRC → SHADER_READ_ONLY`、无回读则 `COLOR_ATTACHMENT → SHADER_READ_ONLY`。
   f. **仅以帧栅栏提交**：`vkQueueSubmit2(graphics_queue, 1, &submit_info /*仅命令*/, slot.in_flight_fence)`；**不取交换链图像、不发 / 等信号量、不呈现**。
   g. 若请求回读：`readback_read(slot, *readback, target.extent)`。
   h. `++frame_count` → `deferred_flush()` → 返回真。
3. **调用方**：离屏结果在帧间恒处于 `SHADER_READ_ONLY_OPTIMAL`，可随时经 `texture_bind_target` 采样合成；如需显示则于后续帧切回交换链路径（`render_target_set(0)`）并绑定目标为纹理绘制。

### 7.6 主流程五：同帧多 pass 一帧（`render_to_target_present`；本轮新增）

1. **调用方（渲染器门面 `frame_render`）**：取本帧槽 UBO / 描述符集；若 `present_target != 0` 且 `post_resources_ensure()` 就绪，先向本帧实例存储**追加一个单位模型矩阵**（后处理全屏四边形以此为实例缓冲来源；需先于实例缓冲写入，且实例存储已满时回落原路径），并把离屏目标颜色写入各帧槽的**后处理采样器集**（`pipeline.post_texture_bind`）。
2. **门面组装**：`render_target.target_get(present_target, ...)` 取目标附件、`mesh.mesh_record_get(fullscreen_mesh, ...)` 取全屏四边形缓冲；组装 `post_item`（后处理管线 `pipeline.pipeline_by_handle_get(post_pipeline)`、布局 `layout_get()`、set0 `scene_set_get(slot)`、set1 `post_set_get(slot)`、顶点/索引 = 全屏网格缓冲、实例 = 本帧槽实例缓冲 + 单位矩阵偏移）后调 `frame.render_to_target_present(swapchain, target, items, count, post_item, clear_color, rebuild_needed, readback_ptr)`。
3. **`render_to_target_present`（第十轮起为薄封装）**：函数体仅一行 `return render_chain_present(swapchain, target, Frame_Render_Target{}, items, item_count, &post_item, 1, clear_color, rebuild_needed_out, readback);`——后续「前置校验（含**目标范围硬校验**）→ 取帧槽 → `slot_fence_wait` → 取图像 → `vkAcquireNextImageKHR`（过期 / 次优置 `rebuild_needed_out`）→ `vkResetFences` → `vkResetCommandPool` → 回读准备 → `command_record_chain_present(...)`（单级即两 pass，见 §6.17 / §6.20）→ 取呈现完成信号量 → `submit_present` → 可选回读 → 统计累计 → `++frame_count` → `deferred_flush`」全部由 `render_chain_present` 执行（见 §7.8 / §3.18）；单级时 `post_count = 1`，`second_target` 不被使用。
4. **前置不完整回落**：目标或全屏网格不就绪、后处理资源未就绪或实例存储已满时，回落原路径（离屏 / 交换链）。

### 7.7 资源卸载收口与帧统计示例（本轮新增）

**链路一：运行时卸载网格（门面 `mesh_unload`）**

1. 门面调 `impl->mesh.mesh_detach(handle, record)`（见《渲染层-网格》）：句柄无效或记录已空 → 返回假，门面直接返回（不销毁）；
2. 摘出成功 → 组装 `Deferred_Entry`（`memory_resources` 填一条 `{buffer = record.buffer, buffer_allocation = record.allocation}`）；
3. `impl->frame.deferred_push(std::move(entry), impl->frame.in_flight_count_get() + 1)`——`release_frame = frame_count + 在途帧数 + 1`；
4. 之后每帧 `deferred_flush()` 检查：`release_frame <= frame_count` 时 `deferred_entry_release` 把该缓冲经 `memory->buffer_destroy` 归还并移除条目。**纹理**同法（填 `image` ＋ `image_allocation` ＋ `view`）；**渲染目标**填颜色与深度两条。

**链路二：写满帧槽 `set1` / 切采样器 / 注销管线前收口（门面 `texture_bind_set` / `texture_sampler_state_set` / `texture_bind_target` / `pipeline_unload`）**

1. 门面解析目标视图 → 记录 `impl->bound_view`（纹理与渲染目标共用该语义）；
2. **`impl->frame.frames_wait()`**——等全部帧槽前一次提交完成（此时无命令缓冲在途引用旧 `set1`）；
3. 逐帧槽 `pipeline.texture_bind(slot, sampler, view)` 写满 `set1`；`pipeline_unload` 则先 `frames_wait()` 再注销图形管线与两个着色器模块。

**链路三：帧统计取用（门面 `frame_stats_get`）**

1. 每帧 `frame_render`（或其离屏 / 同帧多 pass / 后处理链分支）在提交后写 `last_frame_ms` 并 `frame_stats_accumulate`；
2. 门面 `frame_stats_get()` 组装 `Frame_Stats{frames = impl->frame_count, frame_ms = frame.last_frame_ms_get(), draw_items = frame.total_draw_items_get(), instances = frame.total_instances_get(), drawn_items = frame.total_drawn_items_get(), drawn_instances = frame.total_drawn_instances_get(), …}`（**第十一轮起**另填实际绘制量两项）；未初始化返回全零。

### 7.8 主流程六：N 级后处理链一帧（`render_chain_present`；本轮新增）

1. **调用方（渲染器门面）**：门面按需组装 `scene_target` / `second_target` / `items` / `post_items`（各级后处理绘制项，其 `sampler_set` 分别取 `post_set_get(slot, stage % POST_SET_PER_SLOT)`），并调用 `frame.render_chain_present(swapchain, scene_target, second_target, items, count, post_items, post_count, clear_color, rebuild_needed, readback_ptr)`。
2. **`render_chain_present`**：前置校验（帧上下文 / 交换链 / 级数 / 场景目标 / 级数 ≥ 2 时第二目标 / 逐级后处理项完整性 / **各目标范围与交换链范围一致——第十轮新增硬校验，处置 `R-FRAME-09`**）→ 取帧槽 → `slot_fence_wait` → `gpu_timestamp_read` → 取图像（过期 / 次优置 `rebuild_needed_out`）→ `vkResetFences` → `vkResetCommandPool` → 回读准备 → `command_record_chain_present(...)`（场景 pass ＋ 逐级 ping-pong 后处理 pass，见 §6.20）→ 取呈现完成信号量 → `submit_present` → 可选回读 → 统计累计（场景项 ＋ 逐级后处理项）→ `++frame_count` → `deferred_flush`。
3. **调用方**：若 `rebuild_needed_out == true`，组织交换链重建后继续。

- **R-FRAME-11**：GPU 耗时的**口径**为实现所定——`last_gpu_frame_ms` 为**帧槽环形读回**（滞后 = 在途帧数，需「在途帧数 + 1」帧才读得到首轮结果）；同帧多 pass 路径含两个 pass 之和；`timestampValidBits < 64` 时按位**掩高位**再相减；设备 / 队列族不支持时间戳时 `timestamp_supported` 为假、查询池不建、耗时恒 0（优雅降级）。是否需「同步等待本帧时间戳就绪」或调整读回时机，源码未定；以实现为准，登记待确认（与门面 `R-FACADE-10` 同源）。

**本版次（后处理链扩展）待确认（编号 `R-FRAME-12`；第十轮部分结案）**：

- **R-FRAME-12**：N 级后处理链（`render_chain_present` / `command_record_chain_present`）的取舍与分工——
  ① **级数上限（第十轮已结案，改由门面约束）**：帧模块 `render_chain_present` **本身不设级数上限**（只接受 `post_count`，仅约束「`post_count >= 1`」与「`post_count >= 2` 时须给出 `second_target`」）；级数上限改由**门面** `post_chain_set` 约束（`Impl::POST_CHAIN_MAX_STAGES = 8`，`count` 超出即整链拒绝并 `logger.error` 记录实际级数与上限）。分工：帧模块只管「给定级数能否执行」，门面管「链能设多长」。
  ② **链只存管线句柄（第十一轮已结案）**：链加载时只登记后处理管线句柄，句柄失效由门面在 `pipeline_unload` 时摘除；**两层均有防护** —— 门面 `frame_render` 组装各级绘制项时逐级 `pipeline_by_handle_get`，任一级为空即 `items_ready = false` 并整帧回落原路径；帧模块 `render_chain_present` 又在录制前逐级硬校验绘制项完整性并记「第 N 级」错误。故「帧模块不校验链成员」不构成隐患。
  ③ **两套录制实现并存（第十轮已结案）**：单级 `render_to_target_present` 已薄封装至 `render_chain_present`（`post_count = 1`），`command_record_target_present` 已删除，录制统一由 `command_record_chain_present` 承担。
  剩余开放项仅「每帧后处理共用 1 个实例位（队列到期前不得复用该实例）」。以上以实现为准，登记备查。

全量清单见同版次目录下的 `待答疑清单.md`。
