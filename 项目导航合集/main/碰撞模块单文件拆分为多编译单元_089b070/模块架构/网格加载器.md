## 一、模块功能

### 1.1 模块定位

「网格加载器」（`Mesh_Loader`）是引擎层 `src/tools/` 下的**资源加载型工具模块**，职责单一：把磁盘上的 Wavefront OBJ 网格文件（`.obj` 文本格式）解析为内存中的**三角形网格数据** `engine::Mesh_Data`，供上层碰撞系统等几何消费者使用。

模块由三份文件构成：

- `引擎层/src/tools/Mesh_Loader/网格加载器.h` —— 公共头文件，声明 `Mesh_Data` 与 `Mesh_Loader`；
- `引擎层/src/tools/Mesh_Loader/局部命名空间使用.h` —— 模块内部 `using` 别名收敛；
- `引擎层/src/tools/Mesh_Loader/core/网格加载器.cpp` —— 全部实现。

**零第三方依赖**：不使用任何第三方 OBJ 解析库，只用 C++ 标准库的流式输入（`ifstream`、`istringstream`、`getline`、`stoll`）手工逐行解析。好处是零外部依赖、行为完全可控；代价是只实现 OBJ 的一个子集（顶点 `v` 与面 `f`），其余记录（法线 `vn`、纹理坐标 `vt`、对象名 `o`、材质库 `mtllib` 等）一律跳过。

### 1.2 解决的核心问题

碰撞系统需要把任意静态网格（地形、建筑、道具）当作碰撞形状。Bullet Physics 的 `btBvhTriangleMeshShape` 需要「三角形网格」（`btTriangleMesh`：顶点数组 + 三角形索引数组）作为数据源。网格加载器正是这条链路的最前端：

```text
.obj 文件（磁盘）
    │  Mesh_Loader::load_obj()
    ▼
Mesh_Data（vertices 平铺顶点 + indices 三角面索引）
    │  Collision_Region::mesh_shape_build()
    ▼
btTriangleMesh（32 位索引 + btVector3 顶点）
    │  btBvhTriangleMeshShape(mesh, true, true)：构建 BVH
    ▼
btBvhTriangleMeshShape（BVH 加速的静态三角形网格碰撞形状）
```

即：**网格加载器是「磁盘资源 → 碰撞形状」转换链的入口**。它只保证：解析成功时输出的 `Mesh_Data` 自洽（索引全部落在顶点数组范围内、每个三角面恰好三个索引）；解析失败时输出被清空并返回 `false`。

### 1.3 功能要点一览

| 能力 | 说明 |
| --- | --- |
| OBJ 顶点解析 | 行首标记 `v` 的行，读取前三个坐标分量（`double` 精度读取、`float` 精度存储），允许附带第四个齐次分量（忽略） |
| OBJ 面解析 | 行首标记 `f` 的行，逐个读取面顶点标记，支持 `v`、`v/vt`、`v/vt/vn`、`v//vn` 四种写法 |
| 多边形三角化 | 任意 ≥3 顶点的多边形面，以首个顶点为扇形中心展开为若干三角面 |
| 索引换算 | 正向索引按 OBJ 约定自 1 起算，换算为自 0 起算的内部下标；负索引自顶点数组末尾起算 |
| 索引越界防护 | 任何换算后的索引超出 `[0, 顶点数)` 立即判定整个加载失败 |
| 路径双源解析 | 先按原样路径（相对当前工作目录）尝试，失败后回退到可执行文件目录下的绝对路径 |
| 体量防护 | 文件体量上限 64 MiB；顶点数量上限 1,000,000 |
| 失败清理 | 任何失败路径都清空输出 `Mesh_Data`，保证调用方拿到的要么是完整数据、要么是空数据 |

### 1.4 非目标（明确不做的事）

- 不解析法线 / 纹理坐标（`vn` / `vt` 行整体跳过，面标记中的 `vt` / `vn` 索引部分被丢弃）；
- 不加载材质（`.mtl`）；
- 不产出顶点属性（UV、切线、顶点色）——`Mesh_Data` 只有位置数据；
- 不处理平滑组、分组（`g`）、对象名（`o`）语义；
- 不执行多线程解析，`load_obj` 为同步阻塞式加载。

## 二、模块提供接口

### 2.1 数据结构 `engine::Mesh_Data`

```cpp
namespace engine
{
	//网格数据
	struct Mesh_Data
	{
		//顶点坐标（按 x、y、z 依次平铺）
		std::vector<float> vertices;
		//三角面索引（每三个一组，指向顶点数组）
		std::vector<uint32_t> indices;
	};
}
```

字段语义：

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `vertices` | `std::vector<float>` | 顶点坐标按 x、y、z 依次平铺：第 i 个顶点为 `(vertices[3i], vertices[3i+1], vertices[3i+2])`，顶点数 = `vertices.size() / 3` |
| `indices` | `std::vector<uint32_t>` | 三角面索引，每三个一组构成一个三角面：第 j 个三角面为 `(indices[3j], indices[3j+1], indices[3j+2])`，三角面数 = `indices.size() / 3` |

约定：

- 调用方无需预先清空该结构体——`load_obj` 第一步就会 `clear()` 两个数组；
- 结构体是纯数据聚合，无自定义构造 / 析构 / 拷贝控制，语义为值类型；
- 索引类型 `uint32_t`（无符号 32 位），与子弹库 `btTriangleMesh` 的 32 位索引模式匹配。

### 2.2 类 `engine::Mesh_Loader`

```cpp
namespace engine
{
	//网格加载器
	class Mesh_Loader
	{
	public:
		//加载OBJ网格文件
		static bool load_obj(const std::string& mesh_path, Mesh_Data& receiver);
	private:
		//文件体量上限（64 MiB）
		inline static constexpr uint64_t max_file_size = 64ull * 1024 * 1024;
		//顶点数量上限
		inline static constexpr size_t max_vertex_count = 1000000;

		//面顶点索引解析（支持 v、v/vt、v/vt/vn、v//vn 四种写法）
		static bool face_index_parse(const std::string& token, size_t vertex_count,
			int64_t& receiver);
		//多边形面三角化（以首个顶点为扇形中心）
		static void face_triangulate(const std::vector<int64_t>& face, Mesh_Data& receiver);
	};
}
```

`Mesh_Loader` 是**只有静态成员的类**（无实例、无状态、无构造语义），可视为命名空间式的接口容器。

### 2.3 公有接口 `load_obj`

```cpp
static bool load_obj(const std::string& mesh_path, Mesh_Data& receiver);
```

参数语义：

| 参数 | 语义 |
| --- | --- |
| `mesh_path` | 网格文件路径（UTF-8 的 `std::string`）。可为相对路径（按当前工作目录或可执行文件目录解释）或绝对路径；中文路径经 `string_to_path` 转换后受支持 |
| `receiver` | 输出接收器。成功时填充 `vertices` 与 `indices`；失败时两者被清空 |

返回值语义：

- `true`：加载成功。`vertices` 非空、`indices` 非空（至少一个三角面），且全部索引合法；
- `false`：加载失败。`receiver` 两个数组均被清空（空容器）。

调用前提：

- 无前置初始化要求（模块无全局状态需初始化）；
- `mesh_path` 为空字符串时立即失败；
- 文件须存在且为普通可读文件（经 `Data_Validator::path_check` 校验）且体量 ≤ 64 MiB；
- 文件内容须含至少一个合法三角面。

### 2.4 私有接口（不对外暴露）

**`face_index_parse`**：

```cpp
static bool face_index_parse(const std::string& token, size_t vertex_count, int64_t& receiver);
```

- `token`：面顶点标记（如 `"3"`、`"1/2"`、`"2/3/4"`、`"1//5"`）；
- `vertex_count`：当前已解析顶点数（`receiver.vertices.size() / 3`）；
- `receiver`：输出换算后**自 0 起算**的顶点下标；
- 返回 `true` 表示成功；`false` 表示空索引 / 数值非法 / 越界。

**`face_triangulate`**：

```cpp
static void face_triangulate(const std::vector<int64_t>& face, Mesh_Data& receiver);
```

- `face`：已换算为自 0 起算下标的多边形顶点序列（≥3 个）；
- 无返回值、无失败路径（调用前已保证 `face.size() >= 3` 且索引全部合法）；
- 效果：以 `face[0]` 为扇形中心，把 n 边形展开为 n-2 个三角面写入 `receiver.indices`。

### 2.5 失败路径总表

`load_obj` 共 10 条失败路径，每条**先清空输出再返回 `false`**：

| # | 触发条件 | 代码位置 | 日志文本 | 输出状态 |
| --- | --- | --- | --- | --- |
| 1 | `mesh_path` 为空串 | 阶段 2 `if (mesh_path.empty())` | `Mesh_Loader::网格路径为空` | 已清空 → false |
| 2 | 原样路径与可执行目录绝对路径均无效（`path_check` 均假） | 阶段 3 `else` | `Mesh_Loader::网格路径不可读取({})` | 空输出 → false |
| 3 | `file_size` 查询出错（`error_code` 非空） | 阶段 4 `if (ec)` | `Mesh_Loader::网格体量查询失败({})` | 空输出 → false |
| 4 | 体量 > 64 MiB | 阶段 4 `if (body_size > max_file_size)` | `Mesh_Loader::网格体量超限({} 字节)` | 空输出 → false |
| 5 | `ifstream` 打开失败 | 阶段 5 `!file.is_open()` | `Mesh_Loader::网格文件打开失败({})` | 空输出 → false |
| 6 | `v` 行读不出三个 `double` 分量 | `v` 分支读入判定 | `Mesh_Loader::顶点行格式非法` | 清空两数组 → false |
| 7 | 顶点数已达 1,000,000 再遇 `v` 行 | `v` 分支上限检查 | `Mesh_Loader::顶点数量超限({})` | 清空两数组 → false |
| 8 | 面顶点标记解析失败（8a 空索引 / 8b 非数字或超范围 / 8c 越界） | `f` 分支循环内 | `面顶点索引为空` / `面顶点索引非法({})` / `面顶点索引越界({})` | 清空两数组 → false |
| 9 | `f` 行解析出的顶点数 < 3 | `f` 分支 `if (face.size() < 3)` | `Mesh_Loader::面顶点不足三个` | 清空两数组 → false |
| 10 | 整文件解析完毕 `indices` 仍为空 | 阶段 7 终检 | `Mesh_Loader::网格未包含有效三角面({})` | 只清空 `vertices`（`indices` 本就空）→ false |

**失败原子性结论**：全部失败路径都保证「返回 `false` 时 `receiver` 两个数组为空」。因为顶点 / 面是**边解析边写入**的，「先解析到一半、后失败」的路径（6 / 7 / 8 / 9）必须显式 `clear()`——这正是代码中重复出现 `receiver.vertices.clear(); receiver.indices.clear();` 的原因；路径 10 只清空 `vertices`，此时 `indices` 已保证为空。调用方可无条件信任「`true` → 数据完整可用；`false` → 无残留数据」。

### 2.6 行为契约速查

| 契约项 | 内容 |
| --- | --- |
| 前置条件 | `mesh_path` 为 UTF-8 编码的字符串；调用方无需初始化 `receiver`（`load_obj` 首先清空） |
| 后置条件（成功） | `vertices.size()` 非空且为 3 的倍数；`indices.size()` 非空且为 3 的倍数；全部索引 ∈ `[0, vertices.size()/3)` |
| 后置条件（失败） | `vertices` 与 `indices` 均为空容器 |
| 不变量 | 三角面只引用「已解析出」的顶点；面出现在其引用顶点之后才能成功，乱序文件会因越界失败 |
| 异常约定 | 不向调用方抛出；全部失败以返回 `false` + `Log::warn` 表达 |
| 线程安全 | 模块无可变静态状态（两个上限为 `constexpr` 只读）；并发调用且各自持有独立 `receiver` 安全，共享同一 `receiver` 需外部同步 |
| 下游契约 | 消费方按顺序写入且关闭查重时，`btTriangleMesh` 内部顶点下标与 `Mesh_Data` 下标一致 |

### 3.3 `load_obj` 内部流程（七阶段）

`load_obj` 内部按「清空 → 校验 → 定路径 → 量体 → 开流 → 逐行解析 → 终检」组织：

```text
阶段1 清空输出：receiver.vertices.clear(); receiver.indices.clear();
阶段2 空路径检查：mesh_path.empty() → warn + return false
阶段3 路径双源解析：
        absolute_path = Engine_Env::absolute_path_get(mesh_path)   // exe_dir / mesh_path
        若 Data_Validator::path_check(mesh_path)         → read_path = string_to_path(mesh_path)
        否则若 Data_Validator::path_check(absolute_path) → read_path = absolute_path
        否则 → warn + return false
阶段4 体量检查：file_size(read_path, ec)；ec 非空 → warn + false；
                body_size > max_file_size(64MiB) → warn + false
阶段5 开流：ifstream file(read_path)；!file.is_open() → warn + false
阶段6 逐行解析：getline(file, line)，按行首标记 flag 分派
        "v" → 读三个 double → 顶点上限检查 → 三个 float 入 vertices
        "f" → 逐 token face_index_parse → face.size()<3 检查 → face_triangulate
        其余 → 跳过（vn/vt/o/g/mtllib/#/s/空行…）
阶段7 终检：receiver.indices.empty() → warn + 清空 vertices + false
        返回 true
```

### 3.4 数据流与类型转换

```text
.obj 文本行流 ──► 顶点行(v) ──► [double x,y,z] ──► [float ×3 push_back] ──► Mesh_Data::vertices
             └──► 面行(f)  ──► [token] ──► face_index_parse ──► int64_t 下标
                          └──► face 集合 ──► face_triangulate ──► uint32_t ×3/三角 ──► Mesh_Data::indices
```

两处类型转换链路：

- 顶点：`double`（文本读取）→ `float`（内存存储）。精度降为单精度，是为与子弹库 `btVector3`（`btScalar` 典型为 `float`）对齐；
- 索引：`int64_t`（`stoll` 解析 + 负索引换算的中间类型）→ `uint32_t`（写索引时 `static_cast<uint32_t>`）。中间用 `int64_t` 是为安全承载「负数 + 顶点数」的换算结果，避免无符号溢出。

复杂度：`load_obj` 为单遍流式解析，时间与文件大小线性相关（`file_size` 为 O(1)、逐行主循环 O(行数)、`face_index_parse` O(token 长度)、`face_triangulate` O(面顶点数)），无二次复杂度路径。内存峰值 ≈ 文件体量 + 行缓冲 + 输出网格体量；顶点上限 1,000,000 对应 `vertices` 约 12 MB。

## 四、模块设计 / 实现细节

### 4.1 路径解析策略（双源回退）

```cpp
//拼可执行文件目录下的绝对路径
path absolute_path = Engine_Env::absolute_path_get(mesh_path);

//实际读取路径
path read_path;
//若原样路径有效（按当前工作目录解释）
if (Data_Validator::path_check(mesh_path))
	read_path = string_to_path(mesh_path);
//若可执行文件目录下的路径有效
else if (Data_Validator::path_check(absolute_path))
	read_path = absolute_path;
//若两者均无效
else
{
	Log::warn("Mesh_Loader::网格路径不可读取({})", mesh_path);
	return false;
}
```

设计动机：

1. **工作目录优先**：传入路径先按「当前工作目录下的相对路径」解释，便于测试用相对路径直接命中；
2. **可执行目录兜底**：工作目录解释失败时，再按「可执行文件所在目录 + 相对路径」解释（`absolute_path_get` 即 `exe_dir_get() / path`），保证**打包部署**场景下资源仍可按相对可执行文件的路径找到；
3. **`path_check` 把关**：两种解释都须通过路径有效性检查（可解析 → 存在 → 普通文件），任一不通过即切换候选；
4. **`string_to_path` 转换**：`mesh_path` 是 UTF-8 的 `std::string`，而 `std::filesystem::path` 在 Windows 需宽字符；`string_to_path` 把 UTF-8 字节序列原样包进 `u8string` 再构造 `path`，从而支持中文路径。

踩坑点：

- **顺序敏感**：先工作目录、后可执行目录。若工作目录下恰有同名但内容不同的文件，而调用方本意是引用可执行目录下的文件，会「错读」；当前无强制指定解析基址的开关；
- **`absolute_path` 无条件计算**：即使工作目录解释成功，也会先调用一次 `absolute_path_get`（内部触发 `exe_dir_get` 的懒初始化），属轻微开销，语义无碍。

### 4.2 体量限制（64 MiB 上限）

```cpp
//异常信息记录
error_code ec;
//获取文件体量
uintmax_t body_size = file_size(read_path, ec);
//若体量查询失败
if (ec)
{
	Log::warn("Mesh_Loader::网格体量查询失败({})", mesh_path);
	return false;
}
//若文件体量超限
if (body_size > max_file_size)
{
	Log::warn("Mesh_Loader::网格体量超限({} 字节)", body_size);
	return false;
}
```

要点：

- 使用 `std::filesystem::file_size(path, ec)` 的无异常重载，用 `error_code` 吸收系统错误，符合引擎层「接口不抛异常、失败返回标记」的约定；
- 64 MiB 是**加载前的预检查**，比「边读边检查」更早拦截超大文件；
- 上限是「文件体量」而非「解析后内存占用」：一个 64 MiB、几乎全是 `v` 行的 OBJ 可能解析出更大内存数据，故另有顶点数量上限兜底（见 4.3）。

### 4.3 顶点数量上限（1,000,000）

```cpp
//顶点数量超限检查
if (receiver.vertices.size() / 3 >= max_vertex_count)
{
	Log::warn("Mesh_Loader::顶点数量超限({})", max_vertex_count);
	receiver.vertices.clear();
	receiver.indices.clear();
	return false;
}
```

要点：

- 检查时机在「读入新顶点之前」，用 `>=` 比较，故实际顶点数最多为 1,000,000；
- `receiver.vertices.size() / 3` 即当前顶点数（`vertices` 严格按每顶点三个分量平铺，除法无余数）；
- 1,000,000 顶点 × 12 字节 ≈ 12 MB，内存可控；同时保证索引换算用 `int64_t` 时 `vertex_count` 不会超出 `uint32_t` 索引表示范围（远低于 `2^31`，匹配子弹库 32 位索引模式）；
- 失败时清空输出，与其余失败路径一致。

### 4.4 逐行解析主循环

```cpp
//逐行解析
string line;
while (getline(file, line))
{
	//行输入流
	istringstream stream(line);
	//行首标记
	string flag;
	stream >> flag;

	//顶点行
	if (flag == "v")
	{
		//顶点坐标分量
		double coordinate_X = 0.0, coordinate_Y = 0.0, coordinate_Z = 0.0;
		//读取前三个分量（OBJ 允许附带齐次分量，本加载器忽略）
		if (!(stream >> coordinate_X >> coordinate_Y >> coordinate_Z))
		{
			Log::warn("Mesh_Loader::顶点行格式非法");
			receiver.vertices.clear();
			receiver.indices.clear();
			return false;
		}
		//…顶点上限检查后，三个分量 static_cast<float> 压入 vertices
	}
	//面行
	else if (flag == "f")
	{
		//…逐 token face_index_parse；face.size()<3 检查；face_triangulate
	}
	//其余行（法线、纹理坐标、注释、对象名等）一律跳过
}
```

解析细节：

1. **行首标记**：`istringstream stream(line); stream >> flag;` 提取第一个空白分隔 token 作为行类型；`stream >>` 天然跳过行首空白与空行；
2. **`v` 行**：用 `double` 读三个分量；`stream >>` 失败（分量非数字或不足三个）即置流失败位；OBJ 规范允许 `v` 行带第 4 个齐次坐标 w（缺省 1），本模块**只读前三个、忽略后续**（即隐式假设 w=1，不执行 `x/w` 规范化，属已知简化）；读入后三个分量 `static_cast<float>` 压入 `vertices`；
3. **`f` 行**：`while (stream >> token)` 循环读取面顶点标记直到行尾，每个 token 交 `face_index_parse`；任一失败 → 整体失败；收集完毕后 `face.size() < 3` → 失败；否则 `face_triangulate`；
4. **其余行**：`vn` / `vt` / `o` / `g` / `mtllib` / `usemtl` / `#` / `s` 等一律忽略——`stream >> flag` 取走标记后不再消费行内其余内容。

**本模块实现的 OBJ 子集对照表**：

| OBJ 关键字 | 标准语义 | 本模块处理 | 说明 |
| --- | --- | --- | --- |
| `v x y z [w]` | 几何顶点（w 为齐次坐标，缺省 1） | 支持 | 读前三个分量（`double`），忽略 w；`float` 存储 |
| `vt u [v] [w]` | 纹理坐标 | 跳过 | 不产出 UV |
| `vn i j k` | 法线向量 | 跳过 | 不产出法线 |
| `f v1[/vt1][/vn1] ...` | 面（多边形，≥3 顶点） | 支持 | 四种顶点写法全兼容；仅取顶点索引，其余丢弃 |
| `o name` / `g name` | 对象名 / 分组名 | 跳过 | |
| `s n` / `s off` | 平滑组 | 跳过 | |
| `mtllib` / `usemtl` | 材质库引用 / 材质使用 | 跳过 | |
| `# comment` | 注释 | 跳过 | 行首标记不匹配任何处理分支 |
| 空行 | — | 跳过 | `stream >> flag` 失败，flag 为空串 |
| 未知关键字 | 扩展 / 厂商自定义 | 跳过 | 如 `vp`、`l`、`p` 等 |

**边界情况**：

- **行首前导空格**：`stream >> flag` 自动跳过；
- **Windows CRLF 行尾**：`getline` 以 `\n` 分隔，`\r` 残留在行尾；但 `\r` 是空白字符，`stream >> token` 不会让 `\r` 进入 token，故 CRLF 文件安全；
- **仅 `\r` 换行（经典 Mac 格式）**：`getline` 不以 `\r` 为分隔，整文件会被视为一行——当前**未支持**；
- **空行**：`stream >> flag` 失败，`flag` 为空串，落入「其余行」跳过；
- **UTF-8 BOM**：若文件带 BOM（`EF BB BF`），首行首 token 为 `"\xEF\xBB\xBFv"`，不匹配 `"v"`，首行被跳过——当前**未处理 BOM**（OBJ 通常为纯 ASCII，影响低）；
- **行内注释**：`v 1 1 2 # 注释` 安全（`v` 行只精确读三个数值）；但 `f 1 2 3 # 注释` 中 `#` 会被当作 token 交给 `face_index_parse`，经 `stoll` 抛异常 → **整个加载失败**（日志 `面顶点索引非法(#)`）。OBJ 规范中面行注释应单独成行；本模块未过滤行内 `#`，导出 OBJ 时不应写行内注释。

### 4.5 `face_index_parse`：面顶点索引解析

```cpp
bool Mesh_Loader::face_index_parse(const string& token, size_t vertex_count,
	int64_t& receiver)
{
	//截取首个斜杠之前的内容（顶点索引部分）
	size_t cut = token.find('/');
	string number = (cut == string::npos) ? token : token.substr(0, cut);

	//若索引内容为空
	if (number.empty())
	{
		Log::warn("Mesh_Loader::面顶点索引为空");
		return false;
	}

	//索引数值
	int64_t index = 0;
	try
	{
		//十进制整数转换
		index = stoll(number);
	}
	catch (const std::exception&)
	{
		Log::warn("Mesh_Loader::面顶点索引非法({})", number);
		return false;
	}

	//若为负索引（自末尾起算）
	if (index < 0)
		//换算为绝对下标
		index = static_cast<int64_t>(vertex_count) + index;
	//若为正向索引（OBJ 自 1 起算）
	else
		index -= 1;

	//越界检查
	if (index < 0 || static_cast<size_t>(index) >= vertex_count)
	{
		Log::warn("Mesh_Loader::面顶点索引越界({})", number);
		return false;
	}

	receiver = index;
	return true;
}
```

**四种写法的统一处理**：顶点索引永远是标记的第一个字段，因此「截取首个 `/` 之前」在所有写法下都恰好得到顶点索引字符串；`vt` / `vn` 索引部分被直接丢弃。这是「格式归一化」的实例——无需为四种写法分别写解析分支。

| 写法 | 示例 | `token.find('/')` | `number` |
| --- | --- | --- | --- |
| `v` | `3` | `npos` | `"3"` |
| `v/vt` | `3/2` | 位置 1 | `"3"` |
| `v/vt/vn` | `3/2/1` | 位置 1 | `"3"` |
| `v//vn` | `3//1` | 位置 1 | `"3"` |

**索引换算规则**：

- 正向索引：OBJ 顶点自 1 起算，`index -= 1` 变为自 0 起算；OBJ 中 0 是非法值，`0 → -1` 会被越界检查拦下，与本模块「0 索引即失败」的处理一致；
- 负索引：OBJ 负索引表示「自当前顶点末尾起算」，`-1` 指最后一个顶点。换算公式 `index = static_cast<int64_t>(vertex_count) + index`，数学上等价于 `(int64_t)vertex_count - k`（k 为负索引绝对值）：`-vertex_count` 换算为首顶点下标 0，`-(vertex_count+1)` 换算为 -1（越界失败）。显式 `static_cast<int64_t>` 是为防止 `size_t` 与 `int64_t` 混算时负数被提升为巨大无符号值的经典坑。

**越界检查的双重覆盖**：

```cpp
if (index < 0 || static_cast<size_t>(index) >= vertex_count)
```

- `index < 0`：捕获负索引绝对值过大的情况（如 `vertex_count=3` 时 `-5 → -2`）；
- `static_cast<size_t>(index) >= vertex_count`：捕获正向索引超界（如 `vertex_count=3` 时 `9 → 8`）；零索引 `0 → -1` 已由前一条件捕获；
- 由于 `vertex_count ≤ 1,000,000`，`static_cast<size_t>(index)` 不会发生无符号回绕，比较正确。

**`stoll` 的接受范围与异常**：`std::stoll` 默认按**十进制**（`base = 10`）解析，接受可选正负号（`+` / `-`）、十进制数字串（可带前导零）；`stream >>` 已剥离空白，故前导空白不会出现。以下情况抛异常，被 `catch (const std::exception&)` 统一捕获并返回 `false`：无数字字符（`std::invalid_argument`，如 `"abc"`、`"#"`）、数值超出 `int64_t` 范围（`std::out_of_range`）。注意：因基数为 10，`"0x10"` 只会解析出 `0`（停在 `x`），**不按十六进制 / 八进制前缀解释**；`catch` 中的 `std::exception` 基类捕获使两类异常都被收敛，不向调用方抛出。

### 4.6 `face_triangulate`：多边形扇形三角化

```cpp
void Mesh_Loader::face_triangulate(const vector<int64_t>& face, Mesh_Data& receiver)
{
	//以首个顶点为扇形中心，逐个三角面展开
	for (size_t i = 1; i + 1 < face.size(); ++i)
	{
		receiver.indices.push_back(static_cast<uint32_t>(face[0]));
		receiver.indices.push_back(static_cast<uint32_t>(face[i]));
		receiver.indices.push_back(static_cast<uint32_t>(face[i + 1]));
	}
}
```

算法结论：

- 对 n 个顶点的多边形面输出 n-2 个三角面 `(p0, pi, pi+1)`（i 从 1 到 n-2），共享顶点 `p0`，形似扇骨，故称「扇形三角化」（fan triangulation）；
- 实例：三角形 `[a,b,c]` → `(a,b,c)`；四边形 `[a,b,c,d]` → `(a,b,c)`、`(a,c,d)`（测试用例「四边形面被三角化」验证的正是此结果）；
- **环绕方向与面朝向**：若多边形顶点按逆时针排列，各输出三角形保持相同环绕方向、法线一致；子弹库 `btTriangleMesh` 不依赖特定环绕方向（双面检测），故本模块不矫正环绕方向，镜像模型环绕反转仍可正常碰撞，仅影响法线可视化 / 单面材质语义；
- **退化三角形**：两点重合或三点共线会产出零面积三角形，本模块**不检测退化**直接写入（如 `f 5 -1 -3 -2` 在 `vertex_count=5` 时 `5→4`、`-1→4`，产生退化面 `(4,4,2)`）；子弹库对零面积三角形返回「不接触」，通常无害，仅轻微浪费 BVH 节点；
- **凹多边形限制（已知）**：扇形三角化不判断凹凸性，对凹多边形（如 L 形、U 形）会生成**越出多边形边界**的三角形，导致碰撞形状「多一块」或「少一块」。缓解方式为导出时预三角化（建模软件的 Triangulate 命令）或用耳切法等凸分解预处理；本模块选扇形法而非耳切法的理由是实现仅 10 行、零依赖、对凸 / 已三角化输入完全正确，且碰撞资产凹面概率低。

### 4.7 终检：无三角面即失败

```cpp
//若未解析出任何三角面
if (receiver.indices.empty())
{
	Log::warn("Mesh_Loader::网格未包含有效三角面({})", mesh_path);
	receiver.vertices.clear();
	return false;
}
```

要点：只检查 `indices`（碰撞形状需要三角形，只有顶点没有面的网格无用）；失败时**只清空 `vertices`**（此时 `indices` 本就为空），以履行「失败时输出被清空」的契约；该检查覆盖「文件里只有顶点 / 注释 / 法线」的场景（测试用例「无有效三角面时加载失败」）。

### 4.8 与子弹库的数据对接（消费方视角）

当前唯一消费方是 `Collision_Region::mesh_shape_build`（`引擎层/src/core/spatial/collision/Collision_Region/core/形状构建.cpp`）：

```cpp
//网格数据
Mesh_Data mesh_data;
//加载网格文件
if (!Mesh_Loader::load_obj(mesh_path, mesh_data))
	return false;

//分配三角形网格内存（32 位索引 + btVector3 顶点）
if (!memory_malloc<Triangle_Mesh>(mesh_receiver, true, true))
	return false;

//预留顶点与索引容量
mesh_receiver->preallocateVertices(static_cast<int>(mesh_data.vertices.size() / 3));
mesh_receiver->preallocateIndices(static_cast<int>(mesh_data.indices.size()));

/*
写入顶点坐标
findOrAddVertex 在关闭查重时按调用顺序追加顶点并返回其顺序下标，
故按索引顺序写入后，顶点数组下标与网格数据下标一一对应。
*/
for (size_t i = 0; i + 2 < mesh_data.vertices.size(); i += 3)
	mesh_receiver->findOrAddVertex(Vector3(mesh_data.vertices[i], mesh_data.vertices[i + 1],
		mesh_data.vertices[i + 2]), false);
//写入三角面索引（顶点须先行写入）
for (size_t i = 0; i + 2 < mesh_data.indices.size(); i += 3)
	mesh_receiver->addTriangleIndices(mesh_data.indices[i], mesh_data.indices[i + 1],
		mesh_data.indices[i + 2]);

//分配BVH三角形网格形状（数据源由调用方一并持有）
if (!memory_malloc<Bvh_Triangle_Mesh>(shape_receiver, mesh_receiver.get(), true, true))
{
	mesh_receiver.reset();
	return false;
}
```

关键约定：

1. **平铺布局的消费方式**：按 `i += 3` 步进读 `vertices` 组装 `btVector3`，按 `i += 3` 步进读 `indices` 调 `addTriangleIndices`——`Mesh_Data` 的平铺 / 三一组布局与子弹库逐顶点 / 逐三角形写入模型一一对应；
2. **关闭查重**：`findOrAddVertex(..., false)` 关闭顶点去重，按调用顺序追加顶点，从而保证子弹库内部顶点下标 == `Mesh_Data` 顶点下标；若开启查重，重复顶点会被合并导致索引错位；
3. **写入顺序**：顶点必须先于索引写入（`addTriangleIndices` 依赖顶点已存在）；
4. **数据所有权**：`btBvhTriangleMeshShape` 构造参数直接持有 `btTriangleMesh*`，故 `mesh_receiver` 与 `shape_receiver` 由 `Collision_Region` 以 `unique_ptr` 成对持有，保证数据源生命周期长于形状（成员声明顺序 `mesh` 先于 `shape`，析构逆序：先 shape 后 mesh）；
5. **`memory_malloc` 包装**：子弹库形状类经 `BT_DECLARE_ALIGNED_ALLOCATOR` 只声明抛异常形式的 `new`，无法用 `new(std::nothrow)`；`形状构建.cpp` 用 `try/catch` 包成「失败返回 `false`」的 `memory_malloc`，符合引擎层「接口不抛异常」约定；
6. **`Mesh_Data` 是栈上局部**：组装完成后随作用域销毁；`btTriangleMesh` 保存的是**拷贝后的顶点 / 索引数据**，非指向 `mesh_data` 的指针，无悬垂风险。

**从磁盘字节到碰撞形状的数据流**：

```text
磁盘 .obj（≤64MiB，≤1,000,000 顶点）
  │ Mesh_Loader::load_obj
  ▼
Mesh_Data{ vector<float> vertices; vector<uint32_t> indices; }
  │ mesh_shape_build：preallocate + findOrAddVertex(...,false) + addTriangleIndices
  ▼
btTriangleMesh（btVector3 顶点；uint32_t 三角面索引；量化 AABB）
  │ btBvhTriangleMeshShape(mesh, true, true)：构建 BVH
  ▼
btBvhTriangleMeshShape（BVH 加速的静态网格碰撞形状）
  │ Collision_Region::boundary_build：挂载 + 静态标志 + 原点变换
  ▼
btCollisionWorld 中的空间边界碰撞对象（参与 broadphase / narrowphase 检测）
```

### 4.9 设计决策复盘

| 决策 | 理由 | 代价 |
| --- | --- | --- |
| 手工解析而非第三方 OBJ 库 | 零依赖、行为可控、便于测试 | 只支持子集，不处理材质 / 法线语义 |
| `double` 读、`float` 存 | 文本解析精度余量 + 与子弹库浮点类型对齐 | 单精度坐标（碰撞场景可接受） |
| 中间用 `int64_t` 承载索引换算 | 负索引 + 顶点数换算避免无符号溢出 | 一次额外类型转换 |
| 失败即清空输出 | 调用方拿到「要么完整、要么为空」的确定状态 | 无（调用方无需自行清理） |
| 顶点上限 1,000,000 | 控制内存峰值与索引表示范围 | 超大网格需外部切分 |
| 文件上限 64 MiB | 拦截超大文件、防御性编程 | 超大网格文件被拒 |
| 路径双源回退 | 兼顾开发（工作目录）与部署（exe 目录）两种运行形态 | 同名文件歧义时按工作目录优先 |
| 扇形三角化而非耳切法 | 10 行实现、零依赖、对凸 / 三角化输入完全正确 | 凹多边形三角化失真 |

### 4.10 异常安全与错误处理约定

- **不向调用方抛异常**：本模块唯一的异常源是 `stoll`（`std::invalid_argument` / `std::out_of_range`），已在 `face_index_parse` 内用 `catch (const std::exception&)` 收敛为返回值 `false`；
- **无资源泄漏**：全部资源由标准库设施经 RAII 管理——`ifstream`（文件句柄）、`istringstream`（行缓冲）、`vector`（输出与中间 `face` 向量）都在栈展开时自动释放；模块内无裸 `new` / `delete`，任何提前 `return` 都不遗留资源；
- **错误吸收**：`file_size(path, ec)` 使用 `error_code` 重载避免 `filesystem` 异常；`ifstream` 打开失败、体量查询失败、顶点 / 面行格式失败均转为「标记返回 + `Log::warn`」；
- **失败清理是显式契约而非异常保证**：失败时主动 `clear()` 输出，见 2.5 / 2.6；
- 该约定与引擎层整体一致：接口以返回标记表达失败，日志记录原因，调用方无需 `try/catch`。

以「碰撞空间构建静态网格边界」为例（`Collision_Region::boundary_build` → `mesh_shape_build` → `load_obj`）：

```text
调用方（测试用例或碰撞代理器）

   ▼
① Collision_Region::boundary_build(mesh_path)                 [空间与边界.cpp]
```

### 5.2 模块间协作矩阵与接口语义

| 协作方 | 交互方式 | 方向 | 接口语义 |
| --- | --- | --- | --- |
| `Engine_Env`（引擎环境） | `absolute_path_get(mesh_path)` | 调用 | 内部把 UTF-8 字符串包为 `u8string`，再拼 `exe_dir_get() / u8_path`；`exe_dir_get()` 首次调用触发 exe 路径查询（Windows `GetModuleFileNameW`）并静态缓存 |
| `Data_Validator`（数据校验器） | `path_check(string)` / `path_check(path)` | 调用 | 三重判定：路径可解析（`begin()==end()` 为假）→ 存在（`exists`）→ 普通文件（`is_regular_file`）；任一失败记 `Log::info` 并返回 false。**不检查体量**（体量由 `load_obj` 自查） |
| `Auxi_Algorithm`（辅助算法） | `string_to_path(mesh_path)` | 调用 | 把 UTF-8 字节序列无转码地包进 `u8string` 构造 `path`，支持中文路径 |
| `Logging`（日志系统） | `Log::warn(...)` | 调用 | 记录全部失败场景；成功路径不记录日志，避免高频刷屏 |
| `Collision_Region`（碰撞空间） | `mesh_shape_build` 消费 `Mesh_Data` | 被调用（上游） | 组装 `btTriangleMesh` 与 `btBvhTriangleMeshShape`，作为空间边界 |
| 测试层 | `网格加载器测试.cpp` 9 例直接调用 `load_obj` | 被调用（测试） | 覆盖成功与失败路径 |

补充：`load_obj` 在双源回退中会调用 `path_check` 两次，若两条路径各有三重失败，可能先产生若干 `Log::info`（校验器级别）再输出 `Log::warn`（加载器级别）。与 `Config_Loader` 的路径语义不完全一致：后者要求以 `assets/config/` 开头并拒绝 `..`（防路径穿越），而网格加载器路径来自引擎内部调用，信任边界不同，无前缀约束与 `..` 检查，且基准目录为「工作目录 + exe 目录」双源。

### 5.4 网格形状在碰撞检测中的角色

`btBvhTriangleMeshShape` 是子弹库常用的**静态三角网格形状**，其检测路径：

1. **宽相位（broadphase）**：`btCollisionWorld` 维护动态 AABB 树，空间边界对象（静态网格）的 AABB 参与重叠对筛选；
2. **窄相位（narrowphase）**：AABB 重叠后，把查询形状与 BVH 中命中的三角形逐个做凸-三角形检测；
3. **BVH 加速**：构造期（`buildBvh=true`）对三角形构建 AABB 层次树，查询按包围盒剪枝，把「全网格三角形」缩小为「可能相交的少数三角形」；
4. **空间边界语义**：`Static_Object_Flag` 使对象不参与连续碰撞（CCD）、只参与离散检测；边界固定在原点，`Collision_Region` 用位移字段描述碰撞体相对位置；典型用于划定碰撞空间的物理边界（地板、墙壁、地形）。

工程约束：三角形数并无硬性上限，但越多则 BVH 构建越久、单次查询命中的三角形越多；1,000,000 顶点上限配合 64 MiB 文件上限，把单网格规模控制在「初始化期构建成本可接受、运行期查询高效」的量级。大世界场景建议按区块拆分（多个 `Collision_Region` / 边界网格），配合四叉树分区做裁剪。

### 7.2 遗留事项与已知边界

1. **UTF-8 BOM 未处理**：带 BOM 的 OBJ 首行（`EF BB BF` + `v ...`）会被当作未知行跳过；若整文件仅该行含顶点，可能触发「无三角面」失败。影响低（OBJ 常规为 ASCII），未修；
2. **凹多边形三角化失真**：`face_triangulate` 的扇形三角化不判断凹凸性，凹面会生成越界三角形。建议上游导出时预三角化；
3. **退化三角形不检测**：零面积三角形被直接写入，靠子弹库自行忽略；
4. **路径解析顺序固化为「工作目录优先」**：无法显式指定仅按可执行目录解析；同名文件歧义时按工作目录优先；
5. **`f` 行行内注释会导致失败**：`#` 会被当作面顶点 token 交 `stoll` 抛异常 → 整体失败。导出 OBJ 时面行注释须单独成行；
6. **经典 Mac（仅 `\r`）换行未支持**：整文件会被视为一行；
7. **顶点上限与文件上限为编译期常量**：不可运行时配置；如需更大网格，应改常量或改为可配置参数；
8. **`load_obj` 为同步阻塞加载**：超大网格会阻塞调用线程（碰撞边界构建发生在初始化阶段，可接受），无异步方案；
9. **与 `Config_Loader` 路径语义不一致**：后者基于 `exe_dir_get()` 且含 `..` 与前缀约束，网格加载器额外支持「工作目录优先」且无安全约束，文档层面需留意。

### 7.3 与源码核对的差异说明

- **原文对 `stoll` 接受范围的描述有误**：原文（附章 D.2.5）称 `std::stoll` 会按基数 0 把 `"0x10"` 解析为 16。实际源码调用的是单参数 `stoll(number)`，默认 `base = 10`，`"0x10"` 只会解析出 `0`（在 `x` 处停止），**不按十六进制 / 八进制前缀解释**。本文已按源码更正；
- **直接依赖文件行数微调**：原文记 `数据校验器.h` 154 行、`引擎环境.h` 142 行、`路径字符串转换.h` 29 行、`碰撞空间.h` 124 行；本次按当前工作区实测分别为 155、143、30、125 行（各多 1 行，属统计口径差异）。模块自身与消费方文件行数与原文一致。
