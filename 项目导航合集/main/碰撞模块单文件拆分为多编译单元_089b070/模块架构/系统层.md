## 1. 模块功能

### 1.1 模块定位

系统层是白银纪元的**玩法逻辑层**，位于引擎层之上、游戏层之下，产出 `SystemCore` 静态库。它把引擎层提供的「对象 / 事件 / 数据校验 / 资源路径」等基础能力，组合成三类游戏要素：

| 子系统 | 目录 | 核心类型 | 解决什么问题 |
|---|---|---|---|
| 实体子系统 | `src/entity/` | `Entity`、`Entity_Manager` | 「游戏对象」的创建、卸载、行为（决策树）驱动；实体是事件参与者与 Lua 行为脚本的宿主 |
| 属性子系统 | `src/prop/` | `Prop`、`Prop_Distributor` | 实体的数值面板（`unordered_map<string,double>` 属性槽）；把「属性槽集合」按分发密钥安全地借给效应系统 |
| 效应子系统 | `src/effect/` | `Prop_Effect`、`Effect_Manager` | 「技能/效果」的构建、分组、按执行阶段触发；效应以 Lua 脚本实现，修改实体的属性槽 |

### 1.2 模块解决的问题

1. **数据与行为的解耦**：实体（Entity）持有行为脚本（Lua 决策树）与属性槽**指针**；属性槽本体由 `Prop` 承载、由 `Entity_Manager` 统一管理。实体「是什么、怎么动」与「数值是多少」分离。
2. **事件驱动的模块协作**：`Entity_Manager`、`Prop_Distributor`、`Effect_Manager` 三个管理器都通过 `Event_Terminal` 接入引擎层事件中转站（`Event_Broker`），以事件（`event`）为唯一协作媒介——配置加载、实体构建/卸载/行动、效应构建/卸载/触发全部走事件通道，模块之间不直接互相持有指针（属性槽借用除外）。
3. **Lua 脚本化**：实体行为、效应逻辑全部由 Lua 脚本承载；C++ 侧负责生命周期、事件路由与属性槽绑定，Sol2 负责 C++/Lua 桥接。脚本里可以读写 `pros`（属性槽表）、`event_set`（事件集合引用）、调用 `send()`（事件发送）。
4. **权限控制**：事件发送与查阅均需 `acl_key`（事件终端生成的权限密钥）；属性槽集合的借用需 `distribute_key`（64 位随机分发密钥）——防止任意模块越权读改属性。
5. **配置驱动**：实体类型与效应的行为/属性/订阅事件均从 JSON 配置加载，配置字段经 `Config_Checker`（注：引擎层现名 `Data_Validator`，遗留问题见 §4.9）校验后注册为加载路径。

### 1.3 服务对象

- **游戏层（未来）**：通过 `SystemCore` 的对外面接入，创建实体、发事件、触发效应。
- **测试层**：对实体/属性/效应子系统做单元测试（当前测试层用例集中在引擎层，系统层用例尚未落位）。
- **配置编辑器 `Config_Editor`**：本层 `src/gui/` 下的独立工具（含 `main`，当前被 CMake 排除，未接入构建，见 §4.10）。

## 2. 模块提供接口

> 系统层对外面（`cmake/对外接口.cmake`）已在《构建与层间契约》文档详述；本节聚焦**运行时接口**——即系统层公共头暴露的类与方法。

### 2.1 `Entity`（动态实体）—— `src/entity/Entity/实体.h`

继承引擎层 `Object`（提供 `object_ID`、`is_valid`、`ID()`/`ID_set()`/`valid()`/`valid_set()`）。

```cpp
namespace engine
{
    class Entity : public Object
    {
    private:
        std::string entity_type{};                                   // 实体类型标签
        std::unordered_map<std::string, double>* property_slot;      // 通用属性槽（指针，绑定到外部）
    public:
        Event_Terminal event_terminal;                               // 事件终端（公开）
    private:
        int64_t acl_key = 0;                                         // 权限密钥
        LuaState action;                                             // 行为脚本（Lua 状态机）
    public:
        Entity(void);                                                // 构造函数
        Entity(const int64_t& ID);                                   // 构造函数
        Entity(const int64_t& ID, const std::string& load_path);     // 构造函数（加载行为）
        Entity(const Entity&) = delete;                              // 禁用拷贝构造
        Entity& operator=(const Entity&) = delete;                   // 禁用拷贝赋值
        Entity(Entity&&) = default;                                  // 默认移动构造
        Entity& operator=(Entity&&) = default;                       // 默认移动赋值
        ~Entity();                                                   // 析构函数
        std::string type(void);                                      // 类型信息获取
        void prop_slot_bind(std::unordered_map<std::string, double>* ptr); // 属性槽绑定
        void action_load(const std::string& load_path);              // 行为加载
        virtual void act(void);                                      // 行为决策
    };
}
```

**逐条解释**：

| 接口 | 签名 | 含义 |
|---|---|---|
| 构造 | `Entity(void)` | 从 `event_terminal.acl_key_gen()` 生成权限密钥 |
| 构造 | `Entity(const int64_t& ID)` | 委托默认构造后设置 `object_ID = ID` |
| 构造 | `Entity(const int64_t& ID, const std::string& load_path)` | 委托 ID 构造后 `action_load(load_path)` |
| 拷贝 | `delete` | **禁用拷贝**——实体含 `LuaState`（sol::state 不可拷贝）与外部指针 |
| 移动 | `default` | **允许移动**——使 `Object_Pool<Entity>` 的 `std::vector<Entity>` 扩容可行 |
| `type` | `std::string type(void)` | 返回 `entity_type`（注意：当前仅声明于头文件，`实体.cpp` 中只返回成员；**无任何地方写入 `entity_type`**，恒为空串，见 §4.5） |
| `prop_slot_bind` | `void(ptr)` | 绑定属性槽指针（不拥有，外部生命周期由 `Entity_Manager` 的 `Object_Pool<Prop>` 保证） |
| `action_load` | `void(load_path)` | 打开全部标准库 → `load_file` → 注册 `pros`/`event_set`/`send` 到 Lua（详见 §4.2） |
| `act` | `virtual void(void)` | 运行 `action["decision"]()` 后清空事件集合 `event_terminal.clear(acl_key)` |

**关键点**：`act()` 是 `virtual`——实体决策可被子类覆盖；`action["decision"]()` 要求 Lua 脚本必须定义 `decision` 函数，否则 Sol2 抛异常（无 try/catch 包裹，属于已知边界）。

### 2.2 `Prop`（属性）—— `src/prop/Prop/属性.h`

```cpp
namespace engine
{
    class Prop : public Object
    {
    private:
        std::unordered_map<std::string, double> property_slot;       // 通用属性槽
    public:
        std::unordered_map<std::string, double>& prop_get(void)
        {
            return property_slot;
        }
    };
}
```

**逐条解释**：

| 接口 | 签名 | 含义 |
|---|---|---|
| `prop_get` | `std::unordered_map<std::string, double>&`（内联） | 返回属性槽**引用**（可读写）；属性名 `string` → 数值 `double` |

`Prop` 是最轻量的容器类：无构造/析构自定义、无拷贝限制（内含可拷贝的 unordered_map）。它继承 `Object` 才能进入 `Object_Pool<Prop>`（`Object_Pool` 有 `requires std::is_base_of_v<Object, T>` 约束）。

### 2.3 `Prop_Distributor`（属性槽分发器）—— `src/prop/Prop_Distributor/属性槽分发器.h`

```cpp
namespace engine
{
    class Prop_Distributor
    {
    private:
        Object_Pool<Prop>* props = nullptr;                          // 属性槽记录集合（指针）
    public:
        Event_Terminal event_terminal;                               // 事件终端
    private:
        int64_t acl_key = 0;                                         // 事件发送权限密钥
        std::optional<uint64_t> distribute_key = std::nullopt;       // 属性槽分发权限密钥
    public:
        Prop_Distributor();                                          // 构造函数
        ~Prop_Distributor();                                         // 析构函数
        void attach(void);                                           // 事件中转站接入
        void prop_slots_bind(std::function< Object_Pool<Prop>*
            (const uint64_t& distribute_key)> bind_entry);           // 属性槽集合绑定
        std::unordered_map<std::string, double>* prop_slot_get(const uint64_t& ID);            // 属性槽获取
        const std::unordered_map<std::string, double>* const_prop_slot_get(const uint64_t& ID) const; // 只读属性槽获取
    private:
        void event_process(std::shared_ptr<event> evt);              // 事件处理
    };
}
```

**逐条解释**：

| 接口 | 签名 | 含义 |
|---|---|---|
| `attach` | `void(void)` | 注册事件接收入口（`event_receiver_register`），并以空订阅集合 `attach("Prop_Distributor", {}, acl_key)` 接入中转站 |
| `prop_slots_bind` | `void(std::function<Object_Pool<Prop>*(const uint64_t&)>)` | 用 `bind_entry(distribute_key.value())` 拿到属性槽对象池指针；**若 `distribute_key` 未生成则警告并直接返回** |
| `prop_slot_get` | `std::unordered_map<std::string, double>*(const uint64_t& ID)` | 可写版本，内部 `const_cast` 复用只读版本 |
| `const_prop_slot_get` | `const ...*(const uint64_t& ID) const` | 只读版本：`props->find(ID)`，找到返回 `&prop->prop_get()`，否则 `nullptr` |
| `event_process` | `void(std::shared_ptr<event>)` | 仅处理 `category=="Key" && tag=="Distributor"` 的事件，取出 `config["key"]`（uint64_t）写入 `distribute_key` |

**关键点**：`Prop_Distributor` **不继承 `Object`**（无需进入对象池）。它通过事件通道获取分发密钥，通过 `bind_entry` 回调（由 `Entity_Manager::prop_slot_get` 提供）拿到属性槽池——两个管理器以「密钥 + 回调」模式协作，不直接持有对方实例。

### 2.4 `Prop_Effect`（效应）—— `src/effect/Effect/效应.h`

```cpp
namespace engine
{
    class Prop_Effect
    {
    private:
        uint64_t inclusion{};                                        // 效应归属（所属实体 ID）
        std::optional<uint64_t> ID;                                  // 效应编号
        std::string name{};                                          // 效应名称
        LuaState script;                                             // Lua 脚本实例
        std::unordered_map<std::string, double>* effect_object;      // 效应作用对象（属性槽指针）
    public:
        Event_Terminal event_terminal;                               // 事件终端
    private:
        int64_t acl_key = 0;                                         // 事件发送密钥
    public:
        Prop_Effect();                                               // 构造函数
        ~Prop_Effect();                                              // 析构函数
        Prop_Effect(Prop_Effect&&) = default;                        // 默认移动构造
        Prop_Effect& operator=(Prop_Effect&&) = default;             // 默认移动赋值
        bool config_read(const nlohmann::json& config);              // 配置读取
        void data_injection(void);                                   // 数据注入
        void ID_bind(const uint64_t& ID);                            // 编号绑定
        void effect_object_bind(std::unordered_map<std::string, double>* object); // 作用对象绑定
        const std::string& effect_name_get(void);                    // 效应名称获取
        void effect_act(void);                                       // 效应触发
    };
}
```

**逐条解释**：

| 接口 | 签名 | 含义 |
|---|---|---|
| 构造 | `Prop_Effect()` | `acl_key = event_terminal.acl_key_gen()` |
| 移动 | `default` | 允许移动（`Object_Pool<effect_record>` 需要）；**无删除拷贝声明但含 LuaState（不可拷贝），拷贝构造被隐式删除** |
| `config_read` | `bool(const nlohmann::json&)` | 校验 `path`/`inclusion`/`name` 字段 → 绝对路径化 → `path_check` → 重置 `script = LuaState{}` → `load_file` → 打开 base/math/string/table 四个标准库 → 记录 inclusion/name；失败返回 false |
| `data_injection` | `void(void)` | 将 `inclusion`/`ID`/`name`/`effect_object`（`sol::as_table`）注入 Lua；注册 `event_set` 与 `send()`；**ID 未绑定时 `Log::error` 后 return** |
| `ID_bind` | `void(const uint64_t&)` | **仅当 `ID` 尚未有值时**才写入（防覆盖，幂等） |
| `effect_object_bind` | `void(ptr)` | 绑定作用对象（属性槽指针） |
| `effect_name_get` | `const std::string&(void)` | 返回 `name` 引用 |
| `effect_act` | `void(void)` | 执行 `script["action"]()`——要求 Lua 脚本定义 `action` 函数 |

### 2.5 `Effect_Manager`（效应管理器）—— `src/effect/Effect_Manager/效应管理器.h`

```cpp
namespace engine
{
    class Effect_Manager
    {
    private:
        struct effect_record : public Object                      // 效应记录（进对象池）
        {
            uint64_t inclusion;                                    // 效应归属
            uint64_t act_phase = 0;                                // 效应执行阶段（哈希值）
            uint64_t priority = 0;                                 // 效应执行优先级（数值越大越先执行）
            Prop_Effect pro_effect;                                // 效应本体
        };
        struct effect_group                                       // 效应组（不进对象池）
        {
            uint64_t inclusion;                                    // 效应归属
            std::vector<effect_record*> effects{};                 // 效应组（指针数组）
        };
    public:
        Effect_Manager();                                          // 构造函数
        ~Effect_Manager() = default;                               // 析构函数
        void bind_entry_register(std::function<std::unordered_map<std::string, double>*
            (const uint64_t& ID)> bind_entry);                     // 注册属性槽绑定通道
        void attach(void);                                         // 事件中转站接入
    private:
        int64_t effect_group_seek(const uint64_t& inclusion);      // 效应分组查找（二分）
        std::optional<uint64_t> effect_build(std::shared_ptr<event> evt); // 效应构建
        bool effect_unload(std::shared_ptr<event> evt);            // 效应卸载
        void effect_act(uint64_t phase);                           // 效应执行（按阶段）
        void event_process(std::shared_ptr<event> evt);            // 事件处理
    public:
        Event_Terminal event_terminal;                             // 事件终端
    private:
        int64_t acl_key = 0;                                       // 事件发送密钥
        std::function<std::unordered_map<std::string, double>* (const uint64_t& ID)> bind_entry; // 属性槽绑定通道
        std::vector<effect_group> effect_groups;                   // 分组效应集合
        Object_Pool<effect_record> effect_set;                     // 效应总集合
    };
}
```

**逐条解释**：

| 接口 | 签名 | 含义 |
|---|---|---|
| 构造 | `Effect_Manager()` | `acl_key = event_terminal.acl_key_gen()` |
| `bind_entry_register` | `void(std::function<...*(const uint64_t& ID)>)` | 保存属性槽绑定通道（由外部注入，通常绑定 `Prop_Distributor::prop_slot_get` 或 `Entity_Manager::prop_slot_get`） |
| `attach` | `void(void)` | 订阅 4 类事件（Config/Load、Effect/Build、Effect/Unload、Effect/Act）并注册接收入口（详见 §4.3） |
| `effect_group_seek` | `int64_t(const uint64_t&)` | 在 `effect_groups`（按 `inclusion` 排序）上二分查找，返回索引；找不到返回负数 |
| `effect_build` | `std::optional<uint64_t>(std::shared_ptr<event>)` | 从事件 config 构建效应（详见 §4.4） |
| `effect_unload` | `bool(std::shared_ptr<event>)` | 从事件 config 卸载效应（详见 §4.4） |
| `effect_act` | `void(uint64_t phase)` | 遍历 `effect_set.data()`，对 `valid()` 且 `act_phase == phase` 的记录调用 `pro_effect.effect_act()` |
| `event_process` | `void(std::shared_ptr<event>)` | 事件分派（详见 §4.3） |

**关键点**：`effect_record` 继承 `Object` 以便进 `Object_Pool`；`effect_group` 不继承 `Object`，用 `vector<effect_record*>` 存放**指针**（指向对象池内的记录；对象池只在 unload 时标记无效并交换位置，记录地址除 unload 目标外保持稳定——但 `effect_set.build()` 触发的 `push_back` 可能使 vector 扩容导致**旧记录地址失效**，这是重要边界，见 §4.4）。

### 2.6 `Entity_Manager`（实体管理器）—— `src/entity/Entity_Manager/实体管理器.h`

```cpp
namespace engine
{
    class Entity_Manager
    {
    private:
        std::unordered_set<event> event_map{};                     // 订阅事件集合（按 event 值去重）
    public:
        Event_Terminal event_terminal;                             // 事件终端

        int64_t acl_key = 0;                                       // 事件发送权限密钥

        std::unordered_map<std::string, std::string> action_load_path; // 行为脚本加载路径集合
        Object_Pool<Prop> props;                                   // 属性槽集合
        Object_Pool<Entity> entities;                              // 实体集合
    public:

    private:
        bool config_field_parse(const nlohmann::json& config);     // 配置字段检验
        void action_load_path_register(const std::string& entity_type, const nlohmann::json& config); // 决策树加载路径注册
        void prop_load_path_register(const std::string& entity_type, const nlohmann::json& config);   // 属性槽配置加载路径注册
    public:
        std::vector<uint64_t> entity_build(const std::string& type, const int& counts); // 实体创建
        void entity_unload(std::vector<uint64_t>& ID);             // 实体卸载
        void entity_act(std::vector<uint64_t>& IDs);               // 实体行动（指定）
        void entity_act(void);                                     // 实体行动（全量）
        bool distribute_key_gen(void);                             // 属性槽分发密钥生成
        Object_Pool<Prop>* prop_slot_get(const uint64_t& distribute_key); // 属性槽获取（按密钥）
    public:
        void event_broadcast(std::shared_ptr<event> evt);          // 事件广播
        bool event_unicast(const std::string& type, const uint64_t& ID, std::shared_ptr<event> evt); // 事件定向发送
    private:
        void event_process(std::shared_ptr<event> evt);            // 事件处理
    };
}
```

**逐条解释**：

| 接口 | 签名 | 含义 |
|---|---|---|
| 构造 | `Entity_Manager()` | `acl_key = event_terminal.acl_key_gen()` |
| `attach` | `void(void)` | 用 `event_map` 中的订阅集合接入中转站（详见 §4.3） |
| `config_field_parse` | `bool(const nlohmann::json&)` | 校验 `type`/`prop_load_path`/`action_load_path`/`needed_events` 四个字段 |
| `action_load_path_register` | `void(type, config)` | 取 `config["decision_load_path"]` 绝对路径化后写入 `action_load_path[type]` |
| `prop_load_path_register` | `void(type, config)` | 取 `config["prop_load_path"]` 绝对路径化后 `prop_config_paths[type].load_file(...)` |
| `entity_build` | `std::vector<uint64_t>(type, counts)` | 创建 counts 个实体 + 同数属性槽并初始化（详见 §4.1，**含两个已知缺陷**） |

### 3.4 事件接入模式（attach → 订阅 → 分派）

系统层所有管理器遵循同一「事件接入模式」：

```
模块.attach()
  │  ① event_terminal->event_receiver_register(λ(evt){ event_process(evt); })
  │  ② event_terminal.attach("<模块名>", needed_events, acl_key)
  ▼
Event_Broker（引擎层中转站）——按订阅集合把事件路由给各模块的 event_process
  ▼
event_process(evt) —— 按 category/tag 分派到具体业务函数
```

| 模块 | 模块名（attach 第一个参数） | 订阅集合 | 分派逻辑 |
|---|---|---|---|
| `Entity_Manager` | `"Entity_Manager"` | 动态（`event_map`，由配置事件填充） | category=="Config" → 配置解析；否则按 tag：Build/Unload/Act/其他（unicast） |
| `Prop_Distributor` | `"Prop_Distributor"` | 空 `{}` | category=="Key" && tag=="Distributor" → 取分发密钥 |
| `Effect_Manager` | `"Effect_Manager"` | 4 类固定事件 | category=="Effect" 按 tag：Build/Unload/Act/其他（定向） |

## 4. 模块设计/实现细节

### 4.1 实体构建流程（`entity_build`）与已知缺陷

```cpp
vector<uint64_t> Entity_Manager::entity_build(const string& type, const int& counts)
{
    auto action_it = action_load_path.find(type);
    if (action_it == action_load_path.end())
    {
        Log::warn("Entity_Manager::未定义目标实体类型行为加载路径");
        return {};
    }
    auto prop_it = prop_config_paths.find(type);
    if (prop_it == prop_config_paths.end())
    {
        Log::warn("Entity_Manager::未定义目标实体类型属性槽配置加载路径");
        return {};
    }
    vector<uint64_t> IDs{};
    for (int build_times = 0; build_times < counts; build_times++)
    {
        IDs.push_back(entities.build());    // 构建新实体
        props.build();                      // 构造新属性槽（同索引）
    }
    for (const auto& ID : IDs)
    {
        auto new_entity = entities.find(ID);
        auto& new_prop_slot = props.find(ID)->prop_get();
        new_prop_slot.clear();              // 清空避免数据残留
        auto event_entry = [this](vector<shared_ptr<event>> events)->void
            { event_terminal.receive(events); };   // 事件发送入口（转发到外部）
        new_entity->event_terminal->event_sender_register(event_entry);
        new_entity->prop_slot_bind(&new_prop_slot);
        new_entity->action_load(action_it->second);
        return IDs;                          // ⚠️ 缺陷 1：return 在循环体内
    }
}
```

**流程**：查路径 → 建实体+属性槽（池内 build，同 ID）→ 逐个初始化（清槽、注册事件发送入口、绑属性槽、加载决策树）。

**缺陷 1（return 提前）**：`return IDs;` 位于初始化 `for` 循环**体内**，第一次迭代即返回——当 `counts > 1` 时，只有第一个实体完成初始化（绑槽、加载决策树），其余实体虽已 `build()` 但**未初始化**（行为未加载、属性槽未绑定），处于半成品状态。这是明确的实现缺陷，重开发时应把 `return IDs` 移到循环外。

**缺陷 2（ID 池与属性槽池错位风险）**：`entities.build()` 与 `props.build()` 各自维护独立的 `Number_Allocator`。正常情况下两者分配序列一致（同索引同 ID），但若曾对 `props` 单独 unload/回收过，两池的 ID 可能错位。当前代码**没有对齐校验**。

**边界**：`counts <= 0` 时返回空向量（`config.value<int>("counts", 0)` 默认 0），调用方需自行判空。

### 4.2 实体行为加载与 Lua 注册（`action_load`）

```cpp
void Entity::action_load(const std::string& load_path)
{
    action.open_libraries();                       // 打开所有标准库
    action.load_file(load_path);                   // 加载决策树脚本

    action.set("pros", sol::as_table(property_slot));   // 注册通用属性槽（表）
    //TODO: register_event 已从 common/external/Sol2/sol类型注册.h 移除，
    //      待确认原事件注册内容后补回，暂时停用。
    //register_event(action);
    action.set("event_set", ref(event_terminal.query(acl_key)));   // 注册事件集合引用
    action.set_function("send", [this](shared_ptr<event> evt)->void
        { this->event_terminal.send({ evt }, acl_key); });         // 注册事件发送函数
}
```

**Lua 侧可见符号**：

| Lua 符号 | C++ 来源 | 类型 | 用途 |
|---|---|---|---|
| `pros` | `property_slot` | `sol::as_table`（属性槽表引用） | 脚本读写实体属性，如 `pros["hp"] = pros["hp"] - 10` |
| `event_set` | `event_terminal.query(acl_key)` | `std::vector<std::shared_ptr<event>>` 引用 | 脚本查阅本实体收到的事件 |
| `send` | `event_terminal.send({evt}, acl_key)` | Lua 函数 | 脚本发送事件（转发到外部） |
| `decision` | 脚本自身定义 | Lua 函数 | `act()` 调用的决策入口 |

**边界**：`action.set("pros", sol::as_table(property_slot))` 要求 `property_slot` **已非空**——若直接 `Entity(ID)` 构造后未 `prop_slot_bind` 就 `action_load`，`as_table(nullptr)` 行为未定义（当前 `Entity` 的 `property_slot` 成员未初始化，只有 `prop_slot_bind` 会写）。`Entity_Manager` 路径先绑后加载是安全的。

**已知缺口**：`register_event`（C++ 事件类型注册到 Lua）已从 `sol类型注册.h` 移除，代码中留有 TODO——脚本目前**无法**直接构造 `event` 对象，只能通过 `send` 接收已构造的 `shared_ptr<event>`。

### 4.3 事件处理与分派（`event_process`）

**`Entity_Manager::event_process`**（配置事件 vs 业务事件）：

```cpp
void Entity_Manager::event_process(shared_ptr<event> evt)
{
    if (evt->category == "Config")                       // —— 配置事件 ——
    {
        auto& config = evt->config;
        if (config_field_parse(config))
        {
            string target_type = config["target_type"];
            action_load_path_register(target_type, config);
            prop_load_path_register(target_type, config);
            vector<pair<string, string>> buffer = config["needed_events"];
            for (int transform_time = 0; transform_time < buffer.size(); transform_time++)
            {
                auto& tag = buffer[transform_time];
                event needed_event("Entity_Manager","", tag.first, tag.second, json::object());
                if (!event_map.count(needed_event))
                    event_map.insert(needed_event);
            }
            attach();                                     // 更新接入信息（重新订阅）
        }
    }
    else                                                  // —— 业务事件 ——
    {
        auto& tag = evt->tag;
        auto& config = evt->config;
        if (!Config_Checker::field_check<string>(config, "target_type"))
            return;
        string target_type = config["target_type"];
        if (tag == "Build")
        {
            vector<uint64_t> ID_set{};
            ID_set = entity_build(target_type, config.value<int>("counts", 0));
            if (!ID_set.empty())                          // ⚠️ 缺陷 3：判断疑似写反
            {
                Log::warn("Entity_Manager::未定义实体创建数量\n实体创建事件已驳回");
                return;
            }
            else
            {
                config.erase("counts");
                config.emplace("ID_set", ID_set);
                event_terminal.send(evt, acl_key);        // 向外界发布修饰后事件
            }
        }
        else if (tag == "Unload")
        {
            if (!Config_Checker::field_check<vector<int64_t>>(config, "ID_set"))
                return;
            vector<uint64_t> ID_set = config["ID_set"];
            entity_unload(ID_set);
        }
        else if (tag == "Act")
        {
            if (!Config_Checker::field_check<vector<int64_t>>(config, "ID_set"))
                return;
            // ⚠️ 缺陷 4：Act 分支只校验字段，没有实际调用 entity_act
        }
        else
        {
            if (!Config_Checker::field_check<string>(config, "target_ID"))
                return;
            uint64_t target_ID = config["target_ID"];
            event_unicast(target_type, target_ID, evt);
        }
    }
}
```

**缺陷 3（Build 分支判断写反）**：`if (!ID_set.empty())` 时警告「未定义实体创建数量」并**驳回**——语义与代码相反：`entity_build` 返回空意味着构建失败（路径未注册或 counts=0），此时应驳回；返回非空表示成功，应继续广播。当前代码在**成功时驳回、失败时空转**，且会把空的 `ID_set` 写回 config 广播出去。这是明确的逻辑反转缺陷。

**缺陷 4（Act 分支空转）**：`tag == "Act"` 分支只做了 `field_check<vector<int64_t>>(config, "ID_set")` 字段校验，**没有调用 `entity_act`**——实体行动事件实际上不驱动任何实体。`entity_act` 目前只能由外部直接调用（C++ 侧）。

**`Effect_Manager::event_process`**（category=="Effect"）：

```cpp
if (evt->category == "Effect")
```

### 4.4 效应构建 / 卸载 / 执行（`effect_build` / `effect_unload` / `effect_act`）

**`effect_build` 完整流程**：

```cpp
optional<uint64_t> Effect_Manager::effect_build(shared_ptr<event> evt)
{
    auto& config = evt->config;
    // 1. 字段校验：inclusion / act_phase / priority（priority 允许 string 或 uint64）
    if (!Config_Checker::field_check<uint64_t>(config, "inclusion")) { ... return nullopt; }
    if (!Config_Checker::field_check<uint64_t>(config, "act_phase")) { ... return nullopt; }
    if (!Config_Checker::field_check<string>(config, "priority") &&
        !Config_Checker::field_check<uint64_t>(config, "priority")) { ... return nullopt; }

    // 2. 对象池建记录
    uint64_t ID = effect_set.build();
    auto new_record_it = effect_set.find(ID);
    auto* new_record = &(*new_record_it);
    auto& new_effect = new_record->pro_effect;

    // 3. 配置解析（读 Lua 脚本）
    if (!new_effect.config_read(config))
    {
        effect_set.unload(ID);                                // 失败回滚
        return nullopt;
    }
    else
    {
        new_record->inclusion = config["inclusion"].get<uint64_t>();
        new_record->pro_effect.ID_bind(new_record->ID());
        // act_phase：字符串转唯一哈希
        new_record->act_phase = hash<string>{}(config["act_phase"].get<string>());
        // priority："max" → uint64 最大值；其余字符串 → 警告 + 回滚
        if (config["priority"].is_string())
        {
            if (config["priority"].get<string>() == "max")
                new_record->priority = (numeric_limits<uint64_t>::max)();
            else { Log::warn(...); effect_set.unload(ID); return nullopt; }
        }
        else
            new_record->priority = config["priority"].get<uint64_t>();

        // 4. 绑定作用对象（经 bind_entry 借属性槽）
        new_record->pro_effect.effect_object_bind(bind_entry(new_record->inclusion));

        // 5. 配置效应的事件发送入口（转发到外部）
        auto& terminal = new_effect.event_terminal;
        auto event_send_entry = [this](vector<shared_ptr<event>> events)->void
            { this->event_terminal.send(events, acl_key); };
        terminal->event_sender_register(event_send_entry);

        // 6. 分组：二分查找，找不到则新建组
        int64_t group_index = effect_group_seek(new_record->inclusion);
        if (group_index < 0)
        {
            effect_groups.push_back({ new_record->inclusion, {} });
            group_index = effect_groups.size() - 1;
        }
        auto& group = effect_groups[group_index];

        // 7. 把带 ID 的修饰事件通知组内已有效应，再加入分组
        evt->config["ID"] = new_record->ID();
        for (auto& effect : group.effects)
            effect->pro_effect.event_terminal.receive(evt);
        group.effects.push_back(new_record);

        // 8. 效应集按 priority 降序排序
        effect_set.sort_order_set(true, &effect_record::priority);
        return new_record->ID();
    }
}
```

**设计决策**：

| 决策 | 理由 |
|---|---|
| `act_phase` 用 `std::hash<std::string>` 转哈希存储 | 执行阶段以字符串（如 `"combat"`）配置，哈希化后可用 `uint64_t` 快速比较；代价是哈希冲突理论风险与字符串可读性丢失 |
| `priority` 支持 `"max"` 字符串 | 语义化配置「最高优先级」；仅接受 `"max"`，其它字符串一律回滚 |
| 优先级降序排序（`sort_order_set(true, ...)`） | 注释约定「数值越大越先执行」；排序模式下的 `Object_Pool` 用二分查找替代索引映射 |
| 构建成功后通知同组已有效应 | 组内效应共享构建上下文（收到带 `ID` 的修饰事件），形成「组感知」 |

**`effect_unload` 流程**：

```cpp
bool Effect_Manager::effect_unload(shared_ptr<event> evt)
{
    auto& config = evt->config;
    if (!Config_Checker::field_check<uint64_t>(config, "target_ID")) { ... return false; }
    uint64_t target_ID = config["target_ID"].get<uint64_t>();
    auto target_record_it = effect_set.find(target_ID);
    auto* target_record = &(*target_record_it);
    int64_t group_index = effect_group_seek(target_record->inclusion);
    auto& group = effect_groups[group_index];
    auto& effects = group.effects;

    if (effects.size() == 1)
        effect_groups.erase(effect_groups.begin() + group_index);   // 组内仅此一效应 → 删整组
    else
    {
        // 通知组内其它效应（携 inclusion/name 的卸载事件），记录目标索引
        evt->config["inclusion"] = target_record->inclusion;
        evt->config["name"] = target_record->pro_effect.effect_name_get();
        int64_t target_index = -1;
        for (int match_time = 0; match_time < effects.size(); match_time++)
        {
            auto& effect = effects[match_time];
            if (effect->ID() != target_record->ID())
                effect->pro_effect.event_terminal.receive(evt);
            else
                target_index = match_time;
        }
        effects.erase(effects.begin() + target_index);
    }
    effect_set.unload(target_ID);
    return true;
}
```

**`effect_act(phase)` 执行**：遍历 `effect_set.data()`，跳过 `!valid()`，`act_phase == phase` 的调用 `pro_effect.effect_act()`（即 Lua `action()`）。排序模式下有效记录集中在 `min_valid_index` 之后，但此处仍**全量遍历**（含无效记录头段），属于轻微性能冗余。

**关键边界**：`effect_record*` 指针被 `effect_group.effects` 持有。当 `effect_set.build()` 触发 `std::vector` **扩容**时，所有旧 `effect_record` 地址失效，分组内的悬垂指针将指向未定义内存。当前 `Object_Pool<effect_record>::build()` 在 `index >= objects.size()` 时 `push_back` 会扩容——**多次构建不同归属效应后分组指针可能悬垂**，这是本项目效应系统最危险的隐患，重开发时需改用索引/ID 而非裸指针。

### 4.6 属性槽分发密钥机制（`distribute_key_gen` / `prop_slot_get`）

```cpp
bool Entity_Manager::distribute_key_gen(void)
{
    /*/                                 // 被注释掉的校验块
    //if (!event_terminal.interact("Prop_Distributor")) { ... return false; }
    /**/
    if (this->distribute_key.has_value())
    {
        Log::warn("Entity_Manager::分发密钥未已生成!!!");     // 文案本身有语病
        return false;
    }
    this->distribute_key = []() {
        std::random_device rd;
        std::mt19937 gen(rd());
        std::uniform_int_distribution<uint64_t> dis(0, (numeric_limits<uint64_t>::max)());
        return dis(gen);
    }();
    shared_ptr<event> evt(new(nothrow) event());
    evt->sender_object = "Entity_Manager";
    evt->target_object = "Prop_Distributor";
    evt->category = "Key";
    evt->tag = "Distribute";
    evt->config["key"] = this->distribute_key;
    event_terminal.receive(evt);        // 注意：receive 而非 send —— 不经中转站广播？
    // ⚠️ 无 return 语句（缺陷 6）
}
```

**密钥传递链路**：

```
Entity_Manager::distribute_key_gen()
  → 生成 64 位随机密钥（random_device + mt19937 + uniform_int_distribution）
  → 构造 Key/Distribute 事件（config["key"]=密钥）
  → event_terminal.receive(evt)          ← 注意这里用的是 receive
  → （若经中转站路由）Prop_Distributor::event_process 收到
  → distribute_key = config["key"]
  → 外部再调用 prop_slots_bind(bind_entry)
  → bind_entry 实为 Entity_Manager::prop_slot_get(distribute_key)
  → 密钥匹配（optional 相等）→ 返回 &props
```

**设计意图**：密钥机制保证「谁拿到密钥谁才能借属性槽池」。但注意 `distribute_key_gen` 里密钥生成后**先检查 `has_value()` 就不允许重复生成**——若首次生成后分发链路失败（Prop_Distributor 未收到），没有重试通道；且 `event_terminal.receive` 单发不经 `Event_Broker` 路由语义存疑（receive 是把事件送进本终端的事件集，不触发其它模块的 event_process；真正路由靠 `send`）。重开发时需确认中转站对 receive/send 的语义。

### 4.7 Lua 状态机生命周期

| 阶段 | 操作 | 位置 |
|---|---|---|
| 创建 | `LuaState{}` 默认构造（sol::state 惰性初始化） | `Entity::action`、`Prop_Effect::script`、`prop_config_paths` 值 |
| 加载 | `load_file(绝对路径)`（Sol2 会立即执行脚本顶层） | `action_load`、`config_read`、`prop_load_path_register` |
| 开库 | `open_libraries()`（全库）/ `open_libraries(base, math, string, table)`（效应） | 同上 |
| 注入 | `set("pros", ...)`、`set("event_set", ...)`、`set_function("send", ...)` | `action_load`、`data_injection` |
| 执行 | `script["decision"]()`、`script["action"]()` | `Entity::act`、`Prop_Effect::effect_act` |
| 重置 | `script = LuaState{}`（重新赋值触发旧状态机析构） | `Prop_Effect::config_read` 开头 |

**边界**：`LuaState` 不可拷贝、可移动；`Entity` 的移动是 `default`——**移动后旧对象的 `action` 被移走，新对象持有状态机**，`Object_Pool<Entity>::build()` 里 `new_object = T{}` 需要 Entity 可移动赋值，这是移动语义存在的原因。

### 4.8 配置格式约定（运行时数据契约）

**实体类型配置**（Config 事件 config 字段）：

| 字段 | 类型 | 说明 | 校验者 |
|---|---|---|---|
| `type` | string | 实体类型 | `config_field_parse` |
| `prop_load_path` | string | 属性槽配置脚本相对路径 | 同上 |
| `action_load_path` | string | 行为脚本相对路径 | 同上（但注册时读的是 `decision_load_path`，见下） |
| `needed_events` | `vector<pair<string,string>>` | 订阅事件列表（category, tag） | 同上 |
| `target_type` | string | 目标实体类型 | `event_process`（Config 分支读取，但 `config_field_parse` 校验的是 `type`——**字段不一致**：校验 `type`、读取 `target_type`） |
| `decision_load_path` | string | 决策树脚本相对路径（`action_load_path_register` 实际读取） | 无显式校验 |

> **字段不一致陷阱**：`config_field_parse` 校验 `type` 字段，但 `event_process` 里用 `config["target_type"]` 取目标类型；`action_load_path_register` 读取 `config["decision_load_path"]` 而校验的是 `action_load_path`。JSON 配置必须同时提供这些字段才能跑通，缺一即路径注册不全或读默认值。

**效应配置**（Effect/Build 事件 config 字段）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `path` | string | 效应 Lua 脚本相对路径 |
| `inclusion` | uint64 | 效应归属（实体 ID） |
| `name` | string | 效应名称 |
| `act_phase` | uint64（校验）/ string（哈希） | 执行阶段——**校验要求 uint64，但执行时按 string 哈希**，见下 |
| `priority` | string 或 uint64 | 执行优先级；`"max"` → uint64 最大值 |

> **act_phase 类型陷阱**：`effect_build` 用 `field_check<uint64_t>(config, "act_phase")` 校验（要求整数），随后却执行 `hash<string>{}(config["act_phase"].get<string>())`（把整数转字符串再哈希）——配置若是整数 `1`，`get<string>()` 会抛 `nlohmann::json::type_error`（**无 try/catch**）。效应触发端 `event_process`(Act) 则用 `field_check<string>` 校验（要求字符串）。两端口径矛盾：**构建端要整数、触发端要字符串**，实际配置需用字符串（如 `"1"`），否则构建期抛异常。

| `Entity_Manager ↔ Prop_Distributor` | 协作 | 分发密钥（Key/Distribute 事件）+ `prop_slot_get` 回调借池 |

| `Entity ↔ Entity_Manager` | 协作 | 事件发送入口注册（实体事件转发到管理器终端）、属性槽绑定、行为加载 |
| 游戏层（未来） | 提供服务 | 通过 `SystemCore` 对外面创建实体、触发效应 |
| 配置编辑器 `Config_Editor` | 未接入 | 被 CMake 排除，将来独立 `add_executable` |

### 5.5 事件流示例（实体被攻击）

```
外部（游戏逻辑/测试）
  │ event_unicast("Monster", 42, 伤害事件)   // 或经 Event_Broker 广播
  ▼
Entity_Manager::event_unicast
  │ 校验 entities.find(42) 存在 && type()==type（缺陷 5：type 恒空串，过滤失效）
  ▼
Entity(42).event_terminal.receive(evt)        // 事件进入实体终端
  ▼
Entity::act() → Lua decision()                 // 行为决策
  │ 读 pros["hp"] → 减伤计算
  │ send(受击反馈事件)                          // 实体事件 → 管理器终端 → 外部
  ▼
event_terminal.clear(acl_key)                  // 清空本帧事件
```
