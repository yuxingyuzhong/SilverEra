## 1. 模块功能

### 1.1 模块是什么

「坐标类型与依赖封装」是引擎层 `core/spatial/common` 下的三个头文件组成的公共基础包：

| 文件 | 作用 |
| --- | --- |
| `core/坐标类型.h` | 定义引擎自有的二维坐标/矩形基元类型：`Point2<T>`、`Rect2<T>` 模板及其三个精度别名；提供带容差的浮点相等比较与精度间转换函数 |
| `core/依赖库封装.h` | 将第三方物理引擎 bullet3（Bullet Physics）的核心类型收敛为 `engine` 命名空间下的语义化别名；定义碰撞检测后端聚合结构体 `Collision_Backend` 与静态碰撞对象标记常量 |
| `碰撞系统运行包.h` | 无逻辑聚合头文件（facade），一行包含即可引入"依赖库封装 + 碰撞体（Collider）+ 碰撞空间（Collision_Region）"全部碰撞模块定义 |

### 1.2 模块解决什么问题

- **坐标基元缺失与重复定义问题**：引擎此前在碰撞、四叉树分区（Quadtree）、网格加载等多个子系统中都需要二维坐标与矩形范围类型。若各子系统各自定义，会导致类型不互通、相等语义不一致。本模块提供唯一权威的 `Point2<T>` / `Rect2<T>`，全引擎共用。
- **浮点比较不可靠问题**：直接使用 `==` 比较浮点坐标在物理模拟场景（网格加载、四叉树节点范围判定）中会因舍入误差产生抖动与假阴性。本模块引入 **ULP（Unit in the Last Place，最小精度单位）距离 ≤ 4** 的容差比较，把"数学上相等"和"位模式相同"解耦。
- **第三方库类型污染问题**：碰撞子系统直接使用 bullet3 的 `btCollisionWorld`、`btVector3` 等类型，若散落各处，一旦更换物理库（如换到 PhysX / Jolt）将面临全量替换。本模块把 bullet3 类型统一收敛为 engine 语义别名，上层只依赖 `engine::` 名字。
- **碰撞后端装配繁琐问题**：使用 bullet3 至少需要四个对象协同：配置（`btDefaultCollisionConfiguration`）、窄阶段调度器（`btCollisionDispatcher`）、宽阶段接口（`btBroadphaseInterface`，常用 `btDbvtBroadphase`）、碰撞世界（`btCollisionWorld`）。`Collision_Backend` 把四者装配、生命周期管理、失败回滚封装为单一值对象。
- **头文件组织散乱问题**：碰撞模块被拆分为多编译单元后（本版次主题），调用方需要同时包含多个头文件且注意顺序。`碰撞系统运行包.h` 收敛为单点包含，降低耦合。

### 1.3 模块服务谁

- **服务方（被包含方）**：`Collision_Region`（碰撞空间）、`Collider`（碰撞体）、`Collision_Proxy`（碰撞代理器）、四叉树分区（Quadtree / Quadtree_Manager）等空间与碰撞子系统；网格加载器（Mesh_Loader）中的顶点坐标容器也复用 `Point2`/`Rect2` 语义。
- **调用方（使用者）**：引擎层空间系统内部各模块；系统层实体、效应等业务模块通过碰撞空间间接受益。
- **不服务**：窗口、渲染、事件等与空间坐标无关的子系统（除非显式包含）。

## 2. 模块提供接口

### 2.1 坐标类型.h 公开接口

#### 2.1.1 `Point2<T>` 模板

```cpp
namespace engine
{
    //二维点
    template <typename T>
    struct Point2
    {
        T X = T{};   // 横坐标（默认值初始化）
        T Y = T{};   // 纵坐标（默认值初始化）

        Point2() = default;                                        // 默认构造
        Point2(T x, T y) : X(x), Y(y) {}                           // 带参构造

        bool operator==(const Point2& other) const noexcept;       // 等于（浮点走 ULP 容差）
        bool operator!=(const Point2& other) const noexcept;       // 不等于（取反）

        friend std::ostream& operator<<(std::ostream& os, const Point2& p);  // 流输出
    };
}
```

逐项解释：

| 成员 | 签名 | 说明 |
| --- | --- | --- |
| 数据成员 `X`、`Y` | `T X = T{};` / `T Y = T{};` | 横纵坐标。使用 `T{}` 值初始化：整数/浮点为 0，指针为空，保证默认构造后坐标恒为零值，无未初始化读风险 |
| 默认构造 | `Point2() = default;` | 依赖成员默认初始化器，坐标归零 |
| 带参构造 | `Point2(T x, T y)` | 以两个同类型标量构造点 |
| 等于运算符 | `bool operator==(const Point2& other) const noexcept` | 返回 true 表示"按模块相等语义相等"。语义分派见 2.1.4 节：浮点类型走 ULP ≤ 4 容差比较（NaN 恒不等、无穷精确比），整数类型走精确比较。`noexcept` 保证不抛异常 |
| 不等于运算符 | `bool operator!=(const Point2& other) const noexcept` | 恒等于 `!(*this == other)`，语义与等于完全对称 |
| 流输出 | `friend std::ostream& operator<<(std::ostream& os, const Point2& p)` | 输出两行文本：`X轴坐标: {X}\nY轴坐标: {Y}\n`。内部使用 C++20 `std::format` 格式化，返回原流以支持链式调用。注意是 `friend` 非成员函数，支持左操作数为任意 `std::ostream` 派生流 |

#### 2.1.2 `Rect2<T>` 模板

```cpp
namespace engine
{
    //二维矩形范围
    template <typename T>
    struct Rect2
    {
        T left  = T{};   // 左边界
        T right = T{};   // 右边界
        T up    = T{};   // 上边界
        T down  = T{};   // 下边界

        Rect2() = default;                                         // 默认构造
        Rect2(T l, T r, T u, T d) : left(l), right(r), up(u), down(d) {}  // 带参构造

        bool operator==(const Rect2& other) const noexcept;        // 等于（四边界全等）
        bool operator!=(const Rect2& other) const noexcept;        // 不等于

        friend std::ostream& operator<<(std::ostream& os, const Rect2& r);  // 流输出
    };
}
```

逐项解释：

| 成员 | 签名 | 说明 |
| --- | --- | --- |
| 数据成员 | `left` / `right` / `up` / `down` | 四边界。命名采用"左/右/上/下"而非常见 x/y/w/h，语义直白：矩形由四根边界线定义，左≤右、上≥下（屏幕坐标系 y 轴向下时 up 数值上小于 down）由调用方保证，本结构体不校验 |
| 默认构造 | `Rect2() = default;` | 四边界全部零值 |
| 带参构造 | `Rect2(T l, T r, T u, T d)` | 参数顺序固定为 l、r、u、d，与成员声明顺序一致 |
| 等于运算符 | `bool operator==(const Rect2& other) const noexcept` | **注意**：此处是四边界**逐项精确比较**（`left == other.left && right == other.right && up == other.up && down == other.down`），**不**复用 `Point2` 的 ULP 容差逻辑。这是当前实现的既定语义：矩形比较是严格相等 |
| 不等于运算符 | `bool operator!=(const Rect2& other) const noexcept` | 等于取反 |
| 流输出 | `friend std::ostream& operator<<(std::ostream& os, const Rect2& r)` | 输出四行：`左边界: {}\n右边界: {}\n上边界: {}\n下边界: {}\n`，`std::format` 格式化 |

#### 2.1.3 精度别名

```cpp
namespace engine
{
    //二维点 —— 整数精度
    using Point2i = Point2<int>;
    //二维点 —— 64 位整数精度
    using Point2l = Point2<int64_t>;
    //二维点 —— 双精度浮点
    using Point2d = Point2<double>;

    //二维矩形范围 —— 整数精度
    using Rect2i = Rect2<int>;
    //二维矩形范围 —— 64 位整数精度
    using Rect2l = Rect2<int64_t>;
    //二维矩形范围 —— 双精度浮点
    using Rect2d = Rect2<double>;
}
```

| 别名 | 模板实参 | 适用场景 |
| --- | --- | --- |
| `Point2i` / `Rect2i` | `int`（32 位） | 屏幕坐标、栅格索引、窗口尺寸等 32 位整数精度场景 |
| `Point2l` / `Rect2l` | `int64_t`（64 位） | 大规模世界坐标、区块编号、超大地图索引等需要 64 位整数精度的场景 |
| `Point2d` / `Rect2d` | `double`（64 位浮点） | 物理模拟、连续世界坐标、几何运算等浮点精度场景 |

设计要点：
- 别名与模板定义位于同一头文件、同一命名空间，使用方既可以写 `Point2d` 快捷名，也可以显式实例化 `Point2<float>` 获得自定义精度点。
- **无跨精度隐式转换**：`Point2i` 与 `Point2d` 是不同类类型，不存在隐式构造函数/转换运算符，赋值或函数实参传递时必须显式调用转换函数（见 2.1.4），从语言层面杜绝精度丢失的静默发生。

#### 2.1.4 精度转换函数（自由函数）

```cpp
namespace engine
{
    //精度转换 —— 浮点转整数
    inline Point2i point_to_int(const Point2d& p) noexcept
    {
        return { static_cast<int>(std::lround(p.X)),
                 static_cast<int>(std::lround(p.Y)) };
    }

    //精度转换 —— 整数转浮点
    inline Point2d point_to_double(const Point2i& p) noexcept
    {
        return { static_cast<double>(p.X),
                 static_cast<double>(p.Y) };
    }

    //精度转换 —— 浮点转 64 位整数
    inline Point2l point_to_l(const Point2d& p) noexcept
    {
        return { static_cast<int64_t>(std::llround(p.X)),
                 static_cast<int64_t>(std::llround(p.Y)) };
    }

    //精度转换 —— 64 位整数转浮点
    inline Point2d point_to_double(const Point2l& p) noexcept
    {
        return { static_cast<double>(p.X),
                 static_cast<double>(p.Y) };
    }
}
```

| 函数签名 | 参数 | 返回值 | 行为说明 |
| --- | --- | --- | --- |
| `inline Point2i point_to_int(const Point2d& p) noexcept` | `p`：双精度点 | `Point2i` | 对 X、Y 分别执行 `std::lround`（四舍五入到最近整数，半分（.5）远离零）后 `static_cast<int>` 收窄。**范围风险**：`lround` 返回 `long`，再收窄到 `int`；若 `|p|` 超出 int 范围（如超过 21 亿）将产生实现定义的截断结果，调用方须自行保证数值在范围内 |
| `inline Point2d point_to_double(const Point2i& p) noexcept` | `p`：32 位整型点 | `Point2d` | 逐分量 `static_cast<double>` 精确提升，32 位 int 可被 double 精确表示（double 尾数 52 位），无损 |
| `inline Point2l point_to_l(const Point2d& p) noexcept` | `p`：双精度点 | `Point2l` | 对 X、Y 分别执行 `std::llround`（四舍五入，返回 `long long`）后 `static_cast<int64_t>`。**注意**：与 `point_to_int` 不同，此处是 `llround` + `int64_t`，对超出 `int64_t` 范围的值（`|p| > 9.2e18`）行为未定义，工程上不会出现 |
| `inline Point2d point_to_double(const Point2l& p) noexcept` | `p`：64 位整型点 | `Point2d` | 逐分量 `static_cast<double>`。**有损风险**：`int64_t` 超过 2^53 时 double 无法精确表示，会四舍五入到最近的可表示 double。大坐标世界（超过 9e15 单位）需注意精度损失 |

四舍五入口径总结：**浮点 → 整数一律四舍五入（round-half-away-from-zero）**，而非截断（truncation）或向下取整（floor）。这保证 ±2.5 → ±3、±2.4 → ±2，与直觉一致。

#### 2.1.5 `detail::ulp_distance` 内部工具

```cpp
namespace engine::detail
{
    //浮点数 ULP 距离计算
    inline uint64_t ulp_distance(double lhs, double rhs) noexcept
    {
        if (lhs == rhs)                       // 完全相同直接返回零
            return 0;
        uint64_t lhs_bits = std::bit_cast<uint64_t>(lhs);   // 按位取位模式
        uint64_t rhs_bits = std::bit_cast<uint64_t>(rhs);
        if ((lhs_bits & 0x8000000000000000ULL) !=           // 符号不同视为差值极大
            (rhs_bits & 0x8000000000000000ULL))
            return UINT64_MAX;
        if (lhs_bits > rhs_bits)              // 保证相减顺序
            std::swap(lhs_bits, rhs_bits);
        return rhs_bits - lhs_bits;           // ULP 数量
    }
}
```

| 要点 | 说明 |
| --- | --- |
| 所在命名空间 | `engine::detail`，标记为内部实现细节，外部模块不应直接依赖（无显式禁止，但约定不直接使用） |
| 原理 | IEEE 754 double 的位模式按无符号整数解释后，相邻可表示浮点数相差恰好 1。因此"两个 double 之间隔了多少个可表示数"= 位模式差的绝对值。这就是 ULP 距离 |
| 快速路径 | 位模式或值完全相同（`lhs == rhs`，含 +0.0/-0.0 特殊情况）直接返回 0。注意 `lhs == rhs` 对 NaN 恒为 false，故 NaN 不会走快速路径 |
| 符号处理 | 符号位不同（一正一负）直接返回 `UINT64_MAX`，因为跨零的位模式差会巨大且不反映真实数值距离。正负零点（+0.0 与 -0.0）已在第一步被 `==` 捕获返回 0 |
| 差值计算 | 先 swap 保证 `lhs_bits <= rhs_bits` 再相减，避免无符号下溢回绕 |
| 局限 | 只比较两个 double；若需要 float 比较，需先各自提升为 double（位模式改变，ULP 距离语义随之改变），当前 `Point2` 的 `operator==` 未提供 float 特化路径（`std::is_floating_point_v<T>` 对 float 也成立，但 `ulp_distance` 形参固定为 double，float 会隐式转换，位模式按 double 解释，结果仍正确但语义上是以 double 精度衡量） |

### 2.2 依赖库封装.h 公开接口


别名语义说明（按行）：

| 别名 | 原类型 | 语义说明 |
| --- | --- | --- |
| `Collision_Config` | `btDefaultCollisionConfiguration` | 全局碰撞算法配置：内存分配器、持久流形池、窄阶段算法工厂等。通常全引擎共享一份（见 `Collision_Backend` 的共享构造） |
| `Collision_Dispatcher` | `btCollisionDispatcher` | 窄阶段调度器：根据形状对类型选择并调用对应碰撞算法（GJK/EPA、SAT 等），产出接触点流形 |
| `Collision_Interface` | `btBroadphaseInterface` | 宽阶段接口的抽象基类：负责快速剔除不可能碰撞的物体对（broadphase pair），输出候选对列表 |
| `Bvh_Tree` | `btDbvtBroadphase` | 动态 BVH（Bounding Volume Hierarchy）宽阶段实现：适合物体动态增删的通用场景，本引擎默认选择 |
| `SAP` | `btAxisSweep3` | 扫描线剪枝宽阶段：三个轴向排序，静态物体众多时性能好，但需要预设世界边界 |
| `Collision_World` | `btCollisionWorld` | 碰撞世界（无动力学）：管理碰撞对象注册、执行宽/窄阶段检测、提供射线/扫掠查询。`Collision_Backend` 直接持有 |
| `Collision_Object` | `btCollisionObject` | 单个参与碰撞的对象：挂载形状指针、变换、标志位（如 CF_STATIC_OBJECT）、用户指针（`setUserPointer` 反查机制见 `Collider`） |
| `Bvh_Triangle_Mesh` | `btBvhTriangleMeshShape` | 静态三角形网格碰撞形状：内部构建 BVH 加速射线/扫掠查询；**只持有 `btTriangleMesh` 指针不接管所有权**（见 §4.4 生命周期陷阱） |
| `Vector3` | `btVector3` | 三维矢量，SIMD 对齐（16 字节），分量以 double（btScalar）存储 |
| `Transform` | `btTransform` | 变换：`btMatrix3x3` 基 + `btVector3` 原点；常用接口 `setIdentity()`、`setOrigin()`、`setRotation()`、`getOrigin()` 等 |
| `Quaternion` | `btQuaternion` | 四元数：`x/y/z/w` 分量，构造 `btQuaternion(axis, angle)` |
| `Scalar` | `btScalar` | bullet 标量类型（本引擎 bullet 以 double 编译），保持别名是为了让引擎代码不写死 double |
| `Collision_Shape` | `btCollisionShape` | 形状抽象基类；`Collider::shape` 以 `std::unique_ptr<Collision_Shape>` 持有（多态删除） |
| `Convex_Shape` | `btConvexShape` | 凸形状基类：提供局部支撑点计算（support function），供 GJK 使用 |
| `Box_Shape` | `btBoxShape` | 盒体：构造传半边长 `btVector3(halfExtents)`，中心位于局部原点 |
| `Sphere_Shape` | `btSphereShape` | 球体：构造传半径（标量） |
| `Capsule_Shape` | `btCapsuleShape` | 胶囊：构造 `(radius, height)`，注意 height 是**两个半球顶点之间**的距离（圆柱段高度），非总长 |
| `Cylinder_Shape` | `btCylinderShape` | 圆柱：构造传半尺寸 `btVector3(halfX, halfY, halfZ)` |
| `Cone_Shape` | `btConeShape` | 圆锥：构造 `(radius, height)` |
| `Triangle_Mesh` | `btTriangleMesh` | 三角形网格数据源：`addTriangle(v0, v1, v2)` 填充；被 `btBvhTriangleMeshShape` 引用 |
| `Persistent_Manifold` | `btPersistentManifold` | 持久流形：一对碰撞对象间持续存在的接触点集合，跨帧复用接触点（稳定性优化） |
| `Swept_Callback` | `Collision_World::ConvexResultCallback` | 扫掠检测回调基类：重写 `addSingleResult` 收集命中；`hasHit` 判断是否命中 |

#### 2.2.2 静态碰撞对象标记

```cpp
namespace engine
{
    //静态碰撞对象标记
    inline constexpr int Static_Object_Flag = btCollisionObject::CF_STATIC_OBJECT;
}
```

- 类型：`inline constexpr int`（C++17 inline 变量，头文件多包含安全，全程序唯一地址）。
- 值：`btCollisionObject::CF_STATIC_OBJECT`，即 bullet 内部定义的 `1 << 0` 位掩码。
- 用途：标记碰撞对象为"静态"（不移动），bullet 据此跳过某些动态优化并允许静态对静态不产生碰撞事件；`Collision_Region` 的空间边界（region_boundary）即以此标记。
- 语义：静态对象不可被推动、不参与连续碰撞求解；若动态对象移动后与其重叠，行为取决于宽/窄阶段配置。

#### 2.2.3 `Collision_Backend` 结构体

```cpp
namespace engine
{
    //碰撞检测后端
    struct Collision_Backend
    {
        //配置
        std::shared_ptr<Collision_Config> config;
        //窄阶段调度器
        std::unique_ptr<Collision_Dispatcher> dispatcher;
        //宽阶段接口
        std::unique_ptr<Collision_Interface> broadphase;
        //世界
        std::unique_ptr<Collision_World> world;

        //含参构造(配置共享)
        explicit Collision_Backend(std::shared_ptr<Collision_Config> shared_config);
        //默认构造
        Collision_Backend(void);
        //默认析构函数
        ~Collision_Backend() = default;

        //禁止拷贝
        Collision_Backend(const Collision_Backend&) = delete;
        Collision_Backend& operator=(const Collision_Backend&) = delete;

        //默认移动构造/赋值
        Collision_Backend(Collision_Backend&&) = default;
        Collision_Backend& operator=(Collision_Backend&&) = default;

        //有效性检查
        bool valid() const;
    };
}
```

| 成员 | 说明 |
| --- | --- |
| `config` | `std::shared_ptr<Collision_Config>`。**共享所有权设计**：多个 `Collision_Backend`（多个碰撞空间）可共享同一份配置，以复用内存分配器与流形池。含参构造接收外部传入的共享配置 |
| `dispatcher` | `std::unique_ptr<Collision_Dispatcher>`，独占所有权，构造时以 `config.get()` 为参数 |
| `broadphase` | `std::unique_ptr<Collision_Interface>`，独占所有权，基类指针持有多态 `Bvh_Tree` 对象 |
| `world` | `std::unique_ptr<Collision_World>`，独占所有权，构造时依次接收 `dispatcher.get()`、`broadphase.get()`、`config.get()` 三个裸指针 |
| 含参构造 | `explicit Collision_Backend(std::shared_ptr<Collision_Config> shared_config)`：① `config = std::move(shared_config)` 转移配置所有权；② 三个成员全部以 `new(std::nothrow)` 分配；③ **失败回滚**：若任一成员为 nullptr，全部 `reset()` 释放并返回，构造出"空后端" |
| 默认构造 | `Collision_Backend(void) : Collision_Backend(std::make_shared<Collision_Config>())`：委托含参构造，自动创建一份独占的默认配置。因此后端默认自带完整配置，不强制外部注入 |
| 析构 | `= default`，按成员逆序析构：world → broadphase → dispatcher → config。**注意**：world 在构造时保存了 dispatcher/broadphase/config 的裸指针，但三者都在 world 之后析构（逆序），故 world 析构时三者仍存活，安全 |
| 拷贝 | 删除。`unique_ptr` 成员天然不可拷贝，显式 `delete` 使意图明确并给出更好的报错 |
| 移动 | 默认。移动后源对象为空指针集合；被移动后不能调用 `valid()` 以外的方法（`valid()` 返回 false） |
| `valid()` | `bool valid() const`：返回四个成员**全部非空**。构造回滚或移动后为 false。**使用惯例**：任何对 `world` 的调用前应先 `valid()` 检查 |

#### 3.2.1 `Point2<T>` 内存布局

```cpp
template <typename T>
struct Point2
{
    T X;
    T Y;
};
```

#### 3.2.2 `Rect2<T>` 内存布局

```cpp
template <typename T>
struct Rect2
{
    T left, right, up, down;
};
```

- 四个连续标量，`sizeof(Rect2<T>) == 4 * sizeof(T)`。
- 边界值域约定：`left <= right` 且 `up <= down`（或按 y 轴方向理解为 up 为上界）。模块不校验、不修复非法区间，非法区间（left > right）的相等比较仍按位逐项进行，语义由调用方负责。

## 4. 模块设计/实现细节

### 4.1 ULP 相等比较的完整语义（坐标类型.h 核心）

`Point2<T>::operator==` 的分派逻辑（`if constexpr` 编译期分派）：

```cpp
bool operator==(const Point2& other) const noexcept
{
    if constexpr (std::is_floating_point_v<T>)
    {
        // 分支 1：任一坐标 NaN → 恒不等
        if (std::isnan(X) || std::isnan(other.X) ||
            std::isnan(Y) || std::isnan(other.Y))
            return false;
        // 分支 2：任一坐标无穷 → 精确比较
        if (std::isinf(X) || std::isinf(other.X) ||
            std::isinf(Y) || std::isinf(other.Y))
            return X == other.X && Y == other.Y;
        // 分支 3：常规有限数 → ULP 距离 ≤ 4
        constexpr uint64_t max_ulp = 4;
        return detail::ulp_distance(X, other.X) <= max_ulp
            && detail::ulp_distance(Y, other.Y) <= max_ulp;
    }
    else
        return X == other.X && Y == other.Y;   // 整数精确比较
}
```

各分支设计理由与边界情况：

| 分支 | 触发条件 | 行为 | 原因 |
| --- | --- | --- | --- |
| NaN 分支 | 任一坐标 `isnan` | 返回 false | IEEE 754 规定 NaN 与任何值（包括自身）不相等。若走 ULP 位模式比较，`bit_cast` 后 NaN 的位模式参与减法可能意外返回小值（如 qNaN 位模式与某有限数接近），导致"NaN == 数"错误成立。**必须先行拦截** |
| 无穷分支 | 任一坐标 `isinf` | `X == other.X && Y == other.Y` | 无穷没有"附近的可表示数"（±∞ 是端点），ULP 距离无意义（+∞ 与 DBL_MAX 位模式差是 1，会误判相等）。因此无穷与无穷必须位级精确相等才返回 true：`+∞==+∞` 成立、`+∞==-∞` 不成立、`∞==DBL_MAX` 不成立 |
| 常规分支 | 全部有限 | 双轴 ULP 距离均 ≤ 4 | 4 ULP 容差覆盖：网格加载后多次加减运算累积的舍入、`btTransform` 与坐标转换的微小漂移。两轴**同时**满足才返回 true（任一轴偏差超 4 ULP 即不等） |
| 整数分支 | T 非浮点 | 逐分量精确比较 | 整数无舍入问题，容差比较毫无意义且有害（会掩盖真实数值差异） |

为什么选择"ULP 距离 ≤ 4"而不是"相对误差 < ε"或"绝对误差 < ε"：

1. **绝对误差（如 1e-9）不可靠**：对数值量级敏感。1e9 级别的坐标，double 的最小步长已是 ~1.2e-7，1e-9 的绝对容差永远无法命中（过于严格）；而对 1e-9 级别的坐标，1e-9 容差又过于宽松（把相差 1e-8 都算相等）。
2. **相对误差对零值失效**：一个坐标恰好为 0 时相对误差无定义。
3. **ULP 距离与量级自适应**：任何量级下，4 ULP 意味着"数值上相邻到第 52-2=50 位有效二进制位"，等价于约 15 位十进制有效数字的一致性。这是"几乎相等"的业界标准做法（参考 Go 的 `math/big` 与各类物理引擎）。

易踩坑点：

- **ULP 比较不可传递**：`a≈b` 且 `b≈c` 不能推出 `a≈c`（每步最多偏 4 ULP，两步可偏 8 ULP）。因此**不要**把 `Point2d` 当 `std::map` 的 key 或用它做去重容器——相等语义不满足等价关系，容器行为未定义。
- **`Point2d` 不能用于 `std::unordered_set` 等哈希容器**：`operator==` 的容差语义与哈希一致性要求（相等对象哈希必相同）冲突。
- **`Rect2d` 的 `operator==` 是精确比较**，与 `Point2d` 语义不同。若希望矩形也走容差，需自行逐边界调用 ULP 工具（当前未暴露公开 ULP 接口，只能复用 `Point2d::operator==` 技巧或复制实现）。
- **对称性**：`a == b` 与 `b == a` 结果一致（ulp_distance 内部 swap 保证方向无关），满足相等运算符的对称性要求。
- **`-0.0` 与 `+0.0`**：位模式不同（符号位），但值相等，第一步 `lhs == rhs` 捕获返回 0，故 `Point2d{0,-0.0}` 与 `Point2d{0,0.0}` 判定相等，符合预期。

### 4.2 转换函数的设计决策

1. **显式函数而非运算符重载**：C++ 禁止自定义类型间隐式转换滥用，选择四个具名函数让"精度转换"在调用点显式可见，代码审查时可定位每一处收窄。
2. **四舍五入而非截断**：`lround`/`llround` 保证 ±2.5 → ±3。若用 `static_cast<int>(double)` 是**向零截断**（±2.5 → ±2），物理坐标取整会系统性偏向零。网格/像素坐标取整采用四舍五入更符合直觉。
3. **`noexcept`**：转换函数不分配内存、不抛异常，标记 noexcept 利于编译器优化与移动语义链。
4. **收窄风险由调用方承担**：`point_to_int` 的 int 收窄不做范围检查（性能优先，模块定位为"信任调用方"的基础工具）。防御性重开发可加 `std::clamp` 或断言，但会改变现状语义，需权衡。

### 4.3 依赖库封装的抽象策略

1. **为什么用 `using` 别名而不是继承/包装类**：bullet3 类型体系庞大（形状、调度器、回调），全量包装成本极高；别名零运行时开销、零内存开销，可无缝使用 bullet 全部能力。代价是**抽象不完全**——若未来换物理库，凡是使用了 bullet 特有 API（如 `btTransform::setOrigin`）的上层代码仍需修改。折中方案：别名收敛"类型名"，复杂 API 由上层（碰撞空间等）二次封装。
2. **`Collision_Backend` 是"装配 + 生命周期"封装**：它不隐藏 bullet 的用法，而是把"按正确顺序创建四个对象、正确传指针、失败回滚、保证析构顺序"这四件最容易出错的事固化为构造/析构逻辑，消除 use-after-free 类 bug。
3. **`config` 共享 vs 其余独占**：配置对象包含内存分配器与流形缓存，多个世界共享可复用资源；dispatcher/broadphase/world 是"世界实例"级别的状态，必须独占。这一选择直接支持了 `Collision_Region` 的"每空间一后端、配置可共享"设计。
4. **`Static_Object_Flag` 提升为引擎常量**：避免上层到处写 `btCollisionObject::CF_STATIC_OBJECT`，同时给"静态"语义一个引擎级名字。
5. **头文件裁剪**：只包含 `btBulletCollisionCommon.h` + 三个具体头文件，不包含整个 `btBulletDynamics`（动力学/刚体），从编译层面保证本引擎的"碰撞检测-only、无动力学"定位。

### 4.4 生命周期与所有权陷阱（重开发必读）

| 陷阱 | 场景 | 规避方式 |
| --- | --- | --- |
| **网格悬空指针** | `btBvhTriangleMeshShape` 只持有 `btTriangleMesh*`，不接管所有权 | `Collider` 的成员声明顺序：`mesh`（unique_ptr）**先于** `shape`（unique_ptr）声明 → 析构逆序 → shape 先亡、mesh 后亡，网格寿命 ≥ 形状寿命，安全。**重开发时切勿调整该声明顺序** |
| **世界内对象地址失效** | `btCollisionWorld` 记录的是 `btCollisionObject*`，若 Collider 被移动，object 地址变化 | `Collider` 显式实现移动构造/赋值：搬移后 `object.setUserPointer(this)` 重挂自指针、源对象置空指针（见 §4.5）。且 `Collision_Region` 的注释明确"object 加入 world 后不能搬移" |
| **后端四件套析构顺序** | world 持 dispatcher/broadphase/config 裸指针 | 成员声明顺序 config→dispatcher→broadphase→world，逆序析构 world 最先亡，安全。**不要**手动调整声明顺序 |
| **`new(std::nothrow)` 失败** | 任一分配失败 | 构造回滚全部释放，返回无效后端；调用方须先 `valid()` 再使用，否则对 nullptr world 调用将 UB |
| **拷贝后端** | unique_ptr 成员 | 拷贝已删除，编译器报错。确需复制时应显式重建世界（成本高，正常流程不需要） |
| **移动后使用** | 移动后端 | 移动后源端 `valid()==false`；继续使用源端 world 是空指针解引用 |

### 4.5 `Collider` 反查机制（本模块支撑的关键协作）

`碰撞系统运行包.h` 聚合的 `Collider` 结构体（`Collision_Region` 依赖它）使用 `Collision_Object::setUserPointer`：

```cpp
struct Collider
{
    uint64_t ID = 0;
    Collision_Object object;                       // 直接成员，非指针
    std::unique_ptr<Triangle_Mesh> mesh;           // 先声明
    std::unique_ptr<Collision_Shape> shape;        // 后声明

    Collider() { object.setUserPointer(this); }    // 自指针 = 本 Collider

    // 移动构造/赋值：搬移后重挂 this、清空源对象自指针
    Collider(Collider&& other) noexcept { /* ... */ object.setUserPointer(this);
             other.object.setUserPointer(nullptr); }

    static Collider* recover(const Collision_Object* obj) {
        return static_cast<Collider*>(obj->getUserPointer());  // 反查
    }
};
```

- bullet 检测回调（如扫掠 `Swept_Callback::addSingleResult`）拿到的是 `btCollisionObject*`，经 `Collider::recover` 反查出 `engine::Collider`，再读取 `ID`、`displacement_vector` 等。
- 这正是"坐标类型与依赖封装"提供 `Collision_Object` 别名 + 反查钩子的意义所在。

### 4.6 与其它模块的协作

| 协作方 | 协作内容 |
| --- | --- |
| `Collision_Region`（碰撞空间） | 成员 `Collision_Backend backend{}`（默认构造自动建世界）；`region_boundary`（静态边界 Collider）标记 `Static_Object_Flag`；检测流程调用后端世界的宽/窄阶段 |
| `Collider`（碰撞体） | 使用 `Collision_Object`、`Triangle_Mesh`、`Collision_Shape`、`Vector3` 别名；网格/形状生命周期依赖声明顺序 |
| `Collision_Proxy`（碰撞代理器） | 使用后端与形状别名，承载碰撞体与空间之间的代理 |
| `Mesh_Loader`（网格加载器） | 产出顶点/索引数据填充 `Triangle_Mesh`；坐标可能经 `Point2`/`Rect2` 定义局部范围 |
| `Quadtree` / `Quadtree_Manager`（四叉树分区） | 节点范围判定使用 `Rect2`/`Point2` 及 ULP 比较，避免浮点边界抖动 |
| `Number_Allocator`（数值分配器） | 被 `Collision_Region` 用于碰撞体 ID 分配（与本模块无直接依赖，但同属空间系统装配链） |
| bullet3 | 全部别名与被封装对象的最终实现方 |

### 4.7 易踩坑点汇总（快速排查清单）

1. `Point2d` 相等是容差比较——**别用于 map/set 键、别期望 `==` 表示位级相等**。
2. `Rect2d` 相等是精确比较——与 Point2d 语义不对称，跨模块混用时注意。
3. `point_to_int` 会四舍五入且 int 收窄可能溢出——大坐标先自查范围。
4. `point_to_double(Point2l)` 对 >2^53 的坐标有损——超大世界坐标考虑改用 double 全程。
5. `Collision_Backend` 使用前必须 `valid()`；移动/分配失败后不可用。
6. `Collider` 的 mesh/shape 声明顺序是**生命周期契约**，不得调换。
7. bullet 形状加入世界后**移动 Collider 会留下悬空对象指针**（世界仍指向旧地址）。
8. 引用本模块类型时优先用 `engine::` 全限定名；不要直接混用 `btXxx` 与别名（换库时全盘搜索 `bt` 前缀替换即可）。
9. `SAP` 宽阶段需要世界边界（`setWorldBounds`），默认 `Bvh_Tree` 无需边界——别在默认后端上期望 SAP 特性。
10. 编译期确认 `btScalar` 为 double（bullet 编译选项），若为 float 则 `Scalar` 别名语义变化，`Vector3` 精度随之降低。

## 5. 模块运行链路

### 5.1 类型使用链路（编译期）

```
引擎源码（如 Collision_Region.cpp）
  → #include "src/core/spatial/common/碰撞系统运行包.h"
  → 展开 core/依赖库封装.h（bullet 别名 + Collision_Backend 定义）
  → 展开 ../collision/Collider/碰撞体.h（Collider 定义）
  → 展开 ../collision/Collision_Region/碰撞空间.h（空间定义）
  → 全部落于 engine 命名空间 → 业务代码以 engine:: 名字使用
```

### 5.2 碰撞后端装配链路（运行期，Collision_Region 构造时）

```
Collision_Region 构造
  → Collision_Backend backend{}  (默认构造)
  → std::make_shared<Collision_Config>()          // 1. 创建配置（引用计数 1）
  → 委托含参构造
  → new(std::nothrow) Collision_Dispatcher(config.get())   // 2. 窄阶段调度器
  → new(std::nothrow) Bvh_Tree{}                              // 3. 宽阶段 BVH
  → new(std::nothrow) Collision_World(dispatcher.get(),
        broadphase.get(), config.get())                       // 4. 碰撞世界
  → 失败检测：任一为空 → 全量 reset 回滚 → valid()==false
  → 成功：valid()==true，世界就绪
```

### 5.3 碰撞检测链路（运行期，Collision_Region::detect）

```
detect() 调用
  → 世界内部 performDiscreteCollisionDetection()
  → 宽阶段（Bvh_Tree）对动态/静态对象对做包围盒剔除 → 候选对
  → 窄阶段（Dispatcher）按形状对选择算法（GJK/EPA/SAT）→ 接触流形
  → 结果经回调/流形遍历取回 → 反查（recover）得 Collider → 组装 Collision_Result
```

### 5.4 坐标转换链路（运行期，网格/物理坐标互转）

```
物理坐标（Vector3 / Point2d 浮点世界）
  → point_to_int / point_to_l（lround 四舍五入）
  → 栅格/像素/区块索引（Point2i / Point2l）
  → point_to_double（整数转浮点）
  → 回到浮点世界参与比较（Point2d::operator== ULP 容差）
```

### 5.5 生命周期链路（析构期）

```
Collision_Region 析构
  → 先将全部碰撞对象移出碰撞世界（避免世界解引用已释放对象）
  → Collision_Backend 成员析构（逆序）：
      world 析构 → broadphase 析构 → dispatcher 析构 → config 引用计数减一
  → 共享同一 config 的其他后端不受影响（shared_ptr 语义）
```
