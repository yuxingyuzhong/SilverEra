## 1. 模块功能

### 1.1 模块是什么

「数据校验器 Data_Validator」是引擎层 `src/tools/Data_Validator/` 目录下的一个静态工具类模块，提供两类校验能力：

| 能力 | 入口 | 解决的问题 |
| --- | --- | --- |
| 配置字段校验 | `Data_Validator::field_check<T>(json, field)` | 校验一个 nlohmann::json 对象中指定字段：① 字段是否存在；② 字段值类型是否与模板实参 T 匹配；③ 内容是否为空 |
| 路径有效性校验 | `Data_Validator::path_check(path)` / `path_check(string)` | 校验一个文件系统路径是否为"存在且可读取的普通文件"，而非目录、不存在路径或空路径 |

### 1.2 模块解决什么问题

- **分散的防御性代码重复问题**：引擎系统层大量业务模块（实体管理器、效应系统、属性槽分发器）在消费配置 JSON 前，都必须重复编写"contains 判断 → is_number / is_string 判断 → empty 判断"三连。本模块将这段逻辑收敛为一个模板函数，消除复制粘贴与不一致。
- **JSON 类型误判问题**：nlohmann::json 中 `42`（整数）与 `42.0`（浮点）是不同类型；直接 `config["x"].get<int>()` 会在类型不符时抛 `type_error`。`field_check` 在类型层面先行把关，把"类型错误"从异常路径转为显式布尔返回，避免未捕获异常导致崩溃。
- **中文/UTF-8 路径处理问题**：Windows 下文件系统路径可能包含中文。`std::string` 到 `std::filesystem::path` 的直接转换依赖系统 locale（Windows 下可能是 GBK），会导致中文路径解析失败。本模块提供 `std::string` → `std::u8string` → `path` 的显式转换链，保证 UTF-8 编码的字符串路径在中文环境下正确解析。
- **路径攻击预防（半套）**：`path_check` 只验证"路径是否指向存在的可读文件"，不做目录白名单限制（目录穿越防护由配置加载器的 `skip_safety_inspect` 承担，见配置加载器文档）。两者职责分离：本模块管"文件是否可用"，配置加载器管"路径是否越界"。

### 1.3 模块服务谁

- **直接服务方（调用者）**：
  - 引擎层 `Config_Loader`（配置加载器）——虽然其 cpp 中安全路径检查逻辑是自实现的（未复用 `path_check`），但语义一致；测试层数据校验器测试直接调用本模块。
  - 系统层 `Entity_Manager`（实体管理器）、`Effect`（效应）、`Effect_Manager`（效应管理器）、`Prop_Distributor`（属性槽分发器）——在 `配置处理.cpp`、`事件处理.cpp`、`效应.cpp` 等实现文件中大量调用 `field_check` 与 `path_check`。
  - 系统层 `Config_Editor`（配置编辑器）——在其注释与内部工具中"复刻 Config_Checker::field_check 逻辑"（见 §4.5 遗留问题）。
- **间接服务方**：所有通过上述模块消费配置数据的业务逻辑。

### 1.4 命名演变（重要背景）

- 旧名：`Config_Checker`（配置检查器），头文件 `src/tools/Config_Checker/配置检查器.h`。
- 现名：`Data_Validator`（数据校验器），头文件 `src/tools/Data_Validator/数据校验器.h`。
- **引擎层已完成改名**：当前引擎层源码中该类名为 `Data_Validator`。
- **系统层遗留未同步**：`系统层/src/effect/Effect_Manager/效应管理器.h`、`系统层/src/effect/Effect/效应.h`、`系统层/src/entity/Entity_Manager/实体管理器.h`、`系统层/src/prop/Prop_Distributor/属性槽分发器.h` 仍 `#include "src/tools/Config_Checker/配置检查器.h"`，且 `效应管理器.cpp`、`事件处理.cpp`、`配置处理.cpp`、`效应.cpp` 等实现中仍以 `Config_Checker::field_check` 调用。这意味着**系统层当前指向的头文件路径在引擎层已不存在**，重开发/编译系统层时需同步修正为 `Data_Validator`（详见 §4.5）。

## 2. 模块提供接口

### 2.1 `Data_Validator` 类

```cpp
namespace engine
{
    //配置检查器（注释为遗留旧名，类名已更新为数据校验器）
    class Data_Validator
    {
    public:
        //字段有效性检查
        template<typename T>
        static bool field_check(const nlohmann::json& config, const std::string& field);

        //路径有效性检查 —— path重载
        static bool path_check(const std::filesystem::path& config_path);

        //路径有效性检查 —— string重载
        static bool path_check(const std::string& config_path);

    private:
        //异常信息输出
        static bool error_out(std::error_code& error_info);
    };
}
```

- 类整体为**纯静态工具类**：无任何成员变量、无构造/析构、所有方法 static。实例化无意义（虽未显式禁止构造）。
- 无 `final`、无虚函数，类体头文件内联实现（`field_check`/`path_check` 定义在头文件内）。
- 依赖日志系统 `Log`（`#include "src/tools/Logging/日志系统.h"`）输出校验失败原因。

### 2.2 `field_check<T>` 模板 —— 完整签名与行为

```cpp
template<typename T>
static bool field_check(const nlohmann::json& config, const std::string& field)
```

| 项 | 说明 |
| --- | --- |
| 模板参数 T | 期望的字段类型。通过编译期特性分派到不同校验分支（见下） |
| 参数 `config` | 待校验的 JSON 对象（`const&`，不修改） |
| 参数 `field` | 字段名（`const std::string&`，UTF-8 编码的键名） |
| 返回值 | `true` = 字段存在、类型匹配且内容非空；`false` = 任一检查失败（并输出一条日志） |

行为总流程（所有分支共用）：

```
field_check<T>(config, field)
  → 步骤 1：config.contains(field)？
      否 → Log::warn("Data_Validator::未包含指定字段: {}", field) → return false
      是 → 进入步骤 2
  → 步骤 2：按 T 的类型特性分派（if constexpr 链）
  → 步骤 3：所有检查通过 → return true
```

#### 分支 A：布尔类型（`std::is_same_v<T, bool>`）

```cpp
if constexpr (std::is_same_v<T, bool>)
{
    if (!config[field].is_boolean())
    {
        Log::info("Data_Validator::字段 {} 非布尔格式", field);
        return false;
    }
}
```

| 项 | 说明 |
| --- | --- |
| 判定 | `config[field].is_boolean()` 为 false 则失败 |
| 放行 | JSON `true` / `false` |
| 拒绝 | 数值（含 0/1，**不**像某些语言那样把 0/1 当布尔）、字符串 `"true"`、数组、对象、null |
| 边界 | 布尔值不存在"空"概念，故无空检查 |

#### 分支 B：整数类型（`std::is_integral_v<T>`，且非 bool——因为 bool 分支在前）

```cpp
else if constexpr (std::is_integral_v<T>)
{
    if (!config[field].is_number_integer())
    {
        Log::info("Data_Validator::字段 {} 非整数格式", field);
        return false;
    }
}
```

| 项 | 说明 |
| --- | --- |
| 判定 | `config[field].is_number_integer()` 为 false 则失败 |
| 覆盖类型 | 所有整数类型：`int`、`int64_t`、`uint64_t`、`short`、`char` 等（`std::is_integral_v<T>` 全匹配） |
| 放行 | JSON 整数（无小数点的数值，如 `42`） |
| 拒绝 | **浮点数值（`42.0`）**、布尔、字符串、数组、对象、null |
| 边界 | nlohmann 的 `is_number_integer()` 对 `42.0` 返回 false——即使数值上相等，类型不匹配即拒绝。注意：**不检查数值范围**（如 `T=int` 时 JSON 存 `999999999999999` 也放行，后续 `get<T>()` 才可能溢出） |
| 空检查 | 数值类型无"空"概念，无空检查 |

#### 分支 C：浮点类型（`std::is_floating_point_v<T>`）

```cpp
else if constexpr (std::is_floating_point_v<T>)
{
    if (!config[field].is_number_float())
    {
        Log::info("Data_Validator::字段 {} 非浮点数格式", field);
        return false;
    }
}
```

| 项 | 说明 |
| --- | --- |
| 判定 | `config[field].is_number_float()` 为 false 则失败 |
| 覆盖类型 | `float`、`double`、`long double` |
| 放行 | JSON 浮点（带小数点的数值，如 `42.5`；`42.0` 在 JSON 文本中写为 `42.0` 时按浮点存储） |
| 拒绝 | 整数（`42`，无小数点）、布尔、字符串、数组、对象、null |
| 边界 | **整数 JSON 不自动提升为浮点**：若配置文件中写 `42` 而代码期望 `double`，`is_number_float()` 返回 false → 校验失败。需要"整浮通吃"的调用方须自行先 `get<double>()`（本模块不做宽松匹配，这是刻意设计，见 §4.1） |

#### 分支 D：字符串类型（`std::is_same_v<T, std::string>`）

```cpp
else if constexpr (std::is_same_v<T, std::string>)
{
    if (!config[field].is_string())
    {
        Log::info("Data_Validator::字段 {} 类型不匹配", field);
        return false;
    }
    if (config[field].get_ref<const std::string&>().empty())
    {
        Log::info("Data_Validator::字段 {} 内容为空", field);
        return false;
    }
}
```

| 项 | 说明 |
| --- | --- |
| 判定 1 | `config[field].is_string()` 为 false → 失败（"类型不匹配"日志） |
| 判定 2 | 字符串 `empty()` → 失败（"内容为空"日志） |
| 技术细节 | 使用 `get_ref<const std::string&>()` 取得底层 `std::string` 引用（零拷贝）判断空串，而非 `get<std::string>()` 复制一份 |
| 放行 | 非空字符串（含中文、空格的"非空"字符串，如 `" "` 视为非空——只查 `empty()`，**不 trim 空白**） |
| 拒绝 | 空字符串 `""`、非字符串类型（数值/布尔/数组/对象/null） |

#### 分支 E：其他类型（else，容器/复合类型兜底）

```cpp
else
{
    try
    {
        config[field].get<T>();
    }
    catch (const nlohmann::json::type_error&)
    {
        Log::info("Data_Validator::字段 {} 类型不匹配", field);
        return false;
    }

    if ((config[field].is_array() || config[field].is_object()) &&
        config[field].empty())
    {
        Log::info("Data_Validator::字段 {} 内容为空", field);
        return false;
    }
}
```

| 项 | 说明 |
| --- | --- |
| 触发条件 | T 非 bool、非整型、非浮点、非 std::string，即**一切其他类型**：`std::vector<T>`、`std::pair<A,B>`、自定义结构体（需 json 可序列化）、`nlohmann::json` 本身等 |
| 判定 1 | 尝试 `config[field].get<T>()`，捕获 `nlohmann::json::type_error`（类型不匹配/转换失败）→ 失败。**注意**：只捕获 `type_error`，其他异常（如 `out_of_range`、`parse_error`、`bad_alloc`）不在此捕获，会继续向上抛出 |
| 判定 2 | 若字段是数组或对象且 `empty()` → 失败（"内容为空"） |
| 放行 | 能被 `get<T>()` 成功转换、且（若是容器）非空 |
| 边界 | 对 `std::vector<int>`：`get<std::vector<int>>()` 要求字段是数组且元素可转 int，否则抛 type_error → 拒绝。对**标量复合**（如 `std::pair`）：不适用空检查（pair 无 is_array/is_object），只做转换检查 |
| 潜在问题 | ① `get<T>()` 成功后结果被丢弃——本函数只校验不取值，调用方需要数据时须再 `get` 一次；② 若 `T` 恰好是 `std::string` 的派生或有 `operator=` 的包装，语义取决于 nlohmann 特化 |

#### `if constexpr` 链的分派顺序（重要）

```
1. std::is_same_v<T, bool>          → 布尔分支
2. std::is_integral_v<T>            → 整数分支（bool 已在 1 截获，不会误入）
3. std::is_floating_point_v<T>      → 浮点分支
4. std::is_same_v<T, std::string>   → 字符串分支
5. else                             → 容器/复合类型兜底
```

- 采用 `else if constexpr` 链（不是独立的 `if constexpr` 堆叠），保证每个 T 只落入一个分支。测试层注释明确指出"修复后语义：数据校验器.h 的 if constexpr 链改为 else if constexpr"，说明历史上存在过"多个分支同时编译/语义冲突"的 bug，本版次已修复。
- `bool` 与 `std::is_integral_v<bool>` 冲突：`bool` 本身满足 `std::is_integral_v`，若把整数分支放前面，`T=bool` 会落入整数分支且 `is_number_integer()` 对 JSON 布尔返回 false → bool 永远校验失败。故 bool 分支**必须**在整数分支之前。

### 2.3 `path_check` —— path 重载

```cpp
static bool path_check(const std::filesystem::path& config_path)
```

| 项 | 说明 |
| --- | --- |
| 参数 | `config_path`：文件系统路径（`const&`） |
| 返回值 | `true` = 是存在的可读普通文件；`false` = 空路径/不存在/非普通文件/系统错误 |

行为流程：

```
path_check(path)
  → 检查 1：config_path.begin() == config_path.end()？
      是 → Log::info("路径无效") → return false     // 空路径
  → 检查 2：std::filesystem::exists(config_path, ec) 为 false？
      是 → Log::info("访问路径不存在") + error_out(ec) → return false
  → 检查 3：std::filesystem::is_regular_file(config_path, ec) 为 false？
      是 → Log::info("访问路径不可读取") + error_out(ec) → return false
  → 全部通过 → return true
```

| 项 | 说明 |
| --- | --- |
| 空路径判定 | `config_path.begin() == config_path.end()`：path 为空（无任何路径元素）时迭代器 begin==end。用迭代器而非 `empty()`，因为 path 可能含相对元素 |
| 存在性 | `exists(config_path, ec)`：用**重载带 error_code 版本**，不抛异常，错误码写入 `ec`。若存在则继续；若不存在或发生系统错误（如权限拒绝、驱动器不可用），返回 false 并 `error_out(ec)` 输出错误码 |
| 文件性 | `is_regular_file(config_path, ec)`：必须为普通文件。目录、符号链接指向目录、设备文件等均拒绝（符号链接指向普通文件时 `is_regular_file` 跟随链接判定为 true） |
| 异常安全 | 全程使用带 `error_code` 的重载版本，**不抛任何异常**（除非 error_out 内部 Log 抛异常） |
| 语义 | 不校验"路径是否在允许目录内"——这是配置加载器 `skip_safety_inspect` 的职责 |

### 2.4 `path_check` —— string 重载

```cpp
static bool path_check(const std::string& config_path)
{
    //转化为可用字符串格式
    //要求string编码格式为UTF-8
    std::u8string u8config_path(config_path.begin(), config_path.end());
    //转化为标准路径
    std::filesystem::path suspect_path = u8config_path;
    //调用path重载
    return path_check(suspect_path);
}
```

| 项 | 说明 |
| --- | --- |
| 参数 | `config_path`：UTF-8 编码的字符串路径 |
| 处理链 | `std::string`（UTF-8）→ `std::u8string` → `std::filesystem::path` → 委托 path 重载 |
| **中文路径关键点** | 从 `std::string` 构造 `std::u8string` 用 `(begin, end)` 迭代器区间构造（逐字节拷贝，UTF-8 字节序列原样保留）。`std::filesystem::path` 从 `u8string` 构造时在 Windows 上会正确地把 UTF-8 转成内部宽字符表示（`std::filesystem::u8path` 的等价路径），从而**正确处理中文路径** |
| 前置条件 | 调用方必须保证传入字符串是 UTF-8 编码。若传入 GBK 编码字符串（如某些 Windows API 返回），逐字节搬移后 UTF-8 解码错误，中文路径解析失败。这是文档化约束（源码注释"要求string编码格式为UTF-8"） |
| 与 path 重载的差异 | 仅做编码转换，最终全部委托 path 重载，校验逻辑单点维护 |

### 2.5 私有工具 `error_out`

```cpp
static bool error_out(std::error_code& error_info)
{
    if (!error_info)                 // 错误码为空（无错误）
        return false;                // 返回"未输出"
    else
    {
        Log::info("{}", error_info); // 输出错误码（依赖 Log 的 error_code formatter 特化）
        error_info.clear();          // 清空错误码，便于复用同一 ec
        return true;                 // 返回"已输出"
    }
}
```

| 项 | 说明 |
| --- | --- |
| 功能 | 将 `std::error_code` 转为一条日志输出，并清空错误码 |
| 返回值 | `true` = 本次确有错误被输出；`false` = 无错误 |
| 输出格式 | `Log::info("{}", error_info)` —— 依赖 `日志系统.h` 中 `std::formatter<std::error_code>` 的显式特化（输出 `[value] message` 形式，详见日志系统文档） |
| 副作用 | `clear()` 使错误码置空，同一 `error_code` 变量可被后续文件系统调用复用而不会残留旧错误 |

## 3. 模块内部架构

### 3.1 文件组织

```
src/tools/Data_Validator/
├── 数据校验器.h            ← 类定义（全部逻辑内联于头文件）
└── 局部命名空间使用.h       ← 仅含 #pragma once（当前为空壳，见 §3.3）
```

- **本模块无 .cpp 文件**：`field_check`、`path_check` 均为模板或内联函数，定义在头文件内，模板无法在 cpp 中实例化（模板需在实例化点可见定义）。
- `数据校验器.h` 的 include 依赖：
  - `common/前置头文件包含.h`（预编译头：提供 `<filesystem>`、`<string>`、nlohmann/json 等）
  - `src/tools/Logging/日志系统.h`（Log 静态类，用于全部校验失败日志）

### 3.2 内部结构

- **无成员变量**：类为纯静态工具，零状态。
- **无内部类/枚举**：只有四个成员函数（2 公开 + 2 私有），其中 `error_out` 为私有工具。
- **无内部数据结构**：唯一使用到的复合类型是形参 `nlohmann::json`（外部类型）。
- **编译期分派结构**：`field_check` 内部为 5 分支 `if constexpr` 链（bool/integral/floating/string/else），是模块唯一"数据结构"——即编译期的类型特性选择逻辑。

### 3.3 局部命名空间使用.h 现状说明

```cpp
#pragma once
```

- 当前文件**只有一个 `#pragma once` 守卫，无任何 `using` 声明**。
- 与同层其他模块（如 Config_Loader 的 `局部命名空间使用.h`、Collision_Region 的 `局部命名空间使用.h`）不同——那些文件内有大量 `using std::xxx;` 收窄声明。本文件是**空壳占位**，`数据校验器.h` 也**未包含**它（数据校验器.h 直接写全限定名 `std::filesystem::path`、`std::error_code`、`std::string`）。
- 重开发时：可保留空壳以维持目录惯例一致性，或补入需要的 `using`（但需同步修改头文件以使用简名）。当前实现不依赖该文件。

- `#pragma once` 防护。

## 4. 模块设计/实现细节

### 4.1 关键设计决策

**决策 1：严格类型匹配，不做宽松转换**

`field_check<int>` 拒绝 `42.0`，`field_check<double>` 拒绝 `42`。理由：
- nlohmann::json 区分 integer 与 float 存储（`is_number_integer` vs `is_number_float`）。
- 宽松匹配（如"整数也可当浮点"）会让配置文件的类型错误被静默掩盖：开发者在 JSON 里误写 `"count": 42.0` 期望整数时，宽松校验会放行，之后 `get<int>()` 仍可能抛异常或截断。
- 严格匹配在**加载入口**就把类型错误暴露出来，符合"fail fast"理念。

**决策 2：`if constexpr` 链而非运行时分派**

- 模板在编译期选定分支，被舍弃的分支（`if constexpr` 的 else 部分）不参与实例化，因此 `T=bool` 时容器分支的 `get<T>()` 代码不会被编译——避免了对 bool 调用 `get<bool>` 这类本会编译错误/语义错误的代码。
- 这也是"else if constexpr 修复"的意义：历史版本若用独立 `if constexpr` 堆叠，多个分支会同时参与编译，可能引发歧义或错误实例化。

**决策 3：校验与取值分离**

- `field_check` 只返回布尔，不把校验通过的 T 值返回给调用方。调用方通常写：
  ```cpp
  if (Data_Validator::field_check<uint64_t>(config, "inclusion"))
  {
      uint64_t value = config["inclusion"].get<uint64_t>();
      // 使用 value
  }
  ```
- 优点：接口简单、可链式校验多个字段、不引入"空值/可选"复杂度。缺点：JSON 被 `operator[]` 访问两次（一次校验、一次取值），但 nlohmann 为高效查找，开销可忽略。

**决策 4：错误码重载而非异常**

- `path_check` 全部使用带 `error_code` 的 `std::filesystem` 重载，避免 `filesystem_error` 异常。原因是路径校验常发生在启动阶段与配置加载路径上，异常安全与可恢复性优先，且便于与 `error_out` 的日志输出结合。

**决策 5：错误信息分级**

- 字段不存在 → `Log::warn`（警告级）。
- 字段存在但类型/内容错误 → `Log::info`（信息级）。
- 路径无效 → `Log::info`。
- 这一分级说明：**字段缺失被视为比类型错误更严重**（缺失可能导致后续逻辑缺省值错误，而类型错误至少说明字段已提供）。重开发时若需调整日志级别需同步测试。

### 4.2 边界情况处理

| 边界情况 | 处理 |
| --- | --- |
| 字段不存在 | 返回 false，`Log::warn` 提示 |
| 字段值为 null | 所有分支拒绝：bool 的 `is_boolean()`=false、整数的 `is_number_integer()`=false、浮点的 `is_number_float()`=false、字符串的 `is_string()`=false；容器分支 `get<T>()` 从 null 转换通常抛 type_error（取决于 T） |
| 空字符串 `""` | 字符串分支拒绝（`empty()`） |
| 仅空白字符串 `" "` | **放行**（只查 empty，不 trim） |
| 空数组 `[]` / 空对象 `{}` | 容器分支拒绝（`is_array/is_object && empty()`）；若 T 恰好是 `nlohmann::json` 本身，`get<json>()` 成功但 empty 检查拒绝 |
| 整数/浮点数值范围溢出 | **不检查**。`field_check<int>` 对 `999999999999` 放行，后续 `get<int>()` 行为取决于 nlohmann（可能截断或抛）。调用方对大数值应自行加范围校验 |
| 路径为 `""`（空字符串） | string 重载转为空 u8string → path 空 → begin==end → 拒绝 |
| 路径为目录 | `is_regular_file` 返回 false → 拒绝 |
| 路径不存在 | `exists` 返回 false（ec 可能含错误码）→ 拒绝 |
| 路径含 `..` | **不拒绝**。`path_check` 不做目录穿越防护（交给配置加载器） |
| 相对路径 | `exists`/`is_regular_file` 相对当前工作目录解析，正常判定 |
| `std::filesystem` 系统错误（如磁盘故障） | `ec` 非空 → `error_out` 输出错误码 → 拒绝 |
| 中文路径 | string 重载经 u8string 转换正确处理（Windows UTF-8→宽字符内部表示） |

### 4.3 与其它模块的协作

| 协作方 | 协作内容 |
| --- | --- |
| `Log`（日志系统，`src/tools/Logging/日志系统.h`） | 全部失败/成功提示经 `Log::warn`/`Log::info` 输出；`error_out` 依赖 `std::formatter<std::error_code>` 特化（该特化定义在日志系统.h 尾部） |

### 4.6 易踩坑点汇总

1. **bool 分支必须在 integral 分支之前**：`bool` 满足 `is_integral_v`，顺序颠倒会导致 bool 校验永远失败。
2. **严格类型匹配**：`42` 与 `42.0` 在 JSON 中是不同类型，别期望 `field_check<int>` 放行 `42.0`。
3. **`get<T>()` 只捕获 type_error**：`T` 为复杂类型时若 get 抛出其他异常（如递归类型转换中的 out_of_range）不会被捕获，调用方需自行 try-catch。
4. **空串 vs 空白串**：`""` 拒绝、`" "` 放行。需要 trim 时调用方自己处理。
5. **不检查数值范围**：大数溢出由后续 `get<T>()` 或业务逻辑兜底。
6. **string 重载要求 UTF-8 输入**：传 GBK 字符串会解析错中文路径。
7. **path_check 不防目录穿越**：不要拿它当安全边界，安全边界在配置加载器。
8. **`error_out` 会 clear 错误码**：若调用方还想保留错误信息需先复制。
9. **系统层旧名 Config_Checker**：改文件路径与类名时容易遗漏系统层，编译期报"找不到 Config_Checker"。

