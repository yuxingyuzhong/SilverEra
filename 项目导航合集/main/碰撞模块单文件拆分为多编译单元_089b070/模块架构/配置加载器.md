## 1. 模块功能

### 1.1 模块是什么

「配置加载器 Config_Loader」是引擎层 `src/tools/Config_Loader/` 目录下的一个类，负责把磁盘上的配置文件**批量、安全地**分发到引擎各业务模块。其核心思想是**路由驱动**：

- 磁盘上存在一个"路由目录"（默认 `assets/config/route/`），内含若干**路由文件**（JSON）。
- 每个路由文件是一个 JSON **数组**，数组每个元素描述一条配置装载指令：`{"module": "<目标模块名>", "config_path": "<配置文件的相对路径>"}`。
- Config_Loader 递归扫描路由目录 → 逐个读取路由文件 → 逐条解析指令 → 对 `config_path` 做**目录越界安全检查**（防路径穿越）→ 读取目标配置文件 → 构造 `category="Config"`、`tag="Load"` 的事件 → 通过 `Event_Terminal`（事件终端）把配置事件发送给指定模块。

```
                      ┌──────────────────────────────────────────┐
  资产目录             │              Config_Loader               │
  assets/config/      │                                          │
  ├── route/          │  content_scan()  递归扫描路由目录          │
  │   ├── route_a.json│  file_read()     读路由文件（JSON数组）     │
  │   └── route_b.json│  逐条解析 module / config_path            │
  ├── module_x.json   │  skip_safety_inspect()  路径越界检查       │
  ├── module_y.json   │  file_read()     读目标配置文件            │
  └── ...             │  构造 event{category=Config, tag=Load}    │
                      │  event_terminal.send(evt, acl_key)        │
                      └───────────────┬──────────────────────────┘
                                      │ 事件
                                      ▼
                              Event_Broker 中转 → 目标模块订阅入口
```

### 1.2 模块解决什么问题

- **配置装载路径统一化**：业务模块无需自己拼磁盘路径、自己判断"配置在哪"；只需注册事件订阅（`Event_Terminal::attach`），等待 `Config/Load` 事件携带配置 JSON 送达。
- **配置变更免重编译**：新增/修改配置只需改 JSON 文件，不改代码、不重编译。
- **多模块配置集中装载**：一次 `act()` 可装载任意数量模块的配置，路由文件充当"装载清单"。
- **路径穿越攻击防护**：`config_path` 来自配置文件（外部输入），可能被恶意写成 `../../../etc/passwd`。`skip_safety_inspect` 强制路径必须以 `assets/config/` 开头且不含 `..`，从源头阻断越界读取。
- **中文路径支持**：全链路使用 `u8string`（UTF-8）承载路径字符串，保证 Windows 下中文目录/文件名正常解析。
- **失败容错**：单个路由文件损坏、单个指令非法、单个配置读取失败均不会中断整体流程（记录日志后继续），只有结构性故障（扫描失败、事件发送依赖缺失）才会中止。

### 1.3 模块服务谁

- **直接服务方（配置消费方）**：引擎层/系统层一切注册了事件订阅的模块——如系统层的 `Entity_Manager`（实体管理器）、`Effect`（效应系统）等。它们通过 `Event_Terminal::attach(module_name, needed_events, handler)` 登记对 `category="Config"` 事件的兴趣，收到 `event.config` 即消费配置。
- **协作方**：
  - `Event_Terminal`（事件终端，`src/core/event/Event_Terminal/事件终端.h`）——发送通道与权限密钥来源。
  - `Engine_Env`（引擎环境，`src/tools/Engine_Env/引擎环境.h`）——提供可执行文件目录作为基目录（`exe_dir_get()`）。
  - `Log`（日志系统）——全部运行日志。
- **不服务**：不直接读配置给调用方"返回值"——所有配置都通过事件异步/同步送达（当前实现为同步 send）。

## 2. 模块提供接口

### 2.1 `Config_Loader` 类

```cpp
namespace engine
{
    //配置加载器
    class Config_Loader
    {
    private:
        //扫描子目录（相对于基目录）
        std::u8string scan_content = u8"assets/config/route/";
        //允许的根目录（相对于基目录）
        std::u8string allowed_root = u8"assets/config/";
    public:
        //事件终端
        Event_Terminal event_terminal;
    private:
        //权限密钥
        int64_t acl_key = 0;

    public:
        //构造函数
        Config_Loader();
        //析构函数
        ~Config_Loader() = default;

        //任务执行
        void act(void);
    private:
        //基目录获取
        const std::filesystem::path base_dir_get(void);
        //目录递归扫描
        void content_scan(std::vector<std::u8string>& receiver);
        //路径安全检查
        bool skip_safety_inspect(const std::u8string& config_path);
        //文件读取
        void file_read(const std::filesystem::path& file_path, nlohmann::json& receiver);
        //异常信息输出
        bool error_out(std::error_code& info);
    };
}
```

#### 2.1.1 成员变量

| 成员 | 类型 | 访问级别 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `scan_content` | `std::u8string` | private | `u8"assets/config/route/"` | 路由目录（相对基目录）。**注意**：末尾带 `/` |
| `allowed_root` | `std::u8string` | private | `u8"assets/config/"` | 允许的配置根目录（相对基目录）。**当前实现中该成员被声明但未在 cpp 中被实际引用**（安全检查是硬编码 `assets`/`config` 两段判断，见 §4.2）——是设计意图（可配置白名单）与实现（硬编码）之间的偏差，重开发时二选一收敛 |
| `event_terminal` | `Event_Terminal` | **public** | 默认构造 | 事件终端。公开可见以便调用方在必要时访问终端（如注册事件处理）；其生命周期随 Config_Loader 共存亡 |
| `acl_key` | `int64_t` | private | `0` | 权限密钥，构造时经 `event_terminal.acl_key_gen()` 生成，后续所有 `send` 都携带它以通过事件系统的权限校验 |

#### 2.1.2 公开方法

| 方法签名 | 参数 | 返回值 | 行为说明 |
| --- | --- | --- | --- |
| `Config_Loader()` | 无 | — | 生成权限密钥：`acl_key = event_terminal.acl_key_gen()`。**注意**：`event_terminal` 是成员，其构造先于构造函数体执行（成员初始化顺序），因此构造函数体内可直接调用其方法 |
| `~Config_Loader() = default` | — | — | 平凡析构；`event_terminal` 与 `acl_key` 随类消亡 |
| `void act(void)` | 无 | void | **主入口**：执行完整配置装载流程（见 §5 运行链路）。无参数无返回，结果全部通过事件与日志表达 |

#### 2.1.3 私有方法

| 方法签名 | 参数 | 返回值 | 行为说明 |
| --- | --- | --- | --- |
| `const std::filesystem::path base_dir_get(void)` | 无 | `const path` | 返回配置装载的基目录：委托 `Engine_Env::exe_dir_get()`（即可执行文件所在目录）。所有相对路径（scan_content、config_path）最终都拼接在基目录下 |
| `void content_scan(std::vector<std::u8string>& receiver)` | `receiver`：出参，接收扫描到的**路由文件**绝对路径（UTF-8 字符串）列表 | void | 递归扫描 `base_dir / scan_content` 目录，收集所有普通文件的绝对路径到 receiver |
| `bool skip_safety_inspect(const std::u8string& config_path)` | `config_path`：待校验的相对路径（UTF-8） | `true` = 路径安全且文件可用；`false` = 越界/不存在/非文件 | 三段式检查：① 相对路径前两段必须为 `assets`/`config`；② 全程不得出现 `..`；③ 拼接基目录后必须是存在的普通文件 |
| `void file_read(const std::filesystem::path& file_path, nlohmann::json& receiver)` | `file_path`：要读取的文件；`receiver`：出参，接收解析出的 JSON | void | 打开文件并以 `operator>>` 解析为 JSON；任何失败（打不开/解析错/未知异常）都置 `receiver = json()`（空 JSON，即 null）并记日志 |
| `bool error_out(std::error_code& info)` | `info`：错误码（引用，可能被 clear） | `true` = 本次确有错误被输出 | 错误码非空时输出到 `std::cout` 并 clear，返回是否输出。**注意**：此处的 error_out 走 `cout` 而非 Log（与 Data_Validator 的 error_out 走 Log 不同，是历史实现差异） |

### 2.2 事件系统协作接口（本模块使用的外部接口摘录）

```cpp
namespace engine
{
    //事件（src/core/event/Event/事件.h）
    struct event
    {
        event();                                                       // 默认构造
        event(const std::string& category, const std::string& tag);    // 标签构造
        event(const std::string& sender_object, const std::string& target_object,
              const std::string& category, const std::string& tag);    // 对象标签构造
        event(const std::string& sender_object, const std::string& target_object,
              const std::string& category, const std::string& tag,
              const nlohmann::json& config);                           // 全量构造

        std::string sender_object{};   // 事件发起者
        std::string target_object{};   // 事件目标
        std::string category;          // 事件大类
        std::string tag;               // 类内标签
        nlohmann::json config;         // 配置包
        bool operator==(const event& other) const;  // 相等（category/tag/target/config 全比）
    };
}

namespace engine
{
    //事件终端（src/core/event/Event_Terminal/事件终端.h）
    class Event_Terminal
    {
    public:
        int64_t acl_key_gen(void);                                              // 权限密钥生成
        bool attach(const std::string& module_name, const std::vector<event>& needed_events,
                    const int64_t& acl_key);                                    // 中转站接入
        bool send(std::vector<std::shared_ptr<event>> events, const int64_t& acl_key);  // 多事件发送
        // ...（interact/query/clear/build 等未在 Config_Loader 中使用）
    };
}
```

本模块使用方式：

```cpp
// 发送（act 内）
shared_ptr<event> evt(new(nothrow) event());   // 默认构造 + 字段填充
evt->category       = "Config";                // 事件大类
evt->tag            = "Load";                  // 类内标签
evt->target_object  = module;                  // 目标模块名（路由文件 module 字段）
evt->config         = config_data;             // 配置 JSON 本体
event_terminal.send({ evt }, acl_key);         // 多事件重载发送（单元素 vector）
```

## 3. 模块内部架构

### 3.1 文件组织

```

├── 配置加载器.h            ← 类声明 + 成员变量（默认值）
```

- 头文件仅含声明；实现全部在 `core/配置加载器.cpp`（本版次"多编译单元拆分"风格：每个模块一个 core 子目录）。
- `配置加载器.cpp` 的 include：
  - `src/tools/Config_Loader/局部命名空间使用.h`（含 `配置加载器.h`，并注入 `using std::cout;`、`using std::ifstream;` 等简名）
  - `src/tools/Logging/日志系统.h`（Log 日志）
- `配置加载器.h` 的 include：
  - `common/前置头文件包含.h`（预编译头）
  - `src/core/event/事件系统运行包.h`（引入 `event` 结构 + `Event_Terminal` 类）
  - `src/tools/Engine_Env/引擎环境.h`（`Engine_Env::exe_dir_get()`）

- 该头文件把 cpp 中频繁使用的标准库符号**收窄为全局简名**（非 `using namespace` 式全量导入），减少 `std::` 前缀噪声，同时把依赖面显式文档化。

### 3.3 内部数据结构与流程状态

本模块**无实例数据缓存**（除 4 个成员变量），所有工作数据均为 `act()` 内局部变量：

| act() 局部变量 | 类型 | 用途 |
| --- | --- | --- |
| `route_config` | `json` | 当前路由文件的解析结果（应为数组） |
| `paths` | `vector<u8string>` | content_scan 输出的路由文件绝对路径集合 |
| `path_string` | `const u8string&` | 遍历 paths 的当前路由文件路径 |
| `read_path` | `path` | 路由文件路径转换后的 filesystem path |
| `route_data` | `const auto&`（json 元素） | 路由数组中的单条指令 |
| `module` | `std::string` | 指令的 `module` 字段（目标模块名） |
| `config_path` | `std::string` | 指令的 `config_path` 字段（相对路径，UTF-8） |
| `u8config_path` | `u8string` | config_path 转换后的 u8string |
| `absolute_config_path` | `path` | `base_dir / u8config_path` 拼接的绝对路径 |
| `config_data` | `json` | 目标配置文件解析结果 |
| `evt` | `shared_ptr<event>` | 构造的配置事件 |

### 3.4 事件协作结构

```
Config_Loader
├── event_terminal (Event_Terminal)
│     ├── acl_key        (optional<int64_t>，由 acl_key_gen 生成)
│     ├── key_generator  (Random_Generator，PCG32)
│     ├── event_set      (vector<shared_ptr<event>>)
│     └── terminal_interface (Terminal_Interface，转发函数注册表)
└── acl_key (int64_t，Config_Loader 自己的副本，发送时出示)
```

- `Event_Terminal::acl_key_gen()` 内部使用 `Random_Generator`（PCG32 随机数生成器）产生一个 `int64_t` 密钥。
- `send(events, acl_key)` 内部校验密钥并调用终端接口中已注册的事件发送函数（由 `Event_Broker` 注入），最终把事件投入事件中转器按 `category`/`tag` 分发。

## 4. 模块设计/实现细节

### 4.1 `act()` 完整流程（逐行级说明）

```
act()
│
├─[1] content_scan(paths)
│     构建扫描目录 = base_dir_get() / scan_content
│        = exe目录 / assets/config/route/
│     创建 recursive_directory_iterator（带 ec 不抛异常）
│     若迭代器创建失败 → error_out(ec) → 直接 return
│     遍历：it->is_regular_file(ec) 为真 → paths.push_back(it->path().u8string())
│           递增中/查询中的 ec 由 error_out 处理（输出并 continue）
│     （receiver 收到的都是绝对路径）
│
├─[2] 若 paths 为空
│     → Log::info("Config_Loader::未检测到任何路由文件") → return
│
├─[3] for each path_string in paths：            （遍历每个路由文件）
│   ├─[3.1] read_path = path_string
│   │        file_read(read_path, route_config)   （读路由文件 → JSON）
│   │
│   ├─[3.2] 若 route_config 非数组
│   │        → Log::info("当前路由文件内容格式非json数组") + "正在读取下一份配置文件" → continue
│   │
│   ├─[3.3] for each route_data in route_config：（遍历每条装载指令）
│   │   ├─[3.3.1] 字段存在性：!contains("module") || !contains("config_path")
│   │   │          → Log::info("未包含指定字段:") + "\"module\" and \"config_path\"" → continue
│   │   ├─[3.3.2] 类型检查：module/config_path 必须 is_string()
│   │   │          → 否则 Log::info("所需字段存储内容异常") + "非所需字符串格式" → continue
│   │   ├─[3.3.3] 空内容检查：module.empty() || config_path.empty()
│   │   │          → Log::info("所需字段无内容") → continue
│   │   ├─[3.3.4] module   = route_data["module"]        （std::string 取值）
│   │   │          config_path = route_data["config_path"]
│   │   │          u8config_path = u8string(config_path.begin(), config_path.end())
│   │   │          （std::string→std::u8string 逐字节转换，要求 UTF-8 编码）
│   │   │
│   │   ├─[3.3.5] skip_safety_inspect(u8config_path) 为 false
│   │   │          → Log::info("Config_Loader::存在恶意跳转") + "跳转路径: {}" → continue
│   │   │
│   │   ├─[3.3.6] absolute_config_path = base_dir_get() / u8config_path
│   │   │          file_read(absolute_config_path, config_data)
│   │   │
│   │   ├─[3.3.7] 若 config_data.is_null()
│   │   │          → Log::info("Config_Loader::配置读取失败") + "失败路径:{}" → continue
│   │   │          （file_read 失败时 receiver 被置为 json() = null）
│   │   │
│   │   ├─[3.3.8] evt = shared_ptr<event>(new(nothrow) event())
│   │   │          若 evt == nullptr → return（内存分配失败，整体中止）
│   │   │          evt->category = "Config"
│   │   │          evt->tag      = "Load"
│   │   │          evt->target_object = module
│   │   │          evt->config   = config_data
│   │   │
│   │   └─[3.3.9] event_terminal.send({evt}, acl_key)
│   │            失败（false）→ Log::info("Config_Loader::未注册事件中转站依赖")
│   │                          + "配置工作无法完成" → return（整体中止）
│   │            成功（true） → Log::info("Config_Loader::已发送配置事件: {}", module)
│   │
│   └─（继续下一条指令 / 下一个路由文件）
```

关键中止点（`return`）只有 3 处：
1. 扫描目录迭代器创建失败（[1]）——环境级故障。
2. `new(nothrow)` 分配事件失败（[3.3.8]）——内存级故障。
3. `send` 返回 false（[3.3.9]）——事件系统未就绪（未注册事件中转站依赖），后续所有配置都无法送达，继续循环无意义。

其余一切失败（路由文件非数组、字段缺失、类型错、空内容、路径越界、配置读取失败）都只影响**单条指令**，记录日志后继续——"部分成功"是可接受的装载语义。

### 4.2 `skip_safety_inspect` 安全检查详解

```cpp
bool Config_Loader::skip_safety_inspect(const u8string& config_path)
{
    path suspect_path = config_path;              // u8string → path（UTF-8 正确解析中文）

    if (suspect_path.begin() == suspect_path.end())   // ① 空路径
    { Log::info("路径无效"); return false; }

    auto it = suspect_path.begin();
    if (it->string() != "assets")                 // ② 第一段必须 assets
    { Log::info("路径跳出指定目录: \"assets\""); return false; }

    it++;
    if (it->string() != "config")                 // ③ 第二段必须 config
    { Log::info("路径跳出指定目录: \"assets/config\""); return false; }

    for (const auto& part : suspect_path)         // ④ 全路径不得含 ".."
        if (part.string() == "..")
        { Log::info("存在父目录返回符号"); return false; }

    error_code ec;
    suspect_path = base_dir_get() / suspect_path; // ⑤ 拼接基目录成绝对路径
    if (!exists(suspect_path, ec))                // ⑥ 必须存在
    { Log::info("访问路径不存在"); error_out(ec); return false; }
    if (!is_regular_file(suspect_path, ec))       // ⑦ 必须是普通文件
    { Log::info("访问路径不可读取"); error_out(ec); return false; }

    return true;                                  // ⑧ 全部通过
}
```

检查项对照表：

| 序号 | 检查 | 拒绝示例 | 目的 |
| --- | --- | --- | --- |
| ① | 路径可解析 | 空字符串 | 拦截空指令 |
| ② | 首段 == `assets` | `foo/bar.json`、`C:/x`（首段 `C:`）、`../x`（首段 `..`） | 限制于 assets 树下 |
| ③ | 次段 == `config` | `assets/other/x.json`、`assets/config2/x.json` | 限制于 assets/config 下 |
| ④ | 无 `..` 段 | `assets/config/../../secrets` | 防父目录跳转（即使前两段合法） |
| ⑤~⑦ | 拼接后存在且为普通文件 | 不存在 / 目录 / 符号链接到目录 | 保证可读 |

**边界与缺陷分析**：
- `allowed_root`（`assets/config/`）成员变量**未被 cpp 使用**——白名单根是硬编码在两段 `it->string()` 判断里的。若未来把白名单根改为 `assets/data/`，须同时改 cpp 与成员默认值，存在"改了一处漏一处"风险。
- 检查④ 的 `for` 遍历对象是**拼接前的相对路径**（`suspect_path` 尚未拼接基目录），`..` 检查作用于相对路径自身，正确。但若 `config_path` 本身就是绝对路径（如 `C:\...`），则①的 begin 迭代首段是 `C:` 或根，② 会拒绝（首段非 assets）——**绝对路径天然被拒**，这也是安全边界的一部分。
- Windows 分隔符：`path::begin()` 按平台分隔符切分，`assets/config/x.json` 中的 `/` 在 Windows 上同样正确切分（`std::filesystem` 接受 `/`）。但**检查②③用的是 `it->string()` 比较**——`string()` 返回窄字符本地编码（Windows 上是当前代码页，通常 GBK），比较对象 `"assets"`/`"config"` 是 ASCII，无编码问题；中文段落在比较时不受影响（不比较中文段）。真正的中文段落在 `exists`/`is_regular_file` 阶段由 u8string→path 的宽字符内部表示正确解析。
- `exists`/`is_regular_file` 带 `ec` 版本不抛异常；`ec` 非空时 `error_out` 输出并清空，之后返回 false。注意 `error_out` 输出到 **cout**（非 Log），与模块其余日志风格不一致（历史实现），重开发可统一。

### 4.3 `content_scan` 递归扫描细节

```cpp
void Config_Loader::content_scan(vector<u8string>& receiver)
{
    path actual_scan_dir = base_dir_get() / scan_content;
    error_code ec;
    auto it = recursive_directory_iterator(actual_scan_dir, ec);
    if (error_out(ec))      // 目录不存在/无权限 → 输出错误并中止本次扫描
        return;

    for (; it != recursive_directory_iterator(); it.increment(ec))
    {
        if (error_out(ec))  // 递增中出错 → 跳过当前项
            continue;
        if (it->is_regular_file(ec))
            receiver.push_back(it->path().u8string());
        if (error_out(ec))  // 查询属性出错 → 跳过（该文件未入列）
            continue;
    }
}
```

| 项 | 说明 |
| --- | --- |
| 递归性 | `recursive_directory_iterator` 深度优先递归子目录；默认不跟随符号链接目录（防循环） |
| 错误策略 | 迭代器构造失败（目录不存在）→ 整体 return；遍历中错误 → 跳过该项继续。`error_out` 的 true/false 返回值用于区分"有无错误" |
| 收集内容 | 全部普通文件（含非 JSON 文件！）。**重要**：`content_scan` 不做扩展名过滤，路由目录里任何普通文件都会被当作路由文件尝试解析；非 JSON 内容在 `file_read` 时 parse_error 被捕获，记日志后跳过 |
| 路径形式 | `it->path().u8string()` 得到**绝对路径**（迭代器路径 = 传入路径 + 相对段），以 UTF-8 字符串入列 |
| 未列出的行为 | 目录、符号链接、设备文件不入列（`is_regular_file` 过滤） |

### 4.4 `file_read` 读取与异常处理

```cpp
void Config_Loader::file_read(const path& file_path, json& receiver)
{
    try
    {
        ifstream file(file_path);
        if (!file.is_open())                      // 打开失败
        { Log::info("Config_Loader::文件打开失败"); receiver = json(); return; }
        file >> receiver;                          // 流解析 JSON
    }
    catch (const json::parse_error& e)             // 语法错误
    { Log::info("Config_Loader::文件格式非法"); receiver = json(); }
    catch (const std::exception& e)                // 其他异常
    {
        Log::info("Config_Loader::未知错误:");
        Log::info("错误路径如下: {}", file_path.string());
        Log::info("错误信息如下: {}", e.what());
        receiver = json();
    }
}
```

| 项 | 说明 |
| --- | --- |
| 打开方式 | `ifstream file(file_path)`：path 直接构造流。Windows 下 path 内部宽字符 → 正确打开中文路径文件 |
| 解析方式 | `file >> receiver`：nlohmann 的流提取运算符；遇语法错误抛 `json::parse_error` |
| 失败哨兵 | **所有失败路径都把 receiver 置为 `json()`（即 JSON null）**。调用方（act 的 [3.3.7]）以 `config_data.is_null()` 判定读取失败。**陷阱**：合法配置内容恰好为 JSON null（文件内容只有 `null`）也会被误判为失败——工程上配置不会写成 null，可接受 |
| 异常捕获面 | `parse_error` 专门处理；`std::exception` 兜底（含 `bad_alloc` 等）。`ifstream` 打开失败走 is_open 分支（不抛异常） |
| 日志 | 失败时输出"文件打开失败"/"文件格式非法"/"未知错误 + 路径 + what()"三种级别信息 |
| 与 Data_Validator 的关系 | 本模块**未调用** `Data_Validator::path_check`（路径可用性检查内置于 `skip_safety_inspect`），校验职责由自身完成；两个模块的路径处理逻辑相似但独立演进（历史重复实现） |

### 4.5 事件发送与权限机制

```cpp
// 构造事件
shared_ptr<event> evt(new(nothrow) event());
if (evt == nullptr) return;
evt->category      = "Config";
evt->tag           = "Load";
evt->target_object = module;
evt->config        = config_data;

// 发送
if (!event_terminal.send({ evt }, acl_key))
{
    Log::info("Config_Loader::未注册事件中转站依赖");
    Log::info("配置工作无法完成");
    return;
}
else
    Log::info("Config_Loader::已发送配置事件: {}", module);
```

| 项 | 说明 |
| --- | --- |
| 事件字段 | `category="Config"`（事件大类）、`tag="Load"`（装载标签）、`target_object=module`（路由指定的目标模块）、`config=配置JSON`。**sender_object 未设置**（默认空串）——事件系统按 target 分发 |
| 事件标识语义 | 订阅方通过 `needed_events` 向量声明关心的 `event`（比较 category/tag/target/config）。`Config/Load` 是被订阅方识别的"配置装载"信号 |
| 权限密钥 | `acl_key` 在构造时生成一次，send 时出示；Event_Terminal 校验通过后调用已注册的发送函数。密钥机制防止"未 attach 的模块"冒充发送方 |
| 失败语义 | send 返回 false 表示事件中转站（Event_Broker）未接入终端（未注册发送回调）——配置工作无法完成，**整体中止**（后续模块配置即使可读也不再发送） |
| 内存 | 事件以 `shared_ptr` 传递；`new(nothrow)` 失败返回 nullptr → 直接 return（无日志——分配失败时日志系统也可能不可用，属合理保守） |

### 4.6 中文路径全链路（u8string 流）

```
路由文件中的 config_path（JSON 字符串，UTF-8）
  → std::string config_path                       （UTF-8 字节串）
  → std::u8string u8config_path(begin, end)        （逐字节转 u8string）
  → skip_safety_inspect：path suspect = u8config_path  （u8string→path，UTF-8 语义解析）
  → base_dir / u8config_path                        （拼接绝对路径）
  → ifstream file(绝对路径)                         （Windows 宽字符打开，中文 OK）
```

- 关键点：**绝不**直接用 `std::string` 构造 `std::filesystem::path`（那会走本地代码页，Windows 下 GBK 与 UTF-8 不一致导致中文路径乱码）。全程经 u8string 中转，保证 UTF-8 → 宽字符的正确转换。
- `content_scan` 输出的路径已经是 u8string（`it->path().u8string()`），回读时 `path read_path = path_string;` 从 u8string 构造 path，同样正确。

### 4.7 设计决策与理由

| 决策 | 理由 |
| --- | --- |
| 路由文件驱动（不硬编码模块-配置映射） | 配置装载清单外置，新增模块配置只需新增路由条目，不重编译 |
| 相对路径 + 基目录拼接 | 配置与可执行文件同目录部署（`exe_dir`），便于整包拷贝迁移 |
| 事件分发而非直接回调 | 模块与配置源解耦：模块只声明"我要 Config 事件"，不知配置从哪来；Config_Loader 只发事件，不知模块内部结构 |
| 部分失败容忍 | 单条指令失败不影响整体装载，保证"能装的尽量装" |
| 全程不抛异常（文件系统用 ec 重载） | 装载流程健壮性优先，异常只在 file_read 内局部捕获 |
| allowed_root 声明但未用 | 历史遗留：可能是为"白名单可配置化"预留；当前是硬编码 assets/config |
| error_out 走 cout 而非 Log | 历史实现差异（与 Data_Validator 的 error_out 走 Log 不同），无功能性影响 |

### 4.8 易踩坑点汇总

1. **路由文件必须是 JSON 数组**：顶层是对象或标量会被拒绝（"内容格式非json数组"）。
2. **content_scan 不过滤扩展名**：路由目录内任何普通文件都被当路由文件解析，注意不要放杂文件（解析失败会有日志噪音，但不致命）。
3. **config_path 不能以 `/` 或 `C:` 开头**：绝对路径在安全检查 ② 段直接被拒；必须写相对路径 `assets/config/xxx.json`。
4. **config_path 前两段必须是 assets/config**：这是硬编码约束，与 `allowed_root` 成员（未使用）语义需保持一致。
5. **`..` 会被拒绝**：即使前两段合法（`assets/config/../../evil` 也被拦）。
6. **JSON null 配置文件被判读取失败**：`file_read` 失败哨兵是 null，若配置文件合法内容就是 null 会被误判。
7. **send 失败会中止整个流程**：事件中转站未接入时，后面所有路由文件/指令都不再处理。
8. **中文路径必须 UTF-8**：路由文件本身必须是 UTF-8 编码（含 BOM 可能影响 nlohmann 解析首字符，建议无 BOM），config_path 字段中文须 UTF-8。
9. **`scan_content` 末尾斜杠**：`u8"assets/config/route/"` 带尾斜杠，拼接时 `path / u8string` 会自动处理分隔符，尾斜杠无实际影响但保持默认值不变更稳妥。
10. **error_out 输出到 cout**：与模块其他 Log 输出不在同一流，排查日志时注意两处都可能出现错误信息。

## 5. 模块运行链路

### 5.1 完整调用时序（启动阶段装载配置）

```
[启动] 主程序
  │
  ├─ 创建 Config_Loader loader;
  │    └─ 构造函数：acl_key = event_terminal.acl_key_gen()   （PCG32 生成密钥）
  │
  ├─ 各业务模块注册订阅（事件系统侧）：
  │    module.event_terminal.attach(module_name, needed_events, handler)
  │    └─ Event_Broker.info_register(...) → 记录 module 对 "Config/Load" 的兴趣
  │
  ├─ loader.act()
  │    ├─ 1. content_scan：扫描 exe/assets/config/route/ 全部普通文件
  │    ├─ 2. 空目录检查（空则返回）
  │    ├─ 3. 循环每个路由文件：
  │    │     ├─ file_read → route_config
  │    │     ├─ 数组校验（非数组 → 跳过）
  │    │     └─ 循环每条指令：
  │    │           ├─ 字段/类型/空值校验
  │    │           ├─ skip_safety_inspect（越界 → 跳过该条）
  │    │           ├─ file_read → config_data（失败 → 跳过该条）
  │    │           ├─ 构造 event{Config, Load, module, config_data}
  │    │           └─ event_terminal.send({evt}, acl_key)
  │    │                 └─ Event_Terminal 校验密钥 → 调用已注册发送回调
  │    │                       └─ Event_Broker.process → 按 target/category/tag 分发
  │    │                             └─ 目标模块 handler(evt)  → 消费 config
  │    └─ 全部指令处理完 → act() 返回
  │
  └─ 后续正常游戏循环（配置已就位）
```

### 5.2 模块协作关系图

```
                    ┌─────────────────────┐
                    │      Engine_Env     │
                    │  exe_dir_get()      │
                    └──────────┬──────────┘
                               │ 基目录
                               ▼
┌──────────────────────────────────────────────────┐
│                  Config_Loader                    │
│   content_scan ──► skip_safety_inspect ──► file_read│
│                        │              │          │
│                        │ 安全通过      │ JSON     │
│                        ▼              ▼          │
│              event{Config,Load}──►send(acl_key)  │
└────────────────────────────────────┬─────────────┘
                                     │ 事件
                                     ▼
┌──────────────────────────────────────────────────┐
│              Event_Terminal / Event_Broker        │
│   acl 校验 → 按 target/category/tag 分发           │
└────────────────────────────────────┬─────────────┘
                                     │
                                     ▼
                 目标模块订阅入口（handler）→ 消费 config
```

| 协作对象 | 依赖方向 | 协作内容 |
| --- | --- | --- |
| `Engine_Env` | Config_Loader → Engine_Env | 获取 exe 目录作为所有相对路径的基目录 |
| `Event_Terminal` | Config_Loader → Event_Terminal | `acl_key_gen()` 生成密钥、`send()` 发送事件；`event_terminal` 为公开成员供外部接入 |
| `Event_Broker`（经终端） | Config_Loader →（间接） | 事件中转：向订阅模块分发 Config/Load |
| `Log` | Config_Loader → Log | 全流程日志（信息/警告） |
| 目标业务模块（如 Entity_Manager） | 业务模块 ← Config_Loader | 通过事件接收配置 JSON |
| `Data_Validator` | 无直接调用 | 路径/字段校验逻辑重复实现（历史），语义互补不协作 |

### 5.3 异常与失败链路

| 失败点 | 处理 | 影响范围 |
| --- | --- | --- |
| 路由目录不存在/不可访问 | content_scan 迭代器构造错误 → error_out → return | 整体中止（无路由可扫） |
| 路由文件非 JSON / 语法错误 | file_read parse_error → receiver=null → 非数组检查拦截 | 跳过该路由文件 |
| 指令缺字段/类型错/空值 | 三段校验拦截 | 跳过该条指令 |
| 路径越界（非 assets/config、含 `..`） | skip_safety_inspect 拦截 | 跳过该条指令 |
| 目标配置文件不存在/解析失败 | file_read → null → is_null 拦截 | 跳过该条指令 |
| 事件分配失败（OOM） | new(nothrow) 返回 nullptr → return | 整体中止 |
| 事件发送失败（中转站未注册） | send 返回 false → return | 整体中止 |
