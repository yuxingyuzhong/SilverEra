## 一、模块功能（该模块做什么，解决什么问题，在引擎中的定位）

### 1.1 模块定位

事件系统（Event System）是「白银纪元」游戏引擎引擎层（`engine` 命名空间）的**核心通信基础设施**。它位于 `引擎层\src\core\event\` 目录下，为引擎内部各模块（如碰撞模块 Collision_Proxy、配置加载模块 Config_Loader、以及未来接入的渲染、逻辑、音频等模块）提供一套**基于订阅-发布（Publish-Subscribe）模式的解耦通信机制**。

在引擎的分层结构中，事件系统属于 `core`（核心层）的组成部分，其依赖方向遵循"核心层可依赖工具层、不可依赖业务模块"的原则：

- **上游依赖（被事件系统依赖）**：工具层（`src\tools\`）的随机数生成器（用于权限密钥生成）、日志系统（用于告警/错误输出）、nlohmann::json（用于事件载荷 config 字段）、标准库容器与智能指针。
- **下游消费方（依赖事件系统）**：碰撞模块的 `Collision_Proxy`（订阅/发布碰撞相关事件）、配置加载模块 `Config_Loader`（发布 Config/Load 事件）、以及引擎中任何需要跨模块通信的组件。

### 1.2 解决的核心问题

在没有事件系统的情况下，模块间直接调用会产生以下问题：

1. **强耦合**：模块 A 要通知模块 B，必须持有 B 的实例指针或接口引用，导致模块间依赖关系错综复杂、难以独立测试与替换。
2. **扩展困难**：新增一个关心某类消息的模块时，需要改动所有消息发送方。
3. **时序脆弱**：模块初始化顺序一旦变化，直接调用就可能踩空指针。
4. **权限失控**：任何组件都可以随意调用任意模块的接口，缺乏"谁有资格向中转站发事件/读事件"的约束。

事件系统通过三层设计解决上述问题：

- **`event`（事件结构体）**：定义事件的数据载体，包含发起者、目标、大类、标签、载荷五个维度，并配套 `std::hash` 特化以支持哈希容器使用。
- **`Event_Terminal`（事件终端）**：每个模块持有的事件出口/入口对象。终端封装了"生成事件、发送事件、接收事件、查阅事件、清空事件"等操作，并以 **ACL 密钥（acl_key）** 机制保证只有持钥者能操作终端，实现模块级权限隔离。终端还内嵌一个 `Terminal_Interface`（终端接口）注册表，用于把终端操作挂钩到具体的"回调函数通道"（即中转站接入入口、发送入口、接收入口、交互入口）。
- **`Event_Broker`（事件中转器）**：全局的订阅-发布中心。维护"模块名 → 订阅者编号"映射（`mapping_set`）、"事件大类 → 事件标签 → 订阅者编号集合"的权限表（`acl_set`）、"订阅者编号 → 事件入口回调"的转发表（`event_entries`）。当 `Event_Terminal::send` 触发时，事件经中转器按订阅关系分发给所有订阅者；`Event_Terminal::receive` 则是从中转器接收被分发下来的事件。

### 1.3 与其他核心模块的协同

- **配置加载（Config_Loader）**：`Config_Loader` 构造时调用 `event_terminal.acl_key_gen()` 获得密钥；`act()` 中扫描路由文件后，构造 `category="Config"`、`tag="Load"`、`target_object=模块名` 的事件，通过 `event_terminal.send({evt}, acl_key)` 将配置事件发布到中转器，从而把配置文件内容投递给对应模块。
- **碰撞模块（Collision_Proxy）**：`Collision_Proxy::attach()` 先检查 `ATTACH_HANDLER` 接口是否已注册，然后注册自己的事件接收入口（`event_receiver_register`），列出 11 个待订阅事件（Config/Load 与 Collision 大类下的 10 个标签），最后调用 `event_terminal.attach(module_name, needed_events, acl_key)` 接入中转站；其内部 `event_process` 根据事件的 `category/tag` 分派到具体的碰撞空间/碰撞体操作；`event_publish` 则通过 `event_terminal.build(...)` + `event_terminal.send(...)` 发布结果事件（如 ColliderBuildResult）。

### 1.4 设计要点总览（本版次 089b070）

1. **权限模型**：`Event_Terminal` 维护 `std::optional<int64_t> acl_key`。**密钥未生成即锁定**——所有需要密钥的公开操作（attach/interact/send/query/clear）在 `acl_key` 无值时统一打印告警并拒绝执行（返回 false / nullptr）。密钥只能生成一次（重复生成返回 0 表示"已存在"），且必须由事件中转站的所有者/模块自持，作为调用凭据。
2. **接口注册表**：`Terminal_Interface` 用 `std::vector<interface_ID> map` 记录已注册接口 ID，用一组 `std::unique_ptr<std::function<...>>` 持有实际回调；公开的 `*_register` 方法统一走 `function_register` 模板完成"分配内存 → 写入回调 → 记录 ID"三步。
3. **订阅语义**：`Event_Broker::info_register` 中，每个 `event_acl` 行首（`tag` 为空）是"该大类全订阅"标记，其后为具体标签的订阅行；`receive` 分发时先收集"全订阅者 + 标签匹配订阅者"，再排除事件发起者本人，避免自己给自己回环。
4. **定向与广播**：`receive` 中若 `target_object` 非空且存在于 `mapping_set`，则定向投递到该模块；否则按 acl 表广播。
5. **应答协议**：`process` 仅处理 `category=="Subscriber"` 且 `tag=="Check"/"Call"` 的事件，返回一个 `Subscriber/Response` 应答事件；`Call` 会额外将原事件转发给目标模块。

> 说明：以下接口签名全部摘自 089b070 版次源码（`引擎层\src\core\event\` 目录），方法名、参数类型、返回值、const 修饰与源码严格一致。参数名仅作语义说明。

### 2.1 `event` 结构体（`Event\事件.h`）

`engine::event` 是一个 POD 风格的数据结构，承载事件的全部信息。成员与构造函数如下：

```cpp
//游戏引擎命名空间
namespace engine
{
    //事件
    struct event
    {
        //默认构造函数
        event()
        {
        }
        //含参构造函数 —— 构造事件标签
        event(const std::string& category, const std::string& tag)
        {
            this->category = category;
            this->tag = tag;
        }

        //含参构造函数 —— 构造对象标签
        event(const std::string& sender_object, const std::string& target_object,
            const std::string& category, const std::string& tag)
        {
            this->sender_object = sender_object;
            this->target_object = target_object;
            this->category = category;
            this->tag = tag;
        }

        //含参构造函数 —— 全量构造
        event(const std::string& sender_object,const std::string& target_object,
            const std::string& category,const std::string& tag,
            const nlohmann::json& config)
        {
            this->sender_object = sender_object;
            this->target_object = target_object;
            this->category = category;
            this->tag = tag;
            this->config = config;
        }

        //默认析构函数
        ~event()
        {
        }

        //事件发起者
        std::string sender_object{};
        //事件目标
        std::string target_object{};
        //事件大类
        std::string category;
        //类内标签
        std::string tag;
        //配置包
        nlohmann::json config;

        //使用默认等于运算符
        bool operator==(const event& other) const
        {
            if (this->category == other.category &&
                this->tag == other.tag &&
                this->target_object == other.target_object &&
                this->config == other.config)
                return true;
            else
                return false;
        }
    };
```

#### 2.1.1 成员字段语义

| 字段 | 类型 | 默认值 | 语义 |
| --- | --- | --- | --- |
| `sender_object` | `std::string` | `{}`（空串） | 事件发起者（模块名）。`Event_Broker::receive` 用它排除发起者自身；`process` 要求它非空，否则事件无法处理。 |
| `target_object` | `std::string` | `{}`（空串） | 事件目标（模块名）。非空且目标存在时触发定向投递；`process` 要求它非空。 |
| `category` | `std::string` | 空串 | 事件大类（如 `"Config"`、`"Collision"`、`"Subscriber"`）。空串会导致 `receive` 直接丢弃、`info_register` 跳过订阅。 |
| `tag` | `std::string` | 空串 | 类内标签（如 `"Load"`、`"RegionBuild"`）。空串会导致 `receive` 直接丢弃。 |
| `config` | `nlohmann::json` | 默认 json | 事件载荷/配置包。承载业务数据（如配置内容、region 名、collider_ID、active 标志、object_existence 等）。 |

#### 2.1.2 构造函数语义

- **`event()`**：全默认构造，四个字符串字段与 config 均保持默认值。`Config_Loader` 用它构造事件后再逐字段填充。
- **`event(const std::string& category, const std::string& tag)`**：仅填充大类与标签，常用于声明"待订阅事件清单"（如 `Collision_Proxy::attach` 中的 `needed_events` 列表：`event("", "", "Config", "Load")` 使用四参构造，但这里两参构造适用于不关心发起者/目标、只关心订阅模式的声明场景）。
- **`event(sender_object, target_object, category, tag)`**：填充发起者、目标、大类、标签四个维度。
- **`event(sender_object, target_object, category, tag, config)`**：全量构造，额外填充载荷。

#### 2.1.3 相等运算符语义（重要）

`operator==` 的判等维度是：**category + tag + target_object + config**。注意两点：

1. **不比较 `sender_object`**：即两个事件的发起者不同，但只要大类、标签、目标、载荷相同，就视为相等。这一设计配合 `std::hash` 使用（见 2.1.4），使哈希与相等语义对齐。
2. **比较 `config`（json 对象）**：`nlohmann::json` 的 `==` 是**结构化比较**，即键值完全一致才相等，与 json 的序列化顺序无关（对象内部按键排序比较）。因此 json 对象 `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 相等。

#### 2.1.4 `std::hash<engine::event>` 特化

`事件.h` 在 `namespace std` 内特化了 `hash<engine::event>`，使 `event` 可以放入 `std::unordered_map` / `std::unordered_set`：

```cpp
namespace std
{
    template<>
    struct hash<engine::event>
    {
        size_t operator()(const engine::event& evt) const noexcept
        {
            std::hash<std::string> str_hasher;
            size_t seed = 0;

            // 1. 哈希基类成员（与 event 一致）
            seed = str_hasher(evt.category);
            engine::detail::hash_combine(seed, str_hasher(evt.tag));
            engine::detail::hash_combine(seed, str_hasher(evt.target_object));

            // 2. 哈希派生类成员 config（将 json 转为字符串再哈希）
            //    注意：dump() 可能抛出异常，但 noexcept 标记要求不抛，这里假设不会。
            //    若担心，可以捕获异常并返回一个默认值（但会破坏一致性）。
            std::string config_str = evt.config.dump();
            engine::detail::hash_combine(seed, str_hasher(config_str));

            return seed;
        }
    };
}
```

哈希组合工具位于 `engine::detail` 命名空间：

```cpp
    // 哈希组合工具
    namespace detail
    {
        inline void hash_combine(size_t& seed, size_t val) noexcept {
            seed ^= val + 0x9e3779b9 + (seed << 6) + (seed >> 2);
        }
    }
```

细节分析：

- 哈希维度与 `operator==` 严格一致：category、tag、target_object、config（字符串化）。这与"相等对象必须同哈希"的容器要求一致。注意 `sender_object` 同样**不参与哈希**。
- `config` 通过 `evt.config.dump()` 转成紧凑 JSON 字符串后再哈希。**注意 `dump()` 对浮点数、键顺序的序列化确定性**：`nlohmann::json` 的 `dump()` 对同一个 json 值总是输出相同字符串（对象按键的字典序），因此相同 json 哈希一致；但不同"数值表示"（如整数 `1` 与浮点 `1.0`）在 dump 后字符串不同、判等也不等，行为自洽。
- **潜在风险（源码注释已标注）**：`operator()` 被声明为 `noexcept`，但 `config.dump()` 在极端情况下（如深度嵌套导致栈溢出或内存不足）可能抛异常。若抛出，将直接触发 `std::terminate`。源码注释说明"这里假设不会"。
- `hash_combine` 使用黄金比例常数 `0x9e3779b9`（即 2^32 的黄金分割近似值），是一种广为使用的组合散列手法，可有效降低不同输入组合的碰撞概率。

#### 2.1.5 使用前提与注意事项

- `event` 不管理任何资源（纯数据），可安全拷贝、移动、放进容器、用 `shared_ptr` 管理。
- 引擎内事件**一律以 `std::shared_ptr<event>` 形式流转**（`Event_Terminal::build` 返回 `shared_ptr<event>`，`send/receive/process` 均以 `shared_ptr<event>` 为参数），保证多个订阅者共享同一事件对象、避免拷贝开销。

#### 2.2.1 `acl_key_gen` —— 权限密钥生成

- **签名**：`int64_t acl_key_gen(void);`
- **参数**：无。
- **返回值**：
  - 首次调用且成功生成：返回生成的非零密钥（`int64_t`）。
  - 重复调用（密钥已存在）：返回 `0`，表示"密钥已生成，拒绝再次生成"。
- **行为**：若当前 `acl_key` 无值，则进入无限循环调用 `key_generator()`（`Random_Generator` 的函数调用运算符，生成全范围 int64 随机数），直到生成的数不为 0 才返回。这是因为 0 被用作"无效/未授权"哨兵值，不允许把 0 当作真实密钥。
- **调用前提**：任何需要操作终端的模块，构造时必须先调用本方法取得密钥并妥善保存（如 `Config_Loader` 构造函数中的 `this->acl_key = event_terminal.acl_key_gen();`）。
- **注意事项**：
  - 密钥一旦生成不可变更、不可重置（`Event_Terminal` 无公开的密钥重置接口）。
  - 由于采用 `std::optional<int64_t>`，默认构造的终端（未调用 `acl_key_gen`）处于"未生成密钥"状态，此时**所有受保护操作全部锁定**（见 2.2.2 起各接口的"密钥未生成"分支）。
  - `Random_Generator` 默认构造函数内部通过 `pcg32_seed_init()` 用"高精度时钟纳秒 ^ 系统时间 ^ 计数器"混合作种子，因此每次运行/每个终端生成的密钥序列不同，防猜测性较好。

#### 2.2.2 `attach` —— 中转站接入

- **签名**：`bool attach(const std::string& module_name, const std::vector<event>& needed_events, const int64_t& acl_key);`
- **参数**：
  - `module_name`：本模块在事件系统中的注册名（订阅者名），需与中转站 `mapping_set` 中登记的名字一致（`info_register` 传入同一名字）。例如 `Collision_Proxy::attach` 传入其成员 `module_name`。
  - `needed_events`：本模块声明需要订阅的事件清单（用 `event` 对象描述 category/tag 组合；发起者、目标通常留空）。
  - `acl_key`：调用者持有的权限密钥。
- **返回值**：`bool`。密钥未生成 → `false`（并打印 `Log::warn("Event_Terminal::密钥未生成\n功能已锁定")`）；密钥不匹配 → `false`；接入成功 → `true`。
- **行为流程**：
  1. 密钥检查（未生成 → 告警并返回 false）。
  2. 密钥比对（`this->acl_key != acl_key` → 返回 false）。
  3. 取 `terminal_interface` 引用简化访问。
  4. 若单事件接收入口 `event_receiver` 尚未注册，则用 lambda 包装 `this->receive(evt)` 作为接收入口；否则直接使用已注册的 `*Tinterface.event_receiver`。
  5. 调用 `(*Tinterface.attach_handler)(module_name, needed_events, it)` 完成实际接入——**attach_handler 必须已通过 `attach_handler_register` 注册**，其内部应当调用 `Event_Broker::info_register`（由中转站持有者负责注册此入口，例如碰撞模块所属的引擎初始化代码）。
- **调用前提**：
  - `attach_handler` 已注册（`interface_check(interface_ID::ATTACH_HANDLER)` 为真）；`Collision_Proxy::attach` 在接入前会显式检查此前提并输出 `Log::error`。
  - 已通过 `acl_key_gen()` 取得密钥。
- **关键实现代码**：

```cpp
	//中转站接入
	bool Event_Terminal::attach(const string& module_name, const vector<event>& needed_events,
		const int64_t& acl_key)
	{
		//若当前尚未生成密钥
		if (!this->acl_key.has_value())
		{
			Log::warn("Event_Terminal::密钥未生成\n功能已锁定");
			return false;
		}
		//若密钥权限未匹配
		if (this->acl_key != acl_key)
			return false;

		//简化表示路径
		auto& Tinterface = terminal_interface;

		//若未注册单事件接收入口
		if(!Tinterface.event_receiver)
		{
			//包装单事件接收入口
			auto it = [this](shared_ptr<event> evt) -> void
				{
					this->receive(evt);
				};
			//接入中转站
			(*Tinterface.attach_handler)(module_name, needed_events, it);
		}
		else
		    //接入中转站
		    (*Tinterface.attach_handler)(module_name, needed_events, *Tinterface.event_receiver);
		//返回接入成功
		return true;
	}
```

- **设计意图**：`attach` 是模块与中转站之间的"接线"操作。模块声明"我需要哪些事件"，中转站据此建立订阅关系。**注意：`attach` 本身不调用中转站的任何方法，真正完成订阅注册的是 `attach_handler` 所指向的回调（典型实现为 `Event_Broker::info_register`）**。这种间接设计使 `Event_Terminal` 不直接依赖 `Event_Broker` 类型，两个模块解耦，仅通过 `std::function` 回调桥接。

#### 2.2.3 `interact` —— 中转站交互（两处重载）

- **签名**：
  - `bool interact(std::shared_ptr<event> evt, const int64_t& acl_key);`（单事件）
  - `bool interact(std::vector<std::shared_ptr<event>> events, const int64_t& acl_key);`（多事件）
- **参数**：待处理事件（或事件集合）+ 权限密钥。
- **返回值**：`bool`。密钥未生成 → `false`（告警）；密钥不匹配 → `false`；对应交互接口未注册 → `false`；成功调用 → `true`。
- **行为**：
  - 单事件重载：密钥校验通过后，`interface_check(EVENT_INTERACTOR)` 为真则执行 `(*event_interactor)(evt)` 并返回 true，否则 false。
  - 多事件重载：优先使用 `EVENTS_INTERACTOR`（多事件交互入口，一次性传递整个 vector）；若未注册多事件入口但注册了单事件入口 `EVENT_INTERACTOR`，则退化为**逐事件循环调用**单事件入口；两者都未注册则返回 false。
- **调用前提**：交互入口需由中转站持有者通过 `event_interactor_register` / `events_interactor_register` 注册（通常指向 `Event_Broker::receive` 的对应重载）。
- **实现代码要点**（多事件重载的退化逻辑）：

```cpp
	//中转站交互 —— 多事件重载
	bool Event_Terminal::interact(std::vector<std::shared_ptr<event>> events, const int64_t& acl_key)
	{
		//若当前尚未生成密钥
		if (!this->acl_key.has_value())
		{
			Log::warn("Event_Terminal::密钥未生成\n功能已锁定");
			return false;
		}
		//若权限密钥匹配
		if (this->acl_key == acl_key)
		{
			//若已注册多事件交互接口
			if (terminal_interface.interface_check(interface_ID::EVENTS_INTERACTOR))
			{
				(*terminal_interface.events_interactor)(events);
				return true;
			}
			//若已注册单事件交互接口则返回
			else if (terminal_interface.interface_check(interface_ID::EVENT_INTERACTOR))
			{
				//分多次发送事件
				for (auto& evt : events)
					(*terminal_interface.event_interactor)(evt);
				return true;
			}
			else
				return false;
		}
		else
			return false;
	}
```

#### 2.2.4 `build` —— 事件构造（三处重载）

- **签名**：
  - `std::shared_ptr<event> build(void);`
  - `std::shared_ptr<event> build(const std::string& category, const std::string& tag);`
  - `std::shared_ptr<event> build(const std::string& sender_object, const std::string& target_object, const std::string& category, const std::string& tag);`
- **参数**：与 `event` 构造函数对应（无参 / 大类+标签 / 发起者+目标+大类+标签）。
- **返回值**：`std::shared_ptr<event>`，使用 `new(nothrow)` 分配，**分配失败返回空指针**（`shared_ptr<event>(new(nothrow)event(...))` 在 `new` 返回 nullptr 时得到空 shared_ptr）。
- **行为**：分别调用 `event()`、`event(category, tag)`、`event(sender_object, target_object, category, tag)` 构造后包装为 shared_ptr。
- **调用前提**：无（build 不需要密钥，属于"纯构造"接口）。
- **注意事项**：调用方必须检查返回值是否为空（`Collision_Proxy::event_publish` 中 `if (!evt)` 即为此检查）；`Config_Loader` 未走 build，而是直接 `new(nothrow) event()` 并逐字段填充。
- **实现代码**：

```cpp
	//事件构造
	shared_ptr<event> Event_Terminal::build(void)
	{
		return shared_ptr<event> (new(nothrow)event());
	}

	//事件构造
	shared_ptr<event> Event_Terminal::build(const string& category, const string& tag)
	{
		return shared_ptr<event>(new(nothrow)event(category,tag));
	}

	//事件构造
	shared_ptr<event> Event_Terminal::build(const string& sender_object, const string& target_object,
		const string& category, const string& tag)
	{
		return shared_ptr<event>(new(nothrow)event(sender_object,target_object,category,tag));
	}
```

#### 2.2.5 `send` —— 事件发送（两处重载）

- **签名**：
  - `bool send(std::shared_ptr<event> evt, const int64_t& acl_key);`（单事件）
  - `bool send(std::vector<std::shared_ptr<event>> events, const int64_t& acl_key);`（多事件）
- **参数**：待发送事件（或事件集合）+ 权限密钥。
- **返回值**：`bool`。密钥未生成 → `false`（告警）；密钥不匹配 → `false`；对应发送入口（`event_sender` / `events_sender`）未激活 → `false`；成功 → `true`。
- **行为**：密钥校验通过后，若对应发送入口已注册（`terminal_interface.event_sender` / `events_sender` 非空），则调用 `(*event_sender)(evt)` 或 `(*events_sender)(events)` 并返回 true。
- **调用前提**：发送入口已由中转站持有者注册（通常指向 `Event_Broker::receive`）；模块已取得密钥。`Config_Loader::act` 与 `Collision_Proxy::event_publish` 均依赖此接口发送事件。
- **关键语义**：`send` 是"**把事件交给中转站**"的动作。发送入口（`event_sender`）与中转站的 `receive` 绑定后，事件便进入 `Event_Broker` 的分发流程（详见第五章运行链路）。**`send` 不保证事件一定被某个模块消费**——如果没有任何模块订阅该事件的 category/tag，事件会被 `Event_Broker::receive` 静默忽略。
- **实现代码**（单事件重载）：

```cpp
	//事件发送 —— 单事件重载
	bool Event_Terminal::send(shared_ptr<event> evt, const int64_t& acl_key)
	{
		//若当前尚未生成密钥
		if (!this->acl_key.has_value())
		{
			Log::warn("Event_Terminal::密钥未生成\n功能已锁定");
			return false;
		}
		//若权限密钥匹配
		if (this->acl_key == acl_key)
		{
			//若事件发送入口已激活
			if (terminal_interface.event_sender)
			{
				//发送事件
				(*terminal_interface.event_sender)(evt);
				//返回发送成功
				return true;
			}
			else
				return false;
		}
		//若密钥不匹配则发送失败
		else
			return false;
	}
```

#### 2.2.6 `receive` —— 事件接收（两处重载，无需密钥）

- **签名**：
  - `void receive(std::shared_ptr<event> evt);`（单事件）
  - `void receive(std::vector<std::shared_ptr<event>> events);`（多事件）
- **参数**：从中转站分发下来的事件（或事件集合）。
- **返回值**：`void`（无返回值——这是**回调型接口**，由中转站分发给本终端时被调用）。
- **行为**：
  - 若 `event_receiver`（单事件接收入口）已额外注册：调用 `(*event_receiver)(evt)`，**不再放入本地 `event_set`**。
  - 若未注册：走"原生通道"，将事件 `push_back` 进本地 `event_set`。
  - 多事件重载同理：已注册 `events_receiver` 则整体转发；否则 `event_set.insert(event_set.end(), events.begin(), events.end())` 批量追加。
- **调用前提**：无密钥要求。该接口被 `Event_Broker` 分发时经由 `event_entries[订阅者ID]` 调用（`attach` 中包装的 `this->receive(evt)` lambda 正是这个通道）。
- **设计意图**：`receive` 是模块的"事件落地口"。默认情况下事件进入终端的 `event_set` 队列，模块可用 `query` 查阅、`clear` 清空；若模块希望"事件一到就立刻处理"，可通过 `event_receiver_register` 注册处理回调（如 `Collision_Proxy::event_receiver_register([this](shared_ptr<event> evt){ this->event_process(evt); })`），此时事件不再积压队列，而是实时处理。
- **实现代码**：

```cpp
	//事件接收 —— 单事件重载
	void Event_Terminal::receive(shared_ptr<event> evt)
	{
		//若事件接收入口已额外注册
		if (terminal_interface.event_receiver)
			(*terminal_interface.event_receiver)(evt);
		//若未额外注册则使用原生通道
		else
			event_set.push_back(evt);
	}

	//事件接收 —— 多事件重载
	void Event_Terminal::receive(vector<shared_ptr<event>> events)
	{
		//若事件接收入口已额外注册
		if (terminal_interface.events_receiver)
			(*terminal_interface.events_receiver)(events);
		//若未额外注册则使用原生通道
		else
			event_set.insert(event_set.end(), events.begin(), events.end());
	}
```

#### 2.2.7 `query` —— 事件查阅

- **签名**：`const std::vector<std::shared_ptr<event>>* query(const int64_t& acl_key);`
- **参数**：权限密钥。
- **返回值**：
  - 密钥未生成：`nullptr`（并告警）。
  - 密钥匹配：指向 `event_set` 的**常量指针**（`const std::vector<std::shared_ptr<event>>*`），可只读遍历本终端已接收但尚未处理/清空的事件。
  - 密钥不匹配：`nullptr`。
- **调用前提**：模块须持有密钥。
- **注意事项**：返回的是内部容器地址，**生命周期由终端管理**；调用方不得通过该指针修改容器内容（const 约束），也不应在终端析构后继续使用。

#### 2.2.8 `clear` —— 事件清空

- **签名**：`bool clear(const int64_t& acl_key);`
- **参数**：权限密钥。
- **返回值**：`bool`。密钥未生成 → `false`（告警）；密钥匹配 → 清空 `event_set` 并返回 `true`；不匹配 → `false`。
- **行为**：`event_set.clear()` 释放全部已接收事件（shared_ptr 引用计数减一）。
- **调用前提**：模块须持有密钥。
- **实现代码**：

```cpp
	//事件清空
	bool Event_Terminal::clear(const int64_t& acl_key)
	{
		//若当前尚未生成密钥
		if (!this->acl_key.has_value())
		{
			Log::warn("Event_Terminal::密钥未生成\n功能已锁定");
			return false;
		}
		//若密钥匹配则清空所有事件
		if (acl_key == this->acl_key)
		{
			event_set.clear();
			//返回清空成功
			return true;
		}
		//返回无权清空
		else
			return false;
	}
```

#### 2.2.9 `operator->` —— 终端接口快捷通道

- **签名**：`Terminal_Interface* operator->(void);`
- **参数**：无。
- **返回值**：指向内部 `Terminal_Interface` 的裸指针。
- **语义**：使得 `event_terminal->event_receiver_register(...)`、`event_terminal->interface_check(...)` 等写法可直接穿透到终端接口注册表，用于模块注册自己的回调或查询接口状态（如 `Collision_Proxy::attach` 中的 `event_terminal->interface_check(interface_ID::ATTACH_HANDLER)` 与 `event_terminal->event_receiver_register(...)`）。
- **注意事项**：返回非 const 裸指针，调用方可借此修改 `Terminal_Interface` 内部状态（注册回调），这是**有意设计**——`Terminal_Interface` 与 `Event_Terminal` 为友元关系且接口本身就是供模块配置的注册表。

#### 2.2.10 特殊成员函数

- `Event_Terminal() = default;`：默认构造。此时 `acl_key` 无值（锁定态）、`key_generator` 以默认种子初始化、`event_set` 为空。
- `~Event_Terminal() = default;`：默认析构。
- `Event_Terminal(Event_Terminal&&) = default;`：**默认移动构造**。
- `Event_Terminal& operator=(Event_Terminal&&) = default;`：**默认移动赋值**。
- **注意**：未定义拷贝构造/拷贝赋值，因此 `Event_Terminal` **不可拷贝**（拷贝会因 `std::optional`、`Random_Generator`、`std::vector`、`Terminal_Interface`（含 unique_ptr）而隐式删除）。若需要传递终端，应使用引用、指针或移动语义。

### 2.3 `Terminal_Interface`（终端接口，`Event_Terminal\终端接口.h`）

`engine::Terminal_Interface` 是 `Event_Terminal` 内部的**回调注册表**。它把"终端应执行的动作"（发送、接收、交互、接入）以 `std::function` 形式保存，供模块注册、供 `Event_Terminal` 调用。完整声明如下：

```cpp
namespace engine
{
	//终端接口列表
	enum class interface_ID
	{
		NONE,
		ATTACH_HANDLER,
		EVENT_INTERACTOR,
		EVENTS_INTERACTOR,
		EVENT_SENDOR,
		EVENTS_SENDOR,
		EVENT_RECEIVER,
		EVENTS_RECEIVER
	};

	//事件终端前置声明
	class Event_Terminal;

	//终端接口
	class Terminal_Interface
	{
	private:
		//订阅事件类型别名
		using needed_events = const std::vector<event>&;
		//事件入口类型别名 —— 单事件重载
		using event_handler = std::function<void(std::shared_ptr<event> evt)>;
		//事件入口类型别名 —— 多事件重载
		using events_handler = std::function<void(std::vector<std::shared_ptr<event>>)>;
		//接口入口类型别名
		using attch_handler = std::function<void(const std::string& name,needed_events events,
			event_handler receiver)>;

		//接口注册表
		std::vector<interface_ID> map{};

		//中转站接入入口
		std::unique_ptr<attch_handler> attach_handler;
		//中转站交互入口 —— 单事件重载
		std::unique_ptr<event_handler> event_interactor;
		//中转站交互入口 —— 单事件重载
		std::unique_ptr<events_handler> events_interactor;

		//事件发送入口 —— 单事件重载
		std::unique_ptr<event_handler> event_sender;
		//事件发送入口 —— 多事件重载
		std::unique_ptr<events_handler> events_sender;

		//事件接收入口 —— 单事件重载
		std::unique_ptr<event_handler> event_receiver;
		//事件接收入口 —— 多事件重载
		std::unique_ptr<events_handler> events_receiver;

		//函数包装器内存分配
		template <typename... Args>
		bool memory_malloc(std::unique_ptr<std::function<void(Args ...)>>& target);

		//函数接口注册
		template <typename... Args>
		bool function_register(interface_ID ID,std::unique_ptr<std::function<void(Args ...)>>& target,
			std::function<void(Args ...)> function);
	public:
		//事件终端友元
		friend class Event_Terminal;

		//中转站接入入口注册
		bool attach_handler_register(attch_handler callback);
		//中转站交互入口注册
		bool event_interactor_register(event_handler callback);
		//中转站交互入口注册
		bool events_interactor_register(events_handler callback);

		//事件发送入口注册 —— 单事件重载
		bool event_sender_register(event_handler callback);
		//事件发送入口注册 —— 多事件重载
		bool event_sender_register(events_handler callback);

		//事件接收入口注册 —— 单事件重载
		bool event_receiver_register(event_handler callback);
		//事件接收入口注册 —— 多事件重载
		bool event_receiver_register(events_handler callback);

		//接口注入验证
		bool interface_check(const interface_ID& ID);
	};
}
```

#### 2.3.1 `interface_ID` 枚举

| 枚举值 | 语义 | 对应成员 |
| --- | --- | --- |
| `NONE` | 空占位（无实际用途，map 中不会被写入） | — |
| `ATTACH_HANDLER` | 中转站接入入口 | `attach_handler` |
| `EVENT_INTERACTOR` | 中转站交互入口（单事件） | `event_interactor` |
| `EVENTS_INTERACTOR` | 中转站交互入口（多事件） | `events_interactor` |
| `EVENT_SENDOR` | 事件发送入口（单事件） | `event_sender` |
| `EVENTS_SENDOR` | 事件发送入口（多事件） | `events_sender` |
| `EVENT_RECEIVER` | 事件接收入口（单事件） | `event_receiver` |
| `EVENTS_RECEIVER` | 事件接收入口（多事件） | `events_receiver` |

`interface_ID` 是 `interface_check` 判断接口是否注册的依据：`function_register` 每注册一个入口，就把对应的枚举值 `push_back` 进 `map`；`interface_check` 遍历 `map` 查找。

#### 2.3.2 私有类型别名

```cpp
		//订阅事件类型别名
		using needed_events = const std::vector<event>&;
		//事件入口类型别名 —— 单事件重载
		using event_handler = std::function<void(std::shared_ptr<event> evt)>;
		//事件入口类型别名 —— 多事件重载
		using events_handler = std::function<void(std::vector<std::shared_ptr<event>>)>;
		//接口入口类型别名
		using attch_handler = std::function<void(const std::string& name,needed_events events,
			event_handler receiver)>;
```

- `needed_events`：`const std::vector<event>&`——订阅事件清单（以引用传递避免拷贝）。
- `event_handler`：`std::function<void(std::shared_ptr<event> evt)>`——单事件回调签名。
- `events_handler`：`std::function<void(std::vector<std::shared_ptr<event>>)>`——多事件回调签名（按值传 vector，注意语义）。
- `attch_handler`：`std::function<void(const std::string& name, needed_events events, event_handler receiver)>`——接入回调签名：模块名 + 订阅清单 + 接收入口。**该签名与 `Event_Broker::info_register` 的三个参数（module_name、needed_events、event_entry）完全对应**，因此可用 `std::bind` 或 lambda 将 `info_register` 包装后注册为 `attach_handler`。

#### 2.3.3 模板私有工具：`memory_malloc` 与 `function_register`

```cpp
	//函数包装器内存分配
	template <typename... Args>
	bool Terminal_Interface::memory_malloc(unique_ptr<function<void(Args ...)>>& target)
	{
		//为目标对象分配内存
		target.reset(new(nothrow) function<void(Args ...)>);
		//返回内存分配结果
		return static_cast<bool>(target);
	}
	//函数接口注册
	template <typename... Args>
	bool Terminal_Interface::function_register(interface_ID ID, 
		std::unique_ptr<std::function<void(Args ...)>>& target,
		std::function<void(Args ...)> function)
	{
		//若内存分配成功
		if (memory_malloc(target))
		{
			//注册函数接口
			*(target) = function;
			//记录当前接口已注册
			map.push_back(ID);
			//返回注册成功
			return true;
		}
		//若内存分配失败
		else
			//返回注册失败
			return false;
	}
```

- `memory_malloc`：用 `new(nothrow)` 为 `std::function` 分配堆内存并 reset 进 `unique_ptr`；返回指针是否非空。
- `function_register`：通用注册三步曲——(1) 分配内存；(2) 若成功则写入回调 `*(target) = function`；(3) 把接口 ID 压入 `map` 记录"已注册"。**重复注册同一个接口会覆盖旧的回调**（`target.reset` 释放旧对象后写入新值，且 `map` 会重复记录 ID；`interface_check` 只查存在性，不受重复影响）。
- 注意 `map` 的重复记录不会导致 `interface_check` 误判，因为其只做存在性检查。

#### 2.4.1 私有嵌套结构体 `event_acl`

```cpp
        //事件订阅权限结构体
        struct event_acl
        {

            std::string tag;                
            //订阅者编号集合
            std::vector<int32_t> ID_set{};

```

- `tag`：该行对应的事件标签；**首个元素的 tag 为空串，表示"该大类全订阅"标记行**（见 `info_register` 中 `acl_set[evt.category].push_back({})`，即 push 一个 tag 为空的 event_acl 作为全订阅行）。
- `ID_set`：订阅该标签（或该大类全部）的订阅者编号集合（`int32_t`，由 `mapping_set` 分配）。注意 `receive` 中使用 `vector<uint16_t> acled_IDs` 收集授权订阅者，存在**类型收缩**（int32_t → uint16_t）的潜在风险，见第四章。

#### 2.4.2 `info_register` —— 订阅者登记注册

- **签名**：`void info_register(const std::string& module_name, const std::vector<event>& needed_events, std::function<void(std::shared_ptr<event>)> event_entry);`
- **参数**：
  - `module_name`：订阅者模块名，用作 `mapping_set` 的键。
  - `needed_events`：该模块需要订阅的事件清单（category/tag 组合）。
  - `event_entry`：该模块的事件入口回调（`std::function<void(std::shared_ptr<event>)>`），中转站分发事件时调用它。`Event_Terminal::attach` 中传入的接收入口（`this->receive` 包装 lambda）最终成为此回调。
- **返回值**：`void`（注意：本接口不返回成功/失败，注册过程静默进行）。
- **行为流程**：
  1. **订阅者 ID 登记**：若 `module_name` 已在 `mapping_set` 中（二次注册），取回原 ID 并**覆盖** `event_entries[subscriber_ID]` 为新入口；否则以 `mapping_set.size()` 作为新 ID，插入 `mapping_set` 与 `event_entries`。**注意新 ID 等于当前映射数量**，即从 0 开始递增分配。
  2. **逐事件登记订阅**：遍历 `needed_events`：
     - `category.empty()` → 跳过（`continue`）。
     - `acl_set` 中无该分类 → 创建 `acl_set[category]`，并 `push_back({})` 一个**全订阅标记行**（空 tag 行）。
     - 遍历该分类下的 `acl_row`：
       - 若某个已有行 tag 与事件 tag 相同 → 把 `subscriber_ID` 加入该行的 `ID_set`（**去重检查**：遍历已有 ID_set，若已存在则 break，若遍历到末尾仍未发现则 push_back）。
       - 若遍历完所有行都未匹配 → `acl_row.push_back({evt.tag, {subscriber_ID}})` 新建标签行。
- **调用前提**：通常由中转站持有者把本方法包装成 `Terminal_Interface::attach_handler` 后，由各模块 `Event_Terminal::attach` 间接调用。
- **关键实现代码**：

```cpp
    //订阅者登记注册
    void Event_Broker::info_register
    (const string& module_name, const vector<event>& needed_events,
        function<void(shared_ptr<event> evt)> event_entry)
    {
        //订阅者ID记录
        int32_t subscriber_ID = -1;

        //若本次为二次注册
        if (mapping_set.count(module_name))
        {
            //获取订阅者ID
            subscriber_ID = mapping_set[module_name];
            //重新注册事件入口
            event_entries[subscriber_ID] = event_entry;
        }
        //若本次为首次注册
        else
        {
            //获取当前映射数目作为新订阅者编号
            subscriber_ID = mapping_set.size();
            //注册订阅者内部ID
            mapping_set.insert({ module_name, subscriber_ID });
            //注册事件入口
            event_entries.insert({ subscriber_ID ,event_entry });
        }

        //注册需要事件
        for (int register_time = 0; register_time < needed_events.size(); register_time++)
        {
            //简化表示路径
            auto& evt = needed_events[register_time];

            //若事件所属分类未指定则略过
            if (evt.category.empty())
                continue;

            //若事件所属分类未注册则略过
            if (!acl_set.count(evt.category))
            {
                //创建该事件分类
                acl_set.insert({ evt.category,{} });
                //全订阅标记初始化
                acl_set[evt.category].push_back({});
            }

            //获取事件分类内部信息
            auto& acl_row = acl_set[evt.category];

            //匹配事件标签
            for (int match_time = 0; match_time < acl_row.size(); match_time++)
            {
                //若事件标签匹配则订阅该事件
                if (evt.tag == acl_row[match_time].tag)
                {
                    //简化表示路径
                    auto& ID_set = acl_row[match_time].ID_set;
                    //若不存在任何订阅者
                    if (ID_set.empty())
                        ID_set.push_back(subscriber_ID);
                    //若已经存在订阅者
                    else
                    {
                        //检查是否已经注册
                        for (int exam_time = 0; exam_time < ID_set.size(); exam_time++)
                        {
                            //若已经注册则处理下一事件
                            if (ID_set[exam_time] == subscriber_ID)
                                break;
                            //若未注册则注册
                            else if (exam_time == ID_set.size() - 1)
                                ID_set.push_back(subscriber_ID);
                        }
                    }

                    break;
                }
                //若匹配失败则创建该事件标签
                else if (match_time == acl_row.size() - 1)
                    acl_row.push_back({ evt.tag, { subscriber_ID } });
            }
        }

    }
```

- **踩坑点（已存在于源码逻辑中）**：
  - 当某分类下已有行的 `ID_set` 为空、且匹配到空 tag 的全订阅行时，`if (ID_set.empty()) ID_set.push_back(...)` 会直接把订阅者加入全订阅行。
  - 去重循环 `for (int exam_time = 0; ...)` 中，若 `ID_set` 只有一个元素且恰好就是 `subscriber_ID`，则 `break`；若只有一个元素但不是，`exam_time == ID_set.size()-1` 成立（0 == 0），`push_back` 追加。逻辑正确。但注意：**若 `ID_set` 为空，则外层 `if (ID_set.empty())` 已处理，不会进入 for 循环**。
  - 标签匹配使用字符串全等比较（`evt.tag == acl_row[match_time].tag`），大小写敏感。

#### 2.4.3 `receive` —— 事件接收/分发（两处重载）

- **签名**：
  - `void receive(std::shared_ptr<event> evt);`（单事件）
  - `void receive(std::vector<std::shared_ptr<event>> event_set);`（多事件）
- **参数**：进入中转站的事件（或事件集合）。
- **返回值**：`void`。
- **行为（单事件重载，核心分发逻辑）**：
  1. 取 `sender_object`、`target_object` 引用。
  2. **丢弃条件**：
     - `evt->category.empty()` 或 `!acl_set.count(evt->category)` → return（分类为空或无人注册该分类）。
     - `evt->tag.empty()` → return（标签为空）。
  3. **定向投递**：若 `!target_object.empty() && mapping_set.count(target_object)`，取目标 ID，直接调用 `event_entries[target_ID](evt)` 并 return。
  4. **广播分发**（无定向目标时）：
     - 取该分类的 `acl_row`。
     - 先收集**全订阅者**：`acled_IDs.insert(... acl_row.front().ID_set ...)`（首行即全订阅行）。
     - 再从 `match_time=1` 起遍历其余行，若 `evt->tag == acl.tag` 则把该行 `ID_set` 并入 `acled_IDs`。
     - 解析发送者 ID：`mapping_set.find(sender_object)`，存在则取其 ID，否则 `-1`。
     - 遍历 `acled_IDs`，**跳过 `sender_ID` 本人**（避免事件回环给自己），其余逐一调用 `event_entries[acled_IDs[send_time]](evt)`。
- **行为（多事件重载）**：循环逐事件调用单事件重载。
- **调用前提**：`receive` 通常被注册为 `Terminal_Interface` 的 `event_sender` / `events_sender` / `event_interactor` / `events_interactor`，由 `Event_Terminal::send` / `interact` 触发。也可被直接调用（中转站持有者）。
- **关键实现代码**：

```cpp
    //事件接收 —— 单事件重载
    void Event_Broker::receive(shared_ptr<event> evt)
    {
        //简化表示路径
        auto& sender_object = evt->sender_object;
        auto& target_object = evt->target_object;

        //若事件所属分类不存在或未注册
        if (evt->category.empty() || !acl_set.count(evt->category))
            return;

        //若事件标签不存在
        if (evt->tag.empty())
            return;

        //若为定向发送且目标存在
        if (!target_object.empty() && mapping_set.count(target_object))
        {
            //获取目标ID
            int target_ID = mapping_set[target_object];
            //定向发送事件
            event_entries[target_ID](evt);
            //处理下一事件
            return;
        }

        //简化表示路径
        auto& acl_row = acl_set[evt->category];

        //授权订阅者ID记录
        vector<uint16_t> acled_IDs;

        //插入订阅事件分类内全部事件标签订阅者集合
        acled_IDs.insert(acled_IDs.end(),
            acl_row.front().ID_set.begin(), acl_row.front().ID_set.end());

        //在部分订阅集合内匹配授权订阅者
        for (int match_time = 1; match_time < acl_row.size(); match_time++)
        {
            //简化表示路径
            auto& acl = acl_row[match_time];
            //若事件标签匹配
            if (evt->tag == acl.tag)
                acled_IDs.insert(acled_IDs.end(), acl.ID_set.begin(),
                    acl.ID_set.end());
        }

        //事件发起者ID记录
        int32_t sender_ID;
        //获取事件发送者ID
        auto it = mapping_set.find(sender_object);
        //若事件发起者映射存在
        if (it != mapping_set.end())
            sender_ID = it->second;
        //若事件发起者映射不存在
        else
            sender_ID = -1;

        //发送事件
        for (int send_time = 0; send_time < acled_IDs.size(); send_time++)
        {
            //若非事件发起者
            if(acled_IDs[send_time] != sender_ID)
                event_entries[acled_IDs[send_time]](evt);
        }
    }
```

- **边界条件**：
  - **重复投递**：全订阅行与具体标签行可能同时包含同一订阅者 ID（模块既全订阅又单独订阅某标签），此时 `acled_IDs` 中会**出现重复 ID**，该模块的入口会被**调用两次**。订阅方应避免同时声明全订阅与具体标签订阅同一事件。
  - **发送者不在 mapping_set**：`sender_ID = -1`，与任何 uint16_t 订阅者 ID 均不同（ID 从 0 开始），因此不会错误跳过任何订阅者——但注意 `acled_IDs` 是 `uint16_t`，而 `-1` 参与比较时会被提升为整型，`acled_IDs[send_time] != sender_ID` 的比较中 `acled_IDs[send_time]`（uint16_t）提升为 int 与 -1 比较，恒真，故发送者自身不会被排除（因为发送者本就不在 acled_IDs 中）。此分支正常。
  - **订阅者数量超过 65535**：`acled_IDs` 用 `uint16_t`，超过 65535 个订阅者时 ID 截断，可能误投/漏投——**已知潜在缺陷**。

#### 2.4.4 `process` —— 事件处理/应答（两处重载）

- **签名**：
  - `std::shared_ptr<event> process(std::shared_ptr<event> evt);`（单事件）
  - `std::vector<std::shared_ptr<event>> process(std::vector<std::shared_ptr<event>> event_set);`（多事件）
- **参数**：待处理事件（或事件集合）。
- **返回值**：
  - 单事件：处理成功后返回应答事件（`shared_ptr<event>`）；无法处理返回 `nullptr`。
  - 多事件：收集所有单事件处理的返回值（含 nullptr）组成 vector 返回（注意：**返回的 vector 中可能混有 nullptr 元素**，调用方需自行判空）。
- **行为（单事件重载）**：
  1. `sender_object.empty()` → `Log::warn("Event_Broker::事件发送者未定义\n事件无法处理")`，返回 `nullptr`。
  2. `target_object.empty()` → 同上告警（"事件目标未定义"），返回 `nullptr`。
  3. `!mapping_set.count(sender_object)` → `Log::warn("Event_Broker::事件发送者不存在\n事件无法处理")`，返回 `nullptr`。
  4. 仅处理 `category == "Subscriber"` 且 `tag == "Check" || tag == "Call"`：
     - 构造应答事件 `response_event(new(nothrow)event("Subscriber","Response"))`。
     - `mapping_set.find(evt->target_object)`：不存在 → `response_event->config["object_existence"] = false`；存在 → 置 `true`，若 `tag == "Call"` 则**将原事件转发给目标模块** `event_entries[it->second](evt)`。
     - 返回 `response_event`。
  5. 其他 category/tag 组合：函数体走到末尾，**无显式 return，返回未定义值**（源码缺省路径没有 `return nullptr;`——这是一个值得注意的缺陷，见第四章）。
- **调用前提**：由中转站持有者在合适时机调用（如轮询 `event_set` 后逐个 `process`）。
- **关键实现代码**：

```cpp
    //事件处理 —— 单事件重载
    shared_ptr<event> Event_Broker::process(shared_ptr<event> evt)
    {
        //简化表示路径
        auto& config = evt->config;

        //若未定义事件发送者则直接返回
        if (evt->sender_object.empty())
        {
            Log::warn("Event_Broker::事件发送者未定义\n事件无法处理");
            return nullptr;
        }
        //若未定义事件目标则直接返回
        if (evt->target_object.empty())
        {
            Log::warn("Event_Broker::事件目标未定义\n事件无法处理");
            return nullptr;
        }
        //若事件发送者不存在则直接返回
        if (!mapping_set.count(evt->sender_object))
        {
            Log::warn("Event_Broker::事件发送者不存在\n事件无法处理");
            return nullptr;
        }

        //若事件大类可处理
        if (evt->category == "Subscriber")
        {
            //若事件标签可处理
            if (evt->tag == "Check" || evt->tag == "Call")
            {
                //构造回复事件
                shared_ptr<event> response_event(new(nothrow)event("Subscriber","Response"));
                //查询目标对象
                auto it = mapping_set.find(evt->target_object);
                //若目标对象不存在
                if (it == mapping_set.end())
                    //设置目标对象不存在
                    response_event->config["object_existence"] = false;
                else
                {
                    //设置目标对象存在
                    response_event->config["object_existence"] = true;
                    //若为目标呼叫事件
                    if (evt->tag == "Call")
                        //将呼叫事件转发给目标对象
                        event_entries[it->second](evt);
                }

                //返回答复事件
                return response_event;
            }
            
        }
    }
```

- **语义说明**：`process` 承担"Subscriber 协议"——用于模块间"探测/呼叫"：
  - **Check**：询问"目标模块是否存在于事件系统"，应答事件 `config["object_existence"]` 反映结果，不打扰目标模块。
  - **Call**：询问 + 转发，目标存在时把原 Call 事件直接投递给目标模块的入口，同时应答事件仍返回给调用方。
- **调用前提**：需要持有 `mapping_set`/`event_entries` 有效状态；返回的应答事件可能为 `nullptr`（未定义发送者/目标等），多事件重载的返回 vector 中会混有 nullptr。

关系要点：

1. **`Event_Terminal` 与 `Terminal_Interface` 是组合（has-a）关系**：`Event_Terminal` 持有成员 `Terminal_Interface terminal_interface`；通过 `operator->` 暴露给外部；`Terminal_Interface` 声明 `friend class Event_Terminal;` 允许终端直接访问其私有注册表成员（如 `attach` 中直接读取 `Tinterface.event_receiver`）。

3. **`Event_Broker` 内部三层表**：
   - `mapping_set`：`unordered_map<string, int32_t>`——模块名 → 订阅者编号。
   - `event_entries`：`unordered_map<int32_t, std::function<void(shared_ptr<event>)>>`——订阅者编号 → 事件入口回调。

4. **`event` 是唯一的"消息载体"**，被 `shared_ptr` 包裹在终端、中转站、消费方之间传递；同一事件对象在广播时被多个订阅者共享（引用计数增加），不复制载荷。

## 四、模块设计/实现细节（关键算法流程、边界条件处理、设计决策及其原因、踩坑点、注意事项）

### 4.1 ACL 权限模型：密钥未生成即锁定

**设计决策**：`Event_Terminal` 使用 `std::optional<int64_t> acl_key` 承载权限密钥。`optional` 的"有值/无值"天然表达"密钥已生成/未生成"两态：

- **未生成（无值）**：`attach`、`interact`（两重载）、`send`（两重载）、`query`、`clear` 六个受保护操作全部在入口处检查 `!this->acl_key.has_value()`，命中则 `Log::warn("Event_Terminal::密钥未生成\n功能已锁定")` 并返回失败值（false / nullptr）。这是**防御性设计**：任何忘记调用 `acl_key_gen` 就操作终端的模块，会得到明确的日志告警而不是静默的未定义行为。
- **已生成但未匹配**：`this->acl_key != acl_key` 时静默返回失败（不告警，避免噪音）。
- **重复生成**：`acl_key_gen` 在已有时返回 0。0 是哨兵值：所有受保护接口的密钥比对都是 `==`，真实密钥永不取 0（`acl_key_gen` 内部循环保证），因此 0 永远无法通过校验。

**设计原因**：事件系统是跨模块的公共通道，若不加权限，任何代码都能伪造模块名发送事件、冒充他人订阅，导致事件流失控。密钥机制让"谁持有终端、谁有资格操作"显式化。**局限**：密钥是"终端级"而非"调用级"权限——模块拿到密钥后其内部所有代码都能调用，属于粗粒度控制；且密钥以 `int64_t` 存储，若被日志输出/序列化泄漏则权限失效。

**交互语义总结（源码中的统一模式）**：

```cpp
        //以 send 单事件重载为例，所有受保护操作的统一三段式：
        //1) 密钥未生成 → 告警 + 拒绝
        if (!this->acl_key.has_value())
        {
            Log::warn("Event_Terminal::密钥未生成\n功能已锁定");
            return false;
        }
        //2) 密钥匹配 → 执行动作
        if (this->acl_key == acl_key) { ... return true; }
        //3) 密钥不匹配 → 拒绝
        else return false;
```

### 4.2 终端接口注册表的设计

**设计决策**：`Terminal_Interface` 把"终端要做的动作"抽象成 7 个可注册回调，配合 `map`（interface_ID 记录）做能力检查。这样 `Event_Terminal` 不需要知道动作的真实实现（是 `Event_Broker` 还是别的什么），实现"控制反转（IoC）"：

- 中转站持有者在启动阶段注册：`attach_handler_register`（接 `info_register`）、`event_sender_register`（接 `receive`）、`event_interactor_register` 等。
- 业务模块在接入阶段注册：`event_receiver_register`（接自己的事件处理函数）。
- 终端方法执行时只检查"入口是否注册"（指针非空或 `interface_check`），再调用。

**踩坑点**：

1. **`send` 与 `interact` 的入口检查方式不一致**：`send` 直接判 `terminal_interface.event_sender`（unique_ptr 的 bool 转换），`interact` 走 `interface_check(interface_ID::...)`。两者语义等价，但 `interface_check` 查的是 `map`（历史记录），而 `send` 查的是指针（当前状态）。**若出现"map 有记录但指针为空"的不一致状态（理论上只有手动破坏内部状态才会发生），两种检查结果会不同**。
2. **重复注册覆盖旧回调**：`function_register` 每次都会 `target.reset(new(nothrow)...)` 重建，旧回调被覆盖；`map` 中 ID 会重复累积（不影响 `interface_check` 的存在性判断，但 `map` 会随注册次数增长，属轻微内存/性能浪费）。
3. **内存分配失败处理**：`memory_malloc` 用 `new(nothrow)`，失败时 `function_register` 返回 false，注册方法返回 false——调用方应检查返回值（如 `Collision_Proxy::attach` 检查 `event_receiver_register` 的返回值并 `Log::error`）。

### 4.3 订阅表（acl_set）的"全订阅标记行"约定

`acl_set[category]` 是一个 `vector<event_acl>`，其**下标 0（首元素）是特殊行**：`tag` 为空串，表示"订阅该大类的全部事件"。该行在分类首次创建时由 `info_register` 插入：

```cpp
            //若事件所属分类未注册则略过
            if (!acl_set.count(evt.category))
            {
                //创建该事件分类
                acl_set.insert({ evt.category,{} });
                //全订阅标记初始化
                acl_set[evt.category].push_back({});
            }
```

`push_back({})` 构造一个 `tag=""`、`ID_set={}` 的 event_acl。随后所有声明了该分类（无论具体标签）的订阅者，其 ID 都登记在**对应的标签行**或**全订阅行**中：

- 订阅者声明 `event("", "", "Collision", "RegionBuild")` → ID 进入 `acl_set["Collision"]` 中 tag=="RegionBuild" 的行。
- **如何全订阅**：声明 `event("", "", "Collision", "")`（tag 为空）→ 在 `info_register` 的匹配循环中，`evt.tag == acl_row[match_time].tag` 在 match_time=0 处命中（两边都为空串），于是 ID 进入全订阅行。但注意——**`receive` 分发时 `evt->tag.empty()` 的事件会被直接丢弃**，因此"全订阅"语义是"接收该分类下所有**带标签**的事件"，空标签事件本身不会被广播。

**分发时的合并逻辑**（`receive`）：

```
acled_IDs = 全订阅行.ID_set            // 所有"订阅整个大类"的模块
for 每个标签行:
    若 evt.tag == 行.tag:
        acled_IDs += 行.ID_set         // 加"订阅该具体标签"的模块
for id in acled_IDs:
    若 id != sender_ID: 调用 event_entries[id](evt)
```

### 4.4 定向投递 vs 广播

`receive` 中定向投递优先于广播：

```cpp
        //若为定向发送且目标存在
        if (!target_object.empty() && mapping_set.count(target_object))
        {
            //获取目标ID
            int target_ID = mapping_set[target_object];
            //定向发送事件
            event_entries[target_ID](evt);
            //处理下一事件
            return;
        }
```

**语义要点**：

- `Config/Load` 事件正是利用定向投递：`Config_Loader` 填充 `evt->target_object = module`（如 "Collision_Proxy"），`receive` 直接投给该模块，**不经过 acl 匹配**（即目标模块即使没在 `needed_events` 里声明 Config/Load 也能收到）。
- 若 `target_object` 非空但 `mapping_set` 中无此模块（目标未注册）→ 条件不成立，**退化为广播**（按 category/tag 匹配所有订阅者）。这是源码的既定行为：对未注册目标的定向事件不会静默丢弃，而是广播。调用方需注意这一"意外广播"语义。
- 定向投递**不排除发送者**：即使发送者就是目标，也会收到自己的事件（与广播路径的"排除自身"不同）。

### 4.5 Subscriber 应答协议（process）

`process` 实现了轻量级的"模块存在性探测"协议，事件类型约定：

| 事件 | category | tag | 语义 | 应答 |
| --- | --- | --- | --- | --- |
| 探测 | `Subscriber` | `Check` | 询问目标模块是否存在 | `Subscriber/Response`，`config["object_existence"]` 布尔 |
| 呼叫 | `Subscriber` | `Call` | 询问目标是否存在，且要求转发 | 应答同上；目标存在时原事件被转发给目标入口 |

实现中的细节：

- 应答事件构造：`shared_ptr<event> response_event(new(nothrow)event("Subscriber","Response"));`——注意 `event("Subscriber","Response")` 用的是**两参构造函数**（category, tag），sender/target 为空，config 随后填充 `object_existence` 字段。
- **Check 与 Call 的差异仅在"是否转发原事件"**：`if (evt->tag == "Call") event_entries[it->second](evt);`。
- **缺陷**：`process` 对非 `Subscriber/Check|Call` 组合的事件**没有兜底 return**，函数会从末尾"掉出去"。在 C++ 中，非 void 函数到达末尾返回未定义值（通常是调用约定寄存器残留值），可能产生"非 nullptr 的野应答指针"。**多事件重载 `process` 会把该未定义值 push 进 buffer**，调用方判空时可能误判。这是源码中值得修复的隐患（建议补 `return nullptr;`）。

### 4.6 哈希与判等的一致性

`std::hash<engine::event>` 与 `event::operator==` 的维度完全对齐：category、tag、target_object、config（哈希时 dump 成字符串）。这保证把 `event` 用作 `unordered_*` 键时满足"相等对象哈希值必相同"。

**踩坑点**：

1. **`config.dump()` 在 `noexcept` 函数中可能抛异常**：`operator()` 标记 `noexcept`，而 `dump()` 对非法 json（如含 NaN/Inf 的浮点，nlohmann::json 默认 `dump()` 会因 `allow_nan_inf` 默认为 false 而抛 `type_error`）会抛异常 → `std::terminate`。**若业务代码在 config 中写入 NaN/Inf 且事件被哈希，将直接崩溃**。
2. **浮点载荷的哈希不稳定**：`dump()` 对浮点数输出位数受全局序列化配置影响，理论上同一 json 值的 `dump()` 结果在程序内一致，但跨运行（不同浮点舍入）可能不一致——对单进程容器使用无碍。
3. **`operator==` 不比较 sender_object**：两个 sender 不同但其余相同的事件判等。若未来把 event 放进需要"全字段判等"的容器（如去重集合），需注意此语义是**有意设计**（哈希也忽略 sender）。

### 4.7 移动语义与不可拷贝性

- `Event_Terminal` 只提供移动构造/移动赋值（default），**拷贝被隐式删除**。原因：成员 `Random_Generator`（含非平凡成员 `pcg32` 结构体与 `uint64_t seed`，可拷贝但拷贝会复制 PRNG 状态）、`Terminal_Interface`（含 `unique_ptr`，不可拷贝）。
- 引擎内 `Event_Terminal` 通常作为模块的成员对象直接持有（如 `Collision_Proxy::event_terminal`、`Config_Loader::event_terminal`），移动语义主要用于容器重排等场景。
- `event` 与 `Terminal_Interface` 无此限制（event 可拷贝；Terminal_Interface 因 unique_ptr 同样不可拷贝，但未被 default 声明移动——**注意 `Terminal_Interface` 没有显式移动构造/赋值声明，其移动操作会被 unique_ptr 成员隐式生成但可能不符合预期**，实际使用中依赖 `Event_Terminal` 整体移动）。

### 4.8 `Event_Broker::receive` 中的类型收缩风险

`acled_IDs` 声明为 `vector<uint16_t>`，而 `event_acl::ID_set` 是 `vector<int32_t>`：

```cpp
        //授权订阅者ID记录
        vector<uint16_t> acled_IDs;
        acled_IDs.insert(acled_IDs.end(),
            acl_row.front().ID_set.begin(), acl_row.front().ID_set.end());
```

`int32_t` → `uint16_t` 隐式收缩：当订阅者编号 ≥ 65536 时发生截断，多个 ID 映射到同一 uint16_t 值，导致：
- 事件投递给错误的模块（误投）。
- 发送者排除失效（截断后的值恰好等于 sender 截断值）。
- 负值（不可能出现，ID 从 0 分配，但防御性角度）转成大正数。

**当前引擎模块数量远未达到 65535，此缺陷为潜在风险而非现役问题**，记录以供后续版本关注。

### 4.9 `interface_ID` 枚举与 `map` 记录

`function_register` 每次成功注册都会 `map.push_back(ID)`，但**不会先查重**。因此重复注册 N 次同一接口，`map` 会有 N 个相同 ID。`interface_check` 是线性遍历，性能 O(map 长度)，重复注册会略微降低检查速度并增加内存。**建议**：注册前先 `interface_check` 或改为 `unordered_set`。当前引擎注册次数有限，属轻微问题。

### 4.10 日志输出的统一约定

事件系统在以下路径输出日志（均为 `Log::warn` / `Log::error` / `Log::debug`）：

| 场景 | 日志级别 | 消息 |
| --- | --- | --- |
| 受保护操作遇"密钥未生成" | warn | `Event_Terminal::密钥未生成\n功能已锁定` |
| `process` 未定义发送者 | warn | `Event_Broker::事件发送者未定义\n事件无法处理` |
| `process` 未定义目标 | warn | `Event_Broker::事件目标未定义\n事件无法处理` |

## 五、模块运行链路（从构建/初始化到一次典型操作的完整调用时序；与其他模块的协作关系）

### 5.1 总体协作拓扑

事件系统在引擎中的总体协作关系如下：

```
                 ┌─────────────────────────────────────────────┐
                 │            引擎初始化（中转站持有者）          │
                 │                                             │
                 │   Event_Broker broker;                      │
                 │   Event_Terminal terminal;                  │
                 │   terminal.attach_handler_register(         │
                 │       [&](name, events, receiver){          │
                 │           broker.info_register(name,        │
                 │               events, receiver); });        │
                 │   terminal.event_sender_register(           │
                 │       [&](shared_ptr<event> evt){           │
                 │           broker.receive(evt); });          │
                 │   terminal.events_sender_register(          │
                 │       [&](vector<shared_ptr<event>> evts){  │
                 │           broker.receive(evts); });         │
                 └───────┬──────────────────┬──────────────────┘
                         │                  │
         持有同一 terminal（或各自终端，回调指向同一 broker）
                         │                  │
        ┌────────────────▼───┐    ┌─────────▼────────────────┐
        │  Config_Loader     │    │  Collision_Proxy         │
        │  - event_terminal  │    │  - event_terminal        │
        │  - acl_key         │    │  - acl_key               │
        └─────────┬──────────┘    └─────────┬────────────────┘
                  │ 发送 Config/Load         │ attach 订阅 11 个事件
                  │                         │ event_receiver_register
                  ▼                         ▼
             ┌───────────────────────────────────────────────┐
             │              Event_Broker (broker)            │
             │  acl_set / mapping_set / event_entries        │
             │  info_register → 建立订阅                      │
             │  receive → 定向/广播分发                       │
             │  process → Subscriber 应答                    │
             └───────────────────────────────────────────────┘
```

### 5.2 链路一：引擎初始化（中转站接线）

**时序**：

```
引擎入口
  ├─ 1. 构造 Event_Broker broker;                     // 空表
  ├─ 2. 构造 Event_Terminal terminal;                 // 密钥未生成（锁定态）
  ├─ 3. terminal.attach_handler_register(lambda1)     // lambda1: (name, evts, recv) => broker.info_register(name, evts, recv)
  │      → Terminal_Interface::function_register(ATTACH_HANDLER, attach_handler, lambda1)
  │      → memory_malloc: attach_handler.reset(new(nothrow) function<...>)
  │      → *(attach_handler) = lambda1; map.push_back(ATTACH_HANDLER)
  ├─ 4. terminal.event_sender_register(lambda2)       // lambda2: (evt) => broker.receive(evt)
  │      → function_register(EVENT_SENDOR, event_sender, lambda2); map.push_back(EVENT_SENDOR)
  ├─ 5. terminal.events_sender_register(lambda3)      // lambda3: (evts) => broker.receive(evts)
  │      → function_register(EVENTS_SENDOR, events_sender, lambda3); map.push_back(EVENTS_SENDOR)
  └─ 6. （可选）event_interactor_register / events_interactor_register
          → 绑定 broker.receive 的单/多事件重载，供 interact 使用
```

初始化后，`terminal` 的发送/接入通道指向 `broker`，但此时尚无任何订阅者。

### 5.3 链路二：模块接入（Collision_Proxy::attach 订阅事件）

`Collision_Proxy` 代表典型的"订阅方"接入流程。源码路径：`引擎层\src\core\spatial\collision\Collision_Proxy\core\事件交互.cpp`。

**完整时序**：

```
Collision_Proxy 构造
  ├─ 成员 event_terminal（Event_Terminal）
  ├─ 成员 acl_key = 0（待赋值）
  └─ 成员 module_name（如 "Collision_Proxy"）

Collision_Proxy::attach()
  ├─ 1. 前置检查：event_terminal->interface_check(interface_ID::ATTACH_HANDLER)
  │      └─ 若 false：Log::error("Collision_Proxy::事件中转站接入入口未注册，接入中止"); return;
  ├─ 2. 注册本模块事件接收入口：
  │      event_terminal->event_receiver_register(
  │          [this](shared_ptr<event> evt) { this->event_process(evt); })
  │      └─ 若 false：Log::error("Collision_Proxy::事件接收入口注册失败，接入中止"); return;
  ├─ 3. 构造待订阅事件清单 needed_events（11 个）：
  │      event("", "", "Config", "Load")                       // Config/Load
  │      event("", "", "Collision", "RegionBuild")
  │      event("", "", "Collision", "RegionUnload")
  │      event("", "", "Collision", "RegionState")
  │      event("", "", "Collision", "RegionBoundary")
  │      event("", "", "Collision", "RegionDetect")
  │      event("", "", "Collision", "ColliderBuild")
  │      event("", "", "Collision", "ColliderUnload")
  │      event("", "", "Collision", "ColliderTransfer")
  │      event("", "", "Collision", "ColliderMirror")
  │      event("", "", "Collision", "ColliderSet")
  └─ 4. 接入：event_terminal.attach(module_name, needed_events, acl_key)
        ├─ 4.1 密钥检查：!acl_key.has_value() → warn + return false
        ├─ 4.2 密钥比对：this->acl_key == acl_key?（不匹配 → return false）
        ├─ 4.3 event_receiver 已注册（步骤2）→ 取 *Tinterface.event_receiver
        ├─ 4.4 (*Tinterface.attach_handler)(module_name, needed_events, receiver)
        │      └─ 即 lambda1 → broker.info_register("Collision_Proxy", needed_events, receiver)
        │            ├─ mapping_set["Collision_Proxy"] = 0（假设首个订阅者，ID=0）
        │            ├─ event_entries[0] = receiver
        │            └─ acl_set["Config"]    → [{tag:"", ID_set:[]}, {tag:"Load", ID_set:[0]}]
        │               acl_set["Collision"] → [{tag:"", ID_set:[]},
        │                                       {tag:"RegionBuild", ID_set:[0]},
        │                                       {tag:"RegionUnload", ID_set:[0]},
        │                                       {tag:"RegionState", ID_set:[0]},
        │                                       {tag:"RegionBoundary", ID_set:[0]},
        │                                       {tag:"RegionDetect", ID_set:[0]},
        │                                       {tag:"ColliderBuild", ID_set:[0]},
        │                                       {tag:"ColliderUnload", ID_set:[0]},
        │                                       {tag:"ColliderTransfer", ID_set:[0]},
        │                                       {tag:"ColliderMirror", ID_set:[0]},
        │                                       {tag:"ColliderSet", ID_set:[0]}]
        └─ 4.5 返回 true；若 false → Log::error("Collision_Proxy::事件中转站接入失败")
```

接入完成后，`Collision_Proxy` 已注册：
- 自己的事件处理回调（`event_process`），作为 `broker` 中 `event_entries[0]`。
- 订阅关系：Config/Load 与 Collision 大类下 10 个标签。
- 模块名 "Collision_Proxy" ↔ 订阅者 ID 0 的映射。

**要点**：`Collision_Proxy::attach` 中**未先调用 `acl_key_gen`**——`acl_key` 的取得时机取决于碰撞模块构造逻辑（该成员在事件交互.cpp 外部初始化，通常与 attach 在同一初始化流程中由持有方赋值）。文档仅记录事件系统侧契约：**使用 terminal 前必须先 acl_key_gen 并保存**。

### 5.4 链路三：配置加载（Config_Loader 发送 Config/Load 事件）

`Config_Loader` 代表典型的"发布方"流程。源码路径：`引擎层\src\tools\Config_Loader\core\配置加载器.cpp`。

**构造时序**：

```
Config_Loader::Config_Loader()
  └─ this->acl_key = event_terminal.acl_key_gen();
       └─ Event_Terminal::acl_key_gen()
            ├─ acl_key 无值 → 循环 key_generator() 直到非 0
            ├─ acl_key = 非零随机值
            └─ 返回 acl_key.value()
```

**act() 时序（核心发布链路）**：

```
Config_Loader::act()
  ├─ 1. content_scan(paths)          // 递归扫描 exe目录/scan_content 下的路由文件
  ├─ 2. 若 paths 为空 → Log::info + return
  ├─ 3. 对每个路由文件：
  │     ├─ 3.1 file_read(read_path, route_config)     // 读取 JSON（数组）
  │     ├─ 3.2 校验 route_config 是数组；每个元素含 "module" 与 "config_path" 字符串
  │     ├─ 3.3 skip_safety_inspect(u8config_path)     // 路径安全检查（assets/config 前缀、禁 ".."）
  │     ├─ 3.4 file_read(absolute_config_path, config_data)  // 读取目标模块配置文件
  │     ├─ 3.5 构造事件：
  │     │      shared_ptr<event> evt(new(nothrow) event());   // 默认构造
  │     │      evt->category = "Config";
  │     │      evt->tag = "Load";
  │     │      evt->target_object = module;      // 例如 "Collision_Proxy"
  │     │      evt->config = config_data;        // 配置文件 JSON 载荷
  │     └─ 3.6 发送：event_terminal.send({ evt }, acl_key)
  │            ├─ 密钥检查（未生成 → warn + false）
  │            ├─ 密钥比对
  │            ├─ events_sender 已注册？→ (*events_sender)({evt})
  │            │      └─ lambda3 → broker.receive({evt})
  │            │             └─ 多事件重载 → 循环 broker.receive(evt)
  │            │                    ├─ category="Config" 非空且 acl_set 有 "Config" → 继续
  │            │                    ├─ tag="Load" 非空 → 继续
  │            │                    ├─ target_object="Collision_Proxy" 非空且在 mapping_set → 定向投递
  │            │                    │      └─ event_entries[0](evt)
  │            │                    │             └─ Collision_Proxy 的 event_receiver 回调
  │            │                    │                    └─ Collision_Proxy::event_process(evt)
  │            │                    └─ （返回）
  │            ├─ 成功 → Log::info("Config_Loader::已发送配置事件: {}", module)
  │            └─ 失败 → Log::info("Config_Loader::未注册事件中转站依赖\n配置工作无法完成"); return;
  └─ 4. 继续处理下一个路由条目
```

**Config/Load 到达 Collision_Proxy 后的处理**（`event_process`）：

```
Collision_Proxy::event_process(evt)
  ├─ evt 空检查
  ├─ category=="Config" && tag=="Load"？
  │    ├─ 是：target_object != module_name → 忽略（其他模块的配置不处理）
  │    │       target_object == module_name → config_apply(evt->config)  // 应用配置
  │    └─ 否：进入 Collision 指令分派（略）
  └─ 若 category 非 "Config" 且非 "Collision" → Log::debug("未识别事件")
```

### 5.5 链路四：事件发布与回告（Collision_Proxy::event_publish）

`Collision_Proxy` 处理完 ColliderBuild 等指令后，需要把结果告知请求方，源码实现：

```cpp
	//事件发布
	bool Collision_Proxy::event_publish(const string& tag, const json& payload)
	{
		//构造发布事件
		shared_ptr<event> evt = event_terminal.build(module_name, "", "Collision", tag);
		//若事件内存分配失败
		if (!evt)
		{
			Log::error("Collision_Proxy::事件内存分配失败，发布中止");
			return false;
		}
		//写入事件载荷
		evt->config = payload;

		//发送事件（事件终端按单事件通道发送）
		if (!event_terminal.send(evt, acl_key))
		{
			Log::warn("Collision_Proxy::事件({})发送失败，事件发送通道不可用", tag);
			return false;
		}

		return true;
	}
```

**时序**：

```
Collision_Proxy::event_process（ColliderBuild 分支）
  ├─ collider_ID = collider_build(region)
  ├─ 若失败 return（无回告）
  ├─ payload["region"] = region; payload["collider_ID"] = *collider_ID
  └─ event_publish("ColliderBuildResult", payload)
       ├─ build(module_name, "", "Collision", "ColliderBuildResult")
       │     → shared_ptr<event>(new(nothrow) event("Collision_Proxy","","Collision","ColliderBuildResult"))
       ├─ evt->config = payload
       └─ send(evt, acl_key) → 单事件通道
            └─ (*event_sender)(evt) → lambda2 → broker.receive(evt)
                 ├─ category="Collision" 已注册 → 继续；tag 非空 → 继续
                 ├─ target_object 为空 → 走广播
                 ├─ acled_IDs = 全订阅行.ID_set + 标签匹配行.ID_set
                 ├─ sender_ID = mapping_set["Collision_Proxy"]（即 0）
                 └─ 对每个 id != sender_ID 的订阅者调用 event_entries[id](evt)
                      └─ 若请求方已订阅 Collision/ColliderBuildResult 则收到
```

**注意**：`event_publish` 发送的事件 `sender_object = module_name`、`target_object` 为空，因此走**广播**而非定向；结果事件 `tag` 为 "ColliderBuildResult"（订阅清单里没有，但若其他模块全订阅了 Collision 大类，或请求方定向注册该标签，就能收到）。

### 5.6 链路五：Subscriber 探测协议（process）

适用于需要"询问某模块是否存在/呼叫某模块"的场景：

```
调用方（假设模块 X）
  ├─ evt = terminal.build("X", "目标模块名", "Subscriber", "Check")   // 或 Call
  ├─ terminal.send(evt, acl_key) → broker.receive(evt)
  │    ├─ category="Subscriber" 已注册？若 acl_set 无 "Subscriber"，receive 直接丢弃！
  │    └─ 注意：若无人注册过 Subscriber 分类，Check/Call 事件无法进入 process
  └─ 中转站持有者（或调用方）在收到应答前调用 broker.process(evt)：
       ├─ sender_object 非空、target_object 非空、sender 已注册 → 继续
       ├─ category=="Subscriber" && tag=="Check|Call" → 构造 Response 事件
       ├─ mapping_set.find(target_object)：
       │    ├─ 不存在 → response->config["object_existence"] = false
       │    └─ 存在 → response->config["object_existence"] = true
       │              若 Call → event_entries[target_ID](evt)  // 转发原事件给目标
       └─ 返回 response_event（Check/Call 调用方拿到应答）
```

**调用前提**：`process` 前需要 `acl_set` 中存在 "Subscriber" 分类（否则 `receive` 已丢弃、事件进不了 process 的正常流转）。若使用定向发送（target_object 非空且目标注册），则即使无 Subscriber 订阅也能让目标收到 Call 转发——但**应答事件仍然依赖调用方直接调用 `process`**。

### 5.7 典型完整时序图（一次 Config/Load 端到端）

```
时间轴
────────────────────────────────────────────────────────────────────────────
引擎启动

  │ terminal.attach_handler_register(lambda1)
  │ terminal.event_sender_register(lambda2)      // lambda2 → broker.receive
  │ terminal.events_sender_register(lambda3)     // lambda3 → broker.receive(批量)
  ▼

  │   ├─ interface_check(ATTACH_HANDLER) == true
  │   ├─ event_receiver_register(event_process 包装)

  │        └─ lambda1 → broker.info_register(...)   // 建立订阅表
  ▼

  │ acl_key = event_terminal.acl_key_gen()
  ▼
Config_Loader::act()
  │ 扫描路由 → 读取 module/config_path → 安全检查 → 读取配置 JSON
  │ 构造 evt(category="Config", tag="Load", target="Collision_Proxy", config=配置数据)
  │ terminal.send({evt}, acl_key)
  │   └─ lambda3 → broker.receive({evt})
  │        └─ broker.receive(evt)
  │             ├─ 定向投递: event_entries[0](evt)
  │             │     └─ Collision_Proxy::event_process(evt)
  │             │          └─ Config/Load → config_apply(evt->config)
  │             └─ 完成
  ▼
（此后 Collision_Proxy 处理配置，可能 event_publish 广播结果事件……）
────────────────────────────────────────────────────────────────────────────
```

### 5.8 与其他模块协作的注意事项

1. **Config_Loader 依赖"发送通道已注册"**：若引擎初始化未注册 `events_sender`，`send` 返回 false，`Config_Loader` 输出"未注册事件中转站依赖"并中止配置工作。
2. **Collision_Proxy 依赖"接入通道已注册"**：若 `ATTACH_HANDLER` 未注册，`attach` 前置检查直接中止接入。
3. **订阅与发送的相对顺序**：`info_register` 必须发生在 `receive` 之前（先订阅后发事件），否则事件因无订阅者被丢弃。引擎初始化顺序应保证：中转站接线 → 各模块 attach → 各模块发送。
4. **模块名唯一性**：`mapping_set` 以模块名做键；两个模块用同名注册会共享同一订阅者 ID 且后注册者覆盖事件入口。模块名应全局唯一。
5. **事件对象的生命周期**：事件以 `shared_ptr` 流转，广播时被 N 个订阅者共享；若某订阅者在处理中修改 `evt->config`，其他订阅者会看到修改后的内容（**共享可变状态**）——需要订阅方遵守"只读"约定或自行拷贝。

## 七、本版次相关与遗留事项

### 7.1 本版次（089b070）改动情况

**本模块（事件系统）在 089b070 版次无改动**。本版次聚焦"碰撞模块单文件拆分为多编译单元"，事件系统作为碰撞模块的通信依赖被引用，但事件系统自身源码未发生变更（`事件.h` 中 `std::hash` 特化的注释风格、`Event_Broker` 的三表结构、`Terminal_Interface` 的注册表机制均保持既有状态）。

### 7.2 源码中的已知注意事项与潜在缺陷（供后续版本关注）

1. **`Event_Broker::process` 缺省路径无 return（既有 warning C4715，位于 `事件中转器.cpp` 第 221 行附近）**：非 `Subscriber/Check|Call` 事件会"掉落"函数尾，返回未定义值。这是**既有编译告警 C4715**（"不是所有控件路径都返回值"），本版次（089b070）及前序版次（fa8459a）均未修复，属已知缺陷。**建议**：在函数末尾补 `return nullptr;`。
2. **`Event_Broker::receive` 的 `acled_IDs` 类型收缩**：`uint16_t` 承接 `int32_t` 订阅者 ID，订阅者 ≥ 65536 时误投/漏投。**建议**：改为 `vector<int32_t>`。
3. **广播重复投递**：模块同时全订阅某大类 + 订阅该大类下具体标签时，`acled_IDs` 含重复 ID，事件被调用两次。**建议**：收集后去重（如对 `acled_IDs` 排序去重或使用 `unordered_set`）。
4. **`std::hash<event>::operator()` 的 noexcept 与 `dump()` 抛异常冲突**（源码注释已自我标注）：config 含 NaN/Inf 时 `dump()` 抛异常 → `std::terminate`。**建议**：`dump()` 加 try-catch 或配置 `allow_nan_inf`。
5. **`interface_check` 与指针直判不一致**：`send` 查指针、`interact` 查 `map`，两套判定并存。**建议**：统一为一种检查方式。
6. **`Terminal_Interface::map` 重复记录**：重复注册同一接口导致 map 冗余增长。**建议**：注册前查重或改用集合。
7. **`attach` 中"接收入口未注册时用 lambda 包装 receive"的语义**：若模块先 `attach` 后注册 `event_receiver`，中转站的 `event_entries` 中保存的是**旧 lambda**（指向 `this->receive`），之后模块再注册 `event_receiver` 时，`event_entries` 并不会自动更新——**中转站侧仍会调用 receive（进入 event_set 积压队列），而不是模块新注册的实时回调**。`Collision_Proxy` 的流程（先注册回调再 attach）规避了此问题；其他模块若反序操作需注意。
8. **定向投递不排除发送者**：`receive` 的定向分支直接 `event_entries[target_ID](evt)`，发送者即目标时模块会收到自己的事件；广播分支则排除。两分支语义不对称，调用方需知晓。
9. **`events_handler` 按值传 `vector<shared_ptr<event>>`**：多事件接口参数是拷贝（shared_ptr 浅拷贝，代价为 vector 拷贝 + 引用计数增减），批量事件较大时建议改用 const 引用（但签名已定，改动需评估影响面）。
10. **`Config_Loader` 使用 `send({ evt }, acl_key)` 多事件重载**：实际只发一个事件，依赖 `events_sender` 通道注册；若引擎只注册了单事件通道 `event_sender` 而未注册 `events_sender`，`send` 多事件重载会失败。**接线时两个通道都应注册**。
11. **`Collision_Proxy::attach` 未在自身方法内取得密钥**：`acl_key` 必须由外部初始化流程赋值（先 `acl_key_gen` 再 attach），否则 attach 的密钥比对永远失败。文档记录此契约供集成参考。
12. **事件处理回调的悬空捕获风险**：`event_receiver_register` 捕获 `this`（如 Collision_Proxy 的 lambda），若模块在 `Event_Broker` 仍持有其入口时析构，再收到事件将调用悬空 `this`。**建议**：模块析构时从事件系统注销（当前版次无注销接口，需后续补充）。
13. **`acl_key_gen` 仅能成功一次（既有约束）**：`Event_Terminal::acl_key_gen` 在 `acl_key` 已持有值（`has_value()` 为真）时直接返回 `0` 表示"密钥已存在"，**无法重新生成/轮换密钥**。这意味着：① 一旦生成密钥，终端终身绑定该密钥，无法重置（除非整体析构重建终端）；② 返回值 `0` 是"已存在"哨兵，与"生成失败"在语义上无法区分（调用方若把 `0` 当失败会误判）。这是既有的设计约束，本版次未变更。**建议**：在文档/调用方层面明确"每个终端只调用一次 `acl_key_gen`"。
14. **密钥错误分支返回空结果（既有约束）**：`Event_Terminal::query` 在密钥不匹配（`this->acl_key != acl_key`）时返回 `nullptr` 而非"空集合指针"，调用方若不判空直接解引用会崩溃；`attach`/`interact`/`send`/`clear` 在密钥不匹配时返回 `false`（其中 `attach` 的密钥不匹配分支**不打日志**，仅静默返回 false，与"密钥未生成"分支的 `Log::warn` 行为不一致）。这是既有行为约束，调用方应统一按"返回 false / nullptr 即失败"处理。
15. **`Event_Broker::process` 中 `target_object_check` 已被移除（既有变更）**：`Event_Broker::process` 仅检查 `sender_object` 是否存在于 `mapping_set`，**不再检查 `target_object` 是否存在于 `mapping_set`**（`target_object` 的存在性改由 `Subscriber/Response` 应答中的 `config["object_existence"]` 承载，见 4.5 与 2.4.4）。若旧代码依赖"process 校验目标存在性"，本版次该防线已移除——`Call` 事件在目标不存在时不会转发（`event_entries[it->second]` 仅在目标存在分支执行），但 `process` 本身仍返回 `Response` 事件（`object_existence=false`）。重开发时勿再假设 process 会拦截非法目标。

### 7.3 接口变更建议汇总（备忘）

- 为 `Event_Broker` 增加 `unregister(module_name)` 注销接口（配合 7.2-12）。
- 为 `Terminal_Interface::function_register` 增加查重。
- 统一 `receive` 定向/广播的"排除发送者"语义。
- 补全 `process` 的兜底 return。

```cpp
	bool Event_Terminal::attach(const string& module_name, const vector<event>& needed_events,
		const int64_t& acl_key)
	{
		//若当前尚未生成密钥
		if (!this->acl_key.has_value())
		{
			Log::warn("Event_Terminal::密钥未生成\n功能已锁定");
			return false;
		}
		//若密钥权限未匹配
		if (this->acl_key != acl_key)
			return false;

		//简化表示路径
		auto& Tinterface = terminal_interface;

		//若未注册单事件接收入口
		if(!Tinterface.event_receiver)
		{
			//包装单事件接收入口
			auto it = [this](shared_ptr<event> evt) -> void
				{
					this->receive(evt);
				};
			//接入中转站
			(*Tinterface.attach_handler)(module_name, needed_events, it);
		}
		else
		    //接入中转站
		    (*Tinterface.attach_handler)(module_name, needed_events, *Tinterface.event_receiver);
		//返回接入成功
		return true;
	}
```

**走读要点**：
- 密钥双检查（未生成/不匹配）。
- 接收入口选择逻辑：**若模块已注册 `event_receiver`，中转站拿到的是模块自己的实时处理回调；否则拿到 `receive` 的包装 lambda（事件进入 event_set 队列）**。因此"先注册回调再 attach"的顺序能保证中转站直达处理函数。

### H.1 Random_Generator（随机数生成器）与密钥

`Event_Terminal::key_generator` 类型为 `Random_Generator`（`src\tools\Random\随机数生成器.h`，39 行声明 / cpp 83 行实现）。核心算法为 **PCG32（Permuted Congruential Generator，32 位输出）**：

```cpp
namespace engine
{
	class Random_Generator
	{
		// PCG32 状态结构体
		struct pcg32
		{
			uint64_t state = 0;
			uint64_t inc = 0;
		} g_pcg32;

		uint64_t seed = 0;

		// 底层原始 32 位随机数生成（PCG32 核心）
		uint32_t pcg32_random_raw();

		// 生成 [min, max] 范围内的 64 位随机数（无偏）
		int64_t pcg64_random_range(int64_t min, int64_t max);

	public:
		// 生成一个 int64_t 全范围随机数
		int64_t operator()();

		// 生成 [min, max] 范围内的 int64_t 随机数（包含两端）
		int64_t operator()(int64_t min, int64_t max);

		// 构造函数
		Random_Generator(void) ;
		explicit Random_Generator(uint64_t seed_out);

		// 种子初始化
		void pcg32_seed_init(uint64_t seed_out);
		void pcg32_seed_init();
	};
}
```

**实现要点**（随机数生成器.cpp）：

```cpp
// ======== 原始 PCG32 核心（返回 uint32_t）========
uint32_t Random_Generator::pcg32_random_raw()
{
    uint64_t old_state = g_pcg32.state;
    g_pcg32.state = old_state * 6364136223846793005ULL + g_pcg32.inc;
    uint32_t xorshifted = (uint32_t)(((old_state >> 18u) ^ old_state) >> 27u);
    uint32_t rot = (uint32_t)(old_state >> 59u);
    return (xorshifted >> rot) | (xorshifted << ((-(int)rot) & 31));
}
```

- 状态递推：`state = state * 6364136223846793005ULL + inc`（线性同余）。
- 输出函数：Xorshift + 旋转（rot 由高 5 位决定），输出 32 位。
- **无参种子初始化**（默认构造调用）：以 `high_resolution_clock` 纳秒 ^ `time(nullptr)` ^ 递增计数器 混合为种子，保证每次运行种子不同：

```cpp
void Random_Generator::pcg32_seed_init()
{
    static uint64_t counter = 0;
    auto now = std::chrono::high_resolution_clock::now();
    auto ns = std::chrono::duration_cast<std::chrono::nanoseconds>(now.time_since_epoch()).count();
    uint64_t seed = static_cast<uint64_t>(ns) ^ static_cast<uint64_t>(std::time(nullptr)) ^ (++counter);
    g_pcg32.state = 0;
    g_pcg32.inc = (seed << 1u) | 1u;
    (void)pcg32_random_raw();   // 预热一次
}
```

- **64 位随机数**（`operator()()`）：组合两次 32 位输出 `(high << 32) | low`，强制转换 `int64_t`——**覆盖全部 int64 值域，包括负数**。这正是 `acl_key_gen` 要求"非 0"的原因：全范围随机数可能为 0，须重试。
- **区间随机** `operator()(min, max)`：拒绝采样法（rejection sampling）保证无偏；`range == 0`（全范围）时直接返回 `operator()()`。
- **密钥安全性评估**：64 位随机密钥，猜测成功概率约 2^-63（每次尝试），暴力枚举不可行；但密钥在进程内明文存储（`std::optional<int64_t>`），且不参与任何加密用途——仅作"调用资格"标记，安全模型是"防误用"而非"防恶意攻击"。

## 附录 I：常见问题（FAQ）

### I.1 为什么 `send` 返回 true 但模块没收到事件？

可能原因（按概率排序）：
1. 事件 `category` 未被任何模块订阅过（`acl_set` 无该分类）→ `Event_Broker::receive` 直接丢弃。
2. 事件 `tag` 为空 → 被丢弃。
3. `target_object` 指向未注册模块 → 退化为广播，但无人订阅该 category/tag。
4. 发送者就是唯一订阅者 → 广播时被"排除自身"逻辑跳过。
5. 目标模块 `attach` 失败（未注册订阅）。
6. 模块注册了 `event_receiver` 回调但回调内部丢弃（如 `Collision_Proxy` 对非本模块的 Config/Load 直接 return）。

排查顺序：先确认 `attach` 成功（日志无"接入失败"），再确认 `acl_set` 中存在该分类，再检查 target 是否注册、tag 是否非空。

### I.2 `acl_key_gen` 返回 0 是什么意思？

表示密钥**已经生成**（重复调用）。0 不是有效密钥——任何受保护接口用 0 调用都会因 `this->acl_key != 0` 而失败。若首次调用就返回 0（理论上不可能，生成循环保证非 0），说明内部状态异常。

### I.3 事件接收后去哪里了？

取决于模块是否注册了 `event_receiver`：
- 未注册：进入终端 `event_set` 队列，可用 `query(acl_key)` 查阅、`clear(acl_key)` 清空。
- 已注册：直接调用模块回调（如 `Collision_Proxy::event_process`），**不进入队列**。

### I.4 模块如何全订阅某大类？

在 `needed_events` 中声明 `event("", "", "Collision", "")`（tag 为空）。注意：
- `info_register` 会把它登记到全订阅行（tag=="" 行）。
- `receive` 广播时该模块会收到该大类下所有带标签的事件。
- **同一模块若同时在清单中声明了具体标签，也会被并入全订阅行**（匹配循环先命中全订阅行即 break），实际效果等同全订阅。

### I.5 为什么 `Event_Broker::process` 返回的 vector 里有 nullptr？

多事件重载对每个入参调用单事件重载并把返回值（可能为 nullptr）全部 push 进 buffer。入参中的事件若缺发送者/目标/发送者未注册，或非 Subscriber/Check|Call 组合（缺省路径未定义值），对应槽位即为 nullptr 或未定义值。调用方须逐元素判空。

### I.6 如何调试"事件没分发"？

- 检查引擎初始化是否注册了 `attach_handler`、`event_sender`、`events_sender`（`interface_check` 可查）。
- 检查模块 `attach` 是否成功（有无 `Log::error`）。
- 检查发送侧 `send` 返回值。
- 检查 `Event_Broker` 三表内容（可在调试器中查看 `acl_set`/`mapping_set`/`event_entries`）。

### I.7 事件可以在多线程使用吗？

**当前版次事件系统不是线程安全的**：
- `Event_Terminal::event_set`（vector）无锁。
- `Event_Broker` 三表（unordered_map）无锁。
- `Terminal_Interface` 注册表无锁。
- 分发调用 `std::function` 也是同步的。
若多线程同时 `send`/`receive`/`info_register`，会产生数据竞争。当前引擎为单线程帧循环架构，无此问题；未来多线程化需加锁或改为无锁队列。

### I.8 `receive` 和 `process` 有什么区别？

- `receive`：**分发**——把事件按订阅关系投递给订阅者（发往各终端）。
- `process`：**处理/应答**——由中转站持有者调用，执行 Subscriber 协议（Check/Call），返回应答事件。
二者职责不同：`receive` 是"事件广播"，`process` 是"请求-应答"。目前没有看到事件系统内部自动串联二者（`process` 不自动调用 `receive` 的结果），应答需要显式调用。

### I.9 为什么 `Collision_Proxy` 订阅清单里有 `Config/Load`？

因为 `Config_Loader` 的配置事件是**定向投递**（target_object=module_name），定向投递不经过 acl 匹配也能送达。`Collision_Proxy` 声明 Config/Load 订阅属于**冗余声明**（无害）——但若 Config_Loader 未来改为广播方式发送，该订阅就变成必需项。此冗余声明同时也使"Collision 模块能收到 Config/Load"这一意图显式化。

### I.10 事件对象的 config 可以被多个订阅者共享修改吗？

可以——`shared_ptr<event>` 广播时所有订阅者共享同一对象。某订阅者修改 `evt->config` 后，其他订阅者（若在同一次分发循环中稍后执行）会看到修改。**当前引擎中订阅者均按只读约定处理事件**，但代码层面无强制。如需隔离，订阅方应自行 `evt->config = json()` 深拷贝后再改。

## 附录 J：性能与复杂度分析

### J.1 `Event_Broker::info_register`

- 订阅者登记：`unordered_map` 操作均摊 O(1)。
- 每个 needed_event：遍历该分类的 `acl_row`（O(行数)），行内 ID_set 去重检查 O(ID 数)。总体 O(N × (行数 + ID数))，N 为订阅事件数。
- 引擎规模下（每模块十来个事件、几十个模块）开销可忽略。

### J.2 `Event_Broker::receive`（单事件）

- 丢弃检查：O(1)。
- 定向投递：O(1)（两次 unordered_map 查找 + 一次回调）。
- 广播：遍历 `acl_row` 收集 `acled_IDs` O(行数 × ID 数) + 分发循环 O(acled_IDs 数)。每个订阅者一次回调调用。
- **重复 ID 会重复调用回调**（前文已述），最坏情况 O(2 × 订阅者数)。

### J.3 `Event_Broker::process`

- 三连检查 O(1)；Subscriber 分支 O(1)（一次 find + 一次回调）。

### J.4 `Terminal_Interface::interface_check`

- 线性遍历 `map`，O(已注册接口数)。7 种接口 + 重复注册次数，量级极小。

### J.5 内存开销

- 每个事件对象：`event` 本体（3 个 std::string + json + 共享控制块）≈ 数百字节量级。
- `shared_ptr` 广播：每次引用计数原子增减（无锁时非原子，见 I.7）。
- `event_set` 积压：若模块不消费，队列无限增长——`receive` 无上限检查。**长期运行模块应周期性 `clear` 或注册处理回调**。

## 附录 Q：事件流转状态机

事件从构造到被消费，经历以下状态：

```
┌─────────┐   build / new    ┌──────────┐   send+密钥   ┌──────────┐
│ 未构造    │ ───────────────▶│ 已构造     │ ────────────▶│ 已入站     │
│ (无对象)  │                  │ (shared_ptr)│             │ (Broker)  │
└─────────┘                  └──────────┘             └────┬─────┘
                                                          │ receive
                                        ┌─────────────────┴─────────────────┐
                                        ▼                                 ▼
                               ┌────────────────┐                  ┌──────────────┐
                               │ 定向投递（target  │                 │ 广播分发       │
                               │ 存在于 mapping） │                 │ (acl 匹配)    │
                               └───────┬────────┘                  └──────┬───────┘
                                       │                                  │
                                       ▼                                  ▼
                            ┌──────────────────────────────────────────────────┐
                            │  分发到订阅者：event_entries[订阅者ID](evt)        │
                            └──────────────────────┬───────────────────────────┘
                                                   │
                              ┌────────────────────┴─────────────────────┐
                              ▼                                          ▼
                     ┌──────────────────┐                        ┌──────────────────┐
                     │ 已注册 event_receiver │                     │ 未注册（原生通道）  │
                     │ → 模块实时处理回调     │                     │ → 进入 event_set   │
                     └──────────────────┘                        └──────────────────┘
                                                                        │
                                                        query(密钥) 查阅 / clear(密钥) 清空
                                                                        ▼
                                                                  事件 shared_ptr 引用归零 → 析构
```

**状态说明**：
1. **未构造**：事件对象尚未分配。由 `build` 或 `new(nothrow)` 进入"已构造"。
2. **已构造**：事件在发送方手中，可填充字段。`send`/`interact` 需要密钥。
3. **已入站**：事件进入 `Event_Broker`，由 `receive` 分发。此状态下事件被 0~N 个订阅者共享。
4. **分发**：定向或广播，调用各订阅者的入口回调。
5. **落地**：进入订阅者的 `event_set`（可查询/清空）或模块实时回调。
6. **消亡**：所有 shared_ptr 引用释放后事件对象析构。

**转换条件**：
- 已构造 → 已入站：`send` 成功（密钥匹配 + 发送入口已注册）。
- 已入站 → 丢弃：category/tag 为空或无人订阅该分类（receive 内 return）。
- 已入站 → 分发：receive 定向/广播路径。
- 已构造 → 永不入站：`send` 返回 false（密钥未生成/不匹配/发送入口未注册）。

## 附录 T：设计权衡与备选方案讨论

### T.1 为什么用"终端 + 中转站"两层而不是单一全局单例？

- **终端（Event_Terminal）**：每模块一个，携带密钥与本地事件队列，天然表达"模块私有事件状态"；移动语义便于组合进模块类。
- **中转站（Event_Broker）**：全局共享，集中管理订阅表与转发表。
- 若只有全局单例，则密钥、队列都要挂在单例上，模块边界模糊；若只有终端，则订阅关系分散，无法统一广播。两层分离实现"模块私有"与"全局共享"的平衡。
- **代价**：两对象间通过 `std::function` 回调桥接，增加间接层；接线代码（引擎初始化）需手动把中转站方法包装进终端接口，属"样板代码"。

### T.2 为什么回调用 `unique_ptr<std::function>` 而不是直接成员？

- 直接成员 `std::function` 也可行且更简单；`unique_ptr` 方式让 `memory_malloc` 能显式处理 `new(nothrow)` 失败，且注册过程统一。
- **权衡**：增加堆分配与解引用开销（每次调用 `(*ptr)(...)` 一次间接寻址），但在事件系统低频路径下可忽略。
- 若追求简单，未来可重构为 `std::optional<std::function>` 或直接成员。

### T.3 为什么 `Event_Broker` 用 `unordered_map` 而非 `vector`/`map`？

- `mapping_set`、`event_entries` 按模块名/编号查找，`unordered_map` 均摊 O(1)。
- `acl_set` 按 category 字符串查找，`unordered_map` O(1)；行内是 `vector`（数量小，线性匹配足够）。
- 若事件量大、需保序，可换 `std::map`（有序，O(log n)）——当前无保序需求。

### T.4 权限密钥 vs 其它鉴权方案

- 备选：直接传 `Event_Terminal*` 指针作为凭据、或布尔开关、或加密令牌。
- 当前方案（`optional<int64_t>` 随机密钥）优点：简单、无需额外依赖、可区分"未生成"与"不匹配"两种失败态。
- 缺点：密钥不随调用者变化（粗粒度）；若模块间共享同一终端（如 Config_Loader 与 Collision_Proxy 若用同一 terminal），两者持同一密钥，无法区分权限。

### T.5 事件是同步分发还是异步队列？

- 当前 `send` → `receive` → 分发回调**全程同步**（调用栈内完成）。好处：时序确定、无需锁；坏处：订阅者回调若耗时，会阻塞发送者帧循环。
- 若未来需要异步，可在 `Event_Broker` 入口加工作队列，由引擎主循环或独立线程 drain。当前架构为同步设计预留了扩展点（`receive` 作为唯一入口，可替换为队列 push）。

### T.6 `event` 用 `shared_ptr` 而非值/`unique_ptr`？

- `shared_ptr` 支持多订阅者共享同一事件对象（广播零拷贝）；`unique_ptr` 无法多所有权；值传递每次分发都要深拷贝（含 json），代价高。
- 代价：引用计数开销 + 共享可变状态风险（前文 I.10）。

## 附录 Y：事件系统与碰撞模块的联动细节（089b070 版次背景）

### Y.1 版次背景

089b070 版次的主题是"碰撞模块单文件拆分为多编译单元"。碰撞模块原为单文件（可能包含碰撞空间、碰撞体、代理等全部逻辑），本版次拆分为多个编译单元（.cpp/.h），其中 `Collision_Proxy\core\事件交互.cpp` 是拆分后的"事件交互"单元。事件系统本身未改动，但作为拆分后的碰撞模块的**事件接入面**，与本版次直接相关。

### Y.2 拆分后的协作结构（推测示意）

```
引擎层\src\core\spatial\collision\
├── Collision_Proxy\
│   ├── （代理头文件）
│   └── core\
│       ├── 事件交互.cpp      ← 本文档走读的消费方单元（272 行）
│       ├── （其他拆分单元，如空间/碰撞体管理）
│       └── ...
└── ...
```

`事件交互.cpp` 承担碰撞模块与事件系统的全部交互：attach（订阅）、event_process（分派）、event_publish（发布）。拆分后，这些职责集中在独立编译单元，便于单独编译与维护。

### Y.3 事件驱动的碰撞模块工作循环

```
帧循环：
  ┌────────────────────────────────────────────────────────┐
```

## 附录 Z：事件系统源码质量评估（导航辅助）

### Z.1 优点

1. **解耦彻底**：终端与中转站无类型依赖，通过 `std::function` 桥接，模块可插拔。
2. **权限显式**：`optional` 密钥 + "未生成即锁定"防御，杜绝误用。
3. **命名清晰**：`send/receive/attach/process/query/clear` 语义直白；`interface_ID` 枚举名与用途对应。
4. **内存安全基调**：`new(nothrow)` + `unique_ptr`/`shared_ptr`，避免裸指针与异常泄漏。
5. **注释完整**：关键分支均有中文注释，可读性好。
6. **订阅模型灵活**：全订阅/标签订阅、定向/广播、单/多事件重载并存。

### Z.2 可改进点（结合第七章）

1. `process` 缺省路径返回值未定义（U12）。
2. `acled_IDs` 类型收缩（U11）。
3. 广播重复投递（U10）。
4. `interface_check` 与指针直判不一致（前文 4.2）。
5. 无注销接口（U19 关联）。
6. 无线程安全保证（U17）。
7. `event_entries` 用 `operator[]` 可能插入空 function（D.2）。
8. `hash` 的 noexcept 与 dump 抛异常冲突（U18）。
9. `Terminal_Interface` 冗余包含随机数生成器头（M.1）。
10. `using` 别名污染全局命名空间（O.1/O.2）。

## 附录 EE：Event_Terminal 的移动语义深入分析

### EE.1 为什么需要移动语义？

`Event_Terminal` 通常作为模块类的成员。模块对象可能放入容器（如 `std::vector<Module>`）、被工厂函数返回、或被引擎注册表管理——这些场景需要移动构造/赋值。`Event_Terminal` 显式 `= default` 移动操作，语义如下：

- 移动构造：`acl_key`（optional，移动后源对象无值）、`key_generator`（Random_Generator 移动/拷贝，PCG 状态复制）、`event_set`（vector 移动，源清空）、`terminal_interface`（Terminal_Interface 移动，unique_ptr 转移所有权）。
- **移动后源对象状态**：源 `Event_Terminal` 变为"密钥丢失 + 队列清空 + 接口为空"的空壳。**若移动后误用源对象**：受保护操作全部因密钥未生成而锁定（日志告警），receive 会进入空 event_set——行为可预测但需避免。

### EE.2 为什么没有拷贝语义？

- `Terminal_Interface` 含 7 个 `unique_ptr`，拷贝被隐式删除。
- `Random_Generator` 可拷贝（无禁用），但拷贝 PRNG 状态可能导致两个生成器产生相同序列（若用于密钥，安全性降低）。
- 因此 `Event_Terminal` 拷贝被禁用是**正确设计**：每个终端应是唯一实体，复制终端会复制密钥（权限扩散）与回调（重复注册风险）。

### EE.3 移动对已接入中转站的影响

若模块在 attach（已接入中转站、`event_entries` 已登记）后移动 `Event_Terminal`：

- 中转站的 `event_entries[ID]` 保存的是**回调对象**（lambda 或 std::function），其中 `attach` 时若未注册 `event_receiver`，保存的是捕获 `this`（旧终端地址）的 lambda——**移动后旧地址失效，事件会分发到已移动的旧终端（UB）**。
- 若 `attach` 时已注册 `event_receiver`，回调捕获的是模块的 `this`（模块对象地址），与终端移动无关——安全。
- **结论**：终端应在 attach 前完成移动/就位；attach 后不应移动终端（除非模块通过 `event_receiver` 独立于终端地址）。

### EE.4 与容器结合

```cpp
std::vector<Event_Terminal> terminals;
terminals.push_back(Event_Terminal{});   // 移动构造入容器
terminals.emplace_back();                 // 原地构造
```

容器扩容会移动已有元素（若元素已生成密钥并接入中转站，见 EE.3 的风险）。**建议**：终端用 `unique_ptr` 或固定地址存储，避免容器重排。

## 附录 FF：Event_Broker 的多实例与生命周期

### FF.1 引擎中 Event_Broker 是单例吗？

源码未强制单例——`Event_Broker` 是普通类，可多实例。但**事件系统语义上要求所有模块接入同一个 Broker**：若两个 Broker 实例，各自维护独立的 `mapping_set`/`acl_set`，模块 A 接入 Broker1、模块 B 接入 Broker2，则 A 发的事件 B 收不到（订阅表分离）。

**约定**：引擎中应存在**唯一**的 Event_Broker 实例（由引擎核心持有），所有模块的终端回调都指向它。

### FF.2 Event_Broker 生命周期

- 构造：三表空。
- 使用期：`info_register` 增加订阅者与订阅关系；`receive` 分发；`process` 应答。
- 析构：三表自动释放（回调 `std::function` 释放；若回调捕获了模块对象指针，不自动解引用，仅释放函数对象本身）。
- **注意**：`event_entries` 中的回调若捕获模块 `this`，模块析构后 Broker 仍持有悬空回调——Broker 析构不感知。因此**模块应比 Broker 先析构**（或模块析构前注销，当前版次无注销接口）。

### FF.3 与 Event_Terminal 的生存期配对

```
引擎生命周期：
  ├─ 构造 Event_Broker（最早）
  ├─ 构造各模块 Event_Terminal
  ├─ 模块 attach（终端回调登记进 Broker）
  ├─ ... 运行 ...
  ├─ 模块析构（先于 Broker）
  └─ 析构 Event_Broker（最后）
```

若顺序颠倒（Broker 先析构），模块终端中的回调仍指向已析构 Broker 的方法（lambda 捕获的 broker 引用）——调用即 UB。

## 附录 HH：事件系统设计模式对照

### HH.1 观察者模式（Observer）

事件系统本质是观察者模式的扩展实现：

| 观察者模式要素 | 事件系统对应 |
| --- | --- |
| 主题（Subject） | Event_Broker（中转站） |
| 观察者（Observer） | 订阅模块（如 Collision_Proxy） |
| 通知（Notify） | receive 分发 |
| 订阅/退订 | info_register（attach）/（无退订接口） |

### HH.2 中介者模式（Mediator）

Event_Broker 是典型中介者：模块间不直接通信，全部经由 Broker 转发，减少网状依赖。

### HH.3 命令模式（Command）

事件即"命令对象"：携带执行所需数据（config），由处理方解释执行。`Collision_Proxy::event_process` 对 Collision 大类事件的分派就是命令分发。

### HH.4 控制反转（IoC）/ 依赖注入（DI）

`Terminal_Interface` 的回调注册机制是 IoC 容器的一种轻量实现：终端不依赖具体中转站实现，运行时注入回调。

### HH.5 与 ECS（实体组件系统）的关系

事件系统可作为 ECS 的通信层：系统之间通过事件协作，实体状态经对象系统管理。事件系统不关心实体，只关心模块（订阅者）。

## 附录 II：错误处理哲学总结

事件系统的错误处理遵循以下原则：

### II.1 三层失败语义

| 层级 | 失败类型 | 处理方式 | 返回值 |
| --- | --- | --- | --- |
| 前置条件 | 密钥未生成/不匹配 | 告警（仅未生成）+ 拒绝 | false / nullptr |
| 能力缺失 | 接口未注册 | 静默拒绝 | false |
| 业务失败 | 事件无效/无订阅者 | 告警（部分）+ 丢弃 | void / nullptr |

### II.2 不抛异常策略

- 事件系统代码**不使用异常**：`new(nothrow)` 避免分配异常；`json::dump()` 的异常风险已标注（hash 特化）。
- 调用方不应期待事件系统抛异常——失败一律通过返回值表达。

### II.3 日志 vs 静默

- **会输出日志**：密钥未生成（warn）、process 校验失败（warn）、模块接入失败（error）。
- **静默失败**：密钥不匹配、接口未注册、事件被丢弃（category/tag 问题）。
- 设计考量：静默路径多为"正常可预期"的过滤逻辑（无订阅者、非本模块事件），避免日志噪音；告警路径多为"开发期错误"（忘取密钥、配置错误）。

### II.4 空指针防护

- `build` 分配失败 → 空 shared_ptr，调用方判空（Collision_Proxy 已做）。
- `receive` 收到空指针 → 无防护（解引用崩溃）——调用方应保证。
- `process` 的 response 分配失败 → 无防护（解引用崩溃）——缺陷 U14。
- `attach` 时 attach_handler 未注册 → 解引用空 unique_ptr（UB）——前提 U16。

## 附录 KK：常见误解澄清

### KK.1 "send 就是广播"

**错误**。`send` 只是把事件交给中转站；是定向还是广播由 `Event_Broker::receive` 根据 `target_object` 决定。`send` 本身不知道也不关心投递方式。

### KK.2 "attach 是发送事件"

**错误**。`attach` 是**订阅**（登记"我需要哪些事件"），不是发送。发送是 `send`。

### KK.3 "query 返回的指针可以修改"

**错误**。`query` 返回 `const std::vector<...>*`，只读。修改应通过 `clear`（清空）或直接操作成员（模块内部）。

### KK.4 "receive 是模块主动接收"

**部分正确**。`receive` 是被中转站调用的入口（回调性质），不是主动拉取。主动查阅用 `query`。

### KK.5 "process 会自动分发事件"

**错误**。`process` 只处理 Subscriber 协议并返回应答；它不遍历 acl 表分发。分发是 `receive` 的职责。

### KK.6 "事件系统是线程安全的"

**错误**。见 I.7，当前无锁、单线程假定。

### KK.7 "hash 与 == 一定一致"

**正确**（设计上）。但注意：`==` 比较 sender_object 吗？**不比较**。所以"只有 sender 不同"的两个事件既相等、哈希也相同——一致。若有人误以为 event 是全字段判等，会踩坑。

### KK.8 "全订阅 = 接收该分类所有事件（含空标签）"

**错误**。空标签事件在 `receive` 中被丢弃（U7/U8），全订阅只覆盖"带标签事件"。

### KK.9 "Config/Load 必须订阅才能收到"

**不必须**。Config_Loader 定向投递（target 已注册）不经过 acl 匹配。订阅 Config/Load 是冗余但无害（I.9）。

### KK.10 "interact 和 send 一样"

**不完全一样**。`send` 走发送通道（event_sender），`interact` 走交互通道（event_interactor）；两者均可绑定到 `Broker::receive`，但注册入口不同、接口检查方式不同（4.2）。

## 附录 LL：事件系统性能基准建议（供未来压测）

### LL.1 基准场景

| 场景 | 规模 | 关注指标 |
| --- | --- | --- |
| 单订阅者单事件 | 1 模块订阅 1 标签 | 端到端延迟（send→receive） |
| 多订阅者广播 | 100 模块订阅同标签 | 分发总耗时 |
| 定向投递 | 100 模块，定向 1 个 | 延迟对比广播 |
| 全订阅广播 | 100 模块全订阅某大类 | 分发耗时 |
| 重复注册 | 同模块注册 100 次 | interface_check 耗时退化 |

### LL.2 预估量级

- 单次 `send` → `receive` → 回调：微秒级（unordered_map 查找 + function 调用）。
- 100 订阅者广播：约 100 次 function 调用 + 若干 vector 操作，< 0.1ms。
- 事件系统开销在帧循环中占比极小（除非每帧上千事件）。

### LL.3 优化方向（如需）

- 广播前对 `acled_IDs` 去重（当前可能重复调用）。
- `interface_check` 改 `unordered_set`。
- 事件池化（复用 event 对象）减少分配。
- 若需要，`event_set` 改环形缓冲。

> 帮助开发者决定"该用哪个接口"。

```
│    ├─ 希望实时处理 → event_receiver_register(回调)（先于 attach）
│    ├─ 希望积压再批量处理 → 不注册回调，用 query + clear
│    └─ 两者都要 → 注册回调（回调内自行缓冲）
│

│    └─ attach(module_name, needed_events, acl_key)
│         ├─ 订阅特定标签 → event("", "", cat, tag)
│         └─ 订阅整个大类 → event("", "", cat, "")（全订阅）
│
├─ 查询目标模块是否存在 / 呼叫目标模块

│
├─ 把事件交给中转站但不确定走发送还是交互
│    ├─ 语义是"发布给订阅者" → send
│    └─ 语义是"交给中转站处理" → interact（需交互入口注册）
│
├─ 事件已进入 event_set，想取出处理
│    └─ query(acl_key) → 遍历 → clear(acl_key)
│
```

## 附录 VV：事件系统关键决策记录（ADR 风格）

> 记录事件系统演进中的关键架构决策（基于源码反推的合理决策记录，供后续维护参考）。

### VV.1 ADR-001：终端与中转站解耦

- **决策**：`Event_Terminal` 不直接依赖 `Event_Broker`，通过 `Terminal_Interface` 回调注入。
- **理由**：降低编译依赖、便于替换实现（mock/测试）、模块可独立编译。
- **后果**：接线代码（引擎初始化）负责组装；新增回调通道需扩展 `Terminal_Interface`。

### VV.2 ADR-002：权限密钥采用 optional<int64_t>

- **决策**：密钥为可选 64 位随机整数，未生成即锁定。
- **理由**：简单、无外部依赖；optional 表达两态。
- **后果**：0 为哨兵值；密钥不可重置；粗粒度权限。

### VV.3 ADR-003：订阅表采用"首行全订阅"约定

- **决策**：`acl_set[category]` 首元素（空 tag）为全订阅标记行。
- **理由**：单容器同时表达"全订阅"与"标签订阅"，分发时一次合并。
- **后果**：全订阅与具体标签可能重复收集 ID（缺陷 U10）；空 tag 事件无法表达订阅（被 receive 丢弃）。

### VV.4 ADR-004：事件以 shared_ptr 流转

- **决策**：事件生命周期由 `shared_ptr` 管理。
- **理由**：广播零拷贝、自动回收。
- **后果**：共享可变状态风险（I.10）。

### VV.5 ADR-005：同步分发

- **决策**：`send` → `receive` → 回调同步完成。
- **理由**：时序确定、无锁、实现简单。
- **后果**：回调阻塞发送者；不支持跨线程。

### VV.6 ADR-006：模板定义置于 .cpp

- **决策**：`memory_malloc`/`function_register` 模板定义在终端接口.cpp。
- **理由**：私有实现细节，避免头文件膨胀。
- **后果**：模板仅在同 TU 实例化（M.3），公开方法增加调用点时需保证 .cpp 内可见。

## 附录 WW：事件系统调试技巧

### WW.1 常用调试手段

1. **日志**：观察 `Log::warn/error/debug` 输出（默认控制台）。
2. **断点**：
   - `Event_Broker::receive` 入口——查看事件是否入站。
   - `Event_Broker::info_register`——查看订阅关系建立。
   - `Event_Terminal::send`——查看发送前置检查。
   - 分发循环内 `event_entries[...]` 调用处——查看投递给谁。
3. **观察窗口**：`acl_set`、`mapping_set`、`event_entries` 三表内容。
4. **临时日志**：在 `receive` 的丢弃分支加日志，定位"事件为何消失"。

### WW.2 常见症状 → 定位

| 症状 | 可能原因 | 定位方法 |
| --- | --- | --- |
| 模块收不到事件 | 未 attach / 未订阅 / 发送者排除 / category 未注册 | 检查 attach 日志、三表内容 |
| send 返回 false | 密钥问题 / 发送入口未注册 | 检查密钥生成时机、接口注册 |
| 事件被处理两次 | 重复订阅（全订阅+标签） | 检查 acl_set 中 ID 重复 |
| process 返回奇怪指针 | 缺省路径未定义值 | 断点 process 末尾 |
| 程序崩溃（receive 内） | 发送了空 shared_ptr | 检查 send 调用处判空 |
| 程序崩溃（attach 内） | attach_handler 未注册 | 检查 interface_check 前置 |

### WW.3 一键诊断建议

```
  { "module": "Collision_Proxy", "config_path": "assets/config/collision.json" }
]

推演步骤：
1. Config_Loader::act() 扫描路由文件，读到上述条目。
2. 读取 collision.json 为 config_data（json 对象）。
3. 构造事件：
   evt->category = "Config"
   evt->tag = "Load"
   evt->target_object = "Collision_Proxy"
   evt->config = config_data
4. event_terminal.send({evt}, acl_key)
   → 多事件发送通道 → broker.receive({evt}) → broker.receive(evt)
   → target_object="Collision_Proxy" 在 mapping_set → 定向投递
   → event_entries[Collision_Proxy的ID](evt)
   → Collision_Proxy 的 event_receiver 回调 → event_process(evt)
5. event_process 识别 Config/Load，且 target==module_name
   → config_apply(config_data)
   → 解析 regions/colliders，构建碰撞空间与碰撞体
6. 构建碰撞体时 collider_build 返回 ID
   → event_publish("ColliderBuildResult", {region, collider_ID})
   → 广播（若其他模块订阅则收到）
```

**涉及接口**：`acl_key_gen`、`attach`、`info_register`（间接）、`send`（多）、`receive`（多/单）、`event_receiver_register`、`event_process`、`build`、`event_publish`。

### YY.2 场景：实时碰撞指令

```
输入：逻辑模块调用 send(Collision/RegionDetect, {region:"main_world"})

推演步骤：
1. 逻辑模块构造事件：
   evt->category = "Collision"
   evt->tag = "RegionDetect"
   evt->target_object = ""（广播）
   evt->config = {"region": "main_world"}
2. send(evt, acl_key) → broker.receive(evt)
   → category="Collision" 已注册（Collision_Proxy 订阅过）
   → tag="RegionDetect" 非空
   → target_object 为空 → 广播
   → acled_IDs = 全订阅行.ID_set + 匹配"RegionDetect"标签行的.ID_set
   → 排除发送者自身
   → 调用各订阅者入口
   → Collision_Proxy 收到 → event_process
   → text_read(config,"region",region) 成功 → region_detect("main_world")
```

**要点**：广播模式下，所有订阅了 Collision 大类或 RegionDetect 标签的模块都会收到；发送者若也订阅了则被排除。

### YY.3 场景：模块存在性探测

```
输入：模块 A 想知道模块 B 是否存在

推演步骤：
1. A 构造事件：
   evt->category = "Subscriber"
   evt->tag = "Check"
   evt->sender_object = "A"
   evt->target_object = "B"
2. A 的终端 send → broker.receive
   → 若 acl_set 有 "Subscriber" 分类才不丢弃
   → （若 A 未订阅过 Subscriber，需要目标或全订阅支持）
3. 中转站持有者调用 broker.process(evt)
   → sender="A" 已注册、target="B" 非空
   → mapping_set.find("B")：
      - 存在 → response.config["object_existence"]=true
      - 不存在 → response.config["object_existence"]=false
   → 返回 response 事件
4. A 收到 response，读取 object_existence 判断 B 是否存在
```

**注意**：`process` 的应答需要显式调用（中转站持有者或调用方主动调用），事件系统不会自动把应答发给 A。

### YY.4 场景：呼叫目标模块

```
输入：模块 A 呼叫模块 B（B 存在时）

推演步骤：
1. A 构造 Subscriber/Call 事件，target="B"
2. send → broker.receive
3. 中转站持有者调用 broker.process(evt)
   → B 存在 → response.config["object_existence"]=true
   → tag=="Call" → event_entries[B的ID](evt)  // 原 Call 事件转发给 B
   → B 收到 Call 事件（经由其 event_receiver 回调）
4. process 返回 response 给调用方
```

**语义差异**：Check 只探测不打扰目标；Call 探测并转发指令。

> 以下为接口的预期使用频率与优化关注点，供性能调优参考。

| 接口 | 预期频率 | 优化关注点 |
| --- | --- | --- |

| `interface_check` | 低 | 线性遍历可优化 |

**优化建议（如需）**：
- 分派用事件 ID 而非字符串比较（在 event 中加 `uint32_t category_id/tag_id`，注册时编码）。
- `event` 池化复用，减少 `build` 的分配。
- 广播去重（U10）避免重复回调。

## 附录 AB：事件系统与对象系统在碰撞模块中的协同

> 碰撞模块（089b070 版次拆分后的多编译单元结构）是事件系统与对象系统的主要交汇点。本节描述两者在碰撞模块中的潜在协同方式（基于源码推断）。

### AB.1 分工

- **事件系统**：碰撞模块与外部模块的通信面——接收指令（RegionBuild/ColliderBuild 等）、发布结果（ColliderBuildResult）。
- **对象系统**：碰撞模块内部的对象管理——碰撞空间、碰撞体作为对象存入 `Object_Pool`，用对象 ID 快速查找与生命周期管理。

### AB.2 协同流程（推演）

```
外部事件（Collision/ColliderBuild）到达
  → Collision_Proxy::event_process
  → collider_build(region)
       → 内部使用 Object_Pool 构建碰撞体对象
       → 返回对象 ID（uint64_t）
  → 回告事件 ColliderBuildResult（携带 object_ID / collider_ID）
  → 外部通过事件收到结果，后续用 ID 引用该对象
```

### AB.3 数据交叉

- 事件载荷中的 `collider_ID`（uint64_t）与对象系统的 `Object::ID()`（uint64_t）语义一致——事件系统传递对象 ID，对象系统管理 ID 对应的对象。
- 若碰撞体由 `Object_Pool` 管理，`collider_build` 内部大概率调用 `Object_Pool::build()` 返回 ID。

### AB.4 生命周期协作

- 事件驱动的 `ColliderUnload` 指令 → 内部 `Object_Pool::unload(collider_ID)` 释放对象。
- 对象池 `clear`（场景切换）可能需要配套广播事件通知外部"对象已全部销毁"（当前版次未见，属扩展建议）。

## 附录 AG：事件系统各版本演进推测（基于代码注释与结构）

> 以下为基于源码结构的合理推测，帮助理解事件系统为何是现在的样子（非源码事实，仅供背景参考）。

### AG.1 推测：从直接调用到回调解耦

`Terminal_Interface` 的回调注册表结构暗示事件系统经历过"终端直接持有中转站指针"到"回调注入"的演进。`memory_malloc` 的 `new(nothrow)` 显式分配风格与 `unique_ptr` 使用，说明作者重视内存失败处理与所有权清晰。

### AG.2 推测：密钥机制为后加安全层

`acl_key` 的 `optional` 两态设计 + 所有受保护接口统一的三段式检查（未生成→告警、匹配→执行、不匹配→拒绝），像是后期统一加入的"安全门"。0 哨兵值贯穿生成与校验，设计意图明确。

### AG.3 推测：Subscriber 协议为扩展预留

`process` 只处理 `Subscriber/Check|Call`，且返回 `Response` 事件——这是事件系统中少有的"请求-应答"形态，暗示作者为"模块间查询/呼叫"预留了协议通道。

### AG.4 推测：全订阅行约定是后续优化

`acl_set[category]` 首行为全订阅标记行，避免"全订阅者需要为每个标签各登记一次"的重复——这是订阅模型的性能优化。

## 附录 AK：事件系统核心不变式（Invariants）

> 以下不变式是事件系统正确运行的前提，任何代码修改不得破坏。理解这些不变式有助于避免引入回归。

### AK.1 密钥相关不变式

1. **密钥唯一性**：一个 `Event_Terminal` 最多生成一次密钥；生成后 `acl_key` 永不为 0 且不可重置。
2. **锁定态不变式**：`acl_key` 无值时，所有受保护操作（attach/interact/send/query/clear）必须失败并输出"密钥未生成"告警。
3. **0 哨兵不变式**：0 永远不是有效密钥；所有密钥比对使用 `==`，真实密钥非 0。

### AK.2 订阅表相关不变式

4. **首行全订阅**：`acl_set[category]` 的首元素（下标 0）的 `tag` 必为空串，表示全订阅行；该行在分类首次创建时被插入，此后不可删除。
5. **订阅者 ID 唯一性**：`mapping_set` 中每个模块名对应唯一 ID；同一模块二次注册复用同一 ID（不新增）。
6. **入口一致性**：`mapping_set` 中存在的每个 ID，`event_entries` 中必有对应入口（两者同步增删）。
7. **ID 非负**：订阅者 ID 从 0 开始递增分配，永不为负（-1 仅作为"未找到发送者"的局部哨兵）。

### AK.3 分发相关不变式

8. **空字段丢弃**：`receive` 对 category 为空/未注册、tag 为空的事件必须丢弃（不投递、不崩溃）。
9. **定向优先**：target_object 非空且目标已注册时，事件只投递目标（不广播、不排除发送者）。
10. **广播排除发送者**：广播路径下，发送者本人（若在订阅者集合中）不得收到自己的事件。

### AK.4 事件生命周期不变式

11. **shared_ptr 所有权**：事件对象经 `shared_ptr` 流转；任何接口不得持有事件裸指针超过调用周期（除非明确说明）。
12. **回调同步**：分发回调在 `receive` 调用栈内同步执行；不得在回调中修改 `acl_set`/`mapping_set`/`event_entries` 的结构（可能引发迭代器失效——当前代码无此保护，调用方应遵守）。

### AK.5 注册表不变式

13. **接口记录**：`interface_check` 返回 true 当且仅当对应接口曾被注册（map 中存在 ID）。
14. **回调覆盖**：重复注册同一接口覆盖旧回调（`function_register` 重建）。

## 附录 AS：事件系统核心链路一句话总结

- **构造**：引擎构造唯一 `Event_Broker`，各模块构造 `Event_Terminal` 并 `acl_key_gen()` 取钥。
- **接线**：引擎注册 `attach_handler`/`event_sender`/`events_sender`（接 Broker），模块 `attach` 登记订阅。
- **订阅**：`info_register` 建立 `mapping_set`（模块名→ID）、`event_entries`（ID→入口）、`acl_set`（分类→标签→订阅者）。
- **发送**：模块 `build` 事件 → `send(evt, key)` → 发送通道 → `Broker::receive`。
- **分发**：`receive` 依 `target_object` 定向投递或按 `acl_set` 广播（排除发送者）。
- **接收**：订阅者入口回调 → `Terminal::receive` → 模块回调（已注册）或 `event_set` 队列（未注册）。
- **处理**：模块经 `event_process`/`query` 消费事件。
- **应答**：Subscriber/Check|Call 经 `process` 返回 Response。
- **清理**：`clear(key)` 清空队列；模块析构先于 Broker。
