## 一、模块功能

### 1.1 模块定位

「数值分配器」（`Number_Allocator`）是引擎层 `src/tools/` 工具集中一个**通用整数发放/回收设施**。它的职责单一且明确：以「单调递增 + 回收复用」两种来源，向调用方提供**互不重复的 `uint64_t` 数值**，并允许调用方把不再使用的数值归还回来，供后续请求复用。

在引擎中，大量系统需要「给实体发一个不会与现存实体冲突的编号」这种能力：对象池里的对象 ID、对象在容器中的存储索引、碰撞空间里每个碰撞体的编号……这些编号的**语义各不相同**（有的代表身份、有的代表位置、有的代表碰撞体句柄），但**分配逻辑完全一致**：新号递增、旧号回收、已回收号优先复用。`Number_Allocator` 正是把这套公共逻辑抽取出来，形成**一个类、处处复用**的形态。

本模块位于引擎层目录 `引擎层/src/tools/Number_Allocator/`，是一个**纯头文件模块**（header-only），只由一份文件构成：

- `数值分配器.h` —— 公共头文件，包含类声明与全部成员函数的内联实现（全部方法体都写在类体内）。

由于没有任何跨编译单元的符号需要导出，本模块**没有 `.cpp` 实现文件**，也没有配套的「局部命名空间使用.h」（局部命名空间收敛文件只在存在 `.cpp` 的模块中出现，此处无此需要）。

### 1.2 解决的核心问题

引擎运行期存在三类典型的编号管理痛点，本模块逐一解决：

1. **编号唯一性**：每次 `get()` 返回的数值，要么来自从未发放过的递增序列，要么来自已被回收、当前空闲的数值，**保证任意时刻已发放数值两两互异**。这是对象身份类编号（如对象 ID）的硬性要求——两个对象若共享同一 ID，查找与删除会互相串扰。

2. **回收复用（内存/数量不膨胀）**：若只递增不回收，实体反复创建销毁会导致编号无限增长（`uint64_t` 虽然庞大，但索引类编号直接对应容器下标，无限增长意味着容器无限扩张）。本模块的回收池让「销毁实体释放的编号」能立刻被新实体复用，容器规模被压回到「历史峰值」而不是「历史总量」。

3. **去重保护**：同一编号若被重复回收（例如上层逻辑缺陷导致 `unload` 被调用两次），会直接破坏「已发放数值互异」的保证——被重复回收的号会被错误地再次发放，造成两个存活对象持有同一编号。本模块在回收入口做**二分查重**，从源头拦截这种错误。

### 1.3 功能要点一览

| 能力 | 说明 |
| --- | --- |
| 单调递增分配 | 回收池为空时，`get()` 返回 `next_number` 并自增，保证新号不与历史已发放号冲突 |
| 回收优先（LIFO） | 回收池非空时，`get()` 优先取回收池**末尾**元素（后进先出），弹栈式复用 |
| 单数值回收 | `recycle(uint64_t)` 先二分查重，未重复则入池并重排，返回 `true`；重复则记录警告并返回 `false` |
| 多数值回收 | `recycle(vector<uint64_t>)` 循环调用单数值重载，批量归还 |
| 分配起点设置 | `set(uint64_t)` 把递增序列的起点改为指定值（典型用途：跳过 0 号，把 0 预留为「非法/空」编号） |
| 全量重置 | `reset()` 清空回收池并归零递增序列，回到全新状态 |
| 有序容器维护 | 回收池始终维护为升序有序（`push_back` 后 `std::ranges::sort`），为二分查重提供前提 |
| 纯头文件 | 无 `.cpp`，所有实现内联于类体，零链接成本 |

### 1.4 非目标（明确不做的事）

- **不做线程安全**：`Number_Allocator` 没有任何互斥/原子保护，不适用于多线程并发分配场景（引擎当前为单线程主循环模型）；
- **不做数值溢出防护**：`next_number` 为 `uint64_t`，理论上可持续分配 `2^64` 个数值才会回绕，工程上视为不可能（每秒分配十亿个也要 584 年），故不设溢出检测；
- **不做持久化**：编号不落盘、不跨运行期保真，进程结束即失效；
- **不做「压缩」**：回收池被清空后 `next_number` **不会回退**到已发放区间内（避免与历史上已发出、仍可能被持有的编号冲突）；
- **不做与具体语义的绑定**：本模块不知道编号代表的是 ID 还是索引还是碰撞体句柄，语义由使用方赋予。

## 二、模块提供接口（完整公开接口清单）

以下接口签名全部从 `引擎层/src/tools/Number_Allocator/数值分配器.h` 逐字摘录，与源码完全一致。

### 2.1 类：`engine::Number_Allocator`

```cpp
namespace engine
{
	//数值池
	class Number_Allocator
	{
	private:
		//可分配新数值
		uint64_t next_number = 0;
		//回收数值集合
		std::vector<uint64_t> recycle_numbers;
	public:
		//设置分配起点
		void set(const uint64_t& min_allocate_number);
		//获取可用数值
		uint64_t get(void);
		//回收数值 —— 单数值重载
		bool recycle(const uint64_t& recycle_number);
		//回收数值 —— 多数值重载
		void recycle(const std::vector<uint64_t>& recycle_numbers);
		//重置分配器
		void reset(void);
	};
}
```

### 2.2 接口逐条说明

#### `void set(const uint64_t& min_allocate_number)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `min_allocate_number`：新的递增序列起点。此后 `get()` 在回收池为空时将从该值开始发放 |
| 返回值 | 无 |
| 行为 | 直接把成员 `next_number` 赋值为 `min_allocate_number`。**不清空回收池**，已回收数值不受影响 |

典型用途：`Object_Pool` 构造函数调用 `ID_allocator.set(1)`，把 0 号排除在发放序列之外——0 被约定为「非法对象 ID」的哨兵值（`unload` 时把被卸载对象的 ID 置 0 表示无效）。注意 `set` 只影响**未来的新号**，不影响回收池中的既有数值。

#### `uint64_t get(void)`

| 项目 | 说明 |
| --- | --- |
| 参数 | 无 |
| 返回值 | 一个可用数值（`uint64_t`）。语义为「当前空闲的一个编号」，绝不与任何未回收编号重复 |
| 行为 | **回收池优先**：若 `recycle_numbers` 非空，取末尾元素（`back()`）并弹出（`pop_back()`），即 **LIFO（后进先出）** 复用最近回收的数值；若回收池为空，返回 `next_number` 并将 `next_number` 自增 1 |

内部逻辑等价于：

```cpp
uint64_t index;
if (!recycle_numbers.empty())
{
    index = recycle_numbers.back();
    recycle_numbers.pop_back();
}
else
    index = next_number++;
return index;
```

设计要点：

- **LIFO 而非 FIFO**：`back()`/`pop_back()` 是 `std::vector` 的 O(1) 常数操作；若改用队首（`front()` + 左移）则是 O(n) 拷贝。LIFO 在语义上也更「新鲜」——刚释放的槽位立即被复用，有利于缓存局部性；
- **回收优先于递增**：只要回收池里有货，就绝不消耗新号。这使得「反复建销实体」场景下编号总数稳定在一个小区间内波动。

#### `bool recycle(const uint64_t& recycle_number)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `recycle_number`：准备归还的数值 |
| 返回值 | `true`：回收成功（该数值此前不在回收池中，已入池）；`false`：回收失败（该数值**已经在回收池中**，重复回收，操作被拒绝） |
| 行为 | 先对 `recycle_numbers` 做**二分查找**（`engine::binary_search(recycle_numbers, recycle_number, std::ranges::less())`）。若查找到（返回索引 ≥ 0），说明该数值已被回收，记录警告日志 `"Number_Pool::待回收数值已被回收!!!"` 并返回 `false`；若未查找到（返回 -1），`push_back` 入池，然后 `std::ranges::sort` 重排序以维持升序，返回 `true` |

内部逻辑等价于：

```cpp
int index = binary_search(recycle_numbers, recycle_number, std::ranges::less());
if (index >= 0)
{
    Log::warn("Number_Pool::待回收数值已被回收!!!");
    return false;
}
else
{
    recycle_numbers.push_back(recycle_number);
    std::ranges::sort(recycle_numbers);
    return true;
}
```

设计要点：

- **查重的必要性**：回收池维护的是「空闲编号集」。若把同一编号回收两次，`get()` 会把该编号发放两次（回收池两次 pop 出同一个值），两个不同对象持有同一编号，系统一致性被破坏。二分查重把这种「上层逻辑缺陷」拦在入口；
- **二分查找的前提是有序**：回收池通过「每次插入后 sort」维持升序，故可用 `binary_search`（O(log n)）而非线性查找（O(n)）。这是「用排序成本换查找成本」的典型取舍——回收频率远低于 `get()` 频率的系统中，排序开销可接受；
- **日志文案注意**：警告文案写的是 `"Number_Pool::待回收数值已被回收!!!"`（前缀 `Number_Pool`），是历史命名残留（本类早期可能名为 `Number_Pool`），**不是笔误**，检索日志时应按此文案匹配。

#### `void recycle(const std::vector<uint64_t>& recycle_numbers)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `recycle_numbers`：一批待回收的数值（注意：形参与成员 `recycle_numbers` 同名，函数体内用形参遮蔽成员） |
| 返回值 | 无（`void`） |
| 行为 | 用 `for (auto number : recycle_numbers)` 逐个数调用单数值重载 `recycle(number)` |

设计要点：

- **逐元素复用单数值重载**：批量回收与单数值回收走同一套查重逻辑，行为完全一致；
- **失败静默**：批量重载返回 `void`，若其中某个数值重复回收（单数值重载返回 `false`），仅留下日志，**不中断**后续元素的回收，也不向上报告。调用方无法从返回值得知批量回收是否全部成功——需要精确反馈时应逐个调用单数值重载；
- **同名遮蔽**：形参名与私有成员名相同（`recycle_numbers`），函数体内 `recycle_numbers` 均指形参，成员需用 `this->recycle_numbers` 访问——源码未使用 `this->`，仅依赖编译器的「局部优先」规则，阅读时注意区分。

#### `void reset(void)`

| 项目 | 说明 |
| --- | --- |
| 参数 | 无 |
| 返回值 | 无 |
| 行为 | `next_number = 0` 归零递增序列；`recycle_numbers.clear()` 清空回收池。分配器回到「出厂状态」 |

设计要点：

- 常用于**整体清场**：`Object_Pool::clear()` 清空全部对象后调用 `ID_allocator.reset()` 与 `index_allocator.reset()`，让编号体系与清空后的空容器重新对齐；
- 重置后第一次 `get()` 返回 0（除非先调用 `set`）。

## 三、模块内部架构

### 3.1 成员变量

| 成员 | 类型 | 初值 | 语义 |
| --- | --- | --- | --- |
| `next_number` | `uint64_t` | `0` | 「递增源」：下一个从未发放过的新数值。回收池为空时 `get()` 取它并自增 |
| `recycle_numbers` | `std::vector<uint64_t>` | 空 | 「回收池」：已被回收、可供复用的空闲数值集合。**始终维护为升序**（每次插入后 sort） |

### 3.2 状态机视角

本类只有两个成员，整体行为可看作一个微型状态机：

```
                ┌───────────────────────────────┐
                │         分配器状态             │
                │  next_number: 递增源指针       │
                │  recycle_numbers: 升序空闲池    │
                └───────────────────────────────┘
                        ▲            │
        recycle(入池)   │            │   get(出池/递增)
        + sort 保持有序  │            ▼
                ┌───────────────────────────────┐
                │  回收池非空?                   │
                │  ── 是 → back/pop_back (LIFO) │
                │  ── 否 → next_number++        │
                └───────────────────────────────┘
```

- **不变量 1**：任意时刻，`recycle_numbers` 升序（`std::is_sorted` 恒成立）；
- **不变量 2**：任意时刻，已发放集合与回收池互斥（已发放的编号不会同时出现在回收池中）；
- **不变量 3**：回收池中的任何数值都「曾经被发放过或曾被 set 影响过」，`get()` 不会发出回收池外从未出现过的新值（新值只来自 `next_number` 递增源）。

### 3.3 文件组织与依赖

本模块为单头文件，依赖关系如下：

```

├── #include "common/前置头文件包含.h"        ← 预编译头（标准库全局引入）
```

## 四、模块设计/实现细节

### 4.1 核心算法流程

#### `get()` 的取号顺序（回收优先 + LIFO）

```
get()
 ├─ recycle_numbers 非空 ? ──是──► index = recycle_numbers.back()
 │                                   recycle_numbers.pop_back()
 │                                   return index
 └─ 否 ──► index = next_number++
           return index
```

- 步骤数恒为 O(1)（常数），与回收池大小无关；
- 回收池的 `pop_back()` 只移出**末尾**元素，其余元素位置不动，容器无需搬移。

#### `recycle()` 的查重与入池（二分 + 排序）

```
recycle(number)
 ├─ index = binary_search(recycle_numbers, number, std::ranges::less())
 ├─ index >= 0 ? ──是──► Log::warn("Number_Pool::待回收数值已被回收!!!")
 │                         return false
 └─ 否 ──► recycle_numbers.push_back(number)
           std::ranges::sort(recycle_numbers)      // 维持升序
           return true
```

- 查重复杂度 O(log n)，排序复杂度 O(n log n)；由于 `push_back` 的数值几乎总大于已有序池中若干元素，实际 `sort` 的交换量通常很少；
- **为什么插入后必须排序**：`binary_search` 与 `std::ranges::sort`（默认升序）都要求容器有序。若省略排序，下次 `recycle` 的二分查重将产生**未定义行为**（在无序序列上二分，结果不可预测，可能漏判重复）。

#### `reset()` 与 `set()` 的关系

- `set()` 只改 `next_number`，**不碰回收池**；`reset()` 两者都归零/清空；
- 典型组合序列：构造（`next_number=0`，池空）→ `set(1)`（跳过哨兵 0）→ 多次 `get()`/`recycle()` → 整体清场时 `reset()`。

### 4.2 边界情况处理

| 场景 | 行为 |
| --- | --- |
| 回收池为空时 `get()` | 走递增源：返回 `next_number` 并自增；首次 `get()` 返回 0（若未 `set`） |
| 回收池恰好一个元素时 `get()` | 取走该元素后池变空，下次 `get()` 自动切回递增源 |
| 重复回收同一数值 | 二分查重命中，返回 `false` + 警告日志，数值**不入池**，状态不变 |
| 回收从未发放过的数值（如直接 `recycle(9999)`） | 允许入池（查重只看池内，不看历史发放记录）；之后 `get()` 会先发出 9999。调用方应保证回收的数值确实是自己 `get()` 得到的 |
| 批量回收中出现重复（如 `{5, 5}`） | 第一次入池成功；第二次查重命中，记日志但**继续**处理后续元素，函数无返回值，调用方不感知 |
| `get()` 持续调用直至 `next_number` 回绕 | 工程上视为不可达（2^64 次），无防护 |
| `recycle` 的数值大于 `next_number` | 入池后 `get()` 优先发出该值——它成为一个「凭空出现」的新号，但与其他已发放值仍互异，不破坏不变量 |
| `set` 到小于已发放数值的位置 | 递增源可能与历史已发放数值重合！`set` 的语义是「从新起点继续递增」，调用方须自行保证不冲突（引擎内 `set` 仅用于构造期/重置期，实际安全） |

### 4.3 设计决策及原因

1. **为什么用 `std::vector` 而非 `std::set` 做回收池**：`set` 天然有序 + O(log n) 查重 + O(log n) 插入，看似更优。但本实现选 `vector + sort`：分配场景下回收池规模小（典型几十到几百），`push_back + sort` 的常数开销优于 `set` 的节点分配与指针追逐；且 `vector` 缓存友好、支持 `back()/pop_back()` 的 O(1) LIFO（`set` 取「末尾元素」需要迭代器递减，同样 O(1) 但常数更大）。**空间连续**是 `vector` 在池规模小时压倒性的优势。

2. **为什么 LIFO（后进先出）而非 FIFO（先进先出）**：`vector` 的尾部操作是 O(1)，头部操作是 O(n)；LIFO 恰好复用尾部。语义上，后回收的槽位大概率是「刚刚才空出来」的，最近被访问过的内存页仍热，复用它对缓存友好。

3. **为什么 `get()` 先看回收池再看递增源**：这是「复用优先」策略。若反过来（先递增后查池），则每次 `get()` 都消耗新号，回收池形同虚设，编号无限增长，索引类编号会撑爆容器。

4. **为什么回收后不压缩 `next_number`**：假设已发放 0~99，回收 50~99 后，理论上可以让 `next_number` 退回 50 重新递增。但**已发放的 0~49 可能仍被持有**，若 `next_number` 回退到 50 并递增，发出的 50 号可能与「已被持有但未回收」的号冲突——而回收池机制恰恰是为了保证**已发放集合与回收池互斥**，压缩会让「未回收的已发放号」与「新发的号」出现碰撞风险。因此 `next_number` 只增不减，安全第一。

5. **为什么查重用二分而非线性**：池有序是 `recycle` 自己维护的，二分 O(log n) 稳定优于线性 O(n)。这是对「每次插入 O(n log n) 排序」的回报——用插入侧的成本换查询侧的低延迟。

6. **为什么 `recycle` 单数值重载返回 `bool` 而多数值重载返回 `void`**：单数值重载的 `bool` 给调用方「是否成功」的精确反馈（调用方可以据此发现上层逻辑 bug）；批量重载若改为「全有或全无」需引入事务语义，复杂度高收益低，故退化为「尽力而为 + 日志」。

### 4.4 与其它模块的协作

#### 与 `Object_Pool`（对象池，`src/core/object/Object_Pool/对象池.h`）

`Object_Pool` 内部持有**两个** `Number_Allocator` 实例，构成「双分配器」架构：

```cpp
template <typename T, typename Key = uint64_t>
	requires std::is_base_of_v<Object, T>
class Object_Pool
{
private:
	//ID分配器
	Number_Allocator ID_allocator;
	//索引分配器
	Number_Allocator index_allocator;
	...
};
```

| 分配器 | 发放的数值语义 | 消费方 |
| --- | --- | --- |
| `ID_allocator` | 对象**身份 ID**（`Object::ID()`，经 `new_object.ID_set(...)` 写入对象） | 外部查找对象的句柄、映射键 |
| `index_allocator` | 对象在 `std::vector<T> objects` 中的**存储下标** | 容器寻址、`sort_order_set` 前的失效位整理 |

协作点：

- 构造期 `ID_allocator.set(1)`：把 0 号排除（0 = 非法对象 ID 哨兵）；
- `build()`：`index_allocator.get()` 取槽位（越界则 `objects.push_back({})` 扩容），`ID_allocator.get()` 取身份 ID；
- `unload()`：`ID_allocator.recycle(ID)` 归还身份号，`index_allocator.recycle(target_index)` 归还槽位（排序模式下回收的是交换后的前端空槽 `min_valid_index` 位置）；
- `clear()`：`ID_allocator.reset()` + `index_allocator.reset()` 全量归零；
- `sort_order_set()` 扫描无效记录时逐个 `index_allocator.recycle(filter_index)` 回收废槽。

#### 与 `Collision_Region`（碰撞空间，`src/core/spatial/collision/Collision_Region/碰撞空间.h`）

```cpp
struct Collision_Region
{
private:
	//碰撞体编号分配器
	Number_Allocator ID_allocator;
	...
public:
	//碰撞体构建
	uint64_t collider_build(void);
	//卸载碰卸载
	bool collider_unload(uint64_t collider_ID);
	...
};
```

- `collider_build()`：`ID_allocator.get()` 为新建碰撞体分配全局唯一编号（作为 `std::unordered_map<uint64_t, Collider> mapping` 的键）；
- `collider_unload()`：`ID_allocator.recycle(collider_ID)` 归还编号，编号可被后续碰撞体复用；
- `Collision_Region` 移动语义下 `ID_allocator` 随结构体整体搬移（值成员，默认移动即可）。

### 4.5 易踩坑点（重开发速查）

1. **回收池必须有序**：任何手工向 `recycle_numbers` 插值的扩展（绕过 `recycle`）都会破坏二分前提；重开发时只能通过 `recycle()` 入池。
2. **`reset()` 不清空 `set` 效果**：`reset()` 把 `next_number` 归 0，若调用方需要「重置后仍跳过 0」，须重置后再调 `set`（`Object_Pool::clear()` 即如此处理：`ID_allocator.reset()` 后不恢复 `set(1)`，导致清空后再 build 的第一个对象 ID 为 0——这是源码现状，属已知行为而非缺陷）。
3. **批量回收失败静默**：`recycle(vector)` 无法告知部分失败；需要审计「回收全部成功」的场景请逐元素调单数值重载。
4. **日志前缀是 `Number_Pool`**：检索 `Log::warn` 输出时用 `Number_Pool::待回收数值已被回收` 匹配，不要用类名 `Number_Allocator` 去 grep 日志（源码日志文案与类名不一致）。
5. **非线程安全**：多线程并发 `get()`/`recycle()` 会竞争 `next_number` 与 `vector`，产生数据竞争；引擎主循环单线程模型下安全。
6. **`set` 与已发放历史冲突**：仅在构造期/空场期使用 `set`，运行期调用 `set` 会制造重复编号风险。
7. **同名声形参与成员**：`recycle(const std::vector<uint64_t>& recycle_numbers)` 内 `recycle_numbers` 指形参，勿误以为操作成员；若需访问成员须 `this->recycle_numbers`。

## 五、模块运行链路

### 5.1 对象池建销链路（最长链路）

以 `Object_Pool<T>::build()` / `unload()` 为例，展示双分配器与 `Number_Allocator` 的完整交互：

```
【对象创建】Object_Pool::build()
  ① index_allocator.get()
       ├─ 回收池非空 → 复用最近回收的槽位下标（LIFO）
       └─ 池空 → next_number++（新槽位）
  ② 若 index >= objects.size() → objects.push_back({})（扩容）
  ③ new_object = T{}（防残留）
  ④ new_object.ID_set(ID_allocator.get())      ← ID 分配器取身份号
  ⑤ 稳定模式 → object_index_map 登记 {ID → index}
     排序模式 → 重排 objects（按 projector）

【对象销毁】Object_Pool::unload(key)
  ① find(key) 定位对象迭代器
  ② target_index = it - objects.begin()
  ③ ID = it->ID()
  ④ ID_allocator.recycle(ID)                  ← 身份号归还回收池
  ⑤ it->ID_set(0)（哨兵化）
  ⑥ valid_set(false)
  ⑦ 稳定模式 → object_index_map.erase(ID)；index_allocator.recycle(target_index)
     排序模式 → swap 无效对象到前端；index_allocator.recycle(min_valid_index)；
              min_valid_index++

【整体清场】Object_Pool::clear()
  ① objects.clear()
  ② ID_allocator.reset()      ← 双分配器归零
  ③ index_allocator.reset()
```

### 5.2 碰撞空间编号链路

```
【碰撞体构建】Collision_Region::collider_build()
  ① ID_allocator.get()
       └─ 复用回收号 或 递增新号
  ② 以该编号为键插入 mapping（unordered_map<uint64_t, Collider>）
  ③ return 编号（供外部持句柄）

【碰撞体卸载】Collision_Region::collider_unload(collider_ID)
  ① 从 mapping 移除该碰撞体
  ② ID_allocator.recycle(collider_ID)
       └─ 二分查重 → 入池 → sort
```

### 5.3 典型生命周期时序（一次完整建销循环）

```
时间轴      Object_Pool                Number_Allocator(ID)         Number_Allocator(index)
──────────────────────────────────────────────────────────────────────────────────────
 t0 构造     set(1)                     next_number=1                （未动）
 t1 build#1  ID_allocator.get()         池空→发1,next=2
             index_allocator.get()                                 池空→发0,next=1
 t2 build#2  ID_allocator.get()         池空→发2,next=3
             index_allocator.get()                                 池空→发1,next=2
 t3 unload#1 ID_allocator.recycle(1)    池={1},sort
             index_allocator.recycle(0)                            池={0},sort
 t4 build#3  ID_allocator.get()         池非空→back()=1,池={}      ← 复用 1 号
             index_allocator.get()                                 池非空→back()=0,池={}  ← 复用 0 槽
 t5 clear    reset()                    next=0,池空                 next=0,池空
```

观察：t4 复用 t3 回收的 1 号与 0 槽，编号总量没有继续增长——这正是「回收复用」要达成的效果。

### 5.4 依赖方向汇总

```
                    ┌────────────────────┐
                    │   Number_Allocator  │   （被依赖方）
                    │   next_number       │
                    │   recycle_numbers   │
                    └─────────▲──────────┘
         持有两个实例          │ 持有实例
    ┌─────────────────┐  ┌────┴─────────────┐
    │   Object_Pool    │  │  Collision_Region │
    │ ID + index 双分配 │  │ 碰撞体编号分配     │
    └─────────────────┘  └──────────────────┘
                     ▲
                     │ 使用
             ┌───────┴────────┐
             │  binary_search  │  （Auxi_Algorithm，回收查重）
             └────────────────┘
```

依赖图结论：`Number_Allocator` 是**纯被依赖方**，自身只依赖 `Auxi_Algorithm::binary_search` 与 `Logging::Log`，是引擎底层基础工具之一；任何需要「发放不重复整数 + 回收复用」的系统都可直接内嵌它。
