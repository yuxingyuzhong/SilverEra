## 一、模块功能

### 1.1 模块定位

「辅助算法」（`Auxi_Algorithm`）是引擎层 `src/tools/` 工具集中一个**无状态算法函数集模块**。它不定义任何类、不持有任何数据，只提供两组**命名空间级函数模板与内联函数**：

1. **二分查找族**（`二分查找.h`）：
   - `binary_search` —— 在有序区间内精确查找单个目标，返回**全局下标**（相对原始起始迭代器，而非相对当前查找窗口）；
   - `range_binary_search` —— 在有序区间内查找目标值所在的**闭区间** `[left, right]`（处理重复元素），返回 `{左下标, 右下标}`。
2. **路径字符串转换族**（`路径字符串转换.h`）：
   - `path_to_string` —— `std::filesystem::path` → `std::string`（UTF-8 字节保真转换）；
   - `string_to_path` —— `std::string`（UTF-8）→ `std::filesystem::path`。

这两个算法族虽然都挂在「通用算法模块」下，但服务场景完全不同：二分查找服务于**引擎内部有序容器的 O(log n) 定位**（对象池的排序查找、四叉树管理器的坐标区间查询、数值分配器的回收查重）；路径转换服务于**跨平台中文路径的 UTF-8 保真传递**（引擎环境、网格加载、配置加载的路径出入参）。把它们收敛在一个模块内，是「通用、无状态、可复用的纯函数」这一类工具的归集。

本模块位于引擎层目录 `引擎层/src/tools/Auxi_Algorithm/`，由两份头文件构成：

- `二分查找.h` —— `binary_search` / `range_binary_search` 的函数模板（迭代器版本 + 容器版本）；
- `路径字符串转换.h` —— `path_to_string` / `string_to_path` 的 `inline` 函数。

两份头文件均为 **header-only**（模板天然只能放头文件；路径转换函数以 `inline` 规避 ODR 违规），**无 `.cpp` 实现文件**。

### 1.2 解决的核心问题

#### 二分查找族

引擎内部大量「有序容器 + 按序键查找」场景，直接使用 `std::binary_search`（返回 `bool`）、`std::lower_bound`/`std::upper_bound`（返回迭代器）需要调用方自行组装：

- `std::binary_search` 只回答「在不在」，不返回位置；要拿下标还得再 `lower_bound` + 迭代器相减；
- `lower_bound`/`upper_bound` 返回的迭代器需要调用方换算成索引（`it - begin`），且在「查找窗口不是从容器头开始」（如对象池的 `min_valid_index` 偏移窗口）时，**直接相减会得到窗口内相对下标而非容器全局下标**——这正是本模块 `binary_search` 用「保存 `original_first`」修复的经典 bug（头文件注释即写明「修复后的 binary_search：返回全局索引（相对于原始 first）」）；
- 重复元素场景（如四叉树管理器中多棵树的根节点 X 坐标相同）需要「区间查询」能力：找齐所有等价元素的首尾下标，`std::lower_bound + std::upper_bound` 的两次搜索逻辑需要手工拼接。

`binary_search` / `range_binary_search` 把这三种需求封装为「一个调用、返回下标/区间」的形态，并额外提供**容器重载**（直接传容器对象，免去 `begin/end` 样板），把迭代器细节全部隐藏。

#### 路径字符串转换族

`std::filesystem::path` 在 Windows 上是 `wchar_t` 宽字符存储（`path::value_type = wchar_t`），在 Linux/macOS 上是 `char` 窄字符存储（`value_type = char`）。引擎内部统一约定「**出入参路径一律为 UTF-8 编码的 `std::string`**」（引擎环境、网格加载器、配置加载器均遵循此约定），因此：

- 把 `path` 传给外部接口（日志、JSON 配置字段、用户输入输出）时，需要 `path → std::string`；
- 把调用方给的 UTF-8 `std::string` 路径交给文件系统 API 时，需要 `std::string → path`。

C++20 的 `path::u8string()` 返回 `std::u8string`（`char8_t` 序列，UTF-8 保证），本模块负责在其与 `std::string`/`std::filesystem::path` 之间做**逐字节零损失**转换——这是中文路径（如 `D:/代码存储/代码仓库/白银纪元/...`）在引擎全链路中正确传递的基石。

### 1.3 功能要点一览

| --- | --- |

### 1.4 非目标（明确不做的事）

- **不做二分查找的排序保障**：本模块假定传入区间**已按 `comp` 有序**；在无序区间上调用是未定义行为（与标准库一致）；
- **不做区间插入/删除类算法**：只查询，不修改容器；
- **不做 `std::ranges` 命名空间扩展**：`binary_search` 等位于 `engine` 命名空间，调用需 `engine::` 前缀或用 `using` 引入；
- **不做路径规范化**：`path_to_string`/`string_to_path` 是纯字节搬运，不解析 `.`/`..`、不统一分隔符、不判绝对相对；
- **不做编码猜测/转换**：只认「入参就是 UTF-8」的约定，不做 GBK→UTF-8 之类的转码。

## 二、模块提供接口（完整公开接口清单）

以下接口签名全部从 `引擎层/src/tools/Auxi_Algorithm/二分查找.h` 与 `引擎层/src/tools/Auxi_Algorithm/路径字符串转换.h` 逐字摘录，与源码完全一致。

### 2.1 `engine::binary_search` —— 迭代器版本

```cpp
namespace engine
{
	// 修复后的 binary_search：返回全局索引（相对于原始 first）
	template<typename RandomIt, typename T, typename Compare, typename Projection = std::identity>
	int binary_search(RandomIt first, RandomIt last, const T& target,
		const Compare& comp, Projection proj = {})
	{
		RandomIt original_first = first;  // 保存原始起始位置
		while (first < last) {
			RandomIt mid = first + (last - first) / 2;
			if (comp(target, std::invoke(proj, *mid)))
				last = mid;
			else if (comp(std::invoke(proj, *mid), target))
				first = mid + 1;
			else
				return static_cast<int>(mid - original_first);  // 使用原始起始位置计算索引
		}
		//若查找失败则返回无效索引
		return -1;
	}
}
```

| 模板参数 | 含义 |
| --- | --- |
| `RandomIt` | 随机访问迭代器类型（`vector::iterator`、原生指针等） |
| `T` | 目标值类型（与比较器配合可不同于元素类型） |
| `Compare` | 比较器：`comp(a, b)` 返回 `bool`，表达「a 严格小于 b」（严格弱序） |
| `Projection` | 投影（默认 `std::identity`）：`std::invoke(proj, *it)` 取出参与比较的元素字段/变换值 |

| 参数 | 含义 |
| --- | --- |
| `first`/`last` | 查找区间 `[first, last)`，**须已按 `comp` 有序** |
| `target` | 查找目标 |
| `comp` | 比较器 |
| `proj` | 投影，默认恒等 |
| 返回值 | 命中：目标在**原始 `first` 起始的全局下标**（`int`）；未命中：`-1` |

行为与算法：

- 经典迭代二分：`mid = first + (last - first) / 2`（用差值避免指针/迭代器相加溢出）；
- 三分支判定：`comp(target, proj(*mid))` 为真 → 目标在左半（`last = mid`）；`comp(proj(*mid), target)` 为真 → 目标在右半（`first = mid + 1`）；两者皆假 → **命中**（严格弱序下两者皆假 ⇔ 等价）；
- **关键修复点**：返回 `mid - original_first` 而非 `mid - first`——因为循环中 `first` 会移动，`mid - first` 是**窗口内相对下标**；保存最初 `first` 到 `original_first`，`mid - original_first` 才是相对「调用方传入起点」的全局下标。对象池 `find()` 正是以「偏移窗口起点 `objects.begin() + min_valid_index`」调用，再用返回值**加上偏移**回算容器内真实位置——若本函数返回相对下标，对象池的换算就会错位；
- 复杂度：O(log n) 次比较，O(1) 额外空间（迭代器版本，非递归）。

### 2.3 `engine::range_binary_search` —— 迭代器版本

```cpp
	template<typename RandomIt, typename T, typename Compare,
		typename Projection = std::identity>
	std::pair<int, int> range_binary_search(RandomIt first, RandomIt last,
		const T& target,
		const Compare& comp,
		Projection proj = {})
	{
		// 1. 计算下界：第一个使得 comp(proj(*it), target) 为 false 的元素
		//    即第一个不小于 target 的元素
		auto lower = first;
		auto end = last;
		auto count = std::distance(first, last);
		while (count > 0) {
			auto step = count / 2;
			auto it = lower;
			std::advance(it, step);
			if (comp(proj(*it), target)) {
				lower = ++it;
				count -= step + 1;
			}
			else {
				count = step;
			}
		}

		// 2. 计算上界：第一个使得 comp(target, proj(*it)) 为 true 的元素
		//    即第一个大于 target 的元素
		auto upper = lower;      // 从上界开始搜索
		count = std::distance(upper, last);
		while (count > 0) {
			auto step = count / 2;
			auto it = upper;
			std::advance(it, step);
			if (!comp(target, proj(*it))) {   // 即 target >= proj(*it) 
				upper = ++it;
				count -= step + 1;
			}
			else {
				count = step;
			}
		}

		// 3. 检查下界是否有效且与目标等价
		if (lower == last || comp(proj(*lower), target) || comp(target, proj(*lower))) {
			return { -1, -1 };   // 未找到任何等价元素
		}

		// 4. 返回闭区间的下标
		auto left_index = static_cast<int>(std::distance(first, lower));
		auto right_index = static_cast<int>(std::distance(first, upper)) - 1;
		return { left_index, right_index };
	}
```

| 模板参数 | 含义 |
| --- | --- |
| `RandomIt` | 随机访问迭代器 |
| `T` | 目标值类型 |
| `Compare` | 比较器（严格弱序） |
| `Projection` | 投影，默认 `std::identity` |

| 参数 | 含义 |
| --- | --- |
| `first`/`last` | 查找区间 `[first, last)`，**须已按 `comp` 有序** |
| `target` | 查找目标 |
| `comp` | 比较器 |
| `proj` | 投影 |
| 返回值 | 命中：`std::pair<int,int>{left, right}`，闭区间 `[left, right]` 内的元素全部与目标等价（按 `comp` 双向比较均不严格小于）；未命中：`{-1, -1}` |

行为与算法（**两阶段二分**）：

- **阶段 1（下界）**：标准库风格的 `lower_bound` 手工实现——用 `count`/`step` 步进法寻找「第一个满足 `!(comp(proj(*it), target))`」（即第一个不小于目标）的位置 `lower`。循环不变量：`lower` 始终指向「可能的第一个等价元素」；
- **阶段 2（上界）**：从 `lower` 继续（不重头搜），寻找「第一个满足 `comp(target, proj(*it))`」（即第一个严格大于目标）的位置 `upper`。实现用 `!comp(target, proj(*it))` 判定「目标不小于当前元素」→ 向右收缩，等价于标准 `upper_bound`；
- **阶段 3（命中判定）**：`lower == last`（区间内无任何不小于目标的元素）或 `comp(proj(*lower), target)`（`lower` 处元素仍严格小于目标）或 `comp(target, proj(*lower))`（`lower` 处元素严格大于目标）——三者任一成立说明「与目标等价的元素不存在」，返回 `{-1, -1}`；
- **阶段 4（闭区间组装）**：`left = distance(first, lower)`；`right = distance(first, upper) - 1`（`upper` 是第一个大于目标的元素，其前一个下标即最后一个等价元素）。若 `upper == first`（目标小于全部元素），`right = -1`——但此时阶段 3 的 `comp(target, proj(*lower))` 已拦截（`lower == first` 且首元素大于目标），不会走到此处输出误导区间；
- 复杂度：O(log n)，两次扫描合计；`std::distance`/`std::advance` 在随机访问迭代器上为 O(1)。

### 2.5 `engine::path_to_string`

    inline std::string path_to_string(const std::filesystem::path& path)
    {
        //转化为UTF-8编码的U8字符串
        const std::u8string& u8string = path.u8string();

## 三、模块内部架构

### 3.1 数据与状态

本模块**无任何数据成员、无静态变量、无内部类、无枚举**——全部为自由函数（模板或 `inline`）。调用不产生任何持久状态，纯函数语义（同输入同输出，无副作用）。这是「辅助算法」模块的本质特征。

### 3.2 文件组织与依赖

```
Auxi_Algorithm/
├── 二分查找.h            ← binary_search / range_binary_search（模板，header-only）
└── 路径字符串转换.h      ← path_to_string / string_to_path（inline，header-only）
```

```
二分查找.h
└── #include "common/前置头文件包含.h"     ← <functional>(std::invoke) <iterator> <utility>(std::pair) 等

路径字符串转换.h
├── #include "common/前置头文件包含.h"     ← <string> <filesystem>
└── #include "src/tools/Engine_Env/引擎环境.h"   ← 头文件包含（本模块自身未使用 Engine_Env 符号，仅为调用方顺带引入）
```

注意：`路径字符串转换.h` 顶部的 `#include "src/tools/Engine_Env/引擎环境.h"` 是**冗余包含**（该头文件内未使用 `Engine_Env` 的任何符号）。它存在的实际效果是：任何包含本头的翻译单元会连带获得引擎环境声明——这是源码现状，重开发时可保留（兼容既有依赖链）或清理（纯化依赖），二者皆可行。

### 3.3 模板的编译期形态

两个查找算法各有「迭代器版本 + 容器版本」两个模板重载，构成**转发链**：

```
binary_search(container, target, comp, proj)
        └──► binary_search(begin(c), end(c), target, comp, proj)     （迭代器版）

range_binary_search(container, target, comp, proj)
        └──► range_binary_search(begin(c), end(c), target, comp, proj)
```

重载决议：容器版本要求第一实参是「支持 ADL `begin/end` 的容器对象」；若第一实参本身就是迭代器（如 `objects.begin() + offset`），则直接命中迭代器版本。两种形态的**返回值约定一致**（全局下标 / 闭区间），调用方无需区分。

## 四、模块设计/实现细节

### 4.1 `binary_search` 的「全局索引」修复（历史 bug 复盘）

头文件注释明确写着「修复后的 binary_search：返回全局索引（相对于原始 first）」，说明此前版本存在一个真实缺陷。缺陷推演：

```
旧实现（伪码）：return mid - first;      // first 是当前窗口起点，会随二分移动
调用场景（对象池 find）：
  binary_search(objects.begin() + 100, objects.end(), key, less, proj)
  命中在容器第 150 个元素：mid = (begin+100) 之后第 50 步 → mid - first = 50
  旧实现返回 50，对象池以为元素在「窗口起点 + 50」= 容器第 150 个 —— 恰好正确？
```

实际上旧实现返回的是「相对当前迭代位置的步数」，而二分过程中 `first` 只缩不扩，**最后一次比较时 `mid` 相对最初 `first` 的偏移**才是真实命中位置。若用「命中时刻的 `mid - first`」——`first` 已收缩到命中点左侧很近处，偏移量偏小，对象池换算 `objects.begin() + min_valid_index + index` 会错位到错误对象。修复方案（现源码）：**在进入循环前保存 `original_first`，返回 `mid - original_first`**，一劳永逸。

这个修复对「查找窗口 ≠ 容器头」的调用（对象池偏移窗口、四叉树分段区间）至关重要，是理解本模块价值的关键锚点。

### 4.2 `range_binary_search` 两阶段二分逐步推演

以有序序列 `[1, 3, 3, 3, 5, 7]`、`target = 3`、`comp = std::ranges::less` 为例：

```
阶段1 下界（第一个 >= 3 的元素）：
  count=6, step=3, it=元素[3]=3；comp(3,3)=false → count=3
  count=3, step=1, it=元素[1]=1；comp(1,3)=true  → lower=元素[2], count=3-1-1=1
  count=1, step=0, it=元素[2]=3；comp(3,3)=false → count=0
  lower = 元素[2]（下标 1）

阶段2 上界（第一个 > 3 的元素），从 lower 继续：
  count=6-1=5, step=2, it=元素[4]=5；!comp(3,5)=!true=false → count=2
  count=2, step=1, it=元素[3]=3；!comp(3,3)=!false=true → upper=元素[4], count=2-1-1=0
  upper = 元素[4]（下标 4）

阶段3 判定：lower≠end；comp(3,3)=false；comp(3,3)=false → 命中
阶段4 区间：left = distance(begin, 元素[2]) = 1
           right = distance(begin, 元素[4]) - 1 = 4 - 1 = 3
           → {1, 3}，即下标 1~3 全为 3 ✓
```

未命中推演（`target = 4`）：

```
阶段1：lower 落在元素[4]（第一个 >=4 的 5，下标 4）
阶段2：upper = lower（第一个 >4 的也是 5，下标 4）
阶段3：lower≠end；comp(proj(5), 4)=false；comp(4, proj(5))=true → 第三条件成立 → {-1,-1} ✓
```

边界推演（`target` 小于全部元素，`target=0`）：

```
阶段1：lower=begin（下标 0，1>=0）
阶段2：upper=lower=begin
阶段3：comp(proj(1), 0)=false；comp(0, proj(1))=true → 第三条件成立 → {-1,-1} ✓
```

边界推演（`target` 大于全部元素，`target=9`）：

```
阶段1：所有 comp(x,9)=true → lower=end（下标 6）
阶段3：lower == last → {-1,-1} ✓
```

### 4.3 比较语义与投影的配合约定

- **`comp(a, b)` = 「a 严格小于 b」**：与 `std::ranges::less()`、`std::ranges::greater()` 兼容。`greater` 语义下「有序」是**降序**，此时「等价」判定（`comp(target,x)` 与 `comp(x,target)` 皆假）依然正确——四叉树管理器即用 `std::ranges::greater()` 在降序 X 序列上做区间查询；
- **`proj` 默认 `std::identity`**：直接比较元素本身；传投影函数（如 `[](const Object& o){ return o.ID(); }`）时，**排序键 = 投影值**，二分在「按投影值排序」的序列上按投影值查找；
- **`std::invoke(proj, *mid)`**：支持成员函数指针、`std::reference_wrapper` 等可调用形态；
- 一致性要求：调用方必须保证「序列排序所用比较器 + 投影」与「查找所用比较器 + 投影」**完全一致**，否则二分结果未定义。

### 4.4 路径转换的跨平台行为矩阵

| 平台 | `path` 内部字符 | `u8string()` 产出 | 转换后行为 |
| --- | --- | --- | --- |
| Windows (MSVC) | `wchar_t`（UTF-16 编码的宽字符） | UTF-8 `u8string`（正确转码） | `path_to_string` 得到 UTF-8 字节；`string_to_path` 把 UTF-8 字节解码回 UTF-16 宽字符 |
| Linux (libstdc++) | `char`（原生字节序，通常即 UTF-8） | UTF-8（原样） | 均为字节搬运，无损失 |
| macOS (libc++) | `char`（UTF-8 语义） | UTF-8（原样） | 同上 |

关键点：转换函数本身**不做转码**，只做「`path` ↔ UTF-8 字节序列」的桥接；真正的编码转换由 `path::u8string()` 与 `path(u8string)` 构造函数在 Windows 上完成。因此引擎全链路（`Engine_Env` → `Mesh_Loader` → `Config_Loader`）统一约定「UTF-8 `std::string` 出入参」后，中文路径在三平台行为一致。

### 4.6 易踩坑点（重开发速查）

1. **有序性前提**：两个查找函数都不检查序列是否有序；无序输入 = 未定义行为（可能返回任意下标/区间）；
2. **窗口偏移与返回值的关系**：迭代器版返回「相对**入参 `first`**」的下标，不是相对容器头！容器版才是容器内下标。对象池的用法是「入参窗口起点 = `begin + min_valid_index`，再用返回值**加回** `min_valid_index`」——照抄此模式时务必配对偏移；
3. **`range_binary_search` 的右端点**：返回的 `right` 是闭区间右端（`upper - 1`），遍历时用 `for (i = left; i <= right; ++i)` 而非 `<`；
4. **未命中返回 `{-1,-1}` 的判断**：调用方应同时检查 `first < 0 && second < 0`（四叉树管理器即如此），不要只查一个；
5. **比较器方向**：降序序列必须配 `std::ranges::greater()`，且「小于」语义也随之反转；混用 `less` 与降序序列会得到错误结果；
6. **投影必须一致**：排序用 `proj1`、查找用 `proj2`（哪怕结果等价但函数对象不同）时，须保证对每个元素 `proj1(x) == proj2(x)`，否则二分失效；
7. **路径转换不做合法性校验**：`string_to_path` 对非法 UTF-8 字节不做检查（逐字节搬运）；路径是否存在由调用方后续用 `Data_Validator::path_check` 或文件系统 API 验证；
8. **`u8string()` 的 C++20 差异**：C++17 时代 `u8string` 返回 `std::string`，C++20 改为 `std::u8string`（`char8_t`）——本实现按 C++20 写（`const std::u8string&` 接引用），若项目降到 C++17 会编译失败；
9. **`reinterpret_cast` 的字节语义**：`char8_t` 与 `char` 大小相同（1 字节），逐字节重解释安全；勿用 `static_cast`（会做「值转换」语义，对 8 位类型虽等价但表意不清）。

## 五、模块运行链路

### 5.1 对象池排序查找链路（`binary_search` 迭代器版 + 投影）

```
Object_Pool<T>::find(key)
  │  （排序模式 is_sorted == true）
  ├─ 目标窗口 = [objects.begin() + min_valid_index.value(), objects.end())
  ├─ binary_search(窗口首, 窗口尾, key, comp, projector)
  │     ├─ original_first = 窗口首
  │     ├─ 迭代二分（比较 comp(proj(*mid), key) / comp(key, proj(*mid))）
  │     ├─ 命中 → return mid - original_first        ← 窗口内相对下标
  │     └─ 未命中 → return -1
  ├─ index >= 0 ?
  │     ├─ 是 → return objects.begin() + min_valid_index + index   ← 加回偏移
  │     └─ 否 → return objects.end()
```

### 5.2 四叉树管理器区间查询链路（`range_binary_search` 降序 + 投影）

```
Quadtree_Manager 基础操作（X_sequence 降序树组）
  ├─ range = range_binary_search(X_sequence.begin(), X_sequence.end(),
  │          root.X, std::ranges::greater(), [](auto* p){ return p->root.X; })
  ├─ range.first < 0 && range.second < 0 ?
  │     ├─ 是 → 返回 -1（无同 X 坐标树）
  │     └─ 否 → 遍历 X_sequence[range.first .. range.second]
  │              处理所有「根 X 坐标 == root.X」的树节点
```

### 5.3 数值分配器回收查重链路（`binary_search` 容器版）

```
Number_Allocator::recycle(number)
  ├─ 回收池 recycle_numbers（升序，每次插入后 sort）
  ├─ index = binary_search(recycle_numbers, number, std::ranges::less())
  │        └─► binary_search(begin(池), end(池), number, less, identity)
  │              ├─ 命中（index >= 0）→ 重复回收 → warn + return false
  │              └─ 未命中（-1）→ push_back + sort + return true
```

### 5.4 网格加载路径转换链路（`string_to_path`）

```
Mesh_Loader::load_obj(mesh_path /* UTF-8 std::string */)
  ├─ Data_Validator::path_check(mesh_path) 校验原样路径
  ├─ 有效 → read_path = string_to_path(mesh_path)     ← 本模块
  │              └─ std::u8string 逐字节搬运 → path（中文路径无损）
  └─ ifstream(read_path) 打开文件
```

### 5.5 依赖方向汇总

```
调用方（Object_Pool / Quadtree_Manager / Number_Allocator / Mesh_Loader / ...）
        │
        ▼
Auxi_Algorithm（tools/Auxi_Algorithm）
        ├── 二分查找.h    → engine::binary_search / engine::range_binary_search（模板）
        ├── 路径字符串转换.h → engine::path_to_string / engine::string_to_path（inline）
        ├── 依赖：common/前置头文件包含.h（标准库）
        └── （冗余）包含 Engine_Env/引擎环境.h
```

结论：`Auxi_Algorithm` 是引擎**被引用面最广的叶子工具模块**之一——几乎所有涉及「有序定位」或「路径出入参」的模块都直接或间接依赖它。重开发时保持四个函数模板的**签名与返回值约定**（全局下标、闭区间、UTF-8 字节保真）不变，即可保证全部下游调用方兼容。
