## 一、模块功能

### 1.1 模块定位

「引擎环境」（`Engine_Env`）是引擎层 `src/tools/` 工具集中一个**进程运行时环境查询模块**。它的职责是：在**进程启动后的任意时刻**，向引擎其他模块提供两个基础事实——

1. **可执行文件（exe）自身的绝对路径**（`exe_path_get`）；
2. **可执行文件所在目录**（`exe_dir_get`）。

并基于「可执行文件目录」提供**绝对路径拼接**服务（`absolute_path_get`），用于把引擎的资源相对路径（网格文件、配置文件等）解析为「以可执行文件所在目录为基准的绝对路径」。

这三个能力是三平台（Windows / Linux / macOS）差异的**统一封装点**：获取可执行文件路径的 API 在三个平台完全不同（`GetModuleFileNameW` / `readlink /proc/self/exe` / `_NSGetExecutablePath`），`Engine_Env` 用 `#if defined(...)` 预处理分支把这套差异收敛为一个稳定接口，引擎其余模块只需调用 `Engine_Env::exe_dir_get()` 即可，**无需感知平台**。

本模块位于引擎层目录 `引擎层/src/tools/Engine_Env/`，是一个**纯头文件模块**（header-only）：

- `引擎环境.h` —— 公共头文件，包含类声明与全部成员函数的内联实现（方法体全部写在类体内）。

无 `.cpp` 实现文件、无「局部命名空间使用.h」。全部成员为 `static`，类本身从不需要实例化（构造是隐式默认的，但引擎内不会有人创建 `Engine_Env` 对象——它本质是一个「命名空间 + 静态状态」的容器）。

### 1.2 解决的核心问题

引擎部署形态通常是「一个可执行文件 + 若干资源目录」整体打包分发（如 `EngineTests.exe` 与 `assets/`、`config/` 同目录）。此时存在一个经典路径问题：

- **工作目录（CWD）不可靠**：用户从资源管理器双击启动时，工作目录是 exe 所在目录；但从命令行、IDE、脚本、计划任务启动时，工作目录可能是任意位置（`C:\Users\...`、构建输出目录等）。以「相对当前工作目录」解释资源路径会**时灵时不灵**；
- **绝对路径不可移植**：硬编码绝对路径（如 `D:/xxx/资源/网格.obj`）在换机器、换目录后全部失效，且把部署细节泄漏进代码/配置。

`Engine_Env` 的解法：**以「可执行文件自身所在目录」作为稳定锚点**——无论从何处启动，exe 路径总能通过操作系统 API 精确取得，因此 `exe_dir / 相对资源路径` 恒成立。`Mesh_Loader`、`Config_Loader` 等资源型模块正是基于这一锚点实现「打包即部署」。

同时，三平台 API 的差异（宽字符 vs 窄字符、固定缓冲 vs 动态扩容、符号链接 vs 进程 API）在本模块内被彻底消化，调用方得到的是**统一语义**的 `std::filesystem::path`。

### 1.3 功能要点一览

| 能力 | 说明 |
| --- | --- |
| exe 路径获取 | `exe_path_get()` 返回可执行文件完整绝对路径（`const path&`），惰性初始化 |
| exe 目录获取 | `exe_dir_get()` 返回可执行文件所在目录（`const path&`），惰性初始化 |
| 绝对路径拼接（path 重载） | `absolute_path_get(path)` = `exe_dir_get() / path` |
| 绝对路径拼接（string 重载） | `absolute_path_get(string)` 把 UTF-8 `std::string` 先转为 `u8string` 再拼接 |
| 三平台实现 | Windows `GetModuleFileNameW`（宽字符/32767 缓冲）；Linux `/proc/self/exe` `readlink`（动态扩容）；macOS `_NSGetExecutablePath`（两阶段取长度） |
| 惰性初始化 | 首次调用才真正查询系统 API，结果缓存于静态成员，后续调用零开销 |
| 失败回落 | 平台 API 失败时记录错误日志并**回落**到 `std::filesystem::current_path()`（工作目录），保证引擎不因路径查询失败而崩溃 |
| 中文路径 | Windows 走宽字符 API（`GetModuleFileNameW`），exe 路径含中文（如 `D:/代码存储/...`）时无乱码 |

### 1.4 非目标（明确不做的事）

- **不做进程内其他信息查询**：不提供命令行参数、环境变量、系统信息、CPU/内存状态等；
- **不做路径存在性校验**：`absolute_path_get` 只做字符串拼接，不检查结果路径是否真实存在（存在性由调用方经 `Data_Validator::path_check` 或文件系统 API 验证）；
- **不做相对化/规范化**：不提供 `path` 的 `..` 折叠、符号链接解析（Linux 分支除外——`/proc/self/exe` 本身解析出的是真实路径）；
- **不做运行期路径变更**：exe 路径缓存后不再刷新（进程运行中 exe 路径理论上不会变）；
- **不做多线程保护**：惰性初始化无锁；若多线程并发首次调用存在数据竞争（引擎单线程模型下安全）。

## 二、模块提供接口（完整公开接口清单）

以下接口签名全部从 `引擎层/src/tools/Engine_Env/引擎环境.h` 逐字摘录，与源码完全一致。

### 2.1 类：`engine::Engine_Env`

```cpp
namespace engine
{
	//引擎环境
	class Engine_Env
	{
	private:
		//存储可执行文件路径
		static void exe_path_store(void);
	public:
		//获取可执行文件路径
		static const std::filesystem::path& exe_path_get(void);
		//获取可执行文件目录
		static const std::filesystem::path& exe_dir_get(void);
		//绝对路径获取 —— 路径重载
		static std::filesystem::path absolute_path_get(const std::filesystem::path& path);
		//绝对路径获取 —— 字符串重载
		static std::filesystem::path absolute_path_get(const std::string& path);
	private:
		//可执行文件路径
		inline static std::filesystem::path exe_path{};
		//可执行文件目录
		inline static std::filesystem::path exe_dir{};
	};
}
```

### 2.2 接口逐条说明

#### `static const std::filesystem::path& exe_path_get(void)`

| 项目 | 说明 |
| --- | --- |
| 参数 | 无 |
| 返回值 | `const std::filesystem::path&`——**引用**可执行文件完整绝对路径（含文件名，如 `D:/game/EngineTests.exe`）。引用的是静态成员 `exe_path`，生命周期与进程等长 |
| 行为 | **惰性初始化**：若 `exe_path` 为空（首次调用），调用私有 `exe_path_store()` 查询系统 API 并填充 `exe_path`/`exe_dir`；查询抛异常（平台 API 失败）时记录两条错误日志（`"错误: {异常消息}"`、`"已回退到工作目录"`）并回落：`exe_path = current_path(); exe_dir = exe_path.parent_path();`。后续调用直接返回缓存 |

注意返回值是**引用**（`const path&`）：调用方拿到的是静态成员的别名，拷贝会复制、不可通过此引用修改（const）。返回引用而非值，省去每次调用的路径拷贝开销。

#### `static const std::filesystem::path& exe_dir_get(void)`

| 项目 | 说明 |
| --- | --- |
| 参数 | 无 |
| 返回值 | `const std::filesystem::path&`——**引用**可执行文件所在目录（不含文件名，如 `D:/game/`）。引用静态成员 `exe_dir` |
| 行为 | 与 `exe_path_get` 相同的惰性初始化逻辑（判断 `exe_path.empty()`，需要时 `exe_path_store()`，异常回落）。返回 `exe_dir` |

注意：`exe_dir` 的填充**依赖 `exe_path_store()`**（其末尾统一执行 `exe_dir = exe_path.parent_path();`）。若直接调用 `exe_dir_get()`，会触发同一初始化路径，`exe_dir` 与 `exe_path` 同时就绪。

#### `static std::filesystem::path absolute_path_get(const std::filesystem::path& path)` —— path 重载

| 项目 | 说明 |
| --- | --- |
| 参数 | `path`：相对路径（或任意路径），`std::filesystem::path` 类型 |
| 返回值 | `std::filesystem::path`：`exe_dir_get() / path` 的拼接结果（值返回） |
| 行为 | 先触发 `exe_dir_get()`（惰性初始化），再执行 `exe_dir / path`（`path::operator/` 拼接） |

设计要点：

- 若 `path` 本身是绝对路径，`operator/` 的拼接结果仍是 `path`（`path` 拼接规则：右操作数为绝对路径时左操作数被忽略）——因此本函数对「绝对/相对」输入都安全；
- 返回值是**值**（非引用），因为拼接产生新路径。

#### `static std::filesystem::path absolute_path_get(const std::string& path)` —— string 重载

| 项目 | 说明 |
| --- | --- |
| 参数 | `path`：**UTF-8 编码**的 `std::string` 相对路径（引擎内部路径出入参约定） |
| 返回值 | `std::filesystem::path`：`exe_dir_get() / u8_path` |
| 行为 | 先把 `std::string` 逐字节重解释为 `std::u8string`（`reinterpret_cast<const char8_t*>(path.data()), path.size()`），再与 `exe_dir_get()` 拼接 |

设计要点：

- 与「路径字符串转换.h」的 `string_to_path` 思路一致（UTF-8 字节 → `u8string` → path），但**直接内联在拼接前**，不依赖外部函数；
- 源码注释明确「要求 string 编码格式为 UTF-8」——入参若不是 UTF-8（如 GBK），中文路径会按 UTF-8 误解，产生乱码路径；
- 调用方典型用例：`Mesh_Loader::load_obj` 中 `path absolute_path = Engine_Env::absolute_path_get(mesh_path);` 把调用方给的 UTF-8 字符串路径拼成可执行目录下的绝对路径。

#### 私有：`static void exe_path_store(void)`

平台相关的路径获取内核，仅在惰性初始化时调用一次。三平台实现详见 §4.1。行为约定：成功时填充 `exe_path`（完整路径）并在末尾执行 `exe_dir = exe_path.parent_path();`；失败时**抛异常**（`std::runtime_error`），由 `exe_path_get`/`exe_dir_get` 捕获后回落。

## 三、模块内部架构

### 3.1 成员变量

| 成员 | 类型 | 初值 | 语义 |
| --- | --- | --- | --- |
| `exe_path` | `inline static std::filesystem::path` | 空路径 `{}` | 可执行文件完整绝对路径；空值同时充当「未初始化」哨兵（惰性初始化判据） |
| `exe_dir` | `inline static std::filesystem::path` | 空路径 `{}` | 可执行文件目录（= `exe_path.parent_path()`）；由 `exe_path_store` 统一填充 |

- `inline static`：C++17 起，`inline` 静态数据成员在头文件中定义不触发 ODR 违规——这是本模块能做成 **header-only** 的关键语言特性；
- 「`exe_path.empty()` 即未初始化」的判据成立的前提：真实 exe 路径**永远不可能为空字符串**（任何合法 exe 路径至少含一个字符），哨兵无歧义；
- 两个静态成员构成「初始化锁存」：任一 getter 首次调用触发存储后，两者同时就绪，后续调用直接返回。

### 3.2 文件组织与依赖

```
引擎环境.h（单文件，header-only）
├── #include "common/前置头文件包含.h"     ← <string> <filesystem> <stdexcept>(runtime_error)
├── #include "src/tools/Logging/日志系统.h" ← Log::error（平台 API 失败回落日志）
├── #ifdef _WIN32      → #include <windows.h>          （GetModuleFileNameW）
├── #elif defined(__linux__) → #include <unistd.h> <limits.h>  （readlink / PATH_MAX）
├── #elif defined(__APPLE__) → #include <mach-o/dyld.h> <limits.h> （_NSGetExecutablePath）
└── #else → #error "Unsupported platform"
```

| 依赖项 | 用途 |
| --- | --- |
| `日志系统.h` | `Log::error` 输出平台 API 失败信息与回落提示（两条日志：异常消息 + "已回退到工作目录"） |
| `<windows.h>`（仅 Windows） | `GetModuleFileNameW`、`DWORD` |
| `<unistd.h>`/`<limits.h>`（仅 Linux） | `readlink`、`ssize_t`、`PATH_MAX` |
| `<mach-o/dyld.h>`/`<limits.h>`（仅 macOS） | `_NSGetExecutablePath`、`uint32_t`、`PATH_MAX` |

### 3.3 内部状态流转

```
进程启动（exe_path / exe_dir 均为空）
        │
        ▼
任意调用 exe_path_get() / exe_dir_get()
        │
        ├─ exe_path.empty() ?
        │     ├─ 否 → 直接返回缓存（后续调用 O(1)）
        │     └─ 是 → exe_path_store()
        │               ├─ 成功 → exe_path = 系统API结果
        │               │         exe_dir  = exe_path.parent_path()
        │               └─ 失败(抛异常) → Log::error ×2
        │                                  exe_path = current_path()
        │                                  exe_dir  = exe_path.parent_path()
        ▼
  返回引用（此后路径恒为已初始化）
```

## 四、模块设计/实现细节

### 4.1 三平台 `exe_path_store` 实现逐平台拆解

#### Windows（`_WIN32` / `_WIN64`）：`GetModuleFileNameW` 宽字符 + 32767 缓冲

```cpp
#if defined(_WIN32) || defined(_WIN64)
		std::wstring buffer(32767, L'\0');
		DWORD size = GetModuleFileNameW(nullptr, buffer.data(),
			static_cast<DWORD>(buffer.size()));
		if (size == 0) {
			throw std::runtime_error("GetModuleFileNameW failed");
		}
		if (size >= buffer.size()) {
			buffer.resize(size + 1);
			size = GetModuleFileNameW(nullptr, buffer.data(),
				static_cast<DWORD>(buffer.size()));
			if (size == 0) {
				throw std::runtime_error("GetModuleFileNameW failed after resize");
			}
		}
		buffer.resize(size);
		exe_path = std::filesystem::path(buffer);
#endif
```

| 细节 | 说明 |
| --- | --- |
| 宽字符 | `GetModuleFileNameW`（宽字符版）而非 `GetModuleFileNameA`（ANSI 版）：exe 路径含中文（如 `D:/代码存储/...`）时，ANSI 版按系统代码页解释会乱码或截断，宽字符版返回 UTF-16，交给 `path(buffer)` 正确转为内部宽字符表示 |
| 缓冲大小 32767 | Windows 路径最大长度（`MAX_PATH` 扩展后为 32767 字符）；一次申请足够覆盖绝大多数情况 |
| 失败判定 `size == 0` | `GetModuleFileNameW` 失败返回 0（`GetLastError` 可查原因），抛 `runtime_error` 交上层回落 |
| 截断重试 `size >= buffer.size()` | 若返回长度 ≥ 缓冲容量，说明**缓冲区不够被截断**（理论场景：路径恰好超过 32767 字符，或 API 语义中的「缓冲区不足」），扩到 `size + 1` 再调一次；二次失败抛异常 |
| `buffer.resize(size)` | 按真实长度收尾（去掉 `\0` 尾随空间） |
| `exe_path = path(buffer)` | 宽字符串直接构造 `filesystem::path`（Windows 下 `path` 内部即 `wstring`） |

#### Linux（`__linux__`）：`/proc/self/exe` 符号链接 `readlink` 动态扩容

```cpp
#elif defined(__linux__)
		std::string buffer(PATH_MAX, '\0');
		ssize_t len;
		while ((len = readlink("/proc/self/exe", buffer.data(), buffer.size()))
			== static_cast<ssize_t>(buffer.size())) {
			buffer.resize(buffer.size() * 2);
		}
		if (len == -1) {
			throw std::runtime_error("readlink /proc/self/exe failed");
		}
		buffer.resize(len);
		exe_path = std::filesystem::path(buffer);
#endif
```

| 细节 | 说明 |
| --- | --- |
| `/proc/self/exe` | Linux 内核提供的进程 exe 符号链接；`readlink` 解析出真实可执行文件绝对路径 |
| 初始缓冲 `PATH_MAX` | 典型 4096；路径可能更长（深层目录），故动态扩容 |
| 循环扩容 | `readlink` 返回 `buffer.size()`（满写）时说明缓冲不够，**翻倍扩容**重试；直至返回值 < 缓冲大小（正常截断语义） |
| `len == -1` | `readlink` 失败（罕见，如 `/proc` 未挂载），抛异常交上层回落 |
| `buffer.resize(len)` | 收尾到真实长度 |
| 窄字符 | Linux 路径原生 `char` 字节（通常 UTF-8），`path(buffer)` 直接构造 |

#### macOS（`__APPLE__`）：`_NSGetExecutablePath` 两阶段取长度

```cpp
#elif defined(__APPLE__)
		uint32_t size = 0;
		_NSGetExecutablePath(nullptr, &size);
		if (size == 0) {
			throw std::runtime_error("_NSGetExecutablePath failed to get size");
		}
		std::string buffer(size, '\0');
		if (_NSGetExecutablePath(buffer.data(), &size) != 0) {
			throw std::runtime_error("_NSGetExecutablePath failed");
		}
		exe_path = std::filesystem::path(buffer);
#endif
```

| 细节 | 说明 |
| --- | --- |
| 两阶段 | 第一次调用 `_NSGetExecutablePath(nullptr, &size)` 只取所需大小（写回 `size`）；第二次用该大小分配缓冲后真正写入 |
| 返回约定 | 成功返回 0；缓冲不足返回 -1（本实现已按首次大小分配，正常不会触发） |
| `size == 0` 保护 | 理论上路径长度不会为 0，若为 0 视为异常抛错 |
| 注：`_NSGetExecutablePath` 返回的可能是**相对路径** | macOS 官方文档说明该 API 可能返回非绝对路径（极少见），严格场景需再 `realpath` 规范化——本实现未做，属已知简化 |

#### 不支持平台：`#error "Unsupported platform"`

编译期强制失败，杜绝「静默编译一个永远查询不到路径的实现」。

### 4.2 失败回落策略分析

`exe_path_get`/`exe_dir_get` 的异常处理：

```cpp
if (exe_path.empty())
{
    try { exe_path_store(); }
    catch (const std::exception& e)
    {
        Log::error("错误: {}", e.what());
        Log::error("已回退到工作目录");
        exe_path = std::filesystem::current_path();
        exe_dir = exe_path.parent_path();
    }
}
return exe_path;   // 或 exe_dir
```

设计决策：

- **绝不因路径查询失败而让引擎启动失败**：即使三平台 API 全部失效（如 Windows 上 `GetModuleFileNameW` 被沙箱拦截），引擎仍以「工作目录」为锚点继续运行——资源路径语义退化为「相对工作目录」，与 CWD 方案等价，功能不崩；
- **回落值 = 工作目录（current_path）**：`current_path()` 是标准库函数，失败概率极低；其值与 exe 目录在「双击启动」场景下恰好一致，回落损失最小；
- **两条错误日志**：`"错误: {e.what()}"` 输出平台异常详情，`"已回退到工作目录"` 明示行为变化，方便排查「为什么资源找不到了」；
- **回落也走 `parent_path()`**：`exe_path = current_path()`（把工作目录整体当作「伪 exe 路径」），`exe_dir = exe_path.parent_path()`（其上级）——注意这与「把工作目录当作伪 exe 目录」的直觉不同：回落后的 `exe_dir_get()` 返回的是工作目录的**上级目录**。这是源码的实际行为（回落代码与成功路径共用 `parent_path()` 逻辑），重开发/排查时注意此语义。

### 4.3 惰性初始化的收益

- **启动零开销**：进程启动时并不查询 exe 路径（`static` 成员仅空初始化）；只有第一个真正需要路径的模块（如 `Mesh_Loader`、`Config_Loader`）才触发系统调用；
- **单次查询**：首次查询结果缓存，后续 `exe_path_get()`/`exe_dir_get()`/`absolute_path_get()` 全部直接读静态成员，路径构造成本 O(1)；
- **线程安全注意**：惰性初始化无锁。单线程主循环下安全；若未来多线程，两个线程可能同时看到 `exe_path.empty()` 并重复执行 `exe_path_store()`（结果幂等——都写同样的路径，无数据损坏，但理论上构成数据竞争，需加 `std::once_flag` 或局部静态）。

### 4.4 `absolute_path_get` 的拼接语义细节

```cpp
static std::filesystem::path absolute_path_get(const std::filesystem::path& path)
{
    return exe_dir_get() / path;
}
static std::filesystem::path absolute_path_get(const std::string& path)
{
    std::u8string u8_path(reinterpret_cast<const char8_t*>(path.data()), path.size());
    return exe_dir_get() / u8_path;
}
```

`path::operator/` 的拼接规则（`a / b`）：

| 输入 `b` | 结果 |
| --- | --- |
| 相对路径（如 `assets/mesh.obj`） | `a` 与 `b` 拼接：`D:/game/assets/mesh.obj` |
| 绝对路径（如 `C:/other/x.obj`） | 直接取 `b`（忽略 `a`）：`C:/other/x.obj` |
| 空路径 | `a` 原样返回 |

因此 `absolute_path_get` 对「相对/绝对/空」三种输入都安全——**传入绝对路径时不产生「绝对路径被错误拼接」的 bug**。这也解释了 `Mesh_Loader` 的路径双源解析为何可靠：`Engine_Env::absolute_path_get(mesh_path)` 对绝对路径入参会原样返回（走 exe_dir 拼接分支无意义但无害），对相对路径入参生成 exe 目录下的候选路径。

### 4.5 与其它模块的协作

#### 与 `Config_Loader`（配置加载器，`src/tools/Config_Loader/`）

`配置加载器.h` 直接 `#include "src/tools/Engine_Env/引擎环境.h"`；其实现 `core/配置加载器.cpp` 中：

```cpp
//基目录获取
const path Config_Loader::base_dir_get(void)
{
    //返回配置基目录
    return Engine_Env::exe_dir_get();
}
```

配置系统以「可执行文件目录」为**配置基目录**，配置文件（JSON 等）按 `exe_dir / 相对路径` 定位——打包部署后配置与 exe 同目录即可被找到，与启动方式无关。

#### 与 `Mesh_Loader`（网格加载器，`src/tools/Mesh_Loader/core/网格加载器.cpp`）

```cpp
//拼可执行文件目录下的绝对路径
path absolute_path = Engine_Env::absolute_path_get(mesh_path);
//若原样路径有效（按当前工作目录解释）
if (Data_Validator::path_check(mesh_path))
    read_path = string_to_path(mesh_path);
//若可执行文件目录下的路径有效
else if (Data_Validator::path_check(absolute_path))
    read_path = absolute_path;
```

网格加载的**路径双源解析**：优先按「原样路径（相对工作目录）」解释，失败则按「可执行目录下的绝对路径」（本模块产出）解释。`Engine_Env` 是第二解析源的提供者，也是「打包部署场景下网格资源可定位」的保证。

#### 与 `Auxi_Algorithm`（辅助算法，`src/tools/Auxi_Algorithm/路径字符串转换.h`）

`路径字符串转换.h` 反向 `#include "引擎环境.h"`（冗余包含，见辅助算法文档 §3.2）。两者职责互补：`Engine_Env` 负责「进程锚点路径」，`Auxi_Algorithm` 负责「path ↔ UTF-8 string 字节转换」；`Mesh_Loader` 实际同时使用二者。

#### 与 `Collision_Proxy`（碰撞代理器，`src/core/spatial/collision/Collision_Proxy/碰撞代理器.h`）

该头文件包含引擎环境头文件（头文件包含链传播），代理器内部间接获得 exe 路径能力（源码中未见直接调用 `Engine_Env` 符号，属间接/潜在使用）。

### 4.6 易踩坑点（重开发速查）

1. **回落后的 `exe_dir` 语义**：平台 API 失败回落时 `exe_dir = current_path().parent_path()`——是工作目录的**上级**目录，不是工作目录本身。排查「回落模式下资源找不到」时先确认此语义；
2. **`exe_dir_get()` 与 `exe_path_get()` 的初始化耦合**：两者都靠「`exe_path.empty()`」判断是否初始化；`exe_path_store` 一次性填两个成员。**不要**只初始化 `exe_dir` 而留空 `exe_path`（否则下次调用会重复查询，且 `exe_dir` 依赖 `exe_path` 计算）；
3. **返回值是引用**：`const path&` 返回值绑定静态成员。调用方若 `auto p = Engine_Env::exe_dir_get();` 会拷贝（安全）；若 `const auto& p = ...` 则引用静态成员（生命周期长，安全，但不可赋值）；
4. **Windows 必须用宽字符 API**：勿为省事改用 `GetModuleFileNameA`——中文/Unicode exe 路径（本引擎部署目录即含中文「代码存储/白银纪元」）会乱码；
5. **Linux 扩容循环**：`readlink` 满写时返回值恰好等于缓冲大小，**不能**把这个「恰好满」误判为成功——源码用 `== buffer.size()` 判满并扩容，重写时保持此判据；
6. **macOS 的相对路径可能**：`_NSGetExecutablePath` 在极少数情况下返回相对路径，本实现未做 `realpath` 规范化；如需绝对保证可在其后补一次规范化；
7. **头文件平台的 `#error`**：新增平台（如 FreeBSD、Emscripten）时编译会立即失败——这是有意设计，新增平台须补齐 `exe_path_store` 分支；
8. **惰性初始化无锁**：多线程首调存在竞争；工程上引擎单线程，若引入多线程需用 `std::once_flag` 或函数局部 `static`（C++11 起线程安全初始化）；
9. **`absolute_path_get` 不校验存在性**：拼接结果可能指向不存在的文件，调用方须自行 `path_check`/`exists`（`Mesh_Loader` 即先拼后验）；
10. **string 重载要求 UTF-8 入参**：非 UTF-8 的 `std::string`（如 GBK）会按 UTF-8 误解，中文乱码；引擎统一约定出入参为 UTF-8，勿传系统代码页字符串。

## 五、模块运行链路

### 5.1 首次路径查询（惰性初始化）时序

```
调用方（如 Mesh_Loader::load_obj 或 Config_Loader::base_dir_get）
        │
        ▼
Engine_Env::absolute_path_get(mesh_path)      ← 或 exe_dir_get()/exe_path_get()
        │
        ├─ exe_dir_get()
        │     ├─ exe_path.empty() ?  是
        │     └─ exe_path_store()
        │           ├─ [Windows] GetModuleFileNameW 宽字符查询（32767 缓冲）
        │           │     └─ 成功 → exe_path = 完整路径
        │           ├─ [Linux]  readlink /proc/self/exe（扩容循环）
        │           │     └─ 成功 → exe_path = 真实路径
        │           ├─ [macOS] _NSGetExecutablePath 两阶段
        │           │     └─ 成功 → exe_path = 路径
        │           └─ 统一收尾：exe_dir = exe_path.parent_path()
        │                          （失败时 catch → Log::error×2 → 回落 current_path）
        └─ 返回 exe_dir 引用
        │
        ▼
exe_dir / mesh_path   →  绝对路径（如 D:/game/assets/网格.obj）
```

### 5.2 网格加载路径双源解析链路（含引擎环境参与）

```
Mesh_Loader::load_obj(mesh_path)
  │
  ├─ ① absolute_path = Engine_Env::absolute_path_get(mesh_path)
  │       └─ 触发 exe_dir 惰性初始化 → 拼出「可执行目录下」候选路径
  ├─ ② Data_Validator::path_check(mesh_path)     → 原样路径（工作目录）有效？
  │       ├─ 是 → read_path = 原样路径
  │       └─ 否 → ③ Data_Validator::path_check(absolute_path) → exe 目录路径有效？
  │                   ├─ 是 → read_path = absolute_path
  │                   └─ 否 → 双源皆败 → 警告 + 返回 false
  └─ ④ ifstream(read_path) 加载
```

### 5.3 配置加载链路（含引擎环境参与）

```
Config_Loader 初始化
  ├─ base_dir = Engine_Env::exe_dir_get()          ← 配置基目录 = exe 目录
  ├─ 以 base_dir 为根递归扫描配置文件（content_scan）
  └─ 按需加载 JSON 配置（路径相对 base_dir 解析）
```

### 5.4 依赖方向汇总

```
调用方（Mesh_Loader / Config_Loader / Collision_Proxy(间接) / ...）
        │  调用 exe_path_get / exe_dir_get / absolute_path_get
        ▼
Engine_Env（tools/Engine_Env，header-only）
        ├── 内部：exe_path / exe_dir（inline static，惰性初始化）
        ├── 依赖：Logging::Log（失败回落日志）
        ├── 依赖：<windows.h> / <unistd.h> / <mach-o/dyld.h>（平台 API）
        └── 依赖：common/前置头文件包含.h（标准库）
```

结论：`Engine_Env` 是引擎资源寻址体系的**根基模块**——`Config_Loader`（配置基目录）、`Mesh_Loader`（网格路径兜底源）直接依赖它，`Auxi_Algorithm` 反向包含它（形成头文件级依赖环但无符号级循环，编译器可处理）。重开发时保持「exe 路径/目录 + 惰性初始化 + 失败回落 + 绝对路径拼接」四个契约不变，即可保持下游全部兼容。
