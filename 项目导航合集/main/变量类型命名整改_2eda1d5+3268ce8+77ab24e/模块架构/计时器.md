## 一、模块功能

### 1.1 模块定位

「计时器」（`Timer`）是引擎层 `src/tools/` 工具集中一个**性能测量/耗时统计工具模块**。它围绕 C++20 标准库的 `std::chrono::steady_clock` 建立了一组**命名任务式的计时设施**：调用方可以给一段代码段起一个名字（如 `"physics_step"`、`"mesh_load"`），在代码段开始处 `task_build` 打点，在结束处 `elapsed` 取耗时，需要时还可以 `restart` 实现「打点-复位」的一次性测量语义。

与手写 `auto start = std::chrono::steady_clock::now(); ... auto end = ...;` 相比，本模块提供的核心价值是：

1. **任务化管理**：多个命名计时任务并存于一张内部表中，互不干扰，避免调用方各自维护 `time_point` 变量；
2. **精度换算封装**：把「纳秒/微秒/毫秒/秒」四种单位的换算收敛为四个静态方法，调用方无需记忆 `duration_cast` 模板语法；
3. **时钟一致性**：整个引擎统一使用 `steady_clock`（单调时钟），杜绝 `system_clock` 受系统时间调整影响的测量误差。

本模块位于引擎层目录 `引擎层/src/tools/Timer/`，由三份文件构成：

- `计时器.h` —— 公共头文件，声明 `Clock`/`TimePoint`/`Duration` 三个别名与 `Timer` 类；
- `局部命名空间使用.h` —— 模块内部使用的 `using` 别名收敛文件（不对外暴露）；
- `core/计时器.cpp` —— 模块全部实现（`task_build`、`task_unload`、`elapsed` 与四个精度转换方法）。

### 1.2 解决的核心问题

引擎开发与调优期需要反复回答同一类问题：「某段逻辑跑了多久？某帧里物理、渲染、事件分发各占多少时间？」直接使用 `std::chrono` 的痛点在于：

- **样板代码重复**：每次测量都要写 `auto t0 = Clock::now(); ... auto dt = Clock::now() - t0;`，且不同精度的换算写法各不相同；
- **状态散落**：多个并行测量需要多个局部变量，作用域管理繁琐，容易把起点变量放错位置；
- **不可复用**：测量代码与业务代码耦合，无法沉淀为引擎公共能力。

`Timer` 用「命名任务表」解决上述问题：任务名即状态，`task_build` 建点、`elapsed` 取差、`restart` 复位，测量逻辑完全与业务解耦。同时，四个静态精度转换方法（`units`/`Milli_units`/`Micro_units`/`Nano_units`）作为 `Duration` 的通用「翻译器」，即便不用任务表，也可单独拿出来把任意 `Duration` 换算成目标单位数值。

### 1.3 功能要点一览

| 能力 | 说明 |
| --- | --- |
| 命名计时任务 | `task_build(task_name)` 注册任务并打起点；同名任务不可重复注册 |
| 任务卸载 | `task_unload(task_name)` 移除任务及其起点 |
| 耗时读取 | `elapsed(task_name)` 返回任务起点到当前时刻的时间段（`Duration`） |
| 复位读取 | `elapsed(task_name, true)` 返回上次起点到当前的时间段，**并**把起点重置为当前时刻（restart 语义） |
| 秒级换算 | `units(Duration)` → `double`（秒） |
| 毫秒级换算 | `Milli_units(Duration)` → `double`（毫秒） |
| 微秒级换算 | `Micro_units(Duration)` → `double`（微秒） |
| 纳秒级换算 | `Nano_units(Duration)` → `long long`（纳秒，整型） |
| 时钟统一 | 全部基于 `std::chrono::steady_clock`（单调时钟，不受系统时间调整影响） |
| 别名体系 | `Clock`/`TimePoint`/`Duration` 三个公开别名，调用方可直接引用 |

### 1.4 非目标（明确不做的事）

- **不做帧率统计/平均耗时聚合**：本模块只做单次测量，不做多次采样平均、最大最小、直方图等统计；
- **不做日志自动输出**：测量结果由调用方自行 `Log` 或使用，模块不主动打日志；
- **不做跨线程计时**：`std::unordered_map` 无并发保护，非线程安全；
- **不做挂钟时间/日期功能**：无 `system_clock` 相关能力，不提供「当前几点几分」；
- **不做自动析构清理**：任务表随 `Timer` 对象析构而释放；单次任务用后须显式 `task_unload`（或依赖对象析构）清理。

## 二、模块提供接口（完整公开接口清单）

以下接口签名全部从 `引擎层/src/tools/Timer/计时器.h` 与 `引擎层/src/tools/Timer/core/计时器.cpp` 逐字摘录，与源码完全一致。

### 2.1 命名空间级别名（`engine` 命名空间）

```cpp
namespace engine
{
    //时钟别名
    using Clock = std::chrono::steady_clock;
    //时间戳别名
    using TimePoint = Clock::time_point;
    //时间段别名
    using Duration = Clock::duration;
    ...
}
```

| 别名 | 实体类型 | 语义 |
| --- | --- | --- |
| `engine::Clock` | `std::chrono::steady_clock` | 单调时钟：仅可测量时间间隔，不可获取日历时间；`now()` 不受系统时间修改影响，是性能测量的标准选择 |
| `engine::TimePoint` | `Clock::time_point` | 时间戳：任务起点的存储类型 |
| `engine::Duration` | `Clock::duration` | 时间段：`elapsed` 的返回值类型；在主流实现上为 `std::chrono::nanoseconds`（纳秒精度）的别名 |

注意：`Duration` 是**时钟自带的纳秒精度时长类型**。在 Windows MSVC 与 Linux libstdc++ 的典型实现中 `steady_clock::duration` 即 `nanoseconds`，故 `Nano_units` 的实现（`duration_cast<nanoseconds>`）在多数平台上近似恒等变换，但在理论上有差异的实现上仍是正确的显式换算。

### 2.2 类：`engine::Timer`

```cpp
namespace engine
{
    //计时器
    class Timer 
    {
    public:
        //构造函数
        Timer(void) = default;
        
        //析构函数
        ~Timer() = default;

        //构建计时任务
        bool task_build(const std::string& task_name);

        //卸载计时任务
        bool task_unload(const std::string& task_name);

        //获取时间间隔
        Duration elapsed(const std::string& task_name,bool restart = false);

        //获取秒级时间精度
        static double units(const Duration& duration);

        //获取毫秒级时间精度
        static double Milli_units(const Duration& duration);

        //获取微秒级时间精度
        static double Micro_units(const Duration& duration);

        //获取纳秒级时间精度
        static long long Nano_units(const Duration& duration);

    private:
        //计时任务起点集合
        std::unordered_map<std::string, TimePoint> task_origin_set;
    };
}
```

### 2.3 接口逐条说明

#### `Timer(void) = default` / `~Timer() = default`

默认构造与默认析构。类不持有堆资源（`unordered_map` 自管），无特殊构造/析构语义。构造后任务表为空，首次使用前须 `task_build`。

#### `bool task_build(const std::string& task_name)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `task_name`：计时任务名称，用作任务表的键 |
| 返回值 | `true`：任务注册成功（该名称此前不存在，已建立起点）；`false`：任务注册失败（同名任务已存在，未做任何修改） |
| 行为 | 若 `task_origin_set` 中不存在该名称（`count == 0`），插入 `{task_name, Clock::now()}`，起点即当前时刻；否则直接返回 `false`，**不更新**既有起点 |

典型用法：在待测代码段**开头**调用 `task_build("某任务")` 打点。重复调用同名任务不会覆盖旧起点——这避免了「误打点导致耗时被拉长」的隐晦 bug（若允许覆盖，第二次 `task_build` 会吞掉第一次测量的时间窗）。

#### `bool task_unload(const std::string& task_name)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `task_name`：待卸载的计时任务名称 |
| 返回值 | `true`：卸载成功（任务存在，已从表中移除）；`false`：卸载失败（任务不存在，无操作） |
| 行为 | `find(task_name)` 定位；命中则 `erase(it)` 移除该任务及其起点；未命中返回 `false` |

典型用法：计时结束后清理任务表，防止任务表无限膨胀（每个不重名的任务都会永久占一个表项）。对**单次测量**（建点→取差→卸载）模式是必需的一步。

#### `Duration elapsed(const std::string& task_name, bool restart = false)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `task_name`：目标任务名称；`restart`：是否在读取后复位起点，默认 `false` |
| 返回值 | 目标任务存在时：`Clock::now() - 起点`（自建点/上次复位以来的时间间隔）；任务不存在时：**默认构造的 `Duration{}`（零时长）** |
| 行为 | 三分支逻辑：<br>① 任务存在且 `restart == false`：返回 `Clock::now() - it->second`，起点不动——重复调用会得到**单调递增**的累计耗时；<br>② 任务存在且 `restart == true`：先把旧起点缓存到局部 `buffer`，再把 `it->second` 更新为 `Clock::now()`，最后返回 `Clock::now() - buffer`——**先复位后计时**，本次返回的是「上一次打点至今」的完整时间窗，下次调用起算新窗；<br>③ 任务不存在：返回 `{}`（零 `Duration`），无日志、无异常 |

`restart` 语义的精确定义（源码逐行翻译）：

```cpp
Duration Timer::elapsed(const string& task_name, bool restart)
{
    auto it = task_origin_set.find(task_name);
    if (it != task_origin_set.end() && restart == false)
        return Clock::now() - it->second;              // 分支①：纯读取
    else if (it != task_origin_set.end() && restart == true)
    {
        TimePoint buffer = it->second;                 // 缓存旧起点
        it->second = Clock::now();                     // 复位起点
        return Clock::now() - buffer;                  // 返回旧窗
    }
    else
        return {};                                     // 分支③：任务不存在
}
```

易混淆点：

- 分支②的返回值是 **`Clock::now() - buffer`**，其中 `buffer` 是**旧起点**，`Clock::now()` 是复位后的当前时刻——两者之间的差恰好是「上一个计时窗」的完整时长。复位动作本身不丢时间；
- 分支②存在一个理论上的亚微秒误差：`it->second = Clock::now()` 与 `return Clock::now() - buffer` 两次调用 `Clock::now()`，第二次比第一次晚几个时钟 tick，返回值略大于真实窗长（误差为两次 `now()` 之间的开销，纳秒级，可忽略）；
- `restart == true` 的典型场景：**帧间步进**——每帧结束时取「本帧耗时」并复位起点，下一帧继续累计（帧耗时的差分测量）。

#### `static double units(const Duration& duration)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `duration`：任意时长 |
| 返回值 | 以**秒**为单位的 `double` 浮点数值 |
| 行为 | `return duration<double>(sometime).count();` —— 用 `duration<double>`（period 为 1，即秒）重新解释并计数 |

#### `static double Milli_units(const Duration& duration)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `duration`：任意时长 |
| 返回值 | 以**毫秒**为单位的 `double` 浮点数值 |
| 行为 | `return duration<double, milli>(sometime).count();` —— 毫秒精度浮点换算（1 ms = 1e-3 s） |

#### `static double Micro_units(const Duration& duration)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `duration`：任意时长 |
| 返回值 | 以**微秒**为单位的 `double` 浮点数值 |
| 行为 | `return duration<double, micro>(sometime).count();` —— 微秒精度浮点换算（1 µs = 1e-6 s） |

#### `static long long Nano_units(const Duration& duration)`

| 项目 | 说明 |
| --- | --- |
| 参数 | `duration`：任意时长 |
| 返回值 | 以**纳秒**为单位的 `long long` **整型**数值 |
| 行为 | `return duration_cast<nanoseconds>(sometime).count();` —— 与前三者不同：使用 `duration_cast` **截断式**整型换算（向下取整），返回 `long long` |

四个换算方法的对比：

| 方法 | 内部类型 | 返回值类型 | 换算精度 | 典型用途 |
| --- | --- | --- | --- | --- |
| `units` | `duration<double>` | `double` | 浮点，保留小数 | 秒级宏观耗时展示 |
| `Milli_units` | `duration<double, milli>` | `double` | 浮点，保留小数 | 帧耗时（毫秒）常规测量 |
| `Micro_units` | `duration<double, micro>` | `double` | 浮点，保留小数 | 微秒级精细测量 |
| `Nano_units` | `duration_cast<nanoseconds>` | `long long` | 整型截断 | 需要精确整型纳秒数（如与外部整型纳秒 API 对接） |

## 三、模块内部架构

### 3.1 成员变量

| 成员 | 类型 | 语义 |
| --- | --- | --- |
| `task_origin_set` | `std::unordered_map<std::string, TimePoint>` | 计时任务起点集合：键为任务名，值为该任务最近的计时起点时间戳 |

- 键（`std::string`）：任务名，作为任务的唯一标识。同名任务不可重复建点（见 `task_build`）；
- 值（`TimePoint` = `steady_clock::time_point`）：任务起点。`elapsed` 用 `Clock::now() - 该值` 得到时间段；
- 无其他成员变量，无内部类/枚举，无静态成员。

### 3.3 数据流概览

```
task_build("A") ──► task_origin_set["A"] = Clock::now()     （打点）
elapsed("A")    ──► return Clock::now() - task_origin_set["A"]  （取差）
elapsed("A",true)─► 旧起点暂存 → 起点更新 → return now()-旧起点    （取差+复位）
task_unload("A")──► task_origin_set.erase("A")               （清点）
```

## 四、模块设计/实现细节

### 4.1 时钟选型：为什么是 `steady_clock`

`std::chrono` 提供三种时钟，选型依据：

| 时钟 | 单调性 | 受系统时间调整影响 | 适用场景 |
| --- | --- | --- | --- |
| `system_clock` | 否（可能跳变） | 是（NTP 校准、手动改时间会使其前进/后退） | 日历时间、时间戳落盘 |
| `steady_clock` | 是（保证只增不减） | 否 | **性能测量**（本模块选型） |
| `high_resolution_clock` | 实现相关（常为 steady 别名） | 实现相关 | 高精度测量（本引擎在随机数模块另作种子源使用） |

`steady_clock` 保证「两次 `now()` 之差恒为非负且单调递增」，是测量代码段耗时的唯一可靠选择。`system_clock` 若在测量中途被 NTP 校准，可能出现**负耗时**或**异常大耗时**，故本模块刻意排除。

### 4.2 任务表的数据结构选择：`unordered_map` 而非 `map`/`vector`

- `unordered_map` 的平均查找/插入 O(1)，适合「任务名 → 起点」的键值查询语义；
- 任务表规模小（引擎内同时计时任务通常个位数），哈希开销可忽略；
- 相比 `std::map`（O(log n) 红黑树）：省去树节点分配与比较开销；
- 相比 `vector<pair>`：提供 O(1) 平均的 `count`/`find`/`erase` 语义，代码更直接。

代价：迭代顺序不确定（对「列出所有任务」场景不友好），但本模块无此需求。

### 4.3 关键边界情况处理

| 场景 | 行为 | 说明 |
| --- | --- | --- |
| 对不存在的任务 `elapsed` | 返回零时长 `{}` | **静默**：无日志无异常。调用方须自行保证任务已建点，否则拿到 0 而不知情（易踩坑） |
| 对不存在的任务 `task_unload` | 返回 `false` | 幂等安全：重复卸载同一任务第二次返回 `false`，无副作用 |
| 重复 `task_build` 同名任务 | 返回 `false`，起点不变 | 保护既有计时窗，防止误覆盖 |
| `elapsed` 后不 `restart` 再次调用 | 返回更大的累计值 | 起点不变，得到的是「建点至今」的总耗时（单调增长） |
| `restart` 连续调用 | 每次返回「上一次调用至今」的时长 | 形成帧间差分测量 |
| 任务表满（内存耗尽） | `insert` 抛 `std::bad_alloc` | 未捕获，会向上传播（工程上不可达） |
| 任务名含中文 | 正常（`std::string` 按 UTF-8 存储） | 键的相等比较按字节序，同名中文字符串可正确命中 |

### 4.4 设计决策及原因

1. **`elapsed` 的 `restart` 默认参数为 `false`**：读取（不改变状态）是最常见用法，默认值让调用最简；`restart` 作为显式开启的「副作用模式」符合「默认无副作用」的接口设计原则。

2. **复位语义采用「先缓存旧起点」**：源码先用局部变量 `buffer` 保存旧起点，再更新成员，最后用 `Clock::now() - buffer` 计算——保证了「返回值 = 上一个完整计时窗」，且复位后新窗从当前时刻起算。若直接 `return Clock::now() - (it->second = Clock::now())` 则会把复位点之后的时间也漏掉，语义不正确。

3. **四个精度方法全是静态的**：换算只依赖参数 `Duration`，与任务表状态无关，故设计为 `static`——即使没有 `Timer` 实例，也能 `Timer::Milli_units(some_duration)` 直接用。这使精度换算与任务管理**解耦**，成为独立的纯函数工具。

4. **纳秒换算用整型、其余用浮点**：秒/毫秒/微秒的浮点表示能保留小数（如 0.5 ms），展示友好；纳秒量级整型即足够精确（1 ns 远小于时钟分辨率），用 `long long` 避免浮点精度浪费，也与「纳秒整型 API」生态对接。

5. **任务不存在时 `elapsed` 返回零而非报错**：与 `task_unload` 的 `false` 形成对比。选择「静默零值」的原因是：调用方在**正常流程**中总是先 `task_build` 再 `elapsed`，任务不存在只可能是编程错误；此时返回零时长不会导致崩溃/异常流，便于上层继续运行（后续可结合日志排查）。这是「容错优先」的设计取向。

### 4.5 与其它模块的协作

`Timer` 在引擎层**源码中尚无实际消费者**（检索 `src/tools/Timer` 引用，目前只有本模块自身文件）。它是引擎预留的**性能分析基础设施**，设计上可被任何耗时敏感模块直接引用，例如：

- 物理步进耗时测量：`task_build("physics")` → 步进 → `Timer::Milli_units(elapsed("physics", true))` 每帧输出；
- 网格加载耗时：`task_build("mesh_load")` → `Mesh_Loader::load_obj(...)` → `elapsed` 取整次加载时长；
- 碰撞检测耗时：`Collision_Region::detect()` 前后打点。

由于无现成消费者，本模块的接口约定（任务名唯一、restart 语义、静默零值）都需在**首次接入**时被上层验证与遵守。

### 4.6 易踩坑点（重开发速查）

1. **`elapsed` 不存在的任务返回 0 而非报错**：排查耗时异常为 0 时，先确认任务是否已 `task_build`；
2. **`task_build` 重复调用同名任务返回 `false` 且不改起点**：若想「重新打点」，先 `task_unload` 再 `task_build`（或利用 `elapsed(task, true)` 复位）；
3. **`restart` 的返回值是旧窗**：第一次 `elapsed(task, true)` 返回「建点至今」的时长并复位；此后再调用返回「上次至今」——不要在循环外先 `task_build` 又在循环内 `restart` 期待第一帧从循环起点计时（实际第一帧会包含建点后的空闲期）；
4. **`Nano_units` 是整型截断**：负时长（不应出现，见时钟选型）或亚纳秒尾数会被截断，若需浮点纳秒须自行用 `duration<double, std::nano>`；
5. **非线程安全**：任务表为普通 `unordered_map`，多线程并发 `task_build`/`elapsed` 会产生数据竞争；
6. **忘记 `task_unload` 导致表膨胀**：单次测量任务用后须卸载，否则长期运行的任务表会累积无主键项（虽然量级很小）；
7. **`Duration` 与 `std::chrono::nanoseconds` 的关系**：`elapsed` 返回 `engine::Duration`，直接把它传给期望 `nanoseconds` 的第三方 API 可能因类型不匹配报错——用 `Nano_units` 转换最稳妥。

## 五、模块运行链路

### 5.1 单次测量（建点-取差-卸载）时序

```
调用方                                Timer
────────────────────────────────────────────────────────────
 t0  task_build("mesh_load")
      └─ count("mesh_load")==0? 是
      └─ task_origin_set["mesh_load"] = Clock::now()  ◄── 起点T0
      └─ return true

 t1  Mesh_Loader::load_obj(...)        ← 被测业务代码段（耗时窗 [T0, T1]）

 t2  d = elapsed("mesh_load")
      └─ find 命中
      └─ return Clock::now() - T0      ◄── 时长 [T0, T1]
      └─ 调用方: Timer::Milli_units(d) → 毫秒数值 → 记录/打印

 t3  task_unload("mesh_load")
      └─ erase 成功 → return true
```

### 5.2 帧间步进（restart 复位）时序

```
帧循环                                 Timer
────────────────────────────────────────────────────────────
 帧1开始  task_build("frame")          → 起点 T1
 帧1结束  d1 = elapsed("frame", true)
            └─ 缓存旧起点 T1
            └─ 起点复位为 T2（当前）
            └─ return T2 - T1          → 帧1耗时
 帧2结束  d2 = elapsed("frame", true)
            └─ 缓存旧起点 T2
            └─ 起点复位为 T3
            └─ return T3 - T2          → 帧2耗时
   ...
 帧N结束  dN = elapsed("frame", true)  → 帧N耗时
```

要点：帧间步进模式下 `task_build` 只需调用**一次**（首帧前），此后全靠 `elapsed(task, true)` 的「取差+复位」推进；每帧耗时互不重叠、连续覆盖。

### 5.3 多任务并行计时

`task_origin_set` 支持任意多个命名任务并存：

```
task_build("physics")    task_build("render")     task_build("events")
      │                        │                        │
  物理步进                   渲染提交                 事件分发
      │                        │                        │
elapsed("physics")      elapsed("render")         elapsed("events")
      │                        │                        │
 卸载 / 保留             卸载 / 保留              卸载 / 保留
```

各任务起点相互独立，可在同一线程内交错打点/取差（只要不跨线程），互不干扰。

### 5.4 依赖方向汇总

```
调用方模块（待接入，如物理/渲染/资源加载）
        │  使用 Timer 的五个公开接口 + 三个别名
        ▼
      Timer
        ├── 内部：task_origin_set（unordered_map<string, TimePoint>）
        ├── 依赖：std::chrono::steady_clock（Clock/TimePoint/Duration 别名）
        └── 依赖：common/前置头文件包含.h（标准库头）
```

结论：`Timer` 是**完全独立的叶子工具模块**——不依赖引擎内任何其他模块，仅依赖 C++ 标准库；被其他模块引用时零耦合。重开发时只需保证：① 时钟用 `steady_clock`；② 任务表键唯一；③ `elapsed` 三分支语义与 `restart` 的「旧窗返回」行为不变，即可保持接口兼容。

## 六、附录：使用模式速查与标准库对照

### 6.1 三种典型使用模式（可直接照抄的代码形态）

#### 模式 A：一次性测量（建点 → 业务 → 取差 → 卸载）

```cpp
#include "src/tools/Timer/计时器.h"

using engine::Timer;

// 某次加载流程中
if (!Timer::task_build("mesh_load")) { /* 任务名冲突：改用其他名称 */ }
Mesh_Loader::load_obj(mesh_path, mesh_data);          // 被测业务
auto dt = Timer::elapsed("mesh_load");                // Duration
double ms = Timer::Milli_units(dt);                   // 毫秒
Log::info("网格加载耗时: {} ms", ms);
Timer::task_unload("mesh_load");                      // 清理任务表
```

要点：`task_build` 建点、`elapsed` 取差、`task_unload` 清理，三者缺一不可——漏掉 `task_unload` 会让任务表残留无主项；漏掉 `task_build` 会让 `elapsed` 静默返回零。

#### 模式 B：帧间步进（差分耗时，restart 语义）

```cpp
// 主循环外：一次性建点
Timer::task_build("frame");

// 主循环每帧末尾
auto frame_time = Timer::elapsed("frame", true);      // 本帧耗时 + 复位
double fps_like  = 1.0 / Timer::units(frame_time);    // 由耗时反推频率
```

要点：`task_build` 只调一次；每帧 `elapsed(task, true)` 既取本帧窗长又推进起点。若首帧前忘记 `task_build`，第一帧 `elapsed` 返回零且不产生任何副作用（起点未建，后续帧全部为零——排查时先确认建点）。

#### 模式 C：多任务并存对比（同帧内分项计时）

```cpp
Timer::task_build("physics");
physics_step();                                  // 物理步进
auto t_phys = Timer::elapsed("physics", true);

Timer::task_build("render");
render_submit();                                 // 渲染提交
auto t_rend = Timer::elapsed("render", true);

Log::info("物理 {} ms | 渲染 {} ms",
    Timer::Milli_units(t_phys), Timer::Milli_units(t_rend));
```

要点：各任务键独立，同帧内可多次建点/取差互不干扰；`restart=true` 让下一帧各任务从本帧末尾重新起算。

### 6.2 与裸 `std::chrono` 的逐行对照

| 裸 `std::chrono` 写法 | `Timer` 等价写法 | 差异说明 |
| --- | --- | --- |
| `auto t0 = std::chrono::steady_clock::now();` | `Timer::task_build("t");` | 起点入任务表，可命名、可多任务并存 |
| `auto dt = std::chrono::steady_clock::now() - t0;` | `Timer::elapsed("t");` | 免维护局部 `time_point` 变量 |
| `std::chrono::duration_cast<std::chrono::milliseconds>(dt).count()` | `Timer::Milli_units(dt);` | 免写 `duration_cast` 模板；返回值更统一 |
| `std::chrono::duration<double>(dt).count()` | `Timer::units(dt);` | 秒级浮点 |
| ——（需自写 `t0 = now()` 并重算差值） | `Timer::elapsed("t", true);` | `restart` 一次调用完成「取差+复位」 |
| `std::chrono::nanoseconds(dt).count()` | `Timer::Nano_units(dt);` | 整型纳秒 |

### 6.3 单位换算数值速查

假设某 `Duration` 表示 **1.5 秒**（`steady_clock` 纳秒计数 1'500'000'000）：

| 调用 | 返回值 |
| --- | --- |
| `Timer::units(d)` | `1.5`（秒，double） |
| `Timer::Milli_units(d)` | `1500.0`（毫秒，double） |
| `Timer::Micro_units(d)` | `1500000.0`（微秒，double） |
| `Timer::Nano_units(d)` | `1500000000`（纳秒，long long 整型） |

注意 `Nano_units` 是整型截断：若时长为 1.0000004 秒（1'000'000'400 ns），返回 `1000000400`（纳秒量级无精度损失）；若换算中出现亚纳秒尾数（本平台不可能，`Duration` 本身就是纳秒粒度）则向下截断。

### 6.4 扩展建议（重开发时的可选增强方向）

以下内容为**超出当前源码范围**的改进思路，供重开发时权衡，并非本版次已实现的功能：

1. **统计聚合**：在 `elapsed` 基础上增加「均值/最大/最小/计数」累积器，形成 `Timer` 的统计版，服务于帧率监控面板；
2. **自动日志**：增加「任务超时告警」——`elapsed` 超过阈值时自动 `Log::warn`，辅助定位慢路径；
3. **嵌套计时**：支持任务 A 内嵌任务 B 的父子层级关系，便于「总耗时 vs 分项耗时」对账（当前任务表是扁平结构）；
4. **线程安全**：`task_origin_set` 加锁或换 `std::shared_mutex`，支持多线程并发打点（当前单线程模型下无此需求）；
5. **句柄化接口**：以返回的任务句柄（`uint64_t`/`size_t`）替代字符串键，消除字符串哈希开销（当前任务量小，字符串键可读性优先）；
6. **跨帧持久化**：把测量结果导出为 CSV/JSON，供外部分析工具消费（当前模块无任何输出能力，输出全凭调用方）。

上述方向均不改变既有公开接口约定，可作为增量功能叠加，不影响本文档所述的现有调用方兼容性。

### 6.5 本模块在引擎工具集中的定位总结

`Timer` 处于引擎工具模块金字塔的**最底层叶子位置**：

```
          （上层业务 / 核心模块）
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   资源加载      物理/渲染     事件系统
   (Mesh_Loader)(预留)      (Event_Terminal)
        └───────┬───────────────┘
                ▼
           Timer（tools/Timer）       ← 本模块
                ▼
      std::chrono::steady_clock（标准库）
```

- 它是「计时/性能」领域的唯一标准化出口——引擎内所有耗时测量都应统一走 `Timer`，避免各处手写 `steady_clock::now()` 造成风格分裂与换算错误；
- 它与 `Random_Generator`、`Number_Allocator`、`Auxi_Algorithm` 等并列，属于「无业务语义、可跨模块复用、仅依赖标准库」的基础工具层；
- 当前引擎源码尚无实际消费者（属预留能力），首次接入时建议以「模式 A：一次性测量」起步，验证接口约定后再推广到帧循环等高频路径。
