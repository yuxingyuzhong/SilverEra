## 二、模块功能介绍

### 2.1 模块定位

「内存与资源」模块位于渲染层源码目录 `Application/Renderer/src/render/Memory/`，与设备模块（`render/Device/`）、平台模块（`render/Platform/`）、交换链模块（`render/Swapchain/`）、帧模块（`render/Frame/`）并列为渲染层的底层基础模块之一。它把 Vulkan 中「显存分配器建立 → 缓冲创建 / 销毁 → 图像与图像视图创建 / 销毁 → CPU 到 GPU 的一次性同步上传」这一整段「与显存管理、GPU 资源生命周期」相关的工作，全部收拢进一个门面类 `engine::Memory_Context`，对外只暴露「构建 → 使用 → 销毁」三段式接口外加一小组资源工厂函数与两个 getter。

模块内部把职责拆成五个编译单元，全部放在 `core/` 下：

- `core/VMA实现.cpp`：VMA 的**唯一实现展开单元**（`#define VMA_IMPLEMENTATION`），是全项目唯一允许展开 VMA 函数体的地方；
- `core/分配器创建.cpp`：`Memory_Context` 的析构、`build`、`destroy`、`valid` 与两个 getter 的落地，以及私有 `build_allocator`（把 VMA 分配器与实例 / 物理设备 / 逻辑设备绑定）；
- `core/缓冲创建.cpp`：缓冲的创建、销毁、主机可见缓冲的写入与读回；
- `core/图像创建.cpp`：图像的创建与销毁、图像视图的创建与销毁；
- `core/上传批次.cpp`：**一次性同步上传批次**（upload batch）——复用 `Memory_Context` 持有的上传命令池与完成栅栏：重置命令池 → 分配命令缓冲 → 录制 → 重置栅栏 → 提交 → 等待完成，内含上传到缓冲与上传像素到图像两条路径，以及私有 `upload_resources_ensure`（首次上传时建立命令池与栅栏）。

一句话概括：**本模块是渲染层「拿到可用的显存分配器、可用的 GPU 缓冲与图像，并把 CPU 端数据可靠送进 GPU」的唯一入口，是交换链、网格、纹理等一切需要 GPU 资源的模块的前置依赖。**

### 2.2 职责边界与解决的问题

`Memory_Context` 解决的问题可归纳为六点：

1. **把 VMA 分配器的创建细节封装为一次 `build` 调用**。Vulkan 原生分配显存需要遍历 `VkPhysicalDeviceMemoryProperties`、挑选内存类型、显式 `vkAllocateMemory` 并管理 `VkDeviceMemory` 的生命周期。本模块改用 VMA（Vulkan Memory Allocator）托管显存，把「内存类型挑选、子分配、映射、刷写」全部下沉给 VMA，只在外层暴露 `buffer_create` / `image_create` 这样的「资源即分配」语义。调用方拿到的是一对句柄 `(VkBuffer, VmaAllocation)` 或 `(VkImage, VmaAllocation)`，无需了解内存类型。

2. **把「资源创建」与「资源销毁」绑定在同一模块内**。句柄由调用方持有（谁创建谁保存），但**销毁动作一律回到本模块**（`buffer_destroy` / `image_destroy` / `image_view_destroy`）。这样 VMA 分配器的使用口径只有一份，调用方不可能绕开 VMA 去手写 `vkDestroyBuffer`，也就不会出现「用 VMA 创建、用原生销毁」这类错配。

3. **用 `host_visible` 与 `sequential_write` 两个布尔量屏蔽主机可见性的全部差异**。Vulkan 中「主机可见」的内存类型挑选、映射、刷写 / 无效化是易错且冗长的样板代码；本模块把它收敛为 `buffer_create(..., bool host_visible, bool sequential_write = false)` 的两个开关：`host_visible` 为真即「主机可见并保持持久映射」，调用方可直接 `buffer_write` / `buffer_read`；此时再以 `sequential_write` 区分「仅顺序写入」（上传暂存，选更优内存类型）与「主机随机读写」（读写取回同一指针）。`host_visible` 为假即「设备本地、专用内存」，只能经 `upload_buffer` 写入。

4. **提供不依赖帧模块的一次性同步上传**。本模块自带一条「命令池 + 一次性命令缓冲 + 完成栅栏」的同步上传路径：命令池与完成栅栏由 `Memory_Context` 在**首次上传时创建并跨多次上传复用**（每次仅 `vkResetCommandPool` 重置命令池 → 录制 → `vkResetFences` 复位栅栏 → 提交 → `vkWaitForFences` 等待），不再逐次创建 / 销毁命令池与栅栏，也不依赖帧循环；`upload_buffer` 与 `upload_image` 在调用返回时**保证数据已拷贝完成**，调用方无需处理同步。这条路径刻意不依赖帧模块，使资源上传可以在任何时刻独立发生。

5. **把图像上传的布局（layout）转换全流程内置**。`upload_image` 内部完成「`UNDEFINED → TRANSFER_DST_OPTIMAL`（布局转换）→ 拷贝（`vkCmdCopyBufferToImage`）→ `TRANSFER_DST_OPTIMAL → SHADER_READ_ONLY_OPTIMAL`（布局转换）」三步，并设置正确的管线阶段与访问掩码，把图像留在「着色器可读」的默认终态。调用方拿到图像后可直接作为采样纹理使用，无需自行处理布局。**本版次新增 `image_generate_mips`（mip 链生成）**：对第 1..n-1 级逐级 `vkCmdBlitImage`（线性过滤）降采样，每级走「源级 着色器可读→传输源 ＋ 目标级 未定义→传输目标 → blit → 目标级 传输目标→着色器可读」，循环末以**一条覆盖 `0 .. mip_levels-2` 级**的屏障，把这些曾作 blit 源的级一并由传输源恢复为着色器可读（**本轮修正**：原实现只恢复第 0 级，致 `1 .. mip_levels-2` 级遗留 `TRANSFER_SRC` 布局，采样时触发布局校验错误）；全部命令**一次提交**（复用既有上传命令池与栅栏）。同时 `image_create` 增 `mip_levels` 形参（默认 1）、`image_view_create` 增 `level_count` 形参（默认 1）。

6. **为图像视图的创建与销毁提供同源入口**。图像（`VkImage`）与其视图（`VkImageView`）的生命周期主要由本模块承担，`image_view_create` / `image_view_destroy` 与图像创建 / 销毁成对出现，避免视图生命周期散落在上层。

### 2.3 在整体架构中的位置

内存与资源模块处于渲染层依赖链的底层：它**不依赖**任何渲染层同级资源模块（交换链、帧、着色器、管线、网格、纹理、场景都不依赖），只依赖设备模块给出的设备侧句柄，以及引擎核心层的日志系统与渲染层共用的 `VkResult` 检查头。

```
                ┌───────────────────────────────────────────────┐
                │              Renderer（渲染器门面）             │
                │   持有 Memory_Context 成员，按依赖顺序编排      │
                └───────────────┬───────────────────────────────┘
                                │ memory.build(instance, phys, device, family, queue)
                                ▼
        ┌───────────────────────────────────────────────────────────────┐
        │                    Memory_Context（内存上下文）                │
        │  VmaAllocator / VkDevice / VkPhysicalDevice / VkInstance      │
        │  图形族索引 / 图形队列 / 上传命令池 / 上传栅栏                 │
        └───┬───────────┬──────────────┬───────────────┬───────────────┘
     依赖│        依赖│          依赖  │          提供   │
            ▼           ▼              ▼               ▼
   ┌────────────┐ ┌──────────┐ ┌────────────┐ ┌──────────────────────────┐
   │ 设备模块    │ │ 日志系统 │ │ 结果检查.h │ │ VMA（就地编入 VMA实现）  │
   │ Device_    │ │ logger   │ │ vk_result_ │ │ vmaCreateAllocator /     │
   │ Context    │ │ 全局实例 │ │ check      │ │ vmaCreateBuffer / ...    │
   └────────────┘ └──────────┘ └────────────┘ └──────────────────────────┘
                                │
                                ▼ 提供 buffer/image/upload/allocator 能力
        交换链 / 网格 / 纹理 / 管线 / 帧 / 门面 等模块
```

- **向上**：调用方是渲染器门面（`render/Renderer/`）。门面在自身实现中**以成员方式持有** `Memory_Context`（`render/Renderer/core/渲染器实现.h` 中声明 `Memory_Context memory;`），在设备模块就绪后调用 `memory.build(...)`，并把 `memory` 以引用方式交给网格、纹理、交换链等模块使用。
- **向下**：依赖设备模块（提供 `VkInstance`、`VkPhysicalDevice`、`VkDevice`、图形队列族索引与图形队列）、引擎核心层日志系统（`engine::logger`）、渲染层共用的 `vk_result_check`（归属 `render/Renderer/core/结果检查.h`）、Vulkan Loader（`vk*` 全部调用）、VMA（`vma*` 全部调用）。
- **横向**：本模块不依赖任何同级资源模块；反之网格、纹理、交换链等模块都直接依赖本模块提供的缓冲 / 图像 / 上传能力。

### 2.4 与相邻模块的职责分界

| 相邻模块 | 分界 |
| --- | --- |
| 设备模块（`render/Device/`） | 设备模块负责创建 `VkInstance` / `VkPhysicalDevice` / `VkDevice` / 图形队列并保存族索引；本模块**不**创建设备侧对象，只在 `build` 时**接收**这五项句柄，转交给 VMA 并保存供上传使用。`build` 的五个入参即设备模块 getter 的直出值（`instance_get` / `physical_device_get` / `device_get` / `graphics_family_get` / `graphics_queue_get`）。 |
| 渲染器门面（`render/Renderer/`） | 门面负责**拥有** `Memory_Context` 实例、编排 `build → 使用 → destroy` 的顺序，并在销毁时**先**让所有句柄持有者销毁各自资源、**再**调用 `memory.destroy()`。本模块自身只保证「`destroy` 幂等、析构兜底、失败不留半初始化」。 |
| 网格模块（`render/Mesh/`） | 网格模块以 `build(Memory_Context& memory)` 接收本模块的**引用**（非拥有），借 `buffer_create` / `upload_buffer` 建立顶点 / 索引缓冲，并把 `Memory_Context*` 指针记为成员以便后续销毁。缓冲句柄由网格模块持有，销毁时回调本模块。 |
| 纹理模块（`render/Texture/`） | 纹理模块同样以引用的方式接收本模块，借 `image_create` / `image_view_create` / `upload_image` 建立纹理与其视图；图像与视图的销毁回调本模块。 |
| 交换链模块（`render/Swapchain/`） | 交换链模块使用本模块的 `allocator_get()` / `device_get()` 以创建自有资源（交换链相关图像由交换链模块自行经 Vulkan 创建，**不**经本模块的 `image_create`，因为其图像由交换链本身拥有），并复用 `vk_result_check` 口径。 |
| 日志系统（`Engine/EngineCore/src/tools/Logging/`） | 本模块只把 `logger` 当作输出通道使用（`logger.info` / `logger.error`），不配置日志规则、不绑定输出流。 |
| 「渲染层-渲染器」模块的 `结果检查.h` | 本模块的全部 `VkResult` 检查都调用该头提供的 `vk_result_check`，不另写检查逻辑。 |
| 帧模块（`render/Frame/`） | 帧模块**经本模块的 `image_view_destroy` / `image_destroy` 归还其延迟销毁的旧交换链深度图像与视图**（延迟销毁的一部分，见帧模块文档 §6.7；本模块为被调用方、不感知帧模块），其像素回读缓冲亦经本模块 `buffer_create` / `buffer_destroy` / `buffer_read`。本模块自身**不依赖**帧模块：一次性上传复用自身持有的上传命令池与完成栅栏（不逐次创建 / 销毁，也不使用帧槽）；`上传批次.cpp` 与 `内存上下文.h` 注释均说明「复用本类持有的上传命令池与完成栅栏（首次上传时创建，之后每次仅重置命令池 → 录制 → 提交 → 等待），不逐次创建 / 销毁命令池，也不依赖帧模块」。即未来可能把一次性上传改走帧槽命令池，但当前源码仍为自持命令池复用。 |

### 2.5 生命周期与所有权总览

`Memory_Context` 的完整生命周期为：

```
构造（default，不创建任何对象）
   → build(instance, physical_device, device, graphics_family, graphics_queue)
        └─ 记录设备侧句柄 → build_allocator（vmaCreateAllocator）
   → [被下游模块使用：buffer_create / image_create（增 mip_levels） / image_view_create（增 level_count） /
                        buffer_write / buffer_read / upload_buffer / upload_image / image_generate_mips（本版次新增）]
        └─ 首次 upload_* 时经 upload_resources_ensure 建立上传命令池与栅栏（之后复用）
   → destroy()（幂等；先销毁上传命令池与完成栅栏，再 vmaDestroyAllocator，最后清空记录的全部句柄）
   → 析构（兜底再调用一次 destroy，保证分配器不泄漏）
```

所有权约定（关键约定，务必按此理解）：

1. **分配器归 `Memory_Context` 所有**：`VmaAllocator` 由 `build_allocator` 创建，由 `destroy` 通过 `vmaDestroyAllocator` 销毁。
2. **缓冲 / 图像 / 图像视图的句柄归调用方所有，但销毁动作归本模块**：`buffer_create` / `image_create` / `image_view_create` 以出参形式把句柄交给调用方保存；销毁时由调用方把句柄传回 `buffer_destroy` / `image_destroy` / `image_view_destroy`。
3. **销毁分配器不连带销毁其下资源**：`vmaDestroyAllocator` 只释放分配器自身，缓冲 / 图像 / 视图必须由调用方**先行**销毁，否则会泄漏（VMA 会在销毁分配器时报告仍有存活分配）。此约定在 `内存上下文.h` 与 `destroy` 实现中均有明文注释。
4. **上传产生的暂存缓冲由本模块自建自销**：`upload_buffer` / `upload_image` 内部创建的暂存缓冲（staging buffer）无论上传成败，都在函数返回前由本模块销毁，不泄漏给调用方。
5. **上传命令池与完成栅栏归 `Memory_Context` 所有**：二者由 `upload_resources_ensure` 在首次上传时创建，跨多次上传复用（命令池每次经 `vkResetCommandPool` 重置），由 `destroy` 在销毁分配器之前归还；不转移给调用方。

## 三、模块公开接口介绍

本章列出内存与资源模块**对外可见的类型与成员**。需要区分两层可见性：

- **对外层**（渲染层其它模块可见）：仅 `engine::Memory_Context` 类，声明于 `Application/Renderer/src/render/Memory/内存上下文.h`。该头虽然暴露了 `VkBuffer` / `VmaAllocation` / `VkImage` 等 Vulkan 与 VMA 类型，但该头属渲染层「实现细节」，不进渲染层公共头；层外看不到这些第三方类型（依据头文件注释「本头属本层实现细节：只被本层 .cpp 与层内模块头包含，不进公共头，故可以合法暴露这两者的类型 —— 层外仍看不到 —— 见 cmake/对外接口.cmake 的私有包含根」）。该「私有包含根」约定落实在构建脚本而非源码：`Application/Renderer/cmake/对外接口.cmake` 承接「对外面」（`BYJY_RENDERER_OUT_INC` 只含 EngineCore 头快照根与项目根），SDL3 / Vulkan / VMA 的包含根全部由 `Application/Renderer/CMakeLists.txt` 的 `target_include_directories(RendererCore PRIVATE ...)` 段声明，PRIVATE 不进导入目标的接口，故层外拿到本层头快照后仍看不到这些类型（该 .cmake 本轮已补「私有包含根」一节，使头注释的指向成立；本条同 R-DEV-02）。
- **模块内部层**（仅本模块编译单元 / 本类内部可见）：私有成员函数 `build_allocator`、`upload_resources_ensure`，以及 `core/上传批次.cpp` 匿名命名空间中的模板函数 `upload_submit_once`——均归**第四节**；类的数据成员（含上传命令池与栅栏）归**第五节**。它们不被渲染层其它模块使用，属模块内部分解；为便于「凭本文直接理解与复现」，仍逐条列出其签名（见第四节）。

### 3.2 构造 / 析构 / 拷贝禁用

**`Memory_Context(void) = default`**（`内存上下文.h`）

- 参数：无。
- 返回：无。
- 行为：默认构造，**不创建任何 Vulkan / VMA 对象**，全部成员保持初值（句柄为 `VK_NULL_HANDLE`、族索引为 `0`）。
- 约束：构造后处于「未构建」态，`valid()` 返回假，任何资源工厂调用会因前置校验失败而返回假（`buffer_create` / `image_create` 打印「内存上下文尚未构建」错误）。

**`~Memory_Context(void)`**（`core/分配器创建.cpp`）

- 参数：无。
- 返回：无。
- 行为：内部调用 `destroy()`，保证分配器（以及上传命令池与栅栏）不泄漏。
- 约束：无异常抛出（项目禁用异常）。若调用方已显式 `destroy()`，析构内的 `destroy()` 为幂等无操作。

**`Memory_Context(const Memory_Context&) = delete` / `Memory_Context& operator=(const Memory_Context&) = delete`**

- 行为：显式删除拷贝构造与拷贝赋值。
- 设计意图：类持有 `VmaAllocator` 与 `VkDevice` 句柄，拷贝会造成「两个对象指向同一分配器」的双重释放与句柄来源混淆。头注释「不可拷贝、不可移动（持有 VMA 分配器与设备句柄）」亦如此说明。
- 约束：移动构造 / 移动赋值**未显式声明**；因拷贝构造被删除、析构被用户声明，编译器**不**隐式生成移动操作，因此该类在实践中亦不可移动。

### 3.3 `build`

**签名**：`bool build(VkInstance instance, VkPhysicalDevice physical_device, VkDevice device, uint32_t graphics_family, VkQueue graphics_queue)`
**位置**：声明 `内存上下文.h`；实现 `core/分配器创建.cpp`

- **参数**：
  - `instance`（`VkInstance`）：Vulkan 实例句柄。VMA 分配器必需入参。
  - `physical_device`（`VkPhysicalDevice`）：物理设备句柄。VMA 用于查询内存类型与堆属性。
  - `device`（`VkDevice`）：逻辑设备句柄。VMA 分配器必需入参，同时被保存供视图创建 / 销毁与命令提交使用。
  - `graphics_family`（`uint32_t`）：图形队列族索引。一次性上传的命令池据此创建。
  - `graphics_queue`（`VkQueue`）：图形队列。一次性上传的提交目标。
- **返回**：成功为真；任一步失败为假。
- **行为**：
  1. 先把五项句柄 / 索引记录到 `this` 的对应成员（后续分配器创建与一次性上传都要用）；
  2. 调用私有 `build_allocator(instance, physical_device, device)` 创建 VMA 分配器；
  3. 若分配器创建失败，调用 `destroy()` **回退已记录的句柄**，使对象回到未构建态，返回假；
  4. 成功则打印 `logger.info("内存上下文:: 内存基础设施构建完成")`，返回真。
- **约束 / 异常行为**：
  - 五个入参**必须**来自同一设备模块的同一构建序列（`instance` / `physical_device` / `device` 三者互相匹配），否则 VMA 分配的显存无法绑到正确的逻辑设备；本模块不做交叉校验。
  - `graphics_family` 必须是该 `device` 上**确实存在**的队列族索引，且 `graphics_queue` 应取自该族；否则一次性上传的 `vkCreateCommandPool` / `vkQueueSubmit` 会失败。本模块不做族有效性校验。
  - 无异常抛出，全部失败以返回假 + 日志表达。
  - 本函数**不**创建上传命令池与栅栏（它们延迟到首次上传时由 `upload_resources_ensure` 建立，见 §4.2）。

### 3.4 `destroy`

**签名**：`void destroy(void)`
**位置**：声明 `内存上下文.h`；实现 `core/分配器创建.cpp`

- **参数**：无。
- **返回**：无。
- **行为**（幂等）：
  1. 若 `device != VK_NULL_HANDLE`，先归还上传侧资源（二者不依赖 VMA 分配器）：`upload_fence` 非空则 `vkDestroyFence(device, upload_fence, nullptr)`；`upload_pool` 非空则 `vkDestroyCommandPool(device, upload_pool, nullptr)`（连带回收其分配的命令缓冲）；随后把 `upload_fence`、`upload_pool` 均置 `VK_NULL_HANDLE`。
  2. 若 `allocator != VK_NULL_HANDLE`，调用 `vmaDestroyAllocator(allocator)` 并置空 `allocator`；
  3. 清空设备侧句柄：`graphics_queue = VK_NULL_HANDLE`、`graphics_family = 0`、`device = VK_NULL_HANDLE`、`physical_device = VK_NULL_HANDLE`、`instance = VK_NULL_HANDLE`。
- **约束 / 易错点**：
  - **销毁分配器不会连带销毁其下的缓冲 / 图像 / 视图**。调用方必须先行销毁这些句柄（`buffer_destroy` / `image_destroy` / `image_view_destroy`），否则 VMA 会在 `vmaDestroyAllocator` 时报告「仍有存活分配」。此约定在头注释与实现注释中均有明文。
  - **上传命令池与栅栏在销毁分配器之前归还**：二者由本类自持、不依赖分配器，故先于 `vmaDestroyAllocator` 销毁；销毁命令池的时机还隐含「须在无在途上传提交时调用」的外部同步契约（本模块不做保护）。
  - 可重复调用；第二次及以后 `allocator` 已为 `VK_NULL_HANDLE`、`upload_pool` / `upload_fence` 已空，跳过各销毁分支，为安全无操作。
  - 若 `destroy` 时仍有使用该分配器的缓冲句柄，其句柄值不会被本函数改写，会在销毁分配器后变成悬垂句柄；这是「先销毁资源、再销毁分配器」顺序被违反的后果，本模块不做防护。

### 3.5 `valid`

**签名**：`bool valid(void) const`
**位置**：声明 `内存上下文.h`；实现 `core/分配器创建.cpp`

- **参数**：无。
- **返回**：`allocator != VK_NULL_HANDLE && device != VK_NULL_HANDLE`。
- **行为**：只判定「VMA 分配器已建 且 逻辑设备已记录」这一最小条件。
- **约束**：`valid()` 为真是后续 `buffer_create` / `image_create` / `upload_buffer` / `upload_image` 等调用的前置条件。注意 `valid()` **不**校验 `graphics_queue` 非空；`upload_*` 在 `valid()` 之外**另行**检查 `graphics_queue != VK_NULL_HANDLE`。

### 3.6 `buffer_create`

**签名**：`bool buffer_create(VkBuffer& buffer_out, VmaAllocation& alloc_out, VkDeviceSize size, VkBufferUsageFlags usage, bool host_visible, bool sequential_write = false)`
**位置**：声明 `内存上下文.h`；实现 `core/缓冲创建.cpp`

- **参数**：
  - `buffer_out`（`VkBuffer&`，出参）：创建出的缓冲句柄。
  - `alloc_out`（`VmaAllocation&`，出参）：与缓冲绑定的 VMA 分配句柄。
  - `size`（`VkDeviceSize`）：缓冲字节数。
  - `usage`（`VkBufferUsageFlags`）：Vulkan 缓冲用途位（如 `VK_BUFFER_USAGE_VERTEX_BUFFER_BIT`、`VK_BUFFER_USAGE_TRANSFER_SRC_BIT` 等），原样透传。
  - `host_visible`（`bool`）：为真 = 主机可见 + 持久映射（可直接写入 / 读回，亦可作上传暂存）；为假 = 设备本地 + 申请专用内存（长命且体积大，不做子分配复用）。
  - `sequential_write`（`bool`，默认 `false`）：仅在 `host_visible` 为真时有意义；为真 = 该分配只做**顺序写入**（上传暂存），据此选用更优的内存类型；为假 = 主机**随机读写**（读写取回同一指针）。非上传暂存的调用方无需传此参。
- **返回**：成功为真；失败为假。
- **行为**：
  1. 前置校验 `valid()`；不通过则打印 `logger.error("缓冲创建:: 内存上下文尚未构建，无法创建缓冲")` 并返回假（**不改写出参**，出参保持调用方原值）。
  2. 填充 `VkBufferCreateInfo`：`sType`、`size`、`usage` 原样，`sharingMode = VK_SHARING_MODE_EXCLUSIVE`；**不设初始数据**（`pNext`/`flags` 默认）。
  3. 填充 `VmaAllocationCreateInfo`：`usage = VMA_MEMORY_USAGE_AUTO`；若 `host_visible` 为真，再按 `sequential_write` 分派——为真则 `flags = VMA_ALLOCATION_CREATE_HOST_ACCESS_SEQUENTIAL_WRITE_BIT | VMA_ALLOCATION_CREATE_MAPPED_BIT`（仅顺序写入优化，用于上传暂存），为假则 `flags = VMA_ALLOCATION_CREATE_HOST_ACCESS_RANDOM_BIT | VMA_ALLOCATION_CREATE_MAPPED_BIT`（主机随机读写，读写取回同一指针）；若 `host_visible` 为假则 `flags = VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT`。
  4. 调用 `vmaCreateBuffer(allocator, &buffer_info, &alloc_info, &buffer_out, &alloc_out, nullptr)`（第六参 `pAllocationInfo` 传 `nullptr`）。
  5. 失败（`vk_result_check` 为假）则把 `buffer_out`、`alloc_out` **显式置 `VK_NULL_HANDLE`** 并返回假；成功则打印 `logger.info("缓冲创建:: 缓冲已建立（{} 字节，{}）", size, host_visible ? "主机可见" : "设备本地")` 并返回真。
- **约束 / 易错点**：
  - `usage` 必须与后续用途一致：作上传目标需含 `VK_BUFFER_USAGE_TRANSFER_DST_BIT`；作上传源需含 `VK_BUFFER_USAGE_TRANSFER_SRC_BIT`。
  - 设备本地缓冲（`host_visible == false`）**不可**直接 `buffer_write`（无主机可见内存，映射会失败）；必须经 `upload_buffer` 写入。本模块不对此误用做防护，只在 `buffer_write` 的映射失败处报错。
  - `VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT` 表示「每资源独占一份内存，不做子分配复用」：适用于长命且体积大的缓冲；小缓冲若大量使用会造成内存碎片，应由调用方权衡（源码注释已直接写明该取舍「长命且体积大，不做子分配复用」，属有意为之的设计口径；源码不给量化阈值，适用规模由调用方权衡，故不单列答疑条目）。

### 3.7 `buffer_destroy`

**签名**：`void buffer_destroy(VkBuffer buffer, VmaAllocation alloc)`
**位置**：声明 `内存上下文.h`；实现 `core/缓冲创建.cpp`

- **参数**：`buffer`（`VkBuffer`）缓冲句柄；`alloc`（`VmaAllocation`）与之绑定的分配句柄。
- **返回**：无。
- **行为**（幂等）：若 `buffer == VK_NULL_HANDLE || alloc == VK_NULL_HANDLE || allocator == VK_NULL_HANDLE` 任一成立，直接返回（视为无需销毁）；否则调用 `vmaDestroyBuffer(allocator, buffer, alloc)` 一并归还缓冲与它的内存。
- **约束**：调用方须保证该缓冲**不再被 GPU 使用**（无在途命令缓冲引用），否则会产生使用后销毁（use-after-free）；本模块不做同步防护。**不**置空调用方的句柄（传值入参），调用方应自行把本地句柄置空以防重复销毁。

### 3.8 `buffer_write`

**签名**：`bool buffer_write(VkBuffer buffer, VmaAllocation alloc, const void* data, VkDeviceSize size, VkDeviceSize offset)`
**位置**：声明 `内存上下文.h`；实现 `core/缓冲创建.cpp`

- **参数**：`buffer` 目标缓冲句柄；`alloc` 其分配句柄；`data` 源数据指针；`size` 写入字节数；`offset` 在目标缓冲内的起始偏移。
- **返回**：成功为真；前置不满足或映射失败为假。
- **行为**：
  1. 前置校验：`buffer`、`alloc`、`allocator` 均非空且 `data != nullptr`；不满足则打印 `logger.error("缓冲创建:: 写入参数不完整，已跳过")` 返回假。
  2. `vmaMapMemory(allocator, alloc, &mapped)` 取得映射指针；失败则经 `vk_result_check` 报错并返回假（注意：**不**调用 `vmaUnmapMemory`）。
  3. `memcpy(static_cast<uint8_t*>(mapped) + offset, data, static_cast<size_t>(size))` 写入。
  4. `vmaFlushAllocation(allocator, alloc, offset, size)` 把写入内容刷向设备可见（非主机一致内存类型必需，主机一致时为无操作）。
  5. `vmaUnmapMemory(allocator, alloc)` 解除映射（注释：持久映射下不释放映射本体）。
  6. 返回真。
- **约束 / 易错点**：
  - **仅对主机可见的缓冲有意义**；对设备本地缓冲映射会失败。
  - `offset + size` 不得超过缓冲创建时的 `size`；本模块**不**做越界校验，越界会写坏内存。
  - 调用方须保证 `data` 在调用期间有效且至少有 `size` 字节。
  - 该函数**不检查** `valid()`，只检查句柄三件套；但 `allocator` 非空即隐含已构建（`destroy` 会置空 `allocator`），故实际等价。
  - 在带 `VMA_ALLOCATION_CREATE_MAPPED_BIT` 的持久映射分配上仍成对调用 `vmaMapMemory` / `vmaUnmapMemory`，语义成立且安全，属 VMA 明确支持的用法：`vmaMapMemory` 返回的正是 `pMappedData` 指向的同一指针，`vmaUnmapMemory` 在持久映射下不解除映射（映射生命周期由分配持有），故不会导致指针失效，`buffer_write` 全程拿到有效指针；显式成对调用还使非持久映射的分配也能走同一套代码。（R-MEM-02）
  - 主机可见分配的内存类型口径由 `host_visible` 与 `sequential_write` 两参决定：仅上传暂存（`sequential_write == true`）走「仅顺序写入」优化，其余主机可见分配走「主机随机读写」（读写取回同一指针）。属有意为之——原实现把主机可见分配统一走 `HOST_ACCESS_RANDOM` 属可改进项，本轮已改为按参分派。（R-MEM-01）

### 3.9 `buffer_read`

**签名**：`bool buffer_read(VkBuffer buffer, VmaAllocation alloc, void* data, VkDeviceSize size, VkDeviceSize offset)`
**位置**：声明 `内存上下文.h`；实现 `core/缓冲创建.cpp`

- **参数**：`buffer` 缓冲句柄；`alloc` 其分配句柄；`data` 接收缓冲指针；`size` 读回字节数；`offset` 起始偏移。
- **返回**：成功为真；前置不满足或映射失败为假。
- **行为**：
  1. 前置校验：`buffer`、`alloc`、`allocator` 均非空且 `data != nullptr`；不满足则打印 `logger.error("缓冲创建:: 读回参数不完整，已跳过")` 返回假。
  2. `vmaMapMemory`；失败报错返回假。
  3. `vmaInvalidateAllocation(allocator, alloc, offset, size)` 使设备侧写入对主机可见（非主机一致时必需，一致时无操作）。
  4. `memcpy(data, static_cast<const uint8_t*>(mapped) + offset, static_cast<size_t>(size))` 读回。
  5. `vmaUnmapMemory`；返回真。
- **约束**：用途为**校验与调试**（头注释「仅对主机可见的缓冲有意义；用于校验与调试」）。同样不做越界校验；读回的是该主机可见缓冲当前内容，若写入由 GPU 完成则需先确保 GPU 执行完毕并 `invalidate`。读回路径同样在持久映射上成对调用 `vmaMapMemory` / `vmaUnmapMemory`，指针全程有效（同 §3.8 的 R-MEM-02 说明）。

### 3.10 `image_create`

**签名**：`bool image_create(VkImage& image_out, VmaAllocation& alloc_out, uint32_t width, uint32_t height, VkFormat format, VkImageUsageFlags usage)`
**位置**：声明 `内存上下文.h`；实现 `core/图像创建.cpp`

- **参数**：`image_out`（出参）图像句柄；`alloc_out`（出参）分配句柄；`width` / `height` 像素尺寸；`format` 像素格式；`usage` 用途位。
- **返回**：成功为真；失败为假。
- **行为**：
  1. 前置校验 `valid()`；不通过打印 `logger.error("图像创建:: 内存上下文尚未构建，无法创建图像")` 返回假（不改写出参）。
  2. 填充 `VkImageCreateInfo`：`imageType = VK_IMAGE_TYPE_2D`、`format` 原样、`extent = { width, height, 1 }`、`mipLevels = 1`、`arrayLayers = 1`、`samples = VK_SAMPLE_COUNT_1_BIT`、`tiling = VK_IMAGE_TILING_OPTIMAL`、`usage` 原样、`sharingMode = VK_SHARING_MODE_EXCLUSIVE`、`initialLayout = VK_IMAGE_LAYOUT_UNDEFINED`。
  3. 填充 `VmaAllocationCreateInfo`：`usage = VMA_MEMORY_USAGE_AUTO`、`flags = VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT`（图像一律设备本地）。
  4. `vmaCreateImage(allocator, &image_info, &alloc_info, &image_out, &alloc_out, nullptr)`。
  5. 失败显式置空两出参返回假；成功打印 `logger.info("图像创建:: 图像已建立（{}x{}）", width, height)` 返回真。
- **约束 / 易错点**：
  - **布局固定 `VK_IMAGE_TILING_OPTIMAL`**；初始布局 `UNDEFINED`，表示内容未定义，使用前必须经布局转换。
  - **`usage` 须含 `VK_IMAGE_USAGE_TRANSFER_DST_BIT` 才能经 `upload_image` 写入像素**（头注释明文）。
  - 级数 / 层数 / 采样数均固定为 `1`：本模块**不支持** mipmap、数组层与多重采样图像。需要这些能力的模块须另建其它路径（当前本模块不提供）。
  - 图像为设备本地专用内存，**不可**主机映射读写；像素写入唯一入口是 `upload_image`。

### 3.11 `image_destroy`

**签名**：`void image_destroy(VkImage image, VmaAllocation alloc)`
**位置**：声明 `内存上下文.h`；实现 `core/图像创建.cpp`

- **参数**：`image` 图像句柄；`alloc` 其分配句柄。
- **返回**：无。
- **行为**（幂等）：任一为 `VK_NULL_HANDLE` 或 `allocator` 为空即返回；否则 `vmaDestroyImage(allocator, image, alloc)` 一并归还图像与内存。
- **约束**：调用方须**先**销毁该图像的全部视图（`image_view_destroy`）再 `image_destroy`；销毁图像不会自动销毁关联视图。且须保证无在途 GPU 使用。

### 3.12 `image_view_create`

**签名**：`bool image_view_create(VkImageView& view_out, VkImage image, VkFormat format, VkImageAspectFlags aspect)`
**位置**：声明 `内存上下文.h`；实现 `core/图像创建.cpp`

- **参数**：`view_out`（出参）视图句柄；`image` 目标图像；`format` 视图格式（通常与图像格式一致）；`aspect` 纵横比掩码（`VK_IMAGE_ASPECT_COLOR_BIT` / `VK_IMAGE_ASPECT_DEPTH_BIT` 等）。
- **返回**：成功为真；失败为假。
- **行为**：
  1. 前置校验：`image != VK_NULL_HANDLE && device != VK_NULL_HANDLE`；不满足打印 `logger.error("图像创建:: 创建图像视图的前置句柄不完整")` 返回假。
  2. 填充 `VkImageViewCreateInfo`：`image` 原样、`viewType = VK_IMAGE_VIEW_TYPE_2D`、`format` 原样、`subresourceRange.aspectMask = aspect`、`baseMipLevel = 0`、`levelCount = 1`、`baseArrayLayer = 0`、`layerCount = 1`。
  3. `vkCreateImageView(device, &view_info, nullptr, &view_out)`；失败经 `vk_result_check` 报错并置 `view_out = VK_NULL_HANDLE` 返回假；成功返回真（不打印 info）。
- **约束 / 易错点**：
  - 视图固定为**二维、单层、单 mip**，与本模块图像口径一致。
  - **`vkCreateImageView` 不经过 VMA**（走原生 Vulkan），因此视图句柄与 VMA 分配无关；但视图的销毁同样回到本模块。
  - `aspect` 必须与图像内容匹配：颜色纹理传 `VK_IMAGE_ASPECT_COLOR_BIT`；深度 / 模板图像须传相应位，否则校验层报错。

### 3.13 `image_view_destroy`

**签名**：`void image_view_destroy(VkImageView view)`
**位置**：声明 `内存上下文.h`；实现 `core/图像创建.cpp`

- **参数**：`view` 视图句柄。
- **返回**：无。
- **行为**（幂等）：若 `view == VK_NULL_HANDLE || device == VK_NULL_HANDLE` 直接返回；否则 `vkDestroyImageView(device, view, nullptr)`（注释：图像本身由 `image_destroy` 负责）。
- **约束**：须在对应 `image_destroy` 之前调用。

### 3.14 `upload_buffer`

**签名**：`bool upload_buffer(VkBuffer dst_buffer, const void* data, VkDeviceSize size, VkDeviceSize offset)`
**位置**：声明 `内存上下文.h`；实现 `core/上传批次.cpp`

- **参数**：`dst_buffer` 目标缓冲（应为设备本地，且 `usage` 含 `VK_BUFFER_USAGE_TRANSFER_DST_BIT`）；`data` 源数据；`size` 拷贝字节数；`offset` 在目标缓冲内的起始偏移。
- **返回**：成功为真；前置不满足或任一步失败为假。
- **行为**（**一次性同步上传**）：
  1. 前置校验：`valid()` 且 `dst_buffer != VK_NULL_HANDLE` 且 `data != nullptr` 且 `graphics_queue != VK_NULL_HANDLE`；不满足打印 `logger.error("上传批次:: 上传缓冲的参数不完整")` 返回假。
  2. `buffer_create(staging_buffer, staging_alloc, size, VK_BUFFER_USAGE_TRANSFER_SRC_BIT, true, true)` 建主机可见且**仅顺序写入**的暂存缓冲（`host_visible = true`、`sequential_write = true`）；失败返回假。
  3. `buffer_write(staging_buffer, staging_alloc, data, size, 0)` 写入暂存；失败则 `buffer_destroy` 暂存并返回假。
  4. `upload_resources_ensure()` 确保上传命令池与栅栏就绪（首次上传时创建，之后复用）；失败则 `buffer_destroy` 暂存并返回假。
  5. `upload_submit_once(device, upload_pool, upload_fence, graphics_queue, record)`，其中 `record` 录制一条 `vkCmdCopyBuffer(command_buffer, staging_buffer, dst_buffer, 1, &copy_region)`（`srcOffset = 0`、`dstOffset = offset`、`size = size`）。
  6. **无论成败**都 `buffer_destroy(staging_buffer, staging_alloc)` 回收暂存缓冲。
  7. 成功则 `logger.info("上传批次:: 缓冲上传完成（{} 字节）", size)`，返回 `ok`。
- **约束 / 易错点**：
  - `offset + size` 不得超出目标缓冲容量；不做校验。
  - **同步**：函数返回时数据已拷贝完成（内部提交后 `vkWaitForFences` 等待完成）。
  - 目标缓冲须为设备本地（`host_visible == false`）才有使用本函数的意义；对主机可见缓冲直接 `buffer_write` 即可。
  - 暂存缓冲使用 `VK_BUFFER_USAGE_TRANSFER_SRC_BIT`（`host_visible = true`、`sequential_write = true`，按仅顺序写入优化），勿复用为其它用途。
  - 命令池与栅栏**不**随本函数创建 / 销毁，而由 `Memory_Context` 自持并复用（见 §4.2、§4.3）。

### 3.15 `upload_image`

**签名**：`bool upload_image(VkImage dst_image, const void* data, VkDeviceSize data_size, uint32_t width, uint32_t height, uint32_t row_pixels)`
**位置**：声明 `内存上下文.h`；实现 `core/上传批次.cpp`

- **参数**：`dst_image` 目标图像（`usage` 须含 `VK_IMAGE_USAGE_TRANSFER_DST_BIT`）；`data` 源像素数据；`data_size` 源数据字节数（= 暂存缓冲大小）；`width` / `height` 图像像素尺寸；`row_pixels` 为一行的纹素数，**传 0 表示按 `width` 紧排**。
- **返回**：成功为真；前置不满足或任一步失败为假。
- **行为**：
  1. 前置校验：`valid()` 且 `dst_image != VK_NULL_HANDLE` 且 `data != nullptr` 且 `graphics_queue != VK_NULL_HANDLE`；不满足打印 `logger.error("上传批次:: 上传图像的参数不完整")` 返回假。
  2. `buffer_create(staging, alloc, data_size, VK_BUFFER_USAGE_TRANSFER_SRC_BIT, true, true)`（主机可见且仅顺序写入）；失败返回假。
  3. `buffer_write(staging, alloc, data, data_size, 0)`；失败则销毁暂存返回假。
  4. `upload_resources_ensure()` 确保上传命令池与栅栏就绪；失败则销毁暂存返回假。
  5. `upload_submit_once(device, upload_pool, upload_fence, graphics_queue, record)`，`record` 内录制**三步**：
     - 布局转换 `UNDEFINED → TRANSFER_DST_OPTIMAL`（`srcAccessMask = 0`、`dstAccessMask = VK_ACCESS_TRANSFER_WRITE_BIT`、阶段 `TOP_OF_PIPE → TRANSFER`、`subresourceRange = { COLOR, 0, 1, 0, 1 }`）；
     - `vkCmdCopyBufferToImage(command_buffer, staging, dst_image, VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL, 1, &copy_region)`，其中 `bufferOffset = 0`、`bufferRowLength = row_pixels`、`bufferImageHeight = 0`、`imageSubresource = { COLOR, 0, 0, 1 }`、`imageOffset = { 0, 0, 0 }`、`imageExtent = { width, height, 1 }`；
     - 布局转换 `TRANSFER_DST_OPTIMAL → SHADER_READ_ONLY_OPTIMAL`（`srcAccessMask = VK_ACCESS_TRANSFER_WRITE_BIT`、`dstAccessMask = VK_ACCESS_SHADER_READ_BIT`、阶段 `TRANSFER → FRAGMENT_SHADER`）。
  6. 无论成败销毁暂存；成功打印 `logger.info("上传批次:: 图像上传完成（{}x{}）", width, height)` 返回 `ok`。
- **约束 / 易错点**：
  - **终态布局固定为 `VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL`**（采样用途）；源码注释说明「若将来需要其他终态（如作为渲染目标或再次传输），在此扩参即可」。
  - `row_pixels` 非 0 时可用于「行间有填充」的数据；为 0 时按 `width` 紧排（Vulkan 语义：`bufferRowLength == 0` 表示按 `imageExtent.width` 紧排）。
  - `bufferImageHeight = 0` 固定，表示按 `imageExtent.height` 紧密排布。
  - 纵横比固定 `VK_IMAGE_ASPECT_COLOR_BIT`：本函数**只**支持颜色图像；深度 / 模板上传不适用。
  - `data_size` 必须足够容纳按 `row_pixels × height` 或 `width × height` 计的行像素与格式字节数；不做校验。
  - 与前两处一致：`offset` 语义不适用（始终从暂存缓冲偏移 0 写入、从图像原点拷贝）。
  - 命令池与栅栏**不**随本函数创建 / 销毁，而由 `Memory_Context` 自持并复用（见 §4.2、§4.3）。

### 3.16 `allocator_get`

**签名**：`VmaAllocator allocator_get(void) const`
**位置**：声明 `内存上下文.h`；实现 `core/分配器创建.cpp`

- **参数**：无。**返回**：内部 `VmaAllocator`（未构建时为 `VK_NULL_HANDLE`）。
- **约束**：头注释「供上层创建自有资源时复用」。调用方须保证在 `destroy` 之前使用；`destroy` 后返回 `VK_NULL_HANDLE`。返回原始句柄不转移所有权。

## 四、模块私有方法介绍

本章逐条列出**仅本模块内部可见**的实现函数（类内 private 成员函数，以及 `core/上传批次.cpp` 匿名命名空间中的模板）。数据成员见 §五.3。它们不对外暴露，属模块内部分解；列出签名与关键行为，便于凭本文直接理解与复现。

### 4.1 `build_allocator`（私有成员）

**签名**：`bool build_allocator(VkInstance instance, VkPhysicalDevice physical_device, VkDevice device)`
**位置**：声明 `内存上下文.h`（private）；实现 `core/分配器创建.cpp`

- **参数**：三项设备侧句柄（同 `build` 的前三参）。
- **返回**：成功为真；失败为假。
- **行为**：
  1. 声明 `VmaAllocatorCreateInfo create_info{}`，设置 `vulkanApiVersion = VK_API_VERSION_1_0`、`instance`、`physicalDevice`、`device`；**不设任何 VMA 特性开关**。
  2. `vmaCreateAllocator(&create_info, &allocator)`。
  3. 失败则 `vk_result_check(vkCreateAllocator, "分配器创建:: 创建 VMA 分配器")` 报错并把 `allocator` 置 `VK_NULL_HANDLE`，返回假；成功打印 `logger.info("分配器创建:: VMA 分配器已建立")` 返回真。
- **约束 / 说明**：
  - 注释明确「第一版不启用任何 VMA 特性开关：不做内存预算、不做环形上传缓冲、不做延迟分配」（即未设 `VMA_ALLOCATOR_CREATE_EXT_MEMORY_BUDGET_BIT` / `VMA_ALLOCATOR_CREATE_BUFFER_DEVICE_ADDRESS_BIT` 等）。
  - 按 Vulkan 1.0 口径，不启用 1.1+ 特性。
  - 未传 `pVulkanFunctions`（保持默认，由 VMA 静态入口点填充，见第六章 6.2）。

### 4.2 `upload_resources_ensure`（私有成员，本轮新增）

**签名**：`bool upload_resources_ensure(void)`
**位置**：声明 `内存上下文.h`（private）；实现 `core/上传批次.cpp`

- **参数**：无。
- **返回**：命令池与栅栏均已就绪为真；否则按创建结果返回真假。
- **行为**（幂等）：
  1. 若 `upload_pool != VK_NULL_HANDLE && upload_fence != VK_NULL_HANDLE` 成立，直接返回真（已就绪，复用）。
  2. 前置：若 `device == VK_NULL_HANDLE`，打印 `logger.error("上传批次:: 逻辑设备未就绪，无法创建上传资源")` 返回假。
  3. 建上传命令池：`flags = VK_COMMAND_POOL_CREATE_TRANSIENT_BIT`、`queueFamilyIndex = graphics_family`；失败则置 `upload_pool = VK_NULL_HANDLE` 返回假。
  4. 建上传完成栅栏（未触发态）；失败则 `vkDestroyCommandPool(device, upload_pool, nullptr)`、置空 `upload_pool` 与 `upload_fence` 返回假。
  5. 成功返回真。
- **约束 / 说明**：
  - **首次调用创建，之后复用**：命令池与栅栏由 `Memory_Context` 自持并跨多次上传复用，避免每资源一次的命令池与栅栏创建 / 销毁开销。
  - 命令池为 `TRANSIENT`（一次性用途）；其分配的命令缓冲随池经 `vkResetCommandPool` 回收与再分配（见 §4.3）。
  - 若两资源中只有一个非空（理论上只在创建中途失败时可能出现），本函数会重新走创建分支；但由于失败分支已把两者一并置空，实践中总是「全空 → 全建」或「全就绪 → 直接返回」。

### 4.3 `upload_submit_once`（匿名命名空间模板，模块内部）

**签名**：

```cpp
template <typename Record_Fn>
bool upload_submit_once(VkDevice device, VkCommandPool pool, VkFence fence,
    VkQueue graphics_queue, Record_Fn record)
```

**位置**：`core/上传批次.cpp` 匿名命名空间（仅该编译单元可见）。

- **参数**：`device` 逻辑设备；`pool` 由 `Memory_Context` 自持的上传命令池（复用）；`fence` 由其自持的上传完成栅栏（复用）；`graphics_queue` 提交目标；`record` 一个可调用体，在当前命令缓冲上录制全部拷贝与布局转换。
- **返回**：整条一次性提交链成功为真；任一步失败为假。
- **行为**（严格按顺序，任一步失败即返回假；**本函数既不创建也不销毁命令池与栅栏**）：
  1. `vkResetCommandPool(device, pool, 0)`（连带回收上次分配的命令缓冲，使其可再次分配）；失败返回假。
  2. 分配 1 个 `VK_COMMAND_BUFFER_LEVEL_PRIMARY` 命令缓冲；失败返回假。
  3. `vkBeginCommandBuffer`，`flags = VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT`；失败返回假。
  4. `record(command_buffer)` 录制。
  5. `vkEndCommandBuffer`；失败返回假。
  6. `vkResetFences(device, 1, &fence)` 复位完成栅栏；失败返回假。
  7. `vkQueueSubmit(graphics_queue, 1, &submit_info, fence)`（`commandBufferCount = 1`、`pCommandBuffers = &command_buffer`；**不设信号量**，因同步等待完成）。
  8. 提交成功则 `vkWaitForFences(device, 1, &fence, VK_TRUE, UINT64_MAX)` 无限等待完成。
  9. 返回提交链结果 `ok`。
- **约束 / 易错点**：
  - 命令池与栅栏**由调用方（`Memory_Context`）持有并跨上传复用**，本函数只重置与使用，不创建 / 销毁；组织者职责归 `upload_resources_ensure`（§4.2）与 `destroy`（§3.4）。
  - 命令池为 `TRANSIENT`；每次上传先 `vkResetCommandPool` 回收上次命令缓冲，再重新分配，避免命令缓冲累积。
  - 栅栏在上一次「等待完成」后已发出（signaled），故提交前须 `vkResetFences` 复位；首次使用时栅栏尚未发出，复位为无操作。
  - `vkWaitForFences` 用 `UINT64_MAX` 无限等待：若 GPU 挂死会在此阻塞，无超时保护。
  - `record` 为模板参数（lambda 捕获暂存缓冲与目标句柄），由 `upload_buffer` / `upload_image` 各自传入。

### 5.2 各编译单元职责

| --- | --- | --- |

四个实现单元均以相同两行开头（**实现文件跨目录包含用本层根相对路径**）：

```cpp
#include "src/render/Memory/局部命名空间使用.h"
#include "src/render/Renderer/core/结果检查.h"
```

并以 `namespace engine { ... }` 包裹实现体。`VMA实现.cpp` 例外：它不包含上述两行，只做 `#define VMA_IMPLEMENTATION` + `#include <vk_mem_alloc.h>`，**不**进入 `namespace engine`。

### 5.3 `Memory_Context` 内部数据字段说明

| 字段 | 类型 | 初值 | 说明 |
| --- | --- | --- | --- |
| `allocator` | `VmaAllocator` | `VK_NULL_HANDLE` | VMA 分配器句柄，`build_allocator` 建立、`destroy` 销毁；是 `valid()` 判据之一，也是所有资源工厂与上传路径的实际执行者。 |
| `device` | `VkDevice` | `VK_NULL_HANDLE` | 逻辑设备句柄。用途有四：传给 VMA 建分配器；`vkCreateImageView` / `vkDestroyImageView`；上传命令池 / 命令缓冲 / 栅栏的创建、重置与销毁；`destroy` 中归还上传侧资源的判据。是 `valid()` 判据之二。 |
| `physical_device` | `VkPhysicalDevice` | `VK_NULL_HANDLE` | 物理设备句柄。仅供 VMA 建分配器时查询内存类型与堆属性；建后本模块不再直接使用。 |
| `instance` | `VkInstance` | `VK_NULL_HANDLE` | 实例句柄。仅供 VMA 建分配器使用；建后本模块不再直接使用。 |
| `graphics_family` | `uint32_t` | `0` | 图形队列族索引。仅用于上传命令池的 `queueFamilyIndex`。 |
| `graphics_queue` | `VkQueue` | `VK_NULL_HANDLE` | 图形队列。仅用于一次性上传的 `vkQueueSubmit`。`upload_*` 在 `valid()` 之外另行检查其非空。 |
| `upload_pool` | `VkCommandPool` | `VK_NULL_HANDLE` | 一次性上传命令池（`TRANSIENT`）。由 `upload_resources_ensure` 首次上传时创建、跨多次上传经 `vkResetCommandPool` 复用，`destroy` 时销毁。 |
| `upload_fence` | `VkFence` | `VK_NULL_HANDLE` | 一次性上传完成栅栏。与 `upload_pool` 同生共死：首次上传时创建、每次上传前 `vkResetFences` 复位、`destroy` 时销毁。 |

设计要点：八个字段中，`instance` / `physical_device` **只在 `build_allocator` 期间被使用**，之后仅作为「已记录的句柄」保留（`destroy` 时清空）；`upload_pool` / `upload_fence` 由 `upload_resources_ensure` 首次建立、跨上传复用、`destroy` 时归还；真正贯穿整个使用期的只有 `allocator`、`device`、`graphics_family`、`graphics_queue` 以及上传侧两资源。

### 5.5 `局部命名空间使用.h` 的做法说明

`Application/Renderer/src/render/Memory/局部命名空间使用.h` 内容极简：

```cpp
#pragma once
#include "内存上下文.h"

// ---------- 基本类型别名 ----------
using std::string;
using std::vector;
```

- **做法**：按《agent开发指南》「编码约束 / 文件架构约束」，模块为 `.cpp` 提供一份内部头，用 `using` 声明引入实现中用到的类型，使 `.cpp` 内部代码**不加命名空间前缀**。本模块实际用到的类型很少，故只引入 `std::string` 与 `std::vector` 两个别名；`vk_mem_alloc.h` / `vulkan.h` 类型（`VkBuffer` / `VmaAllocation` 等）经 `内存上下文.h` 已可见，无需再次 `using`（它们是全局作用域的类型，本就不带 `std::` 前缀）。
- **为什么 `using std::string` / `using std::vector` 在本模块只见声明不见使用**：本模块的实现代码未直接书写这两个类型名（`string` / `vector` 由其它模块与本模块头注释中的签名描述间接涉及），别名保留属**统一模板做法**，为将来扩展留位，不产生任何运行时代价。
- **注意**：`局部命名空间使用.h` 以 `#include "内存上下文.h"` 引入对外头，从而让每个 `.cpp` 一并获得 `Memory_Context` 类声明、预编译头（经对外头内的 `前置头文件包含.h`）与 Vulkan / VMA 头。因此各 `.cpp` 只写两行 `#include` 即可开工。
- **不做的**：不引入 `using namespace engine;`（本模块是 `engine` 命名空间的定义方）；不 `using` VMA / Vulkan 的 C 类型（它们本就在全局作用域）；不在该头放任何函数声明。

### 5.6 VMA 就地编入与「实现单元」归属（含迁移说明）

- **VMA 的来源与形态**：VulkanMemoryAllocator 是「头文件即实现」形态——全部函数体写在 `Application/Renderer/external/VulkanMemoryAllocator/include/vk_mem_alloc.h` 内，由 `VMA_IMPLEMENTATION` 宏开启展开。该头版本为 `VMA_VERSION (VK_MAKE_VERSION(3, 4, 0))`（即 VMA 3.4.0）。项目**不使用** VMA 自带构建系统，以「就地编入」方式把实现展开进渲染层静态库 `RendererCore`（`CMakeLists.txt` 注释：「SDL3 / VMA 不使用其自带构建系统，直接编入本层静态库（无独立的 SDL3.lib / VMA.lib）」）。
- **唯一实现单元**：全项目必须有且只有一个编译单元定义 `VMA_IMPLEMENTATION`，否则会多重定义。此处即那唯一一处——`Application/Renderer/src/render/Memory/core/VMA实现.cpp`。
- **归属迁移（如实记录）**：该实现单元**曾位于 `Renderer/core` 路径下**，现已**迁移至 `Memory/core`**。当前源码中：
  - 文件物理位置为 `Application/Renderer/src/render/Memory/core/VMA实现.cpp`；
  - 文件头部注释自述位置亦为 `Application/Renderer/src/render/Memory/core/VMA实现.cpp`；
  - 构建清单 `Application/Renderer/源文件列表.cmake` 以 `"src/render/Memory/core/VMA实现.cpp"` 列出，已无 `Renderer/core` 下的旧引用；
  - 全渲染层对 `VMA实现.cpp` 的引用仅此一处（`源文件列表.cmake`）。
  即迁移已完成且无残留别名或重复单元。本文按「当前源码为准」记录：**VMA 的实现展开单元归属「内存与资源」模块，物理路径为 `src/render/Memory/core/VMA实现.cpp`**。
- **迁移的架构含义**：VMA 属显存管理，与 `Memory_Context` 同属「内存与资源」职责域；把实现单元从 `Renderer/core`（门面目录）迁到 `Memory/core`，使「显存分配器的实现展开」与「显存分配器的使用者」同处一个模块目录，避免了「门面目录里藏着一个与门面无关的第三方实现单元」这一职责错位。
- **头文件包含路径**：`VMA实现.cpp` 与 `内存上下文.h` 均以 `#include <vk_mem_alloc.h>` 形式引入，该尖括号路径由 `CMakeLists.txt` 的 `PRIVATE` 包含根 `${BYJY_VMA_DIR}/include` 提供（`BYJY_VMA_DIR = ${PROJECT_ROOT_DIR}/external/VulkanMemoryAllocator`）；VMA 所需的 `<vulkan/vulkan.h>` 由 Vulkan SDK 探测结果给出的私有包含根提供。二者均为本层**私有**包含根，不出现在对外面上。
- **换加载器的预留**：`VMA实现.cpp` 头部注释说明「将来换用 volk 之类的加载器时，`VMA_STATIC_VULKAN_FUNCTIONS` / `VMA_DYNAMIC_VULKAN_FUNCTIONS` 只需改这里」——即把「VMA 如何取得 Vulkan 函数入口」这一决策**单点收口**在该单元。

### 5.7 `upload_submit_once` 与 `upload_resources_ensure` 的位置与可见性

`upload_submit_once` 放在 `core/上传批次.cpp` 的**匿名命名空间**内，因此具有内部链接（仅该编译单元可见），不会与其它编译单元的同名模板冲突，也不会污染 `engine` 命名空间的对外符号。它被同文件的两条上传路径以 lambda 形式调用，把「重置命令池 → 命令缓冲 → 录制 → 重置栅栏 → 提交 → 等待」的通用一次性提交骨架与「录制什么」解耦：`upload_buffer` 只需录一条拷贝，`upload_image` 需录三步屏障 / 拷贝 / 屏障。

私有成员 `upload_resources_ensure` 定义在同一 `core/上传批次.cpp`（声明在 `内存上下文.h` 的 private 段），负责命令池与完成栅栏的「首次创建、之后复用」；把它放在上传单元而非 `分配器创建.cpp`，是因为它服务的正是上传路径，与 `upload_submit_once` 同域，便于「上传资源的建立与使用」集中一处。

## 六、模块设计/实现细节

### 6.1 分配器创建口径：Vulkan 版本与特性开关

`build_allocator` 只填四个字段：

```cpp
create_info.vulkanApiVersion = VK_API_VERSION_1_0;
create_info.instance = instance;
create_info.physicalDevice = physical_device;
create_info.device = device;
```

- **按 Vulkan 1.0 口径**：不启用 1.1+ 特性（如 `VK_KHR_buffer_device_address` / `VK_EXT_memory_budget` 对应的分配器开关）。这与项目「第一版最小口径」的整体取向一致（对照图像 `mipLevels / arrayLayers / samples` 均固定为 1）。
- **不启用任何 VMA 特性开关**（源码注释原文）：「第一版不启用任何 VMA 特性开关：不做内存预算、不做环形上传缓冲、不做延迟分配」。具体即未设 `VMA_ALLOCATOR_CREATE_EXT_MEMORY_BUDGET_BIT`、未设 `VMA_ALLOCATOR_CREATE_BUFFER_DEVICE_ADDRESS_BIT`、未设 `VMA_ALLOCATOR_CREATE_KHR_DEDICATED_ALLOCATION_BIT` 等。
- **未传 `pVulkanFunctions`**：见 §6.2。
- **失败回退**：`build_allocator` 失败时把 `allocator` 置 `VK_NULL_HANDLE`；`build` 再调用 `destroy()` 清空已记录的五项句柄，保证「失败不留半初始化」。这一点很重要：若 `build` 不 `destroy()`，对象会停留在「句柄已记录但无分配器」的中间态，`valid()` 虽因 `allocator` 为空而返回假，但 `graphics_queue` 等残留值会误导后续调用。

### 6.2 Vulkan 函数入口的静态 / 动态约定

`分配器创建.cpp` 注释称：「VMA 默认按 `VMA_STATIC_VULKAN_FUNCTIONS=1` 直接使用已静态链接的 vulkan-1 入口，故不需要（也不应）额外传入函数表。」

从 VMA 3.4.0 头文件看，该判断成立，机制如下：

- `vk_mem_alloc.h` 在未定义 `VMA_STATIC_VULKAN_FUNCTIONS` 且未定义 `VK_NO_PROTOTYPES` 时，**默认**把 `VMA_STATIC_VULKAN_FUNCTIONS` 定义为 `1`（头内 `#if !defined(VMA_STATIC_VULKAN_FUNCTIONS) && !defined(VK_NO_PROTOTYPES) #define VMA_STATIC_VULKAN_FUNCTIONS 1`）。
- 项目**未**在任何 CMake 或源码中覆盖该宏，也**未**定义 `VK_NO_PROTOTYPES`，故走静态分支：VMA 在 `ImportVulkanFunctions_Static`（`#if VMA_STATIC_VULKAN_FUNCTIONS == 1`）中直接用已链接的 Vulkan 入口点（如 `vkGetInstanceProcAddr`、`vkAllocateMemory` 等）填充内部函数表。
- 该静态分支同时填入了 `vkGetInstanceProcAddr` 与 `vkGetDeviceProcAddr`，因此即使 VMA 头默认也把 `VMA_DYNAMIC_VULKAN_FUNCTIONS` 定义为 `1`，其动态分支的前置断言（要求这两个函数指针非空）也已被静态分支满足，**无需**调用方在 `VmaAllocatorCreateInfo::pVulkanFunctions` 里额外提供函数表。
- 结论：本模块 `create_info` 留空 `pVulkanFunctions` 是正确且符合注释意图的。若将来改用 `volk` 之类加载器（不再静态链接 vulkan-1 入口，常需 `VK_NO_PROTOTYPES`），则应在此单元改宏口径并按需传函数表——这正是把该决策收口到 `VMA实现.cpp` 的用意。

### 6.3 缓冲分配策略

`buffer_create` 的分配口径由 `host_visible` 与 `sequential_write` 决定，对应三组 VMA 标志：

| `host_visible` | `sequential_write` | `VmaAllocationCreateInfo.flags` | 语义 | 典型用途 |
| --- | --- | --- | --- | --- |
| `true` | `true` | `VMA_ALLOCATION_CREATE_HOST_ACCESS_SEQUENTIAL_WRITE_BIT \| VMA_ALLOCATION_CREATE_MAPPED_BIT` | 主机**仅顺序写入**，且**保持映射**（VMA 在分配时即建立持久映射，`vmaMapMemory` 取回同一指针） | 一次性上传的暂存缓冲（只顺序写一次、随后即作传输源） |
| `true` | `false` | `VMA_ALLOCATION_CREATE_HOST_ACCESS_RANDOM_BIT \| VMA_ALLOCATION_CREATE_MAPPED_BIT` | 主机**可随机读写**，且**保持映射**（读写取回同一指针） | 需 CPU 频繁读写的缓冲、调试读回缓冲 |
| `false` | （不适用） | `VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT` | 设备本地，且**申请专用内存**（每资源独占一份内存，不做子分配复用） | 顶点 / 索引缓冲等长命且体积大的 GPU 资源 |

- 三者都以 `usage = VMA_MEMORY_USAGE_AUTO` 为前提。VMA 的 `AUTO` 口径要求：使用 `AUTO` 且需要主机访问时**必须**显式给出 `HOST_ACCESS_SEQUENTIAL_WRITE` 或 `HOST_ACCESS_RANDOM` 之一，否则 VMA 会断言失败。本模块按 `sequential_write` 分派：上传暂存走 `SEQUENTIAL_WRITE`（只有顺序写、VMA 据此给出利于顺序写的内存类型），其余主机可见分配走 `RANDOM`（同时满足读与写、读写取回同一指针）；两种分支都带 `MAPPED_BIT` 让分配成为持久映射，避免每次写都重新映射。
- **`DEDICATED_MEMORY` 取舍**：源码注释「长命且体积大，不做子分配复用」。这一口径偏向**简单与可预期**（每个资源一块独立内存，便于排查），代价是放弃子分配带来的碎片优化。适合起步阶段少量大资源；若将来出现大量小缓冲，应改为默认子分配并只在超大资源上用专用内存（源码注释已明示该取舍「长命且体积大，不做子分配复用」，属有意为之；源码不给量化阈值，适用规模由调用方权衡，故不单列答疑条目）。
- **`sharingMode` 固定 `EXCLUSIVE`**：本模块不支持跨队列族共享缓冲（如需共享须改）。（当前上传走图形队列，独占即可。）
- 主机可见分配按 `sequential_write` 分派内存类型：仅上传暂存（`sequential_write == true`）走 `HOST_ACCESS_SEQUENTIAL_WRITE_BIT`（顺序写优化），其余主机可见分配走 `HOST_ACCESS_RANDOM_BIT`（读写取回同一指针）。属有意为之：原实现统一走 `RANDOM` 会令 VMA 给出不利于顺序写的内存类型，对只做顺序写入的暂存缓冲而言性能与语义均不恰当，本轮已改为按参分派。（R-MEM-01）
- 持久映射分配上仍成对调用 `vmaMapMemory` / `vmaUnmapMemory`，语义成立且安全：`vmaMapMemory` 返回的正是 `pMappedData` 指向的同一指针，`vmaUnmapMemory` 在持久映射下不解除映射（映射生命周期由分配持有），故指针不会失效，`buffer_write` / `buffer_read` 全程拿到有效指针；显式成对调用还使非持久映射的分配也能走同一套代码。（R-MEM-02）

### 6.4 图像分配策略与 `usage` 约束

`image_create` 的分配口径与缓冲的设备本地分支一致：`usage = VMA_MEMORY_USAGE_AUTO` + `flags = VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT`（图像一律设备本地专用内存）。

- **`usage` 必须含 `VK_IMAGE_USAGE_TRANSFER_DST_BIT`** 才能经 `upload_image` 写入像素（头注释明文）。`upload_image` 内部会把图像当作传输目标（`TRANSFER_DST_OPTIMAL`）。
- **`tiling` 固定 `VK_IMAGE_TILING_OPTIMAL`**：最优布局，设备本地，适合采样。若要主机直写（`LINEAR`）则本模块不支持。
- **格式与纵横比分离**：`image_create` 接收 `format` 但不接收 aspect；aspect 在 `image_view_create` 时给出。因此同一图像可有不同 aspect 的视图（当前 `upload_image` 硬编码 `COLOR`，暗示本模块当前只服务颜色纹理）。
- **初值最小口径**：`mipLevels = 1`、`arrayLayers = 1`、`samples = VK_SAMPLE_COUNT_1_BIT`。即不支持 mipmap、立方体贴图 / 数组纹理、MSAA 图像。需要者须扩展本函数（增加参数）或另建路径。
- **`initialLayout = VK_IMAGE_LAYOUT_UNDEFINED`**：内容未定义，使用前必须经布局转换。`upload_image` 承担的正是「首次转换」，其第一步即声明 `oldLayout = UNDEFINED`（旧内容不必保留）。这意味着**未经上传就采样的图像其内容未定义**——本模块不提供「创建即初始化」路径。

### 6.5 一次性同步上传批次（upload batch）算法

这是本模块的核心算法，语义为：**用一条一次性命令缓冲完成 CPU→GPU 拷贝，提交后等待完成，使调用返回时数据已就位。**

骨架（`upload_resources_ensure` + `upload_submit_once`）：

```
upload_resources_ensure()                   # 首次创建上传命令池与栅栏，之后直接返回（复用）
  → vkResetCommandPool(pool)                # 连带回收上次分配的命令缓冲，可再分配
    → 分配 1 个 PRIMARY 命令缓冲
      → vkBeginCommandBuffer(ONE_TIME_SUBMIT)
        → record(command_buffer)            # 录拷贝 / 布局转换
      → vkEndCommandBuffer
  → vkResetFences(fence)                    # 复位上次已发出的完成栅栏
  → vkQueueSubmit(graphics_queue, [cb], fence)   # 不设信号量
  → vkWaitForFences(fence, UINT64_MAX)
返回整链结果
```

关键设计点：

1. **自持命令池与栅栏，跨上传复用，不依赖帧模块**：命令池与完成栅栏由 `Memory_Context` 首次上传时经 `upload_resources_ensure` 创建，之后每次上传仅重置命令池、复位栅栏，不再逐次创建 / 销毁，避免「每资源一次命令池与栅栏」的开销；同时不使用帧循环的命令池，因此上传可在渲染循环之外任意时刻发生。源码/头注释原文：「复用本类持有的上传命令池与完成栅栏（首次上传时创建，之后每次仅重置命令池 → 录制 → 提交 → 等待），不逐次创建 / 销毁命令池，也不依赖帧模块」。
2. **同步等待而非信号量**：`submit_info` 未设 `pSignalSemaphores` / `pWaitSemaphores`，改用栅栏 `vkWaitForFences(VK_TRUE, UINT64_MAX)` 等待完成。理由是「本函数即应当同步返回」，无需与其它队列操作编排。代价是 CPU 阻塞。
3. **`ONE_TIME_SUBMIT` + `TRANSIENT` + `vkResetCommandPool`**：命令缓冲声明为一次性提交，命令池声明为短命池（`TRANSIENT`）；每次上传前 `vkResetCommandPool` 回收上次命令缓冲并重新分配，向驱动传达「不复用」的语义以换取潜在优化，同时避免命令缓冲累积。
4. **失败即返回**：命令池重置失败、命令缓冲分配失败、录制（`vkBeginCommandBuffer` / `record` / `vkEndCommandBuffer`）、栅栏复位失败、提交失败都会在失败点直接返回假——**本函数不再销毁命令池 / 栅栏**（它们由 `Memory_Context` 持有，由 `destroy` 归还）；`upload_*` 随后回收暂存缓冲并返回假。唯一无法回收的是「提交已发出但等待失败」这一支：此时已提交的 GPU 工作无法撤回，属 Vulkan 语义边界（提交后无法取消），调用方须把返回值假视为「可能已部分完成」。源码未就此做额外说明。
5. **record 的泛化**：`record` 是模板类型参数，`upload_buffer` 传「一条 `vkCmdCopyBuffer`」，`upload_image` 传「屏障 + `vkCmdCopyBufferToImage` + 屏障」。因此同一骨架服务两条路径，命令池重置 / 栅栏复位 / 提交逻辑零重复。

两次上传的差异：

| 路径 | 暂存缓冲用途位 | 录制内容 | 目标终态 |
| --- | --- | --- | --- |
| `upload_buffer` | `TRANSFER_SRC`（顺序写暂存） | `vkCmdCopyBuffer`（`srcOffset = 0`、`dstOffset = offset`） | 无布局概念（线性缓冲） |
| `upload_image` | `TRANSFER_SRC`（顺序写暂存） | 屏障 `UNDEFINED→TRANSFER_DST_OPTIMAL` + `vkCmdCopyBufferToImage` + 屏障 `TRANSFER_DST_OPTIMAL→SHADER_READ_ONLY_OPTIMAL` | `SHADER_READ_ONLY_OPTIMAL`（固定） |

### 6.6 图像上传的布局转换链与同步

`upload_image` 的三步记录，其管线阶段与访问掩码如下：

| 步 | 屏障 | oldLayout → newLayout | srcAccessMask | dstAccessMask | srcStage → dstStage |
| --- | --- | --- | --- | --- | --- |
| 1 | `to_transfer` | `UNDEFINED → TRANSFER_DST_OPTIMAL` | `0` | `VK_ACCESS_TRANSFER_WRITE_BIT` | `TOP_OF_PIPE → TRANSFER` |
| 2 | （拷贝） | — | — | — | — |
| 3 | `to_shader` | `TRANSFER_DST_OPTIMAL → SHADER_READ_ONLY_OPTIMAL` | `VK_ACCESS_TRANSFER_WRITE_BIT` | `VK_ACCESS_SHADER_READ_BIT` | `TRANSFER → FRAGMENT_SHADER` |

- 两个屏障的 `srcQueueFamilyIndex` / `dstQueueFamilyIndex` 均为 `VK_QUEUE_FAMILY_IGNORED`（同队列族内转换，不涉及队列族所有权转移）。
- `subresourceRange` 固定 `{ VK_IMAGE_ASPECT_COLOR_BIT, 0, 1, 0, 1 }`（单 mip、单层、颜色），与 `image_create` 的最小口径一致。
- 第二步的 `imageSubresource` 同为 `{ COLOR, 0, 0, 1 }`；`bufferRowLength = row_pixels`、`bufferImageHeight = 0`、`imageOffset = { 0, 0, 0 }`、`imageExtent = { width, height, 1 }`。
- **同步正确性**：步 1 用 `TOP_OF_PIPE → TRANSFER` 把「进入传输阶段前的所有工作」与传输写对齐；步 3 用 `TRANSFER → FRAGMENT_SHADER` 把传输写与后续片元着色器读对齐。这保证采样该图像时能看到已上传的内容。
- **终态固定 `SHADER_READ_ONLY_OPTIMAL`**：与「采样用途」绑定。若图像要作渲染目标或再次传输，需扩展终态参数（源码注释「在此扩参即可」）。
- **潜在易错点**：若同一图像被 `upload_image` 调用两次，第二次仍以 `oldLayout = UNDEFINED` 起步——由于第一次调用后图像实际处于 `SHADER_READ_ONLY_OPTIMAL`，以 `UNDEFINED` 声明会丢失内容（破坏性）且可能触发校验层对布局不匹配的告警。本模块的语义是「`upload_image` 用于首次填充」，不支持对同一图像重复上传累积。

### 6.7 缓冲读写中的映射 / 刷写 / 无效化

- **写入**（`buffer_write`）：`vmaMapMemory` → `memcpy` → `vmaFlushAllocation` → `vmaUnmapMemory`。`flush` 的作用是把 CPU 写入落到「设备可见」：对非主机一致（non-coherent）内存类型必需，对主机一致类型为无操作。**先写后刷**顺序不可颠倒。
- **读回**（`buffer_read`）：`vmaMapMemory` → `vmaInvalidateAllocation` → `memcpy` → `vmaUnmapMemory`。`invalidate` 的作用是把设备侧写入对 CPU 可见：**必须先无效化再读**，否则可能读到 CPU 缓存中的旧值。
- **持久映射**：主机可见分配带 `VMA_ALLOCATION_CREATE_MAPPED_BIT`，映射指针在分配生命周期内一直有效；本模块仍成对调用 `vmaMapMemory` / `vmaUnmapMemory`，并在注释中说明「持久映射下不释放映射本体」。该用法为 VMA 明确支持（`vmaMapMemory` 返回 `pMappedData` 同一指针，`vmaUnmapMemory` 在持久映射下不解除映射），使非持久映射的分配也能走同一套代码，取指针路径统一。（R-MEM-02）
- **读写的边界不做校验**：`offset + size` 越界会直接踩内存，源码不防护，属调用方契约。
- 上述两点（R-MEM-01 主机可见分配按 `sequential_write` 分派内存类型、R-MEM-02 持久映射下成对映射调用的语义）均已在 §6.3 确证说明。

### 6.8 销毁与所有权约定（贯穿全模块）

1. **创建与销毁同源**：`buffer_create↔buffer_destroy`、`image_create↔image_destroy`、`image_view_create↔image_view_destroy`、`build↔destroy` 四对严格对应（上传命令池与栅栏亦由 `upload_resources_ensure` 建立、`destroy` 归还）。句柄由调用方持有，销毁动作回本模块。
2. **先资源后分配器**：`destroy` 只销毁分配器，**不**遍历其下资源；调用方必须先销毁全部缓冲 / 图像 / 视图。源码注释：「分配器不负责销毁其下缓冲 / 图像：那些必须由调用方先行销毁，否则会泄漏（VMA 会在销毁分配器时报告仍有存活分配）」。
3. **先上传侧资源、后分配器**：`destroy` 在销毁分配器**之前**先归还上传命令池与完成栅栏（二者不依赖分配器）；若调用方已存在在途上传提交，销毁命令池存在非法使用风险，须由调用方保证调用时机的外部同步。
4. **图像视图先于图像**：`image_view_destroy` 须在 `image_destroy` 之前调用（视图引用图像）。
5. **暂存缓冲自建自销**：`upload_buffer` / `upload_image` 的暂存缓冲由本模块创建并在返回前销毁，不转移给调用方，也不依赖调用方回收。
6. **幂等**：`destroy` / `buffer_destroy` / `image_destroy` / `image_view_destroy` 均对空句柄直接返回，可重复调用；`upload_resources_ensure` 亦幂等。
7. **析构兜底**：`~Memory_Context` 调 `destroy()`；若调用方已显式销毁，为无操作。

### 6.9 错误处理与日志约定

- **唯一检查出口**：全部 Vulkan 调用经 `vk_result_check(result, "操作描述")`。`VK_SUCCESS` 为真；`VK_ERROR_OUT_OF_DATE_KHR` / `VK_SUBOPTIMAL_KHR` / `VK_TIMEOUT` 记 `logger.debug` 并返回假；其余非成功码记 `logger.error` 并返回假。本模块据此把失败统一为「返回假 + 日志」。
- **异常禁用**：本模块不抛异常，不 `new` 抛出型内存（不使用 `new`，资源由 VMA / Vulkan 分配）。`memcpy` 是唯一可能与内存相关的操作，不作异常处理（C 函数不抛）。
- **日志前缀统一为「操作域:: 描述」**：`分配器创建::`、`内存上下文::`、`缓冲创建::`、`图像创建::`、`上传批次::`。便于按域检索。其中 `缓冲创建.cpp` 内的 `buffer_write` / `buffer_read` 错误信息亦用 `缓冲创建::` 前缀（沿用同一编译单元域，未另起 `缓冲写入::` 前缀）。新增上传侧日志均用 `上传批次::` 前缀（`重置上传命令池` / `分配命令缓冲` / `重置上传栅栏` / `创建上传命令池` / `创建上传栅栏` / `逻辑设备未就绪，无法创建上传资源` 等）。
- **失败时不改写出参（前置失败）vs 置空出参（创建失败）**：`buffer_create` / `image_create` 在**前置校验失败**（未构建）时返回假但**不**动出参；在 **VMA 创建失败**时**显式置空**出参。两者语义不同：前者「未尝试创建」，后者「尝试了但没成功，出参归零」。`image_view_create` 在前置失败时不改写出参，在 `vkCreateImageView` 失败时置空。

### 6.10 线程 / 并发约定

源码**未**为 `Memory_Context` 提供任何互斥或线程标注。可推断的约定：

- 本模块应被**单一渲染线程**拥有与调用；`graphics_queue` 的提交（`vkQueueSubmit`）本身在 Vulkan 层面可跨线程但需外部同步，本模块不做保护。
- `vmaMapMemory` / `vmaUnmapMemory` 的配对在同一线程内完成，无并发映射问题。
- 一次性上传使用**本类自持**的命令池与完成栅栏（跨上传复用）：**同一时刻只应有一次上传在途**，否则两次上传会争用同一命令池 / 栅栏并互相破坏（本模块不做保护）；至今源码未对上传加锁。
- 结论：**调用方负责所有并发同步**；本模块内部不额外加锁。

### 6.11 编码与文件约定（本模块做法）

- **UTF-8 与 `/utf-8`**：本模块源码为 UTF-8，MSVC 下由 `CMakeLists.txt` 的 `target_compile_options(RendererCore PRIVATE /MP /utf-8)` 保证源码按 UTF-8 解析，避免中文注释乱码。
- **大括号换行**：所有控制语句的 `{` 另起一行（符合《agent开发指南》编码风格）。
- **单语句控制流不加块**：外层 `if (host_visible)` 带块包围内层的单语句 `if (sequential_write)` / `else`（各自只一条赋值语句，不加块），符合「嵌套控制流外层加块」的约束；上传路径中 `if (!upload_resources_ensure()) { ... }` 亦带块。
- **命名**：函数 / 变量全小写下划线分隔（`build_allocator`、`upload_resources_ensure`、`buffer_out`、`host_visible`、`staging_alloc`、`upload_pool`、`upload_fence`）；自定义类型首字母大写单词无分隔（`Memory_Context`）；文件名中文优先（`内存上下文.h`、`分配器创建.cpp`）。
- **注释风格**：函数头用 `/* ... */` 多行注释（≥3 行），行内用 `//`，注释**置于被注释语句的上方**而非行尾。
- **术语中英混排**：注释中直接使用 `host_visible`、`staging buffer`、layout 等英文术语，与代码标识符一致。
- **包含路径口径（本轮统一）**：头文件（`内存上下文.h`）跨目录包含写**项目根全路径**（`Application/Renderer/common/前置头文件包含.h`）；实现文件（`.cpp`）跨目录包含写**本层根相对**（`src/render/Memory/局部命名空间使用.h`、`src/render/Renderer/core/结果检查.h`）。

### 6.12 易错点清单（面向调用方）

| 易错点 | 后果 | 规避 |
| --- | --- | --- |
| 未先销毁缓冲 / 图像就 `destroy()` | VMA 报告存活分配，显存泄漏 | 严格「先资源、后分配器」 |
| 未先销毁视图就 `image_destroy` | 视图悬垂 | 视图先于图像销毁 |
| 对设备本地缓冲调 `buffer_write` | 映射失败，写入无效 | 设备本地缓冲一律走 `upload_buffer` |
| 用 `image_create` 建图但 `usage` 未含 `TRANSFER_DST` 后调 `upload_image` | 校验层报错 / 上传无效 | 计划上传的图像必须带 `TRANSFER_DST` |
| 同一图像多次 `upload_image` | 第二次以 `UNDEFINED` 起步，内容被破坏 | `upload_image` 仅用于首次填充 |
| 缓冲 `offset+size` 越界 | 踩内存 | 调用方自行校验 |
| `build` 传入与 `device` 不匹配的 `instance`/`physical_device` | VMA 分配失败或未定义行为 | 五项入参同源取自同一设备模块 |
| `graphics_family` 非该设备的有效族 | 上传命令池创建失败 | 用设备模块给出的族索引 |
| 上传时 `graphics_queue` 为空 | `upload_*` 前置校验失败，返回假 | 确保 `build` 传入非空队列 |
| 多线程并发上传 | 争用同一命令池 / 栅栏，互相破坏 | 保证同一时刻单次上传 |
| 未经上传就采样图像 | 内容未定义 | 每次创建图像后必须上传 |
| 销毁后继续使用 `allocator_get()` / `device_get()` 返回的句柄 | 悬垂句柄 | 句柄仅在 `build` 与 `destroy` 之间有效 |

### 6.13 设计意图层面的解释

- **为什么把 VMA 实现单元放进 `Memory/core`**：VMA 是显存分配器的实现载体，与 `Memory_Context` 职责域一致；放进 `Renderer/core`（门面目录）会使「门面目录出现与其职责无关的第三方实现单元」。（迁移已如实记录于 §5.6。）
- **为什么销毁动作回本模块**：只有把创建与销毁放在同一模块，才能保证使用的销毁 API 与创建 API 匹配（都用 VMA），避免「VMA 创建、原生销毁」的错配。
- **为什么上传要同步**：起步阶段无帧模块，资源上传需要「调用完即完成」的确定语义；同步实现最简单且可预测。将来有帧槽后可能改异步，但当前保持同步。
- **为什么上传命令池与栅栏由本类自持并复用**：原实现「每次上传各建 / 各销一次命令池与栅栏」，在资源较多时开销可观测；本轮改为首次建立、跨多次上传复用（`vkResetCommandPool` + `vkResetFences`），既保留「不依赖帧模块」的独立性，又去掉逐次创建 / 销毁的开销。代价是引入「同一时刻只应有一次上传在途」的隐含约束（无加锁保护）。
- **为什么图像终态固定 `SHADER_READ_ONLY_OPTIMAL`**：当前图像唯一用途是采样。固定终态让调用方零心智负担；未来若需其它用途，按源码注释扩参即可。
- **为什么用 `DEDICATED_MEMORY`**：起步阶段资源少而大，专用内存简单可预期，牺牲子分配到后期再议。

### 6.14 `image_generate_mips` 的末段布局恢复（本轮修正）

`image_generate_mips` 的降采样循环中，第 `level-1` 级（源级）每轮被转入 `TRANSFER_SRC_OPTIMAL` 作 `vkCmdBlitImage` 的源，而每轮只把**目标级**（第 `level` 级）转回 `SHADER_READ_ONLY_OPTIMAL`。于是循环结束时，`0 .. mip_levels-2` 这些「曾作 blit 源」的级仍停在 `TRANSFER_SRC_OPTIMAL`；末级（`mip_levels-1`）仅作目标级、已是着色器可读。

**原实现缺陷**：收尾只把**第 0 级**转回着色器可读，致 `1 .. mip_levels-2` 级遗留 `TRANSFER_SRC_OPTIMAL`；此后采样该图像的这些 mip 级会因布局不符触发**布局校验错误**（属「顺手修」）。

**本轮修正**：末段改为**一条**覆盖 `subresourceRange = { COLOR, 0, mip_levels - 1, 0, 1 }` 的屏障，把这些曾作源级的级（`0 .. mip_levels-2`）一并由 `TRANSFER_SRC_OPTIMAL` 恢复为 `SHADER_READ_ONLY_OPTIMAL`（`srcStage = TRANSFER`、`srcAccess = TRANSFER_READ` → `dstStage = FRAGMENT_SHADER`、`dstAccess = SHADER_READ`）；末级（`mip_levels-1`）不纳入。

**调用方说明**：帧模块的 `deferred_entry_release` 会经本模块的 `image_view_destroy` / `image_destroy` 归还旧交换链深度图像与视图（延迟销毁的一部分），故帧模块对本模块形成依赖边（见 §2.4）。

## 七、模块运行链路详例

本章以「调用方 → 模块 → 被调方」时序描述典型链路。调用方指渲染器门面与网格 / 纹理等资源模块；被调方指设备模块（仅取句柄）、VMA、Vulkan Loader、日志系统。

### 7.1 主链路：构建内存基础设施（`build`）

1. **调用方**（渲染器门面）在设备模块完成 `build_instance` 与 `build_device` 后，从其 getter 取出 `instance` / `physical_device` / `device` / `graphics_family` / `graphics_queue`。
2. **调用方 → 本模块**：`memory.build(instance, physical_device, device, graphics_family, graphics_queue)`。
3. **本模块**：把五项记录进成员（`this->instance = instance; ...`）。
4. **本模块 → 本模块**：调私有 `build_allocator(instance, physical_device, device)`。
5. **本模块**：填充 `VmaAllocatorCreateInfo`（`vulkanApiVersion = VK_API_VERSION_1_0` + 三句柄）。
6. **本模块 → VMA**：`vmaCreateAllocator(&create_info, &allocator)`；VMA 内部（经静态函数入口）调用 `vkGetPhysicalDeviceMemoryProperties`、`vkAllocateMemory` 等完成初始化。
7. **本模块 → 日志系统**：成功时 `logger.info("分配器创建:: VMA 分配器已建立")`。
8. **本模块 → 调用方**：`build` 成功再打印 `logger.info("内存上下文:: 内存基础设施构建完成")` 并返回真。
9. **异常分支**：若第 6 步失败，`vk_result_check` 记 `logger.error`，`allocator` 置空，`build_allocator` 返回假；`build` 随即 `destroy()`（清空五项句柄）并返回假。**结果**：对象回到未构建态，`valid()` 为假，无半初始化残留。

> 注：`build` **不**创建上传命令池与栅栏；它们延迟到首次 `upload_*` 时由 `upload_resources_ensure` 建立（见 §7.5 / §7.6）。

### 7.2 主链路：创建 / 销毁缓冲

**创建（设备本地，供网格使用）**：

1. **调用方**（如网格模块）准备 `size` 与 `usage`（如 `VK_BUFFER_USAGE_VERTEX_BUFFER_BIT | VK_BUFFER_USAGE_TRANSFER_DST_BIT`），调 `memory.buffer_create(buf, alloc, size, usage, false)`。
2. **本模块**：`valid()` 通过后填 `VkBufferCreateInfo`（`sharingMode = EXCLUSIVE`、无初始数据）与 `VmaAllocationCreateInfo`（`AUTO` + `DEDICATED_MEMORY`）。
3. **本模块 → VMA**：`vmaCreateBuffer(...)`，VMA 内部 `vkCreateBuffer` + `vkAllocateMemory` + `vkBindBufferMemory`。
4. **本模块 → 日志系统**：成功 `logger.info("缓冲创建:: 缓冲已建立（{} 字节，设备本地）")`。
5. **本模块 → 调用方**：返回真，调用方保存 `(buf, alloc)`。
6. **异常分支**：`valid()` 失败 → `logger.error("缓冲创建:: 内存上下文尚未构建，无法创建缓冲")`，出参不动，返回假；VMA 创建失败 → `logger.error("缓冲创建:: 创建缓冲")`（经 `vk_result_check`），两出参置空，返回假。

**销毁**：

1. **调用方**确保该缓冲无在途 GPU 使用后，调 `memory.buffer_destroy(buf, alloc)`。
2. **本模块**：三句柄任一为空即返回（幂等）；否则 `vmaDestroyBuffer(allocator, buf, alloc)`，VMA 内部 `vkDestroyBuffer` + `vkFreeMemory`。
3. **调用方**应把本地 `buf`、`alloc` 置空以防重复销毁。

### 7.3 主链路：主机可见缓冲的写入与读回

**写入（如更新 uniform 缓冲）**：

1. **调用方**调 `memory.buffer_write(buf, alloc, data, size, offset)`。
2. **本模块**：句柄与 `data` 校验通过后 `vmaMapMemory` 取指针。
3. **本模块**：`memcpy` 写入 → `vmaFlushAllocation` 刷向设备可见 → `vmaUnmapMemory`。
4. **本模块 → 调用方**：返回真。
5. **异常分支**：参数不全 → `logger.error("缓冲创建:: 写入参数不完整，已跳过")` 返回假；`vmaMapMemory` 失败（如对设备本地缓冲）→ 经 `vk_result_check` 记错并返回假（**不** unmap）。

**读回（调试 / 校验）**：

1. **调用方**（在确保 GPU 已完成后）调 `memory.buffer_read(buf, alloc, out, size, offset)`。
2. **本模块**：`vmaMapMemory` → `vmaInvalidateAllocation` → `memcpy` 读出 → `vmaUnmapMemory`。
3. **异常分支**：参数不全 → `logger.error("缓冲创建:: 读回参数不完整，已跳过")`；映射失败 → 经 `vk_result_check` 记错。

### 7.4 主链路：创建 / 销毁图像与视图

**创建图像与视图**：

1. **调用方**（纹理模块）调 `memory.image_create(img, alloc, w, h, format, usage)`，`usage` 含 `VK_IMAGE_USAGE_TRANSFER_DST_BIT | VK_IMAGE_USAGE_SAMPLED_BIT`。
2. **本模块**：`valid()` 通过后填最小口径 `VkImageCreateInfo`（2D、单 mip、单层、单采样、`TILING_OPTIMAL`、`initialLayout = UNDEFINED`）与 `AUTO` + `DEDICATED_MEMORY` 分配信息。
3. **本模块 → VMA**：`vmaCreateImage(...)`（内部 `vkCreateImage` + 分配 + 绑定）。
4. **本模块 → 日志系统**：`logger.info("图像创建:: 图像已建立（{}x{}）")`。
5. **调用方 → 本模块**：`memory.image_view_create(view, img, format, VK_IMAGE_ASPECT_COLOR_BIT)`。
6. **本模块 → Vulkan**：`vkCreateImageView`（原生，不经 VMA），固定 2D / 单 mip / 单层。
7. **本模块 → 调用方**：返回真，调用方保存 `(img, alloc, view)`。

**销毁（严格逆序）**：

1. **调用方**调 `memory.image_view_destroy(view)` → 本模块 `vkDestroyImageView`。
2. **调用方**调 `memory.image_destroy(img, alloc)` → 本模块 `vmaDestroyImage`。

### 7.5 主链路：`upload_buffer`（CPU→设备本地缓冲）

1. **调用方**调 `memory.upload_buffer(dst, data, size, offset)`。
2. **本模块**：前置校验 `valid() && dst != null && data != null && graphics_queue != null`；不满足 → `logger.error("上传批次:: 上传缓冲的参数不完整")` 返回假。
3. **本模块 → 本模块**：`buffer_create(staging, staging_alloc, size, TRANSFER_SRC, true, true)` 建主机可见且仅顺序写入的暂存。
4. **本模块 → 本模块**：`buffer_write(staging, staging_alloc, data, size, 0)` 写入暂存；失败 → `buffer_destroy(staging)` 返回假。
5. **本模块 → 本模块**：`upload_resources_ensure()` 确保上传命令池与栅栏就绪（首次创建，之后复用）；失败 → `buffer_destroy(staging)` 返回假。
6. **本模块 → 本模块**：`upload_submit_once(device, upload_pool, upload_fence, graphics_queue, record)`：
   - **本模块 → Vulkan**：`vkResetCommandPool(pool)`（连带回收上次命令缓冲）→ 分配 `PRIMARY` 命令缓冲 → `vkBeginCommandBuffer(ONE_TIME_SUBMIT)`。
   - **本模块**：`record` 录 `vkCmdCopyBuffer(staging → dst, srcOffset=0, dstOffset=offset, size)`。
   - **本模块 → Vulkan**：`vkEndCommandBuffer` → `vkResetFences(fence)` → `vkQueueSubmit(graphics_queue, [cb], fence)` → `vkWaitForFences(fence, UINT64_MAX)`。
7. **本模块 → 本模块**：**无论成败** `buffer_destroy(staging, staging_alloc)` 回收暂存。
8. **本模块 → 日志系统 / 调用方**：成功 `logger.info("上传批次:: 缓冲上传完成（{} 字节）")`，返回 `ok`。
9. **异常分支**：第 3 步失败直接返回假（无暂存可回收）；第 4 步失败回收暂存返回假；第 5 步失败回收暂存返回假；第 6 步任一步失败，`upload_submit_once` 在失败点返回假（命令池 / 栅栏归 `destroy` 回收，不在此销毁），`upload_buffer` 随后回收暂存返回假。

### 7.6 主链路：`upload_image`（CPU→图像，含布局转换）

1. **调用方**调 `memory.upload_image(img, data, data_size, w, h, row_pixels)`。
2. **本模块**：前置校验（同上）；不满足 → `logger.error("上传批次:: 上传图像的参数不完整")` 返回假。
3. **本模块 → 本模块**：`buffer_create(staging, alloc, data_size, TRANSFER_SRC, true, true)` 建主机可见且仅顺序写入的暂存。
4. **本模块 → 本模块**：`buffer_write(staging, alloc, data, data_size, 0)`。
5. **本模块 → 本模块**：`upload_resources_ensure()` 确保上传命令池与栅栏就绪；失败 → 回收暂存返回假。
6. **本模块 → 本模块**：`upload_submit_once(..., record)`，`record` 内三步：
   - `vkCmdPipelineBarrier`：`UNDEFINED → TRANSFER_DST_OPTIMAL`（`0 → TRANSFER_WRITE`，`TOP_OF_PIPE → TRANSFER`）。
   - `vkCmdCopyBufferToImage(staging → img, TRANSFER_DST_OPTIMAL, bufferRowLength = row_pixels, bufferImageHeight = 0, imageExtent = {w,h,1})`。
   - `vkCmdPipelineBarrier`：`TRANSFER_DST_OPTIMAL → SHADER_READ_ONLY_OPTIMAL`（`TRANSFER_WRITE → SHADER_READ`，`TRANSFER → FRAGMENT_SHADER`）。
7. **本模块 → Vulkan**：`vkResetCommandPool` → `vkResetFences` → `vkQueueSubmit` + `vkWaitForFences`（命令池 / 栅栏为自持复用资源，不在本函数创建 / 销毁）。
8. **本模块 → 本模块**：回收暂存缓冲（无论成败）。
9. **本模块 → 日志系统 / 调用方**：成功 `logger.info("上传批次:: 图像上传完成（{}x{}）")`，返回 `ok`；此后图像处于 `SHADER_READ_ONLY_OPTIMAL`，可直接作采样纹理。

### 7.7 全模块销毁链路（`destroy`）

1. **调用方**（门面）依次让其下各模块销毁自有资源（网格销毁缓冲、纹理销毁视图与图像、交换链销毁自身资源）。
2. **调用方 → 本模块**：`memory.destroy()`。
3. **本模块**：若 `device` 非空，先归还上传侧资源——`upload_fence` 非空则 `vkDestroyFence`，`upload_pool` 非空则 `vkDestroyCommandPool`（连带回收其分配的命令缓冲）；随后置空 `upload_fence` / `upload_pool`。
4. **本模块**：若 `allocator` 非空，`vmaDestroyAllocator(allocator)`（VMA 断言检查是否仍有存活分配）并置空。
5. **本模块**：清空 `graphics_queue` / `graphics_family` / `device` / `physical_device` / `instance`。
6. **本模块 → 调用方**：返回。`valid()` 自此为假。
7. **兜底**：对象析构时再调一次 `destroy()`，为无操作。

### 7.8 异常 / 边界分支汇总

| 场景 | 触发点 | 模块行为 | 返回 |
| --- | --- | --- | --- |
| 未构建即创建缓冲 / 图像 | `buffer_create` / `image_create` | `logger.error`，出参不动 | 假 |
| 未构建即上传 | `upload_*`（`valid()` 失败） | `logger.error("…参数不完整")` | 假 |
| `graphics_queue` 为空 | `upload_*` | 同上 | 假 |
| `dst_buffer` / `dst_image` / `data` 为空 | `upload_*` | 同上 | 假 |
| VMA 分配器创建失败 | `build_allocator` | `logger.error`，`allocator` 置空 | 假（`build` 再 `destroy` 回退） |
| VMA 建缓冲 / 图像失败 | `buffer_create` / `image_create` | `logger.error`，两出参置空 | 假 |
| `vkCreateImageView` 失败 | `image_view_create` | `logger.error`，`view_out` 置空 | 假 |
| 对设备本地缓冲 `buffer_write` | `buffer_write` | `vmaMapMemory` 失败 → `logger.error` | 假 |
| 参数不全即写 / 读缓冲 | `buffer_write` / `buffer_read` | `logger.error`，不映射 | 假 |
| 逻辑设备未就绪即建上传资源 | `upload_resources_ensure` 前置 | `logger.error("…逻辑设备未就绪…")` | 假（无对象可回收） |
| 上传命令池创建失败 | `upload_resources_ensure` 第 3 步 | `logger.error`，`upload_pool` 置空 | 假 |
| 上传栅栏创建失败 | `upload_resources_ensure` 第 4 步 | `logger.error`，销毁命令池，两资源置空 | 假 |
| `vkResetCommandPool` 失败 | `upload_submit_once` 第 1 步 | `logger.error` | 假 |
| 命令缓冲分配失败 | 第 2 步 | `logger.error` | 假 |
| `vkBeginCommandBuffer` 失败 | 第 3 步 | `logger.error` | 假 |
| `vkEndCommandBuffer` 失败 | 第 5 步 | `logger.error` | 假 |
| `vkResetFences` 失败 | 第 6 步 | `logger.error` | 假 |
| `vkQueueSubmit` 失败 | 第 7 步 | `logger.error` | 假 |
| `vkWaitForFences` 失败 / 超时 | 第 8 步 | `vk_result_check`（`VK_TIMEOUT` 记 `debug`，其余记 `error`） | 假 |
| 销毁时仍有存活资源 | `destroy` | VMA 报告存活分配（不阻止销毁） | 无返回（void） |
| 重复 `destroy` / 空句柄销毁 | 各 `*_destroy` | 直接返回（幂等） | 无返回（void） |

### 7.9 本文与相邻文档的关系

- 本模块的 `VkResult` 检查出口 `结果检查.h` 物理上归属「渲染层-渲染器」模块；其接口语义（含「可接受结果码」口径）在「渲染层-设备」「渲染层-渲染器」等文档中亦有记载。
- 设备侧句柄由「渲染层-设备」模块的 `Device_Context` 提供，本模块只消费不创建；二者通过 `build` 的五个入参形成层内契约。
- VMA 以「就地编入」方式进入 `RendererCore`，其构建细节（私有包含根、`VMA实现.cpp` 的加入点）同时属「构建系统与层间契约」模块记载范围；本模块仅记录与实现直接相关的部分（实现单元归属、宏口径、包含路径）。
- 历史演进（已实现）：原实现的一次性上传每次自立命令池 / 栅栏并逐次创建销毁；本轮改为 `Memory_Context` 自持命令池与栅栏、跨上传复用。头注释的旧表述「帧槽命令池自 Phase 5 起提供，届时改走帧槽」在本轮已被「复用本类持有的上传命令池与完成栅栏」取代，未来仍可能进一步改走帧槽——该演进属跨模块约定，改动发生时需同步更新本模块文档与「渲染层-帧」文档。
