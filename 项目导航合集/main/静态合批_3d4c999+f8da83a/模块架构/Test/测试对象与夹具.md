## 二、模块功能介绍

### 2.1 模块定位

「测试对象与夹具」编译单元对应 Test 层的构建目标 `EngineTestObjects`（OBJECT 库）。它把 `src/单元测试/` 下 31 份用例源文件编成一组目标对象（`.obj`），由本层唯一可执行目标 `EngineTests` 以 `$<TARGET_OBJECTS:EngineTestObjects>` 收编。

本单元自身**不产出、不暴露任何库接口**：它没有对外头，也没有函数被层外调用。它的价值在于承载两样东西：

1. **googletest 夹具类（fixture）**——每个套件的 `class Xxx_Test : public ::testing::Test`，为用例体提供隔离的运行环境（每用例一份新夹具实例、可选的 `SetUp`/`TearDown`、以及按需持有的被测引擎对象或静态辅助函数）。
2. **测试用辅助对象与工具**——供用例体构造输入/承载投影字段/捕获输出的**非夹具类型**（派生被测对象、投影器仿函数、投影记录结构体、控制台捕获器等），以及文件级 `static` 辅助函数。

一句话概括：**本单元是「测试代码的骨架层」——把 gtest 的注册机制与夹具/辅助对象组织成可被反射枚举、可每用例隔离运行的编译单元，用例正文本身由四份 `单元测试-*.md` 描述。**

### 2.2 职责边界与文档分界

本单元与相邻单元/文档的分界如下：

| 对象 | 分界 |
| --- | --- |
| 本单元（`EngineTestObjects`） | 只写**测试对象/夹具**这一编译单元：夹具类、辅助测试对象、生命周期与隔离、编译口径与依赖。 |
| `Test/单元测试-主调.md`、`-工具.md`、`-核心.md`、`-渲染.md` | 写**用例正文**：各 `TEST_F` 的覆盖意图、断言与边界。本单元不重述用例内容，只说明用例「站在什么夹具/对象上」。 |
| `Test/构建与源文件清单.md` | 写 **构建清单与三/四目标的完整关系**。本单元仅在 6.1/6.8 说明与 `EngineTestObjects` 直接相关的构建事实。 |
| `TestLauncher` 库 | 提供 `engine::Test_Selection_Model` 与 `engine::解析控制台选择` 的**实现**；本单元的 `测试选择模型测试` 用例链接它取用被测逻辑（见 6.7）。 |
| `EngineTests` 可执行目标 | 收编本单元的 `.obj`，并额外编入 `src/主调/` 的主调源码；`退出暂停判定测试`、`Log_Test` 所依赖的两个符号即由它提供（见 6.7）。 |

### 2.3 在 Test 层与依赖链中的位置

```
                        ┌──────────────────────── EngineTests.exe（可执行） ───────────────────────┐
                        │  main（src/主调/主程序.cpp）                                            │
                        │  $<TARGET_OBJECTS:EngineTestObjects>  ← 本编译单元（31 份用例 .obj）      │
                        └───────────────┬───────────────────────────────────┬─────────────────────┘
                                        │ 链接                                │ 链接
              ┌─────────────────────────▼──────────┐            ┌────────────▼─────────────┐
              │ EngineCore.lib / EngineSystem.lib  │            │ RendererCore.lib          │
              │ （被测引擎实现，用例直接 include 头）│            │ （渲染层公共面）           │
              └────────────────────────────────────┘            └───────────────────────────┘
                        ▲                                                        ▲
                        │ GTest::gtest（夹具基类 / TEST_F 注册 / 反射）            │
                        └────────────────────────  TestLauncher.lib（选择模型实现）
```

- **用例只接「已构建好的」下层静态库**并直接 include 其源码头验证真实现（无源码回退）。
- 本单元链接项（`target_link_libraries(EngineTestObjects PUBLIC ...)`）：`EngineCore`、`EngineSystem`、`RendererCore`、`GTest::gtest`、`TestLauncher`。
- 当前 31 份用例**只覆盖 EngineCore（工具/核心）与渲染层公共面**；`EngineSystem` 快照已接线但暂无含系统头的用例（见 `README.md` 与 6.8）。

### 2.4 夹具三形态与用例三种取用方式

按 `README.md` 第 11.1 节归纳，夹具（本单元）分三种形态，对应用例体三种取用方式：

| 形态 | 特征 | 取用方式 | 典型夹具 |
| --- | --- | --- | --- |
| 空夹具 | 类体为空，无成员无钩子 | 用例体内自行构造被测对象与输入 | `Engine_Env_Test`、`Event_Test`、`Object_Test`、`Renderer_Init_Test` 等 |
| 持有被测对象 | `protected` 成员即被测对象（每用例独立构造） | 用例体直接在其上操作 | `Number_Allocator_Test`、`Timer_Test`、`Event_Terminal_Test`、`Collision_Proxy_Test`、`Config_Loader_Test` 等 |
| 静态辅助函数 | 以 `static` 成员/自由函数复用建树、写临时文件等公共逻辑 | 用例体调用夹具的静态辅助 | `Hash_Combine_Test`、`Field_Check_Test`、`Quadtree_Test`、`Quadtree_Manager_Test`、`Collider_Move_Test` |

此外，四类夹具带**钩子**（`SetUp`/`TearDown`）以管理外部资源或全局态：`Log_Test`、`Path_Check_Test`、`Renderer_Shader_Test`、`Config_Loader_Test`。

### 2.5 生命周期与隔离总览

- **每用例一份新夹具实例**：googletest 对每条 `TEST_F` 独立构造、析构一次夹具，故以「值成员」持有的被测对象天然隔离，用例之间不共享可变态。
- **钩子顺序**：夹具构造 → `SetUp()` → 用例体 → `TearDown()` → 夹具析构。
- **全局态**：`engine::logger` 是引擎层全局实例，`Log_Test` 会改动其规则/流绑定，靠 `SetUp`/`TearDown` 成对收放（见 6.4/7.2）；其余夹具不触碰全局态。
- **外部资源**：临时文件/目录由用例体或钩子写出、并在用例末（或 `TearDown`）删除；探针类文件已纳入 `.gitignore`。

## 三、模块公开接口介绍

### 3.1 可见性总览

本单元**无对外头，也没有对层外可见的接口**。全部类型与函数都定义在各自 `.cpp` 编译单元内部（多数夹具为编译单元作用域类型，部分被 `TEST_F` 宏引用）；唯一「对外生效」的产物是 googletest 的**静态注册**——`TEST_F` 把「套件名 = 夹具类名 + 用例名」登记进 gtest 注册表，因而可经 `::testing::UnitTest` 反射枚举（`测试选择模型` 正是以此建树）。

因此本文的「公开接口」指**本单元向同编译单元内的用例体暴露的接口面**，分三层：

- 夹具基类统一接口（`::testing::Test` 的 `SetUp`/`TearDown`）：见 3.2；
- 测试对象（非夹具辅助类型）的接口：见 3.3；
- 文件级 `static` 辅助函数的接口：见 3.4（签名逐条列于 §4.2）。

### 3.2 统一接口面：`TEST_F` 与 `::testing::Test`

本单元 34 个夹具类一律直接继承 `::testing::Test`，无中间基类。继承面固定为：

| 成员 | 签名 | 说明 |
| --- | --- | --- |
| `SetUp` | `virtual void SetUp()`（覆写） | 仅 `Log_Test`、`Path_Check_Test`、`Renderer_Shader_Test` 覆写（见 §4.1） |
| `TearDown` | `virtual void TearDown()`（覆写） | 仅 `Log_Test`、`Path_Check_Test`、`Renderer_Shader_Test`、`Config_Loader_Test` 覆写（见 §4.1） |
| 构造/析构 | 隐式 | 未定义自定义构造/析构 |
| `TEST_F` 注册 | 宏，非成员 | 以夹具类名为套件名、以中文用例名为用例名 |

- 用例体不直接调用 `SetUp`/`TearDown`；二者由 gtest 框架按 2.5 顺序调用。
- 除钩子外，夹具类**不暴露任何成员函数**；`protected`/`public` 成员为数据成员或静态辅助（见 5.2/5.3）。

### 3.3 测试对象的接口面

「测试对象」指本单元内**非夹具**的辅助类型，供用例体构造输入/承载字段/捕获输出。它们的类型与接口：

| `Tagged_Object` | `src/单元测试/核心/对象池测试.cpp` | `class Tagged_Object : public engine::Object` | 无成员函数；public 数据成员 `std::string tag` | 验证非整数投影键（字符串定位字段） |

## 四、模块私有方法介绍

### 4.2 文件级 `static` 辅助函数

| 文件 | 函数 | 签名 | 作用 |

## 六、模块设计/实现细节

### 6.1 为何用 `OBJECT` 库

`EngineTestObjects` 建成 `OBJECT` 库而非静态库，是本单元最关键的构建决策（`CMakeLists.txt` 与 `README.md` 均说明）：用例靠 `TEST_F` 宏的**静态注册**生效，而静态库中未被引用的 `.obj` 会被链接器丢弃，注册随之丢失，用例便**静默不跑**（不报错、只是数量变少）。`OBJECT` 库把 `.obj` 直接交给 `EngineTests` 的 `$<TARGET_OBJECTS:...>`，绕过丢弃，保证 34 夹具/全部用例都进注册表。

### 6.2 夹具三形态

见 2.4 的三形态表。设计意图：让夹具**只承载「用例之间需要隔离或被复用的东西」**——纯函数式用例用空夹具；需要每用例独立可变态就用值成员持被测对象（天然隔离）；公共建树/写文件逻辑抽成静态辅助，避免在每条用例里重复。

### 6.3 生命周期与隔离

- googletest 对每条 `TEST_F` **独立构造/析构一次夹具**，故 `protected` 值成员在用例间互不影响（如 `Timer_Test` 的 `timer`、`Collision_Region_Test` 的 `region`）。
- `SetUp`/`TearDown` 用于管理**跨用例存在的外部资源/全局态**（临时文件、临时目录、日志全局态），并在用例结束时归还，保证「前一条用例的副作用不泄漏给后一条」。
- 静态辅助（`make_tree` 等）**每次返回新对象**，不缓存，避免隐性共享。

### 6.4 全局日志态的处理

`engine::logger` 是引擎层的**全局实例**（`日志系统运行包.h`）。`Log_Test` 需要验证「未绑定即走控制台」的行为，因此在 `SetUp` 中关闭日志屏蔽、把日志根目录设为整个项目、清空三张输出许可表、清本文件路径/目录节点的自有流并清理探针文件；`TearDown` 逆序还原（清流、清探针、`root_clear`/`rule_clear`、重开屏蔽）。这样既能让本套件观察控制台兜底行为，又不把副作用留给其余套件（其余套件运行时引擎日志被屏蔽到文件，不与 gtest 输出混在同一位置）。

### 6.5 临时文件/目录策略

### 6.8 编译目标与包含口径

- **目标**：`add_library(EngineTestObjects OBJECT)`；源文件经 `源文件列表_EngineTestObjects.cmake` 的 `target_sources` 提供；头文件段为空。
- **包含根**（`target_include_directories(EngineTestObjects PUBLIC ${BYJY_APP_INC})`，次序即如下）：
  1. `EngineCore` 对外头快照根；2. `EngineSystem` 快照根；3. `RendererCore` 快照根；4. **项目根**；5. **本层根**（`Application/Test`）。快照根排在前，防止 `Engine/...`、`Application/Renderer/...` 命中源码树、绕过快照。
- **包含口径**（本单元 `.cpp` 实测写法）：
  - 他层头文件（引擎/渲染）写**项目根全路径**：`#include "Engine/EngineCore/src/tools/Engine_Env/引擎环境.h"`、`#include "Application/Renderer/src/render/Renderer/渲染器.h"`；
  - 本层 `src/` 下头文件写**本层根相对**：`#include "src/主调/引擎日志屏蔽.h"`、`#include "src/主调/退出等待判定.h"`、`#include "src/主调/测试选择模型.h"`；
  - 框架头 `#include <gtest/gtest.h>` 置于文件最前。
- **链接**：`EngineCore`、`EngineSystem`、`RendererCore`、`GTest::gtest`、`TestLauncher`（见 2.3）。
- **编译选项**：MSVC `/MP /utf-8` + 宏 `_CRT_SECURE_NO_WARNINGS`；非 MSVC `-Wall -Wextra -pedantic` + `_GNU_SOURCE`。
- **产物去向**：`.obj` 随 `$<TARGET_OBJECTS:EngineTestObjects>` 进入 `EngineTests`；本目标不产出 `.lib`。

### 6.9 易错点

| 易错点 | 说明与规避 |
| --- | --- |
| 把 `EngineTestObjects` 改回 `STATIC` | 未引用 `.obj` 被丢弃 → `TEST_F` 注册丢失 → 用例静默不跑（见 6.1） |
| 中文路径下用 gtest 自带 `CaptureStdout` | 其在含中文的临时目录建 `.tmp`，窄字符 `fopen` 失败会 FATAL 打断进程；本单元改用自研 `Console_Capture`（接 `std::cout` rdbuf） |
| 临时文件不清理 | 会残留在可执行文件目录；须用 `std::error_code` 容错删除，并把探针文件名登记进 `.gitignore` |
| 日志探针删除失败 | 须先清除绑定释放文件流再删（Windows） |
| 单目标链接缺失符号 | `需要等待退出`/`日志屏蔽_*` 实现不在本目标，须经 `EngineTests` 提供（见 6.7） |
| 夹具同名类型 | `Test_Object` 在两个文件各定义一份，同名不同实体（见 TEST-21） |
| 依赖未重建的下层头 | 本层按快照编译，改了引擎源码头但未重建该层时不会看到新头（`README.md` 第 9.2 节） |

## 七、模块运行链路详例

### 7.1 主流程：单个用例的生命周期

1. `EngineTests` 启动后调用 `InitGoogleTest()`，gtest 注册表已由本单元各 `.obj` 的 `TEST_F` 静态注册填满；`--gtest_filter` 决定本轮执行哪些用例。
2. 对每条命中的 `TEST_F`：gtest **构造夹具实例**（值成员就地构造，如 `Timer_Test::timer`、`Collision_Region_Test::region{ "测试空间" }`）。
3. 若夹具覆写了 `SetUp` → 调用之（`Log_Test`/`Path_Check_Test`/`Renderer_Shader_Test`；`Config_Loader_Test` 不覆写 `SetUp`）。
4. 执行用例体：在其中构造/取用被测对象、调用辅助函数、`EXPECT_*/ASSERT_*` 断言。
5. 若覆写了 `TearDown` → 调用之（同名四夹具），归还资源/全局态。
6. **析构夹具**，进入下一条用例；用例间无共享可变态。

### 7.2 `Log_Test` 的全局态收放链路

1. `SetUp`：`日志屏蔽_关闭()` → `logger.root_set("")` → `logger.rule_clear()` → `logger.stream_clear(log_test_path())` → `logger.stream_clear(log_test_dir())` → `log_remove_all()`。
2. 用例体：构造 `Console_Capture`（接管 `std::cout` rdbuf）→ 调 `logger.info/warn/error/debug` → `capture.text()` 取输出断言；或 `logger.stream_bind(路径节点, 文件名)` 后 `log_read` 读回并断言落盘。
3. `TearDown`：清本文件路径/目录/根节点自有流 → `log_remove_all()` → `logger.root_clear()` + `logger.rule_clear()` → `日志屏蔽_开启()`。
4. 由此保证：本套件可观察控制台兜底行为，且不把全局态改动留给其它套件（见 6.4）。

### 7.3 主流程：渲染隐藏窗口用例链路（L2）

1. 用例体用匿名命名空间 `hidden_config(...)` 构造 `engine::Renderer_Config`（尺寸 320×180、`hidden=true`）。
2. `engine::Renderer renderer; renderer.init(config)` 建立真实窗口与表面（隐藏仍需真实 Vulkan 设备与显示环境）。
3. 网格/纹理/相机用例在 `init` 成功后调 `mesh_load`/`texture_load_checkerboard`/`camera_*_set`，再 `frame_render()` 推进帧；用完 `mesh_unload`/`texture_unload`。
4. L3 可见窗口用例先判 `l3_enabled()`（读 `BYJY_RUN_L3`），未开启即 `GTEST_SKIP`，避免无人值守被弹窗挂住。

### 7.4 辅助边界分支汇总表

| 场景 | 触发点 | 处理 | 结果 |
| --- | --- | --- | --- |
| 静态库形式收集用例 | `EngineTestObjects` 目标类型 | 改 `OBJECT` 库 | `.obj` 不被丢弃，34 夹具全部注册（6.1） |
| 环境变量未开启 | `l3_enabled()` 返回假 | `GTEST_SKIP` | L3 用例跳过、不弹窗 |
| 日志可用但未绑定 | `logger` 输出 | 走控制台兜底 | `Log_Test` 捕获 `[LEVEL]正文` |
| 探针文件残留 | `SetUp`/`TearDown` | `log_remove_all` 清理 | 不污染下次运行 |
| 临时目录/文件已存在 | `SetUp` 先 `remove_all`/`create_directories` | 覆盖重建 | 初态可控 |
| 夹具依赖可执行符号 | 链接 `EngineTests` | 由可执行提供实现 | `需要等待退出`/`日志屏蔽_*` 可解析 |
