## 阅读约定

- 本文件与 30 份模块文档中的**源码路径一律为相对源码根**（源码根即顶层工作区目录）的路径，例如 `Engine/EngineCore/src/tools/Timer/计时器.h`。
- 引用同目录模块文档时**按层**写作 `模块架构/<层>/<模块>.md`，例如 `模块架构/EngineCore/工具集.md`、`模块架构/构建系统/构建与层间契约.md`。
- 术语：**层**指 `Engine`、`Engine/Engine*`、`Application/*` 这类具备独立 CMake 工程与独立 git 仓库的构建单元；**模块**指层内按职责切分的目录（如 `Engine/EngineCore/src/core/object/`、`Application/Renderer/src/render/Frame/`）。
- 层内文件名**不写层名前缀**（如 `模块架构/EngineSystem/实体.md` 而非 `系统层-实体.md`）；正文叙述沿用既有「系统层-实体」等称呼。
- 本轮包含路径口径统一为：**头文件跨目录包含写项目根全路径**（`Engine/EngineCore/...`、`Application/Test/...`）；**实现文件（`.cpp`）跨目录包含写本层根相对**（`src/...`）；**各层私有包含根 = 项目根 ＋ 本层根**。

### 1.2 分层职责

项目采用**分层静态库**架构：每一层是一个可独立构建的 CMake 工程（含独立本地 git 仓库），通过**层间契约变量**向下层索取「库文件路径」与「头文件快照路径」，从而做到「每一层只依赖它声明的下层」，且上层不必构建下层源码即可链接。

| 层 | 目录 | 是否产出静态库 | 依赖 | 说明 |
| --- | --- | --- | --- | --- |
| 引擎聚合层 | `Engine/` | 否 | — | 只做聚合编排与对外接口（聚合面）；**不产出库、不导出快照** |
| 引擎核心层 | `Engine/EngineCore/` | 是 | 仅外部库（bullet3、glfw、Json 等） | 引擎基础设施：工具集、对象系统、事件系统、配置系统、空间系统 |
| 引擎系统层 | `Engine/EngineSystem/` | 是 | EngineCore | 引擎业务系统：实体、属性、效果 |
| 渲染层 | `Application/Renderer/` | 是 | EngineCore（＋外部库 SDL3、VMA、glm） | Vulkan 渲染，自平台贯通至纹理采样，并新增 UI 通道 |
| 测试层 | `Application/Test/` | 是 | **Engine 聚合面（EngineSystem＋EngineCore）＋ Renderer** | 本版次新增收录：gtest 用例 ＋ 图形/控制台主调，可经渲染层 UI 通道图形化运行 |
| 游戏层 | `Application/Game/` | 是 | EngineCore、EngineSystem | 本版次不收录 |
| 编辑器层 | `Application/Editor/` | 是 | 顶层仓库 | 本版次不收录 |

**关键结论（限定依赖）**：渲染层**只接 EngineCore**，不接 EngineSystem——「渲染层不感知实体/属性/效应等业务概念」，这是本版次渲染层分层设计的硬约束；测试层则**同时接 Engine 聚合面与渲染层**，是本版次新增的第 6 个消费层关系（见 §三.1）。

### 1.7 构建系统与工作范围

- **工作区（只读）**：本项目的全部源码树，即上文目录架构（顶层 f4fbe3e ＋ 各层 HEAD）。
- **工作站（可写）**：独立于工作区的文档仓库（本导航即置于其中），含「任务报告合集／项目导航合集／下层库快照」。
- **下层库快照**：工作站内的 `下层库快照/EngineCore`、`下层库快照/EngineSystem`，暂存已构建的静态库与头快照，供上层在无法构建下层时链接使用（体积大，不入库）。
- **构建期通用规则**：每层一个 CMake 工程（Ninja 单配置，Debug/Release 双构建树）；层间通过 `cmake/接入下层.cmake` 的契约变量传递「下层库文件」与「下层头快照路径」；源文件经 `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)` 收集并落成层根显式清单。详见 `模块架构/构建系统/构建与层间契约.md`。

### 2.2 EngineCore 模块功能

**工具集（`src/tools/`）** — 引擎的地基，被其余所有模块直接或间接使用。分七组：
- `Detail/`：细粒度纯工具——路径规范化与字符串转换（中文路径与 UTF-8/本地编码转换的关键）、文件/JSON 字段可用性校验、哈希混合、二分查找、标准库 `std::format` 特化。是「路径转换操作」的官方入口（`文件路径规范化.h` 的 `path_key_normalize` 支持空锚点＝不剥离、先补尾 `/` 再匹配）。
- `Engine_Env/`：引擎环境全局态，提供逻辑帧计数等运行期环境量（位移按逻辑帧节流依赖于此）。
- `Logging/`：日志系统运行包，拆为 `Log`（门面）／`Stream_Tree`（流节点树）／`Stream_Sink`（输出目标）／`Rule`（规则）／`Node_Cache`（节点缓存）五个类；经 `std::source_location` 捕获调用处路径，按路径公共前缀建链表树分流；对外以 `logger.` 实例语义调用。本版次删除流节点树自有 `path_normalize`、日志规则新增 `key_make`。
- `Mesh_Loader/`：OBJ 网格文件加载工具（供上层消费）。
- `Number_Allocator/`：数值分配器，为对象池等提供索引/ID 的分配与回收（本版次 `capacity()` 增溢出日志分支）。
- `Random_Generator/`：随机数生成器。
- `Timer/`：计时器，提供帧计时、逻辑帧计数与节流判据。

**对象系统（`src/core/object/`）** — 统一的「对象托管」基础设施。
- `Object/`：对象基类及其标识（ID）、有效性等公共概念。
- `Object_Pool/`：对象池，按「ID ↔ 槽位索引」双映射管理对象记录，支持构建、遍历（迭代器化）、卸载与回收；`build` 采用**按值形参 `T object = {}` ＋ `std::move`**，兼容默认构造且不要求可拷贝；定位模式接口由 `order_set`/`order_reset` 合并为 `mode_set(Object_Order, Compare)`；排序模式下 `build` **不再默认重排**（改为打印日志提醒调用方手动 `sort()`），`unload` 在排序模式下自行 `sort()` 重排有效区；哈希映射写入统一为 `insert_or_assign`。

**事件系统（`src/core/event/`）** — 模块间的解耦通信总线。
- `Event/`：事件类型（含发起者/目标/分类/标签/配置包 JSON，及可比较/哈希语义）。
- `Event_Broker/`：事件中转器，持有注册关系并在事件到达时向接收方分发；**自身也是一个订阅者**，构造时接入事件系统；维护订阅者名↔权限密钥映射（`mapping`）、订阅权限表（`acl_set`）、接收入口表（`receivers`）、订阅管理契约（`process`：`Subscriber/Check|Detach`、`Subscribed_Events/Add|Remove`）。
- `Event_Terminal/`：**端口化**的事件终端——`终端端口.h` 定义端口，`事件终端.h` 定义终端；终端作为模块对外暴露的接线口，通过端口与中转器形成**依赖反转**接线，避免模块间直接互相持有。本版次**取消订阅者编号**，改由订阅者提交自身权限密钥；**接入接口改两参 `attach(模块名, acl_key)`**，订阅清单不再随接入携带，改由 `Subscribed_Events/Add` 事件在运行期提交；删除「中转站呼叫（interact）」接口，与中转站交互一律由事件发送完成；补齐接入端口检查、满订广播纳入发起者排除。

**配置系统（`src/core/config/）`** — 运行期配置的加载、缓存与回写。
- `Config_Loader/`：配置加载器，拆为 `core/` 下六个编译单元——`配置加载`／`路由文件操作`／`路径与文件`／`脏标记`／`缓存清除`／`事件处理`；核心机制为**脏标记 ＋ 缓存副本回写**：加载后缓存副本，运行期改动置脏标记，再由回写路径写回磁盘；并响应事件契约（`Load`）触发二次加载；以「可信根目录（`Believed_Root`）」隔离可加载目录（`path_safety_check` 三重校验）。
- `bridge/Logging_Config_Bridge/`：日志配置桥接，把配置项翻译为日志系统规则，隔离「配置」与「日志」两模块的直接依赖。**本版次自 `src/core/config/Logging_Config_Bridge/` 迁入 `src/core/config/bridge/Logging_Config_Bridge/`**。

**空间系统（`src/core/spatial/`）** — 空间划分与碰撞。
- `common/`：坐标类型（`Point2`/`Rect2` 模板，浮点相等采用 ULP 容差）与依赖库封装（Bullet 类型别名与 `Collision_Backend` 后端生命周期）。
- `partition/Quadtree/`：四叉树，节点所有权为 `std::shared_ptr<Node>` 的**递归 RAII**，子节点以固定数组槽访问，裸 `Node*` 仅作非持有观察者；提供构建、区块信息检索、范围/单点查询、树扩大、设置与交互；内部函数采用 `chunk_operate`／`leaf_recur` 等命名。
- `partition/Quadtree_Manager/`：四叉树管理器，管理多棵四叉树的智能创建、合并、扩大回调、相邻查找；对外 API 风格与四叉树本身一致；单点查询复用范围查询重载（把点格式化为坐标范围）。
- `collision/Collider/`：碰撞体定义。
- `collision/Collision_Proxy/`：碰撞代理器，负责位移管理（按逻辑帧节流，`frequency` 须整除帧率）、碰撞体配置与管理、碰撞响应、空间边界与配置、事件交互；本版次 `attach` 订阅流程改写。
- `collision/Collision_Region/`：碰撞空间，负责形状构建、检测执行（按 `step_length` 分段推进）、碰撞体管理、空间与边界、跨越通知。

### 2.3 EngineSystem 模块功能

**实体（`src/entity/`）** — 实体是引擎业务对象的基本单位。
- `Entity/`：派生自 `Object` 的动态对象——拥有类型标签、属性槽引用、事件终端、行为脚本、行为决策入口；只封装「单个实体怎么行动、怎么发事件」。
- `Entity_Manager/`：实体管理器，拆为 `core/` 下四个编译单元——`实体处理`／`属性槽处理`／`配置处理`／`事件处理`；作为实体的**总装配与调度中枢**，持有实体对象池与属性槽对象池，负责按类型批量创建实体、按集合卸载、按集合或全量驱动行动、经事件驱动方式接入事件中转站；通过权限密钥（`distribute_key`）把属性槽集合同所有权以指针形式对外分发，并把实体事件经绑定发送端口转发回自身终端。

**属性（`src/prop/`）** — 属性的存储与分发。
- `Prop/`：派生自 `Object` 的极简记录类型，内部仅持有一个「字符串键 → `double` 值」的哈希表（属性槽 `property_slot`），负责存放某实体的全部具名数值属性。
- `Prop_Distributor/`：属性槽分发器，以「托管方持有—分发器借指针」的关系工作；自身不拥有属性槽集合，持有一个裸指针 `props`，只有在先经事件通道收到合法「分发权限密钥」后才允许绑定；对外提供「按实体 ID 取可写属性槽 / 取只读属性槽」两类接口，配套密钥握手校验。

**效果（`src/effect/`）** — 作用于实体的效果（如增益/减益）的注册与结算。
- `Effect/`：效应载体 `Prop_Effect`（**非 `Object` 派生**、不进对象池）——持有归属 `inclusion`、编号 `ID`、名称 `name`、Sol2 的 Lua 状态机 `script`、指向「作用对象属性表」的裸指针 `effect_object` 与内嵌事件终端；对外提供一次「触发（`effect_act`）」。
- `Effect_Manager/`：效应管理器——**事件驱动的调度中枢**，以对象池 `Object_Pool<Effect_Record>` 集中托管全部 `Prop_Effect`，以 `Effect_Group` 按「归属」把效应分组；对内完成分组二分查找、优先级/阶段记录、事件转发与 Lua 数据注入；对外提供「按事件注册/卸载/结算效应」的入口。

### 2.4 Renderer 模块功能

渲染层由**门面**收口、内部拆十二个子模块，自下而上形成「平台 → 设备 → 交换链 → 帧 → 管线 → 网格/纹理 → 场景 → 门面」的完整链路，并在门面侧新增 **UI 通道**转接上层 UI 后端。

- **设备**：Vulkan 实例创建（含校验层与调试回调）、物理设备打分选择、逻辑设备与队列创建；是本层**唯一 `VkResult` 检查出口**所在模块（检查函数/宏 `vk_result_check` 定义于门面的 `core/结果检查.h`），故各模块文档均标注其归属。
- **平台与表面**：经 SDL3 创建窗口、创建 Vulkan 表面（`VkSurfaceKHR` 与 SDL 窗口绑定）、事件泵收集窗口事件；本版次另提供一条**可选的原始事件转发出口**，供上层 UI/输入后端订阅原始 SDL 事件。
- **交换链**：交换链查询（表面能力/格式/呈现模式/范围）、创建、重建；**深度附件随交换链一并管理**（一图像一张）；本版次「每交换链图像」呈现完成信号量由交换链模块持有、帧模块借用。
- **帧**：帧槽（命令缓冲/图像可用信号量/飞行围栏）创建与轮转、命令录制、提交呈现、延迟销毁；含 `slot_wait()` 写入前置等待与「先取图像、后重置围栏」的防死锁约定；本版次单一帧计数 `frame_count` 与 UI 绘制回调衔接（`Frame_Ui_Callback`）；**本版次新增离屏渲染路径 `render_to_target`**（把场景渲染进离屏目标，不取交换链图像、不呈现，与 `render` 共用同一批帧槽与帧计数轮转）。
- **内存与资源**：VMA 分配器（实现单元位于本模块 `core/VMA实现.cpp`）、缓冲创建、图像创建、一次性同步上传批次。
- **着色器**：SPIR-V 字节码 → `VkShaderModule` 的创建与销毁（不含着色器阶段组装，后者在管线模块）；本版次补魔数与 4 字节倍数自检。
- **管线**：描述符布局、管线布局与**多条图形管线**（**本版次由单一管线扩为「按句柄的管线工厂／缓存」**：句柄 0 默认场景管线 ＋ 具名管线，全部共享同一管线布局与描述符集布局，仅「着色器对 ＋ 混合档」不同）；采用 Vulkan 1.3 动态渲染（无 renderPass），固定 set0=场景 UBO（顶点阶段）、set1=采样器（片元阶段）。
- **渲染目标（本版次新增）**：离屏渲染目标（颜色 ＋ 深度图像与视图）的创建 / 销毁 / 取用（`Render_Target_Context`）；颜色帧间恒处于 `SHADER_READ_ONLY`（可被采样）、深度恒处于 `DEPTH_ATTACHMENT`；与帧模块 `render_to_target` 配合构成「离屏渲染 → 采样合成」闭环。
- **网格**：网格数据结构、网格加载、顶点/索引缓冲创建（经内存模块）；本版次改为**顶点/索引共用一条缓冲**（`Mesh_Record` 以 `buffer`/`allocation`/`index_offset` 描述，单次分配、单次上传）。
- **场景与相机**：相机参数与视图/投影矩阵计算，产出与着色器 set0 场景 UBO 对应的数据（列主序 16 浮点）；是渲染层内唯一直接使用 `glm` 的编译单元（头文件不暴露 `glm` 类型）。
- **纹理**：纹理句柄容器与**模块级共享采样器**；向外输出「视图句柄 ＋ 采样器句柄」供描述符写入。
- **UI 通道**：渲染层对上层提供的**唯一 UI 接入口**——交出「通道信息 `Ui_Channel_Info`（与 `ImGui_ImplVulkan_InitInfo` 字段对齐但不 include imgui）／每帧绘制时机 `Frame_Ui_Callback`／输入事件出送口」；只提供通道，不代管 UI、不 include imgui、不建渲染通道。
- **门面**：`Renderer` 类以 PIMPL 收口，持有并编排十一子模块的初始化/销毁顺序，对外提供渲染层唯一入口；`init` 十七阶段（末尾第 ⑰ 阶段构建 UI 通道并桥接事件泵），销毁按逆序。

### 2.6 构建系统与层间契约

- 每层一个 CMake 工程，层与层之间通过 `cmake/接入下层.cmake` 定义的**契约变量**（六变量：`_OUT_LIB`/`_OUT_INC`/`_OUT_DEF`/`_OUT_LINK`/`_OUT_SYS` 五项必需 ＋ `_OUT_LIBDIR` 可选）传递「下层库文件」与「下层头快照路径」。
- `接入下层.cmake` 各消费层各持一份副本，本版次实测**五份**（`Engine/`、`Engine/EngineSystem/`、`Application/Renderer/`、`Application/Test/`、`Application/Game/`），MD5 一致（`42572FE9...`），**必须逐字节相同**；改动契约须同步全部副本。`Engine/EngineCore` 不含该文件（无下层可接）。
- **聚合层**（`Engine/`、`Application/`）不产出库、不导出快照，只做聚合与对外接口导出；`Engine/` 的对外接口（前缀 `BYJY_ENGINE`）把 `EngineSystem;EngineCore` 摊平为聚合面，供 Test/Game 一次接入。
- **源文件清单**：各层以 `file(GLOB_RECURSE ...)` 收集源码，并落成层根显式清单 `源文件列表*.cmake`（`target_sources` 形式，为源/头的**唯一加入点**），使 VS 文件视图中的改名/迁移可改写清单并自动触发重配。
- **目录级 `CMAKE_CONFIGURE_DEPENDS`**：把被 GLOB 的源根目录登记为配置依赖，解决「仅靠 `CONFIGURE_DEPENDS` 不足以让 VS 感知增删文件」的问题。
- **头快照**：每个产出层在构建时把本层自有头镜像到自己的构建目录 `include/`，形成头快照；消费层把下层快照根作为**消费层自身的包含目录**并排在项目根之前（MSVC 下目标自身 `-I` 恒早于导入目标传递的 `/external:I`，否则快照被源码树旁路），保证「头与库同版次」。
- **包含路径口径**（本版次统一）：头文件跨目录包含写**项目根全路径**；实现文件（`.cpp`）跨目录包含写**本层根相对**；各层私有包含根改为 **项目根 ＋ 本层根**（EngineCore／EngineSystem／Renderer／Game；Test 见其「构建与源文件清单」）。
- **外部库**：置于各层 `external/`（与 `src/` 平级），以基于项目根相对路径引入；渲染层额外把 SDL3 源文件就地编入（`cmake/SDL3源文件列表.cmake`），VMA 亦就地编入；Test 层就地引入 Dear_ImGui／glad／googletest 三库。

## 三、项目各模块之间的交互关系

### 3.1 层间依赖总图

```
                    ┌──────────────────────────────────────────────┐
                    │            Application/Test                   │
                    │  测试主调 · 图形界面 · 用例 ／ OBJECT 库       │
                    └───────┬───────────────────────────┬──────────┘
                            │ 接 Engine 聚合面            │ 接 Renderer
                            │ (EngineSystem+EngineCore)  │ (RendererCore)
                            ▼                            ▼
        ┌──────────────────────────────┐   ┌──────────────────────────────────┐
        │      Engine/（聚合层）        │   │      Application/Renderer         │
        │  不产库 · 不导出快照          │   │  门面 + 十一子模块（含 UI 通道）   │
        │  （仅聚合 + 对外聚合面）       │   └──────────────┬───────────────────┘
        └──────────────┬───────────────┘                  │ 只依赖 EngineCore
                       │ 聚合面 = EngineSystem;EngineCore  │
        ┌──────────────┴───────────────┐                  │
        ▼                              ▼                  ▼
┌───────────────────────┐   ┌────────────────────────────────────────────────────┐
│ Engine/EngineSystem   │   │                   Engine/EngineCore                  │
│ 实体 · 属性 · 效果     │──►│ 工具集 · 对象系统 · 事件系统 · 配置系统 · 空间系统     │
└───────────────────────┘   └────────────────────────────────────────────────────┘

   Application/Game（→EngineCore+EngineSystem）、Application/Editor（属顶层仓库）：本轮不收录，不在依赖图内展开
```

**关键结论**：
1. 渲染层**只接 EngineCore**，不接 EngineSystem——「渲染层不感知实体/属性/效应等业务概念」（硬约束）。
2. 测试层是本版次新增的第 6 消费关系：**同时接 Engine 聚合面（取 `EngineSystem.lib ＋ EngineCore.lib`）与渲染层（取 `RendererCore.lib`）**，并**绝不 `add_subdirectory` 拉入下层源码**，只链接下层已构建静态库。
3. 聚合层 `Engine/` **不产出库、不导出快照**，只以聚合面（`EngineSystem;EngineCore` 摊平）供上层一次接入。
4. EngineSystem → EngineCore 是系统层的唯一下层依赖。

### 3.2 事件总线接入协议（本版次定版）

各模块经事件终端接入事件系统，采用**两段式**协议：

1. **`attach(模块名, acl_key)`**：接入时只登记「订阅者名 ＋ 自身权限密钥」，**不再携带订阅清单**（此前订阅者编号已取消，改为提交自身权限密钥）。
2. **`Subscribed_Events/Add` 事件提交订阅清单**：模块接入后，另经事件发送接口把「关心的事件标识（`category` ＋ `tag`）」以 `Subscribed_Events/Add` 事件在运行期登记；中转器侧对应 `Subscribed_Events/Remove` 下线。

- **中转器也是订阅者**：`Event_Broker` 构造时即接入事件系统，借由事件发送接口接收订阅管理请求（`Subscriber/Check|Detach`、`Subscribed_Events/Add|Remove`）。
- **依赖反转**：终端与中转器之间以 `Terminal_Port`（函数指针契约层）接线，二者互不持有对方；模块间通信只经事件标识解耦。
- **纯接收方**：如「属性」模块只执行接入第一步（`attach`），不发送订阅事件；满订广播时中转器**排除发起者**。
- 事件字段为 `sender`/`receiver`/`category`/`tag`/`config`（JSON）。

### 3.3 EngineCore 内部交互

- **工具集是共用地基**：对象池的槽位分配用 `Number_Allocator`；几乎所有模块的告警/信息输出用 `Logging`；所有涉及文件与中文路径的模块用 `Detail` 的路径工具；节流与帧计数用 `Timer` 与 `Engine_Env`；空间系统加载形状/网格数据用 `Mesh_Loader`。
- **对象系统是被托管者**：系统层与空间系统都通过对象池托管自身对象（实体、碰撞体、四叉树区块数据等），对象池以 ID 索引与迭代器对外服务。
- **事件系统是解耦总线**：配置加载器、实体管理器、碰撞代理器等均通过事件终端/端口接入事件系统；事件系统自身不依赖上述任何模块，形成单向依赖。
- **配置系统与日志系统通过桥接解耦**：`Config_Loader` 不直接依赖 `Logging`，而经 `bridge/Logging_Config_Bridge` 转换，保证两模块可独立演进。
- **空间系统内部**：`Collision_Proxy` 组合 `Collision_Region`（空间）与 `Collider`（碰撞体），并借 `Quadtree_Manager`/`Quadtree` 做空间划分；位移与检测按逻辑帧与步长分段推进，跨越事件经事件系统外发。

### 3.4 EngineSystem 内部交互

- `Entity_Manager` 是系统层中枢：创建/销毁实体、为实体分配属性槽、装载配置、接入事件。
- `Prop_Distributor` 为实体提供属性槽的分配与访问；`Prop` 是属性的值/描述载体，二者为「托管方持有—分发器借指针」关系，并经分发密钥（事件）握手校验。
- `Effect_Manager` 管理效应并结算到实体；效应组按归属 ID 组织，`Effect` 内嵌事件终端与实体事件通道协作。
- 三者均建立在 EngineCore 的**对象池**之上，并经**事件系统**与外部交互；配置来自**配置系统**。

### 3.5 Renderer 内部交互

门面 `Renderer` 是唯一对外入口，内部按固定顺序编排十一子模块：

```
Platform ──► Device ──► Swapchain ──► Frame ──► Ui_Channel（帧内绘制回调）
   │            │            │           │
   │            └──► Memory ─┴──► Pipeline ◄── Shader
   │                              ▲  ▲
   │                     Mesh ────┘  └──── Texture
   │                              │
   └──────────► 事件泵 ──► Ui_Channel（原始事件转发）      └──► Scene（相机 UBO）
```

- **平台与表面 → 设备**：表面（`VkSurfaceKHR`）由平台模块创建，设备模块在物理设备选择与逻辑设备创建时需表面能力（呈现队列族、扩展支持）。
- **设备 → 内存**：VMA 分配器绑定实例/物理设备/逻辑设备，是所有 GPU 资源分配的底座。
- **设备 ＋ 表面 → 交换链**：交换链按表面能力与呈现模式创建，并随窗口尺寸变化重建；深度附件与交换链同步生命周期。
- **交换链 → 帧**：帧模块按交换链图像数与飞行帧数建立帧槽，取图像/提交/呈现均与交换链交互；「先取图像、后重置围栏」的顺序约定是二者间的关键契约；呈现完成信号量按「每交换链图像」归属由交换链持有。
- **内存 → 网格/纹理/交换链深度**：三者都经内存模块创建图像/缓冲，并经上传批次完成 CPU→GPU 数据搬运。
- **着色器 → 管线**：管线消费着色器模块创建的各阶段 `VkShaderModule`；管线与交换链格式级耦合（尺寸解耦，靠动态视口/裁剪）。
- **场景 → 帧**：相机的视图/投影矩阵写入帧槽的场景 UBO（set0 自 `init` 起一次性写入、缓冲句柄恒定，每帧只更新 UBO 内容），供顶点着色器读取。
- **门面统一收口**：`Renderer` 以 PIMPL 隐藏实现，初始化按依赖顺序、销毁按逆序，并把 `VkResult` 检查集中在唯一出口。
- **UI 通道横向接线**：门面在 `init` ⑰ 构建 UI 通道并从设备/交换链/平台取信息灌入；帧链路的 `command_record` 在场景动态渲染通道内、`vkCmdEndRendering` 之前调用 UI 绘制回调；平台 `events_pump` 每帧经事件转发出口把原始 SDL 事件送入 UI 通道再转上层。

### 3.6 Test 内部交互

- 测试主调 `main` 四步分流：透传/`off`（自动化）、`console`（控制台菜单）、`window`（图形界面）、停住等待；`window` 分支失败时**安全降级**到 `console`。
- `Test_Selection_Model` 以运行期 gtest 注册表反射建树（套件/用例），产出过滤串；控制台与图形界面**共用**该模型。
- 图形界面四部分协作：`图形操作界面`（会话外壳，初始化渲染层与两条 ImGui 后端）↔ `测试界面`（每帧绘制）↔ `测试运行器`（工作线程跑 `RUN_ALL_TESTS()`，界面线程读只读快照）↔ `gtest输出镜像`（采集结果与输出行）。
- 用例（`EngineTestObjects`）直接 include 被测模块真实现头并调用真实类型/函数（无 mock）；夹具与测试对象提供隔离环境与辅助工具。
- 跨目标符号：渲染用例只触 `渲染器.h` 公共面；`引擎日志屏蔽` 与主调存在跨目标符号依赖（见 `模块架构/Test/测试对象与夹具.md` §6.7）。

### 3.7 构建期交互

- 上层构建时先经 `接入下层.cmake` 找到下层的**库文件**与**头快照目录**；若下层不可构建，可改用工作站的**下层库快照**。
- 「头快照根前置」是保证「头与库同版次」的机制前提；「显式源文件清单 ＋ 目录级配置依赖」是保证 VS 增删文件自动重配的机制前提。
- 五份 `接入下层.cmake` 副本必须逐字节一致，否则同一契约在不同层行为不一致。
- 测试层额外接入 `Renderer`（`BYJY_RENDERER_LIB_PATH`）并把三个头快照根（EngineCore/EngineSystem/RendererCore）连同项目根、本层根组装成包含根。

### 3.8 典型端到端链路（引擎启动 → 渲染一帧 → 测试图形界面）

**引擎侧（EngineCore/EngineSystem/Renderer）**

1. **引擎环境就绪**：`Engine_Env` 初始化；`Timer` 建立逻辑帧计数。
2. **日志就绪**：`Logging` 运行包建立流节点树与输出目标；随后经 `bridge/Logging_Config_Bridge` 从配置装载日志规则。
3. **配置加载**：`Config_Loader` 从磁盘加载配置（经 `Detail` 路径工具处理中文路径），缓存副本；后续配置变更置脏标记并回写。
4. **事件接线**：各模块以「`attach(模块名, acl_key)` ＋ `Subscribed_Events/Add`」接入 `Event_Terminal`，由 `Event_Broker` 中转；配置加载器监听 `Load` 类事件以支持二次加载。
5. **系统层构建**：`Entity_Manager` 创建实体 → 经 `Prop_Distributor` 分配属性槽 → `Effect_Manager` 结算效应；对象实体托管于对象池。
6. **空间构建**：`Collision_Proxy` 建立 `Collision_Region` 与碰撞体，经 `Quadtree_Manager` 组织空间划分。
7. **渲染层初始化**（门面按序，`init` 十八阶段）：平台创建窗口与表面 → 设备创建实例/选择物理设备/建逻辑设备 → 内存建立 VMA → 交换链创建（含深度附件）→ 帧槽创建 → 着色器加载 SPIR-V → 管线创建 → 网格/纹理装载 → **⑯ 渲染目标模块构建**（离屏目标资源按需创建）→ 相机就绪 → **⑱ 构建 UI 通道并把事件泵 SDL 事件桥接至 UI 通道**。
8. **帧循环**（每帧）：门面 `slot_wait()` 等待当前帧槽可用 → 相机矩阵写入该槽场景 UBO → 录制命令（绑定管线/描述符/顶点索引共用缓冲/纹理，动态渲染设定附件）→ **场景 pass 内、`vkCmdEndRendering` 之前调用 UI 绘制回调** → 提交（等待图像可用信号量、置渲染完成信号量、置飞行围栏）→ 呈现。
9. **交换链异常**：取得过期/次优图像时触发交换链重建（并重连管线格式），随后回到第 8 步。
10. **销毁**：门面按初始化的逆序释放各子模块资源（含先解除事件桥接再销毁 UI 通道）。

**测试层图形界面运行链路（本版次新增）**

1. **进程入口分流**：`EngineTests.exe` 的 `main` 摘取参数，无参数或 `--selector=window` 走图形界面分支。
2. **渲染器门面 `init`**：初始化渲染层（含第 ⑰ 阶段构建 UI 通道）。
3. **取 UI 通道参数**：`图形操作界面` 经 `Renderer::ui_channel()` 取 `Ui_Channel_Info`（实例/物理设备/设备/队列/窗口/图像数/格式/动态渲染口径）。
4. **ImGui 初始化**：据此调用 `ImGui_ImplVulkan_Init`（自建 ImGui 管线与本通道附件格式相容）与 `ImGui_ImplSDL3_InitForVulkan`，并接线帧绘制回调与平台事件转发出口。
5. **平台事件转发**：每帧 `Platform::events_pump` 取出原始 `SDL_Event`，经事件转发出口送入 `Ui_Channel_Context::event_dispatch` 再转 `imgui_impl_sdl3`（SDL 队列单点轮询不被破坏）。
6. **帧内回调绘制**：帧链路在场景动态渲染通道内调用 `Frame_Ui_Callback` → `ImGui_ImplVulkan_RenderDrawData`，把界面直接画在本帧已开启的通道内。
7. **测试运行器跑用例**：用户在界面点「运行选中」→ `Test_Runner` 在**工作线程**串行执行一轮 `RUN_ALL_TESTS()`；界面线程只经只读快照读取进度与结果；`gtest输出镜像` 采集每用例结果与输出行供界面滚动显示与结果表引用。
8. **退出清理**：请求退出 → 解除事件桥接 → `ui_channel.destroy()` → 渲染器 `shutdown` 逆序释放。
