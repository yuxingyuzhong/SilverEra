## 1. 模块功能

### 1.1 模块定位

Game 层是白银纪元分层仓库的**拓扑最上层**：

```
┌─────────────────────────────┐
│  Game 层（Game）  ← 本文档     │  游戏本体逻辑（当前为空壳）
│  依赖：EngineSystem 层（EngineSystem）   │
├─────────────────────────────┤
│  EngineSystem 层（System）            │  实体 / 属性 / 效应三大子系统
│  依赖：EngineCore 层（EngineCore）   │
├─────────────────────────────┤
│  EngineCore 层（Engine）            │  对象 / 事件 / 空间划分 / 碰撞 / 工具
└─────────────────────────────┘
```

- **位置**：`D:/代码存储/代码仓库/白银纪元/Game 层`
- **依赖**：EngineSystem 层（`EngineSystem` 静态库）——一律链接「已经构建好的」静态库，不拉入任何下层源码，也没有源码回退路径（层级契约统一）。
- **产物**：`GameCore` 静态库（**当前无源码，尚未产出**）。

### 1.2 模块解决/承担的问题

1. **游戏本体逻辑的归属地**：实体类型如何组合、战斗规则、玩法系统等「游戏玩法」代码未来都落在 `Application/Game/src/` 下，与引擎/系统的通用能力分离。
2. **数据驱动的配置资产**：`assets/` 目录承载全部运行时数据——实体配置 JSON、属性槽配置 JSON、格式定义 JSON、路由表 JSON、行为 Lua 脚本、初始化 Lua 脚本。这些资产是EngineCore / EngineSystem 层消费的数据源。
3. **层间契约闭环**：作为四层链路的最上层，Game 层的 `对外接口.cmake` 完整并入EngineSystem 层（进而并入EngineCore 层）对外面，验证「对外面逐层传递」契约的末端形态。

### 1.3 当前状态（空壳）的事实清单

| 项目 | 现状 |
|---|---|
| `src/` 源码目录 | **不存在**（LS 检查确认：Game 层仅有 `assets/`、`cmake/`、`.gitignore`、`CMakeLists.txt`、`CMakeSettings.json`） |
| `GameCore` 目标 | 未生成（CMake 条件分支跳过，不报错） |
| 可执行文件 | 无（本层不产出可执行文件，全项目唯一可执行文件在Test 层 `EngineTests.exe`） |
| `GameCore.lib` 产物 | 不存在（`out/build/*/lib/` 下无该文件） |
| 构建行为 | `cmake --build` 仍可成功：配置期完成「接入EngineSystem 层 + 空源文件判定」，构建期无编译任务 |

## 2. 模块提供接口

### 2.1 对外接口契约（`Application/Game/cmake/对外接口.cmake`）

```cmake
# =============================================================================
# Game 层 —— 对外接口（对外自描述）
# 位置：Application/Game/cmake/对外接口.cmake
# 作用
#     声明「本层向上层提供什么」。上层通过本文件读取本层对外面，据此建立
#     IMPORTED 静态库目标（不使用 add_subdirectory 回退编源码）。
#     Game 层目前是拓扑最上层，还没有使用方；本文件先把边界写清楚，
#     将来Test 层要接 GameCore 时不必再补。
# 契约（变量名与含义是层间契约的一部分，改名必须同步上层）
#     BYJY_<P>_OUT_LIB    本层静态库名（多个用分号分隔）；不产出库时留空
#     BYJY_<P>_OUT_LIBDIR 与 OUT_LIB 一一对应的「该库所在层目录」
#     BYJY_<P>_OUT_INC    使用本层公共头文件所需的包含目录
#     BYJY_<P>_OUT_DEF    使用本层公共头文件所需的编译定义
#     BYJY_<P>_OUT_LINK   本层对外传递的第三方库（文件路径）
#     BYJY_<P>_OUT_SYS    本层对外传递的系统库
#     本层前缀 <P> = GAME
# 并入下层
#     本层依赖 Engine 聚合层，因此本层对外面 = 本层自有面 + Engine 对外面。
#     下面这一句 include 会依次并入 EngineSystem 与 EngineCore 的对外面。
#
# 备注：GameCore 只在 src/ 下有源文件时才产出（当前尚未产出库）；
#       本层不产出可执行文件，可执行文件只在 Test 层产生（EngineTests.exe）。
# =============================================================================

include("${CMAKE_CURRENT_LIST_DIR}/../../../Engine/cmake/对外接口.cmake")

get_filename_component(BYJY_GAME_ROOT "${CMAKE_CURRENT_LIST_DIR}/.." ABSOLUTE)

set(BYJY_GAME_OUT_LIB "GameCore")
set(BYJY_GAME_OUT_LIBDIR "${BYJY_GAME_ROOT}")

# 本层自有包含目录由「项目根」统一承担（Application/Game/... 全路径），
# 它已在 Engine 对外面的首项里，故此处只承接即可。
set(BYJY_GAME_OUT_INC
    ${BYJY_ENGINE_OUT_INC}
)

set(BYJY_GAME_OUT_DEF  ${BYJY_ENGINE_OUT_DEF})
set(BYJY_GAME_OUT_LINK ${BYJY_ENGINE_OUT_LINK})
set(BYJY_GAME_OUT_SYS  ${BYJY_ENGINE_OUT_SYS})
```

**逐条解释**：

| 项 | 值 | 含义 |
|---|---|---|
| 首行 include | `Engine/cmake/对外接口.cmake` | 并入 Engine 聚合层对外面（聚合面已摊平 EngineSystem 与 EngineCore 两面，因此 Game 对外面 = 自有面 + 引擎子层两面） |
| `BYJY_GAME_ROOT` | Game 目录绝对路径 | 从接口文件位置推导 |
| `BYJY_GAME_OUT_LIB` | `GameCore` | 本层静态库名；**当前 `src/` 为空，尚未产出该库** —— 声明先于产物 |
| `BYJY_GAME_OUT_LIBDIR` | `Application/Game` | 与 `OUT_LIB` 一一对应，供上层自动探测 |
| `BYJY_GAME_OUT_INC` | `${BYJY_ENGINE_OUT_INC}` | 本层自有包含目录由「项目根」统一承担（`Application/Game/...` 全路径），该条目在引擎面首项里，故只承接即可 |
| `BYJY_GAME_OUT_DEF` | `=${BYJY_ENGINE_OUT_DEF}` | 继承引擎面的编译定义（`GLFW_STATIC`） |
| `BYJY_GAME_OUT_LINK` | `=${BYJY_ENGINE_OUT_LINK}` | 继承引擎面的第三方链接库（`glfw3.lib`） |
| `BYJY_GAME_OUT_SYS` | `=${BYJY_ENGINE_OUT_SYS}` | 继承引擎面的系统库（opengl32/user32/gdi32/shell32） |

### 2.2 构建目标清单

| 目标名 | 类型 | 状态 | 说明 |
|---|---|---|---|
| `GameCore` | STATIC | **条件产出**（`GAME_SOURCES` 非空时） | 当前未生成；未来是游戏逻辑静态库 |
| （无） | EXECUTABLE | — | 本层**不产出**可执行文件 |

**CMake 缓存变量**：

| 变量 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `BYJY_ENGINE_LIB_PATH` | `STRING` | `""` | Engine 聚合层静态库路径（**分号列表**，顺序同 `EngineSystem;EngineCore`）；留空则自动探测 |

### 2.3 接入函数调用（`CMakeLists.txt` 第 1 节）

```cmake
include("${CMAKE_CURRENT_SOURCE_DIR}/cmake/接入下层.cmake")

set(BYJY_ENGINE_LIB_PATH "" CACHE STRING
    "Engine 聚合层静态库路径（分号列表，顺序同 EngineSystem;EngineCore）；留空则自动探测")

byjy_jieru_xiaceng(
    "${PROJECT_ROOT_DIR}/../../Engine/cmake/对外接口.cmake"
    "BYJY_ENGINE"
    "BYJY_ENGINE_LIB_PATH"
)
```

- 复用 `byjy_jieru_xiaceng()`（EngineSystem / Engine / Test / Game **四份逐字节相同**的通用接入函数，详见《构建与层间契约.md》§2.6）。
- 同一 `接入下层.cmake` 内另含头快照契约函数 `byjy_tou_kuaizhao_gen(<结果变量> <导入目标>)`（由导入目标反推下层快照根；缺失即 `FATAL_ERROR`，与另三份逐字节相同）。本层**会调用**它两次（EngineCore / EngineSystem），把两个快照根列为自身包含目录并排在项目根之前。
- 库定位三级策略：① 覆盖变量非空 → 用它（须与 `OUT_LIB` 等长、文件不存在则 `FATAL_ERROR`）；② 留空 → **逐库**自动探测 `<该库所在层目录>/out/build/*/lib/<库名>.lib` 取时间戳最新；③ 都没有 → `FATAL_ERROR` 并给出构建相应下层的命令。
- 接入 Engine 聚合层一次即同时取得两个子层（EngineSystem ＋ EngineCore）的公共包含路径与两个库。

### 3.2 `CMakeLists.txt` 结构（骨架逐节解析）

```cmake
cmake_minimum_required(VERSION 3.20)          # 与其余各层一致

if(MSVC)
    add_compile_options(/WX-)                 # 不把警告当错误
endif()

project(Game LANGUAGES C CXX)                 # 项目名已改为英文（本版次）

set(CMAKE_CXX_STANDARD 20)                    # 强制 C++20
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

get_filename_component(PROJECT_ROOT_DIR "${CMAKE_CURRENT_SOURCE_DIR}" ABSOLUTE)
get_filename_component(BYJY_PROJECT_ROOT "${PROJECT_ROOT_DIR}/../.." ABSOLUTE)   # 项目根

# ── 1. 接入下层：Engine 聚合层（链接已构建好的静态库）──
include("${CMAKE_CURRENT_SOURCE_DIR}/cmake/接入下层.cmake")
set(BYJY_ENGINE_LIB_PATH "" CACHE STRING "...")
byjy_jieru_xiaceng(
    "${PROJECT_ROOT_DIR}/../../Engine/cmake/对外接口.cmake"
    "BYJY_ENGINE" "BYJY_ENGINE_LIB_PATH")

# ── 1.5 下层头快照接入：两个子层快照根作为本层自身包含目录，排在项目根之前 ──
byjy_tou_kuaizhao_gen(BYJY_CORE_SNAPSHOT   EngineCore)
byjy_tou_kuaizhao_gen(BYJY_SYSTEM_SNAPSHOT EngineSystem)
set(BYJY_APP_INC
    "${BYJY_CORE_SNAPSHOT}"
    "${BYJY_SYSTEM_SNAPSHOT}"
    "${BYJY_PROJECT_ROOT}")

# ── 2. 源文件收集：GLOB_RECURSE src/*.cpp、src/*.c ──
file(GLOB_RECURSE GAME_SOURCES CONFIGURE_DEPENDS
    "${PROJECT_ROOT_DIR}/src/*.cpp"
    "${PROJECT_ROOT_DIR}/src/*.c"
)

# ── 2.5 头文件收集 ＋ 编译数据库（仅供 IDE / 生成系统索引，不参与编译）──
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
file(GLOB_RECURSE GAME_HEADERS CONFIGURE_DEPENDS
    "${PROJECT_ROOT_DIR}/src/*.h"
    "${PROJECT_ROOT_DIR}/src/*.hpp"
)
if(GAME_SOURCES)
    # 排除构建目录下的文件（正则转义）
    string(REPLACE "\\" "/" SAFE_BINARY_DIR "${CMAKE_BINARY_DIR}")
    string(REGEX REPLACE "([.+*?^$()])" "\\\\\\1" SAFE_BINARY_REGEX "${SAFE_BINARY_DIR}")
    list(FILTER GAME_SOURCES EXCLUDE REGEX "^${SAFE_BINARY_REGEX}/")
    # 头文件同样排除构建目录下的生成物
    list(FILTER GAME_HEADERS EXCLUDE REGEX "^${SAFE_BINARY_REGEX}/")
endif()

# ── 3. 创建 GameCore（无源码时跳过，不报错）──
if(GAME_SOURCES)
    add_library(GameCore STATIC ${GAME_SOURCES} ${GAME_HEADERS})
    target_include_directories(GameCore PUBLIC ${BYJY_APP_INC})
    target_link_libraries(GameCore PUBLIC EngineCore EngineSystem)
    if(MSVC)
        target_compile_options(GameCore PRIVATE /MP /utf-8)
        target_compile_definitions(GameCore PRIVATE _CRT_SECURE_NO_WARNINGS)
    else()
        target_compile_options(GameCore PRIVATE -Wall -Wextra -pedantic)
        target_compile_definitions(GameCore PRIVATE _GNU_SOURCE)
    endif()
    set_target_properties(GameCore PROPERTIES
        ARCHIVE_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib"
        LIBRARY_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib"
    )
    message(STATUS "Game 层源文件: ${GAME_SOURCES}")
else()
    message(STATUS "Game 层暂无源码，未生成 GameCore 目标。")
endif()

# ── 4. 可执行文件：本层不产出 ──
```

**设计要点**：

1. **空源文件不是错误**：与EngineCore 层（`FATAL_ERROR` 强制有源）、EngineSystem 层（`FATAL_ERROR` 强制有源）不同，Game 层在 `GAME_SOURCES` 为空时**仅打印 STATUS 信息并跳过**——空壳是当前**预期状态**，不允许把「没有代码」当成配置错误。
2. **`target_link_libraries(GameCore PUBLIC EngineSystem)`**：链接的是导入目标 `EngineSystem`（由 `byjy_jieru_xiaceng` 建立），其 INTERFACE 上挂有EngineSystem 层+EngineCore 层全部对外面。
3. **本层不产出可执行文件**：过去这里挂着一个「组合根可执行文件」（把EngineCore 层与EngineSystem 层接在一起从本层启动），以及「把Test 层宿主并入本构建树」的开关。两者都已移除（详见 §4.2）。
4. **IDE 索引支持（上一版次新增）**：§2 追加 `.h/.hpp` 递归收集（`GAME_HEADERS`）并纳入 `GameCore`，同时开启 `CMAKE_EXPORT_COMPILE_COMMANDS ON`。前者**仅供 IDE 与生成系统建立文件索引、不参与编译**；后者生成 `compile_commands.json` 供语言工具链读取本层包含路径与宏（Ninja 生成器默认不产出该文件）。详见 §4.6。

### 3.4 资产数据体系（数据契约）

Game 层的 `assets/` 是四层中**唯一有实质内容**的部分。它定义了「数据如何描述实体」的契约：

**路由表 `config/route/entity.json`**（配置路径 → 模块）：

```json
[
  { "config_path": "config/entities/牛头人 (Minotaur).json", "module": "Entity_Mangaer" },
  { "config_path": "config/entities/牛头人战士 (Minotaur_Warrior).json", "module": "Entity_Mangaer" },
  { "config_path": "config/entities/哥布林 (Goblin).json",        "module": "Entity_Mangaer" },
  { "config_path": "config/entities/哥布林祭司 (Goblin_Priest).json", "module": "Entity_Mangaer" },
  { "config_path": "config/entities/史莱姆 (Slime).json",         "module": "Entity_Mangaer" },
  { "config_path": "config/entities/史莱姆王 (Slime_King).json",  "module": "Entity_Mangaer" }
]
```

> 注意：源码原文 `module` 值为 `"Entity_Mangaer"`（**拼写错误**，Mangaer 应为 Manager）。这是资产数据里的既有笔误，重开发时需统一（引擎/系统侧的读取方若按 `"Entity_Manager"` 匹配将落空）。

**路由表 `config/route/property.json`**：同样的 6 个实体，`module` 为 `"Property_Manager"`。

**格式定义 `config/format/Entity_Manager.json`**（实体配置的字段契约）：

| 字段 | 类型 | required | 说明 |
|---|---|---|---|
| `type` | string | true | 实体类型标识，保存后配置文件会自动迁移 |
| `decision_load_path` | script | true | 决策树行为脚本路径，相对 `assets/` 目录，Entity_Manager 使用 |
| `acls` | string_list | true | 允许从属的实体类型列表（master 为实体类型自身） |
| `Needed_Events` | pair_list | true | 订阅事件列表，每项 = [分类, 标签]，如 [Entity, Request] |

另有 `dir: "entities"`、`route: "entity.json"`、`builtin: true`、`module: "Entity_Manager"` 元字段。

**格式定义 `config/format/Property_Manager.json`**：

| 字段 | 类型 | required | 说明 |
|---|---|---|---|
| `type` | string | true | 实体类型标识，与实体配置的 type 一致 |
| `initialize_path` | script | true | 属性槽初始化 Lua 脚本路径，相对 `assets/` 目录，Property_Manager 使用 |

**实体配置实例**（`config/entities/史莱姆 (Slime).json`）：

```json
{
  "type": "Slime",
  "acls": []
}
```

（`config/entities/哥布林 (Goblin).json` 更完整：`acls.master`、`acls.minion_set`、`needed_events` 数组等。）

**属性槽配置实例**（`config/property/史莱姆 (Slime).json`）：

```json
{
  "type": "Slime",
  "initialize_path": "scripts/monster/slime.lua"
}
```

> 注意：`initialize_path` 指向 `scripts/monster/slime.lua`，但当前 `assets/scripts/` 下只有 `behavior/` 与 `initialize/` 两个子目录，**不存在 `monster/` 子目录**——即该脚本路径当前悬空（文件缺失）。这是资产与脚本目录不一致的现状，重开发时需对齐。

**脚本资产**：
- `assets/scripts/behavior/哥布林 (Goblin)_Behavior.lua`：哥布林决策树行为脚本（`Entity::action_load` 加载，脚本须定义 `decision` 函数）。
- `assets/scripts/initialize/哥布林 (Goblin).lua`：哥布林属性槽初始化脚本（属性槽配置加载执行，向属性槽写入初始值）。

## 4. 模块设计/实现细节

### 4.1 空壳设计的意图

Game 层在当前版次没有源码是**有意的阶段性状态**：

1. **分层进度独立**：四层各自独立推进。EngineCore 层（碰撞拆分）、EngineSystem 层（实体/属性/效应）先行，游戏玩法逻辑尚未开始。
2. **契约先行**：即使没有代码，`CMakeLists.txt`、`对外接口.cmake`、`接入下层.cmake` 已全部就位——将来Game 层写第一行代码时，只需在 `src/` 下放 `.cpp/.c`，`CONFIGURE_DEPENDS` 自动纳入，零 CMake 改动。
3. **数据先行**：`assets/` 的实体/属性/格式/路由 JSON 已经描述了「游戏里有哪些怪物（史莱姆、哥布林、牛头人系列）、每个怪物订阅什么事件、属性怎么初始化」，等于把玩法数据先于代码落盘。

### 4.2 宿主机制取消（历史决策）

`CMakeLists.txt` 第 4 节注释完整记录了这段历史：

```
# 4. 可执行文件：本层不产出
# 过去这里挂着一个组合根可执行文件（把EngineCore 层与EngineSystem 层接在一起，从本层启动），
# 以及「把Test 层宿主并入本构建树」的开关。两者都已移除：
#     1) 宿主机制取消 —— 可执行文件只在Test 层产生（EngineTests.exe），
#        各层不再各自维护一个可运行的入口；
#     2) 组合根与宿主职责重叠，且会把下层源码拉进本构建树重复编译，
#        与「层间一律链接已构建静态库」的契约冲突。
# 现在各层的分工：下层各自构建静态库（EngineCore 层 EngineCore、EngineSystem 层 EngineSystem），
# 本层构建 GameCore 静态库，Test 层构建唯一可执行文件 EngineTests.exe。
```

**取消的两个机制**：

| 被移除的机制 | 形态 | 移除原因 |
|---|---|---|
| 组合根可执行文件 | 从Game 层启动、把EngineCore 层+EngineSystem 层接在一起 | 与宿主职责重叠；会把下层源码拉进本构建树重复编译，违反「层间一律链接已构建静态库」契约 |
| Test 层宿主并入开关（`BYJY_JOIN_TEST_HOST`） | CMake 开关，把Test 层宿主接进本构建树 | 同上；开关本身在 `CMakeSettings.json` 里残留 |

**现在的职责分工**（全项目）：

| 层 | 产出 |
|---|---|
| EngineCore 层 | `EngineCore` 静态库 |
| EngineSystem 层 | `EngineSystem` 静态库 |
| Game 层 | `GameCore` 静态库（条件产出，当前无） |
| Test 层 | `EngineTests.exe`（**唯一可执行入口**）+ TestCore/TestLauncher/TestGui 静态库 |

**未来游戏入口的路径**（源码注释原文）：「游戏本体将来需要入口时，再在本层单独开一个可执行目标」。

### 4.3 条件构建 `GameCore` 的实现细节

```cmake
if(GAME_SOURCES)
    add_library(GameCore STATIC ${GAME_SOURCES} ${GAME_HEADERS})
    ...
else()
    message(STATUS "Game 层暂无源码，未生成 GameCore 目标。")
endif()
```

**易踩坑点**：

1. **`GameCore` 目标不存在时，上层链接它会在配置期报错**：`对外接口.cmake` 已声明 `BYJY_GAME_OUT_LIB = "GameCore"`，若未来Test 层真的去 `byjy_jieru_xiaceng(Game 层对外接口...)`，自动探测 `Application/Game/out/build/*/lib/GameCore.lib` 会**找不到而 FATAL_ERROR**——这是源码注释明确标注的「预期行为」。因此**Test 层接入Game 层的动作必须发生在Game 层有源码之后**。
2. **GLOB 过滤只排除构建目录**：与EngineSystem 层不同，Game 层没有 `Tests/`、`Config_Editor` 之类排除规则——将来若有内部测试代码需自行加规则。
3. **`CONFIGURE_DEPENDS` 自动纳入**：在 `src/` 下新建 `.cpp` 无需重跑 cmake，构建时自动检测。

### 4.4 资产数据与EngineSystem 层代码的对应关系

Game 层资产是EngineSystem 层运行时的数据源，映射关系（结合《EngineSystem 层》文档 §4.8）：

| 资产文件 | EngineSystem 层消费方 | 对应代码逻辑 |
|---|---|---|
| `config/entities/*.json` 的 `type`/`needed_events`/`decision_load_path` | `Entity_Manager::config_field_parse` / `action_load_path_register` | 校验字段、注册决策树路径、订阅事件 |
| `config/property/*.json` 的 `initialize_path` | `Entity_Manager::prop_load_path_register` | 加载属性槽初始化脚本到 `prop_config_paths` |
| `scripts/behavior/*.lua` | `Entity::action_load` | 加载决策树（须定义 `decision`） |
| `scripts/initialize/*.lua` | `prop_config_paths[type].load_file` | 初始化属性槽 |
| `config/format/*.json` | 配置编辑器 `Config_Editor` | 字段格式定义（编辑器生成/校验配置） |
| `config/route/*.json` | 配置加载流程 | 配置路径 → 模块路由 |

**数据不一致现状（重开发注意）**：

1. `route/entity.json` 的 `module` 拼写为 `"Entity_Mangaer"`（笔误）。
2. `property/史莱姆 (Slime).json` 的 `initialize_path` 指向 `scripts/monster/slime.lua`，但 `assets/scripts/` 下无 `monster/` 目录（悬空路径）。
3. `entities/史莱姆 (Slime).json` 只有 `type` + 空 `acls`，缺 `decision_load_path` / `needed_events`——与 `format/Entity_Manager.json` 的 required 字段契约不符（配置不完整）。
4. `entities/` 与 `property/` 的配置文件名带**空格与括号**（如 `史莱姆 (Slime).json`）——中文+空格路径在 MSVC/Ninja 构建与 googletest 的 ANSI 解析下是已知风险区（参见《构建与层间契约》文档 §4.7 的坑位表）。

### 4.5 与其它层的契约要点（Game 层视角）

| 契约面 | 内容 | 说明 |
|---|---|---|
| 依赖方向 | Game → Engine 聚合层 → {EngineSystem → EngineCore} | 单向，不反向依赖 |
| 链接方式 | `target_link_libraries(GameCore PUBLIC EngineCore EngineSystem)` | 两个库都是同一份聚合面引入的 IMPORTED 导入目标，INTERFACE 上已含全部对外面 |
| 静态库定位 | `BYJY_ENGINE_LIB_PATH` 覆盖变量（分号列表，须与 `OUT_LIB` 等长） / 逐库自动探测 / `FATAL_ERROR` | 复用 `byjy_jieru_xiaceng()` 三级策略 |
| 对外面 | `BYJY_GAME_OUT_*` = 自有面 + Engine 聚合面（= EngineSystem 面 ＋ EngineCore 面） | 链式 include，幂等 |
| 头快照 | 两个子层快照根由 `byjy_tou_kuaizhao_gen()` 反推，作为本层自身包含目录并排在项目根之前 | 快照缺失即 `FATAL_ERROR` |
| C++ 标准 | C++20，`/WX-`，MSVC `/MP /utf-8`，`_CRT_SECURE_NO_WARNINGS` | 与各层一致 |
| 构建目录 | `Application/Game/out/build/<配置>/`，库落 `lib/` | 与自动探测路径一致 |

### 4.6 IDE 索引与构建说明

本版次 Game 仅随目录迁移与契约升级同步构建脚本，**仍无源码、无新增用例、无行为变化**：

| 文件 | 改动 |
|---|---|
| `Application/Game/CMakeLists.txt` | `project(Game)`；接入改为 **Engine 聚合层一次**；新增快照接入（`byjy_tou_kuaizhao_gen` ×2）与 `BYJY_APP_INC`；新增目录级 `CMAKE_CONFIGURE_DEPENDS`；路径与包含根改项目根 |
| `Application/Game/cmake/对外接口.cmake` | 并入路径改 `../../../Engine/cmake/对外接口.cmake`；新增 `OUT_LIBDIR` |
| `Application/Game/cmake/接入下层.cmake` | 与 EngineSystem / Engine / Test 三份**逐字节相同**（含 `byjy_jieru_xiaceng()` 与 `byjy_tou_kuaizhao_gen()`） |
| `Application/Game/README.md` | 同步新架构与构建说明 |

**背景与要点**：

1. **头文件索引**：各层 `CMakeLists.txt` 一律 `GLOB_RECURSE` 收 `.cpp`/`.c`，另**单独递归收 `.h/.hpp`** 并纳入对应 target —— **仅供 IDE 与生成系统建立索引，不参与编译**；否则 VS 解析 include 时两头都找不到头文件、总是报「未找到文件」。
2. **`compile_commands.json`**：Ninja 生成器默认不产出该文件，故各层统一 `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)`。
3. **增删文件自动重配（本版次）**：除 `GLOB_RECURSE CONFIGURE_DEPENDS` 外，还把被 GLOB 的**源根目录**登记进 `CMAKE_CONFIGURE_DEPENDS`，目录内容变化即触发重配并重扫，不必手动「重新生成缓存」。
4. **UTF-8 代码页**：Ninja 增量构建对头依赖的捕获，依赖「CMake 探测到的 `/showIncludes` 前缀」与「cl 实际输出的字节」一致 —— **配置阶段本身必须处于 UTF-8 代码页**，否则头依赖全部丢失（`ninja -t deps` 为 `#deps 0`）。详见《构建与层间契约.md》§4.11。
5. **VS 侧残留**：即使已删缓存并重新配置，IntelliSense 数据库仍独立于 CMake 缓存；若仍无效，须**完全退出 VS** 后删除 `Engine/EngineCore/.vs` 与仓库根 `.vs` 再重开。
6. **验收**：Game 层 `cmake --build` 仍 exit=0（本层无源码、无编译任务）。

## 5. 模块运行链路

### 5.1 构建时序

```
第 1 步（前置）：构建 EngineCore
  cmake -S Engine/EngineCore -B Engine/EngineCore/out/build/x64-Debug -G Ninja
  cmake --build Engine/EngineCore/out/build/x64-Debug
    → Engine/EngineCore/out/build/x64-Debug/lib/EngineCore.lib ＋ include/（头快照）
第 2 步（前置）：构建 EngineSystem
  cmake --build Engine/EngineSystem/out/build/x64-Debug
    → Engine/EngineSystem/out/build/x64-Debug/lib/EngineSystem.lib ＋ include/
第 3 步（前置，聚合面自检）：构建 Engine 聚合层
  cmake --build Engine/out/build/x64-Debug
    → EngineAggregateCheck（校验两个库齐备；不产出库）
第 4 步：构建 Application/Game（当前空壳）
  cmake -S Application/Game -B Application/Game/out/build/x64-Debug -G Ninja
  cmake --build Application/Game/out/build/x64-Debug
    ├─ cmake configure
    │   ├─ project(Game)
    │   ├─ include 接入下层.cmake
    │   ├─ byjy_jieru_xiaceng(Engine/cmake/对外接口.cmake, BYJY_ENGINE, BYJY_ENGINE_LIB_PATH)
    │   │   ├─ include Engine 聚合层对外接口（链式并入 EngineSystem、EngineCore 两面）
    │   │   ├─ 校验六个契约变量
    │   │   ├─ OUT_LIB = "EngineSystem;EngineCore" → 逐库自动探测 out/build/*/lib/*.lib（取最新）
    │   │   └─ add_library(EngineSystem/EngineCore STATIC IMPORTED GLOBAL) + INTERFACE 三件套
    │   ├─ byjy_tou_kuaizhao_gen ×2 → 两个子层快照根（缺失即 FATAL_ERROR）
    │   ├─ BYJY_APP_INC = [EngineCore 快照根, EngineSystem 快照根, 项目根]
    │   ├─ GLOB src/*.cpp src/*.c → GAME_SOURCES（当前为空）＋ 目录级 CONFIGURE_DEPENDS
    │   └─ GAME_SOURCES 为空 → 跳过 GameCore 目标（STATUS 提示）
    └─ cmake --build
        └─ 无编译任务（无目标），立即成功退出
```

### 5.2 未来「Game 层有源码」的构建时序（预期）

```
1. 在 Application/Game/src/ 下放置源文件（如 src/游戏世界.cpp、src/战斗系统.cpp）
2. 下次构建自动触发（GLOB_RECURSE CONFIGURE_DEPENDS ＋ 目录级 CMAKE_CONFIGURE_DEPENDS）
3. add_library(GameCore STATIC ...) 生成
4. GameCore 链接 EngineCore ＋ EngineSystem（同一聚合面引入的导入目标，自动继承全部对外面）
5. 本层源码以 Application/Game/... 全路径互相包含（项目根在包含根中）
6. 产物：Application/Game/out/build/x64-Debug/lib/GameCore.lib
7. （可选）上层接入 GameCore：byjy_jieru_xiaceng(Application/Game/cmake/对外接口.cmake, BYJY_GAME, BYJY_GAME_LIB_PATH)
   —— 注意：此时 Game 必须已产出库，否则探测失败属预期行为
```

### 5.3 运行时链路（数据流视角）

```
assets/config/route/entity.json、property.json
  │（配置加载流程：路由表 → 逐条读取 config_path）
  ▼
assets/config/entities/*.json ──→ Entity_Manager（EngineSystem 层）──→ 注册决策树路径 / 订阅事件
assets/config/property/*.json ──→ Entity_Manager（EngineSystem 层）──→ 加载属性槽初始化脚本
assets/scripts/behavior/*.lua ──→ Entity::action_load（EngineSystem 层）──→ LuaState（decision 函数）
assets/scripts/initialize/*.lua ─→ prop_config_paths[type].load_file（EngineSystem 层）──→ 属性槽初始化
assets/config/format/*.json ────→ Config_Editor（EngineSystem 层 gui，未接入构建）──→ 配置编辑/校验
```

**当前闭环状态**：数据已就位，但**执行链路的最后一环（Game 层代码）缺失**——`assets/` 的配置目前只能被EngineSystem 层的接口消费（需要外部触发 Config 事件），Game 层没有自己的运行时来驱动「配置 → 实体 → 战斗」的完整闭环。这是空壳层与数据先行状态的直接体现。

### 5.4 与其它模块的协作关系

| 协作对象 | 方向 | 机制 |
|---|---|---|
| EngineSystem 层 `EngineSystem` | 依赖（链接） | IMPORTED 导入目标；运行时消费EngineSystem 层的事件/实体/属性/效应接口 |
| EngineCore 层 `EngineCore` | 间接依赖 | 经EngineSystem 层对外面传递（包含路径/链接库/系统库/GLFW_STATIC） |
| Test 层 `EngineTests` | 未来可选 | Test 层可接入 GameCore 做游戏逻辑测试（当前未接） |
| `assets/` 资产 | 数据源 | Game 层代码未来读取/驱动资产数据 |
| 配置编辑器 `Config_Editor` | 数据工具 | 编辑 `assets/config/` 下 JSON（编辑器在EngineSystem 层，未接入构建） |
