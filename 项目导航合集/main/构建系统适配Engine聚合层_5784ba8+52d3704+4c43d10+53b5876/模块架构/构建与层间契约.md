## 1. 模块功能

### 1.1 模块定位

本项目**没有顶层构建编排**。五个可构建层各自持有独立的 `CMakeLists.txt`，逐层独立配置、独立构建；层与层之间通过一套**两层式文件契约**交接：

```
<层>/cmake/对外接口.cmake     声明「本层向上层提供什么」（纯数据赋值）
<层>/cmake/接入下层.cmake     提供通用函数，读下层对外面 → 定位已构建静态库 → 建导入目标
```

该契约加上「对外头快照」与「目录级配置依赖」两项机制，构成本项目全部的编译期约束。本文件即这套约束的规格说明。

### 1.2 模块解决的问题

| 问题 | 本项目的做法 |
| --- | --- |
| 层与层如何交接，而不把下层源码拖进本次构建 | 层间**只链接已构建静态库**：读下层 `对外接口.cmake` → 配置期定位 `<下层>/out/build/*/lib/<库名>.lib` → 建 `IMPORTED STATIC GLOBAL` 目标。**定位不到即硬失败，绝不回退编译下层源码** |
| 上层「头已改、库未重建」导致新头配旧库 | 各层把自有头镜像到 `<本层构建目录>/include`（对外头快照），上层按快照根编译 ⇒ **头与 `.lib` 同版次** |
| 一次改动要手动重跑 CMake / VS 报「文件名未找到」 | 保留 `GLOB_RECURSE CONFIGURE_DEPENDS`，并把每个被 GLOB 的**源根目录**登记进 `CMAKE_CONFIGURE_DEPENDS`；增删文件后构建前自动重配并重扫 |
| 直接 `#include "src/..."` 带来的路径归属不明与文件重名 | 项目内部一律写**项目根相对全路径**（`Engine/EngineCore/...`、`Engine/EngineSystem/...`、`Application/Test/...`），各层编译包含根统一收敛为**项目根** |
| 多个下层如何被一次接入 | `OUT_LIB` 支持**分号列表**；顶层 `Engine/` 作为**聚合层**把 `EngineSystem` 与 `EngineCore` 两面摊平为 `BYJY_ENGINE_*`，`Application/` 各层只接一层、只读一个接口文件 |

### 1.3 服务对象

| 对象 | 关注点 |
| --- | --- |
| 各层开发者 | 在本层增删文件后无需手动重配；新头按全路径写法即可被解析 |
| 上层接入者 | 只读一层接口文件、只接一层；覆盖变量与自动探测两条入口 |
| IDE / 语言工具链 | `compile_commands.json`（各层开启 `CMAKE_EXPORT_COMPILE_COMMANDS`）与头文件索引（`.h/.hpp` 纳入目标） |
| 构建/回归流程 | 严格串行的五层构建顺序与「缺库即失败」的确定性报错 |

## 2. 模块提供接口

### 2.1 对外接口契约：`BYJY_<P>_OUT_*` 六个变量

每个 `<层>/cmake/对外接口.cmake` 必须定义下列变量。<P> 为该层前缀：`ENGINE_CORE` / `ENGINE_SYSTEM` / `ENGINE` / `TEST` / `GAME`。

| 变量 | 必需 | 含义 |
| --- | --- | --- |
| `BYJY_<P>_OUT_LIB` | 是 | 本层静态库名**列表**（分号分隔）；不产出库时留空 |
| `BYJY_<P>_OUT_LIBDIR` | 否（本版次新增） | 与 `OUT_LIB` **一一对应**的「该库所在层目录」，供自动探测；缺省或少于库数时，缺少项按「本层目录」补齐 |
| `BYJY_<P>_OUT_INC` | 是 | 使用本层公共头文件所需的包含目录 |
| `BYJY_<P>_OUT_DEF` | 是 | 使用本层公共头文件所需的编译定义 |
| `BYJY_<P>_OUT_LINK` | 是 | 本层对外传递的第三方库（文件路径） |
| `BYJY_<P>_OUT_SYS` | 是 | 本层对外传递的系统库 |

```cmake
# 契约（变量名与含义是层间契约的一部分，改名必须同步上层）
#     BYJY_<P>_OUT_LIB    本层静态库名（多个用分号分隔）；不产出库时留空
#     BYJY_<P>_OUT_LIBDIR 与 OUT_LIB 一一对应的「该库所在层目录」
#     BYJY_<P>_OUT_INC    使用本层公共头文件所需的包含目录
#     BYJY_<P>_OUT_DEF    使用本层公共头文件所需的编译定义
#     BYJY_<P>_OUT_LINK   本层对外传递的第三方库（文件路径）
#     BYJY_<P>_OUT_SYS    本层对外传递的系统库
```

**并入方式**：`本层对外面 = 本层自有面 + 下层对外面`，并入动作就是一句 `include(<下层>/cmake/对外接口.cmake)` —— 它把下层的 `BYJY_<下层前缀>_OUT_*` 赋值进来，本层再在自己的列表里直接引用。**纯数据赋值，重复 include 无副作用**（CMake 变量赋值幂等）。

### 2.2 EngineCore 对外面（`Engine/EngineCore/cmake/对外接口.cmake`）

前缀 `<P> = ENGINE_CORE`。本层是拓扑最底层，**没有** `cmake/接入下层.cmake`。

| 变量 | 取值 |
| --- | --- |
| `OUT_LIB` | `EngineCore` |
| `OUT_LIBDIR` | `Engine/EngineCore`（本层根） |
| `OUT_INC` | ① **项目根**（`Engine/EngineCore` 上溯两级）② `external/Json` ③ `external/glfw` ④ `external` ⑤ `external/bullet3/src` |
| `OUT_DEF` | `GLFW_STATIC` |
| `OUT_LINK` | `external/glfw/glfw3.lib` |
| `OUT_SYS` | `opengl32` / `user32` / `gdi32` / `shell32` |

- **首项为什么是「项目根」而不是本层根**：项目内部一律写「项目根相对全路径」（`Engine/EngineCore/...`）。本层自身编译同样按此写法（私有包含根也是项目根），从而彻底消除直接 `src/...` 包含带来的路径归属不明与文件重名。这是本版次任务<2>的核心。
- 其余四项是第三方：本层预编译头 `Engine/EngineCore/common/前置头文件包含.h` 内部 include 了 `<nlohmann/json.hpp>` 与 `<GLFW/glfw3.h>`；本层碰撞相关公共头引用 bullet3 头；故这些路径必须随对外面传递。
- 原 `glm` 条目已移除（`external/glm` 目录在上一版次删除且无引用）。

### 2.3 EngineSystem 对外面（`Engine/EngineSystem/cmake/对外接口.cmake`）

前缀 `<P> = ENGINE_SYSTEM`。首句并入 EngineCore：

```cmake
include("${CMAKE_CURRENT_LIST_DIR}/../../EngineCore/cmake/对外接口.cmake")
```

| 变量 | 取值 |
| --- | --- |
| `OUT_LIB` | `EngineSystem` |
| `OUT_LIBDIR` | `Engine/EngineSystem`（本层根） |
| `OUT_INC` | ① `EngineSystem/external/Sol2/include` ② `EngineSystem/external/Lua` ③ `${BYJY_ENGINE_CORE_OUT_INC}`（并入的引擎面，含项目根） |
| `OUT_DEF` / `OUT_LINK` / `OUT_SYS` | 直接继承 `BYJY_ENGINE_CORE_OUT_*` |

- 本层自有部分只有 Sol2 与 Lua：公共头 `Engine/EngineSystem/src/entity/Entity/实体.h` 与 `Engine/EngineSystem/src/effect/Effect/效应.h` 对外暴露 `LuaState`（`sol::state` 别名），`EngineSystem/common/external/Sol2/` 下的包装头也直接用 `sol::` 类型。
- **本层不再声明自身层根 / `src` 两个条目**：项目内部一律写「项目根相对全路径」（`Engine/EngineSystem/src/...`），由 EngineCore 对外面首项「项目根」统一解析。
- 未列入的第三方：`EngineSystem/external/` 下的 Dear_ImGui、glad、glfw、glm、stb 目前不被本层静态库源文件直接引用（唯一直接引用 `stb_image.h` 的 `EngineSystem/src/gui/Config_Editor/` 含独立 `main()`，已排除在静态库外）。将来接入配置编辑器时需一并补上其包含路径。

### 2.4 Engine 聚合层对外面（`Engine/cmake/对外接口.cmake`）

前缀 `<P> = ENGINE`。首句并入 EngineSystem（进而并入 EngineCore）：

```cmake
include("${CMAKE_CURRENT_LIST_DIR}/../EngineSystem/cmake/对外接口.cmake")

set(BYJY_ENGINE_OUT_LIB
    "${BYJY_ENGINE_SYSTEM_OUT_LIB};${BYJY_ENGINE_CORE_OUT_LIB}")   # = EngineSystem;EngineCore
set(BYJY_ENGINE_OUT_LIBDIR
    "${BYJY_ENGINE_SYSTEM_ROOT};${BYJY_ENGINE_CORE_ROOT}")
```

| 变量 | 取值 |
| --- | --- |
| `OUT_LIB` | **`EngineSystem;EngineCore`**（两个库的分号列表） |
| `OUT_LIBDIR` | `Engine/EngineSystem;Engine/EngineCore`（与 `OUT_LIB` 逐项对应） |
| `OUT_INC` | `${BYJY_ENGINE_SYSTEM_OUT_INC}`（已含 EngineCore 面） |
| `OUT_DEF` / `OUT_LINK` / `OUT_SYS` | 继承 `BYJY_ENGINE_SYSTEM_OUT_*` |

- **聚合层只做「面」的合并，不合并二进制产物**：`EngineSystem.lib` 与 `EngineCore.lib` 仍由两个子层各自产出，被上层一并链接，因此**不生成 `Engine.lib`**。
- 聚合层本体不产出静态库，故 `BYJY_ENGINE_ROOT` 不进入包含目录列表；`Engine/` 下只有 `EngineCore/`、`EngineSystem/` 两个子层与 `cmake/` 目录。

### 2.5 Test 与 Game 对外面

| 层 | 前缀 | 并入 | `OUT_LIB` | `OUT_INC` |
| --- | --- | --- | --- | --- |
| `Application/Test` | `BYJY_TEST_` | `include(../../../Engine/cmake/对外接口.cmake)` | `TestCore` | `${BYJY_ENGINE_OUT_INC}`（自有面由项目根承担） |
| `Application/Game` | `BYJY_GAME_` | 同上 | `GameCore` | `${BYJY_ENGINE_OUT_INC}` |

### 2.6 接入函数：`byjy_jieru_xiaceng()`

位置：`<层>/cmake/接入下层.cmake`。**EngineSystem / Engine / Test / Game 四份逐字节相同**（EngineCore 无下层，无此文件）。

```cmake
include("${CMAKE_CURRENT_SOURCE_DIR}/cmake/接入下层.cmake")
byjy_jieru_xiaceng(<下层对外接口文件> <对外接口变量前缀> <覆盖库路径变量名>)
```

行为：
1. 校验 `interface_file` 存在（否则 `FATAL_ERROR`），随后 `include()` 读入下层对外面。
2. 校验五项必需变量 `OUT_LIB` / `OUT_INC` / `OUT_DEF` / `OUT_LINK` / `OUT_SYS` 已定义；`OUT_LIBDIR` 为可选扩展项。
3. `OUT_LIB` 为空 → 打印「不产出静态库，跳过库定位」并返回（如聚合层被更上层接入时的语义）。
4. `OUT_LIBDIR` **逐项补齐**（缺省 = 本层目录）后，按 `OUT_LIB` **逐库**定位并建立导入目标。
5. 关键日志格式：`接入下层：<层名> → <库名>` ＋ `库文件：<绝对路径>`。

**为什么函数名是拼音**：CMake 命令名只能是 ASCII 标识符，写中文会在调用处直接报 `Parse error. Expected a command name, got unquoted argument`。

### 2.7 头快照函数：`byjy_tou_kuaizhao_gen()`

同一份 `接入下层.cmake` 内的第二个函数：

```cmake
byjy_tou_kuaizhao_gen(<结果变量> <导入目标名>)
```

行为：取 `<导入目标>` 的 `IMPORTED_LOCATION`（`<下层构建目录>/lib/<库名>.lib`）→ 上溯两级得构建目录 → 拼接 `/include` 即头快照根 → `PARENT_SCOPE` 写回结果变量；目录不存在即 `FATAL_ERROR`（提示先构建产出该快照的下层），**不静默退回源码树**。

**本版次的重要简化**：上一版次的两个映射函数 `byjy_kuaizhao_lujing()`（按路径前缀换算包含目录列表）与 `byjy_qiehuan_tou_kuaizhao()`（改写导入目标的 `INTERFACE_INCLUDE_DIRECTORIES`）**全部删除**，代之以本函数 ＋ 消费层把快照根列为**自身包含目录**（原理见 §4.7）。

### 2.8 各层 CMake 缓存变量（可覆盖入口）

| 层 | 变量 | 类型 | 语义 |
| --- | --- | --- | --- |
| `Engine/EngineSystem` | `BYJY_ENGINE_CORE_LIB_PATH` | `FILEPATH` | EngineCore 静态库路径；留空则自动探测 `Engine/EngineCore/out/build/*/lib/EngineCore.lib` |

## 3. 模块内部架构

### 3.1 文件组织

```
白银纪元/
├── Engine/
│   ├── CMakeLists.txt                     聚合层：project(Engine)，接入聚合面自检
│   ├── cmake/
│   │   ├── 对外接口.cmake                 BYJY_ENGINE_*（摊平两个子层）
│   │   └── 接入下层.cmake                 通用接入函数（四份逐字节相同的规范副本）
│   ├── EngineCore/
│   │   ├── CMakeLists.txt                 project(EngineCore)
│   │   └── cmake/
│   │       ├── 对外接口.cmake             BYJY_ENGINE_CORE_*
│   │       ├── 导出头快照.cmake           cmake -P 脚本：增量镜像头到 <构建目录>/include
│   │       └── ar_rsp_bom.ps1             归档响应文件补 BOM 的包装脚本（MSVC+Ninja）
│   └── EngineSystem/
│       ├── CMakeLists.txt                 project(EngineSystem)
│       └── cmake/
│           ├── 对外接口.cmake             BYJY_ENGINE_SYSTEM_*
│           └── 接入下层.cmake             （与 Engine/Test/Game 四份逐字节相同）
└── Application/
    ├── Test/
    │   ├── CMakeLists.txt                 project(Test)
    │   └── cmake/{对外接口.cmake,接入下层.cmake}
    └── Game/
        ├── CMakeLists.txt                 project(Game)
        └── cmake/{对外接口.cmake,接入下层.cmake}
```

**顶层没有 `CMakeLists.txt`，也没有 `CMakeSettings.json`** —— 这是本版次与上一版次的显著差异（上一版次顶层有统一编排；本版次删除，改为逐层独立构建）。

### 3.2 EngineCore 层 `CMakeLists.txt` 结构（自上而下）

1. **头部注释**：位置、依赖（无）、产物、用法、包含路径规则、层间契约文件、以及「本层不含 `接入下层.cmake`」的说明。

## 4. 模块设计/实现细节

### 4.1 归档响应文件 BOM 包装器（`ar_rsp_bom.ps1`）

- **背景**：Ninja 写出的归档响应文件（`*.rsp`）是 UTF-8 **无 BOM**，而 MSVC 的 `lib.exe` 在没有 BOM 时按系统 ANSI 代码页解读文件内容，中文对象名被解成乱码，归档阶段报 `LNK1181`。
- **做法**：把归档命令换成「先给响应文件补 BOM，再调用真实归档器」的包装脚本，使源文件名保持中文、bullet3 继续留在 EngineCore 内。
- **约束**：`CMAKE_CXX_CREATE_STATIC_LIBRARY` 必须在 `project()` **之后**设置，否则会被 `Platform/Windows-MSVC.cmake` 的默认值覆盖回去；只对 **Ninja** 生成器生效，避免影响 Visual Studio 生成器（其归档由 MSBuild 的 `Lib` 任务完成）。
- 包装器与 PowerShell 任一缺失时给出 `WARNING`（中文对象名的归档可能报 `LNK1181`）。

### 4.2 函数名为什么是拼音

`byjy_jieru_xiaceng` / `byjy_tou_kuaizhao_gen` 均为拼音。原因：**CMake 命令名只能是 ASCII 标识符**，写成中文会在调用处直接报 `Parse error. Expected a command name, got unquoted argument`。变量前缀 `BYJY_*` 同理（`BYJY` = 白银纪元）。

### 4.3 四份 `接入下层.cmake` 逐字节相同

`EngineSystem` / `Engine` / `Test` / `Game` 四层各有一份 `cmake/接入下层.cmake`，**内容必须逐字节一致**。`Engine/cmake/接入下层.cmake` 是规范副本，另三份从它复制。理由：这四个函数是层间契约的机器可读部分，任何一份漂移都会让同一接口在不同层产生不同行为；改动契约后须同步四份（可用哈希比对校验）。

`EngineCore` **没有**该文件 —— 它没有下层可接。

### 4.4 库定位三级策略（不回退编源码）

`byjy_jieru_xiaceng()` 对 `OUT_LIB` 中的**每一个库**依次执行：

| 顺序 | 条件 | 行为 |
| --- | --- | --- |
| ① | 覆盖变量非空 | 按元素下标与 `OUT_LIB` 逐项对应；元素个数须与 `OUT_LIB` **等长**，否则 `FATAL_ERROR`。指向的文件不存在 → `FATAL_ERROR`，**不静默降级** |
| ② | 覆盖变量为空 | 扫 `<该库所在层目录>/out/build/*/lib/<库名>.lib`，**取时间戳最新的一份** |
| ③ | 仍没有 | `FATAL_ERROR`，并给出「先构建产出该库的下层」的完整命令与「显式指定库路径」的替代命令 |

任何情况下都**不回退编译下层源码**：本函数只会 `include()` 接口文件（纯数据）与建立 `IMPORTED` 目标，不会 `add_subdirectory` 下层。

### 4.5 IMPORTED 导入目标与 INTERFACE 属性挂载

```cmake
if(NOT TARGET ${_lib_name})
    add_library(${_lib_name} STATIC IMPORTED GLOBAL)
endif()
set_target_properties(${_lib_name} PROPERTIES IMPORTED_LOCATION "${_lib_file}")
set_target_properties(${_lib_name} PROPERTIES
    INTERFACE_INCLUDE_DIRECTORIES "${_include_dirs}"
    INTERFACE_COMPILE_DEFINITIONS   "${_compile_defs}"
    INTERFACE_LINK_LIBRARIES        "${_link_libs};${_system_libs}")
```

- `GLOBAL` 让导入目标在本层整个构建树内可见（`EngineTestObjects`、`EngineTests` 等目标都要用它）。
- `INTERFACE_*` 三项就是「下层对外面」在 CMake 目标层的投影：上层目标 `target_link_libraries(... EngineCore EngineSystem)` 后，包含路径、宏、第三方库自动随之传递。
- 注意：`INTERFACE_INCLUDE_DIRECTORIES` 会以 `/external:I`（MSVC）或 `-isystem` 形式传给消费者，**其优先级低于消费者目标自身的 `-I`** —— 这正是 §4.7 头快照方案成立的前提。

### 4.6 对外头快照机制

- **脚本**：`Engine/EngineCore/cmake/导出头快照.cmake`，以 `cmake -P` 方式运行，参数 `SRC_ROOT` / `DST_ROOT` / `MIRROR_DIRS`（相对**项目根**的目录列表）。
- **语义**：把 `SRC_ROOT/<dir>` 下的头**增量镜像**到 `DST_ROOT/<dir>`；只复制内容有变化的头，**未变头不改变时间戳**，因此不会引起上层无谓重编。
- **镜像范围（本版次收窄）**：
  - EngineCore：`Engine/EngineCore/common`、`Engine/EngineCore/src`；
  - EngineSystem：`Engine/EngineSystem/common`、`Engine/EngineSystem/src`。
  - 第三方（`external/Json`、`external/glfw`、`external/bullet3/src`、`external/Sol2/include`、`external/Lua`）在外对面上是**独立的绝对路径条目**，不经过快照解析，因此**不必镜像** —— 相比上一版次省掉上千个第三方头的逐头复制。
- **路径形态**：镜像目录相对**项目根**保留完整层级，即 `<快照根>/Engine/EngineCore/...`；上层把对外面里的「项目根」条目换成快照根即可无缝解析同一个前缀。
- **常驻目标**：`EngineCoreIncludeSnapshot`、`EngineSystemIncludeSnapshot`（`ALL`），每轮构建都跑，脚本内部按内容比对决定是否落盘。
- **背景（为什么需要它）**：上层的包含目录若直接指向下层源码树，则与该层构建目录里的 `.lib` 无绑定关系；一旦「头已改、库未重建」，上层就会新头配旧库地编译链接。

### 4.7 头快照根作为消费层自身包含目录（关键修正）

**初版做法（已废弃）**：把「导入目标对外面里的项目根条目」替换成快照根。结果 `-I` 次序成了 **项目根 → 快照根**，实测 `compile_commands.json` 证实**快照被源码树旁路**。

**原因**：MSVC 下目标自身的包含目录（`-I`）**恒在**导入目标传递来的 `/external:I` **之前**；一旦项目根只剩「自身包含目录」这一个来源，它反而排到了快照之前。

**修正后做法**：**不动导入目标对外面**，而由消费层把下层快照根解析出来、作为**自身包含目录**列出，并排在项目根**之前**：

```cmake
byjy_tou_kuaizhao_gen(BYJY_CORE_SNAPSHOT   EngineCore)      # 解析并硬失败校验
byjy_tou_kuaizhao_gen(BYJY_SYSTEM_SNAPSHOT EngineSystem)
set(BYJY_APP_INC "${BYJY_CORE_SNAPSHOT}" "${BYJY_SYSTEM_SNAPSHOT}" "${BYJY_PROJECT_ROOT}")
```

由此 `接入下层.cmake` 的辅助函数由「两个映射函数」简化为一个 `byjy_tou_kuaizhao_gen(out_var, imported_target)`。

**验证**：`Application/Test/out/build/x64-Debug/compile_commands.json` 的 `-I` 序列为
`EngineCore 快照根 → EngineSystem 快照根 → 项目根 → 第三方(Sol2/Lua/Json/glfw/bullet3) → gtest`，快照不被旁路。

### 4.8 目录级 `CMAKE_CONFIGURE_DEPENDS`（任务<1> 实现）

**问题**：仅靠 `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)`，CMake 记录的是「GLOB 结果对应的文件集合」；增删文件虽会触发重配，但 VS 侧目录视图仍可能滞后，实践中表现为「需手动『重新生成缓存』」。

**做法**：在各层 GLOB 之后，把每个被 GLOB 的**源根目录**登记进目录属性：

```cmake
set_property(DIRECTORY APPEND PROPERTY CMAKE_CONFIGURE_DEPENDS
    "${PROJECT_ROOT_DIR}/src" ...)
```

**原理**：目录 mtime 变化（= 增删文件）被 ninja 记为 `build.ninja` 的依赖，构建前自动重跑配置并重扫 GLOB。

### 4.10 Test 层特殊处理：OBJECT 库与 ctest 中文路径退化

- **用例为何不并入静态库**：静态库里未被任何符号引用的 `.obj` 会被链接器丢弃，`TEST` 宏的静态注册随之丢失，用例便静默不跑。因此用例收进 `EngineTestObjects`（OBJECT 库），由 `EngineTests` 直接消费其 `.obj`。
- **`EngineTests.exe` 与 `TestLauncher` 的分工**：`TestLauncher` 只含纯逻辑主调（不拖图形库）；`引擎日志屏蔽.cpp` 编在 `EngineTests` 而非 `TestLauncher` —— 后者没有引擎包含路径。
- **ctest 注册**：因项目路径含中文，ctest 注册退化为「整体注册」而不是按用例逐个注册。

### 4.11 构建入口与本机环境坑位

- **构建入口**：顶层无编排；五层按 `Engine/EngineCore → Engine/EngineSystem → Engine → Application/Game / Application/Test` **严格串行**逐层配置与构建。
- **坑位一：配置期必须处于 UTF-8 代码页**。CMake 探测 `/showIncludes` 前缀时不带 `/utf-8`（按系统本地码页输出 GBK），而工程编译带 `/utf-8`（输出 UTF-8 字节），两侧逐字节不等 ⇒ ninja 匹配不到 `msvc_deps_prefix` ⇒ 头依赖全部丢失（`ninja -t deps` 为 `#deps 0`，改头不重编）。
- **坑位二：`chcp 65001` 必须在进入 VS 开发人员环境之后执行**。顺序颠倒不生效。
- **坑位三：`TMP`/`TEMP` 必须指向纯 ASCII 路径**。现象：只要请求调试信息即报 `cl: 命令行 error D8050 :无法执行 c1.dll: 未能将命令行放入调试记录中`，CMake 编译器探测阶段直接失败（`Check for working C compiler - broken`）。定位结论：与路径是否中文、控制台代码页均无关；二分 `/Zi`、`/Od`、`/RTC1`、`-MDd`、`-D_MBCS`、`/showIncludes` 后确认**只有带调试信息的编译会走该失败路径**；把 `TMP`/`TEMP` 指向纯 ASCII 目录后立即恢复。
- **坑位四：测试须在 `Application/Test` 目录下运行**（`Path_Check_Test` 的相对路径基准依赖工作目录）；`ctest` / `ninja` 走绝对路径（不在 Git Bash PATH 中）。

### 4.12 既有编译告警（C4005 / C4715 / C4828）

| 告警 | 位置 | 处置 |
| --- | --- | --- |
| `C4005` 宏重定义 | 第三方与平台头交叉 | 保持现状（非本项目引入） |
| `C4715` 并非所有控制路径都返回值 | `.../Quadtree/core/区块信息检索.hpp(72)` | 未处理（既有，非本版次引入） |
| `C4828` 文件包含在偏移处开始的无效字符 | 第三方/带 BOM 源文件 | 由 `/utf-8` 与 BOM 包装器收敛 |

`add_compile_options(/WX-)` 在各层统一关闭「警告即错误」，保证既有告警不阻断构建。

### 4.13 层间契约合规性检查清单

新增/修改层间关系时逐条核对：

1. `cmake/对外接口.cmake` 六个变量齐备；`OUT_LIB` 与 `OUT_LIBDIR` **等长**。
2. `OUT_INC` 首项是**项目根**（若该层有可被上层 include 的自有头）。
3. `cmake/接入下层.cmake` 四份**逐字节相同**（哈希比对）。
4. 新库名进入 `OUT_LIB` 后，覆盖变量（若有）须同步改为等长列表。
5. 新增对外包含目录时，同步该层 `MIRROR_DIRS`（若属自有头）与 `对外接口.cmake`。
6. 新增源根目录时，同步 `set_property(DIRECTORY ... CMAKE_CONFIGURE_DEPENDS)`。
7. 跨层 `#include` 一律写项目根相对全路径；不得出现 `src/...` 直包含。
8. 消费层须把下层快照根列为**自身包含目录且排在项目根之前**。
9. 各层保持独立可配置（不依赖上层 `add_subdirectory` 注入）。

## 5. 模块运行链路

### 5.1 配置期链路（以 Application/Test 为例）

```
cmake -S Application/Test -B Application/Test/out/build/x64-Debug -G Ninja
  ├─ project(Test)
  ├─ include(Application/Test/cmake/接入下层.cmake)        # 定义两个通用函数
  ├─ byjy_jieru_xiaceng(Engine/cmake/对外接口.cmake, BYJY_ENGINE, BYJY_ENGINE_LIB_PATH)
  │     ├─ include(Engine/.../对外接口.cmake)   → 连带并入 EngineSystem、EngineCore 两面
  │     ├─ 校验 OUT_LIB / OUT_INC / OUT_DEF / OUT_LINK / OUT_SYS 已定义
  │     ├─ OUT_LIB = "EngineSystem;EngineCore"；OUT_LIBDIR 逐项补齐
  │     ├─ 逐库定位：覆盖变量空 → 扫 <层>/out/build/*/lib/<库>.lib 取最新
  │     └─ add_library(<库> STATIC IMPORTED GLOBAL) + 挂 INTERFACE_*
  ├─ byjy_tou_kuaizhao_gen(BYJY_CORE_SNAPSHOT   EngineCore)    → <EngineCore 构建目录>/include
  ├─ byjy_tou_kuaizhao_gen(BYJY_SYSTEM_SNAPSHOT EngineSystem)  → <EngineSystem 构建目录>/include
  ├─ file(GLOB_RECURSE ... CONFIGURE_DEPENDS) + set_property(DIRECTORY ... CMAKE_CONFIGURE_DEPENDS)
  ├─ 按需建 TestCore / TestGui / TestLauncher / EngineTestObjects / EngineTests
  └─ set(CMAKE_EXPORT_COMPILE_COMMANDS ON) → 写出 compile_commands.json
```

任一子层的库或快照缺失，配置在此处**立即失败**并打印「请先构建该下层」的命令与替代方案。

### 5.2 构建期链路

```
cmake --build Application/Test/out/build/x64-Debug
  ├─ 若 build.ninja 的目录依赖 mtime 变化（增删文件）→ 自动重跑配置
  ├─ 编译 TestCore / TestGui / TestLauncher / EngineTestObjects
  │     包含根次序：[EngineCore 快照根, EngineSystem 快照根, 项目根, 第三方…]
  │     → Engine/EngineCore/... 命中快照、Engine/EngineSystem/... 命中快照、
  │       Application/Test/... 命中项目根
  ├─ 链接 EngineTests.exe：EngineCore + EngineSystem（导入目标，携带第三方与系统库）
  └─ 各子层构建时另跑 <层>IncludeSnapshot 常驻目标（增量镜像自有头）
```

### 5.3 增删文件后的重建链路

1. 在 `Engine/EngineCore/src/...` 下新增 `.cpp`（或删除、改名）。
2. 对该目录的 mtime 变化被 ninja 记录为 `build.ninja` 的依赖。
3. 直接执行 `cmake --build` → 打印 `Re-checking globbed directories...` → 自动重跑配置 → 重扫 `GLOB_RECURSE` → 新文件进入目标。
4. VS/IDE 侧目录视图随重配置刷新，**不再需要手动「重新生成缓存」**。

### 5.4 一次完整回归链路

1. **构建五层**（顺序固定；配置期须 UTF-8 代码页、`TMP`/`TEMP` 纯 ASCII）。
2. **运行** `Application/Test/out/build/x64-Debug/EngineTests.exe --selector=off --gtest_filter=*`（工作目录须在 `Application/Test`）。
3. **结果**：625 例 / 619 通过 / 2 跳过 / 4 失败；2 例跳过为按语义判定成立的既有引擎缺陷，4 例失败全在 `Config_Loader_Test`（在建功能缺口，见「项目架构.md」§11.2）。
4. **归因纪律**：本版次为纯构建改造（只影响编译期路径与链接；快照是源码头的逐字节副本），运行期行为零变化，故回归差异不得归因于构建改造。
