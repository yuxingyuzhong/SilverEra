## 1. 模块功能

### 1.1 模块是什么

「配置加载器 Config_Loader」负责把磁盘上的配置文件**按可信根目录批量、安全地**分发给引擎各业务模块。其核心思想是**事件驱动 + 路由文件 + 可信根**：

- **可信根目录**由外部经 `Belived_Root/Load` 事件登记（`route` 为索引目录、`config` 为配置目录）；Config_Loader 只处理可信根范围内的路由与配置。
- 磁盘上存在若干**路由文件**（JSON 对象），形如：

```json
{
  "dirty_mark": 12345678901234567890,
  "config_routes": [
    { "object": "Collision_Proxy", "config_path": "assets/config/collision.json", "dirty_mark": 987654321 }
  ]
}
```

  顶层 `dirty_mark` 记录「该路由文件本轮是否产出过配置投递」；`config_routes` 数组每条描述一条装载指令（`object` 目标对象、`config_path` 配置文件相对路径、可选 `dirty_mark` 条目标记）。
- Config_Loader 收到事件后：递归扫描可信根索引目录 → 逐个读取路由文件 → 逐条解析条目 → 做**路径越界安全检查**与**接收者存在性检查** → 读取目标配置文件 → 构造 `category="Config"`、`tag="Load"` 的事件 → 经 `Event_Terminal` 发送给目标对象。
- **脏标记**：仅当「真正读取配置且成功发送 `Config/Load`」后才写条目标记并回写路由文件；同一进程内再次加载同一「对象×文件」时按标记跳过，避免重复投递。

```
                      ┌──────────────────────────────────────────┐
  可信根/路由目录       │             Config_Loader                 │
  <index>/route/      │                                          │
  ├── route_a.json    │  route_load / event_process  事件入口      │
  │   {dirty_mark,    │  content_scan()     递归扫描索引目录       │
  │    config_routes} │  route_file_read()  读路由文件（对象包裹）  │
  ├── route_b.json    │  field_check<T>()   条目字段校验           │
  └── ...             │  path_safety_check() 逐节前缀安全检查      │
                      │  receiver_check()   接收者存在性检查       │
  <config>/xxx.json   │  object_config_deliver() 读配置 + 发事件   │
                      │  route_file_write() 回写脏标记            │
                      └───────────────┬──────────────────────────┘
                                      │ Event{Config, Load}
                                      ▼
                              Event_Broker 中转 → 目标对象接收入口
```

### 1.2 模块解决什么问题

- **配置装载路径统一化**：业务模块无需自己拼磁盘路径、自己判断"配置在哪"；只需注册事件订阅，等待 `Config/Load` 事件携带配置 JSON 送达。
- **配置变更免重编译**：新增/修改配置只需改 JSON 文件，不改代码、不重编译。
- **多对象配置集中装载**：一次可信根 `Load` 可装载该根下任意数量对象的配置，路由文件充当"装载清单"。
- **路径穿越攻击防护**：`config_path` 来自外部输入，可能被恶意写成 `../../../etc/passwd`。`path_safety_check` 强制 `config_path` 必须落在**对象配置目录**（`Config_Content::config`）之下（逐节前缀比对）且不含 `..`，并最终经 `detail::path_check` 验证存在且为可读普通文件。
- **权威来源约束**：缓存成员资格（`config_routes` / `config_files`）只能由 `Belived_Root` 链路建立，其余链路（`Route/load` / `Config/load` / `Subscriber/Call`）至多等值重写，外部无法借已登记目录写入其他对象缓存。
- **重复投递抑制（脏标记）**：`route_load` 先查路由文件**顶层标记**，命中即跳过；`config_file_process` 再查**条目标记**，命中即跳过。盐由进程内局部 `static` 随机生成（跨运行随机），上一轮遗留标记自动失效。
- **中文路径支持**：全链路路径经 `detail::string_to_path` / `detail::path_to_string`（UTF-8）承载，保证 Windows 下中文目录/文件名正常解析。
- **失败容错**：单个路由文件损坏、单条条目非法、单份配置读取失败均不会中断整体（记录日志后继续）。

### 1.3 模块服务谁

- **直接服务方（配置消费方）**：注册了事件订阅的模块——如EngineSystem 层 `Entity_Manager`（实体管理器）、`Effect`（效应系统）、`Prop_Distributor` 等，以及EngineCore 层 `Collision_Proxy` 等。它们在处理 `Config/Load` 事件时消费配置。
- **协作方**：
  - `Event_Terminal`（事件终端，`Engine/EngineCore/src/core/event/Event_Terminal/事件终端.h`）——事件接入、订阅、发送、`Subscriber/Check` 交互与答复路由。
  - `Event_Broker`（事件中转器）——经终端间接协作，负责订阅匹配与定向投递。
  - `Engine_Env`（引擎环境）——提供可执行文件目录作为基目录（`exe_dir_get()`）。
  - `Detail`（辅助算法）——`path_normalize` / `string_to_path` / `path_to_string` / `field_check<T>` / `path_check` / `hash_combine`。
  - `Logging`（日志系统）——全流程日志（`logger.info/warn/error`）。
- **不服务**：不直接读配置给调用方"返回值"——所有配置都通过事件送达（当前为同步 `send`）。

## 2. 模块提供接口

### 2.1 `Config_Content`（配置目录对）

```cpp
namespace engine
{
    //配置目录
    struct Config_Content
    {
        //索引目录
        std::filesystem::path route{};
        //配置目录
        std::filesystem::path config{};

        //默认等于重载
        bool operator==(const Config_Content&) const = default;

        //构造函数（path 入参）
        explicit Config_Content(const std::filesystem::path& route = {},
            const std::filesystem::path& config = {})
        {
            this->route  = detail::path_normalize(route);
            this->config = detail::path_normalize(config);
        }
        //构造函数（UTF-8 文本入参）
        explicit Config_Content(const std::string& route = {},
            const std::string& config = {})
        {
            this->route  = detail::path_normalize(detail::string_to_path(route));
            this->config = detail::path_normalize(detail::string_to_path(config));
        }
    };
}
```

| 项 | 说明 |
| --- | --- |
| 语义 | 一个「索引目录 + 配置目录」的**目录对**，作为可信根登记键与对象配置目录记录元素 |
| 规范化 | 两个构造函数**均经 `detail::path_normalize`**——统一分隔符、消尾部分隔符、消解 `.`/`..`。事件侧目录对来自 UTF-8 文本（`/` 分隔），磁盘侧来自 `lexically_relative`（Windows 为 `\`），不规范化则直接比较/哈希必不相等 ⇒ `count(content)` 永不命中 |
| 判等 | `operator==` 默认（两 `path` 逐节比较），配合规范化后即可跨来源比较 |
| `explicit` 构造 + 全默认参数 | 使其可默认构造但不可隐式转换；注意「全默认参数构造」会使 `unordered_map::operator[]` 不可用（须用 `insert_or_assign` / `insert`） |

配套两个 `namespace std` 特化（定义于 `配置加载器.h`）：

```cpp
namespace std
{
    //配置目录哈希特化
    template<> struct hash<engine::Config_Content>
    {
        std::size_t operator()(const engine::Config_Content& c) const noexcept
        {
            std::size_t seed = 0;
            engine::detail::hash_combine(seed, std::hash<std::filesystem::path>{}(c.route));
            engine::detail::hash_combine(seed, std::hash<std::filesystem::path>{}(c.config));
            return seed;
        }
    };

    //配置目录格式化特化（输出「索引[索引目录] 配置[配置目录]」，均为 UTF-8 文本）
    template<> struct formatter<engine::Config_Content>
    {
        constexpr auto parse(format_parse_context& ctx) { return ctx.begin(); }
        auto format(const engine::Config_Content& content, format_context& ctx) const
        {
            return std::format_to(ctx.out(), "索引[{}] 配置[{}]",
                engine::detail::path_to_string(content.route),
                engine::detail::path_to_string(content.config));
        }
    };
}
```

### 2.2 `Config_Loader` 类（声明顺序 = 实现顺序）

```cpp
namespace engine
{
    //配置加载器
    class Config_Loader
    {
    private:
        //配置可信加载根目录集合
        std::unordered_set<Config_Content> believed_roots;
        //对象配置目录记录（对象名 → 配置目录；供对象级加载与二次加载做路径安全检查）
        std::unordered_map<std::string, std::unordered_set<Config_Content>> config_routes;
        //对象配置文件路径缓存（对象名 → 配置文件路径集合）
        std::unordered_map<std::string, std::unordered_map<std::string, nlohmann::json>> config_files;
    public:
        //事件终端
        Event_Terminal event_terminal;
    private:
        //权限密钥
        int64_t acl_key = 0;
        //配置待发送对象
        std::unordered_set<std::string> waited_objects{};

    public:
        // ---- 公开门面 ----
        Config_Loader();                      // 构造函数
        ~Config_Loader() = default;           // 析构函数
        void attach(void);                    // 事件终端接入

    private:
        // ---- 组1 路径与文件 ----
        const std::filesystem::path base_dir_get(void) const;
        bool error_out(std::error_code& info) const;
        static bool path_prefix_check(const std::filesystem::path& prefix,
            const std::filesystem::path& target);
        void file_read(const std::filesystem::path& file_path, nlohmann::json& receiver) const;
        void content_scan(const std::string& route, std::vector<std::string>& receiver) const;
        bool path_safety_check(const Config_Content& content, const std::string& config_path) const;

        // ---- 组2 脏标记 ----
        static uint64_t run_salt_get(void);
        static uint64_t mark_make(const std::string& file_key);
        static uint64_t mark_make(const std::string& object, const std::string& config_path);

        // ---- 组3 路由文件读写 ----
        void route_file_read(const std::filesystem::path& file_path, nlohmann::json& mark,
            nlohmann::json& entries) const;
        bool route_file_write(const std::filesystem::path& file_path, uint64_t mark,
            const nlohmann::json& entries) const;

        // ---- 组4 配置投递 ----
        bool receiver_check(const std::string& object);
        bool object_config_deliver(const std::string& object, const std::string& config_path,
            uint64_t mark, nlohmann::json& entry);
        bool config_file_process(const std::string& config_path, nlohmann::json& entry,
            const std::string& object);

        // ---- 组5 路由文件处理 ----
        bool route_file_process(const Config_Content& content, const std::filesystem::path& file_path,
            const std::string& only_object, const std::vector<std::string>& only_files,
            bool deliver = true);

        // ---- 组6 配置加载 ----
        void config_load(const std::string& object, const std::vector<std::string>& paths = {});
        void route_load(const Config_Content& content, bool delivery = true,
            const std::string& object = {});

        // ---- 组7 缓存清除 ----
        void root_cache_clear(const Config_Content& root);

        // ---- 组8 事件分发 ----
        void event_process(std::shared_ptr<Event> evt);
    };
}
```

**声明顺序规则（上一版次重构）**：公开门面（构造 / 析构 / `attach`）置顶，其后的私有方法按「**被依赖者在依赖者前面**」与「**功能相近者相邻排列**」分成八组；**实现分散在 `core/` 下九个编译单元，每个单元内的函数顺序与本声明顺序一致**。拓扑自查覆盖：`content_scan ← error_out`（组1 内）、`mark_make ← run_salt_get`（组2）、`route_file_read ← file_read`（组3←组1）、`config_file_process ← mark_make, object_config_deliver`（组4←组2/组4内）、`route_file_process ← 组1–组4`（组5）、`route_load ← 组1/2/3/5`（组6）、`event_process ← route_load, config_load, root_cache_clear`（组8←组6/7）。

#### 2.2.1 成员变量

| 成员 | 类型 | 访问级别 | 说明 |
| --- | --- | --- | --- |
| `believed_roots` | `unordered_set<Config_Content>` | private | 已登记的可信根目录对集合。`Load` 登记、`Unload` 祛除；`Load` 已登记则告警跳过 |
| `config_routes` | `unordered_map<string, unordered_set<Config_Content>>` | private | **对象配置目录记录**：对象名 → 该对象的目录对集合（`route` = 该对象路由文件所在目录（相对基目录），`config` = 条目 `config_path` 的父目录）。天然满足"对象目录 ⊆ 可信根目录"，`Unload` 可用前缀匹配精确圈定 |
| `config_files` | `unordered_map<string, unordered_map<string, json>>` | private | **对象配置文件路径缓存**：对象名 → {配置文件路径 → 路由条目 JSON}。条目 JSON 承载条目标记；投递成功后**就地回写**（见 §4.4 根因 B） |
| `event_terminal` | `Event_Terminal` | **public** | 事件终端。公开可见以便宿主在必要时访问终端；生命周期随 Config_Loader 共存亡 |
| `acl_key` | `int64_t` | private | 权限密钥，构造时经 `event_terminal.acl_key_gen()` 生成，后续 `attach` / `send` / `interact` 均携带 |
| `waited_objects` | `unordered_set<string>` | private | **配置待发送对象**：接收者存在性检查失败的对象暂记于此；收到该对象的 `Subscriber/Call` 时**全量定向补投** |

#### 2.2.2 公开方法

| 方法签名 | 行为说明 |
| --- | --- |
| `Config_Loader()` | 生成权限密钥：`acl_key = event_terminal.acl_key_gen()`（`event_terminal` 成员先于函数体构造） |
| `~Config_Loader() = default` | 平凡析构；`event_terminal` 与 `acl_key` 随类消亡 |
| `void attach(void)` | **接入入口**：注册事件接收入口（`event_terminal->event_receiver_register([this](shared_ptr<Event> evt){ event_process(evt); })`）；随后订阅四事件接入中转站 |

`attach()` 订阅清单（上一版次事件契约）：

```cpp
vector<Event> needed_events{
    Event("", "", "Belived_Root", "Load"),     // 可信根加载（增量加载 + 即时投递）
    Event("", "", "Belived_Root", "Unload"),   // 可信根卸载（按前缀清缓存）
    Event("", "", "Route", "load"),            // 路由加载（事件指定目录）
    Event("", "", "Config", "load"),           // 对象配置加载（指定文件或全量）
};
event_terminal.attach("Config_Loader", needed_events, acl_key);
```

> **旧契约变更**：`Belived_Root/Add` 已**归并为 `Belived_Root/Load`**，`root_scan`（只建缓存不投递）一并移除；`Load` 分支执行 `route_load(root, true)`，即**加载可信根本身即产生一次配置投递**。

#### 2.2.3 私有方法分组索引

| 组 | 方法 | 一句话职责 |
| --- | --- | --- |
| 1 路径与文件 | `base_dir_get` | 委托 `Engine_Env::exe_dir_get()` 取基目录 |
| | `error_out` | 错误码非空则 `logger.error("{}", ec)` 并 clear，返回是否输出 |
| | `path_prefix_check` | 逐节比对：`prefix` 是否为 `target` 的目录前缀（空前缀恒 false） |
| | `file_read` | 打开并解析 JSON；失败统一置 `receiver = json()`（null 哨兵） |
| | `content_scan` | 递归扫描 `<基目录>/<route>`，收集普通文件绝对路径（UTF-8） |
| | `path_safety_check` | 路径安全检查（`..` 拦截 + 逐节前缀 + `detail::path_check`） |
| 2 脏标记 | `run_salt_get` | 进程内唯一盐（局部 static；随机数 + `steady_clock` 混合） |
| | `mark_make(file_key)` | 顶层标记 = 混合(盐, 路由文件路径) |
| | `mark_make(object, config_path)` | 条目标记 = 混合(盐, 对象名, 配置路径) |
| 3 路由文件读写 | `route_file_read` | 解出顶层 `dirty_mark` 与条目数组 `config_routes` |
| | `route_file_write` | 组装 `{dirty_mark, config_routes}` 并以 `dump(4)` 回写 |
| 4 配置投递 | `receiver_check` | 发 `Subscriber/Check` 并读答复 `existence`；失败记 `waited_objects` |
| | `object_config_deliver` | 读配置 → 剔 `dirty_mark` → `build`+`send` `Config/Load` → 成功后写 `entry["dirty_mark"]` |
| | `config_file_process` | 条目标记比对（命中则告警跳过）→ 调 `object_config_deliver` |
| 5 路由文件处理 | `route_file_process` | **唯一**路由文件处理入口：过滤 → 安全检查 → 写缓存 → 接收者检查 → 投递 → 就地表标记 → 回写 |
| 6 配置加载 | `config_load(object, paths)` | 对象级加载：`paths` 非空逐份、空则全量；未缓存告警 |
| | `route_load(content, delivery, object)` | 扫描目录 → 逐文件查顶层标记 → 命中跳过 → `route_file_process` |
| 7 缓存清除 | `root_cache_clear(root)` | 按双前缀剔除 `config_routes` / 按 config 前缀剔除 `config_files` |
| 8 事件分发 | `event_process(evt)` | 分派 `Subscriber/Call`、`Belived_Root{Load,Unload}`、`Route/load`、`Config/load` |

### 2.3 事件系统协作接口（本模块使用的外部接口摘录）

```cpp
namespace engine
{
    //事件（src/core/event/Event/事件.h）
    struct Event
    {
        Event(const std::string& sender_object, const std::string& target_object,
              const std::string& category, const std::string& tag);   // 对象标签构造
        std::string sender_object{};   // 事件发起者
        std::string target_object{};   // 事件目标
        std::string category;          // 事件大类
        std::string tag;               // 类内标签
        nlohmann::json config;         // 配置包
        bool operator==(const Event& other) const;
    };

    //事件终端（src/core/event/Event_Terminal/事件终端.h）
    class Event_Terminal
    {
    public:
        int64_t acl_key_gen(void);
        bool attach(const std::string& module_name, const std::vector<Event>& needed_events,
                    const int64_t& acl_key);
        bool interact(const std::shared_ptr<Event>& evt, std::shared_ptr<Event>& response,
                      const int64_t& acl_key);
        std::shared_ptr<Event> build(const std::string& sender, const std::string& target,
                                     const std::string& category, const std::string& tag);
```

## 4. 模块设计/实现细节

### 4.1 `event_process` 分派规则（组8）

```cpp
void Config_Loader::event_process(std::shared_ptr<Event> evt)
{
    //接收者答复（存在性检查的答复）
    if (evt->category == "Subscriber" && evt->tag == "Call") { /* 见 §4.5 补投 */ return; }

    //可信根目录修改
    if (evt->category == "Belived_Root")
    {
        // 载荷字段校验（route / config 均须为有效字符串）
        // 构造 root = Config_Content(route, config)；空则驳回
        if (evt->tag == "Load")   { /* 已登记 → 告警跳过；否则 insert + route_load(root, true) */ return; }
        else if (evt->tag == "Unload") { /* 未登记 → 告警跳过；否则 root_cache_clear(root) + erase */ return; }
    }

    //配置路由加载
    if (evt->category == "Route" && evt->tag == "load")
    {
        // 载荷：object / route / config；缺 object → 告警略过；缺 route/config → 驳回
        // 双判定：config_routes 无该 object → 告警；config_routes[object] 无该 content → 告警
        // 命中 → route_load(Config_Content(route_dir, config_dir), true, object)
        return;
    }

    //对象配置加载
    if (evt->category == "Config" && evt->tag == "load")
    {
        // 载荷：object（必需）+ files（可选文件清单）
        // 命中 → config_load(object, files)
        return;
    }
}
```

| 事件 | 行为 | 防御点 |
| --- | --- | --- |
| `Subscriber/Call` | 若发送者在 `waited_objects` 中：先判 `config_routes[sender]` 是否为空（空则告警驳回）；否则**逐目录对** `route_load(content, true, sender)`；最后 `waited_objects.erase` | `config_routes` 为空即驳回；只遍历**已登记**目录对 |
| `Belived_Root/Load` | 已登记 → `logger.warn` 跳过；否则 `believed_roots.insert(root)` + `route_load(root, true)`（**即时投递**） | 载荷 `route`/`config` 须经 `field_check<string>` 且非空 |
| `Belived_Root/Unload` | 未登记 → `logger.warn` 跳过；否则 `root_cache_clear(root)` + `believed_roots.erase(root)` | 同上 |
| `Route/load` | `config_routes.count(object)` + `config_routes[object].count(content)` 双判定，未登记即告警驳回；命中则 `route_load(content, true, object)` | 载荷 `object`/`route`/`config` 校验 |
| `Config/load` | 取 `object` 与可选 `files` 后 `config_load(object, files)` | 载荷 `object` 校验 |

- **载荷缺失一律驳回**：字段经 `detail::field_check<T>` 校验，缺失/类型错/空内容均记 `logger.error` 并 `return`。
- **`Config/load` 的 `files`**：`field_check<vector<string>>` 通过则逐项收集非空元素；未通过分支按源码既有的 else 处理（见 §6 遗留：空清单语义待裁定）。

### 4.2 脏标记方案（组2 + 组3，上一版次核心）

#### 4.2.1 路由文件格式（对象包裹）

```json
{
  "dirty_mark": 12345678901234567890,
  "config_routes": [
    { "object": "Collision_Proxy", "config_path": "assets/config/collision.json", "dirty_mark": 987654321 }
  ]
}
```

- 顶层 `dirty_mark`：`mark_make(路由文件路径)`——该路由文件本轮**是否产出过配置投递**。
- 条目 `dirty_mark`（可选字段）：`mark_make(object, config_path)`——该「对象×文件」本轮**是否已投递**。
- **配置文件本体不写标记**；投递时若正文为对象且含 `dirty_mark` 字段则**剔除**（脏标记不参与投递）。
- **字段名以源码为准**：条目数组字段为 `"config_routes"`（`route_file_read` / `route_file_write` / 测试夹具均用此名），非 `"routes"`。

#### 4.2.2 盐（`run_salt_get`）

```cpp
static const uint64_t salt = []
    {
        //以随机数生成器产生种子
        size_t seed = static_cast<size_t>(Random_Generator<int64_t>()());
        //混入当前时间，保证跨运行随机
        detail::hash_combine(seed, static_cast<size_t>(
            std::chrono::steady_clock::now().time_since_epoch().count()));
        return static_cast<uint64_t>(seed);
    }();
```

函数局部 `static` ⇒ **进程内唯一**、只生成一次；跨运行随机 ⇒ 上一轮遗留标记自动失效，无需收尾。

#### 4.2.3 写入时机（严格遵守口径）

- **只有「真正读取配置文件」且「成功发送 `Config/Load`」之后**才写条目标记（`object_config_deliver` 末尾 `entry["dirty_mark"] = mark;`）；
- 回写路由文件（连同顶层标记）也仅在 `route_file_process` 中 **`delivered == true`**（本轮至少成功投递过一次）时发生；
- **仅缓存路由（写 `config_routes`）绝不写任何脏标记**；
- `route_file_write` 把 `{ "dirty_mark": mark, "config_routes": entries }` 以 `dump(4)` 缩进四空格回写 → **配置资产目录需可写**。

#### 4.2.4 跳过逻辑（两处标记比对）

| 位置 | 比对 | 命中时行为 |
| --- | --- | --- |
| `route_load`（顶层标记） | `mark.is_number_unsigned() && mark.get<uint64_t>() == mark_make(文件路径)` | `logger.warn("Config_Loader::事件指定但无需重新加载的路由文件，已跳过: …")` 并 `continue` |
| `config_file_process`（条目标记） | `field_check<uint64_t>(entry,"dirty_mark") && entry["dirty_mark"].get<uint64_t>() == want_mark` | 若 `object` 非空则 `logger.warn("Config_Loader::事件指定但无需重新加载的文件，已跳过: …")`；返回 false（未投递） |

#### 4.2.5 第三方重置契约

动态改配置者只需把对应条目的 `dirty_mark` 改成任意随机值即可令其重载；若要让 `Route/load` 生效，还需把路由文件**顶层** `dirty_mark` 一并重置（`route_load` 的排除依据是顶层标记）。

### 4.3 路径前缀与安全检查（组1）

```cpp
//路径前缀判定（前缀是否为目标路径的目录前缀）
bool Config_Loader::path_prefix_check(const path& prefix, const path& target)
{
    //空前缀不构成有效前缀
    if (prefix.empty()) return false;
    //逐节比对
    auto prefix_it = prefix.begin();
    auto target_it = target.begin();
    for (; prefix_it != prefix.end(); ++prefix_it, ++target_it)
    {
        //若目标路径短于前缀则不构成前缀
        if (target_it == target.end()) return false;
        //若当前节不同则不构成前缀
        if (*prefix_it != *target_it) return false;
    }
    //所有节均匹配
    return true;
}
```

```cpp
//路径安全检查
bool Config_Loader::path_safety_check(const Config_Content& content,
    const std::string& config_path) const
{
    //安全转换中文路径
    path suspect_path = detail::string_to_path(config_path);
    //若待检查路径为空
    if (suspect_path.empty()) { logger.error("Config_Loader::配置路径为空"); return false; }

    //检查路径中是否存在危险跳转符号".."
    for (const auto& part : suspect_path)
        if (part.string() == "..")
        { logger.error("Config_Loader::存在非法父目录返回符号"); return false; }

    //逐节比对：标准配置目录必须为待检查路径的前缀
    auto standard = content.config.begin();
    auto suspect  = suspect_path.begin();
    for (; standard != content.config.end(); ++standard, ++suspect)
    {
        //若待检查路径短于标准路径则不可能包含标准路径
        if (suspect == suspect_path.end())
        { logger.error("Config_Loader::配置路径超出合法范围"); return false; }
        //若当前节不同则路径非法
        if (*standard != *suspect)
        { logger.error("Config_Loader::配置路径超出合法范围"); return false; }
    }

    //通用检查配置路径有效性（存在且为可读取的普通文件）
    if (!detail::path_check(base_dir_get() / suspect_path))
        return false;
    //若所有检查均通过
    return true;
}
```

| 检查项 | 说明 |
| --- | --- |
| 非空 | 空路径直接拒绝 |
| `..` 拦截 | 逐节比对 `part.string() == ".."`（**拼接前**的相对路径自身），防父目录跳转 |
| 逐节前缀比对 | **标准配置目录（`content.config`）必须为待检查路径的前缀**；等长或真包含均合法，仅前缀不符/更短才拒。这是相对旧版「硬编码 assets/config 两段」的改进——安全边界变为「扫描根目录对」，而非固定字面量 |
| 存在性 | `detail::path_check(base_dir_get() / suspect_path)` 校验存在且为可读普通文件 |
| `content` 语义 | 调用方传入的是**扫描根**（`Belived_Root` 链路为可信根目录对；`Route/load` 为事件给定目录对），安全检查强度不降低 |

```cpp
//目录递归扫描
void Config_Loader::content_scan(const string& route, vector<string>& receiver) const
{
    //构建实际扫描目录（UTF-8 文本经 string_to_path 转换，中文目录方可正确扫描）
    path actual_scan_dir = base_dir_get() / detail::string_to_path(route);
    //异常信息记录
    error_code ec;
    //构建递归查找迭代器
    auto it = recursive_directory_iterator(actual_scan_dir, ec);
    //若迭代器创建出现异常
    if (error_out(ec)) return;
    //递归查找文件
    for (; it != recursive_directory_iterator(); it.increment(ec))
    {
        //若迭代器创建/递增出现异常
        if (error_out(ec)) continue;
        //检查文件是否可读取
        if (it->is_regular_file(ec))
            //若可读取则记录文件路径（UTF-8）
            receiver.push_back(detail::path_to_string(it->path()));
        //若文件查询过程中发生异常
        if (error_out(ec)) continue;
    }
}
```

| 项 | 说明 |
| --- | --- |
| 递归性 | 深度优先递归子目录；默认不跟随符号链接目录（防循环） |
| **中文路径修复** | 旧实现把 UTF-8 路径文本直接 `base_dir_get() / route` 拼接（未过 `string_to_path`）⇒ 中文目录扫描一律失败；现改为 `base_dir_get() / detail::string_to_path(route)` |
| 错误策略 | 迭代器构造失败 → 整体 return；遍历中错误 → 跳过该项继续 |
| 收集内容 | 全部普通文件（**不过滤扩展名**）；非 JSON 文件在 `file_read` 时 parse_error 被捕获后跳过 |
| 路径形式 | `it->path()` 经 `detail::path_to_string` 得 UTF-8 绝对路径 |


### 4.4 `route_file_process`（组5：唯一入口 + 脏标记就地回写）

```cpp
//单份路由文件处理（按可选过滤条件处理其中条目；deliver 表示是否投递配置）
bool Config_Loader::route_file_process(const Config_Content& content, const path& file_path,
    const std::string& only_object, const std::vector<std::string>& only_files, bool deliver)
{
    json mark = json();  json entries = json();
    //读取路由文件
    route_file_read(file_path, mark, entries);
    //若路由条目格式非法
    if (!entries.is_array()) { logger.error("Config_Loader::当前路由文件内容格式非法"); return false; }

    //本轮是否真正投递过配置
    bool delivered = false;
    //逐条读取路由条目
    for (auto& entry : entries)
    {
        //若目标字段无效
        if (!detail::field_check<string>(entry,"object") ||
            !detail::field_check<string>(entry,"config_path"))
        { /* 四条 error 日志（不存在 / 非字符串 / 无内容） */ continue; }

        const std::string object      = entry["object"];
        const std::string config_path = entry["config_path"];

        //若存在对象过滤条件且不匹配则跳过
        if (!only_object.empty() && object != only_object) continue;
        //若存在文件过滤条件且不匹配则跳过
        if (!only_files.empty() && std::ranges::find(only_files, config_path) == only_files.end()) continue;

        //若路径安全检查失败则略过该配置文件
        if (!path_safety_check(content, config_path)) continue;

        //推导对象自身目录对（路由文件所在目录 + 配置文件所在目录）
        const Config_Content object_content(
            file_path.parent_path().lexically_relative(base_dir_get()),
            detail::string_to_path(config_path).parent_path());
        //记录对象配置目录与配置文件条目（内存缓存的唯一写入点）
        config_routes[object].insert(object_content);
        config_files[object][config_path] = entry;

        //若非投递模式则略过投递
        if (!deliver) continue;

        //接收者存在性检查（未接入则取消其配置信息传递）
        if (!receiver_check(object))
        { logger.warn("Config_Loader::接收者尚未接入事件中转站，已取消配置信息传递: {}", object); continue; }

        //处理文件并获取投递标记
        delivered = config_file_process(config_path, entry, object);
        //投递成功后刷新内存缓存副本：缓存里存的是投递前的条目快照，脏标记只写进了
        //循环内的 entry（并随路由文件落盘），不回写会让同一进程内再次加载重复投递
        if (delivered)
            config_files[object][config_path] = entry;
    }

    //仅当本轮真正投递过配置才回写路由文件（仅缓存路由不加脏标记）
    if (delivered)
        route_file_write(file_path, mark_make(detail::path_to_string(file_path)), entries);
    //返回本轮是否投递过配置
    return delivered;
}
```

**上一版次关键修复（根因 B —— 脏标记就地回写缓存副本）**：`config_files[object][config_path] = entry;` 在**投递之前**写入，写入的是条目**快照**；`object_config_deliver` 把脏标记写进的是**循环内的 `entry`**（并随 `route_file_write` 落盘），缓存那份副本若无标记，则同一进程内再次 `Config/load` 会判「未命中脏标记」而**重复投递**。修复：投递成功后就地回写 `config_files[object][config_path] = entry;`。

| 项 | 说明 |
| --- | --- |
| **唯一入口** | `config_load`（两条重载）/ `route_load` / `event_process`（`Subscriber/Call`）全部复用本函数，避免重复实现 |
| 缓存唯一写入点 | `config_routes` / `config_files` 的写入全部收敛于此；非投递模式（`deliver == false`）写缓存后 `continue`，`delivered` 恒假 ⇒ 不回写磁盘 |
| 对象自身目录对 | `config_routes[对象]` = 「路由文件所在目录（`lexically_relative(base_dir_get())`）+ 条目 `config_path` 父目录」；天然满足"对象目录 ⊆ 可信根目录"，`Unload` 可用前缀匹配精确圈定 |
| 安全检查边界 | `path_safety_check(content, …)` 以**扫描根** `content` 为界 |
| 过滤能力 | `only_object` / `only_files` 使外部无法借已登记目录写入其他对象缓存 |

```cpp
//接收者存在性检查（向中转站询问目标对象是否接入）
bool Config_Loader::receiver_check(const std::string& object)
{
    //构造查看事件
    auto evt = event_terminal.build("Config_Loader", object, "Subscriber", "Check");
    //若事件构造失败
    if (evt == nullptr) { waited_objects.insert(object); return false; }

    //构造中转站答复接收事件
    std::shared_ptr<Event> response;
    //查询目标对象是否存在并获取答复
    if (!event_terminal.interact(evt, response, acl_key) || response == nullptr)
    { waited_objects.insert(object); return false; }

    //若答复对象存在性字段无效或目标不存在
    if (!detail::field_check<bool>(response->config, "existence") ||
        !response->config["existence"].get<bool>())
    { waited_objects.insert(object); return false; }
    else return true;
}
```

| 项 | 说明 |
| --- | --- |
| 答复来源 | 读**答复事件** `response->config["existence"]`（旧实现误读请求事件的 `config["existence"]`，且未校验 `response` ⇒ 必抛 `type_error`；上一版次已修） |

| 双通道兜底（历史实现细节） | 中转站 `Subscriber/Response` 事件不携带被查对象标识，早期版本曾按"最近一次检查"关联；现版本直接以 `interact` 出参答复为准 |

```cpp
//对象配置投递（读配置 → 发 Config/Load → 写条目标记）
bool Config_Loader::object_config_deliver(const std::string& object, const std::string& config_path,
    uint64_t mark, json& entry)
{
    //格式化为绝对文件路径
    path absolute_config_path = base_dir_get() / detail::string_to_path(config_path);
    json config_data;
    //读取配置文件
    file_read(absolute_config_path, config_data);
    //若配置数据读取失败
    if (config_data.is_null())
    { logger.error("Config_Loader::配置读取失败");
      logger.error("失败路径:{}", detail::path_to_string(absolute_config_path)); return false; }

    //剔除可能存在的脏标记字段（脏标记不参与投递）
    if (config_data.is_object()) config_data.erase("dirty_mark");

    //构造配置事件
    auto evt = event_terminal.build("Config_Loader", object, "Config", "Load");
    //若配置事件构造失败
    if (evt == nullptr) { logger.error("Config_Loader::配置事件构造失败"); return false; }

    //填充配置数据
    evt->config = config_data;
    //发送配置事件（按已注册通道单/多事件二选一）
    if (event_terminal->interface_check(Interface_ID::EVENT_SENDOR))
        event_terminal.send(evt, acl_key);
    else if (event_terminal->interface_check(Interface_ID::EVENTS_SENDOR))
        event_terminal.send(vector<shared_ptr<Event>>{evt}, acl_key);
    else { logger.error("Config_Loader::配置事件发送失败"); logger.error("配置工作无法完成"); return false; }

    //投递成功后写入条目标记（只有真正阅读配置并发送配置才写脏标记）
    entry["dirty_mark"] = mark;
    //报告事件信息
    logger.info("Config_Loader::已发送配置事件: {}", object);
    //返回投递成功
    return true;
}
```

```cpp
//单份配置文件处理
bool Config_Loader::config_file_process(const string& config_path, json& entry, const string& object)
{
    //计算该「对象×文件」本轮标记
    const uint64_t want_mark = mark_make(object, config_path);
    //脏标记命中表示本轮已加载过该对象该文件
    const bool marked = detail::field_check<uint64_t>(entry, "dirty_mark") &&
        entry["dirty_mark"].get<uint64_t>() == want_mark;
    //若本轮已加载过
    if (marked)
    {
        //若为事件明确指定则发出警告日志
        if (!object.empty())
            logger.warn("Config_Loader::事件指定但无需重新加载的文件，已跳过: {}", config_path);
        return false;
    }
    //若配置投递成功 / 失败
    if (!object_config_deliver(object, config_path, want_mark, entry)) return false;
    else return true;
}
```

| 项 | 说明 |
| --- | --- |
| 投递事件 | `build("Config_Loader", object, "Config", "Load")`——`sender_object` 为 `Config_Loader`、`target_object` 为目标对象；接收方按定向投递接收 |
| 通道二选一 | **优先单事件通道**（`EVENT_SENDOR`），否则批量通道（`EVENTS_SENDOR`）；两者皆无则报错。这是在Test 层曾出现"`send({evt}, acl_key)` 花括号初始化列表被 MSVC 解析为单事件重载"歧义后的显式通道判定 |
| 脏标记写入 | **仅在 `send` 成功之后**（本函数末尾）写 `entry["dirty_mark"]` |
| 配置内容 | 投递前剔除 `dirty_mark` 字段（若配置本体为对象） |

### 4.6 配置加载（组6）

```cpp
//配置加载 —— 对象配置加载
void Config_Loader::config_load(const std::string& object, const vector<string>& paths)
{
    //查找目标对象的配置文件缓存
    auto file_caches = config_files.find(object);
    //若目标对象尚无配置记录
    if (file_caches == config_files.end())
    { logger.error("Config_Loader::目标对象尚无配置记录: {}", object); return; }

    //若指定加载文件集非空
    if (!paths.empty())
    {
        for (const auto& path : paths)
        {
            auto file_cache = file_caches->second.find(path);
            //若目标文件已缓存
            if (file_cache != file_caches->second.end())
                config_file_process(path, file_cache->second, object);
            //若目标文件未缓存
            else
                logger.warn("Config_Loader::目标配置文件未缓存\n请更新配置路由索引再次尝试");
        }
    }
    //若指定加载文件集为空
    else
    {
        //全量加载缓存配置数据
        for (auto& file : file_caches->second)
            config_file_process(file.first, file.second, object);
    }
}
```

| 项 | 说明 |
| --- | --- |
| 成员资格前置 | `config_files.find(object)` 无记录即返回（对象从未登记 ⇒ 不加载） |
| 逐份 vs 全量 | `paths` 非空逐份；为空则**全量**遍历该对象缓存条目（**上一版次落地**：「缺省 = 该对象全部文件」在 `config_load` 内已实现为该 else 分支） |
| 未缓存告警 | 指定文件不在缓存中时 `logger.warn`（提示更新路由索引） |
| 缓存引用 | `config_load` 传入的本就是缓存引用（`file` / `file_cache->second`），`object_config_deliver` 写 `entry` 时**已直接落到缓存上**——故本路径无需额外回写 |

```cpp
//配置路由加载（事件指定配置目录）
void Config_Loader::route_load(const Config_Content& content, bool delivery, const std::string& object)
{
    vector<string> route_files{};
    //扫描路由文件（绝对路径）
    content_scan(detail::path_to_string(content.route), route_files);
    //若未扫描到可用路由文件
    if (route_files.empty()) { logger.error("Config_Loader::未检测到任何路由文件"); return; }

    //逐份处理路由文件
    for (const auto& route_file : route_files)
    {
        const path file_path = detail::string_to_path(route_file);
        json mark = json();  json entries = json();
        //读取路由文件（查阅路由文件头）
        route_file_read(file_path, mark, entries);
        //若路由条目格式非法
        if (!entries.is_array())
        { logger.error("Config_Loader::当前路由文件内容格式非法"); continue; }
        //计算该路由文件本轮标记
        const uint64_t want_mark = mark_make(detail::path_to_string(file_path));
        //若路由文件头命中则无需重新加载
        if (mark.is_number_unsigned() && mark.get<uint64_t>() == want_mark)
        { logger.warn("Config_Loader::事件指定但无需重新加载的路由文件，已跳过: {}", detail::path_to_string(file_path)); continue; }
        //重新解析该路由文件并更新对象配置文件路径缓存
        route_file_process(content, file_path, object, {}, delivery);
    }
}
```

| 项 | 说明 |
| --- | --- |
| 顶层标记抑制 | `route_load` 先查路由文件顶层标记，命中即跳过（增量语义，非重建） |
| 重复读取 | `route_load` 会先 `route_file_read` 判标记，再交 `route_file_process`（内部**再次** `route_file_read`）——换取零重复实现，代价可忽略 |
| 过滤 | `only_object = object`（`delivery` 决定是否投递；可信根 `Load` 传 `true`，历史 `root_scan` 的 `false` 语义已随 `root_scan` 移除） |

### 4.7 缓存清除（组7）

```cpp
//可信根目录缓存清除（按目录前缀清除该根下的对象缓存）
void Config_Loader::root_cache_clear(const Config_Content& root)
{
    //清除对象配置目录缓存
    for (auto it = config_routes.begin(); it != config_routes.end();)
    {
        //剔除位于该可信根目录下的配置目录（路由目录与配置目录均需以可信根对应目录为前缀）
        std::erase_if(it->second, [&root](const Config_Content& content)
            { return path_prefix_check(root.route, content.route) &&
                     path_prefix_check(root.config, content.config); });
        //若该对象已无配置目录记录则删除对象条目
        if (it->second.empty()) it = config_routes.erase(it); else ++it;
    }

    //清除对象配置文件缓存
    for (auto it = config_files.begin(); it != config_files.end();)
    {
        //剔除位于该可信根配置目录下的配置文件（配置文件路径需以可信根配置目录为前缀）
        std::erase_if(it->second, [&root](const auto& pair)
            { return path_prefix_check(root.config, detail::string_to_path(pair.first)); });
        //若该对象已无配置文件记录则删除对象条目
        if (it->second.empty()) it = config_files.erase(it); else ++it;
    }
}
```

| 项 | 说明 |
| --- | --- |
| 双前缀（目录） | `config_routes` 剔除要求 `route` **且** `config` 同为该可信根对应目录的前缀 |
| 单前缀（文件） | `config_files` 剔除按键（`config_path` 转 path）以 `root.config` 为前缀 |
| 空条目回收 | 两侧清空后移除对象键 |

### 4.8 防御机制核查结论

| 链路 | 防御点 |
| --- | --- |
| `Route/load` | `config_routes.count(object)` + `config_routes[object].count(content)` 双判定，未登记即告警驳回 |
| `Subscriber/Call` | `config_routes[sender]` 为空即驳回；非空只遍历**已登记**目录对调 `route_load` |
| `Config/load` | `config_load` 先 `config_files.find(object)`，无记录即返回；逐文件未缓存仅告警 |
| `route_file_process` | 以 `only_object` / `only_files` 过滤，外部无法借已登记目录写入其他对象缓存 |

⇒ 缓存**成员资格**只能由 `Belived_Root` 链路决定，其余链路至多做等值重写。

### 4.9 路径规范化与目录对形态

- 事件侧目录对来自 UTF-8 文本（`/` 分隔），磁盘侧来自 `lexically_relative`（Windows 为 `\`）；不规范化则直接比较/哈希必不相等 ⇒ `count(content)` 永不命中。故 `Config_Content` 构造统一走 `detail::path_normalize`，使两侧落入同一形态。
- `path_safety_check` 的**逐节**比较基于规范化后的 `path`，不受分隔符差异影响。
- **对象目录推导依赖磁盘布局**：`route` = 路由文件所在目录、`config` = `config_path` 父目录；故 `Route/load` 载荷必须与磁盘布局推出的目录对**完全一致**才能命中（分隔符差异已由 `path_normalize` 吸收）。

### 4.10 设计决策与理由

| 决策 | 理由 |
| --- | --- |
| 事件驱动（无 `act()`） | 模块与配置源解耦：模块只声明"我要 Config 事件"，不知配置从哪来；加载时机由事件决定（可信根登记、路由加载、对象加载） |
| 可信根集合（`believed_roots`） | 把"权威来源"显式化为可登记集合，缓存成员资格只能由其建立，形成清晰的安全边界 |
| 相对路径 + 基目录拼接 | 配置与可执行文件同目录部署（`exe_dir`），便于整包拷贝迁移 |
| 运行盐脏标记 | 以「进程内随机盐」使上一轮遗留标记自动失效，无需收尾；顶层 + 条目双层标记分别抑制"整份路由文件"与"单对象单文件"的重复 |
| 脏标记就地回写缓存 | 避免同一进程内二次加载重复投递（根因 B） |
| 部分失败容忍 | 单条条目 / 单份配置失败不影响整体 |
| 全程不抛异常（文件系统用 `ec` 重载） | 健壮性优先，异常只在 `file_read` 内局部捕获 |
| 9 个编译单元 | 按「被依赖者在前、功能相近相邻」分组拆分，声明与实现同序，便于阅读与并发维护 |

### 4.11 易踩坑点汇总

1. **路由文件必须是对象包裹格式** `{ "dirty_mark": …, "config_routes": [ … ] }`：旧数组格式会被判"内容格式非法"并跳过。
2. **`content_scan` 不过滤扩展名**：索引目录内任何普通文件都被当路由文件解析（解析失败有日志噪音，不致命）。
3. **`config_path` 必须位于对象配置目录之下**：路径安全检查以 `content.config` 为前缀边界；绝对路径/越界路径被拒。
4. **`..` 会被拒绝**（即使前缀合法）。
5. **JSON null 配置文件被判读取失败**：`file_read` 失败哨兵是 null。
6. **只有真正投递才写标记**：仅缓存路由（`deliver == false`）不写任何标记，也不回写磁盘。
7. **`Route/load` 的排除依据是路由文件顶层标记**：若第三方只重置条目标记，`Route/load` 仍会被跳过（需同时重置顶层标记）。
8. **脏标记不参与投递**：配置本体若含 `dirty_mark` 字段会在投递前被剔除。
9. **配置资产目录需可写**：路由文件会被运行时回写（`dump(4)` 缩进四空格）。
10. **`error_out` 已走日志系统**：不再输出到 `std::cout`（`using std::cout/endl` 已删除）。
11. **通道二选一**：`object_config_deliver` 优先单事件通道；宿主只注册批量通道时会走批量分支，二者都未注册即失败。
12. **接收者未接入会取消投递**：对象须先接入事件中转站（`Subscriber/Check` 答复 `existence=true`），否则配置被挂起待 `Subscriber/Call` 补投。
13. **`Config_Content` 全默认参数构造**：`unordered_map::operator[]` 对其不可用，须用 `insert_or_assign` / `insert`。
14. **中文路径必须 UTF-8**：路由文件本身与 `config_path` 字段中文须 UTF-8；`content_scan` 拼接前必须过 `string_to_path`。
15. **`waited_objects` 补投为全量**：`Subscriber/Call` 到达时对该对象**全部已登记目录对**强制补投（忽略脏标记），投递成功后照常写标记（幂等）。

## 5. 模块运行链路

### 5.1 完整调用时序（宿主接入 + 可信根加载）

```
[启动] 主程序
  │
  ├─ 创建 Config_Loader loader;
  │    └─ 构造函数：acl_key = event_terminal.acl_key_gen()   （PCG32 生成密钥）
  │
  ├─ 宿主完成事件中转站接线（attach_handler / event_receiver / event_sender / event_interactor 注册）
  │
  ├─ loader.attach();
  │    ├─ event_receiver_register([this](evt){ event_process(evt); })
  │    └─ event_terminal.attach("Config_Loader",
  │           {Belived_Root/Load, Belived_Root/Unload, Route/load, Config/load}, acl_key)
  │
  ├─ 各业务模块注册订阅并 attach（等待 Config/Load）
  │
  ├─ 宿主发送 Belived_Root/Load（route=索引目录, config=配置目录）
  │    └─ loader.event_process → believed_roots.insert(root) → route_load(root, true)
  │          ├─ content_scan(root.route)            扫描索引目录下全部普通文件
  │          ├─ 逐路由文件 route_file_read           取顶层标记 + 条目数组
  │          │     ├─ 顶层标记命中 → warn 跳过
  │          │     └─ route_file_process(root, file_path, "", {}, true)
  │          │           ├─ 逐条目：field_check → path_safety_check
  │          │           ├─ 写 config_routes[object] / config_files[object][config_path]
  │          │           ├─ receiver_check(object)      未接入 → warn 并挂起
  │          │           └─ config_file_process → object_config_deliver
  │          │                 ├─ file_read 读配置 → 剔 dirty_mark
  │          │                 ├─ build("Config_Loader", object, "Config", "Load")
  │          │                 ├─ send（单/多通道）→ Event_Broker → 目标对象
  │          │                 └─ 成功 → entry["dirty_mark"] = mark
  │          │           └─ 投递成功 → 就地回写 config_files[object][config_path] = entry
  │          │           └─ delivered → route_file_write（回写顶层标记 + 条目）
  │          └─ 全部路由文件处理完 → route_load 返回
  │
  └─ 后续正常游戏循环（配置已就位）；如有对象后接入 → 其 Subscriber/Call 触发全量补投
```

### 5.2 事件分派速查

```
event_process(evt)
├─ Subscriber/Call     → waited_objects 命中 → 逐 config_routes 目录对 route_load(…, true, sender)
├─ Belived_Root/Load   → 已登记则跳过；否则 insert + route_load(root, true)         （即时投递）
├─ Belived_Root/Unload → 未登记则跳过；否则 root_cache_clear + erase
├─ Route/load          → config_routes 双判定 → route_load(事件目录对, true, object)
└─ Config/load         → config_load(object, files)
```

### 5.3 脏标记状态机

```
                    [未标记] ──── 真正读配置且成功 send ────► [条目标记 = mark]
                        ▲                                        │
                        │ 第三方改写 dirty_mark / 换新进程（盐变）  │ 同进程再次 Config/load
                        └────────────────────────────────────────┘
                                （命中 → warn 跳过，不重复投递）

路由文件顶层： [未标记] ── 本轮至少投递一次 ──► [顶层标记 = mark]
                        ▲                          │
                        │ 第三方重置顶层标记 / 换新进程 │ Route/load 再次请求
                        └──────────────────────────┘（命中 → warn 跳过整份路由文件）
```

### 5.5 异常与失败链路

| 失败点 | 处理 | 影响范围 |
| --- | --- | --- |
| 索引目录不存在/不可访问 | `content_scan` 迭代器构造错误 → `error_out` → return | 该次 `route_load` 无路由可扫 |
| 路由文件非对象 / 非 JSON / 语法错误 | `route_file_read` 置 `entries = json()` → 非数组校验拦截 | 跳过该路由文件 |
| 条目缺字段/类型错/空值 | `field_check<string>` 三段校验拦截 | 跳过该条条目 |
| 路径越界（含 `..`、非对象配置目录前缀、文件不存在） | `path_safety_check` 拦截 | 跳过该条条目 |
| 目标配置文件不存在/解析失败 | `file_read` → null → `is_null` 拦截 | 跳过该条条目 |
| 接收者未接入 | `receiver_check` false → 记 `waited_objects` + warn | 取消该对象配置传递（待 `Subscriber/Call` 补投） |
| 配置事件构造失败 | `build` 返回 nullptr → error | 该条条目不投递 |
| 发送通道未注册 | `interface_check` 两通道皆 false → error | 该条条目不投递 |
| 路由文件回写失败 | `route_file_write` 打开失败 → error | 磁盘标记未更新（内存缓存已就地回写，仍可正确判重） |

### 7.2 遗留与风险

1. **`Config/load` 空 `files` 语义**：`config_load` 的 else 分支已实现「空清单 ⇒ 全量加载」，但 `event_process` 对 `files` 字段的处理在字段缺失分支存在既有 else 写法（源码原样搬运），重开发时建议显式统一为「缺省 = 该对象全部文件」。
2. **`send` 重载歧义**：早期用 `send({evt}, acl_key)` 花括号初始化列表曾被 MSVC 解析为单事件重载；上一版次已改为**按接口注册情况显式二选一**（优先单事件通道）。
3. **`Belived_Root/Load` 服从路由文件头脏标记**：因缓存链路自身不回写头标记，该标记只可能由 `Route/load` 的投递产生；若某路由文件在 `Load` 之前已被 `Route/load` 投递过，则 `Load` 会跳过它（增量语义，非重建）。
4. **对象目录推导依赖磁盘布局**：`Route/load` 载荷必须与磁盘布局推出的目录对完全一致才能命中。
5. **`content_scan` 为递归扫描**：可信根下任意深度的路由文件都会被收录；同一对象跨多目录时会形成多个目录对（集合语义，已支持）。
6. **根因 A/B 备忘录**：A = 事件标签不一致（实现归并 `Add`→`Load` 而测试仍发 `Add`，导致可信根从未登记、投递数 0），已由Test 层适配修复；B = 脏标记未回写缓存副本（导致用例 4 多投一次），已由 `route_file_process` 就地回写修复。
