## 二、模块功能介绍

### 2.1 模块定位

「构建与源文件清单」是 Test 层的**构建期基础设施**。它不产出任何运行时逻辑，只回答五个问题：

1. **本层如何被配置**：`Application/Test` 是一个**独立的 CMake 工程**（`project(Test LANGUAGES C CXX)`），用 Ninja（单配置生成器）配置成 `x64-Debug` / `x64-Release` 两棵构建树。
2. **本层如何与下层交接**：以 `cmake/接入下层.cmake` 的 `byjy_jieru_xiaceng()` **两次接入**——先接 `Engine` 聚合面（取得 `EngineSystem.lib + EngineCore.lib`），再接 `Renderer` 的 `RendererCore.lib`；**只链接下层已构建的静态库，绝不 `add_subdirectory` 拉入下层源码**。
3. **本层如何拿到「与下层库同版次」的头**：用 `byjy_tou_kuaizhao_gen()` 为 `EngineCore` / `EngineSystem` / `RendererCore` 三个导入目标各解析一个**头快照根**，连同项目根、本层根组装成 `BYJY_APP_INC`，供各目标 `target_include_directories`。
4. **源文件如何进入目标**：`file(GLOB_RECURSE ... CONFIGURE_DEPENDS)` 扫描 `src/`，结果经**共享清单同步工具**落成三份显式 `源文件列表_*.cmake`（`target_sources` 形式）；清单是这些源/头的**唯一加入点**，`add_library` / `add_executable` 不再传它们。
5. **产物如何落地**：本层产出 `EngineTests.exe`（全工程唯一可执行文件，落本层根目录），以及 `TestLauncher.lib`、`TestGui.lib`、`EngineTestObjects`（OBJECT 库，无独立产物）与条件产出 `TestCore.lib`；各静态库落 `<构建树>/lib/`。

### 2.2 职责边界

| 属于本模块 | 不属于本模块 |
| --- | --- |
| `Application/Test/CMakeLists.txt`、`源文件列表_*.cmake`、`CMakeSettings.json`、`.gitignore` | `Application/Test/src/` 下的业务源码与用例语义（见同层各源码文档） |
| Test 层的目标划分、依赖接线、包含根组装、清单同步调用 | `cmake/接入下层.cmake` / `生成源文件列表.cmake` 的**函数实现**（属「构建系统」） |
| `external/` 三库在**本层**的引入方式与用途 | 三库自身的实现（Dear ImGui / glad / googletest 源码） |
| `EngineTests.exe` 的落点与 `ctest` 注册策略 | 用例选择器与界面交互逻辑（见「测试主调.md」「图形界面.md」） |
| 本层对下层的**消费**（库定位、快照解析、着色器拷贝） | 下层的**产出**（各下层库与快照的生成） |

### 2.3 解决的问题

- **「同一个可执行文件服务多类场景」的目标划分**：本层既要跑单元测试，又要提供交互式选择界面，还要维护供主调与用例共用的纯逻辑库。若把所有源码堆进一个目标，例用例的图形依赖会拖累单元测试、主调逻辑无法被用例直接验证。本层以**多目标 + 依赖方向切分**解决（`TestLauncher` 纯逻辑 / `TestGui` 图形 / `EngineTestObjects` 用例 `.obj` / `EngineTests` 可执行）。
- **用例「静默不跑」**：静态库里未被引用的 `.obj` 会被链接器丢弃，`TEST_F` 宏的静态注册随之丢失，结果不报错、只是用例数量变少。本层用 **OBJECT 库**收集用例 `.obj`（见 §6.2），规避该陷阱。
- **源文件「无字面名」导致 IDE 改名失效**：GLOB 收集源文件时构建脚本没有具体文件名，VS 文件视图的改名/迁移找不到可改写引用。本层按共享清单同步工具落成三份 `源文件列表_*.cmake`（见 §6.3）。
- **头/库版本漂移**：源码树里同时能解析到下层**源码副本**。本层把三个下层**头快照根**列为**本层自身包含目录并排在项目根之前**（见 §6.5），使「本层能看到的头」与「本层链接的库」绑定到同一棵构建树。
- **渲染层用例需要渲染层库与素材**：本轮新增「渲染」用例子树，需要 `RendererCore.lib`、Vulkan/SDL3 间接依赖与渲染层 SPIR-V 着色器。本层**接入 Renderer**（§6.4）并把着色器在配置期拷入本层根（§6.6）。
- **中文工程路径下的构建期失败**：`gtest_discover_tests` 写用例枚举 JSON 时按 ANSI 解析路径，中文路径必然失败。本层按路径是否纯 ASCII **分流注册**（§6.9）。
- **无人值守被图形窗口挂住**：默认（无参数）启动会进入图形界面并停住等待按键。因此 `ctest` 退化注册必须带 `--selector=off`（§6.10）。

### 2.4 在整体架构中的位置

```
   Engine/EngineCore ──▶ Engine/EngineSystem ──▶ Engine（聚合，无产物）
   EngineCore.lib        EngineSystem.lib            │
                                                    ├──▶ Application/Game（骨架）
                                                    └──▶ Application/Test（本模块所在层）
   Application/Renderer ──▶ Application/Test            │
   RendererCore.lib + shaders/                          ▼
                                            本层构建期产物：
                                              out/build/<配置>/lib/TestLauncher.lib
                                              out/build/<配置>/lib/TestGui.lib
                                              <本层根>/EngineTests.exe  （＋ .ilk/.pdb）
                                              <本层根>/shaders/          （配置期拷贝）
```

- 依赖方向**单向**；本层是拓扑**最上层**，除 `external/googletest`（第三方副本，非下层源码）外不使用 `add_subdirectory`。
- 本层与 `Application/Renderer` 是**平级消费关系**：Renderer 只接 `EngineCore` 单层，Test 既接 `Engine` 聚合面、又额外接 `Renderer`（见 §6.4）。
- 本层**不产出供上层链接的库**：对外面虽声明 `TestCore`，但 `src/` 下功能测试代码为空时该目标不产出（见 §3.6、§6.12）。

### 2.5 与相邻模块及同层文档的分界

- 与 **「构建系统/构建与层间契约」**：该文档定义通用规则（六变量、接入函数、快照脚本、清单工具、构建前提）；本文只写 **Test 层**的调用点、参数与本层特有条目（如两个缓存变量、三快照、着色器拷贝、`ctest` 退化）。凡规则性内容本文不重述，只写「见 §X」。

## 三、模块公开接口介绍

本模块的「接口」不是 C++ 类型，而是**本层 CMake 对外暴露的目标与产物**、**缓存变量**、**导出面**与**构建命令**。下游（未来的使用方、CI、开发者）都通过这些入口与本层构建交互。

### 3.1 目标与产物总览

| 目标 | 类型 | 创建条件（源码） | 产物 / 落点 | 主要职责 |
| --- | --- | --- | --- | --- |
| `EngineTests` | 可执行文件 | 用例存在且 `GTest::gtest` 可用（§4.8 门控） | `<本层根>/EngineTests.exe`（另 `.ilk` / `.pdb`） | 本层唯一运行产物：用例 `.obj` + 主调六文件 |
| `EngineTestObjects` | OBJECT 库 | 同上 | 无独立文件（`.obj` 集合） | 全部用例 `.obj`，供 `EngineTests` 取用 |
| `TestLauncher` | STATIC 库 | 同上 | `out/build/<配置>/lib/TestLauncher.lib` | 纯逻辑测试选择模型 + 控制台菜单 |
| `TestGui` | STATIC 库 | `external/Dear_ImGui` 三文件存在（§4.6） | `out/build/<配置>/lib/TestGui.lib` | Dear ImGui 核心 + SDL3/Vulkan 后端 |
| `TestCore` | STATIC 库 | `src/` 下存在**非用例非主调**源码（§4.4 过滤后非空） | `out/build/<配置>/lib/TestCore.lib`（**当前不产出**，见 §3.6） | 功能测试代码（当前为空） |
| `gtest` / `gtest_main` | STATIC 库 | `external/googletest/CMakeLists.txt` 存在（§4.7） | `out/build/<配置>/lib/gtest.lib`、`<构建树>/googletest/` 子构建树 | googletest 框架（`gtest_main` 不链接） |

补充（源码确证）：

- `EngineTests.exe` 的落点由 `set_target_properties(EngineTests PROPERTIES RUNTIME_OUTPUT_DIRECTORY "${PROJECT_ROOT_DIR}")` 指定，即**本层根目录**，与 `assets/` 同级；这是**硬性要求**（引擎环境 `Engine_Env` 以「可执行文件所在目录」解析资源路径）。
- 各静态库落点由各自的 `ARCHIVE_OUTPUT_DIRECTORY / LIBRARY_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib"` 指定，即 `<构建树>/lib/`；`EngineTestObjects` 是 OBJECT 库，无归档产物。
- 实测本机 `out/build/x64-Debug/lib/` 现存 `gtest.lib`、`TestGui.lib`、`TestLauncher.lib`——**无 `TestCore.lib`**，印证 §3.6 的条件产出未触发。

### 3.2 `EngineTests`（可执行目标）

**创建处**：`CMakeLists.txt` 第 5 节（`add_executable`）。

**源构成（源码逐条）**：

```cmake
add_executable(EngineTests
    $<TARGET_OBJECTS:EngineTestObjects>
    "${PROJECT_ROOT_DIR}/src/主调/主程序.cpp"
    "${PROJECT_ROOT_DIR}/src/主调/图形操作界面.cpp"
    "${PROJECT_ROOT_DIR}/src/主调/测试界面.cpp"
    "${PROJECT_ROOT_DIR}/src/主调/测试运行器.cpp"
    "${PROJECT_ROOT_DIR}/src/主调/gtest输出镜像.cpp"
    "${PROJECT_ROOT_DIR}/src/主调/引擎日志屏蔽.cpp"
)
```

- 六个 `.cpp` 是**固定字面条目**（本就不属 GLOB 产物）；另经 `include(".../源文件列表_EngineTests.cmake")` 收编 `src/主调/*.h` 的 9 个**主调头**（仅索引、不编译）。
- **`main` 由 `src/主调/主程序.cpp` 提供**，不链接 `GTest::gtest_main`。
- 链接：`EngineTestObjects EngineCore EngineSystem RendererCore GTest::gtest TestLauncher TestGui`（`PRIVATE`）。
- 包含根：`target_include_directories(EngineTests PRIVATE ${BYJY_APP_INC})`（见 §4.2）。
- MSVC 私有选项：`/MP /utf-8`。

**注意**：`控制台选择菜单.cpp` 与 `测试选择模型.cpp` **不在**本目标源内——它们属 `TestLauncher`（§3.4），由链接传递。

### 3.3 `EngineTestObjects`（OBJECT 库）

**创建处**：第 4.5 节。

- `byjy_source_list_sync(... 源文件列表_EngineTestObjects.cmake ... EngineTestObjects BYJY_TEST_SOURCES BYJY_TEST_HEADERS ...)`，随后 `add_library(EngineTestObjects OBJECT)` ＋ `include(源文件列表_EngineTestObjects.cmake)`。
- **源**：`src/单元测试/` 下全部 `*.cpp`（清单实列 **31** 个文件：主调 2 ／ 工具 12 ／ 核心 11 ／ 渲染 6）；**头**：清单头段为空（`target_sources(EngineTestObjects PRIVATE )`），即候选头文件集为空。
- 包含根 `PUBLIC ${BYJY_APP_INC}`；链接 `PUBLIC EngineCore EngineSystem RendererCore GTest::gtest TestLauncher`（经 `TestLauncher` 取得本层自身根，使用例能 `include "Application/Test/src/主调/测试选择模型.h"`）。
- 编译选项：MSVC `/MP /utf-8` ＋ `_CRT_SECURE_NO_WARNINGS`；非 MSVC `-Wall -Wextra -pedantic` ＋ `_GNU_SOURCE`。

### 3.4 `TestLauncher`（STATIC 库）

**创建处**：第 4.5 节。

- 源为**两个固定字面条目**：`src/主调/测试选择模型.cpp`、`src/主调/控制台选择菜单.cpp`；另经 `源文件列表_TestLauncher.cmake` 收编 9 个主调头（仅索引）。
- 调用清单同步时**源变量传占位空列表** `BYJY_NO_SOURCES`（源码：`set(BYJY_NO_SOURCES "")`，供「只登记头文件、无源文件」的清单使用），头变量传 `MAIN_HEADERS`。
- 包含根：`PUBLIC "${BYJY_PROJECT_ROOT}" "${PROJECT_ROOT_DIR}"`——**项目根 + 本层根**，因主调实现文件以**本层根相对**（`src/主调/...`）包含本层头（双基准口径，见 §6.5）。
- 链接 `PUBLIC GTest::gtest`（选择模型反射 googletest 注册表）。

### 3.5 `TestGui`（STATIC 库）

**创建处**：第 3.5 节（`add_library(TestGui STATIC ...)`）。

- 源为固定六文件（见 §6.7 表）；`target_include_directories(PUBLIC "${BYJY_IMGUI_DIR}/imgui" "${BYJY_IMGUI_DIR}/backends")`；链接 `PUBLIC EngineCore RendererCore`（SDL3 / Vulkan 头与链接库随 `RendererCore` 对外面传递）。
- MSVC 私有 `/MP /utf-8` ＋ `_CRT_SECURE_NO_WARNINGS`（源码仅在 MSVC 分支设置）；输出目录同 `<构建树>/lib`。
- **不含 glad**：改造后不再编 `external/glad/src/gl.c`，其 `include` 也不再列入（见 §6.7、§6.13）。

### 3.6 `TestCore`（条件 STATIC 库，当前不产出）

**创建处**：第 3 节，包裹在 `if(TEST_SOURCES) ... endif()` 内。

- `byjy_source_list_sync(... 源文件列表_TestCore.cmake ... TestCore TEST_SOURCES TEST_HEADERS ...)` ＋ `add_library(TestCore STATIC)` ＋ `include(源文件列表_TestCore.cmake)`；包含根 `PUBLIC ${BYJY_APP_INC}`；链接 `PUBLIC EngineCore EngineSystem RendererCore`。
- **触发条件**：`TEST_SOURCES` 非空。而 `TEST_SOURCES` 由 `src/*.cpp`/`*.c` GLOB 后**两次排除**得到（排除 `/src/单元测试/`、`/src/主调/`），本层 `src/` 下当前**只有**这两棵子树，故 `TEST_SOURCES` 恒为空，`TestCore` 与 `源文件列表_TestCore.cmake` **均不产出**。源码注释亦写明「分阶段开发中测试代码尚未落位属正常状态，此时不产出 TestCore」。
- 被引用的 `源文件列表_TestCore.cmake` 在**本层根目录下不存在**。【待确认：TEST-71】

### 3.7 缓存变量接口

本层向使用者暴露两个 `CACHE STRING` 变量，供**显式覆盖**下层库路径（跳过自动探测）：

| 变量 | 声明 | 目标库 | 值形制 | 留空时的行为 |
| --- | --- | --- | --- | --- |
| `BYJY_ENGINE_LIB_PATH` | `set(... "" CACHE STRING "...")` | `EngineSystem;EngineCore`（经聚合面） | **分号列表，顺序同 `OUT_LIB`，须与库数等长** | 由 `byjy_jieru_xiaceng` 自动探测：各库优先 `<库所在层>/out/build/x64-Debug/lib/<库名>.lib`，其次 `out/build/*/lib` 取时间戳最新（见「构建系统」§6.5） |

### 4.1 `byjy_jieru_xiaceng` 两次调用（接入下层）

**调用 2（接渲染层，本版次新增）**：

- 接口文件路径为 `Application/Renderer/cmake/对外接口.cmake`；前缀 `BYJY_RENDERER`；覆盖变量 `BYJY_RENDERER_LIB_PATH`（单库 `RendererCore`）。
- 渲染层对外面**内含 EngineCore 对外面**，故接入即取得引擎侧公共路径与 Vulkan 链接库。
- 渲染层对外面自身还 `include` 了 `VulkanSDK探测.cmake`（见「构建系统」§4.5、§6.14），故本层**不必**自行探测 Vulkan SDK。

**位置**：两段均在 `include(.../cmake/接入下层.cmake)` 之后、头快照接入（§4.2）之前。引擎聚合面段在脚本前言第 1 节（注释标号 `1.`），渲染层段标号 `1.2`。

### 4.2 `byjy_tou_kuaizhao_gen` 三次调用与 `BYJY_APP_INC` 组装

```cmake
byjy_tou_kuaizhao_gen(BYJY_CORE_SNAPSHOT     EngineCore)
byjy_tou_kuaizhao_gen(BYJY_SYSTEM_SNAPSHOT   EngineSystem)
byjy_tou_kuaizhao_gen(BYJY_RENDERER_SNAPSHOT RendererCore)

set(BYJY_APP_INC
    "${BYJY_CORE_SNAPSHOT}"
    "${BYJY_SYSTEM_SNAPSHOT}"
    "${BYJY_RENDERER_SNAPSHOT}"
    "${BYJY_PROJECT_ROOT}"
    "${PROJECT_ROOT_DIR}"
)
```

- 三次调用分别由三个导入目标的 `IMPORTED_LOCATION` 上溯两级拼 `/include` 得快照根；**目录不存在即硬失败**（不静默退回源码树）。
- `BYJY_APP_INC` = **三份下层头快照根 + 项目根 + 本层根**（次序不可颠倒，见 §6.5）。供 `TestCore`、`EngineTestObjects`（`PUBLIC`）、`EngineTests`（`PRIVATE`）使用。
- 本层根（`PROJECT_ROOT_DIR`）在**末位**：本层实现文件（`.cpp`）的跨目录包含写「本层根相对」`src/...`，无需背项目根前缀。**注意**：`BYJY_APP_INC` 被当作 `PUBLIC` 挂到库目标上——意为「本层根条目也随 `PUBLIC` 传播」，与下层「本层根一律 `PRIVATE`」的做法不同（源自 Test/Game 的既有安排，见「构建系统」§6.2 末段）。
- 根路径推导：`PROJECT_ROOT_DIR = ${CMAKE_CURRENT_SOURCE_DIR}`（本层根），`BYJY_PROJECT_ROOT = ${PROJECT_ROOT_DIR}/../..`（项目根）。

### 4.3 渲染层着色器拷贝段（第 1.6 节）

```cmake
get_target_property(_BYJY_RENDERER_LIB_FILE RendererCore IMPORTED_LOCATION)
get_filename_component(_BYJY_RENDERER_BUILD_DIR "${_BYJY_RENDERER_LIB_FILE}/../.." ABSOLUTE)
set(BYJY_RENDERER_SHADERS "${_BYJY_RENDERER_BUILD_DIR}/shaders")

    file(COPY "${BYJY_RENDERER_SHADERS}" DESTINATION "${PROJECT_ROOT_DIR}")

else()
    message(WARNING "未找到渲染层着色器目录：...（渲染层用例需要它，请先构建渲染层）")

```

- **配置期**执行（非构建期 `add_custom_command`）：由 `RendererCore` 的 `IMPORTED_LOCATION` 同源推导渲染层构建树的 `shaders/`，`file(COPY)` 到**本层根目录**（`Application/Test/shaders/`）。
- 目录缺失时**只 `WARNING`**、跳过拷贝、不中断配置（渲染层用例会失败，需先构建渲染层）。
- 「同源推导」保证着色器与所链 `RendererCore.lib` **同版次**（见 §6.6）。

### 4.4 源文件 GLOB 与按目录排除段（第 2 节）

| 步骤（源码顺序） | 行为 |
| --- | --- |
| `file(GLOB_RECURSE TEST_SOURCES CONFIGURE_DEPENDS "src/*.cpp" "src/*.c")` | 收集本层 `src/` 全部源（递归） |
| 构建目录排除 | `string(REPLACE "\\" "/" ...)` ＋ 正则转义后 `list(FILTER TEST_SOURCES EXCLUDE REGEX "^<构建目录>/")`——防止把生成的临时文件误编译 |
| 排除用例 | `list(FILTER TEST_SOURCES EXCLUDE REGEX "/src/单元测试/")` |
| 排除主调 | `list(FILTER TEST_SOURCES EXCLUDE REGEX "/src/主调/")` |
| `file(GLOB_RECURSE TEST_HEADERS ...)` ＋ 同样两条排除 | 头文件集（仅索引） |
| `file(GLOB_RECURSE MAIN_HEADERS "src/主调/*.h" "*.hpp")` | 主调头集（`TestLauncher` 与 `EngineTests` 共用） |
| `file(GLOB_RECURSE BYJY_TEST_SOURCES "src/单元测试/*.cpp")`（第 4 节） | 用例源集 |
| `file(GLOB_RECURSE BYJY_TEST_HEADERS "src/单元测试/*.h" "*.hpp")`（第 4 节） | 用例头集 |
| `if(NOT TEST_SOURCES) message(STATUS "测试层 src/ 下暂无源文件，跳过 TestCore 静态库")` | 空集**不报错** |

- 全部 GLOB 均带 `CONFIGURE_DEPENDS`，配合 §4.5 目录登记实现「增删文件后直接构建即被收编」。
- 与下层不同：本层**不对空集做 `FATAL_ERROR`**——`src/` 为空、用例为空均是合法状态（见 §6.12）。

### 4.5 目录登记段（`CMAKE_CONFIGURE_DEPENDS`）

```cmake
set(BYJY_NO_SOURCES "")   # 占位空列表，供「只登记头文件、无源文件」的清单调用
set_property(DIRECTORY APPEND PROPERTY CMAKE_CONFIGURE_DEPENDS
    "${PROJECT_ROOT_DIR}/src"
    "${PROJECT_ROOT_DIR}/src/单元测试"
    "${PROJECT_ROOT_DIR}/src/主调"
)
```

- 登记**三个 GLOB 基点目录**（覆盖 `src` 及其两棵子树）。`src/单元测试/` 下另有 `主调/`、`工具/`、`核心/`、`渲染/` 四个子目录——源码注释只登记三个基点目录，**更深层目录未逐级登记**（`GLOB_RECURSE` 覆盖内容变化，但 `CONFIGURE_DEPENDS` 的逐目录登记仅到基点；新建**更深一层**子目录时是否触发重配，未见源码明确保证）。【待确认：TEST-72】
- 效果：`Ninja` 检测到基点目录 mtime 变化即自动重跑配置并重扫 GLOB，IDE 目录视图随之更新，无需手动「重新生成缓存」。

```cmake
if(EXISTS "${PROJECT_ROOT_DIR}/external/Dear_ImGui/imgui/imgui.cpp"
```

### 4.7 googletest 接入条件段（第 4 节）

```cmake
if(EXISTS "${PROJECT_ROOT_DIR}/external/googletest/CMakeLists.txt")
    set(INSTALL_GTEST OFF CACHE BOOL "" FORCE)
    set(BUILD_GMOCK OFF CACHE BOOL "" FORCE)
    set(gtest_force_shared_crt ON CACHE BOOL "" FORCE)
    add_subdirectory("${PROJECT_ROOT_DIR}/external/googletest"
        "${CMAKE_BINARY_DIR}/googletest" EXCLUDE_FROM_ALL)
else()
    message(STATUS "未找到 external/googletest，跳过单元测试接入")
endif()
```

- 三个 `CACHE ... FORCE`：**不安装 gtest、不构建 gmock、强制共享运行时库**（避免与下层 CRT 设置冲突产生 `LNK2038`）。
- `add_subdirectory(..., EXCLUDE_FROM_ALL)`：gtest **只在被本层目标依赖时才编译**，不改变其它目标的构建范围。
- googletest 副本缺失**只 `STATUS` 跳过**，不中断配置（后续 §4.8 门控会连带跳过用例目标）。
- **这是本层唯一使用 `add_subdirectory` 之处**，且对象是**第三方副本**、非下层源码，不与「层间只链接已构建静态库」契约冲突。

### 4.8 用例门控段（第 4.5／5 节）

```cmake
if(NOT BYJY_TEST_SOURCES)
    message(STATUS "src/单元测试/ 下暂无用例，跳过 EngineTests 与 EngineTestObjects")
elseif(NOT TARGET GTest::gtest)
    message(STATUS "gtest 目标不可用，跳过 EngineTests 与 EngineTestObjects")
else()
    ... （TestLauncher / EngineTestObjects / EngineTests / ctest 全部在此分支内）
endif()
```

- **双门控**：① 用例集非空；② `GTest::gtest` 目标存在。二者任一不满足则**跳过四个目标**（`TestLauncher`、`EngineTestObjects`、`EngineTests` 与 `ctest` 注册），**只提示不报错**。
- 因此 `EngineTests.exe` 的产出**依赖用例存在**；若 `src/单元测试/` 清空，本层将**不再产出任何可执行文件**。

### 4.9 `ctest` 注册条件段（第 5 节末）

```cmake
enable_testing()
if("${PROJECT_ROOT_DIR}" MATCHES "^[ -~]+$")
    include(GoogleTest)
    gtest_discover_tests(EngineTests WORKING_DIRECTORY "${PROJECT_ROOT_DIR}")
else()
    add_test(NAME EngineTests COMMAND EngineTests --selector=off WORKING_DIRECTORY "${PROJECT_ROOT_DIR}")
endif()
```

- 判定「工程路径是否**纯 ASCII**」（正则 `^[ -~]+$`）：纯 ASCII → `gtest_discover_tests` **逐用例注册**；含非 ASCII（本仓库路径含中文）→ **整体注册一个用例**，命令等价于 `EngineTests --selector=off`。
- 退化分支**必须带 `--selector=off`**：不开窗、不建模型、跑完即走，`ctest` 不会被图形界面或按键等待挂住（见 §6.10）。
- `WORKING_DIRECTORY` 统一设为 `${PROJECT_ROOT_DIR}`（本层根），使用例的相对资源路径与手工运行一致。

### 4.10 清单同步四次调用（`byjy_source_list_sync`）

**工具来源**：`include("${PROJECT_ROOT_DIR}/../../Engine/EngineCore/cmake/生成源文件列表.cmake")`（**共享构建工具，非层间契约**；原理见「构建系统」§4.3、§6.8）。

| 序号 | 清单文件（本层根下） | 目标 | 源变量 | 头变量 | 备注 |
| --- | --- | --- | --- | --- | --- |
| ① | `源文件列表_TestCore.cmake` | `TestCore` | `TEST_SOURCES` | `TEST_HEADERS` | 在 `if(TEST_SOURCES)` 内，**当前不执行** |
| ② | `源文件列表_TestLauncher.cmake` | `TestLauncher` | `BYJY_NO_SOURCES`（空占位） | `MAIN_HEADERS` | 源为固定字面量，清单只登记头 |
| ③ | `源文件列表_EngineTestObjects.cmake` | `EngineTestObjects` | `BYJY_TEST_SOURCES` | `BYJY_TEST_HEADERS` | 用例源清单 |
| ④ | `源文件列表_EngineTests.cmake` | `EngineTests` | `BYJY_NO_SOURCES`（空占位） | `MAIN_HEADERS` | 源为固定字面量，清单只登记头 |

- 六参数形如 `(清单绝对路径, 本层根, target 名, 源列表变量名, 头列表变量名, "Application/Test")`；**仅当路径集合有差异时**整体写回，时间戳稳定则无谓重配不发生。
- **逐目标各一份清单**：因本层目标多为条件创建，逐目标清单可随目标所在条件块按需 `include`，**不会引用到不存在的目标**。
- 清单是这些源/头的**唯一加入点**：`add_library` / `add_executable` 不传它们（`add_library(TestLauncher STATIC <两个字面 .cpp>)`、`add_executable(EngineTests <object表达式+六个字面 .cpp>)`、`add_library(TestCore STATIC)`、`add_library(EngineTestObjects OBJECT)` 均为无 GLOB 源形式）。

## 六、模块设计/实现细节

### 6.1 多目标划分的设计意图

本层五个目标（一个条件产出）按**职责与依赖方向**切分：

- `TestLauncher` 只放**纯逻辑**（选择模型 + 控制台菜单），故能被**单元测试目标直接链接**——用例可 `include "Application/Test/src/主调/测试选择模型.h"` 验证选择逻辑；同时它不含 ImGui，使「用测试选择模型的用例」不必拖上图形库。
- `TestGui` 只放**图形依赖**（ImGui 三后端），只被 `EngineTests` 链接；这样「单元测试目标」不依赖图形库。
- `EngineTestObjects` 只放**用例 `.obj`**，`.cpp` 不含 `main`，供可执行取用。
- `EngineTests` 是**唯一的可执行**，聚合 `main`（`主程序.cpp`）＋ 图形三文件 ＋ 日志分流 ＋ `gtest输出镜像`。
- `TestCore` 预留**功能测试代码**位置（当前空）。

**为什么把 `控制台选择菜单.cpp` 与 `测试选择模型.cpp` 从 `EngineTests` 字面量里移出**：源码注释写明它们属 `TestLauncher`（可被用例链接），字面量只留真属可执行的部分。若既放进 `TestLauncher` 又列进 `add_executable`，会造成重复定义（或 backtrace 归先加入者使清单失效）。

### 6.2 OBJECT 库防止用例静默丢弃

`EngineTestObjects` 必须是 **OBJECT 库而非 STATIC**：静态库里未被任何符号引用的 `.obj` 会被链接器丢弃，`TEST_F` 宏的**静态注册**随之丢失——表现是「不报错、只是跑的用例变少」，极难察觉。OBJECT 库把全部用例 `.obj` 无条件交给 `EngineTests` 的 `$<TARGET_OBJECTS:EngineTestObjects>`，确保注册不丢。

- 副作用：`EngineTestObjects` 是 OBJECT 库，**无独立归档产物**，其 `ARCHIVE_OUTPUT_DIRECTORY` 等属性不适用，故脚本**未**为它设输出目录属性（与 `TestCore`/`TestLauncher`/`TestGui` 不同）。
- 「改回 STATIC」是本体系最危险的「优化」（`README.md` §7.3 亦如此警示）。

### 6.3 清单同步机制在本层

- 本层 GLOB 后**没有**任何字面源名进入 `add_library`/`add_executable`（除了本就不属 GLOB 产物的固定 `.cpp`），故需靠清单给 VS 提供「可改写引用」。清单同步工具把 GLOB 结果落成 `target_sources` 字面量；清单被 `CMakeLists` `include`，属配置依赖，被 VS 改写即触发重配（原理见「构建系统」§6.8）。
- **逐目标一份清单**（三份 + 条件的一份）而非单份：因目标多为条件创建，逐目标清单随目标所在条件块按需 `include`，**不会引用到不存在的目标**（源码注释原文要点）。
- 清单调用时若某类列表为空（`TestLauncher`/`EngineTests` 的源），**必须传空占位变量**（`BYJY_NO_SOURCES`），因为同步函数要求同时传源/头两个变量名。
- 「固定 `.cpp` 仍写字面量」是刻意选择：这些文件本就不属 GLOB 产物，写字面量不破坏清单机制、且让可执行入口一目了然（源码注释）。

### 6.4 接入 Renderer 的必要性与口径

本版次新增渲染用例子树，故本层需 `RendererCore.lib`：

- **为什么另开一条接入、而不走 Engine 聚合面**：渲染层与 Test/Game **平级**、只接 `EngineCore` 单层，**不属 Engine 聚合面**（其产物不经 `Engine/cmake/对外接口.cmake` 转发）。因此本层只能**直接** `byjy_jieru_xiaceng(".../Renderer/cmake/对外接口.cmake", "BYJY_RENDERER", "BYJY_RENDERER_LIB_PATH")`。
- **接入即得引擎侧公共路径**：渲染层对外面自身 `include` 了 EngineCore 对外面（并附带 Vulkan SDK 探测结果），故本层不必重复声明 `Engine/...` 包含根或 Vulkan 库。
- **本层不引入 Vulkan 头**：渲染层**公共主头**（`渲染器.h`、`网格数据.h`）不含 SDL/Vulkan/VMA 类型，故渲染用例按公共面编写即可；`imgui_impl_vulkan.cpp` / `imgui_impl_sdl3.cpp` 的 Vulkan/SDL 头经 `RendererCore` 的 `INTERFACE_INCLUDE_DIRECTORIES` 传递。
- 对外面（导出）**不变**：本层仍是拓扑最上层、无使用方；不把 `RendererCore` 并入本层对外面（见 §3.8）。

### 6.5 包含根次序与双基准

`BYJY_APP_INC` 五条严格有序：

```
① EngineCore 快照根  ② EngineSystem 快照根  ③ Renderer 快照根  ④ 项目根  ⑤ 本层根
```

- **前三项必须排在项目根之前、且作为本层自身包含目录**：MSVC 下目标自身的 `-I` 恒在导入目标传递的 `/external:I` 之前，故 `Engine/...`、`Application/Renderer/...` 必然先命**快照**、不落源码树上的同名头（原理见「构建系统」§6.6）。
- **双基准**：**头文件**里的跨目录包含写**项目根相对全路径**（`Engine/EngineCore/...`、`Application/Test/...`）——这是快照机制可用的前提（快照把本层头镜像到 `<快照根>/Application/Test/...`）；**实现文件（`.cpp`）**的跨目录包含写**本层根相对**（`src/...`）——`.cpp` 不进快照、不被别层消费，`src/...` 又比 `../` 更稳。故末位补本层根。
- **本层根随 `PUBLIC` 传播**（`TestCore`/`EngineTestObjects`）：目的让用例能 `include "Application/Test/src/主调/测试选择模型.h"` 全路径；这与下层「本层根一律 `PRIVATE`」的做法不同，源自 Test/Game 的既有安排（见「构建系统」§6.2 末段）。
- `TestLauncher` 的包含根是**例外**：只挂「项目根 + 本层根」，**不挂快照**——它只引用本层头，无需消费下层头。

### 6.6 着色器拷贝（同版次推导）

- **为何要拷**：渲染层以 **SPIR-V 运行期加载**着色器；`Renderer_Config::shader_dir` 为空时按「**相对可执行文件目录**的 `shaders`」解析。而渲染层的着色器产物在**渲染层构建树** `<Renderer 构建树>/shaders/` 下，与 `EngineTests.exe`（落本层根）不同目录。
- **为何「同源推导」**：由 `RendererCore` 的 `IMPORTED_LOCATION`（`<渲染层构建树>/lib/RendererCore.lib`）上溯两级得渲染层构建目录，拼 `shaders`——从而保证拷入的着色器与**所链 `RendererCore.lib` 同版次**（若用固定路径，可能出现「新库配旧着色器」）。
- **为何在配置期 `file(COPY)`、非构建期 `add_custom_command`**：渲染层着色器的生成属渲染层构建；本层只需在配置期把**已存在**的产物拷进来。缺失时告警跳过（渲染层未构建时，本层仍可配置成功）。

### 6.7 `external/` 三库引入方式与用途

- **引入方式**（沿用《agent开发指南》「外部库引入约束」与下层口径）：三库**以源码副本**放在本层 `external/`（与 `src/` 平级）；不使用投影/符号链接绑定本地其它位置；CMake 中一律以 `${PROJECT_ROOT_DIR}/external/...` 拼接、**无绝对路径**。
- **Dear_ImGui**：`TestGui` 就地编译 4 个核心 + 2 个后端（`imgui_impl_sdl3.cpp`、`imgui_impl_vulkan.cpp`），**不编 `imgui_demo.cpp`**；**不再使用** glfw/opengl3 后端。SDL3/Vulkan 头与 `vulkan-1.lib`、SDL3 系统库经 `RendererCore` 传递。
- **glad**：**保留在源码树内但已不参与编译**（改造前供图形窗口自身的 GL 调用；改造后渲染统一走渲染层 UI 通道 + Vulkan）。源码树仍含 `include/`、`src/gl.c`。【待确认：TEST-74】

### 6.8 分层用例门控

### 6.9 `ctest` 注册策略与 ASCII 退化

- **问题（源码注释）**：`gtest_discover_tests` 在**构建期**以 `--gtest_output=json:<文件>` 枚举用例；googletest 写该报告文件时**按 ANSI 代码页解析路径**，工程路径含中文时必然失败（`[FATAL] Unable to open file ...\cmake_test_discovery_*.json`），**构建会被判失败**。
- **策略**：以正则 `^[ -~]+$` 判定工程路径是否纯 ASCII——纯 ASCII 走 `gtest_discover_tests`（逐用例注册，`WORKING_DIRECTORY` 为本层根）；否则退化为**整体注册一个用例**，命令 `EngineTests --selector=off`。
- 本仓库路径含中文，故**实际走退化分支**：`ctest` 只注册 1 个用例，等价于一次「不开窗全量运行」。这与 `README.md` §9.4 的描述一致（本版次未变）。

### 6.10 无参数启动与 `ctest` 的规避

- **无参数启动的坑位**：`EngineTests.exe` 不带参数时，`选择模式` 默认 `window`，进入**图形操作界面**（常驻界面）并在会话结束后按「退出等待判定」**停住等待按键**（交互运行的既定行为）。因此若 `ctest` 的注册命令不带 `--selector=off`，`ctest` 会**阻塞在图形窗口/按键等待**上。
- **本层规避**：退化分支使用 `--selector=off`——不开窗、不建模型、跑完即走（`需要等待退出` 在该模式下返回 `false`）。
- 运行期命令行行为、四步分流与退出等待判定表属「测试主调.md」（§6.1、§6.6、§6.8）；本文只记录**构建期 `ctest` 注册命令的取值理由**。

### 6.11 `.gitignore` 契约条目

- **`shaders/`（本版次新增）**：着色器拷贝是**构建期**产物，与所链 `RendererCore.lib` 同版次，不入库。
- **`assets/`**：目录联接指向 Game 层资产（**单一真源**）；不加规则时 git 会把联接当真实目录递归追踪，产生大量重复条目。**克隆本层不会得到 `assets/`**，需自行建立联接或复制。
- **`engine_log_probe.txt`**：日志系统用例的落盘探针在用例结束尝试删除，但活跃输出流仍持句柄，Windows 下删除可能失败而残留，故忽略。
- 各静态库落在 `out/`（已被忽略），故 `.gitignore` 的 `*.lib` 规则不影响构建产物转储。

### 6.14 本机构建前提

本层沿用全工程的**三条硬性前提**（详见「构建系统/构建与层间契约」§6.11）：

1. **配置期须处于 UTF-8 代码页**：先 `Enter-VsDevShell` / 开发人员命令行，**再** `chcp 65001`；否则 `/showIncludes` 前缀编码不一致致**头文件依赖一条都不记录**（改头不触发重编）。
2. **`TMP`/`TEMP` 必须纯 ASCII 路径**；否则 `cl.exe` 请求调试信息即报 `D8050`。
3. **`chcp` 与 VS 开发环境的先后顺序**不可颠倒。

本层**特有**的两点：

- **不校验构建类型**：本层脚本**没有**下层的 `CMAKE_BUILD_TYPE` 合法性校验段；单配置生成器下若未传 `-DCMAKE_BUILD_TYPE`（`CMakeSettings.json` 由 VS 传入 `configurationType`），落入裸配置的风险由 VS 侧规避。
- **中文源码依赖 `-f8`/`/utf-8`**：本层源码、include 路径、用例名均含中文，MSVC 各目标均带 `/utf-8`。

### 6.15 易错点汇总

1. **不要改回 STATIC 收集用例**：`EngineTestObjects` 必须是 OBJECT 库，否则用例静默不跑（§6.2）。
2. **不要在 `add_library`/`add_executable` 里再传 GLOB 源文件**：清单是唯一加入点，否则 VS 改名失效（§6.3）。
3. **固定 `.cpp` 仍写进 `add_executable` 是刻意的**：它们不属 GLOB 产物，不要移进清单。
4. **新增/删除用例文件后直接构建即可**，但新建**更深层**子目录的自动重配未见保证（`CMAKE_CONFIGURE_DEPENDS` 只登记三个基点目录）——必要时重新生成缓存（§4.5）。
5. **包含根次序不可颠倒**：三快照根必须排在项目根之前、且作为**本层自身**包含目录（§6.5）。
6. **`ctest` 退化分支必须带 `--selector=off`**：否则阻塞在图形界面/按键等待（§6.10）。
7. **新增渲染素材**：靠渲染层的 `RendererCore.lib` 位置推导着色器目录；改了渲染层着色器须**先重建渲染层**再重建本层（§6.6）。
8. **改 `cmake/接入下层.cmake` 要五份同改**（含 Renderer 副本），否则各层行为漂移（见「构建系统」§6.3）。
9. **本层 `src/` 空不报错**：不要照搬下层「空集 `FATAL_ERROR`」的写法（§6.12）。
10. **README 不可作为本层构建事实依据**：其图形界面/依赖/包含根等章节滞后（§6.13）。
