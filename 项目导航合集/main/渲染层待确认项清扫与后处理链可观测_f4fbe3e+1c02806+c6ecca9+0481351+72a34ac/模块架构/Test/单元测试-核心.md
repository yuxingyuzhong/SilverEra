## 二、模块功能介绍

### 2.1 模块定位

「单元测试-核心」是 Test 层用例的**核心子树**：`Application/Test/src/单元测试/核心/` 下 11 份 `*.cpp`，每份以 `TEST_F(套件名, 中文用例名)` 的静态注册进入 googletest 注册表，并由 Test 层 OBJECT 库 `EngineTestObjects` 收编、最终随 `EngineTests.exe` 执行。

本子树的用例**直接 include 被测模块的真实源码头**、直接调用被测类型与函数（无源码回退、无 mock 层），验证的是 **EngineCore 层五个核心模块**的真实现：

| 被测模块（EngineCore） | 模块文档 | 本子树对应套件 |
| --- | --- | --- |
| 对象系统（`src/core/object/`） | `模块架构/EngineCore/对象系统.md` | `Object_Test`、`Object_Pool_Test` |
| 事件系统（`src/core/event/`） | `模块架构/EngineCore/事件系统.md` | `Event_Test`、`Event_Broker_Test`、`Event_Terminal_Test` |
| 空间系统（`src/core/spatial/`） | `模块架构/EngineCore/空间系统.md` | `Coord_Type_Test`、`Quadtree_Test`、`Quadtree_Manager_Test`、`Collider_Test`、`Collider_Move_Test`、`Collision_Region_Test`、`Collision_Proxy_Test` |
| 配置系统（`src/core/config/`） | `模块架构/EngineCore/配置系统.md` | `Config_Loader_Test` |

一句话概括：**本子树是「用 324 条可复跑的断言，逐行为钉住 EngineCore 核心模块的对外契约与边界」的验证集合——每条用例只问「这个函数在这类输入下是否给出规定的输出/副作用」，不负责搭夹具（夹具归属见同层 `测试对象与夹具.md`）。**

### 2.2 收录范围与文档分界

| 对象 | 归谁写 |
| --- | --- |

| 同层 `测试对象与夹具.md` | 夹具类、测试用辅助对象（`Test_Object`/`Tagged_Object`/投影器等）、生命周期与隔离、编译口径与依赖 |

| 同层 `单元测试-工具.md` / `单元测试-渲染.md` | 工具子树（12 份）与渲染子树（6 份）的用例正文 |

### 2.3 被测模块与依赖链位置

```
        EngineTests.exe（可执行）
          └── $<TARGET_OBJECTS:EngineTestObjects>  ← 本子树的 11 份 .obj（OBJECT 库，注册不丢）
                    │ 直接 #include 被测源码头
                    ▼
        EngineCore.lib（对象系统 / 事件系统 / 空间系统 / 配置系统 / 工具集）
                    ▲
                    │  GTest::gtest（TEST_F 注册、::testing::Test 夹具基类、断言宏）
```

- 本子树用例**只依赖 EngineCore 层**（不含 EngineSystem、不含 Renderer 类型），链接项由 `EngineTestObjects` 统一承担（`EngineCore`、`EngineSystem`、`RendererCore`、`GTest::gtest`、`TestLauncher`）。
- 用例体不持有测试选择模型等主调设施（除工具子树/主调子树外）；也不触碰全局日志态（除工具子树的 `Log_Test`）。
- 临时文件的根一律以 `engine::Engine_Env::exe_dir_get()`（可执行文件所在目录）为基准拼接（见 6.9）。

### 2.4 用例的组织形态

- **套件名 = 夹具类名，用例名一律中文**；本子树 13 个夹具中 12 个英文类名（如 `Event_Broker_Test`），1 个不复存在中文类名（本子树无中文夹具）。按 `TEST_F` 宏，套件与用例两级名字进入注册表，可被 `--gtest_filter` 与主调的反射选择树枚举。
- **一文件一套件**（10 份文件）与**一文件多套件**（1 份文件）两种：
  - 一文件一套件：`对象测试.cpp`、`对象池测试.cpp`、`事件测试.cpp`、`事件中转器测试.cpp`、`事件终端测试.cpp`、`坐标类型测试.cpp`、`四叉树测试.cpp`、`四叉树管理器测试.cpp`、`碰撞体测试.cpp`、`配置加载器测试.cpp`；
  - 一文件三套件：`碰撞测试.cpp`（`Collider_Test`、`Collision_Region_Test`、`Collision_Proxy_Test`）。
- **夹具取用三形态**（空夹具／持有被测对象／静态辅助）在本子树的分布见 6.2；夹具与辅助对象的定义本身见同层 `测试对象与夹具.md` §5.2/§5.3。

## 三、模块公开接口介绍

### 3.1 可见性总览与注册面

本子树**无对外头、无对层外可见的接口**；全部夹具与辅助函数都定义在各自 `.cpp` 编译单元内部。唯一「对外生效」的产物是 googletest 的**静态注册**：`TEST_F` 把「套件名 = 夹具类名 + 用例名」登记进 gtest 注册表，因而可被 `::testing::UnitTest` 反射枚举（主调 `Test_Selection_Model` 正是据此建树）。

因此本章的「公开接口」指**本子树用例对被测引擎暴露出的验证面**，按被测模块分七组逐条列出：**该套件的用例清单 ＋ 每条用例验证的核心行为 ＋ 所验证的引擎接口**。逐条签名与夹具成员见第四章。

### 3.2 对象与对象池

**套件 `Object_Test`**（`核心/对象测试.cpp`，10 例）——验证 `engine::Object`（`Engine/EngineCore/src/core/object/Object/对象.h`）的初值、读写与派生能力。

## 六、模块设计/实现细节

### 6.1 一文件一套件 vs 一文件多套件

本子树 10 份文件采用「一文件一处（一套件）」写法：文件头一句话点明覆盖范围 → `#include <gtest/gtest.h>` → include 被测源码头 → 文件级 `static` 辅助 → 夹具类 → 一串 `TEST_F`。这种「被测模块 ↔ 文件 ↔ 套件」一一对应，使「按模块精准复跑」的过滤串天然可用（`--gtest_filter=Quadtree_Test.*`）。

只有 `碰撞测试.cpp` 例外：一个文件注册三个套件（`Collider_Test` / `Collision_Region_Test` / `Collision_Proxy_Test`），因为三者共用文件级辅助（`box_config`/`collider_payload`/`make_event`/`temp_mesh_write`/`temp_boundary_write`）且属同一头文件 `碰撞代理器.h` 的连带对象；拆文件会重复辅助，故合并。设计意图（是否为体量考虑）见同层 `测试对象与夹具.md` 的 `【待确认：TEST-22】`。

### 6.2 夹具三形态在本子树的分布

| 形态 | 特征 | 本子树使用 | 典型 |
| --- | --- | --- | --- |
| 空夹具 | 类体为空，无成员无钩子 | 5 个（`Object_Test`、`Object_Pool_Test`、`Event_Test`、`Coord_Type_Test`、`Collider_Test`） | 纯函数式用例，用例体内自造输入 |
| 持有被测对象 | `protected` 值成员即被测对象（每用例独立构造） | 4 个（`Event_Broker_Test`、`Event_Terminal_Test`、`Collision_Region_Test`、`Collision_Proxy_Test`） | 用例体直接在成员上操作 |
| 静态辅助 | 以 `static` 成员复用建树/写临时文件等公共逻辑 | 3 个（`Quadtree_Test`、`Quadtree_Manager_Test`、`Collider_Move_Test`） | 用例体调用夹具静态方法 |
| 静态辅助 + 钩子/成员函数（重夹具） | 兼具静态辅助与实例成员函数 | 1 个（`Config_Loader_Test`） | 夹具方法桩造目录、接线、投递 |

- 设计意图：**夹具只承载「用例之间需要隔离或被复用的东西」**——纯函数式用例用空夹具；需要每用例独立可变态就用值成员持被测对象（天然隔离）；公共建树/写文件逻辑抽成静态辅助，避免在每条用例里重复。
- 五类形态的完整定义与 34 套件全局对照见同层 `测试对象与夹具.md` §2.4/§5.2。

### 6.3 边界覆盖策略

本子树对每个被测接口普遍采用「**默认值 → 正向读写 → 边界值 → 非法输入 → 生命周期**」五段式覆盖，且把边界集中为可检索的用例名（便于回归时按名定位）：

| 边界类型 | 代表用例（套件） |
| --- | --- |
| 数值边界（零/极大/超 int） | `ID设置为零与极大值`（`Object_Test`）、`边界ID查询与卸载不崩溃`（`Object_Pool_Test`）、`六十四位点承载超int边界值`（`Coord_Type_Test`）、`超大边长上限下区块检索次数正常`（`Quadtree_Manager_Test`） |
| 空集合/空标识 | `空分类事件被丢弃`、`空标签登记不生效`、`空事件批量发送成功`、`智能创建空坐标集合不建树`、`范围查询空序列返回空结果` |
| 非法输入 | `非法几何配置被拒`、`形状字段类型非法被拒`、`条目缺事件标识被驳回`、`非法卸载目标被驳回` |
| 重复操作 | `重复注册不产生重复投递`、`重复卸载`（碰撞）、`空序列重复清空`、`缓存条目上限为零时查找不崩溃` |
| 退化/极值场景 | `退化树范围查询不产出结果`、`退化树单点查询触发引擎缺陷`（跳过）、`退化树创建被拒绝`（跳过） |
| 浮点特殊值 | `浮点点含NaN时一律不相等`、`浮点点无穷按精确比较`、`ULP距离符号不同返回极大值` |

### 6.4 桩造技艺一：四叉树的外部配置前置

四叉树的 `block_size`（区块单元）与 `max_size`（边长上限）**缺省为 0 / 2^63，不可直接使用**，须由外部显式设置后方可建树与检索。因此 `Quadtree_Test::make_tree(size=256, root={0.5,0.5}, block_size=16, max_size=2^63)` 先构造 `Quadtree(size, root)`，再 `set_block_size`/`set_max_size`，返回一棵**已完成外部配置**的树，供全部建树/检索用例复用（见 §3.5）。

- 该前置使断言可稳定落在固定网格上：区块单元 16 时，原点区块中心恒为 `(-7.5, -7.5)`、相邻区块中心为 `(8.5, 8.5)` 等（`build单点创建叶子后可seek取回` 等用例据此断言）。
- `Quadtree_Manager_Test::build_one_tree` 同理固定上下限 128/256，使管理器的包围矩形与区块划分稳定（见 §3.5）。

### 6.5 桩造技艺二：碰撞用例的事件驱动全链路

`Collision_Proxy_Test` 的多数用例不直接调用内部方法，而是**用事件驱动代理器走完整链路**（也即最贴近真实使用的路径）：

1. `proxy.event_terminal->bind(Port_ID::Evt_Sender, …)` 捕获代理器外发事件；`bind(Port_ID::Broker_Attacher, …)` 取得接收通道 `entry`；
2. `proxy.attach()` 接入中转站，`sent.clear()` 排除接入时发出的订阅登记事件；
3. 经 `entry` 逐条投递 `RegionBuild` → `ColliderBuild` → `ColliderSet` → `RegionState` → `RegionDetect` / `ColliderDisplacement`；
4. 从 `sent.back()`（`DetectResult`）读取 `results` 数组断言碰撞对；
5. 碰撞响应类用例在发送通道内**同步回发** `ColliderCollisionResponse`（`stop`/`keep`/`change`），以验证代理器的响应分支（含缺失时搁置重发）。

- 该桩造把「事件 → 代理器 → 碰撞空间 → 结果事件」的闭环收进单条用例，等价于把事件系统的接线一并纳入验证。
- `Collision_Region_Test` 则退一层，直接用 `region.collider_set`/`displacement_reader_set`/`detect()` 验证空间本身，不经过事件系统。

### 6.6 桩造技艺三：配置加载器的目录/路由文件

`Config_Loader_Test` 是唯一需要**磁盘目录结构**的套件，其 `root_make(name, nest)` 一次性建好：

```
exe_dir_get()/<根目录名>/
├── 索引/                     ← 可信根「索引目录」（root_route）
│   └──[对象甲/]              ← nest 为真时下探一层，用于区分「可信根目录」与「对象自身目录」
│        └── 路由.json         ← 仅含路由条目、无脏标记（route_file_reset 覆盖写回）
└── 配置/                     ← 可信根「配置目录」（root_config）
    └──[对象甲/]
         └── 配置.json         ← { "键": "值" }（对象配置文件）
```

- `route_file_reset()` 写回「顶层无脏标记、条目无脏标记」的路由文件初态；也被需要「让后续扫描再次投递」的用例用于清除脏标记（如 `可信根增量重建恢复缓存`、`路由加载仅认对象自身目录对`、`配置卸载后可重建`）。
- 夹具 `TearDown` 以 `remove_all(exe_dir_get()/root_name)` 逐个用例独立清除根目录（见 4.1）；根名逐用例不同（`可信根测试_添加`、`配置卸载测试` 等），避免用例间串扰。
- 事件一律经 `event_send(category, tag, config)` 以 `event_terminal->build("", "Config_Loader", …)` **定向**到加载器后投递中转站，订阅者 `object_attach` 以固定 `object_key` 登记并把收到的配置事件攒进 `delivered` 供断言。

## 七、模块运行链路详例

### 7.1 主流程：单个用例的生命周期

1. `EngineTests` 启动后 `InitGoogleTest()`，本子树各 `.obj` 的 `TEST_F` 静态注册已填满 gtest 注册表；`--gtest_filter` 决定本轮执行哪些用例。
2. 对每条命中的 `TEST_F`：gtest **构造夹具实例**——空夹具无成员；持有被测对象者就地构造值成员（`Event_Broker_Test::broker`、`Collision_Region_Test::region{"测试空间"}`、`Collision_Proxy_Test::proxy`、`Event_Terminal_Test::terminal`）；`Config_Loader_Test` 同时构造 `broker`/`loader` 并初始化成员默认值（`entry_category="Test"`、`entry_tag="Load"` 等）。
3. **只有 `Config_Loader_Test` 覆写 `TearDown`**（其余套件无钩子）。
4. 执行用例体：桩造（`make_tree`/`root_make`/`temp_mesh_write`）→ 操作被测对象（`build`/`mode_set`/`detect`/`receive`/`quadtree_build_smart`…）→ `EXPECT_*`/`ASSERT_*` 断言。
5. 若覆写 `TearDown` → 调用之（`Config_Loader_Test` 清除可信根目录）。
6. **析构夹具**：值成员随之析构（如 `Collision_Proxy_Test::proxy`、`Event_Broker_Test::broker`），用例间不共享可变态。

### 7.2 事件驱动全链路用例（碰撞代理器）

以 `Collision_Proxy_Test::事件驱动检测链路` 为例：

1. `proxy.event_terminal->bind(Port_ID::Evt_Sender, [&sent](evt){ sent.push_back(evt); })`：接管外发事件；
2. `bind(Port_ID::Broker_Attacher, [&entry](name,key,event_entry){ entry = event_entry; })`：取得接收通道；
3. `proxy.attach()` 接入中转站（此时会发出订阅登记事件）→ `sent.clear()` 排除之；
4. `entry(make_event("RegionBuild", {"region":"事件空间"}))` 建空间 → `entry(ColliderBuild)` 两次 → `sent` 收到两条 `ColliderBuildResult`，取出 `collider_A`/`collider_B`；
5. `ColliderSet` 事件分别为两盒体设几何体（相距 5.0）→ `RegionState`（`active=true`）激活 → `RegionDetect` 得 `DetectResult`，`results` 为空；
6. `ColliderDisplacement`（`-4.0`）把 B 移入重叠位置 → 再 `RegionDetect` → `DetectResult.results` 报告一对碰撞（`collider_A`/`collider_B`）。

### 7.3 目录桩造 + 事件投递用例（配置加载器）

以 `Config_Loader_Test::可信根添加后配置可加载` 为例：

1. `root_make("可信根测试_添加", false)`：建 `<根>/索引`、`<根>/配置` 目录，写回无脏标记路由文件，写 `配置.json`（`{"键":"值"}`）；
2. `loader_attach()`：绑定加载器三端口后 `loader.attach()`；
3. `object_attach()`：以 `object_key=1` 登记订阅对象，投 `Subscribed_Events/Add` 登记订阅清单（订阅 `Test`/`Load`）；
4. `event_send("Believed_Root", "Load", root_payload(root_route, root_config))`：加载可信根，建立缓存并即时投递一次；
5. `event_send("Config", "Load", object_payload())`：请求对象配置加载；
6. 断言 `delivered.size()==1` 且 `delivered[0]->config["键"]=="值"`；
7. 用例结束 → 夹具 `TearDown` 的 `remove_all` 清除该可信根目录。

### 7.4 桩造四叉树 + 检索用例（四叉树管理器）

以 `Quadtree_Manager_Test::范围查询整树返回全部区块` 为例：

1. `Quadtree_Manager<int> manager;`（默认设置：区块单元 16、上下限 128/256…）；
2. `build_one_tree(manager, make_coord(0, 0))`：设上下限 128/256 后 `quadtree_build_smart({(0,0)})`，建成覆盖 `[0,255]×[0,255]` 的树（根 `127.5`、大小 256）；
3. `manager.get(make_range(0, 255, 255, 0), receiver)`：获取模式范围查询；
4. 断言 `receiver.size()==256`（16×16 个最小区块），且每块中心落在 `[0,255]` 管理范围内；
5. `chunk_clean(receiver)` 释放结果集合；用例结束时管理器值成员析构（固定上限 256，可安全析构）。

### 7.5 关键边界分支汇总表

| 场景 | 触发点 | 处理 | 结果 |
| --- | --- | --- | --- |
| 零/极大 ID 查询或卸载 | `find(0)`/`find(UINT64_MAX)`/`unload(0)` | 池内未登记 | 返回超尾 / 只告警不抛 |
| 对象池卸载后重建 | `unload(id)` → `build()` | 复用被回收下标与 ID | 新对象可查、ID 与回收值一致 |
| 事件空分类/空标签 | `receive` 或 `attach` 带空标识 | 丢弃/跳过 | 订阅者不收（登记不生效） |
| 事件定向目标未登记 | `receive` 带未登记 `receiver` | 回落标签广播 | 标签订阅者收到 |
| 事件终端密钥错/未生成 | `send`/`clear`/`attach`/`query` | 拒绝并返回假/空指针 | 状态不落地 |
| 坐标含 NaN | `Point2d` 相等判据 | NaN 一律不等 | 判不等 |
| 四叉树越界检索 | `get` 坐标越出管理范围 | 按回调放行则连续扩大 | 边长翻倍直至容纳或触上限 |
| 四叉树触边长上限 | `get` 远超管理范围 | 不再扩大并通报回调一次 | 边长保持上限、取不到区块 |
| 四叉树退化（递归级数 0） | 区块单元 > 边长一半且 `seek` 单点 | 引擎缺陷（跳过）/ 范围返回空 | 跳过 / 结果为空 |
| 管理器空序列查询 | `seek`/`get` 空管理器 | 只读返回空；获取自动建树 | 空结果 / 建成一棵树 |
| 管理器卸载不存在根坐标 | `quadtree_unload(根集)` | `range_binary_search` 未命中即返回 -1 | 不越界、序列不变 |
| 碰撞体非法几何配置 | `collider_set(json)` | 校验拦截 | 返回假、不进入碰撞世界 |
| 碰撞检测未激活 | `detect()` | 直接返回无值 | `has_value()==false` |
| 碰撞响应缺失 | 收到 `ColliderCollision` 无应答 | 搁置并重发一次 | 仍出 `DetectResult`，不崩溃 |
| 碰撞体跨越边界 | 移出/移入/跨越 | `cross_notices_take` 产 `exit`/`return`/`cross` | 检测前先行发布通知 |
| 配置加载条目缺事件标识 | 条目无 `event_category`/`event_tag` | 条目被驳回 | 订阅者不收 |
| 配置可信根重复加载 | 重复 `Believed_Root/Load` | 已登记即跳过 | 脏标记不重置、不重复投递 |
| 配置卸载后重建 | `Config/Unload` → `Route/Load` | 清缓存后重扫 | 重新投递配置文件正文 |
