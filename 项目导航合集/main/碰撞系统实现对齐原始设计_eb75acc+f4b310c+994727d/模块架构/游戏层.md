## 1. 模块功能

### 1.1 模块定位

游戏层是白银纪元四层仓库的**拓扑最上层**：

```
┌─────────────────────────────┐
│  游戏层（Game）  ← 本文档     │  游戏本体逻辑（当前为空壳）
│  依赖：系统层（SystemCore）   │
├─────────────────────────────┤
│  系统层（System）            │  实体 / 属性 / 效应三大子系统
│  依赖：引擎层（EngineCore）   │
├─────────────────────────────┤
│  引擎层（Engine）            │  对象 / 事件 / 空间划分 / 碰撞 / 工具
└─────────────────────────────┘
```

- **位置**：`D:/代码存储/代码仓库/白银纪元/游戏层`
- **依赖**：系统层（`SystemCore` 静态库）——一律链接「已经构建好的」静态库，不拉入任何下层源码，也没有源码回退路径（层级契约统一）。
- **产物**：`GameCore` 静态库（**当前无源码，尚未产出**）。

### 1.2 模块解决/承担的问题

1. **游戏本体逻辑的归属地**：实体类型如何组合、战斗规则、玩法系统等「游戏玩法」代码未来都落在 `游戏层/src/` 下，与引擎/系统的通用能力分离。
2. **数据驱动的配置资产**：`assets/` 目录承载全部运行时数据——实体配置 JSON、属性槽配置 JSON、格式定义 JSON、路由表 JSON、行为 Lua 脚本、初始化 Lua 脚本。这些资产是引擎层/系统层消费的数据源。
3. **层间契约闭环**：作为四层链路的最上层，游戏层的 `对外接口.cmake` 完整并入系统层（进而并入引擎层）对外面，验证「对外面逐层传递」契约的末端形态。

### 1.3 当前状态（空壳）的事实清单

| 项目 | 现状 |
|---|---|
| `src/` 源码目录 | **不存在**（LS 检查确认：游戏层仅有 `assets/`、`cmake/`、`.gitignore`、`CMakeLists.txt`、`CMakeSettings.json`） |
| `GameCore` 目标 | 未生成（CMake 条件分支跳过，不报错） |
| 可执行文件 | 无（本层不产出可执行文件，全项目唯一可执行文件在测试层 `EngineTests.exe`） |
| `GameCore.lib` 产物 | 不存在（`out/build/*/lib/` 下无该文件） |
| 构建行为 | `cmake --build` 仍可成功：配置期完成「接入系统层 + 空源文件判定」，构建期无编译任务 |

## 2. 模块提供接口

### 2.1 对外接口契约（`游戏层/cmake/对外接口.cmake`）

```cmake
# =============================================================================
# 游戏层 —— 对外接口（对外自描述）
# 位置：游戏层/cmake/对外接口.cmake
# 作用
#     声明「本层向上层提供什么」。上层通过本文件读取本层对外面，据此建立
#     IMPORTED 静态库目标（不使用 add_subdirectory 回退编源码）。
#     游戏层目前是拓扑最上层，还没有使用方；本文件先把边界写清楚，
#     将来测试层要接 GameCore 时不必再补。
# 契约（变量名与含义是层间契约的一部分，改名必须同步上层）
#     BYJY_<P>_OUT_LIB    本层静态库文件名（不含扩展名）；叶层无库时留空
#     BYJY_<P>_OUT_INC    使用本层公共头文件所需的包含目录
#     BYJY_<P>_OUT_DEF    使用本层公共头文件所需的编译定义
#     BYJY_<P>_OUT_LINK   本层对外传递的第三方库（文件路径）
#     BYJY_<P>_OUT_SYS    本层对外传递的系统库
#     本层前缀 <P> = GAME
# 并入下层
#     游戏层依赖系统层，因此本层对外面 = 本层自有面 + 系统层对外面。
#     并入方式就是下面这一句 include：它把系统层的 BYJY_SYSTEM_OUT_* 赋值进来
#     （系统层又并入了引擎层的对外面），本层再在自己的列表里直接引用。
#     纯数据赋值，被重复 include 无副作用。
# =============================================================================

include("${CMAKE_CURRENT_LIST_DIR}/../../系统层/cmake/对外接口.cmake")

get_filename_component(BYJY_GAME_ROOT "${CMAKE_CURRENT_LIST_DIR}/.." ABSOLUTE)

set(BYJY_GAME_OUT_LIB "GameCore")

set(BYJY_GAME_OUT_INC
    "${BYJY_GAME_ROOT}"
    ${BYJY_SYSTEM_OUT_INC}
)

set(BYJY_GAME_OUT_DEF  ${BYJY_SYSTEM_OUT_DEF})
set(BYJY_GAME_OUT_LINK ${BYJY_SYSTEM_OUT_LINK})
set(BYJY_GAME_OUT_SYS  ${BYJY_SYSTEM_OUT_SYS})
```

**逐条解释**：

| 项 | 值 | 含义 |
|---|---|---|
| 首行 include | 系统层对外接口 | 并入系统层对外面（系统层已并入引擎层对外面，因此游戏层对外面 = 自有面 + 系统层面 + 引擎层面，三层全量） |
| `BYJY_GAME_ROOT` | 游戏层目录绝对路径 | 从接口文件位置推导 |
| `BYJY_GAME_OUT_LIB` | `GameCore` | 游戏层静态库文件名（不含扩展名）；**注意：当前 src/ 为空，尚未产出该库**——声明先于产物 |
| `BYJY_GAME_OUT_INC` | 游戏层根目录 + `BYJY_SYSTEM_OUT_INC` | 本层自有包含目录只有根目录（层内以 `"src/..."` 形式互相包含）；系统层对外面整体并入 |
| `BYJY_GAME_OUT_DEF` | `=${BYJY_SYSTEM_OUT_DEF}` | 继承系统层的编译定义（即引擎层的 `GLFW_STATIC`） |
| `BYJY_GAME_OUT_LINK` | `=${BYJY_SYSTEM_OUT_LINK}` | 继承系统层的第三方链接库（`glfw3.lib` 等） |
| `BYJY_GAME_OUT_SYS` | `=${BYJY_SYSTEM_OUT_SYS}` | 继承系统层的系统库（opengl32/user32/gdi32/shell32） |

**备注（源码原文）**：

```
# 备注：GameCore 只在 src/ 下有源文件时才产出（当前 src/ 为空，尚未产出库），
#       此时若真有上层来链接它，会自动探测不到并硬失败 —— 属于预期行为。
#       本层不产出可执行文件，可执行文件只在测试层产生（EngineTests.exe）。
```

### 2.2 构建目标清单

| 目标名 | 类型 | 状态 | 说明 |
|---|---|---|---|
| `GameCore` | STATIC | **条件产出**（`GAME_SOURCES` 非空时） | 当前未生成；未来是游戏逻辑静态库 |
| （无） | EXECUTABLE | — | 本层**不产出**可执行文件 |

**CMake 缓存变量**：

| 变量 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `BYJY_SYSTEM_LIB_PATH` | `FILEPATH` | `""` | 系统层静态库路径覆盖；留空则自动探测 `系统层/out/build/*/lib/SystemCore.lib` |

### 2.3 接入函数调用（`CMakeLists.txt` 第 1 节）

```cmake
include("${CMAKE_CURRENT_SOURCE_DIR}/cmake/接入下层.cmake")

set(BYJY_SYSTEM_LIB_PATH "" CACHE FILEPATH
    "系统层静态库路径；留空则自动探测 系统层/out/build/*/lib/SystemCore.lib")

byjy_jieru_xiaceng(
    "${PROJECT_ROOT_DIR}/../系统层/cmake/对外接口.cmake"
    "BYJY_SYSTEM"
    "BYJY_SYSTEM_LIB_PATH"
)
```

- 复用 `byjy_jieru_xiaceng()`（三份逐字节相同的通用接入函数，详见《构建与层间契约》文档 §2.5）。
- 库定位三级策略：① 覆盖变量非空 → 用它（文件不存在则 FATAL_ERROR）；② 留空 → 自动探测 `系统层/out/build/*/lib/SystemCore.lib` 取时间戳最新；③ 都没有 → FATAL_ERROR 并给出构建系统层的命令。
- 接入系统层即同时取得两层（系统层 + 引擎层）的公共包含路径，因为系统层对外面已并入引擎层对外面。

### 3.2 `CMakeLists.txt` 结构（骨架逐节解析）

```cmake
cmake_minimum_required(VERSION 3.20)          # 与三层一致

if(MSVC)
    add_compile_options(/WX-)                 # 不把警告当错误
endif()

project(游戏层 LANGUAGES C CXX)               # 项目名中文

set(CMAKE_CXX_STANDARD 20)                    # 强制 C++20
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

get_filename_component(PROJECT_ROOT_DIR "${CMAKE_CURRENT_SOURCE_DIR}" ABSOLUTE)

# ── 1. 接入下层：系统层（链接已构建好的静态库）──
include("${CMAKE_CURRENT_SOURCE_DIR}/cmake/接入下层.cmake")
set(BYJY_SYSTEM_LIB_PATH "" CACHE FILEPATH "...")
byjy_jieru_xiaceng(...)

# ── 2. 源文件收集：GLOB_RECURSE src/*.cpp、src/*.c ──
file(GLOB_RECURSE GAME_SOURCES CONFIGURE_DEPENDS
    "${PROJECT_ROOT_DIR}/src/*.cpp"
    "${PROJECT_ROOT_DIR}/src/*.c"
)
if(GAME_SOURCES)
    # 排除构建目录下的文件（正则转义）
    string(REPLACE "\\" "/" SAFE_BINARY_DIR "${CMAKE_BINARY_DIR}")
    string(REGEX REPLACE "([.+*?^$()])" "\\\\\\1" SAFE_BINARY_REGEX "${SAFE_BINARY_DIR}")
    list(FILTER GAME_SOURCES EXCLUDE REGEX "^${SAFE_BINARY_REGEX}/")
endif()

# ── 3. 创建 GameCore（无源码时跳过，不报错）──
if(GAME_SOURCES)
    add_library(GameCore STATIC ${GAME_SOURCES})
    target_include_directories(GameCore PUBLIC "${PROJECT_ROOT_DIR}")
    target_link_libraries(GameCore PUBLIC SystemCore)
    if(MSVC)
        target_compile_options(GameCore PRIVATE /MP /utf-8)
        target_compile_definitions(GameCore PRIVATE _CRT_SECURE_NO_WARNINGS)
    else()
        target_compile_options(GameCore PRIVATE -Wall -Wextra -pedantic)
        target_compile_definitions(GameCore PRIVATE _GNU_SOURCE)
    endif()
    set_target_properties(GameCore PROPERTIES
        ARCHIVE_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib"
        LIBRARY_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib"
    )
    message(STATUS "游戏层源文件: ${GAME_SOURCES}")
else()
    message(STATUS "游戏层暂无源码，未生成 GameCore 目标。")
endif()

# ── 4. 可执行文件：本层不产出 ──
```

**设计要点**：

1. **空源文件不是错误**：与引擎层（`FATAL_ERROR` 强制有源）、系统层（`FATAL_ERROR` 强制有源）不同，游戏层在 `GAME_SOURCES` 为空时**仅打印 STATUS 信息并跳过**——空壳是当前**预期状态**，不允许把「没有代码」当成配置错误。
2. **`target_link_libraries(GameCore PUBLIC SystemCore)`**：链接的是导入目标 `SystemCore`（由 `byjy_jieru_xiaceng` 建立），其 INTERFACE 上挂有系统层+引擎层全部对外面。
3. **本层不产出可执行文件**：过去这里挂着一个「组合根可执行文件」（把引擎层与系统层接在一起从本层启动），以及「把测试层宿主并入本构建树」的开关。两者都已移除（详见 §4.2）。

### 3.4 资产数据体系（数据契约）

游戏层的 `assets/` 是四层中**唯一有实质内容**的部分。它定义了「数据如何描述实体」的契约：

**路由表 `config/route/entity.json`**（配置路径 → 模块）：

```json
[
  { "config_path": "config/entities/牛头人 (Minotaur).json", "module": "Entity_Mangaer" },
  { "config_path": "config/entities/牛头人战士 (Minotaur_Warrior).json", "module": "Entity_Mangaer" },
  { "config_path": "config/entities/哥布林 (Goblin).json",        "module": "Entity_Mangaer" },
  { "config_path": "config/entities/哥布林祭司 (Goblin_Priest).json", "module": "Entity_Mangaer" },
  { "config_path": "config/entities/史莱姆 (Slime).json",         "module": "Entity_Mangaer" },
  { "config_path": "config/entities/史莱姆王 (Slime_King).json",  "module": "Entity_Mangaer" }
]
```

> 注意：源码原文 `module` 值为 `"Entity_Mangaer"`（**拼写错误**，Mangaer 应为 Manager）。这是资产数据里的既有笔误，重开发时需统一（引擎/系统侧的读取方若按 `"Entity_Manager"` 匹配将落空）。

**路由表 `config/route/property.json`**：同样的 6 个实体，`module` 为 `"Property_Manager"`。

**格式定义 `config/format/Entity_Manager.json`**（实体配置的字段契约）：

| 字段 | 类型 | required | 说明 |
|---|---|---|---|
| `type` | string | true | 实体类型标识，保存后配置文件会自动迁移 |
| `decision_load_path` | script | true | 决策树行为脚本路径，相对 `assets/` 目录，Entity_Manager 使用 |
| `acls` | string_list | true | 允许从属的实体类型列表（master 为实体类型自身） |
| `needed_events` | pair_list | true | 订阅事件列表，每项 = [分类, 标签]，如 [Entity, Request] |

另有 `dir: "entities"`、`route: "entity.json"`、`builtin: true`、`module: "Entity_Manager"` 元字段。

**格式定义 `config/format/Property_Manager.json`**：

| 字段 | 类型 | required | 说明 |
|---|---|---|---|
| `type` | string | true | 实体类型标识，与实体配置的 type 一致 |
| `initialize_path` | script | true | 属性槽初始化 Lua 脚本路径，相对 `assets/` 目录，Property_Manager 使用 |

**实体配置实例**（`config/entities/史莱姆 (Slime).json`）：

```json
{
  "type": "Slime",
  "acls": []
}
```

（`config/entities/哥布林 (Goblin).json` 更完整：`acls.master`、`acls.minion_set`、`needed_events` 数组等。）

**属性槽配置实例**（`config/property/史莱姆 (Slime).json`）：

```json
{
  "type": "Slime",
  "initialize_path": "scripts/monster/slime.lua"
}
```

> 注意：`initialize_path` 指向 `scripts/monster/slime.lua`，但当前 `assets/scripts/` 下只有 `behavior/` 与 `initialize/` 两个子目录，**不存在 `monster/` 子目录**——即该脚本路径当前悬空（文件缺失）。这是资产与脚本目录不一致的现状，重开发时需对齐。

**脚本资产**：
- `assets/scripts/behavior/哥布林 (Goblin)_Behavior.lua`：哥布林决策树行为脚本（`Entity::action_load` 加载，脚本须定义 `decision` 函数）。
- `assets/scripts/initialize/哥布林 (Goblin).lua`：哥布林属性槽初始化脚本（属性槽配置加载执行，向属性槽写入初始值）。

## 4. 模块设计/实现细节

### 4.1 空壳设计的意图

游戏层在版次 089b070 没有源码是**有意的阶段性状态**：

1. **分层进度独立**：四层各自独立推进。引擎层（碰撞拆分）、系统层（实体/属性/效应）先行，游戏玩法逻辑尚未开始。
2. **契约先行**：即使没有代码，`CMakeLists.txt`、`对外接口.cmake`、`接入下层.cmake` 已全部就位——将来游戏层写第一行代码时，只需在 `src/` 下放 `.cpp/.c`，`CONFIGURE_DEPENDS` 自动纳入，零 CMake 改动。
3. **数据先行**：`assets/` 的实体/属性/格式/路由 JSON 已经描述了「游戏里有哪些怪物（史莱姆、哥布林、牛头人系列）、每个怪物订阅什么事件、属性怎么初始化」，等于把玩法数据先于代码落盘。

### 4.2 宿主机制取消（历史决策）

`CMakeLists.txt` 第 4 节注释完整记录了这段历史：

```
# 4. 可执行文件：本层不产出
# 过去这里挂着一个组合根可执行文件（把引擎层与系统层接在一起，从本层启动），
# 以及「把测试层宿主并入本构建树」的开关。两者都已移除：
#     1) 宿主机制取消 —— 可执行文件只在测试层产生（EngineTests.exe），
#        各层不再各自维护一个可运行的入口；
#     2) 组合根与宿主职责重叠，且会把下层源码拉进本构建树重复编译，
#        与「层间一律链接已构建静态库」的契约冲突。
# 现在各层的分工：下层各自构建静态库（引擎层 EngineCore、系统层 SystemCore），
# 本层构建 GameCore 静态库，测试层构建唯一可执行文件 EngineTests.exe。
```

**取消的两个机制**：

| 被移除的机制 | 形态 | 移除原因 |
|---|---|---|
| 组合根可执行文件 | 从游戏层启动、把引擎层+系统层接在一起 | 与宿主职责重叠；会把下层源码拉进本构建树重复编译，违反「层间一律链接已构建静态库」契约 |
| 测试层宿主并入开关（`BYJY_JOIN_TEST_HOST`） | CMake 开关，把测试层宿主接进本构建树 | 同上；开关本身在 `CMakeSettings.json` 里残留 |

**现在的职责分工**（全项目）：

| 层 | 产出 |
|---|---|
| 引擎层 | `EngineCore` 静态库 |
| 系统层 | `SystemCore` 静态库 |
| 游戏层 | `GameCore` 静态库（条件产出，当前无） |
| 测试层 | `EngineTests.exe`（**唯一可执行入口**）+ TestCore/TestLauncher/TestGui 静态库 |

**未来游戏入口的路径**（源码注释原文）：「游戏本体将来需要入口时，再在本层单独开一个可执行目标」。

### 4.3 条件构建 `GameCore` 的实现细节

```cmake
if(GAME_SOURCES)
    add_library(GameCore STATIC ${GAME_SOURCES})
    ...
else()
    message(STATUS "游戏层暂无源码，未生成 GameCore 目标。")
endif()
```

**易踩坑点**：

1. **`GameCore` 目标不存在时，上层链接它会在配置期报错**：`对外接口.cmake` 已声明 `BYJY_GAME_OUT_LIB = "GameCore"`，若未来测试层真的去 `byjy_jieru_xiaceng(游戏层对外接口...)`，自动探测 `游戏层/out/build/*/lib/GameCore.lib` 会**找不到而 FATAL_ERROR**——这是源码注释明确标注的「预期行为」。因此**测试层接入游戏层的动作必须发生在游戏层有源码之后**。
2. **GLOB 过滤只排除构建目录**：与系统层不同，游戏层没有 `Tests/`、`Config_Editor` 之类排除规则——将来若有内部测试代码需自行加规则。
3. **`CONFIGURE_DEPENDS` 自动纳入**：在 `src/` 下新建 `.cpp` 无需重跑 cmake，构建时自动检测。

### 4.4 资产数据与系统层代码的对应关系

游戏层资产是系统层运行时的数据源，映射关系（结合《系统层》文档 §4.8）：

| 资产文件 | 系统层消费方 | 对应代码逻辑 |
|---|---|---|
| `config/entities/*.json` 的 `type`/`needed_events`/`decision_load_path` | `Entity_Manager::config_field_parse` / `action_load_path_register` | 校验字段、注册决策树路径、订阅事件 |
| `config/property/*.json` 的 `initialize_path` | `Entity_Manager::prop_load_path_register` | 加载属性槽初始化脚本到 `prop_config_paths` |
| `scripts/behavior/*.lua` | `Entity::action_load` | 加载决策树（须定义 `decision`） |
| `scripts/initialize/*.lua` | `prop_config_paths[type].load_file` | 初始化属性槽 |
| `config/format/*.json` | 配置编辑器 `Config_Editor` | 字段格式定义（编辑器生成/校验配置） |
| `config/route/*.json` | 配置加载流程 | 配置路径 → 模块路由 |

**数据不一致现状（重开发注意）**：

1. `route/entity.json` 的 `module` 拼写为 `"Entity_Mangaer"`（笔误）。
2. `property/史莱姆 (Slime).json` 的 `initialize_path` 指向 `scripts/monster/slime.lua`，但 `assets/scripts/` 下无 `monster/` 目录（悬空路径）。
3. `entities/史莱姆 (Slime).json` 只有 `type` + 空 `acls`，缺 `decision_load_path` / `needed_events`——与 `format/Entity_Manager.json` 的 required 字段契约不符（配置不完整）。
4. `entities/` 与 `property/` 的配置文件名带**空格与括号**（如 `史莱姆 (Slime).json`）——中文+空格路径在 MSVC/Ninja 构建与 googletest 的 ANSI 解析下是已知风险区（参见《构建与层间契约》文档 §4.7 的坑位表）。

### 4.5 与其它层的契约要点（游戏层视角）

| 契约面 | 内容 | 说明 |
|---|---|---|
| 依赖方向 | 游戏层 → 系统层 → 引擎层 | 单向，不反向依赖 |
| 链接方式 | `target_link_libraries(GameCore PUBLIC SystemCore)` | `SystemCore` 是 IMPORTED 导入目标，INTERFACE 上已含两层对外面 |
| 静态库定位 | `BYJY_SYSTEM_LIB_PATH` 覆盖变量 / 自动探测 / FATAL_ERROR | 复用 `byjy_jieru_xiaceng()` 三级策略 |
| 对外面 | `BYJY_GAME_OUT_*` = 自有面 + 系统层面 + 引擎层面 | 链式 include，幂等 |
| C++ 标准 | C++20，`/WX-`，MSVC `/MP /utf-8`，`_CRT_SECURE_NO_WARNINGS` | 与三层一致 |
| 构建目录 | `游戏层/out/build/<配置>/`，库落 `lib/` | 与自动探测路径一致 |

## 5. 模块运行链路

### 5.1 构建时序

```
第 1 步（前置）：构建引擎层
  bash 构建层.sh 引擎层  → 引擎层/out/build/x64-Debug/lib/EngineCore.lib
第 2 步（前置）：构建系统层
  bash 构建层.sh 系统层  → 系统层/out/build/x64-Debug/lib/SystemCore.lib
第 3 步：构建游戏层（当前空壳）
  bash 构建层.sh 游戏层
    ├─ cmake configure
    │   ├─ project(游戏层)
    │   ├─ include 接入下层.cmake
    │   ├─ byjy_jieru_xiaceng(系统层对外接口, BYJY_SYSTEM, BYJY_SYSTEM_LIB_PATH)
    │   │   ├─ include 系统层对外接口（链式并入引擎层对外面）
    │   │   ├─ 校验 BYJY_SYSTEM_OUT_* 五变量
    │   │   ├─ 自动探测 系统层/out/build/*/lib/SystemCore.lib（取最新）
    │   │   └─ add_library(SystemCore STATIC IMPORTED GLOBAL) + INTERFACE 三件套
    │   ├─ GLOB src/*.cpp src/*.c → GAME_SOURCES（当前为空）
    │   └─ GAME_SOURCES 为空 → 跳过 GameCore 目标（STATUS 提示）
    └─ cmake --build
        └─ 无编译任务（无目标），立即成功退出
```

### 5.2 未来「游戏层有源码」的构建时序（预期）

```
1. 在 游戏层/src/ 下放置 GameCore 源文件（如 src/游戏世界.cpp、src/战斗系统.cpp）
2. 下次构建自动触发（CONFIGURE_DEPENDS）
3. add_library(GameCore STATIC ...) 生成
4. GameCore 链接 SystemCore（导入目标，自动继承两层对外面）
5. 产物：游戏层/out/build/x64-Debug/lib/GameCore.lib
6. （可选）测试层接入 GameCore：在测试层 CMakeLists 追加
   byjy_jieru_xiaceng(游戏层对外接口, BYJY_GAME, BYJY_GAME_LIB_PATH)
   —— 注意：此时游戏层必须已产出库，否则探测失败属预期行为
```

### 5.3 运行时链路（数据流视角）

```
assets/config/route/entity.json、property.json
  │（配置加载流程：路由表 → 逐条读取 config_path）
  ▼
assets/config/entities/*.json ──→ Entity_Manager（系统层）──→ 注册决策树路径 / 订阅事件
assets/config/property/*.json ──→ Entity_Manager（系统层）──→ 加载属性槽初始化脚本
assets/scripts/behavior/*.lua ──→ Entity::action_load（系统层）──→ LuaState（decision 函数）
assets/scripts/initialize/*.lua ─→ prop_config_paths[type].load_file（系统层）──→ 属性槽初始化
assets/config/format/*.json ────→ Config_Editor（系统层 gui，未接入构建）──→ 配置编辑/校验
```

**当前闭环状态**：数据已就位，但**执行链路的最后一环（游戏层代码）缺失**——`assets/` 的配置目前只能被系统层的接口消费（需要外部触发 Config 事件），游戏层没有自己的运行时来驱动「配置 → 实体 → 战斗」的完整闭环。这是空壳层与数据先行状态的直接体现。

### 5.4 与其它模块的协作关系

| 协作对象 | 方向 | 机制 |
|---|---|---|
| 系统层 `SystemCore` | 依赖（链接） | IMPORTED 导入目标；运行时消费系统层的事件/实体/属性/效应接口 |
| 引擎层 `EngineCore` | 间接依赖 | 经系统层对外面传递（包含路径/链接库/系统库/GLFW_STATIC） |
| 测试层 `EngineTests` | 未来可选 | 测试层可接入 GameCore 做游戏逻辑测试（当前未接） |
| `assets/` 资产 | 数据源 | 游戏层代码未来读取/驱动资产数据 |
| 配置编辑器 `Config_Editor` | 数据工具 | 编辑 `assets/config/` 下 JSON（编辑器在系统层，未接入构建） |
