## 1. 模块功能

### 1.1 模块定位

「构建与层间契约」不是一个独立的功能模块，而是整个白银纪元项目**四层仓库的组织骨架**。项目采用四层独立仓库结构：

| 层名 | 目录 | 职责 | 构建产物（静态库） |
|---|---|---|---|
| 引擎层 | `白银纪元/引擎层` | 引擎基础能力：对象、事件、空间划分、碰撞、工具链、第三方库（Json/GLFW/bullet3） | `EngineCore.lib` |
| 系统层 | `白银纪元/系统层` | 玩法系统：实体（Entity）、属性（Prop）、效应（Effect）三大子系统，Lua 脚本驱动 | `SystemCore.lib` |
| 游戏层 | `白银纪元/游戏层` | 游戏本体逻辑（当前为空壳，无源码） | `GameCore.lib`（条件产出，当前无） |
| 测试层 | `白银纪元/测试层` | 单元测试与唯一可执行入口 `EngineTests.exe` | `TestCore.lib`、`TestLauncher.lib`、`TestGui.lib`、`EngineTests.exe` |

### 1.2 模块解决的问题

1. **层与层之间的物理隔离**：每一层都是**独立的 CMake 工程**，拥有自己的 `CMakeLists.txt` 与 `out/build/<配置>` 构建目录。层与层之间**一律链接已构建好的静态库**，绝不通过 `add_subdirectory` 把下层源码拉进本构建树重复编译。
2. **对外面的统一自描述**：每一层通过 `<层>/cmake/对外接口.cmake` 声明「本层向上层提供什么」，变量名与含义构成**层间契约的一部分**，改名必须同步上层。
3. **静态库定位的统一策略**：上层消费下层静态库时，通过 `<层>/cmake/接入下层.cmake` 中的通用接入函数 `byjy_jieru_xiaceng()` 完成库定位——三级策略（覆盖变量 → 自动探测最新时间戳 → 硬失败），**任何情况下都不回退编译下层源码**。
4. **MSVC + Ninja 中文路径归档问题**：通过 `ar_rsp_bom.ps1` 包装脚本给归档响应文件补 UTF-8 BOM，解决中文对象名导致的 `LNK1181`。
5. **测试层的特殊地位**：宿主机制取消后，测试层是唯一产出可执行文件的层（`EngineTests.exe`），同时承载单元测试用例。
6. **增量构建对头文件的依赖盲区**：CMake 探测 `/showIncludes` 前缀时不带 `/utf-8`（按系统本地码页输出），而本工程编译带 `/utf-8`（输出 UTF-8 字节），两侧逐字节不等 ⇒ ninja 匹配不到前缀 ⇒ 头文件依赖全部丢失（改头不重编）。修复方式为**配置阶段本身须处于 UTF-8 代码页**（先 `chcp 65001` 再配置），并已以文字固化到顶层与四层 README。详见 §4.10。
7. **头文件与静态库的版次绑定**：各层导出「对外头快照」到构建目录，上层据此按与下层静态库同版次的头编译，消除「下层头已改、库未重建」时的新头配旧库风险。详见 §4.11、§4.12。
8. **IDE / 生成系统的头文件索引**：四层原先只 `GLOB_RECURSE` 收 `.cpp`，头文件从不进入任何 target，VS 报「在当前源文件的目录中或生成系统中未找到文件」；本批四层各补收集头文件并开启 `compile_commands.json` 导出。详见 §4.13。

### 1.3 服务对象

- **开发人员**：通过统一的构建入口（`out/_verify/构建层.sh`）逐层配置与构建；通过层间契约理解「构建某层需要先构建哪些下层」。
- **各层 CMakeLists.txt**：读取下层对外面，建立 IMPORTED 导入目标，挂载包含目录 / 编译定义 / 链接库。
- **测试层**：作为各层的测试产地，同时接入引擎层与系统层。
- **未来上层（如游戏层的使用方）**：通过对外接口文件无感接入 GameCore。

## 2. 模块提供接口

### 2.1 对外接口契约：`BYJY_<P>_OUT_*` 五个变量

**契约来源**：`<层>/cmake/对外接口.cmake` 文件头注释（各层一致）。

每个层必须定义以下五个变量（前缀 `<P>` 按层取 `ENGINE` / `SYSTEM` / `GAME`）：

```cmake
# 契约（变量名与含义是层间契约的一部分，改名必须同步上层）
#     BYJY_<P>_OUT_LIB    本层静态库文件名（不含扩展名）；叶层无库时留空
#     BYJY_<P>_OUT_INC    使用本层公共头文件所需的包含目录
#     BYJY_<P>_OUT_DEF    使用本层公共头文件所需的编译定义
#     BYJY_<P>_OUT_LINK   本层对外传递的第三方库（文件路径）
#     BYJY_<P>_OUT_SYS    本层对外传递的系统库
```

| 变量 | 含义 | 取值示例（引擎层） |
|---|---|---|
| `BYJY_<P>_OUT_LIB` | 静态库文件名（不含扩展名）；叶层（不产出静态库）时留空 | `EngineCore` |
| `BYJY_<P>_OUT_INC` | 使用本层公共头文件所需的**全部**包含目录（含并入的下层目录） | 见 2.2 |
| `BYJY_<P>_OUT_DEF` | 使用本层公共头文件所需的编译定义 | `GLFW_STATIC` |
| `BYJY_<P>_OUT_LINK` | 本层对外传递的第三方库（文件路径列表） | `.../external/glfw/glfw3.lib` |
| `BYJY_<P>_OUT_SYS` | 本层对外传递的系统库 | `opengl32;user32;gdi32;shell32` |

**关键设计**：

- **对外面 = 本层自有面 + 下层对外面**。并入动作由 `<层>/cmake/对外接口.cmake` 直接 `include` 下层接口文件完成。例如系统层：

```cmake
include("${CMAKE_CURRENT_LIST_DIR}/../../引擎层/cmake/对外接口.cmake")
```

这行 include 把引擎层的 `BYJY_ENGINE_OUT_*` 赋值进来，系统层再在自己的列表里直接引用。**纯数据赋值，被重复 include 无副作用**（没有 `include_guard`，但重复赋值结果相同，幂等）。

- **叶层判定**：`BYJY_<P>_OUT_LIB` 为空字符串时表示该层不产出静态库（目前没有这样的层，三层都声明了库名，游戏层虽未产出但已声明 `GameCore`）。

### 2.2 引擎层对外面（`引擎层/cmake/对外接口.cmake`）

**完整内容摘录**：

```cmake
get_filename_component(BYJY_ENGINE_ROOT "${CMAKE_CURRENT_LIST_DIR}/.." ABSOLUTE)

set(BYJY_ENGINE_OUT_LIB "EngineCore")

set(BYJY_ENGINE_OUT_INC
    "${BYJY_ENGINE_ROOT}"
    "${BYJY_ENGINE_ROOT}/external/Json"
    "${BYJY_ENGINE_ROOT}/external/glfw"
    "${BYJY_ENGINE_ROOT}/external"
    "${BYJY_ENGINE_ROOT}/external/bullet3/src"
)

set(BYJY_ENGINE_OUT_DEF
    GLFW_STATIC
)

set(BYJY_ENGINE_OUT_LINK
    "${BYJY_ENGINE_ROOT}/external/glfw/glfw3.lib"
)

set(BYJY_ENGINE_OUT_SYS
    opengl32
    user32
    gdi32
    shell32
)
```

**逐条解释**：

| 项 | 值 | 为什么需要 |
|---|---|---|
| `BYJY_ENGINE_ROOT` | 引擎层目录绝对路径 | 由 `get_filename_component(..., ABSOLUTE)` 从接口文件位置推导，不依赖调用方的工作目录 |
| `BYJY_ENGINE_OUT_LIB` | `EngineCore` | 引擎层静态库文件名（不含扩展名）；导入目标名与库名一致 |
| `OUT_INC` 第 1 项 | 引擎层根目录 | 上层要 include `common/前置头文件包含.h`、`src/core/...` 等引擎层公共头 |
| `OUT_INC` 第 2 项 | `external/Json` | 预编译头 `common/前置头文件包含.h` 内部 include 了 `<nlohmann/json.hpp>`，上层只要 include 该预编译头就需要这条路径 |
| `OUT_INC` 第 3 项 | `external/glfw` | 预编译头内部 include 了 `<GLFW/glfw3.h>` |
| `OUT_INC` 第 4 项 | `external` | 原有声明保留 |
| `OUT_INC` 第 5 项 | `external/bullet3/src` | `src/core/spatial/collision` 下的公共头引用 bullet3 头文件，上层包含这些头同样需要 |
| `OUT_DEF` | `GLFW_STATIC` | 确保 GLFW 头文件按静态库模式编译（避免 dllimport 冲突） |
| `OUT_LINK` | `external/glfw/glfw3.lib` | GLFW 静态库文件路径（引擎层 CMakeLists 里以 `${GLFW_ROOT}/glfw3.lib` 形式链接，此处是文件路径形式） |
| `OUT_SYS` | `opengl32 user32 gdi32 shell32` | MSVC 下 GLFW 依赖的 Windows 系统库 |

> **说明（本批改动）**：原 `OUT_INC` 中的 `external/glm` 条目已移除——`external/glm` 目录不存在，且引擎层源码经检索已无任何 glm 引用（详见 §4.14）。保留该路径会使上层在 CMake 生成阶段直接报 `Imported target "EngineCore" includes non-existent path`。

**注意**：引擎层 `CMakeLists.txt` 里这些包含路径是 **PRIVATE** 的，本文件是按「上层实际需要什么」重新声明的对外面，**两侧出现差异时以对外接口文件为准**。这是刻意的双轨设计——PRIVATE 路径只管本层编译，对外面管上层消费。

### 2.3 系统层对外面（`系统层/cmake/对外接口.cmake`）

**完整内容摘录**：

```cmake
include("${CMAKE_CURRENT_LIST_DIR}/../../引擎层/cmake/对外接口.cmake")

get_filename_component(BYJY_SYSTEM_ROOT "${CMAKE_CURRENT_LIST_DIR}/.." ABSOLUTE)

set(BYJY_SYSTEM_OUT_LIB "SystemCore")

set(BYJY_SYSTEM_OUT_INC
    "${BYJY_SYSTEM_ROOT}"
    "${BYJY_SYSTEM_ROOT}/src"
    "${BYJY_SYSTEM_ROOT}/external/Sol2/include"
    "${BYJY_SYSTEM_ROOT}/external/Lua"
    ${BYJY_ENGINE_OUT_INC}
)

set(BYJY_SYSTEM_OUT_DEF  ${BYJY_ENGINE_OUT_DEF})
set(BYJY_SYSTEM_OUT_LINK ${BYJY_ENGINE_OUT_LINK})
set(BYJY_SYSTEM_OUT_SYS  ${BYJY_ENGINE_OUT_SYS})
```

**逐条解释**：

| 项 | 值 | 为什么需要 |
|---|---|---|
| 首行 include | 引擎层对外接口 | 并入引擎层对外面：系统层对外面 = 自有面 + 引擎层对外面 |
| `BYJY_SYSTEM_ROOT` | 系统层目录绝对路径 | 同上 |
| `OUT_LIB` | `SystemCore` | 系统层静态库文件名 |
| `OUT_INC` 第 1 项 | 系统层根目录 | 层内以 `"entity/..."` 形式互相包含（如 `实体管理器.h` include `"entity/Entity/实体.h"`） |
| `OUT_INC` 第 2 项 | 系统层 `src` | 宿主与上层以 `"entity/Entity/实体.h"` 形式引用 |
| `OUT_INC` 第 3 项 | `external/Sol2/include` | 公共头 `src/entity/Entity/实体.h` 与 `src/effect/Effect/效应.h` 对外暴露 `LuaState`（= `sol::state` 别名），`common/external/Sol2/` 下的包装头也直接用 `sol::` 类型 |
| `OUT_INC` 第 4 项 | `external/Lua` | Sol2 依赖的 Lua 解释器头文件 |
| `OUT_INC` 第 5 项 | `${BYJY_ENGINE_OUT_INC}` | 引擎层对外面整体并入 |
| `OUT_DEF/LINK/SYS` | 直接引用引擎层 | 系统层自身不新增第三方链接需求 |

**备注一**：Sol2 / Lua 必须在对外包含目录里——因为「使用本层公共头文件」必然要解析 `LuaState`。SystemCore 自身编译也依赖同一份声明。

**备注二**：系统层 `external/` 下的 Dear_ImGui、glad、glfw、glm、stb **未列入**对外面——它们目前不被 SystemCore 源文件直接引用（唯一直接引用 stb_image.h 的 `src/gui/Config_Editor/` 含独立 main()，已排除在静态库之外；glfw 由引擎层对外面提供同一份能力）。将来把配置编辑器接进来时需要一起补上。**附**：引擎层 `external/glm` 已移除（见 §4.14），故系统层 `external/glm` 不再有「引擎层对外面提供同一份能力」的说法——它目前仅作为本层副本存在，未被 SystemCore 引用。

### 2.5 接入函数：`byjy_jieru_xiaceng()` 与头快照契约函数

**来源**：`<层>/cmake/接入下层.cmake`（系统层 / 测试层 / 游戏层三份**逐字节相同**，改动必须同步三层）。

**函数签名**：

```cmake
function(byjy_jieru_xiaceng interface_file prefix override_var)
```

| 参数 | 含义 | 示例 |
|---|---|---|
| `interface_file` | 下层对外接口文件绝对路径 | `${PROJECT_ROOT_DIR}/../引擎层/cmake/对外接口.cmake` |
| `prefix` | 下层对外接口变量前缀 | `BYJY_ENGINE` |
| `override_var` | 覆盖库路径的缓存变量名 | `BYJY_ENGINE_LIB_PATH` |

**调用示例**（系统层接引擎层）：

```cmake
include("${CMAKE_CURRENT_SOURCE_DIR}/cmake/接入下层.cmake")

set(BYJY_ENGINE_LIB_PATH "" CACHE FILEPATH
    "引擎层静态库路径；留空则自动探测 引擎层/out/build/*/lib/EngineCore.lib")

byjy_jieru_xiaceng(
    "${PROJECT_ROOT_DIR}/../引擎层/cmake/对外接口.cmake"
    "BYJY_ENGINE"
    "BYJY_ENGINE_LIB_PATH"
)
```

**函数行为（对照源码逐步展开）**：

1. **接口文件存在性校验**：`if(NOT EXISTS "${interface_file}")` → `FATAL_ERROR`，给出期望位置。
2. **读入下层对外面**：`include("${interface_file}")`，此时下层的五个 `_OUT_*` 变量（含其自身已并入的更下层对外面）进入当前作用域。
3. **五变量完整性校验**：对 `<prefix>_OUT_LIB/INC/DEF/LINK/SYS` 逐个检查 `DEFINED`，缺失则 `FATAL_ERROR`。
4. **叶层短路**：若 `<prefix>_OUT_LIB` 为空字符串，`message(STATUS "不产出静态库，跳过库定位")` 后直接 `return()`。
5. **库定位三级策略**（详见 §4.4）。
6. **建立导入目标**：

```cmake
if(NOT TARGET ${_lib_name})
    add_library(${_lib_name} STATIC IMPORTED GLOBAL)
endif()
set_target_properties(${_lib_name} PROPERTIES IMPORTED_LOCATION "${_lib_file}")
set_target_properties(${_lib_name} PROPERTIES
    INTERFACE_INCLUDE_DIRECTORIES "${_include_dirs}"
    INTERFACE_COMPILE_DEFINITIONS "${_compile_defs}"
    INTERFACE_LINK_LIBRARIES "${_link_libs};${_system_libs}"
)
```

   - 目标名为下层库名（如 `EngineCore`），`STATIC IMPORTED GLOBAL`——GLOBAL 作用域使该目标在整个构建树可见（函数内建目标默认只在函数作用域可见，GLOBAL 是必须的）。
   - `IMPORTED_LOCATION` 指向定位到的 `.lib` 文件。
   - 包含目录 / 编译定义 / 链接库（第三方库 + 系统库合并）挂到 **INTERFACE** 上，供本层向上继续传递（`target_link_libraries` 传播）。

**本批新增的两个头快照契约函数**（同文件，三份逐字节相同；详见 §4.12）：

```cmake
# 按路径前缀换算一串包含目录（PARENT_SCOPE 写回结果变量），不做存在性校验
function(byjy_kuaizhao_lujing out_var snapshot_root source_root inc_dirs)

# 切换导入目标的包含面：把「下层源码树包含目录」改指该层构建目录的头快照；
# 快照目录缺失 → FATAL_ERROR，不静默退回源码树
function(byjy_qiehuan_tou_kuaizhao target_name snapshot_root source_root)
```

`byjy_qiehuan_tou_kuaizhao()` 内部复用 `byjy_kuaizhao_lujing()`。**关键坑**：`byjy_kuaizhao_lujing()` 存在的直接原因是 `SystemCore` 是**普通库目标**（非导入目标），其自身编译包含路径由 `INCLUDE_DIRECTORIES` 决定，只 `set_target_properties(... INTERFACE_INCLUDE_DIRECTORIES ...)` 不会生效；普通库目标必须改 `target_include_directories`，导入目标才用 `INTERFACE_*`。当前调用方为系统层（消费引擎快照 + 导出自身快照）与测试层（消费引擎/系统两份快照）。

### 2.7 构建目标清单（全项目）

| 目标名 | 类型 | 产出层 | 产物 | 说明 |
|---|---|---|---|---|
| `EngineCore` | STATIC | 引擎层 | `EngineCore.lib` | 引擎核心静态库 |
| `EngineIncludeSnapshot` | CUSTOM (`ALL`) | 引擎层 | 无（镜像到 `<构建目录>/include`） | 常驻目标，每轮构建导出引擎层对外头快照（235 头，含第三方头）；详见 §4.11 |

| `GameCore` | STATIC（条件） | 游戏层 | `GameCore.lib` | 仅 `GAME_SOURCES` 非空时产出 |
| `TestCore` | STATIC（条件） | 测试层 | `TestCore.lib` | 仅 `TEST_SOURCES` 非空时产出 |
| `TestLauncher` | STATIC | 测试层 | `TestLauncher.lib` | Test_Selection_Model + 控制台菜单（纯逻辑） |

| `EngineTests` | EXECUTABLE | 测试层 | `EngineTests.exe` | 本层唯一可执行文件（全项目唯一入口） |
| `GTest::gtest` | IMPORTED | 测试层 | googletest | `EXCLUDE_FROM_ALL` 接入，被依赖时才编译 |

### 3.2 引擎层 `CMakeLists.txt` 结构（自上而下）

```cmake
cmake_minimum_required(VERSION 3.20)

if(MSVC)
    add_compile_options(/WX-)          # 不把警告当错误（项目既有大量告警）
endif()

project(引擎层 LANGUAGES CXX)          # 项目名支持中文

# 导出编译数据库（供 IDE / 语言工具链读取本层包含路径与宏；Ninja 生成器默认不产出）
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

# —— 归档响应文件 BOM 包装器（见 §4.1）——
if(MSVC AND CMAKE_GENERATOR MATCHES "Ninja")
    set(BYJY_AR_WRAPPER "${CMAKE_CURRENT_SOURCE_DIR}/cmake/ar_rsp_bom.ps1")
    find_program(BYJY_POWERSHELL_EXECUTABLE NAMES powershell powershell.exe)
    if(EXISTS "${BYJY_AR_WRAPPER}" AND BYJY_POWERSHELL_EXECUTABLE)
        set(CMAKE_CXX_CREATE_STATIC_LIBRARY
            "${BYJY_POWERSHELL_EXECUTABLE} -NoProfile -ExecutionPolicy Bypass -File ${BYJY_AR_WRAPPER} <CMAKE_AR> /nologo <LINK_FLAGS> /out:<TARGET> <OBJECTS> ")
    else()
        message(WARNING "...")
    endif()
endif()

# 强制 C++20
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# 源文件收集：GLOB_RECURSE + CONFIGURE_DEPENDS
file(GLOB_RECURSE ENGINE_SOURCES CONFIGURE_DEPENDS
    "${PROJECT_ROOT_DIR}/src/*.cpp"
    "${PROJECT_ROOT_DIR}/common/*.cpp"
    "${PROJECT_ROOT_DIR}/external/*.cpp"
)
# 头文件收集：仅供 IDE 与生成系统建立索引（不参与编译，external/ 第三方头不纳入）
file(GLOB_RECURSE ENGINE_HEADERS CONFIGURE_DEPENDS
    "${PROJECT_ROOT_DIR}/src/*.h"   "${PROJECT_ROOT_DIR}/src/*.hpp"
    "${PROJECT_ROOT_DIR}/common/*.h" "${PROJECT_ROOT_DIR}/common/*.hpp"
)
# 过滤：源文件与头文件均排除构建目录下的文件（正则转义处理）
# 空源文件 → FATAL_ERROR

add_library(EngineCore STATIC ${ENGINE_SOURCES} ${ENGINE_HEADERS})
target_include_directories(EngineCore PRIVATE "${PROJECT_ROOT_DIR}")

# 第三方包含：Json / glfw / bullet3（均为 PRIVATE；glm 条目已随目录移除而删除）
set(JSON_ROOT   "${PROJECT_ROOT_DIR}/external/Json")
set(GLFW_ROOT   "${PROJECT_ROOT_DIR}/external/glfw")
set(BULLET_ROOT "${PROJECT_ROOT_DIR}/external/bullet3/src")

# §5.5 对外头快照导出（常驻目标，见 §4.11）：每轮构建镜像到 <构建目录>/include
add_custom_target(EngineIncludeSnapshot ALL
    COMMAND "${CMAKE_COMMAND}"
        "-DSRC_ROOT=${PROJECT_ROOT_DIR}"
        "-DDST_ROOT=${CMAKE_BINARY_DIR}/include"
        "-DMIRROR_DIRS=common;src;external/Json;external/glfw;external/bullet3/src"
        -P "${PROJECT_ROOT_DIR}/cmake/导出头快照.cmake"
    VERBATIM
)

# 链接
find_package(OpenGL REQUIRED)
target_link_libraries(EngineCore PUBLIC
    "${GLFW_ROOT}/glfw3.lib"
    OpenGL::GL
)
target_compile_definitions(EngineCore PUBLIC GLFW_STATIC)
if(MSVC)
    target_link_libraries(EngineCore PUBLIC opengl32.lib user32.lib gdi32.lib shell32.lib)
endif()

# 编译选项
if(MSVC)
    target_compile_options(EngineCore PRIVATE /MP /utf-8)
    target_compile_definitions(EngineCore PRIVATE _CRT_SECURE_NO_WARNINGS)
else()
    target_compile_options(EngineCore PRIVATE -Wall -Wextra -pedantic)
    target_compile_definitions(EngineCore PRIVATE _GNU_SOURCE)
endif()

# 输出目录
set_target_properties(EngineCore PROPERTIES
    ARCHIVE_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib"
)

# 安装规则（可选部署）
install(DIRECTORY "${PROJECT_ROOT_DIR}/"
    DESTINATION "include/EngineCore"
    FILES_MATCHING PATTERN "*.h" PATTERN "*.hpp"
    PATTERN "Private" EXCLUDE
)
install(TARGETS EngineCore
    ARCHIVE DESTINATION "lib"
    LIBRARY DESTINATION "lib"
    RUNTIME DESTINATION "bin"
)
```

**要点**：

- `GLOB_RECURSE ... CONFIGURE_DEPENDS`：让 CMake 在**构建时**自动检测新增/删除的源文件，不必手动重新运行 cmake 配置。
- 源文件收集覆盖 `src/`、`common/`、`external/` 三个目录下的 `.cpp` 与 `.c`（`external/*.cpp` 意味着 bullet3 的源码会被编进 EngineCore——这也是 BOM 包装器存在的直接原因，bullet3 部分源文件含中文对象名）。
- 过滤构建目录：将 `CMAKE_BINARY_DIR` 反斜杠转正斜杠、正则转义后，`list(FILTER ... EXCLUDE REGEX "^${SAFE_BINARY_REGEX}/")` 排除构建目录内的文件。
- `/WX-` 在文件顶部全局设置：**不把警告当错误**（项目存在 C4005/C4715/C4828 等既有告警，见 §4.7）。
- `_CRT_SECURE_NO_WARNINGS`：Lua 使用传统 C 函数（fopen 等），禁用安全警告。
- `install` 规则将 `.h/.hpp` 安装到 `include/EngineCore`（排除 `Private` 子目录），静态库安装到 `lib`。当前主要供部署参考，实际层间链接走的是 out/build 目录（见 §4.4）。

    ${BYJY_SYSTEM_OUT_LINK}

- `/Tests/` 排除：系统层 src 下若存在功能测试代码不编入静态库。

### 3.4 测试层 `CMakeLists.txt` 结构

```cmake

include("${CMAKE_CURRENT_SOURCE_DIR}/cmake/接入下层.cmake")
set(BYJY_ENGINE_LIB_PATH "" CACHE FILEPATH "...")

#   用例不并入 TestCore：静态库里未被引用的 .obj 会被链接器丢弃，
#   TEST 宏的静态注册会随之丢失，用例便静默不跑。
if(TEST_SOURCES)
    add_library(TestCore STATIC ${TEST_SOURCES} ${TEST_HEADERS})   # 头文件仅供索引
    target_link_libraries(TestCore PUBLIC EngineCore SystemCore)
endif()

# TestGui：Dear ImGui + glad（不编 imgui_demo.cpp）
#   不编 imgui_demo.cpp（示例窗口用不到）；opengl3 后端自带 loader，另编 glad

#   后者没有引擎包含路径），用例经可执行文件同名符号解析
add_executable(EngineTests
    $<TARGET_OBJECTS:EngineTestObjects>
    ${MAIN_HEADERS}
    "${PROJECT_ROOT_DIR}/src/主调/主程序.cpp"
    "${PROJECT_ROOT_DIR}/src/主调/图形选择窗口.cpp"
    "${PROJECT_ROOT_DIR}/src/主调/引擎日志屏蔽.cpp"

    include(GoogleTest)
    gtest_discover_tests(EngineTests WORKING_DIRECTORY "${PROJECT_ROOT_DIR}")
else()
    add_test(NAME EngineTests COMMAND EngineTests --selector=off
        WORKING_DIRECTORY "${PROJECT_ROOT_DIR}")
endif()

**要点**：

- **`gtest_force_shared_crt ON`**：强制共享运行时库，避免与引擎层的 CRT 设置冲突（LNK2038 链接错误）。
- **`RUNTIME_OUTPUT_DIRECTORY` 指向本层根目录**：`Engine_Env` 以「可执行文件所在目录」为基准解析资源路径，这是硬性要求；产物与 `assets/` 同级。
- **ctest 中文路径退化**：`gtest_discover_tests` 以 `--gtest_output=json:<文件>` 枚举用例，而 googletest 写该报告文件时按 ANSI 代码页解析路径；工程路径含中文（本项目正是中文路径 `D:/代码存储/...`）时必然失败（`[FATAL] Unable to open file ...cmake_test_discovery_*.json`），构建会被判失败。因此路径为**纯 ASCII** 时才启用逐用例注册，否则退化为整体注册一个用例，并提示 `EngineTests.exe --gtest_filter=xxx` 手动筛选。
- **主程序不链接 `GTest::gtest_main`**：main 由本层主调提供（`src/主调/主程序.cpp`）。
- **`EXCLUDE_FROM_ALL`**：googletest 只在被测试目标依赖时编译，不改变静态库的既有构建范围。
- 图形选择窗口（依赖 ImGui）**只编进 EngineTests.exe**，不并入 TestLauncher，使用例不必拖上图形库。

    "${PROJECT_ROOT_DIR}/src/*.h" "${PROJECT_ROOT_DIR}/src/*.hpp")

# 有源码才建 GameCore；无源码跳过，不报错
if(GAME_SOURCES)
    add_library(GameCore STATIC ${GAME_SOURCES} ${GAME_HEADERS})
    target_include_directories(GameCore PUBLIC "${PROJECT_ROOT_DIR}")
    target_link_libraries(GameCore PUBLIC SystemCore)
    # 编译选项 / 输出目录同下层
else()
    message(STATUS "游戏层暂无源码，未生成 GameCore 目标。")
endif()
# 不产出可执行文件
```

### 3.6 构建流程分层（配置期 → 构建期）

**配置期（cmake configure）**：

0. **前提：配置进程须处于 UTF-8 代码页**（先 `chcp 65001` 再配置）——否则 CMake 探测出的 `/showIncludes` 前缀为本地码页字节，与本工程 `/utf-8` 编译输出逐字节不等，头依赖将全部丢失（见 §4.10）。
1. 读 `CMakeLists.txt` → `project()` → 设定 C++20 → 开启 `CMAKE_EXPORT_COMPILE_COMMANDS`。
2. 引擎层：`if(MSVC AND Ninja)` 分支先安装 BOM 包装器（必须在 `project()` 之后！），再 GLOB 源文件与头文件、建 `EngineCore` 目标，最后挂 `EngineIncludeSnapshot ALL` 常驻目标（§5.5）。
3. 上层：`include 接入下层.cmake` → 定义缓存变量 → `byjy_jieru_xiaceng()` 读下层对外接口 → 三级定位 `.lib` → 建 `IMPORTED STATIC GLOBAL` 目标 → 挂 INTERFACE 属性。
4. 需要头快照语义的层（系统层 / 测试层）：由 `IMPORTED_LOCATION` 推出下层构建目录 → `byjy_kuaizhao_lujing()` / `byjy_qiehuan_tou_kuaizhao()` 把包含目录改指下层快照；**快照缺失即 `FATAL_ERROR`**（见 §4.12）。
5. 本层源文件 GLOB 与过滤 → 建本层静态库目标 → PUBLIC 面取自对外接口（系统层用换算后的快照路径）→ 链接导入目标；系统层再挂 `SystemIncludeSnapshot ALL`（§3.6）。
6. 生成器（Ninja）写出构建规则与响应文件。

**构建期（cmake --build）**：

1. Ninja 依据依赖图编译各 `.cpp`（MSVC `/MP` 多核并行）。
2. 归档阶段调用 `CMAKE_CXX_CREATE_STATIC_LIBRARY`（已替换为 PowerShell 包装）→ `ar_rsp_bom.ps1` 给 `.rsp` 补 BOM → `lib.exe` 归档 → `EngineCore.lib` 落到 `<构建目录>/lib/`。
3. 常驻快照目标执行：`EngineIncludeSnapshot` / `SystemIncludeSnapshot` 分别镜像本层对外头到 `<构建目录>/include`（`ONLY_IF_DIFFERENT`，未变头保持原 mtime）。
4. `CONFIGURE_DEPENDS` 触发 GLOB 校验：源文件增删时自动重跑配置逻辑。

## 4. 模块设计/实现细节

### 4.1 归档响应文件 BOM 包装器（`ar_rsp_bom.ps1`）

**问题背景**：Ninja 生成器写出的归档响应文件（`*.rsp`，内含 `lib.exe` 的输入对象列表）是 **UTF-8 无 BOM**。MSVC 命令行工具（lib.exe）在没有 BOM 时按**系统 ANSI 代码页**解读响应文件，文件里的**中文对象名**会被解成乱码，`lib.exe` 找不到对应文件，报 **LNK1181**。

**为什么会有中文对象名**：引擎层 GLOB 收集了 `external/*.cpp`（bullet3 源码编进 EngineCore），编译产物 `.obj` 的文件名继承源文件中文名（如 `碰撞代理器.cpp.obj`），响应文件里就出现了中文路径。

**做法**：把归档命令换成「先给响应文件补 BOM，再调用真实归档器」的 PowerShell 包装脚本，使源文件名保持中文、bullet3 继续留在 EngineCore 内。

**CMake 侧接线**（必须在 `project()` 之后设置，否则会被 `Platform/Windows-MSVC.cmake` 的默认值覆盖回去）：

```cmake
if(MSVC AND CMAKE_GENERATOR MATCHES "Ninja")
    set(BYJY_AR_WRAPPER "${CMAKE_CURRENT_SOURCE_DIR}/cmake/ar_rsp_bom.ps1")
    find_program(BYJY_POWERSHELL_EXECUTABLE NAMES powershell powershell.exe)
    if(EXISTS "${BYJY_AR_WRAPPER}" AND BYJY_POWERSHELL_EXECUTABLE)
        set(CMAKE_CXX_CREATE_STATIC_LIBRARY
            "${BYJY_POWERSHELL_EXECUTABLE} -NoProfile -ExecutionPolicy Bypass -File ${BYJY_AR_WRAPPER} <CMAKE_AR> /nologo <LINK_FLAGS> /out:<TARGET> <OBJECTS> ")
    endif()
endif()
```

**脚本处理规则**（对照源码逐条）：

1. 第一个参数是真实归档器路径（`<CMAKE_AR>` 展开），其余参数原样转交。
2. 遍历参数，只处理以 `@` 开头的响应文件参数（`$arg.StartsWith('@')`）。
3. 对响应文件读字节：
   - **已有 UTF-8 BOM**（前 3 字节 `EF BB BF`）→ 不改动；
   - **内容全是 ASCII**（无 >0x7F 字节）→ 与代码页无关，不改动；
   - 否则在文件开头补 `EF BB BF` 三个字节，其余字节原样搬运（`New-Object byte[] (bytes.Length+3)` + `Array::Copy`）。
4. 调用真实归档器 `& $arExe @arArgs`，**原样透传退出码**（`exit $LASTEXITCODE`）。
5. 诊断开关：环境变量 `BYJY_AR_WRAPPER_DISABLE_BOM=1` 可跳过补 BOM，仅用于故障对照实验。

**生效范围**：**只对 Ninja 生成器生效**，避免影响 Visual Studio 生成器（其归档由 MSBuild 的 Lib 任务完成，不需要 BOM 包装）。

**易踩坑点**：
- `CMAKE_CXX_CREATE_STATIC_LIBRARY` 若在 `project()` 之前设置，会被 `Platform/Windows-MSVC.cmake` 的默认值**覆盖回去**——这是 CMake 内部在 `project()` 期间加载平台模块导致的，必须先 `project()` 再覆盖。
- 若找不到包装脚本或 PowerShell，只发 `WARNING` 不中断——此时中文对象名归档会报 LNK1181，属于已知降级路径。

### 4.2 函数名为什么是拼音

CMake 的**命令名只能是 ASCII 标识符**。写成 `byjy_接入下层` 会在调用处直接报 `Parse error. Expected a command name, got unquoted argument`。所以用拼音拼写，读作「byjy 接入下层」。变量名同理，全部使用 ASCII（`BYJY_ENGINE_OUT_LIB` 等）。这是中文项目里 CMake 命令名的硬约束，后续新增函数/变量必须保持 ASCII。

### 4.3 三份 `接入下层.cmake` 逐字节相同

系统层 / 测试层 / 游戏层各维护一份 `cmake/接入下层.cmake`，**三份必须逐字节一致，改动时同步三层**。这是刻意为之的「冗余一致性」设计：每层都能独立配置构建，不依赖其它层的构建脚本目录。同步靠人工纪律，注释头部有醒目标注：「三个副本必须保持一致，改动时同步三层」。

本批该文件含三个函数：`byjy_jieru_xiaceng()`（库定位，见 §2.5、§4.4、§4.5）、`byjy_kuaizhao_lujing()` 与 `byjy_qiehuan_tou_kuaizhao()`（头快照路径换算/切换，见 §2.5、§4.12）。**三份逐字节同步的范围包含这三个函数**——本批新增两个函数时即同步了系统层、测试层、游戏层三份。

### 4.4 库定位三级策略（不回退编源码）

`byjy_jieru_xiaceng()` 的库定位逻辑（任何情况下都不回退编译下层源码）：

```
① 覆盖变量非空且指向已存在的文件 → 用它
   覆盖变量非空但文件不存在       → FATAL_ERROR，不静默降级
② 覆盖变量为空 → 扫 <下层>/out/build/<配置>/lib/<库名>.lib
   多个候选取时间戳最新的一份
③ 仍没有 → FATAL_ERROR，并给出构建下层的命令
```

**① 覆盖变量优先**（源码）：

```cmake
set(_lib_file "")
set(_override_value "${${override_var}}")
if(NOT "${_override_value}" STREQUAL "")
    if(EXISTS "${_override_value}")
        set(_lib_file "${_override_value}")
    else()
        message(FATAL_ERROR
            "接入下层：${override_var} 指向的文件不存在\n"
            "  该变量一旦非空就不再自动探测，也不会退回编译下层源码。\n"
            "  请改成正确路径，或把它置空后改用自动探测。")
    endif()
endif()
```

注意：**覆盖变量一旦非空就不再自动探测**，即使路径写错了也不会降级，直接硬失败——这是防「静默用错库」的设计。

**② 自动探测最新时间戳**（源码）：

```cmake
file(GLOB _candidates "${_layer_dir}/out/build/*/lib/${_lib_name}.lib")
set(_newest_stamp "0")
foreach(_candidate IN LISTS _candidates)
    file(TIMESTAMP "${_candidate}" _candidate_stamp "%Y%m%d%H%M%S")
    if(_candidate_stamp GREATER _newest_stamp)
        set(_newest_stamp "${_candidate_stamp}")
        set(_lib_file "${_candidate}")
    endif()
endforeach()
```

- 探测路径是 `<下层>/out/build/*/lib/<库名>.lib`——通配 `*` 匹配任意配置目录名（`x64-Debug` 等），所以**同一下层存在多个构建配置时取时间戳最新的一份**。
- 时间戳格式 `%Y%m%d%H%M%S` 保证字符串比较即时间比较。

**③ 硬失败**（源码）：

```cmake
message(FATAL_ERROR
    "接入下层：找不到 ${_layer_name} 的静态库 ${_lib_name}.lib\n"
    "  本函数不会退回编译下层源码，请先构建下层：\n"
    "      cmake -S \"${_layer_dir}\" -B \"${_layer_dir}/out/build/x64-Debug\" -G Ninja\n"
    "      cmake --build \"${_layer_dir}/out/build/x64-Debug\"\n"
    "  或显式指定库路径：\n"
    "      cmake -S <本层目录> -B <构建目录> -D${override_var}=<${_lib_name}.lib 绝对路径>")
```

错误信息自带排障指引：给出构建下层的完整命令与显式指定库路径的方法。

### 4.5 IMPORTED 导入目标与 INTERFACE 属性挂载

```cmake
if(NOT TARGET ${_lib_name})
    add_library(${_lib_name} STATIC IMPORTED GLOBAL)
endif()
set_target_properties(${_lib_name} PROPERTIES IMPORTED_LOCATION "${_lib_file}")
set_target_properties(${_lib_name} PROPERTIES
    INTERFACE_INCLUDE_DIRECTORIES "${_include_dirs}"
    INTERFACE_COMPILE_DEFINITIONS "${_compile_defs}"
    INTERFACE_LINK_LIBRARIES "${_link_libs};${_system_libs}"
)
```

- `STATIC IMPORTED`：声明为「外部静态库」，不参与本层编译，只提供链接信息。
- **`GLOBAL` 关键字**：函数内 `add_library` 的目标默认作用域仅限函数，`GLOBAL` 使其在整个构建树可见——否则后续 `target_link_libraries(SystemCore PUBLIC EngineCore)` 会因找不到目标而失败。
- `IMPORTED_LOCATION` 指向真实 `.lib` 绝对路径。
- `INTERFACE_*` 三件套把下层的对外面（包含目录 / 编译定义 / 链接库+系统库）挂到导入目标上，本层目标链接该导入目标时自动继承——这就是「对外面逐层传递」的机制载体。
- 若目标已存在（多次 include 同名下层），`if(NOT TARGET)` 跳过重复创建，只更新属性（幂等）。

### 4.6 测试层特殊处理：OBJECT 库与 ctest 中文路径退化

**为什么用例用 OBJECT 库而非静态库**：静态库里未被引用的 `.obj` 会被链接器**丢弃**，`TEST` 宏的静态注册会随之丢失，用例便**静默不跑**（不报错，只是测试数量少了）。`EngineTestObjects` 用 OBJECT 库收集用例源，`EngineTests.exe` 通过 `$<TARGET_OBJECTS:EngineTestObjects>` 直接取 `.obj` 编入——每个用例的注册代码都保留。

**ctest 中文路径退化**（源码）：

```cmake
if("${PROJECT_ROOT_DIR}" MATCHES "^[ -~]+$")
    include(GoogleTest)
    gtest_discover_tests(EngineTests WORKING_DIRECTORY "${PROJECT_ROOT_DIR}")
else()
    add_test(NAME EngineTests COMMAND EngineTests --selector=off
        WORKING_DIRECTORY "${PROJECT_ROOT_DIR}")
endif()
```

- `gtest_discover_tests` 在**构建期**运行被测程序枚举用例，写 `cmake_test_discovery_*.json` 报告时 googletest 按 ANSI 代码页解析路径，中文路径必然失败。
- 退化分支：整体注册一个 `EngineTests` 用例，用 `--selector=off` **不开窗直接全跑**（无参数的 ctest 不会阻塞在图形窗口上）。
- 正则 `^[ -~]+$` 判断路径是否全为可打印 ASCII（空格到波浪号）。

| 坑位 | 现象 | 原因与对策 |
|---|---|---|

| ctest 中文路径 | `[FATAL] Unable to open file ...cmake_test_discovery_*.json` | googletest 按 ANSI 解析路径；已退化为整体注册（见 §4.6） |

| `CMAKE_CXX_CREATE_STATIC_LIBRARY` 被覆盖 | BOM 包装器不生效 | 必须在 `project()` 之后设置（见 §4.1） |
| 覆盖变量指错路径 | 硬失败且不再探测 | 设计如此：防静默用错库（见 §4.4） |
| 忘记先构建下层 | `接入下层：找不到 ... 的静态库` | 按 FATAL_ERROR 提示先构建下层 |
| `EngineTests.exe` 找不到资源 | 资源路径解析失败 | 产物必须在层根目录（`RUNTIME_OUTPUT_DIRECTORY` 已设置），`Engine_Env` 以可执行文件目录为基准 |
| 配置期非 UTF-8 代码页 | `ninja -t deps <obj>` 为 `#deps 0`、改头不重编 | CMake 探测的 `/showIncludes` 前缀与 `/utf-8` 编译输出字节不等；先 `chcp 65001` 再配置（见 §4.10） |
| 上层读下层源码树头 | 「下层头已改、库未重建」时新头配旧库 | 已改用对外头快照编译（见 §4.11）；快照缺失在配置期即 FATAL_ERROR |
| VS 报「在当前源文件的目录中或生成系统中未找到文件」 | 头文件不在任何 target，删缓存重配无效 | 四层补收头文件并纳入目标 + 开启 `compile_commands.json`（见 §4.13） |
| `Imported target "EngineCore" includes non-existent path` | CMake 生成阶段报错 | `external/glm` 死路径已从对外面移除（见 §4.14） |

**外部符号基线**：`out/_verify/基线-外部符号.txt` 记录了 `EngineCore.lib` 的**外部符号 16342 条**基线（`Measure-Object -Line` 实测 16342 行，每行一条 MSVC 修饰名，含 `?$TSS0@...` 静态初始化守卫、`std::` 模板实例、`engine::` 类型与 `bt*` bullet3 符号）。配套 `当前-外部符号.txt` 与 `符号差异.txt` 用于构建后对比，防止第三方库/编译器版本漂移导致符号集意外变化。

### 4.8 既有编译告警（C4005 / C4715 / C4828）

项目存在既有告警，`/WX-`（不把警告当错误）全局关闭了告警升级：

| 告警 | 含义 | 典型来源 |
|---|---|---|
| `C4005` | 宏重定义 | Windows SDK / 第三方头文件宏冲突（如 `min`/`max` 与 NOMINMAX 相关） |
| `C4715` | 非 void 函数不是所有路径都有返回值 | 部分工具函数分支未全覆盖（既有代码，未修） |
| `C4828` | 文件包含第 0 行字符 | 中文源文件在 UTF-8 无 BOM 与带 BOM 之间的边界问题 |

这些是**既有告警**，重开发时**不要**试图一次性清零（会引入大量无关改动）；新增代码应避免产生新的同类告警。

### 4.9 层间契约的合规性检查清单

重开发/新增层时必须满足：

1. `<层>/cmake/对外接口.cmake` 必须定义五个 `BYJY_<P>_OUT_*` 变量；`<P>` 与上层调用时传的前缀一致。
2. 对外面 = 自有面 + include 下层对外接口；`OUT_INC` 必须覆盖公共头实际引用的第三方路径（对照引擎层 `external/Json`、`external/glfw` 的先例）。
3. `<层>/cmake/接入下层.cmake` 必须与其它层逐字节一致。
4. 缓存变量命名遵循 `BYJY_<下层名>_LIB_PATH`，默认 `""`。
5. 上层消费下层一律 `byjy_jieru_xiaceng()`，**禁止** `add_subdirectory` 下层源码。
6. 静态库输出到 `<构建目录>/lib/`（`ARCHIVE_OUTPUT_DIRECTORY`），否则自动探测失效。
7. MSVC + Ninja 下静态归档必须保留 BOM 包装器接线。
8. **配置期必须处于 UTF-8 代码页**（`chcp 65001`），否则头依赖丢失（见 §4.10）。
9. **新增对外包含目录时，须同步该层的 `MIRROR_DIRS` 与 `对外接口.cmake`**（快照镜像范围与对外面一一对应是人工维护的，见 §4.11）。
10. 需要头快照语义的层，其包含目录切换走 `byjy_kuaizhao_lujing()` / `byjy_qiehuan_tou_kuaizhao()`；**普通库目标改 `target_include_directories`，导入目标才改 `INTERFACE_*`**（见 §4.12）。
11. 各层 `CMakeLists.txt` 须收集头文件并纳入目标、开启 `CMAKE_EXPORT_COMPILE_COMMANDS ON`，保证 IDE 可索引（见 §4.13）。

### 4.10 配置期 UTF-8 代码页要求（增量构建头文件依赖修复）

**问题现象**：增量构建对头文件完全盲区——`ninja -t deps <obj>` 输出 `#deps 0`（该对象只记录 `.cpp` 自身），改动头文件后 `cmake --build` 重编 TU 数为 **0**。

**根因（实测取证）**：CMake 探测 `/showIncludes` 前缀时**不带 `/utf-8`**（编译器按系统本地码页输出，CP936 下为 GBK 字节），而本工程编译**带 `/utf-8`**（cl 实际输出 UTF-8 字节）。两侧逐字节不等 ⇒ ninja 匹配不到 `msvc_deps_prefix` ⇒ 头文件依赖全部丢失。取证要点：

| 取证项 | 实测结果 |
|---|---|
| `rules.ninja` 的 `msvc_deps_prefix` | GBK 字节（按 CP936 可解为「注意: 包含文件: 」） |
| `build.ninja` 中的中文路径 | UTF-8 |
| cl 实际输出的 `/showIncludes` 行 | UTF-8 字节 |
| `ninja -t deps <obj>` | `#deps 0` |
| 改头后 `cmake --build` 重编 TU 数 | 0 |

**修复方式**：**配置阶段本身须处于 UTF-8 代码页**（先 `chcp 65001` 再配置）。生效后 `msvc_deps_prefix` 变为 UTF-8、`ninja -t deps` 出现 `.h` 依赖、touch 底层头重编 119 TU / touch 项目头重编 18 TU（精确子集）。

**已实测排除的仓库内方案**（均无效，勿重试）：

| 候选 | 结论 |
|---|---|
| `project()` 之后覆盖 `CMAKE_CXX_CL_SHOWINCLUDES_PREFIX` | 无效：生成器在 `project()` 的语言启用阶段已取定前缀 |
| `project()` 之前把 `/utf-8` 写入 `CMAKE_CXX_FLAGS` | 无效：探测阶段不读 `CMAKE_CXX_FLAGS` |
| `VSLANG=1033` | 无效：前缀仍为 GBK（cl 消息语言不由该变量决定） |
| CMakeLists 内 `execute_process(cmd /c chcp 65001)` | 无效：必须在**启动 CMake 之前**设定，进程内切换影响不到子进程 |
| **配置阶段处于 UTF-8 代码页** | **✅ 生效（采用）** |

**固化方式**：以文字固化（不新建文档）——顶层 `README.md`「五、构建」新增「配置期必须处于 UTF-8 代码页」说明块，四层 `README.md` 的构建章节各加一条同源说明。**已知限制**：Visual Studio 内建 CMake 集成若在非 UTF-8 代码页下配置仍会丢失头依赖（未实测其行为）；使用该集成时须先 `chcp 65001` 再从该控制台启动，并以 `ninja -t deps` 复核。

### 4.11 对外头快照机制（系统层消费 + 自身导出）

**目的**：上层不再实时读取下层源码树头文件，改为按「与下层静态库同版次」的头编译，消除「下层头已改、库未重建」时新头配旧库地编译链接的风险。

**镜像脚本** `引擎层/cmake/导出头快照.cmake`（`cmake -P` 脚本，系统层复用同一份）：

- 接收 `SRC_ROOT` / `DST_ROOT` / `MIRROR_DIRS` 三个参数（缺任一即 `FATAL_ERROR`）；
- 按 `MIRROR_DIRS` 逐目录收集 `.h` / `.hpp` / `.inl`，先 `MAKE_DIRECTORY` 保证快照根存在；
- 复制采用 `file(COPY_FILE ... ONLY_IF_DIFFERENT)`（仅内容不同才落盘；未变头保持原 mtime ⇒ 不触发上层无谓重编）；
- 清理快照中源侧已删除的头（避免已删头残留在快照里被包含到）；
- 收尾打印「头文件 N 个 / 清理失效 M 个」。

**常驻目标与镜像范围**：

| 目标（`ALL`） | 层 | `MIRROR_DIRS` | 快照根 | 实测头数 |
|---|---|---|---|---|
| `EngineIncludeSnapshot` | 引擎层 | `common;src;external/Json;external/glfw;external/bullet3/src`（**含第三方头**） | `<引擎构建目录>/include` | 235 |
| `SystemIncludeSnapshot` | 系统层 | `common;src;external/Sol2/include;external/Lua` | `<系统构建目录>/include` | 165 |

**消费链路（完整链路）**：引擎层导出快照 → 系统层消费引擎快照（自身包含目录换算 + `EngineCore` 导入面切换）并按同法导出自身快照 → 测试层消费引擎快照**和**系统快照（见 §1.5 接线与 §4.12）。**维护约束**：`MIRROR_DIRS` 与各层 `对外接口.cmake` 的包含目录一一对应，二者均需在新增对外包含目录时同步。

**验收数据**：

| 验收项 | 结果 |
|---|---|
| 快照产出 | 引擎层 235 头；系统层 165 头 |
| 系统层依赖落点 | 引擎快照 **173** ／ 引擎源码树 **0** |
| 测试层依赖落点 | 引擎快照 **388** ／ 引擎源码树 **0**（`ninja -t deps`） |
| 测试层编译包含目录 | 引擎快照 **175** 次、系统快照 **112** 次、两类源码树均 **0** 次 |
| 改引擎源码头、不重建引擎层 → 构建系统层/测试层 | 重编 **0 / 0** TU ⇒ 整链不再实时拉取源码树头 |
| 重建引擎层（刷新快照）→ 构建系统层/测试层 | 重编 **7 / 8** TU ⇒ 新头按需生效且为正确子集 |
| 快照目录缺失 | 配置期 `FATAL_ERROR`（见 §4.12） |

> 局限（如实记录）：测试层现有用例不含任何系统层头（对 `src/entity|prop|effect/` 的包含为 0 处），故「系统层→测试层」的隔离无法用现有用例演示；其接线由编译包含目录核对（系统快照 112 次、系统源码树 0 次）与「配置期无 FATAL_ERROR」证明，含系统层头的用例接入后自动生效。

### 4.12 头快照路径映射与切换契约函数

`接入下层.cmake` 中两个函数（三份逐字节相同，见 §2.5、§4.3）：

```cmake
# 按路径前缀换算一串包含目录，结果经 PARENT_SCOPE 写回，不做存在性校验
function(byjy_kuaizhao_lujing out_var snapshot_root source_root inc_dirs)

# 切换导入目标的 INTERFACE_INCLUDE_DIRECTORIES；快照缺失 → FATAL_ERROR
function(byjy_qiehuan_tou_kuaizhao target_name snapshot_root source_root)
```

**换算规则**（`byjy_kuaizhao_lujing`）：逐条包含目录——等于 `<源根>` → `<快照根>`；位于 `<源根>/` 之下 → `<快照根>/<其余部分>`；其余目录原样保留。`byjy_qiehuan_tou_kuaizhao()` 读取目标的 `INTERFACE_INCLUDE_DIRECTORIES`，经 `byjy_kuaizhao_lujing()` 换算后写回。

**关键坑（本批踩过）**：`SystemCore` 是**普通库目标**（非导入目标），其自身编译包含目录由 `INCLUDE_DIRECTORIES` 决定；只 `set_target_properties(... INTERFACE_INCLUDE_DIRECTORIES ...)` **不会改变它自身的编译包含路径**（首次接线后系统层仍有 165 条依赖命中引擎源码树）。故必须先 `byjy_kuaizhao_lujing()` 换算 `${BYJY_SYSTEM_OUT_INC}` 再交给 `target_include_directories(SystemCore PUBLIC ...)`，同时 `byjy_qiehuan_tou_kuaizhao(EngineCore ...)` 切换导入面。**普通库目标用 `target_include_directories`，导入目标才用 `INTERFACE_*`**。

**失败语义**：快照目录缺失 → 配置期 `FATAL_ERROR`，提示先构建产出该快照的下层；**不静默退回源码树**。

**测试层接线顺序**（§1.5）：引擎映射要对 `EngineCore` 与 `SystemCore` 各做一次（后者承载并入的引擎条目）；系统映射只改 `SystemCore`，且必须放在引擎映射之后，避免误改引擎条目。

### 4.13 CMake 头文件收集与 IDE 索引

**问题**：四层 `CMakeLists.txt` 原只 `file(GLOB_RECURSE ... "src/*.cpp")`，**只收 `.cpp`/`.c`，头文件从不进入任何 target**。VS 解析 include 时只在「当前源文件所在目录」与「生成系统的文件清单」两处找文件，头文件两头都不在，故**总是**报「在当前源文件的目录中或生成系统中未找到文件"XXX.h"」，且「删除缓存并重新配置」无效（头文件依旧不在生成系统里）。

**处置**：

1. 四层 `CMakeLists.txt` 各新增 `.h/.hpp` 递归收集并纳入对应目标（`EngineCore` / `SystemCore` / `TestCore` / `EngineTestObjects` / `TestLauncher` / `EngineTests` / `GameCore`）——**仅供 IDE 与生成系统建立索引，不参与编译**；测试层的 `src/主调/*.h` 单独收为 `MAIN_HEADERS`，由 `TestLauncher` 与 `EngineTests` 共用。引擎层头文件收集**不纳入 `external/` 第三方头**，以免污染索引。
2. 四层开启 `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)`（Ninja 生成器默认不产出 `compile_commands.json`）。
3. VS 侧仍需执行「删除缓存并重新配置」；若仍无效，须**完全退出 VS** 后删除 `引擎层/.vs` 与仓库根 `.vs` 再重开（IntelliSense 数据库独立于 CMake 缓存）。

### 4.14 引擎层移除 `external/glm`

**问题**：`引擎层/external/glm` 目录不存在，却仍在 `cmake/对外接口.cmake` 的 `BYJY_ENGINE_OUT_INC` 里 ⇒ 上层在 CMake 生成阶段报 `Imported target "EngineCore" includes non-existent path`。

**处置**：从对外面移除该条目并更正注释；引擎层源码 `glm` 引用经检索为 **0**，故一并从仓库删除 432 个 glm 文件。（`external/` 目录本身仍保留在 `OUT_INC` 中，为原有声明未改动。）

### 4.15 本批构建机制改动验收汇总

| 改动 | 关键验收 |
|---|---|
| 配置期 UTF-8 代码页（§4.10） | 生效后 `msvc_deps_prefix` 为 UTF-8、`ninja -t deps` 含 `.h`；仓库内四种替代方案实测无效 |
| 头快照机制（§4.11） | 引擎 235 头 / 系统 165 头；改引擎头不重建引擎层 → 系统层/测试层重编 0/0 TU；重建引擎层 → 7/8 TU |
| 契约函数（§4.12） | 快照缺失配置期 FATAL_ERROR；`SystemCore` 需改 `target_include_directories` 方生效 |
| IDE 头文件索引（§4.13） | 四层头文件纳入目标 + `compile_commands.json` 生成；VS 报错消除 |
| 移除 `external/glm`（§4.14） | 上层生成阶段不再报不存在路径；源码 glm 引用 0 |

  ├─ add_library(SystemCore STATIC ${SYSTEM_SOURCES} ${SYSTEM_HEADERS})
  ├─ target_include_directories(SystemCore PUBLIC ${BYJY_SYSTEM_INC_SNAPSHOT})

### 5.3 层间协作关系（数据流）

```
                    ┌─────────────┐
                    │   游戏层     │   GameCore（当前无）
                    │  assets/*   │   JSON 实体/属性配置、Lua 行为脚本（运行时数据）
                    └──────┬──────┘
                           │ BYJY_GAME_OUT_*（对外面链）
                    ┌──────▼──────┐
                    │   测试层     │   EngineTests.exe（唯一可执行入口）
                    │ src/单元测试 │   ──链接──> EngineCore + SystemCore（IMPORTED）
                    └──────┬──────┘
                           │ BYJY_SYSTEM_OUT_*（含并入的引擎层对外面）
                    ┌──────▼──────┐
                    │   系统层     │   SystemCore.lib —— 实体/属性/效应子系统
                    │ src/{entity, │   ──链接──> EngineCore（IMPORTED）
                    │   prop,      │
                    │   effect}    │
                    └──────┬──────┘
                           │ BYJY_ENGINE_OUT_*（五条包含路径 + GLFW_STATIC + glfw3.lib + 系统库）
                    ┌──────▼──────┐
                    │   引擎层     │   EngineCore.lib —— 对象/事件/空间/碰撞/tools
                    │ src/ +      │   第三方：Json、GLFW、bullet3（编入库内）
                    │ common/ +   │
                    │ external/   │
                    └─────────────┘
```

**协作要点**：

- **对外面沿依赖方向单向流动**：引擎层对外面 → 系统层对外面（自有面 + 并入）→ 游戏层对外面（自有面 + 并入）；测试层直接读引擎层与系统层两份接口。
- **包含路径叠加**：测试层接入系统层后，自动获得引擎层的全部包含路径（`common/前置头文件包含.h`、`external/Json`、`external/glfw`、`external/bullet3/src` 等），无需重复声明；这些路径随后被换成下层的对外头快照（见 §4.11）。
- **链接库叠加**：`SystemCore` 的 PUBLIC 链接面 = `EngineCore`（导入目标）+ `glfw3.lib`（引擎层 LINK）+ 四个系统库（引擎层 SYS）；测试层的 `EngineTests` 链接面在此基础上再叠加 `TestGui`、`TestLauncher`、`GTest::gtest`。
- **GLFW_STATIC 的传递**：编译定义挂在 `EngineCore` 导入目标的 INTERFACE 上，链接它的所有上层自动获得 `GLFW_STATIC`，保证 GLFW 头文件在每一层都按静态库模式解析。

### 5.4 验证闭环（符号基线对比）

`out/_verify/` 下的脚本/文本形成验证闭环：

1. `基线-外部符号.txt`（16342 条）保存引擎库符号基线。
2. 构建后导出 `当前-外部符号.txt`，与基线 diff 得到 `符号差异.txt`。
3. 差异为零 → 构建产物符号集稳定；出现差异 → 排查第三方库版本、编译器版本、源文件增删。

## 附：重开发速查表

| 要做什么 | 改哪里 | 注意事项 |
|---|---|---|
| 新增引擎层源文件 | 放 `引擎层/src|common|external/` 下 | `CONFIGURE_DEPENDS` 自动纳入，无需改 CMakeLists |
