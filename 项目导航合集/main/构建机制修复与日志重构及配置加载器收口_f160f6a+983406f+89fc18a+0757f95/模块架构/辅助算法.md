## 一、模块功能

### 1.1 模块定位

「通用算法模块」（`engine::detail`，目录 `引擎层/src/tools/Detail/`）是引擎层 `src/tools/` 下的一个**无状态工具函数集模块**。它不定义任何类、不持有任何数据，只提供若干**命名空间级函数模板与内联函数**，并按主题分文件、以聚合头对外透出：

| 主题 | 文件 | 提供函数 |
| --- | --- | --- |
| 二分查找族 | `二分查找.h`（121 行） | `binary_search`（迭代器/容器重载）、`range_binary_search`（迭代器/容器重载） |
| 哈希 | `哈希混合.h`（17 行） | `hash_combine` |
| 路径字符串转换 | `路径字符串转换.h`（33 行） | `path_to_string`、`string_to_path` |
| 路径规范化 | `文件路径规范化.h`（76 行） | `path_normalize`、`path_key_normalize` |
| 标准库 format 特化 | `标准库format特化.h`（79 行） | `std::formatter<error_code>` / `<error_condition>` / `<filesystem::path>` |
| 校验工具 | `文件路径可用性校验.h`（52 行）、`json字段可用性校验.h`（94 行） | `path_check`（path/string 重载）、`field_check<T>` |
| 聚合头 | `package/路径操作工具.h`（7 行） | 聚合 `路径字符串转换.h` + `文件路径规范化.h` |
| 聚合头 | `package/数据校验工具.h`（7 行） | 聚合 `json字段可用性校验.h` + `文件路径可用性校验.h` |

这些函数族服务场景不同：二分查找服务于**引擎内部有序容器的 O(log n) 定位**（对象池排序查找、四叉树管理器坐标区间查询、数值分配器回收查重）；哈希服务于**多字段组合哈希**（配置目录对、脏标记）；路径转换/规范化服务于**跨平台中文路径的 UTF-8 保真传递与路径键编排**（引擎环境、网格加载、配置加载、日志系统路由）；校验工具服务于**路径可用性与 JSON 字段合法性**检查。把它们收敛在一个 `detail` 命名空间下，是「通用、无状态、可复用的纯工具」这一类工具的归集。

本模块全部头文件均为 **header-only**（模板天然只能放头文件；其余函数以 `inline` 规避 ODR 违规），**无 `.cpp` 实现文件**。

### 1.2 解决的核心问题

#### 二分查找族

引擎内部大量「有序容器 + 按序键查找」场景，直接使用标准库需要调用方自行组装：

- `std::binary_search` 只回答「在不在」，不返回位置；
- `lower_bound`/`upper_bound` 返回迭代器，需换算成索引；且在「查找窗口不是从容器头开始」（如对象池的 `min_valid_index` 偏移窗口）时，**直接相减会得到窗口内相对下标而非容器全局下标**；
- 重复元素场景（如四叉树管理器中多棵树的根节点 X 坐标相同）需要「区间查询」能力。

`binary_search` / `range_binary_search` 把这三种需求封装为「一个调用、返回下标/区间」的形态，并额外提供**容器重载**（直接传容器对象，免去 `begin/end` 样板）。返回值为 `std::optional`（命中给下标，未命中给 `std::nullopt`），消除了旧版 `int` 与 `-1` 哨兵混用的类型风险。

#### 哈希

`std::hash` 只对单值定义；组合多个字段（如 `Config_Content` 的 route/config 两个路径）需要一个稳定的混合函数。`hash_combine` 提供 boost 风格的 mixing（`seed ^= val + 0x9e3779b9 + (seed << 6) + (seed >> 2)`），被 `std::hash<Config_Content>` 与配置加载器的脏标记计算复用。

#### 路径字符串转换族

`std::filesystem::path` 在 Windows 上是 `wchar_t` 宽字符存储，在 Linux/macOS 上是 `char` 窄字符存储。引擎内部统一约定「**出入参路径一律为 UTF-8 编码的 `std::string`**」，因此需要 `path ↔ std::string` 的**逐字节零损失**转换——这是中文路径（如 `D:/代码存储/代码仓库/白银纪元/...`）在引擎全链路中正确传递的基石。

#### 路径规范化族

`path_normalize` 做**词法规范化**（统一平台首选分隔符、消解 `.`/`..`、消除尾部分隔符），供路径比较与哈希使用；`path_key_normalize` 在其基础上进一步把绝对路径**剥离为项目内相对路径**并统一为 `/`、末尾补 `/`，产出稳定的「路径键」，供路径前缀比较与哈希（对象池/配置/日志路由）使用。本模块**不出现项目名**——项目根锚点由调用方以参数传入。

#### 标准库 format 特化集

`std::error_code` / `std::error_condition` / `std::filesystem::path` 在 C++20 标准库均无格式化器，`std::format("{}", ec)` 编译失败。本文件集中补齐三者，使日志系统与业务代码可直接以 `"{}"` 输出。

#### 校验工具

`path_check` 判断路径是否存在且为可读取普通文件；`field_check<T>` 判断 JSON 字段是否存在、类型是否匹配（bool/整数/浮点/字符串/容器），空字符串与空容器视为无效。两者是配置加载器路径安全与字段校验的复用基础。

### 1.3 功能要点一览

| 能力 | 说明 |
| --- | --- |
| 精确查找（迭代器版） | `binary_search(first, last, target, comp, proj)` 返回目标在**原查找窗口**中的全局下标（`std::optional<uint64_t>`）；未命中返回 `std::nullopt` |

| 标准库 format 特化 | `error_code` / `error_condition` / `filesystem::path` 三个 `std::formatter` 显式特化 |

### 1.4 非目标（明确不做的事）

- **不做二分查找的排序保障**：假定传入区间**已按 `comp` 有序**；无序区间上调用是未定义行为（与标准库一致）；
- **不做区间插入/删除类算法**：只查询，不修改容器；
- **不做 `std::ranges` 命名空间扩展**：函数位于 `engine::detail`；
- **路径转换不做编码猜测**：只认「入参就是 UTF-8」的约定，不做 GBK→UTF-8 之类的转码；
- **`path_normalize` 不做词法规范化以外的事**：不判绝对相对、不裁剪锚点（那是 `path_key_normalize` 的职责，且锚点由调用方传入）；
- **不做偏特化 format（技术限制）**：`std::formatter<std::vector<T>>` / `<std::optional<T>>` 属偏特化，标准不允许，故不予添加；项目自定义类型的特化放在其类型所在头文件。

### 2.1 `binary_search` —— 迭代器版本

```cpp
//单点二分查找——迭代器重载
template<typename RandomIt, typename T, typename Compare, typename Projection = std::identity>
std::optional<uint64_t> binary_search(RandomIt first, RandomIt last, const T& target,
    const Compare& comp, Projection proj = {})
{
    //保存原始起始位置
    RandomIt original_first = first;
    while (first < last)
    {
        //获取中间迭代器
        RandomIt mid = first + (last - first) / 2;
        //若目标小于中间元素
        if (comp(target, std::invoke(proj, *mid)))
            last = mid;
        //若中间元素小于目标
        else if (comp(std::invoke(proj, *mid), target))
            first = mid + 1;
        //若中间元素等于目标
        else
            return static_cast<uint64_t>(mid - original_first);
    }
    //若查找失败则返回空值
    return std::nullopt;
}
```

| 模板参数 | 含义 |
| --- | --- |
| `RandomIt` | 随机访问迭代器类型（`vector::iterator`、原生指针等） |
| `T` | 目标值类型（与比较器配合可不同于元素类型） |
| `Compare` | 比较器：`comp(a, b)` 返回 `bool`，表达「a 严格小于 b」（严格弱序） |
| `Projection` | 投影（默认 `std::identity`）：`std::invoke(proj, *it)` 取出参与比较的字段/变换值 |

| 参数 | 含义 |
| --- | --- |
| `first`/`last` | 查找区间 `[first, last)`，**须已按 `comp` 有序** |
| `target` | 查找目标 |
| `comp` / `proj` | 比较器 / 投影 |
| 返回值 | 命中：目标在**原始 `first` 起始的全局下标**（`uint64_t`）；未命中：`std::nullopt` |

行为与算法：

- 经典迭代二分：`mid = first + (last - first) / 2`（用差值避免指针/迭代器相加溢出）；
- 三分支判定：`comp(target, proj(*mid))` 为真 → 目标在左半（`last = mid`）；`comp(proj(*mid), target)` 为真 → 目标在右半（`first = mid + 1`）；两者皆假 → **命中**（严格弱序下两者皆假 ⇔ 等价）；
- **关键点**：返回 `mid - original_first` 而非 `mid - first`——循环中 `first` 会移动，`mid - first` 是**窗口内相对下标**；保存最初 `first` 到 `original_first` 才是相对「调用方传入起点」的全局下标。对象池 `find()` 正是以偏移窗口起点调用，再用返回值**加上偏移**回算容器内真实位置；
- **类型代际差异（相对旧版）**：返回类型由 `int`（`-1` 哨兵）改为 `std::optional<uint64_t>`；调用方判断由 `index >= 0` 改为 `if (index)` / `index.has_value()`；
- 复杂度：O(log n) 次比较，O(1) 额外空间（迭代器版本，非递归）。

### 2.3 `range_binary_search` —— 迭代器版本

```cpp
//范围二分查找——迭代器重载
template<typename RandomIt, typename T, typename Compare,
    typename Projection = std::identity>
std::optional<std::pair<uint64_t, uint64_t>> range_binary_search(RandomIt first, RandomIt last,
    const T& target, const Compare& comp, Projection proj = {})
{
    //计算下界：第一个使得 comp(proj(*it), target) 为 false 的元素
    //即第一个不小于 target 的元素
    auto lower = first;
    //计算区间元素数量
    auto count = std::distance(first, last);
    while (count > 0)
    {
        auto step = count / 2;
        auto it = lower;
        std::advance(it, step);
        //若当前元素小于目标
        if (comp(std::invoke(proj, *it), target)) { lower = ++it; count -= step + 1; }
        else count = step;
    }

    //计算上界：第一个使得 comp(target, proj(*it)) 为 true 的元素
    //即第一个大于 target 的元素
    auto upper = lower;
    count = std::distance(upper, last);
    while (count > 0)
    {
        auto step = count / 2;
        auto it = upper;
        std::advance(it, step);
        //若目标大于等于当前元素
        if (!comp(target, std::invoke(proj, *it))) { upper = ++it; count -= step + 1; }
        else count = step;
    }

    //检查下界是否有效且与目标等价
    if (lower == last || comp(std::invoke(proj, *lower), target) ||
        comp(target, std::invoke(proj, *lower)))
        return std::nullopt;

    //计算左边界下标
    uint64_t left_index  = static_cast<uint64_t>(std::distance(first, lower));
    //计算右边界下标
    uint64_t right_index = static_cast<uint64_t>(std::distance(first, upper)) - 1;
    //返回闭区间下标
    return { {left_index, right_index} };
}
```

| 参数 | 含义 |
| --- | --- |
| `first`/`last` | 查找区间 `[first, last)`，**须已按 `comp` 有序** |
| `target`/`comp`/`proj` | 目标 / 比较器 / 投影 |
| 返回值 | 命中：`std::optional<std::pair<uint64_t,uint64_t>>`，闭区间 `[left, right]` 内的元素全部与目标等价；未命中：`std::nullopt` |

行为与算法（**两阶段二分**）：

- **阶段 1（下界）**：步进法寻找「第一个不小于目标」的位置 `lower`；
- **阶段 2（上界）**：从 `lower` 继续（不重头搜），寻找「第一个严格大于目标」的位置 `upper`（用 `!comp(target, proj(*it))` 判定「目标不小于当前元素」→ 向右收缩，等价于标准 `upper_bound`）；
- **阶段 3（命中判定）**：`lower == last` 或 `comp(proj(*lower), target)` 或 `comp(target, proj(*lower))` 任一成立 ⇒ 等价元素不存在，返回 `std::nullopt`；
- **阶段 4（闭区间组装）**：`left = distance(first, lower)`；`right = distance(first, upper) - 1`；
- **类型代际差异（相对旧版）**：返回类型由 `std::pair<int,int>`（`{-1,-1}` 哨兵）改为 `std::optional<std::pair<uint64_t,uint64_t>>`；调用方判断由 `first < 0 && second < 0` 改为 `if (!range)`；
- 复杂度：O(log n)，两次扫描合计；`std::distance`/`std::advance` 在随机访问迭代器上为 O(1)。

```cpp
inline std::string path_to_string(const std::filesystem::path& path)
```

| 返回值 | `std::filesystem::path`，路径内容与入参逐字节一致 |

行为：把 `std::string` 逐字节重解释为 `std::u8string`，构造 `std::filesystem::path`。C++20 的 `path` 有接受 `u8string` 的构造函数，会按 UTF-8 正确解释——Windows 上转成宽字符内部表示时中文不乱码，Linux 上保持窄字节原样。

### 2.8 `path_normalize`（词法规范化）

```cpp
//路径规范化（统一目录分隔符并消除尾部分隔符，供路径比较与哈希使用）
inline std::filesystem::path path_normalize(const std::filesystem::path& path)
{
    //词法规范化（消解"."与".."）
    const std::filesystem::path normal = path.lexically_normal();
    //取出相对路径成分
    const std::filesystem::path relative = normal.relative_path();
    //以根路径为起点逐节重组（operator/= 统一使用平台首选分隔符，并自动消除尾部分隔符）
    std::filesystem::path result = normal.root_path();
    for (const auto& element : relative)
    {
        //跳过空节（尾部分隔符产生的空节）
        if (element.empty())
            continue;
        //拼接当前节
        result /= element;
    }
    //返回规范化结果
    return result;
}
```

| 步骤 | 作用 |
| --- | --- |
| ① `lexically_normal()` | 纯词法规范化：消解 `.` 与 `..`（不访问文件系统） |
| ② 取 `relative_path()` | 分离根路径与相对成分，便于逐节重组 |
| ③ 以 `root_path()` 为起点**逐节 `operator/=`** | 统一为平台首选分隔符；跳过空节 ⇒ **自动消除尾部分隔符** |

**历史修正记录**：首版曾以 `filename()` 是否非空作为主分支条件，在「尾部分隔符」输入下 `filename()` 为空 ⇒ 尾部分隔符未被消除（缺陷）。现改为「按 `relative_path()` 逐节 `operator/=` 重组」，缺陷已修。签名与语义**对本批未变**，故 `Config_Content` 的构造调用、`operator==`、`std::hash` 特化全部兼容。

### 2.9 `path_key_normalize`（路径键规范化 —— **本批新增**）

```cpp
//路径键规范化（在路径规范化基础上剥离到项目根相对路径，统一 '/' 分隔符并末尾补 '/'，供路径前缀比较与哈希使用）
//root_anchor：项目根目录名（以 '/' 结尾），用于把绝对路径裁剪为项目内相对路径
inline std::string path_key_normalize(const std::string& raw, const std::string& root_anchor)
{
    //复用通用路径规范化（统一分隔符并消解"."与".."）后转回 UTF-8 文本
    std::string path = path_to_string(path_normalize(string_to_path(raw)));
    //统一路径分隔符为正斜杠
    for (char& ch : path)
        if (ch == '\\')
            ch = '/';
    //取项目根锚点最后一次出现的位置
    const size_t anchor_pos = path.rfind(root_anchor);
    //若锚点存在则剥离锚点及其之前的部分
    if (anchor_pos != std::string::npos)
        path.erase(0, anchor_pos + root_anchor.size());
    //剥离开头的前导分隔符与 './' 片段
    for (;;)
    {
        //去掉前导 '/'
        if (!path.empty() && path.front() == '/') { path.erase(0, 1); continue; }
        //去掉前导 './'
        if (path.compare(0, 2, "./") == 0) { path.erase(0, 2); continue; }
        break;
    }
    //末尾补 '/'，使目录节点与文件节点共用同一套路径段前缀比较
    if (!path.empty() && path.back() != '/')
        path.push_back('/');
    //返回规范化路径键
    return path;
}
```

| 步骤 | 作用 |
| --- | --- |
| ① 复用 `path_normalize` | 词法规范化（分隔符统一、`.`/`..` 消解）与 UTF-8 编解码**全部下沉**到本模块；转回 UTF-8 文本 |
| ② `\`→`/` | 统一为正斜杠（Windows 盘符路径与 `lexically_relative` 结果均为 `\`） |
| ③ `rfind(root_anchor)` 后 `erase` | 以项目根目录名为锚，把绝对路径裁剪为**项目内相对路径**；锚点不存在时原样保留 |
| ④ 去前导 `/` 与 `./` | 防相对/绝对混用产生不同键 |
| ⑤ 末尾补 `/` | 使文件键与目录键形式一致，前缀比较落在**路径段边界**（避免 `abc` 误配 `abcd`）；空路径不产生多余 `/` |

| 项 | 说明 |
| --- | --- |
| 锚点归属 | `root_anchor` 由**调用方传入**，通用工具内**不出现项目名**（如日志侧传 `"白银纪元/"`） |
| 返回 `""` | 空输入返回空串（不产生多余 `/`），测试用例「路径键规范化空路径为空」已覆盖 |
| 与 `path_normalize` 的关系 | `path_key_normalize` **在 `path_normalize` 基础上**增加锚点裁剪与 `/` 键编排；二者职责分明 |

### 2.11 `path_check`（路径可用性校验）

```cpp
//路径有效性检查 —— path重载
inline bool path_check(const std::filesystem::path& target_path)
{
    //若未解析出有效路径
    if (target_path.begin() == target_path.end())
    { logger.info("路径无效"); return false; }

    //异常信息记录
    std::error_code ec;
    //若访问路径不存在或发生系统错误或非可读取文件
    if (!std::filesystem::exists(target_path, ec) ||
        !std::filesystem::is_regular_file(target_path, ec))
    {
        logger.info("访问路径异常\n请自行排查访问路径是否存在及是否可读取");
        logger.info("{}", ec);
        ec.clear();
        return false;
    }
    return true;
}
//路径有效性检查 —— string重载
inline bool path_check(const std::string& target_path)
{
    //转化为标准路径
    std::filesystem::path suspect_path = string_to_path(target_path);
    //调用path重载
    return path_check(suspect_path);
}
```

| 项 | 说明 |
| --- | --- |
| 检查内容 | ① 路径可解析（非空）；② 存在且为**可读取的普通文件** |
| 错误码版本 | `exists`/`is_regular_file` 均带 `ec`，不抛异常；`ec` 经 `logger.info("{}", ec)` 输出（依赖 `error_code` format 特化） |

### 2.12 `field_check<T>`（JSON 字段可用性校验）

```cpp
//字段有效性检查
template<typename T>
inline bool field_check(const nlohmann::json& config, const std::string& field)
{
    //字段存在性检查
    if (!config.contains(field))
    { logger.warn("detail::未包含指定字段: {}", field); return false; }

    //萃取布尔类型
    if constexpr (std::is_same_v<T, bool>)
    { if (!config[field].is_boolean()) { logger.info("detail::字段 {} 非布尔格式", field); return false; } }
    //萃取整数类形
    else if constexpr (std::is_integral_v<T>)
    { if (!config[field].is_number_integer()) { logger.info("detail::字段 {} 非整数格式", field); return false; } }
    //萃取浮点类型
    else if constexpr (std::is_floating_point_v<T>)
    { if (!config[field].is_number_float()) { logger.info("detail::字段 {} 非浮点数格式", field); return false; } }
    //萃取字符串类型
    else if constexpr (std::is_same_v<T, std::string>)
    {
        if (!config[field].is_string()) { logger.info("detail::字段 {} 类型不匹配", field); return false; }
        if (config[field].get_ref<const std::string&>().empty())
        { logger.info("detail::字段 {} 内容为空", field); return false; }
    }
    //若为其他类型
    else
    {
        //匹配容器类型
        try { config[field].get<T>(); }
        catch (const nlohmann::json::type_error&)
        { logger.info("detail::字段 {} 类型不匹配", field); return false; }
        //非空检查
        if ((config[field].is_array() || config[field].is_object()) && config[field].empty())
        { logger.info("detail::字段 {} 内容为空", field); return false; }
    }
    return true;
}
```

| 分支 | 条件 | 检查 |
| --- | --- | --- |
| 存在性 | `!contains(field)` | 直接失败（`logger.warn`） |
| `bool` | `is_same_v<T,bool>` | `is_boolean()` |
| 整数 | `is_integral_v<T>` | `is_number_integer()`（含 `uint64_t`，脏标记比较即用此分支） |
| 浮点 | `is_floating_point_v<T>` | `is_number_float()` |
| 字符串 | `is_same_v<T,std::string>` | `is_string()` + **非空** |
| 其他（容器等） | `else` | `get<T>()` 捕获 `type_error` + 数组/对象非空 |

| 项 | 说明 |
| --- | --- |
| 日志依赖 | 本头包含 `src/tools/Logging/日志系统运行包.h`（本批包含路径已同步为运行包） |
| 复用方 | `Config_Loader` 全链路字段校验（`object`/`config_path`/`route`/`config`/`files`/`dirty_mark`/`existence`） |

### 3.3 模板的编译期形态

两个查找算法各有「迭代器版本 + 容器版本」两个模板重载，构成**转发链**：

```
binary_search(container, target, comp, proj)
        └──► binary_search(std::begin(c), std::end(c), target, comp, proj)   （迭代器版）

range_binary_search(container, target, comp, proj)
        └──► range_binary_search(std::begin(c), std::end(c), target, comp, proj)
```

重载决议：容器版本要求第一实参是「支持 `std::begin/std::end` 的容器对象」；若第一实参本身就是迭代器（如 `objects.begin() + offset`），则直接命中迭代器版本。两种形态的**返回值约定一致**（`std::optional` 包裹的全局下标 / 闭区间），调用方无需区分。

### 3.4 命名空间与可见性

- 全部函数位于 `engine::detail`（模块注释「通用算法模块」/「辅助工具命名空间」）。
- `标准库format特化.h` 中的特化位于 `namespace std`（显式特化标准模板，须置于 `namespace std` 内），其中 `filesystem::path` 特化引用 `engine::detail::path_to_string`。
- 调用方：`engine::detail::xxx(...)` 或经 `局部命名空间使用.h` 引入简名（`Config_Loader` 用后者，源码内直接写 `detail::field_check`）。

## 四、模块设计/实现细节

### 4.1 `binary_search` 的「全局索引」修复（历史 bug 复盘）

头文件注释写明「保存原始起始位置」，说明此前版本存在真实缺陷：

```
旧实现（伪码）：return mid - first;      // first 是当前窗口起点，会随二分移动
调用场景（对象池 find）：
  binary_search(objects.begin() + 100, objects.end(), key, less, proj)
  命中在容器第 150 个元素：mid 相对最初 first 偏移 50 → 旧实现返回 50
  —— 但若用「命中时刻的 mid - first」，first 已收缩到命中点左侧很近处，偏移量偏小，对象池
     换算 objects.begin() + min_valid_index + index 会错位到错误对象
```

修复方案（现源码）：**进入循环前保存 `original_first`，返回 `mid - original_first`**。这对「查找窗口 ≠ 容器头」的调用（对象池偏移窗口、四叉树分段区间）至关重要。

### 4.2 `range_binary_search` 两阶段二分逐步推演

以有序序列 `[1, 3, 3, 3, 5, 7]`、`target = 3`、`comp = std::ranges::less` 为例：

```
阶段1 下界（第一个 >= 3 的元素）：
  count=6, step=3, it=元素[3]=3；comp(3,3)=false → count=3
  count=3, step=1, it=元素[1]=1；comp(1,3)=true  → lower=元素[2], count=1
  count=1, step=0, it=元素[2]=3；comp(3,3)=false → count=0
  lower = 元素[2]（下标 1）

阶段2 上界（第一个 > 3 的元素），从 lower 继续：
  count=5, step=2, it=元素[4]=5；!comp(3,5)=false → count=2
  count=2, step=1, it=元素[3]=3；!comp(3,3)=true  → upper=元素[4], count=0
  upper = 元素[4]（下标 4）

阶段3 判定：lower≠end；comp(3,3)=false；comp(3,3)=false → 命中
阶段4 区间：left = 1；right = 4 - 1 = 3 → {1, 3}，下标 1~3 全为 3 ✓
```

未命中（`target = 4`）：阶段 1 下界落在第一个 `>=4` 的 5（下标 4）；阶段 3 第三条件 `comp(4, proj(5))` 成立 → `std::nullopt` ✓
边界（`target` 小于全部元素，`target=0`）：下界 = begin；阶段 3 第三条件成立 → `std::nullopt` ✓
边界（`target` 大于全部元素，`target=9`）：下界 = end → 阶段 3 第一条件成立 → `std::nullopt` ✓

### 4.3 比较语义与投影的配合约定

- **`comp(a, b)` = 「a 严格小于 b」**：与 `std::ranges::less()`、`std::ranges::greater()` 兼容。`greater` 语义下「有序」是**降序**，此时「等价」判定（`comp(target,x)` 与 `comp(x,target)` 皆假）依然正确——四叉树管理器即用 `std::ranges::greater()` 在降序 X 序列上做区间查询；
- **`proj` 默认 `std::identity`**：直接比较元素本身；传投影函数时，**排序键 = 投影值**；
- **`std::invoke(proj, *mid)`**：支持成员函数指针、`std::reference_wrapper` 等可调用形态；
- 一致性要求：调用方必须保证「序列排序所用比较器 + 投影」与「查找所用比较器 + 投影」**完全一致**，否则二分结果未定义。

### 4.4 路径工具链的头文件循环规避（**本批关键**）

`路径字符串转换.h` 旧含 `引擎环境.h`，而 `引擎环境.h`（经运行包）又会包含日志系统，日志系统的 `流节点树.h` 需要包含路径工具 ⇒ 形成：

```
流节点树.h → 路径操作工具.h → 引擎环境.h → 日志系统运行包.h → 日志系统.h → 流节点树.h
```

在「先含运行包」的翻译单元中回卷后，`引擎环境.h` 函数体引用尚未声明的 `logger` ⇒ **编译失败**。

**破解方式**：清理 `文件路径规范化.h` / `路径字符串转换.h` 中**确未使用**的 `引擎环境.h` 包含（两者均只用 `std::filesystem`），循环链即断。清理后的传递依赖影响面经审计仅 **1 个文件**需补显式包含（测试层 `路径字符串转换测试.cpp`，且该文件本就存在预存在编译错误需一并修复）。

### 4.5 路径转换的跨平台行为矩阵

| 平台 | `path` 内部字符 | `u8string()` 产出 | 转换后行为 |
| --- | --- | --- | --- |
| Windows (MSVC) | `wchar_t`（UTF-16 编码的宽字符） | UTF-8 `u8string`（正确转码） | `path_to_string` 得 UTF-8 字节；`string_to_path` 把 UTF-8 字节解码回 UTF-16 宽字符 |
| Linux (libstdc++) | `char`（原生字节序，通常即 UTF-8） | UTF-8（原样） | 均为字节搬运，无损失 |
| macOS (libc++) | `char`（UTF-8 语义） | UTF-8（原样） | 同上 |

关键点：转换函数本身**不做转码**，只做「`path` ↔ UTF-8 字节序列」的桥接；真正的编码转换由 `path::u8string()` 与 `path(u8string)` 构造函数在 Windows 上完成。前提是**输入确为 UTF-8**（构建命令行含 `/utf-8`，`__FILE__` 与 `source_location::file_name()` 均为 UTF-8，前提成立）。

### 4.6 `path_key_normalize` 与 `path_normalize` 的分工

| 维度 | `path_normalize` | `path_key_normalize` |
| --- | --- | --- |
| 入参/出参 | `path` → `path` | `string`（UTF-8）→ `string`（UTF-8） |
| 分隔符 | 平台首选（Windows 为 `\`） | 统一 `/` |
| 尾部分隔符 | 消除 | 补 `/`（非空时） |
| 锚点裁剪 | 无 | 有（`rfind(root_anchor)`，锚点由调用方传入） |
| 用途 | 路径比较、`Config_Content` 的 `operator==`/`std::hash` | 路径前缀比较、路径键哈希、日志路由节点键 |
| 复用方 | `Config_Content` 两构造、`文件路径可用性校验`（间接） | 日志系统 `Stream_Tree::path_normalize`（锚点 `"白银纪元/"`） |

### 4.8 易踩坑点（重开发速查）

1. **有序性前提**：两个查找函数都不检查序列是否有序；无序输入 = 未定义行为；
2. **窗口偏移与返回值的关系**：迭代器版返回「相对**入参 `first`**」的下标，不是相对容器头；容器版才是容器内下标。对象池的用法是「入参窗口起点 = `begin + min_valid_index`，再用返回值**加回** `min_valid_index`」；
3. **返回值为 `std::optional`**：判断命中用 `if (index)` / `if (range)`，**不可再写 `index >= 0`**（会与 `optional` 无该运算符冲突）；
4. **`range_binary_search` 的右端点**：返回的 `second` 是闭区间右端（`upper - 1`），遍历用 `for (i = left; i <= right; ++i)`；
5. **比较器方向**：降序序列必须配 `std::ranges::greater()`，混用 `less` 会得错误结果；
6. **投影必须一致**：排序与查找的比较器 + 投影须完全一致；
7. **路径转换不做合法性校验**：`string_to_path` 对非法 UTF-8 字节不做检查；路径是否存在由调用方用 `detail::path_check` 或文件系统 API 验证；
8. **`u8string()` 的 C++20 差异**：C++20 起返回 `std::u8string`（`char8_t`），本实现按 C++20 写，降到 C++17 会编译失败；
9. **`reinterpret_cast` 的字节语义**：`char8_t` 与 `char` 均 1 字节，逐字节重解释安全；
10. **`文件路径规范化.h` / `路径字符串转换.h` 不得再包含 `引擎环境.h`**：会与日志链构成头文件循环（§4.4）；
11. **`标准库format特化.h` 只允许依赖预编译头与同目录纯工具头**：同样为规避日志系统的包含循环；
12. **`path_key_normalize` 锚点为空时**：`rfind("")` 恒返回 `size()`，会算出错误键——调用方须传非空锚点（日志侧传 `"白银纪元/"`）；
13. **`hash_combine` 的 `size_t` 参数**：混入前需先把字段哈希成 `size_t`（如 `std::hash<...>{}(x)`）。

## 五、模块运行链路

### 5.1 对象池排序查找链路（`binary_search` 迭代器版 + 投影）

```
Object_Pool<T>::find(key)
  │  （排序模式 is_sorted == true）
  ├─ 目标窗口 = [objects.begin() + min_valid_index.value(), objects.end())
  ├─ binary_search(窗口首, 窗口尾, key, comp, projector)
  │     ├─ original_first = 窗口首
  │     ├─ 迭代二分
  │     ├─ 命中 → return mid - original_first        ← 窗口内相对下标（optional<uint64_t>）
  │     └─ 未命中 → return std::nullopt
  ├─ index 有值 ?
  │     ├─ 是 → return objects.begin() + min_valid_index + *index   ← 加回偏移
  │     └─ 否 → return objects.end()
```

### 5.2 四叉树管理器区间查询链路（`range_binary_search` 降序 + 投影）

```
Quadtree_Manager 基础操作（X_sequence 降序树组）
  ├─ range = range_binary_search(X_sequence.begin(), X_sequence.end(),
  │          root.X, std::ranges::greater(), [](auto* p){ return p->root.X; })
  ├─ range 无值 ?
  │     ├─ 是 → 返回 -1（无同 X 坐标树）
  │     └─ 否 → 遍历 X_sequence[range->first .. range->second]
  │              处理所有「根 X 坐标 == root.X」的树节点
```

### 5.3 数值分配器回收查重链路（`binary_search` 容器版）

```
Number_Allocator::recycle(number)
  ├─ 回收池 recycle_numbers（升序，每次插入后 sort）
  ├─ index = binary_search(recycle_numbers, number, std::ranges::less())
  │        └─► binary_search(begin(池), end(池), number, less, identity)
  │              ├─ 命中（有值）→ 重复回收 → warn + return false
  │              └─ 未命中（nullopt）→ push_back + sort + return true
```

### 5.4 网格加载路径转换链路（`string_to_path`）

```
Mesh_Loader::load_obj(mesh_path /* UTF-8 std::string */)
  ├─ detail::path_check(mesh_path) 校验原样路径
  ├─ 有效 → read_path = string_to_path(mesh_path)     ← 本模块
  │              └─ std::u8string 逐字节搬运 → path（中文路径无损）
  └─ ifstream(read_path) 打开文件
```

### 5.5 日志路径键链路（`path_key_normalize` —— 本批新增）

```
logger.info(...) → Stream_Tree::stream_output(file_name, msg)
  └─ node_locate(file_name)
        └─ path_normalize(file_name)                       // Stream_Tree 私有转发
              ├─ static const std::string anchor = "白银纪元/";
              └─ detail::path_key_normalize(raw, anchor)   ← 本模块（本批新增）
                    ├─ path_normalize(string_to_path(raw)) // 词法规范化
                    ├─ path_to_string(...)                 // 转回 UTF-8 文本
                    └─ '\'→'/'、rfind(anchor) 裁剪、去前导、末尾补 '/' → 路径键
```

```
调用方（Object_Pool / Quadtree_Manager / Number_Allocator / Mesh_Loader /

        │
        ▼

        ├── 哈希混合.h            → hash_combine

        ├── 文件路径规范化.h      → path_normalize / path_key_normalize
```

结论：`Detail` 是引擎**被引用面最广的叶子工具模块**之一——几乎所有涉及「有序定位」「路径出入参 / 路径键」「JSON 字段校验」的模块都直接或间接依赖它。重开发时保持各函数签名与返回值约定（`optional` 下标/区间、UTF-8 字节保真、路径键形态）不变，即可保证全部下游调用方兼容。
