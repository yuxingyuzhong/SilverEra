## 二、模块功能介绍

### 2.1 模块定位

「线程」位于 `Application/Renderer/src/render/Thread/`，提供**帧内粗粒度并行执行器** `Thread_Pool`。它不属于对外公共面（不进入 `渲染器.h`），只被 `Renderer::Impl` 持有并由门面在调用侧使用。

一句话概括：**把「遍历 N 个元素、各自只写自己的下标槽位」的纯 CPU 循环按块分派到常驻工作线程，调用方同步等待全部块完成，结果与单线程逐字节一致。**

### 2.2 职责边界

| 属于本模块 | 不属于本模块 |
| --- | --- |
| 工作线程的启动 / 停止 / 收尾等待 | 决定「哪段循环该并行」（由使用方 `Renderer` 决定） |
| 任务分块（块长、块数、原子领取） | Vulkan 命令录制 / 描述符写（需外部同步，不能在此并行） |
| 并行派发次数观测 | 结果合并顺序（使用方保证各块只写自己的槽位） |

### 2.3 与使用方的关系

唯一使用方是 `Renderer::Impl::thread_pool`（见《门面》§5.3）。当前接入两处：
1. `Renderer::mesh_draw_instanced` 的逐实例视锥剔除（阈值 256 实例）；
2. `Renderer::frame_render` 的实例缓冲差异扫描（阈值 512 实例）。

## 三、模块公开接口介绍

| 接口 | 语义 |
| --- | --- |
| `bool threads_start(uint32_t count)` | 启动 `count`（钳 0..64）个工作线程；已启动则先全部回收；0 = 关闭；创建失败时回收已建线程并返回假（仅告警，不影响正确性） |
| `void threads_stop(void)` | 置停止标志、唤醒并 `join` 全部工作线程；幂等；**调用前提：无在途任务**（`ranges_run` 为同步调用，故正常使用下天然成立） |
| `uint32_t thread_count_get(void) const` | 当前工作线程数（0 = 单线程） |
| `bool active(void) const` | 是否已有工作线程 |
| `bool ranges_run(std::size_t total, std::size_t min_chunk, const std::function<void(std::size_t, std::size_t)>& body)` | 把 `[0, total)` 切成若干互不重叠、拼齐全区的半开区间交给 `body`；**同步阻塞到全部块完成**；无线程或 `total < 2 × min_chunk` 时由调用线程整段执行（不计派发次数） |
| `uint64_t dispatch_count_get(void) const` | 累计真正派发的并行任务次数（观测口径，见《门面》`Frame_Stats::parallel_dispatches`） |

约束：`body` 只能写各自区间对应的槽位，不得跨区间写入（否则结果不确定）。

## 四、模块私有方法介绍

| 私有方法 | 作用 |
| --- | --- |
| `void worker_main(void)` | 工作线程主循环：等「任务代号变化 / 停止标志」→ 记录已处理的代号 → `chunks_run()` → 递减未完成线程数 → 最后一个完成者唤醒调用线程 |
| `void chunks_run(void)` | 以 `job_cursor.fetch_add(job_chunk)` 原子领取一块并执行；领取越界即本轮结束；调用线程与工作线程共用此函数 |

同步原语：`mutex` ＋ `wake`（任务广播）＋ `done`（收尾通知）＋ 原子 `job_cursor`。

## 五、模块内部架构介绍

### 5.1 文件结构

```
Thread/
├── 线程池.h              # Thread_Pool 类声明（实现细节头，不进公共面）
├── 局部命名空间使用.h     # using std::function / size_t / vector
└── core/
    └── 作业分派.cpp      # 工作线程主循环、块领取、启动/停止、ranges_run
```

### 5.2 任务状态（`Thread_Pool` 成员）

| 成员 | 含义 |
| --- | --- |
| `workers` | 工作线程集合（仅主线程增删） |
| `job_body` / `job_total` / `job_chunk` | 本轮任务的调用体指针、元素总数、块长 |
| `job_cursor` | 原子游标（块领取） |
| `pending_workers` | 本轮尚未收尾的工作线程数 |
| `job_generation` | 任务代号（每派发自增，工作线程据此醒来且不重复执行同一轮） |
| `stopping` | 停止标志 |
| `dispatch_count` | 累计派发次数 |

## 六、模块设计/实现细节

1. **为什么用「代号」而不是「每轮建任务队列」**：单槽任务 ＋ 代号自增即可保证「醒来一次只执行一轮」，无需分配任务对象，也不存在上一轮任务被重复执行的风险。
2. **块长**：`chunk = max(total / (线程数 × 4), min_chunk)`，且 `chunk ≤ total / 2`（保证至少两块）；`total < 2 × min_chunk` 时退化。
3. **调用线程参与执行**：`ranges_run` 在唤醒工作线程后自己也领块，避免「N 个工作线程干活、调用线程空等」的浪费。
4. **收尾语义**：`done.wait(pred: pending_workers == 0)` 保证返回时全部块必已完成；`pending_workers` 只统计工作线程（调用线程的块在返回前已同步执行完）。
5. **异常口径**：`std::thread` 构造无 nothrow 形式，系统资源不足会抛 `std::system_error`；`threads_start` 捕获该异常并回收已建线程（这是本模块唯一的异常使用，与「内存分配禁用异常」的约束不冲突）。
6. **确定性**：模块本身不合并结果，只保证「每块恰好执行一次且区间不重叠」；顺序由使用方在压缩阶段单线程完成。
7. **生命周期**：`~Thread_Pool()` 调 `threads_stop()`；`Renderer::shutdown` 首行即停止线程池，故任何后续模块销毁都不会被工作线程访问。

## 七、模块运行链路详例

### 7.1 启动（`Renderer::init` 第 ⑧ 阶段前的配置块）

`Renderer_Config::render_threads` → 钳 0..64 → `threads_start(count)`；失败则告警并把生效线程数记为 0。

### 7.2 一次并行剔除（`mesh_draw_instanced`）

1. `instanced_cull_mask.assign(count, 0)`；
2. `thread_pool.active() && count >= 256` → `ranges_run(count, 256, body)`，`body` 对每个实例写 `mask[i] = 可见 ? 1 : 0`；
3. 返回后单线程按原顺序压缩可见实例矩阵到 `instanced_cull_scratch`；
4. 后续容量校验与绘制项组装与单线程路径完全相同。

### 7.3 一次并行差异扫描（`frame_render` 实例缓冲按需写入）

1. `instance_changed_mask.assign(instance_count, 0)`；
2. `instance_count >= 512` → `ranges_run`，`body` 逐实例比较 20 浮点并写掩码；
3. 单线程按掩码扫描连续变化段并 `buffer_write`；上传区间与逐实例比较结果一致。

### 7.4 停止（`Renderer::shutdown` 首行）

`threads_stop()` → 置 `stopping` → `wake.notify_all()` → 逐个 `join` → 清空任务状态。

## 本版次增量（第一百九十七轮：阶段 B —— 场景 pass 并行录制）

1. **新用法**：`ranges_run(段数, 1, body)` 把「单个命令缓冲」当作一个任务——`body` 内 `for (段 ∈ [begin, end))`
   逐段完整录制，**同一段必由同一线程录完**（块内顺序执行），故命令缓冲不跨线程。
2. 调用点：`Frame_Context::command_record_chain_present` 的场景 pass（由帧模块持有 `Thread_Pool*`，门面 init 传入）。
3. 段内统计写入 `std::vector<Recorded_Counts> parallel_counts` 的各自下标（不同元素并发写安全），
   `frame_recorded` 仅由调用线程在 `ranges_run` 返回后汇总。
4. 线程池未启动（0 线程）时帧模块退回单线程录制；`Thread_Pool` 本身无变化（阶段 A 的接口即够用）。

## 本版次增量（第二百一十九轮：实例缓存回写按块并行）

1. **新增用法**：`Renderer::frame_render` 在实例缓冲上传完成后，把「本帧实例 → 帧槽比较缓存」的回写循环
   （每实例 20 浮点）改为按块并行：`ranges_run(instance_count, INSTANCE_SCAN_PARALLEL_MIN, body)`，
   阈值与差异扫描共用 `Impl::INSTANCE_SCAN_PARALLEL_MIN = 512`。
2. **安全前提**：`body` 对每个实例只写 `instance_cache[index * INSTANCE_FLOAT_COUNT + ..]` 自己的槽位，
   块间区间不重叠；源 `pending_instances` 只读，故结果与单线程逐元素拷贝逐字节一致。
3. **回退**：线程池未启动或实例数低于阈值时由调用线程整段执行（与第 177 轮的差异扫描同口径）。
4. 观测口径不变：`parallel_dispatches` 仅在真正派发时递增，故该路径会在实例数达阈值时各多计一次派发。

## 本版次增量（第二百二十二轮：实例剔除并行阈值数据化）

1. **配置**：`Renderer_Config::cull_parallel_min_instances`（默认 256，钳 1..65536）；`init` 把生效值写入 `Impl::cull_parallel_min_instances`（原 `static constexpr CULL_PARALLEL_MIN_INSTANCES` 改为运行时成员）。
2. **门面**：`cull_parallel_min_instances_set(count)`（钳 1..65536、同值空操作、未初始化静默）与 `cull_parallel_min_instances()`（未初始化返回 0）。
3. **使用点**：`Renderer::mesh_draw_instanced` 的实例级剔除改为 `count >= cull_parallel_min_instances` 判定，并把同一阈值作为 `ranges_run` 的块长下限。
4. **不变部分**：差异扫描阈值仍为 `INSTANCE_SCAN_PARALLEL_MIN = 512`；默认 256 与引入配置前逐字节一致。
5. 用例：`实例剔除并行阈值可配`（64 实例 ＋ 阈值 1 触发并行、默认阈值走单线程；统计与画面一致；钳制断言）。

## 本版次增量（第二百二十六轮：实例扫描 / 回写并行阈值数据化）

1. **配置**：`Renderer_Config::instance_scan_parallel_min`（默认 512，钳 1..65536）；`init` 把生效值写入 `Impl::instance_scan_parallel_min`（原 `static constexpr INSTANCE_SCAN_PARALLEL_MIN` 改为运行时成员）。默认 512 与引入配置前逐字节一致。
2. **门面**：`instance_scan_parallel_min_set(count)`（钳 1..65536、同值空操作、未初始化静默）与 `instance_scan_parallel_min()`（未初始化返回 0）。
3. **使用点**：`frame_render` 中两处判定同时改用运行时阈值 —— ①实例缓冲**差异扫描**（`mark_changed_instance` 逐实例比较）；②**缓存回写**（本帧实例 → 帧槽比较缓存的 20 浮点拷贝）。两处均把同一值作为 `ranges_run` 的块长下限。
4. **派发统计**：两处均在 `ranges_run` 前后取 `dispatch_count_get()` 差值，分别累加到 `scan_parallel_dispatches` / `cache_parallel_dispatches`（第 224 轮引入的拆分字段）。
5. 用例（新文件 `渲染多线程阈值测试.cpp`，独立套件 `Renderer_Thread_Threshold_Test`）：同一批 64 实例渲染三帧（两个帧槽各建一次缓存，第 3 帧回首槽改实例触发差异扫描）；
   `instance_scan_parallel_min = 1` 时扫描 / 回写派发均 > 0，默认 512 时均为 0；两侧剔除与绘制实例数一致；配置默认值 512、钳制 0 → 1、超大 → 65536。
6. 说明：`渲染多线程测试.cpp` 已接近 800 行上限，故新用例单独成文件；该文件用 `TEST` ＋ 独立套件名（gtest 不允许同套件混用 `TEST` 与 `TEST_F`）。
