# 通用工具模块

本模块是 `EngineFoundation` 层中 `engine::detail` 命名空间下的一组头文件式工具，覆盖 `src/detail/` 全部 15 个文件与 `common/前置头文件包含.h`。全部实现为 inline 头文件，无 `.cpp`、无独立静态库目标。

## 二、模块功能介绍

**定位**。本模块是 `EngineFoundation` 层的"细节层"（`detail`）：它不实现任何子系统，只提供一批与业务无关、跨模块反复需要的基础手段——编码桥接、路径判定、文件字节读写、JSON 字段校验、整数分配、随机数、二分查找、哈希混合与 `std::format` 补齐。所有能力以头文件 inline 形式提供，调用方只需 `#include`，无需链接额外目标（本层静态库 `EngineFoundation` 也只因 `src/` 下的 `.cpp` 而存在，本模块不贡献任何 `.cpp`）。

**负责什么**。

- 把"UTF-8 文本"与操作系统本地编码的文件系统路径互相转换（`路径字符串转换.h`），并提供以 UTF-8 为唯一外部文本口径的路径函数族（`文件路径规范化.h`、`文件路径可用性校验.h`、`文件路径获取.h`）。
- 提供以错误码（而非异常）表达的路径探测与文件读取结果（`文件路径可用性校验.h` 的 `path_check` / `path_exists` / `file_size_get` / `file_read_whole` / `path_traversal_check`）。
- 提供整数编号的分配—回收闭环（`Number_Pool`），供对象池一类的"槽位 + 编号"双层索引结构使用。
- 提供无偏整数随机数（`Random_Generator`，PCG32 内核，拒绝采样），供 ACL 密钥与运行期盐等场景使用。
- 提供对有序序列的单点定位与等值区间定位（`binary_search` / `range_binary_search`），支持自定义比较器与投影器。
- 提供 `std::hash` 组合用的哈希混合手段（`hash_combine`）。
- 提供 `std::format` 对 `std::error_code`、`std::error_condition`、`std::filesystem::path` 的补齐，使日志与业务代码可以直接 `"{}"` 输出这三类值。
- 提供 `nlohmann::json` 的字段存在性与类型匹配校验，把"字段缺失 / 类型错误 / 内容为空"三态收敛为一个 `bool` 加日志。

**不负责什么**。

- 不做业务语义：不解析配置项含义、不做资源缓存、不定义资产格式；`field_check` 只判"有无且类型对不对"，不判取值范围。
- 不封装第三方：`field_check` 的签名里直接出现 `nlohmann::json`，第三方类型从该函数签名越出，是"读取边界"而非"封装边界"（与该层 `backend/` 约定无关，本模块不存在 backend 目录）。
- 不保证线程安全：除 `exe_path_get` / `exe_dir_get` 的函数局部静态初始化（C++ 保证线程安全）外，`Number_Pool` / `Random_Generator` 的并发访问由宿主负责；`Random_Generator::init()` 内部的 `static uint64_t counter` 无同步（见 §六 6.12、附 12）。
- 不做异常保证：除 `exe_path_probe` 会抛出 `std::runtime_error` 且被 `exe_path_get` 就地捕获外，本模块对外函数均以返回值表达失败（见 §六 6.6）。

**凭什么存在**。这组工具的存在理由是"单点化重复逻辑"，不是"抽象分层"。快照内可直接观察到的重复消除实例：

- 路径编码：`Gltf_Loader`、`Config_Loader`、`Log_Rules` 均需要 UTF-8 路径文本，若各自手写 `u8string` 往返，中文字符集稍有疏漏就会在 Windows 本地编码（GBK / 代码页）下产生截断或乱码。
- 文件读取：`gltf加载器.cpp` 的 tinygltf 回调、`网格加载器.cpp`、`材质加载器.cpp` 共用 `file_size_get` / `file_read_whole`，错误信息统一取 `std::error_code::message()`。
- 字段校验：本层 `Config_Loader`、`Event_Broker`、`Logging_Config_Bridge` 与上层 `EngineSystem` 的 `collision/Common/字段读取.h`、`Input_Manager`、`Focus_Manager` 共 20 余处调用同一条 `detail::field_check<T>`，字段名常量各归其域，判定逻辑只有一份。

**对外职责边界（依赖方向）**。本模块位于 `EngineFoundation` 最底部，除日志（`src/log/日志系统运行包.h` 中的全局 `inline Log logger`）与 `nlohmann::json` 外不依赖任何引擎内模块；反过来它被本层 `object/`、`event/`、`loader/`、`log/Rule`、`spatial/` 以及上层 `EngineSystem`、`EngineRenderer` 直接包含。唯一显式的"反向约束"写在 `标准库format特化.h` 的文件头注释里：该头会被 `log/Log/日志系统.h` 包含，因此只允许依赖预编译头与同目录纯工具头（`路径字符串转换.h`），否则构成"日志系统.h → 本文件 → 上层头 → 日志系统运行包.h → 日志系统.h"的头文件循环。这条约束是本模块内部依赖形态的决定性约束（见 §五）。

**与"预编译头"的关系**。`common/前置头文件包含.h` 被本模块每个文件的第一条业务包含语句引用（注释统一写作"//预编译头"），但构建脚本中并未调用 `target_precompile_headers`，它不参与编译器 PCH 机制，只是一份"每个翻译单元都先包含"的约定式头文件；它只收标准库，平台头由真正需要它们的文件自行包含（`文件路径获取.h` 即如此）。详见 §6.11。

## 三、模块公开接口

命名空间约定：两个类（`Number_Pool`、`Random_Generator`）与枚举 `Allocate_Order` 位于 `namespace engine`；其余全部自由函数位于 `namespace engine::detail`。`前置头文件包含.h` 不含命名空间，只含 `#include`。

### 3.1 数值与随机

#### 3.1.1 `Allocate_Order`（`数值分配器.h`）

```
enum class Allocate_Order
{
    LIFO,
    FIFO
};
```

- 语义：`Number_Pool` 复试（回收→再分配）时的取值顺序。`LIFO` 取回收队列末元素（`std::deque::back` / `pop_back`），`FIFO` 取首元素（`front` / `pop_front`）。
- 无默认值成员；`Number_Pool` 内部默认 `LIFO`。

#### 3.1.2 `Number_Pool`（`数值分配器.h`）

```
template <typename T = uint64_t>
    requires std::is_integral_v<T>
class Number_Pool
```

- 模板约束：`T` 必须为整型（`std::is_integral_v<T>` 为真），默认 `uint64_t`；`T` 同时决定容量上界与回绕点。
- 语义：维护"下一个新编号"与"已回收编号集合"，对外提供 `get` / `recycle` / `counts` / `capacity` / `reset` 与两项设置。首次分配从 `std::numeric_limits<T>::min()` 起（未调用 `set` 时），或从 `set` 指定的起点起。

公开成员逐条：

```
void set(T min_allocate_number)
```

- 语义：设置分配起点。记录 `min_number = min_allocate_number`；若 `min_number < next_number` 则仅打两条 `logger.info`（"Number_Pool::分配起点小于当前待分配新数值"、"Number_Pool::待分配数值保持当前大小"）并保持 `next_number`，否则立即把 `next_number` 拉平到起点。
- 失败/告警：不返回失败，越界或"起点倒退"只产生信息级日志；`set` 不校验已回收集合中是否存在小于新起点的旧编号。

```
void set(Allocate_Order order)
```

- 语义：切换复试顺序（`this->order = order`）。对已在回收队列中的元素立即生效（下次 `get` 按新顺序取）。

```
T get(void)
```

- 语义：取得一个编号。分支为：(1) 回收队列非空 → 按 `order` 弹出（弹出后不检查该值是否仍落在 `[min_number, ...]` 内）；(2) 回收队列空且 `next_number == std::numeric_limits<T>::max()` → 打 `logger.warn("Number_Pool::数值分配殆尽\n已进行回绕分配")`，令 `number = next_number = std::numeric_limits<T>::min()`（注意：回绕点用的是类型最小值的 `min()`，不是 `min_number`）；(3) 其余情况 `number = next_number++`。
- 副作用：无论从哪一路径取号，均执行 `mapping.erase(number)`（清除"已回收"标记）与 `allocated_counts++`。
- 失败：无失败返回；耗尽走回绕并在日志中声明，可能重复发放已在外部的编号（见 §六 6.2）。

```
bool recycle(T recycle_number)
```

- 语义：回收单个编号。若 `mapping.count(recycle_number)` 为真（该值已在回收集合中）→ `logger.warn("Number_Pool::待回收数值已被回收!!!")` 并返回 `false`；否则 `recycle_numbers.push_back(...)`、`mapping.insert(...)`、`allocated_counts--`，返回 `true`。
- 前置条件（实现未校验）：该编号确为先前 `get` 发放过；`allocated_counts` 为 `uint64_t`，回收到未发放编号会使计数下溢（见 附 3）。
- 幂等性：同一编号重复回收被拒绝（返回 `false`），但拒绝只依赖 `mapping`，不依赖"是否曾发放"。

```
void recycle(const std::vector<T>& numbers)
```

- 语义：批量回收，逐个调用单值重载；被调重载的 `bool` 结果被丢弃，因此批量回收**无法观察**部分失败。
- 前置条件：同单值重载。

```
uint64_t counts(void) const
```

- 语义：返回 `allocated_counts`（"当前占用量"计数）。`Object_Pool::size()` 直接用它作为合法对象数（见 §七 7.2）。

```
uint64_t capacity(void) const
```

- 语义：返回 `(std::numeric_limits<T>::max)() - min_number + 1`。当该表达式回绕为 0（可发生在 `T = uint64_t` 且 `min_number == 0`）时，先打两条 `logger.info`（内容为"Numer_Allocator::容量为uint64_t最大值加1"与"Numer_Allocator::表达式已溢出"，注意前缀拼写非 `Number_Pool`），随后**仍然返回 0**。
- 失败/告警：无失败返回；容量语义在回绕场景不可用（见 附 2）。

```
void reset(void)
```

- 语义：复位——`order` 回 `LIFO`、`next_number` 回 `std::numeric_limits<T>::min()`、`allocated_counts = 0`、清空 `recycle_numbers` 与 `mapping`。**不重置 `min_number`**（保留上次 `set` 的起点），因此复位后若仍想沿用旧起点，必须再次 `set(min)`——`Object_Pool::clear()` 正是"`reset()` → `set(LIFO)` → `set(min_ID)`"的写法（见 §七 7.2）。

#### 3.1.3 `Random_Generator`（`随机数生成器.h`）

```
template<typename T>
    requires std::is_integral_v<T>
class Random_Generator
```

- 模板约束：`T` 为整型；有符号/无符号决定全范围口径（有符号按下界 `min()`、无符号按 0）。
- 语义：PCG32（`state * 6364136223846793005ULL + inc` 线性同余 + xorshift + 旋转）驱动的 64 位原始随机流，经拒绝采样映射到目标区间，保证区间内各取值等概率。

公开成员逐条：

```
Random_Generator()
```

- 语义：默认构造即调用 `init()`（时间 + `std::time(nullptr)` + 进程内自增计数器组合种子）。

```
explicit Random_Generator(uint64_t seed_out)
```

- 语义：以指定种子调用 `init(seed_out)`；`explicit` 阻止 `uint64_t` 隐式转换。

```
void init(uint64_t seed_out)
```

- 语义：`random_seed = seed_out`；`g_pcg32.state = 0`；`g_pcg32.inc = (seed_out << 1u) | 1u`；预热一次 `(void)pcg32_random_raw()`。同一 `seed` 得到同一序列（可复现）。

```
void init()
```

- 语义：默认种子初始化。取 `std::chrono::high_resolution_clock::now()` 的纳秒计数，与 `static_cast<uint64_t>(std::time(nullptr))`、函数内 `static uint64_t counter` 的自增结果三者异或，存入 `random_seed` 并同样设置 `state = 0`、`inc = (random_seed << 1u) | 1u`、预热一次。
- 注意：`counter` 为普通静态变量，多线程并发默认构造时存在数据竞争（推测其后果为偶发同种子，见 附 12）。

```
uint64_t seed(void)
```

- 语义：返回最近一次 `init` 记录的 `random_seed`。**非 const 成员函数**，故 `const Random_Generator&` 上不可调用。

```
T operator()()
```

- 语义：生成 `T` 的全范围随机数。实现按 `std::is_signed_v<T>` 分派：有符号时 `u_min = static_cast<uint64_t>((std::numeric_limits<T>::min)())`、`span = static_cast<uint64_t>((std::numeric_limits<T>::max)()) - u_min + 1ULL`；无符号时 `u_min = 0`、`span = static_cast<uint64_t>((std::numeric_limits<T>::max)()) + 1ULL`；最后 `static_cast<T>(generate_in_range(u_min, span))`。
- 关键性质：有符号类型下 `u_min` 是无符号位模式（如 `int64_t` 的 `u_min` 为 `2^64 - 2^63`），`span` 也随之回绕，二者组合后 `u_min + (r % span)` 再回转 `T` 仍落在 `[min, max]`，无需特判。

```
T operator()(T min, T max)
```

- 语义：生成 `[min, max]` 闭区间随机数。若 `min > max` 先 `std::swap`（自动纠正反序，不报错）；`u_min = static_cast<uint64_t>(min)`；`span = static_cast<uint64_t>(max) - u_min + 1ULL`；返回 `static_cast<T>(generate_in_range(u_min, span))`。
- 单点区间：`min == max` 时 `span == 1`，`generate_in_range` 直接返回 `u_min`，不消耗随机数。

### 3.2 查找与哈希混合

#### 3.2.1 单点二分查找（`二分查找.h`）

```
template<typename RandomIt, typename T, typename Compare, typename Projection = std::identity>
std::optional<uint64_t> binary_search(RandomIt first, RandomIt last, const T& target,
    const Compare& comp, Projection proj = {})
```

- 语义：在 `[first, last)` 中按 `comp` 定位与 `target` 等价（`!comp(a,b) && !comp(b,a)`）的第一个元素，返回**相对 `first` 的全局下标**；未命中返回 `std::nullopt`。
- 实现要点：`mid = first + (last - first) / 2`、`while (first < last)`，因此要求随机访问迭代器（模板参数名为 `RandomIt`）；比较经 `std::invoke(proj, *mid)` 取键。
- 前置条件：序列已按 `comp` 严格弱序有序（`comp` 决定升/降序，如 `std::ranges::greater` 用于降序）；`comp` 对元素键与 `target` 必须构成同一等价类划分。
- 失败：仅返回 `std::nullopt`，不打日志。

```
template<typename Container, typename T, typename Compare, typename Projection = std::identity>
std::optional<uint64_t> binary_search(const Container& container, const T& target,
    const Compare& comp, Projection proj = {})
```

- 语义：容器重载，转调迭代器重载（`std::begin` / `std::end`）。
- 注意：与迭代器重载同处 `detail` 命名空间，若实参同时可匹配两组（如首参为容器），按重载决议容器版本优先。

#### 3.2.2 范围二分查找（`二分查找.h`）

```
template<typename RandomIt, typename T, typename Compare, typename Projection = std::identity>
std::optional<std::pair<uint64_t, uint64_t>> range_binary_search(RandomIt first, RandomIt last,
    const T& target, const Compare& comp, Projection proj = {})
```

- 语义：定位与 `target` 等价的**全部连续元素**，返回闭区间 `{左下标, 右下标}`（相对 `first`）；不存在等价元素时返回 `std::nullopt`。
- 实现：手工 `lower_bound`（推进条件 `comp(proj(*it), target)`）＋手工 `upper_bound`（推进条件 `!comp(target, proj(*it))`），两者均用 `std::distance` / `std::advance`；最终以 `lower == last || comp(proj(*lower), target) || comp(target, proj(*lower))` 判空。
- 前置条件：同 `binary_search`（有序 + 同一 `comp`）；与单点版本不同，本函数只依赖 `advance` / `distance`，不写 `first < last`，因此对非随机访问迭代器亦可工作，但模板参数仍命名 `RandomIt`（语义上宽于名字）。
- 失败：`std::nullopt`，无日志。

```
template<typename Container, typename T, typename Compare, typename Projection = std::identity>
std::optional<std::pair<uint64_t, uint64_t>> range_binary_search(const Container& container,
    const T& target, const Compare& comp, Projection proj = {})
```

- 语义：容器重载，转调迭代器重载。

#### 3.2.3 哈希混合（`哈希混合.h`）

```
inline void hash_combine(size_t& seed, size_t val) noexcept
```

- 语义：`seed ^= val + 0x9e3779b9 + (seed << 6) + (seed >> 2)`。`noexcept`；就地修改 `seed`，无返回值。
- 用法：调用方自行初始化 `seed`（快照内既有实践是 `std::size_t seed = 0`，见 `配置加载器.h` 的 `std::hash<Config_Content>` 与 `事件.h` 的 `std::hash<Event>`），再按字段顺序多次调用。
- 性质：顺序敏感（先 A 后 B 与先 B 后 A 结果不同）；常量 `0x9e3779b9` 是 32 位黄金分割常数，在 64 位 `size_t` 上直接沿用该常数（见 §六 6.3）；非加密安全哈希，仅用于桶分布。

### 3.3 路径

#### 3.3.1 字符串 ↔ 路径桥接（`路径字符串转换.h`）

```
inline std::string path_to_string(const std::filesystem::path& path)
```

- 语义：`path.u8string()` 得到 `std::u8string`，再以 `reinterpret_cast<const char*>` + 长度构造 `std::string`，即**输出 UTF-8 字节串**（Windows 下不会得到 GBK）。
- 前置条件：调用方约定该 `std::string` 的语义为 UTF-8；不做规范化，不做分隔符替换。

```
inline std::filesystem::path string_to_path(const std::string& path)
```

- 语义：以 `reinterpret_cast<const char8_t*>` + 长度构造 `std::u8string`，再构造 `std::filesystem::path`（在 Windows 上由标准库完成 UTF-8 → 本地宽字符的转换）。
- 前置条件：入参必须是 UTF-8；传入 GBK 文本会得到错误的宽字符序列（不报错、不校验）。空串得到空路径。

#### 3.3.2 路径规范化（`文件路径规范化.h`）

```
inline std::filesystem::path path_normalize(const std::filesystem::path& path)
```

- 语义：`lexically_normal()` 消解 `.` / `..` → 取 `relative_path()` → 以 `root_path()` 为基点逐节 `operator/=` 重组，跳过空节（尾部分隔符产生的空节由此被吃掉）。
- 结果形态：平台首选分隔符（Windows 为 `\`）、无尾部分隔符（根路径除外）、保留根名与根目录。
- 边界：**纯词法**，不访问文件系统、不解析符号链接、不做大小写折叠、不判断存在性。

```
inline std::string path_key_normalize(const std::string& raw, const std::string& root_anchor)
```

- 语义：生成用于"路径前缀比较与哈希"的路径键。步骤为：(1) `raw`（UTF-8）→ `string_to_path` → `path_normalize` → `path_to_string`；(2) 所有 `\` 改为 `/`；(3) 非空且末尾非 `/` 时补一个 `/`（目的：使"路径本身即锚点"时含尾 `/` 的锚点也能命中，源文件注释明确）；(4) `root_anchor` 非空时用 `rfind` 定位其最后一次出现，命中则 `erase(0, pos + root_anchor.size())`；(5) 循环剥离前导 `/` 与 `./` 片段。
- `root_anchor` 为空 → 只做 (1)(2)(3)(5)，即"基础规范化"；此时返回值恒以 `/` 结尾（或为空串）。
- 前置条件：`root_anchor` 语义上是"以 `/` 结尾的锚点目录"（调用方 `Log_Rules::root_set` 先以空锚点规范化得到该形态）。
- 注意：锚点定位是**子串匹配**而非节边界匹配（见 附 5）；锚点未命中时不报错，返回的是完整基础规范化文本（`Log_Rules::key_make_locked` 在外层先用 `rfind` 判越界）。

```
inline bool path_prefix_check(const std::filesystem::path& prefix,
    const std::filesystem::path& target)
```

- 语义：`prefix` 是否为 `target` 的目录前缀（逐节比较）。空前缀直接返回 `false`；`target` 节数少于 `prefix` 返回 `false`；全部节匹配返回 `true`（含 `prefix == target` 的情形）。
- 前置条件：两侧应已规范化（`path_normalize`）；比较是**节级字节比较、区分大小写**，Windows 大小写不敏感文件系统上的等价路径会被判为不同。
- 失败：纯谓词，无日志。

```
inline bool path_prefix_check(const std::string& prefix, const std::string& target)
```

- 语义：两个字符串按 UTF-8 解释转路径后调用 `path` 重载。

#### 3.3.3 可执行路径探测（`文件路径获取.h`）

```
inline std::filesystem::path exe_path_probe(void)
```

- 语义：平台分派的可执行文件路径探测（该文件为本模块唯一的平台相关代码）。
  - Windows 分支（`_WIN32` / `_WIN64`）：`std::wstring buffer(32767, L'\0')`，`GetModuleFileNameW(nullptr, buffer.data(), static_cast<DWORD>(buffer.size()))`；`size == 0` 抛 `std::runtime_error("GetModuleFileNameW failed")`；`size >= buffer.size()` 视为截断，`resize(size + 1)` 后重试，仍失败抛 `"GetModuleFileNameW failed after resize"`；最后按 `size` 截断并构造 `path(buffer)`（宽字符直接进路径，中文不会乱码）。
  - Linux 分支：`std::string buffer(PATH_MAX, '\0')`，`readlink("/proc/self/exe")`，返回长度恰好等于缓冲区长度时按 2 倍扩容重试；`len == -1` 抛 `"readlink /proc/self/exe failed"`。
  - macOS 分支：`_NSGetExecutablePath(nullptr, &size)` 先取所需长度，`size == 0` 抛 `"failed to get size"`；再以该长度取路径，返回非 0 抛 `"_NSGetExecutablePath failed"`。
  - 其他平台：`#error "Unsupported platform"`。
- 该函数体前的包含按平台条件编译配有 `windows.h`（含 `#ifndef NOMINMAX / #define NOMINMAX`，避免 `min`/`max` 宏污染标准库）、`unistd.h`、`mach-o/dyld.h`。
- 语义上它是 `exe_path_get` 的私有实现细节，但因是 `detail` 命名空间的 inline 自由函数而在编译期可见（见 §四）。

```
inline const std::filesystem::path& exe_path_get(void)
```

- 语义：函数局部 `static const std::filesystem::path path = [] {...}()`，首次调用时执行 `exe_path_probe()`；捕获 `std::exception` 时打两条 `logger.error`（"错误: {}" 与 "已回退到工作目录"）并回退 `std::filesystem::current_path()`。
- 生命周期：进程内只探测一次（magic static），返回常量引用；初始化线程安全由语言保证。注释称此举"规避跨翻译单元静态初始化顺序问题"。

```
inline const std::filesystem::path& exe_dir_get(void)
```

- 语义：函数局部 `static const std::filesystem::path dir = exe_path_get().parent_path()`，首次调用时由可执行路径派生目录，返回常量引用。
- 快照内使用者：`Config_Loader::base_dir_get()`（返回 `detail::exe_dir_get()`）与 `EngineRenderer` 的 `Shader_Context`（`detail::exe_dir_get() / "shaders"`）。

```
inline std::filesystem::path absolute_path_get(const std::filesystem::path& path)
```

- 语义：返回 `exe_dir_get() / path`。按 `std::filesystem::path::operator/` 的标准语义，`path` 本身为绝对路径时右侧覆盖左侧，即原样返回该绝对路径；相对路径则拼到可执行目录下。
- 失败：无（拼接为纯词法操作）。快照内无调用点。

```
inline std::filesystem::path absolute_path_get(const std::string& path)
```

- 语义：入参按 UTF-8 解释（注释明写"要求 string 编码格式为 UTF-8"），先构造 `std::u8string`，再 `exe_dir_get() / u8_path`。作用与上一重载等价，唯一差别是入参形态。

#### 3.3.4 路径可用性与文件读取（`文件路径可用性校验.h`）

```
inline bool path_check(const std::filesystem::path& target_path)
```

- 语义：有效性检查。先判 `target_path.begin() == target_path.end()`（空路径）→ `logger.info("路径无效")` 返回 `false`；再以 `std::error_code ec` 调用 `std::filesystem::exists(target_path, ec)` 与 `std::filesystem::is_regular_file(target_path, ec)`，任一为假 → `logger.info("访问路径异常\n请自行排查访问路径是否存在及是否可读取")`、`logger.info("{}", ec)`（经 `formatter<std::error_code>` 输出 `[值] 消息`）、`ec.clear()`、返回 `false`；全部通过返回 `true`。
- 关键限制：`is_regular_file` 使其**拒绝目录**；因此不能用于"目录是否可访问"的判定。
- 失败表达：`bool` + 日志；不抛异常、不回传错误码。

```
inline bool path_check(const std::string& target_path)
```

- 语义：`string_to_path` 后转调 `path` 重载（UTF-8 入参）。

```
inline bool path_exists(const std::filesystem::path& target_path)
```

- 语义：静默存在性检查——`std::filesystem::exists(target_path, error_info) && !error_info`。不写日志、不区分"不存在"与"系统错误"、不判是否普通文件（目录返回 `true`）。
- 用途：探测式调用（如 tinygltf 的 `FileExists` 回调），避免"预期不存在"的路径刷日志。

```
inline bool path_exists(const std::string& target_path)
```

- 语义：UTF-8 字符串转路径后转调 `path` 重载。

```
inline bool file_size_get(const std::filesystem::path& target_path,
    uintmax_t& size_out, std::error_code& error_info)
```

- 语义：先 `error_info.clear()`，再 `size_out = std::filesystem::file_size(target_path, error_info)`，返回 `!error_info`（成功与否）。
- 出参：`size_out` 为输出；`error_info` 为输入兼输出（进入时不清也无效，函数入口即清）。失败时 `size_out` 被赋为 0，错误码留在 `error_info` 供调用方取 `message()`。

```
inline bool file_size_get(const std::string& target_path,
    uintmax_t& size_out, std::error_code& error_info)
```

- 语义：UTF-8 字符串转路径后转调。

```
inline bool file_read_whole(const std::filesystem::path& target_path,
    std::vector<unsigned char>& bytes_out, std::error_code& error_info)
```

- 语义：整文件二进制读取。先清空 `bytes_out` 与 `error_info`；`std::ifstream file(target_path, std::ios::binary | std::ios::ate)`；打开失败 → `error_info = std::make_error_code(std::errc::no_such_file_or_directory)`、返回 `false`；`tellg()` 为负 → `errc::io_error`、`false`；`resize` 到该字节数、`seekg(0, std::ios::beg)`；非空文件 `read` 后若流失效 → `errc::io_error`、清空 `bytes_out`、`false`；成功返回 `true`（空文件合法，直接为真）。
- 前置条件：体量上限由调用方自行校验（文件头注释明写"本函数只负责读取"；`Gltf_Loader` 用 `gltf_detail::max_file_bytes` 先判）。

```
inline bool file_read_whole(const std::string& target_path,
    std::vector<unsigned char>& bytes_out, std::error_code& error_info)
```

- 语义：UTF-8 字符串转路径后转调。

```
inline bool path_traversal_check(const std::filesystem::path& target_path)
```

- 语义：逐节遍历路径成分，任一成分为 `".."` 即返回 `false`；否则 `true`。纯谓词，不做文件系统访问、不做规范化、不写日志。
- 用途：拒绝"父目录返回"的外部 URI（`gltf加载器.cpp` 的 `fs_exists` / `fs_read` / `fs_size` 三个回调与 `Config_Loader::path_safety_check`）。
- 注意：检查对象是**原始节序列**，因此 `a/../b` 即便规范化后等价于 `b` 也会被拒绝；绝对路径本身不在此限制、由调用方按场景决定（文件头注释明确）。

```
inline bool path_traversal_check(const std::string& target_path)
```

- 语义：UTF-8 字符串转路径后转调。

### 3.4 文本与校验

#### 3.4.1 文本行解析（`文本行解析.h`）

```
inline std::string text_trim(const std::string& text)
```

- 语义：`find_first_not_of(" \t\r\n")` 与 `find_last_not_of(" \t\r\n")` 裁剪两端；全空白（含空串）返回空 `std::string`。
- 字符集：仅空格、制表、回车、换行；不含 `\v` / `\f` / 全角空格 / BOM。
- 返回：新字符串，不改原串。

```
inline void carriage_return_trim(std::string& line)
```

- 语义：若 `line` 非空且末字符为 `\r` 则 `pop_back()`；只处理**一个**行尾回车。原地修改，无返回。

```
inline bool float_parse(const std::string& text, float& value)
```

- 语义：空串直接 `false`；否则 `std::strtof(text.c_str(), &end)`，要求 `end != nullptr && *end == '\0'`（完整消费，含尾随字符即失败）且 `std::isfinite(parsed)`（拒绝 `nan` / `inf`，也拒绝溢出为 inf 的超大指数），通过时写回 `value` 并返回 `true`。
- 前置条件：调用方通常先用 `>>` 切 token 或在行内定位片段；`strtof` 本身会跳过前导空白，故 `" 1.5"` 可解析。
- 失败：返回 `false` 且**不修改** `value`。

#### 3.4.2 数值校验（`数值校验.h`）

```
inline bool finite_check(float value)
```

- 语义：`std::isfinite(value)`，即排除 `NaN` 与 `±inf`。

```
inline bool unit_interval_check(float value)
```

- 语义：`finite_check(value) && value >= 0.0f && value <= 1.0f`（闭区间，两端合法）。

```
inline bool range_check(float value, float min, float max)
```

- 语义：`finite_check(value) && value >= min && value <= max`（闭区间）。
- 注意：不校验 `min <= max`；若调用方传反序区间则恒为 `false`。仅提供 `float` 版本，无 `double` 重载；快照内无调用点（上层实际使用 `finite_check` / `unit_interval_check`）。

#### 3.4.3 JSON 字段校验（`json字段可用性校验.h`）

```
template<typename T>
inline bool field_check(const nlohmann::json& config, const std::string& field)
```

- 语义：分两步。
  1. 存在性：`config.contains(field)` 为假 → `logger.warn("detail::未包含指定字段: {}", field)`、返回 `false`。
  2. 类型匹配（`if constexpr` 分派）：
     - `T == bool`：要求 `is_boolean()`，否则 `logger.info("detail::字段 {} 非布尔格式")`、`false`。
     - `std::is_integral_v<T>`：要求 `is_number_integer()`（该谓词对无符号整数同样为真），否则"字段 {} 非整数格式"、`false`；**不做取值域校验**。
     - `std::is_floating_point_v<T>`：要求 `is_number_float()`，否则"字段 {} 非浮点数格式"、`false`；JSON 里写成整数字面量的字段（如 `1`）会被判为非浮点而失败。
     - `T == std::string`：要求 `is_string()`，再要求 `get_ref<const std::string&>().empty()` 为假，否则"字段 {} 类型不匹配" / "字段 {} 内容为空"、`false`。
     - 其他类型（含 `nlohmann::json`、`std::vector<T>` 等）：`try { config[field].get<T>(); } catch (const nlohmann::json::type_error&)` → "字段 {} 类型不匹配"、`false`；随后若字段是数组或对象且为空 → "字段 {} 内容为空"、`false`。
  3. 全部通过返回 `true`。
- 前置条件：`config` 为紧凑（非 null）JSON 节点；`field` 为 UTF-8 键名。
- 副作用：失败路径写日志（不同分支级别不同：缺失是 `warn`，类型/内容错误是 `info`）；无异常外泄（`get<T>()` 的异常在本函数内被收敛）。
- 注意：对 `T = nlohmann::json`，`get<json>()` 恒成功，故该分支实际等效于"存在 + （数组/对象则须非空）"，`Event_Broker` 与 `Config_Loader` 以此读取 `dirty_mark` / `config_routes` 等动态结构（详见 §6.10）。

### 3.5 格式化定制

`标准库format特化.h` 在 `namespace std` 内定义三个**全特化** `formatter`，每个都提供 `constexpr auto parse(format_parse_context& ctx)`（返回 `ctx.begin()`，即忽略一切格式说明符）与 `auto format(...) const`（返回 `std::format_to` 的迭代器）。

```
template<> struct formatter<std::error_code>
```

- `parse`：忽略说明符。
- `format(const std::error_code& error_info, format_context& ctx) const`：输出 `"[{}] {}"`，即 `value()` 与 `message()`。业务侧 `logger.error("{}", error_info)` 依赖此特化（脚本与 `Config_Loader::error_out` 均如此使用）。

```
template<> struct formatter<std::error_condition>
```

- 同上，字段为 `condition.value()` / `condition.message()`。

```
template<> struct formatter<std::filesystem::path>
```

- `format(const std::filesystem::path& path, format_context& ctx) const`：经 `engine::detail::path_to_string(path)` 转 UTF-8 文本后以 `"{}"` 写出，保证中文路径的日志可读（不出现本地编码乱码）。

文件头注释同时给出**定制点规则**：`std::vector<T>` / `std::optional<T>` 这类需要偏特化 `std::formatter` 的情形标准不允许，故不在本文件补；项目自定义类型的 `formatter` 特化应放在该类型自己的头文件中（示例：`Config_Content` 的特化在 `loader/config/Config_Loader/配置加载器.h`，输出"索引[索引目录] 配置[配置目录]"）。

## 四、模块私有方法

本模块没有 `.cpp`、没有匿名命名空间、没有 `core/` 子目录；"私有"体现在三处：类的私有数据成员语义、类的私有成员函数、以及语义上仅供 `detail` 内部使用的自由函数。

### 4.1 `Number_Pool` 私有数据成员（`数值分配器.h`）

```
Allocate_Order order = Allocate_Order::LIFO;   // 复试顺序
T min_number = (std::numeric_limits<T>::min)(); // 分配起点（set 写入；reset 不恢复）
T next_number = (std::numeric_limits<T>::min)();// 下一个未发放的新编号
uint64_t allocated_counts = 0;                  // 当前占用量计数
std::deque<T> recycle_numbers;                  // 回收队列（复试来源）
std::unordered_set<T> mapping;                  // 回收标记集合（重复回收检测 + 取号时清除）
```

数据关系（实现层面的不变量，供阅读与改码判断）：

- `mapping` 与 `recycle_numbers` 是"同一集合的两种表示"：`recycle` 同时 `push_back` 与 `insert`，`get` 弹出时同时 `erase`。二者必须保持一致，任何只改其一的改动都会破坏"重复回收检测"。
- `next_number` 表示的"新编号区"与 `recycle_numbers` 表示的"回收编号区"**互斥但不校验**：`recycle` 不检查传入值是否 ≤ `next_number`，因此若回收一个尚未发放的未来编号，它会先进入复试队列，之后又可能被 `next_number++` 再发放一次（重复发放风险，见 附 3）。
- `allocated_counts` 只由 `get` 自增、`recycle` 自减，故它是"净占用量"而非"累计发放量"；`reset` 归零。若 `recycle` 多于 `get`（可能由上述未校验路径触发），`uint64_t` 会回绕成极大值。

### 4.2 `Number_Pool` 无私有成员函数

`set` / `get` / `recycle` / `counts` / `capacity` / `reset` 全部在类体内联实现，无转发层。这也意味着修改语义必须直接改 `get` / `recycle` 的分支体，没有独立可替换的辅助点。

### 4.3 `Random_Generator` 私有类型与私有函数（`随机数生成器.h`）

```
struct Pcg32
{
    uint64_t state = 0;
    uint64_t inc = 0;
} g_pcg32;   // PCG32 状态（state 与 inc 均为 64 位）
uint64_t random_seed = 0;   // 最近一次 init 记录的种子（seed() 返回它）
```

```
uint32_t pcg32_random_raw()
```

- 语义：取 `old_state = g_pcg32.state`；`g_pcg32.state = old_state * 6364136223846793005ULL + g_pcg32.inc`；`xorshifted = (uint32_t)(((old_state >> 18u) ^ old_state) >> 27u)`；`rot = (uint32_t)(old_state >> 59u)`；返回 `(xorshifted >> rot) | (xorshifted << ((-(int)rot) & 31))`。这是 PCG32 的标准输出函数（含旋转抵消，`rot == 0` 时左移 0 位不越界）。

```
uint64_t generate_raw_64()
```

- 语义：连续两次 `pcg32_random_raw()`，先取作高 32 位、后取作低 32 位，`(high << 32) | low`。一次 64 位取值推进状态两次。

```
uint64_t generate_in_range(uint64_t u_min, uint64_t span)
```

- 语义：`r = generate_raw_64()`；`span == 0` 视为 `2^64` 全范围，直接返回 `r`；`span == 1` 直接返回 `u_min`（不取随机数）；否则 `limit = u_max - u_max % span`（`u_max = std::numeric_limits<uint64_t>::max()`），`while (r >= limit) r = generate_raw_64();`，最后返回 `u_min + (r % span)`。
- 拒绝采样的正确性：`u_max % span` 与 `2^64 % span` 相差恰好 1（模 `span`），被 `u_max` 而非 `2^64` 作被减数正好抵消，因此 `limit` 等价于"`2^64 - 2^64 % span`"，被接受的取值集合大小是 `span` 的整数倍，映射无偏。
- 已知极端：若 `span` 极大（如 `uint64_t` 全范围时 `span == 0` 已走短路），不会出现 `limit == 0` 的死循环。

### 4.4 语义上私有的自由函数

```
inline std::filesystem::path exe_path_probe(void)
```

- 位置：`engine::detail`（`文件路径获取.h`）。虽为可外部调用的 inline 函数，但快照内唯一调用者是同文件的 `exe_path_get()` 的静态初始化 lambda；语义上属探测实现细节，已记在 §三 3.3.3 以便签名可查，此处只强调它**会抛异常**（本模块唯一抛出点），调用方必须自带捕获，否则异常会穿透到 `exe_path_get` 以外（快照内不存在其他调用者）。

### 4.5 `exe_path_get` / `exe_dir_get` 内部的静态初始化 lambda

```
static const std::filesystem::path path = [] { try { return exe_path_probe(); } catch (const std::exception& e) { logger.error("错误: {}", e.what()); logger.error("已回退到工作目录"); return std::filesystem::current_path(); } }();
static const std::filesystem::path dir = exe_path_get().parent_path();
```

- 这两个 lambda 无名字、不可复用，是"失败即降级"的落点：探测失败不阻断启动，代价是此后所有基于可执行目录的相对路径都会指向进程当前工作目录。该降级只发生一次（magic static 之后不再重试）。

### 4.6 聚合头内部构成（`methods/package/`）

三个聚合头无函数，其"私有构成"就是 `#include` 列表，需按依赖方向记录，因为它们直接决定了包含一个聚合头会拉进哪些平台头与日志：

- `路径操作工具.h` → `../路径字符串转换.h`、`../文件路径规范化.h`、`../文件路径获取.h`。后两者使该聚合头间接带入 `windows.h`（Windows）与 `logger`。
- `数据校验工具.h` → `../json字段可用性校验.h`（带入 `nlohmann/json.hpp` 与 `logger`）、`../文件路径可用性校验.h`（带入 `logger` 与 `路径字符串转换.h`）、`../数值校验.h`。
- `文本处理工具.h` → `../文本行解析.h`（唯一被聚合者，无日志依赖）。

## 五、模块内部架构

### 5.1 子目录分工

目录形态为"`common/` 放预编译头，`src/detail/` 下分 `class/` 与 `methods/`，`methods/package/` 放聚合头"（完整文件清单见 §一）。`class/` 与 `methods/` 的划分是"是否有对象生命周期"：两个类持有状态、可赋值、可多实例共存；`methods/` 下全部为无状态函数，除 `exe_path_get` / `exe_dir_get` 的函数局部静态缓存外不持有任何跨调用状态。

### 5.3 数据流动与所有权

- 两个类（`Number_Pool`、`Random_Generator`）都是**值语义对象**：无堆分配、无指针成员、默认可拷贝/可移动（隐式生成的拷贝构造/赋值不会破坏内部一致性，因为 `mapping` 与 `recycle_numbers` 会被整体复制）。所有权完全归宿主实例（`Object_Pool` 内嵌两个 `Number_Pool`，`Event_Terminal` 内嵌 `Random_Generator<int64_t>`）。
- `methods/` 下函数均为纯数据搬运：入参为 `const&` 或值，出参为返回值 / 引用出参（`float_parse` 的 `value`、`file_size_get` 的 `size_out`、`file_read_whole` 的 `bytes_out`）。没有任何函数持有跨调用的可变状态（唯一例外是 `exe_path_get` / `exe_dir_get` 的只读缓存）。
- 编码边界：`std::filesystem::path` 在引擎内部被当作"原生路径对象"，一旦要进入文本域（日志、配置键、JSON、哈希键）就必须经 `path_to_string` 转 UTF-8；反向从文本域进入路径域必须经 `string_to_path`。所有以 `std::string` 接收路径的函数（`path_check` / `path_exists` / `file_size_get` / `file_read_whole` / `path_traversal_check` / `path_key_normalize` / `absolute_path_get` / `path_prefix_check`）都在内部先做这一步转换，因此调用方只需保证"字符串是 UTF-8"这一条。

### 5.4 生命周期与线程归属

- `exe_path_get()` / `exe_dir_get()`：进程级单次初始化（magic static），之后只读；初始化期线程安全由 C++ 语言保证，初始化完成后并发读取无需同步。探测失败会永久降级到"进程当前工作目录"。
- `Number_Pool`：无锁。线程归属由宿主决定；同一实例跨线程 `get` / `recycle` 会产生数据竞争（`deque` 与 `unordered_set` 均非线程安全）。快照内 `Object_Pool` 未见加锁，说明其线程模型假定单线程或由更高层串行化。
- `Random_Generator`：无锁；`Pcg32` 状态非原子。唯一"全局"状态是 `init()` 内的 `static uint64_t counter`（默认构造时自增），多线程并发默认构造存在竞争（见 附 12）。
- `logger`：`src/log/日志系统运行包.h` 中的 `inline Log logger;` 是进程级单例（C++17 inline 变量，跨翻译单元同一实体）。本模块的日志写点集中在：`Number_Pool`（4 处：2 info + 2 warn）、`文件路径可用性校验.h`（`path_check` 2 处 info）、`文件路径获取.h`（2 处 error）、`json字段可用性校验.h`（缺失 warn / 类型与内容 info）。
- 模块自身无静态构造需求，可安全被任何翻译单元在任意静态初始化阶段包含（`logger` 是 inline 变量，首次使用前已可用）。

### 5.5 与构建的关系

- 无 `.cpp`：`源文件列表.cmake` 把这 16 个文件全部登记在 `target_sources(EngineFoundation PRIVATE ...)` 的**头文件段**，注释明确"头文件不参与编译，只为让 IDE 建立文件索引"，因此改名/迁移会被 IDE 操作同步改写。
- 无预编译头机制：`CMakeLists.txt` 未配置 `target_precompile_headers`；所谓"预编译头"是约定式包含。真正的编译期口径是 MSVC 的 `/utf-8`（`target_compile_options(... /MP /utf-8)`）与 `_CRT_SECURE_NO_WARNINGS`，GCC/Clang 侧为 `-Wall -Wextra -pedantic` 与 `_GNU_SOURCE`。
- 包含根：私有包含根为"项目根 + 本层根"，故头文件内跨目录包含写 `Engine/EngineFoundation/...` 全路径，`.cpp` 内写 `src/...` 层根相对（`gltf加载器.cpp`、`材质加载器.cpp`、`网格加载器.cpp` 对 `package/文本处理工具.h` 就采用 `"src/detail/methods/package/文本处理工具.h"` 写法）。
- 对外面：本层 `cmake/对外接口.cmake` 把整个 `Engine/EngineFoundation/src` 与 `common` 镜像到上层头快照（`MIRROR_DIRS=Engine/EngineFoundation/common;Engine/EngineFoundation/src`），因此本模块的全部头文件**属于上层可见的公共头**，`detail` 只是命名约定而非访问控制。

## 六、模块设计 / 实现细节

### 6.1 UTF-8 与 Windows 本地编码的转换约定（项目级）

**唯一事实口径**：引擎内部一切"路径文本"（`std::string` 承载的路径、日志中的路径、JSON 中的路径、路径键、哈希键）都是 **UTF-8**；一切"操作系统交互"都通过 `std::filesystem::path` 发生，由标准库负责 UTF-8 ↔ 本地编码（Windows 为 UTF-16 宽字符，Linux/macOS 为 UTF-8 字节）。这条口径在源码中有两处显式声明：`absolute_path_get(const std::string&)` 的注释"要求string编码格式为UTF-8"、`文件路径获取.h` 的 Windows 分支注释"使用宽字符 API 获取可执行文件路径，支持中文等 Unicode"。

**转换入口清单**（哪一侧进入哪一侧，全部落在此文件可查）：

| 入口 | 位置 | 方向 | 说明 |
| --- | --- | --- | --- |
| `path_to_string(const path&)` | `路径字符串转换.h` | path → UTF-8 文本 | 唯一的"路径转文本"原语；经 `u8string` + `reinterpret_cast` |
| `string_to_path(const std::string&)` | `路径字符串转换.h` | UTF-8 文本 → path | 唯一的"文本转路径"原语；经 `char8_t` 重新解释后构造 `path` |
| `formatter<std::filesystem::path>::format` | `标准库format特化.h` | path → 日志文本 | 复用 `path_to_string`，使 `logger.info("{}", path)` 不出现本地编码乱码 |
| `path_key_normalize` | `文件路径规范化.h` | UTF-8 → UTF-8 | 内部经 `string_to_path` → `path_normalize` → `path_to_string` |
| 6 个 `std::string` 重载 | `文件路径可用性校验.h` | UTF-8 → path → 判定 | `path_check` / `path_exists` / `file_size_get` / `file_read_whole` / `path_traversal_check`（均先 `string_to_path`） |
| `path_prefix_check(const std::string&, const std::string&)` | `文件路径规范化.h` | UTF-8 → path → 比较 | 两个入参都转路径后再逐节比较 |
| `absolute_path_get(const std::string&)` | `文件路径获取.h` | UTF-8 → path | 直接构造 `u8string` 后与可执行目录拼接 |
| `Config_Content` 的 `std::string` 构造 | `loader/config/Config_Loader/配置加载器.h` | UTF-8 → path | 先 `string_to_path` 再 `path_normalize`（消费者侧遵循口径的实例） |
| `Gltf_Loader::load_file` 的 `base_dir` | `loader/assets/Gltf_Loader/core/gltf加载器.cpp` | path → UTF-8 | 交给 tinygltf 的 URI 回调，注释明写"UTF-8" |

**实现细节与坑**：

- `path.u8string()` 在 C++20 返回 `std::u8string`（元素类型 `char8_t`），`reinterpret_cast<const char*>` 只是位模式重解释，不做编码转换；之所以能"输出 UTF-8"，是因为 `u8string()` 本身保证了编码（Windows 下由标准库把宽字符转成 UTF-8）。
- **不要**用 `path.string()` 做同类事情：在 Windows 上它按本地代码页转换（可能是 GBK / ANSI），中文路径会得到乱码或问号。本模块没有任何一处使用 `path.string()`（`path_traversal_check` 用的是 `part.string()`，但只与 ASCII 字面量 `".."` 比较，不涉输出）。
- 项目未使用 `std::u8path` / `u8string` 之外的 C++20 Unicode 设施，也没有 `codecvt` 方案；`前置头文件包含.h` 未包含 `<codecvt>`、`<locale>`，说明没有第二套转换路径。
- 源文件字符集由 `/utf-8` 编译选项保证（`CMakeLists.txt` 第 7 节注释"指定源文件字符集为 UTF-8，避免中文乱码警告"）；即源码里的中文字面量、文件名与运行时 UTF-8 文本是同一编码域，无需额外转换。归档阶段另由 `cmake/ar_rsp_bom.ps1` 给响应文件补 BOM，以解决 `lib.exe` 按 ANSI 解读中文对象名的问题——这是"中文文件名"在构建链上的配套处理，与本模块的运行时编码约定互不替代。
- 一个可观察的**口径漂移**：`EngineRenderer` 的 `render/Shader/core/着色器.cpp` 在匿名命名空间里自写了一份 `path_to_utf8(const std::filesystem::path&)`（同样 `u8string` + `reinterpret_cast`），未复用 `detail::path_to_string`。这是上层对同一原语的重复实现（见 附 8）。

### 6.2 数值分配器的复用语义

- **两类编号区**：`next_number` 之前的"已发放/可发放"区与回收队列。"新编号只增不减"（除回绕），回收编号优先复试（`recycle_numbers` 非空时永远先取回收），因此 `Number_Pool` 本质是"带复用的单调分配器"，不是空闲链表。
- **LIFO 的实际效果**：`Object_Pool` 构造时显式 `set(Allocate_Order::LIFO)`，配合"卸载时把对象交换到无效区边界再回收索引"，使最近卸载的槽位最可能被下一次 `build` 立刻复用——缓存局部性优先。`FIFO` 未被快照内任何代码使用，保留为选项。
- **回收去重**：`mapping`（`std::unordered_set<T>`）在 `recycle` 入口做 `count` 判定，重复回收返回 `false` 并告警 `"待回收数值已被回收!!!"`。注意这是"回收集合成员去重"，不是"是否曾发放"的校验：回收一个从未发放的值会成功入队并让计数减一（`uint64_t` 下溢风险，见 附 3）。`get` 时 `mapping.erase(number)` 是不可省略的对称操作，漏掉会导致该值再也不能被回收（`count` 恒真）。
- **编号保留**：`Object_Pool` 用 `ID_allocator.set(min_ID = 1)` 把 `0` 留作"非法编号"（卸载后对象写 `object_ID = min_ID - 1`，即 0），`index_allocator.set(0)` 从 0 开始。`min_number` 只影响 `set` 之后的 `next_number` 初始化与 `capacity()` 计算，不影响已回收集合的内容。
- **回绕**：`next_number == numeric_limits<T>::max()` 时不再自增，而是回绕到 `numeric_limits<T>::min()` 并告警"数值分配殆尽"。回绕点用**类型最小值**而非 `min_number`，所以回绕会绕过保留区（例如 `min_ID = 1` 时，回绕首发的编号是 0，与"0 为非法编号"的约定冲突）。这是耗尽场景下的既定取舍：优先"不崩"，一致性靠日志提示人工排查。
- **`reset` 不是"恢复到构造态"**：它不重置 `min_number`。`Object_Pool::clear()` 的三步（`reset()` → `set(LIFO)` → `set(min_ID)`）正是为弥补这一点而写；若只 `reset` 就继续分配，`next_number` 会从类型最小值开始，`min_number` 仍是旧起点，`capacity()` 与保留区都将失配。
- **容量计算**：`capacity()` 的表达式在"全范围可分配"（`min_number == 0` 且 `T = uint64_t`）时回绕为 0，日志却声明"容量为 uint64_t 最大值加 1"，返回值仍是 0——调用方不能把 0 当作"容量 0"来拒绝分配（见 附 2）。另注意日志前缀写作 `Numer_Allocator::`，与类名 `Number_Pool` 不一致。
- **计数语义**：`counts()` 是净占用量，`Object_Pool::size()` 直接返回它，因此"合法性"等价于"是否被发放且未回收"。批量 `recycle(const std::vector<T>&)` 丢弃逐项 `bool`，部分失败不可见——调用方若需知道失败项，必须逐项调用单值重载。

### 6.3 哈希混合算法

- 公式：`seed ^= val + 0x9e3779b9 + (seed << 6) + (seed >> 2)`（`哈希混合.h`，`noexcept`）。这是 Boost 的 32 位 `hash_combine` 形式；在 64 位 `size_t` 平台上，黄金分割常数仍是 32 位的 `0x9e3779b9`，而不是常见的 64 位 `0x9e3779b97f4a7c15`。结果是低位混入强度弱于 64 位变体，但仍满足"位移 + 异或 + 加法"的多字段打散目的。
- 顺序敏感：混合是不可交换运算（`seed` 参与左移右移），因此 `hash_combine(seed, a); hash_combine(seed, b);` 与反过来结果不同。这被当作特性使用：`std::hash<engine::Config_Content>` 先 `route` 后 `config`（`配置加载器.h`），`std::hash<engine::Event>` 依次混 `category` / `tag` / `receiver` / `config.dump()` 哈希（`event/Event/事件.h`），`Event_Broker` 的 ACL 散列先 `category` 后 `tag`。
- 起点约定：调用方自行置 `seed = 0`。`hash_combine` 不提供"从零开始"的封装，也不返回新种子（就地修改引用）。
- 复用为"加盐"：`Config_Loader::run_salt_get()` 先以 `Random_Generator<int64_t>()()` 产一个值作 `seed`，再混入 `std::chrono::steady_clock::now()` 计数，得到进程内唯一且跨运行随机的盐（函数局部 `static const`）；`mark_make` 再以该盐为起点混入文件/对象键，产生"跨运行必然不同"的脏标记。这里同时用到了本模块的随机数与哈希混合两个设施（见 §七 的邻近链路）。
- 边界：非加密哈希，不可用于签名/校验；不得用于持久化标识（跨进程不稳定：`std::hash<std::string>` 的实现与进程有关，`Config_Loader` 的脏标记因此"跨运行自动失效"，其注释明写"使上一轮遗留脏标记自动失效"）。

### 6.4 路径可用性校验的返回策略（三层口径）

本模块刻意把路径判定拆成三种"失败表达"，调用方按场景选择，不要混用：

1. **带日志的布尔判定**：`path_check`（`文件路径可用性校验.h`）。失败必写日志（空前路径 `info("路径无效")`；其余 `info("访问路径异常\n请自行排查访问路径是否存在及是否可读取")` + `info("{}", ec)`）。适用"配置里声明的路径打不开就该被人看见"的场景（`Config_Loader::path_safety_check`、`Collision_Proxy` 的配置路径校验）。代价是路径检查较慢（两次 `std::filesystem` 调用）且会刷日志。
2. **静默布尔判定**：`path_exists`（同文件）。`exists(path, ec) && !ec`，不写日志、不判普通文件。适用"探测式、预期可能不存在"的场景（tinygltf 的 `FileExists` 回调）；也正因静默，失败原因（不存在 vs 系统错误）被合并，调用方若需要原因必须改用别的口径。
3. **布尔 + 错误码出参**：`file_size_get` / `file_read_whole`（同文件）。返回 `bool` 表成败，`std::error_code&` 表原因，函数入口统一 `clear()`；`file_read_whole` 失败时还会清空 `bytes_out`，保证"失败即空"。适用需要把原因拼进上层错误文本的场景（`gltf加载器.cpp` 把 `code.message()` 拼进 tinygltf 的 `err` 字符串）。
4. 另有**纯谓词**：`path_traversal_check`（无 IO、无日志、无错误码），只回答"是否含 `..` 节"。

共同约定与坑：

- 所有带 `std::error_code&` 的函数都不抛异常（`std::filesystem` 的错误码重载），与 §6.6 一致。
- `error_info` 是"出参"，调用方传入的既有值会被入口 `clear()` 覆盖；不要指望它保留上一次错误。
- `file_size_get` 失败时 `size_out` 被写成 0（`file_size` 的失败返回），因此"体量 0"与"读取失败"必须靠返回值区分，不能只看 `size_out`。
- `path_check` 用 `is_regular_file` ⇒ 目录必失败；`path_exists` 不判类型 ⇒ 目录必成功。二者不可互相代替。
- `path_traversal_check` 作用于**未规范化的原文**：`a/../b` 被拒，而 `path_normalize("a/../b")` 得到 `b`。若业务需要"规范化后再判越界"，必须自行先 `path_normalize`（本模块不提供该组合的一步封装）。
- `path_prefix_check` 是**节级、区分大小写**比较；Windows 上 `C:/Data` 与 `c:/data` 判为不相等。`Config_Loader` 的越界检查也采用同款逐节比较，因此该大小写缺口在全项目一致存在（见 附 6、附 11）。

### 6.5 `std::format` 特化的定制点

- 三个特化只补"标准库没给"的类型：`std::error_code`（输出 `[值] 消息`）、`std::error_condition`（同形态）、`std::filesystem::path`（UTF-8 文本）。`parse` 一律 `return ctx.begin();`，即**忽略所有格式说明符**（写 `"{:>20}"` 不会生效，也不会报错，而是按默认输出）。
- 定制点规则（写在该文件头注释里，属设计约定而非实现细节）：
  - 本文件只允许依赖预编译头与同目录纯工具头（当前仅 `路径字符串转换.h`），否则与 `log/Log/日志系统.h` 形成头文件循环。
  - `std::vector<T>` / `std::optional<T>` 需要偏特化 `std::formatter`，标准不允许，故不在此补；项目内需要输出容器的场景应自行展开或提供业务侧格式化函数。
  - 项目自定义类型的 `formatter` 特化必须放在该类型自己的头文件（反例即正例：`Config_Content` 的特化在 `配置加载器.h`，与类型定义同文件）。
- 依赖后果：`日志系统.h` 包含本文件 ⇒ 日志系统获得"可打印 path / error_code"的能力 ⇒ `文件路径可用性校验.h` 与 `文件路径获取.h` 才能直接 `logger.info("{}", ec)` / `logger.error("{}", e.what())`（后者是 `const char*`，标准库自带）。这条"日志系统是格式化能力的第一个消费者"的链路，是本模块内 `文件路径可用性校验.h → 日志系统运行包` 依赖能成立的前提。
- 潜在冲突：`formatter<std::filesystem::path>` 与部分标准库实现可能提供的同类型支持叠加时，全特化优先级最高，不会重复定义；但若未来标准库正式为 `path` 提供 `formatter`，该全特化会与库内实现冲突（`formatter` 是全特化，标准库若也用全特化则构成重定义）。当前无此风险。

### 6.6 禁用异常约定

- **本模块的对外行为**：除 `exe_path_probe` 外全部函数不抛出。IO 一律走 `std::filesystem` 的 `error_code` 重载或 `std::ifstream` 的流状态；解析走返回值；哈希/查找/规范化是纯计算。
- **唯一的抛出点**：`文件路径获取.h` 的 `exe_path_probe`（5 处 `throw std::runtime_error`）。它被 `exe_path_get` 的静态初始化 lambda 用 `catch (const std::exception&)` 就地拦截并降级为 `current_path()`，因此异常不会越过模块边界——但这依赖"只从 `exe_path_get` 调用"的约定（`exe_path_probe` 是可见的 inline 函数，直接调用者需自带捕获）。
- **内存分配**：本模块不做堆分配（两个类无指针成员，`file_read_whole` 的扩容由 `std::vector` 完成）。项目整体约定"分配失败用 `std::nothrow`"，在别处可见（`log/Stream_Tree/流节点树.h`、`event/Event_Terminal`、`spatial/partition/Quadtree` 均写 `new(std::nothrow)`），本模块无需遵守该条的具体落点。
- **第三方异常边界**：`json字段可用性校验.h` 的"其他类型"分支用 `try { config[field].get<T>(); } catch (const nlohmann::json::type_error&)`。这是本模块唯一使用 `try/catch` 的位置，理由是 nlohmann 的 `get<T>()` 以异常报类型不符，没有错误码版本；捕获范围精确到 `type_error`，不外溢。`Config_Loader` 的 JSON 解析同样在边界处捕获（`json::parse_error` 与 `std::exception`），属同一策略：**第三方库的异常只在其调用点被收敛，引擎自身不抛**。

### 6.7 路径规范化只做词法

- `path_normalize` 使用 `lexically_normal()`，因此：不解析符号链接、不折叠大小写、不解析 `~`、不做环境变量展开、不访问磁盘。它适合"比较键 / 哈希键 / 显示"三类用途，不适合"判定两个路径是否指向同一文件"（后者需 `weakly_canonical` 或 `equivalent`）。
- 消尾分隔符的手法值得注意：不是手写 `pop_back`，而是"以 `root_path` 为基、逐节 `operator/=`"，因为 `path::operator/=` 会先移除左值的尾分隔符再追加；这样 `"a/b/"` 与 `"a/b"` 归一，且根路径 `"/"` / `"C:/"` 保留自身形态。空节（由尾部 `/` 产生）被显式 `continue` 跳过。
- `path_key_normalize` 在同一语义上再叠三条：反斜杠统一为 `/`、末尾补 `/`、剥锚点与前导。注意其先后顺序——**先补尾再剥锚点**，是为了让"路径本身就是锚点"（如锚点 `data/`、路径 `data`）也能命中；若顺序反过来，末尾无 `/` 时 `rfind("data/")` 会失败。
- 锚点剥离是 `rfind` 子串定位，不保证节边界（锚点 `abc/` 可命中 `xabc/y` 中的 `abc/`）。当前唯一使用者 `Log_Rules::key_make_locked` 先在基础规范化文本上做一次 `rfind` 判定"是否在域内"，再做锚点剥离，两次都用子串语义，因此行为自洽，但在跨目录名相似（`logs` 与 `mylogs`）时可能误判域内（见 附 5）。
- 前导剥离循环同时处理 `/` 与 `./` 两种前缀，且是 `for(;;)` 循环而非单次 `if`，故 `././a` 会被完整剥净；空串与非空串均安全（每步都先判长度）。

### 6.8 二分查找的语义与前置条件

- 两个函数都**返回下标而非迭代器**（`uint64_t`，相对 `first`），因此结果与容器重分配无关，便于跨调用保存（`Object_Pool::unload` 收集 `Object_Record{ID, index}` 后统一处理）。代价是调用方必须自己 `begin() + index`。
- `binary_search` 要求随机访问迭代器（`first + (last - first) / 2`、`first < last`）；`range_binary_search` 只用 `distance` / `advance`，可处理非随机访问容器，但模板参数名同为 `RandomIt`。若对 `std::list` 调用单点版本，会在 `first < last` 处编译失败（不是运行期问题）。
- 比较器即"序"：`comp` 决定升/降序，`Object_Pool` 用 `std::variant<std::ranges::less, std::ranges::greater>` 包装的 `Comparator`；`Quadtree_Manager::tree_index_seek` 用 `std::ranges::greater()` 在**降序**序列上查找。因此不能假定"升序"，必须与序列实际顺序一致。
- 投影器默认 `std::identity`（C++20，来自 `<functional>`，由预编译头提供）；`Object_Pool` 传 `Default_Projector{...ID()}`，`Quadtree_Manager` 传 `[](auto* p){ return p->root.X; }`。`std::invoke` 使投影结果可以是成员指针以外的可调用形式。
- 失败一律 `std::nullopt`，无日志、无异常；调用方必须显式 `has_value()` 检查（两份消费者都检查了）。
- `range_binary_search` 的返回值是**闭区间** `{first_index, last_index}`（`right_index = distance(first, upper) - 1`），消费者 `Quadtree_Manager` 用 `begin <= end` 遍历，语义一致；若等值组只有 1 个元素，返回 `{i, i}`，不会出现空区间。

### 6.9 文本解析的严格性取舍

- `float_parse` 的"完整消费"要求把"尾随字符"当作错误，而不是静默接受前缀。这让它在"从一行中按空白切 token"后的解析是安全的（token 内不含空格），也让它不适合"从长串里取前导数字"（那需要另写循环）。`strtof` 会跳过前导空白与接受十六进制浮点/科学计数法，这些都不是错误。
- 拒绝 `NaN` / `inf` 是与 `finite_check` 的口径统一：解析与校验共用"有限实数"这一约定，配置中不会出现非有限值（`EngineSystem` 的 `场景清单解析.cpp`、`关卡文本.cpp` 全部走 `float_parse`，`粒子数据.cpp` 全部走 `finite_check` / `unit_interval_check`）。
- `text_trim` 只认 `" \t\r\n"`：`carriage_return_trim` 的单独存在说明"行尾回车"有独立语义（配合 `std::getline` 在 CRLF 文本上留 `\r`）。CRLF 文本的标准处理顺序是"先 `carriage_return_trim`（若用 `getline`）再 `text_trim`"或直接 `text_trim`（它已包含 `\r`）；`材质加载器.cpp` 同时使用两者。
- 三者均不处理 UTF-8 BOM、全角空格、`\v` / `\f`；若资产文件来自其他工具链，需调用方先做预处理。

### 6.10 JSON 字段校验的类型矩阵与取舍

- 三分支结构：存在性（`contains`）→ 类型（`if constexpr` 五路）→ 内容（`string` 非空、数组/对象非空）。
- 类型判定的粒度是"JSON 类别"而非"C++ 类型"：`std::is_integral_v<T>` 全部映射到 `is_number_integer()`（该谓词同时接受有符号与无符号整数），因此 `field_check<uint64_t>` 与 `field_check<int64_t>` 的判定完全相同，**不校验符号、不校验位宽、不校验范围**。需要范围时必须在取值后自行判断（`EngineSystem` 的 `collision/Common/字段读取.h` 就另加了 `>` / `<` 检查）。
- 浮点只接受 `is_number_float()`：JSON 解析器把 `1` 记为整数、`1.0` 记为浮点，故配置文件里写整数字面量给浮点字段会失败。这是"严格按字面类型"的取舍，好处是能抓到"整数误填浮点字段"，坏处是与 JSON 使用者的直觉不符。
- 字符串额外的"非空"是内容级规则，与类型无关；同理数组/对象"非空"也只对该类别生效，空字符串 vs 空数组都失败。
- `else` 分支的 `get<T>()` 是"万能类型断言"：对 `std::vector<double>`、`nlohmann::json` 这类类型，转换失败抛 `type_error`，被捕获后记为类型不匹配；成功后再做容器非空判断。对 `T = nlohmann::json` 而言 `get` 恒成功，故该分支实际是"存在 + 若为容器则非空"，这也是 `field_check<nlohmann::json>` 被用来判"动态字段有内容"的原因（`路由文件操作.cpp` 的 `config_routes`）。
- 日志级别："字段缺失"是 `warn`（多半是真错），"类型/内容不符"是 `info`（可能是可选字段或探测）。两层日志都带 `detail::` 前缀与字段名，便于定位。

### 6.11 预编译头的实际作用与缺口

- `common/前置头文件包含.h` 按功能分区（C 标准库 8 个、通用实用工具 17 个、容器 8 个、字符串与 I/O 6 个、算法与迭代器 3 个、数学与位操作 4 个、时间与随机数 2 个、多线程与并发 5 个、范围 1 个、C++20 调试 1 个），平台头一律不收（第 3 节注释明写"平台头由真正依赖其内容的头文件自行包含"，`文件路径获取.h` 因此自带 `windows.h` / `unistd.h` / `mach-o/dyld.h` 的条件包含并处理 `NOMINMAX`）。
- 它并非真实 PCH（`CMakeLists.txt` 无 `target_precompile_headers`），作用退化为"包含顺序契约 + 单点增删"。这意味着：本模块任何头文件单独被包含时都能自足（每个文件首条包含它），代价是每个翻译单元重复展开约 55 个头（编译时长换可读性）。
- 缺口：未显式提供 `<concepts>`、`<string_view>`、`<charconv>`、`<iomanip>`、`<span>`。其中 `<concepts>` 被本层其它头使用（`object/Object_Pool/对象池.h` 的 `std::same_as` 约束、`std::is_base_of_v` 来自 `<type_traits>`），现依靠 `<ranges>` / `<format>` 的传递包含获得，属隐式依赖（见 附 10）。本模块自身只用到已显式提供者（`<type_traits>`、`<functional>`、`<optional>`、`<filesystem>`、`<system_error>`、`<deque>`、`<unordered_set>`、`<chrono>`）。
- `<memory>` 行注释写作 "std::shared_ptr, std::shared_ptr, std::weak_ptr"（`shared_ptr` 重复、漏 `unique_ptr`），`<stdexcept>` 整行无注释——纯注释瑕疵，不影响编译。

### 6.12 随机数生成器的状态与种子细节

- `init` 先 `state = 0` 再 `inc = (seed << 1u) | 1u`，然后**预热一次**（丢弃第一个输出）。PCG 的标准初始化通常还会 `state += seed` 一次并再推进；本实现以 `state = 0` 起步、仅靠 `inc` 携带种子，因此**不同种子之间的状态差异只体现在 `inc` 的最低有效位附近**（`seed << 1 | 1` 保留了种子的全部位，经过第一次 `state = 0 * 6364136223846793005 + inc = inc` 后状态等于 `inc`）。可复现性成立（同 seed 同序列），但"种子空间的最小扰动"需要若干次推进才能扩散开——这是性能与实现简洁的取舍，不影响统计性质。
- 默认种子 = 纳秒计数 ^ `time(nullptr)` ^ 进程内自增计数，三维度组合的目的分别是"高分辨率差异 / 跨秒差异 / 同刻多次构造差异"。`counter` 非原子（见 附 12）。
- `seed()` 非 const：`Event_Terminal` 只调用 `key_generator()`（`operator()`），不需要读种子，因此该瑕疵未被触发。
- `operator()` 的全范围计算以"无符号位模式"统一处理有符号与无符号，避免为 `int8_t` 写特判；`operator()(min, max)` 的 `min > max` 自动纠正使调用方不必先排序（它是安全的，不改变调用语义）。
- 预编译头虽含 `<random>`，本模块未使用 `std::mt19937` / `uniform_*_distribution`；选择 PCG32 + 自写拒绝采样，是为了显式控制"跨度 0 表示 2^64 全范围"这一边界（标准库对 `[0, UINT64_MAX]` 的端点处理依赖实现）。

### 6.13 聚合头的使用纪律

- 面向消费者：`package/路径操作工具.h` 一次引入"字符串转换 + 规范化 + 可执行路径"，`package/数据校验工具.h` 一次引入"JSON 字段 + 文件路径 + 数值"，`package/文本处理工具.h` 引入"文本行"。`Config_Loader`（配置加载器.h）同时引入数据校验与路径操作两个聚合头，是本模块最大消费者。
- 面向模块内部：日志侧刻意绕开聚合头（`日志规则.h` 只包含 `文件路径规范化.h`），因为聚合头会把 `文件路径获取.h`（`windows.h`、`logger`）带入日志头依赖面，扩大重编译面并引入循环风险。新增聚合头时应沿用同一准则：**聚合头只为"需要整组"的消费者存在，内部实现取最小依赖**。

## 七、模块运行链路详例

### 7.1 链路一：配置路径的规范化 + 可用性校验

参与者：`Config_Loader`（`loader/config/Config_Loader/`）、本模块 `路径字符串转换.h` / `文件路径规范化.h` / `文件路径可用性校验.h` / `文件路径获取.h`，日志系统。

**阶段 A：配置目录在构造期被规范化（键空间的准备）**

1. 调用方构造 `Config_Content`。若使用字符串构造（`配置加载器.h` 第 32-37 行），两个入参（`route`、`config`）先 `detail::string_to_path(...)`（UTF-8 → `std::filesystem::path`），再 `detail::path_normalize(...)`（`lexically_normal` 消解 `.`/`..`、以根为基逐节重组、消尾分隔符），结果存入 `route` / `config` 两个 `std::filesystem::path` 成员。
2. 若使用 `path` 构造（第 25-30 行），只做 `path_normalize`，不做编码转换（入参已是路径对象）。
3. 这两个成员随后成为 `std::hash<Config_Content>` 的输入（第 47-56 行，两次 `detail::hash_combine`）与 `formatter<Config_Content>` 的输出（第 59-74 行，两次 `detail::path_to_string` → UTF-8 文本）。

结果：`Config_Content` 的两个路径字段在**进入任何比较/哈希/日志之前**已统一为"词法规范化 + 平台分隔符"的形态，因此 `Config_Content` 的 `operator==`（`= default`）与哈希是稳的。

**阶段 B：待检路径的越界与范围判定**

4. `Config_Loader::path_safety_check(content, config_path)`（`loader/config/Config_Loader/core/路径与文件.cpp` 第 99-143 行）接收配置里声明的**字符串**路径。
5. `detail::string_to_path(config_path)` → `path suspect_path`（UTF-8 解码在此完成；此后所有比较都在路径域，不再碰编码）。
6. `suspect_path.empty()` → `logger.error("Config_Loader::配置路径为空")`，返回 `false`。
7. `detail::path_traversal_check(suspect_path)`（`文件路径可用性校验.h` 第 142-152 行）：逐节遍历，遇 `".."` 成分即 `false`；失败时 `logger.error("Config_Loader::存在非法父目录返回符号")`，返回 `false`。
8. 逐节比对 `content.config`（标准配置目录，已在阶段 A 规范化）与 `suspect_path`：`suspect` 先耗尽 → `"配置路径超出合法范围"`、`false`；任一节不等 → 同一条错误、`false`。此步在 `路径与文件.cpp` 内联展开，语义等价于 `detail::path_prefix_check(content.config, suspect_path)`（文件第 33 行注释"路径前缀判定已下沉至 detail::path_prefix_check"）。
9. `detail::path_check(base_dir_get() / suspect_path)`（`文件路径可用性校验.h` 第 15-41 行）。其中 `base_dir_get()` 是 `detail::exe_dir_get()`（`路径与文件.cpp` 第 8-12 行）——首次调用触发 `exe_path_probe()`（平台分派获取可执行路径，失败则 `logger.error` 两条并回退 `current_path()`），此后为进程级静态缓存；`operator/` 把相对路径拼到可执行目录下（若 `suspect_path` 为绝对路径则按标准语义覆盖为自身）。
10. `path_check` 内部：路径空 → `logger.info("路径无效")`；否则 `std::filesystem::exists(p, ec)` 与 `is_regular_file(p, ec)` 全为真才通过；任一为假 → `logger.info("访问路径异常\n请自行排查访问路径是否存在及是否可读取")` + `logger.info("{}", ec)`（此处的 `{}` 依赖 `标准库format特化.h` 的 `formatter<std::error_code>` 输出 `[值] 消息`）+ `ec.clear()`，返回 `false`。
11. 全部通过 → `path_safety_check` 返回 `true`；`Config_Loader` 随后才允许以该路径打开文件（`file_read` 用 `ifstream` + `try/catch` 处理 JSON 解析异常，见 `路径与文件.cpp` 第 36-64 行）。

**副作用与要点**：

- 编码转换点仅一处（步骤 5），此后全是路径域比较；`path_check` 的 `std::string` 重载会让步骤 5 与步骤 9 各解码一次（`path_check(const std::string&)` 内部再 `string_to_path`），当前代码传的是 `path`，故只有一次解码。
- 失败一律"日志 + `false`"，无异常；上层只需判 `bool`。
- 该链路只校验"文件"，不校验目录；若未来需要"目录可访问"，不能用 `path_check`（`is_regular_file` 会拒绝目录）。
- 步骤 8 的内联逐节比较与 `path_prefix_check` 是同一语义的两份实现（`缓存清除.cpp` 已直接使用后者，见 附 6）。

### 7.2 链路二：数值分配器的分配 / 回收（以 `Object_Pool` 为宿主）

参与者：`Object_Pool`（`object/Object_Pool/对象池.h`）、本模块 `数值分配器.h`、`二分查找.h`，日志系统。

**阶段 A：构造期的分配器初始化**

1. `Object_Pool()`（第 86-95 行）：`ID_allocator.set(Allocate_Order::LIFO)`、`index_allocator.set(Allocate_Order::LIFO)`（仅切换复试顺序，`order` 成员写入）；`ID_allocator.set(min_ID)` 其中 `min_ID = 1`（`min_number = 1`，此时 `next_number` 仍为类型最小值 0，因 `min_number(1) < next_number(0)` 不成立 → `next_number = 1`）；`index_allocator.set(0)`（`min_number = 0`，`next_number` 由 0 变 0）。
2. 于是：ID 从 1 起、索引从 0 起；两个 `allocated_counts` 均为 0；`0` 被保留为"非法 ID"（`unload` 时写 `object_ID = min_ID - 1`）。

**阶段 B：`build` 分配槽位与 ID**

3. `build(std::vector<T> object_set)`（第 188-237 行）对每个待建对象：
   - `index_allocator.get()`：回收队列为空 → 走 `next_number++` 分支，返回递增索引；若此前有 `unload`，则从 `recycle_numbers` 按 LIFO 取（`back()` + `pop_back()`），并 `mapping.erase(该索引)`。
   - `object_index >= objects.size()` → `objects.push_back(std::move(对象))`（首次扩容）；否则 `std::destroy_at` + `std::construct_at` 在旧槽位原地重建（复用槽位，避免扩容）。
   - 若 `min_valid_index > 0`（存在无效区），`std::swap(objects[object_index], objects[--min_valid_index])` 把新对象换到无效区边界并收缩无效区，同时更新 `object_index`。
   - `ID_allocator.get()`：同样先复试回收编号、否则 `next_number++`；赋值给 `new_object.object_ID`；若耗尽（`next_number == UINT64_MAX`）则告警"数值分配殆尽\n已进行回绕分配"并回绕。
   - `buffer.push_back(new_object.ID())`（`buffer` 是本函数返回的 ID 列表）；`is_valid = true`；哈希模式下 `mapping.insert_or_assign(projector(new_object), object_index)`。
4. 排序模式下最后 `sort()`（`std::ranges::sort(begin(), end(), compare, projector)`），`begin()` 跳过无效区（`objects.begin() + min_valid_index`）。

**阶段 C：`unload` 回收 ID 与索引**

5. `unload(const std::vector<Key>& keys)`（第 257-319 行）先去重（`std::unordered_set<Key> removed_keys`），逐个 `find(key)`：
   - 哈希模式：`mapping.find(key)` 直接定位；排序模式：`detail::binary_search(begin(), end(), key, compare, projector)`——经投影器取键、经比较器定序，返回下标后 `begin() + index`。未命中 → `logger.warn("Object_Pool::目标对象不存在: {}", key)` 并跳过。
   - 记录 `Object_Record{it->ID(), 静态下标}`；哈希模式立即 `mapping.erase(key)`。
6. 记录按升序索引排序（`std::ranges::sort(records, std::ranges::less(), &Object_Record::index)`）——保证后续"交换到无效区"不会使尚未处理的记录索引失效。
7. 逐条卸载：`ID_allocator.recycle(record.ID)`（单值重载：`mapping.count` 判重 → 未回收过则 `recycle_numbers.push_back(ID)` + `mapping.insert(ID)` + `allocated_counts--`；重复回收会 `logger.warn("Number_Pool::待回收数值已被回收!!!")` 并返回 `false`，此返回值在此处被忽略）；该对象 `object_ID = min_ID - 1`（即 0）、`is_valid = false`；若 `record.index != min_valid_index` 则 `std::swap(object, objects[min_valid_index])`（把无效对象换到边界，合法对象换到 `record.index`），哈希模式下对换入的合法对象更新 `mapping`；随后 `index_allocator.recycle(min_valid_index)`、`min_valid_index++`。
8. 排序模式最后再次 `sort()`。

**阶段 D：`clear` 复位**

9. `clear()`（第 322-346 行）：`objects.clear()`；`ID_allocator.reset()`（`order = LIFO`、`next_number = 0`、计数 0、清空 `deque` 与 `set`，**保留 `min_number = 1`**）→ `ID_allocator.set(LIFO)` → `ID_allocator.set(min_ID)`（此时 `min_number(1) >= next_number(0)` → `next_number = 1`，恢复"ID 从 1 起"）；`index_allocator` 同法恢复 `set(0)`；`min_valid_index = 0`；哈希模式清空 `mapping`。

**链路中的关键事实与风险点**：

- 分配与回收是**两套编号独立演进**：ID 与索引各自一个 `Number_Pool`，因此"ID 稳定、槽位可变"（卸载后 ID 被回收，下次 `build` 可能立刻拿到同一个 ID；而索引由 LIFO 复用最近释放的槽位）。
- `size()` 返回 `ID_allocator.counts()`，即"已发放未回收的 ID 数"，与 `objects.size()`（槽位总数）不同；`capacity()` 是槽位总数。
- `recycle` 的返回值在 `unload` 中被丢弃：重复回收同一 ID 会打"待回收数值已被回收!!!"告警，但因 `mapping` 判重提前返回，计数不会错乱。
- 但若上层手工调用 `ID_allocator.recycle(一个从未发放的 ID)`（`Number_Pool` 是私有成员，外部无法直接访问），会入队并让计数减一——这条风险只在 `Number_Pool` 被独立使用（如未来其他宿主）时成立，`Object_Pool` 内部路径安全。
- 回绕只在"回收队列空且 `next_number == UINT64_MAX`"时发生；宿主中需长期 `build` 且从不 `unload` 才可能触达，属极端场景。
