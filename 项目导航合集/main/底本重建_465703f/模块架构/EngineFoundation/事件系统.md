## 一、文件内目录

- `Engine/EngineFoundation/src/event/Common/事件协议.h` —— 定义事件中转协议的全部字符串词汇（订阅登记、订阅者查询、配置投递、保留标签、载荷字段名），供发送侧与接收侧共用同一份常量，避免协议字符串各写一份而漂移。
- `Engine/EngineFoundation/src/event/Event/事件.h` —— 定义事件值对象 `engine::Event`（发送者、目标、分类、标签、JSON 配置包与三类构造），并提供 `std::hash<engine::Event>` 特化。
- `Engine/EngineFoundation/src/event/Event_Broker/事件中转器.h` —— 定义事件标识 `engine::Event_Identity` 及其 `std::hash` 特化，并声明事件中转器类 `engine::Event_Broker` 的三张私有登记表与四个公开成员函数。
- `Engine/EngineFoundation/src/event/Event_Broker/局部命名空间使用.h` —— 为事件中转器实现文件集中引入 `std` 类型的 `using` 声明（string、hash、unordered_map、vector、optional、nullopt、shared_ptr、nothrow、function）。
- `Engine/EngineFoundation/src/event/Event_Broker/core/事件中转器.cpp` —— 实现 `Event_Broker` 的构造函数、接入函数 `attach`、两个 `receive` 重载与事件处理函数 `process`。
- `Engine/EngineFoundation/src/event/Event_Terminal/事件终端.h` —— 定义订阅侧门面类 `engine::Event_Terminal`：权限密钥、事件构造、接入、收发、查阅与清空，并内嵌终端端口成员。
- `Engine/EngineFoundation/src/event/Event_Terminal/终端端口.h` —— 定义端口枚举 `engine::Port_ID` 与终端接口类 `engine::Terminal_Port`（回调绑定、端口注册表、注册状态查询），并前置声明 `Event_Terminal`。
- `Engine/EngineFoundation/src/event/Event_Terminal/局部命名空间使用.h` —— 为事件终端实现文件集中引入 `std` 类型的 `using` 声明（string、optional、nullopt、vector、nothrow、unique_ptr、shared_ptr、function）。
- `Engine/EngineFoundation/src/event/Event_Terminal/core/事件终端.cpp` —— 实现 `Event_Terminal` 的十一个成员函数（密钥、三个 `build`、`attach`、两个 `send`、两个 `receive`、`query`、`clear`）。
- `Engine/EngineFoundation/src/event/事件系统运行包.h` —— 订阅侧聚合头，只把 `Event` 与 `Event_Terminal` 暴露给上层，刻意不包含 `Event_Broker` 与 `事件协议.h`。

## 二、模块功能介绍

事件系统是 `EngineFoundation` 层内的同步事件总线，解决“同一层内多个模块需要互相通知，但不愿互相持有指针、互相包含头文件”的问题。它把一次通信抽象成一个值对象 `Event`：发送者写 `sender`，接收者写 `receiver`（留空表示广播），路由键是二元组 `{category, tag}`，业务数据放在 `config`（`nlohmann::json`）。模块之间只共享这个值对象与一组协议字符串，不共享类型定义，也不共享对象生命周期。

模块内部实际存在四个角色，边界清晰：

1. `Event`（`Event/事件.h`）——纯数据载体，可拷贝、可哈希、可按 `{category, tag, receiver, config}` 判等，不携带任何路由能力。
2. `Event_Broker`（`Event_Broker/事件中转器.h/.cpp`）——总线本体，持有三张私有登记表（名称到密钥、`{category,tag}` 到被授权密钥集合、密钥到投递回调），负责校验、寻址、同步分发与登记表维护。它是“持有总线的一方”才需要看见的类型。
3. `Event_Terminal`（`Event_Terminal/事件终端.h/.cpp`）——订阅侧门面。每个订阅模块持有一个终端；终端负责生成一次性权限密钥、构造事件、在密钥校验通过后收发事件、按需缓存未处理事件。终端不包含 `Event_Broker` 头文件，也不持有总线指针。
4. `Terminal_Port`（`Event_Terminal/终端端口.h`）——终端与外部世界之间的回调插槽。终端的收发与接入动作全部由使用方通过 `bind` 注入；未注入时终端退化为本地缓存队列。

协议词汇（`Common/事件协议.h`）独立成头，原因是发送侧（订阅者）与接收侧（中转站自身）必须对 `Subscriber/Check`、`Subscribed_Events/Add` 等字符串达成一致。该头只放字符串常量，不引入任何类型依赖，任何模块都可以只包含它。

模块负责的能力：

- 订阅者接入与身份登记（名称到权限密钥的映射）；
- 订阅关系登记（`{category, tag}` 到密钥集合的映射，含 `All` 标签的整类展开）；
- 单事件与多事件的同步分发；
- 定向送达（`receiver` 非空）与广播送达（`receiver` 为空）；
- 广播时排除事件发起者本人；
- 订阅清单的增（`Subscribed_Events/Add`）与减（`Subscribed_Events/Remove`）；
- 订阅者存在性查询（`Subscriber/Check`）；
- 订阅者下线注销（`Subscriber/Detach`，含密钥校验与登记表清理）；
- 订阅侧的权限密钥门禁、事件构造、事件缓存、事件查阅与清空；
- 终端端口的回调注册、注册状态查询。

模块明确不负责的能力：

- 不提供线程安全。两个 `.cpp` 与两个头文件中没有任何 `mutex`、原子量或锁；分发完全在调用方线程的栈上同步完成，回调重入即递归。
- 不做事件排队与延迟投递。`receive` 立即遍历订阅者并调用回调；唯一的“队列”是 `Event_Terminal::event_set`，且只在“收件侧未绑定任何接收入口”时作为兜底缓存，不参与定时或批量调度。
- 不做事件持久化、补发与重放。测试用例“未订阅时发布不缓存”明确表明发布早于订阅的事件不会保留。
- 不定义业务事件语义。`category`、`tag`、`config` 字段的业务含义由使用方模块自行约定（如 `Config_Loader` 与 `Log_Config_Bridge` 各自维护自己的 `config_event`、`日志事件` 词汇表）。
- 不做 JSON 载荷的模式校验。`Event_Broker::process` 只用 `detail::field_check<T>` 检查字段存在、类型与非空，不校验字段之间的组合约束。
- 不提供响应事件机制。协议里存在 `call`、`response` 两个常量，但本模块没有任何代码发送或处理它们；`Subscriber/Check` 的结果是直接写回查询事件的 `config` 字段。
- 不托管订阅者生命周期。`Event_Broker` 的 `receivers` 保存的是 `std::function` 值拷贝，回调里通常捕获订阅对象的 `this`；订阅对象必须先于中转站销毁，模块不提供弱引用或自动注销。
- 不导出总线给上层。`事件系统运行包.h` 只含 `Event` 与 `Event_Terminal`，总线类型由持有总线的一侧直接包含 `Event_Broker/事件中转器.h`。

该模块存在的核心理由可以从 `Logging_Config_Bridge/日志配置桥接.h` 的注释直接读出：让日志模块“不反向包含事件系统，否则 Logging 与 Event_Broker 之间形成头文件循环”。因此模块被刻意切成“值对象 + 协议词 + 订阅侧门面 + 总线路由器”四块，且订阅侧与总线侧互不包含：`终端端口.h` 只前置声明 `Event_Terminal`，`事件终端.h` 不包含 `事件中转器.h`；两侧唯一的结合点是使用方在 `Terminal_Port::bind(Port_ID::Broker_Attacher, ...)` 注入的回调，该回调由使用方自己捕获 `Event_Broker&`。这样订阅模块编译时不需要看见总线的私有登记表，消除头文件耦合。

由此形成三条硬约束，贯穿全部接口：

1. 事件必须有非空的 `category` 与 `tag`，且该 `{category, tag}` 必须已被某个订阅者登记过；否则 `receive` 直接丢弃（见 §六 第 4 条）。
2. `All` 是保留标签，禁止作为普通事件的 `tag` 发送（`receive` 会丢弃），但允许作为订阅标签登记，表示“该分类下所有事件”。
3. 终端的权限密钥只能生成一次；未生成密钥时，终端的 `attach`、`send`、`query`、`clear` 一律锁定并告警返回失败。

### 3.1 `engine::event_protocol`（协议常量）

位于 `Common/事件协议.h`，在 `namespace engine { namespace event_protocol { ... } }` 内，全部为 `inline constexpr const char*`，无函数、无类型。

订阅登记协议：

| 常量 | 字面值 | 语义 |
| --- | --- | --- |
| `subscribed_events` | `"Subscribed_Events"` | 订阅事件清单事件所属的 `category` |
| `add` | `"Add"` | 登记订阅清单的 `tag` |
| `remove` | `"Remove"` | 注销订阅清单的 `tag` |

订阅者查询协议：

| 常量 | 字面值 | 语义 |
| --- | --- | --- |
| `subscriber` | `"Subscriber"` | 订阅者相关事件的 `category` |
| `check` | `"Check"` | 查询订阅者是否已接入的 `tag` |
| `detach` | `"Detach"` | 订阅者下线的 `tag` |
| `call` | `"Call"` | 协议中声明的事件调用标签；本模块内无任何读写点（见待确认 10） |
| `response` | `"Response"` | 协议中声明的调用应答标签；本模块内无任何读写点（见待确认 10） |

配置投递约定：

| 常量 | 字面值 | 语义 |
| --- | --- | --- |
| `config` | `"Config"` | 配置类事件的 `category` |
| `load` | `"Load"` | 加载类动作的 `tag` |
| `unload` | `"Unload"` | 卸载类动作的 `tag` |

保留标签：

| 常量 | 字面值 | 语义 |
| --- | --- | --- |
| `all` | `"All"` | 中转站保留标签。作为发送标签时该事件被中转站直接丢弃；作为订阅标签时表示整类订阅 |

载荷字段名：

| 常量 | 字面值 | 语义 |
| --- | --- | --- |
| `field_object` | `"object"` | 载荷中的目标对象名（订阅者名称） |
| `field_acl_key` | `"acl_key"` | 载荷中的权限密钥 |
| `field_subscribed_events` | `"subscribed_events"` | 载荷中的订阅事件清单（JSON 数组） |
| `field_subscribed` | `"subscribed"` | `Check` 查询写回的存在性布尔值 |
| `field_category` | `"category"` | 订阅清单条目中的事件分类 |
| `field_tag` | `"tag"` | 订阅清单条目中的事件标签 |

语义与前置条件：常量本身无运行期行为。`field_*` 与 `subscribed_events`、`subscriber`、`config` 被 `Event_Broker::process` 与使用方（`Config_Loader`、`Log_Config_Bridge`）直接用作 JSON 键或事件 `category/tag`，因此改动字面值等于改动总线协议。`事件系统运行包.h` 不包含本头，使用方需自行包含 `Common/事件协议.h`（快照内 `Config_Loader/局部命名空间使用.h`、`Logging_Config_Bridge/局部命名空间使用.h` 都是这样做的）。

### 3.2 `engine::Event`（事件值对象）

```cpp
struct Event
{
    Event();
    Event(const std::string& category, const std::string& tag);
    Event(const std::string& sender, const std::string& receiver,
        const std::string& category, const std::string& tag);
    Event(const std::string& sender, const std::string& receiver,
        const std::string& category, const std::string& tag,
        const nlohmann::json& config);
    ~Event();

    std::string sender{};
    std::string receiver{};
    std::string category;
    std::string tag;
    nlohmann::json config;

    bool operator==(const Event& other) const;
};
```

逐条语义：

- `Event()`：默认构造。`sender`、`receiver` 由成员初始化器置为空串；`category`、`tag` 默认构造为空串；`config` 默认构造为 JSON null（不是空对象）。
- `Event(const std::string& category, const std::string& tag)`：只填路由键，`sender`/`receiver` 为空串，`config` 为 null。前置条件无；传空串不会报错，但空 `category`/`tag` 的事件在 `receive` 阶段被丢弃。
- `Event(const std::string& sender, const std::string& receiver, const std::string& category, const std::string& tag)`：填发起者、目标与路由键，`config` 为 null。
- `Event(const std::string& sender, const std::string& receiver, const std::string& category, const std::string& tag, const nlohmann::json& config)`：全量构造，`config` 按值拷贝。
- `~Event()`：空实现，非虚析构。`Event` 可被继承，但通过基类指针删除派生对象是未定义行为（模块内未出现继承用法）。
- 成员：`sender` 是发起者名称，参与广播时的“排除发起者”判定；`receiver` 是目标名称，非空即走定向路径；`category` 与 `tag` 构成路由标识 `Event_Identity`；`config` 是业务载荷。
- `bool operator==(const Event& other) const`：仅比较 `category`、`tag`、`receiver`、`config` 四项，**不比较 `sender`**。返回布尔值，不抛异常；`nlohmann::json` 的比较不会抛出，除非比较含非法类型（正常 JSON 值不会）。
- 隐含成员：未声明拷贝/移动构造与赋值，四者均由编译器生成；`Event` 的拷贝是深拷贝 JSON。

失败/告警行为：构造函数不做任何校验、不记日志、不抛异常。空 `category`/`tag` 的后果延迟到 `Event_Broker::receive` 才体现（warn 并丢弃）。

### 3.3 `std::hash<engine::Event>`（特化）

```cpp
namespace std
{
    template<>
    struct hash<engine::Event>
    {
        size_t operator()(const engine::Event& evt) const noexcept;
    };
}
```

语义：`seed = hash<string>(evt.category)`；依次用 `engine::detail::hash_combine(seed, ...)` 混入 `tag`、`receiver` 的字符串哈希；把 `evt.config.dump()` 转成字符串后再混入。返回 `size_t`。

- 前置条件：无。`config` 为 null 时 `dump()` 返回 `"null"`。
- 与 `operator==` 的一致性：`operator==` 忽略 `sender`，本哈希同样忽略 `sender`，满足“相等对象哈希相同”。
- 失败行为：函数标记 `noexcept`，但 `nlohmann::json::dump()` 在载荷含二进制类型（`binary`）且未指定 `allow_exceptions=false` 时会抛 `type_error`；`noexcept` 下抛出会直接 `std::terminate`（见待确认 7）。

### 3.4 `engine::Event_Identity`（事件标识）与 `std::hash<engine::Event_Identity>`

```cpp
struct Event_Identity
{
    std::string category{};
    std::string tag{};

    Event_Identity();
    Event_Identity(const std::string& category, const std::string& tag);

    bool operator==(const Event_Identity& other) const;
};
```

```cpp
namespace std
{
    template<>
    struct hash<engine::Event_Identity>
    {
        size_t operator()(const engine::Event_Identity& acl) const noexcept;
    };
}
```

- `Event_Identity()`：两字段均为空串。
- `Event_Identity(const std::string& category, const std::string& tag)`：按值写入两字段，不做非空校验。
- `operator==`：比较 `category` 与 `tag` 两项，返回布尔值，不抛异常。
- 哈希：`seed = 0`，先混入 `hash<string>{}(category)`，再混入 `hash<string>{}(tag)`，返回 `size_t`，`noexcept` 且不会抛。
- 用途：`Event_Broker::acl_set` 的键类型。声明顺序上，该特化位于 `Event_Identity` 之后、`Event_Broker` 之前，头文件注释明确“必须先于 `Event_Broker` 内 `unordered_map<Event_Identity,...>` 的实例化”。

### 3.5 `engine::Event_Broker`（事件中转器）

```cpp
class Event_Broker
{
    std::unordered_map<Event_Identity, std::vector<uint64_t>> acl_set;
    std::unordered_map<std::string, uint64_t> mapping{};
    std::unordered_map<uint64_t, std::function<void(std::shared_ptr<Event> evt)>> receivers;

public:
    Event_Broker(void);
    ~Event_Broker(void) = default;
    Event_Broker(const Event_Broker&) = default;
    Event_Broker& operator=(const Event_Broker&) = default;
    Event_Broker(Event_Broker&&) = default;
    Event_Broker& operator=(Event_Broker&&) = default;

    void attach(const std::string& subscriber, const uint64_t& acl_key,
        std::function<void(std::shared_ptr<Event>)> receiver);
    void receive(std::shared_ptr<Event> evt);
    void receive(std::vector<std::shared_ptr<Event>> event_set);
    void process(std::shared_ptr<Event> evt);
};
```

逐条语义与失败行为：

- `Event_Broker(void)`：构造即完成自接入：以 `hash("Event_Broker")` 生成自身密钥、构造捕获 `this` 的 `process` 回调、`attach("Event_Broker", ...)`、把四个维护标识写入 `acl_set`。步骤见 §四 4.1.1；由此产生的“固定自身订阅者”后果见 §六 第 2、11、13 条。
- `attach(const std::string& subscriber, const uint64_t& acl_key, std::function<void(std::shared_ptr<Event>)> receiver)`：只登记“名称→密钥”与“密钥→回调”两份映射（`insert_or_assign`），不注册任何订阅标识。前置条件：名称非空且回调可调用，否则 warn `"Event_Broker::订阅者为空或未包含有效事件接收器"` 后返回。返回值 `void`，调用方无法得知成功与否；重接残留见待确认 9。
- `receive(std::shared_ptr<Event> evt)`：单事件投递。按顺序做四道判定（空指针、`category`/`tag` 非空、标识已登记、`tag` 不为 `All`），再分定向/广播两路同步送达。每道失败均为 warn + 返回，不抛异常。详见 §七 链路一。
- `receive(std::vector<std::shared_ptr<Event>> event_set)`：多事件投递，按值接收容器，内部逐元素转调单事件重载。单个事件失败只影响自身，不中断批次。空容器为合法输入，立即返回。
- `process(std::shared_ptr<Event> evt)`：登记表维护入口，按 `category`/`tag` 执行四类登记操作：`Subscriber/Check`（写回 `subscribed` 布尔）、`Subscriber/Detach`（校验密钥后删除名称映射、接收入口与所有订阅授权）、`Subscribed_Events/Add`（校验密钥后逐条登记订阅标识）、`Subscribed_Events/Remove`（校验密钥后逐条移除订阅授权）。前置条件：`evt` 非空且 `config` 含非空字符串字段 `object`；否则 warn 返回。该函数为 `public`，调用方可绕过 `receive` 的“标识已登记”“发起者排除”等门禁直接调用（快照内 `Application/Game/星屑弹幕/source/communication/事件总线.cpp` 即以 `broker.process(subscribe)` 直接登记订阅，见 §六 第 12 条）。
- 特殊成员：析构、拷贝构造、拷贝赋值、移动构造、移动赋值全部 `= default`。拷贝是逐表深拷贝 `std::function` 值，构造函数中注入的“自身回调对象”也被原样拷贝，副本的 `receivers[hash("Event_Broker")]` 仍指向原对象的 `process`（见待确认 4）。
- 可见性：三张登记表均为私有，无任何 getter；外部无法查询某标识的订阅者列表，也无法查询某名称的密钥。

### 3.6 `engine::Port_ID`（端口枚举）

```cpp
enum class Port_ID
{
    None,
    Broker_Attacher,
    Evt_Sender,
    Evts_Sender,
    Evt_Receiver,
    Evts_Receiver
};
```

语义：

| 枚举值 | 对应回调签名 | 用途 |
| --- | --- | --- |
| `None` | 无 | 占位值，任何 `bind`/`check` 传入都会因 ID 不匹配而失败或无意义 |
| `Broker_Attacher` | `void(const std::string&, const uint64_t&, std::function<void(std::shared_ptr<Event>)>)` | 终端 `attach` 时调用的“接入动作”，由使用方包装成 `Event_Broker::attach` |
| `Evt_Sender` | `void(std::shared_ptr<Event>)` | 单事件发送通道，由使用方包装成 `Event_Broker::receive` |
| `Evts_Sender` | `void(std::vector<std::shared_ptr<Event>>)` | 多事件发送通道 |
| `Evt_Receiver` | `void(std::shared_ptr<Event>)` | 单事件接收入口，指向订阅者业务回调 |
| `Evts_Receiver` | `void(std::vector<std::shared_ptr<Event>>)` | 多事件接收入口 |

失败行为：枚举本身无运行期行为；ID 与回调类型不匹配时的处理见 3.7。

### 3.7 `engine::Terminal_Port`（终端端口）

```cpp
class Terminal_Port
{
private:
    using Event_Handler   = std::function<void(std::shared_ptr<Event>)>;
    using Events_Handler  = std::function<void(std::vector<std::shared_ptr<Event>>)>;
    using Broker_Attacher = std::function<void(const std::string& name, const uint64_t& acl_key,
        Event_Handler receiver)>;

    std::vector<Port_ID> binding_table{};
    std::unique_ptr<Broker_Attacher> broker_attacher;
    std::unique_ptr<Event_Handler> evt_sender;
    std::unique_ptr<Events_Handler> evts_sender;
    std::unique_ptr<Event_Handler> evt_receiver;
    std::unique_ptr<Events_Handler> evts_receiver;

    template <typename Ret, typename... Args>
    bool memory_malloc(std::unique_ptr<std::function<Ret(Args...)>>& target) const;

    template <typename Ret, typename... Args>
    bool function_register(Port_ID ID,
        std::unique_ptr<std::function<Ret(Args...)>>& target,
        std::function<Ret(Args...)> function);

public:
    friend class Event_Terminal;

    template <typename T>
    Terminal_Port& bind(const Port_ID& ID, T callback);

    bool check(const Port_ID& ID) const;
    std::vector<Port_ID> state(void) const;
};
```

`bind` 是模板，编译期按 `T` 的可调用形态分派，返回 `*this` 以支持链式调用：

- 若 `T` 可被调用为 `(const std::string&, const uint64_t&, Event_Handler)`：先要求返回类型为 `void`；再要求 `ID == Port_ID::Broker_Attacher`，否则 `logger.error("Event_Terminal::ID匹配失败\n已驳回中转站接入端口绑定请求")` 并返回；匹配则 `function_register(Port_ID::Broker_Attacher, broker_attacher, Broker_Attacher(callback))`。
- 否则若 `T` 可被调用为 `(std::shared_ptr<Event>)`：`ID == Evt_Sender` 绑定单事件发送端口，`ID == Evt_Receiver` 绑定单事件接收端口，其他 ID 记 `logger.error("Event_Terminal::ID匹配失败\n已驳回单事件发送/接收端口绑定请求")`。
- 否则若 `T` 可被调用为 `(std::vector<std::shared_ptr<Event>>)`：`ID == Evts_Sender` 绑多事件发送端口，`ID == Evts_Receiver` 绑多事件接收端口，其他 ID 记 `logger.error("Event_Terminal::ID匹配失败\n已驳回多事件发送/接收端口绑定请求")`。
- 否则编译期 `static_assert(!sizeof(T), "Terminal_Port::bind: 不支持的callback类型")`。
- 前置条件：`callback` 可拷贝；端口对象已构造。注册成功的前提是 `memory_malloc` 成功（`new(std::nothrow)`）。
- 失败行为：内存分配失败时 `function_register` 返回 `false`，但 `bind` 丢弃该返回值，仍返回 `*this`，且 `binding_table` 不记录该端口，后续 `check` 返回 `false`。此外“三参数但返回非 `void`”的回调会落入第一分支后因内层 `if constexpr` 不成立而**静默不注册**，既不打日志也不报错（见待确认 13）。

`check(const Port_ID& ID) const`：线性扫描 `binding_table`，命中返回 `true`，否则 `false`；不抛异常。由于 `binding_table` 按注册次数 `push_back`，同一端口重复绑定会在表中出现多次，`check` 仍只回布尔。

`state(void) const`：把 `binding_table` 逐项拷贝到新 `vector` 并返回；空表返回空 `vector`。返回值是快照，调用方修改它不影响端口内部状态；不抛异常。

### 3.8 `engine::Event_Terminal`（事件终端）

```cpp
class Event_Terminal
{
    std::optional<int64_t> acl_key;
    Random_Generator<int64_t> key_generator{};
    std::vector<std::shared_ptr<Event>> event_set{};

public:
    Event_Terminal() = default;
    ~Event_Terminal() = default;
    Event_Terminal(Event_Terminal&&) = default;
    Event_Terminal& operator=(Event_Terminal&&) = default;

    Terminal_Port* operator->(void);

    std::optional<int64_t> key(void);

    std::shared_ptr<Event> build(void) const;
    std::shared_ptr<Event> build(const std::string& category, const std::string& tag) const;
    std::shared_ptr<Event> build(const std::string& sender, const std::string& receiver,
        const std::string& category, const std::string& tag) const;

    bool attach(const std::string& subscriber, const int64_t& acl_key);

    bool send(std::shared_ptr<Event> evt, const int64_t& acl_key) const;
    bool send(std::vector<std::shared_ptr<Event>> events, const int64_t& acl_key) const;

    void receive(std::vector<std::shared_ptr<Event>> events);

    const std::vector<std::shared_ptr<Event>>* query(const int64_t& acl_key) const;
    bool clear(const int64_t& acl_key);

```

逐条语义与失败行为：

- `Event_Terminal() = default`：不生成密钥，端口全未绑定；`~Event_Terminal() = default` 不向总线注销（见 §六 第 17 条）。
- 移动构造/移动赋值 `= default`：搬运密钥、生成器、缓存与端口；拷贝被隐式删除；移动后总线回调悬垂（见待确认 5）。
- `Terminal_Port* operator->(void)`：返回内部 `terminal_port` 地址，供 `terminal->bind(...)`/`check(...)`；非 const，不转移所有权。
- `std::optional<int64_t> key(void)`：首次生成并返回密钥，之后一律返回 `std::nullopt`（见 §六 第 18 条与待确认 16）。
- 三个 `build`：均以 `new(std::nothrow)` 分配，失败返回空 `shared_ptr`；分别构造空事件、`(category, tag)`、`(sender, receiver, category, tag)`。无“带 config”重载，载荷由调用方写 `evt->config`。
- `bool attach(const std::string& subscriber, const int64_t& acl_key)`：前置条件为密钥已生成且匹配、`Broker_Attacher` 已绑定，任一不满足即 warn/error 返回 `false`；满足后未绑 `Evt_Receiver` 则包装捕获 `this`、转调 `receive` 的 lambda，已绑则传入该回调副本，再调用 `(*broker_attacher)(subscriber, acl_key, 接收入口)` 并返回 `true`。不登记任何订阅标识，接入失败不可回传（见 §六 第 8 条、§七 7.2）。
- `bool send(std::shared_ptr<Event> evt, const int64_t& acl_key) const`：密钥门禁通过后校验非空，优先 `Evt_Sender`，未绑定则降级 `Evts_Sender` 并 warn 两条，两槽皆无 error 返回 `false`。
- `bool send(std::vector<std::shared_ptr<Event>> events, const int64_t& acl_key) const`：与单事件版同构，优先 `Evts_Sender`，未绑定则逐条走 `Evt_Sender`；按值接收容器，不校验元素。
- `void receive(std::shared_ptr<Event> evt)`：优先 `Evt_Receiver`，否则降级 `Evts_Receiver`，两者皆无则 `event_set.push_back(evt)`；不校验密钥、不判空。
- `void receive(std::vector<std::shared_ptr<Event>> events)`：优先 `Evts_Receiver`，否则逐条走 `Evt_Receiver`，两者皆无则整批 `insert` 到 `event_set`。
- `const std::vector<std::shared_ptr<Event>>* query(const int64_t& acl_key) const`：密钥已生成且匹配则返回 `&event_set`，否则 `nullptr`（不匹配时无日志）。返回内部裸指针，内容随 `receive`/`clear` 变化（见待确认 18）。
- `bool clear(const int64_t& acl_key)`：密钥已生成且匹配则清空并返回 `true`；未生成 warn，不匹配静默 `false`。
- 可见性：`acl_key`、`key_generator`、`event_set`、`terminal_port` 全部私有；端口只能经 `operator->` 访问。

### 3.9 `事件系统运行包.h`（聚合头）

该文件只含 `#pragma once`、包含 `common/前置头文件包含.h`、包含 `Event/事件.h` 与 `Event_Terminal/事件终端.h` 四行预处理指令，不声明任何类型或函数。作用是让订阅侧模块一条包含即可拿到 `Event`、`Event_Terminal`、`Port_ID`、`Terminal_Port`（后两者经 `事件终端.h` → `终端端口.h` 传递）。

## 四、模块私有方法

本模块的两个实现文件 `Event_Broker/core/事件中转器.cpp` 与 `Event_Terminal/core/事件终端.cpp` 中**没有匿名命名空间，也没有文件级静态函数**；全部实现都是类的成员函数。下面按文件与调用链分组列出签名与职责。

### 4.1 `Event_Broker` 实现（`Event_Broker/core/事件中转器.cpp`）

该文件结构为：包含 `../局部命名空间使用.h`（间接带入 `事件中转器.h` 与 `../Common/事件协议.h`，并引入 std 类型的 `using`），再包含 `"src/log/日志系统运行包.h"`（层根相对路径，符合本层 `.cpp` 包含约定），主体在 `namespace engine` 内，共五个有函数体的成员（构造函数、`attach`、两个 `receive`、`process`）；六个特殊成员函数在头文件中 `= default`，`.cpp` 无实现。

#### 4.1.1 `Event_Broker::Event_Broker(void)`

职责：构造即完成“总线把自己也登记为订阅者”的初始化，使 `Subscriber/*` 与 `Subscribed_Events/*` 四类维护事件能通过 `receive` 的“标识已登记”门禁并回到自己的 `process`。

实现步骤（对应源码顺序）：

1. `uint64_t acl_key = static_cast<uint64_t>(std::hash<std::string>{}("Event_Broker"));` —— 以字面名 `"Event_Broker"` 的字符串哈希作为自身密钥。该值是编译期确定的常量（同进程内恒定），不是随机密钥。
2. 构造 `auto evt_process = [this](std::shared_ptr<Event> evt) { this->process(evt); };` —— 捕获当前对象指针。该 lambda 被存入 `receivers`，因此 `Event_Broker` 的地址在构造后不可再变（移动/拷贝会带来语义偏差，见待确认 4、5）。
3. `attach("Event_Broker", acl_key, evt_process)` —— 写入 `mapping["Event_Broker"] = acl_key` 与 `receivers[acl_key] = evt_process`。
4. 构造 `vector<Event_Identity> reserved_identities` 四个元素：`{subscriber, check}`、`{subscriber, detach}`、`{subscribed_events, add}`、`{subscribed_events, remove}`。
5. `for (const auto& identity : reserved_identities) acl_set[identity].push_back(acl_key);` —— 逐条登记自身订阅授权。注释明确：不登记则这些事件会在 `receive` 阶段被直接丢弃。

前置条件：无。失败行为：无（`std::hash` 与容器插入不会因业务原因失败；内存不足时抛 `std::bad_alloc`，与模块其余部分的 `nothrow` 风格不一致）。

#### 4.1.2 `void Event_Broker::attach(const std::string& subscriber, const uint64_t& acl_key, std::function<void(std::shared_ptr<Event>)> receiver)`

职责：把“名称、密钥、投递回调”三件套写入两张表。

实现步骤：

1. 若 `subscriber.empty() || !receiver`：`logger.warn("Event_Broker::订阅者为空或未包含有效事件接收器")`、`logger.info("接入失败")`，返回。
2. `mapping.insert_or_assign(subscriber, acl_key)` —— 同名再次接入会覆盖旧密钥。
3. `receivers.insert_or_assign(acl_key, receiver)` —— 同密钥再次接入会覆盖旧回调。

隐含行为：不校验 `acl_key` 是否已被别的名称使用；不清理旧密钥对应的 `receivers` 条目与 `acl_set` 中残留的旧密钥（同名换钥时会留下“幽灵授权”，见待确认 9）。无返回值。

#### 4.1.3 `void Event_Broker::receive(std::shared_ptr<Event> evt)` —— 单事件重载

职责：校验事件并在当前线程同步分发。完整步骤：

1. 空指针 → warn 返回；取 `auto& sender = evt->sender;` 与 `auto& receiver = evt->receiver;` 引用别名。
2. `category`/`tag` 为空 → warn 返回。
3. `!acl_set.count({category, tag})` → warn 返回。该判定要求精确标识至少被登记过一次，不认“只登记了 `{category, All}`”（见 §六 第 4 条）。
4. `tag == event_protocol::all` → warn 返回。`All` 只能作为订阅标签。
5. 进入定向分支 `if (!receiver.empty())`：
   - 若 `mapping.count(receiver)`：`uint64_t target_key = mapping[receiver];`，然后 `receivers[target_key](evt)`。
   - 无论目标是否存在，随后 `return`（目标不存在时静默丢弃，不回落为广播，也不记日志）。
   - 该分支不检查目标是否订阅了该标识，不排除 `sender == receiver` 的自发自收。
6. 广播分支：
   - `std::optional<uint64_t> sender_key = nullopt;` 后 `mapping.find(sender)`；找到则记录，找不到保持空。注释称为“事件发起者权限密钥记录”。
   - `vector<uint64_t> acl_keys = acl_set[{ evt->category, evt->tag }];` —— 拷贝精确标识的授权列表（`operator[]`，键一定存在，因为第 3 步已保证）。
   - `acl_keys.insert(acl_keys.end(), acl_set[{evt->category, event_protocol::all}].begin(), acl_set[{evt->category, event_protocol::all}].end());` —— 追加该分类下 `All` 授权列表。这里对 `acl_set` 使用 `operator[]`，即使分类从未登记过 `All` 也会插入一个空 `vector` 条目（见待确认 6）。
   - `for (int send_time = 0; send_time < acl_keys.size(); send_time++)`：若 `!sender_key.has_value() || acl_keys[send_time] != sender_key`，则 `receivers[acl_keys[send_time]](evt)`。即发起者未登记时不排除任何人；发起者已登记时跳过与其密钥相同的表项。
   - 循环用 `int` 与 `size()`（`size_t`）比较，存在有符号/无符号比较隐患；循环变量在函数内声明。

关键副作用：`receivers[...]` 使用 `operator[]`，若授权列表中残留一个已不存在的密钥，会默认构造空 `std::function` 并调用，抛 `std::bad_function_call`（见待确认 6）。

#### 4.1.4 `void Event_Broker::receive(std::vector<std::shared_ptr<Event>> event_set)` —— 多事件重载

职责：批处理入口，按值接收容器后 `for (int process_time = 0; process_time < event_set.size(); process_time++) receive(event_set[process_time]);`。逐个复用单事件全部门禁；单条失败只 warn 并返回该次调用，不中断批次。无额外校验、无返回值、无异常处理。

#### 4.1.5 `void Event_Broker::process(std::shared_ptr<Event> evt)`

职责：维护登记表（不投递）。公共前置校验与四个分支如下。

公共部分：空指针 warn 返回；取 `auto& config = evt->config;`；`field_check<string>(config, field_object)` 失败则 warn `"目标对象字段无效"` 返回。四类分支统一要求载荷带非空字符串 `object`。

`Subscriber/Check`：取 `string obejct = config[field_object]`（源码拼写 `obejct`），查 `mapping.find`；不存在写 `config[field_subscribed] = false`，存在写 `true`。结果原地写回查询事件的 `config`，不发应答、无日志。

`Subscriber/Detach`：取 `object` 与未初始化的 `uint64_t suscriber_key`；`mapping.find` 落空则两条 warn（`目标订阅者不存在`、`无法卸载其订阅记录`）返回；`field_check<uint64_t>(field_acl_key)` 失败则 warn 返回。密钥相等时 `mapping.erase(object)`、`receivers.erase(key)`、遍历 `acl_set` 每个列表删除第一个匹配密钥（`break`），记 `"事件中转站接入已下线"`；不相等则两条 error（`权限密钥不匹配`、`已驳回该违规操作`）。不清 `event_set`、不失效终端 `acl_key`、不删空条目。

`Subscribed_Events/Add`：先查 `mapping[object]` 与 `acl_key`（失败 warn/返回，密钥不等则两条 error 后落到函数末尾）；校验 `field_subscribed_events` 存在且为数组，否则 warn 返回；逐条要求 `category`/`tag` 为非空字符串，否则 warn 并 `continue`；对 `acl_set[identity]` 线性查重后 `push_back(key)`（幂等）；记 `"事件中转站订阅事件已登记"`。

`Subscribed_Events/Remove`：同样的 mapping/密钥/清单校验；`acl_set.find(identity)` 未找到则 warn `"订阅事件标识未登记"` 并 `continue`；找到则线性删除第一个匹配密钥（`break`）；记 `"事件中转站订阅事件已注销"`，空列表条目保留。

其他 `category`/`tag`：静默结束、无日志。`process` 不检查 `tag == all`、也不检查 `category`/`tag` 是否为空，完全信任调用方已做过 `receive` 门禁；因此直接调用可绕过全部投递门禁。

### 4.2 `Terminal_Port` 私有模板（`Event_Terminal/终端端口.h`）

#### 4.2.1 `template <typename Ret, typename... Args> bool Terminal_Port::memory_malloc(std::unique_ptr<std::function<Ret(Args...)>>& target) const`

职责：为端口回调分配函数包装器内存。实现为 `target.reset(new(std::nothrow) std::function<Ret(Args...)>);` 后返回 `static_cast<bool>(target)`。前置条件：`target` 为有效 `unique_ptr` 引用。失败行为：分配失败返回 `false`，`target` 保持空，不记日志、不抛异常。`const` 修饰，因为只改 `target` 指向对象（`unique_ptr` 本身是外部对象，`reset` 不修改 `this` 成员，但 `target` 是引用参数）。

#### 4.2.2 `template <typename Ret, typename... Args> bool Terminal_Port::function_register(Port_ID ID, std::unique_ptr<std::function<Ret(Args...)>>& target, std::function<Ret(Args...)> function)`

职责：分配并写入回调，同时记录端口已绑定。实现：

1. `if (memory_malloc(target))`：`*(target) = function;` 赋值；`binding_table.push_back(ID);` 记录；返回 `true`。
2. 否则返回 `false`。

前置条件：`function` 可拷贝；`ID` 与目标端口语义一致（该前置条件由调用方 `bind` 保证）。失败行为：仅内存分配失败时返回 `false`；重复注册同一 `ID` 会重复 `push_back` 表项（表中出现重复 `Port_ID`），回调本体由 `*(target) = function` 覆盖，旧函数对象由赋值运算符销毁，不泄漏。

#### 4.2.3 私有类型别名

`Event_Handler = std::function<void(std::shared_ptr<Event>)>`、`Events_Handler = std::function<void(std::vector<std::shared_ptr<Event>>)>`、`Broker_Attacher = std::function<void(const std::string& name, const uint64_t& acl_key, Event_Handler receiver)>`。`bind` 的类型分派与 `function_register` 的实参构造都依赖它们。`Event_Terminal` 是 `Terminal_Port` 的友元，因此可以直接读取 `broker_attacher`、`evt_sender`、`evts_sender`、`evt_receiver`、`evts_receiver` 五个私有成员并解引用调用。

### 4.3 `Event_Terminal` 实现（`Event_Terminal/core/事件终端.cpp`）

文件包含 `../局部命名空间使用.h` 与 `"src/log/日志系统运行包.h"`，在 `namespace engine` 内实现十一个函数。

#### 4.3.1 `std::optional<int64_t> Event_Terminal::key(void)`

- `if (!acl_key.has_value()) return acl_key = key_generator();` —— 首次调用生成并返回。
- `else return nullopt;` —— 已生成时返回空 `optional`。
- 副作用：首次调用把随机密钥写入成员；`Random_Generator<int64_t>` 的默认构造以时间、`time(nullptr)` 与静态计数器混合做种子（该实现属“随机数生成器”模块，本模块只作背景）。

#### 4.3.2 三个 `build` 重载

均 `const`，均以 `new(std::nothrow)` 构造并交给 `shared_ptr<Event>`：

- `build(void)` → `shared_ptr<Event>(new(nothrow) Event())`
- `build(const string& category, const string& tag)` → `Event(category, tag)`
- `build(const string& sender, const string& receiver, const string& category, const string& tag)` → `Event(sender, receiver, category, tag)`

不判空、不记日志；失败时返回空 `shared_ptr`，由调用方检查（快照内 `Config_Loader` 与 `Log_Config_Bridge` 都会检查 `== nullptr`）。

#### 4.3.3 `bool Event_Terminal::attach(const std::string& subscriber, const int64_t& acl_key)`

步骤：

1. 密钥未生成 → warn `"Event_Terminal::密钥未生成\n功能已锁定"`，`return false`。
2. `this->acl_key != acl_key` → warn `"Event_Terminal::密钥匹配失败"`，`return false`。
3. 取 `auto& Tinterface = terminal_port;`；`if (!Tinterface.check(Port_ID::Broker_Attacher))` → error `"Event_Terminal::事件中转站接入端口未绑定"` + `"Event_Terminal::接入失败"`，`return false`。
4. `if (!Tinterface.check(Port_ID::Evt_Receiver))`：构造 `auto it = [this](shared_ptr<Event> evt) -> void { this->receive(evt); };`，调用 `(*Tinterface.broker_attacher)(subscriber, this->acl_key.value(), it);`。
5. `else`：调用 `(*Tinterface.broker_attacher)(subscriber, this->acl_key.value(), *Tinterface.evt_receiver);` —— 传入已绑定接收回调的**副本**。
6. `return true`。

关键语义：接入成功与否不反映总线侧结果；`int64_t` 到 `Broker_Attacher` 形参 `uint64_t` 的隐式转换发生在这里。

#### 4.3.4 `bool Event_Terminal::send(shared_ptr<Event> evt, const int64_t& acl_key) const`

密钥门禁（未生成 warn、不匹配 error）通过后：空事件 warn 返回 `false`；优先 `(*evt_sender)(evt)` 返回 `true`；未绑定时降级 `(*evts_sender)({ evt })` 并 warn 两条返回 `true`；两槽皆无则 error `"未注册有效入口"` 返回 `false`。日志文本与前置条件见 §三 3.8。

#### 4.3.5 `bool Event_Terminal::send(vector<shared_ptr<Event>> events, const int64_t& acl_key) const`

与单事件版同构，优先 `Evts_Sender`，未绑定则逐条 `(*evt_sender)(evt)` 并 warn 两条；不校验元素是否为空；密钥门禁相同。

#### 4.3.6 `void Event_Terminal::receive(shared_ptr<Event> evt)`

`check(Evt_Receiver)` → `(*evt_receiver)(evt)`；否则 `check(Evts_Receiver)` → `(*evts_receiver)({ evt })` + warn 两条；两者皆无 → `event_set.push_back(evt)`。不校验密钥、不判空。

#### 4.3.7 `void Event_Terminal::receive(vector<shared_ptr<Event>> events)`

`check(Evts_Receiver)` → `(*evts_receiver)(events)`；否则 `check(Evt_Receiver)` → 逐条转发 + warn 两条；两者皆无 → `event_set.insert(event_set.end(), ...)`。

#### 4.3.8 `const std::vector<std::shared_ptr<Event>>* Event_Terminal::query(const int64_t& acl_key) const`

未生成密钥 → warn 返回 `nullptr`；密钥相等 → 返回 `&event_set`；不等 → `nullptr`（无日志）。

#### 4.3.9 `bool Event_Terminal::clear(const int64_t& acl_key)`

未生成密钥 → warn 返回 `false`；密钥相等 → `event_set.clear()` 返回 `true`；不等 → `false`（无日志）。

### 4.4 模块外部的私有支撑（不属于本模块，仅说明调用依据）

- `engine::detail::field_check<T>(const nlohmann::json& config, const std::string& field)`（定义在 `Engine/EngineFoundation/src/detail/methods/json字段可用性校验.h`）：先查字段存在性（缺失时 `logger.warn`），再按 `T` 派生检查：`bool` 要求 `is_boolean`；整型要求 `is_number_integer`；浮点要求 `is_number_float`；`std::string` 要求 `is_string` 且非空；其他类型尝试 `get<T>()` 并捕获 `type_error`，再对空数组/空对象返回失败。`Event_Broker::process` 的全部字段校验都经由它，因此“字段类型正确但语义非法”（如负密钥、超范围整数）不会被拦截。
- `engine::detail::hash_combine(size_t& seed, size_t val) noexcept`（定义在 `Engine/EngineFoundation/src/detail/methods/哈希混合.h`）：`seed ^= val + 0x9e3779b9 + (seed << 6) + (seed >> 2)`，供 `Event` 与 `Event_Identity` 的哈希特化使用。本模块头文件不直接包含该头，`事件中转器.h` 依赖 `事件.h` 的传递包含（见待确认 17）。

### 5.3 数据所有权

| 数据 | 所有者 | 类型 | 生命周期 |
| --- | --- | --- | --- |
| 名称到密钥映射 | `Event_Broker::mapping` | `unordered_map<std::string, uint64_t>` | 与 Broker 实例同寿；`attach` 写入、`Detach` 删除 |
| 标识到授权密钥集合 | `Event_Broker::acl_set` | `unordered_map<Event_Identity, std::vector<uint64_t>>` | 与 Broker 实例同寿；构造写保留项、`Add` 增加、`Remove`/`Detach` 删除 |
| 密钥到投递回调 | `Event_Broker::receivers` | `unordered_map<uint64_t, std::function<void(std::shared_ptr<Event>)>>` | 与 Broker 实例同寿；`attach` 写入、`Detach` 删除 |
| 权限密钥 | `Event_Terminal::acl_key` | `std::optional<int64_t>` | 与终端实例同寿；首次 `key()` 后不再变化 |
| 密钥生成器 | `Event_Terminal::key_generator` | `Random_Generator<int64_t>` | 与终端实例同寿 |
| 未处理事件缓存 | `Event_Terminal::event_set` | `std::vector<std::shared_ptr<Event>>` | 与终端实例同寿；`receive` 入缓存、`clear` 清空 |
| 端口回调与注册表 | `Event_Terminal::terminal_port` | `Terminal_Port`（内含 `unique_ptr<function>` 与 `vector<Port_ID>`） | 与终端实例同寿；`bind` 写入 |
| 事件对象 | 投递方与所有接收方共享 | `std::shared_ptr<Event>` | 由 `shared_ptr` 引用计数决定；`receive` 全程按值拷贝 `shared_ptr`，不复制事件内容 |

回调所有权是本模块最需要注意的非显式契约：`Event_Broker::receivers` 存的是 `std::function` 值。若使用方把订阅对象的成员函数或捕获 `this` 的 lambda 传进去，总线就间接持有一个指向订阅对象的裸指针，但没有生命周期感知。`Event_Terminal` 自己的接收入口也是捕获 `this` 的 lambda（未绑定 `Evt_Receiver` 时由 `attach` 临时构造），因此终端的地址必须稳定，且终端必须活得比“它在总线中的登记”更久。

### 5.4 端口接线模型

`Terminal_Port` 是终端与总线之间的唯一接缝。典型接法（快照内 `Application/Game/星屑弹幕/source/communication/事件总线.cpp` 的 `Event_Node` 构造函数）：

1. `bind(Port_ID::Broker_Attacher, ...)`：lambda 捕获 `Event_Broker&`，在终端 `attach` 时把 `(name, key, receiver)` 转交 `broker.attach`。
2. `bind(Port_ID::Evt_Sender, ...)`：lambda 捕获 `Event_Broker&`，把事件交给 `broker.receive`。
3. `bind(Port_ID::Evt_Receiver, handler)`：订阅者业务回调。
4. 可选：`bind(Port_ID::Evts_Sender / Evts_Receiver)` 绑定批量通道。

绑定关系不进入终端内部状态机，只是回调表；`Event_Terminal::attach` 只读取 `Broker_Attacher` 与 `Evt_Receiver` 两个槽。未绑定发送槽时 `send` 返回 `false`（除非另一槽可降级）；未绑定接收槽时 `receive` 落到 `event_set`。

### 5.5 运行期对象关系

```
持有总线的一方（例如测试夹具 / 应用装配层 / 使用方自己的单例）
   └── Event_Broker broker
          ├── mapping["Event_Broker"] ──► 固定密钥 hash("Event_Broker")
          ├── receivers[该密钥] ──► lambda{ broker.process }（捕获 broker 的 this）
          └── acl_set 四条保留标识 ──► [该密钥]

每个订阅模块
   └── Event_Terminal terminal
          ├── acl_key（首次 key() 生成）
          ├── terminal_port
          │      ├── broker_attacher ──► lambda{ broker.attach }（捕获 broker 的引用）
          │      ├── evt_sender      ──► lambda{ broker.receive }
          │      └── evt_receiver    ──► 业务回调（捕获订阅对象的 this）
          └── event_set（仅在未绑定接收入口时使用）

总线登记表中的一条授权
   acl_set[{category, tag}] += terminal.acl_key   ← 由 Subscribed_Events/Add 写入
   receivers[terminal.acl_key] = 终端的接收入口      ← 由 terminal.attach 写入
```

配置加载器与日志配置桥接是快照内两个已接入的订阅方：两者都在构造函数里 `acl_key = event_terminal.key().value()`，在 `attach()` 中先 `bind(Port_ID::Evt_Receiver, ...)` 再 `event_terminal.attach(名称, acl_key)`，最后用 `build("", "", Subscribed_Events, Add)` 构造订阅事件、填入 `object`/`acl_key`/`subscribed_events` 三字段并 `send`。

### 5.6 线程归属与重入

- 全部函数都是同步的，没有后台线程、没有锁、没有原子量。`receive` 在调用 `send` 的那个线程上完成全部分发；回调里再 `send` 就是递归，栈深度由业务决定。
- 分发期间容器可能被回调修改：`receive` 的广播分支在进入循环前把授权列表**拷贝**为局部 `vector`，因此本次分发不受“回调内新增订阅”的影响；但若回调内 `Detach` 了某个尚未轮到的订阅者，`receivers` 中该密钥被 `erase`，后续 `receivers[该密钥]` 会默认构造空函数并调用，抛 `std::bad_function_call`。
- `Event_Terminal` 的 `event_set` 无同步；`query` 返回内部指针，若在另一线程读写即为数据竞争。
- `Event_Broker` 的默认拷贝/移动会把捕获 `this` 的自身回调一并搬运/复制，破坏“回调指向本对象”的隐含关系（见 §六 第 11 条）。

### 5.7 状态表形态示例

以订阅者甲接入并订阅 `{输入, 按键}` 与 `{输入, All}` 为例：`mapping` 含 `"Event_Broker"` 与 `"甲"`；`receivers` 含总线自身回调与 `K_甲` 的接收入口；`acl_set` 含四条保留标识（各 `[hash("Event_Broker")]`）与 `{输入, 按键}`、`{输入, All}`（各 `[K_甲]`）。此后 `{输入, 按键}` 的广播会合并精确列表与 `All` 列表投递给 `K_甲`；`{输入, 松开}` 若从未被任何人登记，连 `receive` 第 3 步都过不去，`All` 订阅也收不到（见 §六 第 4 条）。

## 六、模块设计 / 实现细节

以下每条都能落到具体文件与函数，编号在全文其他段落被引用。

1. **登记是两段式的，`attach` 与“订阅清单”分离。** `Event_Terminal::attach` 只调用 `Broker_Attacher` 登记“名称 + 密钥 + 接收入口”（`Event_Broker::attach`）；订阅关系必须另发一条 `{Subscribed_Events, Add}` 事件，由 `Event_Broker::process` 写 `acl_set`。这么设计让 `attach` 的回调签名保持三参数、让订阅清单可用任意 JSON 载荷表达；代价是“接入了但忘了发 Add”时终端完全收不到事件且没有任何告警——`receive` 只会因“标识未登记”丢弃，而发送方无从判断。快照内 `Config_Loader::attach`、`Log_Config_Bridge::attach` 都显式补发了 Add，测试夹具 `attach_and_subscribe` 也把这一步封装起来。

2. **总线在构造时把自己登记成订阅者，这是四类维护事件能“走通”的前提。** 见 `Event_Broker::Event_Broker(void)`。`Subscriber/Check`、`Subscriber/Detach`、`Subscribed_Events/Add`、`Subscribed_Events/Remove` 四个标识预先写入 `acl_set`，密钥为 `hash("Event_Broker")`，投递回调为捕获 `this` 的 `process` lambda。因此普通订阅者发这些维护事件时，`receive` 的“标识已登记”门禁能通过，事件再经广播路径回到总线自己的 `process`。若有人删掉这四条保留项，所有订阅登记都会在 `receive` 第 3 步被丢弃。

3. **`receive` 的门禁顺序是有意的，且先于一切寻址。** 顺序为：空指针 → `category`/`tag` 非空 → 精确标识已登记 → 禁止发送 `All` → 定向/广播。这意味着：一个“目标存在但该标识从未被任何人登记”的定向事件也会被丢弃（测试 `定向投递需标识已登记` 验证了这一点）；一个 `category` 合法、`tag` 为空的事件同样被丢弃；`All` 检查放在定向分支之前，所以即便定向发送也不允许 `tag == All`。

4. **`All` 的实际语义是“放大已登记标识”，不是“整类兜底”。** `receive` 第 3 步要求精确标识 `{category, tag}` 已经存在，之后才把 `{category, All}` 的授权列表并入。因此一个只登记了 `{输入, All}` 的订阅者，收不到 `{输入, 松开}`——除非另有别人登记过 `{输入, 松开}`。测试 `All标签登记订阅全分类` 能通过，是因为同一用例里另有“精确订阅者”先登记了 `{输入, 按键}`。若要实现“整类兜底”，第 3 步必须放宽为“精确标识存在 **或** `{category, All}` 存在”，当前实现没有这样做（见待确认 2）。

5. **定向投递只查“目标是否接入”，不查“目标是否订阅”，也不排除发起者。** `receive` 的定向分支仅执行 `mapping.count(receiver)` 与 `receivers[target_key](evt)`；目标接入过任意标识即可收到任意标识的定向事件（只要该标识已登记）；`sender == receiver` 时事件照发。目标未接入则静默丢弃且 `return`，不回落广播。测试 `定向目标未登记不广播` 与注释“2026-10-19 引擎层行为变更：查找失败即丢弃”记录了该决策。

6. **广播的“发起者排除”按密钥相等判断，不是按名称。** `receive` 先用 `mapping.find(sender)` 取 `sender_key`，再在授权列表中跳过与之相等的密钥。后果：发起者名称未登记时谁都不排除（测试 `未登记发起者不排除订阅者`）；若两个不同名称被 `attach` 登记成同一密钥（`attach` 不禁止），两者都会被排除；若发起者名称对应的密钥已被覆盖，排除依据是新密钥。

7. **读路径存在容器 `operator[]` 的写副作用。** `receive` 广播分支取 `acl_set[{category, All}]` 用的是 `operator[]`，即使该分类从未登记过 `All` 也会插入一个空 `vector` 条目并永久保留；`receivers[acl_keys[i]]` 同样用 `operator[]`，若授权列表残留一个已无回调的密钥，会默认构造空 `std::function` 并调用，抛 `std::bad_function_call`。`process` 的 `Add` 分支对 `acl_set[identity]` 也用 `operator[]`（此处是预期写入）。这些都是“用 `operator[]` 代替 `find/at`”带来的隐式扩容与异常风险（见待确认 6）。

8. **`Detach` 的清理不完整。** `Event_Broker::process` 的 `Subscriber/Detach` 分支只做三件事：`mapping.erase(object)`、`receivers.erase(key)`、遍历全部 `acl_set` 列表删除该密钥的**第一个**匹配项。它不删除已清空的 `acl_set` 条目，不清理终端 `event_set` 缓存，不失效终端的 `acl_key`，也不校验该订阅者是否仍有未处理事件。因此 `Detach` 之后：同名可再次 `attach`（密钥仍是旧值，必须用同一密钥才通过终端门禁）；`acl_set` 中会残留大量空列表；若某标识列表因历史原因重复登记了同一密钥，只删一处。

9. **`Add` 幂等、`Remove` 静默。** `Add` 在 `acl_set[identity]` 中线性查重后才 `push_back`，重复 `Add` 不产生重复投递（测试 `重复注册不产生重复投递`）；`Remove` 找不到标识只 warn `"订阅事件标识未登记"` 并 `continue`，找到则只删第一个匹配。两者都要求载荷含非空 `object`、整数 `acl_key` 与数组 `subscribed_events`，且密钥必须与 `mapping[object]` 相等；任一失败只写日志、不抛异常。`Remove` 与 `Detach` 的区别是：`Remove` 只撤销订阅授权，保留名称映射与接收入口，终端仍可接收定向事件；`Detach` 连身份一起撤销。

10. **`Subscriber/Check` 的返回值是“原地改共享事件”，没有应答事件。** `process` 在查询分支把 `config["subscribed"] = true/false` 写回**调用方传进来的那个 `Event` 对象**。由于 `send` 是把同一个 `shared_ptr` 交给总线（不是拷贝事件），调用方在 `send` 返回后读取自己手里的 `evt->config["subscribed"]` 即可拿到结果。这条链路依赖三点：`send` 同步执行、事件对象按引用共享、调用方保留 `shared_ptr`。协议里的 `call`/`response` 完全未使用，若将来改成异步或事件拷贝，查询语义会立刻失效（见待确认 10）。

11. **`Event_Broker` 的默认特殊成员函数与“自捕获回调”冲突。** 构造函数把捕获 `this` 的 lambda 存进 `receivers`，而 `~Event_Broker() = default`、拷贝/移动全部 `= default`。拷贝出来的 Broker 的 `receivers[hash("Event_Broker")]` 仍指向**原对象**的 `process`：副本收到的维护事件会改原对象的登记表。移动同理（移动后原对象的回调仍指向旧地址）。若要安全复制，必须自定义拷贝/移动并在新对象里重建自身登记。

12. **`process` 是公开的，可绕过 `receive` 的全部门禁。** 直接调用 `broker.process(evt)` 不检查标识是否登记、不检查 `sender` 排除、不检查 `tag == All`；只检查 `config["object"]` 非空。快照内 `Application/Game/星屑弹幕/source/communication/事件总线.cpp` 的 `Event_Node` 正是用 `broker.process(subscribe)` 直接登记订阅，以避免订阅维护事件被广播给其他订阅者。这把“登记表维护”变成了任何持有 `Event_Broker&` 的代码都可调用的公共操作。

13. **权限密钥不构成安全边界。** 三处事实：`attach` 接受调用方任意给定的 `acl_key`，不验证其来源；测试夹具直接以 `std::hash<std::string>{}(subscriber)` 派生密钥；总线自身密钥是公开常量 `hash("Event_Broker")`。因此任何能拿到 `Event_Broker&` 的代码，只要知道目标名称，就能算出/覆盖其密钥并发送 `Detach`、`Remove`。密钥的实际作用是“防止误用与意外串线”，不是防对抗。

14. **密钥在终端侧是 `int64_t`、在总线侧是 `uint64_t`。** `Event_Terminal::key` 返回 `optional<int64_t>`，`Event_Broker::mapping`/`acl_set`/`receivers` 全部用 `uint64_t`。`attach` 的隐式转换与使用方写载荷时的 `static_cast<uint64_t>` 是两处转换点。若终端密钥为负，转换为大无符号数后仍能自洽；但若有人手工把负整数写进 `config["acl_key"]` 并经 `field_check<uint64_t>`（`is_number_integer` 对负数同样返回真），比较时会按无符号语义失败，表现为“密钥不匹配”而非格式错误。

15. **`std::hash<engine::Event>` 的 `noexcept` 与其 `dump()` 实现不完全匹配。** 哈希对 `config` 调用 `dump()`，对含二进制值（`nlohmann::json::binary`）的 JSON 会抛 `type_error`；标记 `noexcept` 后抛出即 `std::terminate`。另外 `operator==` 与哈希都忽略 `sender`，这是自洽的；但把 `Event` 作为无序容器键时，修改 `config` 会破坏哈希。当前模块未把 `Event` 直接用作容器键（容器键是 `Event_Identity`），该特化主要供外部使用。

16. **终端的接收入口在 `attach` 时被“快照”。** `Event_Terminal::attach` 若发现 `Evt_Receiver` 已绑定，会把该端口的 `std::function` **拷贝**给总线；之后再用 `bind` 替换接收入口，总线里的旧副本不会更新。这正是 `Application/Game/星屑弹幕/source/communication/事件总线.h` 注释里“event_receiver 必须在 attach 之前注册，否则中转站保存的是入队包装，之后注册的实时回调不会自动更新”的来源。若未绑定接收入口就 `attach`，总线拿到的是捕获 `this`、转调 `receive` 的包装 lambda；此后再绑定 `Evt_Receiver`，分发会先进入 `Event_Terminal::receive` 再转到新回调，多一层转发但语义正确。

17. **终端可移动、不可拷贝、销毁不注销。** 用户声明了移动构造/赋值，拷贝被隐式删除；`~Event_Terminal() = default` 不会向总线发 `Detach`，也不会清除 `receivers` 中指向自己的回调。移动终端后，总线里保存的捕获 `this` 的回调仍指向旧地址，调用即悬垂。使用方必须保证：终端地址稳定、终端寿命长于总线登记、销毁前显式 `Detach`（模块未提供自动机制）。

18. **密钥只能生成一次，`key()` 第二次返回 `nullopt`。** 这不是“重新生成”，而是“已生成”的信号。快照内 `Config_Loader` 与 `Log_Config_Bridge` 都在构造函数里写 `acl_key = event_terminal.key().value()` 且只调用一次，因此安全；任何“先探测再取值”的写法（连续两次 `key().value()`）都会抛 `std::bad_optional_access`（见待确认 16）。

19. **原生缓存是兜底，不是队列。** `Event_Terminal::receive` 只有在两个接收入口都未绑定时才 `event_set.push_back`；`receive(vector)` 同理整批 `insert`。缓存没有容量上限、没有背压、没有淘汰；`query` 返回内部指针，`clear` 才能清空。由于 `receive` 不校验密钥，任何持有终端引用的代码都能往缓存里塞事件；读取却要密钥。

20. **`Terminal_Port::bind` 的编译期分派有两处静默失败。** 其一：三参数回调但返回非 `void`——外层 `if constexpr (is_invocable_v<...>)` 成立，内层 `is_same_v<..., void>` 不成立，函数什么都不做，也不进入后续 `else if`，最终 `bind` 返回 `*this` 且无日志。其二：`memory_malloc` 失败时 `function_register` 返回 `false`，`bind` 丢弃返回值，端口未登记但调用方以为成功。`binding_table` 可记录重复 `ID`；`static_assert` 覆盖不可调用类型。

21. **性能取舍偏“实现简单”，不是“高频总线”。** 具体成本点：每次广播都拷贝一份授权 `vector` 并在尾部追加 `All` 列表；`Add` 的查重与 `Remove`/`Detach` 的删除都是线性扫描；`attach` 与每次投递都按值拷贝 `std::function`/`shared_ptr`；`Event` 哈希对 `config` 做 `dump()`（O(载荷大小)）；`acl_set`/`mapping`/`receivers` 均为 `unordered_map`，但 `Event_Identity` 的哈希要算两次字符串哈希。高频场景下成本会叠加。

22. **同步分发带来重入语义，模块不做保护。** `receive` 在调用方栈上直接遍历并调用回调；回调内再 `send` 就是递归，没有队列、没有深度限制、没有“分发中”标志。更危险的是分发中 `Detach` 其他订阅者：外层已持有授权列表快照，后续 `receivers[key]` 会因 `erase` 而默认构造空函数（见第 7 条）。使用方若需要在回调中改订阅关系，应把操作推迟到分发结束之后。

23. **包含卫生有两处依赖传递。** `事件中转器.h` 的哈希特化调用 `hash_combine`，但未直接包含 `哈希混合.h`，依赖 `Event/事件.h` 的传递包含（见待确认 17）；`终端端口.h` 因 `bind` 内写 `logger.error` 而包含 `log/日志系统运行包.h`，使所有包含终端端口的编译单元都拉入日志系统。

24. **运行包与协议的边界是刻意的，但协议常量有两个“死词”。** `事件系统运行包.h` 只导出 `Event` + `Event_Terminal`，订阅模块看不到 `Event_Broker`。`Common/事件协议.h` 里 `call` 与 `response` 在本模块无任何读写点；`config`/`load`/`unload` 由使用方（`Config_Loader`、`Log_Config_Bridge` 的 `config_event`/`日志事件`）复用，不由总线消费。

25. **日志策略不统一：关键失败有 `warn`/`error`，部分路径完全静默。** 静默路径包括：`receive` 定向目标不存在、`process` 中 category/tag 不匹配任何分支、`query` 密钥不匹配、`clear` 密钥不匹配、`Event_Broker::attach` 无返回值导致终端 `attach` 的 `true` 不代表成功。排障时不能只看 `send`/`attach` 的布尔返回值，必须结合“标识是否已登记”“接收端口是否在 attach 前绑定”“Add 是否发出”三件事。

## 七、模块运行链路详例

### 7.1 链路一：广播事件从投递到被终端消费

场景：订阅者甲、乙各持一个 `Event_Terminal`，均已接入同一个 `Event_Broker` 并各自登记了 `{输入, 按键}`；甲构造一条 `sender = "甲"`、`receiver = ""` 的事件并发起广播，乙绑定了 `Evt_Receiver = on_event`。

调用链与副作用：

1. 甲的业务代码调用 `Event_Terminal::build("甲", "", "输入", "按键")`（`Event_Terminal/core/事件终端.cpp`），得到 `shared_ptr<Event>`；`new(std::nothrow)` 失败时返回空指针，链路在此终止（使用方需自行判空）。
2. 甲调用 `Event_Terminal::send(evt, acl_key)`（同文件）。
   - 内部先判断 `acl_key.has_value()`；未生成则 warn `"密钥未生成\n功能已锁定"` 并返回 `false`。
   - 再判断 `this->acl_key == acl_key`；不等则 error `"密钥不匹配"` 返回 `false`。
   - 判断 `evt` 非空；为空则 warn `"事件为空\n已取消该事件发送"` 返回 `false`。
   - `terminal_port.check(Port_ID::Evt_Sender)` 为真 → 调用 `(*terminal_port.evt_sender)(evt)`；该函数对象通常由使用方在装配时 `bind(Port_ID::Evt_Sender, lambda{ broker.receive(evt); })` 注入。
   - 若只绑定了 `Evts_Sender`，则降级 `(*evts_sender)({evt})` 并 warn 两条；两者皆无则 error `"未注册有效入口"` 返回 `false`。
3. 进入 `Event_Broker::receive(std::shared_ptr<Event>)`（`Event_Broker/core/事件中转器.cpp`）。
   - `!evt` → warn 并返回（甲侧已判空，正常不会走到）。
   - `category`/`tag` 为空 → warn `"事件标识信息不完整"` 返回。
   - `acl_set.count({输入, 按键})` 为 0 → warn `"事件订阅者不存在"` 返回。甲的本次投递到此结束。
   - `tag == "All"` → warn `"All标签已占用"` 返回。
   - `receiver` 为空 → 进入广播分支。
4. 广播寻址：`mapping.find("甲")` 命中（甲已 `attach`），得到 `sender_key = K_甲`；`acl_keys = acl_set[{输入, 按键}]`（拷贝，含 `K_甲`、`K_乙`）；再追加 `acl_set[{输入, All}]`（若无人登记 `All`，此处 `operator[]` 在表中插入空条目）。
5. 逐项投递：`K_甲` 与 `sender_key` 相等，被跳过（甲不会收到自己发的事件）；`K_乙` 不等，执行 `receivers[K_乙](evt)`。
6. `receivers[K_乙]` 是乙终端在 `attach` 时交给总线的接收入口。
   - 若乙在 `attach` **之前**已 `bind(Port_ID::Evt_Receiver, on_event)`：入口是该回调的副本，总线直接调用 `on_event(evt)`，乙的业务逻辑执行；`Event_Terminal::receive` 不在这条路径上，`event_set` 也不会被使用。
   - 若乙未绑定接收入口就 `attach`：入口是 `attach` 内部构造的 `[this](evt){ this->receive(evt); }`，总线调用它 → `Event_Terminal::receive(evt)` → 此时若仍无接收入口则 `event_set.push_back(evt)`；若之后补绑了 `Evt_Receiver`，则转入 `(*evt_receiver)(evt)` 并执行乙的业务回调。
7. 返回链路：`on_event` 返回后，`receivers[K_乙]` 返回、循环继续（若还有下一个订阅者，如 `K_乙2`，依次同步调用）、`receive` 返回、`evt_sender` 返回、`send` 返回 `true`、甲的业务代码继续。
8. 副作用汇总：事件对象在所有订阅者之间共享同一个 `shared_ptr`，回调对 `evt->config` 的修改对后续订阅者与发起者可见；没有任何拷贝、没有任何排队；任一订阅者抛异常会沿调用栈直接传给甲的 `send` 调用点（模块不做 `try/catch`）。

| 终止点 | 判定 | 日志 | 结果 |
| --- | --- | --- | --- |
| `send` | 密钥未生成 | warn `密钥未生成\n功能已锁定` | `false`，事件未进总线 |
| `send` | 密钥不匹配 | error `密钥不匹配` | `false` |
| `send` | 事件为空 | warn `事件为空\n已取消该事件发送` | `false` |
| `send` | 无发送端口 | error `未注册有效入口` | `false` |
| `receive` | 事件为空 | warn `事件为空\n已略过该事件处理` | 静默丢弃 |
| `receive` | 标识不完整 | warn `事件标识信息不完整\n已略过该事件处理` | 静默丢弃 |
| `receive` | 标识未登记 | warn `事件订阅者不存在\n已略过该事件处理` | 静默丢弃 |
| `receive` | 发送 `All` | warn `All标签已占用\n已略过该事件处理` | 静默丢弃 |
| `receive` 定向 | 目标未接入 | 无 | 静默丢弃，不回落广播 |

### 7.2 链路二：订阅登记与退订的完整生命周期

场景：`Config_Loader` 持有一个 `Event_Terminal` 成员，外部装配层持有一个 `Event_Broker`；模块要把自己接入总线并登记 `{Config, Load}` 等订阅，最后在关闭阶段下线。

阶段 A：端口接线（使用方装配层，发生在业务 `attach` 之前）

1. `Config_Loader::attach()`（`Engine/EngineFoundation/src/loader/config/Config_Loader/core/事件处理.cpp`）先执行 `event_terminal->bind(Port_ID::Evt_Receiver, [this](shared_ptr<Event> evt){ this->event_process(evt); })`。
   - `Terminal_Port::bind`（`Event_Terminal/终端端口.h`）按回调类型进入“单事件”分支，`ID == Evt_Receiver` 匹配 → `function_register(Evt_Receiver, evt_receiver, Event_Handler(callback))` → `memory_malloc` 成功则写入函数对象并把 `Evt_Receiver` 追加进 `binding_table`。
2. 使用方还需在终端上 `bind(Port_ID::Broker_Attacher, lambda(name, key, receiver){ broker.attach(name, key, receiver); })` 与 `bind(Port_ID::Evt_Sender, lambda(evt){ broker.receive(evt); })`。快照内引擎层的 `Config_Loader` 没有自己建总线，因此这两个槽由外部装配层（或测试）注入；`Application/Game/星屑弹幕` 的 `Event_Node` 则把三步一起做（见 7.4）。
3. `Config_Loader` 构造函数执行 `acl_key = event_terminal.key().value()`：首次 `key()` 用 `Random_Generator<int64_t>` 生成密钥并写入成员，返回 `optional` 有值，`value()` 安全。

阶段 B：接入登记

4. `event_terminal->check(Port_ID::Evt_Receiver)`（`事件处理.cpp` 显式校验）返回真；否则 error `"事件接收入口注册失败，接入中止"` 并 `return`。
5. `event_terminal.attach("Config_Loader", acl_key)`（`Event_Terminal/core/事件终端.cpp`）：
   - 密钥已生成且匹配；
   - `check(Port_ID::Broker_Attacher)` 为真；
   - `check(Port_ID::Evt_Receiver)` 为真 → 取 `*terminal_port.evt_receiver`（**副本**）作为接收入口；
   - 调用 `(*broker_attacher)("Config_Loader", static_cast<uint64_t>(acl_key), 副本)`。
6. 进入 `Event_Broker::attach`：`mapping.insert_or_assign("Config_Loader", K)`、`receivers.insert_or_assign(K, 副本)`。总线尚不知道 `Config_Loader` 订阅了什么；此时若有人给 `Config_Loader` 发定向事件，`receive` 会因标识未登记而丢弃（定向分支在第 3 步之前已返回）。
7. 回填 `Event_Terminal::attach` 返回 `true`；`Config_Loader::attach` 继续。

阶段 C：订阅清单登记

8. `Config_Loader` 用 `reserved_events_get()` 生成 `json::array` 清单，逐条写 `{category: ..., tag: ...}`。
9. `event_terminal.build("", "", Subscribed_Events, Add)`（三参数 `build`）构造维护事件；为空则 error `"订阅事件构造失败"` 返回。
10. 写入三个载荷字段：`config["object"] = "Config_Loader"`、`config["acl_key"] = static_cast<uint64_t>(acl_key)`、`config["subscribed_events"] = 清单`。
11. `event_terminal.send(attach_evt, acl_key)` → `evt_sender` → `Event_Broker::receive`：
    - 标识 `{Subscribed_Events, Add}` 已由总线构造函数登记 → 通过第 3 步门禁；
    - `tag != All`；
    - `receiver` 为空 → 广播分支；
    - `sender` 为空串，`mapping.find("")` 不命中 → `sender_key` 为空 → 不排除任何人；
    - 授权列表为 `[hash("Event_Broker")]`（只有总线自己） → 调用 `receivers[hash("Event_Broker")](evt)`，即构造时存入的 `process` lambda。
12. `Event_Broker::process(evt)`：
    - 校验 `config["object"]` 非空；
    - `category == Subscribed_Events` → 取 `mapping["Config_Loader"]` 得 `K`；校验 `acl_key` 整数且等于 `K`；
    - `tag == Add` → 校验 `subscribed_events` 为数组；逐条校验 `category`/`tag` 非空字符串；对每条 `acl_set[{category, tag}]` 线性查重后 `push_back(K)`；
    - 记 `"事件中转站订阅事件已登记"`。
13. 此后任何标识命中清单的广播事件都会把 `K` 加入授权列表并投递给 `Config_Loader` 的 `Evt_Receiver`（链路一）。

阶段 D：撤销部分订阅或整体下线

14. 撤销部分订阅：构造 `{Subscribed_Events, Remove}` 事件，载荷同样带 `object`/`acl_key`/`subscribed_events`，经 `send` → `receive` → 总线 `process`：
    - 密钥校验失败 → error 两条并结束；
    - 每条标识在 `acl_set` 中找不到 → warn `"订阅事件标识未登记"` 并跳过该条；
    - 找到则删除第一个等于 `K` 的表项。`mapping`、`receivers` 保留，`Config_Loader` 仍可被定向投递，只是不再收到该标识的广播。
15. 整体下线：构造 `{Subscriber, Detach}` 事件，载荷带 `object = "Config_Loader"` 与 `acl_key = K`，经 `send` → `receive` → `process`：
    - `mapping.find("Config_Loader")` 命中；
    - 密钥校验通过 → `mapping.erase`、`receivers.erase(K)`、遍历全部 `acl_set` 删除 `K`；记 `"事件中转站接入已下线"`；
    - 之后该标识的广播授权列表不再含 `K`，即使终端仍存活也不会再被调用；终端自身的 `event_set` 与 `acl_key` 不受影响。
16. 若使用方跳过第 15 步直接销毁终端：总线 `receivers` 仍保存捕获终端 `this` 的回调，下一次匹配事件会调用悬垂指针。模块不提供析构自动注销。

关键顺序约束（同样适用于 `Log_Config_Bridge`）：`bind(Broker_Attacher)`、`bind(Evt_Sender)`、`bind(Evt_Receiver)` 必须在 `attach` 之前完成；`key()` 必须在 `attach`/`send` 之前调用；`Subscribed_Events/Add` 必须在 `attach` 之后发（否则 `process` 找不到 `mapping[object]`，warn `"目标订阅者不存在"` 并返回）。

### 7.3 链路三：定向投递与订阅者存在性查询

场景一：甲向乙定向发送 `{输入, 按键}`，乙已接入但未订阅该标识。

1. `build("甲", "乙", "输入", "按键")` 构造事件；
2. `send(evt, acl_key)` → `broker.receive`；
3. `receive` 的四道门禁：非空、标识完整、`{输入, 按键}` 已被某人登记（可能是丙，也可能就是乙）、`tag != All`；
4. 进入定向分支：`mapping.count("乙")` 为真 → `receivers[K_乙](evt)`；
5. 乙的接收入口执行，业务回调收到该事件；**不看**乙是否订阅 `{输入, 按键}`，也**不**排除 `sender == receiver`。
6. 若 `mapping.count("乙")` 为假：直接 `return`，无日志、无广播兜底。

场景二：查询某名称是否已接入。

1. 调用方 `build("", "", "Subscriber", "Check")`；
2. 写入 `config["object"] = "待查名称"`；
3. `send(evt, acl_key)` → `receive`：标识 `{Subscriber, Check}` 由总线构造函数保留 → 通过门禁；`sender` 为空 → 不排除；授权列表为 `[hash("Event_Broker")]` → 调用总线 `process`；
4. `process` 查 `mapping.find("待查名称")`，把 `config["subscribed"]` 写为 `true` 或 `false`；
5. `send` 同步返回后，调用方读取同一个 `evt->config["subscribed"]` 得到结果；
6. 副作用：若还有别的订阅者订阅了 `{Subscriber, Check}`，它们会收到同一条事件（查询结果字段对它们同样可见）；`sender` 若已登记，则发起者自己被排除，但事件对象仍在调用方手里，不影响读取。

### 7.4 链路四：消费方装配样例（快照内游戏侧 `Event_Node`）

`Application/Game/星屑弹幕/source/communication/事件总线.cpp` 的 `Event_Node` 构造函数演示了真实装配顺序：`bind(Broker_Attacher, λ{ broker.attach })` → `bind(Evt_Sender, λ{ broker.receive })` → `bind(Evt_Receiver, handler)` → `key()` 取密钥 → `terminal.attach(module_name, acl_key)` → `build("Subscribed_Events", "Add")` 填入 `object`/`acl_key`/`subscribed_events` 后 `broker.process(subscribe)`。第 6 步直接调 `process` 而非 `send`，是对 §六 第 12 条的利用：避免维护事件被广播。该工程内嵌 `external/silver_era` 的**旧版头副本**（路径为 `src/core/event`），只能作为同 API 消费方样例，不能作为当前包含路径依据（见待确认 14）。

**待确认 1：`README.md` 对事件系统的路径与类型名已过时。**
`README.md` 第 79 行把事件系统写成 `Engine/EngineFoundation/src/core/event/`，并列出类型“事件终端 `Event_Terminal`、终端接口 `Terminal_Interface`、事件中转器 `Event_Broker`”。快照实际路径是 `Engine/EngineFoundation/src/event/`，终端接口实际类型名是 `Terminal_Port`（`Event_Terminal/终端端口.h`），不存在 `Terminal_Interface`。`README.md` 的描述与源码不一致，以实现为准。

**待确认 2：`All` 的“整类订阅”语义与精确标识门禁冲突。**
`事件协议.h` 把 `all` 注释为“中转站保留标签（该标签下的事件会被中转站直接丢弃）”，测试用例名 `All标签登记订阅全分类` 又把 `All` 描述为“订阅全分类”。但 `Event_Broker::receive` 在合并 `All` 列表之前先执行 `if (!acl_set.count({ evt->category, evt->tag })) return;`，导致只登记 `{category, All}` 的订阅者收不到任何“精确标识未登记”的事件。设计意图究竟是“All 放大已登记标识”还是“All 覆盖整类”，源码与注释/测试命名不一致，需要设计者确认；若要后者，门禁条件需改成“精确标识存在或 `{category, All}` 存在”。

**待确认 3：`Event_Broker::attach` 返回 `void`，终端 `attach` 的成功返回值无法反映总线侧结果。**
`Event_Terminal::attach` 在调用 `broker_attacher` 后无条件返回 `true`；`Event_Broker::attach` 对空名称/空回调只写日志并返回，无失败信号。名称非法时终端仍报告成功，直到事件全部丢失才暴露。是否有意“接入失败不阻断业务”需确认。

**待确认 4：`Event_Broker` 的默认拷贝/移动与构造期自捕获回调冲突。**
构造函数把 `[this](std::shared_ptr<Event> evt){ this->process(evt); }` 存入 `receivers`，而拷贝构造、拷贝赋值、移动构造、移动赋值全部 `= default`。拷贝后的总线副本会保留指向原对象的 `process` 回调；副本上的 `Subscriber/*`、`Subscribed_Events/*` 事件会改原对象的登记表。移动后原对象的 `receivers` 仍持有指向旧地址的回调。是否需要禁用拷贝/移动或自定义重建，需要设计决策。

**待确认 5：`Event_Terminal` 默认移动后总线回调悬垂。**
移动构造/赋值允许终端被搬移，但 `attach` 交给总线的接收入口捕获的是原对象 `this`（包装 lambda 或用户回调）。移动后总线回调仍指向旧地址，下一次投递即访问已搬移对象。终端是否应禁止移动，需要确认。

**待确认 6：投递读路径使用 `operator[]` 带来隐式插入与空函数调用。**
`Event_Broker::receive` 广播分支中 `acl_set[{category, event_protocol::all}]` 使用 `operator[]`，会为从未登记 `All` 的分类永久插入空 `vector`；每次广播都可能增加表项，属于读路径写副作用。另一处 `receivers[acl_keys[send_time]](evt)` 未用 `find`/`at` 校验密钥是否有回调；若授权列表残留已 `erase` 的密钥（例如分发中途 `Detach`），会默认构造空 `std::function` 并调用，抛 `std::bad_function_call`。是否应改为 `find` 并跳过缺失项，需要确认。

**待确认 7：`std::hash<engine::Event>` 标记 `noexcept` 但内部 `config.dump()` 可能抛异常。**
`事件.h` 第 96 行注释已写明“dump() 可能抛出异常，但 noexcept 标记要求不抛，这里假设不会”。对含 `nlohmann::json::binary` 的载荷，`dump()` 会抛 `type_error`，在 `noexcept` 函数中导致 `std::terminate`。注释意识到风险但未处理，需要确认是否接受该假设。

**待确认 8：`Event_Terminal::attach` 不登记订阅清单，行为依赖调用方补发 `Add`。**
`attach` 只登记名称、密钥与接收入口；未发 `Subscribed_Events/Add` 时终端收不到任何广播，且没有任何告警（`receive` 的失败原因是“标识未登记”，与发送方无关）。该两段式设计已在 `Config_Loader`、`Log_Config_Bridge` 与游戏侧 `Event_Node` 中统一遵守，但接口本身没有强制或文档提示，是否需要把订阅清单并入 `attach` 需要确认。

**待确认 9：同一订阅者以新密钥重新 `attach` 会留下“幽灵授权”。**
`Event_Broker::attach` 用 `mapping.insert_or_assign` 覆盖名称对应密钥、用 `receivers.insert_or_assign` 写入新密钥回调，但不删除旧密钥在 `acl_set` 中的授权、也不删除旧密钥的 `receivers` 条目。之后广播仍会向旧密钥投递（旧回调仍可调用），`Detach` 只按新密钥清理。测试中的密钥由 `std::hash(名称)` 派生，同名恒定，因此未暴露该问题。是否需要“同名重接时清理旧密钥”需要确认。

**待确认 10：`Subscriber/Check` 通过原地修改共享事件返回结果，`call`/`response` 协议未使用。**
`Event_Broker::process` 的 `Check` 分支直接写 `config[field_subscribed]`，没有构造 `Response` 事件；`事件协议.h` 的 `call`、`response` 两个常量在本模块内无任何引用。该查询依赖“同步调用 + 事件对象共享 + 调用方保留 `shared_ptr`”三个隐式条件，接口层面没有任何说明。是否保留该隐式查询方式或改为 `Response` 事件，需要确认。

**待确认 11：分发中途 `Detach` 其他订阅者可能导致 `bad_function_call`。**
`receive` 广播分支在循环前拷贝授权列表，但回调中若发送 `Subscriber/Detach` 删除尚未轮到的订阅者，`receivers` 条目被 `erase`；后续循环仍按快照访问该密钥，`operator[]` 默认构造空函数并调用，抛异常。模块没有“分发中禁止改登记表”的约束或延迟机制。是否需要在 `receive` 内加保护，需要确认。

**待确认 12：`Event_Broker::process` 公开，可绕过 `receive` 的全部投递门禁。**
`process` 声明在 `public` 区，只校验 `config["object"]`；不检查标识是否已登记、不检查 `tag == All`、不排除发起者。快照内游戏侧 `Event_Node` 直接 `broker.process(subscribe)` 来登记订阅。该设计是有意暴露“登记表维护入口”，还是应当降为私有并提供受控包装，需要确认。

**待确认 13：`Terminal_Port::bind` 对“三参数但返回非 `void`”的回调静默无操作。**
`bind` 的外层 `if constexpr (std::is_invocable_v<T, const std::string&, const uint64_t&, Event_Handler>)` 命中后，内层 `if constexpr (std::is_same_v<... , void>)` 不成立时函数体为空，且不会落入后面的 `else if` 分支。结果是端口未注册、`binding_table` 无记录、无日志、`bind` 仍返回 `*this`。`memory_malloc` 失败时同样静默（`bind` 丢弃 `function_register` 的 `false`）。是否需要 `static_assert` 或错误日志，需要确认。

**待确认 14：快照内游戏侧带有事件系统的旧版头副本，与当前布局分叉。**
`Application/Game/星屑弹幕/external/silver_era/include/Engine/EngineFoundation/src/core/event/...` 是旧布局（`src/core/event`）的事件系统头副本；当前引擎源码在 `Engine/EngineFoundation/src/event/`，且 `源文件列表.cmake` 只编译后者。游戏侧 `source/communication/事件总线.cpp` 用到的 `Event_Broker::attach`、`receive`、`process` 与 `Event_Terminal` 接口与当前源码一致（按签名核对），但其包含路径与注释引用的“模块架构/事件系统.md”属于旧版语境。是否需要同步该 vendored 副本，需要确认。

**待确认 15：模块完全没有并发保护。**
`Event_Broker` 三张表与 `Event_Terminal::event_set` 均无锁、无原子量；`receive` 的同步分发可被任意线程调用；`query` 返回内部指针。若引擎未来在渲染线程/逻辑线程同时投递事件，会出现数据竞争。当前是否有“事件系统只在主线程使用”的全局约定，需要确认。

**待确认 16：`Event_Terminal::key()` 第二次返回 `nullopt`，使用方 `.value()` 可能抛异常。**
`key()` 的语义是“首次生成并返回，之后返回空”，而非“重复调用返回同一密钥”。快照内 `Config_Loader`、`Log_Config_Bridge` 都在构造函数里只调用一次并 `.value()`，因此安全；任何“先探测再取值”或“延迟再取”的写法都会抛 `std::bad_optional_access`。是否应改为“始终返回同一密钥”的幂等接口，需要确认。

**待确认 17：`事件中转器.h` 依赖传递包含获得 `hash_combine`。**
`std::hash<Event_Identity>` 使用 `engine::detail::hash_combine`，但 `事件中转器.h` 只包含 `Event/事件.h` 与 `数据校验工具.h`；`hash_combine` 由 `事件.h` 包含的 `../../detail/methods/哈希混合.h` 传递提供。若 `事件.h` 调整包含，`事件中转器.h` 会编译失败。是否需要在中转器头显式包含，属于包含卫生问题。

**待确认 18：`Event_Terminal::query` 返回内部容器的裸指针。**
返回值 `const std::vector<std::shared_ptr<Event>>*` 指向 `event_set`；调用方可在终端后续 `receive`/`clear` 后继续持有该指针，内容随时变化，也可跨越线程。接口没有文档说明生命周期。是否应改为返回值拷贝或提供快照视图，需要确认。

**待确认 19：`Event_Terminal::receive` 不校验密钥，任何持有终端引用者都可写入缓存。**
`receive` 是 `public` 且无密钥参数，只按端口绑定情况分发或入队；`query`/`clear` 却要密钥。也就是说“写入无门禁、读取有门禁”。这是有意（接收方必须能被总线调用）还是接口设计缺口，需要确认。

**待确认 20：`Event::operator==` 忽略 `sender`，与“发起者排除”语义无关。**
`operator==` 只比较 `category`、`tag`、`receiver`、`config`；`std::hash<Event>` 同样忽略 `sender`。因此两个仅 `sender` 不同的事件被判等且哈希相同。模块内未把 `Event` 用作容器键，但外部若以 `Event` 为键，会把不同发起者的事件合并。是否有意忽略 `sender`，需要确认。

**待确认 21：密钥的有符号/无符号双重表示。**
终端侧 `optional<int64_t>` 经 `Random_Generator<int64_t>` 生成，可能为负；总线侧全部 `uint64_t`。`Event_Terminal::attach` 的隐式转换与使用方载荷的 `static_cast<uint64_t>` 是约定俗成的两处转换点，但 `Event_Broker::process` 对 `config["acl_key"]` 只做“整数”检查，不检查范围/符号。若使用方直接写入 `int64_t` 负值，会按无符号语义比较失败。是否统一为 `uint64_t` 全链路，需要确认。

**待确认 22：`Detach` 只删除每个标识列表中的第一个匹配项。**
`process` 的 `Detach` 分支对每个 `acl_set` 条目只 `erase` 第一个等于该密钥的元素并 `break`。正常路径下 `Add` 已做幂等，因此每个标识最多一个表项；但若出现“同名换钥后残留旧密钥再被新密钥覆盖”等异常路径，列表可能同时含新旧密钥，`Detach` 只清一个。该实现是否以“列表内密钥唯一”为不变量，需要确认。

**待确认 23：测试注释提到已移除的 `target_object_check`。**
`Application/Test/tests/Foundation/src/核心/事件中转器测试.cpp` 多处注释称 `Event_Broker::target_object_check` 已在“引擎层 e430610”移除，改为“投递匹配事件应送达一次”的行为验证。当前头文件确实没有该接口，测试已随接口调整；但“登记状态不可查询”意味着外部只能靠探测事件判断订阅是否生效。是否有意，需要确认。
