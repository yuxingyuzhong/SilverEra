## 二、模块功能介绍

日志子系统是 `EngineFoundation` 最底层的旁路设施。它在依赖上只允许指向预编译头、纯工具头（路径规范化、路径字符串转换、标准库 `std::format` 特化）与事件系统，绝不反向依赖上层模块；这使任何模块（包括 `detail/` 工具、事件终端、配置加载器、资源加载器）都可以包含 `日志系统运行包.h` 并调用全局 `logger`，而不引入头文件循环。日志子系统因此承担“全层最小可用诊断输出”的职责。

日志子系统对外表现为单一门面 `engine::logger`（类型 `Log`）。调用方只使用 `info` / `warn` / `error` / `debug` 四个模板方法与少量配置方法；调用点不直接接触树、规则或输出目标。门面内部持有规则集 `Log_Rules` 与流节点树 `Stream_Tree`，把“是否输出”和“输出到哪里”分别委托给二者。

“是否输出”的判定完全由调用处文件路径与日志级别决定。调用处文件路径不是显式参数，而是由 `std::source_location::current()` 在调用表达式处捕获后随格式对象传入；因此同一行代码无论在哪个函数、哪个线程执行，都归属于同一个文件节点。日志子系统据此实现按文件、按目录、按级别的白/黑名单，以及根目录作用域截断。

“输出到哪里”由以调用处路径公共前缀构造的链表树决定。树节点可绑定文件输出流或任意外部 `std::ostream`；未绑定自有流的节点向上继承最近祖先的自有流；整棵树都没有绑定时回落到控制台。一个节点可以持有多个输出目标，一条日志会写入该节点解析出的全部目标。

日志子系统不提供异步队列、日志轮转、时间戳、线程标识、来源行号、级别阈值语义、日志文件目录创建、日志压缩或远程传输。级别只是一个参与规则匹配的字符串；模块内不存在级别枚举或阈值比较。文件名通过 `source_location` 取到，但只用于路由，不写入正文。

配置桥接 `Log_Config_Bridge` 是日志子系统与事件系统/配置加载之间的适配层。它不实现日志功能，只订阅类别 `Log` 的 `Load` / `Unload` 事件，把 JSON 载荷逐字段翻译成 `Log` 的公开设置调用；它位于日志目录内，但不让 `Log` 反向包含事件系统，避免 `Log` 与事件中转站之间的头文件循环。

时间部分只提供一个轻量命名计时器 `Timer`：以 `std::chrono::steady_clock` 打点，按任务名保存起点，返回两个时间点之间的 `Duration`，并提供秒/毫秒/微秒/纳秒四种换算。它不提供暂停、累计、多次采样、定时回调、时间点序列化或墙钟时间。

本模块的关键约束有三条：第一，日志树的路由键是“根目录相对路径 + 末尾 `/`”，根目录未设置时只做基础规范化且不截断；第二，根目录未设置时允许日志输出（回落到控制台），但拒绝任何输出流绑定；第三，日志行的“越界截断”先于“规则判定”，全局取反不能把域外日志救回（见 §六 6.1、6.2）。

## 三、模块公开接口

### 3.1 别名与全局对象

```cpp
namespace engine
{
    using Log_Stream = std::shared_ptr<std::ostream>;

    inline Log logger;   // 定义于 日志系统运行包.h
}
```

`Log_Stream` 是日志子系统统一的外部输出流持有形式：共享所有权，保证输出目标的流生命周期不短于使用它的 `Stream_Sink`。`inline Log logger` 为 C++17 内联变量，跨翻译单元唯一；所有模块看到的是同一个 `Log` 对象，因此规则与树是进程级全局状态。

本模块不定义任何 `LOG_INFO` 之类宏。调用形式固定为 `logger.info("...", args...)`（`warn` / `error` / `debug` 同理）。

### 3.2 `Log::Format`

`Log` 内嵌的格式对象负责同时携带“编译期校验过的格式串”和“调用处位置”：

```cpp
class Log
{
public:
    template<typename... Args>
    class Format
    {
    public:
        template<typename Text>
        consteval Format(const Text& text,
            std::source_location place = std::source_location::current());

        std::format_string<Args...> pattern;   // 格式串本体
        std::source_location site;             // 调用处信息
    };
};
```

语义与约束：

| 项 | 事实 |
| --- | --- |
| 构造 | `consteval`，只能由编译期可知的格式串构造；`std::format_string<Args...>` 自身也是 `consteval` 构造，运行期字符串无法通过编译 |
| 占位符校验 | 由 `std::format_string<Args...>` 在编译期校验占位符数量、类型与格式说明符 |
| 调用处捕获 | `site` 的默认实参在调用表达式处求值，`file_name()` 即调用方文件路径；行号/列号虽一并捕获但日志链路只使用 `file_name()` |
| 失败行为 | 格式串与实参不匹配是编译错误，不产生运行期回退 |

`Format` 是轻量值对象，按值传入日志方法；`pattern` 内部只引用静态格式串，不复制正文。

### 3.3 `Log` 的四个输出方法

```cpp
template<typename... Args>
void info (Format<std::type_identity_t<Args>...> fmt, Args&&... args);

template<typename... Args>
void warn (Format<std::type_identity_t<Args>...> fmt, Args&&... args);

template<typename... Args>
void error(Format<std::type_identity_t<Args>...> fmt, Args&&... args);

template<typename... Args>
void debug(Format<std::type_identity_t<Args>...> fmt, Args&&... args);
```

四个方法都是非静态、非 `const`、无 `noexcept` 的成员模板。第一个参数用 `std::type_identity_t<Args>...` 构成非推导上下文，避免与尾随参数包竞争推导；`Args` 实际由 `args...` 推导，因此调用点写 `logger.info("x={}", 42)` 即可。

行为完全一致，仅级别字符串不同：

| 方法 | 传给路由链的级别串 | 正文构造 |
| --- | --- | --- |
| `info` | `"INFO"` | `std::format(fmt.pattern, std::forward<Args>(args)...)` |
| `warn` | `"WARN"` | 同上 |
| `error` | `"ERROR"` | 同上 |
| `debug` | `"DEBUG"` | 同上 |

语义链：格式化正文 → 交给私有 `output(fmt.site.file_name(), 级别串, 正文)` → 合成 `"[级别]正文\n"` → 交给 `Stream_Tree::stream_output` 完成截断、规则判定与写 sink。

失败/告警行为：方法无返回值；`std::format` 若在运行期抛出 `std::format_error`（例如动态宽度实参非法），异常会直接穿出日志调用，日志层不做捕获【待确认：17】。正文中的换行不会被改写，调用方自带 `\n` 时最终消息会含多个换行。

### 3.4 `Log` 的根目录与规则接口

```cpp
bool root_set(const std::string& dir);          // 设置日志根目录；空串表示整个项目
void root_clear(void);                           // 清除根目录，回到未设置
std::string root_get(void) const;                // 查询根目录；未设置返回空串

bool priority_set(Rule_Priority mode);           // 设置级别/归属判定先后
Rule_Priority priority_get(void) const;

bool verdict_invert_set(bool invert);            // 设置全局取反
bool verdict_invert_get(void) const;

bool file_rule_set(const std::string& file, bool allowed);
bool dir_rule_set (const std::string& dir,  bool allowed);
bool level_rule_set(const std::string& level, bool allowed);

void rule_clear(void);                           // 清三张许可表并复位优先级/取反，保留根目录
```

逐条语义：

| 接口 | 返回值 | 副作用 | 失败/重复行为 |
| --- | --- | --- | --- |
| `root_set` | 恒 `true`（`Log_Rules::root_set` 无失败路径） | `Log_Rules::root_set` 在规则锁内以空锚点做基础规范化写入 `root_key`；随后 `stream_tree.cache_clear()` 清空调用点缓存 | 重复设置不判重，直接覆盖；即使同值也会清缓存 |
| `root_clear` | 无 | `root_key.reset()`；随后清空调用点缓存 | 重复清除无额外效果，但仍清缓存 |
| `root_get` | 根目录键；未设置返回空串 | 无 | 未设置与“空串表示整个项目”返回值相同，调用方无法区分【待确认：23】 |
| `priority_set` | 模式实际改变返回 `true`，同模式返回 `false` | 改写 `Log_Rules::priority` | 同模式不写、返回 `false` |
| `priority_get` | 当前模式 | 无 | 默认 `Scope_First` |
| `verdict_invert_set` | 同值返回 `false`，否则 `true` | 改写 `Log_Rules::verdict_invert` | 同值不写 |
| `file_rule_set` | 同键同值返回 `false`，否则 `true` | 规则锁内以根目录锚点生成键，写入 `file_rules` | 不校验路径是否存在；域外路径也会被登记但其键不会匹配域内调用处 |
| `dir_rule_set` | 同上 | 写入 `dir_rules` | 同上；空串目录键实际永不命中【待确认：8】 |
| `level_rule_set` | 同上 | 直接以级别字符串为键写入 `level_rules`，不做路径规范化 | 不校验级别名，`"INFO"` 大小写必须完全一致【待确认：1】 |
| `rule_clear` | 无 | 清空三张表；`priority` 复位 `Scope_First`；`verdict_invert` 复位 `false`；**不动** `root_key` | 不触发任何缓存失效（规则是实时读取的） |

### 3.5 `Log` 的流接口

```cpp
bool stream_bind(const std::string& path, const std::string& file_name);
bool stream_bind(const std::string& path, const Stream& stream);   // Stream = Log_Stream
bool stream_clear(const std::string& path);
void stream_flush();
```

语义与失败行为：

| 接口 | 前置条件 | 实现链 | 失败行为 |
| --- | --- | --- | --- |
| `stream_bind(path, file_name)` | 根目录必须已设置（`root_key` 有值，含空串） | 私有 `bind_gate()` → `Stream_Tree::stream_bind(path, file_name, rules)` | 根目录未设置：若控制台目标可用则 `warn("日志系统::日志根目录未设置，输出流绑定已拒绝，日志回落控制台输出")` 并返回 `false`；控制台也不可用则 `error(...)` 并返回 `false`。门禁**不会切换**到控制台，只是打印提示并拒绝【待确认：11】 |
| `stream_bind(path, stream)` | 同上 | 门禁 → `Stream_Tree::stream_bind(path, stream, rules)` | 同上；此外空流直接返回 `false` |
| `stream_clear(path)` | 无门禁 | 转发 `Stream_Tree::stream_clear(path, rules)` | 路径节点不存在返回 `false`；存在则清自有流、清该节点共享缓存、递增树版本号并返回 `true` |
| `stream_flush()` | 无 | 转发 `Stream_Tree::stream_flush()` | 无返回值；逐 sink 调用 `flush()`，不回传任何失败 |

`path` 不要求是已存在的目录或文件；它只是规则键空间内的一段路径，`Stream_Tree` 会按需建节点。`file_name` 为空串时，树侧转为控制台目标并打印 `[FATAL]文件名为空`，仍返回 `group_append` 的结果（真）。若控制台目标分配失败，会向节点容器压入空 `Sink` 并返回 `true`【待确认：28】。

### 3.6 `Rule_Priority` 与 `Log_Rules`

```cpp
enum class Rule_Priority
{
    Scope_First,   // 归属优先（默认）
    Level_First    // 级别优先
};

class Log_Rules
{
public:
    bool root_set(const std::string& dir);
    void root_clear();
    bool root_is_set() const;
    std::string root_get() const;

    bool key_make(const std::string& raw, std::string& out) const;

    bool file_allowed_set(const std::string& file, bool allowed);
    bool dir_allowed_set (const std::string& dir,  bool allowed);
    bool priority_set(Rule_Priority mode);
    Rule_Priority priority_get() const;
    bool verdict_invert_set(bool invert);
    bool verdict_invert_get() const;
    bool level_allowed_set(const std::string& level, bool allowed);

    void clear();
    bool output_pass(const std::string& key, const std::string& level) const;

private:
    void scope_eval_locked(const std::string& key, bool& hit, bool& allowed) const;
    std::string key_make_locked(const std::string& raw, bool& in_scope) const;

    mutable std::mutex rule_mtx{};
    Rule_Priority priority = Rule_Priority::Scope_First;
    bool verdict_invert = false;
    std::optional<std::string> root_key{};
    std::unordered_map<std::string, bool> file_rules{};
    std::unordered_map<std::string, bool> dir_rules{};
    std::unordered_map<std::string, bool> level_rules{};
};
```

接口语义：

| 接口 | 语义 |
| --- | --- |
| `root_set` | 规则锁内 `path_key_normalize(dir, "")`：路径词法规范化、分隔符统一为 `/`、去前导 `/` 与 `./`、末尾补 `/`；空串保持空串；恒返回 `true` |
| `root_clear` | `root_key.reset()`，回到“未设置”（≠“整个项目”） |
| `root_is_set` | `root_key.has_value()`；空串也算已设置 |
| `root_get` | `root_key.value_or("")`；未设置返回 `""` |
| `key_make` | 规则锁内生成路径键并回传是否位于根作用域；根未设置或为空串时恒域内；根非空且键不含根时域外，键仍返回基础规范化文本 |
| `file_allowed_set` / `dir_allowed_set` | 键经根锚点剥离；同键同值返回 `false`，否则写入并返回 `true` |
| `level_allowed_set` | 级别名不规范化；同键同值返回 `false` |
| `priority_set` / `verdict_invert_set` | 同值返回 `false`，否则改写返回 `true` |
| `clear` | 清三表、优先级复位 `Scope_First`、取反复位 `false`，保留根 |
| `output_pass` | 按 `priority` 得出基础结论，再按 `verdict_invert` 取反后返回；不做作用域截断（调用方已先做） |

`output_pass` 的真值规则与短路顺序见 §六 6.1。

### 3.7 `Stream_Tree`

```cpp
class Stream_Tree
{
public:
    bool stream_bind(const std::string& path, const std::string& file_name,
                     const Log_Rules& rules);
    bool stream_bind(const std::string& path, const Log_Stream& stream,
                     const Log_Rules& rules);
    bool stream_clear(const std::string& path, const Log_Rules& rules);
    bool console_available();
    void cache_clear();
    void stream_flush();
    void stream_output(const char* file_name, const std::string& level,
                       const std::string& msg, const Log_Rules& rules);
};
```

私有类型（不对外可写，列在此便于理解公开接口语义）：

```cpp
using Sink            = std::shared_ptr<Stream_Sink>;
using Sink_Group      = std::shared_ptr<std::vector<Sink>>;
using Sink_Group_Weak = std::weak_ptr<std::vector<Sink>>;

struct Stream_Node
{
    std::string key{};                 // 相对根路径段，末尾恒 '/'
    Stream_Node* parent = nullptr;
    std::list<Stream_Node> children{};
    Sink_Group own_group{};
    Sink_Group_Weak shared_group{};
    uint64_t shared_epoch = 0;
    std::mutex node_mtx{};
};

Node_Cache<Stream_Node> node_cache{};
static constexpr size_t file_flush_size = 4096;
```

公开接口语义：

| 接口 | 语义 | 失败行为 |
| --- | --- | --- |
| `stream_bind(path, file_name, rules)` | 整树锁内 `key_make` → `node_ensure` 定位/建节点 → 绑定目标；`file_name` 空串时改绑控制台并打印 `[FATAL]文件名为空\n已切换至控制台输出`；非空时 `new(std::nothrow) std::ofstream(file_name)`（默认 `out|trunc`，会清空同名文件），构造 `Stream_Sink(stream, 4096, true)` 后追加进节点自有容器 | 流内存分配失败打印 `[FATAL]内存不足\n已切换至控制台输出` 并返回 `false`；文件打开失败打印 `[ERROR]文件打开失败\n已切换至控制台输出` 并返回 `false`；`Stream_Sink` 分配失败返回 `false`；自有容器分配失败返回 `false`。这些路径都**没有**真正把控制台目标追加到节点【待确认：11】 |
| `stream_bind(path, stream, rules)` | 空流直接 `false`；否则整树锁内构造 `Stream_Sink(stream, 0, true)`（每次写出即落盘并刷新底层流），定位节点后追加 | 空流或 sink 分配失败返回 `false` |
| `stream_clear(path, rules)` | 整树锁内按键 `node_find`（不新建）；存在则节点锁内 `own_group.reset()`、`shared_group.reset()`、`shared_epoch=0`，随后 `epoch_bump()` | 节点不存在返回 `false` |
| `console_available()` | `sink_console() != nullptr`；首次调用会构造静态控制台 sink | 无 |
| `cache_clear()` | 转发 `node_cache.cache_clear()` | 无 |
| `stream_flush()` | 整树锁内递归 `group_collect` 收集所有自有 sink，再并入控制台 sink；释放树锁后逐个 `sink->flush()` | 无返回值；空 sink 跳过 |
| `stream_output(file_name, level, msg, rules)` | 热路径：`node_locate`（缓存命中不建键）→ 域外直接丢弃 → `output_pass_check` → 未放行丢弃 → `group_resolve` → 解锁后逐个 `sink->write(msg)`；容器为空或不可用时直接 `console->write(msg)` | 节点为空（域外）或规则未放行均静默丢弃；无控制台时该行丢失 |

`Stream_Tree` 的对象不可拷贝（含 `std::mutex` 与 `std::list` 成员，隐式拷贝被删除）；它作为 `Log` 的值成员长期存活。

### 3.8 `Stream_Sink` 与 `Log_Stream`

```cpp
class Stream_Sink
{
public:
    Stream_Sink(const Log_Stream& owner, size_t flush_size, bool flush_target);

    Stream_Sink(const Stream_Sink&) = delete;
    Stream_Sink& operator=(const Stream_Sink&) = delete;

    ~Stream_Sink();                        // 析构时 flush()

    void write(const std::string& text);   // 锁内追加缓冲，达阈值落盘
    void flush();                          // 锁内落盘

private:
    void flush_locked();                   // 须已持锁

    Log_Stream owner{};
    size_t flush_size = 0;
    bool flush_target = false;
    std::string buffer{};
    std::mutex sink_mtx{};
};
```

语义：

| 项 | 事实 |
| --- | --- |
| `flush_size` | 缓冲字节阈值；`write` 后 `buffer.size() >= flush_size` 即 `flush_locked()`；`flush_size=0` 表示每次 `write` 都触发落盘 |
| `flush_target` | 落盘后是否调用 `owner->flush()`；文件流设为 `true` 以使外部可即时读到，控制台设为 `false` |
| `flush_locked` | 缓冲为空或 `owner` 为空直接返回；否则 `*owner << buffer`，按需 `owner->flush()`，然后 `buffer.clear()` |
| 线程安全 | `write` / `flush` 均持 `sink_mtx`，同一条消息在单个 sink 内整体追加，避免多线程交错 |
| 失败行为 | 不返回错误；底层流若启用异常掩码，`<<` 可能抛异常；`buffer += text` 分配失败可抛 `std::bad_alloc`【待确认：27】 |
| 生命周期 | `owner` 共享持有流（控制台用空删除器包装 `std::cout`），sink 析构时把残余缓冲写出 |

`Log_Stream` 的删除器约定：文件流由 `shared_ptr<std::ofstream>` 正常删除；控制台流用 `Log_Stream(&std::cout, [](std::ostream*){})` 不持有其生命周期。

### 3.9 `Node_Cache`

```cpp
template<typename Node>
class Node_Cache
{
public:
    Node* cache_fetch(const char* file_name);
    void cache_store(const char* file_name, Node* node);
    void cache_clear();

private:
    std::unordered_map<const char*, Node*> cache_map{};
    std::mutex cache_mtx{};
};
```

语义：以 `std::source_location::file_name()` 返回的 `const char*` 指针为键，避免热路径字符串比较与哈希构造；返回的节点指针由树拥有，缓存不负责释放。三个操作均持 `cache_mtx`。`cache_store` 用 `operator[]` 登记（值类型 `Node*`，默认空指针），同键覆盖。缓存无容量上限、无淘汰，清空仅由 `Log::root_set` / `Log::root_clear` 间接触发。该设计依赖“文件名指针稳定且同值”的隐式约定【待确认：21】。

### 3.12 `Timer` 与时钟别名

```cpp
namespace engine
{
    using Clock     = std::chrono::steady_clock;
    using TimePoint = Clock::time_point;
    using Duration  = Clock::duration;

    class Timer
    {
    public:
        Timer(void) = default;
        ~Timer() = default;

        bool task_build(const std::string& task_name);
        bool task_unload(const std::string& task_name);
        Duration elapsed(const std::string& task_name, bool restart = false);

        static double      units(const Duration& duration);
        static double      Milli_units(const Duration& duration);
        static double      Micro_units(const Duration& duration);
        static long long   Nano_units(const Duration& duration);

    private:
        std::unordered_map<std::string, TimePoint> task_origin_set;
    };
}
```

语义与失败行为：

| 接口 | 返回值 | 语义 |
| --- | --- | --- |
| `task_build(name)` | 新建成功 `true`；同名已存在 `false` | `count` 判存在后 `insert({name, Clock::now()})`；不覆盖已有起点，不清零 |
| `task_unload(name)` | 存在并删除 `true`；不存在 `false` | `find` + `erase` |
| `elapsed(name, restart=false)` | 任务的 `Clock::now() - origin`；任务不存在返回值初始化 `Duration{}`（零） | `restart=true` 时缓存旧起点、把起点写为 `Clock::now()`，再返回 `Clock::now() - 旧起点`；注意两次 `now()`【待确认：14】 |
| `units` | `double` 秒 | `duration<double>(d).count()` |
| `Milli_units` | `double` 毫秒 | `duration<double, std::milli>(d).count()` |
| `Micro_units` | `double` 微秒 | `duration<double, std::micro>(d).count()` |
| `Nano_units` | `long long` 纳秒 | `duration_cast<std::chrono::nanoseconds>(d).count()`，整型截断【待确认：16】 |

`Timer` 无锁、无 `const` 查询、无容量限制；任务名任意字符串，空串也合法。`Clock` / `TimePoint` / `Duration` 是 `engine` 命名空间内的通用别名，可能与其他同层别名重名（推测，取决于同一命名空间的其他声明）。

### 3.13 被包含的 `std::formatter` 特化（依赖契约）

`日志系统.h` 包含 `Engine/EngineFoundation/src/detail/methods/标准库format特化.h`，该文件不属本模块覆盖范围，但构成日志格式化的类型契约：

```cpp
template<> struct std::formatter<std::error_code>;        // 输出 "[值] 消息"
template<> struct std::formatter<std::error_condition>;   // 输出 "[值] 消息"
template<> struct std::formatter<std::filesystem::path>;  // 经 path_to_string 输出 UTF-8 文本
```

三个特化的 `parse` 均忽略格式说明符并返回 `ctx.begin()`；`format` 分别用 `std::format_to` 输出。`std::filesystem::path` 依赖 `detail::path_to_string` 的 `u8string` 转换，中文路径按 UTF-8 字节输出。该头只允许依赖预编译头与纯工具头，以避免 `日志系统.h → 引擎环境.h → 日志系统运行包.h` 的循环。

### 4.3 `Stream_Tree` 结构维护

| 签名 | 职责 |
| --- | --- |
| `size_t prefix_common(const std::string& left, const std::string& right)` | 求路径段对齐的公共前缀长度：逐字节比较后回退到最近的 `/` 边界，保证公共部分以完整路径段为单位 |
| `Stream_Node& node_ensure(const std::string& key)` | 按路径键自根向下定位或创建节点；空键返回根；子链表中找有公共前缀的子节点；无则就地 `emplace_back` 建新节点；子节点键完整包含于剩余键则下降；公共前缀短于子节点键时拆出中间节点并用 `list::splice` 把原子节点移入中间节点（地址不变），截短原子节点键并重设父指针；最后按剩余键建子节点 |
| `Stream_Node* node_find(const std::string& key)` | 同上定位但不新建；子节点键必须是剩余键的完整前缀（`prefix_common(child.key, rest) == child.key.size()`），否则返回 `nullptr` |
| `void epoch_bump()` | `tree_epoch.fetch_add(1)`，使所有既有共享容器缓存失效 |
| `uint64_t epoch_current() const` | `tree_epoch.load()` |

### 4.4 `Stream_Tree` 定位、判定与容器解析

| 签名 | 职责 | 关键点 |
| --- | --- | --- |
| `Stream_Node* node_locate(const char* file_name, const Log_Rules& rules)` | 调用点定位 | 先 `node_cache.cache_fetch(file_name)`，命中直接返回；未命中持 `tree_mtx`，`rules.key_make(file_name, key)`，域外返回 `nullptr`（越界截断且不建节点），否则 `node_ensure(key)`、`epoch_bump()`、`cache_store(file_name,node)` |
| `bool output_pass_check(Stream_Node& node, const std::string& level, const Log_Rules& rules)` | 选择性输出判定 | 沿父链向上，每级仅持该节点锁把本段 `key` 前插到 `full_key` 并取父指针，取到即放、不嵌套；拼接完后调用 `rules.output_pass(full_key, level)` |
| `Sink_Group group_resolve(Stream_Node& node)` | 解析生效输出容器 | 记录 `epoch_begin`；起点锁内：有 `own_group` 直接返回；`shared_epoch == epoch_begin` 且弱引用可锁则返回缓存；否则取父指针。沿父链逐级锁：命中 `own_group` 即停；否则在版本一致时尝试共享缓存；仍未命中继续向上。到根仍无则回落 `group_console()`。最后在起点锁内以 `epoch_begin` 登记 `shared_group` 与 `shared_epoch` |
| `void group_collect(Stream_Node& node, std::vector<Sink>& sinks)` | 落盘收集 | 节点锁内把本节点 `own_group` 内所有 sink 拷入结果；随后递归子节点（调用方持 `tree_mtx`） |

```text
│   ├── rule_mtx : std::mutex       [保护下列全部字段]
│   ├── root_key : std::optional<std::string>
│   │      无值 = 未设置；"" = 整个项目；非空 = 根锚点兼作用域
│   ├── priority : Rule_Priority    [Scope_First 默认]
│   ├── verdict_invert : bool       [默认 false]
│   ├── file_rules : unordered_map<string,bool>
│   ├── dir_rules  : unordered_map<string,bool>
│   └── level_rules: unordered_map<string,bool>
│
└── Stream_Tree stream_tree         [值成员，见 流节点树.h]
    ├── Node_Cache<Stream_Node> node_cache   [cache_mtx]
    │      const char* (source_location.file_name) → Stream_Node*
    ├── tree_epoch : std::atomic<uint64_t>
    ├── tree_mtx   : std::mutex      [整树结构：建节点/设流/清流/落盘收集]
    ├── file_flush_size = 4096
    └── Stream_Node node_root        [key = ""]
        └── children : std::list<Stream_Node>
              ├── key : string                   [相对根路径段，末尾 '/']
              ├── parent : Stream_Node*           [裸指针，向上]
              ├── node_mtx : std::mutex
              ├── own_group    : shared_ptr<vector<shared_ptr<Stream_Sink>>>
              ├── shared_group : weak_ptr<vector<shared_ptr<Stream_Sink>>>
              └── shared_epoch : uint64_t
                     │
                     ▼
              Stream_Sink（输出目标，可多个）
              ├── owner : shared_ptr<ostream>
              ├── flush_size / flush_target
              ├── buffer : string
              ├── sink_mtx : std::mutex
              └── flush_locked() → *owner << buffer [+ owner->flush()]
```

`Log` 只拥有规则与树；树拥有节点容器；节点容器拥有 sink；sink 共享持有流。`Node_Cache` 只持有裸节点指针，不拥有节点。控制台 sink 与容器是 `Stream_Tree` 的函数局部静态对象，生命周期与进程相同。

### 5.2 所有权、生命周期与地址稳定性

- `logger` 是内联全局变量，构造顺序在跨翻译单元间不确定；其 `Log_Rules`、`Stream_Tree` 为值成员，随 `logger` 构造/析构【待确认：2】。
- 树节点存放在 `std::list` 中，`list::splice` 只改链表钩子、不搬移元素，因此节点地址在拆分、重排后仍然有效；调用点缓存与 `parent` 指针都依赖这一性质。
- 树不做节点删除，节点数量等于出现过的不同路径前缀数；根切换会让新键空间产生新节点，旧节点保留【待确认：20】。
- `Stream_Node` 含 `std::mutex`，不可移动/拷贝；`std::list<Stream_Node>` 的 `emplace_back` 默认构造新节点，符合要求。
- `Sink_Group_Weak` 只弱引用祖先的 `own_group`。祖先 `stream_clear` 后弱引用失效，配合 `epoch_bump` 使缓存不可信，节点下次重新沿父链解析。
- `Stream_Sink` 析构触发 `flush()`；文件 sink 的 `owner` 是 `shared_ptr<ofstream>`，最后一个引用释放时关闭文件。`stream_flush()` 只 flush 不关闭。
- `Log_Config_Bridge` 是普通对象，不持有 `Log`（使用全局 `logger`），其 `event_terminal` 与 `bound_paths` 随对象析构。

### 5.3 日志事件数据流

```text
调用点 logger.info("...", args...)
   │  Format 构造（consteval；source_location::current() 捕获调用处 file_name）
   ▼
Log::info
   │  std::format(fmt.pattern, args...) → 正文 text
   ▼
Log::output
   │  std::format("[{}]{}\n", "INFO", text) → 消息行 msg
   ▼
Stream_Tree::stream_output(file_name, "INFO", msg, rules)
   │
   ├─(1) node_locate(file_name)
   │      ├─ Node_Cache::cache_fetch  [命中：无树锁、无字符串构造]
   │      └─ 未命中：tree_mtx → Log_Rules::key_make → 域外? → node_ensure → epoch_bump → cache_store
   │      域外 → 直接 return（越界截断）
   │
   ├─(2) output_pass_check(node, level)
   │      ├─ 沿 parent 链逐级持 node_mtx 读 key，拼接 full_key
   │      └─ Log_Rules::output_pass(full_key, level)  [rule_mtx]
   │            ├─ Scope_First：文件精确 → 目录最长前缀；命中即终裁；否则级别可否决
   │            ├─ Level_First：级别命中即终裁；否则归属可否决
   │            └─ verdict_invert 对最终结论取反
   │      未放行 → return（选择性丢弃）
   │
   ├─(3) group_resolve(node)
   │      ├─ own_group 优先
   │      ├─ shared_group（shared_epoch == 当前 epoch 才可信）
   │      ├─ 沿 parent 链向上找最近 own_group
   │      └─ 都没有 → group_console()（std::cout 兜底）
   │
   └─(4) for each sink in group: sink->write(msg)   [sink_mtx]
          └─ buffer += msg；buffer.size() >= flush_size → *owner << buffer
             [+ flush_target ? owner->flush()]
```

关键点：规则过滤发生在“节点定位之后、容器解析之前”。域外日志在节点定位阶段就被丢弃，规则层的全局取反无法把它救回；规则未放行则在写 sink 之前丢弃，不会产生任何输出缓冲。

### 5.4 线程归属与锁域

日志子系统没有专属线程，也没有异步队列；所有工作都在调用线程内完成。并发保护由五类互斥量构成：

| 锁 | 位置 | 保护对象 | 持有范围 |
| --- | --- | --- | --- |
| `rule_mtx` | `Log_Rules::rule_mtx`（`mutable`） | 根键、优先级、取反、三张许可表 | 每个规则读写方法内 |
| `tree_mtx` | `Stream_Tree::tree_mtx` | 节点链表结构、建节点/拆分、设流/清流、落盘收集 | 结构操作全程；日志热路径**不**使用（仅缓存未命中建节点时使用） |
| `node_mtx` | 每个 `Stream_Node` | 本节点 `key`、`parent`、`own_group`、`shared_group`、`shared_epoch` | 短临界区；父链遍历时逐节点加锁、取到即放，不嵌套 |
| `cache_mtx` | `Node_Cache::cache_mtx` | `const char* → Stream_Node*` 映射 | 缓存查/存/清 |
| `sink_mtx` | 每个 `Stream_Sink` | 缓冲与目标流 | 单次写/落盘 |

锁序：`tree_mtx → rule_mtx → node_mtx → cache_mtx`（`node_locate` 同时经历四者）；`tree_mtx → rule_mtx → node_mtx`（绑定/清流）；`node_mtx → rule_mtx`（输出判定）；`cache_mtx` 单独获取；`sink_mtx` 在所有结构锁释放后获取。代码中没有反向获取（`rule_mtx` 不请求树锁或节点锁，`node_mtx` 不请求树锁）。热路径（缓存命中）典型锁序列为：`cache_mtx` → 若干次 `node_mtx`（拼键）→ `rule_mtx` → 若干次 `node_mtx`（解析容器）→ 每个 sink 一次 `sink_mtx`。

同一源文件的所有调用点共用一个节点，因而也共用同一组 `node_mtx`；不同文件若共享路径前缀，会在祖先节点上产生锁竞争。`sink_mtx` 在单个输出目标内串行化写入；文件 sink 的 4096 字节缓冲把多次 `operator<<` 合并为一次系统调用。

## 六、模块设计 / 实现细节

### 6.1 级别判定与规则短路

`Log_Rules::output_pass(key, level)` 的完整真值逻辑（基础结论 `base`，最后再取反）：

| 模式 | 条件 | `base` | 说明 |
| --- | --- | --- | --- |
| `Scope_First`（默认） | 归属命中（文件或目录） | 归属结论 `scope_allowed` | 归属为高优先，命中即终裁；级别即使明确允许/否决也不参与 |
| `Scope_First` | 归属未命中，级别命中 | 级别结论 `level_allowed` | 级别为低优先，可允许（等于默认）也可否决 |
| `Scope_First` | 归属未命中，级别未命中 | `true` | 无规则即放行 |
| `Level_First` | 级别命中 | 级别结论 `level_allowed` | 级别为高优先，命中即终裁；归属即使否决也不参与 |
| `Level_First` | 级别未命中，归属命中 | 归属结论 `scope_allowed` | 归属为低优先，可允许（等于默认）也可否决 |
| `Level_First` | 级别未命中，归属未命中 | `true` | 无规则即放行 |

最终返回 `verdict_invert ? !base : base`。

实现中的短路细节：

1. 高优先级的“允许”也是终裁：例如 `Level_First` 下 `levels["DEBUG"]=true` 会让所有文件/目录的 `DEBUG` 日志通过，即使某目录已被 `dirs[...]=false` 否决；反过来 `levels["DEBUG"]=false` 会让所有 `DEBUG` 被否决，即使文件规则允许。这是与常见“级别阈值 + 白名单”模型不同的语义，配置时需注意。
2. 低优先级的“允许”实际上不改变结果（默认就是放行），只有“否决”有效；因此两张表叠加时的效果是“高优先表可双向终裁，低优先表只能否决”。
3. 归属内部恒为“文件精确优先，再目录最长前缀”：`scope_eval_locked` 先查 `file_rules.find(key)`，命中即返回；否则遍历全部 `dir_rules`，以“键长严格大于当前最优且为目标前缀”选最长。`key` 与规则键都以 `/` 结尾，前缀比较天然落在路径段边界。
4. 全局取反作用于最终结论，包括“无任何规则”的默认放行；`verdict_invert=true` 且无表项时，所有域内日志都会被丢弃。它不作用于作用域截断：域外日志在 `node_locate` 已返回空指针，不会进入 `output_pass`。
5. 级别是任意字符串，判定为 `unordered_map` 精确查找，大小写敏感；本模块没有级别枚举，调用侧固定使用 `"INFO"/"WARN"/"ERROR"/"DEBUG"`，配置侧可写入任意键但永远不会匹配到未知级别【待确认：1】。
6. 文件表键与目录表键都由 `key_make_locked` 规范化（含末尾 `/`），因此“文件名规则”实际上也带目录尾斜杠；若同一路径既有 `file_rules` 又有 `dir_rules`，文件表优先。
7. 规则表实时读取，没有快照或预编译匹配器；配置变更后无需重建任何规则对象，仅改表内容。

### 6.2 路径键与作用域

`detail::path_key_normalize(raw, root_anchor)` 的完整步骤（`Rule/日志规则.h` 依赖，实现在 `detail/methods/文件路径规范化.h`）：

1. `string_to_path(raw)` 把 UTF-8 文本转 `std::filesystem::path`；
2. `path_normalize` 做 `lexically_normal()`（消解 `.` 与 `..`），以根路径为起点逐节重组，跳过空节（消除尾分隔符）；
3. `path_to_string` 转回 UTF-8 文本；
4. 把所有 `\` 替换为 `/`；
5. 末尾补 `/`（非空且未以 `/` 结尾时）；
6. 若锚点非空，`rfind` 锚点最后一次出现并 `erase` 到锚点之后；
7. 循环剥离前导 `/` 与 `./`。

由此得到的键具有“以 `/` 结尾、无前导 `/`、分隔符统一”的不变量，树的前缀拼接与规则前缀比较都依赖它。根目录为空串时不做第 6 步，键为整个路径的基础规范化文本。

作用域判定在 `key_make_locked` 中：

- `root_key` 无值 → 视为整个项目，`in_scope=true`；
- `root_key` 为空串 → 视为整个项目，`in_scope=true`；
- `root_key` 非空：先对 `raw` 做基础规范化得到 `basic`，若 `basic.rfind(root_key)==npos` 则 `in_scope=false`；否则以 `root_key` 为锚点重新规范化为相对键，`in_scope=true`。

注意两处“根”匹配都依赖调用处路径文本与配置根目录文本的**前缀字面一致**：Windows 大小写差异（`D:/Proj` 与 `d:/proj`）不会被归一化；编译器记录的路径若是相对路径而根是绝对路径，也不会命中。匹配失败时该文件所有日志被视为域外而丢弃【待确认：7】。此外，根键匹配使用 `rfind`（最后一次出现），路径中间若恰好包含根文本片段也可能被误剥离（推测风险较低，但算法如此）。

根目录变更只清空调用点缓存，不清空树。旧根下的节点仍保留其键、父链、自有 sink 与共享缓存；由于缓存被清，后续日志按新根重新生成键并创建/命中新节点，旧节点不会再被新日志访问，但其 sink 仍会被 `stream_flush` 收集并落盘【待确认：6、9】。

### 6.3 流节点树的节点缓存复用

缓存分两层：

1. **调用点缓存**（`Node_Cache<Stream_Node>`）：键是 `std::source_location::file_name()` 的原始指针，值是树节点地址。缓存命中时 `node_locate` 不做任何字符串构造、不加树锁，只加一次 `cache_mtx`。这是日志热路径的主要优化。
2. **节点共享容器缓存**（`Stream_Node::shared_group` + `shared_epoch`）：节点未设置自有流时，`group_resolve` 需要沿父链找最近的有流祖先。第一次解析后把结果（`Sink_Group` 的弱引用）与当时的 `tree_epoch` 记在节点上；后续同节点的日志只要 `shared_epoch` 与当前 `tree_epoch` 一致且弱引用可锁，就直接复用，不再走父链。

缓存有效的三个前提：

- **节点地址稳定**：节点只存在于 `std::list` 中，`splice` 不搬移元素；树从不删除节点。因此缓存与 `parent` 指针长期有效。
- **指针键稳定**：`source_location::file_name()` 在主流实现中指向编译期字符串字面量；同一文件的调用点拿到同一指针。若两个翻译单元包含相同文件文本但字面量未合并，指针不同、缓存项不同，但 `node_ensure` 会按相同的键合并到同一节点，结果仍正确；只是缓存多一项。
- **版本号及时失效**：任何节点结构变化或流设置变化都 `epoch_bump`，让所有节点的共享缓存立即不可信；`shared_epoch` 采用“解析开始时的版本号”，若解析期间版本变化，登记结果自动被判过期。

`epoch_bump` 的触发点：`node_locate` 在缓存未命中并调用 `node_ensure` 后（即使节点已存在）、`stream_clear` 成功清流后、`group_append` 首次为节点创建自有容器后。`root_set` / `root_clear` 不 bump，而是直接 `cache_clear`；根变化时键空间整体改变，旧节点不再被新键命中，共享缓存对旧节点仍然自洽。

`cache_clear` 只发生在 `Log::root_set` 与 `Log::root_clear`。规则表变化（文件/目录/级别/优先级/取反）不触发清缓存，因为规则是每行实时读取的；流绑定追加到已有容器也不 bump，因为容器地址未变，已有共享缓存仍指向同一容器。

缓存无淘汰。正常情况下条目数等于参与日志的源文件数；若调用方手工构造 `Log::Format` 并传入运行期生成的文件名，键指针可能指向临时字符串，缓存会持续膨胀且可能复用已释放地址【待确认：21】。

### 6.4 输出容器解析与弱引用复用

`group_resolve` 的解析顺序与缓存登记：

1. 读取 `epoch_begin = tree_epoch.load()`；
2. 起点节点锁内：`own_group` 存在 → 直接返回（不看缓存）；否则 `shared_epoch == epoch_begin` 时尝试 `shared_group.lock()`，成功即返回；
3. 否则记录 `parent`，沿父链逐级：每级只持一个节点锁；命中 `own_group` 即停止；否则版本一致时尝试共享缓存；仍未命中则继续向上；
4. 到根仍无 → `group_console()`（静态控制台容器）；
5. 最后在起点节点锁内登记 `shared_group = found`、`shared_epoch = epoch_begin`。

设计意图：把“向上找流”的结果缓存在每个调用点节点上，使绝大多数日志只需一次起点节点锁，而不是逐级父链加锁。弱引用保证祖先 `stream_clear` 后缓存自然失效；版本号保证结构变化（拆分/新增节点/新自有流）后旧结果不被误用。

边界行为：若 `group_console()` 分配失败返回空容器，`stream_output` 检测到 `!group || group->empty()` 后会直接 `console->write(msg)`；若控制台 sink 也为空，该行静默丢失。若祖先 `own_group` 是非空但空的向量（实际不会由 `group_append` 产生），`stream_output` 同样回落控制台。

### 6.5 锁策略与已知竞态

设计意图是“结构操作粗锁、日志输出细锁、I/O 不持树锁”：

- `stream_bind` / `stream_clear` / `node_locate` 未命中 / `stream_flush` 收集阶段持 `tree_mtx`；日志热路径不碰它，只有首次出现的新调用点会短暂持树锁建节点。
- `output_pass_check` 与 `group_resolve` 都采用“逐节点加锁、取到即放”，避免在父链上嵌套持锁；`sink->write` 在所有树/节点/规则锁释放后执行，I/O 不阻塞结构操作。
- `stream_flush` 先在树锁内把所有 sink 的 `shared_ptr` 拷入局部 `vector`，释放树锁后再逐个 `flush`，避免持锁做 I/O。

已确认的竞态与薄弱点：

1. **sink 容器遍历与追加并发**：`group_resolve` 返回 `shared_ptr<vector<Sink>>` 后，`stream_output` 在**不持节点锁**的情况下遍历 `*group`；而 `group_append` 在持节点锁时对该同一 `vector` 执行 `push_back`。若线程 A 正在输出、线程 B 同时绑定同一路径，`vector` 可能重新分配，A 的迭代器失效，构成数据竞争/未定义行为【待确认：10】。`group_collect` 因为先把 sink 拷入新向量，不受此影响。
2. **新建节点的字段发布**：`node_ensure` 对新建节点的 `key`、`parent` 赋值不加 `node_mtx`，依赖“节点在 `cache_store` 之前完成写入，读者通过 `cache_mtx` 获取指针”的 happens-before 顺序；被拆分搬移的旧节点其 `key`/`parent` 写入则持锁。该顺序在当前实现下可行，但没有文档化强制（推测）。
3. **根切换与并发输出**：`root_set` 在规则锁内换根，释放后清调用点缓存；并发日志可能已从缓存拿到旧节点并继续输出。旧节点地址有效，行为是“该行仍按旧节点输出”，不会崩溃；下一行开始按新键空间。属于弱一致而非强同步。
4. `Timer` 完全无锁，见 6.11。

### 6.6 格式化方式

- 格式串在编译期确定：`Log::Format` 的 `consteval` 构造 + `std::format_string<Args...>` 的编译期检查，拒绝运行期拼接格式串，也拒绝占位符/类型不匹配。
- 调用处信息由默认实参 `std::source_location::current()` 在调用表达式处求值捕获；日志链只使用 `file_name()`，不使用 `line()` / `column()`，所以输出中没有行号。
- 每条日志做两次 `std::format`：一次格式化业务正文，一次合成 `"[级别]正文\n"`。级别括在方括号内，方括号与正文之间没有空格。
- `std::format` 的分配与解析成本按调用发生，没有缓存或预编译格式；正文、消息行、sink 缓冲各自持有字符串。
- 异常：编译期校验覆盖了绝大多数错误；运行期仍可能因动态宽度/精度实参非法抛出 `std::format_error`，日志方法未捕获，会传播到调用方【待确认：17】。
- 可格式化的类型受 `std::format` 与依赖头中的三个特化限制：`std::error_code`、`std::error_condition`、`std::filesystem::path`；`std::filesystem::path` 按 UTF-8 文本输出，中文不丢字节。

### 6.7 输出目标、缓冲与落盘

| 目标类型 | 构造 | `flush_size` | `flush_target` | 行为 |
| --- | --- | --- | --- | --- |
| 文件 | `new(std::nothrow) std::ofstream(file_name)` + `Stream_Sink(stream, 4096, true)` | 4096 | true | 默认 `out|trunc`，绑定即清空同名文件；累计 4096 字节后整段写入并 `ofstream::flush()`；外部可即时读取；不自动创建目录、不追加、不轮转 |
| 外部流 | `Stream_Sink(stream, 0, true)` | 0 | true | 每次 `write` 立即写入并刷新底层流，保持外部流即时可读语义；性能开销最大 |
| 控制台 | `Stream_Sink(&std::cout 的空删除器包装, 0, false)` | 0 | false | 每次 `write` 立即写入 `std::cout`，但不调用 `std::cout.flush()`；是否真正出现在终端取决于 `std::cout` 自身缓冲 |

落盘入口有三处：sink 内部阈值触发、`Stream_Sink` 析构、`Stream_Tree::stream_flush()`。`stream_flush` 会递归收集所有节点的自有容器并追加控制台 sink，逐个 `flush`；它不 flush `std::cout`（控制台 sink 的 `flush_target=false`），因此控制台尾部输出在异常退出时可能丢失【待确认：12】。

所有输出目标写入都加 `sink_mtx`，单条消息在单 sink 内不会与其他线程的消息交错；但多个 sink 之间没有全局顺序保证，两个线程的日志可以以任意顺序落到不同文件。

### 6.8 配置桥接的字段映射

| JSON 字段 | 类型/结构 | 调用的 `Log` 接口 | 落到 `Log_Rules` / `Stream_Tree` 的形态 | 非法输入处理 |
| --- | --- | --- | --- | --- |
| `root` | 字符串，允许空串 | `root_set(root)` | `root_key = path_key_normalize(root, "")`；空串 = 整个项目 | 非字符串：`error(...已驳回)`，保留旧根 |
| `priority` | 字符串 `"scope_first"` / `"level_first"` | `priority_set(mode)` | `priority = Scope_First / Level_First` | 非字符串或未知值：错误日志并略过 |
| `verdict_invert` | 布尔 | `verdict_invert_set(b)` | `verdict_invert = b` | 非布尔：错误日志并驳回 |
| `streams` | 数组，元素对象含 `path`、`file`（均非空字符串） | `stream_bind(path, file)` | `Stream_Tree` 中按 `path` 键建节点，追加文件 `Stream_Sink(4096,true)`；路径记入 `bound_paths` | 非数组：错误并驳回；元素缺字段/空串/非字符串：`warn(...已略过该条目)`；绑定失败：`warn(...已略过该条目: path)` |
| `files` | 对象，`路径 → 布尔` | `file_rule_set(key, value)` | `file_rules[规范化路径键] = value` | 非对象：错误并驳回；值非布尔：`warn(...已略过: key)` |
| `dirs` | 对象，`目录 → 布尔` | `dir_rule_set(key, value)` | `dir_rules[规范化路径键] = value` | 同上 |
| `levels` | 对象，`级别名 → 布尔` | `level_rule_set(key, value)` | `level_rules[原样字符串] = value` | 同上；键不校验、不规范化 |

映射的设计要点：

- `root` 必须先应用，否则后续 `streams_apply` 的 `stream_bind` 会被 `bind_gate` 拒绝；桥接固定按 `root → priority → verdict → streams → files → dirs → levels` 顺序执行。
- `files`/`dirs` 的键经过与调用处相同的路径规范化，因此配置里写绝对路径还是根相对路径，只要归一化后能匹配调用处键即可；`levels` 的键不参与路径规范化。
- `streams` 的 `path` 也经 `key_make` 生成节点键；`file` 是实际 `ofstream` 打开路径，按当前工作目录解释，不做根目录拼接。
- 配置文件里的未知字段静默忽略；类型错误逐字段跳过而不是整体回滚，因此一次 Load 可能只应用了一部分配置。
- `bound_paths` 只记录绑定成功的 `path`；失败条目不记录，卸载时也不会清理其可能已创建的节点（失败时通常未创建自有容器）。

### 6.9 配置重载与“规则重建”的真实含义

日志子系统没有“编译后的规则对象”。`Log_Rules` 的三张表就是规则本身，`output_pass` 每行都在锁内查表。因此配置变更的“重建”表现为：

1. **根目录变化**：`root_set` 覆盖根键并清空调用点缓存。旧树节点/旧绑定不清除；后续日志按新键空间创建新节点。这是唯一会清缓存的配置项。
2. **优先级/取反/文件/目录/级别变化**：直接改字段或表项，下一行日志立即生效；不清缓存、不动树。已在缓冲中的日志不会追溯重判。
3. **输出流变化**：`stream_bind` 建节点并追加 sink；首次创建自有容器会 `epoch_bump`，使所有共享容器缓存失效。`stream_clear` 清自有容器并 `epoch_bump`。这些变化不影响调用点缓存（节点地址未变）。
4. **重复 Load（未先 Unload）**：`streams_apply` 会向同一路径节点**再追加**一个文件 sink，并在 `bound_paths` 追加重复路径；日志会写多份，文件流以 `trunc` 打开同名文件，后打开的流会截断先写入的内容【待确认：5】。规则表则是覆盖式写入，不会叠加。
5. **Unload 顺序**：先 `streams_revert`（此时根键仍是旧值，路径键能匹配绑定节点）→ `rule_clear` → `root_clear`（清缓存）。因此卸载后：所有由桥接绑定的节点自有流被清除，日志回落控制台；三张表清空、优先级与取反复位；根回到未设置，新的 `stream_bind` 全部被门禁拒绝。
6. **部分应用**：每个 apply 方法内部逐字段处理，非法字段跳过并继续；因此一次 Load 后可能处于“根已换、流只绑了一部分、许可表只写了一部分”的中间状态。桥接的日志（`info`/`warn`/`error`）在这一过程中按当时已生效的规则过滤，可能被旧规则或新根截断【待确认：18】。
7. `config_unload` 末尾的 `info("...已卸载...")` 在 `root_clear` 之后执行，此时根未设置、所有自有流已清，因此该条一定走控制台兜底。

### 6.10 错误处理与降级策略

- 绝大多数接口用 `bool` 表达成功/失败，不抛异常；只有显式 `new(std::nothrow)` 的分配失败会返回空指针并被检查。
- 但容器/字符串分配仍可能抛 `std::bad_alloc`：`std::list::emplace_back`（建节点）、`unordered_map::operator[]`（规则表、缓存表）、`std::string` 拼接（键、消息）都没有 `nothrow` 形式；这使“全面禁用异常”的编码约束只覆盖了显式 `new`【待确认：27】。
- 文件流失败处理：内存不足或打开失败时，树侧只向控制台打印 `[FATAL]` / `[ERROR]` 提示并返回 `false`，不把控制台 sink 绑到该节点；由于该节点此时无自有容器，后续日志会通过 `group_resolve` 回落到控制台（祖先无流时）。行为上等价于“该路径继续走兜底”，但不是显式绑定【待确认：11】。
- 绑定门禁失败时，`Log::bind_gate` 打印 `warn` 或 `error` 并返回 `false`；打印本身走正常日志链，若根未设置则落到控制台，若根已设置但规则过滤掉了该级别，提示可能不可见。
- 清流失败仅返回 `false`，不打印；桥接 `streams_revert` 忽略返回值。
- 日志输出阶段的所有失败都是静默的：域外截断、规则不放行、容器为空且无控制台，都直接返回，不产生诊断（避免日志失败再触发日志）。

### 6.11 计时器的时间源与精度

- 时间源：`std::chrono::steady_clock`，单调时钟，不受系统墙钟调整（NTP、手动改时间）影响；适合测量间隔，不适合生成可展示的日期时间。模块不提供墙钟接口。
- `Duration` 就是 `steady_clock::duration`，其 tick 周期由标准库实现决定（平台/实现相关）；`TimePoint` 是 `steady_clock::time_point`。跨进程/跨重启不可比较，也不应序列化。
- `task_build` 只记录 `Clock::now()`；同名任务已存在时返回 `false` 且不重置起点，因此重复 build 不会清零。
- `elapsed(false)` 返回 `Clock::now() - origin`，单次取时。
- `elapsed(true)` 先缓存旧起点，再把起点写为第一次 `Clock::now()`，然后用第二次 `Clock::now()` 减旧起点。两次取时导致：返回的区间比“旧起点到重置瞬间”略大；新起点与返回终点不是同一时刻；高频调用时误差累积在测量值里，但新起点本身是准确的【待确认：14】。
- 任务不存在返回 `Duration{}`（零），调用方无法区分“任务不存在”和“确实零耗时”【待确认：15】。
- 换算口径：`units` / `Milli_units` / `Micro_units` 用 `duration<double, 周期>` 的转换构造，结果是浮点秒/毫秒/微秒，四舍五入由浮点表示决定；`Nano_units` 用 `duration_cast<nanoseconds>` 得到整数并截断（向零），与前三者口径不同【待确认：16】。
- 线程安全：`task_origin_set` 是无锁 `unordered_map`，`task_build` / `task_unload` / `elapsed(restart=true)` 都写它；多线程并发调用是数据竞争【待确认：13】。`elapsed(false)` 也会 `find`，与写入并发同样不安全。
- 性能：每次操作做一次 `unordered_map` 查找（`task_build` 是 `count` + `insert` 两次），键为 `std::string`，无预分配、无容量上限；任务数量大时查找为平均 O(1)、内存随任务名长度增长。
- 命名细节：`Milli_units` / `Micro_units` / `Nano_units` 首字母大写，与项目“函数名单词首字母不大写”的约定不一致；但项目原始风格优先，且与 `units` 形成对照。`elapsed` 非 `const`，因为 `restart=true` 会改写起点。

### 6.12 内存分配与异常策略

- 显式堆分配一律 `new(std::nothrow)`：文件流、`Stream_Sink`、`Sink_Group` 的 `vector`。
- 非显式分配（容器节点、哈希桶、字符串、`std::format` 内部缓冲）没有异常隔离；失败会抛 `std::bad_alloc` 并穿出日志调用。
- `std::shared_ptr<ofstream>` 由 `Log_Stream`（`shared_ptr<ostream>`）承接：`new(std::nothrow) std::ofstream` 得到裸指针后构造共享指针，再 `static_pointer_cast<std::ofstream>` 检查 `is_open()`；删除经由 `ostream` 的虚析构落到 `ofstream`。
- 控制台流用空删除器包装 `&std::cout`，不会尝试 delete 标准流对象。
- `Node_Cache::cache_store` 使用 `operator[]`，若映射分配失败同样抛异常；没有容错分支。

### 6.13 性能取舍

- 路由键用字符串拼接与前缀比较，换取“任意路径规则、目录继承”的灵活性；每条缓存未命中的调用点会构造多次字符串并可能拆分节点，命中后无字符串成本。
- 每条日志至少经历：`cache_mtx`、若干 `node_mtx`、`rule_mtx`、若干 `node_mtx`、每个 sink 的 `sink_mtx`。锁粒度细但次数多；高并发高频日志会在共享祖先节点与规则锁上形成竞争。
- 目录规则用 `unordered_map` 线性扫描求最长前缀，复杂度 O(目录规则数)；规则多时每行日志都付这个成本，且全程持 `rule_mtx`，所有线程串行【待确认：19】。
- 文件 sink 的 4096 字节阈值显著减少系统调用，但低流量日志可能长时间停在缓冲中，只能靠 `stream_flush` 或退出时落盘。
- 外部流 sink 采用 `flush_size=0` + `flush_target=true`，每行一次写入加一次刷新，语义即时但吞吐最低。
- 节点与 sink 只增不删；根切换、重复绑定、长期运行会累积节点和输出目标；`stream_flush` 每次遍历整棵树，成本随节点数增长【待确认：20】。
- 配置桥接按字段逐条调用公开接口，每次都取规则锁；配置加载不是热路径，未做批量接口。

## 七、模块运行链路详例

### 7.1 链路一：一条日志从调用点到 sink

以任意模块中的 `logger.info("加载器::已读取 {} 字节", n)` 为例：

1. **调用点构造格式对象**：编译器为 `Log::Format<size_t>` 生成 `consteval` 构造调用；`std::format_string<size_t>` 在编译期校验 `{}` 与 `n` 匹配；默认实参 `std::source_location::current()` 在调用表达式处求值，`site.file_name()` 得到该调用点所在源文件路径（编译器记录的文本，通常为包含根下的绝对路径）。
2. **`Log::info` 格式化正文**：`std::format(fmt.pattern, std::forward<size_t>(n))` 生成正文字符串；调用 `output(fmt.site.file_name(), "INFO", text)`。
3. **`Log::output` 合成消息行**：`std::format("[{}]{}\n", "INFO", text)` 得到 `"[INFO]加载器::已读取 N 字节\n"`；调用 `stream_tree.stream_output(file_name, "INFO", msg, rules)`。
4. **`Stream_Tree::stream_output` 定位节点**：
   - 先 `node_cache.cache_fetch(file_name)`。若该文件此前输出过，缓存命中，直接得到 `Stream_Node*`，不构造任何字符串、不取树锁。
   - 未命中：取 `tree_mtx`；`rules.key_make(file_name, key)` 在 `rule_mtx` 内做路径规范化与根剥离，同时返回 `in_scope`；若 `in_scope=false`（文件不在根目录作用域），释放锁并返回 `nullptr`，本条日志被越界截断丢弃。
   - 域内：`node_ensure(key)` 自根向下定位；必要时创建节点、拆分中间节点（`splice` 保持地址）；随后 `epoch_bump()`（使所有共享容器缓存失效），`node_cache.cache_store(file_name, node)`，释放树锁。
5. **`output_pass_check` 规则过滤**：从该节点沿 `parent` 向上，每级持 `node_mtx` 读取 `key` 并前插到 `full_key`，取到父指针即释放；到根后得到完整根相对路径键（与配置里的文件/目录键同空间）。调用 `rules.output_pass(full_key, "INFO")`：
   - 按 `priority` 选中 `Scope_First` 或 `Level_First` 分支；
   - `Scope_First` 下先查文件表精确匹配，再线性找目录最长前缀；命中即用其布尔值；未命中再看级别表，只有 `false` 才否决；
   - 最后按 `verdict_invert` 取反；
   - 返回 `false` 则本条静默丢弃，不触碰任何 sink。
6. **`group_resolve` 解析容器**：记 `epoch_begin`；起点节点锁内优先自有容器，其次版本一致的共享容器；都没有则沿父链向上找最近的自有容器；仍无则用静态控制台容器。结果（`shared_ptr<vector<Sink>>`）以弱引用与 `epoch_begin` 登记回起点节点。
7. **写 sink**：对容器内每个非空 sink 调 `write(msg)`：
   - 文件 sink：`sink_mtx` 内 `buffer += msg`；若累计达到 4096 字节，`*ofstream << buffer` 并 `ofstream::flush()`，清空缓冲；
   - 外部流 sink：阈值 0，立即写入并刷新外部流；
   - 控制台 sink：阈值 0，立即写入 `std::cout`，不调用 `std::cout.flush()`。
8. **结果与副作用**：日志出现在该调用点节点解析出的全部目标中；首次调用会建节点/缓存并递增树版本号；文件 sink 可能暂存于缓冲，直到阈值、`stream_flush()` 或进程退出。

### 7.2 链路二：配置变更后的规则重建

以配置加载侧发出 `category="Log"`、`tag="Load"` 的事件为例（发送方在快照中为 `Config_Loader` 的配置投递路径；本模块只负责接收）：

1. **事件到达**：`Event_Broker` 把事件分发给订阅者 `Log_Config_Bridge`；其 `attach` 时绑定的 `Evt_Receiver` lambda 捕获 `this`，调用 `event_process(evt)`。
2. **分发**：`event_process` 判断 `evt->category == "Log" && evt->tag == "Load"`，按固定顺序执行七个 apply；非该组合直接返回。
3. **根目录**：`root_apply` 检查 `root` 字段存在且为字符串；取字符串（空串合法）调用 `logger.root_set(root)`。`Log_Rules::root_set` 在 `rule_mtx` 内 `path_key_normalize(root, "")` 写入 `root_key`；`Log::root_set` 随后 `stream_tree.cache_clear()`，所有调用点缓存清空（旧树节点保留）。随后 `logger.info("...根目录已设置...")`，此时通常尚无文件流，走控制台。
4. **优先级与取反**：`priority_apply` 把 `"scope_first"` / `"level_first"` 翻成 `Rule_Priority` 调 `priority_set`（同值返回 `false`，无副作用）；`verdict_apply` 校验布尔后调 `verdict_invert_set`。两者只改标量，不清缓存。
5. **输出流**：`streams_apply` 校验数组与每项的 `path`、`file` 非空字符串；逐条 `logger.stream_bind(path, file)`：
   - `Log::bind_gate` 检查 `root_is_set()`；由于第 3 步已设根，放行；
   - `Stream_Tree::stream_bind` 取 `tree_mtx`，`rules.key_make(path, key)`，`node_ensure(key)` 定位/建节点；
   - 用 `new(std::nothrow) std::ofstream(file)` 打开文件（默认截断），构造 `Stream_Sink(stream, 4096, true)`；
   - `group_append` 在节点锁内创建/追加自有容器；若本次首次创建，解锁后 `epoch_bump()`；
   - 成功则 `bound_paths.push_back(path)`。
6. **许可表**：`files_apply` / `dirs_apply` / `levels_apply` 校验对象与布尔值，逐条调 `file_rule_set` / `dir_rule_set` / `level_rule_set`。前两者在 `rule_mtx` 内用当前根生成规范化键，写入对应表；后者原样写级别键。同键同值被静默视为重复设置，不报错。
7. **生效**：Load 返回后，后续每一条日志在 `output_pass` 中实时读取新表与新优先级/取反；根变化已清空调用点缓存，日志会按新键空间重建节点；流绑定已创建节点与 sink，并通过 epoch 使所有共享容器缓存失效。整个过程不重建任何“编译后的规则”，只更新数据。
8. **卸载对照**：`tag=="Unload"` 时 `config_unload` → `streams_revert` 按 `bound_paths` 逐条 `logger.stream_clear(path)`（树锁内 `key_make`、`node_find`、清自有容器、`epoch_bump`）→ `rule_clear`（三表清空、优先级/取反复位、保留根）→ `root_clear`（根置无值、清缓存）→ 记一条“卸载完成”（此时走控制台）。

副作用汇总：根键、优先级、取反、三张表、树节点自有容器、树版本号、调用点缓存。该链路不修改 `Log` 对象本身的成员，只通过 `logger` 的公开接口改写其 `rules` 与 `stream_tree`。

### 7.3 链路三：命名计时任务的建、测、卸

以帧循环使用 `Timer` 为例：

1. **构建**：`Timer timer;` 默认构造空表。首帧 `timer.task_build("frame")` → `task_origin_set.count("frame")==0` → `insert({"frame", Clock::now()})`，返回 `true`。若重复调用，`count` 非零，返回 `false`，起点保持首次值。
2. **测量**：帧末 `const Duration d = timer.elapsed("frame")`（`restart=false`）→ `find("frame")` 命中 → 返回 `Clock::now() - origin`。若任务不存在，返回 `Duration{}`（零），不报错。
3. **重置式测量**：`timer.elapsed("frame", true)` → 缓存旧起点 → `it->second = Clock::now()` → 返回 `Clock::now() - 旧起点`。调用方得到本帧耗时（略偏大），下一帧从新起点开始。
4. **换算**：`Timer::units(d)` → `duration<double>(d).count()` 得秒；`Milli_units` / `Micro_units` 分别得毫秒/微秒；`Nano_units` → `duration_cast<nanoseconds>(d).count()` 得整数纳秒（截断）。
5. **卸载**：`timer.task_unload("frame")` → `find` 命中则 `erase` 返回 `true`；不存在返回 `false`。
6. **副作用与限制**：只改 `task_origin_set`；无日志、无锁、无回调。跨线程共享同一 `Timer` 需要外部加锁（模块自身不提供）。

## 附：待确认正文

【待确认：1】模块内没有日志级别枚举或级别常量。`Log` 的四个方法把 `"INFO"` / `"WARN"` / `"ERROR"` / `"DEBUG"` 作为字符串字面量传给路由；`Log_Rules::level_rules` 接受任意字符串键，配置侧写入未知级别不会报错也不会命中。若需要统一级别词汇，应在日志模块内引入枚举或常量表。

【待确认：2】`日志系统运行包.h` 定义 `inline Log logger;`。`Log` 含 `std::mutex` 与 `std::list`，属于动态初始化对象；跨翻译单元的静态初始化顺序未定义。若其他翻译单元的全局对象在构造期调用 `logger.info`，可能访问尚未构造的 `logger`（未定义行为）。

【待确认：3】`Log_Config_Bridge` 构造函数执行 `this->acl_key = event_terminal.key().value()`。`Event_Terminal::key()` 在密钥已存在时返回 `std::nullopt`，`.value()` 会抛出 `std::bad_optional_access`。对默认构造的终端，首次调用会生成密钥，通常安全；但若终端被替换/移动为已含密钥状态，构造即抛异常。

【待确认：4】`~Log_Config_Bridge() = default`，未向事件中转站注销订阅、未解绑 `Port_ID::Evt_Receiver`。中转站若仍持有 `attach` 时注册的接收函数（lambda 捕获 `this`），桥接对象销毁后继续投递会访问悬垂指针。

【待确认：5】同一桥接对象在未收到 `Unload` 的情况下再次收到 `Load`：`streams_apply` 会向同一路径节点再追加一个文件 `Stream_Sink`，并在 `bound_paths` 追加重复路径。结果是同一行日志写多份；同名文件流以默认 `out|trunc` 打开，后打开的流截断先前内容。代码未在 Load 前清理旧绑定。

【待确认：6】根目录变更后，旧树节点与旧自有流不会被移除或重键。若在根已变更后再执行 `streams_revert`，`stream_clear` 用新根生成键，`node_find` 找不到旧键节点，旧流无法清除；旧节点仍会被 `stream_flush` 收集并落盘。`config_unload` 的顺序（先清流后清根）只在根未中途变更时成立。

【待确认：7】作用域判定用 `basic.rfind(root_key)` 做字面子串匹配：Windows 路径大小写敏感比较、盘符/分隔符差异、编译器记录相对路径而配置为绝对路径，都会导致 `in_scope=false`，该文件所有日志被截断丢弃。`path_key_normalize` 只统一分隔符与 `.`/`..`，不做大小写折叠。

【待确认：8】`dir_allowed_set("")` 若在根未设置/空串时登记，得到空字符串目录键；`scope_eval_locked` 的循环条件 `rule.first.size() <= dir_length` 在初始 `dir_length=0` 时直接跳过该规则，空键永不命中。空串目录规则实际无效。

【待确认：9】根目录未设置时日志仍会输出（`key_make` 视为域内并用完整路径建节点）；此时 `node_locate` 会为每个调用点建节点并缓存。之后 `root_set` 只清调用点缓存，不清树，旧节点（键为完整路径）永久残留。

【待确认：10】`stream_output` 在取得 `Sink_Group` 后不持任何节点锁遍历 `*group` 并调用 `write`；`group_append` 在持节点锁时对同一 `vector` 执行 `push_back`。并发“绑定 + 输出”同一节点会导致 `vector` 重新分配与迭代器失效，属数据竞争/未定义行为。建议遍历前复制容器或在节点锁内取快照。

【待确认：11】`Stream_Tree::stream_bind` 在文件流分配失败或打开失败时，注释写“已切换至控制台输出”，实现只向控制台打印 `[FATAL]` / `[ERROR]` 提示并返回 `false`，未把控制台 sink 追加到节点；后续日志能出现在控制台，是因为该节点无自有容器而走 `group_resolve` 的兜底，不是显式绑定。`Log::bind_gate` 注释“有其他可用接口则切换并告警”同样只告警并返回 `false`，未切换。

【待确认：12】控制台 `Stream_Sink` 的 `flush_size=0`、`flush_target=false`：每次 `write` 都把文本写入 `std::cout` 的缓冲，但从不调用 `std::cout.flush()`；`Stream_Tree::stream_flush` 对控制台 sink 也只调用 `Stream_Sink::flush`（内部缓冲为空，无实际刷新）。异常退出或 `std::cout` 缓冲未刷新时，控制台尾部日志可能丢失。

【待确认：13】`Timer` 的 `task_origin_set` 无互斥保护；`task_build`、`task_unload`、`elapsed(restart=true)` 都写入，`elapsed(false)` 也读取。多线程共享同一 `Timer` 是数据竞争，模块未声明线程安全策略。

【待确认：14】`Timer::elapsed(name, true)` 在重置分支调用两次 `Clock::now()`：新起点是第一次取值，返回值用第二次取值减旧起点。返回值比“旧起点到重置时刻”略大，且重置点与测量终点不同源；若调用方需要精确的“上一段耗时”，应缓存单次 `now()` 后再计算。

【待确认：15】`Timer::elapsed` 对不存在的任务返回 `Duration{}`（零），与真实零耗时无法区分，也没有错误输出/标志。调用方只能先 `task_build` 或另行记录任务存在性。

【待确认：16】`Timer::Nano_units` 用 `duration_cast<nanoseconds>` 返回 `long long`，对非整纳秒的 tick 截断（向零）；`units` / `Milli_units` / `Micro_units` 返回 `double` 且不做截断。四个换算接口的舍入口径不一致。

【待确认：17】`Log::info` / `warn` / `error` / `debug` 未捕获 `std::format` 的运行期异常。编译期格式校验覆盖多数情况，但动态宽度/精度实参非法仍可抛 `std::format_error`，异常会穿出日志调用，可能中断业务流程。

【待确认：18】配置桥接按字段逐个应用并即时记录日志；在 `root_apply` 之后、`levels_apply` 之前的日志使用“新根 + 旧许可表/旧优先级”，可能被旧规则过滤或按新根截断，导致配置过程提示缺失或误导。桥接没有“先构建完整配置再原子切换”的机制。

【待确认：19】`Log_Rules::output_pass` 在持有 `rule_mtx` 的情况下对 `dir_rules` 做全表线性扫描求最长前缀；每条日志都付 O(目录规则数) 成本，且全局串行化所有线程的规则判定。规则数量大时可能成为日志热路径瓶颈。

【待确认：20】`Stream_Tree` 只增节点、`own_group` 只追加 sink；`stream_clear` 只清指定节点的自有容器，不删除节点。根切换、重复 Load、长期运行会累积节点与输出目标；`stream_flush` 每次递归全树收集，成本随规模增长。

【待确认：21】`Node_Cache` 以 `const char*` 为键，依赖 `std::source_location::file_name()` 在进程内返回稳定且同值的指针。正常编译期字面量满足；若调用方手工构造 `Log::Format` 并传入运行期字符串的 `std::source_location`，键可能指向临时/已释放内存，导致缓存错配或持续膨胀。模块没有防御该用法。

【待确认：22】`Log::stream_flush()` 声明为 `void`，实现为 `return stream_tree.stream_flush();`（返回 void 表达式）。C++ 允许在 void 函数中 `return void-expression`，但风格上与其余 void 方法不一致。

【待确认：23】`Log::root_set` 的返回值恒为 `true`（`Log_Rules::root_set` 无失败路径），该 `bool` 不携带信息；`root_get` 对“未设置”和“空串=整个项目”都返回 `""`，调用方无法区分两种状态，只能依赖未公开的 `root_is_set`。

【待确认：24】`Log_Config_Bridge::event_process(std::shared_ptr<Event> evt)` 直接解引用 `evt->category`，未判空。若中转站或调用方传入空指针，行为未定义。

【待确认：25】`Log_Config_Bridge` 将 `Event_Terminal event_terminal` 声明为 `public` 数据成员，外部可直接绑定端口、发送事件或读取/改写终端状态；这削弱了桥接封装，也使 `acl_key` 与终端密钥的一致性依赖外部自律。

【待确认：26】`日志配置桥接.h` 的类注释称“实现集中于 core/Logging_Config_Bridge.cpp”，实际文件为 `core/日志配置桥接.cpp`；注释标题写 `Logging_Config_Bridge`，类名却是 `Log_Config_Bridge`，目录名又是 `Logging_Config_Bridge`。命名/注释与实现存在漂移，易误导检索。

【待确认：27】编码约束要求内存分配全面禁用异常、改用 `std::nothrow`，但本模块仅对显式 `new` 使用 `nothrow`；`std::list::emplace_back`（节点）、`unordered_map::operator[]`（规则表/缓存）、`std::string` 拼接、`std::format` 内部缓冲仍可能抛 `std::bad_alloc`，异常会穿出日志调用。

【待确认：28】`Stream_Tree::stream_bind(path, file_name)` 在 `file_name` 为空且控制台 sink 不可用（分配失败）时，`group_append(node, sink_console())` 会把空 `Sink` 压入节点自有容器并返回 `true`；后续输出遍历时跳过空 sink，该节点表现为“有自有容器但无有效目标”，不会回落控制台（因为 `group_resolve` 命中非空容器）。该边界行为与“切换控制台”的注释不一致。
