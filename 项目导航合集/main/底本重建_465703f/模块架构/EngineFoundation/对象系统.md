## 二、模块功能介绍

本模块只做两件事：给每个对象一个可回收的 64 位身份编号，并用连续内存的对象池承载一批派生自 `Object` 的对象值，提供按键装载、查找、卸载、清空与预分配。

核心取舍是"身份与位置分离"：`Object` 只暴露 ID 与合法位；`Object_Pool` 内部同时维护 ID 分配器与槽位索引分配器，前者产出对外身份，后者只在内部使用。因此 `std::vector` 扩容搬移、`sort()` 重排、`unload` 交换都不会让外部持有的 ID 失效，而索引从不外泄。

池按值拥有对象：`objects` 是 `std::vector<T>`，构造、析构、就地重建都由池完成，不持指针、不管外部 `new`。对 `T` 的显式约束仅为公有派生自 `Object`；隐式要求见 [§三 3.4.1](#341-模板声明与约束)。

有效性不是靠容器大小推断，而由 `is_valid` 位维护。无效对象不从向量删除，而是集中到前段 `[0, min_valid_index)`；有效对象集中在 `[min_valid_index, objects.size())`。该布局让 `begin()/end()` 直接给出有效区间，遍历无需过滤，代价是装载/卸载各可能引入一次元素交换。

两种定位模式：`Unorder` 维护 `unordered_map<Key, uint64_t>` 键→下标，查找平均 O(1)、内存无序；`Sorted` 清空映射、有效区按键有序并走二分查找，查找 O(log n)，但每次装载/卸载后都要全量重排。

不负责：对象业务语义（不调用 `T` 的业务方法，默认只用 `ID()`）、线程同步（全模块无锁无原子）、跨池唯一性（分配器是池内实例）、派生类资源释放（`~Object` 非虚默认）。快照内无任何其他模块包含本运行包或实例化 `Object_Pool`，模块处于"已实现、无内部消费者"状态。

关键约束：投影键在池生命周期内必须唯一。默认投影器取 `ID()`，天然唯一；替换投影器后重复键会导致映射覆盖而对象仍有效，属调用方违约（见 §六 D12）。

## 三、模块公开接口

全部类型位于 `namespace engine`。`Object_Pool` 为头文件内联模板，唯一的 `.cpp` 只做显式实例化。

### 3.1 `engine::Object_Order`

```cpp
enum class Object_Order
{
    Unorder,
    Sorted
};
```

- `Unorder`：哈希定位，`mapping` 生效，对象顺序无业务含义。
- `Sorted`：排序定位，`mapping` 恒空，有效区按键有序。
- 仅是 `mode_set` 的入参标签；真实状态存于私有 `is_sorted`，池不提供模式查询接口。

### 3.2 `engine::Default_Projector`

```cpp
struct Default_Projector
{
    template <typename T>
    uint64_t operator()(const T& object) const;
};
```

- 语义：返回 `object.ID()`，即默认以 ID 为定位键。
- 前置：`T` 有 `const` 成员函数 `ID()`（`Object` 已提供）。
- 失败：无；不检查有效性，无效对象的 `ID()` 为哨兵 0，被当键使用会与哨兵冲突。
- 无状态，池以 `[[no_unique_address]]` 持有，空基类优化下不占空间。

### 3.3 `engine::Object`

私有成员（均为友元可见）：

| 成员 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `object_ID` | `uint64_t` | `0` | 身份编号；0 为非法哨兵 |
| `is_valid` | `bool` | `false` | 合法标记 |

```cpp
template <typename T, typename Projector, typename Key>
    requires std::is_base_of_v<Object, T>
friend class Object_Pool;   // 授权池直接读写上述两成员
```

构造与赋值：

```cpp
Object() = default;                                        // ID=0，valid=false
explicit Object(uint64_t id, bool valid = true) noexcept;  // 显式设置，不做 ID 合法性检查
Object(const Object&) = default;                           // 拷贝构造
Object& operator=(const Object&) = default;                // 拷贝赋值
Object(Object&& other) noexcept;                           // 移动：接管两字段，源置 0/false
Object& operator=(Object&& other) noexcept;                // 移动赋值：带自赋值保护
~Object() = default;                                       // 非虚
```

查询：

```cpp
uint64_t ID(void) const;    // 身份编号
bool valid(void) const;     // 合法标记
```

- 两接口无 `noexcept`、无副作用、无失败路径；是池外唯一可观测的状态出口。
- 析构非虚（源码注释：避免虚表开销），故 `Object` 不可作多态基类：经 `Object*` 删除派生对象为 UB。
- 带参构造在池内从未被调用，池以友元权限直接写字段。

### 3.4 `engine::Object_Pool`

#### 3.4.1 模板声明与约束

```cpp
template <typename T, typename Projector = Default_Projector,
    typename Key = std::invoke_result_t<Projector, const T&>>
    requires std::is_base_of_v<Object, T>
class Object_Pool;
```

- `T` 必须公有派生自 `Object`（约束在类模板与友元声明两处重复书写，保证同一实体）。
- `Key` 由 `Projector` 对 `const T&` 的结果推导；默认投影器下为 `uint64_t`，可显式指定第三参数覆盖。
- 隐式要求（未以 `requires` 表达）：`T` 可默认构造、可移动构造、可析构；`Key` 可哈希、可相等比较；`Key` 可被 `std::format` 格式化（`unload` 告警使用 `"{}"`）。

#### 3.4.2 构造与析构

```cpp
Object_Pool();     // 无 noexcept
~Object_Pool();    // 空体，非虚
```

构造顺序：两个分配器均设 `Allocate_Order::LIFO`；`ID_allocator.set(min_ID)`（`min_ID = 1`，0 永久留给非法对象）；`index_allocator.set(0)`。

析构为空体：成员逆序销毁，`mapping`、`objects`、分配器自行释放，不额外回收编号。

#### 3.4.3 排列模式设置

```cpp
template <typename Compare = std::ranges::less>
    requires std::same_as<Compare, std::ranges::less> ||
             std::same_as<Compare, std::ranges::greater>
void mode_set(Object_Order mode, Compare cmp = {});
```

分支：

1. `Unorder` 且当前为 `Sorted`：置 `is_sorted = false`；遍历全部槽位，对 `valid()` 为真者 `mapping.insert({projector(obj), 绝对下标})`；`compare` 重置为 `std::ranges::less()`。注意用 `insert` 而非 `insert_or_assign`。
2. `Sorted`：若当前非排序模式，先置 `is_sorted = true` 并 `mapping.clear()`；随后无论是否已排序，都记录 `compare = cmp` 并 `sort()`。
3. 其余（`Unorder` 且已哈希模式）：仅 `logger.warn("Object_Pool::当前已为目标模式")`。

- 语义：模式切换是结构重建，非增量维护。
- 前置：调用时不应有外部持有的元素迭代器/引用（排序会搬移值）。
- 告警：重复设 `Unorder` 告警；重复设 `Sorted` 不告警但仍重排（§六 D6）。
- `Compare` 仅接受 `less` 与 `greater`，其余编译期拒绝。

#### 3.4.4 对象查找

```cpp
typename std::vector<T>::iterator       find(const Key& key);
typename std::vector<T>::const_iterator find(const Key& key) const;
```

- 哈希模式：`mapping.find(key)`，命中 `objects.begin() + it->second`，未命中 `objects.end()`。
- 排序模式：`detail::binary_search(begin(), end(), key, compare, projector)`；返回偏移相对 `begin()`（有效区首），故命中为 `begin() + offset`，未命中 `end()`。
- 返回值必在 `[begin(), end())` 或恰为 `end()`；解引用前须比较。
- 复杂度：哈希平均 O(1)；二分 O(log n)，前提是有效区确实有序（由 `mode_set`/`build`/`unload` 末尾的 `sort()` 保证）。
- 常量重载经 `const_cast` 转发非常量重载。未命中不写日志、不抛异常。

#### 3.4.5 对象装载

```cpp
uint64_t build(T object = {});
std::vector<uint64_t> build(std::vector<T> object_set);
```

单对象重载：把入参 `std::move` 进单元素 `std::vector<T>`，调多对象重载，取 `front()`（必非空）。

多对象重载，逐个对象：

1. `index_allocator.get()` 得 `object_index`。
2. `object_index >= objects.size()` 时 `objects.push_back(std::move(...))`。
3. 否则 `std::destroy_at(&objects[object_index])` 后 `std::construct_at(&objects[object_index], std::move(...))` 就地重建。
4. `min_valid_index > 0` 时 `std::swap(objects[object_index], objects[--min_valid_index])`，无效区收缩一格，`object_index` 更新为 `min_valid_index`。
5. 取 `auto& new_object = objects[object_index]`，`object_ID = ID_allocator.get()`，ID 入缓冲。
6. `is_valid = true`。
7. 哈希模式 `mapping.insert_or_assign(projector(new_object), object_index)`。
8. 批次结束，若 `is_sorted` 则调用一次 `sort()`。

- 返回：与入参顺序一一对应的 ID 集合（非槽位顺序）。
- 失败/告警：无失败路径、无错误码；异常仅来自 `T` 的移动构造或向量分配（§六 D8）。

#### 3.4.6 对象排序

```cpp
bool sort(void);
```

- 非排序模式返回 `false` 且不操作；排序模式执行 `std::ranges::sort(begin(), end(), compare, projector)` 并返回 `true`。
- 只排有效区，无效区不动；有效区元素按值搬移，先前索引/迭代器/引用全部失效。
- 前置：无外部持有的元素引用。

#### 3.4.7 对象卸载

```cpp
void unload(const Key& key);
void unload(const std::vector<Key>& keys);
```

单对象重载包装为 `std::vector<Key>{key}`（`Key` 需可拷贝）。

多对象重载顺序：

1. `std::unordered_set<Key> removed_keys` 入参去重，重复键 `continue`。
2. 每键 `find(key)`，未命中 `logger.warn("Object_Pool::目标对象不存在: {}", key)` 并跳过。
3. 命中记录 `Object_Record{it->ID(), static_cast<uint64_t>(it - objects.begin())}`。
4. 哈希模式立即 `mapping.erase(key)`（用入参键）。
5. 收齐后按 `index` 升序排序。
6. 逐条回收：回收 ID → 写哨兵 ID → 置非法 → 必要时与 `min_valid_index` 交换并修正被换出对象映射 → 回收边界索引 → `min_valid_index++`（顺序依赖见 §六 D5）。
7. 若 `is_sorted` 则 `sort()`。

- 返回 `void`：无失败信号，缺失键只告警。
- 前置：不得在遍历中调用；`Key` 可格式化。
- 副作用：对象进入 `ID=0、valid=false` 哨兵态；ID 与索引分别进入两条 LIFO 回收栈；有效区前移；排序模式重排。

#### 3.4.8 对象清除

```cpp
void clear(void);
```

- 执行 `objects.clear()`；两分配器 `reset()` 后重设 LIFO 与起点（`min_ID` / `0`）；`min_valid_index = 0`；哈希模式 `mapping.clear()`。
- 不重置 `is_sorted` 与 `compare`，池保持原模式与比较方向。
- 不释放向量堆内存；`capacity()` 返回 `objects.size()`，故清除后报 0。
- 清除后所有旧 ID 作废，后续装载从 1 重新分配，可能与旧 ID 重复。

#### 3.4.9 槽位预分配

```cpp
bool reserve(const uint64_t& num);
```

- 池非空立即返回 `false`，不做事。
- 空池时循环 `num` 次 `objects.push_back({})`，写 `object_ID = min_ID - 1`（0）、`is_valid = false`；`min_valid_index = num`；返回 `true`。
- 不推进 `index_allocator`：首次 `build` 仍从索引 0 走"就地重建 + 交换"。
- 前置：`T` 可默认构造；`num` 无上限校验；非空池无日志。

#### 3.4.10 容量与数量

```cpp
uint64_t capacity(void) const;   // objects.size()，历史高水位
uint64_t size(void) const;       // ID_allocator.counts()，在用对象数
```

- `capacity()` 含无效占位，只由 `build`/`reserve` 推进，`unload` 不降低，`clear` 归零。
- `size()` 每次 ID `get` 加一、`recycle` 减一。
- 恒等式（未回绕时）：`size() + min_valid_index == capacity()`。

#### 3.4.11 迭代器

```cpp
typename std::vector<T>::iterator       begin(void);          // objects.begin()+min_valid_index
typename std::vector<T>::const_iterator begin(void) const;
typename std::vector<T>::iterator       end(void);            // objects.end()
typename std::vector<T>::const_iterator end(void) const;
```

- `[begin(), end())` 恰为全部有效对象；空池时两者相等。
- 常量重载经 `const_cast` 转发。
- `build`、`unload`、`sort`、`clear`、`mode_set`、`reserve` 及向量扩容后，全部迭代器/引用/指针失效。

## 四、模块私有方法

无自由函数与匿名命名空间；内部逻辑在私有嵌套类型与头文件内联函数体中。

### 4.1 私有嵌套类 `Object_Pool::Comparator`

```cpp
class Comparator
{
    std::variant<std::ranges::less, std::ranges::greater> v;
public:
    Comparator() = default;
    Comparator(std::ranges::less l) : v(l) {}
    Comparator(std::ranges::greater g) : v(g) {}

    template <typename A, typename B>
    bool operator()(A&& a, B&& b) const;
};
```

- 职责：把运行期"升序/降序"选择装成可调用对象，供 `std::ranges::sort` 与 `detail::binary_search` 共用。
- 默认构造落在 `variant` 第 0 备选，即 `less`（默认升序）。
- `operator()` 用 `std::visit` 取实际比较器并完美转发；每次比较一次 `variant` 分派。
- 无状态、无日志、无异常。

### 4.2 私有嵌套结构 `Object_Pool::Object_Record`

```cpp
struct Object_Record
{
    uint64_t ID = 0;      // 待卸载对象身份
    uint64_t index = 0;   // 在 objects 中的绝对下标
};
```

- 职责：在卸载"收集阶段"与"回收阶段"间传递最小快照，不持引用/迭代器，避免后续搬移影响。
- 取值时点为收集阶段（未发生任何交换），与当时槽位严格对应。

### 4.3 内联实现单元：就地重建与无效区交换

无独立函数，散在 `build`/`unload`/`reserve` 体内，是维护"无效区前置"的唯一手段：

- 就地重建：`std::destroy_at` + `std::construct_at` 复用已有槽位，避免尾部增长。
- 无效区收缩（`build`）：`std::swap(objects[object_index], objects[--min_valid_index])`。
- 无效区扩张（`unload`）：`std::swap(objects[record.index], objects[min_valid_index])`。
- 哨兵化：以友元身份直写 `object_ID = min_ID - 1`、`is_valid = false`，不调用 `Object` 成员函数。

### 4.4 内联实现单元：常量转发桥

`find(const Key&) const` 与 `begin(void) const` 用 `const_cast<Object_Pool*>(this)` 转发非常量重载，避免重复实现。流转中不写状态，故无 UB，但绕过了 `const` 契约表达（§六 D18）。

### 4.5 显式实例化单元 `对象池实例化.cpp`

```cpp
#include "src/object/Object_Pool/对象池.h"

namespace engine
{
    template class Object_Pool<Object>;
}
```

- 为 `Object_Pool<Object>`（`Default_Projector`、`Key = uint64_t`）生成实体，落入 `EngineFoundation.lib`。
- 包含用层根相对 `src/...`，符合 `.cpp` 约定。
- 不定义新接口；其他 `T` 组合由使用方隐式实例化，故实现必须全部在头文件。

## 五、模块内部架构

### 5.1 文件分工

```
对象系统运行包.h（聚合入口，无代码）
  ├─ Object/对象.h          → engine::Object
  └─ Object_Pool/对象池.h   → engine::Object_Pool<T, Projector, Key>
        └─ core/对象池实例化.cpp
              └─ template class Object_Pool<Object>;
```

- `对象.h` 只定义类型与前向声明（`class Object;`、`Object_Pool` 模板），使友元声明的参数名与后续定义一致。
- `对象池.h` 承载全部实现。
- `.cpp` 只落地模板符号；运行包只做包含。

### 5.2 包含关系与耦合边界

```
对象池.h
 ├─ Engine/EngineFoundation/common/前置头文件包含.h          标准库预编译头
 ├─ Engine/EngineFoundation/src/object/Object/对象.h         源码写作 ../Object/对象.h
 ├─ Engine/EngineFoundation/src/detail/class/Number_Pool/数值分配器.h
 │     └─ Engine/EngineFoundation/src/log/日志系统运行包.h   间接引入 inline Log logger
 └─ Engine/EngineFoundation/src/detail/methods/二分查找.h
```

- 对外耦合三项：`Number_Pool<uint64_t>`（ID/索引分配）、`detail::binary_search`（排序模式查找）、`engine::logger`（三处告警）；均单向依赖。
- `logger` 由 `数值分配器.h` 传递引入，本文件未直接包含（§六 D15）。
- 无反向依赖，不含任何上层头文件。

### 5.3 数据布局与不变量

```
下标   0                    min_valid_index              objects.size()
       |<---- 无效区 ------>|<-------- 有效区 ---------->|
objects[  占位/已卸载       ][       在用对象值          ]
       is_valid=false        is_valid=true
       object_ID=0           object_ID 为正常分配所得
```

不变量：

1. 无效区对象一律 `is_valid == false`，有效区一律 `true`。
2. `size() + min_valid_index == objects.size()`（ID 未回绕时）。
3. 哈希模式：映射键集合等于有效对象投影键集合，值为绝对下标。
4. 排序模式：映射恒空，有效区严格有序。
5. 无效区对象 `object_ID` 恒为 0（卸载先哨兵化再交换，故成立）。

### 5.4 所有权与生命周期

- 池拥有对象值：元素由池构造/析构，外部只能借用引用，不得跨调用保存。
- 池拥有键副本：映射键是投影结果拷贝，不引用对象内部数据；对象内容变动不会刷新映射。
- 分配器各持回收 `deque` 与去重 `unordered_set`，随池析构。
- 对象生命周期：`reserve` 占位从创建即非法；`build` 生成的对象有效至 `unload`/`clear`；`clear` 统一析构。
- 外部只持 ID；对象卸载后 ID 进入回收栈，可能被新对象复用，"ID 仍指向旧对象"不成立。

### 5.5 线程归属

无 `mutex`、`atomic`、`thread_local`，全部状态为普通成员，故非线程安全；所有不变量都要求"读-改-写"原子。按分层约定推测由单线程（主循环）独占，但快照内无使用方可佐证（§六 D13）。

## 六、模块设计 / 实现细节

### D1 身份与位置分离

- ID：对外身份，起点 `min_ID = 1`，卸载回收、装载复用，不随槽位搬移改变。
- index：内部槽位下标，起点 0，回收复用，随交换/排序变化，绝不出现在接口参数或返回值中。
- 收益：向量扩容、排序、交换都不影响外部句柄；代价是内部定位需 `begin() + index` 或映射重算，O(1)。
- 两套编号各自入栈，回收栈独立，因此"ID 与索引同序"不成立（D7）。

### D2 无效区前置

- "删除"实现为"移到前段 + 置非法 + 回收索引"，而非 `vector::erase`：后者 O(n) 且使全部索引失效，前者 O(1) 且只影响两个槽位。
- 有效区连续，`begin()/end()` 可直接暴露有效区间；`min_valid_index` 一个变量即可描述边界，`clear`/`reserve` 只需重置它。
- 代价：装载/卸载各可能引入一次交换（无效区长度为 0 时 `build` 跳过交换，`unload` 命中边界时也跳过），这正是 D4、D5 顺序链的根源。

### D3 容量扩张

- 仅 `build` 的新槽位路径与 `reserve` 扩大 `objects`，均为逐元素 `push_back`；无 `resize`、无倍数预留、无 `reserve` 调用。
- 路径由 `get()` 返回的索引决定：`>= objects.size()` 走 `push_back`，否则就地重建。无 `reserve` 预分配时回收队列为空等价于 `next_number == objects.size()`，故取新槽位；`reserve` 后 `next_number` 落在已有占位槽内，则先走就地重建，直到 `next_number` 追上 `size` 才重新 `push_back`。回收队列非空时返回的索引必 `< min_valid_index < size`，必定就地重建。
- `push_back` 重分配使元素地址全变；应对方式是把映射值存为下标而非迭代器（该设计成立的关键）。
- `reserve(num)` 是唯一避免多次扩容的手段，但仅对空池生效，且不推进 `index_allocator`。

### D4 装载顺序依赖

1. 先取索引，再决定构造位置。
2. 先 `push_back` 或 `destroy_at + construct_at`，再写字段：占位槽可能残留已析构对象，直写会落到未构造内存。
3. 交换收缩必须早于取引用：交换会改变新对象实际下标，先取引用会指向被换出的占位对象。
4. 交换后重新取 `objects[object_index]`，此时 `object_index` 已更新。
5. ID 分配在取引用之后：`get()` 有副作用（推进 `next_number` 或弹栈、计数加一）。
6. `is_valid = true` 早于映射写入，避免中间态被观察到。
7. 映射写入必须在槽位最终确定之后。
8. `sort()` 整批只调一次：逐对象排序会把代价从 O(n log n) 放大到 O(k n log n)。

### D5 卸载顺序依赖

四段：收集 → 排序 → 回收 → 重排。

收集阶段（不改容器顺序）：

- 先入参去重：否则重复键第二次 `find` 可能命中已被搬走的对象或直接未命中。
- 立即记录 `{ID, 绝对下标}`：后续交换会让下标漂移。
- 哈希模式在此阶段 `erase(key)`：此时键与对象一一对应尚未被破坏；若延后，同键可能已属于被换入的有效对象，导致误删。

排序阶段：按 `index` 升序 `std::ranges::sort(records, std::ranges::less(), &Object_Record::index)`，不是可选项：

- 回收时交换目标恒为 `min_valid_index`，且每处理一条加一；
- 升序保证 `record.index >= min_valid_index`，交换只写当前记录对应槽位，不破坏未处理记录；
- 也保证被换出的边界有效对象落在后续记录之前，不会被误当目标；
- 乱序（先大后小）会让后处理的小下标已被前一次交换改写成别的对象，导致卸载错对象、ID 与槽位错配。

回收阶段每条记录：

1. `ID_allocator.recycle(record.ID)`：ID 来自快照，与槽位无关，先回收不影响后续判断。
2. `object.object_ID = min_ID - 1`（哨兵 0）。
3. `object.is_valid = false`。
4. `record.index != min_valid_index` 时交换，并在哈希模式修被换出对象的映射（此时 `object` 引用已指向换入的有效对象）。
5. `index_allocator.recycle(min_valid_index)`：回收交换后的边界槽位。若改用 `record.index`，会把仍在用的槽位登记为空闲，后续装载覆盖在用对象。
6. `min_valid_index++`。

不可颠倒的三处：ID 用 `record.ID` 而索引用 `min_valid_index`；哨兵化必须早于交换，否则被换出的有效对象会被一并置非法；映射修正在交换之后。

### D6 双模式取舍

- `Unorder`：装载/卸载仅 O(1) 映射更新，查找平均 O(1)；代价是多一张哈希表的内存与哈希开销。
- `Sorted`：不维护映射，省内存；查找 O(log n)；但每次 `build`/`unload` 末尾全量排序，写代价显著更高。
- 切换成本：`Unorder → Sorted` 清表 + 全量排序；`Sorted → Unorder` 全槽位遍历重建映射（O(n) 哈希插入）。
- 一致性缺口：`Unorder` 重复设置只告警不重建；`Sorted` 重复设置不告警但**仍重新排序**，两种"重复设置"处理不对称（待确认 7）。
- 比较器用 `variant` 承载，每次比较一次 `visit` 分派，是为运行期切升降序付出的常数开销。
- 排序模式下 `unload` 跳过两处映射操作，依赖"排序模式映射恒空"；该不变量由 `mode_set(Sorted)` 的 `mapping.clear()` 建立，`clear()` 在排序模式下则跳过 `mapping.clear()`。

### D7 编号复用次序

- 两分配器均 LIFO：`recycle` 把数值 `push_back` 进回收 `deque`，`get` 取 `back()`，即最近回收者最先复用（`FIFO` 则取 `front()`）。
- 结果：`build` 返回的 ID 呈"回填"特征，不单调递增。
- ID 与索引入栈时点不同（索引来自卸载时的边界值），数值对应关系被打乱，禁止"用 ID 推索引"。
- 回绕：底层 `get()` 在 `next_number == max` 时告警并回绕到 `numeric_limits::min()`（0），`set(min_ID = 1)` 只影响起点。`uint64_t` 下不可达；若发生会分配出哨兵 0 并使计数失真（待确认 5）。

### D8 内存与异常策略

- 模块内无 `new`/`delete`：槽位内存由 `std::vector` 分配器管理，元素构造/析构经 `push_back`、`destroy_at`、`construct_at`。
- 故未出现 `std::nothrow`。本层其他模块普遍写 `new(std::nothrow)`（如 `Stream_Tree/流节点树.h`、`Quadtree/core/节点创建与树扩大.hpp`、`Event_Terminal/终端端口.h`），对象池却把异常交给标准库，口径不一致（待确认 3）。
- `destroy_at` + `construct_at` 无强异常保证：`T` 移动构造若抛出，槽位已析构未重建，`objects` 出现"未构造槽位"，后续访问 UB；此时索引已取出、ID 未分配、映射未写入，状态不可恢复。源码无 `static_assert(std::is_nothrow_move_constructible_v<T>)`，也无回滚。推测依赖调用方保证 `T` 移动为 `noexcept`。
- `Object` 移动构造/赋值均 `noexcept` 且清零源；向量扩容依赖 `T` 的移动转发基类，否则扩容后 ID 丢失（变为 0/false）。
- 除 `reserve`（`bool` 表达"非空池"）与 `sort`（`bool` 表达"非排序模式"）外，无失败返回、无错误码、无异常捕获。

### D9 `Object` 的值语义与非虚析构

- 两个标量成员，池按值存储，要求 `T` 可拷贝或可移动（`build` 传值入参、`push_back` 需移动）。
- 带参构造在池内从未调用（池直写字段），仅服务池外独立构造。
- 非虚析构是明确决策；风险在于"经 `Object*` 删除派生对象为 UB"，当前无使用者，风险潜伏（待确认 10）。
- `valid()` 与池内 `is_valid` 是同一数据，无二重状态；对象卸载后仍留在无效区直到复用或 `clear`。

### D10 迭代器与失效

- `begin()/end()` 只覆盖有效区，遍历看不到非法对象，也无法枚举无效槽位。
- `build`、`unload`、`sort`、`clear`、`mode_set`、`reserve` 及扩容后全部失效。
- `find` 返回的迭代器仅"下次修改前"有效，池不提供句柄版本或稳定性检查。
- 不支持遍历中卸载：会搬移元素并移动边界。正确用法是先收集键，再一次性 `unload(keys)`（其内部的快照与升序正为此设计）。

### D11 扩容与缩容不对称

- `capacity()` 是历史高水位，`objects` 从不缩小；`unload` 只抬高 `min_valid_index`。
- `clear()` 析构元素但不归还堆内存，而 `capacity()` 返回 `objects.size()`，故"内存仍占、对外报 0"。
- 锯齿负载下向量保留峰值容量，`min_valid_index` 在 0 与峰值间往复；没有收缩接口。

### D12 投影键唯一性未校验

- 装载用 `insert_or_assign`（后写覆盖）；`mode_set(Unorder)` 重建用 `insert`（先出现者保留）。两处策略相反。
- 重复键时两个对象都有效、`size()` 计 2，但 `find` 只命中一个，另一个成为"不可达但仍占槽位"的孤儿。
- 同一池"装载重复键 → 切排序 → 切回哈希"前后，命中结果可能不同。
- 默认投影器用 ID，天然唯一；替换投影器后约束落在调用方，接口不检测、不告警（待确认 4）。

### D13 线程与并发

- 无锁、无原子；`logger` 为 `inline Log` 全局单例，本模块只被动调用 `warn`。
- 全部不变量要求"读-改-写"原子，并发访问必然破坏结构。
- `find` 的常量重载经 `const_cast` 转发，写线程并行时读路径同样不安全。
- 快照内无消费者，无法从调用方确认线程归属（待确认 9）。

### D14 日志与告警面

| 位置 | 条件 | 消息 |
| --- | --- | --- |
| `mode_set` 的 `else` | `Unorder` 且已是哈希模式 | `Object_Pool::当前已为目标模式` |
| `unload` 收集阶段 | `find(key)` 未命中 | `Object_Pool::目标对象不存在: {}` |
| 底层 `Number_Pool::recycle` | 重复回收同一数值 | `Number_Pool::待回收数值已被回收!!!` |

- 无 `error` 级日志、无异常抛出；失败通过 `bool` 或静默跳过表达。
- 第二条把 `Key` 送入 `std::format` 占位符，故 `Key` 必须可格式化，头文件未声明该要求（待确认 9）。

### D15 包含与编译单元约定

- 本层约定：头文件跨目录写项目根全路径 `Engine/EngineFoundation/...`；`.cpp` 写层根相对 `src/...`（见 `Engine/EngineFoundation/CMakeLists.txt` 第 4 节的包含根说明）。
- `对象池实例化.cpp` 用 `"src/object/Object_Pool/对象池.h"`，符合 `.cpp` 约定。
- `对象池.h` 对同模块对象用 `"../Object/对象.h"`，不符合头文件约定；当前能编译，但头快照/安装产物层级变化时相对基准会变（待确认 2）。
- `logger` 经 `数值分配器.h` 传递引入，未直接包含；若该依赖移除，本文件将因未声明 `logger` 而编译失败（待确认 1）。
- 项目根 `README.md` 记录本模块路径为 `Engine/EngineFoundation/src/core/object/`、数值分配器为 `src/tools/Number_Allocator/`，与快照实际的 `src/object/`、`src/detail/class/Number_Pool/` 不符（待确认 6）。

### D16 模板实例化边界

- 实现全在头文件，唯一 `.cpp` 只做 `template class Object_Pool<Object>;`。
- 其他 `T` 组合在使用方 TU 隐式实例化，不进入本层库，故模板必须保持头文件内联。
- `requires` 在类模板与友元声明中必须逐字一致，否则授权失效。
- `Key` 由 `invoke_result_t` 推导；若投影器返回引用，`Key` 为引用类型，`unordered_map` 不接受引用键——此类错误只在实例化时暴露。

### D17 `const` 契约的绕过

`find(...) const`、`begin() const` 以 `const_cast` 转发。逻辑安全（不写状态），但接口层的"不修改"承诺被实现层绕过；若将来引入惰性缓存（如缓存上次查找结果），该转发会在常量对象上构成 UB。当前无缓存，无实际风险（待确认 8）。

## 七、模块运行链路详例

### 链路一：对象装载 → 取用

场景：默认 `Unorder`、默认投影器、空池，装载一个默认构造的 `Object`。

1. `pool.build()` → 单对象重载构造单元素 `vector<T>`，转发多对象重载。
2. 多对象重载（i=0）：`index_allocator.get()` 返回 0（`next_number` 从 0 起）。
3. `0 >= objects.size()(0)` 成立：`objects.push_back(move(object_set[0]))`，`objects.size()` 变 1。
4. `min_valid_index == 0`：跳过交换。
5. `new_object = objects[0]`；`new_object.object_ID = ID_allocator.get()` 得 1（`min_ID` 起点为 1）；ID 入缓冲。
6. `new_object.is_valid = true`。
7. `!is_sorted`：`mapping.insert_or_assign(projector(new_object) = 1, 0)`。
8. 返回 `buffer = [1]`；单对象重载取 `front()`，返回 ID 1。

取用：`pool.find(1)` 走 `mapping.find(1)`，`it->second == 0`，返回 `objects.begin() + 0`；解引用得 `ID() == 1`、`valid() == true`。遍历 `for (it = pool.begin(); it != pool.end(); ++it)` 中 `begin()` 为 `objects.begin() + 0`、`end()` 为 `objects.end()`，只覆盖有效区。

终态：`capacity() == 1`、`size() == 1`、`min_valid_index == 0`、`mapping == {1 → 0}`。返回的 ID（1）与索引（0）不是同一量，调用方只应持 ID。继续装载时第二次走 `index_allocator.get() → 1`、`1 >= size(1)` 的真分支，即 `push_back`。

排序模式对照：`mode_set(Sorted)` 先 `mapping.clear()`、置 `is_sorted = true`、记比较器并 `sort()`（空池无操作）。`build` 前六步相同，第 7 步映射写入被 `!is_sorted` 跳过；批次末尾一次 `sort()` 对 `[begin(), end())` 按 `ID()` 升序重排。`find` 改走 `detail::binary_search(begin(), end(), key, compare, projector)`，返回相对 `begin()` 的偏移，命中取 `begin() + offset`；比较经 `variant` 的 `visit` 分派。此模式下映射恒空。

### 链路二：对象卸载 → 索引回收

场景：哈希模式，ID 1/2/3 位于槽位 0/1/2，`min_valid_index == 0`、`mapping == {1→0, 2→1, 3→2}`、`size() == 3`、`capacity() == 3`。调用 `pool.unload(2)`。

1. 单对象重载包装为 `vector<Key>{2}`，转发多对象重载。
2. 收集：`removed_keys.count(2) == 0` → 插入 2；`find(2)` 走 `mapping.find(2)` 得 1，`it = objects.begin() + 1`，命中。
3. `records.push_back({2, 1})`；`mapping.erase(2)`，映射变 `{1→0, 3→2}`。
4. 排序：单条记录，`sort` 无实际改动。
5. 回收（`record = {ID=2, index=1}`，`min_valid_index == 0`）：
   - `ID_allocator.recycle(2)`：ID 回收栈 `[2]`，计数 3→2；
   - `objects[1].object_ID = 0`、`is_valid = false`；
   - `record.index(1) != min_valid_index(0)`：`swap(objects[1], objects[0])`，`objects[0]` 变为哨兵对象、`objects[1]` 变为原 ID 1 有效对象；
   - 哈希模式：`mapping.insert_or_assign(projector(objects[1]) = 1, 1)`，映射修为 `{1→1, 3→2}`；
   - `index_allocator.recycle(0)`：索引回收栈 `[0]`；
   - `min_valid_index++` → 1。
6. `!is_sorted`：不调用 `sort()`。

终态：有效区 `[1, 3)` 为 `objects[1]`（ID 1）与 `objects[2]`（ID 3）；`objects[0]` 为哨兵；`capacity() == 3`、`size() == 2`、`min_valid_index == 1`；ID 回收栈 `[2]`、索引回收栈 `[0]`；`find(2)` 未命中，返回 `objects.end()`。

随后一次 `pool.build()`（复用验证）：

1. `index_allocator.get()` LIFO 返回 0；`0 < objects.size()(3)`，走就地重建。
2. `destroy_at(objects[0])` + `construct_at(objects[0], move(新对象))`。
3. `min_valid_index == 1 > 0`：`swap(objects[0], objects[--min_valid_index = 0])`，即自交换（0 == 0），`min_valid_index` 回到 0。
4. `object_ID = ID_allocator.get()` LIFO 返回 2（最近回收先复用）；`is_valid = true`；`mapping.insert_or_assign(2, 0)`。

终态：槽位 0 与 ID 2 双双复用，`capacity()` 仍为 3，`size()` 回 3。

要点：

- 卸载不缩小容量，只抬高 `min_valid_index`；槽位由索引分配器回收，不从向量删除。
- ID 用 `record.ID` 回收，索引用交换后的 `min_valid_index` 回收，二者独立排队。
- 映射擦除在收集阶段（交换前），映射修正在交换后；顺序颠倒会误删被换入对象的映射。
- 若批量卸载 `{1, 3}`，升序处理保证第一次交换写入的是当前记录槽位、第二次的目标仍在原位；乱序则可能出现下标已被改写的情况。
- 排序模式对照：哨兵化、交换、索引回收相同，两处映射操作被跳过；末尾改为 `sort()` 对有效区重排，故 `records` 的下标必须在 `sort()` 前用完——实现正是先逐条回收再排序。
