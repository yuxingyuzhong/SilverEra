## 二、模块功能介绍

本模块是 `EngineFoundation` 的“数据入口层”，分成两条互不耦合的业务线：一条是**资产文本 / 二进制解析**（`assets/`），一条是**配置的事件化加载与缓存**（`config/`）。两条线共享同一套底层工具（`src/detail/methods` 中的路径转换、路径校验、文本处理）和同一套日志门面，但相互之间没有任何 include 关系。

**资产解析线负责**：

1. 把 OBJ 文本解析为引擎唯一的 CPU 侧网格数据 `Mesh_Data`（顶点位置 / UV / 法线与索引），并在 `Mesh_File_Data` 中保留 `usemtl` 分段与材质名。
2. 把 MTL 文本解析为 `Mtl_Material` 字段集合（颜色、指数、不透明度、漫反射贴图与法线贴图路径），只保留原始字段，不做贴图解码、不做材质换算。
3. 把 `.gltf`（JSON 文本）与 `.glb`（二进制容器）解析为 `Gltf_Asset`：节点层级、局部变换矩阵、网格 primitive、PBR 材质描述、纹理 / 图像 / 采样器引用、场景根集合与默认场景。
4. 对三类输入统一实施“体量上限 + 数量上限 + 下标合法性 + 路径越界”四类防护，失败时清空输出并返回 `false`，不抛出异常给调用方。

**资产解析线不负责**：

- 不创建任何 GPU 资源、不建立描述符、不提交命令缓冲；三个头文件均自称 Vulkan-free。
- 不解码贴图（MTL 只存路径，glTF 只存 `uri` / `bufferView` / `mimeType`，内嵌图像字节不解码）。
- 不把 MTL 材质与 OBJ 分段做绑定：`Mesh_File_Data::names` 只给出段序号到材质名的映射，实际匹配由调用方完成。
- 不解析 MTL 贴图路径的相对目录（详见 [§六](#六模块设计--实现细节) 与待确认 1）。
- 不合成 glTF 世界变换：`Gltf_Node::matrix` 只是局部变换，父链累乘由调用方完成。
- 不处理 glTF 的动画、蒙皮、形态目标、稀疏访问器、非 TRIANGLES 图元（直接跳过）。

**配置加载线负责**：

1. 以“可信根目录”为信任边界登记 `{路由目录, 配置目录}` 目录对；只有登记过的目录对才允许其路由文件描述配置。
2. 递归扫描路由目录，读取每份路由文件（JSON），按条目把“对象名 + 配置文件相对路径 + 可选投递事件类别 / 标签”登记进内存缓存。
3. 在投递前向事件中转站查询目标对象是否已接入；已接入才读取配置文件并以 `Config/Load`（或条目覆盖的类别 / 标签）事件广播配置内容。
4. 以“运行盐 + 路径哈希”生成两级脏标记（路由文件头标记、路由条目内标记），实现“同一进程内不重复投递、跨进程自动失效”的缓存语义。
5. 在卸载 / 可信根撤销时按目录前缀清除内存缓存，并把路由文件中的脏标记抹除，使同进程内可再次加载重建。

**配置加载线不负责**：

- 不解释配置内容语义：配置 JSON 去掉顶层 `dirty_mark` 后原样作为事件载荷，字段含义由接收对象自行解释。
- 不监听文件系统变更：是否重载完全由事件（`Route/Load`、`Config_File/Load`）与脏标记决定，不做时间戳 / 内容哈希比对。
- 不主动轮询：所有动作由事件触发，`Config_Loader` 没有公开的“每帧更新”入口。
- 不管理接收者生命周期：接收者必须先经事件中转站接入，否则只登记缓存、不投递。

**存在理由与关键约束**：

- 资产线存在的原因是渲染层 / 碰撞层需要同一份 `Mesh_Data` 定义。`网格加载器.h` 明确记录该结构此前在渲染层另有一份同名定义，本轮合并到本层以消除 ODR 隐患；因此本模块是网格数据类型的唯一定义点。
- 配置线存在的原因是让“配置文件 → 目标对象”的路由解耦：配置文件位置、目标对象名、投递事件名都写在数据文件里，新增接收对象不需要改加载器代码。
- 约束一：所有资产加载失败必须保持输出为空（先清空再工作），调用方据返回值判断，不依赖部分结果。
- 约束二：文件路径字符串一律按 UTF-8 解释，经 `detail::string_to_path` 转为 `std::filesystem::path`；反向输出经 `detail::path_to_string`。
- 约束三：第三方类型（`tinygltf::*`）不得越过 `Gltf_Loader` 边界；公开头只暴露引擎自有类型。
- 约束四：配置路径必须通过“无 `..` + 位于指定配置目录前缀内 + 实际存在且为普通文件”三重检查，才允许读取。

## 三、模块公开接口

本节先列三类资产加载器的公开类型与门面，再列 `Config_Content` / `Config_Loader` 的公开门面，最后单列配置加载器的路由读写、脏标记与缓存 API（这些成员在类内为 `private`，但属于本模块的事件驱动内部契约，签名按头文件原样给出）。

### 3.1 网格数据类型（`网格加载器.h`，`namespace engine`）

#### 3.1.1 `struct Vertex`

| 字段 | 类型 | 缺省 | 语义 |
| --- | --- | --- | --- |
| `position` | `float[3]` | 未初始化（聚合初始化时为零） | 位置 xyz |
| `uv` | `float[2]` | 未初始化（聚合初始化时为零） | 纹理坐标 uv |
| `normal` | `float[3]` | `{0,0,0}` | 法线；零向量表示“未提供”，由解析器补全 |

头文件注释声明步长 32 字节（3+2+3 个 float），与渲染层着色器顶点输入一致。

#### 3.1.2 `struct Mesh_Section`

| 字段 | 类型 | 缺省 | 语义 |
| --- | --- | --- | --- |
| `first_index` | `uint32_t` | `0` | 段在索引区内的起始下标（以 `uint32_t` 元素计，相对索引区起点） |
| `index_count` | `uint32_t` | `0` | 段索引数，须为 3 的倍数 |
| `material` | `uint32_t` | `0` | 材质槽；越界时绘制入口回落 0（由调用方解释） |

#### 3.1.3 `struct Mesh_Data`

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `vertices` | `std::vector<Vertex>` | 顶点集合 |
| `indices` | `std::vector<uint32_t>` | 索引集合 |

#### 3.1.4 `struct Mesh_File_Data`

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `data` | `Mesh_Data` | 顶点与索引 |
| `sections` | `std::vector<Mesh_Section>` | 按 `usemtl` 分组的子网格段；至少一段，未分材质时只有一段 `material = 0` |
| `names` | `std::vector<std::string>` | 段序号对应的材质名；空串表示该文件未分材质 |

#### 3.1.5 `class Mesh_Loader`

```cpp
static bool load_obj(const std::string& mesh_path, Mesh_Data& receiver);
static bool load_file(const std::string& mesh_path, Mesh_File_Data& receiver);
```

- 两个函数均为 `public static`，无实例状态。
- `load_obj`：只取顶点与索引，内部调用 `load_file` 后丢弃分段信息。
- `load_file`：取完整结果（含 `usemtl` 分段与材质名）。
- 两者对同一文件解析出的顶点 / 索引逐字节一致（头文件声明；实现即 `load_obj` 复用 `load_file`）。
- 前置条件：`mesh_path` 为非空 UTF-8 路径字符串；相对路径按进程当前工作目录解释。
- 失败行为：返回 `false`；`receiver` 在任何失败路径上保持空（`load_file` 入口先清空，成功路径整体 `move`；`load_obj` 入口先清空）。
- 不抛异常（文件流与解析均为错误码 / 返回值风格）。

### 3.2 材质数据类型与加载器（`材质加载器.h`，`namespace engine`）

#### 3.2.1 `struct Mtl_Material`

| 字段 | 类型 | 缺省 | 语义 |
| --- | --- | --- | --- |
| `name` | `std::string` | 空 | 材质名，对应 OBJ 的 `usemtl` |
| `diffuse` | `float[3]` | `{1,1,1}` | `Kd` 漫反射颜色 |
| `specular` | `float[3]` | `{0,0,0}` | `Ks` 镜面颜色 |
| `emissive` | `float[3]` | `{0,0,0}` | `Ke` 自发光颜色 |
| `shininess` | `float` | `0.0f` | `Ns` 镜面指数，钳制到 0..1000 |
| `opacity` | `float` | `1.0f` | `d` 不透明度；`Tr` 按 `1 - Tr` 换算 |
| `diffuse_map` | `std::string` | 空 | `map_Kd` 路径，原样保留 |
| `normal_map` | `std::string` | 空 | `map_Bump` / `map_bump` / `bump` / `norm` 路径，原样保留 |

#### 3.2.2 `class Mtl_Loader`

```cpp
static bool load_file(const std::string& mtl_path, std::vector<Mtl_Material>& receiver);
```

- `public static`。
- 前置条件：`mtl_path` 非空 UTC-8 路径字符串。
- 支持的标签：`newmtl` / `Kd` / `Ks` / `Ke` / `Ns` / `d` / `Tr` / `map_Kd` / `map_Bump` / `map_bump` / `bump` / `norm`；其余行忽略。
- 失败行为：返回 `false` 并清空 `receiver`。触发条件包括：路径为空、文件不可读、文件体量为 0 或超过 16 MiB、打开失败、材质数量超过 4096、整份文件没有任何 `newmtl`。
- 部分成功写入后失败的路径（材质超限）会显式 `receiver.clear()`，再返回 `false`。

#### 3.3.10 `class Gltf_Loader`

```cpp
static bool load_file(const std::string& gltf_path, Gltf_Asset& receiver);
```

- `public static`。
- 解析范围：静态子集，仅 `.gltf`（JSON）与 `.glb`（二进制）两种容器，按文件头 4 字节魔数 `glTF` 分流。
- 前置条件：`gltf_path` 为非空 UTF-8 路径字符串。
- 失败行为：返回 `false` 且 `receiver` 为空。头文件列出四类失败：路径不可读、体量超限、JSON 非法、accessor 越界；实现中还包括：路径为空、空文件、外部 buffer 读取失败、模型转换失败、各类集合 / 下标 / 层级非法。
- 解析告警（tinygltf 的 `parse_warning`）只写日志，不阻断成功。

### 3.5 `class Config_Loader` 公开门面

| 成员 | 签名 | 语义 |
| --- | --- | --- |
| `event_terminal` | `Event_Terminal event_terminal`（`public` 数据成员） | 本模块事件终端；提供 `->` 快捷通道到 `Terminal_Port`，并提供 `build` / `attach` / `send` / `receive` / `query` / `clear` / `key` |
| 构造函数 | `Config_Loader()` | 调用 `event_terminal.key()` 生成权限密钥并保存到私有 `acl_key`；若 `key()` 无值则 `.value()` 会抛异常（实现未见保护） |
| 析构函数 | `~Config_Loader() = default` | 默认析构；不做事件中转站注销 |
| 事件接入 | `void attach(void)` | 绑定接收入口、接入中转站、发送订阅清单；失败只写日志 |

`attach()` 的具体步骤（实现事实）：

1. `event_terminal->bind(Port_ID::Evt_Receiver, [this](shared_ptr<Event> evt){ event_process(evt); })`。
2. `event_terminal->check(Port_ID::Evt_Receiver)` 校验绑定；失败则 `logger.error` 并返回。
3. `event_terminal.attach("Config_Loader", acl_key)`；失败只写日志。
4. 由 `reserved_events_get()` 生成订阅清单，逐条写入 `{category, tag}`。
5. `event_terminal.build("", "", event_protocol::subscribed_events, event_protocol::add)` 构造订阅事件；载荷写入 `object = "Config_Loader"`、`acl_key`、`subscribed_events`。
6. `event_terminal.send(attach_evt, acl_key)`；失败只写日志。

`attach()` 没有返回值，调用方无法从接口判断接入是否完成；这是本模块事件是否生效的唯一开关。

#### 3.7.1 缓存成员

| 成员 | 类型 | 语义 |
| --- | --- | --- |
| `believed_roots` | `std::unordered_set<Config_Content>` | 已登记的可信根目录对集合 |

#### 3.7.2 路由文件读写

```cpp
void route_file_read(const std::filesystem::path& file_path,
                     nlohmann::json& mark,
                     nlohmann::json& entries) const;

bool route_file_write(const std::filesystem::path& file_path,
                      const nlohmann::json& mark,
                      const nlohmann::json& entries) const;
```

- `route_file_read`：读取 JSON；若非对象则 `entries = null`；`mark` 取顶层 `dirty_mark`（仅当 `field_check<json>` 通过）；`entries` 取顶层 `config_routes`，缺失或无效时为 `null`。失败只写日志，不返回状态。
- `route_file_write`：组装对象；`mark` 非 `null` 才写顶层 `dirty_mark`；始终写 `config_routes`；以 `dump(4)` 写出。返回文件是否成功打开并写出。
- 语义约定：`mark` 传 `null` 表示有意抹除文件头标记（卸载路径使用）。

#### 3.7.3 脏标记

```cpp
static uint64_t run_salt_get(void);
static uint64_t mark_make(const std::string& file_key);
static uint64_t mark_make(const std::string& object, const std::string& config_path);
```

- `run_salt_get`：函数局部 `static const uint64_t`，首次调用时以 `Random_Generator<int64_t>()()` 产生种子，并混入 `steady_clock` 当前计数值；进程内唯一，跨进程随机。
- `mark_make(file_key)`：运行盐 + `std::hash<std::string>(file_key)` 混合，用于路由文件头标记。
- `mark_make(object, config_path)`：运行盐 + 对象名哈希 + 配置文件路径哈希，用于 `对象 × 文件` 条目内标记。

#### 3.7.4 加载 / 卸载入口与缓存清理

```cpp
void route_load(const Config_Content& content,
                bool delivery = true,
                const std::string& object = {});

void config_load(const std::string object, const nlohmann::json& request);

void route_unload(const Config_Content& content, const std::string& object);

void config_unload(const std::string object, const nlohmann::json& request);

void root_cache_clear(const Config_Content& root);
```

- `route_load`：扫描 `content.route` 目录下全部普通文件，按文件头脏标记跳过已处理文件，其余交 `route_file_process`；`object` 非空时只处理该对象的条目。
- `config_load`：从 `config_files[object]` 取缓存，按 `request.files`（若为非空 `vector<string>`）逐文件处理，否则全量处理。
- `route_unload`：扫描 `content.route`，对每份路由文件执行 `route_file_unload(content, file, object, json())`（即不清洗文件清单）。
- `config_unload`：按 `request.files` 清除 `config_files` 中对应条目（未给出清单则清除该对象全部），再遍历 `config_routes[object]` 定位路由文件，抹除条目标记。
- `root_cache_clear`：先收集所有“路由目录与配置目录均以 `root` 对应目录为前缀”的 `{对象, 目录对}`，逐个 `route_unload`；再按前缀删除 `config_routes` 与 `config_files` 中的记录。

#### 3.7.5 单份路由文件处理 / 卸载

```cpp
bool route_file_process(const Config_Content& content,
                        const std::filesystem::path& file_path,
                        const std::string& only_object,
                        const std::vector<std::string>& only_files,
                        bool deliver = true);

bool route_file_unload(const Config_Content& content,
                       const std::filesystem::path& file_path,
                       const std::string& only_object,
                       const nlohmann::json& only_files);
```

- `route_file_process`：返回“本轮是否真正投递过配置”（`delivered`）。它负责条目校验、过滤、路径安全检查、写内存缓存、接收者检查、单文件投递、按需回写路由文件头标记。
- `route_file_unload`：返回“本轮是否改动过路由条目”（`changed`）。它负责按过滤条件移除内存缓存、抹除条目 `dirty_mark`、按需以空顶层标记回写。

#### 3.7.6 单文件投递

```cpp
bool receiver_check(const std::string& object);

bool object_config_deliver(const std::string& object,
                           const std::string& config_path,
                           uint64_t mark,
                           nlohmann::json& entry);

bool config_file_process(const std::string& config_path,
                         nlohmann::json& entry,
                         const std::string& object);
```

- `receiver_check`：向中转站发 `Subscriber/Check` 查询，读回 `subscribed` 布尔值；构造 / 发送失败或答复缺失均返回 `false`。
- `object_config_deliver`：拼接绝对路径、读 JSON、剔除顶层 `dirty_mark`、取条目事件名（缺省 `Config` / `Load`）、拒绝保留事件标识、构造并发送事件、发送成功后写 `entry.dirty_mark = mark`。
- `config_file_process`：计算 `object × config_path` 的本轮标记；命中则跳过（`object` 非空时告警）；否则调用 `object_config_deliver`。返回“是否投递成功”。

bool error_out(std::error_code& info) const;

#### 4.6.4 组 4 配置投递（`core/配置加载.cpp`）

见 §三.7.6 签名。补充实现事实：

- `receiver_check` 使用 `event_terminal.build("", "", Subscriber, Check)`，把目标对象写入 `config["object"]`，同步等待中转站在同一事件对象上写入 `config["subscribed"]`。
- `object_config_deliver` 的绝对路径为 `base_dir_get() / string_to_path(config_path)`；若配置顶层是对象则 `erase("dirty_mark")`。
- 投递事件类别 / 标签从 `entry` 读取，缺省回落 `Config` / `Load`；命中保留标识则中止并返回 `false`（此时不写脏标记）。
- 发送分支：`Port_ID::Evt_Sender` 存在则单事件发送；否则 `Port_ID::Evts_Sender` 存在则包成 `vector` 多事件发送；两者都不存在则报错返回 `false`。
- 只有走完发送分支才执行 `entry["dirty_mark"] = mark` 并返回 `true`。
- `config_file_process` 的 `marked` 判定要求字段存在、为无符号整数且等于本轮的 `want_mark`；命中即返回 `false`（表示“未投递”）。

#### 4.6.5 组 5 路由文件处理（`core/路由文件操作.cpp`）

见 §三.7.5 签名。`route_file_process` 的精确顺序：

1. `route_file_read` 取 `mark` / `entries`；`entries` 非数组即报错返回 `false`。
2. 逐条目：`object` 与 `config_path` 必须是非空字符串（`field_check<string>`），否则打印三条可能原因并 `continue`。
3. 取 `event_category` / `event_tag`（缺省 `Config` / `Load`）；命中保留标识则驳回该条目。
4. 应用 `only_object` 与 `only_files` 过滤（`std::ranges::find`）。
5. `path_safety_check` 失败则跳过该条目。
6. 推导 `object_content`：路由目录 = `file_path.parent_path().lexically_relative(base_dir_get())`，配置目录 = `string_to_path(config_path).parent_path()`。
7. 写内存缓存：`config_routes[object].insert(object_content)`、`config_files[object][config_path] = entry`。
8. `deliver == false` 时到此为止。
9. `receiver_check(object)` 失败则告警并跳过投递（但缓存已写入）。
10. `config_file_process`；若返回 `true`（已投递），用循环内 `entry` 刷新 `config_files[object][config_path]`。
11. 循环结束后，只要本轮投递过至少一次（`delivered == true`），`route_file_write(file_path, mark_make(path), entries)` 回写文件头标记与条目。

`route_file_unload` 的精确顺序：读取 → 条目字段校验 → `only_object` 过滤 → `only_files` 非 `null` 时按字符串清单过滤 → `path_prefix_check(content.config, config_path.parent_path())` 过滤（不要求文件仍存在）→ 从 `config_files` 移除该文件（对象空了则删对象条目）→ 若条目含 `dirty_mark` 则 `erase` 并置 `changed = true` → 有改动则 `route_file_write(file_path, json(), entries)`（空顶层标记抹除文件头）。

#### 4.6.6 组 6 配置加载（`core/配置加载.cpp`）

见 §三.7.4 签名。`route_load` 实现细节：`content_scan(path_to_string(content.route))` 得到绝对路径列表；为空则 `logger.error` 返回；逐文件 `route_file_read`，`entries` 非数组则跳过；计算 `mark_make(path_to_string(file_path))`，若文件头 `mark` 是无符号整数且相等则告警跳过；否则 `route_file_process(content, file_path, object, {}, delivery)`。注意这里 `route_file_process` 会再次读取同一文件（重复 I/O）。

`config_load` 实现细节：`config_files.find(object)` 失败即报错返回；`request.files` 通过 `field_check<vector<string>>` 判定（同时包含非空检查）；清单中的空字符串跳过、未缓存文件告警；无清单时遍历该对象全部缓存文件。返回值被忽略。

#### 4.6.7 组 7 缓存清除（`core/缓存清除.cpp`）

见 §三.7.4 签名。实现要点：

- `root_cache_clear` 必须先收集命中集合再清除登记，因为 `route_unload` 定位路由文件依赖 `config_routes`；收集条件为 `path_prefix_check(root.route, content.route) && path_prefix_check(root.config, content.config)`。
- 清除 `config_routes` 用 `std::erase_if`，对象集合空了就 `erase` 该对象；清除 `config_files` 只按 `root.config` 前缀判断（配置文件路径维度），对象空了同样删除。
- `route_unload` 无条件向 `route_file_unload` 传 `json()`，因此卸载某对象时清掉该对象在目录下所有路由文件中所有文件的标记。
- `config_unload` 先删内存缓存，再从 `config_routes` 取目录对；无目录对时告警“仅清除内存缓存”并返回；否则逐目录扫描并 `route_file_unload(..., only_files)`。

#### 4.6.8 组 8 事件分发（`core/事件处理.cpp`）

见 §三.7.7 签名。`event_process` 的分派细节：

- `Believed_Root`：先校验 `route` / `config` 均为非空字符串；构造 `Config_Content`；`root.route` 或 `root.config` 为空（规范化后）则驳回。`Load`：已登记则告警返回；否则 `insert` 后 `route_load(root, true)`（不指定对象，= 全量目录扫描）。`Unload`：未登记则告警返回；否则 `root_cache_clear(root)` 后 `erase`。
- `Route/Load`：要求 `object`、`route`、`config` 字段有效；`config_routes` 不含该对象或该目录对则告警略过；否则 `route_load(content, true, object)`。
- `Route/Unload`：同样要求三字段；同样要求缓存中存在；否则 `route_unload(content, object)`（保留目录登记）。
- `Config_File/Load`：要求 `object`；`config_load(object, evt->config)`。
- `Config_File/Unload`：要求 `object`；`config_unload(object, evt->config)`。
- 其它 category / tag 组合直接落空，无日志。

`reserved_events_get` 返回六条：`{Believed_Root, Load}`、`{Believed_Root, Unload}`、`{Route, Load}`、`{Route, Unload}`、`{Config_File, Load}`、`{Config_File, Unload}`。`event_identifier_reserved` 先判 `tag == "All"`，再逐条比对。

三层边界的硬性事实：

1. **第一层不解析 glTF 语义**：只做文件级检查、容器分流、回调装配与解析驱动；不读 `model.*` 的集合内容。
2. **第二层不碰文件系统**：`model_convert` 只接收已解析完成的 `tinygltf::Model`，不打开文件、不读 buffer；图像字节完全不解码。
3. **第三层不对外暴露**：`tinygltf::Model` / `Accessor` / `Primitive` 等只出现在 `core/` 内的头与实现中；`gltf加载器.h` 不包含 tinygltf。
4. **唯一实现单元**：`tinygltf实现.cpp` 只做 `#define TINYGLTF_IMPLEMENTATION` 后包含 `tinygltf包含.h`；其余单元只拿声明，避免多重定义。`gltf转换.h` 也通过 `tinygltf包含.h` 获取声明。
5. **数据所有权**：`tinygltf::Model` 是 `load_file` 栈上临时对象；`Gltf_Asset result` 是栈上局部量，成功后 `std::move` 给调用方接收者。转换完成后不保留任何对 `Model` 的指针 / 引用。

### 5.3 资产线数据流与所有权

```
OBJ 文本 ──ifstream──> 行解析 ──> positions / texcoords / normals 原始数组
                                   │
                                   ├─ Vertex_Key(v,vt,vn) 去重 → Mesh_Data::vertices
                                   └─ 扇形三角化            → Mesh_Data::indices
                                                                 │
                                                        section_close（usemtl 分段）
                                                                 │
                                                        normals_fill（缺法线补全）
                                                                 ▼
                                                        Mesh_File_Data（栈上 result）
                                                                 │ move
                                                                 ▼
                                                        调用方 receiver
```

- 原始 `positions` / `texcoords` / `normals`、去重表 `dedup` 均为 `load_file` 局部量，函数返回即释放。
- `Mesh_File_Data result` 为局部量，只有全部成功（索引非空）才 `receiver = move(result)`；任何中途失败直接 `return false`，`receiver` 保持入口清空状态。
- 分段的 `first_index` / `index_count` 直接引用 `result.data.indices` 的下标区间，不复制索引；`sections` 与 `names` 同步 push，保证下标对齐。
- MTL 与 OBJ 之间没有数据引用：`Mtl_Material::name` 与 `Mesh_File_Data::names` 的匹配是字符串层面的调用方工作。

glTF 线的所有权：

- `bytes`（`vector<unsigned char>`）为 `load_file` 局部量，tinygltf 解析期间只读；解析结束即释放。
- `tinygltf::Model model` 持有 `buffers` 等解析产物（含外部 buffer 读取结果）；`model_convert` 只读。
- `Gltf_Asset result` 内的 `Mesh_Data` 全部为深拷贝 / 新建，不引用 `model.buffers`。
- `Gltf_Image::buffer_view` 只是下标，不持有字节；图像字节仍在 `model.buffers` 中，随 `model` 析构释放。这是“内嵌图像不解码”的直接后果：调用方拿到的只有引用信息。

### 5.4 配置线结构与生命周期

```
外部模块（配置生产者 / 接收者）
        │ 事件
        ▼
┌─────────────────────────────────────────────────────────────┐
│ Event_Terminal event_terminal（Config_Loader 的 public 成员）│
│   Terminal_Port：Broker_Attacher / Evt_Sender / Evts_Sender /│
│                  Evt_Receiver / Evts_Receiver                │
└───────────────────────────┬─────────────────────────────────┘
                            │ attach()：bind + attach + 订阅
                            ▼
                  事件中转站（event/Event_Broker）
                            │ 事件回送
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ Config_Loader::event_process                                │
│   ├── Believed_Root / Load|Unload → believed_roots          │
│   ├── Route / Load|Unload         → route_load / route_unload│
│   └── Config_File / Load|Unload   → config_load / config_unload│
└───────┬─────────────────────────────────────────────────────┘
        │
        ├── 磁盘侧：<exe_dir>/<route>/ **/*.json（路由文件）
        │       顶层 dirty_mark + config_routes[] 条目
        │       条目字段：object / config_path /
        │                 event_category / event_tag / dirty_mark
        │
        ├── 内存侧：
        │   believed_roots : set<Config_Content>
        │   config_routes  : map<object, set<Config_Content>>
        │   config_files   : map<object, map<config_path, entry JSON>>
        │
        └── 进程侧：run_salt（静态常量，进程唯一）
```

所有权与生命周期：

- `Config_Loader` 独占三份缓存；`event_terminal` 虽是 `public` 成员，但缓存与密钥只由类内方法使用。
- 路由文件是**持久化外部状态**：条目内的 `dirty_mark` 由本模块写盘；文件本身不属于任何对象，内容由外部编辑维护。
- `acl_key` 在构造时一次性生成并复制；`Event_Terminal::key()` 每次调用是否返回同一值由事件终端实现决定，本模块只取一次。
- `attach()` 之前的任何事件都不会到达（未绑定、未接入）；`attach()` 之后不提供 detach，析构也不做注销（实现事实）。
- 头文件中未出现互斥量 / 原子量 / 线程标注；缓存写入均为普通 `unordered_map` 操作，因此线程安全完全依赖调用方串行化（推断，非显式契约）。
- `run_salt` 为函数局部 `static const`，C++11 起初始化线程安全；但脏标记读取 / 写盘本身不具原子性。

### 5.5 事件订阅关系

`attach()` 生成的订阅清单固定为六条 `{category, tag}`（见 §三.6）。中转站据此把六类事件投递给 `Config_Loader`。`Config_Loader` 自身向中转站发送的事件有四类：

| 事件 | category | tag | 载荷 | 时机 |
| --- | --- | --- | --- | --- |
| 订阅登记 | `Subscribed_Events` | `Add` | `object`、`acl_key`、`subscribed_events` | `attach()` |
| 接收者查询 | `Subscriber` | `Check` | `object` | 每次投递前 |
| 配置投递（单） | 条目覆盖或 `Config` | 条目覆盖或 `Load` | 配置文件 JSON（去顶层 `dirty_mark`） | `object_config_deliver` |
| 配置投递（批量） | 同上 | 同上 | 单元素事件数组 | 仅当无 `Evt_Sender` 端口而有多事件端口时 |

## 六、模块设计 / 实现细节

### 6.1 两级脏标记与“运行盐”

**事实**（`core/脏标记.cpp`、`core/配置加载.cpp`、`core/路由文件操作.cpp`）：

- 脏标记不是文件时间戳，也不是内容哈希，而是“运行盐 + 关键字哈希”的 64 位值。同一进程内同一关键字得到同一值；不同进程得到几乎必然不同的值。
- 两级标记：
  1. **路由文件头标记**：写在路由文件顶层 `dirty_mark`，关键字为路由文件的绝对路径字符串（`path_to_string(file_path)`）。`route_load` 读文件后若该值等于本轮 `mark_make(path)`，整份文件跳过（`continue`），不再逐条处理。
  2. **条目内标记**：写在 `config_routes[]` 每个条目的 `dirty_mark`，关键字为 `(object, config_path)`。`config_file_process` 若条目标记等于本轮 `mark_make(object, config_path)`，跳过投递。
- 设计目的：进程重启后盐变化，所有旧标记自动失配，从而“跨进程必然重载”；同一进程内重复触发同目录 / 同文件 / 同对象时不会重复广播。
- 副作用：进程内配置文件内容被外部修改后，若对应条目标记仍命中，则不会重载，必须依赖 `Route/Load` 事件且文件头标记也失配才会重新读取。也就是说，**脏标记只表达“本轮是否已投递”，不表达“内容是否变化”**。

### 6.2 路由文件回写条件

**事实**（`core/路由文件操作.cpp`）：

- `route_file_process` 维护 `delivered` 布尔值；只有 `config_file_process` 返回 `true`（真正读取配置并发送事件）才置 `true`。循环结束后：
  - `delivered == true`：`route_file_write(file_path, mark_make(path), entries)`，写顶层标记 + 全部条目（含本轮新增 / 更新的条目内标记）。
  - `delivered == false`：**不回写**。因此“只登记缓存、不投递”（`deliver == false`、或接收者未接入）不会在磁盘留下任何脏标记。
- 条目在内存缓存中的写入发生在投递之前（第 7 步），且投递成功后会用循环内 `entry` 刷新一次；注释明确原因是“缓存里存的是投递前的条目快照，脏标记只写进循环内的 entry 并随路由文件落盘，不回写会让同一进程内再次加载重复投递”。
- 卸载路径 `route_file_unload` 用 `changed` 控制回写：只有实际删掉过至少一个 `dirty_mark` 才写盘，且顶层标记传 `json()`（空值），从而“抹除文件头标记”。`route_file_write` 中 `mark.is_null()` 时不写 `dirty_mark` 字段，旧字段随整文件重写而消失。

### 6.3 路由文件寻址模型（三个坐标系）

**事实**：

1. **基目录**：`base_dir_get()` 恒等于可执行文件所在目录（`detail::exe_dir_get`，Windows 下由 `GetModuleFileNameW` 得到宽字符路径再构造 `std::filesystem::path`）。
2. **路由目录**：`Config_Content::route` 是相对基目录的路径（或外部传入的任意路径，经 `path_normalize`）。`content_scan` 执行 `base_dir_get() / string_to_path(route)`；若 `route` 本身是绝对路径，`operator/` 会得到绝对路径（标准库语义），此时基目录不参与。
3. **配置目录 + 配置文件路径**：`Config_Content::config` 与路由条目里的 `config_path` 都采用“相对基目录”的同一坐标系。`path_safety_check` 逐节要求 `config_path` 以 `config` 为前缀；`object_config_deliver` 实际拼接 `base_dir_get() / config_path`。

由此得出的隐式约定：

- 路由文件条目中的 `config_path` 必须写成“相对可执行文件目录”的路径，且必须落在 `content.config` 目录前缀之下，否则被安全检查拒绝。
- `config_routes` 中登记的目录对由两部分推导：`route` = 路由文件父目录相对基目录的词法相对路径；`config` = `config_path` 的父路径（保持与 `config_path` 同坐标系）。因此 `Config_Content` 在缓存中既用于“重新定位路由文件”，也用于“前缀匹配可信根”。
- 同一对象可登记多个目录对；`config_routes[object]` 是集合，`Route/Unload` 与 `Config_File/Unload` 都会遍历全部目录对定位路由文件。

### 6.4 路径安全检查（`path_safety_check`）

四步，任一失败即拒绝：

1. `string_to_path(config_path).empty()` → 记录“配置路径为空”。
2. `detail::path_traversal_check(suspect_path)`：逐节检查，任一节为 `..` 即拒绝（记录“存在非法父目录返回符号”）。
3. 前缀逐节比对：遍历 `content.config` 的每一节，要求 `suspect_path` 在对应位置有同值节；`suspect_path` 先耗尽则拒绝（“配置路径超出合法范围”）。
4. `detail::path_check(base_dir_get() / suspect_path)`：要求最终路径存在且为普通文件（`std::filesystem::exists` + `is_regular_file`，均带 `error_code`）。这一步把“路径合法”升级为“当前实际可读”。

注意：

- 第 3 步是**纯词法**比较，不解析符号链接；符号链接逃逸不在防护范围内（`std::filesystem` 也未做 `canonical`）。
- 若 `config_path` 是绝对路径，逐节比较通常会在第一节（驱动器名 / 根目录）就与相对 `content.config` 失配而拒绝；但若 `content.config` 本身也是绝对路径且前缀匹配，则第 4 步会用绝对路径覆盖基目录。该行为依赖外部传入的目录对是否可信（见待确认 4）。
- 与资产加载器不同，OBJ / MTL / glTF 的主文件路径**没有**做 `..` 检查，也没有做配置目录前缀限制；只有 glTF 的**外部 buffer / 图像 URI** 经由 `fs_*` 回调做了 `..` 检查。

### 6.5 缓存清除时机

| 触发 | 入口 | 清除内容 | 磁盘副作用 |
| --- | --- | --- | --- |
| 可信根 `Unload` | `root_cache_clear` | 该根前缀下所有对象的 `config_routes` 与 `config_files` 记录 | 先对每个命中的 `{对象, 目录对}` 调 `route_unload`，抹除条目标记与文件头标记 |
| `Route/Unload` | `route_unload` | 仅通过 `route_file_unload` 移除该对象的配置文件缓存；**保留** `config_routes` 登记 | 抹除该对象条目 `dirty_mark`；有改动才写盘 |
| `Config_File/Unload` | `config_unload` | 该对象全部（或清单指定的）`config_files`；**保留** `config_routes` | 遍历其目录对定位路由文件，按清单抹除条目标记 |
| `Route/Load` 文件头命中 | `route_load` | 不清除，仅跳过 | 无 |
| `Config_File/Load` 条目命中 | `config_file_process` | 不清除，仅跳过 | 无 |

关键设计：

- `root_cache_clear` 的“先收集、后清除”顺序是必需的：若先删 `config_routes`，后续 `route_unload` 无法再定位该目录对的路由文件。
- `Route/Unload` 保留 `config_routes`，注释说明“使同目录对可再次加载重建”；`Config_File/Unload` 同样保留。只有可信根撤销或 `root_cache_clear` 才删除目录登记。
- `config_unload` 在定位路由文件之前就删了 `config_files`，而 `route_file_unload` 内部再次尝试删除缓存，属于幂等操作，不会出错。
- 缓存删除以“对象条目空了就删对象”为规则，避免留下空容器。

### 6.6 UTF-8 路径处理

**事实**：

- 所有公开接口接收 `std::string` 路径，按 UTF-8 解释；`detail::string_to_path` 用 `std::u8string(reinterpret_cast<const char8_t*>(...))` 构造 `std::filesystem::path`。
- 所有向外的路径文本（日志、事件载荷、路由文件条目、`Gltf_Image::uri` 等）由 `detail::path_to_string` 用 `path.u8string()` 转回 UTF-8 `std::string`。
- Windows 下 `exe_path_probe` 使用 `GetModuleFileNameW` + 宽字符缓冲，避免 `GetModuleFileNameA` 的 ANSI 代码页对中文路径的破坏；异常时回退 `current_path()` 并记录两条日志。
- 资产加载器打开文件时把 `std::filesystem::path` 直接交给 `ifstream` / `file_size` / `file_read_whole`，依赖 MSVC / libstdc++ 的 `path` 重载，不再经过 `std::string` 二次转换。
- MTL / OBJ 的行内容按原字节处理，文件名与材质名可含 UTF-8；比较是字节比较（大小写敏感）。
- glTF 的 `base_dir` 以 UTF-8 字符串传给 tinygltf；tinygltf 把 `uri` 原样拼到 `base_dir` 后交给 `fs_*`，因此非 ASCII 的 buffer / 图像 URI 在 Windows 上依赖 tinygltf 的拼接方式与 `string_to_path` 的重新解码（见待确认 5）。
- JSON 路由文件用默认 `ifstream`（文本模式）读取；若文件带 UTF-8 BOM，`nlohmann::json` 的解析行为取决于实现（未在本模块处理 BOM，见待确认 6）。

### 6.7 加载失败返回语义（资产线）

统一契约：**先清空输出，再工作；失败返回 `false`，输出为空；成功返回 `true`，输出为完整结果。**

| 加载器 | 入口清空 | 失败清空点 | 边界情况 |
| --- | --- | --- | --- |
| `Mesh_Loader::load_file` | 清 `vertices` / `indices` / `sections` / `names` | 所有错误分支直接 `return false`，不碰 `receiver`（仍是空） | 成功后 `receiver = move(result)` |
| `Mesh_Loader::load_obj` | 清 `vertices` / `indices` | `load_file` 失败即返回 `false` | 成功只 move 顶点与索引 |
| `Mtl_Loader::load_file` | `receiver.clear()` | 材质超限时先 `receiver.clear()` 再 `false`；其余分支 `receiver` 未写入 | 最后无 `newmtl` 时 `false` |
| `Gltf_Loader::load_file` | `receiver = Gltf_Asset{}` | 所有失败分支直接 `return false` | 成功后 `receiver = std::move(result)` |
| `gltf_detail::model_convert` | `receiver = Gltf_Asset{}` | 任一集合 / 下标 / 层级非法即 `false`，`receiver` 可能已部分填充 | 上层不把部分结果交给调用方 |

补充语义：

- `Gltf_Loader::load_file` 解析阶段用局部 `Gltf_Asset result`，只有 `model_convert` 成功才 move 给 `receiver`；因此即使 `model_convert` 中途写入了部分集合，调用方也拿不到。
- 所有失败都伴随 `logger.warn`（资产线）或 `logger.error`（配置线）；日志是唯一的诊断出口，接口不返回错误码 / 异常。
- 资产加载器完全不用异常做控制流；`Gltf_Loader` 唯一 `try/catch` 包住 tinygltf 调用，把 `std::exception` 转成 `parse_error` 字符串并走“解析失败”分支。
- 配置线的 `file_read` 用 `try/catch` 捕获 `json::parse_error` 与 `std::exception`，把接收者置 `null`；调用方以 `is_null()` 判定失败。

### 6.8 tinygltf 宏封装与第三方边界

**事实**（`core/tinygltf包含.h`）：

```cpp
#define TINYGLTF_NO_INCLUDE_JSON
#define TINYGLTF_NO_STB_IMAGE
#define TINYGLTF_NO_STB_IMAGE_WRITE
#define TINYGLTF_NO_EXTERNAL_IMAGE
#include "external/Json/nlohmann/json.hpp"
#ifdef _MSC_VER
#pragma warning(push)
#pragma warning(disable : 4244 4245 4267 4456 4457 4996)
#endif
#include "external/tinygltf/tiny_gltf.h"
#ifdef _MSC_VER
#pragma warning(pop)
#endif
```

逐条解释：

1. `TINYGLTF_NO_INCLUDE_JSON`：禁止 tinygltf 自带 json 头，改为复用本层 `external/Json/nlohmann/json.hpp`。这保证整个工程只有一份 nlohmann json 类型，避免事件载荷 / 配置 / glTF 解析出现两个不兼容的 `json`。
2. `TINYGLTF_NO_STB_IMAGE` / `TINYGLTF_NO_STB_IMAGE_WRITE`：不编译 stb_image 解码 / 写入；图像字节不解码，贴图交给渲染层。直接效果是 tinygltf 不会填充 `Image::image` 像素数据，只会给出 `uri` / `bufferView` / `mimeType`。
3. `TINYGLTF_NO_EXTERNAL_IMAGE`：禁止 tinygltf 自行加载外部图像文件；避免第三方库绕开本模块的路径安全检查。
4. MSVC 告警抑制 4244（窄化）、4245（符号转换）、4267（size_t 转换）、4456/4457（声明遮蔽）、4996（不安全 CRT）；`push` / `pop` 保证不影响本层代码。
5. `tinygltf实现.cpp` 先定义 `TINYGLTF_IMPLEMENTATION` 再包含该头，成为全工程唯一实现单元；`gltf转换.h` 也包含该头，但只有声明。

边界结论：tinygltf 类型只允许出现在 `Gltf_Loader/core/` 内；`gltf加载器.h` 完全不含第三方头。

### 6.9 glTF 访问器解码策略

**事实**（`core/gltf转换.cpp`）：

- **只支持非稀疏访问器**：`accessor.bufferView < 0` 视为“稀疏访问器不支持”，整份失败。glTF 规范允许无 `bufferView` 的稀疏访问器；本实现不处理。
- **步长**：`bufferView.byteStride == 0` 按紧排（`element_size`），否则按声明步长。起点为 `bufferView.byteOffset + accessor.byteOffset`。
- **越界判定**：`last_end = start + stride * (count - 1) + element_size`，再与 `buffer.size()` 比较；`count == 0` 时 `last_end = start + element_size`，空访问器也可能因起点贴边而失败（见待确认 7）。
- **分量数必须精确匹配**：`POSITION` 必须 3、`TEXCOORD_0` 必须 2、`NORMAL` 必须 3；`type_components` 不支持 MAT2 / MAT3 / MAT4。
- **组件类型**：属性读取支持 FLOAT / UNSIGNED_BYTE / UNSIGNED_SHORT / BYTE / SHORT，并按 `accessor.normalized` 归一化；整型 `INT` / `UNSIGNED_INT` 属性不支持（`component_read` 返回 `false`）。索引读取只支持 UNSIGNED_BYTE / SHORT / INT。
- **有符号归一化下限**：`i8/127` 与 `i16/32767` 的最小值会略小于 `-1`，代码用 `std::max(-1.0f, ...)` 钳制。
- **无符号索引**：统一转成 `uint32_t`；不做符号扩展。
- **法线补全**：仅在存在零法线时触发；面积加权（叉积模长即两倍面积）；退化面回落 `+Z`。这与 OBJ 的补全策略完全一致（两处各有一份同名 `normals_fill`，实现逐行相同）。
- **顶点数 / 索引数限制**：单图元顶点 ≤ 4000000，索引 ≤ 12000000；索引数必须为 3 的倍数，且全部索引 < 顶点数。

### 6.10 glTF “跳过”与“失败”的分界

`primitive_convert` 返回三态，`model_convert` 据此决定：

| 情况 | 结果 | 后果 |
| --- | --- | --- |
| `mode != TRIANGLES` | `skip` | 日志告警，该图元被丢弃，其余继续 |
| 缺 `POSITION` | `skip` | 同上 |
| `POSITION` 顶点数为 0 | `skip` | 同上 |
| `POSITION` / `TEXCOORD_0` / `NORMAL` 访问器越界或类型不支持 | `fail` | 整份 glTF 加载失败 |
| `TEXCOORD_0` 数量与顶点数不符 | `fail` | 整份失败 |
| `NORMAL` 数量与顶点数不符 | `fail` | 整份失败 |
| 索引访问器非法 / 索引数不是 3 的倍数 / 索引越界 | `fail` | 整份失败 |
| 顶点数或索引数超过上限 | `fail` | 整份失败 |

集合级校验（`model_convert` 内）一律 `fail`：集合数量超过 65536、图像 `bufferView` 越界、纹理 `source` / `sampler` 越界、材质贴图下标越界、图元材质下标越界、节点网格下标越界、节点子下标越界、节点变换数组长度非 0 且非规范长度、节点自引用 / 重复父、场景根下标越界、默认场景下标越界。

设计取舍：结构性不支持（图元模式、缺 POSITION、空顶点）容忍并跳过；数据损坏（越界、类型错、数量错）整份拒绝。这样保证“部分可用”的模型仍可加载，但不会把错误数据交给渲染层。

### 6.11 glTF 节点矩阵与层级

**事实**：

- 若 `node.matrix.size() == 16`，直接逐项 `static_cast<float>` 拷贝，不做列主序转换（假定 glTF 的 matrix 与引擎约定同为列主序）。
- 否则按 `translation`（默认 0）、`rotation`（默认四元数 `(0,0,0,1)`）、`scale`（默认 1）合成：
  - 四元数先展开为行主序旋转矩阵 `r0..r8`；
  - 写出时按列主序：第 0 列 = `(r0, r3, r6) * scale[0]`，第 1 列 = `(r1, r4, r7) * scale[1]`，第 2 列 = `(r2, r5, r8) * scale[2]`，第 3 列 = translation，末元素 1。
- 变换数组长度校验：`matrix` 只允许 0 或 16；`translation` 0 或 3；`rotation` 0 或 4；`scale` 0 或 3；否则整份失败。
- 父链回填：遍历所有父节点的 `children`，若 `child == parent` 或 `child.parent != -1` 则失败（自引用或重复父）；否则写 `child.parent = parent`。因此“同一节点出现在两个父的 children 中”会被拒。
- 场景根节点只校验下标合法；不要求根节点 `parent == -1`，也不校验根集合与父链一致性（外部数据可写任意节点为根）。

### 6.12 glTF 文件分流与外部资源读取

**事实**（`core/gltf加载器.cpp`）：

- 体量检查：`file_size_get` 失败 → 告警；`byte_count == 0` 或 `> 64 MiB` → 告警失败。
- 魔数判定：读取整文件到 `bytes` 后，`bytes.size() >= 4 && memcmp(bytes.data(), "glTF", 4) == 0` 判为 GLB；否则按 ASCII（JSON 文本）解析。注意：`bytes.size() >= 4 && memcmp` 的第二项之后没有短路问题；不足 4 字节的空 / 短文件会被 `LoadASCIIFromString` 处理并失败。
- `base_dir`：`file_path.parent_path()`；为空则 `"."`；否则 `path_to_string(parent)`。该值直接传给 tinygltf。
- 回调装配：`FileExists = fs_exists`、`ExpandFilePath = fs_expand`、`ReadWholeFile = fs_read`、`WriteWholeFile = fs_write`、`GetFileSizeInBytes = fs_size`、`user_data = nullptr`；`loader.SetFsCallbacks(callbacks, &parse_error)`。
- 二进制解析用 `LoadBinaryFromMemory`，文本解析用 `LoadASCIIFromString`；二者都把 `bytes.size()` 窄转为 `unsigned int`（64 MiB 上限保证不溢出 32 位）。
- `try/catch(const std::exception&)` 把异常文本写进 `parse_error`。
- `parsed == false` 时只告警返回；`parse_warning` 非空时告警但不阻断。
- 外部 buffer 读取路径由 tinygltf 决定：它会用 `base_dir + uri` 调 `fs_read`；`fs_read` 再拒绝含 `..` 的路径。由于 `base_dir` 可能是相对路径（输入 `gltf_path` 为相对时），`string_to_path` 之后的相对路径按**进程当前工作目录**解释，而不是按可执行文件目录——这与配置线的基目录语义不同（见待确认 8）。

### 6.14 OBJ 解析的具体取舍

**事实**（`Mesh_Loader/core/网格加载器.cpp`）：

- **只识别四类行**：`v`、`vt`、`vn`、`usemtl`、`f`；`mtllib`、`o`、`g`、`s` 等全部忽略（注释明确）。
- **`vt` 的 v 分量可选**：先 `stream >> u` 必须成功；再 `stream >> v` 不检查返回值。因此 `vt 0.5` 会得到 `(0.5, 0.0)`；`v` 分量缺省为 0（C++11 后 `float` 局部初始化）。
- **`v` / `vn` 必须三个分量**：任一缺失即整份失败（不是跳过该行）。
- **索引解析**：正索引减 1；负索引按“当前已读数组长度 + 负值”换算；换算后 `[0, count)` 之外失败。索引基数取解析到该 `f` 行时的数组长度，因此 OBJ 中“先引用后定义”不被支持（标准 OBJ 通常也要求先定义）。
- **面顶点去重**：以 `(position, texcoord, normal)` 三元组为键。相同位置但不同 UV / 法线的角点会生成不同顶点；同一三元组复用同一顶点下标。哈希用三常量混合，相等用三字段比较。
- **面顶点数不足 3**：整份失败。
- **三角化**：扇形，固定以 `face[0]` 为首点，生成 `(face[0], face[i], face[i+1])`，`i` 从 1 到 `n-2`。
- **索引上限检查时机**：每写三个索引前检查 `indices.size() + 3 > max_indices`；因此上限按“完整三角形”对齐。
- **`usemtl` 分段**：遇到 `usemtl` 先 `section_close` 关闭上一段，再更新 `section_name`；文件末尾再关闭最后一段。没有面的段被丢弃，因此 `names` 与 `sections` 始终同步且 `material` 槽 = 段序号。
- **未写 `usemtl` 的文件**：`section_name` 为空串，末尾 `section_close` 建立一个 `material = 0`、`names[0] == ""` 的段。
- **无有效三角面**：`indices.empty()` 时整份失败（即使顶点已读入）。
- **法线补全**：见 §6.9；OBJ 与 glTF 两份实现相同。
- **行尾回车**：仅删除一个 `\r`；UTF-8 BOM 未处理（首行若带 BOM，`tag` 会含 BOM 字节，导致该行不被识别；若首行是 `v` 则视为未知行跳过，不致命，但首行若为注释也仍按未知行跳过）。见待确认 9。

### 6.15 MTL 解析的具体取舍

**事实**（`Mtl_Loader/core/材质加载器.cpp`）：

- **标签大小写**：`newmtl` / `Kd` / `Ks` / `Ke` / `Ns` / `d` / `Tr` / `map_Kd` 为精确匹配；法线贴图额外接受 `map_Bump`、`map_bump`、`bump`、`norm`。未列出 `map_kd`、`Map_Kd`、`kd` 等变体。
- **`newmtl` 之前的所有行被忽略**（`in_material == false` 时直接 `continue`）；因此文件开头若先出现 `Kd`，该值不会归入任何材质。
- **`name` 取 `newmtl` 之后整行并 `text_trim`**，允许含空格。
- **颜色**：`color_read` 读三个 float，缺失分量保持 0；每个分量 `unit_clamp`（非有限值→0，负数→0，大于 1→1）。因此 `Kd 2 0 0` 得到 `{1,0,0}`。
- **`Ns`**：只接受有限值；负数→0，大于 1000→1000；非有限值保持默认 0。
- **`d`**：`unit_clamp`；非有限值→0。
- **`Tr`**：`1 - unit_clamp(value)`；`Tr 1` → 不透明度 0。
- **贴图路径**：`texture_path_read` 逐个读 token，跳过以 `-` 开头的选项（如 `-bm`、`-s`、`-o`、`-cl`），保留最后一个非选项 token。因此带空格的路径只能保留最后一段（MTL 未加引号时本就无法表达空格路径）。路径原样保存，不解析相对目录。
- **材质数量**：每遇到新的 `newmtl` 先把上一项 push，再检查 `receiver.size() >= 4096`；超限时清空并整份失败。这意味着“第 4097 个 `newmtl`”会触发失败，且此前已 push 的材质全部丢弃。
- **空文件 / 无 newmtl**：返回 `false`，`receiver` 为空。
- **不检查 `mtllib` 与 OBJ 的对应关系**：MTL 可独立使用（头文件明确“场景清单即显式声明材质库路径”）。
- **注释行**：`tag[0] == '#'` 跳过；行首空白后的 `#` 仍会被识别为 `tag` 首字符（`istringstream >> tag` 跳过前导空白），因此缩进注释也能识别。

### 6.16 配置 JSON 形状约定

**路由文件**（磁盘）：

```json
{
  "dirty_mark": 1234567890123456789,
  "config_routes": [
    {
      "object": "Renderer",
      "config_path": "config/renderer.json",
      "event_category": "Config",
      "event_tag": "Load",
      "dirty_mark": 9876543210987654321
    }
  ]
}
```

- 顶层必须是对象；`config_routes` 必须是数组，否则整份跳过。
- 条目的 `object` 与 `config_path` 必须是非空字符串；`event_category` / `event_tag` 若存在必须是字符串，否则回落缺省。
- 条目可被外部追加任意其它字段：写回时 `entries` 是 `route_file_read` 读出的原 JSON 数组，未知字段原样保留（`route_file_write` 只重写整个数组）。
- `dirty_mark` 类型：读取时路由文件头要求 `is_number_unsigned()` 才参与比较；条目内 `field_check<uint64_t>` 要求 `is_number_integer()`。写入的是 `uint64_t`，`dump` 后为十进制无符号整数。

**配置文件**（被投递）：任意 JSON。若顶层是对象，`dirty_mark` 字段会被删除后再投递；若顶层是数组 / 标量，则原样投递。因此配置内容可以不是对象。

**事件载荷**：见 §三.6。

### 6.17 事件校验与保留标识策略

- 所有外部事件字段校验都用 `detail::field_check<T>`：字段不存在、类型不符、字符串为空、容器为空均视为无效（并各自写日志）。这使“空字符串 object / route / config”在进入业务逻辑前就被驳回。
- `Config_File/Load` 的 `object` 只要求非空字符串；不要求该对象已在 `config_files` 中（`config_load` 自己会报“目标对象尚无配置记录”）。
- 保留标识判定把 `tag == "All"` 视为无条件保留（与中转站“All 标签事件直接丢弃”的约定对齐），并拒绝六条本模块自身订阅的 `{category, tag}`。这样路由条目不能伪造 `Believed_Root/Route/Config_File` 事件来递归驱动加载器。
- 条目事件名的缺省值是 `Config` / `Load`，与事件协议中的配置投递约定一致。
- 投递时 `sender` 固定写 `"Config_Loader"`，`receiver` 写目标对象名；接收方据此识别来源。

### 6.18 接收者存在性检查的时序

`receiver_check` 同步发送 `Subscriber/Check`，依赖中转站“同步处理并就地写入答复字段”的实现（代码注释明确）。因此：

- `event_terminal.build("", "", Subscriber, Check)` 的 sender / receiver 均为空串；目标对象放在载荷里，以命中中转站自身的处理契约（注释明确）。
- 答复字段 `subscribed` 必须是布尔；缺失或为 `false` 都返回 `false`。
- 检查发生在 `config_file_process` 之前；未接入的对象只会留下内存缓存，不投递、不写脏标记。
- 若中转站不可达 / 发送失败，返回 `false`，同样只缓存不投递。

### 6.19 配置线失败与日志策略

- 配置线几乎不在接口层返回错误：`route_load` / `config_load` / `route_unload` / `config_unload` / `root_cache_clear` 都是 `void`；只有内部 `bool` 函数用于流程控制。
- `route_file_process` 返回 `delivered`，调用方 `route_load` 忽略该值；`route_file_unload` 返回 `changed`，`route_unload` 也忽略。
- 失败一律 `logger.error` / `logger.warn`，包括：路由文件未找到、路由条目格式非法、字段无效、路径越界、接收者未接入、配置读取失败、路由写回失败。
- 对“可跳过”的条目（字段无效、过滤不匹配、路径非法、保留标识命中）用 `continue`，不中断其余条目；对“文件级错误”（`entries` 非数组、打不开）整份跳过或返回。
- 写盘失败只报错，不回滚内存缓存；因此内存状态与磁盘状态可能分叉（下一次进程启动会以磁盘为准）。

### 6.20 性能与复杂度

- OBJ：单遍文本扫描；顶点去重 `unordered_map` 预期 O(1)；扇形三角化 O(面顶点数)；法线补全 O(索引数 + 顶点数)。`dedup.reserve(4096)` 只是初始容量，大模型会多次 rehash。
- MTL：单遍文本扫描，每个材质一个 `istringstream`；无随机访问。
- glTF：tinygltf 完成 JSON 解析与 buffer 装载；转换层按集合线性遍历，访问器逐元素逐分量读取（`memcpy` + 分支），没有 SIMD；大模型的顶点装配是主要成本。
- 配置：每次 `route_load` 全目录递归扫描 + 每份路由文件至少读一次（`route_load` 读一次判文件头，`route_file_process` 再读一次）；`Config_File/Load` 只读缓存条目，不重扫目录。缓存均为哈希容器，查找均摊 O(1)。
- 字符串路径在配置线中频繁 `path_to_string` / `string_to_path`（每次事件、每次扫描、每次安全检查），属于可接受的开销；没有路径字符串缓存。

### 6.21 编码风格与局部约定

- 资产线使用中文注释、Allman 大括号、控制流单语句不加块（与项目规范一致）；`Mesh_Section` / `Vertex` 的字段注释为中文。
- `gltf转换.cpp` 的 `data.vertices.resize(vertex_count)` 之后的 `for` 循环左大括号缩进多一层（第 541 行 `{` 缩进 12 空格），属排版瑕疵，不影响语义。
- `配置加载器.h` 中公开成员 `event_terminal` 夹在 `private` 区段之间，随后又是 `private: acl_key`，最后 `public:` 构造函数；这是刻意的“公开门面置顶 / 事件终端可访问 / 密钥私有”布局，注释也说明成员声明顺序与实现顺序一致。
- 配置线的 `std::hash` / `std::formatter` 特化写在 `namespace std` 中，位于两个 `namespace engine` 块之间；这是 C++ 标准允许的特化方式。
- `局部命名空间使用.h` 的 `using` 声明覆盖各实现单元用到的全部类型；实现代码不写 `std::` 前缀（`gltf转换.cpp` 中仍出现 `std::sqrt`、`std::max`、`std::move`、`std::exception`，与“局部命名空间使用”约定不完全一致，属实现现状）。

## 七、模块运行链路详例

### 7.1 链路一：可信根首次加载（含路由解析与事件广播）

**触发**：外部模块向事件中转站发送 `Believed_Root/Load`，载荷 `{ "route": "config/routes", "config": "config/data" }`。

**步骤**：

1. 中转站按订阅清单把事件投递给 `Config_Loader` 的 `Evt_Receiver` 回调；回调即 `Config_Loader::event_process(evt)`（`core/事件处理.cpp`）。
2. `event_process` 判断 `evt->category == config_event::believed_root`：
   - `detail::field_check<string>(evt->config, "route")` 与 `"config"` 均通过（非空字符串）。
   - 构造 `Config_Content root("config/routes", "config/data")`，两个路径经 `path_normalize`；`root.route` / `root.config` 非空。
3. `evt->tag == event_protocol::load`：
   - `believed_roots.count(root)` 为 0，`insert(root)`。
   - 调 `route_load(root, true)`（`delivery = true`，`object = ""`）。
4. `route_load`（`core/配置加载.cpp`）：
   - `content_scan(path_to_string(root.route), route_files)`：以 `exe_dir / "config/routes"` 为根递归遍历，收集所有普通文件的绝对路径。
   - 若为空：`logger.error("未检测到任何路由文件")`，返回。
   - 逐文件：
     a. `route_file_read(file_path, mark, entries)` → 读 JSON，取顶层 `dirty_mark` / `config_routes`。
     b. `entries.is_array()` 为假：报错 `continue`。
     c. `want_mark = mark_make(path_to_string(file_path))`；`mark` 为无符号整数且等于 `want_mark` → 告警跳过（首次运行为旧标记失配，不会跳过）。
     d. `route_file_process(root, file_path, "", {}, true)`。
5. `route_file_process`（`core/路由文件操作.cpp`）：
   - 再次 `route_file_read`（重复读取，见 §6.20）。
   - 逐条目：
     a. 校验 `object` / `config_path` 非空字符串；否则打印三条可能原因并跳过。
     b. `event_category` 缺省 `Config`、`event_tag` 缺省 `Load`；`event_identifier_reserved` 命中则驳回该条目（防止递归）。
     c. `only_object` 为空、`only_files` 为空 → 都不过滤。
     d. `path_safety_check(root, config_path)`：无 `..`、`config_path` 以 `root.config` 逐节为前缀、`exe_dir / config_path` 存在且为普通文件。失败则跳过。
     e. 推导 `object_content(route_file.parent().lexically_relative(exe_dir), config_path.parent())`，插入 `config_routes[object]`；`config_files[object][config_path] = entry`。
     f. `receiver_check(object)`：向中转站发 `Subscriber/Check`，读 `subscribed`。未接入 → 告警 `已取消配置信息传递` 并 `continue`（缓存已留）。
     g. `config_file_process(config_path, entry, object)`：`want_mark = mark_make(object, config_path)`；条目内标记命中 → 跳过；否则 `object_config_deliver`。
     h. `object_config_deliver`：
        - 绝对路径 `exe_dir / config_path`；`file_read` 读 JSON。
        - `config_data.is_null()` → 报错返回 `false`。
        - 顶层为对象则 `erase("dirty_mark")`。
        - 取条目事件名（缺省 `Config` / `Load`），再次 `event_identifier_reserved` 检查。
        - `event_terminal.build("Config_Loader", object, category, tag)`；失败报错。
        - `evt->config = config_data`。
        - 发送：有 `Evt_Sender` 则单发，否则有 `Evts_Sender` 则包成单元素数组发，否则报错返回 `false`。
        - 成功后 `entry["dirty_mark"] = want_mark`；`logger.info("已发送配置事件: <object>")`；返回 `true`。
     i. 投递成功：`config_files[object][config_path] = entry`（刷新为含本轮标记的条目）。
     j. 循环结束：若 `delivered == true`，`route_file_write(file_path, mark_make(file_path), entries)`，把顶层标记与所有条目（含新 `dirty_mark`）以 `dump(4)` 写回。
6. 回到 `route_load`，处理下一份路由文件；全部完成后返回 `event_process`，事件处理结束。

**结果 / 副作用**：

- `believed_roots` 增加一项；`config_routes` 增加若干“对象 → 目录对”；`config_files` 增加若干“对象 → 配置文件 → 条目快照”。
- 已接入的接收者收到 `Config/Load`（或条目覆盖的事件）与配置 JSON；其内部据此加载自身参数。
- 路由文件顶层与条目内被写入本轮 64 位标记；同进程内再次触发 `Believed_Root/Load` 会因“已登记”直接跳过。
- 未接入的接收者只留下缓存，不产生任何磁盘标记。

### 7.2 链路二：单目录对重载与卸载

**触发 A：`Route/Load`**，载荷 `{ "object": "Renderer", "route": "config/routes", "config": "config/data" }`。

1. `event_process` 校验三字段；构造 `Config_Content`。
2. `config_routes.count("Renderer")` 为真，且集合中含该目录对，否则告警略过。
3. `route_load(content, true, "Renderer")`：扫描该路由目录全部文件；文件头标记命中则跳过；否则 `route_file_process(content, file, "Renderer", {}, true)`。
4. `route_file_process` 只处理 `object == "Renderer"` 的条目；其余条目跳过。对命中条目重新执行路径检查、缓存写入、接收者检查、单文件投递。
5. 若该目录内所有路由文件头标记都命中（首次加载后同进程内），则一律跳过，不投递；这是“同进程内不重复广播”的直接体现。要强制重发，可先 `Route/Unload` 抹除标记，再 `Route/Load`。

**触发 B：`Route/Unload`**，同样三字段。

1. `event_process` 校验并构造 `Config_Content`；要求 `config_routes` 中存在该对象与目录对，否则略过。
2. `route_unload(content, "Renderer")`：扫描路由目录；对每份文件 `route_file_unload(content, file, "Renderer", json())`。
3. `route_file_unload`：
   - 读取 JSON；条目逐条过滤 `object == "Renderer"`；`only_files` 为 `null` 所以不按文件清单过滤；`path_prefix_check(content.config, config_path.parent())` 要求文件仍在该配置目录下（不要求文件存在）。
   - 从 `config_files` 删该文件；对象空了删对象条目。
   - 若条目有 `dirty_mark`，`erase` 并 `changed = true`。
4. 若 `changed`，`route_file_write(file_path, json(), entries)`：**不写顶层 `dirty_mark`**，因此文件头标记被抹除；条目内标记也已删除。
5. `config_routes[object]` 保留该目录对（注释明确“保留配置目录登记，使同目录对可再次加载重建”）。

**结果**：内存中该对象的配置文件缓存被清空，磁盘标记被抹除；紧接一次 `Route/Load` 会重新读取并投递。

### 7.3 链路三：glTF 资产加载

**调用方**：渲染层资产加载入口（快照内未出现调用点，链路从公开门面起算）。

1. `Gltf_Loader::load_file(gltf_path, receiver)`（`core/gltf加载器.cpp`）：
   - `receiver = Gltf_Asset{}`。
   - `gltf_path.empty()` → `logger.warn("路径为空")`，`false`。
   - `file_path = detail::string_to_path(gltf_path)`。
   - `detail::file_size_get(file_path, byte_count, code)`：失败 → 告警 `无法读取 glTF 文件`，`false`。
   - `byte_count == 0` 或 `> 64 MiB` → 告警体量非法，`false`。
   - `detail::file_read_whole(file_path, bytes, code)`：失败 → 告警，`false`。
   - `is_binary = bytes.size() >= 4 && memcmp(bytes.data(), "glTF", 4) == 0`。
   - `base_dir = file_path.parent_path()`；空则 `"."`，否则 `path_to_string(parent)`。
2. 装配 tinygltf：
   - `tinygltf::TinyGLTF loader`；`tinygltf::FsCallbacks callbacks` 逐字段赋值（见 §4.3）；`user_data = nullptr`。
   - `string parse_error, parse_warning; loader.SetFsCallbacks(callbacks, &parse_error)`。
   - `tinygltf::Model model`。
   - `try` 内 `parsed = is_binary ? loader.LoadBinaryFromMemory(&model, &parse_error, &parse_warning, bytes.data(), bytes.size(), base_dir) : loader.LoadASCIIFromString(&model, &parse_error, &parse_warning, reinterpret_cast<const char*>(bytes.data()), bytes.size(), base_dir)`。
      - 若 glTF 引用外部 buffer（`buffers[].uri`），tinygltf 会用 `base_dir + uri` 调 `fs_size` / `fs_read`；两者均先 `path_traversal_check`，再走 `detail` 的通用读取。
   - `catch (const std::exception&)` → `parse_error = exception.what()`。
   - `!parsed` → 告警含 `parse_error`，`false`。
   - `parse_warning` 非空 → 告警但不阻断。
3. `Gltf_Asset result; gltf_detail::model_convert(model, result)`（`core/gltf转换.cpp`）：
   - 清空 `result`；七个集合数量均 ≤ 65536，否则告警 `集合数量超限`，`false`。
   - 采样器：逐项拷贝四个 int。
   - 图像：拷贝 `name` / `uri` / `mimeType` / `bufferView`；`bufferView >= 0` 时校验 `< model.bufferViews.size()`，否则 `false`。
   - 纹理：拷贝 `source` / `sampler`，分别校验 `< images.size()` / `< samplers.size()`，否则 `false`。
   - 材质：拷贝 `name`；`baseColorFactor` 仅在长度为 4 时拷贝；`metallicFactor` / `roughnessFactor` 直接拷贝；`emissiveFactor` 仅长度为 3 时拷贝；`alphaMode` 经 `alpha_mode_map`；`alphaCutoff` / `doubleSided`；五个贴图下标与两个强度；五个贴图下标逐一校验 `< textures.size()`，否则 `false`。
   - 网格：逐 mesh 拷贝 `name`；逐 primitive：
     a. 若 `primitive.material >= 0` 且 `>= materials.size()` → 告警，整份 `false`。
     b. `primitive_convert(model, primitive, converted, error)`：
        - `mode != TRIANGLES` → 告警，`skip`。
        - `attributes.find("POSITION")` 不存在 → 告警，`skip`。
        - `accessor_float_read(POSITION, 3)` → 校验下标 / 数量 / `accessor_range_get` / 逐分量；失败 `fail`。
        - `vertex_count = positions.size() / 3`；为 0 → `skip`；`> 4000000` → `fail`。
        - `TEXCOORD_0` 存在则读 2 分量，数量 / 顶点数不符 → `fail`。
        - `NORMAL` 存在则读 3 分量，数量 / 顶点数不符 → `fail`。
        - 索引：`primitive.indices >= 0` 则 `accessor_index_read`；否则生成 `0..n-1`。索引数 `> 12000000` 或 `% 3 != 0` → `fail`。
        - 装配 `Mesh_Data`：逐顶点写 `position`；`texcoords` 非空写 `uv`，否则保持零；`normals` 非空写 `normal`，否则保持零。
        - 逐索引检查 `< vertex_count`，越界 → `fail`。
        - `data.indices = move(indices)`；`normals_fill(data)`。
        - `out.data = move(data)`；`out.material = primitive.material`；`ok`。
     c. `fail` → 告警 `图元数据非法：<error>`，整份 `false`；`skip` → `continue`；`ok` → `push_back(move(converted))`。
   - 节点：逐 node 拷贝 `name` / `mesh`；`mesh >= meshes.size()` → `false`；拷贝 `children` 并逐项校验 `[0, nodes.size())`；变换数组长度非法 → `false`；`node_matrix_build`。
   - 父链回填：对每个父的每个 child，自引用或 `parent != -1` → `false`；否则写 `parent`。
   - 场景：逐 scene 拷贝 `name` / `nodes`，逐根下标校验；默认场景下标校验；写 `default_scene`。
   - 全部通过 → `true`。
4. 回到 `load_file`：`model_convert` 失败 → 告警 `模型转换失败`，`false`；成功 → `receiver = std::move(result)`，`true`。

**结果**：调用方得到纯 CPU 的 `Gltf_Asset`；不产生任何 GPU 资源，不读取图像字节；`model` 与 `bytes` 在函数返回时析构。

### 7.4 链路四：网格与材质加载

**OBJ 完整加载**：

1. `Mesh_Loader::load_file(mesh_path, receiver)`：
   - 清空 `receiver.data.vertices` / `indices` / `sections` / `names`。
   - 空路径 → 告警 `false`。
   - `file_path = string_to_path(mesh_path)`；`file_size_get` 失败 → 告警 `false`；体量 0 或 `> 64 MiB` → 告警 `false`。
   - `ifstream file(file_path, ios::binary)`；打开失败 → 告警 `false`。
   - 局部 `Mesh_File_Data result`，局部 `positions` / `texcoords` / `normals`，局部 `dedup`（`reserve(4096)`），`section_start = 0`，`section_name` 空。
   - 逐行：
     a. 去掉行尾一个 `\r`；`istringstream stream(line)`；空行 / `#` 注释跳过。
     b. `v`：读 x y z，失败 → 告警 `false`；`positions.size() >= 4000000` → 告警 `false`；push。
     c. `vt`：读 u（必须），再读 v（可缺）；`texcoords.size() >= 4000000` → `false`；push。
     d. `vn`：读 x y z，失败 → `false`；超限 → `false`；push。
     e. `usemtl`：`getline` 取余下整行并 `text_trim`；`section_close(result, section_start, section_name)`；`section_name = name`。
     f. `f`：逐 token `face_token_parse`；失败 → 告警含 token，`false`。查 `dedup`；命中复用；否则拼 `Vertex`（位置必填，UV / 法线按 key 可缺），顶点数超限 → `false`，push 并 `dedup.emplace`。面顶点 `< 3` → `false`。扇形三角化，每次写 3 个索引前检查 `indices.size() + 3 > 12000000`。
     g. 其它标签忽略。
   - 循环结束：`indices.empty()` → 告警 `未包含有效三角面`，`false`；`section_close` 收尾；`normals_fill`；`receiver = move(result)`；`true`。
2. `Mesh_Loader::load_obj(mesh_path, receiver)`：清空 `vertices` / `indices`；调 `load_file` 取 `Mesh_File_Data`；失败 `false`；成功把 `file_data.data` 的两个容器 move 到 `receiver`。

**MTL 完整加载**：

1. `Mtl_Loader::load_file(mtl_path, receiver)`：
   - `receiver.clear()`；空路径 → 告警 `false`。
   - `file_path = string_to_path(mtl_path)`；`file_size_get` 失败 → 告警 `false`；体量 0 或 `> 16 MiB` → 告警 `false`。
   - `ifstream file(file_path, ios::binary)`；打开失败 → 告警 `false`。
   - 局部 `Mtl_Material material`、`bool in_material = false`。
   - 逐行：去 `\r`；空行 / `#` 跳过。
     a. `newmtl`：若 `in_material` 先 push 上一项；若 `receiver.size() >= 4096` → 告警并 `receiver.clear()`、`false`；`material = Mtl_Material{}`；`getline` 取名字并 `text_trim`；`in_material = true`。
     b. `in_material == false` 时其余行忽略。
     c. `Kd` / `Ks` / `Ke` → `color_read`；`Ns` → 有限值钳制 0..1000；`d` → `unit_clamp`；`Tr` → `1 - unit_clamp`；`map_Kd` → `texture_path_read` 写 `diffuse_map`；`map_Bump` / `map_bump` / `bump` / `norm` → 写 `normal_map`。
     d. 其余忽略。
   - 收尾：`in_material` 则 push 最后一项；`receiver.empty()` → 告警 `未包含任何 newmtl`，`false`；否则 `true`。

**结果**：网格线与材质线各自独立返回纯数据；调用方自行用 `names` 与 `Mtl_Material::name` 做材质匹配，并把 `diffuse_map` / `normal_map` 交给渲染层解码。

### 7.5 链路五：可信根撤销与缓存清除

1. 外部发送 `Believed_Root/Unload`，载荷同上。
2. `event_process` 校验字段、构造 `Config_Content`；`believed_roots.count(root)` 为假 → 告警“未登记，已略过卸载”，返回。
3. `root_cache_clear(root)`：
   - 遍历 `config_routes` 的每个对象、每个目录对；`path_prefix_check(root.route, content.route) && path_prefix_check(root.config, content.config)` 命中则收集 `{object, content}` 到 `hits`。
   - 逐 `hit` 调 `route_unload(hit.second, hit.first)`：扫描该目录对的路由目录，逐文件 `route_file_unload(..., object, json())`，抹除该对象所有条目标记与文件头标记。
   - 遍历 `config_routes`：`std::erase_if` 删除命中前缀的目录对；对象集合空了删对象。
   - 遍历 `config_files`：`std::erase_if` 删除 `config_path` 以 `root.config` 为前缀的文件；对象空了删对象。
4. `believed_roots.erase(root)`。

**结果**：可信根下的所有对象缓存与磁盘标记被清除，目录登记被移除。之后同一可信根可重新 `Believed_Root/Load`，重新扫描并重新投递（旧标记已抹除 / 盐值相同但条目已删，两种条件都保证不误跳过）。

## 附：待确认正文

【待确认：1】`材质加载器.h` 的字段注释称 `diffuse_map` / `normal_map` 是“相对 MTL 所在目录”的路径，但 `材质加载器.cpp` 的 `texture_path_read` 只做“取最后一个非选项 token”，既不拼接 MTL 目录，也不做规范化。以实现为准：路径原样保留，实际相对基准由调用方决定。需要确认注释是否应改为“原样保留”。

【待确认：2】`core/配置加载.cpp` 的 `object_config_deliver` 在 `event_terminal.send(...)` 之后没有检查返回值：单事件分支与多事件分支都把 `send` 结果丢弃，随后无条件写 `entry["dirty_mark"] = mark` 并返回 `true`。若中转站拒收（比如 ACL 校验失败），本模块仍会把该条目记为“已投递”，同进程内不再重试。需要确认是否应有“发送失败不写脏标记”的语义。

【待确认：3】`config_files` 的键是 `object → config_path`，`config_routes` 的键是 `object → Config_Content`，二者都不含“目录对”维度。同一对象在两个可信根下引用同一相对 `config_path` 时，内存缓存与 `object × file` 脏标记会互相覆盖：后加载的条目替换先加载的条目，先加载的目录对无法再凭缓存投递。需要确认这是预期约束（同一对象同一相对路径只允许一个来源）还是需要将目录对并入键。

【待确认：4】`path_safety_check` 的前缀检查是“逐节比较相对路径”。若外部事件传入的 `content.config` 本身是绝对路径（`Config_Content` 不禁止），则条目 `config_path` 也需为同根绝对路径才能通过；第 4 步 `base_dir_get() / suspect_path` 在 `suspect_path` 为绝对路径时会丢弃基目录（标准库语义）。当前防线是“目录对必须来自可信根事件”，但可信根事件本身也只校验字段非空、不校验目录对是否为相对基目录。需要确认是否要对可信根目录做“必须相对基目录且不含 `..`”的额外约束。

【待确认：5】glTF 外部资源的路径拼接：`fs_read` / `fs_size` 收到的是 tinygltf 拼好的字符串（`base_dir + uri`）。若 `gltf_path` 是相对路径，`base_dir` 也是相对路径，`string_to_path` 后按进程当前工作目录解释，而不是按可执行文件目录或 glTF 文件实际所在目录。配置线的基目录语义是“可执行文件目录”，资产线则没有统一基目录。需要确认资产路径的基准目录约定（进程工作目录 / 可执行文件目录 / 调用方保证绝对路径）。

【待确认：6】`file_read` 使用默认 `ifstream` 读取 JSON，未处理 UTF-8 BOM；若路由文件或配置文件以 BOM 开头，解析可能直接失败并报“文件格式非法”。同时 `route_file_write` 以 `dump(4)` 覆盖写回，不保留原文件缩进风格、字段顺序（`nlohmann::json` 默认按 `std::map` 排序键），也不追加行尾换行。需要确认是否接受“写回后文件被规范化重排”的行为。

【待确认：7】`accessor_range_get` 在 `accessor.count == 0` 时仍计算 `last_end = start + element_size` 并与 `buffer.size()` 比较；若空访问器的 `start` 恰好等于 buffer 末尾，会判定越界并使整份模型失败（而 `primitive_convert` 本会把“顶点数为零”的图元按 `skip` 处理）。需要确认空访问器是否应直接放行。

【待确认：8】`Mesh_Loader` / `Mtl_Loader` 的主文件路径既不做 `..` 检查，也不做“位于某根目录之下”的限制；`Gltf_Loader` 的主文件路径同样不做 `..` 检查，只有外部 buffer / 图像 URI 经 `fs_*` 做了 `..` 检查。三个加载器的路径安全性完全依赖调用方。需要确认资产加载是否也需要统一的“可信资产根”约束。

【待确认：9】OBJ / MTL 读取未处理 UTF-8 BOM：`Mesh_Loader` 遇到首行 `\xEF\xBB\xBFv ...` 时 `tag` 不等于 `"v"`，会被当作未知行跳过，导致首顶点丢失；`Mtl_Loader` 同理可能错过首个 `newmtl`。当前代码没有 BOM 剥离逻辑。需要确认是否应统一在文本行解析入口剥离 BOM。

【待确认：10】`Config_Loader` 的构造函数调用 `event_terminal.key().value()`；`key()` 返回 `std::optional<int64_t>`，若为空则 `.value()` 抛出 `std::bad_optional_access`，而本模块其他位置均以日志返回、不抛异常。需要确认 `key()` 是否保证必有值（例如首次调用即生成）。
