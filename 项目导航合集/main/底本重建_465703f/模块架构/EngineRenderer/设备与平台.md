# 设备与平台模块

本文件覆盖 EngineRenderer 的三个基础设施子目录：`Device`（Vulkan 实例 / 物理设备 / 逻辑设备 / 校验层）、`Platform`（SDL 视频子系统 / 窗口 / 表面 / 事件泵）、`Thread`（帧内粗粒度并行执行器）。三者共同构成渲染层「能拿到一块可用的 Vulkan 设备并持续产出 SDL 事件」的底座，上层交换链、内存、帧、管线等模块都建立在其返回值之上。

写作口径：只依据冻结快照 `465703f` 内的源码；文中所有路径均为相对工作区根；未读到的内容不写，推测处显式标注「推测」。

## 二、模块功能介绍

### 2.1 定位与存在理由

渲染层的一切 Vulkan 对象都必须挂在实例与逻辑设备上，而逻辑设备又必须先有一个可呈现的表面；表面来自平台窗口，窗口来自 SDL 视频子系统。这三个层次互相咬合，无法由任何单一「渲染器」源文件干净地承担，于是被切成三个子目录：

- `Device` 负责「Vulkan 设备侧」：实例、调试信使、物理设备、逻辑设备、图形 / 呈现队列，以及设备能力的少量查询出口（各向异性、LOD 偏置）。
- `Platform` 负责「窗口系统侧」：SDL 视频子系统、窗口、`VkSurfaceKHR`、事件泵与窗口状态标志。
- `Thread` 负责「帧内并行」：一个默认关闭的粗粒度工作线程池，把「逐元素只写自己槽位」的纯 CPU 循环按块分派。

存在理由可以归结为三条：

1. **呈现链的硬依赖**：`vkGetPhysicalDeviceSurfaceSupportKHR` 要求表面已存在，因此实例必须先于设备创建，设备必须先于表面之外的所有渲染对象创建。把这段顺序收敛在单一模块里，避免上层各自拼装。
2. **第三方类型的隔离**：`vulkan.h` 与 `SDL3/SDL.h` 只出现在本层「实现细节」头里（`设备上下文.h`、`平台上下文.h`、`校验层配置.h`），公共头不包含它们，层外看不到 `VkDevice` / `SDL_Window`。
3. **失败回退的可控性**：初始化期任何一步失败都要求「不留下半初始化状态」。三个类都提供幂等的 `destroy`，析构兜底，上层只需按逆序调用即可。

### 2.2 Device 子模块负责什么

- 创建 `VkInstance`（固定请求 `VK_API_VERSION_1_3`），按调用方给出的扩展清单启用实例扩展。
- 决定校验层是否真正启用：请求开启且运行时确实安装了 `VK_LAYER_KHRONOS_validation` 才启用；否则降级为关闭并告警。
- 校验层启用时建立 `VkDebugUtilsMessengerEXT`，并把校验消息按严重级别转投引擎日志。
- 枚举物理设备，按「图形队列族 + 呈现队列族 + `VK_KHR_swapchain`」过滤，再按类型权重与本地显存容量打分选优。
- 创建逻辑设备：声明去重后的队列族（每族 1 个队列、优先级 1.0），启用 Vulkan 1.3 的 `dynamicRendering` 与 `synchronization2`，按支持情况启用 `samplerAnisotropy` 与 `shaderDemoteToHelperInvocation`，启用 `VK_KHR_swapchain`。
- 取图形 / 呈现队列（族内 0 号），并记录采样器各向异性上限与最大 LOD 偏置绝对值。
- 提供只读 getter 供上层取句柄、队列族索引、队列与能力标志。

不负责：交换链、图像与内存分配（VMA）、命令池、帧同步、命令录制、管线。这些模块只消费 `Device_Context` 给出的句柄。

### 2.3 Platform 子模块负责什么

- 初始化 SDL 视频子系统（`SDL_InitSubSystem(SDL_INIT_VIDEO)`，引用计数语义），创建带 `SDL_WINDOW_VULKAN` 的窗口。
- 提供实例扩展清单（`SDL_Vulkan_GetInstanceExtensions`），这是 SDL 侧 `VK_KHR_surface` 等扩展的唯一来源。
- 在实例建立后创建 `VkSurfaceKHR`（`SDL_Vulkan_CreateSurface`），并记录借用实例句柄以便销毁。
- 每帧轮询 SDL 事件，只维护三个主机侧标志（退出 / 待重建 / 最小化），并可选地把每个原始事件转发给上层回调。
- 提供窗口尺寸（像素）、尺寸设置、全屏切换、DPI 缩放与原生窗口句柄查询。

不负责：交换链重建决策、最小化挂起策略、输入语义、UI 事件分发。事件泵只置标志；「尺寸变化后重建交换链」由上层帧链路统一决策（每帧最多一次）。

### 2.4 Thread 子模块负责什么

- 维护 0..64 个工作线程；默认 0，即完全不启动线程。
- 提供同步的 `ranges_run(total, min_chunk, body)`：把 `[0, total)` 切成互不重叠的块，调用线程与工作线程共同以原子游标领取；返回时全部块必已完成。
- 提供启停、线程数查询、活跃判定与累计派发次数观测。

不负责：任务排队、跨帧任务、异步回调、结果合并。池本身不含队列：一次只有一个在途任务，且调用方阻塞到任务收束。

### 2.5 对外职责边界与关键约束

| 约束 | 内容 | 落点 |
| --- | --- | --- |
| 初始化两段化 | 实例先建；设备必须等表面就绪后再建 | `设备上下文.h` 类注释、`build_instance` / `build_device` |
| 表面先于设备 | 呈现队列族查询依赖表面 | `物理设备选择.cpp` `build_physical_device` 前置检查 |
| 平台先于设备销毁 | 销毁表面需要实例仍在途；设备销毁会连带销毁实例 | `平台上下文.cpp` `destroy`、调用方 `渲染器.cpp` `shutdown` |
| 第三方类型不出层 | Vulkan / SDL 头只在实现细节头中包含 | 三个模块头部的包含注释 |
| 单线程调用 | 三个类的公开接口均不保证线程安全，由上层同一线程调用 | 类注释与调用点 |
| 线程池默认关闭 | `render_threads = 0` 时 `ranges_run` 退化为调用线程整段执行 | `线程池.h` 注释、`作业分派.cpp` |
| 失败不硬崩 | 校验层缺失、调试信使入口缺失、各向异性不支持均降级告警 | `实例创建.cpp`、`校验层配置.cpp`、`逻辑设备创建.cpp` |

### 2.6 与上层消费者的关系

上层唯一持有者与编排者是 `Renderer::Impl`（`Engine/EngineRenderer/src/render/Renderer/core/渲染器实现.h`），按声明顺序持有 `Platform_Context platform;`、`Device_Context device;`、`Thread_Pool thread_pool;`。`Renderer::init` 的编号步骤直接对应本模块的调用次序：①`platform.build` → ②`platform.instance_extensions_get` → ③`device.build_instance` → ④`platform.surface_build` → ⑤`device.build_device`；线程池在 ⑧ 段按 `config.render_threads` 启动，并交给帧模块（`frame.thread_pool_set(&thread_pool)`）。

`Renderer::frame_render`（每帧入口）先调 `platform.events_pump()`，随后读 `platform.close_requested()` / `platform.minimized()` / `platform.window_size_get` / `platform.resized_consume()` 决定挂起与交换链重建。

## 三、模块公开接口

本节只列头文件中真实存在的声明。所有声明均位于 `namespace engine`。三个类都禁用拷贝；`Device_Context` 与 `Platform_Context` 的拷贝赋值同样禁用，因此隐式移动构造也一并被抑制（声明拷贝构造即阻止隐式移动生成）。

### 3.1 Device_Context（`Device/设备上下文.h`）

#### 3.1.1 构造与生命周期

| 签名 | 语义 | 前置 / 失败行为 |
| --- | --- | --- |
| `Device_Context(void) = default;` | 不创建任何 Vulkan 对象；成员按初值表置空 | 无 |
| `~Device_Context(void);` | 内部调用 `destroy()`，保证资源不泄漏 | 无 |
| `Device_Context(const Device_Context&) = delete;` | 禁止拷贝（持有句柄与队列） | 编译期拒绝 |
| `Device_Context& operator=(const Device_Context&) = delete;` | 禁止拷贝赋值 | 编译期拒绝 |
| `bool build_instance(const std::vector<const char*>& instance_extensions, bool enable_validation);` | 第一段：创建实例；校验层启用时同时挂接调试信使创建信息并补建信使 | 扩展清单元素须在 `vkCreateInstance` 期间有效（调用方保证字符串为静态或长寿命）；重复调用无前置保护（见 §六 6.12） |
| `bool build_device(VkSurfaceKHR surface);` | 第二段：选物理设备 → 建逻辑设备 → 取队列 | `build_instance` 已成功；`surface` 非空；否则直接失败并返回假 |
| `void destroy(void);` | 逆序释放逻辑设备 → 调试信使 → 实例，并复位派生标志；幂等 | 可对半初始化状态调用 |
| `bool valid(void) const;` | 实例与逻辑设备均已建立时为真 | 只读 |

`build_instance` 的失败路径：`vkCreateInstance` 非 `VK_SUCCESS` 时经 `vk_result_check` 记 `error` 并返回 `false`；此时 `instance` 保持 `VK_NULL_HANDLE`。调试信使创建失败**不**导致 `build_instance` 失败，只记 `warn`。

`build_device` 的失败路径：表面为空、无物理设备、无满足条件的设备、`vkCreateDevice` 失败、缺少 `dynamicRendering` / `synchronization2`，均记 `error` 并返回 `false`；已选中的 `physical_device` / 队列族索引可能残留（见 §六 6.12）。

| 签名 | 语义 | 前置 / 失败行为 |

### 4.5 生命周期内的隐式辅助路径

除上述显式私有函数外，`destroy` / `threads_stop` 内部承担「部分初始化回退」职责：

- `Device_Context::destroy` 对 `device`、`debug_messenger`、`instance` 逐个判空后释放，因此可安全用于任一段失败后的回退。
- `Platform_Context::destroy` 对 `surface` 判空后调用 `vkDestroySurfaceKHR`，再无条件清空 `instance` 记录。
- `Thread_Pool::threads_stop` 在 `workers.empty()` 时直接返回，避免空池上的无谓唤醒与 join。

### 5.2 对象与所有权关系

```
Renderer::Impl
├── Platform_Context platform
│   ├── SDL_Window* window            [自有, SDL_DestroyWindow]
│   ├── VkSurfaceKHR surface          [自有, vkDestroySurfaceKHR(instance, ...)]
│   ├── VkInstance instance           [借用, 由 Device_Context 拥有]
│   ├── bool video_initialized        [SDL 子系统引用计数持有标记]
│   ├── bool close_flag / resize_flag / minimize_flag
│   └── event_callback + event_callback_data   [借用回调, 不拥有 user_data]
├── Device_Context device
│   ├── VkInstance instance           [自有, vkDestroyInstance]
│   ├── VkDebugUtilsMessengerEXT      [自有, 扩展入口销毁]
│   ├── VkPhysicalDevice              [借用, 实例枚举所得]
│   ├── VkDevice device               [自有, vkDestroyDevice]
│   ├── VkQueue graphics_queue        [借用, 随 device 失效]
│   ├── VkQueue present_queue         [借用, 随 device 失效]
│   └── family 索引 / 校验层与采样器派生值
└── Thread_Pool thread_pool
    ├── std::vector<std::thread> workers   [自有, join]
    ├── mutex + wake + done
    └── job_body(借用调用方栈) / job_total / job_chunk / job_cursor / pending_workers / job_generation
```

关键所有权结论：

1. **实例的拥有者是 `Device_Context`，`Platform_Context` 只借用同一句柄用于销毁表面**。这决定了销毁顺序：平台必须先于设备销毁。
2. **物理设备与队列均为借用句柄**，不单独释放；逻辑设备销毁即失效。
3. **`job_body` 不拥有可调用体**：它指向 `ranges_run` 调用方栈上的 `const std::function&`，同步语义保证任务收束前该对象一直存活。
4. **事件回调的 `user_data` 不拥有**：上层（`Renderer::init`）传入 `impl.get()`，销毁前必须 `event_forward_clear()`。

### 5.3 初始化与销毁顺序

初始化（`Renderer::init` 编号取自 `渲染器.cpp`）：

```
platform.build(width, height, title, hidden)          ①  SDL 视频子系统 + 窗口
platform.instance_extensions_get(...)                 ②  SDL 给出的实例扩展
device.build_instance(extensions, validation)         ③  VkInstance (+ 调试信使)
platform.surface_build(device.instance_get())         ④  VkSurfaceKHR
device.build_device(platform.surface_get())           ⑤  物理设备 + 逻辑设备 + 队列
memory / swapchain / frame / ...                      ⑥⑦⑧ 依赖前三步的句柄
thread_pool.threads_start(render_threads)             ⑧  0 则不启动
```

销毁（`Renderer::shutdown` 尾部）：

```
thread_pool.threads_stop()         工作线程先停，后续模块销毁不被工作线程访问
... 其余模块逆序 ...
platform.event_forward_clear()     解除事件泵到 UI 通道的桥接
platform.destroy()                 销毁表面（需要实例在途）→ 窗口 → 视频子系统
device.destroy()                   销毁逻辑设备 → 调试信使 → 实例
```

### 5.4 线程归属

| 对象 / 动作 | 归属线程 | 依据 |
| --- | --- | --- |
| `Device_Context` 全部公开接口 | 调用线程（渲染主线程） | 类注释与 `Renderer::init` / `shutdown` 单线程编排 |
| `Platform_Context` 全部公开接口 | 调用线程 | `events_pump` 每帧由 `frame_render` 调用 |
| `Thread_Pool::threads_start` / `threads_stop` / `ranges_run` | 调用线程 | 启停与派发均由主线程发起 |
| `worker_main` / `chunks_run`（工作线程侧） | 工作线程 | 只访问任务登记与 `job_body` 指定的数据 |
| 池的作业体 | 由消费者决定 | 纯 CPU 掩码写入（实例剔除 / 差异扫描）与帧模块的次级命令缓冲录制 |

`Thread_Pool` 本身不调用任何 Vulkan 函数；它只提供执行能力。作业体内是否触碰 Vulkan 由消费者（`Renderer` 的 CPU 掩码路径为否；`Frame` 的并行录制为是，录进次级命令缓冲）决定。

### 5.5 数据流

- **扩展清单流**：`Platform_Context::instance_extensions_get` 从 SDL 取 `VK_KHR_surface` 等扩展 → `Renderer::init` 局部 `vector<const char*>` → `Device_Context::build_instance` → `instance_extensions_assemble` 追加 `VK_EXT_debug_utils` → `VkInstanceCreateInfo::ppEnabledExtensionNames`。整条链上字符串指针均为静态生命周期（SDL 内部表 / 字面量），`build_instance` 不做深拷贝。
- **句柄流**：`device.instance_get()` → 表面创建；`platform.surface_get()` → 物理设备筛选与逻辑设备创建；`device.physical_device_get()` / `device_get()` / `graphics_family_get()` / `graphics_queue_get()` / `present_family_get()` / `present_queue_get()` → 内存、交换链、帧、管线、计算、UI 通道。
- **事件流**：`SDL_PollEvent` → `event_callback`（若有）→ `Renderer` 注册的 lambda → `Input_Aggregator::event_feed` 与 `Ui_Channel_Context::event_dispatch`；同时 `events_pump` 自身更新三个标志。
- **并行数据流**：主线程写任务登记（`job_body` / `job_total` / `job_chunk` / `job_cursor` / `pending_workers` / `job_generation`）→ `wake.notify_all` → 工作线程与主线程共同 `fetch_add` 领取块 → 工作线程递减 `pending_workers` → 归零 `done.notify_all` → 主线程清空 `job_body`。

## 六、模块设计 / 实现细节

签名见 §三，本节只写「为什么这样实现」与可落地的坑。

### 6.1 两段式初始化：实例先行、设备待表面

`build_instance` 只创建实例与调试信使；`build_device` 才选物理设备并建逻辑设备。原因写在类注释里：呈现队列族必须用 `vkGetPhysicalDeviceSurfaceSupportKHR` 查询，而该调用要求表面已存在；表面又必须用实例创建（`SDL_Vulkan_CreateSurface` 需要 `VkInstance`）。因此合法顺序只有「实例 → 表面 → 设备」，无法压成一次调用。落点：`设备上下文.h` 类注释、`实例创建.cpp`、`逻辑设备创建.cpp`、`物理设备选择.cpp` 的前置检查。

### 6.2 物理设备选择偏好：类型权重压过显存

`device_score` 的权重表：

| `properties.deviceType` | `type_weight` |
| --- | --- |
| `VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU` | 30000 |
| `VK_PHYSICAL_DEVICE_TYPE_INTEGRATED_GPU` | 20000 |
| `VK_PHYSICAL_DEVICE_TYPE_VIRTUAL_GPU` | 10000 |
| `VK_PHYSICAL_DEVICE_TYPE_CPU` | 1000 |
| 其它 / 未知 | 500 |

显存加成 = `local_bytes / (1024 * 1024)` 后**封顶 9999**，其中 `local_bytes` 只累加带 `VK_MEMORY_HEAP_DEVICE_LOCAL_BIT` 的堆。源码注释称封顶值「小于最小类型权重差 10000」，使大显存核显无法反超独显；但按实际权重表，最小值差并非 10000（虚拟 GPU 10000 与 CPU 1000 相差 9000，CPU 1000 与默认 500 相差 500）。因此该不变式只对「独显 30000 vs 核显 20000」成立；极大显存的 CPU / 未知类型设备可能在分数上接近甚至超过虚拟 GPU（见【待确认：9】）。打分不做浮点运算，避免平台差异。

选择是「严格大于才替换」（`if (score > best_score)`），同分时保留先枚举到的设备（驱动枚举顺序），结果稳定且可复现。另外必须先过三条件：有图形族、对该表面有呈现族、支持 `VK_KHR_swapchain`；缺一即 `continue`，不进入打分。

### 6.3 队列完备性与并发配置

- 图形族取「首个带 `VK_QUEUE_GRAPHICS_BIT` 的族」，不做专用图形族优先；呈现族取「首个对该表面 `supported == VK_TRUE` 的族」。两者可以相同。
- `build_device` 对族集合去重：先放图形族，仅当呈现族不同才追加；同一队列族重复声明会触发校验层报错，故必须去重。
- 每族只请求 **1 个队列**（`queueCount = 1`），优先级统一 `1.0f`。所有 `VkDeviceQueueCreateInfo::pQueuePriorities` 指向同一个函数局部 `float queue_priority`，在 `vkCreateDevice` 调用期间有效，无需为每族复制。
- 取队列固定取族内 0 号（`vkGetDeviceQueue(device, family, 0, ...)`），与 `queueCount = 1` 一致。
- 未校验 `VkQueueFamilyProperties::queueCount`：理论上队列族数量属性可能为 0，此时请求 1 个队列会失败（见【待确认：6】）。

### 6.4 Vulkan 1.3 是硬门槛，不做旧路径回退

实例与设备统一请求 `VK_API_VERSION_1_3`。设备创建前用 `VkPhysicalDeviceFeatures2` + `pNext = &VkPhysicalDeviceVulkan13Features` 查询，两个特性缺一即 `error` 返回假：

- `dynamicRendering`：本层走 `vkCmdBeginRendering`，不使用传统 `VkRenderPass`。
- `synchronization2`：本层走 `vkQueueSubmit2`，不使用 `vkQueueSubmit`。

实现明确不做回退，理由是把「两套路径」的成本挡在初始化期，而不是散落到每帧。`VkPhysicalDeviceVulkan13Features` 同时作为 `VkDeviceCreateInfo::pNext` 启用，`pEnabledFeatures` 仍单独指向 `VkPhysicalDeviceFeatures`（传统特性），二者可共存。

### 6.5 可选特性的降级策略

| 特性 | 支持时 | 不支持时 |
| --- | --- | --- |
| `features.samplerAnisotropy` | 置 `VK_TRUE`，`anisotropy_enabled = true`，记录 `maxSamplerAnisotropy` | 保持关闭，`warn`，不硬失败；上限保持 `1.0f` |
| `VkPhysicalDeviceVulkan13Features::shaderDemoteToHelperInvocation` | 置 `VK_TRUE` | 不启用，`warn`；含 `discard` 的片元着色器可能触发校验告警，但仍可运行 |

`shaderDemoteToHelperInvocation` 的启用动机写在源码：当前 `glslc` 对 `discard` 会声明 `DemoteToHelperInvocation` 能力，未启用时校验层报 `VUID-VkShaderModuleCreateInfo-pCode-08740`。这是「为保持校验层 0 消息」的兼容性开关，不是功能需求。

### 6.6 采样器极限的记录与防御

`build_device` 在建逻辑设备前记录两个极限：

- `max_sampler_lod_bias = properties.limits.maxSamplerLodBias`，若非 `> 0.0f` 则归零。写成 `if (!(x > 0.0f))` 而非 `if (x <= 0.0f)` 是为了同时吃掉 `NaN`。
- `max_sampler_anisotropy` 仅在 `anisotropy_enabled` 时读取，且若非 `> 1.0f` 则归 1.0f。上限小于 1 属驱动异常，归 1 保证采样器参数合法。

上层（`Texture` 的采样器创建）按这两个上限钳制用户参数，避免校验层报越界。`destroy` 复位了各向异性标志与上限，但**未**复位 `max_sampler_lod_bias`（见【待确认：1】）。

### 6.7 校验层的三重折算

`build_instance` 的启用条件是 `enable_validation && validation_layer_available()`，即「请求开启」且「运行时确有该层」。原因是：请求一个不存在的层会让 `vkCreateInstance` 直接返回 `VK_ERROR_LAYER_NOT_PRESENT`，整个渲染器初始化失败；而校验层只是调试设施，不该成为运行前提。因此探测失败时降级关闭并 `warn`（源码内标注 K19）。Release 下由调用方（`Renderer::init` 的 `#ifdef NDEBUG`）强制传假，形成第二道闸。

`validation_layer_available` 自身也做了防御：层数为 0 直接返回假；两段枚举任一失败返回假；逐项字符串比较用 `std::string` 而非 `strcmp`，避免空指针风险（`layerName` 是定长数组，必然有终止符）。

### 6.8 调试信使的双重挂接

信使有两条建立路径，配合使用：

1. **预挂接**：校验层启用时，把 `VkDebugUtilsMessengerCreateInfoEXT` 挂到 `VkInstanceCreateInfo::pNext`。这样「实例创建 / 销毁过程本身」产生的校验消息也能被捕获——此刻独立信使尚不存在。
2. **后补建**：`vkCreateInstance` 成功后调 `debug_messenger_create` 建立持久信使。

`debug_info` 与 `layer_name` 都声明在 `build_instance` 函数作用域，保证 `vkCreateInstance` 调用期间指针有效；注释特意强调不要指向临时量造成悬垂。补建失败只 `warn`、不回退实例（否则等于让调试设施阻断渲染）。

### 6.9 消息订阅裁剪：只收警告与错误

`debug_messenger_info_create` 订阅 `WARNING | ERROR`，不订阅 `VERBOSE | INFO`。源码理由是信息级消息量大会淹没引擎日志。因此 `debug_message_callback` 的 `else`（`logger.info`）分支在实际订阅范围内不可达，属于兜底。消息类型三种全开（`GENERAL | VALIDATION | PERFORMANCE`），性能警告也会进日志。

### 6.10 校验回调恒返回 `VK_FALSE`

按 Vulkan 规范，调试回调返回 `VK_TRUE` 会中止触发该消息的调用（通常导致 `VK_ERROR_VALIDATION_FAILED_EXT`）。本层一律返回假，保证「校验消息只记录、不改变执行流」。`message_types` 与 `user_data` 未使用，`pUserData` 固定 `nullptr`。

### 6.11 统一的 Vulkan 结果检查出口

本模块所有返回 `VkResult` 的调用都经 `src/render/Renderer/core/结果检查.h` 的 `vk_result_check(result, operation)`（签名见该头，本文件不重复）。它的分流：`VK_SUCCESS` 为真；`VK_ERROR_OUT_OF_DATE_KHR` / `VK_SUBOPTIMAL_KHR` / `VK_TIMEOUT` 记 `debug` 并返回假；其余记 `error` 并附带调用点字符串与结果码名称。

两个例外：`vkGetPhysicalDeviceQueueFamilyProperties`、`vkGetPhysicalDeviceProperties`、`vkGetPhysicalDeviceMemoryProperties`、`vkGetPhysicalDeviceFeatures2`、`vkGetDeviceQueue`、`vkDestroy*` 返回 `void`，不进入检查。`present_family_query` 对单族查询失败选择 `continue` 而非整体失败——单个族查询失败不排除其它族可用。

### 6.12 销毁顺序、幂等与残留状态

`Device_Context::destroy` 的顺序是「逻辑设备 → 调试信使 → 实例」，即严格逆创建序（信使晚于实例、早于逻辑设备建立）。队列句柄随逻辑设备一起失效，故与 `device` 一起清零；`graphics_family` / `present_family` 一并归 0。物理设备是借用句柄，直接置空。

幂等性靠逐项判空实现：任意一步失败后调用 `destroy` 都不会重复释放。析构再调一次也安全（成员已空）。

两处残留值得注意：

1. `max_sampler_lod_bias` 未在 `destroy` 中复位（`anisotropy_enabled` / `max_sampler_anisotropy` 已复位）。源码注释称「destroy 须复位全部派生标志（R-DEV-04）」，与该字段的实际处理不一致；若同一对象 destroy 后重建到另一台设备前被查询，会读到上一台设备的 LOD 上限。见【待确认：1】。
2. `build_instance` / `build_device` 均无「已构建」前置检查：重复调用会直接覆盖 `instance` / `device` 句柄，旧对象泄漏。当前唯一调用者是 `Renderer::init`（有 `initialized` 闸），故未暴露；但作为公开接口属于隐式约定。见【待确认：2】。

另：`physical_device` 在 `build_device` 的失败路径上可能已被写入（`build_physical_device` 成功后 `vkCreateDevice` 失败），此时 `valid()` 仍为假（`device` 为空），但 `physical_device_get()` 会返回非空。上层以 `valid()` 为准，不要单看物理设备句柄。

### 6.13 SDL 头包含顺序

`平台上下文.h` 的包含顺序是 `SDL3/SDL.h` → `<vulkan/vulkan.h>` → `<SDL3/SDL_vulkan.h>`。注释给出的原因是：`vulkan.h` 会定义 `VULKAN_CORE_H_`，令 `SDL_vulkan.h` 跳过其自带的 Vulkan 句柄 `typedef`，避免 `VkSurfaceKHR` 等被重复定义。`SDL_vulkan.h` 未被 `SDL.h` 带入，故必须显式包含。

这两个头都属「实现细节」：只被本层 `.cpp` 与层内模块头包含，不进公共头；`cmake/对外接口.cmake` 的私有包含根保证层外拿不到这些类型。

### 6.14 不调用 `SDL_SetMainReady`

`window_create` 的注释解释了为什么不调：本层是静态库、不接管入口点（不使用 `SDL_main`）。SDL 仅在 `SDL_MAIN_NEEDED` 平台（如 GDK）要求初始化前调 `SDL_SetMainReady`；Windows 属 `SDL_MAIN_AVAILABLE`，`SDL_MainIsReady` 默认为真。调用它还会引入 `SDL_main.h`，把 `main` 重定义为 `SDL_main`，反而污染宿主程序入口。源码标注 K18。

### 6.15 窗口标志组合

`SDL_WindowFlags flags = SDL_WINDOW_VULKAN;`

- `!hidden` 时追加 `SDL_WINDOW_RESIZABLE`：可见窗口允许用户拖拽改尺寸；事件泵会置 `resize_flag`，帧链路据此重建交换链。
- `hidden` 时追加 `SDL_WINDOW_HIDDEN`，且**不**追加 `SDL_WINDOW_RESIZABLE`：无头用例仍创建真实窗口与真实表面（否则拿不到呈现队列族），只是不显示。

标题按 UTF-8 传入（SDL3 直接接收 UTF-8），宽高由 `uint32_t` 转 `int`。失败时先 `SDL_QuitSubSystem` 再复位 `video_initialized`，不留半初始化状态；`build` 外层再调 `destroy()` 兜底。

### 6.16 事件泵只置标志，不碰 Vulkan

`events_pump` 明确把「交换链重建」与「最小化挂起」留给上层帧链，理由有两条：

1. 重建交换链要求「每帧最多一次」（源码标注 K8）。事件泵一帧可能收到多个尺寸事件，若逐个重建会产生多次重建与资源抖动。
2. 事件泵不知道「当前是否有在途帧」。重建必须走延迟销毁队列（帧模块），不能在平台层直接做。

因此 `events_pump` 的处理集合是五个事件类型、四类状态：

| `event.type` | 动作 |
| --- | --- |
| `SDL_EVENT_QUIT` | `close_flag = true;` |
| `SDL_EVENT_WINDOW_RESIZED` | `resize_flag = true;` |
| `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED` | `resize_flag = true;`（HiDPI 跨不同 DPI 显示器时像素尺寸变化） |
| `SDL_EVENT_WINDOW_MINIMIZED` | `minimize_flag = true;` |
| `SDL_EVENT_WINDOW_RESTORED` | `minimize_flag = false;` |
| 其它 | 忽略（但仍先转发回调） |

转发顺序是「先回调、后 switch」：上层能拿到与标志更新同一批原始事件，且回调内的输入处理不会影响本层标志语义。未处理 `SDL_EVENT_WINDOW_CLOSE_REQUESTED`（见【待确认：3】）。

### 6.17 「待重建」标志的三种置位来源与一次性消费

置位来源：

1. 事件泵收到 `RESIZED` / `PIXEL_SIZE_CHANGED`。
2. `window_size_set` 成功后**显式**置位。原因写在头文件：隐藏窗口下 SDL 不一定派发尺寸变化事件，若只依赖事件，隐藏窗口的尺寸变更将永远不重建交换链。
3. `fullscreen_set` 成功后置位。全屏切换通常伴随客户区尺寸变化，显式置位避免依赖事件时序。

消费方式是 `resized_consume()`：读后立刻清零。上层（`frame_render`）在消费后还要求宽高非零才真正重建，避免用 0×0 建链（源码标注 K7）。

标志为普通 `bool`，无原子性；所有访问都在渲染主线程，故无需同步。

### 6.18 最小化挂起

`minimize_flag` 只由事件泵维护。`frame_render` 在 `close_requested() || minimized()` 时清空待绘制项与实例并直接返回真：不消费绘制项，避免连续挂起期间内存无限累积；同时不触碰交换链，避免以 0×0 尺寸重建。

`window_size_get` 在窗口为空或 `SDL_GetWindowSizeInPixels` 失败时返回 `0, 0`，与挂起语义配合：上层看到 0 尺寸即不重建。

### 6.19 表面的生命周期绑定

三处绑定关系：

- **创建依赖窗口与实例**：`surface_build` 先判窗口非空，再记录 `this->instance`，然后 `SDL_Vulkan_CreateSurface`。表面属于「窗口 × 实例」的交叉产物。
- **销毁依赖实例**：`destroy` 用记录的借用实例调 `vkDestroySurfaceKHR`，随后清空实例记录。若实例已先销毁（顺序错误），该调用是未定义行为；`Renderer::shutdown` 因此把 `platform.destroy()` 排在 `device.destroy()` 之前，并写了注释。
- **重复创建短路**：表面已存在时打 `warn` 并返回真，不重建、不更新实例记录。若调用方换了实例再调，会得到旧表面 + 旧实例记录（见【待确认：5】）。

另：SDL3 为表面销毁提供 `SDL_Vulkan_DestroySurface`，头注释建议在 `SDL_DestroyWindow` 之前销毁表面；本实现改用 `vkDestroySurfaceKHR(instance, surface, nullptr)`（与 SDL 包装等价，且同样在窗口销毁之前），未调用 SDL 包装。

### 6.20 全屏与 DPI 的边界处理

- `fullscreen_get` 用 `SDL_GetWindowFlags(window) & SDL_WINDOW_FULLSCREEN`；SDL3 只有这一个全屏标志位。
- `fullscreen_set` 失败只 `warn` 不 `error`：隐藏窗口下后端可能拒绝全屏，这是预期内的降级，不是故障。
- `display_scale_get` 用 `SDL_GetWindowDisplayScale`（逐窗口），非 `SDL_GetDisplayContentScale`（逐显示器）。多显示器 / 高 DPI 下逐窗口值才准确；非正值归一为 1，避免上层除零。

### 6.21 线程池的作业粒度

`ranges_run` 的块长算法（按执行顺序）：

```
min_chunk == 0            → min_chunk = 1
worker_count == 0
  或 total < min_chunk*2  → body(0, total) 整段执行，返回
chunk = total / (worker_count * 4)      向下取整
chunk < min_chunk         → chunk = min_chunk
chunk * 2 > total         → chunk = total / 2
```

设计意图：

- **×4 倍块数**（每线程约 4 块）用于负载均衡：各块耗时不等时，块数多于线程数可减少尾部空转。
- **`min_chunk` 下限**保证块不太碎，避免每块一次原子操作与函数调用开销大于计算本身。
- **`total / 2` 上限**保证至少有 2 块，否则「并行」退化为单块、白白唤醒线程。
- **`total < min_chunk * 2` 退化**：元素太少时线程唤醒与同步开销超过收益，直接由调用线程整段执行。调用方把 `min_chunk` 同时当作「并行阈值」使用（实例剔除默认 256、差异扫描默认 512）。

块划分只影响耗时，不影响结果：块区间由原子游标切分，互不重叠且拼齐 `[0, total)`。前提是作业体「只写自己区间对应的槽位」，不得跨区间写入；这是接口注释写明的硬约束。

### 6.22 代号唤醒协议

工作线程用「任务代号」而非「队列非空」判断是否有新任务：

- `worker_main` 维护线程本地的 `seen_generation`（启动时 0）。
- `wake.wait(lock, ...)` 的谓词是 `stopping || job_generation != seen_generation`。
- 醒来后若 `stopping` 为真直接 `return`；否则把 `seen_generation = job_generation` 再执行 `chunks_run`。

这样即使工作线程尚未进入第一次 `wait`（刚 `emplace_back` 完），也能因为 `job_generation` 已从 0 变为 1 而跳过等待直接干活，不会丢失唤醒。若换成「布尔 has_job + 消费后清零」，在「置位 → 线程尚未 wait → 消费清零」的竞态下会永久睡死。

### 6.23 收尾计数与等待

- 派发时 `pending_workers = worker_count`（即当前线程集合大小）。
- 每个工作线程执行完本轮全部块后，在 `mutex` 保护下 `--pending_workers`；减到 0 时 `done.notify_all()`。
- 调用线程自己也执行 `chunks_run()`，但不计入 `pending_workers`。
- 调用线程最后 `done.wait(lock, [this]{ return pending_workers == 0; })`，然后清空 `job_body`。

调用线程参与执行是刻意的「不吃空饷」：若调用方只等待，工作线程数 N 时实际只有 N 个执行者；参与后是 N+1（近似），并且主线程在最后一块上不会纯阻塞。`done.wait` 的谓词形式保证不会丢唤醒（即使 worker 在调用线程进入 wait 之前就已全部完成）。

### 6.24 背压：没有队列，也就没有积压

本池没有任务队列，理由是 `ranges_run` 的同步语义：

- 调用方在返回前必定等到全部块完成，因此不存在「上一帧任务未完成、下一帧又派发」的积压。
- 由此 `shutdown` 可以直接 `threads_stop()`，无需先排空队列（源码注释明确这一点）。
- 背压表现为「调用方阻塞」：作业越长，主线程等待越久。若作业体内部再等待其它线程，可能形成等待环；当前消费者只做纯 CPU 掩码 / 命令录制，不阻塞。

`threads_stop` 的停止协议：在 `mutex` 内置 `stopping = true`，解锁后 `notify_all`，逐个 `join`，清空集合，再复位 `stopping / job_body / pending_workers`。源码注释要求「无在途任务时才可安全调用」——若在派发中途停止，工作线程会从 `worker_main` 直接返回，`pending_workers` 永不归零，调用线程将永久阻塞在 `done.wait`。这是隐式约定而非运行时防护。

### 6.25 异常策略

`std::thread` 构造没有 `nothrow` 形式，系统资源不足时会抛 `std::system_error`。`threads_start` 因此只捕获 `std::system_error`：

- 记 `warn`（含已建线程数与 `what()`）；
- 调 `threads_stop()` 回收已建线程；
- 返回假。

不捕获其它异常，也不为内存分配加异常处理。这与项目「内存分配用 `std::nothrow`」的规则不冲突：此处异常来自线程创建这一系统调用，不是 `new`。

### 6.26 线程数上限与默认值

`threads_start` 把 `count` 钳到 64；`ranges_run` 的上游（`Renderer::init` / `render_threads_set`）也各钳一次 64。上限来自「工作线程数超过 CPU 核心数意义有限」的粗粒度定位，而非架构限制。默认 0 意味着「默认单线程」，任何并行收益必须先由上层显式开启，保证与引入并行前逐字节一致（`线程池.h` 口径①②）。

### 6.27 派发计数的观测口径

`dispatch_count` 只在真正走并行分支时自增（`worker_count > 0` 且 `total >= min_chunk*2`）；单线程退化的任务不计。自增发生在 `mutex` 内，读取（`dispatch_count_get`）无锁。因为所有读写都在调用线程，且派发只在 `ranges_run` 内发生，实际不存在并发访问；若未来从其它线程读取则需改为原子。上层用「派发前后差值」把派发归入三类用途（实例剔除 / 差异扫描 / 缓存回写）。

### 6.28 日志级别与文本约定

| 场景 | 级别 | 示例前缀 |
| --- | --- | --- |
| 实例 / 设备 / 表面 / 窗口建成 | `info` | `实例创建::`、`逻辑设备创建::`、`平台上下文::` |
| 资源销毁 | `debug` | `设备上下文:: 销毁逻辑设备`、`平台上下文:: 销毁窗口` |

### 6.29 局部命名空间使用.h 的边界

三个 `局部命名空间使用.h` 都只做 `using`：

- Device：`std::string`、`std::vector`（`校验层配置.cpp` 用 `string` 比较层名）。
- Platform：`std::string`、`std::vector`（`build` 标题与扩展清单）。
- Thread：`std::function`、`std::size_t`、`std::vector`。

`.cpp` 中仍可见 `std::mutex`、`std::condition_variable`、`std::unique_lock`、`std::lock_guard`、`std::atomic`、`std::thread`、`std::system_error`、`std::memory_order_relaxed` 的全限定写法——这些未进 `using` 清单，属于既有风格，不视为不一致。

### 6.30 Vulkan 对象数量与开销

单个 `Device_Context` 创建的对象总数是固定的：1 个实例 + 0/1 个调试信使 + 1 个逻辑设备，外加 2 个借用句柄（物理设备、队列）。队列请求数 = 去重后的队列族数（1 或 2），每族 1 个；同族时图形与呈现句柄指向同一个 0 号队列。初始化期不做任何枚举缓存：物理设备、队列族、扩展属性都在需要时现场枚举，因只发生一次，未引入常驻容器。

## 七、模块运行链路详例

### 7.1 链路一：实例与设备创建

调用方：`Renderer::init`（`Engine/EngineRenderer/src/render/Renderer/core/渲染器.cpp`）。

1. `Renderer::init` 校验宽高非零、`frame_overlap ∈ [1,3]`，随后 `Renderer_Config effective = config;`，在 `#ifdef NDEBUG` 下强制 `effective.validation = false`。
2. `impl->platform.build(effective.width, effective.height, effective.title, effective.hidden)` → `Platform_Context::window_create`：`SDL_InitSubSystem(SDL_INIT_VIDEO)` → 组合 `SDL_WINDOW_VULKAN | (hidden ? SDL_WINDOW_HIDDEN : SDL_WINDOW_RESIZABLE)` → `SDL_CreateWindow`。成功记 `info`，失败记 `error` 并逆序退出子系统。
3. `impl->platform.instance_extensions_get(instance_extensions)` → `SDL_Vulkan_GetInstanceExtensions(&count)`；空指针记 `error` 返回假，`count == 0` 记 `warn` 但返回真。此前 `impl->input.window_set(impl->platform.window_get())` 已把输入聚合器绑定到窗口（源码中紧跟 `platform.build`）。
4. `impl->device.build_instance(instance_extensions, effective.validation)`：
   - `use_validation = enable_validation && validation_layer_available()`；请求但未安装时 `warn` 降级。
   - `validation_enabled = use_validation`。
   - 填 `VkApplicationInfo`（`pApplicationName = "白银纪元"`、`pEngineName = "SilverEra Renderer"`、版本 `0.1.0`、`apiVersion = VK_API_VERSION_1_3`）。
   - `extensions = instance_extensions_assemble(instance_extensions, use_validation)`。
   - 校验层启用时：`debug_info = debug_messenger_info_create()`，`create_info.pNext = &debug_info`，`enabledLayerCount = 1`，`ppEnabledLayerNames = &layer_name`。
   - `vk_result_check(vkCreateInstance(&create_info, nullptr, &instance), "vkCreateInstance")`；失败即返回假。
   - 记 `info`（Vulkan 主/次/补丁版本）。
   - 校验层启用时 `debug_messenger_create(instance, &debug_messenger)`，失败仅 `warn`。
5. `impl->platform.surface_build(impl->device.instance_get())` → 见 §7.2。
6. `impl->device.build_device(impl->platform.surface_get())`：
   - `build_physical_device(surface)`：见 §7.2 的候选过滤与打分。
   - 队列族去重：`unique_families = {graphics_family, (present_family != graphics_family) ? present_family : 略}`。
   - 每族 `VkDeviceQueueCreateInfo{sType, queueFamilyIndex, queueCount = 1, pQueuePriorities = &queue_priority}`。
   - `vkGetPhysicalDeviceFeatures2` 取 `dynamicRendering` / `synchronization2` / `shaderDemoteToHelperInvocation`；前两者缺一即 `error` 返回假。
   - `VkPhysicalDeviceFeatures features{}`，支持时置 `samplerAnisotropy = VK_TRUE` 并记上限。
   - `VkPhysicalDeviceVulkan13Features enabled_13{sType, dynamicRendering = VK_TRUE, synchronization2 = VK_TRUE, 可选 shaderDemoteToHelperInvocation}`。
   - `VkDeviceCreateInfo{pNext = &enabled_13, pQueueCreateInfos, pEnabledFeatures = &features, enabledExtensionCount = 1, ppEnabledExtensionNames = {VK_KHR_SWAPCHAIN_EXTENSION_NAME}}`。
   - `vk_result_check(vkCreateDevice(...), "vkCreateDevice")`；失败返回假。
   - `vkGetDeviceQueue(device, graphics_family, 0, &graphics_queue)`、`vkGetDeviceQueue(device, present_family, 0, &present_queue)`。
   - 记 `info`：族索引、各向异性开关与上限。
7. 结果：`device.valid()` 为真；上层取句柄构建内存 / 交换链 / 帧。任一步失败时 `Renderer::init` 调 `shutdown()`，其尾部按「平台先于设备」销毁。

### 7.2 链路二：窗口到表面创建

调用方：`Renderer::init` 的 ④ 段（表面必须早于设备）。

1. `Platform_Context::surface_build(VkInstance instance)`：
   - `window == nullptr` → `error`「表面创建失败，窗口尚未创建」→ 返回假。
   - `surface != VK_NULL_HANDLE` → `warn`「表面已存在，跳过重复创建」→ 返回真（不更新实例记录）。
   - `this->instance = instance;`（借用，供后续销毁）。
   - `SDL_Vulkan_CreateSurface(window, instance, nullptr, &surface)`：
     - 失败 → `error` 附 `SDL_GetError()` → `this->instance = VK_NULL_HANDLE` → 返回假。
     - 成功 → `info`「Vulkan 表面已创建」→ 返回真。
2. 表面就绪后，`Device_Context::build_device` → `build_physical_device(surface)`：
   - 表面为空 → `error` 返回假（前置硬检查）。
   - `vkEnumeratePhysicalDevices` 两段式枚举；数量为 0 → `error`「未发现任何支持 Vulkan 的物理设备」。
   - 逐候选：
     - `graphics_family_query`：首个 `VK_QUEUE_GRAPHICS_BIT` 族；失败 `continue`。
     - `present_family_query`：逐族 `vkGetPhysicalDeviceSurfaceSupportKHR`，失败族 `continue`，首个 `VK_TRUE` 即命中；失败 `continue`。
     - `device_extension_supported(VK_KHR_SWAPCHAIN_EXTENSION_NAME)`；不支持 `continue`。
     - `device_score`：类型权重 + 显存 MB（封顶 9999）；严格大于才替换候选。
   - 无候选 → `error`「所有物理设备均不满足「图形队列族 + 呈现队列族 + VK_KHR_swapchain」」→ 返回假。
   - 写入 `physical_device / graphics_family / present_family`，记 `info`（设备名、类型、得分、两族索引）。
3. 结果：`platform.surface_get()` 非空且 `device.physical_device_get()` 与两族索引可用；交换链与呈现队列从此可建。

补充（表面销毁）：`Renderer::shutdown` 先 `platform.event_forward_clear()`，再 `platform.destroy()` → `vkDestroySurfaceKHR(instance, surface, nullptr)` → `window_destroy()`（`SDL_DestroyWindow` → `SDL_QuitSubSystem`）→ 复位三个标志；随后 `device.destroy()` 才销毁实例。顺序颠倒会导致表面销毁使用已失效的实例。

### 7.3 链路三：线程池作业分派

以「实例级视锥剔除」与「实例缓冲差异扫描」两条消费者为例（均在 `渲染器.cpp`）。

**启动**（`Renderer::init` ⑧ 段）：

1. 读 `effective.render_threads`，归一到 `≤ 64`。
2. `render_threads > 0` 时 `impl->thread_pool.threads_start(render_threads)`：
   - `threads_stop()` 先清旧线程；
   - `count == 0` 直接真；
   - 在 `mutex` 下复位 `stopping = false`、`job_generation = 0`；
   - 逐线程 `workers.emplace_back(&Thread_Pool::worker_main, this)`；抛 `std::system_error` 则 `warn` + `threads_stop()` + 返回假。
3. 失败回落单线程（`render_threads = 0`），只影响耗时不影响结果。
4. `impl->frame.thread_pool_set(&impl->thread_pool)` 把同一池交给帧模块做次级命令缓冲并行录制。

**派发**（`ranges_run(total, min_chunk, body)`）：

1. `total == 0` → 真；`min_chunk == 0` → 1。
2. `worker_count = workers.size()`；若为 0 或 `total < min_chunk * 2` → `body(0, total)` 单线程整段，返回真（`dispatch_count` 不增）。
3. 计算 `chunk`：`total / (worker_count * 4)`，再钳 `≥ min_chunk`、必要时钳 `≤ total / 2`。
4. 在 `mutex` 下登记：`job_body = &body`、`job_total`、`job_chunk`、`job_cursor.store(0, relaxed)`、`pending_workers = worker_count`、`++job_generation`、`++dispatch_count`。
5. `wake.notify_all()`。
6. 调用线程立即 `chunks_run()`：循环 `begin = job_cursor.fetch_add(job_chunk, relaxed)`；`begin >= job_total` 返回；`end = min(begin + job_chunk, job_total)`；`(*job_body)(begin, end)`。
7. 工作线程侧：`worker_main` 的谓词因 `job_generation != seen_generation` 成立而醒来，`seen_generation = job_generation`，执行同一个 `chunks_run`；完成后在 `mutex` 下 `--pending_workers`，归零时 `done.notify_all()`。
8. 调用线程 `done.wait(lock, pending_workers == 0)`；随后 `job_body = nullptr`，返回真。

**消费者侧**：

- 实例剔除：`count >= cull_parallel_min` 且 `thread_pool.active()` 时，作业体写 `instanced_cull_mask[instance]`（每实例只写自己槽位）；随后的可见实例压缩仍单线程按原序扫描，故绘制顺序与单线程一致。
- 差异扫描：`instance_count >= instance_scan_parallel_min` 时，作业体写 `instance_changed_mask[index]`；随后的连续段扫描与分段缓冲写入仍单线程，故上传区间不变。
- 缓存回写：同一阈值下并行复制 `instance_cache[*]`，每实例独占一段，结果与逐元素拷贝一致。

**停止**：`Renderer::shutdown` 首步 `threads_stop()`；`render_threads_set` 切换线程数时也是「先 `threads_stop`，再按新值 `threads_start`」。因派发同步，调用时不存在在途任务。
