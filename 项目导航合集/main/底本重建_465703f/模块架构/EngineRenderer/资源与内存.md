## 二、模块功能介绍

本模块是 EngineRenderer 全部「VMA 管理的 GPU 资源」的唯一入口与生命周期归属：经本模块创建的 `VkBuffer`、`VmaAllocation`、`VkImage`、`VkImageView`、`VkSampler`，其诞生与归还都在这里（交换链图像由 Swapchain 子域经 `vkCreateSwapchainKHR` 创建，不属本模块）。层内其余模块与渲染器门面自身都只调用本模块的创建 / 销毁接口来获得或归还这类资源，不直接调用 VMA。

**Memory 子域是分配与上传的底座。**`Memory_Context` 是层内唯一持有 `VmaAllocator` 的对象，同时兼任「资源创建器」与「一次性同步上传器」：缓冲创建、图像创建、视图创建、缓冲写读、图像上传 / 读回 / mip 生成全部由其方法完成。该子域不关心资源语义（不知道哪块缓冲是顶点还是索引），只保证内存类型选择、布局转换与命令提交的正确性。

**Mesh 子域负责 CPU 网格数据的收编。**`Mesh_Context` 把 `Mesh_Data`（顶点集 + 索引集）压成「一个设备本地缓冲 + 一条记录」：顶点区在缓冲前段、索引区紧随其后，一次分配、一次上传完成。它同时提供 12 个程序化图元生成器，产出可直接喂给 `mesh_create` 的 `Mesh_Data`，因此「几何来源」既可以是文件（OBJ）也可以是代码。

**Texture 子域负责图像侧的等价职责。**`Texture_Context` 把 RGBA8 像素（内存 / 文件 / 立方体 / 程序生成）变成「图像 + 全 mip 视图 + 共享采样器 + 记录」，并独占全层唯一共享采样器的状态（寻址、mip 过滤、LOD、各向异性）。纹理的全部图像操作（含 mip 链生成、分级更新与读回）都转交 Memory 子域完成，本子域只做语义校验与记录维护。

**Asset 子域负责「按路径复用」。**它把「路径 → 句柄」的映射与引用计数集中在一处：同一路径只创建一次资源，释放按计数归零才真正卸载；另提供一条 `std::async` 后台解析 + 主线程建资源的异步网格加载通道。资产缓存不拥有 GPU 资源，它只拥有「登记表」，真正的创建与卸载仍走渲染器门面。

**不负责的部分：**本模块不做交换链图像的创建与回收（Swapchain 子域负责）、不做描述符写入、不做管线创建、不做帧同步（不参与 semaphore / present 链）、不调度延迟销毁（`mesh_detach` / `texture_detach` 只把归还责任交出去，压帧队列由 Frame 子域执行）、不做材质字段换算与材质对象创建（`Mtl_Material` 只解析为纯字段）。

**存在理由：**把资源创建与销毁收敛到单一所有者，使「谁创谁销」的规则可执行：句柄由调用方持有，销毁一律回到本类；销毁分配器时若有存活分配，VMA 会报告泄漏，这条硬约束反过来强制所有调用方走本模块的销毁路径。

**关键约束：**
1. 三个上下文的生命周期统一为 `build → 使用 → destroy`，`destroy` 幂等，析构兜底。
2. `build` 有前置条件：`Mesh_Context::build` 要求 `Memory_Context::valid()`，`Texture_Context::build` 同时要求内存就绪与逻辑设备非空。
3. 句柄一律「自 1 起，0 为无效，下标 = 句柄 − 1」，记录槽一经分配不复用（详见 §六.9）。
4. 上传接口全部为同步阻塞（提交后 `vkWaitForFences` 无限等待），不进入帧命令流。

## 三、模块公开接口

### 3.1 `Memory_Context`（`Memory/内存上下文.h`）

#### 3.1.1 类型形状与特殊成员

| 成员 | 签名 | 语义 |
| --- | --- | --- |
| 构造 | `Memory_Context(void) = default` | 只置空成员，不创建分配器。 |
| 析构 | `~Memory_Context(void)` | 调用 `destroy()` 兜底，避免分配器泄漏。 |
| 拷贝 | `Memory_Context(const Memory_Context&) = delete` | 持有 `VmaAllocator` 与设备句柄，禁止拷贝。 |
| 赋值 | `Memory_Context& operator=(const Memory_Context&) = delete` | 同上。 |

#### 3.1.2 生命周期接口

| 签名 | 语义 / 前置条件 / 失败行为 |
| --- | --- |
| `bool build(VkInstance instance, VkPhysicalDevice physical_device, VkDevice device, uint32_t graphics_family, VkQueue graphics_queue)` | 先记录 5 个句柄，再 `build_allocator`；分配器创建失败时调用 `destroy()` 回退并返回假，不留半初始化。成功打日志「内存上下文:: 内存基础设施构建完成」。 |
| `void destroy(void)` | 幂等。顺序：若 `device` 非空则先销毁 `upload_fence`、`upload_pool`；再 `vmaDestroyAllocator`；最后清空 `graphics_queue / graphics_family / device / physical_device / instance`。**不销毁**其下缓冲 / 图像（由调用方先行销毁）。 |
| `bool valid(void) const` | `allocator != VK_NULL_HANDLE && device != VK_NULL_HANDLE`。 |
| `VmaAllocator allocator_get(void) const` | 返回分配器句柄，供上层创建自有资源时复用。 |
| `VkDevice device_get(void) const` | 返回逻辑设备句柄。 |

#### 3.1.3 缓冲接口

| 签名 | 语义 / 前置 / 失败 |
| --- | --- |
| `bool buffer_create(VkBuffer& buffer_out, VmaAllocation& alloc_out, VkDeviceSize size, VkBufferUsageFlags usage, bool host_visible, bool sequential_write = false, VkMemoryPropertyFlags required_flags = 0)` | 创建缓冲与其内存。`host_visible = true` 时按 `sequential_write` 选「仅顺序写」或「主机随机读写」，两者都带 `VMA_ALLOCATION_CREATE_MAPPED_BIT`（持久映射）；`host_visible = false` 时申请 `DEDICATED_MEMORY`。`required_flags` 作为 `requiredFlags` 硬约束（0 = 不限制）。内存类型固定 `VMA_MEMORY_USAGE_AUTO`，共享模式 `VK_SHARING_MODE_EXCLUSIVE`。未构建则日志报错返回假；VMA 失败则把两个出参置空返回假。成功打「缓冲已建立（N 字节，主机可见/设备本地）」。 |
| `void buffer_destroy(VkBuffer buffer, VmaAllocation alloc)` | 任一参数为空或分配器缺失则直接返回（幂等）；否则 `vmaDestroyBuffer`。 |
| `bool buffer_write(VkBuffer buffer, VmaAllocation alloc, const void* data, VkDeviceSize size, VkDeviceSize offset)` | 句柄 / 分配器 / `data` 任一缺失则日志报错返回假；否则 `vmaMapMemory` → `memcpy(mapped+offset)` → `vmaFlushAllocation(offset,size)` → `vmaUnmapMemory`。仅对主机可见缓冲有意义。 |
| `bool buffer_read(VkBuffer buffer, VmaAllocation alloc, void* data, VkDeviceSize size, VkDeviceSize offset)` | 同上，但先 `vmaInvalidateAllocation` 再 `memcpy`，用于校验与调试。 |
| `bool buffer_map(VkBuffer buffer, VmaAllocation alloc, void*& mapped_out)` | 取持久映射指针。先置 `mapped_out = nullptr`；上下文无效 / 缓冲或分配为空 / `pMappedData == nullptr` 时返回假。 |

#### 3.1.4 图像接口

| 签名 | 语义 / 前置 / 失败 |
| --- | --- |
| `bool image_create(VkImage& image_out, VmaAllocation& alloc_out, uint32_t width, uint32_t height, VkFormat format, VkImageUsageFlags usage, uint32_t mip_levels = 1, VkSampleCountFlagBits samples = VK_SAMPLE_COUNT_1_BIT, uint32_t array_layers = 1, VkImageCreateFlags flags = 0)` | 固定 `VK_IMAGE_TYPE_2D`、`VK_IMAGE_TILING_OPTIMAL`、`VK_IMAGE_LAYOUT_UNDEFINED`、`SHARING_MODE_EXCLUSIVE`、`extent = {w,h,1}`；`array_layers == 0` 视为 1；分配一律 `DEDICATED_MEMORY`。未构建或 `mip_levels == 0` 时日志报错返回假。 |
| `void image_destroy(VkImage image, VmaAllocation alloc)` | 幂等；`vmaDestroyImage`。 |
| `bool image_view_create(VkImageView& view_out, VkImage image, VkFormat format, VkImageAspectFlags aspect, uint32_t level_count = 1, VkImageViewType view_type = VK_IMAGE_VIEW_TYPE_2D, uint32_t layer_count = 1, uint32_t base_mip_level = 0)` | 视图固定 `baseArrayLayer = 0`、`levelCount = level_count`、`layerCount = layer_count`（0 视为 1）；仅校验图像非空、设备非空、`level_count != 0`。 |
| `void image_view_destroy(VkImageView view)` | 视图或设备为空则返回；否则 `vkDestroyImageView`。图像本体由 `image_destroy` 负责。 |

#### 3.1.5 上传与读回接口

| 签名 | 语义 / 前置 / 失败 |
| --- | --- |
| `bool upload_buffer(VkBuffer dst_buffer, const void* data, VkDeviceSize size, VkDeviceSize offset)` | 每次临时创建 host-visible + `TRANSFER_SRC` 的暂存缓冲，写入后经一次性命令提交一次 `vkCmdCopyBuffer`（`dstOffset = offset`），最后无论成败销毁暂存缓冲。参数缺一即报错返回假。 |
| `bool upload_image(VkImage dst_image, const void* data, VkDeviceSize data_size, uint32_t width, uint32_t height, uint32_t row_pixels, uint32_t layer = 0)` | 暂存 + 三步命令：`UNDEFINED → TRANSFER_DST_OPTIMAL`（第 `layer` 层、第 0 级）→ `vkCmdCopyBufferToImage`（`bufferRowLength = row_pixels`，0 表示按 width 紧排）→ `TRANSFER_DST → SHADER_READ_ONLY_OPTIMAL`（同一层）。终态固定为着色器可读。 |
| `bool upload_image_region(VkImage dst_image, const void* data, uint32_t x, uint32_t y, uint32_t width, uint32_t height, uint32_t mip_level = 0)` | 源数据按 `width × height × 4` 字节计算（RGBA8 紧排）；三步命令在 `mip_level` 级、**第 0 层**：`SHADER_READ_ONLY → TRANSFER_DST` → 区域拷贝（`imageOffset = {x,y,0}`、`bufferRowLength = 0`）→ 恢复着色器可读。区域是否落在该级内由调用方保证。 |
| `bool image_readback(VkImage image, uint32_t width, uint32_t height, void* data, VkDeviceSize data_size)` | 等价于 `image_readback_region(image, 0, 0, width, height, data, data_size)`（第 0 级整幅）。 |
| `bool image_readback_region(VkImage image, uint32_t x, uint32_t y, uint32_t region_width, uint32_t region_height, void* data, VkDeviceSize data_size, uint32_t mip_level = 0)` | 暂存缓冲用途 `TRANSFER_DST`（主机可见、非顺序写）；三步：`SHADER_READ_ONLY → TRANSFER_SRC` → `vkCmdCopyImageToBuffer` → 恢复着色器可读；随后 `buffer_read` 取回。要求 `data_size ≥ region_width × region_height × 4`，否则报错返回假。 |
| `bool image_generate_mips(VkImage image, uint32_t width, uint32_t height, uint32_t mip_levels)` | 等价于 `image_generate_mips_from(image, 0, width, height, mip_levels)`。 |
| `bool image_generate_mips_from(VkImage image, uint32_t base_level, uint32_t base_width, uint32_t base_height, uint32_t mip_levels)` | 以 `base_level` 为源逐级线性 blit 降采样至 `mip_levels-1`；一次提交、一次栅栏等待。`mip_levels ≤ 1` 或 `base_level + 1 ≥ mip_levels` 时先返回真（空操作），**此时不校验图像有效性**。其余前置（上下文、图像、队列）不满足则报错返回假。 |

## 六、模块设计 / 实现细节

### 6.1 VMA 分配器封装与策略

1. **单例编译单元。**`VMA实现.cpp` 是全项目唯一 `#define VMA_IMPLEMENTATION` 处；注释明确「全项目必须有且只有一个编译单元定义该宏，否则会多重定义」。该文件不写任何代码，只负责就近展开，便于将来改 `VMA_STATIC_VULKAN_FUNCTIONS` / `VMA_DYNAMIC_VULKAN_FUNCTIONS`。
2. **API 版本锁 1.0。**`build_allocator` 固定 `vulkanApiVersion = VK_API_VERSION_1_0`；不启用内存预算、环形上传缓冲、延迟分配（注释「第一版不启用任何 VMA 特性开关」）。这意味着没有 `VMA_ALLOCATOR_CREATE_*` 标志，也没有 `VmaBudget` 查询。
3. **显式专用分配为主。**设备本地缓冲（`host_visible = false`）与**全部图像**都带 `VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT`，即一资源一 `VkDeviceMemory`，放弃子分配复用。理由在注释中写明：设备本地资源「长命且体积大，不做子分配复用」。代价是大批小网格 / 小纹理会带来较多设备内存对象（推测：未做实测）。
4. **主机可见缓冲走 AUTO + 映射。**`VMA_MEMORY_USAGE_AUTO` 搭配 `HOST_ACCESS_SEQUENTIAL_WRITE`（上传暂存）或 `HOST_ACCESS_RANDOM`（读写缓冲），并统一带 `MAPPED` 位 → 持久映射。这类分配**没有** `DEDICATED_MEMORY` 位，故 VMA 可将其子分配到较大块中；`buffer_map` 通过 `vmaGetAllocationInfo` 取 `pMappedData`，正是依赖 `MAPPED` 位。
5. **`required_flags` 是硬约束。**`buffer_create` 把 `required_flags` 直接写入 `VmaAllocationCreateInfo::requiredFlags`（0 = 不限制）；头文件注明「第二百五十二轮用于要求主机一致内存」，即调用方可借此强制 `VK_MEMORY_PROPERTY_HOST_COHERENT_BIT`。
6. **映射 / 解映射的成本。**`buffer_write` / `buffer_read` 每次都 `vmaMapMemory` → `memcpy` → `vmaFlushAllocation` / `vmaInvalidateAllocation` → `vmaUnmapMemory`；由于分配是持久映射的，注释称「持久映射下不释放映射本体」，故 unmap 实际不解除持久映射。刷洗仅覆盖 `[offset, offset+size)` 区间。
7. **销毁分配器不回收子资源。**`destroy()` 只销毁栅栏 / 命令池 / 分配器；注释警告「销毁分配器不会连带销毁其下的缓冲 / 图像，那些必须由调用方先行销毁，否则会泄漏（VMA 会在销毁分配器时报告仍有存活分配）」。这就是整个模块「谁创谁销、销毁一律回到本类」的来源。

### 6.2 上传批次的暂存区策略

1. **一资源一暂存缓冲，即用即毁。**`upload_buffer`、`upload_image`、`upload_image_region`、`image_readback_region` 四个入口各自 `buffer_create` 一个临时缓冲，函数结束前 `buffer_destroy`（成功与失败路径都销毁）。
2. **上传暂存选「仅顺序写」。**三处上传都以 `buffer_create(..., host_visible = true, sequential_write = true)` 创建，注释理由为「上传暂存」只需顺序写入，可让 VMA 选更合适的内存类型。
3. **读回暂存不带 `sequential_write`。**`image_readback_region` 用 `buffer_create(..., true)`（默认 `sequential_write = false`），即按「主机随机读写」处理，因为读回方向是设备写、主机读，需要 invalidate。
4. **没有环形 / 持久暂存。**`build_allocator` 未启用 VMA 的环形上传缓冲；每次上传都新建暂存 → 一次 `vkQueueSubmit` → 等待。这是明确的性能取舍：实现简单、无需管理偏移与帧边界，代价是每次上传都有一次缓冲分配 / 销毁与一次 GPU 同步等待。
5. **命令池跨次复用但栅栏必须复位。**`upload_resources_ensure` 只创建一次 `TRANSIENT` 命令池与未触发态栅栏；`upload_submit_once` 每次先 `vkResetCommandPool(device, pool, 0)`（回收上次命令缓冲），再用 `vkAllocateCommandBuffers` 重新分配 1 个 primary 命令缓冲。注释点明「命令池与栅栏由 Memory_Context 持有并跨多次上传复用，不再逐次创建 / 销毁，避免每资源一次的命令池与栅栏开销」。
6. **同步语义。**提交不带信号量，直接 `vkWaitForFences(VK_TRUE, UINT64_MAX)`；失败即返回假，但暂存缓冲已在 `upload_buffer` 等调用方处销毁。等待超时为无限，若队列卡死调用线程会阻塞（推测：无超时保护）。

### 6.3 屏障策略（按函数）

| 函数 | 屏障 / 阶段 | 说明 |
| --- | --- | --- |
| `upload_image` | `TOP_OF_PIPE → TRANSFER`：`UNDEFINED → TRANSFER_DST_OPTIMAL`，`srcAccessMask = 0`，`dst = TRANSFER_WRITE`，范围 `{COLOR, mip 0, 1 级, layer, 1 层}` | 旧内容不保留（第 `layer` 面逐面上传）。 |
| 同上 | `TRANSFER → FRAGMENT_SHADER`：`TRANSFER_DST → SHADER_READ_ONLY`，`src = TRANSFER_WRITE`，`dst = SHADER_READ`，范围同为第 `layer` 层 | 注释记录「第二百一十八轮修正」：此前固定 `baseArrayLayer = 0`，立方体贴图第 1..5 面会停留在传输目标布局，触发 `VUID-vkCmdDraw-None-09600`；现改为与上传层一致。 |
| `upload_image_region` | `FRAGMENT_SHADER → TRANSFER`：`SHADER_READ_ONLY → TRANSFER_DST`，范围 `{COLOR, mip_level, 1, 0, 1}` | 旧布局必须是着色器可读（由创建路径或 mip 生成建立）。 |
| 同上 | `TRANSFER → FRAGMENT_SHADER`：`TRANSFER_DST → SHADER_READ_ONLY`，同一级 | 前后保持默认终态。 |
| `image_readback_region` | `FRAGMENT_SHADER → TRANSFER`：`SHADER_READ_ONLY → TRANSFER_SRC` | 第 `mip_level` 级、第 0 层。 |
| 同上 | `TRANSFER → FRAGMENT_SHADER`：`TRANSFER_SRC → SHADER_READ_ONLY` | 读回后恢复，便于继续采样。 |
| `image_generate_mips_from` | 每级两条：源级 `FRAGMENT_SHADER → TRANSFER`（`SHADER_READ_ONLY → TRANSFER_SRC`，第 `level-1` 级）；目标级 `UNDEFINED → TRANSFER_DST` | 目标级又单独以 `TOP_OF_PIPE → TRANSFER` 再提交一次同一 `target_barrier`（重复，见「附：待确认正文 3」）。 |
| 同上 | 每级一条 `TRANSFER → FRAGMENT_SHADER`：`TRANSFER_DST → SHADER_READ_ONLY`（第 `level` 级） | 使目标级可被下一轮当源级再次转入传输源。 |
| 同上 | 循环后一条：`TRANSFER → FRAGMENT_SHADER`：`TRANSFER_SRC → SHADER_READ_ONLY`，范围 `{COLOR, base_level, mip_levels-1-base_level, 0, 1}` | 把「曾作 blit 源」的 `base_level .. mip_levels-2` 一并恢复；末级仅作目标级故不纳入。注释明确：否则后续采样这些级会触发布局校验错误。 |

共性约定：所有图像的 `aspectMask` 固定为 `COLOR_BIT`，`srcQueueFamilyIndex = dstQueueFamilyIndex = VK_QUEUE_FAMILY_IGNORED`（不跨队列转移），深度 / 模板图像不由本模块的这批上传函数处理（推测：深度图只创建、不在此上传）。

### 6.4 mip 生成策略

1. **完整链。**`texture_create_from_memory` 以 `mip_levels = floor(log2(max(宽,高))) + 1` 建图像，`image_generate_mips` 从第 0 级起逐级减半到 1×1。
2. **逐级线性滤波 blit。**`vkCmdBlitImage(..., VK_FILTER_LINEAR)`，源 = 上一级、目标 = 本级，同图像不同级；目标尺寸 `source > 1 ? source / 2 : 1`（整除，非 2 的幂尺寸也按向下取整）。
3. **一次提交完成全链。**整个循环录制在同一个命令缓冲里，只等一次栅栏；没有逐级提交。
4. **从中间级重生成。**`image_generate_mips_from` 用 `base_level` 作源、`base_width / base_height` 作起始尺寸；`texture_update_region_level` 在更新第 `level` 级后用它重建 `level+1 .. 末级`，避免低级别仍是旧内容。
5. **空操作边界。**`mip_levels ≤ 1` 或 `base_level + 1 ≥ mip_levels` 直接返回真；此时若 `image` 无效也不会报错（见「附：待确认正文 5」）。
6. **目标级旧布局用 `UNDEFINED`。**即便目标级已被写入过（重生成场景），仍以 `UNDEFINED` 作旧布局（内容丢弃），这是合法的「不保留旧内容」写法，但会使重生成的低级别内容整体被覆盖（符合预期）。
7. **立方体贴图不生成 mip。**`texture_create_cube` 固定 `mip_levels = 1`，注释为「简易 IBL 以 LOD 0 采样近似」，因此该路径没有 `TRANSFER_SRC` 用途位。

### 6.5 纹理解码格式与尺寸口径

1. **stb 单实现单元。**`core/纹理解码.cpp` 是全层唯一 `#define STB_IMAGE_IMPLEMENTATION` 处，第三方头以 `#pragma warning(push/disable: 4244 4456 4457 4996/pop)` 包裹，注释称「本层要求零本层新增警告」。
2. **强制 4 通道。**`stbi_load_from_memory(bytes, size, &w, &h, &channels, 4)`，与内存像素路径的 RGBA8 紧排口径一致；解码后仅校验 `width > 0 && height > 0`。
3. **文件读取走 UTF-8 路径。**`path_from_utf8` 用 `std::u8string(reinterpret_cast<const char8_t*>(...))` 构造 `std::filesystem::path`，注释标「第四百二十八轮」，目的是支持中文目录。文件用 `std::ios::binary | std::ios::ate` 打开并 `tellg` 取长度，再 `seekg(0, beg)` 整块读入；空文件（`byte_count <= 0`）直接拒绝。
4. **格式固定 sRGB RGBA8。**创建路径统一 `VK_FORMAT_R8G8B8A8_SRGB`；没有做通道数保留、没有做线性空间变体、没有压缩格式（BCn）路径。
5. **解码缓冲的即时释放。**无论 `texture_create_from_memory` 成功与否，`stbi_image_free(decoded)` 都会执行；失败时把 `handle_out` 归 0。
6. **mip 与采样分离。**纹理总是生成完整 mip 链，但默认 `mip_filter = false`（`max_lod = -1` → 采样器 `maxLod = 0`），因此在默认状态下令牌链不参与采样；只有显式 `sampler_state_set` 打开后才生效。这是「默认行为与本版次之前一致」的兼容设计。
7. **棋盘格是程序纹理基线。**`texture_create_checkerboard` 生成 `0x40` / `0xC0` 两档灰度 RGBA8，转交同一内存路径（因此也带 mip 链）。

### 6.6 网格顶点布局与缓冲切分

1. **顶点步长 32 字节。**`Vertex = { float position[3]; float uv[2]; float normal[3]; }`，注释明确「步长 32 字节，与渲染层着色器顶点输入一致」；`normal` 缺省零向量，由 OBJ 解析器在缺 `vn` 时按三角形面积加权补齐。
2. **一个缓冲装两段。**`mesh_create` 以 `total_bytes = sizeof(Vertex) × 顶点数 + 4 × 索引数` 建一块 `VERTEX_BUFFER | INDEX_BUFFER | TRANSFER_DST` 的设备本地（`DEDICATED`）缓冲；顶点区自 0 起，索引区自 `index_offset = sizeof(Vertex) × 顶点数` 起。
3. **对齐天然满足。**`sizeof(Vertex) = 32`，故 `index_offset` 是 4 的整数倍，满足 uint32 索引偏移对齐（注释明写「20 字节步长的整数倍」——该数字与实际 32 不符，见「附：待确认正文 4」）。
4. **主机侧先拼后传。**为把两段合并为一次 `upload_buffer`，代码先 `std::vector<uint8_t> combined(total_bytes)`，两次 `std::memcpy` 拼成连续内存，再一次性提交；失败则销毁刚建的缓冲。
5. **创建期校验。**`data.vertices.empty() || data.indices.empty()` 直接拒绝；逐索引用 uint32 遍历并比较 `index < data.vertices.size()`；分段校验「`index_count % 3 == 0`」与「`first_index + index_count ≤ indices.size()`」，任一不合法都销毁已建缓冲后返回假（注释特意点明「此时缓冲已创建，失败路径必须先销毁它」）。
6. **包围盒一次算定。**以 `vertices[0].position` 初始化上下界，再逐顶点逐轴取极值；更新顶点时只扩不缩（§6.7）。
7. **程序化图元共用同一数据形态。**12 个生成器都直接产出 `Mesh_Data`（顶点 / 索引），绕序统一「从外部看逆时针」，与管线 `frontFace = COUNTER_CLOCKWISE / cullMode = BACK` 自洽（`cube_generate` 注释）。多分段网格不由生成器产出（生成器只产出整段）。
8. **生成期预留容量。**多数生成器在建前 `reserve`（注释标「第八十五轮：减少生成期重分配」）；`icosphere_generate` 用 `std::unordered_map<uint64_t, uint32_t>` 以「低位索引 × 基数 + 高位索引」缓存中点，避免细分裂缝。

### 6.7 网格更新与包围盒保守扩张

1. **更新走上传而非映射。**`mesh_update_vertices` / `mesh_update_indices` 都调用 `upload_buffer`，即每次更新都新建暂存缓冲 + 一次同步提交；不直接在设备本地缓冲上映射（设备本地分配无 `HOST_ACCESS` 标志）。
2. **区间严格校验。**顶点更新要求 `first_vertex < vertex_count` 且 `count ≤ vertex_count - first_vertex`；索引更新同时要求 `first_index < index_count`、`count ≤ index_count - first_index`，且逐索引 `< vertex_count`。
3. **索引区不动 / 顶点区不动。**顶点更新只写 `[0, vertex_bytes)` 内偏移；索引更新只写 `[index_offset, index_offset + index_bytes)` 内偏移，互不影响。
4. **包围盒只扩不缩。**顶点更新后按新顶点逐轴扩展 `bounds_min / bounds_max`，注释理由「避免旧包围盒小于实际几何导致视锥剔除误剔」。代价是：顶点缩小后包围盒仍偏大，剔除变保守。
5. **更新前需等尽在途帧。**该约束在门面 `Renderer::mesh_update_vertices` 中执行（先 `impl->frame.frames_wait()` 再转交本模块），本模块自身不做帧同步。

### 6.8 纹理更新、读回与容量口径

1. **分级更新 + 下游重建。**`texture_update_region_level` 校验级号与区域后调 `upload_image_region`；若 `level + 1 < mip_levels` 立刻 `image_generate_mips_from` 重建下游。上游（更精细）级不受影响（注释明写）。
2. **级尺寸按右移。**`width >> level`、`height >> level`，结果 0 时钳到 1；与创建时 `floor(log2(...))+1` 的口径一致（非 2 的幂在低级别会提前到 1×1）。
3. **读回容量全部按 RGBA8 计。**整幅 = `w × h × 4`，区域 = `rw × rh × 4`，级 = `level_w × level_h × 4`；容量不足时：`texture_readback` / `texture_readback_region` 打日志报错，`texture_readback_level` / `texture_readback_region_level` 静默返回假（不一致，见「附：待确认正文 6」）。
4. **读回前后布局保持。**内存侧完成 `SHADER_READ_ONLY → TRANSFER_SRC → SHADER_READ_ONLY` 往返，故连续读回不需要外部重建布局。
5. **第 0 层限制。**`upload_image_region` / `image_readback_region` 的 `subresourceRange` 固定 `baseArrayLayer = 0, layerCount = 1`；对有 6 层的立方体贴图，分级更新 / 读回只作用于 +X 面（见「附：待确认正文 7」）。
6. **采样器状态切换的副作用。**`sampler_state_set` 销毁旧采样器并把全部有效记录改指新句柄；但**已写入的描述符集仍持有旧句柄**（头文件明写），故门面必须在切换后重新绑定纹理，否则采样仍按旧参数。

### 6.9 句柄管理与记录槽的隐式约定

1. **句柄不复用。**`handle_out = records.size()`，`records` 只 `push_back` 从不压缩；销毁只置 `valid = false`。因此句柄单调递增，旧句柄不会被新资源「意外复活」。
2. **越界即幂等。**所有查询与销毁函数先用 `handle == 0 || handle > records.size()` 判越界，再判 `valid`；销毁对无效句柄静默返回，不报错。
3. **`mesh_destroy` 复位不彻底。**它只清 `buffer / allocation / index_offset / index_count / valid`，`sections`、`vertex_count`、`bounds_min/max` 保留旧值；而 `mesh_detach` / `texture_destroy` / `texture_detach` 使用整体 `record = Mesh_Record{}` / `Texture_Record{}` 复位。后果：被 `mesh_destroy` 的槽仍持有 `sections` 的堆内存，直到 `destroy()` 清空整个 `records`（见「附：待确认正文 8」）。
4. **摘出即移交。**`mesh_detach` / `texture_detach` 把记录整体拷给调用方并把原槽置默认构造；本模块不再负责归还，调用方（门面）把缓冲 / 图像 / 视图压入帧延迟销毁队列。
5. **句柄类型不隔离。**网格是 `Mesh_Handle = uint64_t`、纹理是 `uint64_t`，两者数值空间独立，误用不会在本模块内被发现（会把另一类记录当作目标记录读取，但 `valid` 通常仍为真）。这是潜在的类型安全弱点（推测：门面封装降低了误用概率）。

### 6.10 资产缓存：键、命中、引用计数与失效

1. **键构造。**`缓存键构建(prefix, path)` → `"mesh:<path>"` / `"texture:<path>"`。归一化只做两件事：`'\\' → '/'`、ASCII 大写转小写（理由：「Windows 路径不区分大小写」）；非 ASCII 字节原样保留，故中文路径大小写不敏感语义不适用。
2. **键不做的归一化。**不去除 `./`、不折叠 `..`、不去尾部分隔符、不区分相对 / 绝对路径、不做长路径前缀处理。因此 `.\a.obj`、`a.obj`、`A.OBJ` 中前两者会得到不同键（后者与 `a.obj` 同键），同一文件可能被创建两次（见「附：待确认正文 9」）。
3. **缓存表按渲染器实例隔离。**`std::map<const Renderer*, 渲染器缓存> 缓存表` 是文件内静态；`缓存取值` 用 `operator[]`，**即使只查询也会为渲染器插入空条目**（`asset_cache_count` / 释放路径均有此副作用）。
4. **命中语义。**命中只 `refs += 1` 并返回原句柄，不触碰 GPU 资源；未命中才走门面创建。创建失败不入表（保持「失败不登记」）。
5. **引用计数无上限保护。**`refs` 为 `uint32_t`，直接 `+= 1` / `-= 1`，没有溢出检测；`refs > 1` 才减一，故不会减到 0 以下（除非外部绕过本 API 直接释放）。
6. **失效（归零）语义。**归零时先 `缓存.mesh.erase(it)`（使迭代器失效后不再使用），再 `renderer.mesh_unload(handle)`；后者走 `mesh_detach` + 帧延迟销毁，因此 GPU 资源不会立刻消失，而是延后 `in_flight_count + 1` 帧。
7. **未登记句柄的兼容。**释放时若表中找不到该句柄，直接调 `mesh_unload` / `texture_unload`，注释「兼容混用」。这使「非共享创建的资源」也能安全释放，但也意味着重复释放未登记句柄会重复 `detach`（第二次 `detach` 因记录无效返回假，门面直接返回，故无实际危害）。
8. **清表不卸载。**`asset_cache_clear` 只 `erase` 渲染器键，不遍历条目释放；注释要求「渲染器销毁后调用以释放登记」。若不调用，`缓存表` 会留下以已销毁 `Renderer*` 为键的条目；若新渲染器恰好分配到同一地址，旧条目会被命中并返回失效句柄（指针复用风险，见「附：待确认正文 10」）。
9. **线性查找。**释放按句柄遍历 `std::map` 的键值（注释「条目数很少，线性查找足够」）；没有建立「句柄 → 键」反向索引，故释放复杂度与条目数线性相关。

### 6.11 异步网格加载

1. **解析在后台、建资源在主线程。**`asset_mesh_async_load` 用 `std::async(std::launch::async, [state, path]{ return obj_mesh_load(path, state->data); })`；lambda 捕获 `state` 的 `shared_ptr` 与 `path` 的副本，故任务生命周期不依赖调用方栈。
2. **状态机四态。**`settled`（是否已取 future 结果）/ `parse_ok` / `built` / `handle`；轮询顺序：已 `built` → 幂等返回；`settled && !parse_ok` → 返回假（后续轮询仍假）；未 `settled` → `wait_for(0s)` 非阻塞查询，ready 时 `future.get()` 并置 `settled`。
3. **建资源分支。**解析成功后在主线程按 `state->data.sections` 是否为空选择 `renderer.mesh_load(handle, data)` 或 `renderer.mesh_load_sections(handle, data, sections.data(), count)`；成功后 `built = true` 并缓存句柄，后续轮询返回同一句柄。
4. **`renderer` 入参未被使用。**`asset_mesh_async_load` 内 `(void)renderer;`；解析不需要渲染器。这与同步接口签名保持一致，便于替换实现。
5. **异步资源不进缓存表。**`asset_mesh_async_poll` 成功建网格后**没有**登记到 `缓存表`，所以该句柄若走 `asset_mesh_release` 会落入「未登记 → 直接卸载」分支，失去引用计数保护（见「附：待确认正文 11」）。
6. **future 析构的阻塞风险。**`Asset_Async_Task` 只持有 `shared_ptr<void>`；若调用方在解析未完成时释放最后一个引用，`std::async` 返回的 future 在析构时会等待任务结束（`std::launch::async` 语义），表现为主线程卡顿（推测：取决于标准库实现，MSVC 下确实会阻塞）。
7. **线程安全边界。**`state->data` 由后台线程写、主线程在 `future.get()` 后读，靠 future 同步；`state->settled / parse_ok / built / handle` 只在主线程写，故注释明写「无需加锁」。

### 6.12 错误处理与日志策略

1. **统一入口。**创建 / 上传类实现文件（`分配器创建.cpp`、`缓冲创建.cpp`、`图像创建.cpp`、`上传批次.cpp`、`网格缓冲.cpp`、`纹理创建.cpp`、`采样器创建.cpp`、`纹理解码.cpp`）均包含 `src/render/Renderer/core/结果检查.h`，用 `vk_result_check(result, "前缀:: 动作")` 做结果判定与日志；日志对象为全局 `logger`（`info` / `error`）。`网格加载器.cpp` 只做数据生成，不含结果检查。
2. **日志前缀按文件命名。**`分配器创建::`、`缓冲创建::`、`图像创建::`、`上传批次::`、`网格上下文::`、`网格缓冲::`、`纹理上下文::`、`纹理创建::`、`纹理::`。注意日志前缀与实际函数归属不完全一致（例如 `buffer_write` 的失败日志用「缓冲创建::」前缀）。
3. **失败即回退。**创建类函数在任一步失败时按「逆序」销毁已建资源：图像 → 视图 → 采样器（`texture_create_*`）；缓冲（`mesh_create` 的分段校验失败；`upload_*` 的暂存缓冲）。无一例留下半初始化记录。
4. **参数错误与执行错误用同一返回通道。**均为 `bool` + 日志（部分读回接口静默返回假，见 §6.8 第 3 条），调用方无法从返回值区分「参数非法」「Vulkan 失败」。
5. **`vk_result_check` 的具体行为**在本模块之外（`Renderer/core/结果检查.h`），本文不展开。

### 6.13 生命周期与析构顺序

1. **三上下文析构均调 `destroy()`。**因此即便调用方忘记显式销毁，也能在栈展开时归还资源；但 `destroy()` 依赖 `device` / `allocator` 仍在途，故析构顺序仍须遵守「子先父后」。
2. **门面 `shutdown()` 顺序（与本模块相关的部分）。**`text.shutdown()` → `mesh.destroy()` → `font.destroy()` → `texture.destroy()` → `render_target.destroy()` → … → `swapchain.destroy()` → `memory.destroy()`。注释明确「网格缓冲依赖内存模块，须先于 memory 销毁」「纹理依赖设备与内存，须先于两者销毁」。
3. **`Memory_Context::destroy()` 自身顺序。**先栅栏、再命令池（二者不依赖分配器），后分配器；这样即便分配器创建失败（`build` 回退调用 `destroy`），也不会漏掉上传资源（此时它们通常为空）。
4. **纹理销毁不碰共享采样器。**`texture_destroy` 只归还图像与视图；共享采样器由 `Texture_Context::destroy()` 统一销毁，避免单条纹理销毁影响其余纹理。
5. **延迟销毁并非本模块职责。**`mesh_detach` / `texture_detach` 是为此提供的「移交原语」，实际压队列由 `Renderer::mesh_unload` / `texture_unload` 调 `frame.deferred_push(entry, in_flight_count + 1)`，最终在 Frame 模块的延迟销毁处理里调 `memory->buffer_destroy` / `image_view_destroy` / `image_destroy`。

### 6.14 性能取舍汇总

| 取舍 | 具体位置 | 代价 / 收益 |
| --- | --- | --- |
| 设备本地与图像一律专用分配 | `缓冲创建.cpp` / `图像创建.cpp` | 无子分配复用 → 设备内存对象多；但生命周期简单、无共享块释放顺序问题。 |
| 每次上传新建暂存缓冲 | `上传批次.cpp` 四个入口 | 多一次分配 / 销毁 + 一次同步等待；换取实现简单、无环形缓冲偏移管理。 |
| 命令池 / 栅栏复用 | `upload_resources_ensure` / `upload_submit_once` | 避免每资源一次池与栅栏创建；但所有上传串行共享同一池与栅栏。 |
| 同步上传（无限等待） | `vkWaitForFences(UINT64_MAX)` | 加载期简单可靠；运行期会阻塞调用线程（故 `mesh_update_*` 前门面先 `frames_wait`）。 |
| 网格顶点索引合批 | `mesh_create` | 一次分配 + 一次提交；但更新顶点 / 索引各需一次整段上传（无法只映射子区间）。 |
| 完整 mip 链总是生成 | `texture_create_from_memory` | 内存与生成时间成本固定；默认采样器不采 mip，收益取决于状态开关。 |
| 全模块共享一个采样器 | `shared_sampler` | 省采样器对象与描述符数量；但切换状态即全局重建，已写描述符失效。 |
| 缓存表静态 + 线性释放查找 | `资产缓存.cpp` | 免传上下文；条目多时释放变慢，且存在指针复用风险。 |

## 七、模块运行链路详例

### 链路 A：纹理从文件到 GPU 就绪（含解码、上传、mip、视图、采样器）

调用方（系统层 / 场景装配）→ `Renderer::texture_load_file(handle_out, path)`（`Renderer/core/渲染器.cpp`，先校验 `impl != nullptr && initialized`）→ `impl->texture.texture_create_from_file`（`Texture/core/纹理解码.cpp`）：

1. `handle_out = 0`；`valid()` 校验（`memory != nullptr && device != VK_NULL_HANDLE`）。
2. `path_from_utf8(path)` 构造 `std::filesystem::path`（UTF-8 → `u8string`）。
3. `std::ifstream(..., binary|ate)` 打开；失败 → `logger.error("纹理:: 打不开纹理文件 {}")` → 返回假（句柄 0）。`tellg()` ≤ 0 → 「纹理文件为空」返回假。
4. `seekg(0, beg)`，`vector<uint8_t> bytes(byte_count)` 整块读；`read` 失败 → 返回假。
5. `stbi_load_from_memory(bytes.data(), size, &w, &h, &channels, 4)`；空指针 → `logger.error("纹理:: 解码失败（{}）", stbi_failure_reason())` 返回假；`w/h <= 0` → `stbi_image_free` 后返回假。
6. 转交 `texture_create_from_memory(handle_out, decoded, w, h)`（`Texture/core/纹理创建.cpp`）：
   - 计算 `mip_levels`：`largest = max(w,h)`，`while (largest > 1) { largest >>= 1; ++mip_levels; }`。
   - `memory->image_create(image, allocation, w, h, VK_FORMAT_R8G8B8A8_SRGB, SAMPLED|TRANSFER_DST|TRANSFER_SRC, mip_levels)`（`Memory/core/图像创建.cpp`）→ 设备本地专用分配 + `TILING_OPTIMAL` + `UNDEFINED` 初始布局。
   - `memory->upload_image(image, pixels, w*h*4, w, h, 0)`（`Memory/core/上传批次.cpp`）：建暂存（`TRANSFER_SRC`，host visible 顺序写）→ `buffer_write` → `upload_resources_ensure`（首次建 `TRANSIENT` 池 + 栅栏）→ 录制 `UNDEFINED→TRANSFER_DST` 屏障、`vkCmdCopyBufferToImage`、`TRANSFER_DST→SHADER_READ_ONLY` 屏障 → 提交 → `vkWaitForFences` → 销毁暂存。失败 → `image_destroy` 后返回假。
   - `memory->image_generate_mips(image, w, h, mip_levels)`：逐级 blit（线性过滤），一次提交；失败 → 日志「mip 链生成失败，回退」+ `image_destroy` 返回假。
   - `memory->image_view_create(view, image, R8G8B8A8_SRGB, COLOR, mip_levels)`：视图覆盖全部级（否则采样器无法选低级别）。
   - `sampler_create(shared_sampler)`（`Texture/core/采样器创建.cpp`）：首次创建共享采样器（线性过滤、`address_mode` 映射、`mip_filter` 决定 `mipmapMode` 与 `maxLod`、LOD 偏置、各向异性）；失败 → 销毁视图与图像返回假。
   - 登记 `Texture_Record{image, allocation, view, sampler = shared_sampler, mip_levels, w, h, valid = true}`；`push_back`；`handle_out = records.size()`；日志「纹理已建立（句柄 N，WxH，mip 级数 M）」。
7. 回到解码处：`stbi_image_free(decoded)`；`created` 为假 → 日志「解码成功但从像素创建纹理失败」+ 句柄归 0 返回假；成功 → 日志「已从文件创建纹理 …（源通道数 N）」。

**结果 / 副作用：**新增一条有效 `Texture_Record`，GPU 上有一张全 mip 的 sRGB 图像与对应视图，模块共享采样器可能被首次创建；无论成败，解码缓冲与临时暂存缓冲均已释放。

### 链路 B：网格从 OBJ 到设备本地缓冲（解析 → 合批 → 上传 → 记录）

调用方 → `Renderer::mesh_load_obj(handle_out, path)`（`Renderer/core/渲染器.cpp` 第 6269 行附近）：

1. `handle_out = 0`；校验渲染器已初始化。
2. `Mesh_File_Data file;` → `obj_mesh_load(path, file)`（`Asset/core/obj文件加载.cpp`）→ `Mesh_Loader::load_file(path, out)`（EngineFoundation）→ 失败返回假（日志由解析器写出）。
3. `impl->mesh.mesh_create(handle_out, file.data, file.sections)`（`Mesh/core/网格缓冲.cpp`）：
   - `handle_out = 0`；校验 `memory != nullptr && memory->valid()`、顶点 / 索引非空、逐索引 `< vertices.size()`。
   - `vertex_bytes = sizeof(Vertex) * vertices.size()`、`index_bytes = 4 * indices.size()`、`total_bytes = 两者之和`。
   - `memory->buffer_create(buffer, allocation, total_bytes, VERTEX|INDEX|TRANSFER_DST, false)` → 设备本地 `DEDICATED` 分配（`Memory/core/缓冲创建.cpp`）。
   - `std::vector<uint8_t> combined(total_bytes)`；`memcpy(combined, vertices, vertex_bytes)`；`memcpy(combined + vertex_bytes, indices, index_bytes)`。
   - `memory->upload_buffer(buffer, combined.data(), total_bytes, 0)`：暂存 `TRANSFER_SRC` → 写入 → `upload_submit_once` 录制 `vkCmdCopyBuffer`（`dstOffset = 0`）→ 提交 → 等待 → 销毁暂存；失败 → `buffer_destroy` 返回假。
   - 组 `Mesh_Record`：`index_offset = vertex_bytes`、`index_count`、`vertex_count`；逐顶点逐轴求 `bounds_min / bounds_max`。
   - 逐段校验 `index_count % 3 == 0` 与 `first_index + index_count <= indices.size()`；不合法 → `buffer_destroy` 返回假。
   - `record.sections = sections`；`valid = true`；`records.push_back(record)`；`handle_out = records.size()`；日志「网格已建立（句柄 N，顶点 V，索引 I）」。
4. 返回门面，句柄已可用。

**结果 / 副作用：**一块含顶点与索引的共用设备缓冲；一条有效 `Mesh_Record`（含分段与包围盒）；若把该流程包在 `asset_mesh_shared_load` 内，还会在缓存表新增一条 `mesh:<路径>` 登记（`refs = 1`）。

### 链路 C：资产缓存的命中、未命中与失效

**命中路径（纹理）：**

1. 调用方 → `asset_texture_shared_load(renderer, handle_out, path)`（`Asset/资产缓存.cpp`）。
2. `handle_out = 0`；`缓存取值(renderer)`（`缓存表[&renderer]`，必要时插入空条目）。
3. `key = 缓存键构建("texture", path)`（分隔符统一 + ASCII 小写）。
4. `缓存.texture.find(key)` 命中 → `refs += 1`，`handle_out = 条目.handle`，返回真（**不创建、不触碰 GPU**）。
5. 命中后即使资产文件在磁盘上被修改，也不会重新解码（缓存只按路径键，无时间戳 / 内容哈希），见「附：待确认正文 12」。

**未命中路径（纹理）：**

1. `uint64_t 句柄 = 0; renderer.texture_load_file(句柄, path)` → `Texture_Context::texture_create_from_file`（链路 A）。
2. 失败 → 返回假且不登记（后续同路径仍视为未命中，会重试创建）。
3. 成功 → `缓存条目{handle, 1}`，`缓存.texture.emplace(key, entry)`，`handle_out = 句柄`。

**释放 / 失效路径：**

1. 调用方 → `asset_texture_release(renderer, handle)`；`handle == 0` 直接返回。
2. `缓存取值(renderer)`；遍历 `缓存.texture` 线性查找 `条目.handle == handle`。
3. 命中且 `refs > 1` → `refs -= 1` 并返回（资源保留）。
4. 命中且 `refs == 1` → 先 `缓存.texture.erase(it)` 使条目失效；再 `renderer.texture_unload(handle)`：
   - `impl->texture.texture_detach(handle, record)` 摘出记录并把原槽置默认（本模块从此不再持有）。
   - 若 `record.view == impl->bound_view` → `texture_bind_set(0)`（回落默认白纹理）；若 `handle == impl->sky_texture` → `sky_texture_set(0)`。
   - 组装 `Deferred_Memory_Resource{image, allocation, view}`，`frame.deferred_push(entry, in_flight_count + 1)`。
   - 帧模块在处理延迟条目时调 `memory->image_view_destroy(view)` + `memory->image_destroy(image, allocation)`，最终归还 VMA。
5. 表中找不到 → `renderer.texture_unload(handle)`（视为非共享资源直接卸载）。

**异步分支（网格）：**

1. `asset_mesh_async_load(renderer, task, path)`：路径空或 `task.state != nullptr` → 假；否则 `make_shared<异步网格状态>()`，`future = std::async(std::launch::async, [state, path]{ return obj_mesh_load(path, state->data); })`，`task.state = state`，立即返回真。
2. 每帧 `asset_mesh_async_poll(renderer, task, handle_out)`：
   - `built` → 返回缓存句柄（幂等）；`settled && !parse_ok` → 假；未 `settled` 且 `wait_for(0s)` 非 ready → 假。
   - ready → `parse_ok = future.get()`，`settled = true`；失败 → 假。
   - 成功 → 按 `data.sections` 空 / 非空分派 `renderer.mesh_load` 或 `renderer.mesh_load_sections` → `handle = 句柄`，`built = true`，返回真。
3. 该句柄未登记进 `缓存表`，故后续释放走「未登记 → 直接卸载」分支。

**结果 / 副作用：**同一路径在缓存表存在期间只创建一次 GPU 资源；释放归零后条目与资源（延迟 `in_flight+1` 帧）一起消失；清表 `asset_cache_clear` 只删登记不卸载。

【待确认 1】范围文件数与落盘位置不一致：调度单称 Asset 为「4 个文件」，但快照实际有 6 个（`资产加载.h`、`资产缓存.h`、`局部命名空间使用.h`、`资产缓存.cpp`、`core/obj文件加载.cpp`、`core/mtl文件加载.cpp`），且 `资产缓存.cpp` 位于 `Asset/` 根目录而非 `Asset/core/`。本文按快照实际结构记录 24 个文件。需确认：Asset 的标准布局是否应为 `core/资产缓存.cpp`，以及调度单计数是否有误。

【待确认 2】`Mesh/网格.h` 中 `mesh_record_get` 前的注释行写着「取网格缓冲、索引区偏移与索引数（句柄无效返回假）//当前有效网格数量（第一百一十三轮；只读诊断）」，把 `mesh_count` 的说明错误地并入 `mesh_record_get` 的注释；两函数声明顺序为 `mesh_count` 在前、`mesh_record_get` 在后，注释归属与声明错位。

【待确认 3】`Memory/core/上传批次.cpp` 的 `image_generate_mips_from` 中，`target_barrier` 被提交两次：先在 `pre_barriers[2]` 里与 `source_barrier` 合并走 `FRAGMENT_SHADER → TRANSFER`，随后又以同一结构单独走 `TOP_OF_PIPE → TRANSFER`。第二条屏障 comment 称「目标级为未定义→传输目标，故其阶段对单独再走一次」，但合并提交中该目标级已以 `FRAGMENT_SHADER → TRANSFER` 提交过一次；是否冗余（或是否应把目标级从 `pre_barriers` 中移除）需确认。

【待确认 4】`Mesh/core/网格缓冲.cpp` 注释称索引区偏移为「20 字节步长的整数倍，天然满足 uint32 索引对齐」，而 `Vertex` 实际为 3 + 2 + 3 个 float = 32 字节（EngineFoundation 头注释亦写「步长 32 字节」）。结论（对齐成立）不受影响，但「20 字节」是过时数字。

【待确认 5】`image_generate_mips_from` 在 `mip_levels <= 1 || base_level + 1 >= mip_levels` 时**先**返回真（空操作），此判断位于 `valid()` / `image` 校验之前；因此传入无效图像与 1 级 mip 会返回成功。是否有意为之需确认（若调用方依赖返回值判断资源有效性，会得到假阳性）。

【待确认 6】读回接口的错误反馈不一致：`texture_readback` / `texture_readback_region` 在容量不足时 `logger.error` 后返回假；`texture_readback_level` / `texture_readback_region_level` 容量不足时静默返回假，无日志。是否应统一。

【待确认 7】`upload_image_region` 与 `image_readback_region` 的 `subresourceRange` 固定 `baseArrayLayer = 0, layerCount = 1`，而 `texture_update_region_level` / `texture_readback_region_level` 没有「层号」参数；对 `texture_create_cube` 产生的 6 层立方体贴图，分级更新 / 读回只能作用于第 0 层（+X 面）。是有意限制（立方体不支持局部更新）还是待补层参数，需确认。

【待确认 8】`Mesh_Context::mesh_destroy` 只复位 `buffer / allocation / index_offset / index_count / valid`，未清 `sections`、`vertex_count`、`bounds_min / bounds_max`；而 `mesh_detach`、`texture_destroy`、`texture_detach` 均用整体默认构造复位。被销毁的网格槽仍持有 `sections` 的堆内存直到 `destroy()`，且 `mesh_counts_get` 因 `valid == false` 不会读到脏值。是否应改为 `record = Mesh_Record{}` 需确认。
