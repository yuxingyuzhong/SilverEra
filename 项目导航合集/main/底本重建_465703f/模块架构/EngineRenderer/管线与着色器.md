## 二、模块功能介绍

本模块是 EngineRenderer 层内的「动力装置」：把 Vulkan 的管线对象、着色器模块、计算上下文与剔除数学收敛为若干可被门面（`Renderer`）直接调用的对象与自由函数。它不做帧循环、不做渲染项排序、不做 GPU 内存分配，也不做材质语义校验以外的业务判断。

**Pipeline 子域负责**：一次性的创建期基础设施（两套 `VkDescriptorSetLayout`、一个共享 `VkPipelineLayout`、一个 `VkPipelineCache`、一个 `VkDescriptorPool`、每帧槽六类描述符集）与图形管线的全生命周期（登记 / 激活 / 重建 / 注销），以及逐帧对描述符集的写入（场景 UBO、簇数据、各类采样器、逐绘制项贴图）。全部图形管线共享同一管线布局与同一套 set 布局，只允许「着色器对 + 固定状态」不同（`管线.h:144-155`）。

**Shader 子域负责**：把磁盘上的 `.spv` 字节加载为 `VkShaderModule`，并在加载顶点着色器时顺带解析 SPIR-V 中声明了 `Location` 的 `Input` 变量，输出位集供图形管线裁剪顶点属性声明（`着色器模块.cpp:22-69`）。模块所有权显式归调用方：本子域只创建与销毁它自己返回的句柄，不持有。

**Compute 子域负责**：与图形完全独立的一套计算描述符布局 / 管线布局 / 描述符池 / 每帧槽集，加上派发封装（绑定管线、绑定集、写推送常量、`vkCmdDispatch`）、组数换算、七种用途的 `VkMemoryBarrier2` 展开、一次性提交、时间戳计时与内置自检。它**不**分配或维护存储缓冲内容（由门面与内存模块负责，`Compute.h:19`）。

**GPU驱动 子域负责**：与 Vulkan 完全无关的 CPU 参考实现——把「网格局部 AABB + 模型矩阵」换成世界包围球与世界 AABB；从「视图 × 投影」矩阵提取六个归一化平面；给出球 / AABB 视锥可见判定、距离剔除与半球（背面）剔除。它的存在理由是把「保守口径」集中到一处，使 GPU 着色器与 CPU 参考判定使用同一公式与同一容差（`剔除数据.h:5-8`、`视锥剔除.comp:4`）。

**不负责的部分（边界）**：
- 缓冲与图像的内存分配（`render/Memory`）、纹理采样器状态（`render/Texture`）、渲染项组织与 pass 顺序（`render/Frame`、`Renderer`）、窗口与交换链（`render/Platform`、`render/Swapchain`）。
- 着色器源码编译：本模块只吃 `.spv`；GLSL → SPIR-V 由 CMake 的 `glslc` 离线步骤产出（`Engine/EngineRenderer/CMakeLists.txt:542-602`）。
- 材质的业务校验与脏值钳制：`Material_Data` 只是数据载体，校验在 `Renderer::material_load`（`渲染器.cpp:7874-8030`）。
- 帧间同步：所有接口均假定调用方已在安全时机调用（写描述符集前由门面 `frames_wait`，重建前本模块自己 `vkDeviceWaitIdle`）。

**关键约束**：
1. 图形管线共享布局，故**不能**通过新增描述符绑定来扩展图形侧接口，否则所有已登记管线的布局失效；计算侧另立布局以规避该耦合（`Compute.h:21-23`）。
2. 颜色 / 深度附件格式与采样数被**烘焙**进管线，交换链换格式或 MSAA 档变化后必须全部重建（`管线.h:160-166`）。
3. 所有 Vulkan 头只出现在本层实现头（`管线.h:4-9`、`Compute.h:4-9`、`着色器.h:4-9`）与 `.cpp`；Vulkan-free 的语义类型另立四头（`管线数据.h`、`材质数据.h`、`计算数据.h`、`包围体.h` / `剔除数据.h`），供门面公共头引用。
4. 销毁一律幂等：每个上下文都在析构里兜底调用 `destroy()`，`destroy()` 自身可在任意中间状态重入（`管线.cpp:237-283`、`Compute.cpp:173-220`）。

## 三、模块公开接口

### 3.1 管线公共语义（Blend_Mode）

`管线数据.h:18-33`，`enum class Blend_Mode`：

| 枚举值 | 烘焙出的颜色混合状态 | 语义 |
| --- | --- | --- |
| `Opaque` | `blendEnable = VK_FALSE` | 忽略源 alpha，写全通道。 |
| `Alpha` | `src = SRC_ALPHA`、`dst = ONE_MINUS_SRC_ALPHA`（颜色与 alpha 通道同参） | 半透明叠加，参与深度测试且写深度。 |
| `Additive` | `src = ONE`、`dst = ONE`（颜色与 alpha 通道同参） | 亮度累加（光晕 / 粒子 / 拖尾）。 |

`Blend_Mode` 是 Vulkan-free 类型，门面公共头可直接引用；切档等价于「格式变化」路径，会触发一次默认管线重建（见 §3.3 的 `pipeline_default_blend_set`）。

### 3.3 Pipeline_Context

`管线.h:123-394`。拷贝构造与赋值被 `delete`（`管线.h:130-131`）。生命周期：`build` → `pipeline_build` / `pipeline_register` → 使用 → `destroy`。

**生命周期与状态**

| 签名 | 语义 | 前置 / 失败行为 |
| --- | --- | --- |
| `Pipeline_Context(void) = default` | 构造不创建任何 Vulkan 对象。 | — |
| `~Pipeline_Context(void)` | 析构内部调用 `destroy()`，保证不泄漏。 | — |
| `bool build(VkDevice device, const Pipeline_Config& config)` | 建立 set 布局、管线布局、空管线缓存、描述符池并按帧槽分配六类描述符集；成功日志记录在途帧与格式。 | 设备为空或 `frame_overlap == 0` 记 error 返回假；任一创建步骤失败即 `destroy()` 回滚并返回假（`管线.cpp:53-234`）。 |
| `void destroy(void)` | 幂等销毁：图形管线 → 描述符池 → 管线布局 → set1 / set0 布局 → 管线缓存；清空容器与句柄，复位配置。 | 无（`管线.cpp:237-283`）。 |
| `bool valid(void) const` | `device`、两套 set 布局均非空。 | 无（`管线.cpp:286-289`）。 |

**图形管线条目管理**

| 签名 | 语义 | 前置 / 失败行为 |
| --- | --- | --- |
| `bool pipeline_build(VkShaderModule vert_module, VkShaderModule frag_module, Blend_Mode blend_mode = Blend_Mode::Opaque, uint32_t input_locations = 0xFF)` | 登记 / 替换并**激活**句柄 0 默认场景管线；已有管线先销毁再重建。 | 未 `valid()` 或模块为空记 error 返回假；创建失败返回假但条目仍保留着色器与档位（`管线.cpp:292-329`）。 |

### 5.2 构建链总览（本模块的主骨架）

```
门面 Renderer::initialize
   │
   ├─(1) Pipeline_Context::build(device, config)
   │        ├── vkCreatePipelineCache（空数据）
   │        ├── descriptor_layouts_create → set0 / set1
   │        ├── pipeline_layout_create   → layout（2 set + push 128/144）
   │        ├── vkCreateDescriptorPool   → maxSets = overlap × 136
   │        └── 6 次 vkAllocateDescriptorSets
   │              scene / sampler / ui / post / draw / particle
   │
   ├─(2) Pipeline_Context::cache_set(文件字节)      ← 必须在建任何图形管线之前

```

```
   ├── descriptor_layout_create（SB × count + sampler × 1 + storage image × 2）
   ├── pipeline_layout_create（单 set + push 128）
   ├── vkCreateDescriptorPool + 每帧槽 vkAllocateDescriptorSets
   ├── 一次性 VkCommandPool（TRANSIENT）+ VkFence（初始信号态）
   └── 可选：2 查询 VkQueryPool（时间戳）
```

### 5.3 所有权与生命周期

| Vulkan 对象 | 创建者 | 销毁者 | 说明 |
| --- | --- | --- | --- |
| `VkDescriptorSetLayout` × 2 | `Pipeline_Context` | `Pipeline_Context::destroy` | 顺序先 set1 后 set0（`管线.cpp:255-260`）。 |
| `VkPipelineLayout` | `Pipeline_Context` | 同上 | 全部图形管线共享，销毁在管线之后。 |
| `VkDescriptorPool` 及其全部集 | `Pipeline_Context` | 同上 | 池销毁连带回收集（`管线.cpp:250-251`），故不单独释放集。 |
| `VkPipelineCache` | `Pipeline_Context` | 同上（最后销毁） | `cache_set` 会先销毁旧缓存再新建；注释明确「已创建图形管线不受影响」。 |
| `VkPipeline`（图形） | `Pipeline_Context` | `pipeline_release` / `pipeline_build` 替换 / `pipeline_rebuild` / `destroy` | 条目内 `pipeline` 字段是唯一所有者。 |
| `VkShaderModule` | 门面（`Shader_Context::module_load` 产出） | 门面（`Shader_Context::module_destroy`） | 本模块与条目只借用；`pipeline_release` 不销毁模块。 |
| `VkShaderModule`（计算同名对象） | 门面 | 门面 | 同上。 |
| `VkPipeline`（计算） | `Compute_Context` | `pipeline_release` / `destroy` | — |
| 存储缓冲 / 图像 | 门面 + Memory 模块 | 门面 + Memory 模块 | 本模块只在描述符里引用。 |

`Pipeline_Context` 的状态机：`未构建(device 空)` → `build 成功` → `登记若干管线` → `destroy` 回到未构建。`destroy` 在任何中间状态可重入（各句柄空时跳过）。`valid()` 只要求设备与两套 set 布局齐备，因此「build 成功但未登记任何管线」也算有效。

`Compute_Context` 的状态机同上，但多了 `supported_flag`：`supported()` 同时要求能力探测通过与基础设施齐备。若队列族不含 COMPUTE 位，`build` 只记录 device / queue 并返回真，此时 `valid()` 为假（布局未建），后续所有登记 / 派发都被拒绝，门面据此整体关闭 GPU 路径。

### 5.4 数据流

- **图形侧一次创建期数据**：`Pipeline_Config`（格式 / 帧数 / 采样数 / 推送常量上限）→ set 布局与管线布局 → 每条管线的 `VkGraphicsPipelineCreateInfo`。配置只影响创建，不影响运行期绑定。
- **图形侧逐帧数据**：门面按帧槽写 set0（UBO 与簇缓冲）与 set1（纹理 / 阴影 / 天空 / 材质贴图），以及每项专属 set1（`draw_sets`）。所有写入都是「立即 `vkUpdateDescriptorSets`」，本模块不缓存待写队列。
- **计算侧逐帧数据**：门面按帧槽 `storage_bind` / `sampler_bind` / `storage_image_bind`，`slot_set` 选定槽后 `dispatch_ceil`。
- **剔除数据**：门面把世界包围球打包成 `float[count*4]` 上传为计算缓冲，平面走推送常量；CPU 参考函数只用于验证与回退。

### 5.5 线程归属

- 全部接口**无锁、无原子**，假定由渲染线程（录制线程）单线程调用；注释与门面代码都遵循该前提（写描述符集前 `frames_wait`）。
- 唯一的全设备同步点在本模块内部：`pipeline_rebuild` 与 `pipeline_default_blend_set` 的 `vkDeviceWaitIdle`（`管线.cpp:432`、`管线.cpp:467`）。
- `GPU驱动` 的六个自由函数是纯函数，可被门面工作线程并行调用（门面按块并行视锥剔除时即如此）。
- `Compute_Context::single_submit` 会提交并阻塞等待围栏，只允许在非帧内时机调用。

## 六、模块设计 / 实现细节

### 6.1 构建顺序的强约束（管线规格 → 布局 → 描述符池 → 管线）

1. `build` 内顺序固定为：`vkCreatePipelineCache` → `descriptor_layouts_create` → `pipeline_layout_create` → `vkCreateDescriptorPool` → 六类集分配（`管线.cpp:72-229`）。任一失败 `destroy()` 回滚，不留半成品。
2. 缓存必须**先于**任何 `vkCreateGraphicsPipelines` 就绪：门面在 `pipeline.build` 之后、`pipeline_build` 之前调用 `cache_set`（`渲染器.cpp:1095-1125`）。`cache_set` 销毁旧缓存再新建，因此若在建管线后调用，已建管线仍有效但不再参与新缓存。
3. 描述符池容量是「按帧槽 × 固定集数」预算出来的，运行期**不再**分配集：
   - UBO：`frame_overlap × 2`（场景集 + 粒子专用集）；
   - SSBO：`frame_overlap × 8`（场景集 4 条 + 粒子集 4 条）；
   - 采样器类：`frame_overlap × (1 + UI_SET_PER_SLOT + POST_SET_PER_SLOT + DRAW_SET_PER_SLOT) × 17 = frame_overlap × 134 × 17`（`管线.cpp:117-118`）；
   - `maxSets = frame_overlap × (3 + 1 + 4 + 128) = frame_overlap × 136`（`管线.cpp:124`），其中 3 = 场景 + 采样器 + 粒子。
   预算比实际用量（134）多 2 集，属预留余量。
4. 图形管线创建不检查 `pipeline_layout` 是否为空：`entry_pipeline_create` 只在 `valid()` 通过后被调用（`pipeline_build` / `pipeline_register` 都先判 `valid()`），故布局必已存在。
5. `pipeline_register` 采用「先建后登记」：把全部字段装进局部 `Pipeline_Entry`，`entry_pipeline_create` 成功后才 `push_back` 并推进 `next_handle`。这样可以保证句柄序列不出现空洞，也不会留下「有句柄无管线」的条目（`管线.cpp:345-371`）。
6. `pipeline_build`（句柄 0）是「替换式」：先销毁旧 `VkPipeline` 再重建；若重建失败，条目仍保留新着色器与档位但 `pipeline` 为空，此时 `pipeline_get()` 返回空——门面初始化阶段据此判定失败（`渲染器.cpp:1125-1131`）。

### 6.2 管线缓存的「键」与命中策略

**工程侧不自建键。** `Pipeline_Context` 只有一个不透明 `VkPipelineCache`（`管线.h:370`），模块内没有任何字符串 / 哈希表 / 字典来索引管线；`pipelines` 是 `std::vector<Pipeline_Entry>`，查找是线性扫描（§4.1）。

**键完全由驱动从完整管线状态推导。** 参与键的输入就是 `VkGraphicsPipelineCreateInfo` 的全部内容：
- `pStages`（着色器模块字节 + `pName = "main"`）；
- `pVertexInputState`（经 `input_locations` 裁剪后的 binding 与 attribute 列表）；
- `pInputAssemblyState`（固定三角形列表）；
- `pRasterizationState`（`cullMode` 与 `frontFace` 随条目参数变化）；
- `pMultisampleState`（`rasterizationSamples`、`alphaToCoverageEnable`）；
- `pDepthStencilState`（测试 / 写入 / 比较算子）；
- `pColorBlendState`（混合档烘焙结果）；
- `pDynamicState`（视口 / 裁剪两项）；
- `pNext` 指向的 `VkPipelineRenderingCreateInfo`（颜色与深度附件格式）；
- `layout`（共享 `VkPipelineLayout`）。

因此「命中」在语义上等价于：**上述静态状态逐项相同**。任何一项不同（例如交换链换了格式、MSAA 档变化、`cull_front` 与 `cull_none` 互换、`alpha_to_coverage` 开关、`input_locations` 位集变化）都会得到不同的键，`pipeline_rebuild` 之后旧键条目自然不再被命中——这也是「格式 / 采样数必须整体重建」在缓存层面的解释。

**工程侧提升命中率的三种手段（都不涉及自建键）**：
1. **句柄级去重**：具名句柄自 1 起递增且稳定（`next_handle`），同一「着色器对 + 状态」只登记一次；`pipeline_has` / `pipeline_by_handle_get` 供门面复用（`管线.cpp:485-593`）。
2. **共享基础设施**：全部图形管线共用同一 `VkPipelineLayout` 与两套 set 布局，故布局不进入「是否可复用」的判断，只需比较条目字段。
3. **门面组合表**：材质路径把「混合档 × 是否写深度 × 覆盖率写入 × 双面」压进 3 × 8 = 24 个槽，同槽材质共享一条具名管线（`渲染器.cpp:8001-8026`）；未命中槽时才 `pipeline_load_ex`。

**持久化与失效**：
- 载入：门面从 `Renderer_Config::pipeline_cache_path` 读文件全部字节 → `cache_set`（`渲染器.cpp:1106-1123`）。文件缺失或读取失败只告警，不阻断初始化。
- 回退：若外部字节非法导致 `vkCreatePipelineCache` 失败，`cache_set` 立即用空数据重建一个空缓存并返回假（`管线.cpp:529-536`），保证后续创建仍可用。
- 写回：关闭时 `cache_get` 取字节并写回同一路径（`渲染器.cpp:2073-2084`）。`cache_get` 先查长度再取内容，最后按返回的实际长度 `resize`（`管线.cpp:549-565`）。
- 文件层没有版本号、没有设备标识、没有哈希命名——「键」在文件维度只有路径一个。跨 GPU 复用同一文件时，不匹配条目由驱动自行忽略（驱动行为，非本模块承诺；推测）。

### 6.3 着色器字节码的加载方式

1. **产物来源**：`assets/shaders/*.vert|*.frag|*.comp` 由 CMake 用 `glslc --target-env=vulkan1.3` 逐个编译为 `<构建树>/shaders/<原名>.spv`（`CMakeLists.txt:578-594`）；本层不产出可执行文件，着色器的取用以门面 / 测试层的输出目录为准。找不到 `glslc` 只告警，不硬失败。
2. **目录解析**：`directory` 为空时取 `detail::exe_dir_get() / "shaders"`，并转成 UTF-8 窄串（`着色器.cpp:11-16`、`着色器.cpp:62-69`）。注释明确「不得使用相对 CWD 的路径」，故运行目录变化不影响加载。
3. **读取**：`ios::ate | ios::binary` 先取文件长度，`tellg()` ≤ 0 视为空文件失败；`gcount() != size` 视为短读失败并清空输出（`着色器.cpp:80-109`）。失败会 `logger.error` 并带文件名。
4. **校验**：`bytes.size() % 4 != 0` 直接拒绝（SPIR-V 以 32 位字为单位）；首字必须为 `0x07230203`，否则记 error 并拒绝（`着色器模块.cpp:134-148`）。这两步在 `vkCreateShaderModule` 之前，把驱动报错转成可读的日志。
5. **创建**：`VkShaderModuleCreateInfo.codeSize = bytes.size()`、`pCode = reinterpret_cast<const uint32_t*>(bytes.data())`；`std::vector<char>` 的存储天然满足 4 字节对齐（`着色器模块.cpp:150-160`）。
6. **失败即置空**：`module_out` 在入口先置 `VK_NULL_HANDLE`，`input_locations_out` 先置 0；任一步失败原样返回，调用方（门面）据此回收另一侧的模块，避免泄漏（`渲染器.cpp:7500-7525`）。
7. **位置位集解析**：只扫描 `OpVariable`（操作码 59，取字 3 为存储类，1 = Input）与 `OpDecorate`（操作码 71，装饰 30 = Location），指令字数从头部高 16 位取；字数非法即终止（防御损坏字节码）。交叉映射时 `location < 32` 才置位，返回 32 位掩码（`着色器模块.cpp:22-69`）。
8. **位集的用途与边界**：`graphics_pipeline_create` 里 `declared_locations = input_locations == 0 ? 0xFF : input_locations`，`add_attribute` 只在位命中时声明属性（`图形管线.cpp:49-85`）。这消除了校验层「属性未被消费」告警，但也使 0xFF 只覆盖 location 0..7（见待确认 5）。

### 6.4 静态状态与动态状态的分离

| 状态项 | 归属 | 变化时的处理 |
| --- | --- | --- |
| 视口 / 裁剪 | **动态**（`VK_DYNAMIC_STATE_VIEWPORT`、`VK_DYNAMIC_STATE_SCISSOR`，`图形管线.cpp:211-216`） | 改窗口 / 换目标尺寸只需在命令缓冲里设视口，**不重建**。 |
| 颜色附件格式 | 静态（`VkPipelineRenderingCreateInfo`） | 交换链换格式 → `pipeline_rebuild` 全部重建。 |
| 深度附件格式 | 静态（同上；`depth_format_override` 可单管线固定） | 同上；UI 管线用 `UNDEFINED` 跳过深度附件。 |
| 采样数 | 静态（`rasterizationSamples`） | MSAA 档变化 → `pipeline_rebuild`；条目固定值（如阴影管线 1）不随配置。 |
| 混合档 | 静态（`VkPipelineColorBlendAttachmentState`） | 默认管线走 `pipeline_default_blend_set`；具名管线在登记时固定。 |
| 剔除模式 / 绕序 | 静态（`cullMode`、`frontFace = COUNTER_CLOCKWISE`） | 登记参数决定；阴影管线 `cull_none`、描边管线 `cull_front`。 |
| 深度测试 / 写入 / 比较 | 静态 | `depth_active = depth_test && 附件格式 != UNDEFINED`；无深度附件时强制关闭测试与写入。 |
| 覆盖率写入 | 静态，且 `effective_samples > 1` 才真 | 单采样时自动关闭，保持旧 alpha 混合路径逐字节不变。 |
| 顶点输入 | 静态（按位集裁剪） | 顶点绑定 stride = 32、实例绑定 stride = 112（来自常量）。 |
| 图元拓扑 / 光栅化杂项 | 固定 | 三角形列表、填充模式、`depthClampEnable`/`depthBiasEnable`/`stencilTestEnable`/`logicOp` 全关、`lineWidth 1.0`。 |
| 推送常量 | 布局级 | 由 `Pipeline_Config::max_push_constant_size` 决定 128 或 144；门面在设备上限不足时降为 128 并禁用逐级 extra（`渲染器.cpp:1091-1094`）。 |

`pipeline_rebuild` 的空操作判定只比较三元组 `(color_format, depth_format, sample_count)`（`管线.cpp:424-427`）；`pipeline_default_blend_set` 的空操作判定是「同档且管线有效」（`管线.cpp:462-464`）。两者都在改动前 `vkDeviceWaitIdle`，避免旧管线被在途帧引用。

### 6.5 描述符集的分层与 17 描述符口径

- **set0**（`描述符布局.cpp:18-44`）：binding 0 = UBO（`VERTEX|FRAGMENT`），binding 1..4 = 存储缓冲（同样 `VERTEX|FRAGMENT`）。后者包含顶点阶段是被动的：粒子绘制在顶点阶段按 `gl_InstanceIndex` 读取状态与紧凑索引，若只给 `FRAGMENT`，顶点阶段读到未定义值 0（`描述符布局.cpp:29-34`）。
- **set1**（`描述符布局.cpp:47-101`）：binding 0..8 各 1 个 `COMBINED_IMAGE_SAMPLER`，binding 9 为 **8 个元素的数组**。单集描述符数 = 9 + 8 = 17；frames 池按 17 倍计。
- **一份布局、五类集合**：`sampler_sets`（场景）、`ui_sets`、`post_sets`、`draw_sets`、`particle_sets` 全部使用同一份 set1 或 set0 布局，靠「独立分配」而不是「独立布局」来隔离同帧多 pass 的绑定覆盖（`管线.h:202-230`）。
- **binding 2 的双重身份**：场景集里它是「场景深度」（后处理用），场景绘制路径不采样它，故 `draw_set_bind` / `draw_sets_bind_batch` 以反照率视图占位以保证描述符完整（`管线.cpp:876-880`、`管线.cpp:953-955`）；批量接口允许用 `Draw_Set_Views::depth` / `depth_sampler` 覆盖，实现「粒子软粒子读 HiZ 历史深度」。
- **批量写入的展开**：`draw_sets_bind_batch` 把 `count` 项压成 `count × 17` 条 `VkDescriptorImageInfo` 与 `count × 10` 条 `VkWriteDescriptorSet`，复用 `draw_batch_infos` / `draw_batch_writes` 两块成员缓冲（容量不足时 `resize` 一次），最后一次 `vkUpdateDescriptorSets` 提交（`管线.cpp:918-992`）。`count` 上限由 `DRAW_SET_PER_SLOT = 128` 硬限。
- **单条接口的不对称**：`draw_set_bind` 只有一个 `spot_shadow_view`，会把 binding 9 的 8 个元素全写成同一张图；需要 8 张不同聚光灯阴影图时必须走批量接口（见待确认 9）。
- **场景 UBO 范围是字面量**：`scene_bind` 与 `particle_buffers_bind` 都把 `range` 写死 3920（`管线.cpp:691`、`管线.cpp:776`），注释里保留了 1792 → 1824 → 1840 → 2480 → 3760 → 3824 → 3920 的历史；该值与门面 UBO 结构必须人工同步（见待确认 6）。
- **视图布局假设**：所有写入都硬编码 `VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL`（存储图像例外，用 `GENERAL`）。调用方必须在写描述符前把图像转入该布局，否则产生校验层错误或未定义读取；本模块不做布局转换。
- **队列约定**：`VkWriteDescriptorSet.dstArrayElement` 对 binding 9 的批量写恒为 0、`descriptorCount = 8`；单条 `spot_shadow_bind` 用 `dstArrayElement = index`、`descriptorCount = 1`，两种写法都合法但要避免对同一集混用导致覆盖。

### 6.6 计算管线与图形管线的资源绑定差异

| 维度 | 图形（Pipeline_Context） | 计算（Compute_Context） |
| --- | --- | --- |
| 描述符集布局 | 2 套：set0（UBO + 4 SSBO）、set1（10 binding / 17 descriptor） | 1 套：SB × N + sampler × 1 + storage image × 2（默认 binding 0..3、4、5..6） |
| 管线布局 | 2 set layout + push（`VERTEX|FRAGMENT`，128 或 144） | 1 set layout + push（`COMPUTE`，128） |
| 描述符池 | 4 种类型、预算式容量、每帧槽 136 集 | 3 种类型、`maxSets = frame_overlap` |
| 管线缓存 | 使用 `pipeline_cache` | **不使用**（`vkCreateComputePipelines` 传 `VK_NULL_HANDLE`，`Compute.cpp:309`） |
| 管线创建参数 | 全部静态状态 + `VkPipelineRenderingCreateInfo` | 单阶段 + `pName = "main"` + layout |
| 绑定方式 | 绑定管线 + 两套集（set 0 / set 1） | 绑定管线 + 单集（set 0） |
| 资源类型 | UBO / SSBO / 采样图像 | SSBO / 采样图像 / **存储图像** |
| 线程与槽 | 帧槽由调用方传参（`slot`） | 内部 `active_slot`（`slot_set` / `slot_get`） |
| 同步 | 由帧模块插入屏障 | 自带 7 种用途的屏障展开 |
| 与对方的耦合 | 无 | 无（注释明确「避免图形侧新增字段导致计算布局失效」） |

计算侧「位置固定」规则（`Compute.cpp:235-270`）：存储缓冲占用 `0..storage_buffer_count-1`；采样器固定占 `storage_buffer_count`；存储图像从 `storage_buffer_count + sampler_count` 起连续。因此改配置只改变数量，不改变排列语义；着色器里的 binding 号必须与此对齐（`视锥剔除.comp:7-8` 用 binding 0 / 1）。

### 6.7 剔除的 CPU 侧数据组织

1. **平面数据**：`Frustum_Planes` 是 6×4 的紧凑数组，顺序固定把「左 / 右 / 下 / 上 / 近 / 远」写死，便于直接拷进推送常量（96 字节）。提取时按行取列主序矩阵，近 / 远用 `row3 ± row2` 是因为 Vulkan 裁剪空间 z ∈ [0, 1]；每平面归一化，使 `dot(n, c) + d` 具有真实距离量纲，容差 1e-4 才有意义。
2. **实例包围数据**：门面为每个实例调一次 `world_bounds_build`，只取 `center` 与 `radius` 打包成 `float[count × 4]`（`渲染器.cpp:4746-4759`）——这正是 `视锥剔除.comp` 里 `vec4 center_r` 的排布。CPU 侧不打包 AABB（AABB 只在 CPU 参考判定里用），GPU 侧也不需要矩形投影（矩形需求属于 Hi-Z 链路的另一侧）。
3. **掩码**：`uint32[count]`，1 = 可见、0 = 剔除；GPU 全量覆写，故不需要初值（`渲染器.cpp:4765-4770`）。
4. **推送常量**：`{ float planes[24]; uint32_t count; }`，偏移 0 与 96（`渲染器.cpp:4784-4792`），与着色器 `layout(offset = 0)` / `layout(offset = 96)` 对齐。
5. **保守性契约（`C ⊆ G`）**：球判定与 GPU 着色器公式逐字相同（含 1e-4）；AABB 判定更紧，只作参照。因此「CPU 用 AABB 判可见」的集合必须是「GPU 用球判可见」集合的子集，GPU 不会多剔。为守住该契约，`world_bounds_build` 做了两次半径估计并取大（局部半对角 × 最大列长；世界 AABB 八角点距离），因为旋转后世界 AABB 的角点可能比变换后的局部角点更远，只按局部半对角估会破坏契约（`包围体.cpp:86-105`）。
6. **距离 / 背面剔除**：`distance_cull` 用严格大于、`backface_cull` 用点积严格小于 0，边界（恰好等于阈值 / 正交）都判可见——与 `实例压缩.comp` 的口径注释一致（`实例压缩.comp:48-52`）。
7. **纯函数**：六个函数不读写全局状态、不分配内存、不做日志，可以并行调用；失败只体现在布尔返回值（空指针 / 非有限矩阵 / min > max）。

### 6.8 错误处理与降级策略

- **唯一检查出口（图形侧）**：`vk_result_check`（`Renderer/core/结果检查.h:61-75`）。成功返回真；`VK_ERROR_OUT_OF_DATE_KHR` / `VK_SUBOPTIMAL_KHR` / `VK_TIMEOUT` 视为「可接受」记 debug 并返回假；其余记 error 并带结果码名称。图形侧全部创建 / 绑定调用都走该出口。
- **计算侧风格不一致**：`Compute.cpp` 多数调用直接比较 `VK_SUCCESS`（`descriptor_layout_create`、`pipeline_layout_create`、`compute_pipeline_create`、池 / 集 / 命令池 / 围栏 / 查询池创建），只有 `single_submit` 内部也不打日志。结果同样是布尔返回，但缺少错误码名称（见待确认 8）。
- **回滚**：`build` 的每一步失败都调用 `destroy()` 再返回假；`destroy` 可在半构建状态安全执行（各句柄判空）。计算侧同理。
- **不失败的能力缺失**：队列族无 `COMPUTE` 位 → `build` 返回真、`supported()` 为假；时间戳查询池创建失败 → `timestamp_flag = false`、计时恒 -1；`timestamp_*` 在不可用时是「返回真的空操作」，调用方无需分支。
- **告警而非致命**：着色器文件缺失在门面层表现为「该管线不登记」，只告警并保持功能关闭（如描边、天空、UI 纯色）；本模块自身对这些情况只返回假。
- **无异常**：本模块不使用异常；全部失败以布尔 + 日志表达（与项目「内存分配禁用异常」风格一致）。
- **重建错误路径无回滚**：`pipeline_rebuild` 逐条目「先销毁后重建」，若中途某条创建失败立即返回假，此前已重建的条目已就绪、后续条目 `pipeline` 为空，`config` 也已更新（见待确认 7）。

### 6.9 性能取舍

- **句柄线性查找**：条目数量是个位到数十，`std::vector` 顺序扫描优于任何哈希（`管线.cpp:15-34` 注释即如此）。
- **描述符写合并**：逐绘制项贴图从「每项 10 次 `vkUpdateDescriptorSets`」合并为「一次提交 count × 10 条记录」；两块成员缓冲避免每帧堆分配（`管线.cpp:932-934`）。
- **避免全设备同步**：只有「格式 / 采样数变化」与「默认混合档切换」才 `vkDeviceWaitIdle`；同档或格式未变时是纯空操作。
- **一次性预算分配**：六类集在 `build` 时全部预分配，运行期零分配；代价是固定占用 136 集/帧槽的池容量。
- **管线缓存**：命中可省去 SPIR-V → 机器码的编译时间，是初始化耗时的主要杠杆；本模块只负责字节搬运。
- **顶点属性裁剪**：按位集只声明真正消费的属性，减少校验层告警与管线状态规模；代价是依赖 SPIR-V 解析的准确性。
- **计算侧一次性资源**：命令池 `TRANSIENT` 位、围栏初始信号态，避免首次等待死锁（`Compute.cpp:123-138`）。
- **自检成本**：`self_check_run` 会建 / 映射 / 释放一块主机可见缓冲并阻塞等待围栏，只在初始化或测试路径调用。

### 6.10 隐式约定清单（调用方必须遵守）

1. `scene_bind` / `particle_buffers_bind` 的 UBO `range = 3920` 必须与门面实际 UBO 字节数一致，否则越界读或截断。
2. 写任何采样器描述符前，图像必须已处于 `SHADER_READ_ONLY_OPTIMAL`；存储图像必须处于 `GENERAL`（计算侧）。
3. 每帧每帧槽的逐绘制项集最多 128 条；超出的绘制项必须回落共享 `sampler_set`（门面已按 `DRAW_SET_PER_SLOT` 截断）。
4. 写逐绘制项集前必须等尽在途帧（门面 `frames_wait`），因为这些集会被下一轮同槽帧复用（`渲染器.cpp:3710-3711`）。
5. `pipeline_release` 不销毁着色器模块：门面必须自行 `module_destroy`，否则泄漏。
6. 具名管线的混合档、剔除、深度状态在登记后不可改；要改只能注销重登（除句柄 0 的混合档有专用接口）。
7. 计算调度的描述符集由 `active_slot` 决定，门面必须与所用帧槽一致地 `slot_set`。
8. `compute_dispatch` 不插入屏障：dispatch 前后需要的 `VkMemoryBarrier2` 由调用方按 §3.6 的枚举自行放置。
9. 无深度附件的管线必须 `depth_test = false` 且 `depth_format_override = true`（UI 路径即如此），否则动态渲染格式不匹配会被校验层拦截。
10. `input_locations` 的位集语义是「位 i = location i」，默认 0xFF 只覆盖 0..7（见待确认 5）。

## 七、模块运行链路详例

### 7.1 链路一：图形管线创建并首次绑定

**参与方**：门面 `Renderer::initialize`（`渲染器.cpp:1050-1131`）→ `Shader_Context` → `Pipeline_Context` → 帧模块录制。

| 步骤 | 调用 | 关键行为与副作用 |
| --- | --- | --- |
| 1 | 门面填 `Pipeline_Config`：`color_format` = 交换链格式、`depth_format` = 深度目标格式、`frame_overlap`、`sample_count`、`max_push_constant_size`（设备上限不足 144 时降为 128 并禁用逐级 extra） | 配置决定后续所有烘焙状态。 |
| 2 | `Pipeline_Context::build(device, config)`（`管线.cpp:53`） | 建空 `VkPipelineCache` → set0 / set1 布局 → 共享布局（推送常量 128/144）→ 描述符池（`maxSets = overlap × 136`）→ 六类集分配。任一步失败 `destroy()` 回滚，初始化中止。 |
| 3 | `cache_set(文件字节)`（`渲染器.cpp:1106-1123` → `管线.cpp:510`） | 销毁空缓存并以磁盘字节重建；失败自动回落空缓存（仅告警）。 |
| 4 | `Shader_Context::build(device)` + `module_load(vert, "场景.vert.spv", &locations)` + `module_load(frag, "场景.frag.spv")` | 每个模块做长度 / 魔数校验后 `vkCreateShaderModule`；顶点侧额外产出顶点输入位置位集。模块所有权留在门面（`extra_pipelines` / `vert_module` / `frag_module`）。 |
| 5 | `pipeline_build(vert, frag, Blend_Mode::Opaque, scene_input_locations)`（`渲染器.cpp:1125` → `管线.cpp:292`） | 建 / 替换句柄 0 条目 → `entry_pipeline_create` → `graphics_pipeline_create`：按位集声明顶点属性（binding 0 step 32 / binding 1 step 112）、烘焙光栅化 / 多重采样 / 深度 / 混合（Opaque）、链入 `VkPipelineRenderingCreateInfo`（颜色 / 深度格式）、`vkCreateGraphicsPipelines(device, pipeline_cache, …)`；成功后 `active_handle = 0`。 |
| 6 | 同理 `pipeline_register` 登记具名管线（如 `反向外扩`：`cull_front = true`、`depth_write = true`；阴影管线：`cull_none = true`、`color_format` 固定阴影目标格式、`sample_count = 1`） | 每条独立 `VkPipeline`，共享同一布局与 set 布局；句柄自 1 起。 |
| 7 | 每帧：门面按帧槽写 set0（`scene_bind` + `scene_cluster_bind`）与 set1（`texture_bind` / `shadow_bind` / `spot_shadow_bind` / `material_textures_bind` / `sky_bind`） | 写入立即生效（`vkUpdateDescriptorSets`），无排队。 |
| 8 | 录制：`vkCmdBindPipeline(GRAPHICS, pipeline_get())` + `vkCmdBindDescriptorSets(GRAPHICS, layout_get(), 0, 2, {scene_set_get(slot), sampler_set_get(slot)})` + 推送常量（模型矩阵占位 / 颜色 / 后处理尺寸 / 泛光参数） | 首次绑定即完成「管线 + 两套集 + 推送常量」三件套；此后切管线只需 `pipeline_activate` 再绑定。 |

**结果**：句柄 0 可用，`pipeline_get()` 返回有效 `VkPipeline`；`layout_get()` 与两套集返回同一帧槽的句柄；缓存对象已记录该管线的二进制（下次启动可命中）。

### 7.2 链路二：材质数据上传到描述符集

**参与方**：`Renderer::material_load` → `material_bind_set` → `mesh_draw_range` → `frame_render`（`渲染器.cpp:7874`、`8073`、`6418`、`3714-3770`）→ `Pipeline_Context::draw_sets_bind_batch` / `material_textures_bind`。

| 步骤 | 调用 | 关键行为与副作用 |
| --- | --- | --- |
| 1 | `material_load(handle_out, data)`（`渲染器.cpp:7874-8030`） | 逐字段校验与钳制：PBR 粗糙度 (0.05, 4]、金属度 [0, 1]；卡通色阶 [0, 8] / 边缘光 / 高光 [0, 1]；色调四分量为 [0, 1] 才视为覆盖；自发光 [0, 8]；`normal_strength` (0, 4]；`alpha_cutoff` (0, 1]；清漆强度 (0, 1] 否则 0、粗糙度 [0.03, 1] 否则 0.15。非法值一律「按不覆盖登记」并告警，绝不把脏值写进实例属性。 |
| 2 | 若 `pipeline == 0` 且（非 Opaque 或 覆盖率写入 或 双面 或 不写深度） | 组合下标 = `blend × 8 + (depth_write ? 0 : 4) + (alpha_to_coverage ? 2 : 0) + (double_sided ? 1 : 0)`；该槽为空则用默认场景着色器对 `pipeline_load_ex` 登记一条具名管线；材质记录该句柄。同槽材质复用同一条管线（`渲染器.cpp:8001-8026`）。 |
| 3 | `material_bind_set(handle)`（`渲染器.cpp:8073`） | 取材质记录 → `pipeline_bind_set(record.pipeline)`（内部 `pipeline_has` 校验、`pipeline_activate`）→ `texture_bind_set(record.texture)`（反照率）→ 其余字段写入门面「吸附态」（PBR / 卡通 / 色调 / 自发光 / UV / 裁剪 / 清漆 / 法线强度）。句柄 0 或无效时统一回落默认场景管线 + 白纹理并清空全部覆盖。 |
| 4 | `mesh_draw_range`（`渲染器.cpp:6418`）→ `instance_matrices_append`（`渲染器.cpp:6347-6409`） | 追加 28 个 float：16 模型矩阵；`[16..19]` = 粗糙度 / 金属度 / 覆盖标志(1/0) / 自发光；`[20..23]` = 色阶 / 边缘光 / 高光 / 卡通覆盖标志；`[24..27]` = 暗部色调 rgb + 0。**标量材质参数走实例属性**，不经推送常量。同时快照采样态：`draw_sampler`、`draw_albedo`、`draw_normal/roughness/emissive/ao/metallic`（`渲染器.cpp:6513-6520`）。 |
| 5 | `frame_render` 收集 `Draw_Set_Views`（`渲染器.cpp:3714-3752`） | 缺贴图字段一律回落内置默认白视图（使乘子恒为 1，画面不变）；阴影 / 天空缺失同样回落白视图；8 个 `spot_shadow[tile]` 逐瓦片填入；可选 `depth` / `depth_sampler`（粒子软粒子用 HiZ 历史）。 |
| 6 | `draw_sets_bind_batch(slot, inputs.data(), count)`（`渲染器.cpp:3756` → `管线.cpp:918`） | 每项写 17 个描述符（binding 0..8 单值 + binding 9 八元素数组），共 `count × 10` 条写记录、一次 `vkUpdateDescriptorSets`。binding 2 用 `depth` 或反照率占位。 |
| 7 | 回填集句柄（`渲染器.cpp:3761-3770`） | 第 i 个收集项的 `item.sampler_set = draw_set_get(slot, i)`；超出 `count` 的项回落共享 `sampler_set_get(slot)`。 |
| 8 | 录制 | 该绘制项绑定 `descriptorSetCount = 2`（set0 场景 / 粒子集 + 上述 set1）、实例缓冲绑定 1（`inputRate = INSTANCE`、stride 112）、`vkCmdDrawIndexed(…, instance_count, …)`。 |

**结果**：贴图走 **per-draw set1**（每项可采样不同纹理，不再被最后一次绑定覆盖）；标量材质走 **实例属性**（片元着色器按覆盖标志决定是否覆盖全局参数）。两条通道各自独立，故「同帧不同材质」不需要重建管线也不需要重写场景集。

补充：共享路径（未走 per-draw 集的绘制项）由 `material_textures_bind(slot, sampler, normal, roughness, emissive, ao, metallic)` 一次写 set1 binding 3/4/6/7/8（`管线.cpp:1132-1170`）；初始化时门面用默认白纹理先写满一遍，保证描述符始终完整（`渲染器.cpp:1541`）。

### 7.3 链路三：计算派发（GPU 实例视锥剔除）

**参与方**：门面 `Renderer::compute_pipeline_load` / `gpu_cull_mask`（`渲染器.cpp:5715`、`4730-4801`）→ `Compute_Context` → `视锥剔除.comp`。

| 步骤 | 调用 | 关键行为与副作用 |
| --- | --- | --- |
| 1 | `shader.module_load(module, "视锥剔除.comp.spv")` → `compute.pipeline_register(handle, module)`（`渲染器.cpp:5715` → `Compute.cpp:313`） | `compute_pipeline_create`：单 `COMPUTE` 阶段、`pName = "main"`、共享计算布局、`vkCreateComputePipelines(device, VK_NULL_HANDLE, …)`；句柄自 1 起，首个自动激活。 |
| 2 | `frustum_planes_extract(planes, view_proj)`（`渲染器.cpp:4743-4745` → `剔除.cpp:14`） | 取相机 `view × proj`，六平面归一化；失败（矩阵非法 / 退化平面）直接返回假，不调度。 |
| 3 | 逐实例 `world_bounds_build(bounds, local_min, local_max, transforms + i*16)`（`渲染器.cpp:4748-4759` → `包围体.cpp:14`） | 八角点变换重求世界 AABB，两次半径估计取大；结果打包为 `float[count × 4]`（球心 xyz + 半径）。任一实例矩阵非法即整体失败。 |
| 4 | `compute_buffer_load(sphere_handle, bytes, data)` / `compute_buffer_load(mask_handle, bytes)`（`渲染器.cpp:4761-4770`） | 由门面 + 内存模块创建缓冲并上传；掩码缓冲不写初值（GPU 全量覆写）。 |
| 5 | `compute_buffer_bind(sphere_handle, 0)`、`compute_buffer_bind(mask_handle, 1)`（`渲染器.cpp:4794-4795`） | 内部转 `Compute_Context::storage_bind(active_slot, binding, buffer, offset, size)`，写 set0 binding 0 / 1。 |
| 6 | `compute_dispatch(handle, count, 256, &push, sizeof(push))`（`渲染器.cpp:4796` → `渲染器.cpp:5766` → `Compute.cpp:647`） | `dispatch_ceil`：组数 = `ceil(count / 256)`；`elements == 0` 直接返回真。 |
| 7 | `Compute_Context::compute_dispatch`（`Compute.cpp:552`） | `vkCmdBindPipeline(COMPUTE, …)` → `vkCmdBindDescriptorSets(COMPUTE, layout, 0, 1, &set(active_slot))` → `vkCmdPushConstants(COMPUTE, 0, push_size)` → `vkCmdDispatch(x, 1, 1)` → `dispatch_count++`。 |
| 8 | `barrier(command_buffer, Compute_Barrier::ComputeToHost)`（`Compute.cpp:665`） | 展开为 `COMPUTE_SHADER/SHADER_WRITE → HOST/HOST_READ` 的 `VkMemoryBarrier2`，`vkCmdPipelineBarrier2`。 |
| 9 | `compute_buffer_read(mask_handle, mask_out, count × 4, 0)`（`渲染器.cpp:4797`） | 回读掩码；门面据此把 `1` 的实例计入绘制、`0` 的计入剔除观测。 |
| 10 | `compute_buffer_unload` 两个句柄 | 释放临时缓冲；管线与模块保留（懒加载复用）。 |

**结果**：CPU 只做平面提取与逐实例包围球构造，判定在 GPU 上按 256 线程/组并行；回读结果与 CPU 的 `frustum_sphere_visible` 口径一致，故可用 `frustum_aabb_visible` 做「GPU 是否多剔」的旁证。

**同族的另一条计算链路**（实例压缩 / 紧凑绘制）：`实例压缩.comp` 在内部按与 `distance_cull` / `backface_cull` 相同口径做距离与半球剔除，并把可见实例压成紧凑索引；门面用 `ComputeToCompute` 屏障串接「压缩 → 间接参数生成」，再用 `ComputeToGraphics` 让顶点 / 间接绘制阶段读取结果（`渲染器.cpp:5671`、`11758-11769`）。
