本模块覆盖白银纪元仓库中全部 CMake 构建脚本、预设、版本锁与构建期工具脚本，不含第三方库自带构建文件与 `out/build`、`build/` 生成物。路径均相对工作区根。

## 二、模块功能介绍

构建系统模块负责把四个可独立配置的引擎工程（Foundation、System、Renderer、Engine 聚合自检）、一个测试主层工程（Application/Test）、三个测试子工程（tests/Foundation、tests/System、tests/Renderer）以及一个游戏工程（Application/Game/星屑弹幕）串成“单向分层、层间只链接已构建静态库”的构建链。它不提供源码级联编，也不提供顶层超级构建：仓库根没有 `CMakeLists.txt`，每个工程各自拥有构建树与预设。

模块的对外职责是产出并维护三类构建契约：

1. 目标契约：每层产出唯一的静态库（Foundation / System / Renderer），应用层产出静态库与可执行文件；可执行文件只允许出现在 Application 层（`EngineTests.exe`、`Test<Layer>.exe`、`星屑弹幕.exe`）。
2. 面契约：每层用 `cmake/对外接口.cmake` 声明 `BYJY_<P>_OUT_LIB / OUT_LIBDIR / OUT_INC / OUT_DEF / OUT_LINK / OUT_SYS` 六个变量；上层通过 `byjy_jieru_xiaceng()` 读入并据此建立 `IMPORTED STATIC` 目标，永不回退编译下层源码。
3. 版次契约：每个库都携带构建期生成的 `版本锚点.h/.cpp`，上层消费 TU 被强制前置包含锚点头；头与库不同版次会在链接期因符号缺失而失败，而不依赖目录约定。

模块不负责：第三方库自身的构建（SDL3、VMA 被就地编入渲染层库，googletest 走上游 CMake 但以 `EXCLUDE_FROM_ALL` 接入，bullet3 / glm 的上游 `CMakeLists.txt` 存在但从不 `add_subdirectory`）；运行期资源加载；代码级模块划分（由各层自己的模块文档描述）；编辑器构建（Editor 无构建脚本）。

关键约束：

- 依赖方向唯一：`EngineFoundation → EngineSystem → EngineRenderer → Application`；渲染层是系统层的消费者，系统层不得引用渲染层任何符号。Engine 聚合面只合并 Foundation 与 System，不并入 Renderer，避免把窗口 / 图形依赖强加给只做逻辑的消费方。
- 版本锁是“全链”的：锁了某一层，所有消费该层的工程必须按同一份锁解析；各工程配置期用 `byjy_banben_hedui()` 比对“被消费层构建时记录的下层版本”与“本次解析结果”，不一致直接 `FATAL_ERROR`。
- 头文件消费一律走头快照：上层包含路径把下层快照根排在项目根之前，`Engine/<层>/...` 先命中快照，避免“头已改、库未重建”的新头旧库组合。
- 构建脚本不做隐式降级：库缺失、快照缺失、Vulkan SDK 缺失、测试子工程库缺失、Dear ImGui 缺失均为硬失败；唯一“只告警不失败”的降级点是 glslc 缺失（静态库仍可构建，着色器产物缺失）。

### 3.2 每层对外契约变量

| 层（前缀） | OUT_LIB | OUT_LIBDIR | OUT_INC | OUT_DEF | OUT_LINK | OUT_SYS |
| --- | --- | --- | --- | --- | --- | --- |
| Foundation（`BYJY_ENGINE_FOUNDATION`） | `EngineFoundation` | 本层根 | 项目根；`external/Json` | 空 | 空 | 空 |
| System（`BYJY_ENGINE_SYSTEM`） | `EngineSystem` | 本层根 | `external/Sol2/include`；`external/Lua`；`external/bullet3/src`；Foundation 的 OUT_INC | 继承 Foundation（空） | 继承 Foundation（空） | 继承 Foundation（空） |
| Renderer（`BYJY_RENDERER`） | `EngineRenderer` | 本层根 | System 的 OUT_INC；Vulkan `Include`；`external/SDL3/include`；`external/SDL3/include/build_config`；`external/VulkanMemoryAllocator/include` | 继承 System（空） | 继承 System（空）；追加 `vulkan-1.lib` 绝对路径 | `user32 gdi32 shell32 setupapi winmm imm32 version ole32 oleaut32 advapi32 uuid` |
| Engine 聚合（`BYJY_ENGINE`） | `EngineSystem;EngineFoundation` | System 根；Foundation 根 | 等于 System 的 OUT_INC | 等于 System 的 OUT_DEF | 等于 System 的 OUT_LINK | 等于 System 的 OUT_SYS |

| TestFoundation（`BYJY_TEST_FOUNDATION`） | `TestFoundation` | 子工程根 | Test 层根 | 空 | 空 | 空 |
| TestSystem（`BYJY_TEST_SYSTEM`） | `TestSystem` | 子工程根 | Test 层根 | 空 | 空 | 空 |
| TestRenderer（`BYJY_TEST_RENDERER`） | `TestRenderer` | 子工程根 | Test 层根 | 空 | 空 | 空 |

契约变量命名与含义属于层间契约，改名必须同步上层；`OUT_LINK` / `OUT_SYS` 在 System 层用带引号赋值，避免空串被 CMake 取消定义（`Engine/EngineSystem/cmake/对外接口.cmake` 有明确注释）。

| 目标 | 链接（PUBLIC / PRIVATE） | 说明 |

| `TestLauncher` | PUBLIC `GTest::gtest EngineFoundation` | 主调纯逻辑库 |

### 3.5 编译选项、定义与运行库口径

| 范围 | 选项 / 定义 |
| --- | --- |
| 全部引擎层与测试工程 | `CMAKE_CXX_STANDARD 20`、`CMAKE_CXX_STANDARD_REQUIRED ON`、`CMAKE_CXX_EXTENSIONS OFF`；MSVC 全局 `add_compile_options(/WX-)`（警告不阻断） |
| MSVC 各层目标 | `PRIVATE /MP /utf-8`；`PRIVATE _CRT_SECURE_NO_WARNINGS` |
| GCC / Clang 各层目标 | `PRIVATE -Wall -Wextra -pedantic`；`PRIVATE _GNU_SOURCE` |
| System 的 `external/` 源 | 单独设 `COMPILE_OPTIONS "/W3"`（第三方代码不跟随本层严口径） |
| Renderer 私有定义 | `GLM_FORCE_DEPTH_ZERO_TO_ONE`、`GLM_FORCE_RADIANS`（PRIVATE，不进公共头） |
| Test 目标 | MSVC `/MP /utf-8` + `_CRT_SECURE_NO_WARNINGS`；非 MSVC `-Wall -Wextra -pedantic` + `_GNU_SOURCE` |
| 测试子工程 | 同上层口径；`CMAKE_CXX_LINKER_LAUNCHER` 前置链接 BOM 包装器（Ninja + MSVC + CMake ≥ 3.21） |
| Game | `CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreadedDLL"`（/MD）；`stardust_barrage` 另加 `/utf-8 /MP /EHsc` 与 `_CRT_SECURE_NO_WARNINGS GLFW_STATIC`；`StardustImGui` 有 `GLFW_STATIC` 与 `/utf-8` |

运行库口径：引擎各层不显式设置 `MSVC_RUNTIME_LIBRARY`，沿用 MSVC 默认映射（Debug `/MDd`、其余 `/MD`）；`生成版本锚点.cmake` 把这一映射写进哈希输入（`Debug → MDd`，其余 `MD`）。Game 主动固定 `/MD` 以与其导入的 Release 静态库一致。

### 3.6 预编译头

构建脚本没有使用 CMake 的 `target_precompile_headers()`，也没有 `/Yu`、`/Yc` 一类 PCH 开关。所谓“预编译头”是各层 `common/前置头文件包含.h` 这一手写聚合头：

- `Engine/EngineFoundation/common/前置头文件包含.h`：C 标准库 + C++ 标准库 + `nlohmann/json`（本层源码统一包含它）。
- `Engine/EngineSystem/common/前置头文件包含.h`：先包含 Foundation 那份，再补 Sol2（`sol::`），因为本层 `common/external/Sol2/` 的别名头直接使用 `sol::table / sol::state`。
- `Engine/EngineRenderer/common/前置头文件包含.h`：仅包含 Foundation 那份；SDL3 / Vulkan / VMA 被明确排除在“预编译头”之外，理由是它们属于实现细节，不得进入公共头。

由于没有真正的 PCH，每个 TU 都要重新解析整份聚合头；这是构建期的明确性能取舍（换取跨层单一真源与公共头洁净）。

### 3.7 源文件清单契约

每个工程（除 Game）都遵循同一套“GLOB + 显式清单”规则：

1. `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)` 扫描源与头，并按构建目录前缀过滤、按目录白名单排除（System 排除 `/Tests/`，Test 排除 `/src/单元测试/` 与 `/src/主调/`）。
2. `byjy_source_list_sync()` 把扫描结果与清单文件比对（只比“路径集合”，不比排版），有差异才整体写回。
3. `add_library()` / `add_executable()` **不传** GLOB 结果；清单随后被 `include()`，由其中的 `target_sources()` 以字面文件名加入目标。
4. 清单必须位于“本层根目录”（与调用它的 `CMakeLists.txt` 同级），路径一律相对本层根、正斜杠。

清单文件清单：Foundation / System / Renderer 各一份 `源文件列表.cmake`；Test 主层按目标拆成 `源文件列表_TestLauncher.cmake`、`源文件列表_EngineTests.cmake`、`源文件列表_EngineTestObjects.cmake`（`源文件列表_TestCore.cmake` 仅在 TestCore 条件成立时才生成）；三个测试子工程各一份 `源文件列表_Test<Layer>.cmake`。SDL3 编译集合是手写清单 `cmake/SDL3源文件列表.cmake`，不走 GLOB。

### 3.8 构建预设契约

六个工程（Engine、Foundation、System、Renderer、Test、三个测试子工程合计八个 `CMakePresets.json`）的预设完全同构：

- `x64-Debug`：Ninja，`binaryDir = ${sourceDir}/out/build/x64-Debug`，`CMAKE_BUILD_TYPE=Debug`。
- `x64-Release`：Ninja，`binaryDir = ${sourceDir}/out/build/x64-Release`，`CMAKE_BUILD_TYPE=Release`。
- `build-Debug` / `build-Release` 构建预设分别绑定上述配置预设。
- 预设声明 `cmakeMinimumRequired 3.25`；各 `CMakeLists.txt` 自身要求 3.20（Test 与测试子工程要求 3.24）。

`CMakeSettings.json` 只在 Foundation、System、Test 三处存在（VS 打开文件夹用，`buildRoot = ${projectDir}/out/build/${name}`）；Engine、Renderer、Game、Editor 没有该文件。

## 六、模块设计 / 实现细节

### 6.1 源文件清单的维护方式与遗漏风险

维护机制（实现见 `Engine/EngineFoundation/cmake/生成源文件列表.cmake`）：

1. 配置期 GLOB 扫描，结果按“相对本层根、正斜杠”归一化。
2. 清单文本由固定说明头 + 两段 `target_sources` 组成；源段与头段各一段。
3. 读旧清单，提取全部引号字符串并排序；与新文本的路径集合比较；集合相同则不写盘。
4. 不比较排版，避免 VS 改写后的缩进差异造成“每次配置都回写 → 清单是配置依赖 → 无限重配”的咬合退化。

为什么必须这么做：GLOB 工程的构建脚本里没有具体文件名，Visual Studio 文件视图的改名 / 迁移操作依赖 File API backtrace 找到“可改写的引用”；只有 `target_sources` 里直接写字面文件名，且该调用位于被 `include` 的 `.cmake` 中，backtrace 才落在清单文件上。清单是配置依赖，被改写即触发重新配置。

由此产生的隐式约束与风险：

- 清单是这些文件的“唯一”加入点。若把 GLOB 结果再传给 `add_library()`，backtrace 归先加入者，VS 又无法改写。
- 清单必须放在本层根。放在 `cmake/` 子目录会让 VS 写出 `../src/...` 这类 CMake 解析不到的相对路径，配置直接失败。
- 清单被 VS 改写后，若有人手工删除条目，下一次配置会按 GLOB 结果“静默恢复”，没有告警；反之若有人手工添加不存在的文件，下一次配置会静默删除。
- 新扩展名不会自动纳入：Foundation 只收 `src/common/external` 下的 `.cpp`（`.c` 不收）、头只收 `src/common` 下的 `.h/.hpp`；Renderer 只收 `src` 下的 `.cpp/.c`，`common` 只收头；System 收 `src/common/external` 的 `.cpp/.c`；Test 收 `src/*.cpp/*.c`。若在 `common/` 放 `.cpp`，Foundation 与 Renderer 都不会编它。
- System 的 GLOB 结果会排除 `/Tests/` 路径段；Test 主层排除 `/src/单元测试/`、`/src/主调/`。这些排除是硬编码正则，新增类似目录名会被误排除。
- `源文件列表_TestCore.cmake` 当前不存在，因为 Test 主层 `src/` 根下无源文件（全部在 `单元测试/` 与 `主调/` 下，已被排除）。这是有意条件目标，不是遗漏；一旦在 `src/` 根或其它子目录新增功能测试代码，`TestCore` 块会自动生效并生成清单。
- Test 主层对“多目标”按目标各建一份清单，避免引用到未创建的条件目标；代价是清单数量多，新增目标必须同步新增清单与调用。
- 生成锚点 `.cpp` 不经清单，而由 `target_sources(EngineFoundation PRIVATE ${ANCHOR_CPP})` 单独加入；它不参与 VS 文件视图改名。

### 6.2 版本锁的用途与升级流程

用途：给上层声明“我要用下层的哪个版本”。

- 锁空（默认，六条目全空）：跟随下层最新构建树 `out/build/x64-<配置>`，天然与下层当前库同版次，不需要副本。
- 锁非空：只从 `Engine/版本缓存/<层>/x64-<配置>/<12 位哈希>` 取头与库；目录缺失即 `FATAL_ERROR`，并给出“先构建该层 / 清空锁 / 改成存在的哈希”三条处置。
- 按配置分开是必须的：同一份源码在 Debug / Release 下锚点哈希不同（哈希含构建类型与运行库口径），否则 Release 会拿 Debug 哈希找不到条目。

一致性要求：锁是“全链”的。若只锁 Foundation 而不让 System / Renderer 按同一份锁解析，System 会用新 Foundation 构建、Renderer 却链旧 Foundation，锚点符号在链接期必失配。`Engine/版本锁.cmake` 被所有层共享读取，天然满足“同一份锁”；各层配置期再做 `byjy_banben_hedui()` 双向比对（被消费层构建时记录的 `BYJY_BUILD_AGAINST_<层>_<配置>` vs 本次 `BYJY_RESOLVED_VERSION_<层>_<配置>`），不一致直接拒绝配置。

升级流程（脚本约定）：

1. 成套改：Foundation / System / Renderer × Debug / Release 六条一起改，不允许单层漂移。
2. 用工作站脚本 `升级测试锁.ps1`（不在本仓库内，注释记录其位置）一次性写入当前构建树版本；各层（含三个测试子工程）只读本文件，不写。
3. 锁值落后于构建树时，`byjy_banben_jiexi` 打印“版本锁滞后”WARNING，不阻断；停在旧版本是合法选择，但必须可见。
4. 升级后必须重建所有消费层的测试库，否则测试库的 `依赖版本.cmake` 与新的解析结果不一致，配置期会被 `byjy_banben_hedui` 拦下。

风险点：

- 锁值全空时，构建顺序敏感：先构建 Foundation 再构建 System，System 才会链到最新的 Foundation；若顺序颠倒，System 链的是旧库，锚点校验会在其上层暴露。
- 版本缓存目录 `Engine/版本缓存/` 是构建产物且被顶层 `.gitignore` 忽略；锁非空状态无法通过仓库分发复现，只能本机重建。
- `byjy_banben_jiexi_shuang()` 对 Debug / Release 无条件解析两次；只构建一棵树时另一配置解析结果为空，单配置生成器只会用当前配置那份，但 `byjy_banben_hedui()` 对空结果静默跳过。

### 6.3 版本缓存的发布与清理

发布由各层 `*VersionPublish` 自定义目标在快照导出后执行，参数统一：

- `LAYER_NAME / LAYER_TOKEN`：`EngineFoundation / engine_foundation`、`EngineSystem / engine_system`、`EngineRenderer / renderer`。
- `CONFIG_TREE = x64-$<CONFIG>`；`KEEP=8`。
- Renderer 额外 `EXTRA_DIR=shaders`：锁定版本时上层只从缓存取该版本，着色器必须一并进来，否则 Test 从 `IMPORTED_LOCATION` 推导出的 `shaders` 目录会落空。

幂等性：头按内容不同才覆盖（保留未变文件 mtime，避免上层无谓重编），库按内容不同才覆盖；同一版本重复发布不产生额外变更。

清理规则：以缓存条目内 `.lib` 的时间戳作为发布时间，按时间排序，从最旧开始删除，直到剩余不超过 `KEEP`；读取 `Engine/版本锁.cmake` 收集全部非空锁值，命中即跳过。锁值列表不区分配置，但缓存目录已按层 / 配置隔离，只影响“保留”判断，不会删除被锁条目。

### 6.4 外部库（`external/`）引入合规性

总体结论：全部第三方依赖都以“项目内拷贝 + 相对路径推导”引入，没有投影文件夹、没有绝对路径字面量；但存在若干偏离“纯源码编入”模型的点。

逐层现状：

| 位置 | 内容 | 引入方式 | 合规性判断 |
| --- | --- | --- | --- |
| `Engine/EngineFoundation/external/` | `Json`（nlohmann）、`tinygltf`（纯头） | `external/Json` 进 PRIVATE 与对外包含根；`tinygltf` 由本层 `gltf加载器` 直接包含 | 符合；两条根均由 `PROJECT_ROOT_DIR` 相对推导 |
| `Engine/EngineSystem/external/` | `bullet3`（仅 LinearMath + BulletCollision 源码）、`Lua`（32 个核心 `.c`）、`Sol2`（纯头） | 源码随 `external/*.{cpp,c}` GLOB 编入 `EngineSystem.lib`；包含根进对外面 | 符合；不使用 bullet3 上游 `src/*/CMakeLists.txt` |
| `Engine/EngineRenderer/external/` | `SDL3`（裁剪源码）、`VulkanMemoryAllocator`（纯头）、`glm`（纯头）、`stb`（纯头） | SDL3 走手写清单就地编入；VMA 实现 `src/render/Memory/core/VMA实现.cpp` 编入；包含根 PRIVATE 为主，SDL3/VMA 的公共头进对外面 | 符合；`external/glm/CMakeLists.txt` 与 bullet3 上游 CMakeLists 为残留，从未 `add_subdirectory` |
| `Application/Test/external/` | `googletest`（源码 + 上游 CMake）、`Dear_ImGui`（源码）、`glad`（残留） | googletest 以 `add_subdirectory(... EXCLUDE_FROM_ALL)` 接入，设 `INSTALL_GTEST OFF`、`BUILD_GMOCK OFF`、`gtest_force_shared_crt ON`；Dear ImGui 由 Test 与 Game 各编一份；glad 未被任何脚本引用 | googletest 属“项目内拷贝 + 上游构建系统”，仍符合相对路径约束，但引入第三套构建逻辑；glad 为无引用残留 |
| `Application/Game/星屑弹幕/external/` | `silver_era`（`lib`、`include`、`third_party`、`shaders`）、`Dear_ImGui` | 全部以 `${CMAKE_SOURCE_DIR}/external/...` 相对引入；三个库直接 `IMPORTED_LOCATION` | 路径合规；但 `lib/` 在快照中为空、`include` 中无 `版本锚点.h`、`third_party/glfw` 只有头没有 `glfw3.lib`，属“人工部署的预编译包”模型 |

与工作区“外部库放在 `external/`、与 `src/` 平级”的约定对照：本仓库把 `external/` 放在各层根（与各层 `src/` 平级），而不是仓库根统一一份。按“项目原始引入方案优先”的规则采用现状；代价是同一第三方在不同层可能各有一份副本（Dear ImGui 在 Test 与 Game 各一份，命名空间与编译选项需各自维护）。

关键绝对性检查：所有 `target_include_directories` / `target_link_libraries` 的第三方路径均由 `PROJECT_ROOT_DIR`、`BYJY_PROJECT_ROOT`、`CMAKE_SOURCE_DIR`、`CMAKE_CURRENT_LIST_DIR` 拼出，没有写死盘符路径；唯一的外部绝对路径是 Vulkan SDK（`VULKAN_SDK` 或 `C:/VulkanSDK/<版本>`）与 Game 的 `glfw3.lib`/`vulkan-1.lib`（实际由 `SILVER_ERA_ROOT` 相对拼出）。Vulkan SDK 属机器级依赖，`VulkanSDK探测.cmake` 明确“不猜路径、不静默降级”。

### 6.5 Debug / Release 与预设配置

- 生成器统一 Ninja（单配置），Debug 与 Release 用两棵独立构建树并存，互不覆盖。
- 单配置下 `CMAKE_BUILD_TYPE` 缺省时被强制设为 `Debug` 并打印提示；非法取值直接 `FATAL_ERROR`。合法集合为 `Debug Release RelWithDebInfo MinSizeRel`（区分大小写）。
- 多配置生成器（VS）由 `CMAKE_CONFIGURATION_TYPES` 管理，脚本不介入构建类型选择，只把快照与库按配置分目录，并用 `$<CONFIG>` / `IMPORTED_LOCATION_<CONFIG>` 分派。
- `RelWithDebInfo` / `MinSizeRel` 在库路径上复用 Release（`IMPORTED_LOCATION_RELWITHDEBINFO / MINSIZEREL` 指向 Release 库），锚点头按 `$<CONFIG>` 独立注入。
- 预设只是把命令固定下来，不改变构建行为；`cmakeMinimumRequired 3.25` 与各脚本 `cmake_minimum_required 3.20/3.24` 的差异只影响“用预设时的最低 CMake 版本”。
- `CMakeSettings.json` 中 Foundation / System 的 `BYJY_JOIN_TEST_HOST` 未被任何脚本读取，属遗留缓存变量；Test 的 `CMakeSettings.json` 没有该变量。

### 6.6 顶层忽略规则

仓库根 `.gitignore` 对构建系统的直接约束：

- 忽略 `out/`、`Debug/`、`Release/`、`x64/`、`x86/`、`bin/`、`obj/`，以及 `*.obj *.exe *.dll *.pdb *.lib *.exp *.ilk *.tlog`。因此所有静态库、可执行文件、构建树都不入库。
- 忽略 `Application/`、`Engine/EngineFoundation/`、`Engine/EngineSystem/`、`Engine/EngineRenderer/`：这四个目录各自是独立 git 仓库，顶层仓库只作为总览线收录 `Engine/CMakeLists.txt`、`Engine/CMakePresets.json`、`Engine/版本锁.cmake`、`Engine/cmake/` 等聚合层文件。
- 忽略 `Engine/版本缓存/`：版本缓存是构建产物（按版次哈希存放的头快照与静态库），不入库。

由此产生两个结构性后果：

1. 渲染层“被顶层忽略”意味着它的构建脚本变更不会出现在顶层 diff 中；导航与版本锁必须按各层独立仓库口径理解。
2. `*.lib` 全局忽略使 Game 的预编译包（`external/silver_era/lib/*.lib`）无法通过顶层仓库分发；Game 的构建前提落在仓库之外的人工部署。

### 6.7 中文源码名与 UTF-8 / BOM 处理

项目源文件名与标识符大量使用中文，构建脚本为此做了两处 Windows 专用适配：

- 归档阶段：Ninja 写出的 `*.rsp` 无 BOM，MSVC `lib.exe` 按系统 ANSI 代码页解读中文对象名，会报 `LNK1181`。Foundation 与 System / Renderer 在 `project()` 之后改写 `CMAKE_CXX_CREATE_STATIC_LIBRARY`，前置 `ar_rsp_bom.ps1`；脚本只在“非 ASCII 且无 BOM”时补三个字节，其余原样搬运。
- 链接阶段：Test 主层与测试子工程用 `CMAKE_CXX_LINKER_LAUNCHER` 前置 `link_rsp_bom.ps1`，对 `@*.rsp` 重写为带 BOM 的 UTF-8，避免 `LNK1104`。
- 编译阶段：MSVC 目标统一加 `/utf-8`，保证源码与执行字符集一致。
- 包装器缺失时只告警（`message(WARNING)`），构建继续，但在中文路径下很可能在归档 / 链接期失败。

### 6.8 头快照与包含次序

- 快照只镜像本层自有头（Foundation 与 System / Renderer 的 `common` + `src`），第三方头不镜像：第三方在外对面上是独立绝对路径条目，不经过快照解析，镜像它们只会多复制上千文件。
- 镜像保留“项目根相对”完整层级：`<快照根>/Engine/<层>/...`。上层把对外面里的“项目根”条目换成快照根即可无缝解析同一前缀。
- 快照目标 `add_dependencies(*IncludeSnapshot <层库>)`，保证库失败不导出新快照。
- 消费层的包含次序为“下层快照根 → 项目根 → 本层根”，快照必须在前。原因：导入目标的 INTERFACE 包含目录会被 CMake 归入 `/external:I` 组，而目标自身的 `-I` 恒在该组之前；把快照写成自身包含目录即可优先命中。
- 兜底校验 `byjy_jiaoyan_xiacengtou()` 以快照为合法头集合，扫描源码里 `Engine/<层>/...` 的 `#include`；下层新增 / 重命名公共头但没重建时，上层配置期直接失败，而不是静默编进源码树的旧头。

### 6.9 版次锚点

- 哈希输入：`MIRROR_DIRS` 下全部 `.h/.hpp/.inl` 的相对路径与内容 + 构建类型 + 运行库口径；System 额外把 `external/` 纳入 `HASH_DIRS`（第三方头变化也触发版次变化），但不进快照。
- 哈希输出：SHA256 前 12 位；符号名 `byjy_stamp_<token>_<hash>`，token 为 `engine_foundation / engine_system / renderer`。
- 锚点头 C / C++ 双兼容：纯 C TU 只保留函数声明与 `/include` 链接指令；C++ TU 追加 `inline void (*const <token>)(void)` 并标记 used；MSVC x64 追加 `#pragma comment(linker, "/include:<symbol>")`。原因是锚点头会被 `/FI` 强灌进每个消费 TU，包括渲染层就地编入的 SDL3 纯 C 源。
- 注入方式：单配置从库路径上溯得快照根，`file(GLOB_RECURSE)` 找 `Engine/*版本锚点.h` 后以 `/FI`（MSVC）或 `-include`（GCC）挂到 IMPORTED 目标的 INTERFACE_COMPILE_OPTIONS；多配置用 `$<$<CONFIG:Debug>:/FI...>` 形式分别注入，RelWithDebInfo / MinSizeRel 复用 Release 锚点。
- 失败语义：头与库不同版次 → 锚点符号缺失 → 链接期 `LNK2019`，不需要运行期比较。

### 6.10 着色器编译与部署

- 源：`Engine/EngineRenderer/assets/shaders/*.vert|*.frag|*.comp`（文件名可为中文）。
- 产物：`<Renderer 构建树>/shaders/<源文件名>.spv`（保留原扩展名，如 `场景.vert.spv`）。
- 工具：优先 `<Vulkan SDK>/Bin/glslc.exe`，其次 PATH；可用 `BYJY_GLSLC_EXECUTABLE` 手工指定。找不到只 `WARNING`，静态库仍构建。
- 目标：逐文件 `add_custom_command` + 汇总到 `RendererShaders`（ALL），并 `add_dependencies(EngineRenderer RendererShaders)`，使“构建渲染层”这一步就能验证着色器语法。
- 分发：版本缓存发布带 `EXTRA_DIR=shaders`；Test 主层配置期从 Renderer 库路径推导 `shaders` 并 `file(COPY)` 到 Test 层根；TestRenderer 子工程同样拷贝；Game 构建后 `copy_directory` 到可执行文件目录。

### 6.11 安装规则

- Foundation：安装整层 `*.h/*.hpp` 到 `include/Engine/EngineFoundation`（排除 `Private` 子目录），库到 `lib`。
- System：只安装 `common` 与 `src` 下的头（第三方头不装），库到 `lib`。
- 两层的安装规则都不包含构建期生成的 `版本锚点.h`；注释已说明“当前没有安装使用方，若将来以 install 产物分发需补装锚点头，否则消费方拿不到版本校验”。这是一处已知缺口。

### 6.12 Game 独立构建

- 工程名 `stardust_barrage`（ASCII，CMake 目标名不允许非 ASCII），输出名才是中文 `星屑弹幕`。
- 配置期硬检查：`external/silver_era/lib/EngineRenderer.lib`、`external/silver_era/include/Engine/EngineRenderer/src/render/Renderer/渲染器.h`、`external/Dear_ImGui/imgui/imgui.cpp`；任一缺失 `FATAL_ERROR`。
- 三个引擎库以 `IMPORTED GLOBAL` 建立，但只设 `IMPORTED_LOCATION`，不挂 INTERFACE 包含目录 / 定义 / 系统库，也不注入锚点头；所有包含根与链接库在手写列表里重复声明。
- `SILVER_ERA_INC` 十项；`SILVER_ERA_THIRD_LIBS` 为 `glfw3.lib + vulkan-1.lib`；`SILVER_ERA_SYS_LIBS` 十二项（比 Renderer 对外面多 `opengl32`）。
- 源码按七个域分组（foundation / world / entity / communication / system / presentation / app），`add_executable` 一次性列出。
- 资产部署：对 Debug / Release / MinSizeRel / RelWithDebInfo 四个目录，若 `bin/<配置>/assets/config/设置.json` 不存在则整目录拷贝 `assets/`（不覆盖玩家已保存的设置）；着色器用 `POST_BUILD` 每次覆盖。
- 未使用 `Engine/版本锁.cmake`，也未使用 `cmake/对外接口.cmake`；Game 的“与引擎同版次”靠部署包人工保证。

## 七、模块运行链路详例

### 7.1 一次 Engine 全层构建（Debug）

调用方：开发者或 CI，在 `Engine` 目录下按层顺序执行三条“配置 + 构建”。

步骤：

1. `cmake --preset x64-Debug`（`Engine/EngineFoundation`）
   - 读取 `CMakePresets.json`，生成 `out/build/x64-Debug`，`CMAKE_BUILD_TYPE=Debug`。
   - `CMakeLists.txt` 第 1.5 节确认构建类型；第 2 节 GLOB 收源；`生成源文件列表.cmake` 比对并可能写回 `源文件列表.cmake`；`add_library(EngineFoundation STATIC)`；`include(源文件列表.cmake)` 把 18 个源与 68 个头加入目标。
   - `add_custom_command` 调 `生成版本锚点.cmake`，求哈希、写 `生成/版本锚点.{h,cpp}`；`target_sources` 加入锚点 cpp。
   - 建立 `EngineFoundationIncludeSnapshot` 与 `EngineFoundationVersionPublish` 两个 ALL 目标，并串成“库 → 快照 → 缓存”依赖。
   - 产物：`lib/EngineFoundation.lib`、`include/Engine/EngineFoundation/...`（含锚点）、`Engine/版本缓存/EngineFoundation/x64-Debug/<哈希>/`。
2. `cmake --preset x64-Debug` + 构建（`Engine/EngineSystem`）
   - `cmake/接入下层.cmake` 读 Foundation 对外接口；`版本工具.cmake` 按 `Engine/版本锁.cmake` 解析（锁空 → `<Foundation>/out/build/x64-Debug`）。
   - `byjy_jieru_xiaceng()` 建立 `EngineFoundation` 导入目标，定位 `lib/EngineFoundation.lib`，挂包含目录 / 定义 / 链接库，并从库路径反推快照根注入 `/FI.../版本锚点.h`。
   - 逐配置 `byjy_jiaoyan_xiacengtou()` 校验本层源码引用的 Foundation 头都在快照里；`byjy_banben_hedui()` 校验 Foundation 版本一致。
   - GLOB 收 `src/common/external`（含 Lua 32 个 `.c` 与 bullet3 111 个源）；`external/` 源单独 `/W3`。
   - 生成 System 锚点（`HASH_DIRS` 含 `external/`）；`add_library`；PUBLIC 包含根 = Foundation 快照 + 项目根 + 对外面；链接 `EngineFoundation`。
   - 产物：`lib/EngineSystem.lib`、快照、缓存条目。
3. 构建 `Engine/EngineRenderer`
   - 先 `VulkanSDK探测.cmake` 定位 SDK（缺失即失败）；再分别解析 Foundation 与 System，建立两个导入目标。
   - 校验两套快照存在与头完整性；包含根 = Foundation 快照、System 快照、项目根、对外面。
   - GLOB 收本层 `src`；`SDL3源文件列表.cmake` 给出 237 条 SDL3 源，补成绝对路径后与自有源一起进 `add_library`。
   - 生成 Renderer 锚点；PUBLIC / PRIVATE 包含根分流；链接 `EngineFoundation`、`EngineSystem`、`vulkan-1.lib`、11 个系统库。
   - glslc 可用则 `RendererShaders` 编 70 余个 GLSL 到 `shaders/*.spv`，并作为 `EngineRenderer` 依赖。
   - 产物：`lib/EngineRenderer.lib`、快照、`shaders/`、缓存条目（含 `shaders/`）。
4. 可选：构建 `Engine` 聚合层
   - `cmake/接入下层.cmake` + `版本工具.cmake` 双配置解析 System 与 Foundation；`byjy_jieru_xiaceng()` 按 `BYJY_ENGINE_OUT_LIB`（System;Foundation）建立两个导入目标，任一库缺失即 `FATAL_ERROR`。
   - `byjy_banben_hedui("Engine" EngineSystem ...)` 校验 System 构建时用的 Foundation 版本；最后 `EngineAggregateCheck` 只打印“聚合面就绪”，不产库。
   - 结果：聚合面可用，Application 各层可直接读 `Engine/cmake/对外接口.cmake`，不依赖该构建树。

### 7.2 一次 TestSystem 构建与用例可执行产物

调用方：修改 EngineSystem 的开发者，只想验证系统层。

步骤：

1. 前置：先构建 Foundation 与 System 的对应配置树（锁空时直接读最新树；锁非空时缓存必须有对应版本）。
2. `cmake -S Application/Test/tests/System -B out/build/x64-Debug -G Ninja`（或 `cmake --preset x64-Debug`）。
   - `CMakeLists.txt` 先算 `BYJY_SUB_ROOT / BYJY_TEST_ROOT / BYJY_PROJECT_ROOT`，`include(测试子工程.cmake)`。
   - `byjy_ceshi_zhunbei()`：C++20、`/WX-`、编译数据库、`CMAKE_CXX_LINKER_LAUNCHER` 指向 `link_rsp_bom.ps1`。
   - `byjy_ceshi_yilai("TestSystem" EngineFoundation ...)` → 解析并建立 `EngineFoundation` 导入目标；再 `byjy_ceshi_yilai("TestSystem" EngineSystem ...)` → 建立 `EngineSystem` 导入目标并做一致性校验。
   - `byjy_ceshi_tou_jiaoyan()` 双配置校验两套快照与头完整性；`byjy_ceshi_jilu()` 写 `依赖版本.cmake`。
3. 配置期同时：
   - `add_subdirectory(external/googletest ... EXCLUDE_FROM_ALL)`，仅在被链接时编 gtest；
   - GLOB `src/*.cpp`，`byjy_source_list_sync()` 生成 / 刷新 `源文件列表_TestSystem.cmake`（10 源 + 1 头）；
   - `add_library(TestSystem STATIC)` + `include(清单)`；PUBLIC 包含 = Foundation 快照、System 快照、项目根、Test 层根；PUBLIC 链接 `EngineSystem EngineFoundation`；PRIVATE 链接 `GTest::gtest`；库输出到 `out/build/x64-Debug/lib/TestSystem.lib`；
   - `add_executable(TestSystemMain entry/薄入口.cpp)`，`WHOLE_ARCHIVE` 收编 `TestSystem`，`OUTPUT_NAME=TestSystem`，`RUNTIME_OUTPUT_DIRECTORY=${BYJY_TEST_ROOT}/$<0:>`。
4. 构建 → 产物：
   - `Application/Test/tests/System/out/build/x64-Debug/lib/TestSystem.lib`；
   - `Application/Test/TestSystem.exe`（薄入口，位于 Test 层根，便于按“可执行文件目录”解析资源）。
5. 运行：`Application/Test/TestSystem.exe --gtest_filter=...`。薄入口以 `WHOLE_ARCHIVE` 收编静态库，静态注册的用例不会被链接器丢弃；该子工程不注册 ctest（ctest 只在 Test 主层注册）。

### 7.3 一次 Game 构建（含对引擎库的引用方式）

调用方：游戏开发者，需已有 `external/silver_era` 预编译包。

步骤：

1. 准备 `Application/Game/星屑弹幕/external/silver_era/`：`lib/{EngineFoundation.lib, EngineSystem.lib, EngineRenderer.lib}`、`include/Engine/...` 三层头快照（与库同版次）、`third_party/{Json, glfw, bullet3/src, Sol2/include, Lua, SDL3/include+build_config, VulkanMemoryAllocator/include, vulkan}`、`shaders/*.spv`；`external/Dear_ImGui` 就位。
2. 配置：`cmake -S Application/Game/星屑弹幕 -B <构建目录> -G "Visual Studio ..." -A x64`（脚本注释给出的口径；该工程没有 `CMakePresets.json`，构建类型由 `--config` 选择）。
   - 检查三个前置文件；缺失即 `FATAL_ERROR`。
   - `add_library(EngineFoundation/EngineSystem/EngineRenderer STATIC IMPORTED GLOBAL)`，各设 `IMPORTED_LOCATION` 指向 `external/silver_era/lib/<层>.lib`；不挂任何 INTERFACE 属性。
   - `StardustImGui` 编 6 个 ImGui 源，PUBLIC 包含根 = ImGui 两个目录 + `SILVER_ERA_INC`，PUBLIC 链接 `EngineRenderer` + `glfw3.lib` + `vulkan-1.lib` + 12 个系统库。
   - `stardust_barrage` 编 19 个自有源，PRIVATE 包含七个源码域目录 + 合并头快照根 + ImGui 目录；PRIVATE 链接 `StardustImGui`、`EngineSystem`、`EngineFoundation`、`EngineRenderer`、第三方库、系统库。
3. 构建：
   - 链接时按 `EngineSystem → EngineFoundation → EngineRenderer` 顺序交给链接器；静态库间符号由链接器按重复扫描解析（Game 未使用 WHOLE_ARCHIVE，也无需它：三库被直接引用）。
   - 产物 `<构建目录>/bin/<配置>/星屑弹幕.exe`。
   - 资产：四个配置目录中若 `assets/config/设置.json` 缺失则播种整份 `assets/`。
   - 着色器：`POST_BUILD` 每次 `copy_directory` 到 `$<TARGET_FILE_DIR:stardust_barrage>/shaders`。
4. 运行前提：可执行文件同目录存在 `assets/` 与 `shaders/`；`Engine_Env` 以可执行文件目录为配置基目录。
5. 与引擎版的绑定强度：Game 不读版本锁、不注入锚点，只按固定目录取库与头；若头与库不同版次，构建期不会报错（锚点符号未参与），运行期行为由部署包一致性决定。这是当前模型下最弱的一环，见“附：待确认正文”第 5 条。
