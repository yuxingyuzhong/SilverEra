## 二、模块功能介绍

本模块是 `EngineRenderer` 层独立测试子工程（`TestRenderer`）中“渲染核心 + 资源 + 光照 + 后处理 + 关卡”这一半用例的集合。它存在的唯一目的是：把渲染层门面 `engine::Renderer` 的公开接口按“特性域”逐条钉死，使渲染层任何一次内部改动都能在编译后立刻以“像素差异 / 统计计数差异 / 接口语义差异”暴露出来。

职责边界如下。

第一，**只测渲染层公共面，不测 Vulkan 细节**。绝大多数用例只包含 `Engine/EngineRenderer/src/render/Renderer/渲染器.h`，不引入 Vulkan / SDL 类型；个别例外是 `渲染后处理链测试.cpp` 为了“UI 后置”临时引入 `渲染器_UI通道.h` 并在回调里直接调用 `vkCmdClearAttachments`，这是本模块内唯一出现 Vulkan 符号的用例（见 §三 第 47 项）。

第二，**分三层依赖**：`EngineFoundation`（前置头 / 日志 / 数学）→ `EngineSystem`（关卡文本、粒子数据、场景数据等中立描述）→ `EngineRenderer`（被测门面）。测试静态库同时链接三层，因此个别用例直接测系统层纯 CPU 逻辑（粒子池、关卡文本），并借助渲染层 `场景装配` 的 `level_bridge_*` 把系统层描述装成渲染资源。

第三，**不负责**：（a）窗口 / 交换链的真实交互语义（只验证“隐藏窗口 + 回读”路径）；（b）文字排版细节、像素回读守卫、中文图集、纹理分级、相机、雾、聚光灯、阴影级联等——这些文件不在本清单内，属于同一测试工程的另一批用例；（c）第三方库（googletest、SDL3、Vulkan）的正确性。

第四，**关键约束**：

1. 所有像素断言必须“通道序无关”。交换链可能为 RGBA 或 BGRA；用例只依赖绿通道恒为字节下标 1、alpha 恒为下标 3，并用“外通道取较大者 / 三通道排序 / 恰有一高”判定红蓝。
2. 所有可跳过的设备能力必须在运行时探测：像素回读、MSAA 档位、计算路径（GPU 剔除 / Hi-Z / Cluster）、系统字体、着色器资源。探测失败走 `GTEST_SKIP()`，不得写成失败。
3. 能力缺失的“数值分支”不跳过而是分两支断言。典型是 GPU 时间戳：支持时断言 `gpu_frame_ms > 0`、`gpu_samples == 2`；不支持时断言三个 GPU 字段恒 0。
4. 每个用例自带设备生命周期：栈上构造 `engine::Renderer`，`init(hidden_config())`，用例末显式卸载资源；渲染器析构再 `shutdown()`。用例之间不共享设备，故不存在跨用例状态污染。
5. 像素比对优先“同场景两帧对比”（关闭 / 开启某特性），而不是硬编码绝对颜色；绝对颜色断言只用于端点色（纯黑 / 纯白 / 纯红）与“清屏色候选”。
6. 所有“参数非法”用例都断言“整次忽略且画面逐字节不变”，而不是断言返回值以外的副作用。

## 三、模块公开接口

本模块是测试模块，没有对外导出的生产接口；它的“公开接口”是 **gtest 套件组织契约** 与 **每个文件覆盖的被测接口 / 特性**。下面先给套件契约，再按文件逐条登记。

### 3.1 测试套件组织契约

**（1）可执行体与注册**

- `entry/薄入口.cpp` 定义 `int main(int argc, char** argv)`：`SetConsoleOutputCP(CP_UTF8)` + `SetConsoleCP(CP_UTF8)` → `::testing::InitGoogleTest(&argc, argv)` → `byjy_test_anchor_renderer()` → `return RUN_ALL_TESTS();`。
- `src/注册锚.cpp` 定义 `extern "C" void byjy_test_anchor_renderer()`，函数体为空；头文件里没有声明，只有入口文件用 `extern "C"` 自行声明。用途是让链接器认为该静态库被引用，从而用 WHOLE_ARCHIVE 收编全部 `.obj`，保留 `TEST` / `TEST_F` 的静态注册项。
- CMake 侧（`Application/Test/tests/Renderer/CMakeLists.txt`）：`add_library(TestRenderer STATIC)` 收集 `src/*.cpp`；`add_executable(TestRendererMain entry/薄入口.cpp)` 以 `$<LINK_LIBRARY:WHOLE_ARCHIVE,TestRenderer>` 链接，输出名 `TestRenderer`，落在 Test 层根目录；配置期从渲染层构建树拷贝 `shaders/`。

**（2）用例命名与夹具**

- 全部使用 gtest 宏：`TEST(套件名, 用例名)` 或 `TEST_F(夹具名, 用例名)`；套件名与用例名均为中文或“英文标识 + 中文”，可直接用 `--gtest_filter` 过滤。

**（3）设备与配置契约**

- 隐藏窗口配置统一为：`width` / `height` / `hidden = true`。常用尺寸：`64×36`（绝大多数像素用例）、`320×180`（初始化 / MSAA）、`128×72`（关卡端到端）、`1920×1080`（GPU / Hi-Z / Cluster 性能用例）。
- 回读口径统一：`std::vector<uint8_t> pixels(宽 × 高 × 4)`，RGBA8 紧排、逐行自上而下；`frame_render(pixels.data(), capacity, &width, &height)`。
- 资源清理契约：按“先创建后释放”的逆序 `pipeline_unload` / `material_unload` / `mesh_unload` / `texture_unload` / `render_target_destroy` / `font_unload`；`ASSERT_*` 提前返回时不保证清理，由进程退出兜底。

**（4）跳过契约**

以下条件任一成立即 `GTEST_SKIP()`，不计失败：

- `!renderer.readback_supported()`（交换链图像不具备传输源用法）；
- `renderer.msaa_samples() <= 1`（要求多重采样的用例）；
- `!renderer.compute_supported()`（GPU 剔除 / 前缀和 / Cluster GPU 路径）；
- `!renderer.cluster_supported()` 或 `!renderer.hiz_supported()`；
- 系统字体 `C:\Windows\Fonts\consola.ttf` 不存在；
- 着色器 / 资产文件缺失（用例内以 `ASSERT_TRUE` 失败，不跳过）。

### 4.3 断言与诊断设施

- `pixel_text()`：所有像素断言失败时输出 `r/g/b/a`，避免只看到“期望真得到假”。
- `RecordProperty("key", value)`：把可量化观测量（差异像素数、亮度、对比度、耗时、支持标志）写入 gtest 属性，供换机 / 换驱动对比；性能用例同时 `std::printf` / `std::cout` 输出中文标签。
- `GTEST_SKIP() << 原因`：能力不足的统一出口；skip 前允许已构造 `Renderer`，析构仍会 `shutdown`。
- `ADD_FAILURE() << ...`：仅 `渲染GPU驱动测试.cpp` 的“CPU 可见但 GPU 剔除”保守性检查使用。
- `SUCCEED()`：`渲染后处理反射测试.cpp` 的“未初始化设置无副作用”用例使用（无返回值可断言，只要求不崩溃）。

### 4.4 GPU 阻塞与同步方式

本模块**不创建任何信号量 / 栅栏 / 查询对象**，完全依赖 `Renderer::frame_render` 的同步语义：内部“等待在途帧 → 录制 → 提交 → 呈现”，回读变体还会在提交后把最终颜色附件拷贝到主机缓冲。因此：

- `frame_render(pixels, capacity, &w, &h)` 返回时，`pixels` 已可直接读取；用例不做额外等待。
- 多帧用例每帧都请求回读。`渲染Cluster测试.cpp` 的注释明确记录“连续无回读帧后再请求回读会得到整幅清屏色”，故所有对比帧均逐帧回读。
- `mesh_update_vertices` / `mesh_update_indices` / `render_target_readback*` 在门面内部等待在途帧（见 `渲染器.h` 注释），用例直接调用后断言，不额外同步。
- `frame_wait_idle()` 在本模块内**未被使用**；需要等待的场景都由上述同步接口覆盖。
- GPU 时间戳结果存在“同一帧槽下一次使用才读回”的滞后，用例通过渲染 `在途帧数 + 1` 帧以上（通常 4 帧）来保证样本可读。

## 六、模块设计 / 实现细节

### 6.1 渲染用例的设备与资源隔离

1. **一用例一设备**。所有用例在函数体内构造 `engine::Renderer`（栈对象），`ASSERT_TRUE(renderer.init(hidden_config()))`；`ASSERT_*` 失败即提前返回，析构仍执行 `shutdown`（门面析构内部调用 `shutdown`，见 `渲染器.h` 类注释）。因此单个用例失败不会污染下一个用例。
2. **A/B 对比一律两台设备**。需要“关特性 / 开特性”两帧时，用例写成两个独立作用域，各自 `init → 画 → 回读 → 卸载 → 析构`，例如 `渲染材质测试.cpp::同一网格不同材质像素可区分` 用同一台设备分两帧，而 `渲染材质贴图测试.cpp::材质无贴图逐字节不变` 用两台设备分别出帧；两种方式都避免“上一帧状态残留”。
3. **设备能力探测与跳过**。像素断言前统一检查 `readback_supported()`；无回读则 `GTEST_SKIP()`，因此“像素级断言”不会在无回读设备上误判。MSAA 用例检查 `msaa_samples() <= 1`；计算路径用例检查 `compute_supported()`；Hi-Z 用例检查 `hiz_supported()`；Cluster 用例检查 `cluster_supported()`；字体用例检查 `std::filesystem::exists(FONT_PATH)` 或直接 `font_load_file` 失败即跳过。
4. **能力不足的“零值分支”**。`渲染GPU耗时测试.cpp` 与 `渲染GPU驱动测试.cpp` 不跳过不支持时间戳的设备，而是走 `else` 分支断言 `gpu_frame_ms / gpu_total_ms / gpu_samples` 全 0；这保证“优雅降级”本身被测试覆盖。
5. **资源清理顺序**。统一为先 `post_chain_set(nullptr, 0)` / `render_target_present_set(0)` 解绑，再 `pipeline_unload` / `material_unload` / `mesh_unload` / `texture_unload` / `render_target_destroy` / `font_unload`。`渲染后处理链测试.cpp::后处理链上UI不被处理` 额外在 `ui_channel()->draw_callback_clear()` 后再卸载。
6. **初始化失败即用例失败**。除“非法配置被拒”类用例外，`init` 一律 `ASSERT_TRUE`；只有 `渲染初始化测试.cpp` 的非法配置用例 `EXPECT_FALSE(init(...))` 并断言 `valid()` 仍为假。
7. **重复 init / shutdown 幂等性**由 `渲染初始化测试.cpp::重复初始化幂等` 与 `隐藏窗口初始化与幂等关闭` 覆盖：已初始化再 `init` 返回真且不破坏状态；`shutdown` 连续两次不报错；关闭后仍可 `init`。
8. **多渲染器并行**。`渲染线程测试` / `渲染GPU驱动测试` / `渲染Cluster测试` 在同一用例内构造 2～3 台 `Renderer`（单线程 / 四线程、关 / 开 GPU 剔除、关 / 开间接绘制），输入矩阵逐字节一致（同一 `std::vector<std::array<float,16>>` 或固定种子 `mt19937`），从而把“结果差异”归因于被测特性本身。

### 6.2 像素级断言的容差与阈值体系

容差不是随手取的，而是按“差异来源”分层：

| 来源 | 取值 | 出现位置与理由 |
| --- | --- | --- |
| 两级后处理“编码→解码”取整累积 | `CHAIN_TOLERANCE = 4` | 两级链恒等（反色→反色、恒等 LUT、恒等调色）允许 4；一级链或直通对比通常要求 0～2。 |
| 纯黑 / 纯白端点判定 | `DARK_THRESHOLD = 4`、`SATURATION_THRESHOLD = 250` | 反色 / 阈值化 / LUT 的中心与角落判定。 |
| 清屏色候选 | 双编码 `{13,13,26}` / `{63,63,89}`，容差 6 | 兼容 UNORM 与 sRGB 附件；只用于“是否仍为背景”的判定与区域统计剔除。 |
| 并行 vs 单线程像素 | `PIXEL_TOLERANCE = 2` | 同一指令流下理论上逐字节相同，容差仅吸收驱动取整。 |
| 开关特性“画面必须不同” | 最大差 > 0 或差异像素 > 阈值 | 模糊参与、LOD 偏置、反射、颗粒、色差等结构性差异。 |
| 中间色 / 混合像素 | 中间亮度区间或“非清屏非白” | MSAA 斜边、SSAA 斜边、FXAA 过渡、覆盖率写入。 |
| 亮度方向断言 | `> 基准 + N` / `< 基准 − N` | 环境光、点光衰减、高光、泛光强度、曝光、伽马、景深。 |
| 比例断言 | 双级 > 单级、半径 4 × 2 ≤ 半径 1、MSAA 与 1× 差 ≤ 50% | 避免绝对数值依赖。 |
| 几何位置 | 质心行上移 > 4 行、允许 ±3 行误差 | 动态网格顶点平移。 |
| 正交 / 透视占比 | 透视远 < 近 × 0.8；正交差 ≤ 2% + 1 像素 | 正交投影用例。 |
| 色阶 / 灰度级计数 | 参考 ≥ 10 级、量化 ≤ 5 级且 ≤ 参考/3 | 像素化、色调分离。 |
| 图像统计 | 高频能量 > 参考 + 200、均值差 ≤ 10 | 胶片颗粒。 |
| 关卡像素覆盖 | 逐通道差 ≥ 6 计为变化；端到端覆盖 ≥ 800 像素 | 关卡装载与聚光阴影。 |
| 逐字节相等 | `EXPECT_EQ(pixelsA, pixelsB)` 或差异 0 | 1× 覆盖率、合批、单级链等价、开关矩阵、关卡等价路径。 |

容差实现的细节：

- `max_channel_diff` 逐字节取绝对值最大，不做通道序归一；`changed_pixels` 只比较前三通道且阈值 ≥ 6；`darkened_count` / `brightened_count` 用 Rec.709 亮度差阈值（常取 0.05 / 5.0 / 8.0）。
- 通道序无关的三种写法：绿通道恒下标 1；`outer_max = max(R,B)`；三通道 `std::sort` 后按“两低一高”判定。
- 端点容差常写成方向不等式而非近似相等，例如“角落 ≥ 200”“中心 ≤ 4”“高光 ≥ 245”。
- 对可能饱和的量（泛光叠加、清屏色）先构造“不会饱和的输入”：泛光用例用 222 灰纹理（线性 ≈0.72）而不是纯白；清漆用例用中性灰 100 反照率。

### 6.3 多线程用例的同步方式

1. **不使用外部线程**。`渲染多线程测试.cpp` / `渲染多线程阈值测试.cpp` 只通过配置 `render_threads` 改变门面内部线程池；用例本身单线程顺序执行 `mesh_draw_instanced → frame_render → frame_stats_get`。门面内部由工作线程并行做实例剔除、差异扫描、场景 / 阴影命令录制，最后在调用线程用 `vkCmdExecuteCommands` 汇总（见 `渲染器.h` 的类注释）。
2. **比较口径**。并行与单线程两侧使用**独立渲染器实例**，输入矩阵逐字节一致；断言 `culled_instances`、`drawn_instances`、`last_draw_items`、`last_instances` 逐值相等，像素最大通道差 ≤ 2。
3. **“确实并行”的证据**。不看耗时（易抖动），看计数：`parallel_dispatches > 0`、`parallel_segments > 0`、`cull_parallel_dispatches > 0`、`scan_parallel_dispatches > 0`、`cache_parallel_dispatches > 0`；单线程侧对应计数必须为 0。
4. **阈值语义**。实例剔除并行阈值默认 256（`cull_parallel_min_instances`），差异扫描 / 缓存回写阈值默认 512（`instance_scan_parallel_min`），并行录制阈值默认 32 项（`parallel_min_items`），段数上限默认 8（`parallel_max_segments`）。用例用 64 / 1000 / 1024 实例与 64 绘制项精确落在这几个阈值两侧。
5. **MSAA + 并行**。`渲染多线程测试.cpp::MSAA下并行录制与单线程一致` 用 4× + 深度描边链 + 64 项，验证“多重采样解析只在末段执行”：若中间段也解析，末段目标会被覆盖，像素会与单线程不一致。
6. **同步点**。唯一同步点是 `frame_render` 返回；用例不在提交后插入额外等待，因为门面在下一帧开始与资源更新前会等待在途帧。

### 6.4 耗时用例的统计口径

1. **GPU 时间戳能力分支**。`gpu_timestamp_supported()` 为真时断言 `gpu_frame_ms > 0` 且 `gpu_samples == 2`（4 帧、默认 `frame_overlap = 2`，即“帧数 − 在途帧数”）；为假时断言 `gpu_frame_ms / gpu_total_ms / gpu_samples` 全 0。
2. **分段耗时**。`gpu_scene_ms`、`gpu_post_ms`、`gpu_shadow_ms` 分别对应场景 / 后处理 / 阴影 pass；断言只做“非负、场景 ≤ 总耗时 + 0.01、场景 + 后处理 ≤ 总 + 0.01、直通路径后处理 ≤ 0.05、未开阴影时阴影 = 0”。
3. **累计口径**。`gpu_scene_total_ms` / `gpu_post_total_ms` / `gpu_shadow_total_ms` 与 `gpu_samples` / `gpu_shadow_samples` 同步累计；`frame_stats_reset()` 清零累计但保留“最近一帧即时量”（`gpu_scene_ms` 等），用例专门验证这点。
4. **性能基线不设绝对阈值**。`渲染GPU驱动测试.cpp::性能基线采集`（1080p + MSAA 4× + 1 万实例 / 6 帧）、`多批次合批基线采集`（100 批 × 100 实例）、`渲染HiZ测试.cpp::性能对照`（1080p + 4× + 1 万实例）、`渲染Cluster测试.cpp::构建性能对照`（2/4/8/64 条记录、CPU/GPU 各 5 次取最小）、`大光源整帧耗时对照`（1920×1080、5 帧平均）都只断言“跑通 + 计数自洽”，数值经 `printf` 输出并写入性能基线文档。
5. **主机侧耗时**。`host_record_ms` 是录制耗时，`cpu_cull_ms` 是主机侧实例剔除耗时；用例把它们累加后取平均，不做跨设备比较。
6. **关卡装载耗时**。`关卡规模装载开销` 用 `std::chrono::steady_clock` 对 100 / 400 / 1000 个对象各测 2 次取最短，断言 < 1000 ms（只防抖，不评价性能优劣）。

### 6.5 隐式约定与坑

1. **包含链里的 `min` / `max` 宏**。多个辅助头注释明确说明：本层包含链存在 min/max 宏，调用 `std::min` / `std::max` 会触发 C2589。故：
   - 辅助函数用三元表达式（`value[0] > value[2] ? value[0] : value[2]`）；
   - 需要函数对象时写 `(std::min)(a, b)` / `(std::max)(a, b)`（`渲染HiZ遮挡测试.cpp`、`渲染Cluster测试.cpp` 的耗时取最小值）。
   - `std::max_element` / `std::min_element` 未被宏污染，可正常使用（大量后处理断言用它）。
2. **`ASSERT_*` 不能出现在有返回值的 lambda 内**。多个文件在注释中记录这一点，改用 `EXPECT_*` + 返回像素；只有 `void` lambda（如 `render_with_bias`）才允许 `ASSERT_*`。
3. **无回读帧会丢失画面**。`渲染Cluster测试.cpp` 注释：连续“无回读帧”后再请求回读会得到整幅清屏色，故对比用例每帧都回读。类似地，后处理多帧用例每帧重新 `mesh_draw`（待绘制项逐帧清空）。
4. **中文路径**。`纹理解码测试.cpp` 用 `std::u8string` → `std::filesystem::path` 写文件，避免窄 `ofstream` 按系统代码页解释中文名；关卡用例反过来：写盘用宽字符 `path`，读 / 写 API 用 UTF-8 窄字符串（`level_utf8`）。
5. **清屏色编码不确定**。同一清屏色在 UNORM / sRGB 附件下回读值不同（13/13/26 vs 63/63/89），所有“背景判定”都准备双候选 + 容差，不假定附件传输函数。
6. **C++ 缩进混用**。`渲染后处理扩展预设测试.cpp`、`渲染MSAA测试.cpp`、`渲染材质测试.cpp` 局部用空格缩进而非 Tab；不影响语义，仅说明拆分 / 合并历史。
7. **注释与断言版本号漂移**。`渲染场景数据测试.cpp::场景UBO按需写入` 的块注释列举到“3824 字节”，断言用 3920；`渲染多线程阈值测试.cpp` 注释说“第 2 帧走并行”，代码实际渲染三帧并读第 3 帧统计。属注释滞后，见待确认第 2、3 条。
8. **场景 UBO / 实例缓冲按需写入**。用例依赖两个字节计数器：`scene_upload_bytes()` 首帧整块 3920 字节、之后静止帧 0、改光照后逐帧槽传播最终回 0；`instance_upload_bytes()` 单实例 112 字节（模型矩阵 16 + 材质 4 + 卡通 4 + 暗部色调 4 个浮点），模型矩阵变化才重传。阈值断言同时检查“不超过整块 / 本帧实例字节数”，防止实现退化为整块上传。
9. **Cluster 缓冲上传公式**。`cluster_gpu_bytes == 簇数 × 8 + 条目 × 4`：计数与偏移各 `簇数 × 4`，列表每条 4 字节。用例在 3456 / 512 / 4032 三档网格下验证重建。
10. **前向光源槽位与 Cluster 槽位语义不同**。前向路径上限 32 盏（`light_truncated` 置 1）；Cluster 开启后可登记到容量 1024，且第 33 盏不再被拒。`渲染光照测试.cpp` 用“前 31 盏零强度 + 第 32 盏强度 1”验证槽位；`渲染Cluster测试.cpp` 用“第 33 盏”验证路径差异。
11. **时间戳样本滞后**。GPU 时间戳在“同一帧槽下一次使用”时才读回；用例统一渲染 4 帧（默认在途 2）来获得 2 个样本。所有缩短帧数的写法都会得到 0 样本。
12. **能力探测顺序**。`readback_supported()` 必须在 `init` 之后调用；`渲染超采样测试.cpp` 的 `UninitializedGuard` 证明未初始化时查询返回保守值（倍率 1），因此“先查询后 init”的写法不可靠。
13. **隐藏窗口下全屏可能被拒**。`渲染窗口属性测试.cpp` 不断言进入全屏一定成功，只断言“成功则状态一致；退出必须成功”。这是对后端行为的显式容忍。
14. **字体用例的跳过粒度**。字体缺失时 `GTEST_SKIP()` 整个用例；`渲染MSAA测试.cpp::文字在MSAA下可绘制` 先判 MSAA 与回读，再判字体，顺序保证跳过原因准确。
15. **着色器名硬编码**。所有后处理用例直接写 `"后处理.vert.spv"`、`"反色.frag.spv"`、`"法线描边.frag.spv"` 等；测试工程依赖配置期从渲染层构建树拷贝 `shaders/`。着色器缺失时 `pipeline_load` 返回假，用例以 `ASSERT_NE(pass, 0u)` 失败。

### 6.6 错误处理策略

- 门面 API 失败 → `ASSERT_TRUE` / `ASSERT_NE(handle, 0u)`，直接终止用例；不继续用无效句柄。
- “非法参数应被拒” → `EXPECT_FALSE` + 断言句柄复位 0 + 后续画面逐字节不变。
- “未初始化调用” → `EXPECT_FALSE` / 查询返回 0 / 静默返回；不崩溃。
- “能力不支持” → `GTEST_SKIP()`（像素 / 功能用例）或零值分支断言（时间戳 / 剔除统计）。
- 文件读失败 → 关卡用例断言 `Level_Data.name` 为空、`Asset_Scene` 三个容器为空（整体回退，不残留半装配）。
- 资源泄漏不在用例内断言，由门面 `shutdown` 的幂等性与进程退出兜底。

## 七、模块运行链路详例

### 7.1 链路一：一个渲染用例从注册到执行到断言（含设备初始化）

以 `渲染材质测试.cpp` 的 `TEST_F(Renderer_Material_Test, 同一网格不同材质像素可区分)` 为例，端到端路径如下。

1. **编译期注册**。`TEST_F` 宏展开为 `gtest_TestInfo` 静态对象 + 注册函数，注册发生在静态初始化期；`.obj` 被链接进 `TestRenderer.lib`。
2. **链接期收编**。`TestRendererMain` 以 `$<LINK_LIBRARY:WHOLE_ARCHIVE,TestRenderer>` 链接，链接器不丢弃未被引用的 `.obj`，故所有 `TEST` / `TEST_F` 注册项保留。
3. **进程启动**。`entry/薄入口.cpp::main`：
   - `SetConsoleOutputCP(CP_UTF8)` / `SetConsoleCP(CP_UTF8)` 让中文用例名与诊断可读；
   - `testing::InitGoogleTest(&argc, argv)` 解析 `--gtest_filter` 等参数；
   - `byjy_test_anchor_renderer()` 强制引用注册锚（若库未被整体收编，这里链接失败，提前暴露配置错误）；
   - `RUN_ALL_TESTS()` 遍历注册表。
4. **用例选择与夹具构造**。gtest 按过滤器命中 `Renderer_Material_Test.同一网格不同材质像素可区分`，构造空夹具 `Renderer_Material_Test`（无成员、无 `SetUp`）。
5. **设备初始化**。用例体：
   - `engine::Renderer renderer;`（构造不建 GPU 资源）；
   - `ASSERT_TRUE(renderer.init(hidden_config()));` → 门面内部依次建 SDL 隐藏窗口（64×36、`hidden = true`）、Vulkan 实例 / 物理设备 / 逻辑设备与队列、交换链、默认场景管线、默认后处理管线、实例缓冲 / 场景 UBO 帧槽、描述符集与采样器；任一失败逆序回退并返回假；
   - `if (!renderer.readback_supported()) GTEST_SKIP() << "本机交换链图像不具备传输源用法";`。
6. **资源与状态**。
   - `mesh_load(mesh, quad_data())`：四边形 4 顶点 / 6 索引上传到设备缓冲，记局部包围盒；
   - `texture_load(red_texture, red_texels, 4, 4)` / 蓝纹理同理；
   - `material_load(red_material, red_data)` / 蓝材质：不透明档复用默认场景管线，记录纹理与混合档；
   - `material_bind_set(red_material)`：记录“当前材质”，下一次 `mesh_draw` 时把材质参数写入待绘制项。
7. **登记与出帧**。
   - `mesh_draw(mesh, full_screen_matrix().data())`：只登记一个待绘制项（模型矩阵 4 倍放大、颜色为空）；
   - `frame_render(red_pixels.data(), red_pixels.size())`：泵事件 → 取交换链图像 → 录制场景 pass（消费待绘制项）→ 提交 → 呈现 → 因请求回读，把最终颜色附件拷贝到 `red_pixels`；待绘制项本帧清空。
8. **像素判定**。
   - `pixel_get(red_pixels, 32, 18)` 取中心 RGBA；
   - `EXPECT_LT(red_center[1], 60)`：绿通道低 → 不是默认白纹理；
   - `EXPECT_TRUE(outer_saturated(red_center))`：R 与 B 恰有一个 ≥ 200 → 单一外色；
   - 蓝帧重复 6～8；
   - `EXPECT_NE(red_center[0], blue_center[0])`、`EXPECT_NE(red_pixels, blue_pixels)` → 不同材质可区分。
9. **清理与销毁**。`material_unload` ×2 → `mesh_unload` → `texture_unload` ×2；`renderer` 离开作用域，析构调用 `shutdown()`（等待在途帧、销毁交换链 / 管线 / 缓冲 / 设备 / 窗口），幂等。
10. **结果汇聚**。gtest 记录该用例通过 / 失败与 `RecordProperty`；`RUN_ALL_TESTS()` 汇总返回码即进程退出码。

同一路径中“跳过”分支：第 5 步若 `readback_supported()` 为假，`GTEST_SKIP()` 直接标记 skipped 并返回，第 6～9 步不执行，但 `renderer` 析构仍执行。

### 7.2 链路二：一条像素回读比对路径

以 `渲染后处理链测试.cpp::两级反色恒等于原画面` 为例（同类路径覆盖恒等 LUT、恒等调色、法线描边强度 0、反射强度 0、接触阴影关闭、景深近零模糊等）。

1. **参考帧（不设链）**。
   - 独立作用域建 `Renderer`；`init(hidden_config())`；`readback_supported()` 检查；
   - `scene_register(renderer, handle)`：`texture_bind_set(0)`（默认白纹理）→ `mesh_load(quad_data())` → `mesh_draw(handle, nullptr)`；
   - `frame_render(reference.data(), size)`：直通路径（无链、无呈现目标）把场景直接写入交换链并回读；
   - `mesh_unload(handle)`。
2. **对照帧（两级链）**。
   - 新作用域建第二台 `Renderer`；`init`；
   - `render_target_create(scene_target, extent_width(), extent_height())` 与 `render_target_create(second_target, ...)`：两张与交换链同尺寸的颜色目标，供两级 ping-pong；
   - `post_pipeline_register(renderer, "反色.frag.spv")` 两次：`pipeline_load(handle, "后处理.vert.spv", "反色.frag.spv")`，得到两个独立句柄（`ASSERT_NE(stages[0], stages[1])`）；
   - `post_chain_set(stages, 2)`：登记级序；
   - `scene_register(renderer, handle)`：同一白纹理四边形场景；
   - `render_target_present_set(scene_target)`：指定第 0 级取源目标；
   - `render_target_present_chain_set(chain_targets, 2)`：指定两级的目标组 `{scene_target, second_target}`；
   - `frame_render(chained.data(), size)`：场景写入 `scene_target` → 第 0 级反色写 `second_target` → 第 1 级反色写交换链 → 回读。
3. **比对**。
   - `max_channel_diff(reference, chained)` 逐字节最大差；
   - `EXPECT_LE(difference, CHAIN_TOLERANCE)`（4）：两级各经历一次“附件编码 → 采样解码”的取整，累积容差 4；若只执行一级，中心与角落通道差会达 200 以上，故 4 仍具决定性。
4. **失败诊断**。断言文本里带 `最大通道差 N`；像素级用例还会用 `pixel_text` 打印中心 / 角落 RGBA。
5. **清理**。`pipeline_unload` ×2 → `render_target_destroy` ×2；两台 `Renderer` 各自析构。

该路径的关键点：**回读发生在 `frame_render` 内部**，测试不需要 `vkQueueWaitIdle` / fence；两张目标的尺寸不必等于交换链（`目标尺寸不一致仍走后处理` 用例显式验证窄 8 像素仍走链，`半尺寸目标链可用` 验证半尺寸升降采样）。

### 7.3 链路三：能力分支与跳过路径

以 `渲染MSAA测试.cpp::斜边像素平滑` 为例：

1. `init(hidden_config(4))`：请求 4×，门面按设备能力钳制（可能只支持 2×）。
2. `if (renderer.msaa_samples() <= 1) GTEST_SKIP() << "当前设备不支持 MSAA（颜色 / 深度格式至少需支持 2×）";`。
3. `mesh_plane_load(plane, 1.0f, 1.0f)` + `diamond_transform`（2× 缩放 + 45°）→ `mesh_draw` → `frame_render` 回读。
4. `blended_pixel_count()`：先取全图亮度极值（暗 = 清屏色、亮 = 平面内部），再统计落在 `(暗 + 20, 亮 - 20)` 的像素，排除内部纯色与纯暗 / 纯亮。
5. `msaa_samples_set(1)` 后再画一帧，比较：开启侧中间色 > 0 且 > 关闭侧。
6. 清理 `mesh_unload`。

这条链路说明：**跳过只发生在“设备能力不足”**，不发生在“断言不满足”；断言不满足仍按失败处理。

### 7.4 链路四：关卡装载到像素覆盖

以 `渲染关卡测试.cpp::关卡装载端到端` 为例：

1. 写资产：`write_box_assets()` 在 `out/关卡测试/` 写 `box.obj`（4 顶点 + UV + 法线 + 2 三角形）与 `box.mtl`（`newmtl 甲` + `Kd 0.8 0.2 0.2` + `Ns 64`）。
2. 写关卡文本 `端到端.level`：`level` / `camera position 0 0 3` / `camera target 0 0 0` / `light direction 0 0 -1` / `light color 1 1 1` / `light intensity 1` / `mesh 方盒 box.obj` / `mtl 方盒材质 box.mtl` / `place 方盒 方盒材质 0 0 0 1 1 1`。
3. `Renderer::init(128×72, hidden)`；`readback_supported()` 检查。
4. 先出空场景基线帧 `reference`。
5. `level_bridge_load(renderer, 关卡, 场景, level_utf8("端到端.level"))`：
   - 系统层 `level_text_read` 解析文本为 `Level_Data`；
   - 校验相机（fov / near / far / 正交高度等有限且合法）；
   - 按资产段落 `mesh` / `mtl` / `place` 创建网格、材质、对象（失败整体回退并清空 `场景`）；
   - `apply_scene = true` 时 `scene_apply(关卡.camera, 关卡.light, 关卡.fog)`。
6. 断言：`关卡.name == "端到端关卡"`、`asset_lines.size() == 3`、`场景.meshes/materials/objects == 1`、`objects[0].materials.size() == 1`。
7. `level_bridge_draw(renderer, 场景)`：逐对象 `level_transform_build`（位置 / 旋转 / 缩放 → 列主序矩阵）→ `mesh_draw_sections(mesh, matrix, materials, count)`；返回成功登记对象数 1。
8. `frame_render(shown, size)`；`changed_pixels(reference, shown)` 统计逐通道差 ≥ 6 的像素，断言 ≥ 800。
9. `level_text_write(关卡, "端到端_保存.level")` → `level_text_read` 再读，名称与资产行数量一致。
10. `level_bridge_unload(renderer, 场景)`：释放网格 / 材质 / 对象，断言容器清空；`Renderer` 析构。

该链路把“系统层文本 → 渲染层资源 → 画面”三段串起来，是关卡用例的核心验收路径；`关卡与手工构造画面一致` 则用同一关卡与手工 `scene_apply + scene_bundle_load + mesh_draw_sections` 两条路径做逐字节对照。
