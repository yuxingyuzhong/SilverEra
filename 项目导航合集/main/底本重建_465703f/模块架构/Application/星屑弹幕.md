## 二、模块功能介绍

本模块是 `Application/Game` 下的示例游戏“星屑弹幕”：一个可独立运行的割草弹幕游戏。它同时承担两个角色：其一，作为完整玩法闭环（输入 → 逻辑帧 → 空间索引 → 事件 → 界面 → 渲染）；其二，作为白银纪元引擎三层的集成样例——把引擎的事件系统、对象池、四叉树、随机数、配置加载器与渲染核心组合到真实负载下，并用无头压测给出可复现的性能口径。

**分层职责。** `foundation` 只提供不含业务规则的约定：值类型、固定常量、界面文案、可调设置、视口与相机；`communication` 负责“跨模块的间接通信”与“跨进程的持久化”：事件总线（引擎 `Event_Terminal` + `Event_Broker` 接线的本地封装）与设置/生涯记录的文件读写；`entity` 只定义实体与局内数据结构，并用引擎 `Object_Pool` 承载敌人、投射物、掉落物；`system` 集中全部每帧规则，其中 `帧推进` 是“一个逻辑帧”的唯一实现；`presentation` 只读实体与统计并绘制三维场景、HUD 与浮层；`world` 持有四叉树并维护逐帧空间索引；`app` 负责装配、主循环、输入与阶段切换。依赖方向单一：`app → system → world/entity → foundation`，`presentation → foundation/entity/communication`（仅通过 `Event_Node` 订阅），`communication → foundation`。

**对外职责边界。** 本模块只使用引擎公开接口：`engine::Event` / `Event_Broker` / `Event_Terminal`、`engine::Object` / `Object_Pool`、`engine::Quadtree` / `Quadtree_Manager` / `Tree_Chunk_Data`、`engine::Random_Generator<int64_t>`、`engine::Engine_Env`、`engine::Config_Loader`、`engine::Mesh_Data` / `Mesh_Handle` / `Material_Handle`、`engine::Renderer` 与 `Ui_Channel_Context`。它不实现渲染后端、空间结构、对象池、随机数算法或第三方库封装；这些属于 `EngineFoundation` / `EngineSystem` / `EngineRenderer`。

**不负责的部分。** 不负责 Vulkan / SDL3 资源生命周期（由 `engine::Renderer` 内部管理，本作只持句柄并在 `render_ctx` 缓存）；不负责配置文件格式的通用解析（优先交给引擎 `Config_Loader`，失败才退为 `nlohmann::json` 直读）；不负责第三方库的编译与链接（`external/silver_era` 与 `external/Dear_ImGui` 提供冻结副本，`CMakeLists.txt` 按相对路径导入）。

**三种运行形态共享同一帧序。** 窗口模式（无参数）走真实输入与可变 `dt`；`--self-test` 不建窗口、不建渲染器，逐项构造系统跑确定性用例；`--soak <秒>` 以固定 `dt = 1/60` 推进与窗口完全相同的 `advance_play_frame`，走位由脚本椭圆巡航提供。这样压测数据才代表真实运行路径。

**关键约束。** 单线程（主循环、事件分发、渲染登记都在同一线程；渲染器内部以 2 帧重叠 + 关闭时 `frame_wait_idle` 兜底）；不依赖异常（内存分配用 `new(std::nothrow)` 语义、事件构造一律判空、JSON 解析与事件回调以 `try/catch` 吞没畸形输入）；源码与标识符均为 UTF-8（CMake 传 `/utf-8`）；对象池**绝不调用 `clear()`**（会把 ID 分配器重置到 0，与“0 = 非法 ID”哨兵冲突）；空间索引逐帧重建且不做全局清空；渲染层只读实体，不反向修改任何玩法状态；世界坐标约定为“游戏 (x, y) 映射到 3D (x, 0, y)，地面 y=0，3D 的 y 为高度”。

**存在理由。** 常量表把“同屏峰值投射物 ≥ 400、峰值敌人 ≥ 150”作为调参目标（注释见 `常量表.h` 文件头）。该目标使对象池与四叉树成为必需品：若同屏只有数十实体，全量两两判定在 60 帧下几乎零成本，空间分区与对象池就没有存在意义。因此本模块同时是引擎能力的“压力样本”。

### 3.1 值类型与工具（`foundation/公共类型.h`，命名空间 `Stardust_Barrage`）

```cpp
struct Vector2 { float x = 0.0f; float y = 0.0f; };
struct Vector3 { float x = 0.0f; float y = 0.0f; float z = 0.0f; };
struct Color   { unsigned char r = 0; unsigned char g = 0; unsigned char b = 0; unsigned char a = 255; };
inline void  color_to_rgba(const Color& color, float out[4]);   // 各通道 /255 归一化写入 out
inline Color color_fade(const Color& base, float t);            // t 先夹到 [0,1]，四通道同乘
using coord_int       = engine::Point2i;
using coord_range     = engine::Rect2i;
using coord_l         = engine::Point2l;
using coord_range_l   = engine::Rect2l;
struct vec2 {
    float x = 0.0f; float y = 0.0f;
    vec2 operator+(const vec2& other) const;
    vec2 operator-(const vec2& other) const;
    vec2 operator*(float scale) const;
    vec2& operator+=(const vec2& other);
    float length_sq(void) const;    // 免开方，比较用
    float length(void) const;
};
inline vec2     vec_normalize(const vec2& v);     // 长度 <= 1e-6 时返回 (0,0)
inline coord_int vec_to_coord(const vec2& v);     // 经 engine::point_to_int（四舍五入）
inline coord_l   vec_to_coord_l(const vec2& v);   // 经 engine::point_to_l
struct chunk_entities { uint32_t stamp = 0; vector<uint32_t> enemies; vector<uint32_t> projectiles; };
enum class bullet_owner { player, enemy };
enum class enemy_kind   { normal, elite, boss, ranged, bomber };
enum class elite_affix  { none, swift, shield, rage };
enum class drop_kind    { small, medium, large };
enum class game_state   { menu, playing, over };
```

语义与约束：
- `chunk_entities::stamp` 是帧戳。写入时“帧戳不符则先 `clear()` 再写”，读取时“只认本帧帧戳”，因此无需全局清空即可逐帧重建索引（见 §六.5）。
- `vec2` 不提供除法与归一化运算符，归一化必须走 `vec_normalize`；零向量返回零向量而非 NaN。
- `公共类型.h` 在引擎预编译头之后 `#undef small`：Windows SDK `rpcndr.h` 把 `small` 定义为宏，会与 `drop_kind::small` 冲突。

### 3.7 事件总线（`communication/事件总线.h`，命名空间 `Stardust_Barrage`）

**3.7.1 `Event_Node`——一个模块与事件总线的完整接线单元**

```cpp
Event_Node(engine::Event_Broker& broker, const string& module_name,
           const vector<engine::Event>& needed_events,
           const function<void(shared_ptr<engine::Event>)>& handler);
Event_Node(const Event_Node&) = delete;
Event_Node& operator=(const Event_Node&) = delete;
shared_ptr<engine::Event> build_event(const string& category, const string& tag);
bool send(shared_ptr<engine::Event> evt);
const string& name(void) const;
```

语义与前置条件：
- 构造内部严格按序：`<1>` 绑 `Port_ID::Broker_Attacher`（转发到 `broker.attach`）→ `<2>` 绑 `Port_ID::Evt_Sender`（转发到 `broker.receive`）→ `<3>` 若 `handler` 非空则绑 `Port_ID::Evt_Receiver` → `<4>` `terminal.key()` 取密钥（失败时 `acl_key=0`）→ `<5>` `terminal.attach(module_name, acl_key)` → `<6>` 若非空订阅清单则构造 `("Subscribed_Events","Add")` 事件，填 `object/acl_key/subscribed_events` 后直接 `broker.process(subscribe)`（不经 `receive` 分发）。
- `build_event` 以本节点模块名为发送者、target 留空（广播）：`terminal.build(module_name, string(), category, tag)`。中转站据此排除发起者自身。
- `send` 经终端发送通道 `terminal.send(evt, acl_key)`；`evt` 为空或密钥无效时返回 `false`。
- 前置条件：`needed_events` 中的 `engine::Event` 由 `("", "", category, tag)` 构造（仅用其 category/tag 字段）；`handler` 可为 `nullptr`（纯发送方）。
- 约定：订阅者类中的 `Event_Node` 必须是**最后声明的成员**，因为其构造会捕获 `this` 并登记回调；若先于其余成员构造，回调一旦立即触发就会读到未初始化字段。

语义与失败行为：
- `spawn_*` 返回对象池分配的编号；内部 `build()` 后立刻按编号重新查找槽位（扩容会使引用失效）。查找失败返回 `0`。
- `unload_*` 对 `id == 0` 与不存在编号安全忽略（不向引擎打出“对象不存在”告警）；卸载首领前先读 `kind` 递减 `boss_alive_num`。
- `enemy_at/projectile_at/drop_at` 先 `find(id)` 再判 `valid()`；已卸载槽位返回 `nullptr`。
- `enemies()/projectiles()/drops()` 返回池的完整区间（含无效槽位），调用方必须逐项 `valid()`。
- `advance` 的副作用包括：位移、玩家 `invuln/fire_timer` 衰减、精英环形弹幕生成、射手瞄准弹生成、投射物超时/越界回收、掉落物吸附与寿命回收；它不做升级、不做命中判定。
- `nearest_enemy` 是线性扫描（距离平方比较），命中时写出单位方向并返回 `true`。

### 5.4 子文件分工与线程归属

- foundation 的五个头各自单一职责，`.cpp` 只承载“需要运行时状态”的两处（设置唯一实例、视口静态状态）。
- communication 的 `.cpp` 中的静态量（`received/dirty/node_holder/loader_holder/current record`）都是进程级单例，不做线程安全。
- entity 的 `Entity_Store` 是“容器所有者 + 计数缓存”；计数（`enemy_alive_num` 等）与 `Object_Pool` 内部状态可能不一致的唯一途径是绕过接口直接操作池，代码未提供该入口。
- system 的六个类各自持有 `Event_Node`，不持有其他系统的引用；跨系统协作只通过“参数传入 `Entity_Store` / `World`”和“事件”两种方式。
- presentation 的 `render_ctx` 是“引擎渲染句柄的会话级缓存”，`Renderer` 是“每帧绘制总装”，`Effects` / `Terrain` 是“持有表现层活动列表的两块状态”，`Screen` / 两个面板是“界面状态机与浮层”。
- 线程：全部单线程。渲染器内部有 2 帧重叠与关闭时的 `frame_wait_idle`，但本模块不创建线程，也不做锁。

## 六、模块设计 / 实现细节

### 6.1 固定常量与可调设置的两分

`foundation/常量表.h` 只保留“不随设置变化”的固定值（设计分辨率、地图尺寸、四叉树参数、字体基准字号、各类玩法基准与呈现高度）；可在设置界面调整的项（刷怪速率、难度增长、精英概率、敌人上限、玩家速度/生命、射击间隔/单发伤害、瞄准模式、屏幕震动、拖尾、命中粒子、帧率显示/上限、地形细节、伤害数字、小地图、建模精度、全屏、分辨率、视野缩放、经验倍率、升级经验系数、拾取半径倍率、首领间隔）统一放在 `foundation/设置数据.h` 的运行时结构里。

为什么必须两分：`inline constexpr` 编译期固化，运行时改不了；而设置界面要求“改动下一帧即生效”。因此凡是“每帧现取 `config::get()`”的字段都能即时生效——本模块的系统确实全部按帧读取，没有任何系统缓存设置副本（`Wave_System::spawn_rate`、`Weapon_System::update`、`Progression_System::absorb/xp_need_for`、`Effects::burst/trigger_shake`、`Renderer::draw_enemies`、`Terrain::draw` 均如此）。唯一例外是 `view::refresh` 用 `static last_view_zoom` 做变化检测，但仍在变化时重算。

### 6.2 配置链路：assets/config 路由如何驱动玩法数值

装载链路（`communication/配置装载.cpp`）：
1. `config::load(broker)` 先把本模块以固定名 `"Stardust_Barrage_Settings"` 注册进中转站：构造 `Event_Node`，订阅 `(Config, Load)`，回调 `on_config_event`。此时本模块名已写入中转站在册表。
2. 再构造 `engine::Config_Loader` 并**长期持有**（`loader_holder` 是 `unique_ptr` 静态量）：中转站里保存着指向其终端的回调，若构造后立即析构会造成悬空指针。
3. 把加载器终端的三路接口接到同一台中转站：`Broker_Attacher → broker.attach`、`Evt_Sender → broker.receive`、`Evts_Sender → broker.receive(events)`（引擎投递配置走“多事件”通道）。
4. `loader_holder->attach()` 完成订阅登记。
5. 本模块发 `Believed_Root / Load` 事件，载荷 `route = "assets/config/route"`、`config = "assets/config"`。引擎扫描可信根下的路由文件，按脏标记把配置本体包装成 `category="Config" / tag="Load" / receiver=<本模块名>` 的定向事件；由于本模块已在册，事件直送 `on_config_event`。
6. 回调内 `parse(evt->config)` → `config::replace(loaded)` → `received = true`。

路由文件实际内容（`Application/Game/星屑弹幕/assets/config/route/设置路由.json`）：`{"config_routes":[{"object":"Stardust_Barrage_Settings","config_path":"assets/config/设置.json"}]}`。`object` 必须与 `settings_module` 完全一致，`config_path` 必须落在可信根 `assets/config` 之下。

退路：若引擎未把配置送达（`received == false`），`load_direct()` 直接用 `ifstream` 读 `Engine_Env::absolute_path_get("assets/config/设置.json")`，`try/catch` 解析后 `replace`；文件缺失或解析失败只打印日志并保留默认值。装载失败只退化为“不经过引擎”，不会让游戏失去设置能力。

写回：`Settings_Panel::draw` 每帧取 `config::get()` 副本 `draft`，控件改写后与 `before` 比对（`same_settings` 逐字段相等），有差异才 `config::replace(draft)` + `config::mark_dirty()`；`mark_dirty` 置脏并清零累计；`config::tick(dt)` 每帧累加，满 `write_delay = 0.4s` 才 `write_file` 一次，故连续拖动滑条只产生一次落盘；写失败保持脏标记、下一周期重试。退出前 `config::flush()` 强制落盘。

玩法数值如何被驱动（示例）：`Wave_System::spawn_rate()` 用 `difficulty.spawn_rate_base × (1 + spawn_rate_growth × 完整周期数)` 并夹到 `spawn_rate_cap`；`spawn_one` 用 `difficulty.elite_chance` 掷精英；`update` 用 `difficulty.enemy_cap` 做投放闸门；`Weapon_System` 用 `combat.weapon_cooldown/weapon_damage/aim_mode`；`帧推进` 用 `combat.player_speed`；`Progression_System` 用 `progression.xp_gain_mul/xp_need_scale/pickup_radius_mul`；`Wave_System::boss_wave` 用 `progression.boss_wave_interval`；`视口` 用 `window.view_zoom`；`渲染上下文` 用 `render.fps_limit`；`Renderer/Effects/Terrain` 用 `render.*` 开关。因此配置文件与设置界面改的是同一份 `config::settings`，没有任何“第二套数值源”。

### 6.3 事件总线的解耦方式

分工：战斗/武器/波次/Boss/成长五个系统只“发事件”；`Score_Board`（计分与连击）、`Combat_Stats`（统计）、`Hud_Notice`（提示）、`Effects`（表现）只“订阅”。发送方与订阅方互不持有指针，系统也不需要知道谁在消费。

接线顺序是硬约束（`事件总线.cpp` 文件头）：`attach_handler` 必须最先（`Event_Terminal::attach` 的真正落点）；`event_sender` 次之；`event_receiver` 必须先于 `attach`（否则中转站保存的是“入队”包装，之后注册的实时回调不会自动更新）；`acl_key_gen` 再后（未生成则终端全程锁定并告警）；`attach` 最后。订阅清单通过 `Subscribed_Events/Add` 事件直接 `broker.process`（不经 `receive`，否则会因“排除发起者”而丢给自己）。

定向投递：`Event_Node::build_event` 把 `sender_object` 填为模块名、target 留空；`Event_Broker::receive` 会按 `sender_object` 排除发起者本人，故发送方不会收到自己的事件。`category` 或 `tag` 为空的事件会被直接丢弃。

事件语义约定：
- `Combat/Hit`：`target/target_kind/damage/crit/pos_x/pos_y/dir_x/dir_y`，`dir` 是弹体入射方向（供特效扇形与伤害数字）。
- `Combat/Death`：`target/target_kind/score/pos_x/pos_y`；`target_kind` 为 `normal/elite/boss/ranged/bomber` 字符串，订阅者按它分支。
- `Combat/Wave`：`wave/rate`；只在“难度档位变化”时发一次，不是整波齐射信号。
- `Combat/Hurt`：`hp/max_hp`。
- `Combat/Fire`：`pos_x/pos_y/aim_x/aim_y`；表现层据此生成枪口迸发，与弹丸出生严格同帧。
- `Combat/BossSpawn`：`hp/max_hp/pos_x/pos_y`；`Combat/BossPhase`：`phase/hp_ratio/pos_x/pos_y`（阶段号 0 起，统计侧存 `phase+1`）。
- `Progression/LevelUp`：`level/level_up_total`；`Progression/Pickup`：`xp/total/pos_x/pos_y`。

`Score_Board` 的连击口径（`on_event`）：每次 `Death` 先 `combo_num++`、刷新 `combo_timer = combo_window`、更新 `combo_best`；计入加成的层数取 `combo_num - 1` 并夹到 `combo_bonus_cap`，倍率 `1 + stack × combo_bonus_per`；首杀倍率恰为 1.0，不改变单杀得分口径。小兵 / 精英 / 首领计数按 `target_kind` 分支，缺失字段按 `"normal"`。

`Hud_Notice::push` 去重：同文案已存在时只刷新计时（避免受击 / 波次在短时间刷屏）；新提示插入最前，超过 `notice_cap = 6` 丢弃最旧。

### 6.4 渲染上下文与引擎渲染层的边界

`render_ctx` 是本工程唯一持有 `engine::Renderer` 与 Dear ImGui 上下文的位置。边界如下：
- **只有本文件出现 Vulkan / SDL3 类型**（`#include <SDL3/SDL.h>`、`渲染器_UI通道.h`、`imgui_impl_sdl3.h`、`imgui_impl_vulkan.h`）；`渲染上下文.h` 只暴露 `engine::Renderer*`、`Mesh_Handle`、`Material_Handle` 与设计单位图形接口，`Color` 用本作值类型。
- **窗口与交换链归渲染层**：`Ui_Channel_Context` 提供 SDL 窗口、Vulkan 实例/设备/队列/图像数等；ImGui 平台后端直接绑定该窗口，Vulkan 后端用通道信息初始化。本作不创建窗口。
- **帧推进归渲染上下文**：`frame()` 计时（`dt` 钳到 0.1）→ `g_renderer.frame_render()`（事件泵 → 取图 → 录制 → 提交 → 呈现）→ 记录 `frame_ms` → 按 `render.fps_limit` 补睡眠。UI 绘制由渲染层在场景 pass 之后、呈现转换之前回调 `on_ui_draw`，`g_ui_draw()` 即 `ui_frame`。
- **输入归渲染层事件泵**：`on_event` 先喂 ImGui 平台后端，再维护本作键鼠状态；`key_pressed/mouse_pressed` 是“本帧按下”沿，消费后由 `input_edges_clear` 清空；窗口事件未在本文件处理的类型直接忽略。
- **资源句柄归本作缓存**：网格与材质以惰性加载 + 键缓存；`material_get` 的颜色量化与自动卡通默认化都在本层完成，`engine::Material_Data` 不越出本文件。
- **场景数据整包回灌**：`g_camera/g_light/g_fog` 是静态副本，`point_light_update` 改一个点光源位置后调用 `scene_apply` 整包写回。这带来一个隐式约定：`scene_apply` 会连同相机一起写回，因此“设置相机”必须放在所有可能触发点光源更新的绘制之后（`Renderer::draw_play` 末尾统一设相机，见 §6.5）。
- **后处理链归本作配置**：初始化创建 2 个离屏目标、加载 4 级管线（亮度阈值 → 泛光叠加 → 色调映射 → 暗角），再 `render_target_present_chain_set` + `post_chain_set`；关闭时先清链再逐个卸载。
- 失败处理：`init` 每步失败都自行回滚（销毁 ImGui 上下文 / `g_renderer.shutdown()`），返回 `false`；`main` 打印启动失败并返回 1。

### 6.5 渲染器的组织：总装 + 分桶实例化

`Renderer::draw_play` 的固定顺序：`effects.draw_background()` → `terrain.draw()` → `draw_contact_shadows()` → `draw_drops()` → `draw_projectiles()` → `effects.draw_glow()` → `draw_enemies()` → `draw_player()` → `effects.draw_world()` → 最后下发相机位姿。

- **分桶实例化**：敌人按“部件 × 常色/闪白”成对收集变换矩阵（`batch_pair = array<vector<float>,2>`），帧末统一 `draw_instanced`；投射物按归属两桶；掉落物按三档本体 + 三档光斑；贴地暗盘按三档透明度；粒子按“颜色 RGB + 透明度 6 桶”编码成 `uint32_t` 键分桶。这样把“逐实体逐部件散绘”压成常数级绘制调用。
- **视野剔除**：敌人 / 投射物 / 掉落物 / 暗盘 / 植被 / 碎石都用 `view::focus()` 与 `visible_half_*` 加余量做矩形剔除；地图 20480×11520，不剔除会导致每帧提交全图实体。
- **单实体叠绘**：玩家与首领保留逐层叠绘（玩家：地面光晕/环 → 瞄准标识 → 主体/内核 → 四翼片 → 瞄准尾迹 → 顶部核心；首领：地面光晕 → 三层熔核 → 晶棱 → 三层光环 → 双角 → 四门浮游炮）。它们只有 1 个实例，不值得分桶。
- **细节档**：`render.model_detail` 只控制“是否画环带（≥1）”与“是否画触角（≥2）”，以及精英核心环带；不改变网格分段（见 §附 待确认 5）。
- **相机下发**：`draw_play` 末尾按 `focus + shake` 重设 `camera_position_set/camera_target_set`。原因写在代码注释中：`point_light_update` 的整包回灌会用启动时相机覆写，若先设相机会被覆写成原点视角（表现为“玩家能跑、镜头不动”）。
- **HUD 走 ImGui 背景列表**：`render_ctx::ui_*` 全部写入 `ImGui::GetBackgroundDrawList()`，位于三维画面之上、ImGui 窗口之下；设计单位统一乘 `scale()`；字号按像素阈值选小/大字图集（42px 分界）。
- `draw_hud` 顺序：边缘告警 → 信息/状态/首领血条/小地图 → 滚动提示 → 伤害数字 → 红闪/升级光环 → 帧率（可选）。

### 6.6 特效与粒子的使用方式

- **事件驱动**：`Effects` 订阅 8 类事件（Hit/Death/Hurt/Fire/BossSpawn/BossPhase/LevelUp/Pickup），在回调中生成粒子、冲击闪光、冲击环、枪口迸发、伤害数字，或置红闪/升级光环计时与震动强度。它不调用逻辑层，不修改实体。
- **回调吞异常**：`Effects` 的 `handler` 用 `try/catch(...){}` 包裹 `on_event`。原因写明：回调穿越引擎分发层，载荷类型不符抛异常会直接终止进程（无日志闪退），畸形事件按忽略处理。
- **容量硬上限**：粒子 900、冲击环 64、枪口 32、冲击闪光 64、伤害数字 96；超限丢弃新请求，保证表现层不拖垮逻辑帧。
- **开关逐帧取**：`render.hit_particle` 关闭时 `burst/burst_dir/spawn_impact/spawn_ring` 直接返回（不生成也不绘制）；`render.bullet_trail` 只削减拖尾三段（光晕仍保留）；`render.screen_shake` 关闭时 `shake_offset` 返回零且 `trigger_shake` 不生效；`render.damage_number` 同时控制生成与绘制。枪口迸发无独立开关（出膛反馈不可关）。
- **推进与衰减**：粒子 `life -= dt`、位移、速度乘 `(1 - 2.6·dt)`；环/枪口/冲击/数字只倒计时；红闪 0.32s、升级光环 0.55s；震动强度按 `strength -= (strength·6 + 6)·dt` 衰减，位移由两路不同频率正弦（62 / 47）交错，避免规则往复；`trigger_shake` 取较强的一次、不叠加。
- **绘制分层**：背景（网格 + 星空，星空按亮度三档实例化并随 `clock` 闪烁）→ 泛光（投射物光晕四批 + 拖尾六批，加性、不写深度）→ 世界特效（冲击环贴地、枪口锥+亮核、冲击闪光锥+亮核、粒子按透明桶）→ 伤害数字（投影到屏幕后换算设计单位，先阴影后主字）→ 红闪/升级光环（四边带状渐变）。
- 粒子不使用任何图像资源，全部为程序化网格 + 加性材质；`Star` 位置在构造时一次性铺满全图（2600 个），每帧只按可视区过滤。

### 6.7 地形的一次性生成与每帧剔除

`Terrain` 构造即 `regenerate()`（每局开局也会由 `Renderer::reset` 再次调用），生成河道采样、色斑、草丛/花朵、碎石；河道三相位（主/次/宽度）每局重随机，主/次相位做最多 32 次拒绝采样，要求 `|river_center(0)| <= river_birth_offset_limit(260)`，保证出生点附近有河。

- 地表分层高度固定为 `-0.60 / -0.45 / -0.30 / -0.15 / +0.06(水光)`，互不共面，避免深度测试抖动（共面会闪烁）。
- 河道条带在 `rebuild_meshes` 中合并为三张静态网格（浅滩 / 河面 / 水光），`mesh_dirty` 首次绘制时才建（此时渲染器已就绪）；`regenerate` 只置脏并释放旧网格（下次绘制重建）。
- 草皮色斑按明暗两档实例化；植被按“草 3 档 + 花 3 档 + 花心 1 批”共 7 批；碎石按位置哈希分三档（同一颗每帧落同一桶，避免闪烁）。
- 细节层受 `render.terrain_detail` 控制：关闭后只画草地与河道，不画草丛/花朵/碎石；草地与河道始终存在，保证地表仍成立。
- 植被与碎石只用 `visible_half_* + terrain_cull_margin(140)` 剔除；色斑与底色不剔除（各是一次整图绘制）。

### 6.8 帧推进：不是固定步长累加器

`advance_play_frame` 接收调用方给的 `dt`，仅做上限钳制（`dt > frame_step_max(0.1)` 则取 0.1），**没有**固定步长累加器、没有子步拆分。因此：
- 窗口模式的逻辑帧率跟随渲染帧率（受 vsync 与 `fps_limit`），`dt` 可变；
- 卡顿（切窗口、断点）时单帧最多推进 0.1s，避免实体瞬移穿过目标；
- 无头压测用固定 `dt = 1/60` 调用同一函数，所以压测不受真实帧率影响，但也**不完全等价**于窗口模式的变步长路径。

十步顺序及其理由（`帧推进.h` 注释与实现逐字对应）：
1. 玩家移动 → 地图边界钳制（按玩家半径内缩）→ `view::follow` 相机跟随。相机必须先定位：波次投放的“画面外出生点”由本帧可视区决定。
2. `Entity_Store::advance`：位移、玩家计时器衰减、精英弹幕、越界弹丸回收、掉落物吸附。此步既有生成也有卸载，必须先于索引重建。
3. `Boss_System::update`：阶段推进与弹幕节拍（生成）。紧随 <2>：血量/阶段在位移后已确定，弹幕也须早于索引重建。
4. `Wave_System::update`：按速率投放、首领档生成。放在 Boss 之后，本帧刚出生的首领不会同帧开火。
5. `Weapon_System::update`：索敌出膛（生成）。
6. `World::frame_begin` + 遍历有效敌人/投射物写入本帧索引。索引重建晚于全部生成，帧戳此前已递增，上一帧残留编号整体失效。
7. `Combat_System::resolve`：广相 + 窄相 + 发事件（卸载）。卸载发生在索引重建之后，索引中不会出现“卸载后又复用同编号”的错配。
8. `Progression_System::update`：吸收 → 经验 → 升级 → 候选。放在战斗之后：本帧击杀产生的掉落要等下一帧才可能被吸收，避免“击杀 → 掉落 → 吸收”同帧互相踩踏。
9. `Score_Board::tick`：连击窗口衰减。计分板订阅死亡事件，而“超时清零”是随时间推进的规则，调用点收敛在帧序。
10. `Hud_Notice::advance`：提示计时衰减。

`帧推进` 不含渲染、不含阶段切换、不含输入轮询；阶段切换与输入留在 `main`，使输入来源唯一（便于压测替换为脚本走位）。

### 6.9 空间索引：帧戳、read_only 与预建树

- 四叉树参数在 `World` 构造时显式覆盖引擎默认值（`block_size=64`、`min_size=32768`、`max_size=65536`）；引擎默认 `block_size=16 / 初始 256` 与地图尺度不匹配。
- 建树种子取地图四角（各内缩 64）与中心共 5 点，`tree_build_smart` 一次落位，避免逐帧插入触发建树造成首帧卡顿。
- 写入路径 `insert` 用 `get(coord_l, handle)`（`read_only=false`：缺失区块即时分配）；查询路径 `query_range` 用 `seek(range, out)`（`read_only=true`：只查既有区块）。注释特别指出新版 `seek` 第三形参 `read_only` 与旧版 `stable` 语义相反，写/查必须分别取 false/true。
- 逐帧重建靠帧戳而非清空：`frame_begin` 只 `stamp++`；`insert` 发现 `data->stamp != stamp` 就先 `clear()` 两个编号数组再写；读取方（`Combat_System`、自检）只认 `chunk.data->stamp == world.frame_stamp()` 的区块。这样既不需要遍历全树清空，也不会读到上一帧残留。
- 区块句柄所有权：引擎以 `shared_ptr` 交出，`release_chunks` 只清容器；无手工释放。

### 6.10 对象池使用纪律

- 敌人 / 投射物 / 掉落物均派生 `engine::Object`（`Object_Pool` 的模板约束），复用槽位避免每秒数百次 `new/delete`。
- **禁止 `clear()`**：它会把 ID 分配器 reset 到 0，而 0 是“非法实体 ID”哨兵。重开一局改为“收集全部有效编号 → 遍历结束后逐个 `unload`”（`reset` 三段收集/卸载）。
- **遍历中不生成**：`build()` 的 `push_back` 可能扩容，使既有迭代器/引用失效。因此统一“先按索引/引用遍历、收集待卸载编号，遍历结束后统一卸载”；`spawn_*` 在 `build` 后**重新按编号查找**槽位再写字段。
- **无效槽位**：`unload` 不擦除容器元素，只置无效并回收索引槽，故所有遍历必须逐项 `valid()`；`enemy_at` 等也先判 `valid()`。
- 计数缓存与池同步：`enemy_alive_num/projectile_alive_num/drop_alive_num/boss_alive_num` 在 spawn/unload 内维护；`reset` 归零。
- 自检专门验证：三个编号互不相同且非 0；卸载中间编号后立即失效；再生成复用刚回收的编号（LIFO）；批量 2000 发计数精确；`reset` 后归零且仍能正常生成。

### 6.11 波次与难度模型

- 难度是闭式公式，不查表：`wave = 1 + floor(elapsed / spawn_rate_period(12s))`；`rate = min(spawn_rate_cap(60), spawn_rate_base × (1 + spawn_rate_growth × 完整周期数))`。速率基数与增长比例取当前设置值。
- “波次”在本作是“难度档位”，不是整波一次性投放：进入新档只发一条 `Wave` 事件，投放由速率持续进行。理由是割草题材下持续投放更能维持压迫感，也避免整波同向移动造成图形重叠与帧内尖峰。
- 投放节奏：`timer -= dt`，`timer <= 0` 时 `spawn_one` 并把计时重置为 `1/rate`。投放闸门在**计时推进之前**：若 `enemy_alive >= enemy_cap` 直接 `return`，计时不推进。于是解压瞬间 `timer` 已是较大负值，会逐帧连续投放直到追平——这是一种隐式的“投放追赶”行为，代码未显式说明。
- 首领档：`boss_wave(wave) = wave % interval == 0`（`interval` 取设置，下限 1）；条件为“本档为首领档 ∧ 当前无首领在场 ∧ 本档尚未生成过（`boss_wave_done != wave`）”。三条合起来保证同一时刻最多一只首领（站桩单只），且下一档不会因上一只存活而叠出双首领。
- 首领在场期间普通投放速率乘 `boss_spawn_rate_scale(0.45)`，压低杂兵压力。
- 出生点：`view::focus()` ± `visible_half_*` + `spawn_margin(60)`，按随机边合成后夹进地图。理由是地图放大且相机跟随后，若按固定设计尺寸投放，玩家走到地图别处就看不到新敌人；相机贴边时“画面外”已在地图之外，夹取使敌人改从地图边界走入场内。
- 类型掷骰：先判精英（`rng(0,9999) < elite_chance × 10000`）；非精英再按固定权重：射手 12% → 自爆兵 6% → 其余小兵。精英再掷词缀：`affix_roll < elite_affix_chance(0.55)` 时取 `static_cast<elite_affix>(1 + rng(0,2))`（1 迅捷 / 2 护盾 / 3 狂暴）。

### 6.12 战斗判定与伤害口径

- 两类判定：玩家弹 → 敌人走“四叉树广相 + 圆-圆窄相”；敌人接触 / 敌弹 → 玩家直接线性遍历（玩家唯一且敌人有上限，为单点对象再走空间查询无收益且增加分配）。
- 广相半径取 `shot.radius + max(elite_radius, boss_radius)=54`，即按最大敌人半径保守估计，保证首领边缘命中不漏检。
- 窄相比较距离平方（免开方）；命中后 `damage_taken_get` 处理护盾词缀（`×0.55`，保底 1），扣血、`flash = 0.12s`、记录命中、发 `Hit`。
- 穿透：`projectile::hit_ids[weapon_hit_cap(4)]` 记录已命中编号，同一发不对同一敌人重复结算；`pierce > 0` 则递减继续飞，否则卸载本发并置 `consumed` 跳出。`projectile_record_hit` 在记录数达上限后不再记录——若 `pierce` 超过 3（例如外部直接构造），去重会失效；卡池穿透上限 3 使正常路径不会越界。
- 死亡流程：先取 `kind/score/pos`，再 `unload_enemy`，再 `publish_death`，再 `spawn_drops`。顺序保证事件与掉落在实体离场后仍能拿到完整数据。
- 同帧结算顺序：先玩家输出（`bullet_to_enemy`），再玩家承伤（`harm_to_player`），使“同帧先击杀逼近的敌人”成为玩家的有利判定。
- 自爆兵：`spawn_enemy` 时 `contact_damage = 0`，伤害全部来自“接触即爆”；`harm_to_player` 先收集接触到的自爆兵编号，遍历结束后统一 `incoming += bomber_blast_damage`、卸载、发死亡事件、生成掉落。这样战斗系统不必区分“接触伤害”与“爆裂伤害”两条口径，且自毁同样计分掉落（玩家没有“必须用枪打死才划算”的动机）。
- 无敌期：`incoming <= 0` 先返回；随后若 `hero.invuln > 0` 直接返回（不扣血、不发 Hurt）。注意敌弹的卸载发生在无敌判定之前，因此无敌期间撞上玩家的敌弹仍会被消耗；自爆兵的引爆与掉落也发生在无敌判定之前。
- 掉落：按类型取数量/单颗经验/档位（小兵 1×2、精英 4×4、首领 12×10；射手与自爆兵沿用“小兵档”）；同一次掉落按圆周均匀铺开位置与速度，避免重叠成一颗。

### 6.13 成长与升级

- 经验需求为几何递推：`xp_need(next) = xp_need_base(6) × xp_need_growth(1.32)^(next-2) × xp_need_scale`，取整且下限 1。几何而非线性，使后期升级速度自然放缓，不必另写“经验通胀”。
- 吸收半径 = `hero.radius × 卡拾取倍率 × 设置拾取倍率 + 掉落半径`；吸附（朝玩家靠拢的位移）在 `Entity_Store::advance`，吸收（判定 + 卸载 + 加经验）在 `Progression_System::absorb`。运动与规则分离。
- 一次可连升多级：`while (xp >= xp_need && level < level_cap)` 逐级扣减、`level++`、`level_up_total++`、`pending_picks++`、重算 `xp_need`、发 `LevelUp`；满级后 `xp = 0`。
- 候选抽取：已有候选则保持（避免每帧刷新卡面抖动）；无待选则返回；收集 `card_stack < max_stack` 的卡；`rng` 洗牌式抽取 `candidate_count(3)` 张互不重复；全部叠满则不给候选。
- `apply_pick`：越界或无候选忽略；`apply_card` 落地后 `pending_picks--`、清空候选；若仍 `pending_picks > 0` 立即 `roll_candidates`，否则升级浮层会在“无候选”的那一帧消失、画面闪断。
- 卡效果只写 `player.stats` 的加值字段，不动 `config` 基础设置；`max_hp` 卡同时抬升 `max_hp` 与 `hp`（升级同时回等量生命）；`crit_chance` 夹到 `[0,1]`。重开一局 `stats` 清零即回到设置强度。

### 6.14 界面、输入与浮层

- 阶段机只有三态（`menu/playing/over`）+ 一个 `pause_flag`；设置与升级是**浮层**而非第四种阶段。浮层语义的好处是“从哪来、回哪去”不需要额外记账，只把逻辑帧整体冻结。
- 主循环的浮层优先级（`main` 的 while 内）：升级浮层打开时本帧不推进帧序、不响应游玩输入；否则设置浮层打开时只响应 ESC 关闭；否则按阶段处理输入。
- 冻结规则：`renderer.advance` 只在“非菜单 ∧ 设置未开 ∧ 升级未开 ∧ 未暂停”时推进；`draw_play` 在非菜单时始终登记（结算与暂停时画冻结画面）。升级浮层期间 `draw_play` 仍登记，但逻辑不推进。
- 输入：`read_move_input` 直接返回未归一化方向；`confirm_pressed` 覆盖回车/小键盘回车/空格；按键沿每帧末尾 `input_edges_clear` 清空。
- 设置面板每帧取副本、帧末差异落库；`window_dirty` 只登记“全屏或分辨率档位变化”，由调用方帧末 `view::apply_window()` 后 `clear_window_pending()`。理由：避免在 ImGui 绘制中途重建窗口。
- 设置面板用 3 列表格（难度+窗口+帧率在上、战斗+成长在中、渲染在右），`BeginTable` 失败时必须 `End + warm_style_pop` 严格配对返回。
- 升级面板以屏幕像素空间绘制（因鼠标命中用 `GetMousePosition` 像素坐标），设计单位乘 `effective_scale = max(scale(), 0.32)`；只读候选，点中的下标回传调用方。
- 零尺寸帧护栏：`Screen` 三个绘制函数先 `layout_valid`（finite 且 >0），设置/升级面板先判 `render_ctx::width()/height() > 0`。原因注释写明：启动或全屏切换瞬间 `scale()` 为 0，`layout_width()` 会产出 inf/NaN，非法坐标灌入 ImGui 绘制列表会导致访问违例/设备丢失（无日志崩溃）。

### 6.15 中文文本、字体与编码

- 源码与标识符均为 UTF-8，CMake 传 `/utf-8`；文件名与路径含中文，`std::filesystem::path` 与 `std::string` 互转时走本地编码，故日志输出统一经 `u8string` 中转（`path_to_text`）。
- 字体分两档：小字号 22px 收录中文全范围 + 界面符号（♪ • … ✓）；大字号 64px 只收录 `text::all_texts` 中实际出现的码点（`add_utf8_codepoints` 手工解析 UTF-8），以控制图集体积。候选字体顺序：`msyh.ttc / msyhbd.ttc / Deng.ttf / simhei.ttf / simsun.ttc`（`%WINDIR%/Fonts`）。失败回退 `AddFontDefault` 并打印警告，界面中文可能不显示。
- `font_for_pixel_size` 以 42px 为界选大/小图集；`ui_text` 按 `align` 以设计单位计算偏移后再乘缩放。

### 6.16 2.5D 相机几何

- 坐标系：游戏 (x, y) → 3D (x, 0, y)，地面 y=0，3D 的 y 为高度。
- 相机俯仰 50°、纵向视场 45°；`solve_camera_geometry` 以“目标纵向可视半高 = 720/2/view_zoom”反解：`theta = camera_pitch_deg`（弧度）、`half_fovy = camera_fov_deg/2`，`far_angle = theta - half_fovy` 并夹到下限 5°，`inv_far = 1/tan(far_angle)`、`inv_near = 1/tan(theta + half_fovy)`，`cam_height = 2·half_h / (inv_far - inv_near)`，`cam_back = cam_height / tan(theta)`；足迹纵向取远近两侧较大值、横向取远边处 `far_dist·tan(half_fovy)·aspect`。
- 关键护栏：远边射线与水平面夹角不得小于 5°，否则 `1/tan` 发散。
- 相机摆放 `cam_position = (focus.x, height, focus.y + back)`、`target = (focus.x, 0, focus.y)`；`camera_apply` 另下发 `fov = 45°`、`near=1`、`far = map_half_width × 8`。
- 鼠标世界点：像素 → 归一化 `(u,v)` → `camera_unproject(u,v,0/1)` 取近远两点 → 与 y=0 求交（`t = -near.y / (far.y - near.y)`），`t` 不在 [0,1] 则退回焦点。

### 6.17 错误处理与日志策略

- 无异常设计：动态分配走 `new(std::nothrow)` 语义（引擎 `Event::build` 内部即如此，故所有 `build_event` 都判空）；JSON 解析与事件回调以 `try/catch` 包裹；引擎接口失败返回 `false` 时逐层回滚。
- 日志统一 `cout`/`cerr` + `std::format`，中文前缀如 `[view]`、`[config]`、`[career]`、`[obs]`、`[self-test]`、`[soak]`。窗口模式 `main` 在装配前调用 `FreeConsole()` 隐藏控制台（日志仍写入但不显示），故窗口模式没有可见日志。
- 自检返回码：`self_test::run` 返回首个失败项编号（1 起），全过返回 0；`soak::run` 达标 0、未达标 3。
- 表现层对非法数据一律“跳过/兜底”：零向量方向退回 `(1,0)`、投影失败跳过、句柄 0 跳过、`layout` 非法整帧跳过。

### 6.18 性能取舍

- 实例化替代散绘：敌人/投射物/掉落物/植被/碎石/粒子全部按“网格 × 材质”分批 `mesh_draw_instanced`。
- 材质缓存键把 alpha 量化到 16 级、自发光量化到 1/100、toon 参数量化到 uint8；避免逐帧淡出值把缓存无限撑大，同时把材质数限制在可枚举规模。
- 粒子与各类活动列表设硬上限并 `reserve`，避免战斗高峰反复扩容。
- 视野剔除 + 颜色/透明度分桶；`Score_Board::tick` 无连击时直接返回。
- 空间索引减少窄相量：`Combat_System::narrow_tests` 作为广相效率的可观测指标（`[obs]` 每秒打印、soak 记录峰值与均值）。

## 七、模块运行链路详例

### 7.1 链路一：一局游戏的一帧推进（帧推进 → 系统 → 渲染）

调用方：`main` 的 while 循环（`Application/Game/星屑弹幕/source/app/主调函数.cpp`）。

1. `view::pointer_position_set(render_ctx::mouse_x(), render_ctx::mouse_y())`；`view::refresh()`（尺寸/视野缩放变化时重算相机）。
2. `dt = render_ctx::dt()`（上一帧间隔，上限 0.1）。
3. 计算 `upgrade_visible = (screen.state()==playing) && hero.alive && prog.candidate_num() > 0`。
4. 按浮层与阶段分派输入：升级浮层 → 不推进；设置浮层 → ESC 关闭；`menu` → 确认键 `reset_run + to_playing` / ESC 开设置；`over` → 确认键或 R `reset_run + to_playing` / ESC 回菜单；`playing` → 暂停时 ESC 回菜单、P 继续；否则 ESC 开设置、P 暂停、或进入游玩帧分支。
5. 游玩帧：`advance_play_frame(world, store, weapon, wave, boss, combat, prog, score_board, hud, read_move_input(), dt)`：
   - `帧推进.cpp` 钳 `dt` → 玩家移动与钳制 → `view::follow(hero.pos)`；
   - `store.advance(dt)`（位移、计时器、精英/射手开火、越界回收、吸附）；
   - `boss.update`（阶段/弹幕）→ `wave.update`（投放/首领档）→ `weapon.update`（索敌/出膛）；
   - `world.frame_begin()` → 逐有效敌人/投射物 `insert_*`；
   - `combat.resolve(world, store)`（广相/窄相/事件/掉落）→ `prog.update(store)`（吸收/升级/候选）；
   - `score_board.tick(dt)` → `hud.advance(dt)`。
6. 死亡判定：`!store.hero().alive` → `screen.to_over()` + `finish_run()`（组结算、`career::submit`、刷新 best）。
7. `config::tick(dt)`（延迟写回）。
8. 表现推进：非菜单且无浮层且未暂停时 `renderer.advance(dt)`（衰减特效）。
9. 绘制登记：非菜单时 `renderer.draw_play(make_view())` → `effects.draw_background` → `terrain.draw` → 暗盘 → 掉落 → 投射物 → 泛光 → 敌人 → 玩家 → 世界特效 → 末尾设相机。
10. 同步 `Ui_State`（state/paused/settings_visible/upgrade_visible/result；清空 pending）。
11. `render_ctx::input_edges_clear()`。
12. `render_ctx::frame()`：`g_renderer.frame_render()`（SDL 事件泵 → 取图 → 录制 → 提交 → 呈现）在其 UI 回调中执行 `on_ui_draw` → `ui_frame()`：
    - `menu` → `Screen::draw_menu(career::best_score, career::best_wave)`；
    - 否则 `Renderer::draw_hud()`（边缘告警/HUD 面板/小地图/提示/伤害数字/红闪/帧率），`over` 再 `draw_over(last_result)`，暂停再 `draw_pause()`；
    - 设置浮层 `Settings_Panel::draw()`；升级浮层 `Upgrade_Panel::draw(prog)`。
    随后 `ImGui::Render()` + `ImGui_ImplVulkan_RenderDrawData` 提交到渲染层命令缓冲。
13. 帧末动作消费：`pending_settings`（resume/menu/quit）、`pending_pick`（`prog.apply_pick(index, store)`）、`window_pending`（`view::apply_window()` + `clear_window_pending()`）。

副作用：玩家位置、实体池、四叉树、事件订阅者计数/提示列表、特效列表、设置脏标记、窗口状态。渲染层不改任何玩法状态。

### 7.2 链路二：敌机生成到命中判定

1. `Wave_System::update(dt, store)`：累计 `elapsed`；算 `now_wave`；跨档发 `Combat/Wave`；首领档条件满足则 `spawn_boss`；`enemy_alive >= enemy_cap` 则返回；`rate = spawn_rate()`（首领在场×0.45）；`timer -= dt`，到点 `spawn_one` 并 `timer = 1/rate`。
2. `spawn_one`：取 `view::focus()`、`visible_half_*`，随机边合成出生点（画面外 `spawn_margin`），夹进地图；掷精英/词缀/杂兵类型与初始速度；`store.spawn_enemy(pos, init_dir * speed, kind, affix)`。
3. `Entity_Store::spawn_enemy`：`enemy_pool.build()` → `enemy_at(id)` 重新取槽 → 写 `pos/vel/speed/flash/affix` → 按 kind 套半径/HP/接触伤害/冷却（精英词缀改写速度或接触伤害；Boss 重置 phase/pattern_timer/spiral_angle；射手出生满冷却；自爆兵 contact=0）→ `enemy_alive_num++` → `max_hp = hp` → Boss 记 `boss_alive_num++`。
4. 同一帧稍后 `Entity_Store::advance(dt)`：`e.vel = vec_normalize(hero.pos - e.pos) * e.speed`（射手按保持距离区间驻停/前进/后退），`e.pos += e.vel * dt`；精英/射手到冷却则 `spawn_projectile` 生成敌弹。
5. `World::frame_begin` 后由 `帧推进` 遍历有效敌人 `world.insert_enemy(uint32_t(foe.ID()), foe.pos)`；投射物同理 `insert_projectile`。
6. `Combat_System::resolve` → `bullet_to_enemy`：对每发玩家弹 `world.query_range(shot.pos, shot.radius + 54, chunks)`；逐区块判 `stamp == world.frame_stamp()`；逐敌人编号 `store.enemy_at(id)` → 跳过已命中 → 圆-圆窄相（`diff.length_sq() <= (target.radius + shot.radius)^2`）。
7. 命中：`damage_taken_get`（护盾 ×0.55，下限 1）→ `target.hp -= taken` → `target.flash = 0.12f` → `projectile_record_hit` → `publish_hit(id, kind, taken, target.pos, normalize(shot.vel), shot.crit)`（发 `Combat/Hit`）。
8. 事件分发：`Combat_Stats::on_event` 累加 `hits/damage`；`Effects::on_event` 生成沿入射方向的扇形火花、反溅、冲击闪光、伤害数字；`Score_Board` 不订阅 Hit（只订阅 Death）。
9. 若 `hp <= 0`：取 kind/score/pos → `store.unload_enemy(id)` → `publish_death`（`Combat/Death`）→ `spawn_drops`（圆周铺开生成掉落物）。订阅者：`Score_Board` 连击与得分、`Combat_Stats` 击杀数、`Hud_Notice` 精英/首领提示、`Effects` 按类型爆散与冲击环/震动。
10. 穿透处理：`pierce > 0` 递减继续；否则 `store.unload_projectile(shot.ID())`，`consumed = true` 跳出区块与敌人循环；最后 `World::release_chunks(chunks)`。

结果：敌人池状态、玩家弹池状态、掉落物池状态、四叉树本帧索引（下一帧重建）、四类订阅者状态、特效列表。

### 7.3 链路三：配置装载到常量生效

1. `main` 构造 `engine::Event_Broker broker`；调用 `config::load(broker)`。
2. `config::load`：`node_holder = make_unique<Event_Node>(broker, "Stardust_Barrage_Settings", {(Config, Load)}, on_config_event)`。`Event_Node` 内部按五步接线并 `attach`；随后投递 `Subscribed_Events/Add`（`broker.process`）。
3. `loader_holder = make_unique<engine::Config_Loader>()`；把其终端 `Broker_Attacher/Evt_Sender/Evts_Sender` 绑到同一 `broker`；`loader_holder->attach()`。
4. `node_holder->build_event(Believed_Root, Load)`，载荷 `route="assets/config/route"`、`config="assets/config"`；`node_holder->send`。
5. 引擎扫描 `assets/config/route` 下的路由文件，读到 `object="Stardust_Barrage_Settings"`、`config_path="assets/config/设置.json"`；按脏标记把文件内容包装成 `Config/Load`、`receiver=Stardust_Barrage_Settings` 的定向事件；经 `Evts_Sender → broker.receive(events)` 分发。
6. 中转站按订阅关系投递给本模块接收入口 → `on_config_event`：判 `evt->config.is_object()` 与 `evt->receiver == settings_module` → `parse(evt->config)`（逐组 `group.value(key, 默认值)`，缺字段/类型不符沿用默认）→ `config::replace(loaded)`（逐项夹取）→ `received = true` → 打印路径。
7. 若 `received == false`：打印“引擎装载未送达，回退直接读取”，`load_direct()` 用 `ifstream` + `try/catch` 解析同一文件并 `replace`；失败则保留默认值。
8. 生效：后续每帧各系统 `config::get()` 现取——`Wave_System::spawn_rate`（刷怪速率/增长）、`spawn_one`（精英概率/权重）、`update`（敌人上限/首领间隔）、`Weapon_System::update`（间隔/伤害/瞄准模式）、`帧推进`（玩家速度）、`Progression_System`（经验与拾取倍率）、`view`（视野缩放）、`render_ctx`（帧率上限）、`Renderer/Effects/Terrain`（渲染开关）。
9. 改动写回：设置面板逐帧副本 → 差异 → `config::replace + mark_dirty` → `config::tick` 累计 0.4s → `write_file`；退出 `config::flush`。

结果：`config::settings` 唯一实例被替换为夹取后的文件值；下一次 `get()` 起，所有玩法/呈现数值随之改变，无需重启或重建对象。

### 7.4 链路四：界面打开与交互

**4a 设置浮层**

1. 主菜单按 ESC（或游玩中未暂停按 ESC，或结算中不响应）→ `settings_panel.open()`（`shown = true`）。
2. 主循环进入“设置打开”分支：本帧只响应 ESC → `close()`；不推进帧序、不响应移动/开火。
3. `ui_frame` 内（ImGui 帧）若 `settings_visible`：`Settings_Panel::draw()`：
   - 判 `render_ctx::width()/height() > 0`；算 `scale_factor = min(render_ctx::scale(), 94%宽/1240, 92%高/580)` 并下限 0.32；
   - 背景列表整屏压暗；`SetNextWindowPos/Size` 居中；`warm_style_push`；`Begin("##设置面板")`；
   - `before = config::get()`、`draft = before`；
   - `BeginTable("##设置列", 3)`；若失败则 `End + warm_style_pop` 并返回 `none`；
   - 第一列：难度 4 项 + 窗口（全屏/分辨率/视野缩放） + 帧率上限；第二列：战斗 5 项 + 成长 4 项；第三列：渲染 8 项（含模型细节）；
   - 底部按钮：恢复默认（`draft = config::make_default()`）、返回游戏（`resume`）、返回主菜单（`menu`）、退出游戏（`quit`）；
   - `End` + `warm_style_pop`；
   - `if (!same_settings(draft, before))`：若全屏或分辨率变化则 `window_dirty = true`；`config::replace(draft)`；`config::mark_dirty()`；
   - 返回 `action`，`ui_frame` 写入 `ui.pending_settings`。
4. 帧末消费：`resume → close()`；`menu → close() + screen.to_menu()`；`quit → ui.quit_requested = true`。
5. 若 `settings_panel.window_pending()`：`view::apply_window()`（全屏对齐；非全屏按档位算尺寸、夹进显示器可用区、居中、`window_size_set`、`refresh` 同步相机）→ `clear_window_pending()`。

**4b 升级浮层**

1. `Progression_System::check_level_up` 使 `pending_picks > 0`；`roll_candidates` 抽取 3 张候选（`candidate_num_ = 3`）。
2. 主循环算 `upgrade_visible = playing ∧ hero.alive ∧ candidate_num() > 0`；为真时本帧不推进帧序、不响应游玩输入。
3. `ui_frame`：先画 HUD，再 `Upgrade_Panel::draw(prog)`：整屏压暗、居中面板、三张卡片（`candidate_info(i)` 为空则跳过）、悬停提亮描边、`IsMouseClicked(0)` 记 `chosen = i`；返回下标写入 `ui.pending_pick`。
4. 帧末消费：`prog.apply_pick(index, store)` → `apply_card`（写 `player.stats` 对应加值，`max_hp` 卡同时加 `max_hp/hp`）→ `pending_picks--` → 清候选 → 若仍有待选则立即 `roll_candidates`；`pending_pick = -1`。

结果：设置项被替换并安排写回（窗口类改动立即作用于窗口）；或玩家获得一张升级卡的加值，候选刷新或关闭。

### 7.5 链路五：玩家阵亡 → 结算 → 生涯记录 → 重开

1. `Combat_System::harm_to_player`：合并承伤 → 无敌判定 → `hero.hp -= incoming`、`hero.invuln = 0.45`；若 `hp <= 0` 则 `hp = 0`、`alive = false`，并发 `Combat/Hurt`（`Hud_Notice` 提示、`Effects` 震动+红闪）。
2. 同帧 `Progression_System::update` 发现 `!hero.alive` 直接返回（阵亡后不再吸收与升级，结算不再弹升级浮层）。
3. `main` 游玩帧分支的死亡判定：`!store.hero().alive` → `screen.to_over()` + `finish_run()`：
   - 从 `score_board/wave/stats/store.hero().prog` 组 `result_summary`；
   - `dps = stats.damage_dealt() / wave.elapsed_time()`（`elapsed > 0.01` 才计算）；
   - `career::submit(score, wave, level, best_combo)`：逐项比最大值，有刷新则 `write_file` 并返回 true；`result.new_record = ...`；`result.best_score = career::get().best_score`；存 `last_result`。
4. 后续帧：`state == over`，`draw_play` 仍登记（冻结画面），`ui_frame` 画 HUD + `Screen::draw_over(last_result)`（九行战绩、mm:ss、DPS、最高连击、历史最高、新纪录标记、重开提示）。
5. 输入：确认键或 R → `reset_run()`（`store.reset` / `weapon.reset` / `wave.reset` / `boss.reset` / `prog.reset` / `score_board.reset` / `stats.reset` / `hud.clear` / `renderer.reset`[特效清空 + 地形重随机]）→ `screen.to_playing()`；ESC → `to_menu()`。
6. `reset_run` 后第一帧：玩家回到原点、`player{}` 默认（`hp/max_hp` 取当前设置）、各计数归零、`wave` 回到 1 档、地形换一张。

### 7.6 链路六：无头自检与压测

1. `main` 解析 `argv`：`--self-test` → `self_test::run()`；`--soak [秒]` → `soak::run(seconds)`。两者都在创建 `broker`/渲染上下文之前返回，故不建窗口。
2. `self_test::run` 依次执行 16 项：每项自建 `World/Entity_Store/Event_Broker/系统`，用确定性构造（零速弹丸、直设 HP、直设冷却）验证；打印 `PASS/FAIL`；首项失败即返回其编号。
3. `soak::run`：建 `broker`、三个订阅者、`World/Entity_Store`、五个系统；`dt = 1/60`、`total_frames = seconds×60`；脚本走位为绕原点的椭圆 `(cos(1.1t)·420, sin(1.1t)·260) - hero.pos`。
4. 每帧：若英雄阵亡则逐系统 `reset` 并 `restart_num++`（重开路径被反复验证）；`advance_play_frame(...)`；累计 `peak_enemy/peak_projectile/peak_narrow/narrow_sum`；每 60 帧打印一行。
5. 结束：打印峰值与均值；验收 `peak_projectile >= 400`，达标返回 0，否则返回 3。

结果：不产生窗口、不依赖显示器与真实帧率，可复现逻辑正确性与负载规模。
