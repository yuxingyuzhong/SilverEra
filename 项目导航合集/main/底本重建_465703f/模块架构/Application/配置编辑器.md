# 配置编辑器模块

> 依据版次：工作区 465703f ｜ 依据：冻结快照 465703f ｜ 更新：2026-11-08

本模块覆盖 `Application/Editor/src/Config_Editor` 下的 24 个源文件，是白银纪元引擎外置“配置编辑器”可执行程序的全部实现。模块内部再分为两层：**实体配置模型**（数据层，负责磁盘读写、路由同步、格式定义与校验）与**配置编辑器**（表现层，负责 ImGui 界面、页面导航、面板生成与保存入口）。本文件按七段结构书写，所有事实均取自冻结快照源码，路径均相对工作区根。

## 二、模块功能介绍

### 2.1 存在理由

引擎实体（Entity）与属性槽（Property）的运行时行为完全由 `assets/` 下的 JSON 配置文件驱动：`Entity_Manager` 的 `config_field_parse` 读取实体四字段，`Property_Manager` 的 `event_process` 读取属性槽两字段。手写这些 JSON 既要记住字段名、必填性、类型嵌套形式，又要同步维护 `assets/config/route/` 下的路由表，否则引擎会静默跳过配置。本模块就是一个独立图形程序（自带 `main()`），把“路由表 + 配置文件 + 校验规则”三件事做成可视化编辑，使配置的生产与维护脱离手写文本。

### 2.2 两层分工

- **数据层（实体配置模型）**：`实体配置模型.h` 定义内存数据模型，`实体配置模型_*.cpp` 实现磁盘读写。它不认识 ImGui，只认 `nlohmann::json`、`std::filesystem` 与 `engine::Engine_Env`（用于定位 exe 同级 `assets/`）。所有“什么算合法配置”的知识集中在 `实体配置仓库`：解析、序列化、校验、路径生成、路由同步。
- **表现层（配置编辑器）**：`配置编辑器.h` 持有 `实体配置仓库` 实例，所有面板直接拿到仓库集合的可写引用，在 ImGui 控件里就地修改内存对象；保存时才调用仓库接口落盘。表现层不负责配置文件读写、序列化与路由维护，只按字段语义摆控件；通用配置面板例外，它需要直接读写 `通用配置::字段值` 这个 JSON 对象的成员（见 §6.4）。字段生成逻辑由数据层的 `配置格式` 驱动。

这条分层边界可在 `配置编辑器::渲染属性面板()`（`core/配置编辑器_实体面板.cpp`）与 `实体配置仓库::保存实体()`（`core/实体配置模型_实体.cpp`）之间直接观察到：前者只改 `实体配置` 的成员并显示状态消息，后者负责“重名检查 → 文件迁移 → 序列化 → 原子写入 → 路由同步”。

### 2.3 负责范围

1. 启动时定位 `<exe 目录>/assets`，读取 `config/route/entity.json`、`config/route/property.json`、`config/route/custom_<模块>.json`，按路由条目加载 `config/entities/`、`config/property/`、`config/custom/` 下的配置。
2. 维护三种配置集合（实体、属性槽、通用配置）与三种格式来源（内置 `Entity_Manager`／`Property_Manager` 种子，以及 `config/format/*.json` 自定义格式）的内存镜像。
3. 提供四页导航（主界面 → 实体档案列表 → 实体档案详情 → 模块配置编辑）与模块浏览／新建／编辑／删除／校验／保存。
4. 维护 `config/entity_image.json` 实体图片元数据，提供图片上传、复制、纹理加载与档案页展示。
5. 提供格式定义管理：自定义模块的新建、字段增删与类型选择、格式删除（连带清理路由与配置目录）。
6. 提供“清理孤儿配置文件”工具：删除未被任何路由引用的配置文件与 `.bak`／`.tmp` 残留。
7. 提供保存链路：单条保存、Ctrl+S、保存全部，以及带未保存确认的窗口关闭流程。

### 2.4 不负责范围

1. 不参与引擎运行时：不加载 Lua、不构造 `Entity`／`Property_Slot` 对象、不执行 `config_field_parse`／`event_process`；校验逻辑是对引擎规则的“复刻”而非调用引擎。
2. 不提供通用 JSON 编辑器：只认识格式定义内的字段，格式外的键在通用配置面板中不显示，但保存时仍原样保留在 `字段值` 中。
3. 不做配置热重载：编辑器内的“重新加载”只重建自身内存镜像，不通知引擎。
4. 不管理 `assets/` 之外的资源；所有路径均以 `assets/` 为基准（`仓库.资源目录()`）。
5. 不负责图片内容编辑：只做原样复制与展示，不压缩、不裁剪、不生成缩略图。

### 2.5 关键约束

1. **文件契约**：实体标准格式为 `{type, decision_load_path, acls[], needed_events[[分类,标签]]}`；属性槽标准格式为 `{type, initialize_path}`；两者字段非空性由校验硬性检查。磁盘上仍存在旧格式（`acls` 为对象、`needed_events` 为对象数组、缺少 `decision_load_path`），加载时兼容读取，保存时统一改写为新格式（见 §六 6.2）。
2. **路径契约**：所有配置路径与路由 `config_path` 都相对 `assets/`；路由条目必须以 `config/` 开头且不含 `..`，否则加载阶段直接跳过并计入“上次跳过数”。
3. **内置格式只读**：`Entity_Manager`／`Property_Manager` 两个格式带 `内置=true`，`保存格式` 与 `删除格式` 均拒绝操作；加载时若磁盘版本与内置种子契约不一致会自动覆盖升级（保留 `.bak`）。
4. **单线程 UI**：所有 ImGui 与 OpenGL 调用都在 `main()` 主循环线程；仓库没有锁，集合引用在渲染过程中被直接修改，不存在并发访问。
5. **写入原子性**：所有配置文件、路由表、格式文件、图片元数据都经 `原子写入文件` 落盘（同目录 `.tmp` → 校验流状态 → 复制 `.bak` → rename 覆盖）。
6. **失败不致命**：单条配置损坏／缺失只会累加 `上次加载跳过数`，只有路由表不可读时 `加载()` 才返回 false；图片元数据损坏不影响实体配置加载。

### 5.2 对象所有权与生命周期

```
main() 栈帧
 └── 配置编辑器 编辑器            （值对象，构造后立即 加载()）
       ├── 实体配置仓库 仓库       （值成员，构造即定位 assets 路径）
       │     ├── assets_dir / route_path / property_route_path / format_dir
       │     ├── 实体集合 + route_json
       │     ├── 属性槽集合 + property_route_json
       │     ├── 格式集合
       │     ├── 通用配置集合 + 自定义路由表（模块名 → JSON 数组）
       │     └── 实体图片表（type → 相对 assets 路径）
       ├── 脚本列表（一次性快照，手动“刷新”）
       ├── UI 状态（页面、模块、两个选中索引、脏标记、浮动窗开关、输入缓冲）
       └── GL 纹理：帮助图 / 封面图 / 实体图片三张映射表
```

- `仓库` 与 `编辑器` 同生共死；`main()` 退出时按栈序析构，GL 纹理依赖随后发生的 `ImGui_ImplOpenGL3_Shutdown`／`glfwDestroyWindow` 释放，代码中没有显式 `glDeleteTextures` 的帮助图／封面图清理。
- 面板不缓存指向集合元素的指针，每帧用索引重新定位；`选中索引` 是唯一索引依据，`加载()`、切页、切模块都会把它重置为 -1。这意味着集合增删后（新建/删除）索引可能失效，代码在每次访问前都做越界检查。
- `格式编辑` 是**副本**：格式管理窗口的所有字段编辑只改副本，`保存格式编辑()` 才写回仓库并落盘；`上传实体图片` 则是“立即写回”模型（复制文件 + 立即保存元数据）。

### 5.5 线程与帧序

全部逻辑运行在 `main()` 的单线程主循环中，帧序固定为：

1. `glfwPollEvents()` → 可能触发 `窗口关闭回调` → `编辑器.请求关闭窗口()`；
2. `ImGui_ImplOpenGL3_NewFrame()` → `ImGui_ImplGlfw_NewFrame()` → `ImGui::NewFrame()`；
3. `渲染梦幻背景()`（背景 DrawList，最先入队）；
4. `编辑器.渲染()`（页面、浮动窗、快捷键、脏标记消费、关闭请求消费）；
5. `应关闭窗口()` 为真则 `glfwSetWindowShouldClose(window, GLFW_TRUE)`；
6. `ImGui::Render()` → 取 framebuffer 尺寸 → `glViewport`／`glClearColor(0.73,0.38,0.82,1)`／`glClear` → `ImGui_ImplOpenGL3_RenderDrawData`；
7. `glfwSwapBuffers`。

仓库没有任何互斥量或原子量；`本帧有编辑失焦` 是命名空间级全局布尔，`渲染梦幻背景()` 内的星光数组与播种标记是函数内 `static`，都只在 UI 线程访问。

## 六、模块设计 / 实现细节

### 6.1 磁盘布局与路由契约

模块把 `<exe 目录>/assets` 当作唯一资源根（`实体配置仓库::实体配置仓库()` 里 `Engine_Env::exe_dir_get() / "assets"`），完全不使用当前工作目录来定位配置。读写的目录与文件关系固定为：

```
assets/
├── config/
│   ├── route/
│   │   ├── entity.json              ← 实体路由（数组，元素 {module, config_path}）
│   │   ├── property.json            ← 属性槽路由（同构）
│   │   └── custom_<模块名>.json      ← 每个自定义模块一份路由
│   ├── entities/<文件名清理(type)>.json
│   ├── property/<文件名清理(type)>.json
│   ├── custom/<文件名清理(模块)>/<文件名清理(条目名)>.json
│   ├── format/<文件名清理(模块名)>.json
│   └── entity_image.json            ← {type: "UI/entity_images/xxx.png"}
├── scripts/**/*.lua                 ← 脚本下拉候选与存在性校验
└── UI/
    ├── cyrene_help.png / cyrene_portrait.jpg   ← 帮助窗右侧图
    ├── cyrene_cover.jpg                        ← 主界面封面
    └── entity_images/<清理后的 type><扩展名>     ← 上传后的实体档案图
```

路由条目只有两个键：`module` 与 `config_path`。`module` 在加载与保存逻辑中**只被写入、从不被读取**：编辑器默认写 `"Entity_Manager"`／`"Property_Manager"`／自定义模块名，但保存已有条目时只改写 `config_path` 字段，原条目的 `module` 值原样保留。快照内的 `Application/Test/assets/config/route/entity.json` 里现存条目写的是拼写错误的 `"Entity_Mangaer"`，这不会影响编辑器，因为编辑器按 `config_path` 匹配条目，而引擎侧是否读取该字段不在本模块范围内。

`config_path` 的安全与有效性检查在三条加载路径中重复出现（`core/实体配置模型_实体.cpp` 实体循环与属性槽循环、`core/实体配置模型_通用配置.cpp` 的 `加载模块通用配置`），顺序固定：

1. 路由项必须是 JSON 对象，否则 `++上次加载跳过数`；
2. 必须含字符串 `config_path`，否则跳过；
3. `config_path.rfind("config/", 0) != 0` 则跳过（必须以 `config/` 开头，绝对路径、`assets/` 前缀、反斜杠路径都会被拒绝）；
4. `config_path.find("..") != std::string::npos` 则跳过（禁止目录穿越）；
5. `assets_dir / utf8_path(config_path)` 必须是常规文件，否则跳过；
6. `ifstream` 必须能打开，否则跳过；
7. `file >> data` 不能抛异常，否则跳过；
8. 解析函数必须返回 true 且顶层是对象，否则跳过。

只有第 2–8 步都能通过，配置才进入内存集合，并把 `config_path` 写回对象。跳过计数只在 `加载()` 开始时清零，由 UI 在 `加载消息` 中汇总显示：“已加载 N 个实体配置、M 个属性槽配置，跳过 K 个损坏/缺失配置”。

实体路由不可读（文件缺失、打开失败、解析异常、顶层非数组）是唯一会让 `加载()` 返回 false 的情况；属性槽路由不可读、单个格式文件损坏、自定义模块路由缺失都不致命。属性槽路由缺失时 `加载()` 直接跳过属性槽加载；自定义模块路由缺失时 `加载模块通用配置` 把该模块的路由缓存置为空数组并返回 0。

### 6.2 配置文件格式与双向映射

#### 6.2.1 实体配置

内存 `实体配置` 与 JSON 的映射是**强类型双向映射**，未知键在加载时被丢弃、在保存时不会重新出现：

| 内存字段 | 写入 JSON | 读取兼容 |
| --- | --- | --- |
| `type` | `data["type"] = cfg.type` | 仅接受字符串；缺失／类型不符置空 |
| `decision_load_path` | `data["decision_load_path"] = cfg.decision_load_path` | 仅接受字符串；旧配置缺失时置空，校验报“旧配置需补填”错误 |
| `acls` | 字符串数组，逐项 `push_back` | 接受字符串数组（新格式）；也接受对象 `{master, minion_set}`，取 `minion_set` 里的字符串项；若对象只有 `master` 且 `minion_set` 为空，则把 `master` 当作唯一从属项 |
| `needed_events` | 二元素数组的数组：`push_back({evt.first, evt.second})` | 接受 `[分类,标签]`（元素个数 `>=2` 即取前两项）；也接受 `{category, tag}` 对象；其余项静默忽略 |
| `config_path` | **不写** | 由路由 `config_path` 填入 |

快照中的旧格式实例（`Application/Test/assets/config/entities/哥布林 (Goblin).json`）正好展示了两点兼容逻辑：`acls` 是 `{"master":"Goblin","minion_set":[]}` 对象、`needed_events` 是 `[{"category":"Entity","tag":"Request"}, …]` 对象数组、且完全没有 `decision_load_path`。编辑器读取后 `acls` 会得到 `["Goblin"]`（`master` 回退规则），`needed_events` 会得到两个 `pair`，`decision_load_path` 为空并在校验区报错误。保存时这三处都会改写成标准新格式，`acls` 变成 `["Goblin"]`、事件变成 `[["Entity","Request"],["config","damage"]]`。

由于是强类型映射，实体 JSON 中任何格式外的键（注释、扩展字段、引擎后续新增字段）在“加载 → 保存”一次往返后都会丢失。这是有意的契约收敛，但也意味着编辑器不能作为无损 JSON 编辑器使用。

#### 6.2.2 属性槽配置

`属性槽配置` 只有两个 JSON 键：`type` 与 `initialize_path`，读写逻辑与实体同构（仅接受字符串、缺失置空、`config_path` 不写入）。保存时 `dump(2)` 覆盖整个文件，同样会丢弃额外键。

#### 6.2.3 通用配置

`通用配置::字段值` 直接保存整份 JSON 对象，因此：

- 格式定义中的字段只决定**显示与校验**，不决定序列化白名单；格式外的键会原样保留并在保存时写回。
- 加载时 `字段值 = std::move(data)`，随后 `条目名 = 提取条目名(字段值)`（依次找 `type`／`name`／`id` 字符串），都找不到时用文件名的 stem（`path_utf8(absolute_path.stem())`）作为条目名。
- 新建时由 UI 调 `生成默认字段值(fmt)` 生成骨架，并尝试把用户输入的条目名写入 `type` 或 `name` 字段（仅当该字段已存在且为字符串）。
- 保存时只写 `字段值.dump(2)`，**不**把 `条目名` 同步回 `type`／`name` 字段。修改条目名只会改变文件名与路由，JSON 内的 `type` 仍是旧值；下次加载时 `提取条目名` 会把旧 `type` 取回来，条目名“回退”【待确认：3】。

#### 6.2.4 缩进与中文转义

所有 JSON 落盘使用 `dump(2)`（图片元数据用 `dump(4)`）。`nlohmann::json::dump` 的 `ensure_ascii` 参数未显式传入，取默认值 `true`，因此配置里的中文 `type`（如 `"史莱姆"`）在文件中被写成 `"\u53f2\u83b0..."` 形式的转义序列，而文件名仍是原样的中文。引擎用 JSON 解析器读取不受影响，但人工直接查看文件时可读性下降；这也解释了为什么快照中文件名是中文、文件内容里的 `type` 却可能是转义形式。

### 6.3 校验分层

校验被明确分成“硬性错误”和“软性警告”两级，返回值的语义是“是否存在硬性错误”，警告永远不影响返回值：

| 对象 | 硬性错误（`errors`） | 软性警告（`warnings`） |
| --- | --- | --- |
| 实体 | `type` 空；`decision_load_path` 空；`acls` 空；`acls` 含空串；`needed_events` 空；事件分类空；事件标签空 | 决策脚本路径不存在；`acls` 引用的类型未登记（`acl == cfg.type` 时豁免）；`acls` 重复；`needed_events` 重复 |
| 属性槽 | `type` 空；`initialize_path` 空 | 初始化脚本路径不存在 |
| 通用配置 | 必填文本／脚本为空；必填列表为空；列表含空串；事件分类／标签为空；`整数` 字段不是整数；`浮点数` 不是数字；`布尔` 不是布尔 | `脚本路径` 字段指向的文件不存在 |

实现要点：

1. 校验只比较内存对象，不比对磁盘：`acls` 中引用的类型只要在 `实体集合` 内存在即视为“已登记”，刚新建但尚未保存的实体也算存在。
2. 重复检查是 O(n²) 的双层循环，内层命中后 `break`，因此**每种重复值只报告一次**，但多个不同的重复值会各报一次。
3. 校验与保存完全解耦：`保存实体`／`保存属性槽`／`保存通用配置` 都不调用校验。用户可以在红色错误未修完时保存成功，错误只会继续显示在“校验结果”折叠区。
4. 实体校验的错误文案直接引用引擎函数名（“引擎 field_check 要求”“Entity_Manager 现要求该字段”），提示用户这是引擎侧的硬约束。
5. 通用配置校验按 `fmt.字段` 顺序逐项检查，`has` 与 `value` 在循环开头一次性取出：`const bool has = cfg.字段值.contains(f.字段名); const auto& value = cfg.字段值[f.字段名];`。`nlohmann::json` 对缺失键的 **const** `operator[]` 会断言（调试）或越界（发布），这里之所以没有崩溃，是因为 `渲染通用字段编辑器` 在同一个面板中先于校验执行，已把缺失字段补成默认值；若将来在别处单独调用 `校验通用配置`，需要先修掉这个取值方式【待确认：6】。
6. 类型检查的严格度不同：`整数` 用 `is_number_integer()`，`浮点数` 用 `is_number()`（整数也能通过浮点检查），`布尔` 用 `is_boolean()`；不做范围检查。
7. 校验结果 UI 三处复用同一文案风格（实体面板、属性槽面板、通用面板），但条目高度与 Child ID 各自独立，避免 ImGui ID 冲突。

### 6.4 属性槽类型系统

`配置字段类型` 是格式系统里唯一的“类型标签”，它同时驱动三件事：格式文件中的持久化键、编辑控件、校验规则。完整对应关系如下：

| 类型 | 格式键 | 编辑控件 | 读取来源 | 默认值 | 写回形式 |
| --- | --- | --- | --- | --- | --- |
| `文本` | `string` | `输入文本` | `is_string()` 才取值，否则空串 | `""` | 字符串（仅改动时写回） |
| `脚本路径` | `script` | `渲染脚本选择器`（文本框 + Lua 下拉 + 刷新） | 同上 | `""` | 字符串（每帧无条件写回） |
| `文本列表` | `string_list` | 逐行文本 + 删除 + “+ 添加” | 只收 `is_array` 中的字符串项 | `[]` | 字符串数组，每帧重建 |
| `事件对列表` | `pair_list` | 每行两个半宽输入 + 删除 + “+ 添加” | `[a,b]` 数组或 `{category, tag}` 对象 | `[]` | 二元素数组的数组，每帧重建 |
| `整数` | `int` | `InputInt` | `is_number_integer()` 才取值 | `0` | 整数（改动即写） |
| `浮点数` | `float` | `InputFloat` | `is_number()` 才取值 | `0.0` | 浮点（改动即写） |
| `布尔` | `bool` | `Checkbox` | `is_boolean()` 才取值 | `false` | 布尔（改动即写） |

几个隐式约定：

1. **未知键回退**：`解析字段类型` 对任何未知字符串返回 `文本`，因此手写格式文件里的拼写错误不会导致加载失败，只会静默降级为普通文本框。
2. **枚举顺序即 UI 顺序**：格式管理窗口的类型下拉用 `for (int t = 0; t <= (int)配置字段类型::布尔; ++t)` 遍历，依赖七个枚举值从 0 连续排列；新增类型必须追加在末尾，否则会改变现有下拉顺序。
3. **列表字段每帧重建 JSON**：`渲染通用字段编辑器` 对 `文本列表`／`事件对列表` 的处理是“读 JSON → 转成 `std::vector` → 画控件 → 写回 `cfg.字段值[f.字段名]`”，即使没有任何编辑，写回也会发生。于是只要打开通用配置面板，旧格式的 `{category, tag}` 事件对就会在内存里被规范化成 `[a,b]` 数组；此时若保存，磁盘上也会被规范化。这个规范化**不置脏标记**，用户不会收到“有未保存修改”的提示。
4. **`脚本路径` 每帧写回**：`渲染脚本选择器` 传入的是临时 `std::string value`，函数返回后无条件执行 `cfg.字段值[f.字段名] = value`，保证下拉选择立即可见。
5. **字段名即 JSON 键**：格式管理窗口允许直接改 `字段名`，保存后旧配置里用旧键的数据不会被映射到新键，只会在新键缺失时被补默认值；旧键作为“格式外键”继续保留在 `字段值` 中。
6. **`pair_list` 读取宽松、写入严格**：读取同时接受数组与对象，写入只输出数组，保证引擎侧看到的始终是 `vector<pair<string,string>>` 可解析的形状。

### 6.5 格式定义的生命周期

格式定义持久化在 `assets/config/format/<文件名清理(模块名)>.json`，结构为：

```json
{
  "module": "Entity_Manager",
  "dir": "entities",
  "route": "entity.json",
  "builtin": true,
  "fields": [
    { "name": "type", "display": "type（实体类型）", "type": "string", "required": true, "desc": "…" }
  ]
}
```

生命周期分四段：

1. **首次生成（种子）**：`加载格式()` 首先调用 `确保内置格式()`。它对 `Entity_Manager`／`Property_Manager` 两套硬编码定义逐个检查：格式文件不存在就 `写入格式文件` 落盘；存在则读回并与种子做 `内置格式一致` 比较。比较只覆盖“契约键”——模块名、配置目录、路由文件名、字段个数、逐字段 `字段名`／`类型`／`必填`；`显示名` 与 `说明` 属于展示文案，不参与比较。不一致时直接覆盖写回并打印 `[ConfigEditor] 内置格式「…」与引擎契约不一致，已自动升级为最新版本。`。这条规则保证了引擎契约升级后，旧的内置格式文件会被自动纠正。
2. **枚举加载**：种子处理完后枚举 `format/` 目录下所有 `.json`，按 `std::filesystem::path` 排序（保证列表顺序稳定），逐个 `读取格式文件` 并追加到 `格式集合`。`读取格式文件` 会跳过 `fields` 中 `name` 为空或非对象的条目。
3. **自定义创建**：格式管理窗口“创建并添加”默认给出 `模块名`、`配置目录 = "custom/" + 模块名`（原始未清理）、`路由文件名 = "custom_" + 模块名 + ".json"`、`内置 = false`，并自动加入一个 `type` 文本必填字段。`保存格式` 校验后写 `format/<清理名>.json` 并更新内存。注意实际配置文件路径由 `生成通用配置路径` 生成，使用 `文件名清理(模块名)`，而 `配置目录` 字段只用于界面展示与帮助窗口文案，可能出现“展示目录”与“真实目录”在含非法字符时不一致的情况。
4. **删除**：`删除格式` 拒绝内置格式；对自定义格式依次删除格式文件、`route/custom_<清理名>.json`、递归删除 `config/custom/<清理名>/`，再从内存中移除格式、该模块的全部通用配置、该模块的路由缓存。界面文案却写着“删除格式不会删除已生成的配置文件”，与实现相反【待确认：5】。

`保存格式` 的约束是：`内置 == true` 拒绝；`模块名`、`配置目录`、`路由文件名` 任一为空拒绝；不校验字段名重复（重复检查只在格式管理窗口的“添加字段”处做），也不校验 `字段` 是否为空列表。因此手工构造一个 `fields = []` 的自定义格式可以通过保存，此时该模块的通用配置面板将没有任何字段可编辑，只剩条目名。

`加载格式()` 是公开接口且**不清空** `格式集合`；正常路径下只有 `加载()` 会先清空再调用它，但格式管理窗口在集合为空时也会直接调用，若将来有其它调用点重复调用，会出现同一格式被追加多次的重复项【待确认：12】。

### 6.6 图片引用与路径处理

#### 6.6.1 引用模型

实体图片与实体配置**完全解耦**：实体 JSON 仍只有四字段，图片引用单独存在 `assets/config/entity_image.json`，结构是一个 `type → 相对 assets/ 路径` 的对象（如 `{"史莱姆 (Slime)": "UI/entity_images/史莱姆 (Slime).png"}`）。这样引擎侧的四字段契约零侵入，图片属于编辑器侧的附加元数据。

读取（`加载实体图片表`）：文件不存在直接返回 true 并视为空表；打开失败／JSON 异常／顶层非对象返回 false 并写 `error`；逐条遍历时只有值为字符串才入表，非字符串条目静默丢弃。写入（`保存实体图片表`）：把整张表重建为 JSON 对象，`dump(4)` 原子写入。两张“表”不是同一对象：`仓库.实体图片表` 是持久化数据，`配置编辑器.实体图片纹理表/宽表/高表` 是运行时 GL 资源缓存，键都是 `type`，前者是路径、后者是纹理 ID 与像素尺寸。

#### 6.6.2 上传与写回链路

`上传实体图片(type)` 的完整副作用：

1. Windows 用 `GetOpenFileNameW` 取源路径（宽字符对话框，中文路径不会经过 ANSI 转换）；用户取消直接 return，不写状态消息；非 Windows 用 ImGui Modal 手输路径【待确认：14】。
2. 源文件必须 `is_regular_file`，否则写“所选文件不存在：…”。
3. `create_directories(assets/UI/entity_images)`（失败不检查 `ec`）。
4. 目标文件名 = `实体图片文件名清理(type) + 源扩展名`；扩展名取自 `源路径.extension().string()`，**保持原样**（`.PNG` 仍是 `.PNG`），头文件注释写的“小写化”并未实现【待确认：17】。
5. `copy_file(..., overwrite_existing)`：同一实体重复上传会覆盖同名旧图；不同实体若清理后同名（例如 `A/B` 与 `A:B`）会互相覆盖。
6. `设置实体图片(type, "UI/entity_images/<清理名><扩展名>")` 只改内存表，随后 `保存实体图片表` 落盘；落盘失败时图片文件已复制、内存已更新，界面提示“图片已复制但元数据保存失败”。
7. 删除旧纹理（`glDeleteTextures`）并清掉三张表的该 `type` 项，再 `加载实体图片(type)` 同步重载，保证本帧即可看到新图。

#### 6.6.3 加载与展示

`加载实体图片(type)` 是懒加载且**只尝试一次**：只要 `实体图片纹理表` 里已有该 `type` 的键（值可能为 0），后续调用直接返回 `纹理 != 0`，不会重试磁盘。加载步骤：取 `仓库.获取实体图片(type)`（空串直接失败）→ 拼绝对路径 `仓库.资源目录() / utf8_path(相对路径)` → 存在则 `stbi_set_flip_vertically_on_load(false)` 后 `stbi_load(path.string().c_str(), &宽, &高, &通道, 4)` → 建纹理（RGBA、线性过滤、边缘钳制）→ 结果三张表一律写入。

纹理方向：不翻转。代码注释给出的约定是“ImGui 的 uv(0,0) 对应纹理左上角、stb 首行即图像顶部”，与 `AddImageRounded` 默认 uv 0–1 配合即正立。帮助图、封面图、实体图三处都显式调用 `stbi_set_flip_vertically_on_load(false)`，避免受 stb 全局状态影响。

展示尺寸在档案详情页固定为 150×170 的图片框，内部可用区 `126×128`（宽减 24、高减 42，底部预留上传按钮）；等比缩放取“宽适配”与“高适配”的较小比例，再在框内水平、垂直居中绘制。主界面封面图与 `0.58` 倍可用高度的区域做同样的等比适配。

#### 6.6.4 图片与 type 的耦合风险

图片元数据以 `type` 为键，而 `type` 是实体配置里可编辑的字段：

- 在档案页或属性面板里改 `type` 后保存，`保存实体` 只迁移 JSON 文件与路由，**不会迁移 `entity_image.json` 的键**；新 type 查不到图片，旧映射成为孤儿【待确认：7】。
- `删除实体` 也不清理图片元数据与纹理表，删除后同名重建的实体会“继承”旧图片。
- 图片文件名与 `type` 绑定，改 type 后再上传会生成第二份图片文件，旧文件不会被删除（孤儿清理只扫 `config/` 下的 json，不扫 `UI/entity_images`）。

帮助图与封面图不参与元数据，路径硬编码为 `assets/UI/cyrene_help.png`、`assets/UI/cyrene_portrait.jpg`、`assets/UI/cyrene_cover.jpg`，经 `解析资源路径` 解析（先试当前工作目录，再试 exe 目录拼接）。

#### 6.7.2 视觉一致性

主题在 `应用粉色主题()` 里统一定义：`WindowBg` 全透明（让 `渲染梦幻背景()` 的粉紫渐变与 80 颗星光透出），`ChildBg` 为半透明亮粉紫 `(0.72,0.48,0.80,0.32)`，按钮为樱花粉系三态，`WindowRounding=12`、`FramePadding=(10,6)`、`ItemSpacing=(10,8)`。四个浮动窗（帮助、格式管理、关闭确认、孤儿清理）在打开时各自 `PushStyleColor` 覆盖为不透明粉紫背景，避免透出下层文字。`core/配置编辑器_视觉.cpp` 的所有函数（投影、渐变、chip、档案纸横线、圆角图）只读入参、不读全局样式，因此三页可以复用同一套视觉语言而不担心状态串扰。

主界面标题的“1.6 倍缩放”只调用了 `SetWindowFontScale`，随后用 `ImDrawList::AddText(font, GetFontSize(), …)` 直接绘制。`AddText` 使用显式传入的字号，不叠加窗口字号缩放，因此该缩放对标题实际不生效（`CalcTextSize` 同样按基础字号计算，居中计算不受影响）【待确认：23】。档案详情的标题则用 `ImGui::TextUnformatted`，`SetWindowFontScale` 对其有效。

#### 6.7.3 刷新策略

- **纯即时模式，无控件缓存**：每帧重新遍历集合、重新生成所有卡片／chip／输入框；集合规模是配置数量级（几十到几百），开销可接受，但 `渲染校验结果` 展开时每帧都会跑一次 O(n²) 的重复检查。
- **列表过滤每帧做**：搜索文本按 `type`／`config_path`（通用配置按 `条目名`／`config_path`）做 `find` 子串匹配，没有缓存过滤结果。
- **选中用索引不用指针**：切页 `切换页面` 与 `加载()` 都会把索引置 -1；`渲染模块面板` 每次访问前检查越界与模块归属，避免集合变化后的悬空访问。
- **返回定位**：从档案详情进入子页面时记录 `子页面返回实体类型`；在子页面改过 type 后返回，先用当前 type 覆盖该记录，再在实体集合里线性查找定位。
- **脏标记**：只由三类事件置位——`输入文本`／`输入文本提示` 的 `IsItemDeactivatedAfterEdit()`（搜索框传 `false` 不置位）、脚本下拉选中、整数／浮点／复选控件的值变更。结构性操作（“+ 添加”行、列表删除按钮、`渲染通用字段编辑器` 的 JSON 每帧规范化）不置脏；面板内的“保存当前实体／保存属性槽配置／保存配置／保存档案”中，只有“保存档案”清脏标记【待确认：18】。
- **快捷键**：F1 帮助、F5 重新加载、Ctrl+S 保存当前选中。F5 直接调 `加载()`，**没有未保存确认**，会丢弃全部未保存编辑，且 `加载()` 只重置 `选中索引`，不重置 `选中通用配置索引`、`当前页面`、`当前模块`【待确认：11】。
- **状态消息是单槽字符串**：每次操作直接覆盖，没有历史与级别；加载结果另存 `加载消息` 供状态栏显示。错误、警告、成功提示共用同一粉色样式，仅校验面板内部用颜色区分。
- 旧头文件顶部注释仍描述“菜单栏只有文件/帮助、左侧实体列表 + 右侧属性编辑器、状态栏含未保存标记”，与实现（四页导航、工具菜单、状态栏只显示模块数量与消息）不符【待确认：4】。

### 6.8 保存时的原子性与一致性

#### 6.8.1 原子写入的五个步骤

`原子写入文件(path, content, error)`（`core/实体配置模型_内部工具.cpp`）：

1. `create_directories(path.parent_path())`；
2. 打开同目录 `path + ".tmp"`（`out|trunc|binary`）；打不开返回“临时文件打开失败：…”；
3. `file << content; file.flush();` 后**显式检查 `if (!file)`**——磁盘满等写入失败时 `ofstream` 不抛异常，不检查就会写出半截文件；失败删除 tmp 并返回“写入临时文件失败：…”；
4. 若目标存在，`copy_file(path, path + ".bak", overwrite_existing)`；失败删除 tmp 并返回“备份原文件失败：…”；
5. `rename(tmp, path)`；代码注释说明 MSVC 实现使用 `MoveFileEx(REPLACE_EXISTING)`，可覆盖已存在文件；失败删除 tmp 并返回“替换文件失败：…”。
   整个函数包在 `try/catch (std::exception)` 中，异常转成 `"写入异常：" + what()`。

由此得到的保证是“目标文件要么是旧内容、要么是完整新内容”，不会出现半截 JSON；`.bak` 提供一代人工回滚兜底（每次保存覆盖，只有一代）。`.tmp`／`.bak` 不属于任何路由，后续会被孤儿清理删除。

#### 6.8.2 单条保存的步骤与失败窗口

以 `保存实体` 为例（属性槽、通用配置同构）：

```
[1] 重名检查（仅内存，按原始 type 比较）
[2] target_path = "config/entities/" + 文件名清理(type) + ".json"
[3] 若 cfg.config_path 非空且 != target_path：rename(旧文件 → target)
[4] cfg.config_path = target_path
[5] 序列化 + 原子写入 target
[6] 路由同步：按 config_path 匹配条目 → 更新 config_path；匹配不到 → 追加 {module, config_path}
[7] 原子写入路由文件
```

失败窗口分析：

| 失败点 | 磁盘状态 | 内存状态 | 后果 |
| --- | --- | --- | --- |
| [2]/[3] 迁移失败 | 旧文件未改名 | 未改 `config_path` | 一致，用户可重试 |
| [4] 之后、[5] 失败 | 若发生迁移，旧文件已被改名成 target，target 仍是旧内容（新建实体则 target 不存在） | `config_path` 已改成 target | 旧路径已消失而路由仍指向它（死条目）；target 成为未被路由引用的孤儿；下次加载跳过旧条目 |
| [5] 成功、[7] 失败 | target 与 `.bak` 已写 | `route_json` 已更新 | 磁盘路由未变，重启后新配置不可见，旧条目指向不存在的旧文件 |

路由同步按**新** `config_path` 匹配旧条目，是 `type` 改名场景的核心缺陷：旧条目存的是旧路径，永远匹配不到，于是 `push_back` 追加一条新条目，旧条目原样保留。示例：`Slime.json` 改名为 `Slime_King.json` 保存后，`entity.json` 同时包含 `config/entities/Slime.json`（文件已不存在）与 `config/entities/Slime_King.json`；下次加载前者被计入跳过数，后者正常加载。多次改名会持续累积死条目【待确认：2】。属性槽的 `保存属性槽` 与通用配置的 `保存通用配置` 有完全相同的写法。

#### 6.8.3 重名检查与文件落点的错位

重名检查比较的是内存里的**原始** `type`／`条目名`，而落盘路径使用**清理后**的名字。两个不同实体名若清理后相同（例如 `A/B` 与 `A:B` 都变成 `A_B`），重名检查都会通过，后保存的实体会覆盖先保存的文件，路由出现两条指向同一路径的条目；`保存全部` 的遍历顺序决定最终内容。同理，若磁盘上已存在同名文件但未登记路由，保存会静默覆盖它（`rename` 与原子写入均可覆盖），没有“目标已存在”检查【待确认：22】。

#### 6.8.4 保存全部与关闭确认

`保存全部()` 不做任何批量事务：逐条保存、逐条写路由，任一条失败只累加失败计数并记录首个错误；已成功的条目不会回滚。它把所有实体、所有属性槽、所有通用配置都当成“脏数据”重新序列化写盘，即便用户只改了一个字段：结果是所有文件都被重写一次、`.bak` 全部刷新、所有 `config_path` 与“清理名”不一致的旧文件被批量改名。文件数量多时保存耗时线性增长，且每次保存都产生一次 `.bak` 复制。

关闭确认窗口的“保存并退出”在调用 `保存全部()` 后**无条件**把 `关闭已确认` 置 true，`保存全部` 的失败数不会阻止退出，可能丢失未写成功的修改【待确认：9】。该窗口的关闭按钮（`&显示关闭确认`）只把窗口隐藏，不会退出，也不会清掉 `关闭请求`（该请求已在 `渲染()` 中消费），因此用户点 × 关确认窗后继续编辑是安全路径。

#### 6.8.5 保存与校验脱钩

三个保存接口都不调用 `校验`，UI 的保存按钮也不检查校验结果。也就是说红色错误（如 `acls` 为空）不会阻止保存；下一步加载时引擎会拒绝该配置。这是“编辑器不替用户做最终裁决”的取舍，代价是错误配置可以落盘，需要用户自行阅读校验区。

### 6.9 编码、路径与安全

1. 项目默认 UTF-8；数据层所有 `std::string` 路径都视为 UTF-8（相对 `assets/` 的正斜杠路径）。写入 `std::filesystem::path` 前统一走 `utf8_path`（逐字节转 `char8_t` 再构造 `u8string`），读出时用 `path_utf8`（`u8string()` 逐字符转回）。
2. 生成的文件名走 `文件名清理`：把 `\ / : * ? " < > |` 全部替换为 `_`，删首尾空格／制表符，空名回退 `"未命名实体"`。它**不处理** Windows 保留名（`CON`、`NUL`、`PRN` 等）与结尾点号，因此极端名字仍可能落盘失败，失败会由原子写入的 `error` 反馈到状态栏。
3. 图片文件名走另一套 `实体图片文件名清理`：只保留 ASCII 字母数字、`_`、`-` 与所有高位字节（中文），其余替换 `_`，空名回退 `"entity"`。两套清理规则不同，同一个 `type` 在 `config/entities/` 与 `UI/entity_images/` 下可能得到不同文件名【待确认：15】。
4. `加载实体图片` 用 `绝对路径.string().c_str()` 传给 stb；`.string()` 在 Windows 上把宽字符路径转成本地 ANSI 窄串。中文文件名在中文代码页下可用，但超出当前代码页的字符（如带 emoji 的实体名）会转换失败，图片加载不到。整条配置链路其它位置都刻意使用 `utf8_path`，此处是例外（推测：依赖运行环境代码页）。
5. 路由路径安全检查只有“以 `config/` 开头”和“不含 `..`”两条。反斜杠写法（`config\entities\x.json`）会因前缀不匹配被拒绝；`config/./entities/x.json` 能通过前缀检查且不含 `..`，之后由文件系统解析为合法路径，没有额外规范化。
6. `nlohmann::json::dump` 未传 `ensure_ascii=false`，中文以 `\uXXXX` 转义写入（见 6.2.4）。
7. 三个头文件（`配置编辑器.h`、`配置编辑器_内部工具.h`、`实体配置模型_内部工具.h`）以及各 `.cpp` 的 `#include` 均写成 `Engine/EngineSystem/src/gui/Config_Editor/…`，而快照内文件实际位于 `Application/Editor/src/Config_Editor/…`，且快照的 `Engine/EngineSystem/src` 下没有 `gui` 目录。若真实工程没有同名的 include 目录映射，这些包含无法解析【待确认：1】。
8. `实体配置模型.h` 直接使用 `nlohmann::json`，但只包含 `Engine/EngineSystem/common/前置头文件包含.h`；该预编译头在快照中只包含 EngineFoundation 版本与 `<sol/sol.hpp>`，两者都没有引入 `<nlohmann/json.hpp>`。当前可编译性依赖构建系统的额外 include 或 PCH 配置，快照内没有找到引入点【待确认：20】。

### 6.10 错误处理与状态消息

1. **异常不越过文件边界**：JSON 解析、路由读取、格式读取、原子写入都包 `try/catch`；`解析实体配置`／`解析属性槽配置` 只对“顶层非对象”返回 false，其余字段类型不符一律静默清空，不产生 `error` 文案（`error` 参数在加载路径中实际未被使用）。
2. **批量加载以“跳过”代替失败**：损坏条目、缺失文件、解析失败都只增加计数，由 `配置编辑器::加载()` 读 `获取上次跳过数()` 拼进 `加载消息`，同时用 `std::printf` 打印 `[ConfigEditor] 加载完成：实体 …、属性槽 …、格式 …、通用配置 …；帮助窗口初始=…`。
3. **状态消息单槽覆盖**：`状态消息` 被保存结果、删除结果、上传结果、创建结果、校验提示共用；后续操作会覆盖前一条。加载失败时 `加载消息` 与 `状态消息` 被写成同一句，状态栏会同时显示两份相同信息。
4. **图片元数据加载失败会覆盖加载消息**：`配置编辑器::加载()` 先写 `状态消息.clear()`，随后若 `加载实体图片表` 失败则把 `error` 写入 `状态消息`；这不会阻断配置加载，只是档案页会显示占位图。
5. **没有全局错误弹窗**：除孤儿清理窗口用 `TextWrapped` 展示扫描／删除失败原因外，所有失败都通过状态栏一句话反馈，用户可能错过。
6. `main()` 无条件调用 `SetConsoleOutputCP(CP_UTF8)` 与 `SetConsoleCP(CP_UTF8)`，但 `配置编辑器主程序.cpp` 并未包含 `<windows.h>`，只能依赖间接包含；在非 Windows 目标上这两个符号不存在，程序无法编译【待确认：21】。
7. 字体加载失败仅打印警告并继续显示（中文呈方块）；图片加载失败打印 `stbi_failure_reason()`（可能为空，用“未知错误”兜底）并回退占位文本／字符画。

### 6.11 资源生命周期与缓存

1. **GL 纹理**：帮助图与封面图各一张，首次使用时创建，之后不再释放（`帮助图片已尝试`／`封面图已尝试` 保证只尝试一次）；实体图片每个 `type` 一张，上传替换时删除旧纹理。程序退出依赖 `ImGui_ImplOpenGL3_Shutdown`／`glfwDestroyWindow` 释放上下文，没有显式遍历删除。
2. **F5 重新加载不清纹理缓存**：`配置编辑器::加载()` 会重建仓库集合与 `实体图片表`，但不会清空 `实体图片纹理表/宽表/高表`。若外部修改了 `entity_image.json` 或替换了图片文件，重新加载后档案页仍显示旧纹理，必须重启或重新上传才能刷新【待确认：19】。
3. **图片元数据表随加载重建**：`加载实体图片表` 开头 `实体图片表.clear()`，失败时也保持空表，不会留半份旧数据。
4. **脚本列表是快照**：`加载()` 与“刷新”按钮各扫描一次 `assets/scripts`；新增脚本不会自动出现，需要手动刷新。
5. **函数级静态状态**：`渲染梦幻背景()` 的 80 颗星光与 `已播种` 只初始化一次，种子固定为 20260814；`本帧有编辑失焦` 是命名空间级全局，`渲染()` 每帧消费后清零，不存在跨帧泄漏（除非当帧未调用 `渲染()`）。
6. **没有长期持有的文件句柄**：所有 `ifstream`／`ofstream` 都在函数作用域内析构；`原子写入文件` 的临时文件失败时会显式 `remove`。

### 7.1 链路一：进程启动 → 打开配置 → 编辑实体 → 保存落盘

#### 7.1.2 `编辑器.加载()` 的展开

1. `仓库.加载()`：
   - 清空 `实体集合`、`route_json`、`属性槽集合`、`property_route_json`，`上次加载跳过数 = 0`；
   - `读取路由()`：读 `assets/config/route/entity.json`，失败则 `加载()` 返回 false，跳到步骤 2；
   - 遍历 `route_json`，对每条执行 6.1 的八步校验；成功者 `解析实体配置` → 填 `config_path` → 压入 `实体集合`；
   - `读取属性槽路由()`：失败则跳过属性槽（不致命）；成功则用同一套八步校验 + `解析属性槽配置` 填充 `属性槽集合`；
   - 清空 `格式集合`、`通用配置集合`、`自定义路由表`，调 `加载格式()`：`确保内置格式()`（缺失则写种子，契约不一致则覆盖升级）→ 枚举 `format/*.json` 排序读入；
   - 遍历非内置格式，调 `加载模块通用配置(fmt)`：读 `custom_<模块>.json` → 逐条八步校验 → `字段值 = data`、`条目名 = 提取条目名(...)`（失败用文件名 stem）→ 压入 `通用配置集合`；返回跳过数累加到总跳过数。
2. `仓库.加载实体图片表(error)`：文件缺失视为空表；失败把 `error` 写到 `状态消息`（不阻断）。
3. `脚本列表 = 仓库.获取脚本列表()`：递归扫描 `assets/scripts/*.lua`，相对路径 + 正斜杠 + 排序。
4. `选中索引 = -1`；写 `加载消息`（实体数、属性槽数、跳过数）；`printf` 输出四项计数与帮助窗初始状态。

#### 7.1.3 打开配置的三条路径

- **路径 A（档案浏览）**：`渲染()` → `渲染主界面()` → “实体配置”卡被点 → `切换页面(编辑页面::实体档案列表)`（两个选中索引清 -1）→ 下一帧 `渲染实体档案列表()` 列出全部实体卡（搜索过滤 `配置.type.find(搜索文本)`）→ 点卡片执行 `选中索引 = i; 当前页面 = 编辑页面::实体档案详情;`（这里直接赋值，没有走 `切换页面`，因此 `选中通用配置索引` 不会被清）→ 下一帧 `渲染实体档案详情()` 用 `实体集合[选中索引]` 绘制档案、`加载实体图片(配置.type)` 懒加载纹理。
- **路径 B（模块直编）**：主界面第二张卡 → `返回目标页面 = 主界面` → `切换页面(模块配置编辑)` → 左栏 `渲染新建配置区()` + `渲染模块列表()`，默认 `当前模块 = "Entity_Manager"` → 列表 Selectable 置 `选中索引` → 右栏 `渲染模块面板()` → `渲染属性面板()`。
- **路径 C（档案条目跳转）**：档案详情底部“实体管理器配置”卡 → 记录 `子页面返回实体类型 = 配置.type`、`当前模块 = "Entity_Manager"`、`返回目标页面 = 档案详情` → `切换页面(模块配置编辑)` → **在切换之后**再按 type 线性查找设 `选中索引`（因为切换会清索引）。

#### 7.1.4 编辑实体

`渲染属性面板()` 每帧执行：

1. 头部 `Text` 显示 `cfg.type` 与 `cfg.config_path`；
2. `输入文本("##type", cfg.type)`：用户键入期间直接改写内存 `type`；失去焦点那一帧 `本帧有编辑失焦 = true`，`渲染()` 末尾把 `有未保存修改 = true`；
3. `渲染脚本选择器("##decision_path", cfg.decision_load_path)`：文本框同上；下拉选择直接写 `path` 并立即置 `有未保存修改`；
4. `渲染权限列表(cfg)` / `渲染事件列表(cfg)`：每行的输入框同样走 `输入文本`；“+ 添加”与删除按钮立即改 vector，但不置脏；
5. 折叠区“校验结果”展开时 `渲染校验结果(cfg)` → `仓库.校验(cfg, errors, warnings)` 实时计算，只影响显示，不回写数据。

#### 7.1.5 保存落盘

用户按 Ctrl+S 或菜单“保存当前配置”：

```
渲染() → io.KeyCtrl && IsKeyPressed(ImGuiKey_S
        → 保存当前选中()
           → 当前模块 == "Entity_Manager"
              → 选中索引合法
                 → 仓库.保存实体(实体集合[选中索引], error)
                    → [1] type 非空 + 与其他实体不重名
                    → [2] target = config/entities/<文件名清理(type)>.json
                    → [3] config_path 不同则 rename 旧文件
                    → [4] config_path = target
                    → [5] 序列化四字段 → 原子写入文件（tmp/bak/rename）
                    → [6] 按 config_path 匹配 entity.json → 更新或追加
                    → [7] 原子写入 entity.json
                 → 成功：状态消息 = "已保存：" + config_path；有未保存修改 = false
                 → 失败：状态消息 = "保存失败：" + error；脏标记保持 true
```

若用户改的是 `type`，第 [3] 步把旧文件改名、第 [5] 步写入新内容、第 [6] 步因匹配不到旧条目而追加新条目（旧条目残留，见 6.8.2）。若用户点的是属性面板里的“保存当前实体”按钮，走同一个 `仓库.保存实体`，但**不清脏标记**，因此之后点窗口 × 仍会看到“还有未保存的修改”。

关闭链路：点窗口 × → GLFW 回调 `窗口关闭回调` → `请求关闭窗口()` 置 `关闭请求`，同时 `glfwSetWindowShouldClose(FALSE)` 拦截 → 下一帧 `渲染()` 消费：`有未保存修改` 为真则 `显示关闭确认 = true`，否则 `关闭已确认 = true` → 若弹窗，“保存并退出”调 `保存全部()` 后无条件置 `关闭已确认`／“直接退出”直接置位／“取消”只关窗 → 主循环检查 `应关闭窗口()` 调 `glfwSetWindowShouldClose(GLFW_TRUE)` → `while` 退出 → `ImGui_ImplOpenGL3_Shutdown` → `ImGui_ImplGlfw_Shutdown` → `ImGui::DestroyContext` → `glfwDestroyWindow` → `glfwTerminate`。

### 7.2 链路二：格式（format）定义如何驱动面板生成

#### 7.2.1 从格式定义到可选模块

1. `加载格式()` 结束后，`格式集合` 至少含两个内置格式。`构建模块候选(候选, 标签)` 把每个 `配置格式` 的 `模块名` 塞进候选，标签加“（内置）”后缀；`渲染新建配置区()` 与 `渲染模块列表()` 共用这份候选，内置与自定义模块因此出现在同一个下拉里。
2. 若 `格式集合` 为空（异常情况），`构建模块候选` 兜底只给 `Entity_Manager（内置）`，避免下拉越界；`渲染新建配置区` 与 `渲染模块列表` 都先检查 `新建模块`／`当前模块` 是否仍在候选内，不在则回退 `候选.front()`。

#### 7.2.2 新建自定义模块及其配置

1. `渲染格式管理窗口()` 左栏输入模块名 → “创建并添加”构造 `配置格式`：`配置目录 = "custom/" + module`、`路由文件名 = "custom_" + module + ".json"`、`内置=false`、字段列表仅一个 `type`（文本、必填、显示名“type（条目标识）”）。
2. `保存格式(fmt, error)`：非内置 → 写 `format/<清理名>.json`（`module`／`dir`／`route`／`builtin`／`fields`）→ `查找格式` 命中则替换内存项，否则追加。下一帧 `构建模块候选` 即能看到新模块。
3. 切到“模块配置编辑”子页面（或停留在该页），把“当前模块”切到新模块 → 左栏列表为空（还没有配置）。
4. 在“新建配置”区选择该模块、输入条目名、点“创建配置”：
   - `仓库.查找格式(新建模块)` 必须命中；
   - `cfg.字段值 = 仓库.生成默认字段值(*fmt)`：文本／脚本 → `""`，文本列表／事件对 → `[]`，整数 → 0，浮点 → 0.0，布尔 → false；
   - 若 `字段值` 含字符串 `type`（或 `name`），把条目名写进去；
   - `新建通用配置` 生成路径 `config/custom/<清理模块名>/<清理条目名>.json`，原子写入默认骨架，读 `自定义路由表`（没有则建空数组）追加 `{"module": 模块名, "config_path": …}` 并原子写 `route/custom_<清理模块名>.json`，最后压入 `通用配置集合`；
   - UI 置 `当前模块 = 新建模块`、`选中通用配置索引 = 集合末尾`。
5. 下一帧 `渲染模块列表()` 过滤 `cfg.模块名 == 当前模块`；`渲染模块面板()` 因模块不是两个内置名而走 `渲染通用配置面板()`。

#### 7.2.3 字段定义如何生成控件

`渲染通用配置面板()` 先 `查找格式(cfg.模块名)`，找不到就只显示“模块格式不存在”；找到则调 `渲染通用字段编辑器(cfg, *fmt)`，对 `fmt.字段` **顺序遍历**：

```
for f in fmt.字段:
    if !cfg.字段值.contains(f.字段名): cfg.字段值[f.字段名] = 生成默认值(f)
    标签 = f.显示名.empty() ? f.字段名 : f.显示名
    switch f.类型:
        文本     → 输入文本(临时 value) → 改动时写回
        脚本路径 → 渲染脚本选择器(临时 value) → 每帧写回
        文本列表 → JSON→vector → 行内输入/删除/添加 → 重建数组写回
        事件对列表 → JSON→vector<pair> → 行内双输入/删除/添加 → 重建二维数组写回
        整数     → InputInt  → 改动写回 + 置脏
        浮点数   → InputFloat→ 改动写回 + 置脏
        布尔     → Checkbox  → 改动写回 + 置脏
    输出 "(必填/可选) 说明"
```

因此“格式里加一个字段”在下一次渲染就会自动出现对应控件，无需改表现层代码；字段顺序就是控件顺序。校验侧同样是遍历 `fmt.字段`，按同一 `f.类型` 分支判断，所以“控件类型”和“校验规则”天然一致。

#### 7.2.4 格式变更与已存在配置的交互

- 格式管理里给已有模块新增字段：`保存格式编辑()` → `仓库.保存格式` 覆盖 `format/*.json` 与内存 `格式集合[*]`；已有通用配置的 `字段值` 没有该键，`渲染通用字段编辑器` 首次渲染时补默认值并写回内存（不置脏）。
- 删除字段：`格式编辑.字段.erase` 后保存，旧配置里的该键不会删除，作为“格式外键”继续保留；保存配置时整份 `字段值` 写回，因此该键会继续留在磁盘。
- 字段改名：新键缺失被补默认值，旧键仍在；面板只显示新键，旧数据不可见但不会丢。
- 删除格式：`删除格式` 会删除 `config/custom/<清理名>/` 整目录与路由，`当前模块`／`新建模块` 若正指向该模块则回退 `Entity_Manager`；内存 `通用配置集合` 中该模块的条目一并移除，`格式编辑有效` 置 false。
- 内置格式在格式管理窗口里字段名、类型、必填、说明全部只读，删除与保存按钮不出现；`保存格式` 与 `删除格式` 在数据层也二次拦截，避免绕过 UI 修改。

### 7.3 链路三：图片引用的解析与写回

#### 7.3.1 写回链路（上传）

触发点：档案详情页图片框底部“上传图片”按钮（`渲染实体档案详情()` 内）→ `上传实体图片(配置.type)`：

1. `GetOpenFileNameW` 返回源路径（用户取消则直接返回，状态栏不变）。
2. `is_regular_file(源路径)` 校验；`create_directories(assets/UI/entity_images)`。
3. `扩展名 = 源路径.extension().string()`；`清理名 = 实体图片文件名清理(type)`；
   `目标路径 = assets/UI/entity_images/<清理名><扩展名>`。
4. `copy_file(源路径, 目标路径, overwrite_existing)`；失败写“复制图片失败：<ec.message()>”并返回。
5. `仓库.设置实体图片(type, "UI/entity_images/<清理名><扩展名>")`（内存表）。
6. `仓库.保存实体图片表(error)` → 重建整表 JSON → `原子写入文件(assets/config/entity_image.json, dump(4))`；失败写“图片已复制但元数据保存失败：…”并返回。
7. 成功后：找到 `实体图片纹理表[type]`，非 0 则 `glDeleteTextures`，从三张表 `erase(type)`，再 `加载实体图片(type)` 立即重建纹理；写状态消息“已设置实体图片：UI/entity_images/…”并 `printf` 日志。

写回的是“相对 `assets/` 的路径”，不是绝对路径；元数据与实体 JSON 完全分离，保存实体配置不会触碰图片表。

#### 7.3.2 解析链路（显示）

1. `配置编辑器.加载()` 调 `仓库.加载实体图片表(error)`：`实体图片表.clear()` → 文件不存在返回 true（空表）→ 解析校验 → 逐条字符串值入表。
2. 档案详情页每帧调 `加载实体图片(配置.type)`：
   - 查 `实体图片纹理表`，命中（含 0）直接返回 `纹理 != 0`；
   - 未命中则 `相对路径 = 仓库.获取实体图片(type)`；
   - 空串 → 记 0，返回 false（显示“暂无图片 点击下方按钮上传”）；
   - 非空 → `绝对 = 仓库.资源目录() / utf8_path(相对路径)`；不是常规文件 → 记 0；
   - 是文件 → `stbi_set_flip_vertically_on_load(false)` → `stbi_load(绝对.string().c_str(), &宽, &高, &通道, 4)`；
   - 解码成功 → `glGenTextures`／`glBindTexture`／`glTexParameteri`（`MIN/MAG=LINEAR`、`WRAP_S/T=CLAMP_TO_EDGE`）／`glTexImage2D(GL_RGBA, …, GL_UNSIGNED_BYTE, 像素)`／解绑／`stbi_image_free`；
   - 无论成败，`纹理/宽/高` 写入三张表并返回。
3. 成功时用 `实体图片宽表[type]`／`高表[type]` 计算等比缩放（可用区 126×128），`绘制圆角图片(画布, (ImTextureID)(intptr_t)纹理, 左上, 右下, 8.0f)` 绘制阴影 + 圆角图 + 1.5px 边框；失败时显示占位文字。

#### 7.3.3 典型问题链路

- **改 type 后图片丢失**：档案页 `输入文本("##档案类型编辑", 配置.type)` 改 type → “保存档案” → `保存实体` 迁移 JSON 与路由，但 `entity_image.json` 的键仍是旧 type → 新 type 调 `获取实体图片` 返回空 → `加载实体图片` 记 0 → 显示占位。旧映射与旧图片文件都残留【待确认：7】。
- **F5 后图片不刷新**：外部替换实体图文件或修改 `entity_image.json` → F5 `加载()` 重建 `实体图片表`，但 `实体图片纹理表` 保留旧纹理，`加载实体图片` 因命中缓存直接返回旧纹理【待确认：19】。
- **同名清理冲突**：两个实体 type 清理后同名（如 `A/B` 与 `A:B`）→ 第二次上传覆盖第一次图片文件；两者元数据指向同一路径，档案页显示同一张图。

【待确认：23】主界面标题缩放未生效。`渲染主界面` 用 `SetWindowFontScale(1.6f)` 设置缩放，但标题通过 `ImDrawList::AddText(ImGui::GetFont(), ImGui::GetFontSize(), …)` 直接绘制；`AddText` 使用显式传入的 `GetFontSize()`（基础字号），不叠加窗口字号缩放，因此标题实际未放大，只有其位置按基础字号计算。

【待确认：24】投影层透明度注释与公式相反。`core/配置编辑器_视觉.cpp` 的 `绘制投影卡片` 注释写“外层更淡、内层稍深”，但循环从 `层 = 阴影层数` 递减到 1，`比例 = 层 / 阴影层数`，`alpha = 28 * 比例²`，扩展距离与 alpha 都随循环递减：最外层 alpha 为 28（最深）、最内层约为 2（最淡）。实际观感是外扩阴影比内层更深，与注释描述相反。

【待确认：25】孤儿清理窗口在“扫描”阶段就已删除文件。`渲染孤儿清理窗口` 首次打开时调用 `仓库.清理孤儿配置(孤儿清理列表, error)`，而该 API（`core/实体配置模型_格式.cpp`）在收集引用集合后就立即 `std::filesystem::remove` 所有未引用文件并把结果写入列表；因此窗口展示的其实是“已删除文件清单”，随后“确认删除”按钮二次调用同一 API 通常只能返回 0。界面要求用户“确认这些文件确实不再需要”后才删除，与实现的“打开即删除”不符。
