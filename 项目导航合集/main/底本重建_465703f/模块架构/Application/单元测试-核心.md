# 单元测试-核心模块

本文件覆盖 `Application/Test/tests` 下 Foundation、System 两套测试子工程中的核心测试源码：引擎基础层（日志、路径、配置、对象池、事件、四叉树、加载器、坐标、计时器等）与系统层（碰撞、输入、关卡文本）的用例、薄入口、注册锚与共享夹具。范围不含 Renderer 子工程、Test 层主调运行器与图形界面。

## 二、模块功能介绍

### 2.1 定位

本模块是“白银纪元”引擎的引擎侧单元测试执行体。它把 EngineFoundation（基础层）与 EngineSystem（系统层）的公开接口行为固化成可重复执行的 gtest 用例，并以两套彼此独立的可执行程序 `TestFoundation.exe`、`TestSystem.exe` 交付。它属于 Application/Test 测试层，不属于引擎本体；引擎源码只作为被测对象经版本锁接入。

### 2.2 负责什么

- 逐模块覆盖基础层工具与核心设施：路径/字符串转换、路径可用性、JSON 字段校验、数据校验、二分查找、哈希混合、计时器、随机数、数值池、日志系统、OBJ/MTL/glTF 加载器、坐标类型、对象与对象池、配置加载器、四叉树与四叉树管理器、事件结构/事件中转器/事件终端。
- 逐模块覆盖系统层：碰撞体/碰撞空间/碰撞代理器/碰撞后端/碰撞响应、输入焦点与输入组合、关卡文本读写与材质实例 CRUD。
- 固化“失败即清空输出”“非法输入被拒”“重复操作幂等或失败”“ID/索引复用”“跨帧延后生效”等隐式契约，使后续重构有可回归的判定基线。
- 为每层提供一条最小执行路径（薄入口）与一条链接期完整性保险（注册锚），避免出现“用例没跑但测试通过”的静默漏跑。

### 2.3 不负责什么

- 不做渲染层用例（`tests/Renderer` 由另一模块文档覆盖），不创建任何 GPU 资源、不初始化窗口与交换链。
- 不做 Test 层主调逻辑（图形选择器、层级版本新鲜度、gtest 输出镜像、测试运行器），也不做面向用户的交互式测试编排。
- 不读取 `Application/Test/assets` 下的编辑器配置与 Lua 脚本；本模块所有输入要么来自被测头文件中的常量，要么由用例在同一用例生命周期内写入临时文件并在结束时清理。
- 不修改引擎源码；发现引擎缺陷时以用例断言固化“当前应有行为”，或在注释中记录规避手段。
- 不承担性能基准；仅少量用例（大量分配、1024 对象、2000 条日志、4 线程 400 行）用于稳定性与并发正确性，不作为耗时门槛。

### 2.4 两套子工程为什么分开

Foundation 子工程的说明写明：只测 EngineFoundation 一层的静态库 + 薄入口；改基础层的人只需构建本子工程即可验证，不必等 System/Renderer 的测试库编过。System 子工程同时接入 Foundation 与 System 两层，先解析 Foundation 再解析 System，因为后者的全链一致性校验要读前者的版本记录。两套子工程各自编一份 googletest（`BUILD_GMOCK OFF`、`INSTALL_GTEST OFF`、`gtest_force_shared_crt ON`），测试静态库本身不内嵌 gtest 目标。

### 2.5 为什么需要薄入口

若直接链接 `gtest_main`，测试二进制仍会依赖静态库成员的静态注册对象；链接器会丢弃未被任何符号引用的 `.obj`，`TEST`/`TEST_F` 的静态注册随之消失，表现为“用例数量变少但不报错”。本模块的做法是：

1. 用例与注册锚编成静态库（`TestFoundation` / `TestSystem`）；
2. 可执行目标以 `$<LINK_LIBRARY:WHOLE_ARCHIVE,...>` 整体收编该库；
3. 薄入口在 `RUN_ALL_TESTS()` 之前显式调用注册锚函数，使“库未被整体收编”退化为链接失败，而不是静默漏跑。

### 2.6 关键约束

- 被测层只经版本锁接入：`Engine/版本锁.cmake` 留空则跟随该层最新构建树；填哈希则取 `Engine/版本缓存/<层>/x64-<配置>/<哈希>/` 的冻结副本。子工程只读版本锁，绝不改写。
- 头快照校验先于编译：`byjy_ceshi_tou_jiaoyan` 扫描本子工程源码里对已接入层的 `#include`，要求每个头都能在下层头快照中找到；下层新增/重命名公共头却未重建时，配置阶段直接失败，而不是到编译期才暴露。这一机制使本测试模块天然成为“测试与源码接口一致性”的探测器。
- 用例以公开头为入口，绝大多数文件只包含被测模块的对外头/运行包；碰撞后端用例显式声明“仅经后端公共接口覆盖，不包含任何后端内部头”。
- 测试源码按 UTF-8 编译（MSVC `/utf-8`），用例名使用中文，运行前把控制台输入/输出代码页切到 UTF-8。

### 2.7 规模

33 个用例 `.cpp`（Foundation 23、System 9，另加 2 个薄入口与 2 个注册锚），共 667 个 `TEST`/`TEST_F` 用例。其中 Foundation 564 个、System 103 个；用例最多的文件为四叉树测试（44）、四叉树管理器测试（43）、坐标类型测试（40）、对象池测试（33）、事件中转器测试（33）。

## 三、模块公开接口 —— 测试套件的组织契约

本模块的“公开接口”不是被测引擎函数，而是测试套件对构建系统与 gtest 的注册契约：薄入口如何启动、注册锚如何保命、用例如何进入注册表、套件与用例如何命名、运行参数如何生效，以及每个文件覆盖了哪个被测模块的哪组用例。

### 3.1 薄入口契约

两套薄入口结构一致，仅注册锚函数名不同：

```cpp
int main(int argc, char** argv)
{
    ::SetConsoleOutputCP(CP_UTF8);
    ::SetConsoleCP(CP_UTF8);
    ::testing::InitGoogleTest(&argc, argv);
    byjy_test_anchor_foundation();   // System 为 byjy_test_anchor_system()
    return RUN_ALL_TESTS();
}
```

契约要点：

1. 不链接 `gtest_main`，`main` 由薄入口自行提供；否则注册锚调用点不存在，整体收编保险失效。
2. `InitGoogleTest` 必须在注册锚调用与 `RUN_ALL_TESTS` 之前完成，因为 `--gtest_filter`、`--gtest_list_tests` 等参数在用例枚举前生效。
3. 注册锚调用位于 `InitGoogleTest` 之后、`RUN_ALL_TESTS` 之前；顺序不影响注册，但放在执行前使“链接失败”尽早暴露。
4. 控制台代码页切 UTF-8 使用 `<windows.h>` 的 `SetConsoleOutputCP`/`SetConsoleCP`，保证中文用例名与断言消息可读。
5. 返回值直接取 `RUN_ALL_TESTS()`；全通过返回 0，有失败返回 1（gtest 语义），不做二次包装。
6. 两个薄入口都只跑本层用例，不做层级选择、不做图形界面、不解析自定义参数。

### 3.2 注册锚契约

```cpp
extern "C" void byjy_test_anchor_foundation(void) { }   // Foundation
extern "C" void byjy_test_anchor_system(void) { }       // System
```

契约要点：

1. 函数体为空，唯一作用是“被引用”。薄入口以 `extern "C"` 声明并调用它，链接器因此必须把定义所在的目标文件纳入链接。
2. 定义与用例同处一个静态库（`src/注册锚.cpp` 被 `源文件列表_*.cmake` 显式列出），所以锚可达即证明库被整体收编。
3. 若 `WHOLE_ARCHIVE` 失效，锚定义不会被拉入，链接期报未解析外部符号；不会退化为“少跑一批用例”。
4. 锚不参与任何测试逻辑，不初始化全局状态，不注册监听器。

### 3.3 用例如何进入 gtest 注册表

- `TEST_F(Suite, Name)` 展开为一个继承 `Suite` 的测试类（类名由 gtest 拼接），其中重写 `TestBody()`；同时在该翻译单元产生一个静态注册变量，其初始化调用 `testing::MakeAndRegisterTestInfo(...)`，把“套件名 + 用例名 + 工厂 + 文件/行号”写入 `UnitTest` 单例的注册表。
- `TEST(Suite, Name)`（仅 `关卡文本测试.cpp` 使用）不产生夹具类，直接注册函数体。
- 这些静态变量的初始化发生在 `main` 之前的动态初始化阶段；因此“目标文件是否被链接”直接决定用例是否存在于注册表。
- `RUN_ALL_TESTS()` 遍历注册表，针对每个 `TestInfo`：`TEST_F` 先构造夹具对象，再依次调用 `SetUp()`、`TestBody()`、`TearDown()`，最后析构夹具；`TEST` 直接调用测试体。断言失败不抛出异常，而是记录到当前 `TestResult`，用例继续执行到下一个 `ASSERT_*` 或函数结束。
- 同一夹具名可以跨多个翻译单元复用（例如 `Collision_Proxy_Test` 同时出现在 `碰撞代理测试.cpp` 与 `碰撞响应测试.cpp`），gtest 以“套件名 + 用例名”为全局唯一键，因此跨文件不得出现同名用例。

### 3.5 运行参数与退出语义

- 入口只调用 `InitGoogleTest`，因此 gtest 原生参数全部可用：`--gtest_filter=套件.用例`、`--gtest_list_tests`、`--gtest_repeat=N`、`--gtest_shuffle`、`--gtest_output=xml:<路径>`、`--gtest_break_on_failure` 等。

- 子工程没有自定义命令行开关、没有环境变量约定、没有配置文件入口；所有测试输入由用例自行构造。

### 3.7 套件边界与重名约束

- `Collision_Proxy_Test` 是唯一跨两份翻译单元复用的夹具；两份文件用例名无交集，满足 gtest 的全局唯一键约束。
- `Collider_Test` 只在 `碰撞测试.cpp` 使用；`Collider_Move_Test` 是 `碰撞体测试.cpp` 为避免与前者重名而另立的独立夹具（文件内注释写明“独立夹具名，避免与其余套件重名”）。
- `EngineSystem_LevelText_Test` 使用 `TEST` 而非 `TEST_F`，因为被测函数是无状态自由函数，不需要夹具。
- 每个 `.cpp` 内可出现多个夹具（`碰撞测试辅助.h` 声明三个、`碰撞体测试.cpp` 定义一个），但同一夹具的用例必须唯一。

### 4.4 资源构造与清理的调用契约

1. 临时文件一律先构造父目录再写入；`关卡文本测试` 的 `write_text` 显式 `create_directories`，其余临时路径的父目录由源码树本身提供（可执行文件目录为 `Application/Test`，其下存在 `tests/Foundation/src/工具`、`tests/System/src/碰撞`）。
2. 删除文件一律带 `std::error_code`，不让清理失败升级为测试失败；但日志探针的删除依赖先释放文件流，否则 Windows 下句柄占用导致删除静默失败。
3. 临时文件在用例内清理（`mesh_remove`/`mtl_remove`/`gltf_remove`/`log_remove_all`/`remove_all`），失败路径同样执行清理；异常中断时可能残留，故 `Log_Test::SetUp` 会先清理上一轮残留。
4. 夹具成员对象按声明顺序构造、逆序析构；碰撞体/碰撞空间的析构顺序由用例显式控制（`碰撞测试.cpp` 有“碰撞体先析构”与“碰撞空间先析构”两条用例）。

## 六、模块设计 / 实现细节

### 6.1 引擎环境隔离

1. 日志分流：Foundation 测试库把 `Application/Test/src/主调/引擎日志屏蔽.cpp` 直接编入（`CMakeLists` 显式 `add_library(TestFoundation STATIC ...)` 后再 `include` 源文件列表），使“屏蔽/恢复”成为测试基础设施，而不是主调程序的私有能力。屏蔽开启时把日志根节点 `""` 绑到 `out/引擎运行日志.txt`（相对可执行文件目录），全部调用处沿父链继承该流，不再落控制台兜底输出。屏蔽使用静态 `屏蔽已开启` 标志做幂等，重复调用不重复绑定。
2. 日志用例反向隔离：`Log_Test::SetUp` 调用 `engine::日志屏蔽_关闭()`，清除根节点绑定与根目录设置，使日志回落到控制台；`TearDown` 恢复 `引擎日志屏蔽_开启()`，避免其他套件的引擎日志混进 gtest 输出。若屏蔽文件打不开，`日志屏蔽_开启` 放弃屏蔽而不阻断测试（日志继续留在控制台）。
3. 控制台捕获：日志系统写 `std::cout` 对象本身，`Console_Capture` 直接替换其 `streambuf`，比 gtest `CaptureStdout` 更稳；后者在临时目录建 `.tmp`，本机临时目录含中文时窄字符 `fopen` 解析失败会 FATAL 打断整个用例进程。
4. 文件句柄顺序：`log_read` 先 `logger.stream_flush()` 再读文件（文件输出目标按阈值批量落盘）；`TearDown` 先 `stream_clear` 释放句柄，再删探针文件，否则 Windows 下删除失败。
5. 探针文件命名固定且集中在一个数组，`SetUp`/`TearDown` 双端清理；这使 `--gtest_shuffle` 与中途失败后重跑不会因残留文件误判。

### 6.2 配置与编辑器资源隔离

1. `Config_Loader_Test` 每个用例在可执行文件目录下创建独立的根目录（`可信根测试_添加`、`可信根测试_重复添加`、`可信根测试_重建`、`可信根测试_目录对`、`配置事件名测试_*`、`配置卸载测试`、`路由卸载测试`、`配置全卸载测试`、`非法卸载测试`），用例结束 `remove_all`；根目录名带用例语义，避免并行/重复运行时相互覆盖。
2. 配置加载器不被直连构造为“真实服务”：夹具在用例内自建 `Event_Broker`，把加载器 `event_terminal` 的 `Broker_Attacher`、`Evt_Sender`、`Evts_Sender` 三个端口绑到 broker，再 `loader.attach()`；订阅对象以固定 `acl_key=1` 登记，只用于接收投递，不参与真实终端鉴权。
3. 路由文件的脏标记是配置加载器的增量扫描依据；需要让后续扫描再次投递的用例显式调用 `route_file_reset()` 覆盖写回无脏标记初态（如“重复添加可信根被跳过”“路由加载仅认对象自身目录对”“可信根增量重建”）。
4. 编辑器资源：本模块不读取 `Application/Test/assets/config`（实体/属性/格式/路由 JSON）与 `assets/scripts`（Lua），也不初始化 `Config_Editor`。所有输入均为用例内构造的 JSON、OBJ/MTL/glTF 文本或关卡文本；因此编辑器资源缺失不会影响本模块。
5. 关卡文本用例的临时目录是 `out/关卡文本测试`（相对当前工作目录），不是可执行文件目录；`write_text` 自动建目录，读取/写出接口入参使用 UTF-8 窄字符串，落盘/读盘对比使用宽字符路径。该设计使文本层用例不依赖可执行文件位置，但要求运行时工作目录可写。
6. 碰撞用例的临时网格/边界文件放在 `tests/System/src/碰撞/...`（相对可执行文件目录），并以绝对路径传给加载器；注释明确“网格加载器按传入字符串原样打开，相对路径会随当前工作目录变化”，故夹具返回绝对路径。

### 6.3 随机与时间相关用例的确定性控制

| 来源 | 控制手段 | 断言口径 |
| --- | --- | --- |
| 随机数生成器 | 显式固定种子（12345、1、2、777、2024–2027、7、11、99、1234、555、321–327、8080、6060、326 等）；`init(seed)` 重置；不读取系统熵 | 同种子序列一致、不同种子有差异、区间上下界、覆盖集合大小、单点返回定值；不做“黄金数值”比对 |
| 关卡文本随机往返 | `std::mt19937 generator(20261103u)` + `uniform_real_distribution<float>` / `uniform_int_distribution<int>`，16 轮固定序列 | 写→读→再写逐字节一致、内存字段逐位一致；浮点以 `%.9g` 保证 32 位浮点可唯一还原 |
| 计时器 | `std::this_thread::sleep_for(5/10/15/20ms)`；只断言正间隔、单调不减、重置后小于累计值、单位换算的精确倍数 | 不做绝对耗时上限；`Milli_units >= 10.0` 是唯一“下界”断言，留出调度抖动余量 |
| 多线程日志 | 4 线程 × 100 条，固定线程号与序号；写内存流（`ostringstream`）而非文件 | 总行数 400、以 `[INFO]并发标记 ` 开头的完整行 400，验证行不交错 |
| 对象池/四叉树 | 固定数量（64/100/256/1024、16×16 区块、固定坐标） | 集合大小、ID 唯一性、区块中心、根坐标、边长 |
| 哈希混合 | 固定种子/输入；`SIZE_MAX`、最高位、零值等边界 | 同输入同结果、不同输入/种子/顺序不同、`noexcept` |

### 6.4 失败信息格式

1. 默认使用 gtest 的标准输出：`[  FAILED  ] 套件.用例` + 文件:行 + 期望/实际值；断言宏区分 `EXPECT_*`（继续）与 `ASSERT_*`（当前用例中止）。
2. 关卡文本测试额外以 `<<` 附加定位信息：`"写出失败：" << name`、`"读回失败：" << name`、`label << " 第 " << index << " 项不一致"`、`"非法文本被接受：" << name`、`"非法材质被接受：" << name`。这使批量循环中的失败能定位到具体文本/字段/下标。
3. 碰撞用例普遍先 `ASSERT_NE(receiver.data, nullptr)` 或 `ASSERT_TRUE(result.has_value())`，避免空指针/空 optional 继续解引用，把“未取到区块/未激活空间”转成清晰的断言失败。
4. 用例不使用自定义 `TestEventListener`、不改变 gtest 默认格式、不做彩色输出；控制台代码页 UTF-8 只影响中文显示，不影响 XML 输出。
5. 时间/日志类失败可能伴随引擎自身日志；Foundation 用日志屏蔽把引擎日志分流到文件，避免与 gtest 输出交织；需要查看时读取 `out/引擎运行日志.txt` 并调用 `日志屏蔽_落盘`。

### 6.5 与构建清单的对应关系

1. `源文件列表_TestFoundation.cmake` 用 `target_sources(TestFoundation PRIVATE ...)` 逐字列出 24 个 `.cpp`（23 个用例 + `src/注册锚.cpp`），头文件段为空（Foundation/src 下无用例头）。`源文件列表_TestSystem.cmake` 列出 10 个 `.cpp`（9 个用例 + `src/注册锚.cpp`），头文件段列出 1 个 `src/碰撞/碰撞测试辅助.h`。
2. 两份清单是“唯一源码加入点”：`CMakeLists` 的 `add_library` 不再传这些源文件，否则 Visual Studio 改名/迁移的 File API backtrace 会落到 `add_library`，无法改写引用。清单由 `Engine/EngineFoundation/cmake/生成源文件列表.cmake` 的 `byjy_source_list_sync` 在每轮配置时按 `file(GLOB_RECURSE)` 结果自动维护，禁止手工编辑。
3. 逐文件核对结果：本模块 37 个文件与两份清单完全对应，无遗漏、无多余；用例 `.cpp` 全部在 `src/` 下被 GLOB 覆盖，薄入口仅由 `add_executable` 直接编译（不进入静态库清单）。
4. Foundation 额外编入 `Application/Test/src/主调/引擎日志屏蔽.cpp`（不在 `tests/Foundation/src` 的 GLOB 范围内，故由 `add_library` 显式加入）；注释说明“主层不再重复编译它（避免同一符号两份）”。System 子工程不编入该文件，因为其用例不触碰日志屏蔽。
5. 包含根顺序：Foundation 为 `EngineFoundation 头快照 → 项目根 → Test 层根`；System 为 `EngineFoundation 头快照 → EngineSystem 头快照 → 项目根 → Test 层根`。Test 层根使用例可以 `#include "src/主调/引擎日志屏蔽.h"`。
6. 编译口径：`byjy_ceshi_zhunbei` 设置 C++20、`CMAKE_CXX_EXTENSIONS OFF`、导出编译数据库；MSVC 加 `/MP /utf-8` 与 `_CRT_SECURE_NO_WARNINGS`，`/WX-`（警告不阻断）；非 MSVC 加 `-Wall -Wextra -pedantic` 与 `_GNU_SOURCE`。Ninja + MSVC 时套用 `link_rsp_bom.ps1` 包装，避免中文对象名导致 LNK1104。
7. 链接：测试库 `PUBLIC EngineFoundation`（System 另加 `EngineSystem`），`PRIVATE GTest::gtest`；可执行目标 `PRIVATE "$<LINK_LIBRARY:WHOLE_ARCHIVE,TestFoundation>"` + `GTest::gtest`。gtest 由子工程各自 `add_subdirectory(external/googletest)` 编一份，`BUILD_GMOCK OFF`。
8. 输出：静态库落 `out/build/<配置>/lib`；可执行目标 `OUTPUT_NAME` 为 `TestFoundation` / `TestSystem`，`RUNTIME_OUTPUT_DIRECTORY` 为 `Application/Test`（`BYJY_TEST_ROOT`），因此用例中 `exe_dir_get()` 指向 `Application/Test`，临时相对路径 `tests/...` 恰好落在源码树内。
9. 头快照校验：`byjy_ceshi_tou_jiaoyan` 逐配置扫描已接入层的快照目录是否存在，并校验源码中的 `#include` 均可在快照中解析；若下层新增/重命名公共头而未重建，配置阶段直接 `FATAL_ERROR`。这也是本模块“接口一致性”的第一道防线。
10. 依赖版本记录：`byjy_ceshi_jilu` 把本次解析到的各下层版本写入构建目录的 `依赖版本.cmake`，供 Test 层图形界面判断“测试库是否用旧版下层编成”；本模块自身不读该文件。

### 6.6 容易误判的实现约定

1. 路径与编码：凡是含中文的路径，用例一律经 `engine::detail::string_to_path` 构造 `std::filesystem::path`，绝不直接用 `const char*` 拼 `filesystem::path`；写出/读入接口的入参用 UTF-8 `std::string`，落盘对比用宽字符 `std::filesystem::path`（关卡文本）。
2. 引擎环境的静态缓存：`exe_path_get()` 返回函数内静态对象的引用，`exe_dir_get()` 亦为静态；`引擎环境测试` 以“两次取址相同”固化该语义。测试不应在运行中改变可执行文件位置或期望其变化。
3. 绝对路径拼接的重载歧义：`absolute_path_get("assets")` 会因 `const char*` 同时可转 `path` 与 `string` 触发 C2668；用例显式构造 `std::string("assets")` 规避。这是接口设计的隐式约束，不是测试缺陷。
4. 网格顶点去重口径：同一组顶点在三种面写法（`v/vt/vn`、`v//vn`、`v/vt`）下按 `(v, vt, vn)` 组合去重；`三角网格与材质解析` 据此期望 9 个顶点、9 个索引，并以第三个面首索引为 6 验证分组边界。
5. `Vertex` 未定义相等算子：重复加载用例以 `std::memcmp(&a, &b, sizeof(engine::Vertex)) == 0` 比较，逐字节依赖结构体无填充差异；若以后给 `Vertex` 加 `operator==` 或改布局，此用例需同步调整。
6. 浮点相等口径：`Point2d` 相等允许 4 ULP，`Rect2d` 相等是逐分量精确比较（无 ULP 容差）；用例分别固化，不能互相套用。`ulp_distance` 对符号不同返回 `UINT64_MAX`，对相同无穷返回 0（先判 `lhs == rhs`）。
7. 对象池的 `size()` 与 `capacity()`：`size()` 是有效对象数，`capacity()` 是记录槽位数；`unload` 只清有效标记与 ID、记录留在容器中，故“卸载后记录保留但 ID 清零”同时断言 `capacity()==1` 与 `size()==0`。ID 0 为非法实体预留；`clear()` 后 ID 游标回到 1。
8. 数值池回绕口径：`next_number == numeric_limits<T>::max()` 即判定耗尽，首次分配直接回到 `min()`；因此 `set(UINT64_MAX)` 的首次 `get()` 返回 0，`set(UINT64_MAX-1)` 先返回 `UINT64_MAX-1`、下一次返回 0。回收池优先于游标，LIFO/FIFO 只影响回收池弹出顺序。
9. 四叉树的退化态：`set_block_size(9)` 因“须为 2 的幂”被拒，`state.block_size` 保持 0；此后 `get/seek/build` 一律安全返回（单点查询返回 false、范围为空）。用例把“配置被拒 + 操作安全空转”作为显式契约。
10. `Quadtree::set_max_size`/`set_block_size` 返回 `bool`；测试中部分调用忽略返回值（`make_tree` 直接调用），依赖固定参数必然成功；若以后参数校验加严，`make_tree` 需改为 `ASSERT_TRUE`。
11. 事件相等与哈希忽略 `sender`：`Event::operator==` 比较 `category/tag/receiver/config`；`std::hash<Event>` 同样不混入 `sender`。无序集合用例据此去重。
12. 事件中转器的定向投递：只要事件标识 `category/tag` 已在订阅表登记，定向事件就直达目标，不再向标签订阅者广播；目标未登记时直接丢弃（不回落广播）。发起者排除仅在发起者已登记且其密钥命中接收列表时生效。
13. `All` 是保留标签：以 `Input/All` 登记会对该分类全部已登记标签广播；直接投递 `tag=="All"` 的事件会被中转器丢弃。`事件中转器测试` 同时固化这两面。
14. 事件终端的密钥是单次生成：首次 `key()` 返回值，再次调用返回 `nullopt`；未生成密钥时 `send/clear/attach` 一律拒绝、`query` 返回 `nullptr`。用例以 0 与 `key+1` 两种错误密钥分别验证。
15. 配置加载器的构造即生成密钥：`Config_Loader` 构造体内 `event_terminal.key().value()`；因此夹具不需要显式生成密钥。条目事件名缺省回落为 `Config/Load`，且仅写 `event_category` 时 `event_tag` 独立回落 `Load`；条目命中预定义事件标识（`Config_File/Load`）会被驳回。
16. 碰撞代理器的位移持续生效：`ColliderDisplacement` 事件提交的位移不再一次性清零，连续检测会按 频率/步长 继续推进；碰撞响应 `stop` 置 `displacement_invalid`，`keep` 保持，`change` 改写位移。`碰撞响应测试` 用“第二次检测是否仍重叠/是否越过”区分三种响应。
17. 碰撞几何的失败保留：`Collider_Backend::geometry_build` 失败时保留当前已挂载几何（`非法几何不改变已挂载几何`），`geometry_mount` 成功后才替换；`geometry_clear` 后包围盒归零。
18. 关卡文本的默认值：只写少量行时其余字段取结构默认（相机 FOV `1.0472f`、光强 1.0、雾密度 0.0、点/聚光计数 0）；失败读取会清空输出为空关卡（名称空、版本 1、计数 0、无资产行、无材质）。
19. 关卡文本的写出前校验：路径非空、名称不含换行、版本 ≥ 1、全部浮点有限、材质数值在范围内；校验失败不落盘。材质 `update` 以关卡内名称为准，传入 `data` 的实例名被覆盖。
20. 碰撞临时文件的 JSON 转义：边界配置用 `nlohmann::json` 序列化写出绝对路径，避免手拼字符串时反斜杠产生非法转义；这是跨平台路径写 JSON 的通用做法。

### 6.7 测试规避的引擎缺陷与历史接口变更

以下条目不是本模块的接口，但直接影响用例写法与“重建”判断，必须记录：

1. 四叉树/四叉树管理器的析构代价：多处用例注释写明“默认边长上限 65536（递归级数 12），其析构会物化整棵树耗时十余秒”，因此以 `new(std::nothrow) engine::Quadtree_Manager<int>()` 构造并刻意不释放，只验证建树与检索本身。涉及用例：`稳定查询自动建树`、`大坐标可智能建树并查询`、`默认边长上限下建成的树记录大小正确`、`默认设置下单点查询能够收敛`、`超大边长上限下区块检索次数正常`。这是快照内**仍然存在**的引擎侧问题（析构语义与性能），不是测试缺陷；重建时应作为高优先级缺陷复核。
2. 事件中转器移除 `target_object_check`：`事件中转器测试.cpp` 注释记录引擎层提交 `e430610` 移除了该查询接口，登记状态不再可直接查询；用例改为观察“登记后匹配事件能否送达”。历史接口名仍留在注释中。

4. Object 的 ID/有效标记私有化：`对象测试.cpp` 注释记录“自第九十七轮起改为私有（仅 Object_Pool 可写）”，原公开 setter 已移除；用例统一经对象池构建观察写入结果。
5. 数据校验器的 `if constexpr` → `else if constexpr`：`数据校验器测试.cpp` 注释记录布尔分支曾落入整数分支，修复后布尔字段可通过；`字段校验测试` 与 `数据校验器测试` 均含布尔回归。

### 7.1 链路一：一个用例从注册到执行

以 `Application/Test/tests/Foundation` 的 `Timer_Test.构建新任务成功` 为例。

   - `byjy_ceshi_tou_jiaoyan("TestFoundation" "${BYJY_SUB_ROOT}/src")` 校验用例中的 `#include` 都能在 Foundation 头快照中找到；

   - `add_library(TestFoundation STATIC ...)` + `include(源文件列表)` 把 `src/工具/计时器测试.cpp` 等目标文件纳入静态库；

3. **进程启动**：`main(argc, argv)`。
   - `SetConsoleOutputCP(CP_UTF8)` / `SetConsoleCP(CP_UTF8)`；

### 7.2 链路二：带夹具的碰撞用例从构造到断言

以 `Application/Test/tests/System/src/碰撞/碰撞区域测试.cpp` 的 `Collision_Region_Test.位移重叠触发碰撞检测` 为例。

1. **夹具构造**：gtest 为每个用例 `new Collision_Region_Test`；其 protected 成员 `engine::Collision_Region region{ "测试空间" }` 由构造函数初始化。
   - `Collision_Region(const std::string& region_name)` 建立 `Region_Backend`（内部创建 Bullet 碰撞世界、边界持有者）；
   - 记录空间名 `"测试空间"`，默认 `state_check()==false`。

2. **用例准备（构造两个盒体）**：
   - `region.collider_build()`：碰撞空间向编号分配器取号（空间边界固定占 0，碰撞体自 1 起），创建 `Collider`（含 `Collider_Backend` 与 Bullet 碰撞对象），返回 `collider_A=1`；
   - 再次 `collider_build()` 得 `collider_B=2`；
   - `region.collider_set(box_config(collider_A, 0.0))`：校验 `collider_ID/type/half_extent/position` 字段，调用 `Collider_Backend::geometry_build(json, Transform::getIdentity())` 建出半长 1 的盒体，再 `geometry_mount()` 挂载，并 `Region_Backend::object_attach(*backend)` 加入碰撞世界；
   - 对 `collider_B` 同理，初始位置 `x=5.0`。

3. **激活与位移回调**：
   - `region.state_set(true)`，使 `detect()` 进入执行分支；
   - `region.displacement_reader_set(lambda)`：闭包捕获局部 `engine::Vector3 displacement` 与 `collider_B`；对非目标碰撞体返回 `false`（无位移），对目标写入 `receiver = displacement` 并返回 `true`。

4. **首次检测（相距五个单位）**：
   - `region.detect()` 校验激活状态；
   - 内部 `检测执行` 先 `Region_Backend::aabbs_refresh()` 刷新包围盒；
   - 为每个有效碰撞体组织 `Collider_Move{ID, backend, step, step_count}`，其中 `step` 来自位移读取回调；
   - `Region_Backend::discrete_run(moves, details, boundary_contacts)`：逐段 `origin_advance(segment)` 推进后端变换，再执行 Bullet 世界求交，收集 `Collision_Detail`；
   - 返回 `std::optional<std::vector<Collision_Result>>`；本例 `detected->empty()` 为真，`ASSERT_TRUE` 通过。

5. **位移进入重叠**：
   - `displacement.setValue(-4.0f, 0.0f, 0.0f)`，使 `collider_B` 从 `x=5` 移到 `x=1`；
   - 再次 `detect()`：`discrete_run` 报告一对重叠；`Collision_Region` 把 `Collision_Detail` 归一化为 `Collision_Result{collider_A, collider_B}`；
   - `ASSERT_EQ(detected->size(), 1u)`、`EXPECT_EQ((*detected)[0].collider_A, collider_A)`、`EXPECT_EQ((*detected)[0].collider_B, collider_B)` 依次断言。

6. **位移移开**：
   - `displacement.setValue(-8.0f, 0.0f, 0.0f)`，把 `collider_B` 推到 `x=-3`；
   - 再次 `detect()`：`detected->empty()` 为真，证明位移是检测输入而非一次性状态。

7. **用例结束与析构**：
   - gtest 调用 `TearDown()`（默认空）；
   - 析构夹具：`Collision_Region` 析构 → `Region_Backend` 析构先摘除全部已挂载对象（含空间边界），再释放 Bullet 世界；
   - 碰撞体 `Collider` 由空间内部容器拥有，随空间析构释放 `Collider_Backend` 与 Bullet 对象；临时网格/边界文件由用例自行删除（本例未使用边界，不涉及）。

### 7.3 补充链路：关卡文本往返的判定路径

`Expect_roundtrip` 的执行顺序为：`level_text_write(level, utf8)` → `level_text_read(utf8, back)` → `expect_level_equal(level, back)`（逐组逐字段逐位）→ `level_text_write(back, 再写)` → `read_bytes(原文件) == read_bytes(再写文件)`。该链路把“内存结构一致”和“文本逐字节稳定”同时固化；写出前校验与失败清空由其他用例覆盖（见 §6.6 第 18、19 条）。
