# 输入模块

## 一、文件内目录

范围：`Engine/EngineSystem/src/input` 下全部 23 个文件（12 个 `.cpp`、11 个头文件）。按两条正交职责分为 `focus/`（焦点管理）与 `mapping/`（映射系统），公共词汇放在 `Common/`。

### 1.1 公共词汇层

- `Engine/EngineSystem/src/input/Common/输入类型.h` —— 键位位域编码、键类枚举、修饰掩码常量、`Input_Binding` 与 `Axis_Binding` 两个配置绑定结构。
- `Engine/EngineSystem/src/input/Common/输入事件.h` —— 输入模块全部事件标签（`category = "Input"`）与载荷字段名常量，映射侧与焦点侧共用一套字符串。

### 1.2 焦点管理（职责 A：谁有权接收输入）

- `Engine/EngineSystem/src/input/focus/焦点管理系统运行包.h` —— 焦点子系统对外聚合头，向上一层暴露事件词汇、输入类型与 `Focus_System`。
- `Engine/EngineSystem/src/input/focus/Focus_Manager/焦点系统.h` —— `Focus_System` 类声明：主对象栈、当前主/子对象、待生效转移槽、模态栈、文本模式、对象归属与能力登记表。

- `Engine/EngineSystem/src/input/focus/Focus_Manager/core/事件处理.cpp` —— 9 类入站事件的分类过滤与分派，以及原始输入/文本会话的定向转发。

## 二、模块功能介绍

### 2.1 定位

本模块是 `EngineSystem` 层的输入子系统，由两个彼此正交、仅通过事件标签耦合的子系统组成：

- **焦点管理（`focus/`）**：回答“此刻谁有权接收输入”。持有主对象焦点栈、当前主/子对象、模态栈、文本输入模式，以及“对象 → 宿主 / 宿主 → 子对象集合 / 对象能力位”的登记表，并对所有入站原始输入执行闸门判定。
- **映射系统（`mapping/`）**：回答“原始输入变成什么语义”。持有映射对象池，把原始键位帧解析成语义命令（`Command`）与轴状态（`AxisState`），并维护“自身映射 / 注入映射 / 监听”三层键位归属关系。

两条职责的名称与代码边界严格对应：`Focus_System` 不解析键位，`Input_Manager` 不做焦点判定；它们之间没有任何直接函数调用，只有 `Event_Terminal` 上的定向事件与广播事件。

### 2.2 职责 A：焦点管理

`Focus_System` 维护一个**主对象栈**（栈顶即当前主对象）与至多一个**当前子对象**。任一时刻“活跃接收者”定义为 `current_child` 非空时取子对象，否则取 `current_main`（见 `Engine/EngineSystem/src/input/focus/Focus_Manager/core/事件处理.cpp` 的 `raw_process`）。原始输入帧只投递给这一个对象，其余对象不直接接收输入。

模态栈用于做输入隔离：栈顶为**模态根**，只有模态根本身及其子孙允许接收输入（`object_within_modal`，见 §四 4.3）。模态只做“放行/拦截”，不会自动搬动焦点；压栈后必须由外部显式把焦点移入模态子树，否则整帧原始输入被丢弃。

所有焦点变更不会立即生效，而是先写入一组**单值待生效槽**（`pending_main` / `pending_child` / `pending_child_clear` / `pending_pop` / `pending_valid`），由 `frame_begin()` 在下一帧开头一次性应用（见 `焦点转移.cpp`）。因此一次 `Enter` 造成的焦点切换对输入的可见效果是“下一帧开始生效”。

### 2.3 职责 B：映射系统

映射系统内部再分三层，职责写在 `输入管理器.h` 的类注释中：

- `Input_Object`（`映射对象.h`）：单个对象的数据与事件终端。自身映射表 `mapping` 为 `Input_Key → vector<Input_Binding>`，同主键可挂多条绑定并以修饰掩码区分；`injected_declared` 是“向宿主声明新增映射”，`injected_active` 是“经宿主优先、先注册优先解析后真正生效的注入”；`listening` 只允许引用宿主自身映射表的主键。
- `input_mapping`（`输入映射.h`）：纯函数层，只做“配置 → 数据结构”的解析与轴值变换，不持有业务状态；其唯一的内部状态是两张 `static const` 名称表（`键位解析.cpp` 中的 `key_name_table` / `modifier_name_table`）。
- `Input_Manager`（`输入管理器.h`）：对象池、名索引、宿主-子对象关系、全局按住集合、事件接入与全部分发逻辑。

映射系统的对象图是**两层**的：宿主必须是主对象，子对象只能挂在主对象下（`object_create` 校验 `object_is_main(host)`），因此不存在“子对象的子对象”。

### 2.4 两条职责如何串联

串联围绕下列事件标签展开（词汇定义见 `Common/输入事件.h`，载荷契约见 §三 3.4）：

1. `Raw`（渲染层 → 焦点系统）：原始帧进入本模块的唯一入口。
2. `Forward`（焦点系统 → 输入管理器，定向）：闸门放行后，把原始帧加上 `object`（活跃对象名）与 `text_mode` 后转发给映射系统。
3. `RawFrame`（管理器 → 具体映射对象，对象终端直投）：把帧投给**唯一**目标对象。
4. `Command`（映射对象 → 中转站广播）：语义动作产出，`sender` 为产出对象名。
5. `Enter` 的特例：若 `Command.target` 是产出对象**自家子对象**，管理器不发广播，而改发 `ChildFocus`（定向焦点系统）——把“切到自己的子对象”变成焦点请求（`command_relay`，见 §四 4.5）。
6. `ObjectLinked` / `ObjectDestroyed`（管理器 → 焦点系统，定向）：对象能力位与归属的反向同步，让焦点系统无需读对象池即可做闸门判定。
7. 焦点侧另有 `FocusChanged` / `TextMode` 广播给中转站，供 UI 与渲染层消费；`TextRoute` 把文本会话从焦点系统送到映射系统再转成 `Text` 广播（见 §七 7.4）。

由此形成的闭环是：**原始输入 → 焦点闸门 → 唯一目标对象 → 语义命令 → 广播（游戏逻辑）与回流（焦点转移）**；焦点转移的结果又决定下一帧谁能收到原始输入。

### 2.5 不负责什么

- **不负责平台扫描码采集与翻译**：渲染层必须把扫描码翻译成合法位域的 `Input_Key`（`输入类型.h` 注释明示）。
- **不负责按键自动重复/去抖**：无跨帧重复按下沿抑制（见 §六 D10），连发口径由渲染层决定。
- **不负责 IME/文本组合**：文本会话只做三跳透传（`TextSession` → `TextRoute` → `Text`）。
- **不负责 UI 命中测试**：鼠标命中由 UI 以 `MouseFocus{object}` 上报，本模块只按名字转移焦点。
- **不负责动作业务语义与改键 UI**：`command` 只是字符串（仅 `Enter`/`Escape` 被内建解释），且无“设置某对象某键”的公开 API，映射只能经 `Create`/`Reload`/`Config.Load` 整体替换。
- **不负责配置持久化、实体/属性/特效逻辑、渲染。**

### 2.6 关键约束（模块级不变量）

| 编号 | 约束 | 依据 |
| --- | --- | --- |
| C1 | 一帧内只有一个“活跃接收者”；同帧其他对象只能经监听表获得**键位边沿拷贝**，拿不到指针/轴/文本模式。 | `raw_process`、`object_copy_to_children` |
| C2 | 子对象只有一层，宿主必须是主对象且已存在。 | `object_create` |
| C3 | 焦点转移延迟一帧生效；同帧多次请求后写覆盖前写。 | `main_push_request` / `child_request` / `transition_apply` |
| C4 | 所有事件回调在发送方调用栈上同步执行，无队列、无线程保护；回调期间对象可能被销毁。 | `Event_Terminal::receive/send` |
| C5 | 订阅晚于事件即永久丢失，模块内无重放、无状态查询补偿。 | `attach` 仅登记订阅；`object_state_notify` 只在创建/重载/更新时发 |
| C6 | 键位 `0` 恒非法；键类必须 1..5；保留位必须 0。 | `input_key_valid` |
| C7 | 任一映射/轴配置项非法则整表拒绝，不做“部分生效”。 | `mapping_parse` / `axis_parse` |
| C8 | 命令只在**按下沿**产生；抬起沿只用于（a）更新按住集合、（b）拷贝给监听子对象。 | `object_keys_process` |

### 2.7 耦合边界

本模块依赖 `EngineFoundation` 的四件基础设施，均在头文件层直接引用，未封装后端：

- `Event_Terminal`（`Engine/EngineFoundation/src/event/Event_Terminal/事件终端.h`）：每个 `Focus_System`、`Input_Manager`、`Input_Object` 各持一个；发送/接收/构造/接入语义见 §三 3.9。
- `Event_Broker`（经 `Event_Terminal` 的 `Broker_Attacher` 端口间接接入，见 §六 D1）。
- `Object_Pool<Input_Object>`（`映射对象.h` 与 `输入管理器.h`）：对象池按 ID 定位，`build` 分配、`unload` 回收、`find` 取迭代器。
- `detail::field_check<T>`（`数据校验工具.h`）：`string` 版要求“存在 + 是字符串 + 非空”，这是绝大多数 `object`/`command`/`name` 字段的准入条件；失败时该工具自身会打日志（`logger.info/warn`），调用点通常不再重复说明原因。

外部消费者只在事件层面与本模块耦合：渲染层发 `Raw`/`TextSession`、UI 发 `MouseFocus`/`ModalPush`/`ModalPop`、游戏逻辑发 `Create`/`Destroy`/`Reload`/`Config.Load` 并订阅 `Command`/`AxisState`/`Text`/`FocusChanged`/`TextMode`。

## 三、模块公开接口

### 3.1 键位编码（`Common/输入类型.h`）

`Input_Key` 是 `uint32_t` 位域：`bit 31..28` 键类，`bit 27..16` 保留恒 0，`bit 15..0` 类内编号（1 起，0 表示无效）。

```cpp
using Input_Key = uint32_t;

inline constexpr uint32_t INPUT_KEY_CLASS_SHIFT = 28;
inline constexpr uint32_t INPUT_KEY_CLASS_MASK  = 0xF0000000u;
inline constexpr uint32_t INPUT_KEY_CODE_MASK   = 0x0000FFFFu;
inline constexpr uint32_t INPUT_KEY_VALID_MASK  = INPUT_KEY_CLASS_MASK | INPUT_KEY_CODE_MASK;

constexpr Input_Key        input_key_make(const Input_Key_Class& key_class, const uint32_t& code);
constexpr Input_Key_Class  input_key_class_get(const Input_Key& key);
constexpr uint32_t         input_key_code_get(const Input_Key& key);
constexpr bool             input_key_valid(const Input_Key& key);
```

| 接口 | 语义 | 前置 / 失败 |
| --- | --- | --- |
| `input_key_make(key_class, code)` | 拼装编码：`(class << 28) \| (code & 0xFFFF)`。 | `code` 超过 16 位会被**静默截断**（掩码后拼装），不做校验。 |
| `input_key_class_get(key)` | 取高 4 位并强转为 `Input_Key_Class`；不校验合法性。 | 非法编码可能返回未定义枚举值。 |
| `input_key_code_get(key)` | 取低 16 位类内编号。 | 无。 |
| `input_key_valid(key)` | 三条同时成立才为真：保留位（16..27）为 0；键类在 1..5；类内编号非 0。 | 任何平铺式旧键码都会因保留位非零被拒（`key_parse` 依赖此点）。 |

键类枚举（`enum class Input_Key_Class : uint32_t`）：

| 枚举值 | 数值 | 含义 | 类内编号使用情况 |
| --- | --- | --- | --- |
| `main` | `0x1` | 主键盘常规键（字母/数字/符号） | 1..26 字母 A..Z；27..36 数字 0..9；37..47 符号 |
| `control` | `0x2` | 控制/功能/导航/修饰键 | 1..41（含 34..41 为修饰键） |
| `keypad` | `0x3` | 小键盘 | 1..16 |
| `mouse` | `0x4` | 鼠标按键 | 1..5 |
| `wheel` | `0x5` | 滚轮 | 1..2 |

修饰键规范化掩码位（`uint8_t`）：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `INPUT_MODIFIER_SHIFT` | `0x01` | Shift（左右合并） |
| `INPUT_MODIFIER_CTRL` | `0x02` | Ctrl（左右合并） |
| `INPUT_MODIFIER_ALT` | `0x04` | Alt（左右合并） |
| `INPUT_MODIFIER_GUI` | `0x08` | GUI/Super（左右合并） |

语义要点：修饰掩码是**规范化**的——不区分左右。左右键的物理编码不同（`LSHIFT` = control 34、`RSHIFT` = control 35），但 `modifier_mask_of` 都映射到 `SHIFT` 位。

### 3.2 绑定结构

```cpp
struct Input_Binding
{
    std::string command{};      // 映射语义（唯一被内建解释的两个值：Enter / Escape）
    std::string target{};       // 语义目标对象名；Enter 必需，其余可空
    uint8_t     modifier_mask = 0; // 组合修饰掩码（0 = 普通单键绑定）
};

struct Axis_Binding
{
    std::string source{};        // pointer.dx / pointer.dy / pointer.x / pointer.y / 原始轴名
    bool        rate = false;    // true = 速率型，false = 位移型
    double      scale = 1.0;     // 缩放系数
    double      deadzone = 0.0;  // 死区（以原始值为单位）
    double      clamp = 1.0;     // 钳制上限（绝对值）；<= 0 视为不钳制
    bool        invert = false;  // 反相
};
```

前置与失败：这两者是**纯数据**，无构造校验。合法性由 `input_mapping` 的解析函数保证（见 3.8）；直接构造时非法值（如 `clamp = -3`）不会报错，只在变换时表现为“不钳制”。

### 3.3 事件词汇（`Common/输入事件.h`）

`namespace engine::input_event`，全部为 `inline constexpr const char*`。`category` 恒为 `"Input"`。

| 常量 | 值 | 方向 / 含义 |
| --- | --- | --- |
| `category` | `"Input"` | 事件类别，本模块只处理该类别（`Config/Load` 除外）。 |
| `create` | `"Create"` | 外部 → 输入管理器：创建映射对象。 |
| `destroy` | `"Destroy"` | 外部 → 输入管理器：销毁对象（含级联）。 |
| `reload` | `"Reload"` | 外部 → 输入管理器：重载映射表/轴表/能力位。 |
| `raw` | `"Raw"` | 渲染层 → 焦点系统：原始输入帧。 |
| `mouse_focus` | `"MouseFocus"` | UI 系统 → 焦点系统：按对象名请求焦点。 |
| `text_session` | `"TextSession"` | 渲染层 → 焦点系统：文本会话；管理器 → 映射对象：同标签的第二跳。 |
| `modal_push` / `modal_pop` | `"ModalPush"` / `"ModalPop"` | 外部 → 焦点系统：模态压栈/弹栈。 |
| `forward` | `"Forward"` | 焦点系统 → 输入管理器（定向）：闸门放行后的原始帧。 |
| `text_route` | `"TextRoute"` | 焦点系统 → 输入管理器（定向）：文本会话转发。 |
| `raw_frame` | `"RawFrame"` | 管理器 → 映射对象（对象终端直投）：待映射的帧。 |
| `command` | `"Command"` | 映射对象 → 中转站广播：语义命令。 |

| 接口 | 语义 | 接受/拒绝规则 | 失败行为 |
| --- | --- | --- | --- |
| `key_parse(spec, out)` | 解析键位：无符号整数 / 有符号整数 / 字符串名。整数必须是合法位域（`input_key_valid`）；字符串先 `toupper` 归一再查表。 | 整数 `0`、负数、超过 `UINT32_MAX`、保留位非零、键类越界、编号 0 全拒。名称表未登记即拒。 | 返回 `false`，`out` 不被写入（保持调用方原值）。 |
| `modifier_mask_of(key)` | 物理键位 → 规范化修饰位。 | 仅 `control` 类 34/35→SHIFT、36/37→CTRL、38/39→ALT、40/41→GUI。 | 其余一律返回 0。 |
| `modifier_parse(spec, out)` | 解析 `modifiers` 数组，名称或键位数字，多项按位或。 | `null` → `out=0` 且返回 `true`；非数组 → 拒；名称必须是修饰键名；数字必须是修饰键编码。 | 返回 `false`，`out` 可能已被部分写入（函数先置 0，再逐项 `\|=`），调用点均不采用该值。 |
| `binding_parse(spec, key, binding)` | 解析单条映射：必需 `key` 与 `command`（非空字符串），可选 `modifiers`、`target`。 | `command == "Enter"` 且 `target` 为空 → 拒；`command == "Escape"` → 强制清空 `target`；`target` 非字符串则忽略。 | 返回 `false`（打日志）。 |
| `mapping_parse(spec, table)` | 解析整个映射数组为 `key → vector<binding>`。 | `null` → `true` 且不改表；非数组 → 拒。同一主键下出现**相同 `modifier_mask`** 视为重复，整表拒。任一项非法整表拒。 | 返回 `false`，`table` 保持原值（函数用局部 `buffer` 后 `std::move` 提交）。 |
| `listening_parse(spec, host, table)` | 解析监听数组，只保留 `host.mapping_has(key)` 的键位。 | `null` → `true` 不改表；非数组 → 拒（但此时 `table` 仍未改）。非法项与“宿主无此键”只跳过并告警，不算失败。 | 几乎总返回 `true`；只有非数组返回 `false`。 |
| `axis_parse(spec, table)` | 解析轴数组：每项必须有非空 `axis` 与 `source`。 | `null` → `true` 不改表；非数组 → 拒；轴名重复 → 整表拒；`mode` 只接受 `"rate"` / `"displacement"`（缺省 `"displacement"`）。`scale/deadzone/clamp` 需为数字，`invert` 需为布尔，否则**忽略该项字段**（用默认值）。 | 任一项非法 → `false`，`table` 保持原值。 |
| `axis_transform(binding, raw_value, dt)` | 按序执行：死区（对 `raw_value` 绝对值，`deadzone > 0 && abs < deadzone` → 0）→ 乘 `scale` → 反相 → 钳制（`clamp > 0 && abs > clamp` → 取符号侧 `±clamp`）。 | 无前置校验；`clamp <= 0` 即不钳制，`deadzone <= 0` 即无死区。 | 不失败；`delta = rate ? value * dt : value`。 |

`key_parse` 的接受范围由名称表决定（`core/键位解析.cpp` 的 `key_name_table()`）：

- `main`：`A`..`Z`（编号 1..26，单字符键名）；`0`..`9`（27..36）；符号 37..47，同时接受字符本身与英文键名（`` ` ``/`BACKQUOTE`、`-`/`MINUS`、`=`/`EQUAL`、`[`/`LEFT_BRACKET`、`]`/`RIGHT_BRACKET`、`\`/`BACKSLASH`、`;`/`SEMICOLON`、`'`/`APOSTROPHE`、`,`/`COMMA`、`.`/`PERIOD`、`/`/`SLASH`）。

### 4.1 `focus/Focus_Manager/core/事件处理.cpp`

```cpp
void Focus_System::event_process(std::shared_ptr<Event> evt);
void Focus_System::raw_process(std::shared_ptr<Event> evt);

```

**`event_process`**：空事件直接返回；`category != "Input"` 直接返回（**不检查 `receiver`**，因此焦点系统会处理任何发到中转站的 Input 类事件）；随后按 `tag` 逐条 `if` 分派到上面 9 个处理函数，每个分支都 `return`。未知标签静默忽略。

**`raw_process`**（闸门核心，顺序固定）：

1. 计算活跃对象 `target = current_child.empty() ? current_main : current_child`。
2. `target` 为空 → `logger.warn("当前无活跃对象\n原始输入已丢弃")` 并返回。
3. `enabled_of[target]` 存在且为 `false` → 告警并丢弃（**表项不存在视为允许**）。
4. `!object_within_modal(target)` → 告警并丢弃。
5. 复制 `evt->config`，写入 `config["object"] = target`、`config["text_mode"] = text_mode`。
6. `focus_send(input_event::forward, config, "Input_Manager")` 定向转发。

副作用：被丢弃的帧不会进入映射系统，因此**按住集合不会更新**（见 §六 D17）。

**`command_process`**（语义回流，顺序固定）：

1. `detail::field_check<string>(evt->config, "command")` 失败即返回（注意用字面量）。
2. `!object_within_modal(evt->sender)` → 告警并丢弃。`sender` 为空时，若存在模态，必然不通过（空名不在模态子树内）。
3. `enabled_of[evt->sender]` 存在且 `false` → 静默丢弃。
4. `command == "Escape"` → `main_pop_request()` 并返回。
5. `command != "Enter"` → 忽略（其余语义只用于业务广播，不参与焦点）。
6. `target = config.value("target", "")` → `target_request(target)`（空目标会被 `target_request` 告警丢弃）。

**`mouse_focus_process`**：`field_check<string>(config, "object")` 通过后直接 `target_request(object)`；不做 sender、不做模态预检（模态检查在 `target_request` 内）。

**`child_focus_process`**：

- 取 `host`、`child`（均为 `value(..., "")`，缺失即空）。
- `child` 空（表示回到宿主）：要求 `host == current_main`，否则告警丢弃；通过则 `child_request("")`。
- `child` 非空：同样要求 `host == current_main`；再查 `focusable_of[child]`，存在且 `false` 则告警丢弃；通过则 `child_request(child)`。
- 本函数**不执行模态闸门**，安全性依赖“`host` 必须是当前主对象”这一约束（见 §六 D9）。

**`object_linked_process`**：

- `name = config.value("object","")`，为空直接返回。
- 写入/覆盖：`host_of[name] = host`、`focusable_of[name] = value("focusable", true)`、`enabled_of[name] = value("enabled", true)`、`text_sink_of[name] = value("text_sink", false)`。
- `host` 非空 → `children_of[host].insert(name)`。
- `host` 空且 `main_stack.empty() && current_main.empty() && !pending_valid` → `main_push_request(name)`，即“**最先接入的主对象**自动获得焦点”。
- 末尾 `text_mode_refresh()`（能力位变化可能改变文本模式）。

**`object_destroyed_process`**（清理顺序）：

1. 取 `name`，空则返回；记录清理前的 `before_main/before_child/before_modal`。
2. 读 `host_of[name]` 取宿主名，然后 `erase` 四个登记表（`host_of`/`focusable_of`/`enabled_of`/`text_sink_of`）。
3. 从宿主的 `children_of[host]` 中移除该名字；若宿主集合变空则删除该宿主表项。
4. `children_of.erase(name)`（丢弃它自己的子对象集合）。
5. `std::erase(main_stack, name)`、`std::erase(modal_stack, name)`（移除**所有**同名项，而非仅栈顶）。
6. 清理 `current_child`、`pending_child`、`pending_main`（若 `pending_main == name` 则连 `pending_valid` 一起清）。
7. `current_main = main_stack.empty() ? "" : main_stack.back()`。
8. `text_mode_refresh()`。
9. 若主/子/模态任一变化 → `focus_changed_publish()`。

注意：直接后代由管理器级联销毁并逐个发 `ObjectDestroyed`，本函数不递归。

**`text_session_process`**：

- `!text_mode` → 告警“非文本模式，文本会话已丢弃”并返回。
- `target = current_child.empty() ? current_main : current_child`，为空则静默返回（不告警）。
- 复制载荷，写 `object = target`，`focus_send(input_event::text_route, config, "Input_Manager")`。
- 与 `raw_process` 不同：这里**不做** `enabled` 与模态检查。

### 4.2 `focus/Focus_Manager/core/焦点转移.cpp`

```cpp
void Focus_System::target_request(const std::string& target);
void Focus_System::main_push_request(const std::string& name);
void Focus_System::main_pop_request(void);
void Focus_System::child_request(const std::string& name);
void Focus_System::transition_apply(void);
```

**`target_request`**（统一入口，顺序固定）：

1. `target` 空 → 告警返回。
2. `host_of.find(target)` 未命中 → 告警“目标对象未知”返回（未知对象一律不转移）。
3. `focusable_of[target]` 存在且 `false` → 告警返回。
4. `!object_within_modal(target)` → 告警返回。
5. 若 `host_of[target].empty()`（目标是主对象）→ `main_push_request(target)`。
6. 否则若宿主 `== current_main` → `child_request(target)`（同主对象内部切子对象）。
7. 否则（目标是别的主对象的子对象）→ 先 `main_push_request(host)`，再 `child_request(target)`，即一次请求同时产生“压栈 + 接管子焦点”。

**`main_push_request(name)`**：

- `name` 空 → 返回。
- `name == current_main`（重复请求当前主对象）→ 清 `pending_main`/`pending_child`，置 `pending_child_clear = true`、`pending_pop = false`、`pending_valid = true`。语义：**重复请求当前主对象 = 把焦点收回主对象自身**。
- 否则登记 `pending_main = name`，清 `pending_child`，`pending_child_clear = false`、`pending_pop = false`、`pending_valid = true`。**同帧后写覆盖前写**。

**`main_pop_request()`**：

- `main_stack.size() < 2` → 告警“无可回退对象，Escape 已忽略”返回。
- 否则清 `pending_main`/`pending_child`，`pending_child_clear = false`，`pending_pop = true`，`pending_valid = true`。
- 只登记弹栈，不与压栈请求共存（覆盖 `pending_main`）。

**`child_request(name)`**：

- `name` 空 → 清 `pending_child`，`pending_child_clear = true`，`pending_valid = true`（焦点回宿主）。
- 非空 → `pending_child = name`，`pending_child_clear = false`，`pending_valid = true`（不清 `pending_main`，允许“换主对象 + 直接接管其子对象”一步完成）。

**`transition_apply`**（帧首统一应用，顺序固定）：

1. `!pending_valid` → 返回。
2. 记录 `before_main`/`before_child`。
3. 若 `pending_pop`：仅在 `main_stack.size() >= 2` 时 `pop_back()`；清 `pending_pop`。
4. 若 `pending_main` 非空：若栈空或栈顶不等于它，先 `std::erase(main_stack, pending_main)`（**移除历史同名项，防止循环压栈**）再 `push_back`；清 `pending_main`。
5. `current_main = 栈顶或空`。
6. 若主对象变化、且没有待生效子对象、且未标记清空 → `current_child.clear()`。
7. 若 `pending_child_clear` → 清 `current_child` 与 `pending_child`，复位标记。
8. 否则若 `pending_child` 非空 → 校验它是否在 `children_of[current_main]` 中；不在则告警丢弃（**不清 `current_child`**），在则 `current_child = pending_child`；最后清 `pending_child`。
9. 复位 `pending_valid`；`text_mode_refresh()`；若主/子变化 → `focus_changed_publish()`。

第 8 步的“丢弃但不清 `current_child`”会在“主对象已切换 + 待生效子对象非法”时留下**陈旧子对象**（见【待确认：3】）。

### 4.3 `focus/Focus_Manager/core/模态闸门.cpp`

```cpp
bool Focus_System::object_within_modal(const std::string& name) const;
void Focus_System::modal_push_process(std::shared_ptr<Event> evt);
void Focus_System::modal_pop_process(std::shared_ptr<Event> evt);
```

**`object_within_modal(name)`**：

- `modal_stack` 空 → 恒 `true`（无模态时全部放行）。
- `name == modal_stack.back()` → `true`。
- 否则以模态根为起点做深度优先遍历（显式 `vector<string> pending` 作为栈，先压根，弹栈取节点，再遍历其 `children_of` 集合）：命中 `name` 即 `true`。
- 遍历完未命中 → `false`。
- 只看**静态归属图**，不看当前焦点；模态子树之外的一切对象（包括当前主对象）都被判为门外。

**`modal_push_process`**：

1. `object` 为空 → 告警返回。
2. `!host_of.count(object)` → 告警“模态对象未知”返回（**模态根必须先经 `ObjectLinked` 登记**）。
3. 与当前栈顶相同 → 静默返回（幂等，不重复压栈）。
4. `modal_stack.push_back(object)`；`focus_changed_publish()`；`logger.info`。

**`modal_pop_process`**：参数完全被忽略（形参未命名）；栈空 → 告警返回；否则 `pop_back()` + `focus_changed_publish()` + 日志。不校验 sender，任意订阅者都能弹。

### 4.4 `focus/Focus_Manager/core/接入与广播.cpp`

**构造 / `attach` / `frame_begin` / 五个 getter**：行为见 §三 3.5。实现细节补充：`attach` 中先 `event_terminal->bind(Port_ID::Evt_Receiver, lambda)`（lambda 捕获 `this`），再 `event_terminal.attach("Focus_System", acl_key)`；订阅清单以 `vector<Event>` 构造，再转成 `[{"category","tag"}, ...]` 数组写入 `subscribed_events`。

### 4.5 `mapping/Input_Manager/core/接入与分发.cpp`

```cpp
Input_Manager::Input_Manager(void);
bool Input_Manager::attach(void);
void Input_Manager::event_process(std::shared_ptr<Event> evt);
void Input_Manager::command_relay(std::shared_ptr<Event> evt);
void Input_Manager::focus_notify(const std::string& tag, const nlohmann::json& config);
void Input_Manager::object_dispatch(const uint64_t& ID, std::shared_ptr<Event> evt);
```

**构造 / `attach`**：见 §三 3.7；订阅清单为 `Create`、`Destroy`、`Reload`、`Forward`、`TextRoute` 与 `Config/Load`。与焦点侧一样只做防重入的 `attached` 标记，不做端口预检。

**`event_process`**（分派顺序）：

1. 空事件返回。
2. `(category, tag) == ("Config","Load")` → `config_apply` 并返回（**先于**类别判断，且不校验 `receiver`）。
3. `category != "Input"` → 返回。
4. 依次：`Create`→`object_create`；`Destroy`→`field_check<string>(config,"object")` 后 `object_destroy`；`Reload`→`object_reload`；`Forward`→`raw_forward`；`TextRoute`→`text_forward`。未知标签静默忽略。

**`command_relay`**（对象终端发送端口的落点）：

1. 空事件 → 告警返回。
2. `command = config.value("command","")`、`target = config.value("target","")`。
3. 若 `command == "Enter"` 且 `target` 非空且 `object_is_child_of(target, evt->sender)` → 构造 `{host: sender, child: target}`，`config` 有 `frame` 时透传，`focus_notify(input_event::child_focus, config)` 定向焦点系统，**返回且不广播**。
4. 否则 `event_terminal.send(evt, acl_key)`（用管理器自己的终端把事件原样送上中转站），失败 `logger.error`。

语义：`sender` 是产出对象名（对象终端 `build(source_name, "", ...)`），所以“自家子对象”判定用的是产出对象本身，而不是当前焦点对象。

**`focus_notify(tag, config)`**：`build("Input_Manager", "Focus_System", "Input", tag)` → 写 config → `send`；失败 `logger.warn`。所有对焦点的同步都走这里。

**`object_dispatch(ID, evt)`**（对象接收入口的落点）：

- 空事件 / 非 `Input` 类别 / 对象不存在 → 返回。
- `tag == TextSession`：用**对象自己的终端** `build(object_name, "", "Input", "Text")`，写会话载荷，`send(text_evt, object->acl_key)`，即把会话提升为广播 `Text`。
- `tag != RawFrame` → 返回。
- `tag == RawFrame` → `object_map(ID, evt->config)`。

注意 `object_dispatch` 与 `object_map` 之间的“原始帧 → 映射”不经过焦点闸门；闸门已在焦点侧完成，监听拷贝则本就绕过闸门（见 §六 D6）。

### 4.6 `mapping/Input_Manager/core/对象生命周期.cpp`

```cpp
void Input_Manager::object_create(const nlohmann::json& config);
void Input_Manager::object_destroy(const std::string& name);
void Input_Manager::object_reload(const nlohmann::json& config);
void Input_Manager::object_update(const nlohmann::json& item);
void Input_Manager::object_cascade_collect(const std::string& name,
                                           std::vector<std::string>& list) const;
void Input_Manager::object_unload_single(const std::string& name);
```

**`object_create`**（“解析先行，分配在后”，任何一步失败都不产生半成品对象）：

1. `field_check<string>(config, "name")` 失败 → 告警驳回。
2. `name` 已存在 → 告警“已驳回重复创建”。
3. `host`：若存在且为字符串则取其值；非空时要求 `name_index.count(host)` 且 `object_is_main(host)`，否则驳回。**禁止三层**。
4. `mapping` 存在 → `mapping_parse`，失败驳回。
5. `added_keys` 存在 → `mapping_parse`（复用映射解析），失败驳回。
6. `axes` 存在 → `axis_parse`，失败驳回。
7. `listen` 存在：无宿主则告警“监听表已忽略”；有宿主则取宿主对象并 `listening_parse`（宿主必存在，因为第 3 步已校验）。
8. `ID = objects.build(Input_Object{})`；`object_find(ID)` 失败 → `logger.error` 返回。
9. 写字段：`object_name`、`host_name`、`focusable=value(true)`、`enabled=value(true)`、`text_sink=value(false)`、`acl_key = object->event_terminal.key().value_or(0)`；四张表 `std::move` 写入。
10. 绑定端口：`Evt_Receiver` 捕获 `[this, ID]` → `object_dispatch(ID, ...)`（**按编号回调，避免捕获会移动的对象地址**）；`Evt_Sender` 捕获 `[this]` → `command_relay`。
11. `name_index.emplace(name, ID)`；有宿主则 `children[host].push_back(name)`（保持注册顺序）并 `injected_resolve(host, name)`（只重算这一个子对象）。
12. `object_state_notify(ID)` → 焦点系统收到 `ObjectLinked`；`logger.info`。

**`object_destroy(name)`**：不存在则告警返回；否则先 `object_cascade_collect(name, cascade)`（**后序**：先递归收集后代，再把当前名字 push 进列表，故最深后代在前），随后逐个 `object_unload_single`，最后卸载自身。

**`object_reload(config)`**：

1. `field_check<string>(config, "object")` 失败告警返回；对象不存在告警返回。
2. `mapping` 存在 → `mapping_parse`；**失败立即 `return`**（后续 `axes`/能力位都不再处理）。
3. `axes` 存在 → `axis_parse`；失败同样立即 `return`；成功则整体替换并 `axis_state.clear()`。
4. `focusable`/`enabled`/`text_sink` 各自存在且为布尔时逐项写入。
5. `injected_rebuild(name)`（先重算注入），再 `listening_rebuild(name)`（再校验监听），最后 `object_state_notify(object->ID())` 同步能力位。

**`object_update(item)`**（供 `config_apply` 热更新用）：与 `object_reload` 的差别是——映射/轴解析失败只 `logger.warn` 并**保留旧表、继续处理后续字段**，不提前返回；其余步骤相同（含 `injected_rebuild` + `listening_rebuild` + `object_state_notify`）。`name` 用 `item.value("name","")`（字面量）。

**`object_cascade_collect(name, list)`**：查 `children[name]`；无则返回；否则对每个子名先递归、再 `push_back`（后序），形成“子先父后”的卸载顺序。

**`object_unload_single(name)`**：

1. 查名索引，未命中返回；取 `ID` 与对象，记录 `host`。
2. 构造 `{object: name, host}` → `focus_notify(input_event::object_destroyed, ...)`（**先通知焦点，再动池**）。
3. 从 `children[host]` 的 `vector` 中用 `std::remove` + `erase` 删除该名字；变空则删表项。
4. `children.erase(name)`；`name_index.erase(it)`；`objects.unload(ID)`。
5. 宿主非空时 `injected_rebuild(host)`：被此前压制的注入键此时可能重新生效。

### 4.7 `mapping/Input_Manager/core/原始输入.cpp`

```cpp
void Input_Manager::held_update(const nlohmann::json& raw);
uint8_t Input_Manager::held_modifier_mask(void) const;
void Input_Manager::raw_forward(std::shared_ptr<Event> evt);

void Input_Manager::object_copy_to_children(const uint64_t& ID, const std::string& source_name,
                                            const Input_Key& key, const nlohmann::json& edge,
                                            const uint64_t& frame);
void Input_Manager::object_axes_process(const uint64_t& ID, const nlohmann::json& raw,
                                        const std::string& source_name, const uint64_t& frame,
                                        const double& dt);
```

**`held_update(raw)`**——按住集合的三路更新（顺序固定）：

1. 读 `frame`（缺省 0）；判断是否存在数组型 `held`（权威快照）。
2. 有权威快照 → `held_keys.clear()` 后逐项 `key_parse` 插入（**整体替换**，非法项静默跳过）。
3. 无权威快照且 `frame_seen && frame != 0 && frame > last_frame + 1` → `held_keys.clear()`（帧号跳变，保守重同步）。
4. `frame != 0` 时更新 `last_frame`/`frame_seen`。
5. `keys` 非数组则返回（**只更新快照与帧号，不处理边沿**）。
6. 逐条边沿：非对象或缺 `key` 跳过；`key_parse` 失败跳过；`pressed` 缺省 `true`；按下 `insert`、抬起 `erase`。

**`held_modifier_mask()`**：遍历 `held_keys`，把 `modifier_mask_of(key)` 按位或起来返回。O(按住键数)。

**`raw_forward(evt)`**：

1. `field_check<string>(config,"object")` 失败告警丢弃；对象不存在告警丢弃。
2. 复制载荷并 `erase("object")`（不让目标字段进入映射阶段）。
3. `object->event_terminal.build("Focus_System", target, "Input", "RawFrame")`；失败 `logger.error`。
4. `config` 移入事件，`object->event_terminal.receive(raw_evt)` → 触发对象自己的 `Evt_Receiver` → `object_dispatch`。

**`text_forward(evt)`**：同上，但构造标签为 `TextSession`，`payload` 剥离 `object` 后 `receive` 到对象终端；随后在 `object_dispatch` 里被提升为 `Text` 广播。

**`object_map(ID, raw)`**（一帧的映射入口）：

1. 取对象；不存在返回。
2. `frame = value("frame", 0)`、`dt = value("dt", 1/60)`、`source_name = object->object_name`（先取字符串，防对象重建）、`text_mode = value("text_mode", false)`。
3. `held_update(raw)`（**无论文本模式都做**，保持物理按键状态）。
4. `!text_mode` → `object_keys_process(ID, raw)`；文本模式下键位映射被挂起。
5. `object_axes_process(ID, raw, source_name, frame, dt > 0 ? dt : 1/60)`；轴不受文本模式影响。

**`object_keys_process(ID, raw)`**（组合解析与命令产出，顺序固定）：

1. 对象不存在或 `keys` 非数组 → 返回。
2. 取 `frame`、`source_name`，并预取 `child_it = children.find(source_name)`。
3. 四条缓冲：`presses`（按下记录）、`copies`（监听拷贝任务）、`commands`（待发命令）、`consumed`（本帧已消费键位集合）。
4. 逐边沿：格式非法或键位无法解析 → 告警跳过；先为每个“监听该键位”的子对象登记 `copies`（**抬起沿也拷贝**）；`pressed == false` → 只拷贝不产命令；否则登记 `presses`。
5. 先派发全部 `copies`（`object_copy_to_children`）。
6. 按 `ID` 重查对象（回调期间可能已销毁）；不存在则返回。
7. `held_mask = held_modifier_mask()`（**帧末状态**）。
8. 第一轮：对每条 `presses`（跳过已 `consumed`）`binding_find`；命中且 `modifier_mask != 0` → 记入 `commands`、`consumed.insert(key)`，并把 `held_keys` 中“属于该组合所需修饰”的物理键也 `consumed.insert`（抑制它们各自产出单键命令）；`modifier_mask == 0` 的命中留到第二轮。
9. 第二轮：对未 `consumed` 的 `presses` 再 `binding_find`；只接受 `modifier_mask == 0`；记入 `commands` 并 `consumed.insert(key)`。
10. 按 `ID` 重查 `source`；不存在返回。
11. 逐条命令：`source->event_terminal.build(source_name, "", "Input", "Command")`（失败 `logger.error` 并 `continue`）；写 `command`、非空 `target`、`key`、`frame`；`source->event_terminal.send(..., source->acl_key)`；**每发一条后按 `ID` 重查 `source`**，为 `nullptr` 立即返回（订阅方可能销毁了发件对象）。

**`object_copy_to_children(ID, source_name, key, edge, frame)`**：

1. 发件对象不存在 / 无子对象 → 返回。
2. `vector<string> child_names = it->second`（复制一份，避免回调改容器）。
3. 逐个：子对象不存在跳过；`!child->listening.count(key)` 跳过；`build(source_name, child_name, "Input", "RawFrame")`（失败 `logger.error` 并 `continue`）。
4. 载荷只写 `frame` 与 `keys = [edge]`（**单条边沿**），`child->event_terminal.receive(...)` → 子对象 `object_dispatch` → `object_map`。

**`object_axes_process(ID, raw, source_name, frame, dt)`**：

1. 对象不存在或无轴绑定 → 返回。
2. `values`/`deltas` 两个 json 对象；判定 `pointer`、`axes` 是否存在且为对象。
3. 逐轴取值：`pointer.dx`/`pointer.dy`/`pointer.x`/`pointer.y` 需 `pointer` 存在（取 `value("dx",0.0)` 等）；否则尝试 `axes[binding.source]` 且必须 `is_number()`；都不满足 → `raw_value = 0.0`（**静默**）。
4. `axis_transform` 后写入 `object->axis_state[axis_name] = result.value`；同时记入 `values`/`deltas`。
5. `values.empty()` → 返回（实际不可达，见【待确认：7】）。
6. 重查 `source`；`build(source_name, "", "Input", "AxisState")`（失败 `logger.error` 返回）；写 `frame`、`values`、`deltas`；`send`。

### 4.8 `mapping/Input_Manager/core/配置加载.cpp`

```cpp
void Input_Manager::config_apply(const nlohmann::json& config);
void Input_Manager::object_state_notify(const uint64_t& ID);
```

**`config_apply(config)`**：`config` 无数组 `objects` → 告警返回。逐项：非对象或 `name` 无效 → 告警跳过；`object_exist(name)` 为假 → `object_create(item)`，为真 → `object_update(item)`。**没有删除语义**：配置里消失的对象不会被卸载。

**`object_state_notify(ID)`**：对象不存在返回；构造 `{object, host, focusable, enabled, text_sink}` 后 `focus_notify(input_event::object_linked, ...)`。这是焦点系统感知“对象世界”的唯一增量通道。

### 4.9 `mapping/Input_Manager/core/映射查询.cpp`

匿名命名空间（仅本编译单元）：

```cpp
namespace { uint64_t binding_token(const engine::Input_Key& key, const uint8_t& modifier_mask); }
```

实现 `(uint64_t(key) << 8) | modifier_mask`，即“主键 + 修饰掩码”的组合标识（掩码 < 256 故无碰撞）。

公开查询实现（9 个）：`object_exist` 直接 `name_index.count`；`object_is_main` 经 `name_index` → `object_find` 判 `host_name` 空；`object_is_child_of` 在 `children[host]` 的 `vector` 上 `std::find`；其余 6 个都是“`object_find` 失败返回默认值，否则转调对象 getter”。

```cpp
Input_Object*       Input_Manager::object_find(const std::string& name);
const Input_Object* Input_Manager::object_find(const std::string& name) const;
Input_Object*       Input_Manager::object_find(const uint64_t& ID);
const Input_Object* Input_Manager::object_find(const uint64_t& ID) const;
```

名 → ID → `objects.find(ID)`；未命中返回 `nullptr`；命中返回 `&(*it)`（**指向池内元素的裸指针**，任何 `build/unload` 都可能使其失效）。

**`binding_find(object, key, held_mask, match_out)`**（命中裁决，三层优先）：

1. 局部 `consider(binding, source, from_host)`：先判 `(binding.modifier_mask & held_mask) == binding.modifier_mask`（**必需修饰必须全部按住，多余修饰容忍**）；再算 `count = popcount(modifier_mask)`；仅当 `count > best_count` 时替换最佳候选（**同数量保留先到者**）。
2. 先登记 `object.mapping[key]` 的全部绑定（`source = object.object_name`、`from_host = true`）。
3. 再按 `children[object.object_name]` 的注册顺序，逐个登记子对象 `injected_active[key]` 的绑定（`source = 子对象名`、`from_host = false`）。
4. 无候选返回 `false`；否则填 `binding`/`source`/`from_host` 返回 `true`。

**`injected_rebuild(host_name)`**（全量重算某宿主的所有子对象注入）：

1. 宿主不存在返回。
2. `taken` 集合先登记宿主自身全部 `(key, mask)`。
3. 无子对象则返回（注意：此时**不会**清空任何子对象的 `injected_active`，因为提前返回）。
4. 按注册顺序逐子对象：先 `injected_active.clear()`，再逐条 `injected_declared`——`taken` 已有同 token → 告警“与已有映射冲突，已丢弃”并跳过；否则写入 `injected_active[key]` 并占位。

**`injected_resolve(host_name, child_name)`**（单子对象增量解析，供创建时用）：

1. 宿主/子对象任一不存在返回。
2. `taken` 先登记宿主自身绑定。
3. 再登记**注册顺序在目标子对象之前**的兄弟对象的现有 `injected_active`（遇到目标名即 `break`）。
4. `child->injected_active.clear()` 后按上述规则逐条解析。

两个函数共同保证：注入优先级 = 宿主自身 > 先注册的兄弟 > 后注册的兄弟；冲突以 `(key, mask)` 为粒度，不同掩码可共存。

**`listening_rebuild(host_name)`**：

1. 宿主不存在返回；`allowed` 收集宿主**自身映射表的主键**（不看掩码）。
2. 无子对象则返回。
3. 逐子对象遍历 `listening`，不在 `allowed` 的键位告警并 `erase`。
4. 只删不增：宿主后来新增的映射键**不会**自动补进子对象监听表。

### 4.10 `Input_Mapping/core/键位解析.cpp`

匿名命名空间（仅本编译单元可见）：

```cpp
const std::unordered_map<std::string, engine::Input_Key>& key_name_table(void);
const std::unordered_map<std::string, uint8_t>&           modifier_name_table(void);
std::string key_name_normalize(const std::string& name);
```

- `key_name_table()`：函数内 `static const` 表，首次调用时由 lambda 构建：字母 A..Z（编号 1..26）、数字 0..9（27..36）、符号 37..47（字符与英文键名双写法）、控制键 1..41、小键盘 1..16、鼠标 1..5、滚轮 1..2。键名一律**大写**。
- `modifier_name_table()`：`static const` 表，`SHIFT/LSHIFT/RSHIFT`→`0x01`；`CTRL/CONTROL/LCTRL/RCTRL/LCONTROL/RCONTROL`→`0x02`；`ALT/LALT/RALT`→`0x04`；`GUI/LGUI/RGUI`→`0x08`。**不含** `LMETA/RMETA` 等别名。
- `key_name_normalize(name)`：逐字符 `std::toupper(static_cast<unsigned char>(c))`，对非 ASCII 字符只做字节级变换。

公开转换函数实现要点见 §三 3.8；补充两点：

- `key_parse` 的数字分支先判 `is_number_unsigned()`（要求 `>0` 且 `<=UINT32_MAX` 且位域合法），再判 `is_number_integer()`（要求 `>0` 且位域合法），最后字符串分支；其他 JSON 类型一律 `false`。
- `modifier_parse` 先 `mask_out = 0`；`null` 直接返回 `true`；数组项字符串走 `modifier_name_table`，数字项走 `key_parse` 后要求 `modifier_mask_of != 0`；任一项失败立即 `false`（`mask_out` 可能残留下已或上的位，调用方均丢弃）。

### 4.11 `Input_Mapping/core/映射解析.cpp`

```cpp
bool input_mapping::binding_parse(const nlohmann::json& spec, Input_Key& key_out,
                                  Input_Binding& binding_out);
bool input_mapping::mapping_parse(const nlohmann::json& spec,
    std::unordered_map<Input_Key, std::vector<Input_Binding>>& table);
bool input_mapping::listening_parse(const nlohmann::json& spec, const Input_Object& host,
    std::unordered_set<Input_Key>& table);
```

**`binding_parse`**：非对象 → 拒；缺 `key` → 拒；`command` 缺失/非字符串/空 → 拒；`key_parse` 失败 → 拒。写 `command` 后先清空 `target` 与 `modifier_mask`，再可选解析 `modifiers`（失败即拒）与 `target`（非字符串忽略）。最后两条规则：`Enter` 无 `target` → 拒；`Escape` → 强制清空 `target`（即使配置给了）。

**`mapping_parse`**：`null` → `true`（不改表）；非数组 → `false`。用局部 `buffer` 累积；每项 `binding_parse` 失败置 `parsed=false` 但**继续扫描**（为了把后续告警都打出来）；同一主键若已有相同 `modifier_mask` → 告警“保留先注册项”并 `parsed=false`。最后 `parsed` 为假则整表拒（原表不变），否则 `table = std::move(buffer)`。

**`listening_parse`**：`null` → `true`；非数组 → `false`；逐项 `key_parse` 失败告警跳过；`!host.mapping_has(key)` 告警跳过（文案带键位数字）；最终总是提交 `buffer`。因此“监听表写错”不会让对象创建失败，只会少监听。

### 4.12 `Input_Mapping/core/轴解析.cpp`

```cpp
bool input_mapping::axis_parse(const nlohmann::json& spec,
                               std::unordered_map<std::string, Axis_Binding>& table);
input_mapping::Axis_Result input_mapping::axis_transform(const Axis_Binding& binding,
                               const double& raw_value, const double& dt);
```

**`axis_parse`**：`null` → `true`；非数组 → `false`。逐项：非对象或缺非空 `axis`/`source` → `parsed=false`；轴名重复 → 告警并 `parsed=false`；`mode` 缺省为 `"displacement"`，只接受 `"rate"`/`"displacement"`，其他 → `parsed=false`；`scale/deadzone/clamp` 仅在“字段存在且是数字”时覆盖默认值（类型不对则**静默保留默认**）；`invert` 同理（仅布尔生效）。最后 `parsed` 为假整表拒。

注意默认值本身有语义：`clamp = 1.0` 意味着**未配置 clamp 的轴会被钳到 ±1**；`scale = 1.0`、`deadzone = 0.0`、`invert = false`。

**`axis_transform`**：局部 `value = raw_value`；`deadzone > 0 && abs(value) < deadzone` → 0；`value *= scale`；`invert` → 取反；`clamp > 0 && abs(value) > clamp` → `value > 0 ? clamp : -clamp`；`result.value = value`、`result.delta = rate ? value * dt : value`。

### 5.5 所有权与生命周期

```
事件中转站的持有者（上层，未出现在本快照的 src/input 内）
  └── 负责为每个 Event_Terminal 绑定 Broker_Attacher（→ Event_Broker::attach）
      与 Evt_Sender（→ Event_Broker::receive），并每帧驱动 Focus_System::frame_begin()
  └── 持有 Focus_System（1 个实例）与 Input_Manager（1 个实例）   【推测：本模块内无实例化点】

Focus_System
  ├── event_terminal（值成员；不可拷贝 → 类禁止拷贝）
  ├── main_stack / modal_stack  （字符串栈，元素是对象名）
  ├── 5 张对象登记表
  └── 待生效槽

Input_Manager
  ├── event_terminal（值成员）
  ├── Object_Pool<Input_Object> objects
  │     └── Input_Object ×N
  │           ├── event_terminal（值成员；对象池原地移动重建依赖 Input_Object 的默认移动构造）
  │           ├── 四张键位表 + 轴表 + 轴状态 + 能力位 + 名字/宿主名
  │           └── acl_key（由 key() 一次性生成的兜底值）

```

生命周期规则：

- `Input_Object` 只由 `objects.build(Input_Object{})` 创建、`objects.unload(ID)` 回收；名字到 ID 的映射由 `name_index` 管；两者必须同时维护（`object_create`/`object_unload_single` 是仅有的两处）。
- 对象池 ID 与索引均以 **LIFO** 分配回收（`Object_Pool` 构造中 `set(Allocate_Order::LIFO)`），因此刚卸载的 ID 会被下一次 `build` 立即复用——这是“按 ID 重查”能等同于“对象重建”检测的前提，也是其风险（见 §六 D7）。
- `Focus_System` 的对象图完全靠 `ObjectLinked`/`ObjectDestroyed` 增量维护，不持有对象池指针，与 `Input_Manager` 生命周期无关（但事件顺序必须保证见 §六 D5）。

### 5.6 线程与同步

全模块无线程、无锁、无原子变量：`Event_Terminal::send` 直接调用已绑定的 `std::function`，`Event_Broker::receive` 直接调用 `receivers[key]`，一切状态变更都在发送方同步调用栈上完成。故假定单线程驱动，多线程调用 `attach()`/`frame_begin()`/事件发送即为数据竞争；发送事件可能在同一栈上回调本模块自身，形成重入（应对方式见 §六 D7）；没有事件队列，`Command`/`AxisState` 均即时广播。

## 六、模块设计 / 实现细节

### D1 接入前置：两个端口由“事件中转站持有者”绑定，本模块只做订阅

`Focus_System::attach` 与 `Input_Manager::attach` 都只 `bind(Port_ID::Evt_Receiver, ...)`，随后直接调用 `event_terminal.attach(name, acl_key)`。而 `Event_Terminal::attach` 在 `terminal_port.check(Port_ID::Broker_Attacher)` 为假时直接 `logger.error("事件中转站接入端口未绑定")` 并返回 `false`。同理，`event_terminal.send(...)` 在既无 `Evt_Sender` 也无 `Evts_Sender` 时返回 `false`。

结论：本模块隐含两条**外部装配前置**——

1. 上层必须对本模块两个 `event_terminal` 绑定 `Broker_Attacher`（落到 `Event_Broker::attach`）与 `Evt_Sender`（落到 `Event_Broker::receive`）；
2. 否则 `attach()` 返回 `false`（焦点订阅全部失效、`raw` 收不到），且 `focus_send`/`command_relay`/`focus_notify` 全部失败（只打 `logger.warn/error`，不崩溃）。

对比同层碰撞模块 `Collision_Proxy::attach`（`Engine/EngineSystem/src/collision/Collision_Proxy/core/事件交互.cpp`）：它显式检查 `Broker_Attacher` 再继续，并注明“接入入口由事件中转站的持有者注册”。本模块缺这一步检查，属实现差异，见【待确认：1】。

### D2 原始输入的锁存（held）与消费（consumed）

**锁存**：`Input_Manager::held_keys` 是**管理器级、跨帧**的物理按键集合，不是对象级状态。它只由 `held_update` 写，三路来源优先级从高到低：

1. 原始帧带数组型 `held`（权威快照）→ 清空后整体写入；随后的 `keys` 边沿仍继续应用（最终状态 = 快照 + 本帧边沿）。
2. 无权威快照且帧号跳变（`frame > last_frame + 1`）→ 清空（保守重同步），随后边沿继续增量。
3. 仅边沿增量 → 只做 `insert`/`erase`。

`frame` 缺省为 0；`frame == 0` 时既不更新 `last_frame` 也不触发跳变清空，因此**不发帧号的渲染层永远得不到自动重同步**。

**消费**：单帧内的“消费”由 `object_keys_process` 的局部 `consumed` 集合表达，粒度是 `Input_Key`：

- 组合命中后，主键进入 `consumed`；同时把**当前按住集合里属于该组合修饰位的物理键**也放入 `consumed`，从而抑制修饰键自身产出单键命令。
- 消费集合不跨帧保留：下一帧同一物理键若再出现按下沿，仍会产出命令（这是“无去抖”的直接原因，见 D10）。
- 抬起沿不参与消费，只影响 `held_keys` 与监听拷贝。

另有强约束：被闸门拦下的帧到不了 `object_map`，`held_update` 不执行（后果见 D17 与【待确认：17】）。

### D3 组合键（modifier）解析的两处优先级

**解析期**（`binding_parse` → `modifier_parse`）：`modifiers` 数组的每一项被折算成**规范化位**（左右合并），最终得到 4 位掩码；空/缺省为 0。`Enter` 必须有 `target`、`Escape` 强制清空 `target` 是解析期仅有的两条语义特判。

**运行期**（`binding_find`）：判定条件是“必需位全部按住”，即 `(binding.mask & held_mask) == binding.mask`，**不要求**多余修饰为空。因此：

- 配置 `Ctrl+S` 后按 `Ctrl+Shift+S` 仍会命中 `Ctrl+S`；
- 同时存在 `Ctrl+S` 与 `Ctrl+Shift+S` 时，`popcount` 较大者优先（按三键必中后者）；
- 若某键只有 `mask == 0` 的绑定，则无论按住什么修饰它都会触发——**“普通单键绑定”并不排斥修饰键**，除非同主键存在竞争的组合绑定。

**优先级三层**：修饰数量多者优先（`popcount`），同数量先到者优先，同数量同来源顺序中“宿主自身 > 注册早的子对象”。这由 `consider` 的 `count <= best_count` 跳过条件保证：后到的等分候选无法取代先到者。

**held_mask 取帧末状态**：`object_keys_process` 在 `held_update` 之后只算一次 `held_modifier_mask()`，故与该帧边沿的先后顺序无关；代价是“同帧内按下又抬起的修饰键”按最终状态判定。

### D4 轴值的死区、缩放、反相、钳制与“速率/位移”

`axis_transform` 的执行顺序是**死区 → 缩放 → 反相 → 钳制**，且死区作用在**原始值**上（不是缩放后）：

1. `deadzone > 0 && |raw| < deadzone` → 0（注意是严格小于，等于死区值不算死区）。
2. `value *= scale`。
3. `invert` → 取反。
4. `clamp > 0 && |value| > clamp` → 取符号侧 `±clamp`（对正负对称钳制）。

`rate` 与 `displacement` 的区别只体现在 `delta` 上：

- `rate = true`：`value` 被当作“每秒速率”，`delta = value * dt`；
- `rate = false`：`value` 被当作“本帧位移”，`delta = value`。

但 `object_axes_process` 把 `result.value` 写入 `axis_state`，且**不累加**：所以位移型轴的 `axis_state` 保存的是“上一帧的单帧位移”，不是累计位置；`object_axis_value_get` 返回的也是这个值。命名与语义存在偏差，见【待确认：6】。

`dt` 的兜底：`object_map` 先 `raw.value("dt", 1/60)`，再传 `dt > 0 ? dt : 1/60`；监听拷贝帧不带 `dt`，因此子对象轴恒定使用 1/60（见 D6）。

**来源解析**是字符串比较 + 动态查找，逐轴固定 5 个分支：`pointer.dx`/`pointer.dy`/`pointer.x`/`pointer.y`（需 `pointer` 是对象，否则 0），最后尝试 `axes[source]` 且必须是数字，否则 0。**未知来源不报错、不告警**，静默按 0 处理（配置写错只表现为轴恒 0）。

### D5 配置驱动映射表的构建顺序与“原子性”

`config_apply` 的语义是“只增改、不删”。单个对象的构建顺序（`object_create`）体现了三条设计决策：

1. **解析先行**：`mapping` → `added_keys` → `axes` → `listen` 全部在对象池分配之前完成，任一失败即驳回创建，池里不会出现“半初始化对象”。
2. **监听依赖宿主现状**：`listening_parse` 需要宿主对象当前的 `mapping`，因此监听表只能引用“宿主此刻已有”的主键；宿主后续新增键不会自动补进监听（`listening_rebuild` 只删不增）。
3. **注册即裁决**：对象入池后立刻 `injected_resolve(host, name)`（只按“宿主 + 更早兄弟”重算该子对象），而不是全量 `injected_rebuild`，避免每次创建子对象都重扫整棵（其实是单层）子树；卸载时反过来必须全量 `injected_rebuild(host)`，因为移走一个子对象会让被它压制的注入键重新可用。

`mapping_parse` 的“整表拒绝”与 `object_reload` 的“提前 return”会让更新行为不对称：

- `Reload`：映射解析失败 → 整个重载中止（轴表与能力位都不更新）；
- `Config.Load` 的已存在对象：`object_update` 中映射解析失败 → 只告警，继续处理轴表与能力位。

见【待确认：8】。

### D6 监听（listening）：子对象为何能“旁听”宿主按键

设计意图：子对象不参与焦点竞争，但仍需感知某些键（典型是 UI 面板要响应快捷键）。机制由两点组成：

1. 准入：`listen` 中的键必须是宿主**自身映射表**的主键（`mapping_has`，与掩码无关）。
2. 投喂：宿主处理帧时，对每条边沿（含抬起）遍历全部子对象，凡 `listening` 含该键者都收到一条**缩小的原始帧**（`frame` + 单条 `keys`）。

由此：子对象会为同一次按下产出**自己的**命令（`sender` 为子对象名），即使该键已在宿主层被组合消费；拷贝**不带** `dt`/`pointer`/`axes`/`text_mode`，故子对象轴全取 0 并每帧发全 0 `AxisState`（见【待确认：4】），且不受宿主文本模式挂起影响（宿主文本模式下不产生拷贝）；拷贝**不检查子对象 `enabled` 与它是否为当前焦点**，禁用或非焦点的子对象照样收到并产命令（`enabled` 只在焦点闸门检查）。

### D7 重入安全：为什么到处“按 ID 重查”和“复制容器”

一次 `send` 会同步进入订阅者；订阅者的合法反应包括发送 `Destroy`（级联卸载对象）甚至 `Create`（重建同名对象）。因此：

- `object_keys_process` 在每个命令发送后 `source = object_find(ID)`；为空即终止。但 `Object_Pool` 的 LIFO 分配意味着**刚卸载的 ID 可能被立即复用**，此时 `object_find(ID)` 会返回一个“新对象”，代码无法区分“原对象还活着”和“原 ID 被新对象复用”。同理，`object_map`/`object_axes_process` 的“计算后重查”也有此风险（见【待确认：7】相关风险说明）。
- `object_copy_to_children` 先把 `children[source_name]` 复制成 `vector<string>` 再遍历，避免循环中容器被改。
- `object_dispatch`/`command_relay` 只按名/编号重新查，不持有跨调用的对象指针。
- 关键反例：`object_keys_process` 先用 `child_it = children.find(source_name)` 收集 `copies`，这段循环内不发事件，是安全的；但 `child_it` 之后不再使用，避免了迭代器失效。
- `object_create` 的 `[this, ID]` 捕获刻意避开对象地址：`objects` 是 `vector`，`build` 可能扩容搬迁元素，捕获裸指针会悬空。

### D8 焦点模态闸门的拦截顺序（四张表）

**原始帧（`raw_process`）**：活跃对象空 → `enabled`（缺表视为允许）→ 模态（无模态直接放行）→ 放行转发。

**语义命令（`command_process`）**：`command` 字段有效 → 发送者模态 → 发送者 `enabled` → `Escape` / `Enter` 语义分派。

**焦点请求（`target_request`，`MouseFocus` 与 `Command Enter` 共用）**：目标空 → 目标已登记 → 目标 `focusable` → 目标模态 → 主/子分派。

**子焦点请求（`child_focus_process`）**：`child` 空分支只校验 `host == current_main`；非空分支额外校验 `focusable(child)`；**不过模态闸门**。其安全性完全依赖“宿主必须是当前主对象”，因为当前主对象若在模态外，其子对象也必在模态外（子对象集合是静态归属）。

对比可见，闸门在“原始输入”和“命令”两条产线各拦一次，构成**双闸门**：外部输入进不来，内部命令也出不去。这也解释了为什么“命令来自模态外对象”会被丢弃——`Command` 的 `sender` 是产出对象，而产出对象必须曾经收到过 `Forward`（已在焦点闸门内）。

### D9 模态的“进入”与“隔离”是两个独立动作

`modal_push_process` 只做两件事：压栈 + 广播。它**不改变焦点**。于是存在一个必然后果：

- 压栈瞬间，若当前活跃对象不在新模态根的子树内，下一帧 `raw_process` 直接丢弃整帧输入；
- 想恢复输入，必须由外部显式发 `MouseFocus`（或 `Command Enter`）把焦点移到模态子树内；
- 模态根自身也必须在 `host_of` 中有登记（即已经收到过 `ObjectLinked`），否则压栈被拒——这要求模态对象必须先 `Create` 成功。

配套的两个细节：模态栈允许“同根重复压栈”被静默忽略（`modal_stack.back() == object` 直接返回），也允许压入非根对象（栈顶即新的模态根，等于嵌套模态）；`Escape` **不会弹模态栈**，只能显式 `ModalPop`（见【待确认：12】）。对象销毁会把它从模态栈中彻底抹掉（`std::erase` 全删），并广播焦点变化。

### D10 重复触发抑制：只有“帧内”去重，没有“跨帧”去抖

已有抑制：

1. 同一帧同一键出现多条 `pressed` 边沿：第一轮命中后 `consumed.insert(key)`，第二条被跳过（抬起沿不产命令）。
2. 组合 vs 单键：第一轮只处理 `modifier_mask != 0`，第二轮才处理 0，天然“组合优先”。
3. 组合所需的物理修饰键被 `consumed` 抑制，不会同时产出它们各自的单键命令。

不存在的抑制：

1. 跨帧不去抖：渲染层若因平台按键自动重复而每帧发一条 `pressed` 边沿，本模块每帧都会产出一条命令。
2. 没有“按住状态到命令”的边沿检测（例如“从 held 集合推断新按下”）：命令完全依赖输入帧是否显式给出按下沿。
3. 没有时间窗（最小间隔）抑制。

这使“连发”语义事实上由渲染层决定（见【待确认：10】）。

### D11 注入（added_keys）与冲突裁决

子对象想“在宿主上新增按键”但不能覆盖宿主已有功能，于是引入注入声明与裁决：

- 声明：`added_keys` 经 `mapping_parse` 解析成 `injected_declared`（结构与自身映射表相同）。
- 裁决粒度为 `binding_token(key, modifier_mask)`：`(X,0)` 与 `(X,CTRL)` 可共存；优先级为宿主自身 → 注册早的子对象 → 注册晚的子对象，冲突方告警丢弃。
- 生效表 `injected_active` 只存被接受的条目；`binding_find` 只在**宿主**处理帧时读它（子对象处理自己的帧时读自己的 `mapping`）。
- 命中注入绑定后命令 `sender` 仍是宿主（`source_name`），`Binding_Match.source`/`from_host` 算出但未使用，故焦点侧的模态/启用校验校验的是宿主（见【待确认：5】）。

### D12 只增不删的配置语义与“热重载残留”

`config_apply` 只 create/update，**没有“配置中不存在则销毁”**：删除必须显式 `Destroy`；配置删项后旧对象仍在且仍参与映射与焦点图；`object_update` 也不读 `host`/`name`，无法“搬家”。见【待确认：9】。

### D13 事件字段名的双轨制

`Common/输入事件.h` 声称“标签与载荷字段名集中于此，避免映射侧与焦点侧各写一份字符串导致漂移”，但实现中大量字段名以字面量写死，且有些字段根本没有常量：

分三类：一是**有常量却未用**（`text_mode`、`frame`、`dt`、`keys`、`key`、`pressed`、`command`、`target`、`object`）；二是**根本没有常量**（`main`/`child`/`modal`/`text`/`active`/`values`/`deltas`/`name`/`host`/`mapping`/`added_keys`/`axes`/`listen`/`objects`/`axis`/`source`/`mode`/`scale`/`deadzone`/`clamp`/`invert`）；三是**同名不同键**（见下句）。

且**创建与重载的字段名不一致**：`Create` 用 `"name"`，`Destroy`/`Reload` 用 `"object"`（`event_protocol::field_object` 与 `input_event::field_object` 都等于 `"object"`）。见【待确认：2】。

### D14 文本模式的判定与传播

判定：`text_mode = (活跃对象是 text_sink) && (活跃对象未禁用)`，在 `text_mode_refresh` 中重算，仅在值变化时广播 `TextMode`。触发点只有三处：`transition_apply`（焦点变化后）、`object_linked_process`、`object_destroyed_process`。

传播：焦点在 `raw_process` 中把当前 `text_mode` 布尔写进转发载荷；映射系统据此**挂起键位映射**（`object_keys_process` 不执行），但**继续更新按住集合与轴**。文本会话则走另一条：`TextSession` → 焦点（要求 `text_mode` 为真）→ `TextRoute` → 管理器 → 对象终端 → `Text` 广播。

一个不对称点：`text_session_process` 只检查 `text_mode`，**不检查**活跃对象的 `enabled` 与模态（与 `raw_process` 的三重检查不同）。见【待确认：11】。

### D15 性能取舍

每帧多次整帧 json 拷贝（`raw_process` 一份、`raw_forward` 再一份并 `erase`），`object_map` 又按 `value()` 多次查找；帧越大（尤其 `held` 数组）越贵。`binding_find` 对每个按下键遍历宿主绑定 + **全部子对象**的 `injected_active[key]`（`children` 必须是 vector 以保证顺序），复杂度 O(按下数 × 子对象数 × 单键注入数)。`held_modifier_mask` 每对象帧一次 O(按住数)；`object_within_modal` 每次闸门一次子树 DFS；轴来源靠 5 路字符串比较；`std::erase(main_stack/modal_stack, name)` 线性但栈深很小。

### D16 错误处理策略（统一模式）

统一模式：准入失败即丢弃 + 一条日志（结构性缺失/非法配置 `logger.warn`，内存/事件构造失败 `logger.error`），不抛异常、不部分生效；查询与轴来源、缺失能力位表项一律“默认值 + 静默”（只有焦点侧显式拒绝才告警），代价是对象名拼错时上层几乎无从察觉；内存统一 `new(std::nothrow)`；失败**不撤销已完成步骤**（`object_reload` 轴表失败时映射表已替换，不是事务语义）。

### D17 被丢弃帧的副作用缺口

`raw_process` 的三道闸门（空活跃对象、禁用、模态外）都在进入映射系统之前返回，故整帧状态全不更新：`held_keys` 不刷新、`last_frame` 不推进、轴不计算也不广播。后果：被拦截期间按下的键（若无权威 `held` 且帧号连续）会滞留在下一次判定里；轴值在拦截期间“冻结”在上一帧，而非归零。

### D18 无聚合装配、无实例化点

23 个文件里没有 `main`、没有装配类、没有对 `Focus_System`/`Input_Manager` 的 `new` 或成员声明，也没有 `frame_begin()` 的调用者；两个运行包互不包含，且 `mapping/输入映射系统运行包.h` 连 `Input_Manager` 都不含。故上层必须自行持有两个对象、绑定端口、每帧驱动 `frame_begin()`；见【待确认：13】。

### D19 键位编码“单一真源”的边界

编码定义在 `输入类型.h`、名称表在 `键位解析.cpp`、修饰判定又在 `modifier_mask_of` 重新枚举 control 34..41，三处必须同步修改。当前一致：`LSHIFT/RSHIFT` = 34/35、`modifier_mask_of` 覆盖 34..41；名称表最大编号 41，`default: return 0` 覆盖 42+；名称表只有 `GUI`，没有 `META`/`WIN`/`SUPER` 别名。

## 七、模块运行链路详例

### 7.1 链路一：一次键盘事件 → 语义命令（完整端到端）

**前提**：`Focus_System::attach()`、`Input_Manager::attach()` 均已成功；宿主对象 `Overworld`（主对象）已 `Create` 并收到焦点；配置含 `{key:"W", command:"MoveForward"}` 与 `{key:"X", modifiers:["CTRL"], command:"Cut"}`；`Overworld` 有一个监听 `W` 的子对象 `Hud`。

1. **渲染层**在帧 `N` 构造事件：`Event("", "", "Input", "Raw")`，载荷 `{frame:N, dt:0.0166, keys:[{key:"W", pressed:true}], held:["W"], pointer:{...}, axes:{...}}`，送中转站。`Event_Broker::receive` 因 `receiver` 空，按 `("Input","Raw")` 的订阅集合广播。
2. **`Focus_System::event_process`**：`evt` 非空、`category == "Input"` → 匹配 `raw` → `raw_process(evt)`。
3. **`raw_process`**：`current_child` 为空 → `target = current_main = "Overworld"`；`enabled_of["Overworld"]` 为真 → 通过；`modal_stack` 空 → `object_within_modal` 恒真 → 通过。
4. 复制载荷，写 `object="Overworld"`、`text_mode=false`；`focus_send("Forward", config, "Input_Manager")` → `event_terminal.build("Focus_System","Input_Manager","Input","Forward")` → `send` → 中转站定向投递到 `Input_Manager`（`receiver` 非空，只查 `mapping["Input_Manager"]`）。
5. **`Input_Manager::event_process`**：非 `Config/Load`，`category == "Input"`，`tag == "Forward"` → `raw_forward(evt)`。
6. **`raw_forward`**：`object` 字段有效 → `object_find("Overworld")` 命中；复制载荷并 `erase("object")`；`object->event_terminal.build("Focus_System","Overworld","Input","RawFrame")`；`object->event_terminal.receive(raw_evt)`。
7. **对象终端**的 `Evt_Receiver`（`object_create` 时绑定的 `[this, ID]`）被同步调用 → `object_dispatch(ID, raw_evt)`：`tag == RawFrame` → `object_map(ID, evt->config)`。
8. **`object_map`**：`frame=N`、`dt=0.0166`、`source_name="Overworld"`、`text_mode=false`。
9. **`held_update`**：有 `held` 数组 → `held_keys` 整体替换为 `{W}`；`last_frame=N`、`frame_seen=true`；随后边沿 `W pressed` 再 `insert`（幂等）。
10. 非文本模式 → **`object_keys_process(ID, raw)`**：`keys` 是数组；`child_it = children.find("Overworld")` 命中 `[Hud]`；边沿 `W` 解析成功；`Hud.listening` 含 `W` → 登记一条拷贝任务；`pressed=true` → 登记 `presses=[W]`。
11. **先派发拷贝**：`object_copy_to_children(ID, "Overworld", W, edge, N)` → 构造 `{frame:N, keys:[{key:"W",pressed:true}]}` → `Hud` 终端 `receive` → `Hud` 的 `object_dispatch` → `Hud` 自己的 `object_map`（`held_update` 再执行一次、`keys` 处理、若 `Hud` 有轴绑定则发全 0 `AxisState`）。`Hud` 若自身映射 `W`，此时会产出一条 `sender="Hud"` 的命令。
12. **回到宿主**：按 `ID` 重查 `Overworld`；`held_mask = held_modifier_mask() = 0`。
13. **第一轮**：`binding_find(Overworld, W, 0, match)`；`W` 的候选绑定中 `MoveForward`（mask 0）命中但 `modifier_mask == 0` → 跳过（留第二轮）；无组合候选。
14. **第二轮**：再次 `binding_find` → 命中 `{command:"MoveForward", mask:0}` → `commands.push_back`、`consumed.insert(W)`。
15. **命令派发**：重查 `source`；`build("Overworld","","Input","Command")`；写 `command="MoveForward"`、`key=W`、`frame=N`（无 `target` 不写）；`source->event_terminal.send(cmd, acl_key)` → 触发对象终端 `Evt_Sender` 的 lambda → **`command_relay(cmd)`**。
16. **`command_relay`**：`command != "Enter"` → 直接 `event_terminal.send(cmd, acl_key)`（管理器终端）→ 中转站广播 `("Input","Command")`，广播跳过发送者自身（`sender="Overworld"` 不在中转站登记，故不跳过任何人）。
17. **订阅者**：游戏逻辑收到 `Command{command:"MoveForward", key, frame}` 执行动作；`Focus_System` 也收到（它订阅了 `command`）→ `command_process`：`command` 字段有效；`object_within_modal("Overworld")` 真；`enabled` 真；`command != "Escape"` 且 `!= "Enter"` → **忽略**。
18. **轴**：`object_axes_process` 按 `Overworld` 的轴绑定计算，写 `axis_state`，`build("Overworld","","Input","AxisState")` 后 `send` → 广播 `{frame, values, deltas}`。若此刻有订阅者因动作销毁了 `Overworld`，第 11 步后的重查会把 `source` 置空并终止。
19. **副作用清单**：`held_keys` 增加 `W`；`Hud` 收到一条键位拷贝；`Command` 与 `AxisState` 各广播一次；焦点不变（`MoveForward` 不是 `Enter`/`Escape`）。

**若本帧按下的是 `Ctrl+X`（且按住集合里已有 `Ctrl`）**：第 13 步第一轮命中 `{command:"Cut", mask:CTRL}`（`popcount=1 > -1`），`commands` 收 `Cut`，`consumed` 收 `X` 与 `Ctrl`（`Ctrl` 属于组合所需修饰）；第二轮跳过 `X` 与 `Ctrl`。若 `Ctrl` 自身也有单键绑定，则它不会产出命令。

### 7.2 链路二：焦点转移（含模态拦截）

场景：`Overworld`（主）→ 其子对象 `Hud`；再打开模态对话框 `Dialog`（不在 `Overworld` 子树内）。

**A. 打开模态**

1. 游戏逻辑发 `ModalPush{object:"Dialog"}`（`Dialog` 必须已 `Create` 且已收到过 `ObjectLinked`）。
2. `Focus_System::modal_push_process`：`object` 非空 → `host_of.count("Dialog")` 命中 → 栈顶不等于它 → `modal_stack = ["Dialog"]` → `focus_changed_publish()` 广播 `{main:"Overworld", child:"Hud", modal:"Dialog", text:false}`。
3. 此时焦点仍在 `Overworld/Hud`。

**B. 模态外输入的拦截**

4. 渲染层发 `Raw`。`raw_process`：`target = "Hud"`（`current_child` 非空）；`enabled` 通过；`object_within_modal("Hud")`：模态根 `Dialog`，`Hud` 不是 `Dialog` 也不在 `children_of["Dialog"]` 子树 → `false` → 告警“活跃对象在模态闸门外，原始输入已丢弃”，**整帧丢弃**（`held_keys` 不更新、轴不更新）。
5. 同理，游戏逻辑若试图发 `Command{command:"Enter", target:"Hud.Sub"}`，`command_process` 第 2 步 `object_within_modal(sender)` 失败 → 丢弃。

**C. 把焦点搬进模态**

6. UI 发 `MouseFocus{object:"Dialog"}` → `target_request("Dialog")`：非空 → `host_of` 命中 → `focusable` 通过 → `object_within_modal("Dialog")`：`name == modal_stack.back()` → `true` → 因 `host_of["Dialog"]` 为空 → `main_push_request("Dialog")`：`Dialog != current_main` → `pending_main="Dialog"`、清 `pending_child`、`pending_valid=true`。
7. 下一帧 `frame_begin()` → `transition_apply()`：无弹栈；`pending_main` 非空且栈顶不是它 → `std::erase(main_stack,"Dialog")`（历史同名重入时先删）→ `push_back("Dialog")`；`current_main="Dialog"`；因主对象变化且无待生效子对象 → `current_child.clear()`；`text_mode_refresh()`；主/子变化 → `focus_changed_publish()` 广播 `{main:"Dialog", child:"", modal:"Dialog", text:...}`。
8. 之后 `Raw` 的 `target="Dialog"`，`object_within_modal("Dialog")` 为真 → 放行。

**D. 子焦点与 Escape**

9. `Dialog` 的子对象 `Dialog.OK` 请求接管：可发 `ChildFocus{host:"Dialog", child:"Dialog.OK"}` 或 `Command{command:"Enter", target:"Dialog.OK"}`（后者由 `target_request` 走“宿主 == current_main → `child_request`”）。`child_focus_process` 校验 `host == current_main` 与 `focusable_of["Dialog.OK"]`，通过 → `child_request("Dialog.OK")` → 下一帧 `current_child` 生效 → `focus_changed_publish()`。
10. 按 `Escape`：`Enter` 的反向路径——`Command{command:"Escape"}` → `command_process` 通过模态与启用检查 → `main_pop_request()`：`main_stack.size()` 为 2（`["Overworld","Dialog"]`）≥ 2 → `pending_pop=true`、清 `pending_main/pending_child` → 下一帧 `transition_apply` 弹栈 → `current_main="Overworld"`；由于主对象变化且没有待生效子对象 → `current_child` 被清空（`Hud` 失去焦点，回到 `Overworld` 自身）；此时模态栈仍为 `["Dialog"]`，所以**下一帧 `Raw` 仍然被拦截**——必须再发 `ModalPop`。
11. `ModalPop` → `modal_pop_process` 忽略参数 → `pop_back()`（栈空）→ `focus_changed_publish()`。此后 `raw` 正常放行。
12. 若在模态期间 `Dialog` 被 `Destroy`：`object_unload_single` 先发 `ObjectDestroyed{object:"Dialog", host:""}`；`object_destroyed_process` 从 `main_stack` 与 `modal_stack` 全删 `Dialog`、同步 `current_main`、重算文本模式，并因焦点/模态变化广播 `FocusChanged`。

### 7.3 链路三：配置加载 → 映射表重建 → 焦点图建立

1. **配置源**发 `Config/Load`，载荷：
   ```json
   {"objects":[
     {"name":"Overworld","focusable":true,"enabled":true,
      "mapping":[{"key":"W","command":"MoveForward"},
                 {"key":"X","modifiers":["CTRL"],"command":"Cut"}],
      "axes":[{"axis":"look_x","source":"pointer.dx","scale":0.1,"deadzone":0.01,"clamp":1.0}]},
     {"name":"Hud","host":"Overworld","listen":["W","Escape"],
      "mapping":[{"key":"ESCAPE","command":"CloseHud"}],
      "added_keys":[{"key":"Q","command":"Hud.Toggle"}]},
     {"name":"Dialog","focusable":true,"enabled":false,
      "mapping":[{"key":"ENTER","command":"Enter","target":"Dialog.OK"}],
      "added_keys":[{"key":"Q","command":"Dialog.Confirm"}]}
   ]}
   ```
2. **`Input_Manager::event_process`**：`(category,tag)==("Config","Load")` → `config_apply`。
3. **`config_apply`**：`objects` 是数组 → 逐项 `name` 有效。
4. **`object_create("Overworld")`**：`host` 空 → 跳过宿主校验；`mapping_parse`：`W`→`{MoveForward,0}`、`X`→`{Cut,CTRL}`，无重复 `(key,mask)`，成功；`added_keys` 缺省；`axes` 由 `axis_parse` 生成 `look_x` 绑定（`rate=false`、`scale=0.1`、`deadzone=0.01`、`clamp=1.0`）；`listen` 缺省。`objects.build` 分配 ID，写字段，绑定两端口，`name_index["Overworld"]=ID`。`object_state_notify` → `ObjectLinked{host:"",focusable:true,enabled:true,text_sink:false}` 定向焦点系统 → `object_linked_process` 登记三张能力表；因 `main_stack` 空、`current_main` 空、`pending_valid` 假 → `main_push_request("Overworld")`（**首个主对象自动获焦，下一帧生效**）。
5. **`object_create("Hud")`**：`host="Overworld"` 存在且为主对象 → 通过；`mapping_parse` 得到 `ESCAPE→{CloseHud,0}`；`added_keys` 得到 `Q→{Hud.Toggle,0}`；`listen` 走 `listening_parse`，以宿主**当前** `mapping` 为准：`W` 在（保留），`Escape` 不在（丢弃并告警）；对象入池后 `children["Overworld"]=["Hud"]`，`injected_resolve("Overworld","Hud")`：`taken` 先收宿主 `(W,0)`、`(X,CTRL)`；目标子对象的 `(Q,0)` 不在 `taken` → 写入 `Hud.injected_active[Q]` 并占位；`ObjectLinked{host:"Overworld",...}` → 焦点登记 `children_of["Overworld"]={Hud}`。
6. **`object_create("Dialog")`**：`mapping` 含 `Enter` 且有 `target="Dialog.OK"` → 通过（注意 `Dialog.OK` 此刻还没创建，解析期**不校验目标是否存在**）；`enabled=false`；`injected_declared` 含 `(Q,0)`；无宿主 → `host_of["Dialog"]=""`；`ObjectLinked` 使焦点登记 `enabled_of["Dialog"]=false`。`object_create("Dialog.OK")` 若随后出现，`host="Dialog"` 是主对象 → 允许，`children_of["Dialog"]={Dialog.OK}`。
7. **热重载**：再次 `Config/Load` 且 `Overworld.mapping` 改为 `[{key:"W",command:"MoveFast"}]` → `object_update`：`mapping_parse` 成功整体替换（旧的 `X/Cut` 消失）；`axes` 缺省不动；能力位缺省不动；`injected_rebuild("Overworld")` 重算 `Hud` 的注入（`Q` 仍不冲突 → 保留）；`listening_rebuild("Overworld")`：`Hud.listening={W}` 仍合法 → 保留（`Q` 不会自动加入）。
8. **重载失败**：若 `Overworld.mapping` 写成 `[{key:"W"}]`（缺 `command`）→ `mapping_parse` 返回 `false` → `object_update` 告警“已保留旧表”，继续处理轴/能力位；若同样的事件走 `Reload` 路径，则 `object_reload` 会提前 `return`，轴与能力位都不更新。
9. **副作用清单**：`objects` 池三条（或多条）记录、`name_index`、`children`（注册顺序 `["Hud"]`）、`Hud.injected_active[Q]`、`Hud.listening={W}`、焦点侧 5 张表、首个主对象在下一帧成为 `current_main`。

### 7.4 链路四：文本会话三跳

1. 渲染层在文本模式下（已收到 `TextMode{active:true}`）发 `TextSession{ch:"a", ...}`。
2. `Focus_System::event_process` → `text_session_process`：`text_mode` 为真 → 通过；`target = current_child`（假设 `Dialog.Edit`）非空；复制载荷写 `object="Dialog.Edit"`；`focus_send("TextRoute", config, "Input_Manager")`。
3. `Input_Manager::event_process` → `text_forward(evt)`：`object` 有效 → 对象存在；复制载荷 `erase("object")`；`build("Focus_System","Dialog.Edit","Input","TextSession")`；`object->event_terminal.receive(...)`。
4. 对象终端 `Evt_Receiver` → `object_dispatch(ID, evt)`：`tag == TextSession` → `build("Dialog.Edit","","Input","Text")`，`config = evt->config`，`send(text_evt, object->acl_key)` → 对象 `Evt_Sender` → `command_relay` → 不是 `Enter` → 管理器终端 `send` → 广播 `Text`。
5. 订阅者（文本控件/业务逻辑）收到 `{ch:"a", ...}`；本模块不解释内容。
6. 同一帧的 `Raw` 若到达：`object_map` 中 `text_mode=true` → `held_update` 仍执行、`object_keys_process` 被跳过、轴仍计算；因此文本模式下“快捷键被挂起，但鼠标视角仍工作”。

### 7.5 链路五：监听子对象的命令归属

1. 帧 `N`，`Overworld` 收到 `{keys:[{key:"W",pressed:true}]}`（同 7.1 第 10 步）；`object_keys_process` 收集 `copies`（`Hud` 监听 `W`）。
2. `object_copy_to_children` 为 `Hud` 构造 `{frame:N, keys:[{key:"W",pressed:true}]}` 并 `receive` → `Hud` 自己的 `object_map`：`dt` 兜底 1/60、`text_mode` 兜底 false、`held_update` 用同帧号再次应用该边沿（幂等）、`Hud` 自身 `mapping` 若含 `W` 则产出 `sender="Hud"` 的 `Command`；若 `Hud` 有轴绑定，因缺 `pointer`/`axes` 全取 0 并广播全 0 `AxisState`。
3. 回到宿主，宿主命令按 7.1 第 13 步产出。**结果**：一次按键可产生“宿主命令 + 每个监听子对象各自的命令”，顺序为“拷贝（子）先、宿主命令后”；若只想让宿主响应，子对象不应在自身 `mapping` 中重复配置该键（监听表不阻止同名映射）。

以下正文集中说明 §三～§七 中以【待确认：N】标记的疑点。标记点只留编号，详情在此。

**【待确认：1】接入端口的前置绑定责任归属**
`Focus_System::attach` 与 `Input_Manager::attach` 都没有检查/绑定 `Port_ID::Broker_Attacher` 与 `Port_ID::Evt_Sender`；而 `Event_Terminal::attach` 要求 `Broker_Attacher` 已注册、`Event_Terminal::send` 要求 `Evt_Sender` 或 `Evts_Sender` 已注册。同层 `Collision_Proxy::attach` 会先 `check(Port_ID::Broker_Attacher)` 并注明“接入入口由事件中转站的持有者注册”。因此本模块的正确装配顺序（谁在什么时机为这两个终端绑定两个端口）在快照 `src/input` 内**无任何依据**；若漏绑，`attach()` 返回 `false` 且所有发送静默失败（只剩日志）。

**【待确认：2】事件字段名的双轨制与 Create/Reload 字段不一致**
`Common/输入事件.h` 声明“字段名集中于此”，但实现大量使用字面量（清单见 §六 D13）。其中两处会造成实际歧义：`Create` 读 `"name"`，而 `Destroy`/`Reload` 读 `"object"`；`Config.Load` 的对象项又用 `"name"`。此外 `FocusChanged`/`TextMode`/`AxisState` 的载荷键（`main`/`child`/`modal`/`text`/`active`/`values`/`deltas`）没有常量，只能靠约定。是否应统一到常量，需设计确认。

**【待确认：3】`transition_apply` 可能留下陈旧 `current_child`**
若同一次请求序列为“切主对象 + 指定一个不属于新主对象的子对象”且 `pending_child` 非空，则第 6 步不会清 `current_child`（条件要求 `pending_child.empty()`），第 8 步发现子对象非法只告警并把 `pending_child` 清掉，`current_child` 仍保留**旧主对象**的子对象名。随后 `raw_process` 会把原始输入投给这个已不属于当前主对象的子对象（`enabled` 与模态仍会拦截，但归属校验缺失）。该路径可通过 `ChildFocus{host:旧主, child:旧子}` 与 `MouseFocus{新主}` 同帧组合触发。

**【待确认：4】监听拷贝帧缺 `dt`/`pointer`/`axes`/`text_mode`**
`object_copy_to_children` 只写 `frame` 与 `keys`。后果：子对象 `object_map` 的 `dt` 兜底 1/60、`text_mode` 兜底 false、轴来源全缺失 → 所有轴绑定得到 `raw_value=0` 并每帧广播全 0 的 `AxisState`（覆盖子对象自己的轴状态）。若子对象确有轴需求，这是可观察的功能缺失；若设计上子对象不该有轴，则应禁止子对象配置 `axes`。

**【待确认：5】注入绑定命中后的 `sender` 归属与 `Binding_Match` 未用字段**
`binding_find` 计算了 `match.source` 与 `match.from_host`，但 `object_keys_process` 只取 `match.binding`，命令一律以 `source_name`（宿主）为 `sender`。因此：注入绑定（子对象声明）产出的命令在焦点侧的模态/启用校验针对**宿主**；`Input_Manager::command_relay` 的“Enter 目标是自家子对象”判定也针对宿主。若子对象自身被 `enabled=false`，其注入绑定仍能触发（因为校验的是宿主）。

**【待确认：6】位移型轴的 `value`/`delta` 语义与 `axis_state` 不累加**
`axis_transform` 对 `rate=false` 返回 `delta=value`，`object_axes_process` 把 `value` 覆盖写入 `axis_state`，不累加。于是 `object_axis_value_get` 对位移型轴返回“上一帧单帧位移”，配置名 `displacement` 与“位置”直觉不符。需确认是否本意（每帧增量）还是应为累计位置。

**【待确认：7】`values.empty()` 分支不可达与“ID 复用”的重查语义**
`object_axes_process` 中 `values` 在 `axis_binding` 非空时必然被逐轴写入，末尾 `if (values.empty()) return;` 不可达。更实质的是：`object_keys_process`/`object_axes_process`/`object_map` 在回调后按 `ID` 重查以检测“对象已销毁”，但对象池 LIFO 会立即复用刚释放的 ID，`object_find(ID)` 可能返回**新建的同 ID 对象**，代码无法区分。是否存在“回调内立刻重建同 ID 对象”的实际场景，需确认。

**【待确认：8】`object_reload` 与 `object_update` 的失败语义不一致**
`object_reload`：`mapping` 解析失败 → 立即 `return`，轴表与能力位不更新；`axes` 解析失败 → 同样立即 `return`，能力位不更新。`object_update`：两处失败都只告警并继续。两路径服务于同类需求（外部 `Reload` 事件 vs `Config.Load` 热更新），行为差异是否为有意设计需确认。

**【待确认：9】配置无删除语义、`object_update` 不改 `host`**
`config_apply` 只 create/update，不清理配置中缺失的对象；`object_update` 完全不读 `name`/`host` 之外的归属字段，无法把子对象迁移宿主。若配置是“权威全量清单”，当前实现会留下幽灵对象。

**【待确认：10】跨帧重复按下沿不去抖**
模块内没有任何时间窗/边沿去重，命令产出完全依赖输入帧显式的 `pressed` 边沿；平台按键自动重复若被渲染层逐帧转成 `pressed=true`，就会逐帧触发命令。需确认“连发”的归属层（渲染层口径）。

**【待确认：11】文本会话通道跳过 `enabled` 与模态检查**
`text_session_process` 只判 `text_mode`，不判活跃对象的 `enabled` 与模态；而 `text_mode_refresh` 的判定已包含 `enabled`（禁用对象不会让 `text_mode` 为真）。两者在“文本模式为真之后对象被禁用”的时序下会短暂不一致；另外模态外对象理论上也能通过 `TextRoute`（若其为活跃对象，模态会同时拦 `Raw` 但不拦 `TextRoute`）。

**【待确认：12】`Escape` 不弹模态；`ModalPop` 无参数**
`command_process` 的 `Escape` 只走 `main_pop_request`，模态需要外部显式 `ModalPop`；`modal_pop_process` 忽略参数与 sender，任何能发 `Input/ModalPop` 的订阅者都能弹栈。是否为预期的权限模型需确认。

**【待确认：13】无聚合头、无实例化点、无帧驱动点**
`src/input` 内没有把 `Focus_System` 与 `Input_Manager` 装配到一起的“输入系统运行包”，两个运行包互不包含；也没有任何 `new`/成员声明/`frame_begin()` 调用点。`mapping/输入映射系统运行包.h` 名为“输入映射系统”，却不包含 `Input_Manager` 自身（需使用方另行包含 `输入管理器.h`）。上层持有与驱动方式需确认。

**【待确认：14】焦点系统对 `Raw` 的发送者不做校验**
`raw_process`/`mouse_focus_process`/`modal_push_process` 都不看 `evt->sender`，任何能发对应标签的订阅者都能驱动输入与焦点决策。安全模型依赖“中转站只有引擎内部模块在用”。

**【待确认：15】映射表禁止“同键同掩码多绑定”，注入裁决同粒度**
`mapping_parse` 与 `injected_rebuild`/`injected_resolve` 都以 `(key, mask)` 为冲突粒度，因此“同键同组合绑两个动作”不可表达，只能靠多个订阅者消费同一条 `Command`。是否为有意限制需确认。

**【待确认：16】监听键位准入用“主键存在”而非“任何掩码存在”**
`listening_parse`/`listening_rebuild` 只看 `mapping_has(key)` 的主键。于是子对象可监听“宿主只有 `Ctrl+X`”的 `X`，裸按 `X` 也收到拷贝，而宿主只在按住 Ctrl 时才产命令。语义是否如预期需确认。

**【待确认：17】被闸门拦截的帧不刷新按住状态**
`held_update` 只在 `object_map` 内调用，而 `object_map` 仅在闸门放行后到达。若渲染层不给 `held` 权威数组且帧号连续，被拦截期间按下的键不会被记录，解除后组合判定会缺修饰位；`last_frame` 同样不推进。

**【待确认：18】首个主对象自动获焦的条件偏严**
仅 `main_stack.empty() && current_main.empty() && !pending_valid` 时自动 `main_push_request`。若首个主对象接入时已有待生效请求（如同帧 `MouseFocus`），则不会自动获焦，必须外部显式转移。

**【待确认：19】`modifier_mask_of` 只认 control 34..41**
组合语义依赖渲染层把修饰键编码为 `control` 类且编号 34..41；若用 `main` 类编号表示 Shift/Ctrl，`modifier_mask_of` 返回 0，组合永不命中，`modifier_parse` 的数字写法也会被拒。该编码契约应由渲染层固化。

**【待确认：20】`reload` 不处理 `added_keys` 与 `listen`**
`object_reload` 只处理 `mapping`/`axes`/能力位，不读 `added_keys`/`listen`（只有 `object_create` 解析）。因此“重载后新增注入键或新增监听”没有事件路径，除非销毁重建。
