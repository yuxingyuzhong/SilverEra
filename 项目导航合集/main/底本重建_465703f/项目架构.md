## 一、项目定位与分层

白银纪元是一个自研 C++ 引擎加三个应用工程：

| 层 | 工程 | 产物 | 职责 |
| --- | --- | --- | --- |
| 基础层 | `Engine/EngineFoundation` | 静态库 | 事件、对象池、空间分区、配置与资产解析、日志、通用工具 |
| 系统层 | `Engine/EngineSystem` | 静态库 | 碰撞、输入、世界数据（场景/关卡/粒子） |
| 渲染层 | `Engine/EngineRenderer` | 静态库 | Vulkan 设备、交换链、帧、管线、资源、文字/UI、门面 |
| 应用层 | `Application/Test`、`Application/Game/星屑弹幕`、`Application/Editor` | 可执行 / 无构建脚本 | 测试启动器与三套用例、示例游戏、配置编辑器 |

依赖方向唯一：`Foundation → System → Renderer → Application`。系统层不得引用渲染层符号；
引擎聚合面只合并 Foundation 与 System，不把窗口/图形依赖强加给纯逻辑消费方（见 [构建系统](模块架构/构建系统/构建系统.md)）。

## 四、模块交互关系

### 4.1 编译期依赖

```
EngineFoundation ──► EngineSystem ──► EngineRenderer ──► Application(Test / Game)
        │                  │                  │
        └──── 事件协议/通用工具/日志 ────┘      │
                          世界数据 ─────────────┘（渲染层消费系统层场景/关卡数据）
```

- 上层消费下层的**已构建静态库 + 头快照**，不 `add_subdirectory` 下层源码；层间通过 `cmake/对外接口.cmake` 的 `BYJY_<层>_OUT_*` 变量与 `byjy_jieru_xiaceng()` 建立 `IMPORTED STATIC` 目标（见 [构建系统 §五](模块架构/构建系统/构建系统.md)）。
- 每个库携带构建期生成的 `版本锚点.h/.cpp`，头与库不同版次会在链接期失败，不靠目录约定。
- 第三方边界：渲染层的 `external/`（SDL3、VMA、Dear ImGui）就地编入渲染层库；Bullet 只出现在碰撞模块的 `backend/` 与 `Common/数学转换.h`；glTF 的 tinygltf 只在配置与加载模块的 `Gltf_Loader/core/`。

### 4.2 运行期主链路

```
Application
   │  （配置 + 事件 + 资源路径）
   ▼
Renderer 门面 ── 持有 ──┬ 设备与平台（实例/设备/队列/SDL 窗口）
                       ├ 交换链与呈现（交换链、离屏目标）
                       ├ 帧与场景（帧槽/录制/提交、场景与相机、HiZ、簇）
                       ├ 管线与着色器 / 资源与内存 / 文字与UI
                       └ 各子模块的 rebuild 编排
   │  每帧
   ▼
EngineSystem ── 输入（原始输入→动作）· 碰撞（区域检测/跨越通知）· 世界（场景/关卡/粒子）
   │
   ▼
EngineFoundation ── 事件系统（总线）· 配置与加载 · 日志 · 空间分区 · 工具
```

门面对子模块的持有关系与装配顺序见 [门面 §五](模块架构/EngineRenderer/门面.md)；一帧的录制与呈递细节见 [帧与场景 §七](模块架构/EngineRenderer/帧与场景.md)。

### 4.3 事件总线贯穿

事件系统是全项目唯一的跨模块通信底座，使用方式是“类别 + 密钥 + JSON 载荷”：

| 生产者 | 事件类别 | 消费者 |
| --- | --- | --- |
| 配置加载（`Config_Loader`） | 配置类 `Load` / `Unload` | 日志配置桥接（类别 `Log`）、输入映射（重建映射表）、各业务子系统 |
| 输入系统 | 输入/焦点类事件 | 应用层（游戏、测试界面）、UI 交互 |
| 碰撞代理 | `Collision/*`（运动事件投递、跨越通知/查询） | 应用层与场景逻辑 |
| 应用层（游戏/测试/编辑器） | 自定义类别 | 引擎侧桥接与自身模块 |

日志配置桥接刻意位于日志目录内而不让 `Log` 反向依赖事件系统，避免头文件循环（见 [日志与时间 §二](模块架构/EngineFoundation/日志与时间.md)）。

### 4.4 渲染层内部装配

```
Device ─► Memory ─► (Buffer/Image 上传批次)
   │         │
   │         ├─► Mesh / Texture ─► Asset缓存
   │         ├─► RenderTarget ─► Swapchain
   │         └─► Pipeline / Shader / Compute ─► Frame（命令录制）
Platform ─►（窗口/表面）──► Swapchain ─┘
Frame ─► Scene/相机 · Cluster · HiZ · Particle · Text/UI ─► 提交/呈现 ─► 延迟销毁
```

重建（交换链/渲染目标/管线）与旧资源回收统一由门面编排，删除一律走延迟销毁列表，避免销毁在途帧仍在引用的资源。

### 4.5 应用层挂接方式

- **测试**：`Test/src/主调` 是启动器，用 gtest 子进程跑 `tests/{Foundation,Renderer,System}` 三套；引擎日志在子进程侧被屏蔽后桥接为界面输出（见 [测试主调](模块架构/Application/测试主调.md)）。
- **游戏**：`foundation`（常量/类型/文案/设置/视口）→ `communication`（事件总线/配置装载/生涯记录）→ `entity` → `system`（帧推进驱动各系统）→ `presentation`（自绘渲染上下文/界面/特效）→ `world` → `app`（主调与自检）（见 [星屑弹幕](模块架构/Application/星屑弹幕.md)）。
- **编辑器**：`Config_Editor` 只有源码、没有构建脚本，读写的配置格式由 foundation 配置与加载模块的格式定义统一（见 [配置编辑器](模块架构/Application/配置编辑器.md)、[构建系统 §六](模块架构/构建系统/构建系统.md)）。

## 六、本版底本的重建口径与已知空缺

1. 拆模块依据**目录结构**而非旧导航，故模块粒度与旧版不同（旧版按“工具集/配置系统”等命名拆 45 份，本版 23 份）。
2. `Engine/EngineRenderer/src/render/Level` 是空目录，未建伪内容；关卡数据实际落在系统层 `world/data/scene/Level`。
3. `Application/Test/src/单元测试/{EngineFoundation,EngineSystem,渲染}` 为空目录，用例实体在 `tests/` 下。
4. `EngineRenderer/src/render/Renderer` 单文件规模异常（`渲染器.cpp` 560 KB），本版底本按“门面”如实记录，并在 [门面 §六](模块架构/EngineRenderer/门面.md) 给出拆分建议，是否拆由用户拍板。
5. 各模块文档内标注的全部【待确认】点汇总在 `待答疑清单.md`。
6. 资源（`assets/`、`shaders/`、`UI/`）未纳入架构文档，仅在代码引用处点名。
