## 一、模块功能

### 1.1 模块定位

「设备」模块位于渲染层源码目录 `Application/Renderer/src/render/Device/`，与平台模块（`render/Platform/`）、内存模块（`render/Memory/`）、交换链模块（`render/Swapchain/`）等并列为渲染层的底层基础模块之一。它把 Vulkan 中「实例 → 物理设备 → 逻辑设备 → 队列」这一段**与窗口表面强相关、且必须在任何 GPU 资源创建之前完成**的初始化工作，全部收拢进一个门面类 `Device_Context`，对外只暴露「构建两段 + 销毁 + 一组 getter」的极简接口。

模块内部把「校验层探测与调试回调」「物理设备打分选型」「逻辑设备与队列创建」三件事拆成三个编译单元，分别放在 `core/实例创建.cpp`、`core/物理设备选择.cpp`、`core/逻辑设备创建.cpp`；另有一个内部编译单元 `core/校验层配置.cpp` 承担校验层名称、可用性探测、调试扩展清单组装、调试信使建立/销毁、调试消息回调等专门职责。设备上下文自身的销毁、状态查询与 getter 集中放在 `core/设备上下文.cpp`。

一句话概括：**本模块是渲染层「拿到可用的 Vulkan 逻辑设备与图形/呈现队列」的唯一入口，是渲染层其它所有模块（交换链、帧、内存、着色器、管线、网格、纹理）的前置依赖。**

### 1.2 职责边界与解决的问题

`Device_Context` 解决的问题可归纳为五点：

1. **把 Vulkan 设备初始化的长流程封装成两段式调用**。Vulkan 的呈现队列族查询（`vkGetPhysicalDeviceSurfaceSupportKHR`）**要求窗口表面已经存在**，而窗口表面又依赖平台模块（窗口/表面）先行创建。因此设备初始化天然无法「一步到位」。本模块把流程切为两段：`build_instance`（只依赖调用方给出的扩展清单，不依赖表面）与 `build_device`（依赖已创建的 `VkSurfaceKHR`）。这样渲染器门面可以在平台模块创建窗口与表面之前先建实例，表面就绪后再建设备，从而绕开顺序死结。

2. **屏蔽校验层（Validation Layer）的可用性差异**。开发期希望开启 `VK_LAYER_KHRONOS_validation` 以获得校验消息，但若运行环境未安装该层，直接请求会导致 `vkCreateInstance` 失败。本模块在创建实例之前先探测运行时是否**确有**该层（`validation_layer_available`），探测不中则降级关闭并告警，绝不因校验层缺失而使整个渲染初始化失败。

3. **把 Vulkan 校验消息转投到引擎统一日志系统**。校验层本身只回吐 C 风格回调消息；本模块通过调试信使（`VkDebugUtilsMessengerEXT`）回调 `debug_message_callback`，按严重级别分派到 `logger.error` / `logger.warn` / `logger.info`，使 Vulkan 校验信息与引擎其它日志同源可检索。

4. **从多块物理设备中自动挑选最合适的一块**。`vkEnumeratePhysicalDevices` 可能返回集成显卡、独立显卡、虚拟显卡、CPU 设备等多块设备。本模块对每块候选设备先施加「图形队列族 + 呈现队列族 + 支持 `VK_KHR_swapchain`」三重硬门槛，再按「设备类型权重 + 显存容量加成」打分，取最高分者，避免在多 GPU 机器上误选到能力不足或性能偏弱的设备。

5. **把逻辑设备创建与队列获取的公共细节固化**。本模块负责队列族去重（图形族与呈现族可能落在同一族，重复声明会触发校验层报错）、创建逻辑设备、取回图形队列与呈现队列并保存族索引，向后续模块提供自洽的设备上下文。

### 1.3 在整体架构中的位置

设备模块处于渲染层依赖链的最底部（仅次于平台模块的表面创建）。下游模块均以 `Device_Context` 的 getter 取用 `VkDevice`、队列与族索引。

```
                ┌───────────────────────────────────────────────┐
                │              Renderer（渲染器门面）             │
                │   init()：按依赖顺序编排各模块的创建与销毁      │
                └───────────────┬───────────────┬───────────────┘
                                │               │
                   build_instance│               │build_device(surface)
                                │               │
        ┌───────────────────────▼───────────────▼───────────────────────┐
        │                       Device_Context（设备上下文）             │
        │  实例 / 调试信使 / 物理设备 / 逻辑设备 / 图形队列 / 呈现队列    │
        └───────┬───────────────┬────────────────┬──────────────────────┘
      依赖      │               │                │              提供句柄
                ▼               ▼                ▼                     │
    ┌───────────────┐  ┌────────────────┐  ┌───────────────┐          │
    │ 平台模块       │  │ 日志系统       │  │ Vulkan Loader │          │
    │ （提供表面扩展 │  │ （logger 全局）│  │ （vk* 调用）  │          │
    │  / 表面句柄）  │  │                │  │               │          │
    └───────────────┘  └────────────────┘  └───────────────┘          │
                                                                      ▼
                         交换链 / 帧 / 内存 / 着色器 / 管线 / 网格 / 纹理 等模块
```

- **向上**：设备模块的调用方是渲染器门面（`render/Renderer/`）。门面在其 `init` 编排中调用 `build_instance`，待平台模块建好表面后调用 `build_device(surface)`。
- **向下**：设备模块依赖平台模块（提供 `VkSurfaceKHR` 与表面相关实例扩展名）、引擎核心层日志系统（`logger`）、Vulkan Loader（`vk*` 全部调用）。
- **横向**：设备模块不依赖内存、交换链、帧、着色器、管线、网格、纹理等任何同级模块；反之这些模块都直接或间接依赖设备上下文提供的句柄。

### 1.4 与相邻模块的职责分界

| 相邻模块 | 分界 |
| --- | --- |
| 平台模块（`render/Platform/`） | 平台模块负责创建窗口与 `VkSurfaceKHR`，并把「表面所需的实例扩展名」（如 `VK_KHR_surface`、各平台专用表面扩展）作为**入参**交给 `build_instance`；设备模块**不**创建表面，只在 `build_device` 时接收表面句柄并据此把「呈现」纳入设备选型门槛。设备模块的头文件注释明确「实例扩展清单自 Phase 4 起由平台模块提供」。 |
| 渲染器门面（`render/Renderer/`） | 门面负责**编排顺序与失败回退**：任一段失败即逆序释放此前已建对象；设备模块自身只保证「单段调用内部失败时不留半成品、`destroy` 幂等」。门面还负责在 Release 构建下把 `enable_validation` 强制置假（见 `Renderer_Config::validation` 注释）。 |
| 日志系统（`Engine/EngineCore/src/tools/Logging/`） | 设备模块只把 `logger` 当作输出通道使用，不配置日志规则、不绑定输出流。 |
| 「渲染层-渲染器」模块的 `结果检查.h` | 设备模块的全部 `VkResult` 检查都调用该头提供的 `vk_result_check`。该头是**渲染层内所有模块共用的唯一检查出口**，物理上归属渲染器模块，此处仅列为依赖。 |
| 交换链模块（`render/Swapchain/`） | 交换链所需的 `VK_KHR_swapchain` 设备扩展是否受支持，由设备模块在选型阶段**先行把关**（不支持的物理设备直接被排除）；交换链模块自身仍会在创建时使用 `device_get()` 返回的逻辑设备。 |

### 1.5 生命周期与两段式构建

`Device_Context` 的完整生命周期为：

```
构造（default，不创建任何 Vulkan 对象）
   → build_instance(instance_extensions, enable_validation)   ← 第一段：创建实例（+ 可选调试信使）
   → build_device(surface)                                    ← 第二段：选物理设备 → 建逻辑设备 → 取队列
   → [被下游模块使用：交换链 / 帧 / 内存 / 着色器 / 管线 / 网格 / 纹理]
   → destroy()                                                ← 幂等；严格按创建逆序释放
   → 析构（兜底再调用一次 destroy，保证资源不泄漏）
```

- 状态机只有两态：**未构建完成**与**构建完成**。`valid()` 的判据是「实例与逻辑设备均已建立」，即两段都成功。任意一段失败都会使 `valid()` 为假。
- `destroy()` 可重复调用，第二次及以后为无操作；析构函数内部再调一次 `destroy()`，因此「显式销毁 + 析构」不会重复释放。
- 类**不可拷贝、不可移动**（持有 Vulkan 句柄与队列，拷贝会造成双重释放与句柄来源混淆），以 `= delete` 显式禁用。

### 2.2 构造与析构

#### 2.2.1 `Device_Context(void) = default`

- **签名**：隐式等价于默认构造。
- **参数**：无。
- **返回值**：无（构造）。
- **约束**：构造**不创建任何 Vulkan 对象**，各句柄成员保持 `VK_NULL_HANDLE` 初值，`graphics_family`/`present_family` 保持 `0`，`validation_enabled` 保持 `false`。因此默认构造后的对象处于「未构建完成」态，`valid()` 为假。

#### 2.2.2 `~Device_Context(void)`

- **签名**：`~Device_Context(void)`
- **参数**：无。
- **返回值**：无（析构）。
- **约束与行为**：实现见 `core/设备上下文.cpp`，函数体只有一步——调用 `destroy()`。因此析构是**资源不泄漏的最后兜底**：即便调用方忘记显式 `destroy()`，析构也会释放已创建的实例、调试信使与逻辑设备。因 `destroy()` 幂等，析构不会重复释放。

#### 2.2.3 拷贝/移动删除

- **签名**：`Device_Context(const Device_Context&) = delete` 与 `Device_Context& operator=(const Device_Context&) = delete`。
- **约束**：显式删除拷贝构造与拷贝赋值；未声明移动构造/移动赋值，故移动同样不可用（拷贝被删除即移动被隐式抑制）。原因：对象持有 Vulkan 句柄与队列，浅拷贝会导致同一句柄被 `destroy` 两次。

### 2.3 `build_instance`（第一段：构建实例）

- **签名**：`bool build_instance(const std::vector<const char*>& instance_extensions, bool enable_validation)`
- **声明**：`设备上下文.h`；**实现**：`core/实例创建.cpp`。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `instance_extensions` | `const std::vector<const char*>&` | 调用方（平台模块）要求的实例扩展名清单，如表面相关扩展。函数将其**原样保序前置**到内部组装的扩展清单头部 | 各指针须在 `vkCreateInstance` 调用期间保持有效；通常指向静态字符串常量或长期存活的名字数组 |
| `enable_validation` | `bool` | 是否**请求**启用校验层。`true` 时函数还会二次探测运行时是否确有该层；`false` 表示不请求 | 仅 Debug 构建有意义；Release 由调用方（渲染器门面）强制传假 |

- **返回值**：`bool`。`true` 表示实例创建成功（可能同时建立调试信使）；`false` 表示实例创建失败（或校验层请求降级后仍……见下），调用方应视为硬失败并停止后续构建。
- **行为要点**：
  1. **校验层开关折算**：`use_validation = enable_validation && validation_layer_available()`。若请求开启但运行时未安装，记 `logger.warn` 降级关闭，并把 `validation_enabled` 置为折算结果（`use_validation`），而非原始请求值。原因：请求不存在的层会使 `vkCreateInstance` 直接失败。
  2. **目标 API 版本固定为 `VK_API_VERSION_1_3`**（`uint32_t api_version = VK_API_VERSION_1_3`），实例与设备统一按 1.3 请求；运行时不支持 1.3 时 `vkCreateInstance` 失败并记日志，**不做静默降级**。
  3. **`VkApplicationInfo` 填装**：`pApplicationName = "白银纪元"`，`applicationVersion = VK_MAKE_VERSION(0,1,0)`，`pEngineName = "SilverEra Renderer"`，`engineVersion = VK_MAKE_VERSION(0,1,0)`，`apiVersion = 1.3`。
  4. **扩展清单组装**：调用 `instance_extensions_assemble(instance_extensions, use_validation)`，在调用方清单之后追加 `VK_EXT_DEBUG_UTILS_EXTENSION_NAME`（仅 `use_validation` 为真时）。
  5. **校验层名称声明在函数作用域**：`const char* layer_name = validation_layer_name_get();` 注释明确指出 `create_info.ppEnabledLayerNames` 指向该局部变量，**不能指向临时量或悬垂指针**。
  6. **启用校验层时把调试信使创建信息挂到 `pNext`**：`create_info.pNext = &debug_info;`、`enabledLayerCount = 1`、`ppEnabledLayerNames = &layer_name`；未启用时 `enabledLayerCount = 0`、`ppEnabledLayerNames = nullptr`。挂 `pNext` 的目的：捕获「实例创建/销毁本身」产生的校验消息（此时信使尚未建立）。
  7. **实例创建**：`vk_result_check(vkCreateInstance(&create_info, nullptr, &instance), "vkCreateInstance")`，失败即 `return false`。
  8. 成功后记 `logger.info`（打印 Vulkan 主/次/补丁版本）。
  9. **补建调试信使**：`use_validation` 为真时调用 `debug_messenger_create(instance, &debug_messenger)`；**失败仅告警，不回退实例**（K19）。

### 2.4 `build_device`（第二段：构建设备）

- **签名**：`bool build_device(VkSurfaceKHR surface)`
- **声明**：`设备上下文.h`；**实现**：`core/逻辑设备创建.cpp`。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `surface` | `VkSurfaceKHR` | 已创建的窗口表面。用于查询呈现队列族、判定候选物理设备能否呈现到该表面 | 必须非 `VK_NULL_HANDLE`（为空则 `build_physical_device` 报错返回假）；须在设备选型期间有效 |

- **返回值**：`bool`。`true` 表示「物理设备已选定 + 逻辑设备已创建 + 图形/呈现队列已取回」；`false` 表示任一环节失败（调用方应逆序释放实例）。
- **前置**：通常要求 `build_instance` 已成功（`instance` 非空），否则 `vkEnumeratePhysicalDevices` 必然失败。
- **行为要点**：
  1. 调用私有 `build_physical_device(surface)`；失败记 `logger.error("逻辑设备创建:: 物理设备选取失败")` 并返回假。
  2. **队列族去重**：先登记 `graphics_family`；若 `present_family != graphics_family` 再追加 `present_family`。原因：Phase 5 两者可能落在同一族，重复声明会触发校验层报错。
  3. **队列创建信息**：每个唯一族一份 `VkDeviceQueueCreateInfo`，`queueCount = 1`，`pQueuePriorities = &queue_priority`（`queue_priority = 1.0f`，所有族共用同一份取值，指向同一局部变量）。
  4. **查询并校验 Vulkan 1.3 特性**：以 `VkPhysicalDeviceFeatures2` 链接 `VkPhysicalDeviceVulkan13Features` 调用 `vkGetPhysicalDeviceFeatures2`；若 `supported_13.dynamicRendering != VK_TRUE`，记 `logger.error("逻辑设备创建:: 物理设备不支持 Vulkan 1.3 动态渲染（dynamicRendering），本层无法继续")` 并返回假（**不做传统 RenderPass 回退**，设计 §11）。
  5. **启用的特性**：`VkPhysicalDeviceFeatures features{}`（传统特性全关），`VkPhysicalDeviceVulkan13Features enabled_13{}` 只开 `dynamicRendering = VK_TRUE`，经 `create_info.pNext = &enabled_13` 链入。
  6. **启用的设备扩展**：`const char* device_extensions[] = { VK_KHR_SWAPCHAIN_EXTENSION_NAME };`，`enabledExtensionCount = 1`。
  7. **创建逻辑设备**：`vk_result_check(vkCreateDevice(physical_device, &create_info, nullptr, &device), "vkCreateDevice")`，失败即返回假。
  8. **取回队列**：`vkGetDeviceQueue(device, graphics_family, 0, &graphics_queue)` 与 `vkGetDeviceQueue(device, present_family, 0, &present_queue)`，均取族内第 0 号队列。
  9. 成功后记 `logger.info`（打印图形/呈现队列族索引），返回真。

### 2.5 `destroy`（销毁）

- **签名**：`void destroy(void)`
- **声明**：`设备上下文.h`；**实现**：`core/设备上下文.cpp`。
- **参数**：无。
- **返回值**：无。
- **约束与行为**：**幂等**，严格按创建逆序释放：
  1. 若 `device != VK_NULL_HANDLE`：记 `logger.debug("设备上下文:: 销毁逻辑设备")`，`vkDestroyDevice(device, nullptr)`，随后把 `device`、`graphics_queue`、`graphics_family`、`present_queue`、`present_family` 一并复位（`VK_NULL_HANDLE` / `0`）。
  2. 若 `debug_messenger != VK_NULL_HANDLE`：记 `logger.debug("设备上下文:: 销毁调试信使")`，调用 `debug_messenger_destroy(instance, debug_messenger)`，把 `debug_messenger` 复位。
  3. 若 `instance != VK_NULL_HANDLE`：记 `logger.debug("设备上下文:: 销毁实例")`，`vkDestroyInstance(instance, nullptr)`，把 `instance` 复位。
  4. 无条件复位 `physical_device = VK_NULL_HANDLE` 与 `validation_enabled = false`。
- **顺序说明**：逻辑设备必须先于实例销毁；调试信使必须先于实例销毁（信使依附实例）。物理设备是「由实例枚举得到、无需显式销毁」的对象，故仅清记录。

### 2.6 `valid`（状态查询）

- **签名**：`bool valid(void) const`
- **返回值**：`instance != VK_NULL_HANDLE && device != VK_NULL_HANDLE`。
- **约束/语义**：仅当「实例与逻辑设备均已建立」时为真。**不**检查 `debug_messenger`、`physical_device`、两个队列及 `validation_enabled`。【待确认】`<valid() 未纳入 physical_device 与队列的非空判定，是否为「只要可提交命令所需的最小条件」的有意取舍，源码无从确证>`

## 三、模块内部架构

### 3.1 目录/文件结构树

```
Application/Renderer/src/render/Device/
│
├── 设备上下文.h                       # 对外头：Device_Context 类声明（含私有成员与私有方法）
├── 局部命名空间使用.h                 # 内部头：using 声明（string / vector）
│
└── core/
    ├── 设备上下文.cpp                 # 编译单元：析构 / destroy / valid / 全部 getter
    ├── 实例创建.cpp                   # 编译单元：build_instance
    ├── 物理设备选择.cpp               # 编译单元：build_physical_device + 3 个静态辅助 + device_score
    ├── 逻辑设备创建.cpp               # 编译单元：build_device
    ├── 校验层配置.h                   # 内部头：校验层相关自由函数与调试回调声明
    └── 校验层配置.cpp                 # 编译单元：校验层名称/可用性/扩展组装/信使/回调实现
```

> 该结构符合《agent开发指南》「标准模块架构」：对外头在模块根，实现放 `core/`，另有 `局部命名空间使用.h` 承担命名空间收敛。注意本模块**没有**把对外头拆成「类声明在 `engine` 命名空间展开、其余加前缀」的复杂形态——因为本模块对外只暴露一个类 `Device_Context`，所有 getter 均为类成员，天然处于类作用域内，无需额外命名空间前缀。

### 3.2 各编译单元职责

| 编译单元 | 职责 | 关键依赖 |
| --- | --- | --- |
| `core/设备上下文.cpp` | 设备上下文的**生命周期后端**：析构兜底、`destroy` 逆序释放、`valid` 判据、全部 getter | `../局部命名空间使用.h`、`core/校验层配置.h`（仅为 `debug_messenger_destroy`）、`结果检查.h`（间接引入 logger） |
| `core/实例创建.cpp` | 实现 `build_instance`：校验层折算、`VkApplicationInfo`/`VkInstanceCreateInfo` 填装、扩展组装、`vkCreateInstance`、补建调试信使 | `../局部命名空间使用.h`、`core/校验层配置.h`、`结果检查.h` |
| `core/物理设备选择.cpp` | 实现私有 `build_physical_device` 与四个静态辅助：队列族查询（图形/呈现）、设备扩展支持查询、设备打分 | `../局部命名空间使用.h`、`结果检查.h` |
| `core/逻辑设备创建.cpp` | 实现 `build_device`：队列族去重、队列创建信息、1.3 特性查询与启用、`vkCreateDevice`、取回两条队列 | `../局部命名空间使用.h`、`结果检查.h` |
| `core/校验层配置.cpp` | 校验层名称提供、运行时可用性探测、扩展清单组装、调试信使创建/销毁、调试消息回调 | `../局部命名空间使用.h`、`core/校验层配置.h`、`结果检查.h` |

**包含关系要点**：四个 `.cpp` 一律以 `#include "../局部命名空间使用.h"` 起始，其次按需 `#include "校验层配置.h"`，最后 `#include ".../结果检查.h"`（注释：`//获取结果检查出口（含日志系统）`）。`物理设备选择.cpp` 与 `逻辑设备创建.cpp` **不**包含 `校验层配置.h`（它们不需要校验层相关函数）。`局部命名空间使用.h` 又包含 `设备上下文.h`，故 `.cpp` 通过它间接拿到 Vulkan 头与预编译头。

### 3.3 内部数据结构逐字段说明

本模块只有一个自定义类型 `Device_Context`（class）。以下逐字段解释其私有数据成员的含义、初值与不变量。

| 字段 | 类型 | 初值 | 含义 | 不变量/使用约束 |
| --- | --- | --- | --- | --- |
| `instance` | `VkInstance` | `VK_NULL_HANDLE` | Vulkan 实例句柄 | 由 `build_instance` 建立；`destroy` 复位；`valid()` 判据之一 |
| `debug_messenger` | `VkDebugUtilsMessengerEXT` | `VK_NULL_HANDLE` | 调试信使句柄 | 未启用校验层时恒为 `VK_NULL_HANDLE`；建立失败也保持空（仅告警） |
| `physical_device` | `VkPhysicalDevice` | `VK_NULL_HANDLE` | 选中的物理设备句柄 | 由 `build_physical_device` 写入；无显式销毁（实例枚举所得）；`destroy` 仅清记录 |
| `device` | `VkDevice` | `VK_NULL_HANDLE` | 逻辑设备句柄 | 由 `build_device` 建立；`destroy` 先于实例释放；`valid()` 判据之一 |
| `graphics_family` | `uint32_t` | `0` | 图形队列族索引 | 由选型阶段写入；队列取自该族第 0 号 |
| `graphics_queue` | `VkQueue` | `VK_NULL_HANDLE` | 图形队列句柄 | `vkGetDeviceQueue` 取回；随 `device` 销毁而失效 |
| `present_family` | `uint32_t` | `0` | 呈现队列族索引 | 可能与 `graphics_family` 相同（去重后只声明一份） |
| `present_queue` | `VkQueue` | `VK_NULL_HANDLE` | 呈现队列句柄 | 同上；可由与图形族相同的族提供 |
| `validation_enabled` | `bool` | `false` | 校验层**实际**是否启用 | 由 `build_instance` 写入折算结果；`destroy` 复位为假 |

**自定义类型的成员命名**：字段名遵循「英文、单词间 `_`、首字母小写」，与《agent开发指南》变量命名约束一致。`VkQueue`/`VkDevice` 等 Vulkan 句柄为不透明指针类型，未做额外封装。

### 3.5 `局部命名空间使用.h` 的做法

```cpp
#pragma once
#include "设备上下文.h"

// ---------- 基本类型别名 ----------
using std::string;
using std::vector;
```

- **只需两条 `using`**：本模块 `.cpp` 用到的标准库类型只有 `std::string`（在 `validation_layer_available`、`device_extension_supported` 中做名称比对）与 `std::vector`（扩展清单、层清单、设备清单、队列族清单、队列创建信息清单）。Vulkan 类型位于全局命名空间，无需 `using`；`std::size_t` 在 `逻辑设备创建.cpp` 中以 `std::size_t` 全名书写，未收敛。
- **`.cpp` 实现一律不加命名空间前缀**：因收敛了 `string`/`vector`，四个 `.cpp` 内写 `vector<const char*>`、`string(layer.layerName)` 等；但 `engine` 命名空间本身仍显式包住实现（`namespace engine { ... }`），类成员定义写 `Device_Context::xxx`。
- **头文件不引用该别名**：`设备上下文.h` 与 `core/校验层配置.h` 均以 `std::vector`/`std::string` 全名书写，保持头文件自洽、不依赖收敛头。这一点与「`局部命名空间使用.h` 只被 `.cpp` 使用」的定位吻合。

## 四、模块设计/实现细节

### 4.1 两段式构建的成因（核心设计意图）

Vulkan 中，**呈现队列族的判定必须知道「要呈现到哪个表面」**——`vkGetPhysicalDeviceSurfaceSupportKHR(physical_device, family_index, surface, &supported)` 的第三个参数就是表面。而窗口表面属于平台模块，其创建又要用到「已创建的实例」（`vkCreateWin32SurfaceKHR` / `SDL_Vulkan_CreateSurface` 等都需要 `VkInstance`）。这构成一个环：

```
实例 → 表面 → 呈现队列族判定 → 设备选型 → 逻辑设备
```

破环的办法是**把「实例创建」与「设备创建」切开**，让实例先行（实例只需扩展清单，不需要表面），表面在两者之间由平台模块补上：

```
build_instance(extensions)                        ← 无表面依赖
      │
      ▼
平台模块：创建窗口 + 表面（需要 instance_get()）
      │
      ▼
build_device(surface)                             ← 需要表面
```

头文件注释明确记录了这一取舍：「Phase 5 因呈现队列族查询需求而两段化：呈现队列族必须用 `vkGetPhysicalDeviceSurfaceSupportKHR` 查询，而该调用要求表面已存在，故实例先行、设备待表面就绪后再建。」

### 4.2 校验层探测与降级（K19 约定）

设计意图：**「请求开启校验层」与「运行时是否真有该层」是两件事**。若调用方请求的层不存在，Vulkan 的 `vkCreateInstance` 会直接返回 `VK_ERROR_LAYER_NOT_PRESENT`，导致整个渲染初始化失败——这在「开发机装了校验层、CI/发布机没装」的场景下不可接受。因此 `build_instance` 采用「先探测后请求」：

1. `validation_layer_available()` 枚举运行时实例层，比对 `VK_LAYER_KHRONOS_validation`；
2. 探测不中 → `logger.warn("实例创建:: 请求开启 Vulkan 校验层，但运行时未安装 ... 已降级关闭")`，并把 `validation_enabled` 记为假；
3. 探测命中 → 正常请求该层，`validation_enabled` 为真。

**K19 的两次体现**：
- 「补建调试信使」失败仅告警、不回退实例（`实例创建.cpp`）；
- 「调试信使创建入口不可用」记警告并返回假，不视为硬错误（`校验层配置.cpp`）。

即：**校验层/调试能力是「尽力而为」的开发期辅助，不能因其缺失而阻断主流程。**【待确认】`<「K19」「设计 §11」等编号指向的本层设计文档不在本轮收录范围，无法在本模块源码内确证其条目原文>`

### 4.3 调试回调与 `pNext` 挂接的两处时机

调试信使的建立存在**两处**，共同覆盖实例的全生命周期：

1. **实例创建时**：`instance_extensions` 追加 `VK_EXT_debug_utils` 后，把 `debug_messenger_info_create()` 的返回值挂到 `VkInstanceCreateInfo::pNext`，使「实例创建/销毁本身」产生的校验消息也能被捕获（此刻信使尚未建立）。
2. **实例创建成功后**：调用 `debug_messenger_create(instance, &debug_messenger)` **补建**一个长期存活的信使，覆盖后续整个运行期。

回调 `debug_message_callback` 固定返回 `VK_FALSE`。注释解释了原因：Vulkan 规范约定「回调返回真会中止触发该消息的调用」，本层不希望因一条校验消息而中断引擎运行，故一律返回假。回调按严重级别分流到 `logger.error` / `logger.warn` / `logger.info`；`messageSeverity` 只订阅 `WARNING`/`ERROR`，不订阅 `VERBOSE`/`INFO`（避免噪音）。

### 4.4 物理设备打分算法

`device_score` 的取值表：

| 设备类型 | 权重 |
| --- | --- |
| `VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU`（独立显卡） | 30000 |
| `VK_PHYSICAL_DEVICE_TYPE_INTEGRATED_GPU`（集成显卡） | 20000 |
| `VK_PHYSICAL_DEVICE_TYPE_VIRTUAL_GPU`（虚拟显卡） | 10000 |
| `VK_PHYSICAL_DEVICE_TYPE_CPU`（CPU/软件设备） | 1000 |
| 其余（含 `OTHER`/`MAX_ENUM`） | 500 |

**显存容量加成**：累加所有带 `VK_MEMORY_HEAP_DEVICE_LOCAL_BIT` 的内存堆容量，换算为 MB（`local_bytes / (1024*1024)`），**封顶 9999**；得分 = 类型权重 + 加成。

**关键取舍（注释明示）**：类型权重**占绝对主导**，显存加成封顶 9999 <「最小类型权重差 10000」（相邻类型权重之差均为 10000 或以上，最大类型与次大之差为 10000），从而避免「大显存的核显/CPU 设备反超独显」。即：**先保类型，再比显存**。

### 4.5 设备选型的三重硬门槛与「先筛后比」

`build_physical_device` 对每块候选设备依次施加三道门槛，**任一不满足即跳过该设备**：

1. `graphics_family_query` 成功（存在带 `VK_QUEUE_GRAPHICS_BIT` 的队列族）；
2. `present_family_query` 成功（存在支持呈现到目标表面的队列族）；
3. `device_extension_supported(candidate, VK_KHR_SWAPCHAIN_EXTENSION_NAME)` 为真（支持交换链扩展）。

通过三道门槛后计算 `device_score`，仅当 `score > best_score` 时更新最优候选（严格大于，即并列取先遇到者）。全部设备筛完后，若 `best_device == VK_NULL_HANDLE`，记 `logger.error("物理设备选择:: 所有物理设备均不满足「图形队列族 + 呈现队列族 + VK_KHR_swapchain」")` 并返回假。

**边界处理**：
- `surface == VK_NULL_HANDLE` 时（前置检查）直接报错返回假，避免无谓的枚举；
- `vkEnumeratePhysicalDevices` 返回 0 台设备时报错返回假；
- `vkEnumeratePhysicalDevices` 两次调用（先取数量、后取清单）均经检查出口；
- 选型成功后才写 `physical_device`/`graphics_family`/`present_family`，失败时保持原值不回写。

### 4.6 队列族去重与队列创建

`graphics_family` 与 `present_family` 允许相同（同一族同时支持图形与呈现）。若不去重，`VkDeviceCreateInfo::pQueueCreateInfos` 会在同一 `queueFamilyIndex` 上重复声明两次，从而触发校验层报错（`VUID-VkDeviceCreateInfo-pQueueCreateInfos-...`）。因此 `build_device` 构造 `unique_families`：先放 `graphics_family`，仅当 `present_family != graphics_family` 时再放 `present_family`。每个唯一族一份 `VkDeviceQueueCreateInfo`，`queueCount = 1`，优先级数组 `pQueuePriorities = &queue_priority`（`1.0f`）。取回时仍分别按 `graphics_family`/`present_family` 取族内第 0 号，因两族各自都有创建队列。

### 4.7 Vulkan 1.3 特性查询与启用（dynamicRendering 无回退）

本层统一走**动态渲染**（`vkCmdBeginRendering`），因此逻辑设备必须启用 `VkPhysicalDeviceVulkan13Features::dynamicRendering`。做法是「**同一结构体先查询后启用**」：

- 查询：`VkPhysicalDeviceVulkan13Features supported_13{}` 经 `VkPhysicalDeviceFeatures2::pNext` 链入 `vkGetPhysicalDeviceFeatures2`；
- 判定：`supported_13.dynamicRendering != VK_TRUE` 即报错返回假；
- 启用：另建 `VkPhysicalDeviceVulkan13Features enabled_13{}`，只置 `dynamicRendering = VK_TRUE`，经 `VkDeviceCreateInfo::pNext` 链入。

注释明确「不支持则明确报错，**不做传统 RenderPass 回退**（设计 §11）」。同时 `VkPhysicalDeviceFeatures features{}`（传统特性）全关，只把 1.3 特性通过 `pNext` 链入，避免启用无关特性。【待确认】`<「设计 §11」原文不在收录范围，无法确证「无回退」是硬性产品约束还是阶段性实现选择>`

### 4.8 本层唯一 `VkResult` 检查出口的约定

本模块全部有返回值的 Vulkan 调用，**一律**通过 `vk_result_check(result, operation)` 判定成败，不出现「有的地方查、有的地方不查」的分裂。该约定由 `结果检查.h` 头注释明文规定：「本层所有 Vulkan 调用的唯一检查出口」。三态语义：

| 结果 | `vk_result_check` 返回 | 日志 | 语义 |
| --- | --- | --- | --- |
| `VK_SUCCESS` | `true` | 无 | 调用成功 |
| 可接受码（`OUT_OF_DATE`/`SUBOPTIMAL`/`TIMEOUT`） | `false` | `logger.debug` | 不算失败，但调用方**必须自行分支处理**，不能当成功用 |
| 硬错误 | `false` | `logger.error` | 失败，带调用点描述与结果码名称 |

对设备模块而言，所有调用点（见 2.11 表）都只可能落到「成功 / 硬错误」两态——设备初始化阶段不会产生 `OUT_OF_DATE`/`SUBOPTIMAL`；「可接受码」主要服务于交换链获取图像等后续模块。**约定要点**：返回值统一为 `bool`，`operation` 传一个字面量字符串标识调用点（如 `"vkCreateInstance"`），以便日志定位。

### 4.9 销毁逆序与幂等

`destroy` 严格逆创建序释放：**逻辑设备 → 调试信使 → 实例**。

- 逻辑设备必须先于实例：`vkDestroyDevice` 之后其队列句柄全部失效，故同批复位队列与族索引；
- 调试信使必须先于实例：信使依附实例，实例销毁后无法再取 `vkDestroyDebugUtilsMessengerEXT` 入口；
- 物理设备无需显式销毁，仅清记录；
- 每步都以「句柄非空」为守卫，故**幂等**：重复调用时第一步（`device` 已空）即跳过，后续同理；
- 析构函数兜底调用一次 `destroy()`，使「显式 `destroy` + 析构」安全。

### 4.10 内存所有权与句柄所有权约定

| 资源 | 所有权归属 | 释放责任 |
| --- | --- | --- |
| `VkInstance` | `Device_Context` | `destroy` 经 `vkDestroyInstance` |
| `VkDebugUtilsMessengerEXT` | `Device_Context` | `destroy` 经 `debug_messenger_destroy` |
| `VkPhysicalDevice` | 由实例枚举得到，**不属**调用方所有权 | 无需释放，实例销毁后失效 |
| `VkDevice` | `Device_Context` | `destroy` 经 `vkDestroyDevice` |
| `VkQueue` | 由逻辑设备派生，随 `VkDevice` 存亡 | 无需单独释放 |
| `VkSurfaceKHR` | **调用方（平台模块）** | 设备模块只借用，不释放 |
| `instance_extensions` 里的指针 | 调用方 | 函数只借用，须在 `vkCreateInstance` 期间有效 |

`build_instance`/`build_device` 接收的指针与向量均为**借用**，设备模块不持有所有权；`build_device` 只在选型期间使用 `surface`，后续不保存该句柄。

### 4.11 线程/并发约定

本模块未引入任何互斥量、原子量或同步原语，成员均为普通标量/句柄。推断的调用约定为：**设备上下文的 `build_*` / `destroy` / getter 全部在渲染主线程串行调用**，与渲染器门面的「非线程安全、要求所有调用来自同一线程」一致（见 `渲染器.h` 注释）。因此无需加锁。getter 为 `const` 且只读字段，若仅读取句柄可在其它线程安全读取，但本模块未对此作显式承诺。

### 4.12 易错点与编码约定

| 易错点 | 说明与规避 |
| --- | --- |
| `ppEnabledLayerNames` 悬垂指针 | 层名必须指向**函数作用域内**的 `const char* layer_name`（或静态字符串）。源码将其声明在 `build_instance` 函数作用域，并用 `&layer_name` 取地址；若指向临时量或已销毁对象，`vkCreateInstance` 会读悬垂指针 |
| `extensions` 空时传空指针 | `create_info.ppEnabledExtensionNames = extensions.empty() ? nullptr : extensions.data();` 避免空 `vector::data()` 的未定义行为 |
| 队列族重复声明 | 必须去重（见 4.6），否则触发校验层错误 |
| 队列优先级数组生命周期 | `pQueuePriorities = &queue_priority`，`queue_priority` 为局部变量，在 `vkCreateDevice` 期间有效即可 |
| 结构体 `sType` 遗漏 | 所有 `Vk*CreateInfo` / `Vk*Properties` / `Vk*Features` 均显式置 `sType`（如 `VK_STRUCTURE_TYPE_INSTANCE_CREATE_INFO`），并 `{}` 值初始化清零 |
| `pNext` 链使用局部结构体 | `debug_info`（实例创建）与 `enabled_13`（设备创建）均为局部变量，但传给对应 `vkCreate*` 调用时仍有效；不可在调用返回后继续引用 |
| 校验层消息用 `info` 级 | 回调对非错误/警告的校验消息走 `logger.info`，属有意分流 |
| 内存不匹配 | 本模块不使用智能指针管理 Vulkan 句柄（Vulkan 句柄非 C++ 堆指针），由 `destroy` 手动释放；调用 `vk*` 均传 `nullptr` 分配器（用默认分配器） |

**编码约定**：`//` 行注释为中文、可多于三行时用 `/* */`；`.cpp` 内注释多使用 `//`（含跨多行的 `/* */` 块注释用于说明设计意图）；文件编码 UTF-8；源码不含中文路径处理逻辑（本模块不涉及 `std::filesystem`）。

### 4.13 `#include` 顺序与依赖闭包

四个 `.cpp` 的包含顺序固定为：

1. `#include "../局部命名空间使用.h"`（间接含 `设备上下文.h` → 预编译头 → `<vulkan/vulkan.h>`）；
2. `#include "校验层配置.h"`（仅需者包含）；
3. `#include "Application/Renderer/src/render/Renderer/core/结果检查.h"`（引入 `logger` 与检查出口）。

`结果检查.h` 自身包含 `Application/Renderer/common/前置头文件包含.h` 与 `Engine/EngineCore/src/tools/Logging/日志系统运行包.h`（后者在 `engine` 命名空间内定义 `inline Log logger;` 全局实例）。因此设备模块的日志能力完全来自该头，不重复创建日志对象。

## 五、模块运行链路

本章以「调用方 → 模块 → 被调方」的时序描述典型链路。调用方在渲染层内主要是渲染器门面。

### 5.1 主流程一：`build_instance`（实例与校验层）

1. **调用方（渲染器门面）** 在 `init` 编排中、在平台模块建表面之前，调用 `device.build_instance(instance_extensions, enable_validation)`。`instance_extensions` 由平台模块提供（表面扩展名清单）；Release 构建下门面强制 `enable_validation = false`。
2. **`build_instance`** 调 `validation_layer_available()`：
   - 调 `vkEnumerateInstanceLayerProperties(&count, nullptr)`（经 `vk_result_check`）；
   - 数量为 0 或调用失败 → 返回假；
   - 依据数量分配 `vector<VkLayerProperties>`，再调 `vkEnumerateInstanceLayerProperties(&count, layers.data())`；
   - 逐项比对 `layer.layerName == "VK_LAYER_KHRONOS_validation"`，命中返回真。
3. **折算校验层开关**：`use_validation = enable_validation && 探测结果`。若请求开启但探测失败 → `logger.warn` 降级；把 `validation_enabled = use_validation`。
4. **填装 `VkApplicationInfo`**（应用名「白银纪元」、引擎名「SilverEra Renderer」、`apiVersion = VK_API_VERSION_1_3`）。
5. **组装扩展**：调 `instance_extensions_assemble(instance_extensions, use_validation)` → 前置调用方扩展、必要时追加 `VK_EXT_debug_utils`。
6. **取层名**：`layer_name = validation_layer_name_get()`（函数作用域）。
7. **填装 `VkInstanceCreateInfo`**；若 `use_validation`：
   - `debug_info = debug_messenger_info_create()`（订阅 WARNING/ERROR、类型全开、回调 `debug_message_callback`）；
   - `create_info.pNext = &debug_info`、`enabledLayerCount = 1`、`ppEnabledLayerNames = &layer_name`；
   - 否则 `enabledLayerCount = 0`、`ppEnabledLayerNames = nullptr`、`pNext` 保持空。
8. **创建实例**：`vk_result_check(vkCreateInstance(&create_info, nullptr, &instance), "vkCreateInstance")`；失败 → `return false`。
9. 成功 → `logger.info("实例创建:: 实例已建立（Vulkan {}.{}.{}）", 主, 次, 补丁)`。
10. 若 `use_validation` → `debug_messenger_create(instance, &debug_messenger)`：
    - 经 `vkGetInstanceProcAddr(instance, "vkCreateDebugUtilsMessengerEXT")` 取入口；
    - 入口空 → `logger.warn` 并返回假（不回退实例）；
    - 否则调入口创建，经 `vk_result_check` 判定；成功 → `logger.info("校验层配置:: 调试信使已建立")`。
11. **返回真**。此后 `instance_get()` 可被平台模块用于创建表面。

**异常/边界分支**：
- 请求校验层但未安装 → 降级关闭并告警，实例仍建立成功（流程继续）；
- 运行时不支持 Vulkan 1.3 → `vkCreateInstance` 返回 `VK_ERROR_INCOMPATIBLE_DRIVER`/`VK_ERROR_INITIALIZATION_FAILED` 等，`vk_result_check` 记 `logger.error` 并返回假，流程终止并**无静默降级**；
- `vkCreateDebugUtilsMessengerEXT` 入口不可用 → 仅告警，实例可用性不受影响。

### 5.2 主流程二：`build_device`（设备与队列）

1. **调用方（渲染器门面）** 在平台模块建好 `VkSurfaceKHR` 后调用 `device.build_device(surface)`。
2. **`build_device`** 先调私有 `build_physical_device(surface)`：
   a. **前置检查**：`surface == VK_NULL_HANDLE` → `logger.error("物理设备选择:: 表面句柄为空，无法查询呈现队列族")`，返回假。
   b. **枚举设备**：`vkEnumeratePhysicalDevices(instance, &count, nullptr)` 经检查；数量 0 → `logger.error("... 未发现任何支持 Vulkan 的物理设备")`，返回假；再按数量取清单（经检查）。
   c. **遍历候选**，对每块执行 `graphics_family_query` → `present_family_query` → `device_extension_supported(..., VK_KHR_swapchain)` → `device_score`；用 `score > best_score` 更新最优。
   d. `best_device == VK_NULL_HANDLE` → `logger.error("... 所有物理设备均不满足「图形队列族 + 呈现队列族 + VK_KHR_swapchain」")`，返回假。
   e. 写回 `physical_device`/`graphics_family`/`present_family`，`logger.info("物理设备选择:: 选中设备 {}（类型 {}，得分 {}，图形队列族 {}，呈现队列族 {}）", ...)`，返回真。
3. 若选型失败 → `logger.error("逻辑设备创建:: 物理设备选取失败")`，`build_device` 返回假。
4. **队列族去重** → `unique_families`（见 4.6）。
5. **构造队列创建信息** `vector<VkDeviceQueueCreateInfo>`（每族 `queueCount = 1`、`pQueuePriorities = &queue_priority`）。
6. **查询 1.3 特性**：`vkGetPhysicalDeviceFeatures2(physical_device, &supported_features)`（`supported_13` 经 `pNext` 链入）；`supported_13.dynamicRendering != VK_TRUE` → `logger.error("... 物理设备不支持 Vulkan 1.3 动态渲染（dynamicRendering），本层无法继续")`，返回假。
7. **准备启用结构体**：`features{}` 全关、`enabled_13{}` 只开 `dynamicRendering`、设备扩展仅 `VK_KHR_swapchain`。
8. **填装 `VkDeviceCreateInfo`** 并 **创建逻辑设备**：`vk_result_check(vkCreateDevice(physical_device, &create_info, nullptr, &device), "vkCreateDevice")`；失败 → 返回假。
9. **取回队列**：`vkGetDeviceQueue(device, graphics_family, 0, &graphics_queue)`、`vkGetDeviceQueue(device, present_family, 0, &present_queue)`（无返回值，不经检查出口）。
10. `logger.info("逻辑设备创建:: 逻辑设备已建立（图形队列族 {}，呈现队列族 {}）", ...)`，**返回真**。此后 `device_get()`/`graphics_queue_get()`/`present_queue_get()` 等可供交换链、帧、内存等模块使用。

**异常/边界分支**：
- 表面为空 → 前置检查拦截；
- 无任何物理设备 / 无任何设备同时满足三重门槛 → 报错返回假；
- 唯一候选设备 1.3 特性查询报「不支持 dynamicRendering」→ 报错返回假；
- 图形族与呈现族相同 → 去重后只声明一份队列；
- `vkGetPhysicalDeviceSurfaceSupportKHR` 对某族查询失败 → `continue` 跳过该族（不中断整体选型）。

### 5.3 主流程三：`destroy`（逆序释放）

1. **调用方（渲染器门面）** 在关闭流程中调用 `device.destroy()`（通常在交换链、帧、内存等下游模块销毁之后）。
2. 若 `device` 非空 → `logger.debug("设备上下文:: 销毁逻辑设备")`、`vkDestroyDevice(device, nullptr)`，复位 `device`/两条队列/两个族索引。
3. 若 `debug_messenger` 非空 → `logger.debug("设备上下文:: 销毁调试信使")`、`debug_messenger_destroy(instance, debug_messenger)`（内部经 `vkGetInstanceProcAddr` 取入口，取不到静默跳过），复位句柄。
4. 若 `instance` 非空 → `logger.debug("设备上下文:: 销毁实例")`、`vkDestroyInstance(instance, nullptr)`，复位句柄。
5. 复位 `physical_device`、`validation_enabled`。
6. 再次调用 `destroy` → 各守卫均不成立 → 无操作（幂等）。**析构兜底**：对象析构时再调一次 `destroy()`，保证即便调用方遗漏显式销毁也不泄漏。

### 5.4 关键边界分支汇总表

| 场景 | 触发点 | 处理 | 结果 |
| --- | --- | --- | --- |
| 运行时不支持 Vulkan 1.3 | `vkCreateInstance` | `vk_result_check` 记 error | `build_instance` 返回假，无回退 |
| 请求校验层但未安装 | `validation_layer_available` 返回假 | `logger.warn` 降级关闭 | 实例仍成功，`validation_enabled=false` |
| 调试信使创建入口不可用 | `vkGetInstanceProcAddr` 返回空 | `logger.warn` | `debug_messenger_create` 返回假，实例不受影响 |
| `surface == VK_NULL_HANDLE` | `build_physical_device` 前置检查 | `logger.error` | `build_device` 返回假 |
| 无任何物理设备 | `vkEnumeratePhysicalDevices` 数量 0 | `logger.error` | `build_device` 返回假 |
| 无设备满足三重门槛 | 遍历结束 `best_device` 空 | `logger.error` | `build_device` 返回假 |
| 设备不支持 dynamicRendering | 特性查询 | `logger.error` | `build_device` 返回假，无 RenderPass 回退 |
| `vkCreateDevice` 失败 | 创建逻辑设备 | `vk_result_check` 记 error | `build_device` 返回假 |
| 图形族 == 呈现族 | 队列族去重 | 只声明一份队列 | 正常继续，队列仍各自取回 |
| 重复 `destroy` / 析构 | `destroy` 各守卫 | 跳过已释放对象 | 幂等无副作用 |
