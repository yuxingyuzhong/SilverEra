## 一、模块功能

### 1.1 模块定位

「帧」模块位于渲染层源码目录 `Application/Renderer/src/render/Frame/`，与设备模块（`render/Device/`）、交换链模块（`render/Swapchain/`）、内存模块（`render/Memory/`）等并列，是渲染层中**唯一承担「一帧生命周期编排」的基础模块**。它把 Vulkan 每帧必须重复的一整套动作——**等待上一轮提交完成、向交换链取图像、重置并录制命令缓冲、提交到图形队列、呈现到呈现队列**——收拢进一个门面类 `Frame_Context`，并额外提供「在途帧轮转（帧槽）」与「延迟销毁队列」两项基础设施。

模块内部把「帧槽（命令池 / 命令缓冲 / 栅栏 / 信号量）的创建与销毁」「命令缓冲的录制内容」「提交与呈现」「延迟销毁队列」四件事拆成四个编译单元，分别放在 `core/帧槽创建.cpp`、`core/命令录制.cpp`、`core/提交呈现.cpp`、`core/延迟销毁.cpp`。`Frame_Context` 自身的构建、销毁、状态查询、帧号查询与帧槽等待则与帧槽创建同置一处（`core/帧槽创建.cpp`）。

一句话概括：**本模块是渲染层「把一幅画面真正送到屏幕上」的执行末端——它把门面组装好的渲染项列表转成 Vulkan 命令，并管理多帧并行所必需的同步原语。**

### 1.2 职责边界与解决的问题

`Frame_Context` 解决的问题可归纳为六点：

1. **在途帧轮转（帧槽 / Frame-in-Flight）**。GPU 与 CPU 并行工作时，若只用一份命令缓冲与一套同步原语，CPU 在录制下一帧时会覆写 GPU 仍在执行的命令。本模块创建 `frame_overlap` 份**帧槽**（每槽独立持有命令池、主命令缓冲、完成栅栏、呈现完成信号量），按下标轮转使用，使 CPU 至多领先 GPU `frame_overlap` 帧，兼顾吞吐与安全。

2. **把「每帧重复的 Vulkan 命令」固化成一次 `render` 调用**。上层的渲染门面只需依次给出「交换链、渲染项列表、清屏色」，本模块内部完成：等栅栏 → 取图像 → 重置命令池与栅栏 → 录制布局转换与动态渲染 → 提交 → 呈现，并把「交换链过期/次优」这种非致命结果通过出参回传。

3. **动态渲染（Dynamic Rendering）的布局管理**。本模块不依赖传统 `VkRenderPass`，而是使用 Vulkan 1.3 的 `vkCmdBeginRendering`/`vkCmdEndRendering`。命令录制中手工完成颜色附件从 `UNDEFINED` → `COLOR_ATTACHMENT_OPTIMAL` → `PRESENT_SRC_KHR` 的两次布局转换，深度附件则由交换链模块预先转好布局，本帧仅做清屏。

4. **正确的同步原语归属与数量**。同步原语按「每帧槽」与「每交换链图像」两类归属拆分：呈现完成信号量（`render_finished`）与完成栅栏（`in_flight_fence`）属**每帧槽**，数量 = `frame_overlap`；图像可用信号量（`image_available`）属**每交换链图像**，数量 = 交换链图像数，由交换链模块持有。本模块只「借用」图像可用信号量，不拥有、不销毁。

5. **写入前置等待（竞态修复点）**。渲染门面在调用 `render` **之前**就要写入本帧槽的场景 UBO（因为描述符集要指向本帧槽的 UBO）。若此时该帧槽上一轮提交仍在飞行，CPU 覆写会破坏 GPU 正在读取的数据。为此本模块提供 `slot_wait()`，让门面在写入前先等本帧槽栅栏；`render` 内部还会对**同一根栅栏**再等一次（届时栅栏仍为已发出态，`vkWaitForFences` 立即返回，无副作用），形成双保险。`slot_wait` 为**可选推荐**：跳过它直接 `render`，`render` 内部的等待本身也对同一栅栏有效。

6. **延迟销毁队列备用机制**。交换链重建会牵连旧的交换链、图像视图与图像可用信号量。本模块提供了「把旧对象登记到延迟销毁队列、在 N 帧后回收」的机制（`deferred_push`/`deferred_flush`），以支持无停顿重建；当前 Phase 5 的重建路径走在交换链模块侧、以 `vkDeviceWaitIdle` 立即销毁，故本机制**在场但尚未启用**。

### 1.3 在整体架构中的位置

「帧」模块位于渲染层的**执行层**：其上游是渲染门面（`render/Renderer/`），其下游依赖交换链模块（取图像、取图像视图、取深度视图、取范围、取与归还同步原语）与 Vulkan Loader。它自身不创建任何图像或缓冲，也不持有设备——设备句柄与两条队列由门面在 `build` 时以入参注入。

```
                ┌───────────────────────────────────────────────┐
                │              Renderer（渲染器门面）             │
                │  每帧：slot_wait() → 写本帧槽 UBO/描述符集      │
                │        → render(swapchain, items, clear)       │
                │  rebuild_needed 为真 → 触发交换链重建            │
                └───────┬───────────────────────────┬───────────┘
                        │ build(device, queues,      │ render / slot_wait
                        │  swapchain, frame_overlap) │
                        ▼                            ▼
        ┌───────────────────────────────────────────────────────────┐
        │                    Frame_Context（帧上下文）                │
        │  帧槽集合[frame_overlap]：命令池/命令缓冲/栅栏/呈现信号量    │
        │  延迟销毁队列 / acquire_cursor / frame_count（轮转+释放判据）│
        └───────┬───────────────┬───────────────┬───────────────────┘
        取图像/视图 │        提交命令 │      呈现     │
                ▼               ▼               ▼
        ┌───────────────┐ ┌───────────────┐ ┌───────────────┐
        │ Swapchain     │ │ 图形队列       │ │ 呈现队列       │
        │ （图像、视图、 │ │ graphics_queue│ │ present_queue  │
        │  深度视图、   │ └───────────────┘ └───────────────┘
        │  图像可用信号 │
        │  量、范围）   │
        └───────────────┘
```

- **向上**：调用方是渲染器门面。门面按依赖顺序在交换链就绪后调用 `build` 注入设备与交换链，每帧调用 `slot_wait` 与 `render`，并在 `rebuild_needed_out` 为真时组织交换链重建。
- **向下**：依赖交换链模块（`Swapchain_Context` 的 getter 与 `image_available_semaphore_get`）、Vulkan Loader（`vk*` 全部调用）、引擎核心层日志系统（`logger`，经 `结果检查.h` 间接引入）。
- **横向**：本模块不依赖内存、设备、管线、网格、纹理等模块的头文件——它只持裸 Vulkan 句柄，故与这些模块无编译期依赖边。

### 1.4 与相邻模块的职责分界

| 相邻模块 | 分界 |
| --- | --- |
| 交换链模块（`render/Swapchain/`） | 交换链模块**拥有**交换链、图像视图、图像可用信号量与深度图像，并负责重建；帧模块只**借用**它们（`handle_get`/`image_get`/`image_view_get`/`depth_view_get`/`extent_get`/`image_available_semaphore_get` 等），并在取图像返回过期/次优时**置标志**交由上层重建，自身**不重建**交换链。 |
| 渲染器门面（`render/Renderer/`） | 门面负责**编排与决策**：组装渲染项、在写 UBO 前调用 `slot_wait`、依据 `rebuild_needed_out` 组织重建、决定 `frame_overlap` 取值；帧模块只保证「单帧执行正确、失败不留半成品、`destroy` 幂等」。门面还负责在 `init` 中把 `frame_overlap` 钳制到图像可用信号量数以内（K13 的前提，见 4.8），再把调整后的值传入 `build`。 |
| 设备模块（`render/Device/`） | 设备模块提供 `VkDevice`、物理设备、图形/呈现队列族与两条队列；帧模块**不创建设备**，只在 `build` 时接收并保存这些句柄（`physical_device`/`present_family` 仅保存备用，当前源码未使用）。 |
| 内存模块（`render/Memory/`） | 帧模块**不创建任何缓冲/图像**；命令缓冲由 `vkAllocateCommandBuffers` 直接分配，不经内存模块。深度图像由交换链模块经内存模块创建。 |
| 「渲染层-渲染器」模块的 `结果检查.h` | 帧模块全部 `VkResult` 检查都调用该头的 `vk_result_check`（唯一检查出口），而 `vkWaitForFences`/`vkResetFences` 的等待与重置亦统一经它判定。 |
| 日志系统（`Engine/EngineCore/src/tools/Logging/`） | 帧模块只把 `logger` 当输出通道使用，不配置日志规则。 |

### 1.5 生命周期与调用契约

`Frame_Context` 的完整生命周期为：

```
构造（default，不创建任何 Vulkan 对象）
   → build(device, physical_device,
           graphics_family, graphics_queue,
           present_family, present_queue,
           swapchain, frame_overlap)          ← 创建 frame_overlap 个帧槽
   → [每帧]
        slot_wait()                            ← 门面写本帧槽 UBO 之前（可选但推荐）
        render(swapchain, items, count,
               rebuild_needed_out, clear)      ← 取图像 → 录制 → 提交 → 呈现
        （rebuild_needed_out 为真 → 上层重建交换链）
   → destroy()                                 ← 幂等；先 vkDeviceWaitIdle，再逆序销毁帧槽
   → 析构（兜底再调用一次 destroy，保证资源不泄漏）
```

- 状态机只有两态：**未构建完成**与**构建完成**。`valid()` 的判据是「逻辑设备句柄非空 且 帧槽集合非空」。
- `destroy()` 可重复调用，第二次及以后为空操作；析构函数内部再调一次 `destroy()`，因此「显式销毁 + 析构」不会重复释放。
- 类**不可拷贝、不可移动**（持有 Vulkan 句柄与队列），以 `= delete` 显式禁用。
- **调用契约（重要）**：帧槽集合一旦按 `frame_overlap` 建立，`frame_overlap` 在生命周期内**不应改变**（`slot_index_get` 与 `render` 均以下标 `% frame_overlap` 定位帧槽）；同一帧内「门面写 UBO 的槽」必须与「`render` 实际使用的槽」一致，这正是 `slot_wait`/`slot_index_get` 存在的意义。

### 2.3 构造与析构

#### 2.3.1 `Frame_Context(void) = default`

- **签名**：隐式等价于默认构造。
- **参数**：无。**返回值**：无（构造）。
- **约束**：**不创建任何 Vulkan 对象**。各句柄成员保持 `VK_NULL_HANDLE`、各计数保持 `0`、`slots` 与 `deferred_entries` 为空。默认构造后的对象处于「未构建完成」态，`valid()` 为假。

#### 2.3.2 `~Frame_Context(void)`

- **签名**：`~Frame_Context(void)`。**实现**：`core/帧槽创建.cpp`。
- **约束与行为**：函数体只有一步——调用 `destroy()`。因此析构是**资源不泄漏的最后兜底**：即便调用方忘记显式 `destroy()`，析构也会在设备句柄仍有效时释放全部帧槽。因 `destroy()` 幂等，析构不会重复释放。

#### 2.3.3 拷贝/移动删除

- **签名**：`Frame_Context(const Frame_Context&) = delete` 与 `Frame_Context& operator=(const Frame_Context&) = delete`。
- **约束**：显式删除拷贝构造与拷贝赋值；未声明移动构造/移动赋值，故移动同样不可用。原因：对象持有 Vulkan 句柄与队列，浅拷贝会导致同一句柄被 `destroy` 两次。

### 2.4 `build`（构建：创建帧槽集合）

- **签名**：`bool build(VkDevice device, VkPhysicalDevice physical_device, uint32_t graphics_family, VkQueue graphics_queue, uint32_t present_family, VkQueue present_queue, Swapchain_Context& swapchain, uint32_t frame_overlap)`
- **声明**：`帧上下文.h`；**实现**：`core/帧槽创建.cpp`。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `device` | `VkDevice` | 逻辑设备句柄 | 必须非 `VK_NULL_HANDLE`，否则报错返回假 |
| `physical_device` | `VkPhysicalDevice` | 物理设备句柄 | 仅**保存备用**，当前源码未使用；允许为空 |
| `graphics_family` | `uint32_t` | 图形队列族索引 | 用于命令池的 `queueFamilyIndex`，须与 `graphics_queue` 所属族一致 |
| `graphics_queue` | `VkQueue` | 图形队列 | 必须非 `VK_NULL_HANDLE`，否则报错返回假；提交命令的目标队列 |
| `present_family` | `uint32_t` | 呈现队列族索引 | 仅保存备用，当前源码未使用 |
| `present_queue` | `VkQueue` | 呈现队列 | 必须非 `VK_NULL_HANDLE`，否则报错返回假；呈现的目标队列 |
| `swapchain` | `Swapchain_Context&` | 已构建的交换链上下文 | `swapchain.valid()` 必须为真，否则报错返回假；帧链路取图像依赖它 |
| `frame_overlap` | `uint32_t` | 在途帧数（帧槽数量） | 必须为正，为 0 报错返回假 |

- **返回值**：`bool`。`true` 表示全部帧槽创建成功；`false` 表示前置检查失败或任一帧槽创建失败（此时已内部回退）。
- **行为要点**：
  1. **三重前置检查**（均为 `logger.error` 后返回假）：`device`/`graphics_queue`/`present_queue` 任一为 `VK_NULL_HANDLE`；`!swapchain.valid()`；`frame_overlap == 0`。
  2. 记录设备与队列到私有字段（含 `physical_device`/`present_family`）。
  3. `slots.resize(frame_overlap)` 后**逐个**调用 `frame_slot_create(slots[index])`。
  4. **任一帧槽失败即整体回退**：记 `logger.error("帧上下文:: 第 {} 个帧槽创建失败，回退", index)`，调用 `destroy()`（先 `vkDeviceWaitIdle` 再逆序销毁已建帧槽、清空集合），返回假。
  5. 成功记 `logger.info("帧上下文:: 帧基础设施构建完成（在途帧 {}，交换链图像 {}，图像可用信号量 {}）", frame_overlap, swapchain.image_count_get(), swapchain.image_available_count_get())`，返回真。
- **幂等/重入**：`build` 本身**不**先 `destroy`；若在已构建对象上重复调用 `build`，会覆盖 `slots.resize` 造成旧帧槽句柄泄漏。故约定 `build` 只在未构建状态下调用一次。

### 2.5 `destroy`（销毁）

- **签名**：`void destroy(void)`。**实现**：`core/帧槽创建.cpp`。
- **参数/返回值**：无。
- **约束与行为**：**幂等**：
  1. 若 `device != VK_NULL_HANDLE`：先 `vkDeviceWaitIdle(device)`（等设备空闲，避免销毁仍在使用的对象），再**顺序**遍历 `slots` 逐个 `frame_slot_destroy`（注：源码为 `for` 正序遍历，注释称「逆序销毁全部帧槽」，实际为顺序遍历，因各帧槽相互独立，顺序不影响正确性）。
  2. `slots.clear()`、`deferred_entries.clear()`。
  3. 复位全部句柄与计数：`device`/`physical_device`/`graphics_queue`/`present_queue` 置 `VK_NULL_HANDLE`，`graphics_family`/`present_family`/`frame_overlap`/`acquire_cursor`/`frame_count` 置 `0`。
- **注意**：`destroy` 只销毁帧槽自有对象；借用的交换链对象（图像、图像视图、深度图像、图像可用信号量）**不**在其职责内。

### 2.6 `valid`（状态查询）

- **签名**：`bool valid(void) const`。
- **返回值**：`device != VK_NULL_HANDLE && !slots.empty()`。
- **语义**：仅当「逻辑设备已记录 且 至少一个帧槽存在」时为真。**不**检查各帧槽内部句柄是否齐全（`frame_slot_create` 已保证成功返回时帧槽自洽）。

### 2.7 `render`（渲染一帧）

- **签名**：`bool render(Swapchain_Context& swapchain, const Frame_Render_Item* items, uint32_t item_count, bool& rebuild_needed_out, const float clear_color[4])`
- **声明**：`帧上下文.h`；**实现**：`core/提交呈现.cpp`。

| 参数 | 类型 | 含义 | 约束 |
| --- | --- | --- | --- |
| `swapchain` | `Swapchain_Context&` | 当前交换链 | `valid()` 须为真，且图像数与图像可用信号量数均非 0，否则报错返回假 |
| `items` | `const Frame_Render_Item*` | 渲染项数组首地址 | 可为空指针；为空或 `item_count == 0` 时只清屏 |
| `item_count` | `uint32_t` | 渲染项数量 | `items` 非空时表示有效元素个数 |
| `rebuild_needed_out` | `bool&` | 出参：是否需要重建交换链 | 进入时被**无条件置假**；取图像或呈现返回过期/次优时置真 |
| `clear_color` | `const float[4]` | 清屏色 RGBA | 须至少 4 个 `float` 有效 |

- **返回值**：`bool`。`true` 表示本帧被正常处理（**含**「取图像/呈现返回过期或次优、已置 `rebuild_needed_out` 并跳过本帧」的情形）；`false` 视为硬错误（前置失败、等栅栏失败、取图像硬错误、重置栅栏/命令池失败、提交/呈现硬错误）。
- **行为要点（完整顺序）**：
  1. `rebuild_needed_out = false`。
  2. 前置检查 `!valid() || !swapchain.valid()` → `logger.error("提交呈现:: 帧上下文或交换链尚未构建")`，返回假。
  3. 前置检查 `swapchain.image_count_get() == 0 || swapchain.image_available_count_get() == 0` → `logger.error("提交呈现:: 交换链图像或图像可用信号量为空")`，返回假。
  4. **取当前帧槽**：`Frame_Slot& slot = slots[frame_count % frame_overlap]`（此处按 `frame_count` 取槽，与 `slot_index_get` 同一基准）。
  5. **等待该帧槽前一次提交完成**：`vkWaitForFences(device, 1, &slot.in_flight_fence, VK_TRUE, UINT64_MAX)` 经 `vk_result_check`；失败返回假。
  6. **取图像可用信号量**：`swapchain.image_available_semaphore_get(acquire_cursor % swapchain.image_available_count_get())`（轮转游标在信号量池中顺序取用；取图像前图像索引未知）。
  7. **取下一张交换链图像**：`vkAcquireNextImageKHR(device, swapchain.handle_get(), UINT64_MAX, image_available, VK_NULL_HANDLE, &image_index)`。
     - 若返回 `VK_ERROR_OUT_OF_DATE_KHR` 或 `VK_SUBOPTIMAL_KHR`：置 `rebuild_needed_out = true`，记 `logger.debug("提交呈现:: 取图像返回 {}，标记交换链待重建", vk_result_name_get(acquire))`，**提前返回真**（不作为硬错误）。
     - 若为其它非成功码：经 `vk_result_check` 记日志，返回假。
     - 成功：`++acquire_cursor`。
  8. **重置本帧槽完成栅栏**（**放在取图像成功之后**）：`vkResetFences(device, 1, &slot.in_flight_fence)` 经检查；失败返回假。
  9. **重置本帧槽命令池**：`vkResetCommandPool(device, slot.command_pool, 0)` 经检查；失败返回假。
  10. **录制命令缓冲**：`command_record(slot.command_buffer, swapchain.image_get(image_index), swapchain.image_view_get(image_index), swapchain.depth_view_get(image_index), swapchain.extent_get(), items, item_count, clear_color)`。
  11. **提交并呈现**：`submit_present(slot, image_index, image_available, swapchain, rebuild_needed_out)`；失败返回假。
  12. **推进计数**：`++frame_count;`（单一帧计数，兼作帧槽轮转依据与延迟销毁的释放判据）。
  13. **释放到期延迟销毁条目**：`deferred_flush()`。
  14. 返回真。

### 2.8 `frame_count_get`（已推进帧数查询）

- **签名**：`uint32_t frame_count_get(void) const`。**返回值**：`frame_count`。
- **语义**：返回自 `build` 成功以来**成功提交并呈现**的帧数（每次 `render` 走到末尾才自增；取图像/呈现返回过期而提前返回时**不自增**）。`destroy` 后复位为 `0`。

### 2.9 `slot_index_get`（本帧槽序号查询）

- **签名**：`uint32_t slot_index_get(void) const`。**返回值**：`frame_overlap == 0 ? 0 : frame_count % frame_overlap`。
- **语义**：返回「**本次 `render` 将要使用的**帧槽序号」，供门面在调用 `render` **之前**取用同一槽的场景 UBO / 描述符集，保证与帧内部一致。
- **实现注意**：本函数与 `render` 内部**同以 `frame_count % frame_overlap` 计算槽号**（本轮起已把原 64 位帧序号成员并入 `frame_count`，见 4.6），故两者结果必然一致，门面依据 `slot_index_get` 写入的槽与 `render` 实际使用的槽不会错位。

### 2.10 `slot_wait`（等待本帧槽栅栏）

- **签名**：`bool slot_wait(void)`。**实现**：`core/帧槽创建.cpp`。
- **参数**：无。
- **返回值**：`bool`。`true` 表示等待成功；`false` 表示帧上下文未构建或等待失败。
- **语义与约束**：**供门面在写入「本帧槽」资源（如场景 UBO）之前调用**，避免 CPU 覆写 GPU 仍在读取的上一轮内容。
  - 若 `!valid()`：记 `logger.error("帧槽创建:: 帧上下文尚未构建，无法等待帧槽")`，返回假。
  - 取本帧槽 `slots[frame_count % frame_overlap]`，调用 `vkWaitForFences(device, 1, &slot.in_flight_fence, VK_TRUE, UINT64_MAX)` 经 `vk_result_check`。
  - `render` 内部还会再等一次**同一根帧栅栏**。两处等待之间**不发生栅栏重置**（重置只发生在 `vkAcquireNextImageKHR` 成功之后，见 R-SWAP-02 与 4.2），届时该栅栏仍为已发出态，`vkWaitForFences` 立即返回，无副作用。源码注释描述的是「先 `slot_wait` 后 `render`」的**推荐时序**，而非调用必要性约束：**跳过 `slot_wait` 直接 `render` 也能正确等待该槽栅栏**（`render` 内部对同一栅栏的等待本身即有效）。

### 2.11 私有 `frame_slot_create` / `frame_slot_destroy`

- **`bool frame_slot_create(Frame_Slot& slot)`**（private，实现 `core/帧槽创建.cpp`）：创建一个帧槽的全部对象，成功返回真；任一步失败时**先** `frame_slot_destroy(slot)` 回退该槽半成品，**再**返回假。创建顺序：命令池 → 命令缓冲 → 完成栅栏（`VK_FENCE_CREATE_SIGNALED_BIT`）→ 呈现完成信号量。
- **`void frame_slot_destroy(Frame_Slot& slot)`**（private，实现 `core/帧槽创建.cpp`）：销毁一个帧槽的对象并复位句柄。仅在 `device != VK_NULL_HANDLE` 时执行销毁；销毁顺序为：呈现完成信号量 → 完成栅栏 → 命令池（连带回收其分配的命令缓冲）；随后把四个句柄全部复位为 `VK_NULL_HANDLE`。**幂等**（句柄空则跳过）。

### 2.12 私有 `command_record`

- **签名**：`void command_record(VkCommandBuffer command_buffer, VkImage image, VkImageView image_view, VkImageView depth_view, VkExtent2D extent, const Frame_Render_Item* items, uint32_t item_count, const float clear_color[4])`（private，实现 `core/命令录制.cpp`）。
- **语义**：无返回值（录制失败经内部 `vk_result_check` 记日志，但不向上回传）。详见 4.4 的逐命令说明。

### 2.13 私有 `submit_present`

- **签名**：`bool submit_present(Frame_Slot& slot, uint32_t image_index, VkSemaphore image_available, Swapchain_Context& swapchain, bool& rebuild_needed_out)`（private，实现 `core/提交呈现.cpp`）。
- **语义**：以 `VkSubmitInfo2` 提交命令缓冲（等待图像可用信号量、发出呈现完成信号量、以帧栅栏作完成信号），随后 `vkQueuePresentKHR` 呈现；呈现返回过期/次优时置 `rebuild_needed_out` 并返回真。详见 4.5。

### 2.14 私有 `deferred_push` / `deferred_flush`

- **`void deferred_push(Deferred_Entry entry, uint32_t delay_frames)`**（private，实现 `core/延迟销毁.cpp`）：把一组旧对象的 `release_frame` 置为 `frame_count + delay_frames` 后入队 `deferred_entries`。
- **`void deferred_flush(void)`**（private，实现 `core/延迟销毁.cpp`）：若队列为空或 `device` 不可用则直接返回；否则遍历队列，释放 `release_frame <= frame_count` 的条目（先销毁图像视图、再销毁信号量、最后销毁交换链），并 `erase` 该条目。
- **启用状态**：`deferred_push` 在本模块 `core/` 内**当前无调用者**（交换链重建走在交换链模块侧、以 `vkDeviceWaitIdle` 立即销毁），故队列在实践中恒为空；`deferred_flush` 每帧被 `render` 末尾调用，此时为空操作。见 4.7。

### 2.15 辅助结构体逐字段

#### 2.15.1 `Frame_Slot`（帧槽，`帧上下文.h`）

> 头注释：每帧槽持有命令池、主命令缓冲、完成栅栏、呈现完成信号量；数量 = 在途帧数 `frame_overlap`，与交换链图像数无关。

| 字段 | 类型 | 初值 | 含义 | 约束/不变量 |
| --- | --- | --- | --- | --- |
| `command_pool` | `VkCommandPool` | `VK_NULL_HANDLE` | 命令池（每帧经 `vkResetCommandPool` 重置） | 建自 `graphics_family`；`VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT` 未置位，故命令缓冲随池整体重置 |
| `command_buffer` | `VkCommandBuffer` | `VK_NULL_HANDLE` | 主命令缓冲（逐帧录制） | `VK_COMMAND_BUFFER_LEVEL_PRIMARY`，每池一个 |
| `in_flight_fence` | `VkFence` | `VK_NULL_HANDLE` | 完成栅栏（主机侧等待该槽前一次提交完成） | 创建时置 `SIGNALED`，首帧等待不阻塞 |
| `render_finished` | `VkSemaphore` | `VK_NULL_HANDLE` | 呈现完成信号量（提交信号 / present 等待） | 属「每帧槽」，数量 = `frame_overlap` |

#### 2.15.2 `Deferred_Entry`（延迟销毁条目，`帧上下文.h`）

> 头注释：记录一组「被交换链重建牵连」的旧对象，标记可在某帧号及以后释放；Phase 5 重建走 `vkDeviceWaitIdle` 立即销毁，本机制在场备用。

| 字段 | 类型 | 初值 | 含义 |
| --- | --- | --- | --- |
| `swapchain` | `VkSwapchainKHR` | `VK_NULL_HANDLE` | 待销毁的旧交换链（可为空） |
| `image_views` | `std::vector<VkImageView>` | 空 | 待销毁的旧图像视图 |
| `semaphores` | `std::vector<VkSemaphore>` | 空 | 待销毁的旧图像可用信号量 |
| `release_frame` | `uint64_t` | `0` | 可在该帧号及以后释放（`deferred_push` 写入 `frame_count + delay_frames`） |

#### 2.15.3 `Frame_Render_Item`（渲染项，`帧上下文.h`）

> 头注释：持裸 Vulkan 句柄，由门面组装后交给帧模块录制（不引入模块间依赖边）。

| 字段 | 类型 | 初值 | 含义 | 约束/不变量 |
| --- | --- | --- | --- | --- |
| `pipeline` | `VkPipeline` | `VK_NULL_HANDLE` | 图形管线 | 为空则该渲染项被**跳过** |
| `layout` | `VkPipelineLayout` | `VK_NULL_HANDLE` | 管线布局（绑定描述符集与推送常量需要） | 绑描述符集/推常量时使用 |
| `scene_set` | `VkDescriptorSet` | `VK_NULL_HANDLE` | 场景 UBO 描述符集（set 0） | 可为空 |
| `sampler_set` | `VkDescriptorSet` | `VK_NULL_HANDLE` | 采样器描述符集（set 1） | 可为空 |
| `descriptor_set_count` | `uint32_t` | `0` | 描述符集数量 | 取值 0/1/2；`>0` 时才绑定 `{scene_set, sampler_set}` 前 N 个 |
| `vertex_buffer` | `VkBuffer` | `VK_NULL_HANDLE` | 顶点缓冲 | 为空则该渲染项被**跳过** |
| `index_buffer` | `VkBuffer` | `VK_NULL_HANDLE` | 索引缓冲 | 为空则该渲染项被**跳过** |
| `index_count` | `uint32_t` | `0` | 索引数 | 为 0 则该渲染项被**跳过** |
| `push_constants` | `const void*` | `nullptr` | 推送常量数据 | 可为空；非空且 `push_constant_size > 0` 才推送 |
| `push_constant_size` | `uint32_t` | `0` | 推送常量字节数 | 为 0 表示不推送 |

## 三、模块内部架构

### 3.1 目录/文件结构树

```
Application/Renderer/src/render/Frame/
│
├── 帧上下文.h                     # 对外头：Frame_Context 类 + Frame_Slot/Deferred_Entry/Frame_Render_Item
├── 局部命名空间使用.h             # 内部头：using 声明（string / vector）
│
└── core/
    ├── 帧槽创建.cpp               # 编译单元：析构/build/destroy/valid/getter/slot_wait + frame_slot_create/destroy
    ├── 命令录制.cpp               # 编译单元：command_record（布局转换 + 动态渲染 + 逐项绘制）
    ├── 提交呈现.cpp               # 编译单元：render + submit_present
    └── 延迟销毁.cpp               # 编译单元：deferred_push + deferred_flush
```

> 该结构符合《agent开发指南》「标准模块架构」：对外头在模块根，实现放 `core/`，另有 `局部命名空间使用.h` 承担命名空间收敛。本模块无独立内部头，`Frame_Context` 的私有成员函数声明直接置于对外头的 `private` 段（与设备模块做法一致）。

### 3.2 各编译单元职责

| 编译单元 | 职责 | 关键依赖 |
| --- | --- | --- |
| `core/帧槽创建.cpp` | 帧上下文的**生命周期后端与帧槽管理**：析构兜底、`build`、`destroy`、`valid`、`frame_count_get`、`slot_index_get`、`slot_wait`、私有 `frame_slot_create`/`frame_slot_destroy` | `../局部命名空间使用.h`、`结果检查.h` |
| `core/命令录制.cpp` | 实现私有 `command_record`：颜色布局两次转换、动态渲染进入/退出、视口/裁剪、逐渲染项绑定与 `vkCmdDrawIndexed` | `../局部命名空间使用.h`、`结果检查.h` |
| `core/提交呈现.cpp` | 实现 `render`（一帧全流程）与私有 `submit_present`（`vkQueueSubmit2` + `vkQueuePresentKHR`） | `../局部命名空间使用.h`、`结果检查.h` |
| `core/延迟销毁.cpp` | 实现私有 `deferred_push`/`deferred_flush`（延迟销毁队列） | `../局部命名空间使用.h`、`结果检查.h` |

**包含关系要点**：四个 `.cpp` 一律以 `#include "../局部命名空间使用.h"` 起始，其后 `#include "Application/Renderer/src/render/Renderer/core/结果检查.h"`（注释：`//获取结果检查出口（含日志系统）`）。`局部命名空间使用.h` 又包含 `帧上下文.h`，故 `.cpp` 通过它间接拿到预编译头、Vulkan 头与交换链对外头；**四个 `.cpp` 均未直接包含交换链头**（依赖经 `帧上下文.h` 传递）。

## 四、模块设计/实现细节

### 4.1 帧槽与在途帧轮转（核心设计）

**问题**：CPU 录制命令与 GPU 执行命令是并行的。若只有一份命令缓冲，CPU 录制第 N+1 帧时会覆写 GPU 尚在执行的第 N 帧命令，导致画面错乱或校验层报错；若只有一套同步原语，等栅栏会退化为「每帧完全串行」，丧失并行度。

**解法**：把「一帧所需的一整套对象」打包成**帧槽**（`Frame_Slot`），创建 `frame_overlap` 份并按下标轮转。每槽独立持有：

- `command_pool` + `command_buffer`：命令录制与重置的独立容器（重置本槽命令池不影响其它槽）；
- `in_flight_fence`：主机侧等待「该槽前一次提交」完成的完成栅栏；
- `render_finished`：该槽提交发出、供 present 等待的呈现完成信号量。

于是 CPU 至多领先 GPU `frame_overlap` 帧：在录制第 N 帧槽时，等待的是该槽第 N-`frame_overlap` 帧的提交，此时 GPU 不可能仍在读取第 N-`frame_overlap` 帧的该槽资源。

**关键设计（数量与图像数解耦）**：帧槽数量 = `frame_overlap`，**与交换链图像数无关**。头注释明确「数量 = 在途帧数 `frame_overlap`，与交换链图像数无关（§5.2 / §6.2）」。这正是同步原语归属拆分的直接后果：呈现信号量与栅栏属每帧槽（数量 = `frame_overlap`），图像可用信号量属每交换链图像（数量 = 图像数，由交换链模块持有）。

**取图像信号量的轮转**：取图像前不知道会拿到哪张图像，因此无法「按图像索引」选信号量。本模块以 `acquire_cursor` 在「图像可用信号量池」（大小 = `image_available_count`）中顺序轮转取用，即第 k 次成功取图像用第 `k % image_available_count` 个信号量。

### 4.2 栅栏的初始状态与「重置时机」（K9 关键坑位）

**初始已发出**：`frame_slot_create` 创建 `in_flight_fence` 时置 `VK_FENCE_CREATE_SIGNALED_BIT`。原因（源码注释）：「初始即置为『已发出』状态：首帧 `vkWaitForFences` 才不至于无限等待。」若初始为未发出，首次 `render` 的等栅栏将永远阻塞。

**重置放在取图像成功之后**：`render` 中 `vkResetFences` 的位置刻意**不在**「等栅栏之后」，而在「`vkAcquireNextImageKHR` 成功之后」。源码注释给出成因：

> 重置本帧槽完成栅栏，放在「取图像成功之后」而非「等待栅栏之后」：若取图像返回过期 / 次优而提前返回，栅栏必须保持已发出状态，否则下一帧（复用同一帧槽）`vkWaitForFences` 将无限等待（K9）。

也就是说：若取图像返回 `VK_ERROR_OUT_OF_DATE_KHR`/`VK_SUBOPTIMAL_KHR`，`render` 会**提前返回真且不自增帧计数**，下一帧仍复用**同一个帧槽**。此时该槽栅栏若已被重置为未发出、又没有任何提交去发出它，下一帧的 `vkWaitForFences` 就会死锁。把重置推迟到「确定要提交本帧」之后，天然规避了这一死锁。

**对称约束**：`render` 的任一**硬错误提前返回路径**也必须保证「本槽栅栏处于已发出状态」或「后续不会对该槽无提交地等待」。当前源码的提前返回点：
- 前置检查失败（未取槽、未重置）→ 栅栏保持原状态（此前刚 `slot_wait`/等过，已发出或将被后续帧正常处理）；
- 等栅栏失败 → 直接返回假（调用方视为硬错误，通常终止）；
- 取图像硬错误 → 未重置栅栏，保持已发出；
- **取图像成功后**的 `vkResetFences`/`vkResetCommandPool`/`submit_present` 失败 → 已重置栅栏但未成功提交，**这会使该槽栅栏停留于未发出态**；由于这些均为「视为终止的硬错误」（返回假），调用方应停止渲染并销毁，故不构成死锁回放。此点属硬错误后续语义，见 4.10 边界表。

### 4.3 `slot_wait`：写入前置等待（竞态修复点）

**问题**：渲染门面在调用 `render` **之前**就要写入本帧槽的场景 UBO（因为要先把描述符集指向本帧槽的 UBO，再录制使用该描述符集的命令）。若此时该帧槽前一轮提交仍在 GPU 飞行中，CPU 直接覆写 UBO 会破坏 GPU 正在读取的内容（数据竞争 / 撕裂）。

**解法**：新增 `Frame_Context::slot_wait()`。门面在写本帧槽 UBO 之前先调用它，函数内部对**本帧槽**（`slots[frame_count % frame_overlap]`）的 `in_flight_fence` 执行 `vkWaitForFences(..., VK_TRUE, UINT64_MAX)`，从而保证「本帧槽前一次提交已完成」后才允许 CPU 覆写。

**与 `render` 内部等待的关系（双保险）**：`render` 内部第 5 步也会等同一栅栏。头注释说明：

> `render` 内部还会再等一次，届时栅栏已发出，`vkWaitForFences` 立即返回，无副作用。

时序推演（正常无插帧情形）：
1. 帧 f 开始，门面调 `slot_wait()`：等待槽 `f % F` 的栅栏（该栅栏由帧 `f - F` 的提交发出）。**注意**：若调用方此前从未提交过该槽（首次使用），栅栏因创建时即置 `SIGNALED` 而立即通过。
2. 门面写本帧槽 UBO/描述符集（此时 GPU 已确定不再读取该槽 UBO）。
3. 门面调 `render`：内部再等同一栅栏——**该栅栏此时仍为已发出态**（步骤 1 只等待未重置），故立即返回。
4. `render` 取图像成功后 `vkResetFences`（转为未发出）→ 录制 → 提交（提交完成时由 GPU 重新发出该栅栏）。

因此两次等待不冲突：`slot_wait` 与 `render` 内部等待之间**不发生栅栏重置**，第二次等待必为「已发出」而立即通过。这解释了源码注释「届时栅栏已发出」。**约定（已确证）**：若调用方**跳过** `slot_wait` 直接 `render`，`render` 内部对该槽栅栏的等待**本身即有效**（栅栏若已由前一次提交发出则立即通过，否则正常等待），语义与调用 `slot_wait` 一致；`slot_wait` 因此是**可选推荐**（用于保护「门面写 UBO」这一 render 之前的写操作），而非强制。

### 4.4 `command_record`：动态渲染录制细节

录制流程（`core/命令录制.cpp`）逐命令说明：

1. `vkBeginCommandBuffer`，`flags = VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT`。
2. **颜色布局转换 #1**：`UNDEFINED → COLOR_ATTACHMENT_OPTIMAL`。`srcStage = COLOR_ATTACHMENT_OUTPUT`、`dstStage = COLOR_ATTACHMENT_OUTPUT`、`srcAccessMask = 0`、`dstAccessMask = COLOR_ATTACHMENT_WRITE`。源码注释（K11）：同步由 acquire 信号量保护，故 `srcStage = COLOR_ATTACHMENT_OUTPUT`、`srcAccess = 0`（也就是布局转换前的隐式内容无需等待内存依赖，仅需在颜色输出阶段开始前完成布局）。
3. **颜色附件信息**：`loadOp = CLEAR`、`storeOp = STORE`，`clearValue` 取入参 `clear_color[0..3]`，`imageLayout = COLOR_ATTACHMENT_OPTIMAL`。
4. **深度附件信息**：`loadOp = CLEAR`、`storeOp = STORE`，`clearValue.depthStencil = {1.0f, 0}`，`imageLayout = DEPTH_ATTACHMENT_OPTIMAL`。源码注释说明：深度图像由交换链模块持有，布局已在交换链重建时统一转为 `DEPTH_ATTACHMENT_OPTIMAL`，故此处**不再逐帧转换**，仅清屏后保留。
5. **渲染信息**：`renderArea = {0,0} .. extent`、`layerCount = 1`、单颜色附件 + 深度附件。
6. `vkCmdBeginRendering` 进入动态渲染。
7. **视口**：`x=y=0`，`width/height = extent`，`minDepth = 0`、`maxDepth = 1`。注释（K2）：视口高度为正，Y 轴向下由投影处理。
8. **裁剪区**：`{0,0} .. extent`。
9. **逐渲染项绘制**（`for index in [0, item_count)`）：
   - 取 `const Frame_Render_Item& item = items[index]`；
   - **跳过条件**：`pipeline`、`vertex_buffer`、`index_buffer` 任一为空，或 `index_count == 0` → `continue`；
   - `vkCmdBindPipeline(GRAPHICS, item.pipeline)`；
   - 若 `descriptor_set_count > 0`：以 `VkDescriptorSet sets[2] = {scene_set, sampler_set}`（set0 在前、set1 在后），`vkCmdBindDescriptorSets(..., layout, 0, descriptor_set_count, sets, 0, nullptr)`；
   - 若 `push_constants != nullptr && push_constant_size > 0`：`vkCmdPushConstants(..., VK_SHADER_STAGE_VERTEX_BIT, 0, push_constant_size, push_constants)`（**只推给顶点阶段**）；
   - 绑定顶点缓冲：`vkCmdBindVertexBuffers(0, 1, &item.vertex_buffer, &offset)`，`offset = 0`（binding 0）；
   - 绑定索引缓冲：`vkCmdBindIndexBuffer(item.index_buffer, 0, VK_INDEX_TYPE_UINT32)`（uint32 索引）；
   - `vkCmdDrawIndexed(item.index_count, 1, 0, 0, 0)`。
10. `vkCmdEndRendering` 退出动态渲染。
11. **颜色布局转换 #2**：`COLOR_ATTACHMENT_OPTIMAL → PRESENT_SRC_KHR`。`srcStage = COLOR_ATTACHMENT_OUTPUT`、`dstStage = BOTTOM_OF_PIPE`、`srcAccessMask = COLOR_ATTACHMENT_WRITE`、`dstAccessMask = 0`。源码注释（K12）：呈现同步由 `render_finished` 信号量与 present 等待承担，故 `dstStage = BOTTOM_OF_PIPE`、`dstAccess = 0`。
12. `vkEndCommandBuffer`。

**取舍说明**：全程使用 Vulkan 1.3 动态渲染，无 `VkRenderPass`/`VkFramebuffer`。布局转换是**显式写死**的（因为附件布局转换是动态渲染不再自动处理的部分）；深度布局之所以不复用同一段转换，是因为交换链模块已在重建时把深度图统一置于 `DEPTH_ATTACHMENT_OPTIMAL`，逐帧重复转换既无必要也增加屏障开销。

**一处细节（复用 `barrier` 变量）**：颜色布局转换 #1 与 #2 复用同一个 `VkImageMemoryBarrier barrier` 局部量，仅在 #2 处改写 `oldLayout/newLayout/srcAccessMask/dstAccessMask`（`image`/`subresourceRange`/队列族索引保持不变）。这是可行的，因为 `vkCmdPipelineBarrier` 会**立即拷贝**屏障内容入命令流。

### 4.5 `submit_present`：提交与呈现

**提交（`vkQueueSubmit2`）**：使用 Vulkan 1.3 的 `VkSubmitInfo2`：

| 部分 | 内容 | 说明 |
| --- | --- | --- |
| `waitSemaphoreInfoCount = 1` | `{ semaphore = image_available, stageMask = COLOR_ATTACHMENT_OUTPUT }` | 等图像可用后才进入颜色输出阶段（与布局转换 #1 的 `srcStage` 呼应） |
| `commandBufferInfoCount = 1` | `{ commandBuffer = slot.command_buffer }` | 本帧槽命令缓冲 |
| `signalSemaphoreInfoCount = 1` | `{ semaphore = slot.render_finished, stageMask = ALL_COMMANDS }` | 全部命令完成后发出呈现完成信号量 |
| 完成信号 | `vkQueueSubmit2(graphics_queue, 1, &submit_info, slot.in_flight_fence)` | 帧栅栏作提交完成信号 |

**呈现（`vkQueuePresentKHR`）**：`waitSemaphoreCount = 1`、`pWaitSemaphores = &slot.render_finished`（等本槽呈现完成信号量）、`swapchainCount = 1`、`pSwapchains = &swapchain_handle`（局部量承接 `handle_get()`，因需取地址）、`pImageIndices = &image_index`。

**过期/次优分支（K7/K8）**：`vkQueuePresentKHR` 返回 `VK_ERROR_OUT_OF_DATE_KHR` 或 `VK_SUBOPTIMAL_KHR` 时，置 `rebuild_needed_out = true`，记 `logger.debug("提交呈现:: 呈现返回 {}，标记交换链待重建", vk_result_name_get(present_result))`，**返回真**（非硬错误）；其它非成功码经 `vk_result_check` 判定并返回其结果。

**取图像的过期/次优分支（K7/K8）**：在 `render` 中，`vkAcquireNextImageKHR` 返回过期/次优时置标志、提前返回真、**不重置栅栏、不自增计数**（见 4.2）。

**同步语义小结**：一整帧的同步链为「图像可用信号量（acquire → 提交的等待）→ 颜色输出 → 呈现完成信号量（提交的信号 → present 的等待）→ 帧栅栏（提交的完成信号 → 主机侧等待）」。

### 4.6 单一帧计数 `frame_count`（本轮起合并）

本模块**只维护一个帧计数** `frame_count`（`uint32_t`），由它同时承担三项职责：① `frame_count_get` 对外查询「已推进帧数」；② `slot_index_get` 与 `render` 共用的**帧槽轮转依据**（`slots[frame_count % frame_overlap]`）；③ 延迟销毁队列的**释放判据**（`release_frame = frame_count + delay_frames`，`release_frame <= frame_count` 时释放）。

**合并由来**：此前本模块并存两个计数器——一个 64 位内部帧序号（供 `render` 槽轮转与延迟销毁判据）与一个 32 位对外计数 `frame_count`（供对外查询）。两者始终**同步自增**（仅在 `render` 成功走到末尾时一起 `++`；取图像/呈现过期提前返回时不增；硬错误返回时不增），唯一差异是取模基准与位宽，属**冗余而非有意设计**；且「两计数器必须恒同步」是一条**隐式前提**，一旦被破坏（如重建时仅复位其一），门面依据 `slot_index_get` 写入的槽将与 `render` 实际使用的槽错位。

本轮已把该 64 位帧序号成员并入 `frame_count`，消除该隐式前提：`Frame/帧上下文.h` 删除该成员、`frame_count` 注释改为「已推进帧数（同时用作帧槽轮转依据与延迟销毁的释放判据）」；`Frame/core/提交呈现.cpp` 取槽改 `slots[frame_count % frame_overlap]`、帧末只 `++frame_count`；`Frame/core/延迟销毁.cpp` 的 `deferred_push` 改用 `frame_count + delay_frames`、`deferred_flush` 改用 `release_frame > frame_count`；`Frame/core/帧槽创建.cpp` 移除对该成员的复位。

### 4.7 延迟销毁队列（备用机制）

**设计意图**：交换链重建时，旧的交换链、图像视图与图像可用信号量可能仍被 GPU 飞行中的帧使用，不能立即销毁。理想做法是「登记到队列，待 `frame_overlap` 帧之后再销毁」，以避免 `vkDeviceWaitIdle` 造成的全暂停。

**当前实现**：
- `deferred_push(entry, delay_frames)`：`release_frame = frame_count + delay_frames` 后入队。**本模块 `core/` 内当前无调用者**。
- `deferred_flush()`：每帧 `render` 末尾调用；遍历队列，释放 `release_frame <= frame_count` 的条目（销毁顺序：图像视图 → 信号量 → 交换链，再 `erase`）。
- 头注释明确：`Phase 5 重建走 vkDeviceWaitIdle 立即销毁，本机制在场备用，尚未启用。`

因此，`deferred_entries` 在实践中恒为空，`deferred_flush` 每帧为空操作。**属阶段性取舍（有意约定，非遗漏）**：当前交换链重建路径采用 `vkDeviceWaitIdle` 后立即销毁旧资源（§6.4 的简化实现），无需延迟销毁；本机制是为后续「不等设备空闲的逐帧回收」预留——接口与容器均已就位，接线留待后续阶段。

**释放判据的选取**：`release_frame` 现直接以 `frame_count`（32 位）为基准（`frame_count + delay_frames`），与帧槽轮转共用同一计数；`destroy` 复位 `frame_count` 的同时清空 `deferred_entries`，故不存在「跨生命周期沿用旧帧号」的问题（源码未就 32 位计数的超长运行回绕做额外防护）。

### 4.8 同步原语归属与所有权约定

| 同步原语 | 归属 | 数量 | 创建/销毁方 | 帧模块的角色 |
| --- | --- | --- | --- | --- |
| `image_available`（图像可用信号量） | 每交换链图像 | = 交换链图像数 | 交换链模块（随重建而重建） | **借用**：取图像时传入，提交时等待；**不**创建、**不**销毁 |
| `render_finished`（呈现完成信号量） | 每帧槽 | = `frame_overlap` | 帧模块（`frame_slot_create`/`frame_slot_destroy`） | 拥有；提交时发出、present 时等待 |
| `in_flight_fence`（完成栅栏） | 每帧槽 | = `frame_overlap` | 帧模块 | 拥有；主机侧等待该槽提交完成 |

**「借用信号量的复用安全」**（K13）：图像的轮转信号量被复用时，必须保证它上一次的等待已被消费（二元信号量不得在等待完成前再次发出）。源码注释：

> 由「先等帧栅栏」保证：被取用的信号量在前一次使用时已被等待消费（K13）。

推演：信号量索引 = `acquire_cursor % image_available_count`（`acquire_cursor` 与 `frame_count` 在同一帧成功取图后同步推进），上一次使用它是在 `frame_count - image_available_count` 帧，其提交会等待该信号量；而「先等帧栅栏」在每帧开头等待 `slot(frame_count % frame_overlap)` 的栅栏。**该保证显式依赖 `image_available_count >= frame_overlap`**：当 `image_available_count >= frame_overlap` 时，`frame_count - image_available_count` 帧所用的槽（下标 `(frame_count - image_available_count) % frame_overlap`）的栅栏必已在此前某帧被等待过，故其提交已完成、信号量等待已消费；当 `image_available_count < frame_overlap` 时，轮转到某信号量时其上一次等待可能尚未发生（复用帧的槽栅栏未被等待），保证即不成立。

**前提显式化（本轮修复）**：源码此前既未断言也未钳制该前提，属遗漏；现已在**门面 `init` 的交换链建成处**加钳制——取 `swapchain.image_available_count_get()`，若 `frame_overlap > image_available_count`（且后者非 0）则下调 `frame_overlap` 至图像可用信号量数并 `logger.warn`，再以调整后的值调用帧模块 `build` 与管线 `build`。该钳制实现位于 `Application/Renderer/src/render/Renderer/core/渲染器.cpp`（门面属「渲染层-渲染器」模块，此处仅作说明）。

### 4.9 保存但未使用的句柄

`physical_device` 与 `present_family` 在 `build` 中被记录、在 `destroy` 中被复位，但**在帧模块全部实现中未被读取使用**——帧模块的运行链路只用到设备、图形/呈现队列与交换链，不消费这两个字段。**属有意保留的预留字段**（保持上下文信息完整、与设备/交换链模块接口对称）：后续若需「呈现队列族查询」或「物理设备特性核对」，可直接取用，无需改动 `build` 签名。

### 4.10 线程/并发与调用约定

- **非线程安全**：`Frame_Context` 无任何互斥保护，`slots`/`acquire_cursor`/`frame_count`/`deferred_entries` 的更新均为非原子。约定**由单一渲染线程**独占调用 `build`/`render`/`slot_wait`/`destroy`。
- **GPU/CPU 并行由 Vulkan 同步原语承担**，而非主机锁：帧栅栏保护「本槽资源不被 CPU 提前覆写」，信号量保护「取图像与呈现的队列侧顺序」。
- **`slot_wait` 与 `render` 必须在同一线程、同一帧内成对（顺序）调用**：`slot_wait`（写 UBO 前）→ 写 UBO → `render`。`slot_wait` 之后到 `render` 内部等待之前，不得有其它帧的推进（否则槽号变化）。

### 4.11 编码约定与易错点清单

- **异常禁用**：本模块不做任何可能抛异常的内存分配（唯一动态分配是 `std::vector` 的 `resize`/`push_back`，属标准库内部行为）；未使用 `new`，故无需 `std::nothrow`。
- **等待超时给足**：两处 `vkWaitForFences` 均传 `timeout = UINT64_MAX`（永不超时），确保等待直到发出；`vkAcquireNextImageKHR` 的 timeout 亦为 `UINT64_MAX`。
- **`vkResetFences` 位置**：见 4.2，是最易错点，改动顺序会引入死锁。
- **`slot_index_get` 与 `frame_count`**：见 4.6，`slot_index_get` 与 `render` 同以 `frame_count % frame_overlap` 取槽，基准唯一、不会错位。
- **`image_available` 游标不自增的路径**：取图像**硬错误**时 `++acquire_cursor` 不执行（仅成功时自增），避免跳过信号量；但**过期/次优提前返回**时也不自增（因为取图像未成功拿图）——这与「过期返回后下一帧复用同一信号量」一致。
- **`command_record` 不向上回传失败**：内部 `vk_result_check` 只记日志；但因录制错误（如 `vkBeginCommandBuffer` 失败）在正常参数下极罕见，故未向上传递。
- **`destroy` 的 `for` 遍历注释为「逆序」，实际为正序**：因帧槽相互独立，顺序正确。
- **`build` 不自动先 `destroy`**：重复 `build` 会泄漏旧帧槽，调用方须保证「未构建态调用一次」。

### 4.12 与 Vulkan 版本和「编号」的关系

本模块全程使用 Vulkan 1.3 能力：`vkQueueSubmit2`、`vkCmdBeginRendering`/`vkCmdEndRendering`（动态渲染）、`VkSubmitInfo2`/`VkSemaphoreSubmitInfo`/`VkCommandBufferSubmitInfo`。设备模块已把 `dynamicRendering` 设为硬性启用特性，故帧模块可直接依赖。

## 五、模块运行链路

本章以「调用方 → 模块 → 被调方」的时序描述典型链路。调用方在渲染层内主要是渲染器门面。

### 5.1 主流程一：`build`（创建帧槽集合）

1. **调用方（渲染器门面）** 在设备、交换链、内存等模块就绪后，从设备模块取 `device`/`physical_device`/`graphics_family`/`graphics_queue`/`present_family`/`present_queue`，并传入已构建的 `swapchain` 与选定的 `frame_overlap`，调用 `frame.build(...)`。其中 `frame_overlap` 由门面在 `init` 中先按图像可用信号量数钳制（若选定值超过 `swapchain.image_available_count_get()` 则下调至后者并告警，见 4.8），故传入 `build` 的是钳制后的值。
2. **`build`** 前置检查：设备句柄与两条队列非空、`swapchain.valid()` 为真、`frame_overlap > 0`；任一不满足 → `logger.error` 并返回假。
3. 记录设备与队列字段。
4. `slots.resize(frame_overlap)`；对 `index ∈ [0, frame_overlap)` 调 `frame_slot_create(slots[index])`：
   a. `vkCreateCommandPool`（`queueFamilyIndex = graphics_family`）；
   b. `vkAllocateCommandBuffers`（`PRIMARY`、数量 1）；
   c. `vkCreateFence`（`VK_FENCE_CREATE_SIGNALED_BIT`）；
   d. `vkCreateSemaphore`（`render_finished`）；
   e. 任一步失败 → 内部 `frame_slot_destroy(slot)` 回退该槽 → 返回假。
5. 若某槽失败 → **`build` 整体回退**：`logger.error("帧上下文:: 第 {} 个帧槽创建失败，回退", index)` → `destroy()` → 返回假。
6. 全部成功 → `logger.info("帧上下文:: 帧基础设施构建完成（…）")` → 返回真。此后 `valid()` 为真，可开始逐帧 `render`。

### 5.2 主流程二：一帧渲染（`slot_wait` + `render`）

1. **调用方（渲染器门面）**：
   a. 调 `slot_index_get()` 取「本帧槽序号」（用于定位本帧槽 UBO/描述符集）；
   b. 调 `slot_wait()` 等本帧槽栅栏完成（保护即将进行的 UBO 写入）；
   c. 写入本帧槽的场景 UBO、组装 `Frame_Render_Item` 数组（管线、布局、描述符集、顶点/索引缓冲、推送常量）。
2. **`render(swapchain, items, item_count, rebuild_needed_out, clear_color)`**：
   a. `rebuild_needed_out = false`；前置检查 `valid()`、`swapchain.valid()`、图像数与图像可用信号量数非 0。
   b. 取当前帧槽 `slots[frame_count % frame_overlap]`。
   c. `vkWaitForFences(..., slot.in_flight_fence, VK_TRUE, UINT64_MAX)`（该槽前一次提交完成）。
   d. 从交换链取图像可用信号量 `image_available_semaphore_get(acquire_cursor % image_available_count)`。
   e. `vkAcquireNextImageKHR(device, swapchain.handle_get(), UINT64_MAX, image_available, VK_NULL_HANDLE, &image_index)`：
      - 过期/次优 → `rebuild_needed_out = true`、`logger.debug`、**提前返回真**；
      - 其它非成功 → `logger.error`，返回假；
      - 成功 → `++acquire_cursor`。
   f. `vkResetFences`（**此时才重置**）；`vkResetCommandPool`。
   g. `command_record(slot.command_buffer, swapchain.image_get(image_index), image_view_get, depth_view_get, extent_get, items, item_count, clear_color)`：
      - 颜色布局转换（UNDEFINED→COLOR_ATTACHMENT_OPTIMAL）→ 动态渲染（清屏 + 逐项绑定与 `vkCmdDrawIndexed`）→ 颜色布局转换（COLOR_ATTACHMENT_OPTIMAL→PRESENT_SRC_KHR）。
   h. `submit_present(slot, image_index, image_available, swapchain, rebuild_needed_out)`：
      - `vkQueueSubmit2`（等 `image_available`@COLOR_ATTACHMENT_OUTPUT → 执行命令 → 发 `render_finished`@ALL_COMMANDS，`in_flight_fence` 作完成信号）；
      - `vkQueuePresentKHR(present_queue, {pWaitSemaphores = &render_finished, pImageIndices = &image_index})`；
      - 呈现过期/次优 → `rebuild_needed_out = true`、`logger.debug`、返回真；其它非成功 → `logger.error`、返回假。
   i. `++frame_count;`（单一帧计数，兼作轮转与释放判据）。
   j. `deferred_flush()`（当前为空操作）。
   k. 返回真。
3. **调用方**：若 `rebuild_needed_out == true`，组织交换链重建（重建由上层/交换链模块执行，帧模块只出标志），并在重建完成后继续后续帧。

### 5.3 主流程三：`destroy`（销毁）

1. **调用方** 在关闭流程中调用 `frame.destroy()`（通常在交换链销毁之前，因为帧槽借用交换链的图像可用信号量）。
2. 若 `device` 非空：`vkDeviceWaitIdle(device)`；遍历 `slots` 逐个 `frame_slot_destroy`（呈现信号量 → 栅栏 → 命令池）。
3. `slots.clear()`、`deferred_entries.clear()`。
4. 复位全部句柄与计数。
5. 再次调用 `destroy` → 各守卫均不成立 → 无操作（幂等）。**析构兜底**：对象析构时再调一次 `destroy()`。

### 5.4 关键边界分支汇总表

| 场景 | 触发点 | 处理 | 结果 |
| --- | --- | --- | --- |
| `build` 时设备/队列为空 | `build` 前置检查 | `logger.error("…句柄或队列不完整")` | 返回假，无副作用 |
| `build` 时交换链未构建 | `build` 前置检查 | `logger.error("…交换链尚未构建…")` | 返回假 |
| `build` 时 `frame_overlap == 0` | `build` 前置检查 | `logger.error("…在途帧数必须为正")` | 返回假 |
| 第 i 个帧槽创建失败 | `frame_slot_create` | 内部先销毁该槽半成品；`build` 记 error 后 `destroy()` 整体回退 | 返回假，已建帧槽全部回收 |
| 帧上下文/交换链未就绪 | `render` 前置检查 | `logger.error("提交呈现:: …尚未构建")` | 返回假（硬错误） |
| 交换链图像或图像可用信号量为空 | `render` 前置检查 | `logger.error("提交呈现:: …为空")` | 返回假（硬错误） |
| 等当前帧槽栅栏失败 | `render` 第 c 步 | `vk_result_check` 记日志 | 返回假（硬错误） |
| 取图像返回 `VK_ERROR_OUT_OF_DATE_KHR` | `render` 第 e 步 | 置 `rebuild_needed_out=true`、`logger.debug`、**不重置栅栏、不自增计数** | **返回真**（提前返回，上层重建） |
| 取图像返回 `VK_SUBOPTIMAL_KHR` | `render` 第 e 步 | 同上 | 返回真 |
| 取图像其它非成功码 | `render` 第 e 步 | `vk_result_check` 记 error | 返回假（硬错误） |
| `vkResetFences` 失败（取图像成功后） | `render` 第 f 步 | `vk_result_check` 记 error；栅栏停留于未发出 | 返回假（视为终止；调用方须停止渲染） |
| `vkResetCommandPool` 失败 | `render` 第 f 步 | `vk_result_check` 记 error | 返回假（硬错误） |
| `vkQueueSubmit2` 失败 | `submit_present` | `vk_result_check` 记 error | 返回假（硬错误） |
| 呈现返回 `VK_ERROR_OUT_OF_DATE_KHR`/`VK_SUBOPTIMAL_KHR` | `submit_present` | 置 `rebuild_needed_out=true`、`logger.debug` | 返回真（非硬错误） |
| 呈现其它非成功码 | `submit_present` | `vk_result_check` 记 error | 返回假（硬错误） |
| 渲染项缺管线/顶点/索引缓冲或索引数为 0 | `command_record` | `continue` 跳过该项 | 该项不绘制，其余继续 |
| 描述符集数量为 0 | `command_record` | 不绑定描述符集 | 该渲染项按无描述符集绘制 |
| 推送常量为空或大小为 0 | `command_record` | 不推送 | 该渲染项按无推送常量绘制 |
| `slot_wait` 时帧上下文未构建 | `slot_wait` | `logger.error("帧槽创建:: …无法等待帧槽")` | 返回假（硬错误） |
| 延迟队列为空 | `deferred_flush` | 直接返回 | 空操作 |
| 重复 `destroy` / 析构 | `destroy` 各守卫 | 跳过已释放对象 | 幂等无副作用 |
